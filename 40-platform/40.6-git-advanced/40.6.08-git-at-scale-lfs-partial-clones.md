# Git at Scale: LFS & Partial Clones

A large repository becomes slow when downloading objects, materializing files, or repeatedly scanning the working tree costs too much. Git offers separate tools for each cost; a smaller checkout does not imply a smaller history download.

## Definition

**Git Large File Storage (LFS)**, **partial clones**, **sparse checkouts**, and **shallow clones** each reduce a different large-repository cost. A smaller checkout does not imply a smaller history download.

> **Textbook Definition:** Large-repository techniques reduce transferred history, fetched objects, or materialized files through shallow clones, partial clones, sparse checkout, and external large-file storage, each with distinct availability and workflow constraints.

| Technique | What changes | Availability consequence |
| ---------------------------- | ---------------------------------------------------------------- | ------------------------------------------------------ |
| Git Large File Storage (LFS) | Git holds a content pointer; a separate service holds the binary | A Git backup alone may lack the file bytes |
| Partial clone | Some objects are omitted until requested | Later reads can require the promisor remote |
| Sparse checkout | Only selected paths are materialized | Full history may still be downloaded |
| Shallow clone | Ancestry stops at an explicit boundary | History queries can miss a required ancestor |
| Scalar and maintenance | Configure repository accelerators and upkeep | Benefits depend on Git version, platform, and workload |

## First Principles

A build needs today's file bytes; a blame query may need yesterday's bytes; a release comparison needs an ancestor. These are different data demands. Avoiding transfer helps only until the next operation asks for omitted data. Separately, even with every object available, scanning hundreds of thousands of paths can dominate `status`. First identify the expensive operation, then choose a tool that reduces its particular input.

## How It Works

### 1. Separate History from Binary Storage with LFS

The clean filter runs when a file is staged. It saves binary content in the local LFS object store and places a small pointer in Git. A pre-push hook normally uploads required LFS objects to the server; staging alone does not upload them. At checkout, the smudge/filter process retrieves the content named by the pointer.

```text
stage video → local LFS bytes + pointer blob in Git
push        → Git objects and LFS objects uploaded by separate paths
checkout    → pointer resolved to binary bytes, if available
```

The pointer records a SHA-256 content identity and size:

```text
version https://git-lfs.github.com/spec/v1
oid sha256:4d7a214614ab2935c943f9e0ff69d22eadbb8f32b06882dcae35913e34e709f6
size 134218528
```

```bash
# Repository-local filters and push hook; requires git-lfs installation.
git lfs install --local
git lfs track '*.psd' '*.mp4'
git add .gitattributes media/demo.mp4
git commit -m 'Track demo video via LFS'
git lfs ls-files
git lfs pull --include='media/**'
```

Tracking a pattern affects files staged afterward; it does not convert existing commits. If checkout skips LFS smudging, the working tree keeps pointer text until `git lfs pull` downloads the selected payloads. Git LFS storage and Git object history are separate recovery requirements.

`git lfs migrate import --everything --include='*.mp4'` considers commits reachable from all known refs, but rewrites only local refs. It does not push the rewritten history or upload LFS payloads for you. Rehearse on a disposable mirror, verify the migrated files and payloads, then coordinate the required LFS upload and history cutover with every consumer. Existing clones and retained refs can keep the old blobs alive; migration is neither secure deletion nor a guarantee that the local pack immediately shrinks. See the [Git LFS migration manual](https://github.com/git-lfs/git-lfs/blob/main/docs/man/git-lfs-migrate.adoc) for ref and push behavior.

### 2. Defer Objects with Partial Clone, Select Files with Sparse Checkout

```bash
git clone --filter=blob:none --no-checkout --branch main <repository-url> narrow-repo
cd narrow-repo
git sparse-checkout set --cone services/api packages/shared
git checkout main
```

Replace `main` with the branch the job needs. `blob:none` asks the server to omit file-content blobs during the initial transfer; the checkout fetches blobs for the selected files. `git sparse-checkout set` initializes the sparse rules in cone mode. The final checkout materializes those paths. The client records the request in `remote.origin.promisor` and `remote.origin.partialclonefilter`; check them with `git config --get remote.origin.promisor` and `git config --get remote.origin.partialclonefilter`. These values prove what the client requested, not that the server honored it. Compare transfer size or check for a known historical missing object with `git rev-list --objects --missing=print <older-commit>`. A server that does not support filtering can warn and send a full clone anyway.

A **promisor remote** promises to supply omitted objects later. A diff, blame, or historical grep can trigger network reads; expired credentials or an unavailable server can therefore break operations that look local. Sparse checkout limits working-tree paths, not history. Cone mode includes every file at the repository root, files immediately inside parent directories leading to each selected directory, and all files beneath the selected directories. Disable sparse checkout with `git sparse-checkout disable` to materialize the full tree.

For an offline incident kit, fetch every object needed for the investigation beforehand. A partial clone plus a bundle is not automatically complete: verify prerequisites and restore it without network access. LFS bytes remain a separate concern.

### 3. Choose History Depth from the Job's Actual Questions

A one-commit build can use a shallow checkout. Changelog generation, merge-base checks, version-from-tags tools, and blame need the relevant ancestors and refs. Fetching a tag alone does not prove that the necessary connecting history is present.

```bash
git rev-parse --is-shallow-repository
# Deepen the exact remote branch and update its tracking ref.
git fetch --deepen=100 origin refs/heads/main:refs/remotes/origin/main
# If the job requires complete ancestry and the source is complete:
git fetch --unshallow --tags origin refs/heads/main:refs/remotes/origin/main
git merge-base refs/remotes/origin/main HEAD
```

Use the full source-to-destination refspec for the branch the job compares. With only `git fetch origin main`, whether Git also updates `origin/main` depends on the remote's configured ref mapping; the fetched commit is recorded in `FETCH_HEAD` either way. The explicit mapping removes that ambiguity. Check the merge-base command's exit status and output; a guessed depth such as 500 is not a correctness guarantee. A pipeline building an untrusted contribution also needs reviewed permissions and credential isolation; history depth does not solve those concerns.

### 4. Reduce Repeated Local Work with Accelerators

A commit graph stores commit metadata and can accelerate ancestry queries; changed-path Bloom filters can avoid some irrelevant history walks. Neither makes an arbitrary history query constant-time. The untracked cache avoids some directory rescans. A supported filesystem monitor reports changed paths rather than forcing a full scan. Scalar is Git's repository-management tool for applying large-repository settings and scheduled maintenance; inspect the installed version's recommendations instead of copying defaults blindly.

```bash
git commit-graph write --reachable --changed-paths
git config core.untrackedCache true
git config feature.manyFiles true
# Enable only where the installed Git/platform supports the built-in daemon:
git config core.fsmonitor true
```

Measure before and after on the same filesystem with the same paths and warm/cold cache conditions. Schedule maintenance around shared-server load and disk budgets. Repacking changes object representation; it does not remove reachable large objects from history.

### 5. Audit Stored Objects, Then Enforce a Bounded Policy

```bash
git count-objects -vH
git rev-list --objects --all |
  git cat-file --batch-check='%(objecttype) %(objectname) %(objectsize) %(rest)' |
  awk '$1=="blob" {print}' | sort -k3,3nr | head -25
```

`size-pack` measures stored pack bytes; a blob's `objectsize` measures its uncompressed content. Neither alone predicts clone latency or LFS storage. `git-sizer` adds structural diagnostics such as tree width and history shape.

For a contribution gate, check new reachable objects relative to a **verified, available base**. This Python example streams object IDs into `cat-file`, fails if the base or an object cannot be inspected, and reports offending IDs. Use the inventory above to map those IDs to paths.

```python
# Run from the repository after fetching/reviewing the base ref.
import subprocess

base = "origin/main"
limit = 512 * 1024  # illustrative repository policy, not a Git limit
subprocess.run(["git", "rev-parse", "--verify", base + "^{commit}"], check=True)
ids = subprocess.check_output(
    ["git", "rev-list", "--objects", "--no-object-names", base + "..HEAD"]
)
rows = subprocess.check_output(
    ["git", "cat-file", "--batch-check=%(objectname) %(objecttype) %(objectsize)"],
    input=ids,
).decode().splitlines()
offenders = []
for row in rows:
    fields = row.split()
    if len(fields) != 3 or fields[1] not in {"blob", "tree", "commit", "tag"}:
        raise SystemExit("Object inspection failed: " + row)
    oid, kind, size = fields
    if kind == "blob" and int(size) > limit:
        offenders.append(oid)
if offenders:
    raise SystemExit("Large Git blobs require review/LFS: " + ", ".join(offenders))
```

Use `git log --all --find-object=<oid> --name-status` to locate commits and changed paths for a reported object ID; see the [git-log manual](https://git-scm.com/docs/git-log). An LFS pointer may pass this size gate even when its actual content is missing or disallowed, so validate LFS object availability and content policy separately. An empty range means no new objects; an unavailable base must fail before the range is calculated.

## Real-World Use Cases

| If the bottleneck is… | Start with… | Verify the trade-off |
| -------------------------------------- | --------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------- |
| Repeated large binaries in Git history | LFS or an artifact/dataset registry | Budget storage/transfer quotas and test payload restoration; LFS changes storage, not binary mergeability |
| Downloading irrelevant file contents | Partial clone | Confirm server filtering and test offline/history operations that may need omitted blobs |
| Checking out irrelevant directories | Cone-mode sparse checkout | Build targets must be explicit; a missing directory must fail the build rather than skip it |
| Missing ancestry in CI | A deeper or complete fetch of the exact comparison ref | Versioning, changelogs, merge-base checks and blame must see the required commits and tags |
| Slow `status` or history walks | Filesystem monitor, untracked cache, commit graph and scheduled maintenance | Measure the same workload; accelerators do not remove history or make every query constant-time |

`.gitignore` only affects untracked paths; it does not remove already committed objects. Garbage collection cannot discard objects that remain reachable from required refs.

## Summary

Choose the optimization from the expensive operation: LFS separates binary storage, partial clone defers objects, sparse checkout narrows files, and shallow clone limits ancestry. Verify the data needed by builds and investigations, measure accelerators on your workload, and rehearse Git plus LFS recovery independently.

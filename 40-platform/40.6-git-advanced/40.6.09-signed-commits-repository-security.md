# Signed Commits & Repository Security

## Definition

An author name and email in a commit are ordinary text: anyone can set them. Signing adds evidence that a particular signing key approved the commit's exact content. You still need a policy that decides which keys and identities may approve a change.

> **Textbook Definition:** A commit signature cryptographically binds the signed commit payload to a signing key. Verification establishes signature validity; trust and authorization policies determine whether that key or identity is acceptable for a protected operation.

## First Principles

A content hash can detect changed object bytes, but an attacker can create a different, well-formed object. A signature binds an approved payload to a key the attacker should not control. Yet a valid signature from an unknown or stolen key does not authorize a release, and a trusted signer can approve harmful code. Repository security therefore needs three separate decisions: are the bytes valid, is the signing identity trusted for this operation, and has the change passed review and tests?

## What is covered, and what is not

A signed commit covers its tree reference, parent references, author/committer metadata, and message in the signed payload. Changing those fields requires a new object and signature. Signing does not prove that the person named in the author field wrote the code. Nor does it cover branch permissions, a deployed artifact's build environment, or external LFS availability.

```text
commit payload → signature verified with key
trusted key/identity + reviewed change + allowed ref update → integration decision
source commit + controlled build + artifact identity → separate release provenance
```

A signed annotated tag signs a tag object that names a target object. Verify both the tag and the intended target/type before building. A valid signature on a reused or unexpected release name is insufficient.

| Scheme | Verification needs | Operational concern |
| ---------------- | ---------------------------------------------------------------- | --------------------------------------------------- |
| GPG/OpenPGP | Public key plus an explicit trust policy | Key expiry, revocation, distribution |
| SSH signing | Public key and allowed signer/principal policy | Signing-key ownership and offboarding |
| S/MIME/X.509 | Certificate chain and a trusted root | Organizational CA, renewal and revocation |
| Sigstore/gitsign | Certificate chain, identity/issuer policy, transparency evidence | Identity provider and verifier policy/configuration |

## A focused SSH signing example

Use a dedicated signing key when that separation fits your threat model. The following is a repository-local setup; replace the paths/principal with reviewed values. A public key path can select a matching private key through the local agent.

```bash
git config gpg.format ssh
git config user.signingkey /absolute/path/signing_key.pub
git config commit.gpgsign true
git config gpg.ssh.allowedSignersFile /absolute/path/allowed_signers
```

The allowed-signers file contains a trusted principal and public key, for example:

```text
dev@example.com namespaces="git" ssh-ed25519 AAAA...reviewed-public-key...
```

```bash
git commit -S -m 'fix: serialize token refresh'
git verify-commit HEAD
git tag -s v1.4.0 -m 'release 1.4.0'
git verify-tag v1.4.0
git rev-parse 'v1.4.0^{commit}'
```

Do not bootstrap trust from an allowed-signers file modified by the contribution being checked. Provision it through a reviewed policy path. Repositories using GPG similarly require installed public keys and an explicit trust decision; installing a key from a keyserver is not proof of its owner's authority.

## Cryptographic status is different from a host badge

`git verify-commit` verifies the object under the local verifier configuration. `%G?` is a diagnostic status: `G` means good, `B` bad, `U` good with unknown validity, `N` no signature, and other letters distinguish unavailable/expired/revoked cases. It is not a universal identity allowlist parser. Signer output also differs by signature format; parsing a display string as an email can reject legitimate signatures or admit an unintended identity.

A code host's **Verified** badge follows its own supported formats and identity rules. GitHub's current documentation lists GPG, SSH, and S/MIME; Gitsign's documentation says GitHub does not recognize its signatures as Verified at present. Check the host's behavior for your chosen scheme. Required-signature rules, bypass privileges, merge methods, reviews, and status checks must all agree with the intended integration policy.

GitHub stores a verification record when a signature is first verified in a repository network. Later key expiry or revocation does not change that saved status. Treat the badge as historical host evidence, not as a live authorization check; enforce current key and identity policy in a protected verifier.

## Check the actual contribution range and fail closed

For GPG, SSH, or S/MIME signatures, evaluate the actual contribution head rather than an automatically generated PR merge commit. The verifier needs an explicitly fetched base, enough ancestry to select the range, and a trusted key policy provisioned outside the contribution:

```bash
#!/bin/sh
set -eu
base_ref=${1:?pass the verified base ref}
head_ref=${2:?pass the actual contribution head ref}
git rev-parse --verify "$base_ref^{commit}" >/dev/null
git rev-parse --verify "$head_ref^{commit}" >/dev/null
commits=$(git rev-list "$base_ref..$head_ref")
for oid in $commits; do
  git verify-commit "$oid"
done
```

This checks commit signatures; it does not replace review authorization or resolve ambiguous identity mappings. Define how to handle an empty range, merges, and historical trusted commits. Test an unsigned commit, an untrusted key, a missing base, and a signed allowed contribution before enabling a required check.

This range loop uses `git verify-commit` for GPG or SSH policy. A repository that accepts Gitsign needs its certificate identity and issuer constraints checked for each commit; generic `git verify-commit` does not receive those expected claims.

Never grep human-readable output for `Good signature` as the only gate: diagnostic text is not a stable trust-policy API, and a pipeline can obscure the verifier's exit status. Use the verifier's success status with trusted policy and inspect the expected object identity separately.

## Keyless signing changes key management, not authorization

Gitsign obtains a short-lived certificate through an identity-provider flow and records transparency evidence. Its verifier accepts the identity and issuer the policy expects:

```bash
gitsign verify \
  --certificate-identity='release-bot@example.com' \
  --certificate-oidc-issuer='https://accounts.google.com' \
  <commit>
```

Use the exact identity for the release workflow and its OIDC issuer, then require the verifier's success status. Current Gitsign guidance prefers `gitsign verify`: `git verify-commit` can validate the signature and transparency record without validating that the certificate claims match the expected signer. Pin the verifier version. Accepting any valid certificate or a broad company-domain suffix is too permissive for a release.

CI workload identity can avoid a stored long-lived signing key. The workflow's permissions, repository/ref identity, protected environment, and reviewed definition become part of the trust boundary. Inspect the gitsign documentation for the installed version rather than assuming the code host uses the same verifier.

## Merge methods and history rewriting

Rebase and cherry-pick create new objects; old signatures do not transfer to the new payloads. Re-sign newly approved commits according to team policy. Squash creates a different final commit, and host-created commits may be signed by the host rather than the contributor. Verify the resulting object and the merge actor your policy expects.

`.mailmap` normalizes displayed names/emails for history reports. It neither edits signed metadata nor authenticates anyone. Keep identity cleanup distinct from signing-key trust.

## Real-world decisions and failure cases

- **Offboarding:** Revoke repository access, remove authorized signing identities/keys, and rotate exposed credentials. A client-side email allowlist does not enforce offboarding.
- **Compromised token:** Ref protections and required reviews/checks can limit writes; an attacker may still submit previously signed objects or exploit bypass privileges. A valid signature is not a malicious-content detector.
- **Compromised signing key:** Publish revocation, update trusted verifier policy, identify affected releases, and issue approved replacements. A host's saved Verified badge may remain after revocation; rewriting old history cannot retract downloaded copies.
- **Leaked secret:** Rotate/revoke it first. Then remove exposed copies and coordinate history cleanup where appropriate; signing and scanning do not undo exposure.
- **Audit evidence:** Record protected-ref policy, key/identity lifecycle, check results, approved object IDs, and artifact provenance. Signing alone is not an automatic compliance certification.

Keep verifier policy outside untrusted changes and enforce it through protected CI and server-side ref rules. Hooks improve local feedback but are bypassable. Test unsigned, untrusted, expired, and revoked identities, and retain the approved commit and artifact identities for release recovery.

## Summary

A valid signature establishes a binding to a key under a verifier policy. It does not independently prove human authorship, review quality, authorization, or artifact provenance. Combine trusted identity policy, protected integration, reviews, tests, and controlled release builds; verify the final objects created by your merge method.

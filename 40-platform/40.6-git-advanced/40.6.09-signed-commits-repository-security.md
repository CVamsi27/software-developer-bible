# Signed Commits & Repository Security

## TL;DR

**Authorship is not authentication** — anyone can set `user.name` to a maintainer's, so provenance comes from a signature over the commit object bytes (GPG, or SSH keys since Git 2.34) rather than from the author field. Pair signing with the controls that make it meaningful: required signature verification on protected branches, secret scanning, least-privilege tokens, and signed tags for releases, because a verified commit on a branch anyone can push to proves less than it appears.

---

> Author strings in commits are trivially forgeable. Cryptographic commit signing plus branch-protection enforcement turns "Alice said she wrote this" into "Alice's key signed this" — a baseline control for supply-chain security reviews.

## First Principles

Repository security is identity + integrity of the DAG:

1. **Signed commits prove authorship beyond email-string trust** — GPG/SSH signatures make the log legally-meaningful and impersonation visible; required-signatures branch protection turns it into policy.
2. **Branch protection is the security boundary**: required reviews, status checks, signed commits, force-push denial — the repo's *rules* matter more than its crypto (the human layer, → 20.5.3.03's threat modeling applied).
3. **Secrets in history are forever** (→ 20.5.3.04): scanning (gitleaks) in hooks + CI prevents; rotation is the only cure — the repo is a public-ish artifact by default.

## Definition

**Commit signing** attaches a cryptographic signature over the commit object bytes (see [Git Internals](40.6.01-git-internals-objects-refs-packfiles.md) — the signature covers tree, parents, author, committer, and message). Three mainstream schemes:

| Scheme | Key type | Trust anchor | Best for |
| ---------------------- | ----------------------------------- | ---------------------------------- | ----------------------------------------------- |
| **GPG/GnuPG** | PGP key | Web of trust / keyserver | Long-standing default; works everywhere |
| **SSH** | Existing SSH key (`gpg.format=ssh`) | `allowed_signers` file | Devs who already use SSH keys; zero new tooling |
| **Sigstore (gitsign)** | Ephemeral key from OIDC login | Fulcio CA + Rekor transparency log | Keyless signing; orgs with SSO; modern CI |

A commit shows **Verified** on GitHub only when the signature validates *and* the signer identity matches the committer email on record. Branch protection can then **require** signed commits, making unsigned pushes impossible to merge.

```text
SIGNATURE COVERAGE

  commit object ──► gpg/gitsign signs ──► signature embedded in object header
  ┌──────────────────────────────┐
  │ tree <sha>                   │◄── covered
  │ parent <sha>                 │◄── covered
  │ author/committer             │◄── covered
  │ message                      │◄── covered
  │ gpgsig -----BEGIN PGP ...    │
  └──────────────────────────────┘
  Tag objects sign the same way (git tag -s / gitsign).
```

## Why Do We Need It?

1. **Authorship is not authentication** — anyone can set `user.name "Linus Torvalds"`; unsigned history proves nothing during incident forensics.
2. **Supply-chain attacks target repos** — build-from-source pipelines inherit whatever commits landed; signatures give verifiable provenance (SLSA-aligned expectations).
3. **Insider-risk containment** — required signing + protected branches means a stolen laptop password alone cannot mint trusted history.
4. **Compliance checkboxes** — SOC2/ISO audits increasingly ask "how do you verify code provenance?"; this chapter is the answer.
5. **Tag integrity for releases** — signed tags let consumers verify artifacts trace to intended releases, not tampered ones.
6. **Cheap to adopt** — SSH signing reuses keys developers already manage; Sigstore removes key management entirely.

## How It Works

### GPG Setup

```bash
# Generate an Ed25519 signing-capable key (no encryption subkey needed)
gpg --quick-gen-key "Dev Vamsi <dev@company.com>" ed25519 sign 2y

# Point Git at it
gpg --list-secret-keys --keyid-format=long          # copy the KEYID
git config user.signingkey KEYID
git config commit.gpgsign true                       # sign every commit by default

# Publish so hosts can verify
gpg --armor --export dev@company.com                 # paste into GitHub → Settings → SSH and GPG keys
```

Daily use is transparent:

```bash
git commit -m "fix: token refresh race"      # auto-signed via commit.gpgsign
git tag -s v1.4.0 -m "release 1.4.0"         # signed TAG (annotated + signature)
git log --show-signature -1                  # local verification output
```

### SSH Signing (Lowest Friction)

```bash
git config gpg.format ssh
git config user.signingkey ~/.ssh/id_ed25519.pub     # PUBLIC key path works
git config commit.gpgsign true

# Local verification needs an allowed_signers map:
echo "$(git config user.email) namespaces=\"git\" $(cat ~/.ssh/id_ed25519.pub)" \
  > ~/.ssh/allowed_signers
git config gpg.ssh.allowedSignersFile ~/.ssh/allowed_signers
```

Upload the same public key to GitHub choosing **Signing Key** (distinct from the auth key slot — common gotcha).

### Sigstore Keyless Signing (gitsign)

```bash
go install github.com/sigstore/gitsign@latest
git config commit.gpgsign true
git config gpg.x509.program gitsign
git config gpg.format x509
```

On commit, gitsign opens an OIDC browser flow (or uses CI workload identity), gets a short-lived certificate from Fulcio, signs, and records the signature in the Rekor transparency log — no long-lived key anywhere. Verification pulls cert + log entry:

```bash
gitsign verify HEAD           # checks cert chain against your org's identity regex
gitsign verify-ref --cert-identity-regexp='^.*@company\.com$' main
```

### Enforcement: Verified Badges and Branch Protection

GitHub-side checklist:

1. Every developer adds their signing key (GPG/SSH) or uses gitsign with SSO.
2. Settings → Emails: keep `keep my email addresses private` consistent with what Git sends (mismatch = Unverified even with valid crypto).
3. Repo/Branch protection on `main`: enable **Require signed commits**.
4. Combine with status checks + linear-history requirement for full provenance posture.

```text
MERGE GATE FLOW

PR opened ──► host verifies each commit's signature
                     │
        valid + identity matches? ──no──► merge blocked (unverified)
                     │yes
        required checks pass? ──────no──► merge blocked (failing checks)
                     │yes
                     ▼
        merge proceeds (note: see squash-merge caveat below)
```

### Identity Hygiene: mailmap and Consistent Emails

Old repos accumulate duplicate identities (`vamsi@macbook.local`, `v@corp.com`). `.mailmap` normalizes display without rewriting history:

```text
# .mailmap  — correct name/email mapping for blame/log/shortlog
Vamsi K <vamsi@company.com>                    vamsi@oldpersonal.example
Vamsi K <vamsi@company.com>                    <vk@contractor.example>
Proper Name <proper@company.com>               Nickname <nick@company.com>
```

```bash
git shortlog -sne --mailmap       # audit current identity sprawl
git check-mailmap vk@contractor.example
```

Pair mailmap hygiene with signing: decide one canonical email per human, enforce via pre-commit hook, and keep it verified on the code host.

## Code Examples

### Pre-Commit Guard Against Unsigned/Alien Identities

```typescript
// scripts/ensure-signed.ts — wire as pre-commit or run in CI gate
import { execFile } from 'node:child_process';
import { promisify } from 'node:util';

const run = promisify(execFile);

const ALLOWED = /^[^@]+@(company\.com|contractors\.partnerco\.io)$/;

export async function assertPushIsSigned(range = 'origin/main..HEAD'): Promise<void> {
  const { stdout } = await run('git', ['rev-list', range]);
  const shas = stdout.split('\n').filter(Boolean);

  for (const sha of shas) {
    // %G?: signature status (G=good, B=bad, U=unsigned, N=no pubkey, E=expired...)
    const { stdout: meta } = await run('git', ['log', '-1', '--format=%G? %GE %ae', sha]);
    const [status, signerEmail = '', authorEmail = ''] = meta.trim().split(/\s+/);

    if (status !== 'G') {
      throw new Error(`${sha} signature status=${status} (must be G)`);
    }
    if (!ALLOWED.test(signerEmail) || !ALLOWED.test(authorEmail)) {
      throw new Error(`${sha} identity outside allowlist: ${signerEmail} ${authorEmail}`);
    }
  }
  console.log(`OK: ${shas.length} commits signed by trusted identities`);
}
```

### GitHub Actions Verify Step (Runs Before Tests)

```yaml
name: verify-signatures
on:
  pull_request:
jobs:
  sigcheck:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0            # need full ancestry of PR commits
      - name: Verify all PR commit signatures
        run: |
          git fetch origin "${{ github.base_ref }}"
          for sha in $(git rev-list "origin/${{ github.base_ref }}..HEAD"); do
            git verify-commit "$sha" || {
              echo "::error::unsigned/invalid commit $sha"; exit 1;
            }
          done
```

For Sigstore-based repos substitute `gitsign verify "$sha"` (install step included) — verification uses Rekor, so runners need no shared public-key distribution.

### Verifying Release Tags in a Downstream Pipeline

```bash
# Only build from cryptographically attested releases
git fetch origin 'refs/tags/v*:refs/tags/v*'
git tag -v v2.11.0 2>&1 | grep -q 'Good signature' || { echo 'tag not signed'; exit 1; }
git checkout --detach v2.11.0 && make release
```

## Real-World Use Cases

### 1. Fintech Audit Response

Auditor asks how code provenance is guaranteed post-merge. Answer: branch protection requires signed commits; CI fails unsigned ranges; release tags are `-s` signed and downstream builds verify before compiling. Mapping table goes straight into the SOC2 evidence pack.

### 2. OSS Project Adopting Keyless CI Signing

Maintainers enable gitsign in GitHub Actions: workflow OIDC tokens mint ephemeral certs scoped to the repo, every bot commit is Verified without storing any private key, and Rekor gives third parties a public ledger of who signed what and when.

### 3. Contractor Offboarding

Offboarded contractor's future commits fail the identity allowlist hook even if they retain write access temporarily — signing turns access revocation into immediate provenance enforcement rather than hoping nobody notices.

### 4. Cleaning Up Years of Identity Sprawl Before Enabling Policy

Team runs `git shortlog -sne`, writes `.mailmap`, asks everyone to fix `user.email` once, then flips on require-signed-commits. Without the cleanup phase the policy would lock out half the team on day one.

### 5. Tamper Attempt Postmortem

An attacker with a compromised PAT force-pushes malicious history. Because protected refs require signatures and old SHAs' signatures cover parents, the rewritten tip fails verification; the transparency-log entry for the original commits provides forensic proof of substitution window.

## Common Mistakes

### 1. Valid Signature, Wrong Email → Still Unverified

Signature math can be perfect while GitHub shows Unverified because `user.email` differs from any verified address on the account. Fix identity first; crypto second.

### 2. Squash Merges Silently Dropping Per-Commit Signatures

The squashed commit is created **by the merger**, signed with their credentials. If the merger has no signing configured, the whole PR's verified chain collapses into one unsigned commit. Configure signing for bots/service accounts that press merge buttons too.

### 3. Rebasing After Signing

Rewriting a commit changes its bytes, invalidating the signature — expected behavior, but teams get surprised when `Verified` badges vanish after a late `rebase`/`amend`. Re-sign (`git rebase --exec 'git commit --amend --no-edit -S'` pattern or just rely on `commit.gpgsign`).

### 4. Expired Keys Blocking Releases Mid-Sprint

GPG keys expire by design. Set calendar reminders, extend with `gpg --quick-set-expire`, and monitor CI signature checks — a red `verify-signatures` job is often just an expired key.

### 5. Treating Require-Signed-Commits as Complete Supply-Chain Security

It authenticates authors, not content quality or dependency safety. Pair with dependency pinning, SBOM generation, and artifact signing — signatures are one control in a stack.

### 6. Uploading the SSH Auth Key Into the Wrong Slot

GitHub distinguishes **authentication keys** from **signing keys**. Adding your signing pub key under auth does nothing for badges; commits stay unverified while you debug Git locally.

## Best Practices

1. **Prefer SSH signing for greenfield adoption** — no new key ceremony; Sigstore when SSO-driven, keyless flows fit.
2. **Set `commit.gpgsign true` globally per machine**, not per-repo muscle memory — forgetting one `-S` breaks the whole PR.
3. **Keep one canonical email per person** and mirror it in `.mailmap`, host account, and Git config.
4. **Sign release tags, not just commits** (`git tag -s`) — consumers and downstream CI verify the tag, inheriting confidence in its commit.
5. **Enforce server-side** (branch protection), never by convention — client hooks are advisory.
6. **Add a CI verify job before expensive steps** so unsigned PRs fail in seconds.
7. **Rotate and publish revocations**: document key-compromise runbooks (revoke key, update host, re-sign forward-only).
8. **Log signature status in release notes** (`git log --format='%h %G? %an' v1..v2`) for auditable changelogs.

## Performance Considerations

| Concern | Impact | Mitigation |
| ------------------------------- | --------------------------- | ------------------------------------------------------------ |
| GPG agent cold-start per commit | ~100-300 ms | keep agent cached; `gpgconf --launch gpg-agent` |
| CI verify on huge PR ranges | O(commits) subprocess calls | batch with `%G?` format in single `git log` pass |
| gitsign OIDC roundtrip | seconds, interactive | use workload-identity in CI; cache cert within process |
| History rewrite mass re-signing | hours on monorepos | sign going forward; backfill only compliance-critical ranges |

None of these are reasons to skip enforcement — they are tuning notes.

## Summary

- Commit signatures cryptographically bind author identity to exact object bytes; author fields alone are forgeable strings.
- Choose GPG (traditional), SSH (least friction, reuse existing keys), or Sigstore/gitsign (keyless, OIDC + transparency log).
- The host **Verified** badge requires both valid crypto and matching verified email; branch protection makes it mandatory, not optional.
- Squash merges re-author the final commit — service accounts doing merges must be configured to sign.
- `.mailmap` plus canonical emails cleans identity sprawl before enabling policy; expired keys and rebases are the operational footguns to plan for.
- In supply-chain terms, signed commits/tags are the provenance layer under SLSA-style programs — pair with dependency and artifact controls.

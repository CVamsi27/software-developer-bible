# Git Advanced Interview Questions

## First Principles

Every operation changes some combination of objects, references, index, and working tree. A strong answer identifies that state transition, who depends on it, and what evidence would establish safe recovery. Explain the mechanism, trace one failure, then choose a policy.

## Practice the complete reasoning

These 40 authored prompts progress from everyday state transitions to team policy and recovery design. Attempt them after the separate revision companion; each answer links to its canonical mechanism.

## Foundations

### 1. What is the difference between git merge and git rebase?

**Answer:** Merge joins histories and may fast-forward without creating a merge commit. Rebase replays selected changes on a new base, creating different commit identities. Choose from the collaboration contract: preserve shared ancestry with merge; rewrite a coordinated private branch when a linear series helps review. Linear history is not proof of correctness.

Source: [Mechanism and examples](40.6.03-rebase-cherry-pick.md).

### 2. What is git stash and when should you use it?

**Answer:** Stash records tracked work by default; `-u` includes untracked paths and `-a` also includes ignored paths. Inspect the entry, apply it, resolve conflicts, and only then drop it. Successful pop removes the entry, while a conflicting pop normally retains it. A stash is local saved state, not an independent backup.

Source: [Mechanism and examples](40.6.05-git-advanced-commands.md).

### 3. What is git cherry-pick and how does it work?

**Answer:** Cherry-pick applies a commit’s change relative to its parent onto the current tip. It normally creates a new commit and may need prerequisites or conflict resolution. For a backport, record the source with `-x`, test against the target release, and avoid assuming a single feature commit is self-contained.

Source: [Mechanism and examples](40.6.03-rebase-cherry-pick.md).

### 4. What is git bisect?

**Answer:** Bisect selects candidate ancestry between a confirmed good and bad snapshot. A reliable reproduction classifies each candidate; automated exit 0 is good, 1–127 except 125 is bad, and 125 skips an untestable candidate. Skips can make the answer ambiguous; dependency failures must not masquerade as the target bug.

Source: [Mechanism and examples](40.6.07-code-archaeology.md).

### 5. What is git reflog?

**Answer:** Reflogs record local movements of refs that have logging enabled; HEAD has its own movement history. They are not fetched history and entries expire under retention policy. Inspect the recorded object, then create a rescue branch before changing the active checkout. Unrecorded work is outside this recovery mechanism.

Source: [Mechanism and examples](40.6.01-git-internals-objects-refs-packfiles.md).

### 6. What is the difference between git revert and git reset?

**Answer:** Revert adds a compensating commit, preserving shared ancestry. Reset moves the selected commit; soft preserves index/worktree, mixed resets the index, and hard replaces tracked state and may delete obstructing untracked paths. Pick the operation from which state must change, then preserve required local work.

Source: [Mechanism and examples](40.6.05-git-advanced-commands.md).

### 7. What is git worktree?

**Answer:** A linked worktree has its own checkout, index, and HEAD while sharing objects and most refs. Use it to test a release while retaining unfinished feature work. The same branch normally cannot be active in two worktrees; remove a checkout through Git after preserving changes. It is not a separate backup.

Source: [Mechanism and examples](40.6.05-git-advanced-commands.md).

### 8. What is git submodule?

**Answer:** A superproject stores a gitlink naming a commit in another repository. `update --init --recursive` restores recorded revisions; `--remote` follows tracking tips and requires reviewing changed gitlinks. CI must have access to every referenced object; cloning the superproject alone does not guarantee that.

Source: [Mechanism and examples](40.6.05-git-advanced-commands.md).

## Integration and investigation

### 9. How do you resolve merge conflicts during rebase?

**Answer:** Inspect the stopped commit and both sides of the conflict, edit the intended result, stage only resolved paths, and continue. Run the target tests after replay. Abort restores the pre-rebase branch state; skip discards that commit’s replayed change, so use it only after deciding the change is unnecessary.

Source: [Mechanism and examples](40.6.03-rebase-cherry-pick.md).

### 10. What is interactive rebase and when should you use it?

**Answer:** Interactive rebase edits the selected commit sequence with operations such as reword, squash, edit, or drop. Check the selected range and preserve its original tip first. Parent/metadata changes create new identities and signatures; coordinate any already-shared series and compare the old/new patch series.

Source: [Mechanism and examples](40.6.03-rebase-cherry-pick.md).

### 11. How do you handle large files in Git?

**Answer:** Choose whether the bytes belong in Git, LFS, an artifact registry, or a dataset store. LFS records pointers and requires separately available binary objects. Tracking a new pattern does not remove historical blobs, and ignore rules do not untrack existing paths. Rehearse any migration and restore both stores.

Source: [Mechanism and examples](40.6.08-git-at-scale-lfs-partial-clones.md).

### 12. What is git subtree?

**Answer:** A subtree imports an external project under a directory in the main repository; unlike a submodule, its files are ordinary tracked content. Squashed imports trade detailed upstream ancestry for a compact record. Decide update ownership, licensing, and conflict handling before choosing either dependency model.

Source: [Mechanism and examples](40.6.05-git-advanced-commands.md).

### 13. How do you find which commit introduced a bug?

**Answer:** Confirm a reproduction at both endpoints, isolate it from unrelated environment failures, then bisect. Inspect the first failing candidate’s diff and test the preceding state before concluding causality. Preserve the bisect log; if historical snapshots cannot be tested, report the remaining candidate set rather than certainty.

Source: [Mechanism and examples](40.6.07-code-archaeology.md).

### 14. What is git blame and when to use it?

**Answer:** Blame attributes the last recorded line change, not fault or design rationale. Follow the identified commit into its diff, review, tests, and earlier history; use whitespace/move detection when relevant. A formatting commit can hide the behavior change, and author metadata alone is not authenticated identity.

Source: [Mechanism and examples](40.6.07-code-archaeology.md).

### 15. How do you clean up repository history?

**Answer:** For a private patch series, interactive rebase can improve review units. For sensitive or oversized history, first preserve a verified backup, rotate any leaked secret, and rehearse a scoped filter-repo/LFS migration. Coordinate refs, signatures, forks, and client cutover; history rewriting is not secure deletion.

Source: [Mechanism and examples](40.6.03-rebase-cherry-pick.md).

### 16. What is git sparse-checkout?

**Answer:** Sparse checkout limits materialized paths; cone mode efficiently selects directories plus relevant ancestor/root files. Full object history may still be present. Combine with a supported partial clone when transfer is the bottleneck, and verify that build tools fail if required targets are missing.

Source: [Mechanism and examples](40.6.08-git-at-scale-lfs-partial-clones.md).

### 17. How do you handle multiple remotes?

**Answer:** Name each remote’s role, inspect its fetch/push URLs and refspecs, then fetch and compare before integrating. Fetching all remotes does not authorize publishing to all of them. Keep the fork push destination explicit and review tracking branches so an upstream cannot be overwritten accidentally.

Source: [Mechanism and examples](40.6.02-branching-strategies.md).

### 18. What is the difference between git pull and git pull --rebase?

**Answer:** Pull fetches and then integrates according to options/configuration; it is not universally a merge default. `--rebase` replays local changes, while `--ff-only` refuses divergent integration. Inspect divergence and choose the team’s explicit policy rather than relying on machine-specific defaults.

Source: [Mechanism and examples](40.6.03-rebase-cherry-pick.md).

## Senior decisions

### 19. How do you implement a Git workflow for a large team?

**Answer:** Start with deployment cadence, supported release lines, ownership, and rollback needs. Select short integration cycles or coordinated release branches, then add reviewed changes, required checks, conflict ownership, and a tested backport procedure. Branch names do not deploy software or enforce permission.

Source: [Mechanism and examples](40.6.02-branching-strategies.md).

### 20. What is the impact of force pushing?

**Answer:** A forced update can remove commits from the remote ref that others use. Coordinate first, preserve the prior tip, and compare the exact expected remote object ID. An explicit force-with-lease rejects a changed tip; it does not prove the rewritten series is safe or authorize bypassing branch policy.

Source: [Mechanism and examples](40.6.03-rebase-cherry-pick.md).

### 21. How do you handle monorepos with Git?

**Answer:** Measure transfer, checkout, status, and history-query costs separately. Use partial clone, sparse checkout, supported monitors, and maintenance where their mechanisms address the bottleneck. Build targets and release ownership remain explicit; a smaller checkout must not silently omit required package checks.

Source: [Mechanism and examples](40.6.08-git-at-scale-lfs-partial-clones.md).

### 22. What is git notes?

**Answer:** Git notes attach data through a separate notes ref without modifying the target commit. They are not automatically transferred with every clone/push and are not part of the target commit’s signature. Define the ref, permissions, synchronization, and whether the metadata must be independently authenticated.

Source: [Mechanism and examples](40.6.01-git-internals-objects-refs-packfiles.md).

### 23. How do you implement Git hooks for CI/CD?

**Answer:** Use local hooks for fast feedback and server-side required checks for enforcement. Check the staged snapshot or actual pushed range, propagate nonzero statuses, and use an actual secret scanner rather than searching for the word password. Hooks can be absent or bypassed; untrusted hook code also needs review.

Source: [Mechanism and examples](40.6.04-git-hooks.md).

### 24. What is git bundle?

**Answer:** A bundle carries Git objects and advertised refs, possibly with prerequisite commits. A full bundle can restore a repository offline; an incremental one requires an existing receiver with its prerequisites. Verify and test a network-free restoration; LFS bytes and host permissions/issues are separate backups.

Source: [Mechanism and examples](40.6.06-patch-and-bundle.md).

### 25. How do you handle Git in CI/CD pipelines?

**Answer:** Give each job enough refs/history for its task and fail if a required base or ancestor is unavailable. A build may be shallow; release/version/signature checks often need additional ancestry. Pin tools, isolate untrusted contributions from write credentials, and record the exact checked-out object ID.

Source: [Mechanism and examples](40.6.08-git-at-scale-lfs-partial-clones.md).

### 26. What is the difference between git fetch and git pull?

**Answer:** Fetch downloads objects and updates configured remote-tracking refs without integrating into the active branch. Pull adds integration through merge/rebase/fast-forward policy. Fetch can still alter repository refs and use credentials; inspect the fetched tip before choosing how to integrate it.

Source: [Mechanism and examples](40.6.05-git-advanced-commands.md).

### 27. How do you manage Git permissions?

**Answer:** Authentication credentials and host/server authorization determine who can update refs. Protect important refs with least privilege, reviews, required checks, and carefully scoped bypass roles. User.name/email are commit metadata, not permissions. Signing trust and offboarding must be maintained separately.

Source: [Mechanism and examples](40.6.09-signed-commits-repository-security.md).

### 28. What is git archive?

**Answer:** Archive exports selected tree content, not a repository history or reflog backup. Attributes such as export-ignore/export-subst can affect output. LFS content may remain pointers depending on the export path; verify the resulting artifact and provenance rather than assuming archive reconstructs every dependency.

Source: [Mechanism and examples](40.6.06-patch-and-bundle.md).

### 29. How do you handle Git in containerized environments?

**Answer:** Prefer building from an explicit verified source snapshot and exclude .git from runtime images unless the application needs it. Inject read credentials only at the build step that needs them; do not bake them or a credential-bearing Git config into layers. Track source/artifact identity and required external dependencies.

Source: [Mechanism and examples](40.6.09-signed-commits-repository-security.md).

### 30. What is the future of Git?

**Answer:** Separate documented current capabilities from predictions. Evaluate candidate improvements with representative clone/status/history benchmarks, interoperability, and recovery tests. A proposed storage or signing feature is not a reason to change production policy until tool versions and host support are verified.

Source: [Mechanism and examples](40.6.08-git-at-scale-lfs-partial-clones.md).

## Design scenarios

### 31. Design a Git workflow for a 100+ engineer team.

**Answer:** Specify the integration contract: owners, maximum branch age, merge checks, supported release branches, backport responsibility, deployment approval, and rollback. Trace a conflicting change and an urgent fix through it. Team size alone does not mandate Git Flow, trunk-based development, or a weekly release.

Source: [Mechanism and examples](40.6.02-branching-strategies.md).

### 32. How would you handle a corrupted Git repository?

**Answer:** Stop writes and preserve the damaged store plus local work before attempting repair. Run fsck to identify missing/corrupt objects, compare a trusted complete backup/remote, and restore verified objects/refs into a separate checkout. Reflog can name an object but cannot recreate missing bytes; BFG is not corruption repair.

Source: [Mechanism and examples](40.6.01-git-internals-objects-refs-packfiles.md).

### 33. What are the trade-offs between Git and other VCS?

**Answer:** Compare actual constraints: offline commits, centralized authorization, branching/merging, large-file workflows, ecosystem integration, and recovery. Avoid generic fast/slow rankings across unrelated workloads. Git’s distributed object model is useful, but external binary storage and server policy add operational requirements.

Source: [Mechanism and examples](40.6.08-git-at-scale-lfs-partial-clones.md).

### 34. How would you migrate a large repository to Git?

**Answer:** Inventory branches/tags, identity mapping, permissions, binaries, and consumers before a trial conversion. Compare representative trees and release tags, test builds and LFS restoration, plan cutover/freeze and rollback, and retain the source system until acceptance. A successful import command alone is insufficient evidence.

Source: [Mechanism and examples](40.6.08-git-at-scale-lfs-partial-clones.md).

### 35. Design a Git backup and disaster recovery system.

**Answer:** Define recovery point/time targets and back up refs/objects, LFS bytes, local required work, and host metadata/permissions through their respective mechanisms. Protect backups from shared credentials and deletion. Verify object integrity and restore on an isolated machine without network dependencies; measure recovery time.

Source: [Mechanism and examples](40.6.06-patch-and-bundle.md).

## Follow-ups

### 36. How does Git handle binary files?

**Answer:** Git blobs store content independent of filenames; packfiles can delta-compress binary content, but effectiveness depends on the format. Compressed/encrypted changing binaries often compress poorly. LFS changes storage and transfer behavior, not the intrinsic mergeability of binary formats.

Source: [Mechanism and examples](40.6.08-git-at-scale-lfs-partial-clones.md).

### 37. What is the difference between git merge and git rebase historically?

**Answer:** Both operations have long existed; age is not the useful distinction. Merge preserves ancestry or fast-forwards, while rebase creates a revised patch series on a new base. The deciding constraint is whether consumers depend on existing commit identities and how the team reviews integration.

Source: [Mechanism and examples](40.6.03-rebase-cherry-pick.md).

### 38. How do you handle Git in a microservices architecture?

**Answer:** Choose repository boundaries from ownership, atomic cross-service changes, release independence, access isolation, and tooling. A monorepo can retain independent deployment; multiple repositories require explicit dependency/version coordination. Git refs alone do not provide service compatibility or runtime rollback.

Source: [Mechanism and examples](40.6.02-branching-strategies.md).

### 39. What is the impact of Git on developer productivity?

**Answer:** Measure time spent integrating, debugging, waiting for CI, and recovering failures. Short branches, searchable commits, and reliable reproduction can reduce that cost; misuse of rewriting or incomplete history can increase it. Attribute measured improvements to a workflow change rather than claiming Git eliminates conflicts.

Source: [Mechanism and examples](40.6.07-code-archaeology.md).

### 40. How do you train team members on advanced Git?

**Answer:** Use disposable repositories with concrete failures: preserve a lost committed tip, contrast reset modes, resolve a rebase conflict, bisect a seeded bug, and restore a bundle. Ask learners to explain which state changes and what remains unrecoverable. Review the result and repeat failed mechanisms, rather than memorizing command lists.

Source: [Mechanism and examples](40.6.05-git-advanced-commands.md).

## Summary
Advanced Git commands are essential for complex development workflows. Master bisect for debugging, reflog for recovery, and understand when to use revert vs reset. Practice these commands and understand their implications for team collaboration.

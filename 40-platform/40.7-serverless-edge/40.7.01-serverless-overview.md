# Serverless Overview

## Definition

Serverless is a cloud execution model in which the provider dynamically allocates compute resources on demand, billed according to the service's request, compute, and provisioned-capacity model. Developers deploy functions or applications while the provider manages underlying servers. Concurrency quotas, dependency capacity, scaling behavior, and cost still need planning.

> **Textbook Definition:** Serverless computing delegates infrastructure provisioning and much of runtime lifecycle management to a provider, exposing application execution through managed services with explicit scaling, isolation, quota, and billing contracts.

## First Principles

A bursty application needs capacity when events arrive but little capacity while idle. Provider-managed execution transfers environment provisioning to the service. It does not transfer decisions about downstream limits, authorization or irreversible effects.

Instances can be reused or discarded. Reuse makes shared SDK clients efficient; replacement makes process memory unsuitable as durable business state. A request timeout also cannot tell a caller whether a write committed. These constraints lead to external state, bounded execution and stable operation identity.

## How a request becomes work

```text
HTTP request -> gateway/authentication -> function -> authoritative database
business transaction -> durable event/outbox -> queue -> retryable worker
```

**Function as a service (FaaS)** runs a handler for an invocation. Managed databases, queues and object storage provide the surrounding state. “Serverless application” often includes these services, not just the function. A platform can also manage a whole container rather than individual handlers.

The handler receives a trigger-specific payload. API Gateway HTTP and REST APIs have different event shapes; a queue sends a batch rather than an HTTP request. Parsing the wrong shape is an application error, even if both deployments are called Lambda.

Trace a thumbnail job: an upload commits to object storage; its event identifies a bucket/key and ideally an object version. A worker retrieves that version, validates size/type and writes a deterministic output key. A duplicate event finds the same completed output. An overwritten input needs a new version identity; deduplicating solely by filename would discard legitimate work.

Do not acknowledge durable completion before its effect is committed. Publishing a queue message separately from a database write leaves a loss window; use a transactional outbox or an equivalent recoverable publication protocol. Provider retries do not repair that gap automatically.

## Choose the execution model from the whole workload

| Dimension | Function invocation | Managed container | VM/process you operate |
| ------------------- | --------------------------------------------- | ----------------------------------------------------------- | -------------------------------------------------- |
| Unit shipped | Handler plus dependencies | Image and service/job configuration | Machine image plus application |
| Lifetime | Trigger/service-specific bound | Platform/service lifecycle | Process and host policy |
| Scaling | Provider quotas and scaling rate | Replica/minimum-capacity policy | Capacity policy you implement |
| State | External authority; local cache opportunistic | External/shared state; configured volumes where appropriate | Explicit disks, replication and backups |
| Good starting point | Bursty events and bounded API work | Persistent connections or long-running jobs | Special hardware, OS control or legacy constraints |

These are choices, not universal price rankings. Steady high utilization may favor provisioned containers; a short burst may favor functions. Minimum instances, provisioned concurrency, network transfer, databases, logs and workflow histories can create costs while functions are idle.

## Estimate concurrency before buying capacity

For a stable workload, approximate active invocation concurrency as `requests/second × average duration in seconds`. At 200 requests/s and 0.25 s per request, average concurrency is about 50. At one second per request it becomes 200 without any change in arrival rate.

This is an average, not a peak or latency bound. Account for tail duration, retries, ramp-up limits and queueing. A database allowing 100 usable connections cannot safely receive one new connection from each of 1,000 invocations. Bound function/consumer concurrency, reuse clients and use an appropriate proxy/pool where needed.

For a simple GB-second billing model, one million invocations at 0.25 s and 0.5 GB consume 125,000 GB-s before other charges. Substitute current provider prices and free tiers; other services, including Fluid Compute, may bill different resource dimensions. Faster execution at higher memory can lower or raise total cost, so measure both.

## Cold starts are one part of latency

Creating an execution environment can include runtime startup, dependency loading and application initialization. Cold starts also happen while scaling out or deploying, not only after inactivity. There is no portable fixed cold-start range or universal runtime ordering.

Hoist reusable SDK clients, remove unnecessary dependencies and benchmark the package actually shipped. Keep request identity, authorization and mutable request data inside the invocation. Cached clients must recover from closed connections; module initialization is not a guarantee that a connection remains usable forever.

Provisioned concurrency maintains initialized Lambda capacity with an explicit cost and capacity bound. SnapStart restores snapshots for supported runtime/configuration combinations; the [Lambda chapter](40.7.02-aws-lambda.md) covers uniqueness and restore hazards. Neither promises that every request avoids startup or downstream latency.

## Failure behavior comes from the trigger

| Trigger family | Who retries or buffers? | Application responsibility |
| ------------------------------ | ------------------------------------------------------------- | -------------------------------------------------------------- |
| Synchronous HTTP | Caller/gateway policy; not arbitrary automatic function retry | Defined status, deadlines and stable identity for writes |
| Asynchronous Lambda invocation | Lambda's async retry/destination settings | Idempotent effects, failure destinations and replay procedure |
| Queue event-source mapping | Queue visibility/redrive plus mapping behavior | Batch failure handling, concurrency and durable effects |
| Ordered stream | Mapping checkpoints and retry policy | Partition ordering, bounded retries and poison-record recovery |

A dead-letter queue is a place for unresolved work, not an automatic recovery plan. Define ownership, alerts, retention and a replay process that preserves the original business command. Queue visibility is a lease on a message; extending it does not extend a function's maximum execution lifetime.

## Real-world decisions

Use a short function for a webhook receiver that verifies the raw-body signature and records a durable intent before returning success. Move slow provider work to a queue or workflow. A caller-triggered request must not become an unauthenticated webhook relay merely because scaling is managed.

For a multi-day approval flow, persist workflow state and use durable timers rather than sleeping inside a running invocation. For video transcoding or a persistent socket process, consider a job/container service. An API Gateway WebSocket integration can invoke Lambda for events even though Lambda does not hold each client connection itself.

Edge placement helps when work can complete locally. If each function performs several sequential database calls to one distant region, the data path can dominate; move compute near that authority or change the access pattern.

## Mistakes and best practices

Avoid copying five provider snippets with undefined persistence functions and treating them as complete services. Each executable example needs the selected event shape, runtime, permissions, validated input and dependency configuration. The next chapters provide focused provider and retry examples.

Keep reusable infrastructure clients separate from request state. Set deadlines shorter than the enclosing invocation where appropriate. Record outcome uncertainty, protect dependency capacity and measure complete-path latency, error rate, queue age and cost per successful operation.

## Summary

Serverless delegates execution-environment management while leaving application contracts explicit. Choose functions, containers or VMs from workload duration, concurrency, dependency capacity and total cost. External state, safe retries and trigger-specific failure handling make an application recoverable; automatic scaling alone does not.

# Serverless Overview

A user uploads an image and expects the page to respond quickly. Resizing the image may take longer, so the request stores the original and schedules the resize as separate work. The platform can start a worker when the event arrives and release its compute later. The application still decides what "accepted" and "complete" mean, and how to recover if the worker runs twice.

## Definition

**Serverless** is a cloud operating model in which a provider manages the execution infrastructure, letting developers compose functions, managed containers, queues, databases, and object storage without operating the underlying machines. "Serverless" does not mean there are no servers, unlimited capacity, or no operations work. Each service still has its own runtime, scaling, durability, quota, and billing contract.

> **Textbook Definition:** Serverless computing is a cloud service model in which provider-managed infrastructure executes customer workloads through request-driven or event-driven abstractions, with execution, isolation, scaling, state, and billing governed by the service contract.

## First Principles

Scaling creates more execution capacity; it does not increase the capacity of a database or external API. If many independent workers share a slower dependency, admission must be bounded at that dependency's sustainable rate. An invocation may run on a fresh process, and a caller may retry after losing a response — therefore process memory alone cannot coordinate separate invocations, and a timeout cannot prove that a remote effect did not commit. Durable state, stable operation identity, and an explicit acknowledgment point follow from those boundaries.

## How It Works

### 1. Start with One Job and Follow It Through

```text
client -> authenticated API -> object storage
                               └-> object-created event -> queue
                                   -> bounded worker -> output + job status
```

The API should return success only after the original object is durably stored. That response means "the work was accepted," not "the image is ready." The worker reports completion only after the output and status have been committed. This separation keeps a slow task out of the interactive request while making progress visible to the user.

A **function as a service (FaaS)** runs a handler in response to an invocation. A managed-container service instead runs an application image under a platform lifecycle, often with a persistent process or job. Both may be called serverless because the provider manages the machines; their request concurrency, lifetime, and scaling contracts differ. A serverless application usually combines compute with managed data and messaging services, so the whole request path — not just the handler — determines behavior.

The event is part of that contract. An HTTP request, an object-created event, and a queue batch have different payloads and acknowledgment rules. Do not treat two triggers as interchangeable because they invoke the same function. For a queue worker, acknowledgment usually follows the configured batch or message outcome; for a synchronous request, the caller receives the function's response. Check the specific provider and trigger behavior before writing retry logic.

A duplicate object event should not resize the wrong image or create a second business result. Identify input by its object key and immutable version where available, and include the transform version in the operation identity. Make output and job-status writes idempotent: repeating them must not create another business result. Process memory and temporary files can help with a single execution, but they are not the durable job record: an execution environment may be replaced at any time.

When a database transaction must also publish a queue message, two independent writes can lose the message or publish it without the database change. A **transactional outbox** stores the event in the same database transaction as the business change; a separate publisher retries delivery, so consumers must tolerate duplicate publication. Provider-managed retries do not make two independent writes atomic. For a timeout after a remote effect, reuse a stable idempotency key or query the effect's authority before issuing a new command.

### 2. Trace Capacity, Latency, and Cost Along the Dependency Path

For a stable workload, average in-flight work is approximately `arrival rate × average service time`. At 200 requests per second and 0.25 seconds per request, the average is about 50 concurrent requests. This is a planning estimate, not a peak or a provider's exact instance count. Long-tail durations, bursts, retries, queueing, per-instance concurrency, and scaling rate all affect the capacity needed for a latency target.

The database may be the tighter limit. If hundreds of workers each open a connection, they can exhaust a database long before compute reaches its quota. Bound function or consumer concurrency against the downstream budget, reuse clients when safe, and use a supported proxy or pool where appropriate. Reused connections can go stale; the client must recover without turning a failed operation into an unsafe duplicate.

An invocation that needs a new execution environment incurs startup initialization, commonly called a **cold start**. It can occur during scale-out or deployment as well as after low traffic. Warm reuse is an optimization, not a guarantee. Measure end-to-end p95/p99 latency (the 95th and 99th percentile) and the shipped artifact; reduce unnecessary initialization only after identifying it in the trace. Lambda's Provisioned Concurrency and SnapStart are provider-specific options with capacity, runtime, and cost constraints; see the [Lambda chapter](40.7.02-aws-lambda.md).

The closest compute location is not always the best one. If a request makes several sequential calls to a database in a distant region, those round trips can dominate runtime. Place compute near the authoritative data or reduce round trips; put computation at the edge only when its inputs and required decisions are available there.

Compare total cost per successful operation, not only function duration. Depending on the service, the bill can include requests, execution resources, minimum or provisioned capacity, network transfer, storage, database usage, logs, retries, and workflow history. A failed or retried invocation still consumes resources. Substitute current service pricing and measured traffic rather than assuming serverless is always cheaper than a provisioned service.

### 3. Choose the Execution Model from the Workload

| Model | A useful starting point | What to verify before choosing |
| ------------------------ | ------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------- |
| Function invocation | Bursty APIs and short event handlers | Trigger payload, maximum duration, concurrency, retries, and downstream capacity |
| Managed container or job | Persistent connections, custom process behavior, or longer jobs | Minimum capacity, scale-to-zero behavior, startup time, shutdown handling, and job recovery |
| VM or managed host | OS-level control, special hardware, or a workload that benefits from a stable process | Patching, capacity planning, deployment, failover, and operational ownership |

These are workload choices, not a universal ranking by price or reliability. A long job may fit a managed job service; a multi-day approval needs durable workflow state and timers rather than a sleeping invocation. A WebSocket service may use a managed gateway for connections and invoke functions for events — the function itself need not own each open connection.

### 4. Make Delivery and Recovery Application Behavior

A caller can lose the response after a write has committed and retry the same command. A queue can redeliver after a worker commits its effect but fails before acknowledgment. Some services provide deduplication or ordered checkpoints, but those guarantees do not automatically cover a database or external API effect. Keep a stable operation identity at the effect boundary and make replay safe.

The trigger determines who retries, what is retained, and what counts as acknowledgment. HTTP callers need defined deadlines and retry rules. Asynchronous invocations follow the invoker's retry policy and may support failure destinations. Queues need visibility, redrive, and batch-failure behavior. Ordered streams need checkpoints and a recovery plan for a repeatedly failing record. Confirm the current contract for the chosen provider; then alert on failed work, retain enough context to investigate, and rehearse replay without changing the original business command.

For example, a webhook receiver can verify the signature and persist a uniquely identified intent before returning success. A queue worker then calls the slow provider with the same idempotency key and records the result. If the provider times out, the key lets the receiver or reconciliation process find the original outcome instead of blindly repeating an irreversible action.

## Summary

Serverless moves execution-environment management to a provider; it does not move business correctness, dependency limits, or recovery out of the application. Follow one operation from acceptance through committed effect and acknowledgment. Choose the runtime from its lifetime and dependency path, bound concurrency to what downstream systems can handle, and make retries safe at the boundary where effects occur.

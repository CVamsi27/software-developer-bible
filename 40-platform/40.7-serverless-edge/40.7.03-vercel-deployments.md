# Vercel Deployments

## Definition

Vercel is a managed cloud platform that builds, deploys, and serves web applications with zero configuration for supported frameworks. It abstracts CDN, edge functions, serverless compute, image optimization, and CI/CD behind a single Git push.

> **Textbook Definition:** A Vercel deployment is a versioned set of application build outputs and managed execution resources served through the platform, with routing, environment, and runtime behavior determined by project configuration.

## First Principles

A deployment combines code artifacts, routing and environment configuration. An immutable build URL helps identify what was shipped, but the behavior also depends on mutable databases, external services and secrets. Promoting a build must therefore check its environment and dependency compatibility.

Static content can be served near readers while dynamic code executes near its data. “Delivered by an edge network” does not mean every database query executes nearby. The framework and provider contracts jointly determine which output is static, cached or computed for each request.

## Trace build, preview and production separately

```text
source + lockfile + build settings -> identified deployment artifacts
                                   -> preview routing + preview configuration
verified release -> production domain/alias + production configuration
request -> static/cache path OR managed function -> data authority
```

Git integration can build pushes and provide review URLs when configured. Verify branch settings, ignored builds and deployment protection; a preview URL is not proof of isolation. Use preview databases, scoped credentials and synthetic data where possible. Background jobs and outbound webhooks must also be isolated or disabled.

Framework integrations generate the platform build output; do not assume every project uses a literal `.next/static/api` directory layout. Inspect the supported framework version and build logs. Removing an old `builds: @vercel/next` override lets framework detection work normally unless a documented custom build requires it.

## Runtime choice changed; check the installed framework

As checked on 2026-10-10, Vercel's official Edge runtime documentation recommends Node.js for performance/reliability and says **Next.js 16.3 no longer supports `runtime = 'edge'` for routes and pages**. Older applications and non-Next integrations may have different contracts. Teach the current version explicitly rather than copying an Edge route into a new Next.js application.

Node.js functions can use Fluid Compute, whose concurrency and active CPU/provisioned memory billing need their own budgets. Multiple requests can share an instance; mutable module-level request data risks leaking across requests. Streaming may reduce time to first byte while the function continues work; it does not make the full request free or unlimited.

Co-locate dynamic compute with the database when repeated database trips dominate. Check allowed regions, duration and memory for the selected plan/runtime. There is no universal sub-5-ms initialization guarantee, fixed 300-second Pro default or static per-million price table suitable for every project.

## A complete route core with bounded input

This App Router route uses the Node.js runtime and synthetic data. It demonstrates a safe query bound and uncached response, not a complete authentication/database service.

```typescript
// app/api/example-items/route.ts
export const runtime = 'nodejs';

export async function GET(request: Request): Promise<Response> {
  const value = new URL(request.url).searchParams.get('limit') ?? '20';
  if (!/^\d+$/.test(value)) return Response.json({ error: 'Invalid limit' }, { status: 400 });
  const limit = Number(value);
  if (!Number.isSafeInteger(limit) || limit < 1 || limit > 100) {
    return Response.json({ error: 'Limit must be 1..100' }, { status: 400 });
  }
  return Response.json({ items: [], limit },
                       { headers: { 'cache-control': 'no-store' } });
}
```

A protected route must verify the session/token and tenant permissions before accessing records. A cookie merely being present is not authentication. A redirect layer can improve navigation; it cannot be the only data authorization boundary. Next.js request `geo` and `ip` fields were removed in version 15: use the documented provider helper/trusted ingress metadata when needed, and do not use geography as proof of identity.

## Caching separates reusable content from personal data

Incremental static regeneration (ISR) serves generated content and refreshes it under framework/provider rules. A revalidation request invalidates eligible data/pages; it does not guarantee that every viewer immediately receives new content. Test the selected caching mode, including Next.js Cache Components where enabled.

Keep one canonical implementation in the [Next.js chapters](../../10-frontend/10.4-next.js/INDEX.md). At the deployment boundary, verify that a revalidation webhook authenticates its caller, validates a bounded path/tag, handles malformed payloads and rate limits. A raw secret in a JSON body with arbitrary path construction is not a complete secure webhook.

Private responses need explicit framework data-cache and HTTP cache policies. Setting `no-store` on the outgoing response does not retroactively prevent an earlier private database result from entering a shared framework cache. Test cache keys, identity changes, logout and tenant transitions.

For image optimization, specify dimensions or a supported fill layout and required remote-source policy. A dynamic URL with `placeholder='blur'` needs a blur data URL; it is not automatically generated for every remote image. Keep lazy loading/defaults and preload policy tied to the actual Next.js version.

## Scheduling and background work need durable identity

A cron request is a trigger, not an exactly-once transaction or a durable job engine. Authenticate the endpoint using the platform's current secret mechanism, claim a stable schedule/period identity and write durable work before returning success. Overlapping cron invocations must not generate duplicate billing or reports.

Use the platform-supported post-response API for bounded best-effort work. A long or irreversible operation belongs in a queue/workflow with explicit retries and idempotency. An unawaited promise can disappear on lifecycle termination.

## Promote and recover an identified release

Keep production and preview settings explicit, including domain, secrets, build-time variables and backing services. `NEXT_PUBLIC_*` values can enter browser bundles; they are public by design. A changed build-time value usually requires a new build, while provider runtime settings have different activation rules.

Check migrations and compatible backend APIs before promotion. Rolling a domain back to an earlier deployment does not reverse a migration, revoke a compromised secret or undo a dispatched email. Verify rollback against the current data schema. Document preview cleanup so retained builds and resources do not become unmanaged environments.

## Decisions, mistakes and best practices

| Concern | Evidence to collect |
| --------------------- | --------------------------------------------------------------------------- |
| Fast static site | Cache headers, asset versioning and field browser performance |
| Database-backed route | Function region, query count, dependency latency and connection limits |
| Cold-start concern | Initialization plus complete-request distributions under rollout and bursts |
| Preview safety | Data/secret isolation, access protection and background side effects |
| Cost concern | Current plan, CPU/memory/request/transfer dimensions and workload trace |

Do not call Vercel an AWS Lambda wrapper as an application portability guarantee, or treat externalizing a dependency as tree-shaking it away. External packages still need to be available in deployment artifacts. Use logs, traces and web-vitals metrics for their different purposes; browser analytics does not replace server logs.

## Summary

Vercel deploys versioned application outputs through managed routing, caching and compute. Runtime/framework version, data location and environment settings govern actual behavior. Protected APIs, preview isolation, durable jobs and compatible rollback remain application responsibilities even when Git-based deployment is convenient.

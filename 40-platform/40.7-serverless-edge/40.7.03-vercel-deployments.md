# Vercel Deployments

A pull request can look correct on its preview URL and still write to the production database. Later, rolling the code back cannot undo a payment or restore data changed by a migration. A deployment platform can isolate and route application builds; the application and its environment still determine which systems a build can affect.

## Definition

Vercel is a managed application-hosting platform. It builds application artifacts, connects them to routes and domains, and serves static responses or runs dynamic code through managed runtimes. Git integration can automate a build for each push, but Git is one deployment path rather than the definition of a deployment.

> **Textbook Definition:** A deployment is a versioned application build made available through a serving environment. On Vercel, a deployment has a unique URL; domains and aliases determine which deployment receives production traffic, while project configuration supplies its runtime and environment behavior.

## First Principles

A release has at least three identities: the source revision, the built output, and the environment that serves it. A commit identifies source; it does not by itself identify the exact build inputs, secrets, data stores, or external services involved in production. Record the commit and build details, then verify the configured environment and dependencies before routing users to the release.

```text
commit + lockfile + build configuration
                 │
                 ▼
          build and deploy
          ├── unique deployment URL ── preview checks
          └── production deployment ── domain/alias ── user traffic
                                                  └── routes to static/cache/function
                                                                   └── data and services
```

The deployment URL identifies a build, not a sealed copy of every dependency it uses. Databases, third-party APIs, DNS, and runtime environment variables can change independently. A safe release therefore checks both the build and the systems it can reach.

## 1. Separate Preview from Production

Vercel can create a preview deployment for a branch and a production deployment for the configured production branch. Environment variables can be scoped to Development, Preview, Production, or custom environments. A generated preview URL is not proof that its data or effects are isolated: a preview can still reach a production database, send a real email, invoke a production webhook, or schedule work.

Give previews scoped credentials and non-production data. Protect access to preview deployments when they expose private application content. Vercel Cron invokes production deployments only, but protect job endpoints from manual calls and keep preview webhooks and other side effects isolated. Test the paths that matter, including authentication, tenant boundaries, and writes — not just whether the page renders.

Framework integrations produce platform-specific build output. Inspect the detected framework, build logs, and supported version rather than depending on an internal directory layout or an old custom build override. Keep build-time and runtime configuration distinct: a public `NEXT_PUBLIC_*` value can be included in browser JavaScript, and changing a build-time value generally requires a new build.

## 2. Place Request Work Where Its Dependencies Are

Node.js is Vercel's default runtime for functions and is usually the right starting point when the application needs Node APIs, larger packages, or compatibility with a typical server library. Vercel still documents an Edge runtime for supported function configurations and recommends migrating to Node.js for performance and reliability. Check the framework contract separately: an available platform runtime is not necessarily supported by a framework release.

Framework rules add another boundary. In Next.js 16, Middleware is renamed to Proxy and Proxy runs on Node.js; the Edge runtime is not supported there. Next.js releases before 16.3 can select the Edge runtime for supported routes, subject to its smaller API surface. From Next.js 16.3, routes and pages no longer support `runtime = 'edge'` and run on Node.js, as documented in [Vercel's runtime contract](https://vercel.com/docs/functions/runtimes/edge). Next.js Cache Components require Node.js. Check the deployed framework version and route type rather than applying one runtime rule to the whole application.

Choose a function region based on its dependency path. If a request makes several database calls, placing compute near users can make those calls slower; measure end-to-end latency and place compute near the authoritative data when those round trips dominate. Then verify connection limits, allowed regions, memory, and maximum duration for the selected plan and runtime.

Fluid Compute changes how function capacity is shared. With optimized concurrency for Node.js and Python, one instance can serve multiple invocations at once. Request-specific mutable module state can therefore race or leak between requests; keep request data local and use an external store for shared state. Measure costs using the current plan: active CPU, provisioned memory, invocation, and regional pricing rules can all matter. A streaming response may improve time to first byte while work continues; it does not remove duration, resource, or downstream-capacity limits.

## 3. Treat Caching as a Data-Correctness Rule

Incremental Static Regeneration (ISR) lets supported frameworks serve generated output and refresh it under configured revalidation rules. Revalidation makes content eligible for regeneration; it does not mean every client immediately sees the new value. Test the exact framework version, cache mode, and invalidation path used in production.

With Next.js Cache Components enabled, data is not automatically part of a shared cache merely because a component renders on the server. Cache only data that is safe to reuse, and define its lifetime and invalidation deliberately. Personal data needs cache keys and policies that preserve identity boundaries. A response header such as `Cache-Control: no-store` does not undo a private value that was already written to a framework data cache earlier in the request.

Authenticate revalidation webhooks, validate which bounded path or tag they may invalidate, and rate-limit them. For every private route, test cache behavior across sign-in, sign-out, account changes, and tenant changes. Image optimization has its own configuration: allow only intended remote sources, provide dimensions or a supported fill layout, and supply blur data for remote images when using a blur placeholder.

## 4. Make Scheduled Work Recoverable

A Vercel Cron Job invokes an HTTP endpoint on a schedule. Set `CRON_SECRET` to have Vercel send an authorization header, then verify it at the endpoint before doing work. The platform describes delivery as best effort: a run can be missed or delivered more than once, concurrent runs can overlap, and a failed invocation is not retried automatically.

Make each run safe to repeat. Derive a stable identity from the schedule period or work item, record completed work durably, and use a lock if overlapping runs would conflict. Query for work since the last successful run so a missed trigger can be recovered. If the job needs durable retries, long waits, or multi-step recovery, hand work to a queue or workflow rather than treating the cron request as the job itself.

## 5. Promote and Roll Back with the Data in Mind

Before production promotion, verify the commit, build checks, environment scope, migration order, and compatibility between old and new application versions. Promoting a preview to production can rebuild it using production environment variables; it is not always the same operation as pointing a domain at an unchanged preview build. Confirm the behavior for the chosen promotion path.

An instant rollback can repoint a production domain to a previous deployment without rebuilding it, so it does not pick up changed environment-variable values. It restores application code, not the previous database state or external side effects. Use expand-and-contract migrations when old and new code must coexist, and ensure the prior application version can read the current schema before relying on rollback.

| Decision | Evidence to check |
| ----------------- | -------------------------------------------------------------------------------- |
| Function region | End-to-end latency, database location, connection budget, and failover needs |
| Cache policy | Data sensitivity, cache key, lifetime, invalidation, and identity transitions |
| Preview safety | Environment variables, backing services, access protection, and side effects |
| Function capacity | Concurrent load, active CPU, provisioned memory, duration, and downstream limits |
| Release recovery | Schema compatibility, promotion behavior, rollback target, and external effects |

Use deployment logs to diagnose builds and runtime logs for server execution. Browser analytics and web-vitals help explain client behavior; they do not replace server traces or evidence from the database and external services.

## Summary

A Vercel deployment makes a versioned build available through managed routing and compute. Its real production behavior also depends on environment variables, data services, runtime and framework versions, and cache rules. Senior release decisions protect preview boundaries, place compute near its dependencies, make scheduled work repeatable, and verify that promotion or rollback is compatible with data already changed.

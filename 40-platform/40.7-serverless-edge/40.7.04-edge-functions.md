# Edge Functions

## Definition

An edge function is a serverless compute unit that runs in a CDN edge location (Point of Presence) rather than a centralized cloud region. Some runtimes use V8 isolates; others use different execution environments. Startup latency, available APIs, and resource limits depend on the provider, configuration, and workload.

> **Textbook Definition:** An edge function executes application logic in a provider's distributed serving locations, subject to runtime, resource, routing, and data-access constraints that differ from centralized regional compute.

## First Principles

An edge location can avoid a long trip to the application's origin only when it has enough trustworthy information to make the decision locally. If it must call a remote database first, that trip remains part of the request. Geography therefore changes the placement of work, not the authority of its data.

Different locations can observe different cached values. A personalized cache key must include the right identity/variant or avoid shared caching entirely. A globally replicated store is not automatically an atomic wallet, rate limiter or session-revocation authority.

## Place logic and state deliberately

```text
client -> distributed ingress/Worker -> local public asset/cache
                                  -> selected regional data/service authority
```

Good local decisions include a public redirect map, locale routing, verified token signature or serving immutable public content. Current account revocation and tenant authorization can still require an authoritative lookup. The backend must prevent bypass of any relied-on edge check.

Compare full latency as client-to-edge, edge compute, dependency round trips and streaming/body completion. Startup, CPU time and elapsed duration are distinct measurements. Requests do not necessarily execute in the user's city; routing/placement choices and available regions determine location.

## Providers have different runtime contracts

| Platform | Execution and boundary |
| -------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Cloudflare Workers | V8 isolates with Web APIs, configured Node compatibility and service bindings; check CPU/memory/subrequest limits. |
| Vercel | Node.js is recommended for new server-side work; Edge Functions are deprecated for new projects. In Next.js 16, `proxy` cannot use the Edge runtime; route-segment support and Cache Components have separate constraints. Verify the selected framework and deployment path. |
| Lambda@Edge | CloudFront trigger-specific request/response processing with deployment, runtime and quota restrictions. |
| CloudFront Functions | A distinct constrained request/response runtime, not a generic Node function or interchangeable Worker. |

Do not combine an invocation timeout from one provider with CPU limits from another. Node compatibility in Workers covers supported APIs; it does not turn an isolate into an arbitrary persistent Node process. Lambda@Edge also differs from regional Lambda in configuration and event contracts.

## A small Worker with explicit routing

This standalone example makes no authentication or persistence claims. Generate runtime types from the accompanying configuration and include them in the TypeScript project. `nodejs_compat` is unnecessary for this Web-API-only handler; add it deliberately when a dependency requires supported Node APIs.

```jsonc
// wrangler.jsonc
{
  "$schema": "./node_modules/wrangler/config-schema.json",
  "name": "edge-hello",
  "main": "src/index.ts",
  "compatibility_date": "2026-10-10",
  "observability": { "enabled": true, "head_sampling_rate": 0.1 }
}
```

```typescript
// src/index.ts
export default {
  async fetch(request) {
    const path = new URL(request.url).pathname;
    if (path !== '/api/hello') return new Response('Not found', { status: 404 });
    if (request.method !== 'GET') {
      return new Response('Method not allowed', { status: 405, headers: { allow: 'GET' } });
    }
    return Response.json({ message: 'Hello from the edge' },
                         { headers: { 'cache-control': 'no-store' } });
  },
} satisfies ExportedHandler<Env>;
```

```bash
npm install --save-dev wrangler typescript
npx wrangler types
npx tsc --noEmit
npx wrangler deploy --dry-run
npx wrangler dev
```

A compatibility date selects runtime behavior; it is not a promise to always run the newest behavior. Advance it through regression tests. A local dry run packages code and checks configuration; it does not prove deployed routing, global latency or production authorization.

## Cache reusable public content, not arbitrary requests

Cloudflare's Cache API is local to a data center; inserting into it does not synchronously populate every location. Workers KV is eventually consistent and may cache both existing and missing values. Neither is a cross-location atomic counter or immediate revocation mechanism.

Cache only eligible methods/statuses and explicit public representations. Include query/variant dimensions required by the response and handle `Vary`, `Set-Cookie`, authorization and invalidation deliberately. A path-only key can mix language, pagination or account-specific responses. A generic “fetch request, cache clone” example is unsafe for a protected API.

The [SPA deployment chapter](40.7.10-vite-spa-cloudflare-workers.md) is the canonical streaming proxy example. Its configured target prevents the caller choosing an arbitrary upstream. Service bindings are preferable for Worker-to-Worker calls where available. Keep cookies, redirects and trusted ingress headers explicit rather than forwarding spoofed identity metadata.

## Authenticate and authorize at the correct boundary

Verify token signature with an allowed algorithm/key and validate issuer, audience, expiration and relevant time constraints. A signature alone does not establish tenant permission or current revocation. Key rotation needs a cache/refresh policy. Use reviewed libraries; an example verifier returning true is not a complete security policy.

A replicated denylist may be stale immediately after logout. Choose a tolerable token lifetime or consult a suitable authority for critical operations. Avoid caching authenticated responses in a public cache as an accidental optimization. Fail closed for protected operations when verification fails; returning an unchecked origin request would bypass the boundary.

For A/B testing, a random assignment is acceptable only for a non-security experiment, but validate the allowed cookie values and set a documented persistence policy. Segment identity affects cache variation. Geolocation metadata comes from a trusted ingress/helper, not the removed `NextRequest.geo` field or arbitrary caller header.

## Durable Objects supply a scoped authority

A Durable Object gives one addressable object an authority for its state and coordination. It is useful for a room, coordinator or counter whose updates must serialize. It does not put the same mutable object independently in every edge location.

Use the current `DurableObject` base class, generated namespace types, configured migration and supported transactional storage. Process memory is a cache, not the durable source. An increment that commits then loses its response still needs a stable operation ID if a retry must not increment twice. A mutex or object identity alone does not establish idempotency.

Avoid holding one global object for an unrelated high-volume workload: it becomes a contention boundary. Choose object keys from the domain invariant, consider lifecycle/eviction and bound fan-out. KV suits replicated read-heavy data; Durable Objects suit scoped coordination. D1 and R2 have separate SQL/object contracts and should not be treated as interchangeable state stores.

## Background work and recovery

Await essential effects before reporting success. `ctx.waitUntil()` can extend bounded post-response work, but it is not a durable queue or workflow and does not guarantee retry after process failure. Pass the method through its context rather than destructuring it, and handle failures according to the effect's importance.

For durable jobs, enqueue a stable, serializable command and use a receiver with an explicit retry/dead-letter policy. Stream large bodies instead of buffering unbounded text. Bound upstream deadlines, subrequests and per-client output queues. Keep mutable request data out of module scope because instances can serve multiple requests.

## Mistakes and best practices

Do not substitute a local cache for global consistency, advertise a universal latency number, or copy unsupported Next.js Edge routes. Choose the authority before selecting storage, then type bindings, inspect config/schema and test runtime compatibility. Logs need correlation and sensitive-data controls; sampling also means a missing log is not proof that an operation never occurred.

## Summary

Edge functions move suitable work closer to ingress while authoritative state remains explicit. Provider runtime and routing contracts differ and change. Correct cache keys, verified identity, scoped durable authority and bounded streaming preserve correctness; an edge location by itself guarantees none of them.

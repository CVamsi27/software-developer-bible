# Edge Functions

A request for public documentation can be answered from a nearby cache. A request for an account balance cannot safely use the same shortcut: it may need current identity, permissions, and data from a regional authority. Moving code closer to the user helps only when the work and information it needs are also suitable for that location.

## Definition

An edge function is managed code invoked on a provider's distributed network, often near request ingress. Providers offer different runtime application programming interfaces (APIs) and routing models; "edge" does not promise that code runs in the user's city, has Node.js APIs, or can reach authoritative data without another network trip. Some providers use V8 isolates: lightweight, separately sandboxed JavaScript execution contexts, not full general-purpose machines or ordinary Node.js processes.

> **Textbook Definition:** Edge computing places application computation on distributed infrastructure near data sources or request entry points. An edge function is a provider-managed unit of that computation, constrained by its placement, runtime, resource limits, routing contract, and access to state.

## First Principles

The request still follows a path: client to execution location, computation, any cache or service lookup, then response. Edge placement shortens only the parts of that path the provider can execute locally. A remote database call can dominate the time saved by moving a few lines of code closer to ingress. The origin is the application server or data service that ultimately owns or produces the response.

```text
client -> provider routing/cache/function
                       ├── safe local decision or cache hit -> response
                       └── origin or data authority -> response
```

For `GET /de/docs/caching`, an edge handler can choose an allowed language route and serve a versioned public page from a populated local cache. For `GET /api/accounts/42`, it may validate a signed token, but the account service still checks current tenant permission and reads the authoritative balance. If that service is in another region, its network trip remains on the request path.

The provider decides which locations can execute the function and which request stages invoke it. Measure time to first byte and total completion time with real dependencies; "globally distributed" is not a latency guarantee.

## How It Works

### 1. Put Only Suitable Decisions Near Ingress

Small, repeatable decisions often fit well: normalize a URL, choose a language route, validate a token's signature, apply a cache policy, or serve immutable public content. These decisions can avoid a regional application round trip when they do not need fresh private state.

A signature proves that a token was issued by a trusted signer and has not been altered. It does not prove that an account is still active, that a role has not changed, or that the caller may access a particular tenant's record. For sensitive operations, consult the appropriate authority and authorize again at the data-owning service. The origin must also reject requests that bypass an edge check the system relies on.

### 2. Choose the Provider Contract, Not Just the Label

"Edge function" is a placement category, not one portable runtime. The limits below are part of the design contract; check the live platform documentation and deployed framework version before choosing a feature.

| Provider surface | Useful contract | Boundary to remember |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Cloudflare Workers | Web APIs in V8 isolates; optional supported Node.js APIs | Not a persistent Node.js process. Runtime compatibility and processor (CPU), memory, and outbound subrequest limits depend on configuration and plan. |
| Vercel Edge runtime | Web-API-oriented runtime for supported Vercel Function routes | Vercel recommends Node.js; the standalone Edge Functions product is deprecated, but the runtime remains available. Next.js 16 Proxy uses Node.js. |
| Lambda@Edge | CloudFront viewer- and origin-request/response hooks using Node.js or Python | Create a numbered function version in `us-east-1`; virtual private cloud (VPC) access, custom environment variables, and Lambda layers are unsupported. |
| CloudFront Functions | Small JavaScript handlers for viewer-request/response tasks such as redirects and cache-key changes; JavaScript runtime 2.0 can use CloudFront KeyValueStore | No request body, arbitrary network, filesystem, or environment APIs; use Lambda@Edge when those capabilities or origin events are needed. |

Cloudflare's `nodejs_compat` enables a documented subset of Node.js APIs; it does not make unsupported libraries, native modules, or process assumptions work automatically. A local build or dry run can check types, packaging, and configuration, but it cannot prove deployed routing, production authorization, or latency from every region.

### 3. Match the State Store to Its Consistency Needs

An ordinary Worker can run on different instances and locations. Module memory is useful for data that can be discarded, such as a reusable client or local optimization; it is not shared durable state. A deployment restart, eviction, or request routed elsewhere can lose or miss it.

Cloudflare exposes more than one cache contract. The Workers Cache API is local to the data center handling the request; writing a response there does not synchronously populate every location. Cloudflare's separate Workers Caching behavior has different rules and can collapse concurrent misses so one origin fetch serves waiting requests. Treat neither as a globally consistent database. Build cache keys from the representation — such as language and content version — and never let a public URL key select a personalized response.

Workers KV (key-value storage) suits read-heavy data that tolerates propagation delay. It is eventually consistent, and reads of missing keys can also be cached. It is therefore a poor authority for immediate logout/revocation, atomic counters, or competing writes that must not be lost.

A Durable Object is a globally addressable instance with private persistent storage and a single-threaded event loop. Route related work — such as one chat room or one account's coordination state — to the same object. Its storage is strongly consistent, so completed writes are visible to later reads through that object; Cloudflare recommends SQLite-backed storage for new namespaces. This gives one key a clear coordination authority, but it does not make a multi-step async handler transactional and it does not scale a single hot key horizontally. Shard by the domain invariant instead of funneling an unrelated high-volume workload through one object.

Single-threaded does not mean every asynchronous handler is atomic. When a handler awaits network I/O, another event can run before it resumes. Use a storage transaction or an input gate for the invariant that must not interleave. Persist state that must survive eviction or deployment, and give retryable operations stable IDs: a committed increment whose response was lost must not be applied twice when the caller retries. Choose D1 or R2 for their database or object-storage contracts rather than treating every Cloudflare binding as interchangeable.

### 4. Make Cache and Identity Boundaries Explicit

Cache only representations that are safe to share. Define which request dimensions affect the response, how long an entry remains valid, and how changes invalidate it. A path-only key may mix languages or versions; a user-specific result should not enter a public cache. Provider behavior for `Authorization`, cookies, `Vary`, and cache purges differs, so test the actual route and cache layer.

When verifying a token at the edge, allow only the expected algorithm and key; validate issuer, audience, expiry, and other required claims. Plan key rotation and revocation separately. A replicated denylist can be stale. If the operation needs immediate revocation or current tenant membership, call the authoritative service or use short-lived credentials with a documented risk window. Do not trust a caller-supplied identity or geography header; use metadata added by a trusted ingress and prevent clients from spoofing it.

### 5. Keep Background Work Recoverable

Await an effect before responding when the response depends on its completion. Cloudflare `ctx.waitUntil()` lets bounded work continue after a web response, currently up to 30 seconds after the response is sent or the client disconnects. The runtime cancels work that exceeds that window, so it is appropriate for work such as analytics or a cache write — not as a durable job guarantee.

If the work must complete, retry, or survive a runtime failure, enqueue a durable command and let a queue consumer apply an explicit retry and dead-letter policy. Use stable operation IDs for non-idempotent effects. Stream large request bodies rather than buffering them without a bound, and cap upstream deadlines and per-client queues so one slow dependency cannot consume unbounded resources.

For Cloudflare Workers, pin a `compatibility_date` and review compatibility flags. Advance the date through regression tests because it opts the Worker into runtime changes; it does not mean an old date is automatically moved forward. Test the built configuration locally, then verify the deployed route, bindings, authorization boundary, and dependency path in the target environment.

The [Vite SPA on Cloudflare Workers chapter](40.7.10-vite-spa-cloudflare-workers.md) is the canonical example of a streaming proxy. Its configured upstream prevents a caller from choosing an arbitrary destination; Worker service bindings are another option for Worker-to-Worker calls.

| Decision | Verify before release |
| -------------------- | ------------------------------------------------------------------------------ |
| Place logic at edge | End-to-end dependency latency, runtime APIs, and routing stage |
| Cache a response | Public/private status, key dimensions, lifetime, and invalidation behavior |
| Use KV | Tolerated propagation delay, cached misses, write contention, and recovery |
| Use a Durable Object | Coordination key, transaction boundary, hot-key capacity, and restart recovery |
| Defer work | Whether losing it is acceptable; otherwise use a durable queue/workflow |

Sampled logs can help explain a request, but a missing log does not prove that an operation never ran. Correlate edge and origin traces while avoiding secrets and personal data in logs.

## Summary

Edge execution is useful when a small decision or reusable response can be made near ingress without compromising data authority. Provider runtimes and event stages are not interchangeable. Cache only safe representations, choose state by its consistency contract, recheck sensitive authorization at the authoritative boundary, and use durable queues for work that must survive execution limits.

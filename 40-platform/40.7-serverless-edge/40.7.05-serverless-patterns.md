# Serverless Patterns

## Definition

Serverless patterns combine triggers, managed compute, queues, storage, and orchestration to solve recurring coordination problems. Their value comes from an explicit failure contract, not from wiring several managed services together.

> **Textbook Definition:** Serverless architecture patterns coordinate managed compute, event sources, queues, storage, and orchestration services under explicit delivery, concurrency, failure, and cost contracts.

## First Principles

One process cannot safely hold a multi-day operation in memory. Splitting the operation into shorter tasks avoids that lifetime dependency, but introduces a new gap: a task may commit its effect and lose the acknowledgment. A queue can redeliver the command, while a workflow can remember completed steps; neither automatically knows whether an external payment happened. Persist command identity, authoritative outcomes, and recovery state at the boundaries that actually commit effects.

## Choose the coordination contract

| Need | Pattern | Responsibility that remains |
| -------------------------- | ---------------------------------------- | ------------------------------------------------------- |
| Immediate bounded response | Gateway → function | Authentication, validation, deadline, data authority |
| Buffered work | Queue → bounded consumers | Safe redelivery, backlog budget, dead-letter recovery |
| Independent subscribers | Topic/bus → subscriber queues | Per-subscriber delivery and failure policy |
| Multi-step decisions/waits | Durable orchestrator → tasks | Idempotent tasks and uncertain-outcome reconciliation |
| Read-optimized view | Authoritative write + outbox → projector | Lag, version ordering and rebuildability |
| Parallel chunks | Manifest → workers → completion records | Unique chunk completion and final aggregation condition |

Synchronous service calls can be appropriate when the caller needs a bounded result. Queues change the latency and completion contract; they are not automatically superior. A dead-letter queue retains unresolved work but needs alerts, ownership, and a replay plan.

## Trace an order from acceptance to a recoverable effect

The API validates identity and input, then commits the order and an outbox record in one transaction. It returns an accepted operation identity. A relay publishes that record; a crash can cause publication to repeat, so consumers retain the same business command ID.

```text
order + outbox commit → relay → queue → worker → durable effect/result
                            retry ↘ same command identity ↗
```

A transport message ID is not always the business operation ID: republishing the same order can create a different message. Namespace a stable key such as tenant/order/payment-attempt and compare its input identity. Do not silently accept the same key with a different amount. A durable receipt can make a committed database change retry-safe; an external receiver must enforce its own operation key or support reconciliation.

## A focused Standard SQS partial-batch handler

This example isolates the batch algorithm from application processing. The supplied `processRecord` must validate the command and establish durable idempotency before making side effects. Install `@types/aws-lambda`. On the **event-source mapping**, enable `FunctionResponseTypes: [ReportBatchItemFailures]`; returning this object alone does not enable the feature.

```typescript
import type { SQSBatchResponse, SQSEvent, SQSRecord } from 'aws-lambda';

export function standardBatchHandler(
  processRecord: (record: SQSRecord) => Promise<void>,
): (event: SQSEvent) => Promise<SQSBatchResponse> {
  return async (event) => {
    const batchItemFailures: SQSBatchResponse['batchItemFailures'] = [];
    for (const record of event.Records) {
      try {
        await processRecord(record);
      } catch {
        batchItemFailures.push({ itemIdentifier: record.messageId });
      }
    }
    return { batchItemFailures };
  };
}
```

For an independent Standard-queue batch A/B/C, if B fails, the handler returns B's transport ID and continues C. Configure visibility timeout around the actual function/batch/retry budget. A crash after A's effect but before the batch response can still redeliver A.

FIFO needs an ordering-aware handler. The conservative documented approach stops after the first failure and reports that failed record **plus all unprocessed records**; processing C after a failed B can violate order. FIFO deduplication has a finite service window and does not make an external charge exactly once.

## Publication acknowledgments are part of the protocol

An EventBridge `PutEvents` request can return successfully while individual entries fail. Inspect `FailedEntryCount` and per-entry error fields, retry eligible failed entries with stable event identity, and alert on permanent failures. A successful HTTP response is not proof that every event was accepted. Also verify bus/target configuration and delivery metrics.

SNS fan-out to separate SQS queues provides buffering and independent subscriber backlogs. A single queue has competing consumers rather than one copy for every consumer. Services have distinct retention, ordering, retry, and replay capabilities; configure the chosen contract instead of assuming a topic is always a durable log.

## Orchestration and compensation resolve different failures

A workflow records which tasks were requested and completed, waits durably, and retries by policy. Separate retryable transport failures from business rejection. Step Functions Standard and Express have different duration/execution contracts; a Lambda task remains subject to Lambda's own invocation limit.

After stock reservation and payment capture, a shipping timeout can mean the shipment exists but its acknowledgment was lost. Query the shipping authority before dispatching again or refunding. Compensation is a new business operation, not a database rollback: it can fail, need a distinct stable key, or require manual resolution. Persist reconciliation/compensation state; a process-local array and `catch(console.error)` do not provide a recoverable saga.

The [durable execution chapter](40.7.07-durable-execution-temporal-inngest.md) owns replay, signal, timer, and activity examples. The microservices chapters own saga and transactional-outbox implementation. This chapter explains how provider delivery surrounds those mechanisms.

## Derived views and fan-in need durable completion conditions

For command/query separation, commit the authoritative mutation and publication intent together. A projector handles duplicate/out-of-order events under a version policy and tracks lag. A query may show an older view; expose that state when users need read-after-write confirmation. Event sourcing is a separate choice to make events the authority, with replay/schema evolution requirements.

For parallel processing, persist the expected chunk manifest and one completion/result per chunk ID. Retried chunk 7 must not count twice. Aggregate only after the required unique completions exist and an atomic finalization claim succeeds. Missing/failed chunks need timeouts and recovery; counting in process memory cannot survive replacement.

## Decisions, mistakes and best practices

Keep input sizes, consumer concurrency, database connections, queue age and retry budgets bounded. Propagate command/trace identities without logging secrets. Replays use original business identity, so define how expired deduplication retention changes safety. Test duplicate delivery, acknowledgment loss, poison records, partial batches, stalled publication, and uncertain external outcomes separately.

Do not equate queue visibility with extra function runtime, a successful publish call with accepted entries, or compensating work with an atomic rollback. Prefer one focused executable mechanism and link its neighboring authority rather than duplicating incomplete provider snippets.

## Summary

Choose patterns from delivery and recovery needs. Atomic publication intent closes the write/publish loss gap; stable business identity protects redelivery; partial-batch handling preserves useful progress. Orchestration records coordination, while authoritative receivers and reconciliation decide what actually happened.

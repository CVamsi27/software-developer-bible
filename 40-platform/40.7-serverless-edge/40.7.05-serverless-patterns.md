# Serverless Patterns

A checkout request can save an order and crash before publishing its event. Publishing first can create an event for an order that never committed; publishing after the database commit can lose the event if the process stops in between. Later, a payment can succeed while its response is lost, leaving a retry unsure whether to charge again. These are separate failure boundaries, so the design needs durable intent, stable operation identity, and an explicit recovery path.

## Definition

Serverless patterns are reusable ways to coordinate managed functions, messages, storage, and workflows when no single process owns the whole operation. A pattern defines who starts each step, what state is durable, how delivery and retries work, and how the system recovers when an acknowledgment is missing.

> **Textbook Definition:** A serverless architecture pattern composes managed compute and infrastructure services around explicit delivery, concurrency, persistence, failure, and cost contracts. The pattern is correct only when its retry and recovery behavior preserves the application's invariants.

## First Principles

The database, message broker, and payment provider do not share one atomic transaction. At every boundary, work may commit while its acknowledgment is lost. Treat repeated delivery and uncertain outcomes as normal cases unless the specific provider contract guarantees otherwise. Give each business operation a stable identity, persist what has happened, and reconcile with the system that owns the result before repeating an irreversible effect.

Choose the coordination contract from the user-visible requirement:

| Need | Pattern | Responsibility that remains |
| ---------------------------------------------- | ---------------------------------------- | ----------------------------------------------------------- |
| Bounded result before replying | Gateway → function | Authentication, validation, deadline, and data authority |
| Work may finish after the request | Queue → bounded consumers | Safe redelivery, backlog budget, and dead-letter recovery |
| Independent subscribers need their own backlog | Topic or event bus → subscriber queues | Per-subscriber delivery, ordering, and replay policy |
| Work spans decisions, waits, or retries | Durable orchestrator → tasks | Idempotent effects and uncertain-outcome reconciliation |
| Reads need a different shape from writes | Authoritative write + outbox → projector | View lag, version ordering, and rebuildability |
| One job can be split into independent parts | Manifest → workers → completion records | Unique part completion and a durable finalization condition |

Synchronous calls remain appropriate when a caller needs a bounded answer. A queue changes when the answer is available; it is not automatically safer or faster. A dead-letter queue stores messages that exhausted their retry policy, but people still need to alert on, inspect, and safely replay them.

## How It Works

### 1. Commit the Order and Its Publication Intent Together

The transactional outbox closes the database-to-broker gap. In one database transaction, the application programming interface (API) validates the caller and writes both the order and an outbox row that represents the event it intends to publish. It can then return the durable order identity. A separate relay reads pending rows and publishes them.

```text
order + outbox row commit → relay → queue → worker → durable effect/result
                                 retry ↘ same business command identity ↗
```

The relay can publish an event and crash before recording that it did so. It will publish again after restart. That is safe only when consumers recognize the same business operation. A transport message ID may change when an event is republished, so use a stable key such as tenant, order, and payment-attempt ID. Bind that key to the input: the same key with a different amount or account is a conflict, not a replay to silently accept.

For a database effect, store the idempotency decision and business change in the same transaction. For an external payment or shipping service, use a key the receiver enforces or query that service's authoritative result before retrying. The outbox prevents a lost publication; it does not make the external effect exactly once.

### 2. Retry Only Failed Queue Records

Amazon Simple Queue Service (SQS) can deliver messages to a Lambda function in batches. Standard queues provide at-least-once delivery, so consumers must expect duplicates. By default, one processing failure can also make the whole batch visible again, including records whose effects already succeeded. For a Standard queue, a partial-batch response lets the function identify the records that need another attempt.

This handler isolates the batch algorithm from application logic. `processRecord` must validate the command and make its effects retry-safe. On the event-source mapping, enable `FunctionResponseTypes: [ReportBatchItemFailures]`; returning this object without enabling the mapping option does not activate partial responses. This minimal handler treats every thrown error as retryable; production code should emit sanitized diagnostics and use the queue's redrive policy to stop poison-message loops. Install `@types/aws-lambda` for the types below.

```typescript
import type { SQSBatchResponse, SQSEvent, SQSRecord } from 'aws-lambda';

export function standardBatchHandler(
  processRecord: (record: SQSRecord) => Promise<void>,
): (event: SQSEvent) => Promise<SQSBatchResponse> {
  return async (event) => {
    const batchItemFailures: SQSBatchResponse['batchItemFailures'] = [];
    for (const record of event.Records) {
      try {
        await processRecord(record);
      } catch {
        batchItemFailures.push({ itemIdentifier: record.messageId });
      }
    }
    return { batchItemFailures };
  };
}
```

For a Standard-queue batch A/B/C, if B fails, the handler reports B and can continue with C. If the function crashes after A's effect but before returning the batch response, A can still be delivered again; idempotency remains necessary. Configure the queue's visibility timeout to allow the full batch attempt and retries. AWS recommends at least six times the function timeout, plus the maximum batching window when one is configured.

First-In, First-Out (FIFO) queues preserve order within a message group. A `MessageGroupId` defines that ordered stream: records in one group do not process concurrently, while independent groups can progress in parallel. With partial-batch reporting, stop after the first failure and return that failed record and all unprocessed records; processing C after B fails can violate the group's order. SQS FIFO deduplication only suppresses a repeated send ID during its five-minute deduplication window. It does not prevent a consumer from repeating an external charge after that window or after losing the result.

### 3. Verify Publication and Fan-Out Acknowledgments

An Amazon EventBridge `PutEvents` call can return success while individual entries fail. Inspect `FailedEntryCount` and each entry's error, retry eligible failures with the same business identity, and alert on permanent failures. There is a more subtle configuration case: publishing to a nonexistent event bus can return status 200 without incrementing `FailedEntryCount`, while the event is dropped. Verify the bus name and rule/target path, then monitor delivery beyond the producer response.

Amazon Simple Notification Service (SNS) can fan a notification out to separate SQS queues, giving each subscriber its own buffer and retry backlog. The queue policy must allow the intended topic to send messages. Multiple consumers reading one queue instead compete for messages; each message is normally processed by one consumer, not copied to all of them. Choose a topic or bus for distribution and queues for independent buffering, then define each subscriber's retention, failure, and replay policy.

### 4. Use Workflows for Coordination, Not as Proof of Remote Effects

An orchestrator durably records which tasks it scheduled and which results it observed. It can make waits, branching, retry policy, and operator inspection explicit, but it cannot atomically commit its own history with an external provider. If a payment task times out after the provider accepted the charge, query the payment authority or reuse its idempotency key before issuing another charge.

Amazon Web Services (AWS) Step Functions has two workflow types with different execution contracts. Standard workflows support auditable executions up to one year and execute a task once by default; a configured `Retry` can run that task again. Express workflows last up to five minutes: asynchronous executions are at-least-once and can repeat, while synchronous executions are at-most-once and are not automatically repeated. Choose based on duration, audit needs, throughput, and tolerance for repeats or lost execution — not on a label such as "serverless." A Lambda task still obeys Lambda's own invocation timeout.

Compensation is a new business operation, not a database rollback. If stock was reserved and payment captured before a shipping timeout, first check whether the shipment exists. A refund or inventory release can itself fail, require its own stable key, or need human resolution. Persist the reconciliation and compensation state instead of keeping it in process memory. The [durable-execution chapter](40.7.07-durable-execution-temporal-inngest.md) owns replay, timers, signals, and activity examples; the microservices chapters cover saga and outbox implementations in more depth.

### 5. Make Derived Views and Parallel Work Rebuildable

Command Query Responsibility Segregation (CQRS) keeps the authoritative write model separate from a read model shaped for queries. Publish the change through the outbox, then let a projector update the view. The view may lag, and duplicate or out-of-order events need a version policy. Tell users when a read is eventually consistent; rebuild the projection from its durable source when its state is wrong.

For parallel processing, persist the expected chunk manifest and one result per chunk ID. A retry of chunk 7 must not count as a second completion. Aggregate only when the required unique results exist and an atomic finalization claim succeeds. Give missing or failed chunks a timeout and recovery path; in-memory counters disappear when a worker is replaced. Event sourcing is a separate choice: it makes the event history authoritative and brings its own replay and schema-evolution requirements.

Across these patterns, bound input size, consumer concurrency, downstream connections, queue age, and retry budgets. Carry command and trace identities through logs without recording secrets. Exercise duplicate delivery, poison messages, lost acknowledgments, stalled outbox relays, partial batches, and uncertain external outcomes as distinct failure tests.

## Summary

Choose a serverless pattern from the delivery and recovery contract. The transactional outbox makes publication intent durable with the business write; stable command identity makes repeated delivery safe; partial-batch handling limits unnecessary retries; and workflows persist coordination. Only the authoritative receiver or a reconciliation check can establish what an external effect actually did.

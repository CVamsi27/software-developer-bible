# Serverless Frameworks (SAM, CDK, SST, Serverless Framework)

## Definition

Serverless frameworks describe functions and their surrounding infrastructure as code. They generate resources, package handlers, and coordinate lifecycle operations; the generated system still obeys the provider's IAM, event, networking, and storage contracts.

> **Textbook Definition:** A serverless framework translates application-oriented declarations of compute and event infrastructure into deployable resources, coordinating configuration and lifecycle operations over underlying provider services.

## First Principles

A handler cannot serve an API without routing, permissions, packaging, and configuration. Describing that topology once reduces manual setup drift, but an abstraction can generate a wrong permission or resource just as consistently as a correct one. Inspect the generated plan and test the actual event/runtime boundary before treating a typed declaration as a working application.

## Distinguish infrastructure from application runtime

SAM, CDK, Serverless Framework and SST manage deployment resources. Next.js/Nitro adapters also translate application routing/rendering semantics into deployable outputs. These are different layers: choosing an IaC tool does not make a framework's cache or request APIs portable.

| Tool | Underlying deployment model | Useful distinction |
| -------------------- | ----------------------------------------------------------------------------- | -------------------------------------------------------------------- |
| AWS SAM | Serverless transform over CloudFormation | YAML/JSON plus packaging and local invocation tools |
| AWS CDK | Language constructs synthesize CloudFormation | Inspect synthesized resources and assertion-test critical policy |
| Serverless Framework | Provider/plugin-specific packaging and deployment; verify the installed major | Current licensing, authentication, plugins and target support matter |
| Current SST | Pulumi engine and provider integration, including bridged Terraform providers | Resource linking and development mode; current SST is not CDK-based |

Historical SST/CDK recipes and Serverless Framework v3 configurations need explicit version labels. Do not choose a current tool from an old multi-cloud comparison table. Pin the actual CLI, libraries, plugins and lockfile; SAM's transform identifier is not the CLI version.

## One complete SAM deployment shape

This synthetic read-only HTTP handler reuses the canonical API Gateway version-2 handler from the [Lambda chapter](40.7.02-aws-lambda.md). Save/compile that handler into `dist/index.js` first. The template connects its actual handler and event contract; it intentionally grants no database permissions.

```yaml
AWSTemplateFormatVersion: '2010-09-09'
Transform: AWS::Serverless-2016-10-31
Resources:
  ExampleFunction:
    Type: AWS::Serverless::Function
    Properties:
      CodeUri: dist/
      Handler: index.handler
      Runtime: nodejs22.x
      MemorySize: 256
      Timeout: 5
      Events:
        GetExampleUser:
          Type: HttpApi
          Properties:
            Path: /users/{id}
            Method: GET
```

Confirm the selected runtime remains supported in your deployment region. Compile bundled dependencies for that architecture/runtime. `sam validate` checks the template; `sam local invoke` needs a matching HTTP API v2 fixture and can use Docker. Local invocation does not verify live IAM, routing, account quotas, or actual managed event retries.

## A CDK declaration with the same boundary

This complete construct is the infrastructure layer only. It uses the compiled `dist/index.js` from above; an application entry point must instantiate it. There is no fictional methods object or absent TypeScript handler path.

```typescript
import { Duration, Stack, type StackProps } from 'aws-cdk-lib';
import { Construct } from 'constructs';
import { Code, Function, Runtime } from 'aws-cdk-lib/aws-lambda';
import { HttpApi, HttpMethod } from 'aws-cdk-lib/aws-apigatewayv2';
import { HttpLambdaIntegration } from 'aws-cdk-lib/aws-apigatewayv2-integrations';

export class ExampleStack extends Stack {
  constructor(scope: Construct, id: string, props?: StackProps) {
    super(scope, id, props);
    const fn = new Function(this, 'ExampleFunction', {
      code: Code.fromAsset('dist'),
      handler: 'index.handler',
      runtime: Runtime.NODEJS_22_X,
      timeout: Duration.seconds(5),
    });
    const api = new HttpApi(this, 'ExampleApi');
    api.addRoutes({
      path: '/users/{id}', methods: [HttpMethod.GET],
      integration: new HttpLambdaIntegration('ExampleIntegration', fn),
    });
  }
}
```

Synthesis can assert the route, handler, runtime, and least-privilege permissions without deploying anything. A passing type check does not establish that the packaged file exports the handler or that the runtime can load its dependencies.

## Current SST and Serverless Framework need their own contract

Current SST uses resource linking to give supported handlers access to declared resources and manages provider-backed state through its deployment engine. Development mode can invoke local code while connected to real cloud resources; isolate those stages and credentials. Follow the installed version's component API rather than mixing CDK constructs with current `sst.aws` declarations.

For Serverless Framework, inspect generated IAM and package outputs, configure distinct stages/resources, and verify the current major's authentication/licensing requirements. Offline behavior comes from the installed plugin and configuration; `serverless offline` is not an automatic emulator built into every installation. Provider support is a versioned/plugin contract, not a universal portability promise.

## Preview a change before committing infrastructure effects

Read the synthesized template/change set or provider plan for destructive replacements, wildcard permissions, public ingress and secret exposure. `cdk diff` compares intended deployment changes; it is not by itself complete live-resource drift detection. CloudFormation drift detection has its own supported-resource limitations. SAM can contain ordinary CloudFormation resources; mixing them is not inherently a mistake.

Protect stateful resources with the appropriate retention/deletion settings and tested backups. Termination protection can prevent stack deletion but does not block every resource replacement. A stage name alone is not account-level isolation. Use reviewed environment boundaries, scoped identities, and a rollback path compatible with current data.

## Decisions and best practices

Choose from provider scope, team language, generated-plan transparency, component maturity, local fidelity, cost, and recovery ownership. Prefer one clear owner per resource/state store; several frameworks can coexist if ownership boundaries are explicit. Test handlers, generated infrastructure and deployed boundaries at their different levels. Local success is useful evidence, but release checks must cover the provider contracts it cannot emulate.

## Summary

Frameworks reduce repeated infrastructure wiring without removing resource ownership or runtime contracts. Current SAM/CDK/SST/Serverless Framework use different engines and development models. Inspect generated resources, verify packaged handlers, pin tool versions, and test permissions/events and rollback at the actual deployment boundary.

# Serverless Frameworks (SAM, CDK, SST, Serverless Framework)

A function that passes unit tests can still fail in production because nothing routes requests to it, its role cannot read the required table, or the deployed package uses a different runtime. Infrastructure as code (IaC) describes those resources beside the application so the deployment can create and update them repeatably. A framework helps write that description; it does not replace the cloud provider's resource, permission, or runtime rules.

## Definition

In practical terms, a serverless framework takes declarations such as “run this handler for `GET /users/{id}`” and turns them into a deployable function, route, permissions, and supporting resources. Some use configuration files, some use general-purpose code, and some add development workflows or higher-level resource linking.

> **Textbook Definition:** A serverless framework is an IaC tool that translates application-level declarations of functions, events, permissions, and supporting services into provider-specific deployment artifacts, then coordinates packaging and lifecycle operations against the provider's infrastructure control plane.

## First Principles

A handler is only application code. To serve a request, it also needs a route, an invocation permission, a runtime, a package, and configuration. The framework describes these pieces and emits deployment artifacts; the provider then creates resources and later invokes the packaged handler. Each transition can fail independently. A valid declaration is not proof that the permission is narrow, the artifact contains the handler, or the deployed event matches the handler's expected shape.

## Choose the abstraction whose output your team can own

These tools overlap in deployment work, but they do not produce the same interface or state model:

| Tool | What you author and what it deploys | Useful when |
| ----------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| AWS Serverless Application Model (SAM) | YAML/JSON shorthand plus AWS CloudFormation resources; CloudFormation is AWS's declarative infrastructure deployment service, and the SAM transform expands shorthand into its templates. | The application targets AWS and the team prefers templates with the SAM CLI's build and local-test commands. |
| AWS Cloud Development Kit (CDK) | Constructs in TypeScript, Python, Java, or another supported language; synthesis produces a CloudFormation cloud assembly. | The team needs reusable code abstractions and is willing to review synthesized templates and maintain CDK bootstrap resources. |
| Serverless Framework | A service configuration and plugins; the current v4 AWS provider packages functions and deploys their resources through CloudFormation. | Function- and event-centered configuration fits the service, and the team accepts the current version, plugin, authentication, and license requirements. |
| Current SST | TypeScript configuration and components managed by SST's Pulumi-based engine, with AWS and Cloudflare components and additional Pulumi/Terraform providers. | Resource linking and its local development workflow fit the application and the team understands the resulting provider resources. |

Serverless Framework v4 supports AWS only; earlier non-AWS provider configurations are not portable into v4. Version 4 also requires CLI authentication, and its license terms depend on the use case. Check those terms before adoption, pin the version used in CI, and verify plugins against that version. For every tool, pin the CLI and libraries in the repository's normal package-management workflow. The SAM transform identifier is a template contract, not the SAM CLI version.

These are infrastructure tools, not application-runtime adapters. A Next.js or Nitro adapter translates that application's routing and rendering model into provider-specific outputs. Choosing SAM, CDK, SST, or Serverless Framework does not make framework request, cache, or rendering APIs portable.

## Trace one HTTP function from template to invocation

In SAM, an `HttpApi` event connects a function to a route. The template below describes that relationship; it is not the handler implementation. SAM's transform lets CloudFormation understand the higher-level resource, and the SAM CLI can build, validate, test locally, and deploy the application.

This read-only example reuses the API Gateway HTTP API v2 handler from the [Lambda chapter](40.7.02-aws-lambda.md). Compile it into `dist/index.js` first. No database permission is included, because this handler does not need one.

```yaml
AWSTemplateFormatVersion: '2010-09-09'
Transform: AWS::Serverless-2016-10-31
Resources:
  ExampleFunction:
    Type: AWS::Serverless::Function
    Properties:
      CodeUri: dist/
      Handler: index.handler
      Runtime: nodejs24.x
      MemorySize: 256
      Timeout: 5
      Events:
        GetExampleUser:
          Type: HttpApi
          Properties:
            Path: /users/{id}
            Method: GET
```

The `Runtime` property selects the provider's execution environment; confirm the runtime is supported in the target region and build native dependencies for the same operating system and architecture. `sam validate` checks the template, `sam build` prepares artifacts, and `sam local invoke` can run a handler with a representative event fixture. Those checks do not prove that live IAM, routing, quotas, or managed retries behave as intended.

CDK can express the same function and route with constructs. The code is an input to synthesis, not the deployed resource itself:

```typescript
import { Duration, Stack, type StackProps } from 'aws-cdk-lib';
import { Construct } from 'constructs';
import { Code, Function, Runtime } from 'aws-cdk-lib/aws-lambda';
import { HttpApi, HttpMethod } from 'aws-cdk-lib/aws-apigatewayv2';
import { HttpLambdaIntegration } from 'aws-cdk-lib/aws-apigatewayv2-integrations';

export class ExampleStack extends Stack {
  constructor(scope: Construct, id: string, props?: StackProps) {
    super(scope, id, props);
    const fn = new Function(this, 'ExampleFunction', {
      code: Code.fromAsset('dist'),
      handler: 'index.handler',
      runtime: Runtime.NODEJS_24_X,
      timeout: Duration.seconds(5),
    });
    const api = new HttpApi(this, 'ExampleApi');
    api.addRoutes({
      path: '/users/{id}', methods: [HttpMethod.GET],
      integration: new HttpLambdaIntegration('ExampleIntegration', fn),
    });
  }
}
```

Run `cdk synth` to produce and inspect the CloudFormation template and deployment assets. Before deployment, bootstrap each target AWS account and Region so CDK has the asset bucket, image repository, and deployment roles it needs. Use `cdk diff` to review the proposed change; where appropriate, a CloudFormation change set gives more accurate resource-replacement information than a template-only comparison. A type check or synthesis test still cannot prove the deployed package exports the handler or that live permissions and routing work.

## Review the plan and test the deployed boundary

The same review principle applies to the other frameworks. SAM shorthand, CDK constructs, SST components, and Serverless Framework configuration can all hide the provider resources they create. Inspect the synthesized template or deployment plan for widened Identity and Access Management (IAM) policies, unexpected public access, secret values, resource replacement, and stage-specific configuration before applying it. A preview is evidence about the intended change, not a complete live-drift check.

SST resource linking can expose declared resource values and permissions to supported application components, while `sst dev` can run local code with linked cloud resources. That convenience does not remove IAM review or environment isolation: local code may be using real data and real credentials. SST's current resource model is not the historical CDK-based SST API, so follow the installed release's component contract.

For Serverless Framework v4, the AWS provider maps the service's functions, events, and resources to a CloudFormation stack. Configure distinct stages and AWS accounts deliberately; a stage label alone is not an account security boundary. Review packaged files and generated IAM. Plugins extend lifecycle behavior and can change both the artifact and deployment, so test their installed versions. Local/offline behavior is likewise a tool or plugin contract, not proof of production event delivery.

Use separate checks for each boundary: unit-test the handler, inspect generated resources and permissions, test representative local events, deploy to an isolated account or stage, and verify the actual route and provider event. Protect stateful resources with retention policies and tested backups. Termination protection can prevent stack deletion but does not prevent every resource replacement; rollback must be compatible with the data already written.

SAM can include ordinary CloudFormation resources alongside SAM-specific resources, which is useful when one abstraction does not cover a provider feature. More generally, multiple tools can coexist if each resource and state store has one clear owner. Avoid having two frameworks manage the same resource: their plans can drift and one tool may overwrite the other's change.

## Summary

Serverless frameworks turn application intent into provider resources; they do not erase provider contracts. Choose the tool whose generated model your team can review, follow the source-to-artifact-to-deployment path, and test both the handler and live event boundary. Pin versions, scope permissions, protect stateful data, and plan rollback before changing production infrastructure.

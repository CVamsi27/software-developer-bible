# Durable Execution: Temporal & Inngest

An order may need a manager's approval by tomorrow before a payment can be captured. A web request cannot remain open that long, and a timer held only in server memory disappears on restart. A durable workflow stores the wait and progress so another worker can continue. But if payment succeeds and its response is lost, the workflow still cannot tell whether charging again is safe.

## Definition

Durable execution saves the progress of a multi-step operation so it can resume after a worker or application process stops. Temporal records workflow history and replays deterministic workflow code against it. Inngest stores completed named-step results and reuses them when a function runs again. Both can remember what their engine observed; neither can atomically record a charge made by a separate payment provider.

> **Textbook Definition:** Durable execution persists a workflow's coordination state and recorded outcomes, then resumes or replays the workflow after failure according to explicit retry, timeout, cancellation, and side-effect policies.

## First Principles

A process cannot stay alive for every approval period, shipment, or multi-day job. The engine persists a timer, decision, or completed task so a replacement worker can continue. In Temporal, an Activity is the worker function that performs external work, such as calling a payment provider. That provider commits independently of the workflow engine. The Activity can charge the card and crash before reporting success. Recovery therefore needs both durable workflow history and an idempotency or reconciliation protocol at the system that owns the payment.

```text
workflow schedules charge → Activity calls provider → provider commits
                                                       ↓ acknowledgment lost
workflow retries Activity → same operation key → retrieve original outcome
```

If completion was recorded, replay uses that result. If it was not recorded, another attempt may call the provider again. “Durable” does not mean every external effect happens exactly once.

## Temporal separates replayable decisions from effects

The Temporal Service stores an ordered event history—for example, a timer started, an Activity completed, and an approval signal arrived—and dispatches work through task queues. A Workflow Worker re-runs the coordination code against those events to reconstruct its state; previously completed Activities return their recorded results rather than running again. Activities perform ordinary I/O and report results. A task queue dispatches work; it is not the business data authority.

A **signal** delivers a message into a running workflow; a **query** inspects workflow state without mutating it. Approval endpoints must authorize who may signal which tenant/order. An arbitrary approver string inside workflow code is not an authorization system.

### One focused approval workflow

This TypeScript example shows the workflow/activity boundary with a complete synthetic Activity contract. Save the files separately and configure a Worker with both the workflow module and Activity implementation. The Activity deliberately returns a deterministic fixture receipt; it does not charge a real provider.

```typescript
// activities.ts
export async function charge(orderId: string): Promise<{ receiptId: string }> {
  // Synthetic fixture only. Real providers require receiver-enforced command identity.
  return { receiptId: `demo-receipt:${orderId}` };
}
```

```typescript
// workflows.ts
import { condition, defineQuery, defineSignal, proxyActivities, setHandler }
  from '@temporalio/workflow';
import type * as activities from './activities';

const { charge } = proxyActivities<typeof activities>({
  startToCloseTimeout: '30s', scheduleToCloseTimeout: '5m',
  retry: { maximumAttempts: 3 },
});
export const approve = defineSignal<[string]>('approve');
export const phase = defineQuery<string>('phase');

export async function orderWorkflow(orderId: string): Promise<string> {
  let approver: string | undefined;
  let status = 'awaiting-approval';
  setHandler(approve, (who) => { if (approver === undefined) approver = who; });
  setHandler(phase, () => status);
  const approved = await condition(() => approver !== undefined, '24h');
  if (!approved) {
    status = 'approval-expired';
    return status;
  }
  status = 'charging';
  const receipt = await charge(orderId);
  status = 'paid';
  return receipt.receiptId;
}
```

The condition resolves false on timeout; a timed wait is not implicit approval. A signal delivers the approval into the running workflow, while a query reports its current phase. Neither says that payment succeeded. In the example, a charge Activity can run up to three times; each attempt is limited to 30 seconds and the total scheduled operation to five minutes. A real payment Activity must use the same provider-enforced idempotency key on every attempt or query the provider before retrying. Client setup, credentials, Worker registration, and authorization of the approver belong to the application around this teaching core.

### Replay and change compatibility

External I/O belongs in Activities. The TypeScript Workflow sandbox supplies replay-safe versions of `Date.now()` and `Math.random()`; other SDKs have different restrictions. Determinism means that re-running the workflow against its history emits compatible commands, not that every source of time or randomness is forbidden across all SDKs.

Changing workflow control flow can make old histories incompatible. Use the installed SDK's versioning mechanism and replay representative histories before rollout. Keep compatible Worker code available for executions that still use the old history. `continue-as-new` starts a fresh history with transferred state; carry required values and re-register the signal and query handlers deliberately.

## Bound retries and treat timeouts as uncertain outcomes

A **start-to-close timeout** bounds one Activity attempt. A **schedule-to-close timeout** bounds the total time from scheduling through queueing, attempts, and retries. A **heartbeat timeout** applies only when the Activity sends heartbeats. Set these from the actual task and recovery budget.

A timeout means the engine stopped waiting; it does not prove remote work stopped. Cancellation is cooperative, and an irreversible effect may already exist. Reuse a stable operation identity and inspect the authoritative outcome before compensating. A permanent business rejection such as a declined card should fail into a defined business path, not an endless transport retry loop.

## Inngest records steps under stable identities

Inngest's function handler can run again while completed named steps return recorded results. A `step.run` name is a durable identity: preserve it when changing a function that already has active runs. If a process fails before the step result is recorded, the step body can run again, so an external effect inside it still needs idempotency.

This complete **TypeScript SDK v4** example uses the current two-argument `createFunction` contract: triggers are part of configuration. It records a small serializable value, waits durably, and returns it. It has no database/email side effects.

```typescript
import { Inngest } from 'inngest';

export const inngest = new Inngest({ id: 'durable-demo' });
export const reminder = inngest.createFunction(
  { id: 'reminder-demo', triggers: { event: 'demo/reminder.requested' }, retries: 2 },
  async ({ step }) => {
    const message = await step.run('prepare-message', () => ({ text: 'Example reminder' }));
    await step.sleep('wait-before-reminder', '1 minute');
    return message;
  },
);
```

Here `retries: 2` allows two retries after an initial failed attempt. Each `step.run` has its own retry counter, so a completed earlier step is reused while a later failing step retries. A real application must expose the supported serving endpoint and register it with the executor. Unit tests do not establish durable persistence or deployed event delivery. If an event cancels a wait, match it to the same order or user that started the run; an unfiltered cancellation event can end unrelated work. Cancellation also cannot retract an email that was already sent.

Batching changes the effect boundary. If one step sends a digest to many users and fails halfway, retrying can resend to the first users. Persist per-recipient outcomes or split the work under stable recipient identities. Check the installed SDK's batch, payload, and history limits rather than copying a limit from an older release.

## Choose the engine from operations and integration

| Engine | Useful fit | Contract to verify |
| ------------------ | --------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Step Functions | Amazon Web Services (AWS)-managed state machines and direct integrations with AWS services. | Standard runs up to one year; its API history is available for 90 days after completion. Standard executes each state once unless `Retry` is configured. Express runs up to five minutes: asynchronous is at-least-once, synchronous at-most-once. |
| Temporal | Code-first workflows with long waits, signals, queries, and work dispatched to application Workers. | Workflow code must remain replay-compatible. Activities can retry, so a remote effect needs a stable idempotency key or reconciliation. |
| Inngest | Event-triggered functions with named steps and a managed executor. | Completed `step.run` results are reused, but unfinished step bodies may run again. Preserve function and step IDs, and secure the serving endpoint. |

Step Functions' execution guarantee governs its workflow states, not an atomic transaction with a remote provider. For every engine, compare language/runtime fit, integrations, history and retention, recovery ownership, throughput, cost, and how the team deploys workflow changes.

## Test the recovery path, not just the happy path

For the approval-and-payment flow, test approval before and after its deadline, duplicate signals, a Worker restart during the wait, and a payment success whose response is lost. Verify that the same payment key is reused and that a permanent decline enters the intended business outcome. A refund is a separate effect that can fail; the engine does not define compensation or guarantee rollback.

Also test deployment of changed workflow code against representative old histories. Monitor queue delay, retries, expired waits, stuck runs, and unresolved provider outcomes. Store only the data the workflow needs; histories and step results can outlive an application process, so set access, encryption, and retention deliberately. Long Temporal histories add replay and storage work; use `continue-as-new` when appropriate.

A mock or local executor can validate ordinary handler logic. To claim durability, also test a real execution through the configured service or executor, including worker/process restart and event delivery. Durable waits release the active worker, but histories, storage, and service usage still have costs.

## Summary

Durable engines persist coordination and reuse outcomes they have recorded. Temporal replays compatible workflow code and records Activity results; Inngest reuses completed named steps. Their retries cannot make a payment, email, or other remote effect atomic with workflow history. Choose the engine from its actual execution and operational contract, then test the uncertain-outcome recovery path.

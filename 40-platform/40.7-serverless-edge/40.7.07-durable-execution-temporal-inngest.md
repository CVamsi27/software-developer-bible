# Durable Execution: Temporal & Inngest

## Definition

**Durable execution** is a runtime model that persists workflow progress so work can resume after a crash or deployment. Temporal reconstructs orchestration state from recorded event history; Inngest reuses recorded step outcomes. Neither engine records arbitrary external effects atomically with that history, so side-effecting work still needs a safe retry contract.

> **Textbook Definition:** Durable execution persists workflow progress and coordination state so execution can resume after process failure, using replay or saved step outcomes while applying explicit retry and side-effect policies.

Two dominant styles:

| Engine | Style | Model |
| ---------------------- | ---------------------------------------- | ------------------------------------------------------------------------------ |
| **Temporal** | Code-first SDKs (TS/Go/Java/Python/.NET) | Workflows (deterministic orchestration) call Activities (side-effecting units) |
| **Inngest** | Code-first, HTTP-native step functions | Single function declares `step.run/sleep/waitForEvent`; steps memoized by ID |
| *(AWS Step Functions)* | Config-first (Amazon States Language) | JSON/YAML state machine; Lambda per state |

```text
EVENT-SOURCED REPLAY

run #1                       worker crashes at t=3
  ├─ evt1: activity charge() → ok     ──► persisted
  ├─ evt2: timer 24h started          ──► persisted
  └─ CRASH: worker dies mid-run

run #2 (same history, new worker)
  replay evt1 → charge() NOT re-executed; cached result returned
  replay evt2 → timer resumes
  continue from t=3 as if nothing happened
```

## First Principles

Durable execution solves the FaaS time limit by making *state* the primitive:

1. **The workflow is a state machine persisted step-by-step**: every activity's completion recorded; on crash, replay from the log — code runs to completion despite process death (→ 30.2.2.21's axioms, productized).
2. **Determinism is the contract**: workflow commands must be consistent with recorded history; use the SDK's replay-safe APIs and keep external I/O in activities — the discipline that makes "hours-long try/catch'd logic" possible.
3. **It replaces the saga-plumbing you'd otherwise hand-roll** (→ 20.6.3.01): retries, compensation, timers, and signals are platform features — the trade is running the Temporal/Inngest service (or paying theirs).

## Why Do We Need It?

1. **FaaS is ephemeral** — Lambda's 15-minute cap and stateless memory make multi-day flows (approval chains, onboarding drips, billing retries) awkward glue of queues + databases.
2. **Crash-safety without checkpoint spaghetti** — no manual "save progress to DynamoDB" code; the event log *is* the checkpoint.
3. **Retries with real semantics** — per-step retry policies, heartbeats, and timeouts replace bespoke backoff tables.
4. **Human-in-the-loop fits naturally** — a workflow can wait days for a signal (approval, KYC document) without holding compute.
5. **Observability for free** — every step, retry, and input/output is in the history; debugging is reading, not archaeology.
6. **Senior interview relevance** — "how would you implement order orchestration across flaky services?" has a canonical durable-execution answer now.

## How It Works

### Temporal: Workflow vs Activity Split

```text
┌──────────────────────────────────────────────────┐
│ Temporal Cluster (managed or self-hosted)        │
│  • persists Event History per Workflow Execution │
│  • routes tasks via Task Queues                  │
└──────────────────────────────────────────────────┘
               │ poll                          │ poll
      ┌────────┴────────────────────────────────────────┐            ┌─────────┴────────┐
      │ Workflow Worker │ calls      │ Activity Worker  │
      │ deterministic   │───────────►│ side effects:    │
      │ orchestration   │ task queue │ HTTP, SQL, email │
      └─────────────────────────────────────────────────┘            └──────────────────┘
```

- **Workflow code**: pure orchestration logic. External I/O belongs in activities. SDK-specific time, random, and concurrency APIs must preserve the command sequence during replay.
- **Activities**: the actual work (`chargeCard`, `sendEmail`). Retryable, timeout-bounded, may be non-deterministic.
- **Signals**: asynchronous messages *into* a running workflow (e.g., approval received).
- **Queries**: synchronous read-only inspection of workflow state (e.g., current stage for a dashboard).

### Determinism Rules (the part interviews probe)

Workflow code must produce identical decisions given identical history:

```typescript
// WORKFLOW (deterministic-only APIs)
import { condition, defineQuery, defineSignal, proxyActivities, setHandler } from '@temporalio/workflow';
import type * as activities from './activities';

const { charge } = proxyActivities<typeof activities>({ startToCloseTimeout: '30s' });

export const approve = defineSignal<[string]>('approve');
export const getStatus = defineQuery<string>('status');

export async function orderWorkflow(orderId: string): Promise<string> {
  let approver: string | undefined;
  let status = 'awaiting_approval';
  setHandler(approve, (who) => { approver = who; });
  setHandler(getStatus, () => status);

  // A durable condition waits for a signal or the timeout.
  const approved = await condition(() => approver !== undefined, '24h');
  if (!approved) return 'approval-expired';

  // External I/O and mutable process configuration do not belong here.
  // In the TypeScript Workflow sandbox, Date.now() and Math.random() are replay-safe.
  const payment = await charge(orderId);                  // activity = safe I/O
  status = 'paid';
  return payment.receiptId;
}
```

```typescript
// ACTIVITIES (normal code, normal I/O)
import { Context } from '@temporalio/activity';

export async function charge(orderId: string): Promise<{ receiptId: string }> {
  return gateway.charge(orderId);              // idempotency key = orderId
}

export async function ship(orderId: string): Promise<void> {
  await logistics.dispatch(orderId);
  Context.current().heartbeat();               // long activities report liveness
}
```

Versioning is the second hard rule: because old histories replay against new code, use Temporal's patching API (`patched`/`deprecatePatch`) when changing workflow logic rather than editing freely.

### Inngest: Steps Memoize by ID

```typescript
import { inngest } from './client';

export const trialConversion = inngest.createFunction(
  {
    id: 'trial-conversion-drip',
    retries: 3,
    concurrency: { limit: 100 },
    cancelOn: [{ event: 'user/subscribed' }],
  },
  { event: 'trial/started' },
  async ({ step }) => {
    await step.run('fetch-user', async () => db.users.find(event.data.userId));

    await step.sleep('wait-3-days', '3 days');

    const engaged = await step.run('check-engagement', async () =>
      analytics.wasActive(event.data.userId)
    );
    if (!engaged) {
      await step.sendEvent('nudge', {
        name: 'email/send',
        data: { template: 'trial-nudge' },
      });
    }

    await step.waitForEvent('purchase-or-timeout', {
      event: 'user/subscribed',
      timeout: '7d',
      if: 'async.data.userId == event.data.userId',
    });
  }
);
```

Semantics: each `step.*` call has a stable ID; on re-invocation after failure, completed steps return their stored results instead of re-running. The function itself stays stateless HTTP — Inngest hosts the executor.

### Config-First vs Code-First Engines

| Dimension | AWS Step Functions (ASL) | Temporal / Inngest |
| ----------------- | ----------------------------------- | --------------------------------------- |
| Authoring | JSON/YAML state machine | TypeScript/Go/... code |
| Branching/loops | Expressions inside states | Native language constructs |
| Refactoring/reuse | Copy-paste ARNs, hard | Functions, modules, tests |
| Local dev/test | Limited (StepFunctions Local) | Real unit tests; replay tests |
| Learning curve | Learn ASL quirks | Learn determinism rules |
| Ops burden | Zero infra (AWS-managed) | Cloud-hosted or self-host cluster |
| Best fit | Simple AWS-glue flows, visual audit | Complex business logic, rich ecosystems |

Choose the orchestration model based on integration needs, language ergonomics, deployment ownership, and operational cost. State count alone does not determine which engine is easier to maintain.

### Retries, Timeouts, Heartbeats

```typescript
// Temporal activity options
const { charge } = proxyActivities({
  startToCloseTimeout: '2m',       // max single attempt
  scheduleToCloseTimeout: '1h',    // incl. queueing + retries
  heartbeatTimeout: '30s',         // detect hung attempts
  retry: {
    initialInterval: '2s',
    backoffCoefficient: 2,
    maximumAttempts: 5,
    nonRetryableErrorTypes: ['CardDeclinedError'],   // business failures ≠ retries
  },
});
```

Durable ≠ free from idempotency: at-least-once execution means activities can double-run on edge cases. Pass natural keys (orderId) as idempotency tokens to downstream systems.

## Code Examples

### Approval-Gated Order Flow With Signals and Queries

```typescript
// workflows.ts
import {
  defineQuery, defineSignal, setHandler, condition, sleep,
  proxyActivities,
} from '@temporalio/workflow';
import type * as acts from './activities';

const { reserveStock, releaseStock, capturePayment, createShipment, reconcileOrder } = proxyActivities<typeof acts>({
  startToCloseTimeout: '30s',
  retry: { maximumAttempts: 4 },
});

export const cancelOrder = defineSignal('cancel');
export const approvedBy = defineSignal<[string]>('approved-by');
export const phase = defineQuery<string>('phase');

export async function checkout(orderId: string): Promise<void> {
  let cancelled = false;
  let approver: string | null = null;
  setHandler(cancelOrder, () => { cancelled = true; });
  setHandler(approvedBy, (who) => { approver = who; });
  let currentPhase = 'review';
  setHandler(phase, () => currentPhase);

  // A timeout returns false; it is not an approval.
  const receivedDecision = await condition(() => cancelled || approver !== null, '48h');
  if (!receivedDecision || cancelled) {
    currentPhase = cancelled ? 'cancelled' : 'approval-expired';
    return;
  }

  try {
    currentPhase = 'reserving';
    await reserveStock(orderId);
    if (cancelled) {
      await releaseStock(orderId);
      currentPhase = 'cancelled';
      return;
    }

    currentPhase = 'charging';
    await capturePayment(orderId);
    currentPhase = 'shipping';
    await createShipment(orderId);
    currentPhase = 'completed';
  } catch (error) {
    currentPhase = 'needs-reconciliation';
    await reconcileOrder(orderId); // inspect provider state; do not blindly repeat or refund
    throw error;
  }
}
```

```typescript
// client.ts — starting and messaging running workflows
import { WorkflowClient } from '@temporalio/client';
import { approvedBy, phase } from './workflows';

const client = new WorkflowClient();

const handle = await client.start('checkout', { workflowId: 'checkout-ord_991', args: ['ord_991'], taskQueue: 'orders' });

await handle.signal(approvedBy, 'finance-bot');
console.log(await handle.query(phase));          // current phase; delivery is asynchronous
await handle.result();
```

The approval wait precedes stock reservation. Cancellation in this example is accepted before charging; later cancellation needs a separate business workflow. Each activity must enforce a stable operation key. `reconcileOrder` is an application activity that resolves uncertain payment/shipment outcomes from authoritative provider records and schedules any required compensation; it is not supplied by Temporal. Give reconciliation its own retry, alert, and manual-resolution policy.

## Real-World Use Cases

### 1. Payments Orchestration

Charge, fraud review (human signal), payout scheduling over days, refund handling on cancellation — each as activities with distinct retry policies. A processor outage becomes a retried activity instead of a 3 a.m. page.

### 2. User Onboarding Journeys

Trial-start event kicks off a multi-week drip: durable sleeps between emails, `waitForEvent` exits early on signup, `cancelOn` stops journeys instantly. Marketing edits flow code, not cron jobs.

### 3. Infrastructure Provisioning Pipelines

Terraform apply (activity), DNS propagation wait (durable timer), health verification with rollback path — replacing hand-rolled Step Functions JSON that nobody dared edit.

### 4. Document/KYC Approval Chains

Compliance officers approve via internal tool → signal into workflow. Weeks-long waits cost zero compute; queries power status dashboards without extra storage.

### 5. AI Agent Orchestration

LLM chains with tool calls, human review gates, and rate-limit-aware retries map cleanly onto steps; Inngest's concurrency/throttle controls protect provider quotas.

## Common Mistakes

### 1. Non-Deterministic Workflow Code

```typescript
// BAD: direct external I/O can return a different answer during replay.
const eligible = await externalPricingClient.isEligible(orderId);

// GOOD: an Activity result is recorded for Workflow replay.
const { fetchDiscountEligibility, applyDiscount } = proxyActivities<typeof activities>({
  startToCloseTimeout: '30s',
});
if (await fetchDiscountEligibility(orderId)) await applyDiscount(orderId);
```

Replay failures indicate that commands no longer match history. Move external I/O to activities and use compatible code-versioning strategies. In the TypeScript sandbox, `Date.now()` and `Math.random()` are deterministic replacements; restrictions differ across SDKs.

### 2. Treating Durable Sleep as Free Cron

Thousands of workflows sleeping months consume history storage and cluster resources. For pure scheduled jobs use a scheduler; keep durable execution for stateful flows.

### 3. Skipping Idempotency Because "The Engine Retries"

An activity can complete an external effect and lose its completion acknowledgment, leading to another attempt. Use receiver-enforced idempotency or reconcile the uncertain result before repeating an irreversible effect.

### 4. Giant Monolithic Activities

One activity doing fetch→validate→persist→notify retries *everything* on any failure. Split by failure domain so a notification blip doesn't redo a DB write.

### 5. Unbounded History Growth

Loops that emit events forever (polling every second for weeks) hit history size limits. Use `continue-as-new` (Temporal) or redesign around events instead of polling.

### 6. Assuming Durable Execution Solves Low-Latency Request/Response

Replay and task-queue hops add milliseconds-to-tens-of-ms; interactive API paths belong behind normal services, with workflows orchestrating what happens *after* the response.

## Best Practices

1. **Model side effects only as activities/steps** — workflows decide, workers do.
2. **Give every activity explicit timeouts and a retry policy** — defaults exist but should be chosen deliberately.
3. **Classify errors**: transient (retry) vs business (`NonRetryableError`) — conflating them causes runaway retries.
4. **Use signals for inbound, queries for reads** — never poll a query expecting mutation.
5. **Write replay tests in CI** before deploying workflow changes; they catch determinism drift pre-production.
6. **Keep payloads small** — pass IDs, not blobs; large inputs bloat history permanently.
7. **Prefer code-first engines once logic exceeds trivial graphs**; keep Step Functions for simple AWS-native glue.
8. **Instrument like any service** — export workflow metrics (start/fail/timeout rates) into your observability stack ([Observability](../40.4-observability/INDEX.md)).

## Performance Considerations

| Aspect | Characteristic | Tuning |
| ------------------- | --------------------------------------- | -------------------------------------------------------- |
| Workflow throughput | bounded by worker polling | scale workers horizontally; tune task queue consumers |
| Replay cost | proportional to history length | keep loops short; `continue-as-new` for long-lived loops |
| Timer density | millions of open timers stress clusters | consolidate waits; external schedulers for bulk |
| Activity latency | includes queue hop | co-locate activity workers near dependencies |
| Payload limits | history stores full IO per event | compress/large-payload store refs (S3 pointer pattern) |

## Summary

- Durable execution records each step/timer/signal as events and rebuilds state via deterministic replay — crash-safe long-running code without checkpoint plumbing.
- Temporal splits deterministic workflows from side-effecting activities, adds signals (in), queries (read), and strict determinism/versioning rules.
- Inngest offers HTTP-native functions with recorded step outcomes; compare its retry, concurrency, retention, and versioning contracts with Temporal before choosing.
- Config-first engines (Step Functions) suit simple AWS glue; code-first wins as logic complexity grows.
- Retries and durable timers replace bespoke backoff, but idempotency remains your job under at-least-once semantics.
- Reach for queues/cron instead when flows are short, latency-critical, or purely scheduled — durability has real costs.

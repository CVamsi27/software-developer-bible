# Durable Execution: Temporal & Inngest

## Definition

Durable execution records workflow progress so coordination can resume after a process dies. Temporal rebuilds orchestration state from event history; Inngest reuses recorded step results. A successfully recorded result can be reused, but an external effect that happened before its result was recorded remains an uncertain outcome.

> **Textbook Definition:** Durable execution persists workflow progress and coordination state so execution can resume after process failure, using replay or saved step outcomes while applying explicit retry and side-effect policies.

## First Principles

A process cannot remain alive for every multi-day business operation. Saving a timer, decision, or completed task allows a replacement to continue. But a database or payment provider commits independently of the workflow engine: the worker can charge a card and crash before reporting success. Recovery therefore needs both durable orchestration history and an authoritative retry/reconciliation protocol at the effect's receiver.

```text
workflow schedules charge → Activity calls provider → provider commits
                                                       ↓ acknowledgment lost
workflow retries Activity → same operation key → retrieve original outcome
```

If completion was recorded, replay returns that result. If it was not recorded, another attempt may execute. “Durable” does not mean every external effect happens exactly once.

## Temporal separates replayable decisions from effects

The service stores a Workflow Execution's history and dispatches tasks through task queues. Workflow Workers replay coordination code to produce commands compatible with that history. Activities perform ordinary I/O and report results. A task queue is a dispatch mechanism, not the business data authority.

A **signal** delivers a message into a running workflow; a **query** inspects workflow state without mutating it. Approval endpoints must authorize who may signal which tenant/order. An arbitrary approver string inside workflow code is not an authorization system.

### One focused approval workflow

This TypeScript example shows the workflow/activity boundary with a complete synthetic Activity contract. Save the files separately and configure a Worker with both the workflow module and Activity implementation. The Activity deliberately returns a deterministic fixture receipt; it does not charge a real provider.

```typescript
// activities.ts
export async function charge(orderId: string): Promise<{ receiptId: string }> {
  // Synthetic fixture only. Real providers require receiver-enforced command identity.
  return { receiptId: `demo-receipt:${orderId}` };
}
```

```typescript
// workflows.ts
import { condition, defineQuery, defineSignal, proxyActivities, setHandler }
  from '@temporalio/workflow';
import type * as activities from './activities';

const { charge } = proxyActivities<typeof activities>({
  startToCloseTimeout: '30s', scheduleToCloseTimeout: '5m',
  retry: { maximumAttempts: 3 },
});
export const approve = defineSignal<[string]>('approve');
export const phase = defineQuery<string>('phase');

export async function orderWorkflow(orderId: string): Promise<string> {
  let approver: string | undefined;
  let status = 'awaiting-approval';
  setHandler(approve, (who) => { approver = who; });
  setHandler(phase, () => status);
  const approved = await condition(() => approver !== undefined, '24h');
  if (!approved) {
    status = 'approval-expired';
    return status;
  }
  status = 'charging';
  const receipt = await charge(orderId);
  status = 'paid';
  return receipt.receiptId;
}
```

The condition resolves false on timeout; a timed wait is not implicit approval. Signal delivery and handler execution are asynchronous. A query reports the current phase, not an inference that a charge succeeded because approval was received. Client setup, credentials, task-queue registration and authorized approval routing belong to the application integration around this teaching core.

### Replay and change compatibility

External I/O belongs in Activities. The TypeScript Workflow sandbox supplies replay-safe replacements for `Date.now()` and `Math.random()`; other SDKs have different restrictions. Determinism means compatibility with recorded commands, not a simplistic ban on every source of time or randomness across all SDKs.

Changing control flow can make old histories incompatible. Use the installed SDK's patching/versioning mechanisms and replay representative recorded histories before rollout. Pin the workflow bundle and preserve compatible Worker availability for running executions. `continue-as-new` can start a fresh execution history with transferred state; carry required state and handle signals/handlers deliberately rather than discarding them accidentally.

## Retry limits and cancellation are separate controls

**Start-to-close** bounds one Activity attempt. **Schedule-to-close** bounds the whole scheduled operation including queueing and retries. Heartbeat timeout detects a missed heartbeat for Activities that actually heartbeat. Choose all of them from the task's work and recovery requirements.

A timeout means the engine's waiting policy expired; it does not prove remote work stopped. Cancellation is cooperative, and an irreversible effect may already exist. Use stable operation identity for a retry and inspect the authoritative outcome before compensating. Business rejection such as a declined card should not enter an endless transport retry loop.

## Inngest records steps under stable identities

Inngest's function handler can run again while completed named steps return recorded results. Keep external effects inside supported step boundaries, preserve step identity for existing runs, and treat a crash inside an unfinished step as potentially repeatable work.

This complete **TypeScript SDK v4** example uses the current two-argument `createFunction` contract: triggers are part of configuration. It records a small serializable value, waits durably, and returns it. It has no database/email side effects.

```typescript
import { Inngest } from 'inngest';

export const inngest = new Inngest({ id: 'durable-demo' });
export const reminder = inngest.createFunction(
  { id: 'reminder-demo', triggers: { event: 'demo/reminder.requested' }, retries: 2 },
  async ({ step }) => {
    const message = await step.run('prepare-message', () => ({ text: 'Example reminder' }));
    await step.sleep('wait-before-reminder', '1 minute');
    return message;
  },
);
```

A real application must expose the framework's supported serving endpoint and register it with the executor. Unit tests of this handler do not establish durable persistence or deployed delivery. Correlate waiting/cancellation events to the right entity; an unfiltered subscription event must not cancel unrelated users' trials. Cancellation also cannot retract an already-sent message.

Batching changes the effect boundary. If one step sends a digest to many users and fails halfway, retrying can resend to the first users. Persist per-recipient operation outcomes or split effects under stable recipient IDs. Check current batching/payload/retention limits; do not copy a 500-event batch into a version that allows fewer events.

## Choose the engine from operations and integration

| Dimension | Step Functions | Temporal | Inngest |
| ------------------ | ---------------------------------------------------------- | ---------------------------------------- | ---------------------------------------------------- |
| Coordination model | Service-defined state machine; Standard/Express differ | Deterministic Workflow plus Activities | Functions plus recorded named steps |
| Integration | AWS service integrations and tasks | SDK Workers and task queues | Supported serving adapter and executor |
| Change safety | Definition versions and execution contracts | Replay/Worker version compatibility | Stable step/function identities and version behavior |
| Operations | Managed service still needs permissions, quotas and alarms | Managed/self-hosted service plus Workers | Hosted/self-hosted executor plus serving application |

Native code can help complex logic; visual state machines can help review. Neither universally wins after an arbitrary state count. Compare actual language, integrations, recovery, retention, throughput, cost and team ownership.

## Real-world decisions and mistakes

For an order saga, reserve/capture/ship through independently recoverable tasks. Persist uncertain outcomes and reconciliation ownership; a failed compensating Activity must remain visible and retryable. Durable execution does not supply the business definition of a refund or guarantee rollback.

For onboarding, use bounded payloads and correlated durable waits. Keep sensitive records out of long-lived workflow histories where possible, and choose encryption/access/retention deliberately. History provides useful evidence but does not make observability or compliance free.

For infrastructure provisioning, a timed-out apply can leave resources created. Reconcile actual resource identity and state before reapplying or destroying. For AI/provider calls, bound concurrency and cost, record operation identity, and keep human approval at the authorized boundary.

Large histories increase replay/storage work and can hit limits. Prefer signals/events to rapid perpetual polling, use supported continuation strategies, and monitor queue delay, retry rates, stuck/expired workflows and unresolved effects. Durable sleeping releases active worker execution but still has state/storage/service costs.

## Best practices

Replay representative histories after workflow changes, test a crash after an effect and before completion recording, and classify permanent versus retryable failures. Set explicit budgets, protect sensitive payloads, retain recoverable task identities, and rehearse manual reconciliation. A mock step executor can validate ordinary logic; a real executor test is needed to claim persistence/restart behavior.

## Summary

Durable engines persist coordination and reuse recorded outcomes. Temporal requires replay-compatible workflow commands; Inngest preserves completed step results under stable IDs. Both need explicit external-effect idempotency, deadlines, cancellation boundaries and reconciliation. Choose and test the engine's actual contract rather than promising exactly-once effects from durability alone.

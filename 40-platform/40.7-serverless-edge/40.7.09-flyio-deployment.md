# Fly.io Deployment Patterns

## Definition

Fly.io runs application images in regional Machines and routes requests through Fly Proxy. A Machine is a microVM running your process; it can remain running, stop, or suspend under configured lifecycle rules. You still choose capacity, data placement, health, and recovery.

> **Textbook Definition:** A Fly.io deployment assigns versioned application images and configuration to regional Machines, using platform routing and lifecycle controls alongside explicit capacity, storage, and recovery choices.

## First Principles

A persistent process can hold sockets and run background work, but it can also restart or be replaced. Global ingress cannot make a regional database local to every request. The deployment must therefore decide where authoritative data lives, which Machines can serve it, and what happens when one process or region disappears. More regions improve latency only for work whose data path benefits from them.

## Trace ingress, application and data separately

```text
client → Fly Proxy → selected regional Machine → application → data authority
                           │
                       local volume, if configured
```

Fly Proxy accepts ingress and selects eligible capacity. Health checks influence routing, but an open port does not prove the application is ready to serve requests. Keep shallow liveness separate from bounded readiness where appropriate; a failing readiness check is not automatically a process restart mechanism.

A volume is local persistent storage attached under placement constraints. It is not a globally replicated filesystem or automatic multi-Machine database. Plan replication, backups, attachment/recovery and consistency independently. Managed Postgres and the older unmanaged Fly Postgres application model have different ownership contracts; select from actual recovery requirements rather than a blanket dev/production ranking.

## Autostart wakes existing capacity

`auto_start_machines` starts existing stopped/suspended Machines as traffic needs them. It does **not** create Machines when every configured one is busy. Provisioning/scaling Machine count is a separate action. `min_machines_running` applies to the primary region and matters with configured autostop; it does not keep every region warm.

Stopping ends the process; suspension preserves a runtime snapshot under platform semantics. Neither makes process memory durable business authority. An always-running minimum can still fail or restart. Background workers without request-driven services need a separate lifecycle/scheduler policy; HTTP ingress autostart does not guarantee queue jobs wake them.

## A focused service configuration

This illustrative app assumes a built image whose process listens on `0.0.0.0:3000` and implements the named readiness endpoint. Use an available region near the actual database; `sin` is an example, not proof of co-location with a Mumbai database.

```toml
app = "example-api"
primary_region = "sin"
kill_signal = "SIGTERM"
kill_timeout = "15s"

[build]
  image = "registry.example.com/example-api:reviewed-release"

[http_service]
  internal_port = 3000
  force_https = true
  auto_stop_machines = "stop"
  auto_start_machines = true
  min_machines_running = 1

  [http_service.concurrency]
    type = "requests"
    soft_limit = 40
    hard_limit = 60

  [[http_service.checks]]
    grace_period = "10s"
    interval = "15s"
    timeout = "2s"
    method = "GET"
    path = "/health/ready"

[[vm]]
  cpu_kind = "shared"
  cpus = 1
  memory = "512mb"
```

The request limits are illustrative routing budgets, not benchmarks or strict tenant rate limits. Load-test the process and downstream pool before selecting them. Use an approved image digest for reproducible promotion where supported by your workflow; a mutable tag alone can resolve to different bytes later.

Validate configuration and inspect planned/image changes before deployment. Configure secrets through the platform's secret import/setting mechanism without committing values. Image builds need the correct package-manager workspace files and production dependency layout; the [Docker chapters](../40.1-docker/INDEX.md) own complete build examples rather than an incomplete duplicated monorepo Dockerfile here.

## Deploy and recover an identified release

Build and test the artifact, review routing/secret changes, and apply backward-compatible schema expansion before promoting code that uses it. A release command can perform a guarded migration, but it has its own failure and network/resource contract. Do not run a destructive migration merely because it precedes `fly deploy` in a checklist.

During shutdown, stop accepting new work, drain bounded requests/sockets, finish or return queue leases, and exit inside the configured grace window. Protect jobs with stable command identity: a process can commit an effect just before termination and lose its acknowledgment.

Rollback routes code to an earlier image/configuration; it does not restore a lost volume or reverse external effects. Rehearse image rollback against today's schema, restore a volume/database into an isolated environment, and measure recovery time. Retaining two Machines improves availability only if independent failures and data replication are accounted for.

## Decisions and failure cases

| Workload | Check before choosing Machines |
| ---------------------------- | -------------------------------------------------------------------------------- |
| Persistent WebSocket service | Connection ownership, draining/reconnect, fan-out and durable resume cursor |
| Queue worker | Always-on/wake policy, bounded concurrency, lease and duplicate handling |
| Low-traffic HTTP API | Wake latency, minimum capacity, stopped-resource charges and data-region latency |
| Multi-region reads/writes | Data authority, replication lag, write routing and regional failover policy |
| Volume-backed process | Replication, backup identity, placement and attachment recovery |

Regional containers can be suitable for steady or connection-oriented work. Bursty functions can be suitable for bounded events. Compare total cost from measured utilization, transfer, storage and managed dependencies; neither is universally cheaper. Lambda can participate in API Gateway WebSocket events even though a Lambda invocation is not the persistent socket owner.

## Summary

Fly Proxy routes to regional Machines; lifecycle controls wake existing capacity rather than create it. Choose compute near its authority, separate readiness from liveness, and make state, draining, replication and rollback explicit. A healthy deployed process is one part of an available, recoverable application.

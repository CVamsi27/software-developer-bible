# Fly.io Deployment Patterns

> Stage 9 of the [Serverless & Edge](INDEX.md) — prev: [Durable Execution](40.7.07-durable-execution-temporal-inngest.md)
>
>
> **Why it matters:** This is a Platform interview topic you will be asked about at the senior level (5+ YoE) — not for definition recall, but for tradeoffs, production failure modes, and the ability to compare it against alternatives.

## Definition

Fly.io is a container platform that deploys Docker images to edge locations worldwide. Unlike serverless (Lambda), containers run continuously; unlike Kubernetes, there's no cluster to manage. You `fly launch` to create an app, `fly deploy` to ship code, and Fly handles the infrastructure: health checks, auto-scaling, TLS, DNS, and private networking.

**Key terms:**
- **Machine** — a Firecracker microVM running your container (Fly's unit of compute)
- **Region** — a Fly data center (e.g., `sin` for Singapore, `bom` for Mumbai)
- **Auto-stop/auto-start** — machines scale to zero when idle, start on demand
- **Fly Proxy** — the edge proxy that routes traffic to your machines
- **Volumes** — persistent storage attached to machines (region-local)
- **Fly Postgres** — managed PostgreSQL running on Fly (for dev/staging)

## First Principles

Fly fills the gap between containers-elsewhere and serverless: full containers, near users.

1. **VMs per region with global routing**: your container image (→ 40.1's unit) deployed to multiple regions with anycast/LB steering (→ 40.10.02's traffic logic) — container economics with edge latency.
2. **The trade vs serverless**: you manage instances (scale-to-zero available but not native) — for steady workloads it wins on cost; for spiky, (→ 40.7.01's economics favor functions).

## Why Do We Need It?

1. **Simplicity** — no Kubernetes, no ECS, no cluster management
2. **Edge deployment** — deploy to 30+ regions with one command
3. **Cost control** — auto-stop scales to zero; pay only when running
4. **Container-native** — run any Docker image, any language
5. **Built-in HA** — health checks, restarts, TLS, DNS all handled
6. **Background workers** — run workers alongside API in same region

## How It Works

### Fly.io Architecture

```text
┌────────────────────────────────────────────────────────────────────┐
│ Fly.io Production Architecture                                     │
├────────────────────────────────────────────────────────────────────┤
│                                                                    │
│  User Request                                                      │
│  ├── DNS resolution → Fly Proxy (nearest edge)                     │
│  ├── Fly Proxy → Machine in target region                          │
│  └── Machine → Your Docker container                               │
│                                                                    │
│  Machine (Firecracker microVM)                                     │
│  ├── Your app (Node.js, NestJS, etc.)                              │
│  ├── Health check endpoint (GET /health/live)                      │
│  ├── Volume (optional, persistent storage)                         │
│  └── Private network (WireGuard mesh between machines)             │
│                                                                    │
│  Database                                                          │
│  ├── Fly Postgres (managed, for dev/staging)                       │
│  ├── AWS RDS (recommended for production)                          │
│  └── External (Supabase, Neon, etc.)                               │
│                                                                    │
└────────────────────────────────────────────────────────────────────┘
```

### fly.toml Configuration

```toml
# fly.toml — Fly.io app configuration
app = "docita-api"
primary_region = "sin"  # Singapore (close to Mumbai RDS)

[build]
  dockerfile = "apps/api/Dockerfile"

[http_service]
  internal_port = 3001
  force_https = true
  auto_stop_machines = true    # scale to zero when idle
  auto_start_machines = true   # start on demand
  min_machines_running = 0     # set to 1 if you need always-on

  [http_service.concurrency]
    type = "requests"
    hard_limit = 250
    soft_limit = 200

[[http_service.checks]]
  grace_period = "10s"
  interval = "15s"
  method = "GET"
  path = "/api/health/live"

[vm]
  cpu_kind = "shared"
  cpus = 1
  memory_mb = 2048  # 2 GB RAM
```

### Dockerfile for NestJS on Fly

```dockerfile
# apps/api/Dockerfile
FROM node:22-alpine AS builder
WORKDIR /app
COPY package.json pnpm-lock.yaml ./
RUN corepack enable && pnpm install --frozen-lockfile
COPY . .
RUN pnpm turbo build --filter=api

FROM node:22-alpine AS runner
WORKDIR /app
COPY --from=builder /app/apps/api/dist ./dist
COPY --from=builder /app/node_modules ./node_modules
EXPOSE 3001
CMD ["node", "dist/main.js"]
```

### Deploy Commands

```bash
# First deploy
fly launch --no-deploy  # creates app, generates fly.toml
fly secrets set DATABASE_URL="postgresql://..." JWT_SECRET="..."
fly deploy

# Subsequent deploys
fly deploy

# Scale to specific region
fly scale count 2 --region sin  # 2 machines in Singapore

# View logs
fly logs
fly logs --app docita-api --region sin

# SSH into machine
fly ssh console

# Check machine status
fly status
fly machine list
```

## Real-World Use Cases

| Use Case | Fly.io Pattern | Why |
| ----------------------- | ------------------------ | ----------------------------------------------- |
| **NestJS API** (Docita) | Single region, auto-stop | Low traffic initially, scale to zero saves cost |
| **Background worker** | Same region as API | Shared private network, no egress cost |
| **Multi-region API** | Multi-region deploy | Low latency for global users |
| **WebSocket server** | Long-running machine | Lambda can't do WebSockets |
| **Cron jobs** | Auto-stop + scheduled | Machines start for cron, stop after |

## Common Mistakes

### 1. Auto-Stop With Stateful Apps

```toml
# BAD: Auto-stop kills machines with in-memory state
auto_stop_machines = true  # machine stops → in-memory cache lost

# GOOD: Use external state (Redis, database) or set min_machines_running
auto_stop_machines = true
min_machines_running = 1  # keep at least one machine alive
```

### 2. Wrong Region for Database

```toml
# BAD: API in Singapore, DB in US-East — 200ms latency per query
primary_region = "iad"  # API in US
# Database: aws rds ap-south-1 (Mumbai)

# GOOD: Co-locate API near DB
primary_region = "sin"  # API in Singapore (close to Mumbai)
# Database: aws rds ap-south-1 (Mumbai)
```

### 3. Forgetting Health Checks

```toml
# BAD: No health check — Fly doesn't know if your app is healthy
# (Fly uses default TCP check — port open ≠ app healthy)

# GOOD: HTTP health check on a real endpoint
[[http_service.checks]]
  path = "/api/health/live"
  interval = "15s"
  grace_period = "10s"
```

### 4. Not Using Multi-Stage Docker Builds

```dockerfile
# BAD: 1.2 GB image (includes dev dependencies, source code)
FROM node:22
COPY . .
RUN npm install
CMD ["node", "src/main.js"]

# GOOD: Multi-stage build — 150 MB image
FROM node:22-alpine AS builder
WORKDIR /app
COPY package.json pnpm-lock.yaml ./
RUN corepack enable && pnpm install --frozen-lockfile
COPY . .
RUN pnpm build

FROM node:22-alpine AS runner
COPY --from=builder /app/dist ./dist
COPY --from=builder /app/node_modules ./node_modules
CMD ["node", "dist/main.js"]
```

## Best Practices

1. **Co-locate API and DB** — deploy API in the same region as your database.
2. **Multi-stage Docker builds** — 10x smaller images, faster deploys.
3. **Health checks on real endpoints** — not just port-open, but actual application health.
4. **Secrets via `fly secrets set`** — never commit secrets to fly.toml.
5. **Auto-stop for cost** — scale to zero when idle, auto-start on request.
6. **min_machines_running for always-on** — set to 1 if you need zero cold starts.
7. **Background workers in same region** — shared private network, no egress cost.
8. **Monitor machine RSS** — adjust memory after measuring actual usage.
9. **Separate worker fly.toml** — worker has no HTTP service, different config.
10. **DB migrations before deploy** — run `prisma migrate deploy` before `fly deploy`.

## Summary

Fly.io deploys Docker containers to edge locations with Kubernetes-like power without the management overhead. It's best for long-running processes (APIs, WebSockets, workers) that need persistent connections — where Lambda's 15-minute timeout and cold starts are problematic. The key patterns: co-locate with your database, multi-stage Docker builds, health checks on real endpoints, and auto-stop for cost optimization. Fly.io is not a Lambda replacement — it's a simpler alternative to Kubernetes for small-to-medium deployments.

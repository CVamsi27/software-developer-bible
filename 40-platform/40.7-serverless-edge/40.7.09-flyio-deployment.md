# Fly.io Deployment Patterns

Two Machines can serve a WebSocket application, yet scaling them to zero may strand a queue worker, and a new Machine will not inherit another Machine's volume data. Fly deployment is therefore a set of separate routing, process-lifecycle, and data-recovery decisions.

## Definition

Fly.io runs application images in regional Machines and routes requests through Fly Proxy. A Machine is a small virtual machine (microVM) that runs your process in an isolated operating-system environment; it can remain running, stop, or suspend under configured lifecycle rules. You still choose capacity, data placement, health, and recovery.

> **Textbook Definition:** A Fly.io deployment assigns versioned application images and configuration to regional Machines, using platform routing and lifecycle controls alongside explicit capacity, storage, and recovery choices.

## First Principles

A persistent process can hold sockets and run background work, but it can also restart or be replaced. Global ingress cannot make a regional database local to every request. The deployment must therefore decide where authoritative data lives, which Machines can serve it, and what happens when one process or region disappears. More regions improve latency only for work whose data path benefits from them.

## Trace ingress, application and data separately

```text
client → Fly Proxy → selected regional Machine → application → data authority
                           │
                       local volume, if configured
```

Fly Proxy accepts incoming requests and selects eligible capacity. The service checks in `[http_service]` remove an unhealthy Machine from request routing; they do not restart its process. Top-level Machine checks report Machine health but do not control request routing. An open port alone does not prove the application is ready, so keep shallow liveness separate from bounded readiness where appropriate.

A Fly Volume is persistent storage attached to a Machine under placement constraints. A second Machine does not receive a copy, so a volume is neither a shared filesystem nor database replication. Plan backup, replica identity, attachment recovery, and consistency separately. For relational data, choose a managed service with an explicit backup and recovery contract, or own replication and restore for a self-managed database; multiple application Machines alone do not make the database highly available.

## Autostart wakes existing capacity

`auto_start_machines` starts existing stopped or suspended Machines as traffic needs them. It does **not** create Machines when every configured one is busy; provisioning or scaling Machine count is a separate action. `min_machines_running` applies to the primary region and matters with configured autostop; it does not keep every region warm.

Stopping ends the process. Suspension can save and restore a Machine's memory snapshot, but it is an optimization rather than durable business state: deployments and host events can discard the snapshot, and restored processes must tolerate stale network connections. An always-running minimum can still fail or restart. Background workers without request-driven services need a separate lifecycle or scheduler policy; incoming web traffic does not guarantee queue jobs wake them.

## A focused service configuration

This illustrative app assumes a built image whose process listens on `0.0.0.0:3000` and implements the named readiness endpoint. Use an available region near the actual database; `sin` is an example, not proof of co-location with a Mumbai database.

```toml
app = "example-api"
primary_region = "sin"
kill_signal = "SIGTERM"
kill_timeout = "15s"

[build]
  image = "registry.example.com/example-api:reviewed-release"

[http_service]
  internal_port = 3000
  force_https = true
  auto_stop_machines = "stop"
  auto_start_machines = true
  min_machines_running = 1

  [http_service.concurrency]
    type = "requests"
    soft_limit = 40
    hard_limit = 60

  [[http_service.checks]]
    grace_period = "10s"
    interval = "15s"
    timeout = "2s"
    method = "GET"
    path = "/health/ready"

[[vm]]
  cpu_kind = "shared"
  cpus = 1
  memory = "512mb"
```

The request limits are illustrative routing budgets, not benchmarks or strict tenant rate limits. Load-test the process and downstream pool before selecting them. Use an approved image digest—an immutable content identifier—for reproducible promotion where supported; a mutable tag alone can resolve to different bytes later.

Validate configuration and inspect the image changes before deployment. Configure secrets through the platform's secret mechanism without committing values. Image builds need the correct package-manager workspace files and production dependency layout; the [Docker chapters](../40.1-docker/INDEX.md) own complete build examples rather than an incomplete duplicated monorepo Dockerfile here.

## Deploy and recover an identified release

Build and test an identified artifact, review routing and secret changes, then apply a backward-compatible schema expansion before promoting code that uses it. Fly's `release_command` runs once per deploy attempt in a temporary Machine using the new image. It inherits the app's environment, secrets, and network access, but has no persistent volumes; a non-zero exit stops the deployment. The default timeout is five minutes. Use it for a guarded migration only when the migration does not require a mounted volume, fits the timeout, and remains safe if the deploy is retried. Do not run a destructive migration just because it precedes `fly deploy` in a checklist.

```toml
[deploy]
  release_command = "./scripts/migrate --expand"
```

The command is illustrative. Keep schema expansion compatible with both old and new application versions; remove old columns or constraints only after all deployed code stops using them.

During a controlled shutdown, stop accepting new work, drain bounded requests and sockets, finish or return queue leases (temporary ownership of queued work), and exit inside the configured grace window. Fly documents this timeout as best-effort, so the process must also survive a shorter stop. Give each job a stable idempotency key: a process can commit an effect just before termination and lose its acknowledgment.

Rollback routes code to an earlier image/configuration; it does not restore a lost volume or reverse external effects. Rehearse image rollback against today's schema, restore a volume/database into an isolated environment, and measure recovery time. Retaining two Machines improves availability only if independent failures and data replication are accounted for.

## Decisions and failure cases

| Workload | Check before choosing Machines |
| ---------------------------- | -------------------------------------------------------------------------------- |
| Persistent WebSocket service | Connection ownership, draining/reconnect, fan-out and durable resume cursor |
| Queue worker | Always-on/wake policy, bounded concurrency, lease and duplicate handling |
| Low-traffic HTTP API | Wake latency, minimum capacity, stopped-resource charges and data-region latency |
| Multi-region reads/writes | Data authority, replication lag, write routing and regional failover policy |
| Volume-backed process | Replication, backup identity, placement and attachment recovery |

Regional containers can be suitable for steady or connection-oriented work. Bursty functions can be suitable for bounded events. Compare total cost from measured utilization, transfer, storage and managed dependencies; neither is universally cheaper. Lambda can participate in API Gateway WebSocket events even though a Lambda invocation is not the persistent socket owner.

## Summary

Fly Proxy routes to regional Machines; lifecycle controls wake existing capacity rather than create it. Choose compute near its authority, separate readiness from liveness, and make state, draining, replication and rollback explicit. A healthy deployed process is one part of an available, recoverable application.

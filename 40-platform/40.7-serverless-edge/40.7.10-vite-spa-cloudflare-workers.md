# Vite SPA on Cloudflare Workers

> Stage 10 of the [Serverless & Edge](INDEX.md) — prev: [Fly.io Deployment](40.7.09-flyio-deployment.md)
>
> **TL;DR:** Cloudflare Workers with Static Assets serve Vite-built SPAs from 300+ edge locations worldwide. The pattern: Vite builds your SPA to static files, a tiny Hono proxy Worker handles `/api/*` routing to your backend, and Cloudflare serves the rest from the edge. The senior test is understanding the proxy contract, cache invalidation, bundle size limits (3 MB free, 10 MB paid), and when to use this vs server-side rendering.
>
> **Why it matters:** This is a Platform interview topic you will be asked about at the senior level (5+ YoE) — not for definition recall, but for tradeoffs, production failure modes, and the ability to compare it against alternatives.

## First Principles

The SPA + Workers pairing is the modern static-plus-API architecture:

1. **Static assets are the CDN's native food** (→ 40.10): the Vite-built SPA deploys free and fast; the app shell is never the bottleneck.
2. **Workers replace the API server**: the same edge runtime (→ 40.7.04) serving the API — one deployment unit, one network, no CORS in production (same origin by construction).
3. **The architecture's honest limit**: heavy compute and long connections belong elsewhere (→ 40.7.02) — SPA+Workers is the CRUD-and-content sweet spot.

## Definition

Deploying a Vite-built SPA on Cloudflare Workers uses two components:
1. **Static Assets** — Vite builds your React/Vue/Svelte app to static HTML/CSS/JS files, served from Cloudflare's edge
2. **Worker (Hono proxy)** — a tiny Cloudflare Worker that proxies `/api/*` requests to your backend

This is not server-side rendering (SSR) — the SPA loads as a static HTML file, then JavaScript takes over client-side routing. The Worker only handles API proxying.

**Key terms:**
- **Static Assets** — Cloudflare's built-in static file serving from Workers
- **Hono** — lightweight web framework for Cloudflare Workers (like Express for the edge)
- **API Proxy** — Worker forwards `/api/*` to your backend (Fly.io, AWS, etc.)
- **Bundle size** — Worker JS must be <3 MB (free) or <10 MB (paid) gzip'd
- **SPA routing** — client-side routing with `index.html` fallback for all paths

## Why Do We Need It?

1. **Global low latency** — SPA served from the nearest edge location (<50ms)
2. **Zero server cost for frontend** — Cloudflare Workers Free tier is generous
3. **API proxying** — same domain for frontend and API (no CORS issues)
4. **No build server needed** — Vite builds locally, deploy static files
5. **Simple architecture** — no Next.js SSR complexity, no server runtime for frontend

## How It Works

### Architecture

```text
┌────────────────────────────────────────────────────────────────────┐
│ Vite SPA + Cloudflare Workers Architecture                         │
├────────────────────────────────────────────────────────────────────┤
│                                                                    │
│  User Request: https://app.example.com/dashboard                   │
│  ├── DNS → Cloudflare edge (nearest to user)                       │
│  ├── Edge Worker receives request                                  │
│  ├── Path: /dashboard → Static Assets → serve index.html           │
│  │   (Vite-built SPA, JS/CSS from edge cache)                      │
│  └── SPA loads, JavaScript handles client-side routing             │
│                                                                    │
│  SPA makes API call: https://app.example.com/api/patients          │
│  ├── Edge Worker receives request                                  │
│  ├── Path: /api/* → Hono proxy → forward to Fly.io backend         │
│  ├── Fly.io processes request → returns JSON                       │
│  └── Worker returns response to client                             │
│                                                                    │
│  Build Output:                                                     │
│  ├── dist/          Vite output (index.html, JS, CSS)              │
│  └── api/           Hono proxy Worker (tiny, <100KB)               │
│                                                                    │
└────────────────────────────────────────────────────────────────────┘
```

### Worker Proxy (Hono)

```typescript
// apps/app/api/index.ts — Cloudflare Worker proxy
import { Hono } from 'hono';
import { proxy } from 'hono/proxy';

const app = new Hono<{ Bindings: { API_PROXY_TARGET: string } }>();

// Proxy /api/* to the backend
app.all('/api/*', async (c) => {
  const target = c.env.API_PROXY_TARGET; // e.g., "https://api.docita.work"
  return proxy(c, `${target}${new URL(c.req.url).pathname}`);
});

// SPA fallback: serve index.html for all non-API, non-static routes
app.get('*', async (c) => {
  // Static Assets handles this automatically in production
  // This is the dev fallback
  return c.env.ASSETS.fetch(c.req.url);
});

export default app;
```

### wrangler.toml

```toml
# wrangler.toml — Cloudflare Worker config
name = "app"
main = "api/index.ts"
compatibility_date = "2026-01-01"

# Static Assets (serves Vite build output)
[assets]
directory = "../dist"  # Vite build output
binding = "ASSETS"
html_handling = "auto-trailing-slash"
not_found_handling = "single-page-application"  # SPA fallback

# Environment variables
[vars]
API_PROXY_TARGET = "https://api.docita.work"
```

```typescript
// vite.config.ts
import { defineConfig } from 'vite';
import react from '@vitejs/plugin-react';

export default defineConfig({
```

### Deploy Pipeline

```yaml
# .github/workflows/deploy-app.yml
name: Deploy App
on:
  push:
    branches: [main]
    paths: ['apps/app/**', 'packages/ui/**']

jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - uses: pnpm/action-setup@v4

      - uses: actions/setup-node@v4
        with:
          node-version: 22

      - run: pnpm install --frozen-lockfile

      - name: Build SPA
        run: pnpm --filter app build

      - name: Check Worker bundle size
        run: node scripts/checks/check-worker-size.mjs

      - name: Deploy to Cloudflare
        uses: cloudflare/wrangler-action@v3
        with:
          apiToken: ${{ secrets.CLOUDFLARE_API_TOKEN }}
          workingDirectory: apps/app
          command: deploy
```

## Real-World Use Cases

| Use Case | Why Cloudflare Workers | Why not SSR |
| ---------------------------------- | ---------------------------------- | ---------------------------------- |
| **Clinic SPA** (Docita) | Static app, API proxy, global edge | No SEO needed, no server rendering |
| **Admin portal** (Docita Internal) | Same pattern, different route | Internal tool, no SEO |
| **Marketing site** (Landing) | Astro static + Workers | Content is static |
| **SaaS dashboard** | SPA + API proxy | Dashboard not SEO-critical |
| **Internal tools** | Zero frontend hosting cost | No SSR benefits needed |

## Common Mistakes

### 1. Worker Bundle Too Large

```typescript
// BAD: Importing entire lodash in the Worker
import _ from 'lodash'; // 70KB+ — exceeds free tier limit!

// GOOD: Only import what the proxy needs
import { Hono } from 'hono'; // 14KB
import { proxy } from 'hono/proxy'; // 1KB
```

### 2. Not Using SPA Fallback

```toml
# BAD: 404 for client-side routes
not_found_handling = "none"
# /dashboard → 404 (Worker doesn't have this file)

# GOOD: SPA fallback serves index.html for all routes
not_found_handling = "single-page-application"
# /dashboard → index.html → SPA JavaScript handles routing
```

### 3. CORS Issues With Separate Backend Domain

```typescript
// BAD: SPA on app.example.com, API on api.example.com
// → CORS issues, cookies don't work cross-origin

// GOOD: Same domain with Worker proxy
// SPA: app.example.com/
// API: app.example.com/api/* → proxy to Fly.io
// → Same origin, no CORS, cookies work
```

### 4. Forgetting Cache Headers

```typescript
// BAD: No cache headers — every request hits the Worker
// GOOD: Set cache headers for static assets
app.all('/assets/*', async (c) => {
  const response = await c.env.ASSETS.fetch(c.req.url);
  response.headers.set('Cache-Control', 'public, max-age=31536000, immutable');
  return response;
});
```

## Best Practices

1. **Keep Worker tiny** — the Worker should only proxy `/api/*`. No business logic.
2. **SPA fallback** — `not_found_handling = "single-page-application"` in wrangler.toml.
3. **Check bundle size** — automated CI check: Worker JS <3 MB gzip (free tier).
4. **Cache static assets** — immutable cache headers for hashed assets (`/assets/*.js`).
5. **Same domain** — proxy API through Worker to avoid CORS issues.
6. **Source maps off** — production builds should not expose source maps.
7. **Environment variables** — use `wrangler secret put` for secrets, `[vars]` for non-sensitive config.
8. **Preview deploys** — Cloudflare generates preview URLs for PRs.
9. **Monitor Worker metrics** — Cloudflare dashboard shows requests, errors, CPU time.
10. **Test locally** — `wrangler dev` runs the Worker locally for testing.

## Summary

Vite SPA on Cloudflare Workers is the simplest, cheapest way to deploy a frontend: Vite builds static files, a tiny Hono proxy Worker handles `/api/*` routing, and Cloudflare serves everything from 300+ edge locations. The key patterns: keep the Worker tiny (proxy only), use SPA fallback for client-side routing, same-domain API proxying to avoid CORS, and immutable cache headers for static assets. This is not SSR — it's static file serving with edge proxy, perfect for SPAs that don't need server-side rendering.

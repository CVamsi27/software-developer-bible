# Vite SPA on Cloudflare Workers

When someone refreshes `/dashboard`, the server should return the single-page application (SPA) shell. When the browser requests `/api/orders/42`, it should receive a backend response — even though neither path is a file in `dist/`. These two unmatched paths need different routing contracts.

> Stage 10 of the [Serverless & Edge](INDEX.md) — prev: [Fly.io Deployment](40.7.09-flyio-deployment.md)

## Definition

A Vite single-page application (SPA) deployment on Cloudflare Workers combines **built static assets** with an optional **Worker script**. Static Assets serves the HTML, JavaScript, CSS, and other build files. The script can handle selected application programming interface (API) paths or other dynamic behavior. This chapter uses a same-origin Hypertext Transfer Protocol (HTTP) API proxy; it does not replace the backend that owns authorization and persistence.

> **Textbook Definition:** A Vite single-page application deployment on Cloudflare Workers serves generated static assets and, when configured, executes Worker logic for dynamic routes under a shared deployment and routing configuration.

## First Principles

The browser needs an application shell for a client route that is not a physical file. API callers need an API response for a path that is also not a static file. A blanket HTML fallback cannot distinguish those contracts by path alone. Configure which requests reach the script before choosing how unknown navigation paths fall back to the SPA.

## How It Works

### 1. Trace a Page Navigation and an API Read

1. A browser navigates to `/dashboard`: Static Assets returns the application shell for the client route.
2. The browser loads the emitted assets and the client router renders the page.
3. The app requests `/api/items?page=2`: Worker-first routing selects the script.
4. The proxy preserves method, path, query, and body while selecting a configured backend origin.
5. The backend returns an authorized response; the Worker streams it to the caller.

```text
/dashboard ──> Static Assets ──> index.html + browser app
/api/items?page=2 ──> Worker ──> configured backend ──> API response
```

Static serving is usually asset-first. The SPA fallback returns `index.html` when no asset matches; `run_worker_first` sends the selected API paths through the Worker before that fallback. Match both `/api` and `/api/*` so the collection root and its descendants use the API contract. Requests outside those patterns are served as assets without running this Worker, so script middleware cannot be relied on to protect the SPA shell.

### 2. Keep Asset and API Routing Explicit

Assume `vite build` writes `dist/` next to this config. `API_PROXY_TARGET` is a trusted deployment setting containing a secure HTTP (HTTPS) origin, not a request parameter. Generate `Env` from Wrangler configuration; this Worker needs no asset binding because only the configured API paths execute it.

```jsonc
// wrangler.jsonc
{
  "$schema": "./node_modules/wrangler/config-schema.json",
  "name": "spa-api-proxy",
  "main": "worker/index.ts",
  "compatibility_date": "2026-10-14",
  "assets": {
    "directory": "./dist",
    "not_found_handling": "single-page-application",
    "run_worker_first": ["/api", "/api/*"]
  },
  "vars": { "API_PROXY_TARGET": "https://api.example.com" },
  "observability": { "enabled": true, "head_sampling_rate": 0.1 }
}
```

```typescript
// worker/index.ts
export default {
  async fetch(request, env) {
    const incoming = new URL(request.url);

    let target: URL;
    try {
      target = new URL(env.API_PROXY_TARGET);
    } catch {
      return new Response("Invalid proxy configuration", { status: 500 });
    }
    if (target.protocol !== "https:" || target.username || target.password ||
        target.pathname !== "/" || target.search || target.hash) {
      return new Response("Invalid proxy configuration", { status: 500 });
    }
    target.pathname = incoming.pathname;
    target.search = incoming.search;

    const outbound = new Request(target.toString(), request);
    // Do not pass arbitrary caller identity claims to a trusting backend.
    for (const header of [
      "forwarded", "x-forwarded-for", "x-forwarded-host", "x-forwarded-proto",
      "x-forwarded-port", "x-real-ip", "x-user-id", "x-tenant-id",
    ]) {
      outbound.headers.delete(header);
    }
    try {
      // Preserve the body stream; do not consume an unbounded upload into memory.
      // Manual redirects avoid silently following a backend redirect to another origin.
      return await fetch(outbound, { redirect: "manual" });
    } catch {
      return new Response("Upstream unavailable", { status: 502 });
    }
  },
} satisfies ExportedHandler<Env>;
```

This is a focused HTTP forwarding core, invoked only for `/api` paths by the configuration above. The backend must authenticate and authorize any forwarded cookie or token; deleting spoofable identity headers does not supply authentication. The header list is not universal: remove every identity header the backend trusts unless the Worker overwrites it from verified authentication. If the backend needs the original client IP, define and verify a trusted edge-address contract separately. Validate the configured target per deployment and test the backend's `Origin` and `Host` policy. WebSockets, backend redirect rewriting, cookie Domain/Path rewriting, and application deadlines need explicit additional behavior.

### 3. Build and Verify the Release Boundary

```bash
npm install --save-dev wrangler typescript
npx vite build
npx wrangler types
npx tsc --noEmit
npx wrangler deploy --dry-run --outdir bundled
```

The TypeScript project must include the generated declaration file and target the Worker runtime; do not substitute broad DOM/Node declarations that hide binding mismatches. A dry run bundles the Worker locally and does not deploy it. Pin the toolchain in the lockfile. The compatibility date above is an example checked on 2026-10-14; pin a date supported by the installed Wrangler version and advance it deliberately with tests. Array-based `run_worker_first` route patterns require Wrangler 4.20.0 or later; verify the installed CLI before using this configuration.

The Cloudflare limit page checked on 2026-10-14 sets the **uncompressed Worker bundle** limit to 64 MiB on both Free and Paid plans. Wrangler's `Total Upload` is that uncompressed size; its gzip figure is informational. Static Assets have separate file-count and file-size limits. Browser JavaScript has separate download, parse, execution, rendering, and data-fetch costs, so "served at the edge" is not a user-experience budget. Vite 8 uses Rolldown as its unified bundler; check the installed major before copying version-specific bundler configuration.

Before promoting the release, verify the path and trust boundaries directly:

| Check | Expected result |
| ------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------- |
| Refresh `/dashboard` and a nested client route | SPA HTML shell, then client-side rendering |
| Request `/api` and `/api/orders/42?state=open` | Worker-first routing; backend receives exact path and query |
| Send an unauthenticated API request and a cross-site cookie request | Backend rejects unauthorized access and applies its cross-site request forgery (CSRF) and `Origin` policy |
| Send a large body, backend error, and redirect | Body streams; upstream status is preserved; redirect policy is intentional |
| Request a hashed asset, `index.html`, and a private API response | Cache policy is appropriate for each response class |
| Run the dry-run deploy and inspect `Total Upload` | Bundle fits current limits; generated configuration and bindings match the build |

The proxy makes the browser request same-origin; it does not make backend authorization, cookie scope, `Secure`/`SameSite` settings, CSRF defenses, audit, or persistence automatic. A separate API origin can also be sound when CORS and credential policy are explicit. Cache hashed assets for long periods, but give the SPA shell, mutable config, and private API responses distinct policies. Finally, promote a tested build with scoped deployment credentials and rehearse Worker/assets rollback against the separately deployed backend; rolling back the frontend does not reverse a schema change or external effect. See the [bundle analysis chapter](../../50-quality/50.3-performance-monitoring/03-optimization-and-governance/50.3.3.01-bundle-analysis.md) when browser JavaScript is the bottleneck.

## Summary

Static Assets serves the built SPA; selected Worker-first routes implement dynamic behavior such as an API proxy. Correctness depends on fallback order, request preservation, and explicit backend trust/cookie policy. Use the current uncompressed Worker limit, generated bindings, and deployed-path tests instead of copying obsolete budgets or assuming edge serving removes application costs.

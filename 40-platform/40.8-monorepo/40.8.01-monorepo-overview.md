# Monorepo Overview

Changing a shared component package and its two application consumers in one pull request can keep their source contracts consistent. The applications may still deploy at different times, so the repository does not make their runtime releases atomic.

## Definition

A **monorepo** is one version-controlled repository containing multiple logically distinct projects, such as applications, services, and libraries. A workspace manager can install and link local packages; a task orchestrator can order and cache work. Neither tool is required for the repository to be a monorepo.

> **Textbook Definition:** A monorepo stores multiple distinct projects in one version-controlled repository, enabling coordinated source changes and shared tooling while requiring explicit dependency, ownership, and release boundaries.

## First Principles

Putting projects in one repository makes source changes easy to coordinate; it does not tell package managers how to resolve them, build tools what to order, or release systems what to deploy. For a consumer to use a shared library reliably, the package link, prerequisite build, published entry points, and compatibility policy must agree. Each is a separate contract.

## 1. Keep Three Graphs Separate

A change can pass through three related graphs, each with a different owner:

| Graph | What it answers | What it does not guarantee |
| ----------------- | --------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------- |
| **Package graph** | Which project depends on which library, and how the package manager resolves it | That the dependency has been built or that a published package exposes the same files |
| **Task graph** | Which build, test, or lint task must run before another | That every real dependency was declared or that a skipped test is safe |
| **Release graph** | Which packages or applications are compatible and may be published or deployed together | That one Git commit updates running services or external consumers atomically |

For example, if `web` imports `ui`, the package manifests should declare `web → ui`. The build graph must then build `ui` before compiling `web`. A release pipeline separately decides whether to publish `ui`, deploy both apps, or preserve compatibility while they move at different speeds. Turborepo and Nx provide task-graph behavior; the next chapters explain their different models.

## 2. Decide Where the Repository Boundary Belongs

Keep projects together when teams often need coordinated source changes, benefit from one tested toolchain, and can work under a shared repository access policy. This makes broad refactors easier to review and lets continuous integration (CI) test related projects from the same commit.

Separate repositories when access or compliance rules require different read permissions, projects need materially different source-control/tooling policies, or independently governed products rarely change together. Separate repos move coordination into published package contracts, compatibility policy, and cross-repository automation. A monorepo centralizes source; it does not require one deployment cadence or prevent independent team ownership.

| Decision | Monorepo | Polyrepo |
| --------------------------- | ---------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------- |
| Cross-project source change | Can land in one commit and be tested together | Requires compatible package/interface changes and coordination across repositories |
| Repository permissions | Read access applies at repository level; ownership rules route review | Separate repositories can have separate read permissions |
| Tooling and CI | Shared defaults are easy; project-specific overrides still need clear owners | Each repository can evolve independently; duplicated automation needs maintenance |
| Release and deployment | May be coordinated or independent; choose explicitly | Naturally versioned across repository boundaries, but consumers still need upgrade policy |

## 3. Set Up Workspaces Without Hiding Package Contracts

Workspace configuration tells a package manager which directories contain packages. Each package still declares its own dependencies; a root install layout must not make undeclared dependencies appear valid.

With pnpm, the workspace list lives in `pnpm-workspace.yaml`:

```yaml
packages:
  - "apps/*"
  - "packages/*"
```

With npm or Yarn, declare workspace globs in the root `package.json`:

```json
{
  "private": true,
  "workspaces": ["apps/*", "packages/*"]
}
```

Commit the chosen package manager's lockfile and record its exact version in the root `packageManager` field. A reproducible install requires both; matching package names alone do not pin the toolchain.

Each local dependency belongs in the consuming package's manifest. For pnpm, the `workspace:` protocol forces resolution to a local workspace package instead of silently falling back to a registry version:

```json
{
  "name": "@acme/ui",
  "version": "1.2.0",
  "type": "module",
  "exports": {
    ".": {
      "types": "./dist/index.d.ts",
      "import": "./dist/index.js"
    }
  },
  "dependencies": {
    "@acme/tokens": "workspace:*"
  }
}
```

This manifest describes an ECMAScript module (ESM) package exposing built output. The `type` field makes the JavaScript module format explicit; the `import` condition chooses an entry point but does not itself set that format. Build `dist/` before a consumer imports it; include a `require` export if CommonJS is also part of the supported contract. When a package is packed for publication, pnpm or Yarn rewrites supported `workspace:` ranges to registry-compatible versions. Inspect the tarball before release. npm has its own workspace dependency rules; do not assume another manager's `workspace:` syntax is portable across package managers.

TypeScript `paths` can help an application compile workspace source, but it does not rewrite runtime imports. Choose either a bundler that intentionally compiles the source package or a built package with explicit exports. Test the package through the same resolution path consumers will use; a source alias can otherwise hide a broken package artifact.

## 4. Run Tasks in Dependency Order

After packages are linked, CI still needs to build prerequisites before consumers. The package manager can provide basic workspace traversal; a task orchestrator adds explicit task dependencies, affected-project selection, caching, or distributed execution as needed.

Examples of package-manager traversal are:

```bash
# pnpm: run a task for a package and its workspace dependencies
pnpm --filter "@acme/web..." run build

# npm: run a script in workspaces that define it
npm run test --workspaces --if-present

# Yarn: build all workspaces in dependency order
yarn workspaces foreach -A -t run build
```

These commands do not make all package dependencies visible to every tool. Keep dependency edges in manifests, make the required build order explicit, and verify a clean checkout from the committed lockfile. If simple recursive scripts become hard to reason about, use the [Turborepo](40.8.02-turborepo.md) or [Nx](40.8.03-nx.md) task model rather than layering unexplained shell scripts.

## 5. Treat Ownership and Releases as Separate Policies

Repository structure does not enforce architecture by itself. A project graph can reveal `web → ui → tokens`, but boundary rules must prevent forbidden imports. `CODEOWNERS` can request review from responsible maintainers; it does not hide source from anyone with repository read access.

For private applications that deploy from a commit, package versioning may add little value. For packages consumed outside the repository, choose lockstep or independent versions, define compatibility policy, and validate the packed artifacts. The [versioning and publishing chapter](40.8.05-versioning-publishing-strategies.md) covers release intent, prereleases, registry access, and provenance.

Before trusting affected-only CI, verify what it selects for a leaf change, a shared library change, and a shared config or lockfile change. Retain a periodic full integration run when generated or implicit dependencies are not represented in the graph. Use clean installs and consumer smoke tests to catch errors that workspace linking can mask.

## Summary

A monorepo groups source; workspace managers resolve local packages, task graphs order work, and release policies govern compatibility. Keep those contracts explicit. A commit can coordinate source changes, but builds, permissions, artifact publication, deployments, and external consumers still need their own boundaries.

# Turborepo

## Definition

Turborepo is a workspace task orchestrator from Vercel that builds a dependency graph of workspace tasks, runs them in topological order, parallelizes independent work, and caches declared task outputs locally and optionally remotely. A compiler or module bundler still runs inside each build task.

> **Textbook Definition:** Turborepo is a workspace task orchestrator that orders dependent tasks, schedules independent work, and reuses declared outputs through caching when task inputs match a prior execution.

## First Principles

Turborepo's model: the task graph + content-addressed caching.

1. **Tasks declare dependencies; the orchestrator runs the DAG** — build what changed and what depends on it (topological order), skip the rest. The graph is the correctness mechanism, parallelism the bonus.
2. **Inputs → outputs, cached by hash**: same inputs (files, env, args) → restore outputs from cache — locally and in CI (remote cache). The build stops being recomputation (→ 40.5.1.03's incrementality, generalized).

## Why It Matters

- **Build speed** — a cache hit restores prior outputs; measure hit rate and uncached work before predicting time saved
- **Parallelization** — runs independent tasks concurrently across packages
- **Remote cache** — share compatible artifacts across team and CI; misses and uncached tasks still execute
- **Workspace integration** — uses existing package-manager workspaces, with explicit task configuration
- **Incremental** — only rebuilds what changed, downstream, and what's affected

## Pipeline Configuration (Turborepo 2.x)

Ignore generated `.turbo/`, `dist/`, `.next/`, coverage and dependency directories in version control. Task logs or outputs included as fresh inputs can defeat reuse. The workspace must contain package manifests, scripts and a matching package-manager lockfile.

```json
// turbo.json
{
  "$schema": "https://turbo.build/schema.json",
  "globalDependencies": ["**/.env.*local"],
  "globalEnv": ["NODE_ENV", "CI"],
  "tasks": {
    "build": {
      "dependsOn": ["^build"],
      "outputs": ["dist/**", ".next/**", "!.next/cache/**", "!.next/dev/**"],
      "inputs": ["$TURBO_DEFAULT$", "vite.config.ts"]
    },
    "dev": {
      "cache": false,
      "persistent": true
    },
    "lint": {
      "dependsOn": ["^build"],
      "outputs": []
    },
    "test": {
      "dependsOn": ["^build"],
      "outputs": ["coverage/**"],
      "env": ["NODE_ENV", "TEST_DATABASE_URL"]
    },
    "typecheck": {
      "dependsOn": ["^build"],
      "outputs": []
    },
    "clean": {
      "cache": false
    }
  }
}
```

## Code Examples

### 1. Basic Pipeline (Build, Test, Lint)

```json
// turbo.json (minimal)
{
  "$schema": "https://turbo.build/schema.json",
  "tasks": {
    "build": {
      "dependsOn": ["^build"],
      "outputs": ["dist/**"]
    },
    "test": {
      "dependsOn": ["build"],
      "outputs": ["coverage/**"]
    },
    "lint": { "outputs": [] },
    "dev": { "cache": false, "persistent": true }
  }
}
```

```json
// Root package.json
{
  "scripts": {
    "build": "turbo run build",
    "dev": "turbo run dev",
    "test": "turbo run test",
    "lint": "turbo run lint",
    "typecheck": "turbo run typecheck"
  }
}
```

### 2. Filter (Run on Affected Packages)

```bash
# Only run build for @myorg/web and its dependencies
turbo run build --filter=@myorg/web...

# Only run if the package changed since main
turbo run build --filter=...[origin/main]

# Run on a specific package
turbo run test --filter=@myorg/utils

# Include a package and packages that depend on it
turbo run build --filter=...@myorg/utils
```

### 3. Remote Caching (Vercel / Self-Hosted)

```bash
# Login to Vercel for remote caching
npx turbo login

# Link the repo
npx turbo link

# Or use self-hosted / custom
export TURBO_TOKEN=your-token
export TURBO_TEAM=your-team
```

```json
// turbo.json — enable remote cache signing
{
  "remoteCache": {
    "signature": true
  }
}
```

```yaml
# .github/workflows/ci.yml — pass the cache credentials
permissions:
  contents: read
jobs:
  build:
    runs-on: ubuntu-latest
    env:
      TURBO_TOKEN: ${{ secrets.TURBO_TOKEN }}
      TURBO_TEAM: ${{ vars.TURBO_TEAM }}
    steps:
      - uses: actions/checkout@v7
      - uses: pnpm/action-setup@v4
      - uses: actions/setup-node@v7
        with:
          node-version: 22
          cache: pnpm
      - run: pnpm install --frozen-lockfile
      - run: pnpm turbo build test lint
```

### 4. Docker Layer Caching with Turborepo

The Docker build has two cache systems: Docker may reuse an unchanged instruction layer; Turborepo may restore a workspace task's declared outputs when its own inputs match. Neither replaces packaging the runtime correctly.

For a Next.js app, enable `output: 'standalone'`, configure the tracing root to include needed workspace files, and copy the standalone output plus static/public assets into the runner image. For a Node package, use the package manager's deployment workflow or bundle the runtime dependencies. Copying only a pnpm package's `node_modules` leaves symlinks pointing at missing stores or workspace packages. See [multi-stage builds](../40.1-docker/40.1.04-multi-stage-builds.md) for the image boundary.

### 5. Per-Package Overrides

```json
// packages/ui/package.json — package scripts
{
  "name": "@myorg/ui",
  "scripts": {
    "build": "tsc && vite build",
    "dev": "vite build --watch",
    "lint": "eslint src --ext .ts,.tsx",
    "test": "vitest run"
  }
}
```

Place per-package task overrides in `packages/ui/turbo.json`, with `"extends": ["//"]` and `tasks`; the package.json `turbo` field is not the configuration format.

Remote cache signing also requires the shared `TURBO_REMOTE_CACHE_SIGNATURE_KEY`. An API token/team alone does not configure a custom self-hosted endpoint. The Docker sketch assumes runtime dependencies are self-contained: a pnpm symlinked `node_modules` cannot simply be copied without its store and linked workspace packages. Use deployment/pruning or a framework standalone artifact appropriate to the app.

### 6. With Changesets for Versioning

```bash
# .changeset workflow
pnpm changeset # write a changeset describing the change
pnpm changeset version # bump versions, update CHANGELOG
pnpm changeset publish # publish to npm
```

## Real-World Decision: Changed Inputs and Reused Outputs

Suppose `web` depends on `ui`. `web#build` with `^build` waits for `ui#build`. If the UI source changes, its input hash changes and its build runs. A downstream build must include the dependency's relevant inputs or task hash, so it cannot reuse an incompatible artifact. Independent API work can run concurrently.

On a later identical build, a cache hit restores the declared files and logs. A successful task with missing `outputs` can appear cached while leaving no distributable artifact. Test this by deleting build outputs and confirming the next cached run restores them. Build duration and cache-hit rate require measurement on the actual workload; no timing improvement is guaranteed.

## Common Mistakes

| Mistake | Fix |
| ---------------------------------------------- | ------------------------------------------------------------------------------------------- |
| Missing `outputs` declaration | Specify every file the task produces — Turborepo can't cache what it doesn't know about |
| Wrong `dependsOn` (missing `^`) | Use `^build` for upstream (npm dependency) builds; `build` for same-package prerequisites |
| Caching non-deterministic tasks (e.g., deploy) | Set `cache: false` for tasks with side effects |
| Forgetting to set `globalEnv` | Env vars (NODE_ENV, secrets) affect the cache hash — declare them explicitly |
| Not using remote cache in CI | Set `TURBO_TOKEN` and `TURBO_TEAM`; without them, CI redoes work your laptop already did |
| Pinning `turbo` to `^1` | Turborepo 2.x uses `tasks`; keep configuration aligned with the installed major |

## Best Practices

1. **Define `outputs` precisely** — every file the task produces should be in the outputs list
2. **Use content hashing** — let Turborepo determine cache validity from inputs
3. **Leverage remote caching in CI** — share cache across team and CI
4. **Monitor cache hit rate** — `turbo run build --summarize` writes a JSON report
5. **Use `filter` for affected builds** — only build what changed since main
6. **Cache Docker layers with Turborepo** — see example above
7. **Use `env` for secrets** — declare env vars that affect the cache hash

## Summary

- Turborepo is a build orchestrator that runs tasks in dependency order, parallelizes where possible, and caches declared deterministic outputs
- Configure with `turbo.json` — declare `tasks`, `inputs`, `outputs`, `dependsOn`, and `env`
- Remote cache (`TURBO_TOKEN` + `TURBO_TEAM`) is the killer feature — shared across team and CI
- Use `filter` to build only what changed; `--filter=...[origin/main]` for affected changes
- Common pitfalls: missing outputs, missing env declarations, caching non-deterministic tasks

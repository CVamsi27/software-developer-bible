# Turborepo

Suppose `web` imports a workspace package named `ui`. A correct build must finish `ui` before `web`; a later run may reuse `ui`'s output only if every input that can change it matches. Turborepo models those task dependencies and cache conditions, but it does not infer every input or decide how to package the app for deployment.

## Definition

Turborepo is a task orchestrator for package-manager workspaces. It builds a graph of package tasks, waits for declared prerequisites, runs independent tasks concurrently, and can restore declared outputs when the task's computed inputs match a cached result. Compilers and bundlers still perform the package's build.

> **Textbook Definition:** Turborepo is a workspace task orchestrator that orders dependent tasks, schedules independent work, and reuses declared outputs through caching when task inputs match a prior execution.

## First Principles

A task result is reusable only when its identity represents every factor that can change its output. Dependency edges decide when prerequisites must finish; inputs decide whether a prior result still applies; outputs decide what a cache hit restores. A correct scheduler needs all three.

## How It Works

### 1. Follow a Task from Dependency to Cache

`dependsOn: ["^build"]` means "run this package's `build` after the `build` tasks of its workspace dependencies." `dependsOn: ["build"]` means "run this package's own `build` first." The scheduler applies those edges to the task graph; unrelated tasks can run in parallel.

For a task, Turborepo combines the resolved task configuration with relevant package files, dependency state, declared environment values, and explicit inputs into hashes. A cache hit reuses logs and only the files declared in `outputs`. The hash protects correctness only when the configuration includes every input that can change the result.

```text
web#build ──depends on──> ui#build ──depends on──> tokens#build
    │                         │                           │
    └──────── independent API tasks can run concurrently ─┘

matching task hash → restore declared files and logs
changed task/global hash → execute task, then cache declared result
```

Running `turbo run build` still considers the selected packages and their task graph. Cache hits avoid recomputation; filtering or `--affected` selects a smaller graph. Those are separate ways to reduce work.

### 2. Declare Task Inputs, Outputs, and Order

In Turborepo 2.x, `turbo.json` uses `tasks`. The example hashes the shared TypeScript configuration into every task, includes `NODE_ENV` in all task hashes, and treats integration tests as non-cacheable because their result depends on mutable external data.

```jsonc
// turbo.json
{
  "$schema": "https://turborepo.dev/schema.json",
  "globalDependencies": ["tsconfig.base.json"],
  "globalEnv": ["NODE_ENV"],
  "tasks": {
    "build": {
      "dependsOn": ["^build"],
      "outputs": ["dist/**"]
    },
    "test": {
      "dependsOn": ["^build"],
      "outputs": ["coverage/**"]
    },
    "test:integration": {
      "dependsOn": ["^build"],
      "cache": false,
      "passThroughEnv": ["TEST_DATABASE_URL"]
    },
    "lint": {},
    "typecheck": {
      "dependsOn": ["^build"]
    },
    "dev": {
      "cache": false,
      "persistent": true
    },
    "deploy": {
      "dependsOn": ["build"],
      "cache": false
    }
  }
}
```

By default, package files and manifests contribute to a task's hash. Use `inputs` only when a task needs a narrower or additional file set. `globalDependencies` makes a shared file invalidate every task; `inputs` limits file rules to a task. Keep `outputs` precise: they are package-relative files Turbo restores on a cache hit. An empty or omitted `outputs` list caches logs but no files.

Environment variables need the same care. `env` or `globalEnv` makes values available in strict mode and includes them in the relevant task hash. Use `passThroughEnv` only when a task needs a value that cannot affect its outputs. Inject secrets from the CI secret store; never put their values in `turbo.json` or cached output. Do not cache deploys, migrations, or tests against mutable external state.

Keep framework-specific output paths next to the relevant package. A Next.js package can extend the root task without replacing its output list:

```jsonc
// apps/web/turbo.json
{
  "extends": ["//"],
  "tasks": {
    "build": {
      "outputs": ["$TURBO_EXTENDS$", ".next/**", "!.next/cache/**"]
    }
  }
}
```

Package configuration arrays replace inherited arrays unless they begin with `$TURBO_EXTENDS$`. Without that marker, this package would drop the root `dist/**` output. Ignore generated directories such as `.turbo/`, `dist/`, `.next/`, and coverage in version control; do not ignore configuration or lockfiles that affect results.

### 3. Select Packages Deliberately

Filtering selects package relationships; `--affected` compares a source-control range and selects work associated with changes. Confirm the intended base branch is fetched in continuous integration (CI), or the affected set can be empty or incomplete.

```bash
# Build @acme/web and its workspace dependencies
turbo run build --filter='@acme/web...'

# Test @acme/ui and its workspace dependents
turbo run test --filter='...@acme/ui'

# In CI, select affected tasks relative to the fetched main branch
TURBO_SCM_BASE=origin/main turbo run build test --affected
```

The first filter includes a package and its dependencies; a leading ellipsis includes dependents. `--affected` needs a valid source-control base and head. Inspect its selected package list, and retain periodic wider integration checks for relationships the graph cannot infer.

### 4. Share Remote Results Without Trusting Every Writer

Remote caching lets CI and developer machines reuse compatible task outputs. For Vercel Remote Cache, authenticate and link the repository with the CLI, then provide `TURBO_TOKEN` and `TURBO_TEAM` to the CI job. A custom cache requires an API-compatible endpoint and its own `remoteCache.apiUrl` configuration; setting those two variables alone does not create a self-hosted service.

Cached artifacts are executable build inputs. Limit who can write to the cache, declare only the files consumers need, and make sure tasks never write credentials into outputs or logs. Turborepo can sign remote artifacts; enable `remoteCache.signature` and set the same `TURBO_REMOTE_CACHE_SIGNATURE_KEY` in trusted writers and readers so the client verifies downloaded artifacts. Keep that key in a secret store, not the repository.

### 5. Prove Cache Correctness Before Measuring Speed

Use a repeatable build and check the cache contract before comparing durations:

| Test | Expected result |
| ---------------------------------------------------------------------------------------------- | ---------------------------------------------------- |
| Run a build, delete its declared output, then run it again | Cache hit restores the output files |
| Change a source file, package dependency, shared config, or output-affecting environment value | The relevant task misses cache and runs again |
| Change an unrelated package | Unrelated task remains eligible for a cache hit |
| Run from a clean CI worker with the same lockfile and inputs | It restores only artifacts whose hashes match |
| Use a different database state with an integration test | The test executes instead of reusing a cached result |

Compare uncached duration, cache-hit rate, artifact transfer time, and CI wait time on the real workload. A higher hit rate is not a win if the task graph omits required work or remote artifacts cost more to transfer than to rebuild.

Docker adds another cache boundary: Docker can reuse image layers, while Turborepo can reuse task outputs. Neither creates a deployable runtime by itself. For Next.js, configure tracing to include required workspace files and copy standalone output plus static/public assets. For pnpm packages, preserve workspace links and store contents or use a pruning/deployment workflow; copying only a symlinked `node_modules` directory can leave broken links. See the [Docker multi-stage build chapter](../40.1-docker/40.1.04-multi-stage-builds.md).

## Summary

Turborepo schedules declared package tasks and reuses outputs when their hashes match. `dependsOn` defines order, `outputs` defines what a hit restores, and environment and file inputs define whether reuse is valid. Filtering and `--affected` select work; caching skips recomputation. Verify those boundaries before using remote speedups.

# Nx

## Definition

Nx is a build orchestrator and developer platform from Nrwl. Like Turborepo, it builds a dependency graph, parallelizes work, and caches results. Where it differs: rich plugin ecosystem with generators, executors, and a visual dependency graph. Strongest in large Angular / React / Node monorepos.

> **Textbook Definition:** Nx is a project and task orchestration platform that models dependencies, schedules work, and caches results, with plugins supplying project discovery, generators, and execution behavior.

## First Principles

Projects depend on other projects, and tasks need artifacts from those dependencies. A project graph answers which code can be affected; a task graph adds execution ordering. Neither graph decides which imports are allowed.

1. **Plugins encode framework knowledge**: Nx knows what a Next app's build/test/serve targets *are* — generators and executors standardize the graph. The trade: convention over configuration (→ 20.13.05's Spring insight, for repos).
2. **Module boundaries are enforceable**: lint rules restricting which libs may import which — architecture-as-checked-constraint (→ 30.1's boundaries, mechanized).

## Why It Matters

- **Generators** — scaffold new apps, libs, components with one command
- **Affected commands** — only run tasks on projects that depend on a changed file
- **Computation cache** — local + remote (Nx Cloud) cache by content hash
- **Dependency graph** — visual representation of inter-project relationships
- **Plugin ecosystem** — first-class support for React, Angular, Node, Next.js, etc.

## Nx vs Turborepo (2026)

| Dimension | Nx | Turborepo |
| ----------------- | ----------------------------------------------- | ------------------------------------------------------- |
| Project structure | `project.json` per project (or `package.json`) | `package.json` only |
| Generators | First-class (e.g., `nx g @nx/react:lib`) | Generators via `turbo gen` |
| Dependency graph | Built-in, visual (`nx graph`) | Inspect packages/tasks with CLI tools and dry-run graph |
| Task definition | `project.json` targets with executors | `turbo.json` tasks |
| Affected | `nx affected -t test --base=main` | `turbo run test --filter=...[main]` |
| Remote cache | Nx Cloud (Plan-specific; check current pricing) | Vercel remote cache (free with Vercel account) |
| Plugin ecosystem | Large (React, Angular, Node, Next.js, etc.) | Smaller; framework-agnostic |
| Learning curve | Steeper (more concepts) | Gentler |
| Best for | Large monorepos, Angular, code generation | Simple to medium monorepos, plain JS/TS |

## Code Examples

### 1. Workspace Setup (pnpm + Nx Preset)

```bash
# Create a new Nx workspace with pnpm
npx create-nx-workspace@latest myorg \
  --preset=react-monorepo \
  --packageManager=pnpm \
  --useGitHub

# Add a new React library
npx nx g @nx/react:lib packages/ui-button

# Add a new Node API
npx nx g @nx/node:app apps/api
```

```json
// nx.json (workspace config)
{
  "targetDefaults": {
    "build": {
      "cache": true,
      "dependsOn": ["^build"],
      "inputs": ["production", "^production"]
    },
    "test": {
      "cache": true,
      "inputs": ["default", "^production", "{workspaceRoot}/jest.preset.js"]
    },
    "lint": {
      "cache": true,
      "inputs": ["default", "{workspaceRoot}/eslint.config.mjs"]
    }
  },
  "namedInputs": {
    "default": ["{projectRoot}/**/*", "sharedGlobals"],
    "production": [
      "default",
      "!{projectRoot}/**/?(*.)+(spec|test).[jt]s?(x)?(.snap)",
      "!{projectRoot}/tsconfig.spec.json"
    ],
    "sharedGlobals": ["{workspaceRoot}/tsconfig.base.json"]
  }
}
```

```json

{
  "name": "ui-button",
  "$schema": "../../node_modules/nx/schemas/project-schema.json",
  "sourceRoot": "packages/ui-button/src",
  "projectType": "library",
  "targets": {
    "build": {
      "executor": "@nx/vite:build",
      "outputs": ["{workspaceRoot}/dist/packages/ui-button"],
      "options": {
        "outputPath": "dist/packages/ui-button"
      }
    },
    "test": {
      "executor": "@nx/jest:jest",

      "options": {
        "jestConfig": "packages/ui-button/jest.config.ts"
      }
    },
    "lint": {
      "executor": "@nx/eslint:lint"
    },
    "storybook": {
      "executor": "@nx/storybook:storybook",
      "options": {
        "port": 4400
      }
    }
  },
  "tags": ["scope:ui", "type:lib"]
}
```

### 3. Affected Commands (CI Optimization)

```bash
# Run tests only for projects affected by changes since main
npx nx affected -t test --base=main --head=HEAD

# Build, test, and lint affected projects
npx nx affected --target=build,test,lint --base=main

# Show what would be affected
npx nx graph --affected --base=main
```

### 4. Module Boundary Enforcement (Tags + ESLint)

Tags belong to each project's configuration (the UI library above already declares `scope:ui`). The ESLint rule compares the importing project's tags with the imported project's tags. Put the rule in the root flat ESLint configuration with `@nx/eslint-plugin` installed:

```javascript
// eslint.config.mjs — add to the workspace's generated config
import nx from '@nx/eslint-plugin';
export default [
  ...nx.configs['flat/base'],
  ...nx.configs['flat/typescript'],
  ...nx.configs['flat/javascript'],
  {
    files: ['**/*.{ts,tsx,js,jsx}'],
    rules: {
      '@nx/enforce-module-boundaries': ['error', {
        depConstraints: [
          { sourceTag: 'scope:ui', onlyDependOnLibsWithTags: ['scope:ui', 'scope:utils'] },
          { sourceTag: 'scope:utils', onlyDependOnLibsWithTags: ['scope:utils'] },
          { sourceTag: 'scope:api', onlyDependOnLibsWithTags: ['scope:api', 'scope:utils'] },
        ],
      }],
    },
  },
];
```

A `scope:ui` project importing `scope:api` fails this rule when lint runs. A project also tagged `type:util` must not silently become an exception: a list of allowed target tags is an OR condition. Enforce separate scope/type constraints when both dimensions matter. Run lint through Nx or generate the project graph before invoking ESLint directly. The rule can skip when no cached graph is available; treat that warning as missing enforcement. Lint enforcement is a development gate, not runtime access control.

### 5. Generator Example (Custom Generator)

```typescript
// tools/generators/library/index.ts
import { Tree, formatFiles, generateFiles, names } from '@nx/devkit';

interface Schema {
  name: string;
  directory: string;
}

export default async function (tree: Tree, schema: Schema) {
  const { fileName, className } = names(schema.name);
  generateFiles(tree, __dirname, `${schema.directory}/${fileName}`, {
    fileName,
    className,
    tmpl: '',
  });
  await formatFiles(tree);
}
```

```bash
# Use the generator
npx nx g @myorg/tools:library button --directory=packages/ui
```

### 6. Visualizing the Dependency Graph

```bash
# Open interactive graph in browser
npx nx graph

# Show only affected projects
npx nx graph --affected --base=main

# Headless graph (CI artifact)
npx nx graph --file=graph.json
```

## Real-World Decision: A Shared Library Changes

Suppose `checkout` and `admin` depend on `money`, while `marketing` does not. Changing `money` marks it and its dependent projects affected. Their selected build/test tasks run or restore valid outputs; `marketing` can be excluded. A shared compiler configuration or lockfile change may affect many more projects.

Use a fetched, known base commit and the intended head commit. In a pull request, `main` may be absent or point at the wrong checkout; in post-merge CI, comparing HEAD against itself selects nothing. Check the reported affected projects and retain periodic wider integration checks for dependencies the graph cannot infer.

## Common Mistakes

| Mistake | Fix |
| ------------------------------------------- | --------------------------------------------------------------------------- |
| No `project.json` for non-standard projects | Add a minimal `project.json` so Nx can run tasks against it |
| Manual dependency graph maintenance | Use `nx graph` and `nx show projects` to inspect; let Nx infer from imports |
| Skipping module boundary enforcement | Add `depConstraints` in ESLint to prevent cross-module imports |
| Building the whole monorepo on every PR | Use `nx affected` in CI — only build changed projects + their dependents |
| Not using generators | Generators enforce structure and save hours per new project |

## Best Practices

1. **Use `nx affected` in CI** — only build/test/lint what changed
2. **Enforce module boundaries with tags** — prevent accidental cross-module coupling
3. **Use generators for new projects** — consistent structure, less boilerplate
4. **Cache the lockfile inputs** — declare it in `namedInputs` for stable cache keys
5. **Distribute tasks with Nx Cloud** — even further speedup via task splitting across CI agents
6. **Run `nx graph --watch` in dev** — visualize the impact of your changes
7. **Set `cache: true` only for deterministic tasks** — never cache deploys or migrations

## Summary

- Nx is a build orchestrator and developer platform with first-class generators and a dependency graph
- Strongest in large monorepos with multiple teams and strict module boundaries
- Use `nx affected` in CI to only build changed projects
- Module boundary enforcement via tags + ESLint prevents accidental coupling
- Nx Cloud provides remote cache and distributed task execution

# Nx

Changing a shared library can break several applications even when their source files did not change. Nx helps identify and order the work affected by that change. It can also reuse a prior result, but only when the task’s declared inputs match.

## Definition

**Nx** is a workspace platform that discovers projects, builds project and task graphs, runs tasks, and can cache their results. Plugins can infer project metadata and targets from framework or tool configuration. Nx also provides generators and architectural-boundary checks.

> **Textbook Definition:** Nx is an extensible project- and task-graph orchestration system that analyzes workspace relationships, schedules target executions, selects affected work, and reuses outputs when task inputs match a prior computation.

## First Principles

Three questions require three different models:

1. **Which projects are related?** The project graph records project dependencies.
2. **Which operations must run, and in what order?** The task graph records target-to-target prerequisites.
3. **Which previous result is safe to reuse?** The cache key represents every input that can affect that task’s output.

An accurate graph cannot fix a missing task edge, and a cache cannot fix an incomplete input model. Keep project relationships, task ordering, and result validity distinct when diagnosing CI.

## Trace one library change

Suppose <code>storefront</code> and <code>admin</code> both import <code>money</code>. Nx discovers those projects and their dependencies from workspace manifests, project configuration, source imports, TypeScript configuration, and registered plugins. You can inspect the result with:

~~~bash
npx nx graph
npx nx show project storefront
~~~

The **project graph** describes repository relationships. It is not necessarily the same as the full runtime or deployment graph: dynamic imports, external systems, generated code, and deployment dependencies may need explicit modeling.

A project exposes **targets**, such as <code>build</code>, <code>test</code>, or <code>lint</code>. Nx can get them from package scripts, a project’s <code>project.json</code>, or plugin inference from files such as <code>vite.config.ts</code>. Inspect <code>nx show project storefront</code> to see the resolved targets and their sources. Configuration is layered: plugin-inferred settings, workspace <code>targetDefaults</code>, then project-level settings.

The **task graph** contains concrete operations such as <code>money:build</code> and <code>storefront:build</code>. The project graph says the app uses the library; the target configuration decides whether the library’s build must finish first:

~~~json
{
  "targetDefaults": {
    "build": {
      "dependsOn": ["^build"],
      "cache": true
    }
  }
}
~~~

Here, <code>^build</code> means the build targets of a project’s dependencies. It creates an ordering edge; it does not mean every target depends on every target of every library. Independent tasks can run in parallel.

## Select affected work safely

<code>nx affected</code> compares a Git base and head, maps changed files to projects, and follows the project graph to select work. If <code>money</code> changes, both apps can be affected. A change to a leaf project may select fewer projects; a shared configuration or dependency-lockfile change can select many or all.

In CI, use the merge request’s intended base and head commits, and fetch enough Git history to make both available. A wrong base can under-select changes or make a run appear to affect nothing.

~~~bash
npx nx affected -t lint test build \
  --base=origin/main \
  --head=HEAD

npx nx graph --affected --base=origin/main
~~~

The first command selects all requested targets for affected projects under the default project-selection behavior. In current Nx versions, setting <code>NX_LEGACY_AFFECTED=false</code> opts into task-level selection based on task inputs. This can avoid running a task whose inputs do not reach the changed file, but it depends on correct input, output, and task-dependency declarations. Do not enable it as a speed switch without testing both dependency changes and generated outputs.

Affected selection and caching solve different problems. Affected selection decides which projects or tasks enter the run. Caching decides whether a selected task executes or restores a matching result. A broad affected set can still be fast with valid cache hits; an incorrect affected set can silently skip required checks.

## Make cache reuse a correctness claim

Nx hashes declared task inputs, relevant configuration, dependencies, and other configured values. On a matching local or remote result, it can restore terminal output and declared artifacts instead of recomputing the task.

A task is safe to cache only when its result is determined by the modeled inputs. Include output-affecting source, shared configuration, toolchain versions, and environment values. Declare produced files so they can be restored. Do not cache deployments, migrations, or tests whose answers depend on mutable external state unless that state is represented in a deliberate, reproducible way.

Remote cache adds a trust boundary: an artifact produced by another machine becomes an input to this build. Restrict cache writers, protect credentials, and verify that CI and developer environments use compatible inputs. Nx Agents distribute tasks across machines; distribution changes where work runs, not what makes a task correct.

## Use generators and boundaries to preserve architecture

A generator is a repeatable code transformation. It can create a project with the repository’s expected files, tags, scripts, and configuration:

~~~bash
npx nx g @nx/react:lib packages/ui
~~~

Use a plugin generator when it matches the project. Add a custom generator when a repeated organization-specific change is easier to validate and maintain as code than as a checklist. Generated files still need code review and tests.

Tags can describe project ownership or architectural role. The <code>@nx/enforce-module-boundaries</code> rule for JavaScript and TypeScript checks imports during linting; Nx Conformance can check project-graph boundaries across languages; the current Nx documentation lists this as an Enterprise feature. A graph only reports relationships. Boundary rules define which relationships are allowed.

For example, separate scope from layer so a <code>shared</code> label cannot accidentally let an API depend on a UI project:

~~~json
{
  "depConstraints": [
    {
      "sourceTag": "scope:shared",
      "onlyDependOnLibsWithTags": ["scope:shared"]
    },
    {
      "sourceTag": "scope:api",
      "onlyDependOnLibsWithTags": ["scope:api", "scope:shared"]
    }
  ]
}
~~~

Each allowed-target tag list is an OR condition: a dependency may match any listed tag. When multiple architectural dimensions matter, add separate constraints and test both allowed and forbidden imports. Lint checks are development gates, not runtime authorization.

## Decide whether Nx earns its complexity

Nx is a strong fit when project discovery, plugin-inferred targets, generators, affected selection, architectural constraints, or distributed execution solve recurring problems in the repository. A smaller workspace with package scripts and straightforward dependency order may need only package-manager workspaces and a task runner.

Do not choose by team size or framework label alone. Pilot one shared-library change, one shared-config change, a clean build, and a cache hit/miss. Review the discovered graph, selected tasks, restored files, editor/tool compatibility, and the maintenance cost of custom configuration.

## Summary

Nx discovers projects and their relationships, turns targets into an ordered task graph, selects work from a Git change range, and can restore matching task outputs. Project selection, task ordering, cache validity, and dependency boundaries are separate contracts. Inspect and test each before relying on a faster continuous integration (CI) run.

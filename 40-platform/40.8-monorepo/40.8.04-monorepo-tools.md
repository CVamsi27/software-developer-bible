# Monorepo Tools Deep-Dive (Lerna, pnpm, Yarn, Rush, Bazel)

Edit one shared package and two applications must rebuild — but rerunning every task in the repository wastes hours, and rebuilding only the edited package can ship stale output. Choosing a coordinator starts with the job that is actually hard: installation, task order, caching, or release.

## Definition

**Monorepo tooling** coordinates work across projects stored in one repository. A **package manager** installs and links dependencies. A **task runner** schedules build, test, and lint scripts in dependency order. A **build system** describes how inputs become outputs; release tools manage versions and publication. Some products cover several jobs, so choose the responsibilities before choosing product names.

> **Textbook Definition:** Monorepo tooling coordinates dependency installation, project relationships, task execution, and release workflows across projects; package managers, task orchestrators, and build systems own different parts of that process.

## First Principles

Installing a dependency, deciding which package to build first, and deciding whether an old output is reusable are different problems. A shared library can install correctly while its consumer builds against stale output. Model package links and task dependencies separately. A cache also needs all output-affecting inputs: source, configuration, toolchain, and relevant environment values. Repository size does not establish whether that model is correct. Begin with a reliable uncached build, then measure which repeated work is worth avoiding.

## How It Works

### 1. Follow One Shared-Library Change

Two applications depend on `utils`. A change to `utils` can require rebuilding both applications; an unrelated documentation change may require neither. The package manager makes `utils` resolvable, the task runner orders its build before dependent builds, and the compiler produces each artifact. A release tool separately decides which packages and dependency ranges to publish.

Choose tooling for the part that is difficult to maintain. Generators and boundary rules can help project consistency; declared build actions can improve reproducibility; neither removes the need to validate the actual dependency graph.

### 2. Choose a Workspace Resolver Deliberately

A workspace package is still a package with its own manifest and dependencies. The package manager decides how local packages resolve and which undeclared imports can accidentally work because of installation layout. These behaviors vary with linker configuration, so test the exact repository setup rather than treating a feature table as universal.

| Manager | Local package resolution | What to validate |
| ------------ | ------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------- |
| pnpm | Workspace packages are linked; `workspace:` requires a local match. The default isolated layout reduces accidental access to undeclared packages. | Check tools that expect a hoisted layout, peer-dependency behavior, and the packed manifest. |
| npm | npm workspaces link local packages using version specifications; npm does not use pnpm/Yarn's `workspace:` protocol. | Hoisting can make undeclared imports appear available. Test from each package and in a clean consumer. |
| Modern Yarn | Supports the `workspace:` protocol and either Plug'n'Play or a configured `node-modules` linker. | With Plug'n'Play, validate the loader, editor SDKs, and tools. With `node-modules`, validate the actual hoisting behavior. |
| Yarn Classic | Uses workspaces with the `node-modules` layout and hoisting. | Treat it as a distinct, older toolchain; do not assume modern Yarn commands or configuration apply. |

A successful root install does not prove that a package declares every dependency it imports. Run package-level checks and install the packed artifact in a clean consumer before publishing.

### 3. Compare Task Runners by Responsibility

| Dimension | Turborepo | Nx | Lerna | Rush | Bazel |
| --------------- | ------------------------------ | ---------------------------------------------- | -------------------------- | ------------------------------- | ---------------------------------------------- |
| Configuration | `turbo.json` | `nx.json` plus project/package configuration | `lerna.json` | `rush.json` and project files | `BUILD` files and rules |
| Cache | Local + Vercel | Local + Nx Cloud | Nx-backed local/remote | Local + Rush storage | Local + remote |
| Affected | `--filter=...[base]` | `nx affected` | `lerna changed` | Incremental project selection | Query-based |
| Generators | `turbo gen` | First-class | Limited | Plugins | Rules |
| Toolchain scope | Workspace task scripts | Plugin-supported projects and configured tasks | JavaScript package tasks | JavaScript repository workflows | Declared actions and configured language rules |
| Evaluate for | Script task graphs and caching | Graphs, generators and boundaries | Package tasks and releases | Coordinated package policies | Declared actions and toolchains |

### 4. Choose from Constraints, Then Run a Pilot

| Constraint | Candidate to evaluate | Evidence before adoption |
| ------------------------------------------------ | ------------------------------------------ | --------------------------------------------------------------------- |
| Package links and ordered scripts | Workspaces plus a small task runner | Clean checkout builds in the correct dependency order |
| Project generators and enforceable boundaries | Nx and its applicable plugins | Forbidden dependencies fail; affected selection covers changes |
| Coordinated JavaScript package policies/releases | Rush or an existing Lerna workflow | Install, versioning and publication preserve repository policy |
| Declared actions across toolchains | Bazel with maintained rules | Required languages work; generated inputs and toolchains are declared |
| Independent package releases | Changesets, Nx Release or existing tooling | Tarballs and dependent ranges match the reviewed version set |

Pilot the same representative change, clean build, and cache hit/miss with each candidate. Include editor compatibility, onboarding, maintenance, and migration cost. A ten-person team can need strict reproducibility; a large team can still have a simple script graph. Team size alone cannot select the tool.

## Code Examples

### 1. pnpm Filter (Recursive Operations)

```bash
# Run in a specific package
pnpm --filter @myorg/web dev

# Run in package and its dependencies (build order: deps first)
pnpm --filter @myorg/web... build

# Run in packages that depend on @myorg/utils
pnpm --filter ...@myorg/utils test

# Run in all packages (no filter)
pnpm -r run lint

# Select packages by a directory glob (pnpm filters are not Nx tag selectors)
pnpm --filter './packages/ui-*' run build
```

### 2. Yarn Berry Plug'n'Play (PnP)

```yaml
# .yarnrc.yml
nodeLinker: pnp
enableGlobalCache: false
```

```bash
# Zero-installs — commit .yarn/cache to git
yarn install
yarn workspaces foreach -A -t run build

# Zero-install requires committed .pnp.cjs and cache artifacts.
# Validate pull requests, including cache contents, before using them:
yarn install --immutable --immutable-cache --check-cache
```

PnP's `.pnp.cjs` is the dependency loader, not a replacement for missing dependency declarations. Check editor and tool integration under the selected Yarn version. Use supported SDK integration where needed, or deliberately choose `nodeLinker: node-modules` when the toolchain requires that layout.

### 3. Lerna: Package Tasks and Releases

Modern Lerna uses the package manager for installation and Nx for task scheduling/caching:

```bash
pnpm install --frozen-lockfile
npx lerna run build
npx lerna run test --since=origin/main
npx lerna changed
# Release operation, only in an authorized release workflow:
npx lerna publish
```

`lerna bootstrap` belongs to the removed legacy installation model. Existing Lerna users can keep its version/publish workflow; migrating to Changesets is a policy choice, not a response to Lerna being deprecated.

### 4. Rush — Coordinated JavaScript Projects

With a reviewed Rush CLI installed, run `rush init` in the new repository to generate its configuration. Review `rush.json`, register each project, and preserve compatible pinned Rush/package-manager versions. A three-field object copied from another release is not a complete Rush configuration.

```bash
# New repository: generate configuration, then review it and register projects.
rush init
# After project setup and dependency review, update the tracked install state.
rush update
# Subsequent reproducible installs and builds:
rush install
rush build
rush change
# Publishing requires its own authorized, configured release workflow.
```

Rush owns the repository's package-manager installation and lockfile workflow. Do not independently run a competing root install or publish command and assume Rush's state will stay consistent.

### 5. Bazel (Google) — When You Need Multi-Language

A Bazel target names its source files, dependencies, and the rule/toolchain that transforms them. Building `//apps/web:web` schedules the actions needed by that target; a query such as `bazel query 'deps(//apps/web:web)'` inspects the declared dependency closure.

JavaScript rules require a configured module/lockfile integration and explicit rule imports. A `ts_library` name without its rule definition or repository setup is not a runnable build. Choose maintained rules for the installed Bazel version, declare generated inputs, and verify sandboxed builds before calling them hermetic. Bazel can suit smaller repositories with demanding reproducibility; engineer count alone is not a threshold.

## Common Mistakes

| Mistake | Fix |
| ----------------------------------- | -------------------------------------------------------------------------------- |
| Choosing Bazel from team size alone | Compare reproducibility needs and supported rules against setup/maintenance cost |
| Phantom dependencies in npm/Yarn | Use pnpm strict mode or Yarn PnP |
| Lerna for new projects | Compare active Lerna, Changesets and Nx Release |
| Mixing Rush and pnpm | Rush manages its own pnpm install; don't run `pnpm install` at root |
| Committing `node_modules` | Use pnpm's content-addressable store or Yarn Berry's PnP cache |

## Best Practices

Choose one owner for dependency installation and record compatible toolchain versions. Make local links, task inputs, and outputs explicit. Verify uncached correctness before enabling remote reuse; protect cache writers and exclude secrets from outputs. Add versioning automation only where publication or coordinated releases require it, and document the evidence behind the choice.

Revisit tooling when constraints change, such as another language, unreliable affected selection, or increasing build time. A measured limitation is a stronger migration reason than a calendar date or a vendor's team-size category.

## Summary

Package management, task execution, build rules, and release policy own different jobs. Select the smallest combination that meets the repository's constraints, test dependency order and cache correctness, and evaluate compatibility and maintenance cost. No product or team-size threshold supplies those guarantees automatically.

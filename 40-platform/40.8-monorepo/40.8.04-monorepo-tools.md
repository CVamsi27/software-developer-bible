# Monorepo Tools Deep-Dive (Lerna, pnpm, Yarn, Rush, Bazel)

## Definition

The monorepo toolchain splits into three layers: (1) **package manager** (pnpm, Yarn, npm) handles installs and workspaces; (2) **task graph runner** (Turborepo, Nx, Lerna) orchestrates build/test/lint; (3) **advanced build systems** (Bazel) model build actions and declared toolchains; Rush coordinates large JavaScript package repositories and release workflows. Hermeticity depends on rule and toolchain configuration.

> **Textbook Definition:** Monorepo tooling coordinates dependency installation, project relationships, task execution, and release workflows across projects; package managers, task orchestrators, and build systems own different parts of that process.

## First Principles

The tool comparison follows from where your complexity lives:

1. **Installation, task ordering and reproducibility are different constraints** — choose a resolver for package links, an orchestrator for task dependencies, and hermetic build rules when undeclared host inputs must be excluded.
2. **The shared foundation is non-negotiable**: task graph, remote cache, affected-detection — these capabilities solve distinct problems; package managers and release tools need not supply all three (→ 40.8.01's tooling-is-mandatory axiom).

## Why It Matters

- **Tooling choice compounds** — picking the right stack upfront saves years of pain
- **Lerna is active** — its modern task execution and caching use Nx; its old bootstrap workflow is retired
- **Yarn Berry / pnpm offer workspace isolation choices** for JS/TS
- **Rush / Bazel** solve problems that Turborepo and Nx don't

## Package Managers Compared

| Feature | pnpm 9 | npm 10 | Yarn Berry 4 | Yarn Classic 1 |
| ---------------------- | ---------------------------- | ------------------------ | ---------------------------------------- | ------------------------- |
| Install speed | Measure workload | Measure workload | Fast (PnP) | Medium |
| Disk usage | Lowest (content-addressable) | High (per-project) | Lowest (PnP) | High |
| Phantom dep prevention | Yes (strict) | No | Yes (PnP) | No |
| Workspace protocol | `workspace:*` | Compatible version range | `workspace:*` | Compatible version range |
| Node version manager | Built-in (`pnpm env`) | External (nvm) | External; Corepack selects Yarn versions | External |
| Lockfile | `pnpm-lock.yaml` | `package-lock.json` | `yarn.lock` | `yarn.lock` |
| Best for | Explicit package isolation | Broad npm compatibility | PnP or node-modules workflows | Existing Classic projects |
| Plug'n'Play (PnP) | No | No | Yes (default) | No |

## Task Runners Compared

| Feature | Turborepo | Nx | Lerna (Nx-backed) | Rush | Bazel |
| -------------- | ---------------------- | ----------------------------- | ---------------------- | ----------------------------- | ----------------------------- |
| Status | Active (Vercel) | Active (Nrwl) | Active | Active (Microsoft) | Active (Google) |
| Configuration | `turbo.json` | `nx.json` + `project.json` | `lerna.json` | `rush.json` | `BUILD` files |
| Cache | Local + Vercel | Local + Nx Cloud | Nx-backed local/remote | Local + Rush storage | Local + remote |
| Affected | `--filter=...[base]` | `nx affected` | `lerna changed` | Incremental project selection | Query-based |
| Generators | `turbo gen` | First-class | Limited | Plugins | Rules |
| Polyglot | Runs arbitrary scripts | Plugins and arbitrary scripts | Package scripts | JavaScript package workflows | Rules for declared toolchains |
| Learning curve | Low | Medium | Low | Medium | High |
| Best for | Simple to medium | Large JS/TS | Legacy | Microsoft stacks | Multi-language, Google-scale |

## Code Examples

### 1. pnpm Filter (Recursive Operations)

```bash
# Run in a specific package
pnpm --filter @myorg/web dev

# Run in package and its dependencies (build order: deps first)
pnpm --filter @myorg/web... build

# Run in packages that depend on @myorg/utils
pnpm --filter ...@myorg/utils test

# Run in all packages (no filter)
pnpm -r run lint

# Select packages by a directory glob (pnpm filters are not Nx tag selectors)
pnpm --filter './packages/ui-*' run build
```

### 2. Yarn Berry Plug'n'Play (PnP)

```yaml
# .yarnrc.yml
nodeLinker: pnp
enableGlobalCache: false
```

```bash
# Zero-installs — commit .yarn/cache to git
yarn install
yarn workspaces foreach -A -t run build

# Zero-install requires committed .pnp.cjs and cache artifacts.
# Validate pull requests, including cache contents, before using them:
yarn install --immutable --immutable-cache --check-cache
```

Trade-offs: PnP breaks some tools (Jest, Webpack legacy loaders) — `.pnp.cjs` shim or `nodeLinker: node-modules` for compatibility.

### 3. Lerna: Package Tasks and Releases

Modern Lerna uses the package manager for installation and Nx for task scheduling/caching:

```bash
pnpm install --frozen-lockfile
npx lerna run build
npx lerna run test --since=origin/main
npx lerna changed
# Release operation, only in an authorized release workflow:
npx lerna publish
```

`lerna bootstrap` belongs to the removed legacy installation model. Existing Lerna users can keep its version/publish workflow; migrating to Changesets is a policy choice, not a response to Lerna being deprecated.

### 4. Rush — Coordinated JavaScript Projects

```json
// rush.json (excerpt)
{
  "projects": [
    { "packageName": "@myorg/web", "projectFolder": "apps/web" },
    { "packageName": "@myorg/ui", "projectFolder": "packages/ui" },
    { "packageName": "@myorg/utils", "projectFolder": "packages/utils" }
  ],
  "pnpmVersion": "9.0.0",
  "rushVersion": "5.0.0",
  "repository": { "url": "https://github.com/myorg/monorepo" }
}
```

```bash
rush install # install everything
rush build # build all projects
rush change # write changelog entries
rush publish # version + publish
```

### 5. Bazel (Google) — When You Need Multi-Language

A Bazel target names its source files, dependencies and the rule/toolchain that transforms them. Building `//apps/web:web` schedules the actions needed by that target; a query such as `bazel query 'deps(//apps/web:web)'` inspects the declared dependency closure.

JavaScript rules require a configured module/lockfile integration and explicit rule imports. A `ts_library` name without its rule definition or repository setup is not a runnable build. Choose maintained rules for the installed Bazel version, declare generated inputs, and verify sandboxed builds before calling them hermetic. Bazel can suit smaller repositories with demanding reproducibility; engineer count alone is not a threshold.

## Real-World Architecture Decisions

```text
DECISION TREE:
┌──────────────────────────────────────────────────┐
│ JS/TS only, small team (< 20)                    │
│ → pnpm workspaces + Turborepo                    │
│                                                  │
│ JS/TS only, medium team (20-100)                 │
│ → pnpm + Nx (for generators + module boundaries) │
│ OR pnpm + Turborepo + Changesets                 │
│                                                  │
│ JS/TS only, large team (100+)                    │
│ → pnpm + Nx + Nx Cloud                           │
│ OR Yarn Berry + Rush                             │
│                                                  │
│ Multi-language (TS + Go + Python + Rust)         │
│ → Bazel                                          │
│                                                  │
│ Migrating from Lerna                             │
│ → Changesets + Turborepo (or Nx)                 │
└──────────────────────────────────────────────────┘
```

## Common Mistakes

| Mistake | Fix |
| ----------------------------------- | --------------------------------------------------------------------------- |
| Choosing Bazel for a small monorepo | Bazel's learning curve is brutal; only adopt for multi-language or >100 eng |
| Phantom dependencies in npm/Yarn | Use pnpm strict mode or Yarn PnP |
| Lerna for new projects | Compare active Lerna, Changesets and Nx Release |
| Mixing Rush and pnpm | Rush manages its own pnpm install; don't run `pnpm install` at root |
| Committing `node_modules` | Use pnpm's content-addressable store or Yarn Berry's PnP cache |

## Best Practices

1. **Pick one package manager** — don't mix pnpm and Yarn in the same repo
2. **Use explicit local links** — pnpm/Yarn support `workspace:*`; npm uses compatible workspace version ranges
3. **Pin the toolchain** — `packageManager: pnpm@9.0.0` in root `package.json`
4. **Adopt Changesets for versioning** — even for private packages
5. **Set up remote cache early** — biggest ROI of Turborepo / Nx
6. **Document the choice** — explain in CONTRIBUTING.md why the team uses X over Y
7. **Re-evaluate annually** — the monorepo ecosystem moves fast

## Summary

- Choose the package resolver, task orchestrator and release workflow separately; pnpm plus Turborepo/Nx and Changesets is one combination.
- Lerna remains active with Nx-backed tasks; compare its release workflow with Changesets
- Yarn Berry's PnP is excellent for large monorepos with zero-install
- Rush is the Microsoft-grade alternative for very large JS/TS
- Bazel is the right answer for multi-language or Google-scale builds

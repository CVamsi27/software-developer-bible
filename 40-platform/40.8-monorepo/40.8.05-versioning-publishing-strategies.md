# Versioning & Publishing Strategies

Changing a package and its in-repository consumers in one commit does not make an external release safe. Consumers receive versioned package artifacts, while release automation decides which packages to version, what dependency ranges to publish, and which authorized identity may publish them.

## Definition

**Package versioning** is the policy for assigning versions to packages and updating their dependency references as their public contracts change. **Publishing** is the controlled process that builds, verifies, authorizes, and distributes those package artifacts through a registry.

> **Textbook Definition:** A monorepo release strategy defines how package versions and inter-package compatibility are selected, then governs the validation, authorization, and distribution of the resulting artifacts and metadata.

## First Principles

A safe release keeps four decisions explicit:

- **Intent** (which package changed, and what compatibility level should consumers expect).
- **Version set** (which packages need new versions, and which internal dependency ranges must move with them).
- **Artifact** (what exact files and metadata will consumers install).
- **Authorization and evidence** (which CI identity may publish, and what evidence links the artifact to reviewed source).

A tool can automate these decisions, but its configuration does not prove that the selected packages, tarballs, credentials, or attestations are correct.

## 1. Choose a Version Policy from the Consumer Contract

Semantic Versioning (SemVer) describes compatibility at a package's public API boundary: a patch is a compatible fix, a minor adds backward-compatible functionality, and a major signals an incompatible change. It does not measure code churn. A one-line public type change may be breaking; a large internal refactor may be patch-safe.

| Policy | What receives a version | Fits when | Cost to manage |
| --------------------------- | ------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------- |
| **Lockstep** | A defined package group shares one version, even when only some packages changed. | Consumers adopt and test the packages as a coordinated release set. | Unchanged packages receive new versions, and the group still needs compatibility testing. |
| **Independent** | Each package follows its own public changes and consumer lifecycle. | Packages have distinct owners, audiences, or adoption schedules. | More versions and dependency-range updates must be reviewed. |
| **Commit-based deployment** | Applications deploy a commit or image digest rather than publishing package versions. | Packages are private implementation details inside an application repository. | Cross-repository consumers still need a versioned interface if they emerge. |

Changesets can track independent package intent and can also group packages through configuration. Choose based on how consumers upgrade, not on how many packages happen to be in the repository.

## 2. Make Release Intent Reviewable with Changesets

A changeset is a small Markdown file committed with the code change. Its front matter names affected packages and their version bumps; its body becomes the human-facing release summary.

```markdown
---
'@acme/ui': minor
---

Adds keyboard navigation to the data table.
```

A typical continuous integration (CI) release cycle is:

1. Each feature or fix adds a changeset when it changes a published contract.
2. CI or a maintainer collects pending changesets and creates a version pull request.
3. Reviewers inspect the selected packages, version bumps, changelogs, and internal dependency ranges.
4. After approval, a protected release job builds and publishes the reviewed package set.
5. The job verifies the published versions and records the resulting tags or release evidence.

For a pnpm-managed repository, the relevant CLI steps are:

```bash
pnpm changeset
pnpm changeset version
pnpm changeset publish
```

The first command creates release intent; the version command updates package manifests and changelogs; the publish command sends the prepared versions to the configured registry. A repository may automate these steps with a CI action or its own release job. Keep one canonical path so manual version edits and automation do not compete.

Not every change needs a release. Documentation-only changes, private applications, or internal refactors may need no changeset. Enforce changesets only for packages that the release policy actually publishes.

## 3. Treat Workspace Links as Development Syntax

A workspace protocol such as `workspace:*` makes a package manager resolve a dependency to a local workspace package. It is not a registry version a consumer can install directly. Some package managers rewrite supported workspace ranges when packing or publishing; the behavior depends on the selected package manager and versioning setup.

Before release, pack the package and inspect the resulting manifest. Verify that internal dependencies have registry-compatible ranges, public entry points exist, and all runtime files are present. Install that tarball into a clean consumer and test the imports it advertises. Workspace linking can hide missing build files, undeclared dependencies, and invalid package exports.

For internal-only projects, set `private: true` where publishing must be blocked. For published packages, verify the package scope, registry mapping, and `publishConfig` access or registry settings. A scoped name controls namespace ownership; it does not by itself make a package private.

## 4. Use Prereleases to Test an Upgrade Path

Prereleases let consumers test a candidate before the stable version is released. A Changesets prerelease mode can be entered and exited with:

```bash
pnpm changeset pre enter next
pnpm changeset pre exit
```

The release job must publish candidates under the intended registry tag, such as `next`, and consumers must opt into that tag deliberately. Test the actual package with a representative consumer, then verify the tag and final stable version. Prerelease state and tags are mutable workflow state: include a clear exit and promotion check so a later fix is not accidentally published only to a prerelease channel.

## 5. Protect Publishing Credentials and Prove Origin

Publishing authorization and provenance are different checks. Authorization answers whether this workflow may change the registry. Provenance provides verifiable information about the source and build identity associated with an artifact; it does not prove the code is safe.

When the registry and CI provider support trusted publishing, OpenID Connect (OIDC) can authorize a specific CI workflow without a long-lived write token. Configure the exact repository and workflow in the registry, grant only the required job permission, and protect the release environment. Use a separate read-only credential if the job must install private dependencies. If trusted publishing is unavailable, use a narrowly scoped token kept in the CI secret store and rotate it.

npm currently documents trusted publishing for supported cloud CI providers. Its provenance behavior differs by provider and package visibility; check npm's current requirements before relying on an attestation. Do not keep a token-based fallback that silently bypasses the intended workflow restrictions.

## 6. Verify the Package That Consumers Will Install

A green test run does not prove that the tarball is correct. Before publishing, compare the prepared version set to the approved release request and check the package boundary:

| Check | Evidence to inspect |
| ------------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| Compatibility | Public API change matches the declared SemVer bump; peer and internal dependency ranges permit supported combinations. |
| Package contents | Tarball contains the built entry points, declarations, license, and required metadata, without secrets or unrelated workspace files. |
| Consumer resolution | A clean project can install the tarball and import the documented entry points. |
| Release identity | CI publishes the approved package names and versions from the intended commit and protected workflow. |
| Registry result | Confirm each exact version, integrity, tag, and required provenance after publication. |

Prefer deploying or promoting the exact version or artifact digest that passed validation. A mutable tag such as `latest` or `next` is a pointer, not an immutable release identity. If a publication partially fails, compare the registry state with the approved version set before retrying; do not assume the command either published everything or published nothing.

## Summary

Version policy describes how consumers adopt compatible package contracts. Changesets can make release intent reviewable, but the release job must still validate the package set, dependency ranges, packed files, consumer imports, and authorization. Publish the verified artifacts through a controlled CI identity, then confirm the exact registry result and any required provenance.

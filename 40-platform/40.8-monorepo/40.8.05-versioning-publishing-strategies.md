# Versioning & Publishing Strategies

## TL;DR

**Fixed (lockstep) versioning releases every package together and independent versioning bumps only what changed** — the trade is simplicity for honesty, and the deciding factor is who consumes the packages. Changesets makes the honest path practical: each PR declares release intent in a reviewed markdown file, a Version PR collects them into SemVer bumps and changelogs, and publishing happens from CI (with provenance) rather than a laptop. Prereleases via dist-tags let consumers opt into `next` without touching `latest`.

---

> A monorepo that cannot answer "what version ships, and what changed?" is a liability. This chapter covers fixed vs independent versioning, the changesets workflow in practice, private packages and scopes, npm provenance, and the policy questions (lockstep vs independent, breaking-change handling) seniors get asked.

## First Principles

Versioning in a monorepo is one decision: independent or lockstep?

1. **Lockstep (one version for all packages)**: simple mental model, changelog = release; wasteful for consumers (minor bumps everywhere). Independent (Changesets-style): accurate semver per package, complex release orchestration.
2. **Publishing is content-addressed**: npm tags + provenance (→ 40.3.2.04); the registry is the boundary where the monorepo's atomicity ends — consumers see packages, not the repo.
3. **Internal ≠ published**: workspace protocol (`workspace:*`) gives internal packages instant consistency; published versions are the deliberately slower, semver'd surface.

## Definition

**Versioning strategy** determines how packages inside a shared repository receive version numbers:

- **Fixed / lockstep versioning** — every published package shares one version number, bumped together (Lerna's default heritage). `@corp/ui@3.2.0` and `@corp/utils@3.2.0` released in lockstep even if only UI changed.
- **Independent versioning** — each package versions on its own cadence based on what actually changed (Lerna's `--independent`, today usually driven by changesets).

**Publishing workflow** covers everything from intent ("this PR is a minor bump") to artifacts on the registry: changeset files, automated version PRs, `changesets publish` or equivalent in CI, prerelease channels, provenance attestations.

```text
INTENT ──► ACCUMULATION ──► RELEASE

PR adds .changeset/hot-fix.md      (patch intent + human summary)
        │ merged to main
        ▼
"Version PR" opens automatically    (bumps package.json files,
        │                            consumes changeset md files,
        │                            updates CHANGELOGs)
review & merge
        ▼
CI publish step                    (npm publish with OIDC provenance)
```

## Why Do We Need It?

1. **Consumers outside the repo need real versions** — apps importing `@corp/design-tokens` must resolve meaningful SemVer ranges, not git SHAs.
2. **CHANGELOGs are contracts** — auto-generated, reviewable changelogs prevent "what broke?" archaeology.
3. **Release trains reduce coordination cost** — one reviewed version PR replaces fifteen humans running `npm version` at their desks.
4. **Prereleases de-risk majors** — `next` dist-tags let early adopters test breaking changes before they land for everyone.
5. **Provenance is becoming table stakes** — npm/Sigstore provenance proves an artifact was built by your CI from a given commit, not uploaded from someone's laptop.
6. **Interview signal** — "how do you version packages in your monorepo?" appears in nearly every platform-adjacent senior loop.

## How It Works

### Fixed vs Independent: The Lerna Heritage

Lerna popularized both modes years before modern tooling; the vocabulary stuck.

```text
FIXED (lockstep)                      INDEPENDENT
packages/ui      2.4.0                packages/ui       2.4.0
packages/utils   2.4.0   ← same       packages/utils    1.1.7   ← own line
packages/hooks   2.4.0                packages/hooks    0.9.3

one bump = all packages              bumps follow per-package changesets
simple mental model                  honest SemVer per package
version numbers lie about change     more changelog noise to manage
```

Fixed mode survives because it makes cross-package compatibility trivial (`ui@3.x` works with `utils@3.x`). Independent wins when packages have genuinely separate consumers and lifecycles.

### The Changesets Workflow in Practice

Changesets treats version intent as code-review artifact:

```bash
# In your feature branch, declare intent:
npx changeset
# > which packages changed?  @corp/ui
# > bump types?             minor
# > summary?                "Adds DataTable virtual scrolling"
# writes .changeset/lucky-lions-dance.md  → commit it with the PR
```

```markdown
<!-- .changeset/lucky-lions-dance.md -->
---
'@corp/ui': minor
---

Adds DataTable virtual scrolling; fixes focus trap regression.
```

CI wiring (the canonical three-job setup):

```yaml
name: release
on:
  push:
    branches: [main]
jobs:
  version:
    if: ${{ github.repository == 'corp/monorepo' }}   # forks stay out
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0            # tags + history needed for versioning
      - uses: actions/setup-node@v4
        with:
          node-version: 22
          cache: pnpm
          registry-url: 'https://registry.npmjs.org'
      - run: pnpm install --frozen-lockfile
      - uses: changesets/action@v1
        with:
          version: pnpm changeset version          # consumes *.md, bumps pkgs
          publish: pnpm changeset publish          # npm publish per changed pkg
          title: 'chore(release): version packages'
          commit: 'chore(release): version packages'
        env:
          GITHUB_TOKEN: ${{ secrets.GITHUB_TOKEN }}
          NPM_TOKEN: ${{ secrets.NPM_TOKEN }}
          NPM_CONFIG_PROVENANCE: true               # OIDC provenance (see below)
```

What the bot does when changesets accumulate on `main`: opens/updates a single **Version PR** showing every `package.json` bump plus rendered CHANGELOG entries. Merging it triggers `changeset publish`, then tags.

### Prereleases Without Burning Main

```bash
pnpm changeset pre enter next         # switch mode: all bumps go to -next.N
# merge version PRs as usual → publishes @corp/ui@4.0.0-next.0, next.1, ...

pnpm changeset pre exit               # back to normal; next major exits cleanly
```

Consumers opt in with `pnpm add @corp/ui@next`. Snapshot releases (`changeset version --snapshot`) give ephemeral build-testing versions without touching semver history at all.

### Private Packages, Scopes, and Access

| Concern | Mechanism |
| ---------------------------- | ------------------------------------------------------------------------ |
| Never publish internal tools | `"private": true` blocks `publish` outright |
| Namespace ownership | scoped names `@corp/ui`; org on registry owns `@corp` |
| Public scoped packages | `publishConfig.access: public` (default is restricted) |
| Internal-only registry | GitHub Packages/Gitea/npm enterprise; `.npmrc` maps `@corp:registry=...` |
| Workspace-internal links | `"@corp/utils": "workspace:*"` — never a real version until publish |

```json
// packages/ui/package.json
{
  "name": "@corp/ui",
  "version": "3.1.0",
  "publishConfig": {
    "access": "public",
    "provenance": true
  }
}
```

The `workspace:*` protocol is the monorepo superpower: during development deps resolve to local source; changesets rewrites them to real ranges (`^3.1.0`) at publish time.

### Provenance on Publish

npm supports Sigstore-based provenance when publishing **from supported CI with OIDC** (GitHub Actions/GitLab):

```text
CI job assumes OIDC identity ──► npm publish --provenance
                                        │
                     registry records signed statement:
                       • built by github.com/corp/monorepo
                       • at commit abc1234
                       • via workflow release.yml
                       • timestamped in Rekor transparency log
```

No long-lived NPM_TOKEN needed for this path (granular tokens still required for other steps); consumers can inspect provenance on npmjs.com. This closes the "artifact uploaded from a laptop" gap.

### Lockstep vs Independent Decision Matrix

| Situation | Recommended | Why |
| ------------------------------------------------------ | -------------------------- | ------------------------------------------ |
| Component library where packages co-evolve | Fixed/lockstep | Compatibility guaranteed by construction |
| Platform SDKs consumed by external teams independently | Independent | Honest semver; consumers upgrade piecemeal |
| App-only monorepo (nothing published) | No versioning | Apps deploy by commit SHA/image tag |
| Mixed: design system + utilities | Independent w/ workspace:* | Utilities churn fast; UI stable |
| Regulated release trains (quarterly certification) | Lockstep | One certified version set to audit |
| Open-source core + paid plugins | Independent | Different governance per audience |

### Breaking-Change Policy Across Consuming Apps

When `@corp/api-client` ships a major, the apps *inside the same repo* are often updated atomically (that is the point of a monorepo). External consumers need policy:

1. **Deprecate before delete**: `npm deprecate @corp/api-client@3 "use v4"` plus console warnings one minor ahead.
2. **Codemods ship with the major**: `npx @corp/codemod api-client-v4` — migration effort is part of the release.
3. **Peer-dependency windows**: allow `^3 || ^4` for one cycle so mixed fleets work.
4. **Canary validation**: snapshot releases installed by consuming apps' nightly CI prove the migration before the real major lands.
5. **Document the escape hatch**: pinned dist-tag (`latest-3`) for stragglers, with an explicit sunset date.

## Code Examples

### Changeset Generation Guarded by CI Diff

```typescript
// scripts/require-changeset.ts — warn when touched packages lack intent
import { execFile } from 'node:child_process';
import { promisify } from 'node:util';
import { readdirSync } from 'node:fs';

const run = promisify(execFile);
const IGNORED = new Set(['INDEX.md', '.changeset']);

async function changedPackages(base: string): Promise<string[]> {
  const { stdout } = await run('git', ['diff', '--name-only', `${base}...HEAD`]);
  const dirs = new Set<string>();
  for (const file of stdout.split('\n')) {
    if (!file.startsWith('packages/') || IGNORED.has(file)) continue;
    dirs.add(file.split('/')[1]);                 // packages/<name>/...
  }
  return [...dirs];
}

export async function assertChangesets(base = 'origin/main'): Promise<void> {
  const touched = await changedPackages(base);
  const declared = readdirSync('.changeset')
    .filter((f) => f.endsWith('.md') && f !== 'README.md');

  if (touched.length && !declared.length) {
    console.warn(
      `::warning::Packages ${touched.join(', ')} changed without a changeset.\n` +
      'Run `pnpm changeset` if this should trigger a release.'
    );
  }
}
```

### Publishing Programmatically With Verification

```typescript
import { execFile } from 'node:child_process';
import { promisify } from 'node:util';

const run = promisify(execFile);

export async function publishVerified(): Promise<void> {
  // 1. What would publish? (dry run first — no surprises)
  const { stdout: dry } = await run('pnpm', [
    '-r', '--filter=!./apps/**', 'exec', 'npm', 'publish', '--dry-run',
  ]);
  console.log(dry.split('\n').filter((l) => l.includes('@corp/')).join('\n'));

  // 2. Real publish with provenance (OIDC-backed)
  await run('pnpm', ['changeset', 'publish'], {
    env: { ...process.env, NPM_CONFIG_PROVENANCE: 'true' },
  });

  // 3. Verify what landed actually resolves
  const { stdout: view } = await run('npm', ['view', '@corp/ui', 'dist-tags', '--json']);
  console.log('registry now:', JSON.parse(view));
}
```

### Reading Dist-Tags to Drive a Canary Rollout

```typescript
export async function rolloutPlan(pkg: string): Promise<string[]> {
  const { execFile } = await import('node:child_process');
  const { promisify } = await import('node:util');
  const { stdout } = await promisify(execFile)('npm', ['view', pkg, 'dist-tags', '--json']);

  const tags = JSON.parse(stdout);
  return [
    `canary fleet  → ${pkg}@${tags.next ?? tags.canary}`,
    `prod fleet    → ${pkg}@${tags.latest}   (after 24h error-budget watch)`,
    `rollback path → ${pkg}@${tags['latest-3'] ?? 'previous pin'}`,
  ];
}
```

## Real-World Use Cases

### 1. Design System With External Consumers

UI kit uses independent versioning via changesets; the Version PR doubles as the design-team changelog newsletter; `next` prereleases feed the web app team two sprints ahead of external users.

### 2. Platform Org Publishing SDKs

API client, auth SDK, CLI each independent. Provenance required (NPM_CONFIG_PROVENANCE in the shared reusable workflow), so customer security reviews pass without bespoke evidence.

### 3. Internal-Only Tooling Packages

Everything under `@corp-tools/*` publishes to the private registry scope mapped in `.npmrc`; `"private": true` guards accidentally-publishable app shells; zero public surface means zero semver politics.

### 4. Quarterly-Certified Fintech Releases

Lockstep versioning: one train `v2026.03.0` carries all packages through compliance sign-off together; hotfixes cut `v2026.03.1` trains. Predictability beats granularity here.

### 5. Breaking Migration Done Right

`api-client` v4 lands behind a codemod + dual peer range `^3 || ^4`; consuming apps migrate via nightly canary installs over two weeks; `npm deprecate` emails reach stragglers before support ends.

## Common Mistakes

### 1. Committing Version Bumps Manually Alongside Features

```bash
# Bad: editing package.json version in your feature PR — collides with the Version PR
# Good: leave ALL version mutations to changesets; PRs carry intent files only
npx changeset
```

### 2. Forgetting fetch-depth: 0 in the Release Workflow

Changesets needs full history/tags to compute bumps; a shallow checkout produces wrong versions or silent no-op releases. Always `fetch-depth: 0` in the release job (contrast with [Git at Scale](../40.6-git-advanced/40.6.08-git-at-scale-lfs-partial-clones.md) advice for build jobs).

### 3. Publishing From Laptops

Local `npm publish` bypasses CI provenance, may include dirty working trees, and depends on a long-lived token in `~/.npmrc`. Restrict via automation tokens scoped to CI and `publishConfig` flags.

### 4. Treating workspace:* as Publishable

```bash
# Bad: shipping "dependencies": {"@corp/utils": "workspace:*"} — unresolvable externally
# Good: changesets rewrites these automatically; verify with `npm publish --dry-run`
```

If you bypass changesets, you will ship literal `workspace:*` and break every consumer.

### 5. Majors Without Escape Hatches

Deleting v3 endpoints the day v4 ships strands consumers mid-migration. Ship overlap windows, dist-tag pins, and codemods — or accept the support burden.

### 6. Prerelease Mode Left On After a Major

Teams forget `pre exit`, so subsequent patches publish as `-next.N` forever and prod never receives fixes. Add a checklist item to the post-major retro.

## Best Practices

1. **One canonical flow**: changeset files in PRs, bot-owned Version PR, CI-only publish. Any second path creates drift.
2. **Choose fixed vs independent deliberately** using the matrix above; revisit when audiences diverge.
3. **Namespace ruthlessly**: `@org-scope/package` everywhere; map scopes to the right registry in committed `.npmrc`.
4. **Turn on provenance** for all public publishes; it is free supply-chain credibility.
5. **Use prerelease channels for risky changes**; promote by exiting pre mode, not by hand-editing versions.
6. **Keep changeset summaries user-focused** — they become the changelog verbatim.
7. **Gate releases on green main + docs builds**, not just tests; publishing broken docs costs trust.
8. **Automate breaking-change hygiene**: deprecations, peer ranges, codemods belong in the release checklist template.

## Performance Considerations

| Aspect | Cost | Mitigation |
| ------------------------------------------- | ----------------------------- | ------------------------------------------------------- |
| `changeset publish` cold install | minutes on big repos | dedicated runner cache; `--frozen-lockfile` |
| Version PR churn when many changesets queue | repeated CI runs | batch merges; scheduled release windows (e.g., Tue/Thu) |
| Registry propagation lag | seconds-minutes after publish | poll `npm view` before announcing; retry logic |
| Full-history checkout for versioning job | slower clone | reuse cached bare mirror on self-hosted runners |

Release frequency is a policy lever, not a performance problem — tune cadence to consumer tolerance.

## Summary

- Fixed (lockstep) trades honesty for simplicity; independent versions packages by actual change — pick per audience, not habit.
- Changesets encodes release intent in reviewed markdown files, automates a Version PR, and publishes from CI only.
- `workspace:*` keeps internal deps live-linked; changesets rewrites them to real SemVer at publish time — never hand-manage this.
- Prerelease (`pre enter/exit`) and snapshot modes give safe channels for majors and ephemeral test builds.
- Scoped registries plus `"private": true` control what leaves the building; `publishConfig.access` controls how.
- npm provenance (OIDC + Sigstore) attests artifact origin from CI — enable it for anything public.
- Breaking changes need policy: deprecation windows, peer-range overlaps, codemods, canary validation.

## Cheat Sheet

```text
VERSIONING & PUBLISHING CHEAT SHEET
════════════════════════════════════════════════════

MODES:
  fixed/lockstep   all packages share one version (compat-first)
  independent      per-package versions by actual change (honest semver)

CHANGESETS LOOP:
  npx changeset                    declare intent in branch
  .changeset/*.md                  reviewed with the PR
  changesets/action → Version PR   bot bumps + writes changelogs
  merge Version PR                 CI runs `changeset publish`
  fetch-depth: 0                   REQUIRED in release job

PRERELEASES:
  pnpm changeset pre enter next    bumps become -next.N
  pnpm changeset pre exit          promote cleanly to real semver
  changeset version --snapshot     ephemeral test builds

PACKAGES:
  "private": true                  unpublishable guard
  "@scope/name"                    namespace ownership
  publishConfig.access: public     scoped defaults are restricted
  "dep": "workspace:*"             live link internally (rewritten on publish)
  .npmrc @corp:registry=...        private registry mapping

PROVENANCE:
  NPM_CONFIG_PROVENANCE=true       publish from GH Actions/GitLab OIDC
  • proves repo + commit + workflow; logged in Rekor

BREAKING CHANGES:
  deprecate old major early
  peer range ^3 || ^4 for one cycle
  codemod ships WITH the major
  dist-tag pin (latest-3) + sunset date

INTERVIEW TIPS:
  • Name lockstep-vs-independent trade-off crisply
  • Describe the Version PR loop end-to-end
  • Mention provenance unprompted — strong signal
```

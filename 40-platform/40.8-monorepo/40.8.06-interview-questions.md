# Monorepo Interview Questions

Use these prompts to practice explaining a decision, its mechanism, the failure boundary, and how you would verify it. Avoid tool-name answers without the assumptions that make them correct.

## Definition

A **monorepo** stores multiple distinct projects in one version-controlled repository. Workspace managers, task orchestrators, build systems, and release tools can coordinate those projects, but they own different contracts.

> **Textbook Definition:** A monorepo is a source-control organization model in which multiple projects share one repository while dependency resolution, task execution, ownership, and release boundaries remain explicitly governed.

## First Principles

Trace one change through the system:

1. The package manifest says which project consumes which dependency.
2. The project graph says which projects are related.
3. The task graph says which operations must run and in what order.
4. The cache model says when a previous result is safe to restore.
5. The release policy says which artifact version consumers may install.

A reliable answer names which layer guarantees the behavior and which layer still needs verification.

## Foundations

**Q1: What is a monorepo?**

**A:** One version-controlled repository containing multiple logically distinct projects, such as applications, services, or libraries. Workspaces and task runners are optional tools; they are not part of the definition.

**Q2: When would you choose a monorepo over multiple repositories?**

**A:** Choose a monorepo when coordinated source changes, shared tooling, or cross-project refactors are common and one repository’s access policy is acceptable. Choose multiple repositories when projects need separate read permissions, release governance, or source-control policies. Team size alone does not decide the boundary.

**Q3: What does a monorepo make atomic, and what does it not?**

**A:** Related source changes can be reviewed and committed together. A Git commit does not atomically deploy several applications, migrate a database, publish packages, or update external consumers; each release boundary needs its own compatibility plan.

**Q4: What do package-manager workspaces provide?**

**A:** A package manager discovers local packages, installs their external dependencies, links workspace dependencies, and records the resolved install in its lockfile. Each package still needs to declare what it imports. A workspace does not automatically define build order or release policy.

**Q5: What does the workspace protocol mean?**

**A:** In managers that support it, a value such as <code>workspace:*</code> requires resolution to a local workspace package. It is development-time package-manager syntax; inspect the packed manifest to ensure consumers receive registry-compatible dependency ranges. npm workspaces use npm’s own dependency rules rather than assuming this protocol is portable. See [pnpm workspaces](https://pnpm.io/workspaces) and [Node package entry points](https://nodejs.org/api/packages.html).

**Q6: What are hoisting and phantom dependencies?**

**A:** Hoisting places compatible dependencies higher in a <code>node_modules</code> tree to reduce duplication. A phantom dependency is an import that works only because another package made it reachable, even though the importing package never declared it. Linker behavior varies: pnpm’s isolated layout and Yarn Plug’n’Play make undeclared access harder, while hoisted layouts can hide it. Test each package and a packed consumer.

## Task Graphs, Caching, and CI

**Q7: How are the package, project, task, and release graphs different?**

**A:** The package graph governs how dependencies resolve. A project graph represents workspace relationships. A task graph orders concrete operations such as a library build and an application test. A release graph or policy chooses compatible package versions and deployment units. One graph cannot substitute for the others. See Nx’s [project and task model](https://nx.dev/docs/concepts/mental-model).

**Q8: How does Turborepo decide whether to rebuild a task?**

**A:** It resolves the task configuration and hashes modeled inputs, including relevant files, dependencies, and declared environment values. A matching result can restore declared outputs and logs. A missing input can make different build behavior appear identical and produce a wrong cache hit. See [Turborepo caching](https://turborepo.dev/docs/crafting-your-repository/caching).

**Q9: How does Nx discover projects and targets?**

**A:** Nx can discover projects from project configuration and package-manager workspaces; plugins can infer targets from tool configuration, and package scripts or project-level targets can define them explicitly. Inspect the resolved project with <code>nx show project</code>. Do not assume every target comes from a hand-written <code>project.json</code> or that inferred metadata captures deployment behavior.

**Q10: How should continuous integration (CI) use affected commands safely?**

**A:** Compare the intended merge-base or last-successful commit to the tested head, and fetch sufficient Git history. Verify the selected projects or tasks for a leaf change, shared-library change, lockfile change, and shared configuration change. A bad base or incomplete graph can select too little work. Nx documents the base/head requirements in its [affected guide](https://nx.dev/docs/features/ci-features/affected).

**Q11: Does “affected” mean only the changed package runs?**

**A:** No. A changed library can affect its consumers, and a global config or dependency change can affect most of the workspace. Nx 24 defaults to task-based selection from declared inputs and outputs; Nx 23 and earlier use project-based selection. A migration to Nx 24 preserves project mode with <code>affected.legacy: true</code>, and <code>NX_LEGACY_AFFECTED</code> overrides the mode. A task-ordering edge alone does not propagate a change. Test the resolved mode and dependency inputs before relying on the narrower set.

**Q12: How would you reduce CI time without weakening the gate?**

**A:** Measure queue time, execution time, cache transfer, and p50/p95 feedback first. Then use parallel scheduling, a verified affected set, deterministic caching, and remote distribution where they reduce real work. Keep broader integration checks for relationships the graph cannot represent. A high cache-hit percentage is not a success metric if required work was skipped.

**Q13: What makes a remote build cache a security boundary?**

**A:** A cache reader executes or consumes files written by another machine. Restrict writers to trusted workflows, protect signing or access credentials, exclude secrets from outputs, and ensure inputs match across writers and readers. A signature can protect artifact integrity; it does not make an untrusted producer trustworthy.

**Q14: How would you choose between Nx and Turborepo?**

**A:** Compare the repository’s required contracts. Turborepo focuses on package task scheduling and cache configuration. Nx adds a project graph, plugin-inferred targets, generators, affected analysis, and boundary tooling. Both can cache and run tasks. Pilot the same change and compare graph accuracy, CI behavior, adoption cost, and maintenance rather than using company size or framework as a proxy.

**Q15: How do you enforce module boundaries?**

**A:** Define allowed dependencies and enforce them in a required check. Nx tags can drive JavaScript/TypeScript lint rules, while language-agnostic Conformance is another option where available. Separate dimensions such as scope and layer; an allow-list of target tags is generally an OR condition. CODEOWNERS routes review but does not prevent imports or hide source. See [Nx boundary enforcement](https://nx.dev/docs/features/enforce-module-boundaries).

**Q16: When should you add a generator?**

**A:** Add one when a repeated change must update several files consistently, such as creating a project with its tags, scripts, exports, and test setup. A generator reduces drift only if it is maintained and its output is tested. Use an existing plugin generator when it already matches the repository’s conventions; see [Nx code generation](https://nx.dev/docs/features/generate-code).

## Releases, Ownership, and Operations

**Q17: When should a monorepo use lockstep or independent versions?**

**A:** Lockstep fits packages consumed and certified as one compatible release set. Independent versions fit packages with separate consumers and upgrade schedules. App-only repositories may deploy by commit or image digest without publishing package versions. Decide from the consumer contract, then test compatibility.

**Q18: How does a Changesets workflow work?**

**A:** A contributor commits release intent for affected packages. Automation groups intent into a reviewed version change that updates manifests and changelogs. A protected release job builds and validates the selected package set, publishes it, and verifies the registry result. Changesets automates intent and versioning; it does not prove the tarballs are correct. See [Changesets versioning and publishing](https://changesets.dev/guide/versioning-and-publishing).

**Q19: What should you validate in a package tarball?**

**A:** Check the actual files, public entry points, declarations, license, and dependency ranges. Install the archive in a clean consumer and import what the manifest promises. This catches source aliases, missing build output, undeclared dependencies, and workspace-only ranges that a local link can hide.

**Q20: What is the difference between npm trusted publishing and provenance?**

**A:** Trusted publishing uses a configured CI identity through OpenID Connect (OIDC) to authorize an operation without a long-lived write token. Provenance is verifiable evidence about a package’s source and build origin. An attestation neither grants publish permission nor proves the code is safe. Check npm’s current [trusted publisher](https://docs.npmjs.com/trusted-publishers/) and [provenance](https://docs.npmjs.com/generating-provenance-statements/) requirements.

**Q21: How do you recover from a partial publish?**

**A:** Stop retries until you compare the intended package/version set with registry state. Confirm which exact versions and tarball integrities exist, then publish only missing artifacts or use the documented recovery path. Do not assume a failed command published nothing, and do not overwrite an existing version with different bytes.

**Q22: What does CODEOWNERS enforce?**

**A:** It can request review from owners of paths and support approval policy when branch protection requires those reviews. It does not create a source read-permission boundary and does not enforce architectural import rules. Use repository access controls for confidentiality and dependency checks for architecture.

**Q23: How would you migrate several repositories into a monorepo?**

**A:** Start with one representative set of consumers and define migration exit criteria: reproducible install, unchanged behavior, preserved ownership, release compatibility, and rollback. Move a dependency slice at a time, preserve history only when it helps future maintenance, and keep a clear source of truth during the transition. Remove the old path after consumers and automation have moved, not merely after code is copied.

**Q24: How do you make database migrations safe when several applications share a repository?**

**A:** Repository co-location does not make a schema change compatible with every deployed application. Use an expand-and-contract sequence: add an additive schema, deploy code that tolerates both states, migrate data, then remove old fields after consumers have moved. Assign migration ownership per database and test rollback or forward-fix behavior.

**Q25: How would you organize a monorepo with several programming languages?**

**A:** Let each language use its supported package manager and compiler, then decide whether the repository needs a unified task graph or a declarative cross-language build system. Model cross-language interfaces explicitly with schemas or APIs, and test generated artifacts. Nx can orchestrate configured tasks; it does not automatically make arbitrary toolchains hermetic. Bazel can model declared actions when maintained rules exist for the needed toolchains.

## Senior Design Prompts

**Q26: Design a monorepo for multiple teams with different release cadences.**

**A:** Start with the access boundary: if teams cannot share repository read access, use separate repositories. Otherwise define package ownership, import rules, team-specific CI, and independent deployment contracts. Centralize toolchain policy where it removes drift; let packages override it only with a documented reason. Keep public package releases independent when consumers upgrade separately.

**Q27: What should a monorepo CI pipeline guarantee?**

**A:** It should use the correct source-control base/head, install from the committed lockfile, run required checks for a sound affected set, and preserve enough full integration coverage to catch unmodeled relationships. Build artifacts once and promote the same identity. Treat remote cache writers, publish credentials, preview deployments, and production deployments as separate trust boundaries.

**Q28: How do you investigate a circular project dependency?**

**A:** Inspect the actual import and task edges, because a project cycle can come from an architectural dependency while a task cycle can come from incorrect build ordering. Identify the shared responsibility or inverted dependency, then extract a stable interface or merge modules when they are not independently meaningful. Add a graph or lint check that fails on the forbidden cycle class.

**Q29: How do you handle incompatible TypeScript requirements across packages?**

**A:** First check whether the packages truly need different compiler versions or only different compiler options. Align versions where supported; otherwise declare each package’s toolchain and test emitted JavaScript and declarations as the boundary. TypeScript path aliases affect resolution but do not select the compiler or validate the published package.

**Q30: How do you measure whether monorepo tooling is helping?**

**A:** Compare baseline and current CI feedback time, cache-hit correctness, artifact transfer cost, install/build reliability, change failure rate, and onboarding friction. Segment by task and workflow. A faster build is not useful if stale artifacts or missed consumers increase production failures.

**Q31: What security controls matter in a monorepo?**

**A:** Repository read access determines who can inspect source. Required reviews and protected branches control changes; dependency and secret scanning detect known risks; cache controls govern artifact reuse; and a protected release identity controls publication. Apply least privilege at each boundary and verify that forked or untrusted pull requests cannot access write credentials.

## Summary

Strong senior answers trace a change through package resolution, project relationships, task order, cache validity, and release policy. Explain the conditions under which a tool is safe, the failure that would invalidate that assumption, and the evidence you would use to verify it.

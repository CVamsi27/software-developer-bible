# The Twelve-Factor App

> **The most-cited methodology in modern cloud-native software.** Written by the Heroku founders in 2011, the Twelve-Factor App defines 12 rules for building SaaS applications that are portable, scalable, and deployable on modern cloud platforms. Every senior Platform / DevOps / Backend interview references it. Every "cloud-native" framework (Kubernetes, Cloud Foundry, Fly.io, Render, Vercel) is built around it. Know the 12 factors cold, and you can speak fluently about why a codebase is or isn't production-grade.

## Definition

**The Twelve-Factor App** is a set of twelve guidelines for applications deployed as services. They cover code and configuration, how processes run, and operations. Together, they help make an application process replaceable: it can start, stop, scale, and move between environments without manual setup or changes to its code. A stateless process keeps durable data outside the process, so replacing it does not lose that data.

```text
code & config       1 codebase/1 app · 2 explicit deps · 3 config in env · 4 backing services as attached resources
execution model     5 build/release/run stages · 6 stateless processes · 7 port binding · 8 concurrency by process
operations          9 disposable (fast start, graceful stop) · 10 dev/prod parity · 11 logs as event streams · 12 admin as one-off processes
```

Three properties define why the constraints are stated as they are:

1. **The unit of deployment is a process, not a server** — factors 6, 8, and 9 (stateless, concurrent by process, disposable) are one requirement: any instance must be replaceable at any moment, which is what makes rolling deploys, autoscaling, and crash recovery possible. State belongs in a backing service, never in the process's memory or filesystem.
2. **Configuration is injected, not baked** — factor 3 (`config` in environment variables) and factor 10 (dev/prod parity) together mean the *same artifact* runs in every environment, which eliminates the class of bugs where staging and production differ because a config file or build differs.
3. **The factors describe failure modes you can observe** — sessions in memory, hardcoded credentials, logs written to files, and long migrations run as part of boot are each a documented violation, which is why the chapter's value in an interview is *diagnostic*: given a system that cannot autoscale or cannot deploy during business hours, the violated factor is identifiable.

The unofficial extensions apply the same logic to cloud-native runtimes (API-first, telemetry as a first-class concern, authentication as a boundary, and treating the app as a long-running contract) — they are consequences of the original twelve, not replacements.

## First Principles

The twelve factors are one principle twelve times: **the platform owns the environment; the app is a replaceable process.**

1. **Config, backing services, logs, processes — externalize everything**: env-injected config (→ 20.1.3.03), attached resources by URL (swappable DBs), stdout logs (the platform ships them → 40.4.1.01), stateless share-nothing processes (→ 20.3.1.02).
2. **The payoff is interchangeability**: any instance can die/be added (horizontal scale, → 30.2.1.04), any backing service swapped per environment, any deploy is a new immutable release. The factors are the *contract* that makes platforms (k8s, → 40.2) able to manage your app.
3. **Deviations are debts with names**: sessions in memory, config in code, manual steps — each breaks one interchangeability guarantee; the factor list is a review checklist.

## Why it matters

Twelve-Factor is the **vocabulary of cloud-native**. When someone says "we're twelve-factor", they mean "our app can be deployed on Heroku / Kubernetes / Fly / Render with minimal ops work". When a codebase **violates** a factor, it usually shows up as a specific failure:

| Violation | Failure mode |
| -------------------------- | ------------------------------------------------- |
| Implicit dependencies | "It works on my machine" |
| Config in code | Can't move to a new env without a redeploy |
| Stateful processes | Can't scale out — sessions, files lost on restart |
| Slow startup | Can't auto-scale, slow deploys, slow failover |
| Long-running admin scripts | They crash mid-way, no way to monitor |
| Logs to files | Disk fills, can't aggregate, can't search |

Every production-grade framework you use (Next.js, NestJS, Spring Boot, Rails) has these baked in. Knowing the factors lets you recognize when a codebase is fighting the framework (or the platform).

## The 12 Factors in Depth

### I. Codebase

**One codebase tracked in revision control, many deploys.**

```text
my-app/
├── src/ # the codebase
├── package.json
├── Dockerfile
└── README.md

# Many deploys (instances of the same code, with different config):
my-app-staging ← same code, env=staging
my-app-prod-us ← same code, env=prod, region=us
my-app-prod-eu ← same code, env=prod, region=eu
```

**Violation:** multiple apps sharing one repo (monorepo for unrelated apps). The rule says **one app per repo**; monorepos for related apps (e.g. frontend + backend of the same product) are fine, but each "app" must have its own build artifact.

**In interviews:** "We have one Git repo per service, one Dockerfile, one Helm chart. We deploy to 3 environments (staging, prod-us, prod-eu) from the same image with different env vars."

### II. Dependencies

**Explicitly declare and isolate dependencies.**

```json
// package.json — declared, not implicit
{
  "dependencies": {
    "express": "^4.18.0",
    "pg": "^8.11.0",
    "ioredis": "^5.3.0"
  }
}
```

```typescript
// Lock the transitive tree
$ npm ci // exact install from package-lock.json
$ pip install -r requirements.txt // with --no-deps for CI
$ go mod download // exact module versions
```

**Violation:** "It works because I have a global `npm install -g some-tool`". The app's behavior depends on system state outside its declared deps.

**Rule:** never rely on system tools being installed. If your app needs `ffmpeg`, declare it in the `Dockerfile` and pin the version.

### III. Config

**Store config in environment variables.**

```typescript
// Config from env
const dbUrl = process.env.DATABASE_URL!;
const stripeKey = process.env.STRIPE_SECRET_KEY!;

// Config in code
const dbUrl = "postgres://prod-db.internal:5432/myapp";
const stripeKey = "sk_live_abc123"; // leaked to git
```

```bash
# .env (NEVER commit)
DATABASE_URL=postgres://...
STRIPE_SECRET_KEY=sk_live_...
REDIS_URL=redis://...

# In Kubernetes: ConfigMap + Secret, injected as env
# In Heroku: set via `heroku config:set DATABASE_URL=...`
# In Docker: `-e DATABASE_URL=...` or `--env-file`
```

**Rule:** **strict separation of config from code.** Config is everything that varies between deploys (DB URLs, API keys, feature flags). Code is everything that doesn't.

**Violation pattern:** YAML files committed with `production: true` and real-looking URLs. A config file is a code review surface area — when it changes, you diff and PR. **Env vars are not in the diff.**

**The "12-factor app" rule of thumb:** if you can put it in `.env` and never check it in, it goes in `.env`. If it's in `.env.example`, that's the template for the developer onboarding doc.

### IV. Backing Services

**Treat backing services as attached resources, addressed by URL.**

```typescript
// Local dev: postgres on localhost
const db = process.env.DATABASE_URL ?? "postgres://localhost:5432/myapp_dev";

// Staging: managed postgres
const db = process.env.DATABASE_URL ?? "postgres://staging-db.cluster-abc.us-east-1.rds.amazonaws.com:5432/myapp";

// Prod: same managed postgres, different credentials
const db = process.env.DATABASE_URL!; // injected by the platform
```

**Rule:** the app should not care whether its database is local, RDS, Cloud SQL, or self-hosted Postgres. The URL is the only thing that changes. **No `pg_config` files. No "is this prod?" branches.**

**Backing services include:** databases, message queues (Kafka, RabbitMQ, SQS), caches (Redis, Memcached), SMTP, third-party APIs (Stripe, Twilio, SendGrid).

**Test:** can you swap your local Postgres for a managed one by changing **one environment variable**? If yes, twelve-factor.

### V. Build, Release, Run

**Strictly separate build, release, and run stages.**

```text
  BUILD RELEASE RUN
┌────────────────────────────────┐ ┌──────────┐ ┌──────────┐
│ source │ │ build + │ │ release │
│ + │ → │ config │ → │ running   │
│ deps │ │ = release│ │ in prod  │
└────────────────────────────────┘ └──────────┘ └──────────┘
  immutable immutable can be scaled
  artifact manifest but is immutable
```

- **Build**: source → build artifact. Immutable. e.g. `npm run build` → `dist/`.
- **Release**: build artifact + config = a release. Immutable, versioned (e.g. `release-v123`).
- **Run**: the release running in an environment. Can be scaled (more replicas), but the release itself is immutable.

**Rule:** you cannot mutate a release. If you need a code change, build a new release. If you need a config change, create a new release. **Hot-patching code in a running container is forbidden.**

**The release manifest** is the versioned artifact: `release-2026-01-17-abc123` (a build SHA) + `config: prod-eu-v2`. The platform keeps every release so you can roll back instantly.

### VI. Processes

**Execute the app as one or more stateless processes.**

```typescript
// Stateless: all session state in Redis, all uploads to S3
app.use(session({ store: new RedisStore({ client: redisClient }) }));

// Stateful: session in process memory
app.use(session({ store: new MemoryStore() })); // lost on restart
```

**Rule:** **persistent data goes to a backing service.** Never to local disk, never to process memory. The process can be killed at any time and replaced, and the user should not notice.

**Violations:**
- `express-session` with `MemoryStore` (sessions lost on restart)
- File uploads to local disk
- In-memory rate limiter (count is lost on restart, different per replica)
- In-process job queue (jobs lost on restart)

**Anti-pattern in K8s:** writing to `/tmp` and expecting persistence. K8s pods are ephemeral. Mount a PVC if you need disk; better, use S3.

### VII. Port Binding

**Export services via port binding.**

```typescript
// Self-contained web server, exported on $PORT
const port = parseInt(process.env.PORT ?? "3000", 10);
app.listen(port, () => console.log(`Listening on ${port}`));

// Relies on external Apache/Nginx
// App handles only the app logic; Apache in front proxies
```

**Rule:** the app is its own web server. It binds to a port (declared via `PORT` env) and serves HTTP directly. No external web server is required.

**In Kubernetes:** the container exposes a port; the Service routes traffic to it. No Nginx sidecar needed (unless you want one for static assets / TLS termination).

**The `PORT` convention:** every cloud platform (Heroku, Render, Fly, Vercel) sets `PORT=3000` (or another default) and expects the app to bind to it. Don't hard-code 3000; read from env.

### VIII. Concurrency

**Scale out via the process model.**

```text
    ┌── web.1 (process)
    ├── web.2 (process) ← scale out by adding processes
    ├── web.3 (process)
    ├── worker.1 (process) ← different work type = different process
    ├── worker.2 (process)
    └── clock.1 (process) ← scheduled job
```

**Rule:** the app is decomposed into **process types** that handle specific work:
- `web`: HTTP server
- `worker`: background job runner
- `clock`: scheduled / cron
- `urgent-queue-consumer`: high-priority queue worker
- ...

Each process type can be **scaled independently**. Web gets 10 replicas. Worker gets 2 replicas. Clock stays at 1.

**In Kubernetes:** each process type is a `Deployment` (or `StatefulSet` if it needs stable identity). They share the same image but different `command` and `args`.

**Anti-pattern:** one big monolith that does web + worker + scheduler. If you scale it to 5 replicas, you have 5 schedulers fighting over the same cron job.

### IX. Disposability

**Fast startup and graceful shutdown.**

```typescript
// Fast startup (under 5 seconds)
const server = app.listen(port);

// Graceful shutdown on SIGTERM
process.on("SIGTERM", async () => {
  console.log("SIGTERM received, draining connections...");
  server.close(() => {
    console.log("HTTP server closed");
  });
  // Stop accepting new jobs, finish in-flight, then exit
  worker.stop();
  // Wait for in-flight to finish, then exit
  setTimeout(() => process.exit(0), 30_000); // 30s grace
});
```

**Rule:**
- **Fast startup** — under 5 seconds for a web process. Why? Auto-scaling, fast failover, fast deploys.
- **Graceful shutdown** — when SIGTERM arrives (Kubernetes pod eviction), stop accepting new work, finish in-flight, then exit. Maximum 30 seconds.
- **Crash-only** — if the process crashes, it should be safe to restart with no manual cleanup.

**Violations:**
- 60-second startup because of synchronous connection-warming
- Long-running in-memory state (lost on restart, see Factor VI)
- Cleanup required after a crash (means the process isn't truly stateless)

**In Kubernetes:** `terminationGracePeriodSeconds: 30` and a `preStop` hook if you need extra drain time.

### X. Dev/Prod Parity

**Keep development, staging, and production as similar as possible.**

| Dimension | Dev | Staging | Prod |
| ---------------- | ------------ | --------------------------- | ------------- |
| Time gap | Days | Hours | Real-time |
| Personnel | Dev | Dev + QA | SRE + on-call |
| Tools | SQLite | Postgres | Postgres |
| Backing services | Local Docker | Same as prod, smaller scale | Full |

**Rule:**
- **Same backing services** — don't use SQLite in dev and Postgres in prod. Use Postgres in both.
- **Small time gap** — code that's been on a feature branch for 3 weeks is risky. Trunk-based development with short-lived branches.
- **Same deploy process** — the same Helm chart / CI pipeline deploys to all envs. Only the config differs.

**Violations:**
- Dev uses a SQLite fixture; staging uses Postgres; prod uses Postgres. → "But it works in dev!" syndrome.
- Different code paths in dev vs prod (e.g. "this only happens in prod, here's a special handler").
- Long-lived feature branches with no CI.

**Modern application:** Docker Compose for dev with the same Postgres/Kafka/Redis images. Ephemeral environments per PR (Render, Vercel, Fly.io previews).

### XI. Logs

**Treat logs as event streams.**

```typescript
// Logs go to stdout
console.log(JSON.stringify({
  level: "info",
  msg: "request completed",
  request_id: req.id,
  user_id: req.user?.id,
  duration_ms: Date.now() - req.startTime,
}));

// Logs to a file
fs.appendFileSync("/var/log/myapp.log", message);
```

**Rule:** the app **never manages log files**. It writes structured events to stdout/stderr. The platform's log shipper (Fluentd, Vector, Filebeat, the Docker daemon) picks them up and routes to the log backend (Loki, ELK, CloudWatch, Datadog).

**Violations:**
- `fs.appendFileSync("/var/log/...")` — the app shouldn't know about disk.
- Log rotation in the app (the platform handles it).
- Logging to a database directly from the app (slow; better to log to stdout and let a tail-consumer ingest).

**Production pattern:**
```json
{"timestamp":"2026-01-17T14:30:00Z","level":"info","msg":"order.shipped","order_id":"ord_42","user_id":"u_7","duration_ms":42}
```

Structured JSON. The platform parses, indexes, and you query. **No log strings like `"User 42 just shipped order 99 successfully"`** — that's grep archaeology, not observability.

### XII. Admin Processes

**Run admin/maintenance tasks as one-off processes.**

```bash
# Run a migration as a one-off process
$ heroku run node migrate.js
$ kubectl run migrate --image=myapp:v123 --command -- node migrate.js
$ docker run --rm myapp:v123 node migrate.js
```

**Rule:** admin scripts (DB migrations, data backfills, one-off cleanups) are **the same codebase, run as a one-off process in the same environment**. They have the same code path, the same env vars, the same backing services.

**Violations:**
- Admin scripts live in a separate repo with their own deploy process.
- Admin scripts run on a developer's laptop against prod.
- Admin scripts use different libraries (e.g. raw SQL) than the main app (ORM).

**Modern pattern:** use the same Docker image, override the command. `docker run myapp:v123 node migrate.js` — same code, same env, just a different entrypoint.

## The Unofficial 15-Factor Extension

Beyond the original 12, modern practice adds:

### XIII. API First

Design the API contract before the implementation. Publish an OpenAPI / Protobuf schema. Treat it as a versioned, reviewable artifact. This enables client generation, contract testing, and parallel frontend/backend work.

### XIV. Telemetry

The "three pillars" of observability: **metrics, logs, traces**. All three are first-class. Distributed tracing (OpenTelemetry) connects a request across services. Metrics (Prometheus) drive dashboards and alerts. Logs are for forensic detail.

### XV. Authentication & Authorization

AuthN (who are you) and AuthZ (what can you do) are **separate concerns**, factored out of business logic. Identity is a backing service (Auth0, Cognito, your own). Authorization is enforced consistently at the API gateway and at the service boundary.

## Violation Patterns in Real Codebases

| Factor | Common violation | Symptom |
| -------------------- | --------------------------------------------------------- | -------------------------------------------------------- |
| I. Codebase | Monorepo with 10 apps, each with its own CI | "What broke?" |
| II. Dependencies | `npm install some-tool -g` in deploy script | "It works on my machine" |
| III. Config | Hardcoded DB URLs in source | Secret leaks to git; can't change DB without redeploy |
| IV. Backing services | Code branches on `process.env.NODE_ENV === 'prod'` for DB | Different behavior in different envs |
| V. Build/Release/Run | Hot-patching code in a running container | "We have a release v123 but I edited a file in v124-rc" |
| VI. Processes | In-memory rate limiter, sessions, file uploads | Lost on restart, different per replica |
| VII. Port binding | App only runs behind Apache; can't `npm start` locally | Can't test locally without Apache |
| VIII. Concurrency | One process does web + worker + scheduler | Schedulers fight; can't scale web without scaling worker |
| IX. Disposability | 60s startup, no SIGTERM handler | Slow deploys, lost connections on pod eviction |
| X. Dev/Prod parity | SQLite in dev, Postgres in prod | "It works in dev" |
| XI. Logs | Log to file, no structured fields | Disk fills; grep is your only tool |
| XII. Admin processes | Migration script in a separate repo | Production data migration runs against the wrong DB |

## The Twelve-Factor + Cloud-Native Mapping

| Factor | Kubernetes equivalent | Serverless equivalent |
| -------------------- | ---------------------------------------------- | --------------------------------- |
| I. Codebase | One Git repo per service | One Git repo per function family |
| II. Dependencies | Docker image with pinned deps | Layer with pinned deps |
| III. Config | ConfigMap + Secret → env | Environment variables |
| IV. Backing services | Service + ExternalName | VPC peering; AWS SDK |
| V. Build/Release/Run | CI → image → Helm release | `sls deploy`; SAM |
| VI. Processes | Stateless Deployment | Lambda (truly stateless) |
| VII. Port binding | Service + Ingress | API Gateway |
| VIII. Concurrency | HPA + multiple process types | Auto-scaling concurrency |
| IX. Disposability | `terminationGracePeriodSeconds`, preStop hooks | Function cold start, no shutdown |
| X. Dev/Prod parity | Same Helm chart, different envs | Same SAM template, different envs |
| XI. Logs | stdout → Fluentd/Vector → Loki | CloudWatch Logs |
| XII. Admin processes | `kubectl run --rm` for migrations | Step Functions; one-off Lambda |

The mapping is tight. If you follow twelve-factor, the platform takes care of you. If you violate it, you fight the platform.

## Anti-Patterns to Avoid

1. **Storing config in YAML files committed to git.** The "config" is supposed to be per-deploy, not per-commit.
2. **In-memory state that should be in Redis.** Sessions, rate limits, idempotency windows.
3. **Long startup times.** If it takes 60s to boot, K8s will kill it before it's ready.
4. **Synchronous "warm-up" calls in startup.** Lazy-init everything; fail fast on first request if needed.
5. **No `SIGTERM` handler.** K8s sends SIGTERM, your process ignores it, K8s kills it after 30s, in-flight requests fail.
6. **Different libraries in different envs.** ORM in prod, raw SQL in migrations. Always use the same code path.
7. **Files in containers.** "But my container has `/tmp/uploads` mounted as a PVC" — you have a stateful app, not a twelve-factor one.
8. **Logging to a file.** "But our log shipper is configured to read /var/log/myapp.log" — the platform can do that, but the app shouldn't care.
9. **One big repo with no build artifact boundary.** "We deploy the whole monorepo and run `if (process.env.APP_NAME === 'web') require('./web')`" — that's a 12-factor violation.
10. **Hot-patching a running container.** `kubectl exec` and edit a file. The next deploy wipes it. Don't.

## Twelve-Factor in Interviews

**Q: "Walk me through your deployment pipeline."**

> "We follow the twelve-factor methodology. Each service has its own Git repo, one Dockerfile, and a Helm chart. CI builds the image on every merge to main; the image is tagged with the Git SHA. A release is the image plus a per-environment ConfigMap. We have one Helm release per environment (staging, prod-us, prod-eu). On every PR merge, an automated CD pipeline rolls out the new image to staging. Production deploys are gated; we use ArgoCD for the rollout."

**Q: "How do you handle config?"**

> "Everything goes through env vars. DATABASE_URL, REDIS_URL, STRIPE_SECRET_KEY, feature flags — all env. The 12-factor rule: config varies between deploys, code does not. We never check in production config to git. We use a `.env.example` file in the repo for developer onboarding. Production env vars come from a sealed secret store (or AWS Secrets Manager in our case), mounted by the platform into the pod."

**Q: "What about stateful operations like database migrations?"**

> "Factor XII: admin processes are one-off processes in the same environment. We use the same Docker image, override the command to run `node migrate.js` instead of `node server.js`. The migration runs with the same env vars and backing services as the main app. We treat the migration as a release of its own — the CI runs the migration as a step before rolling out the new app release. If the migration fails, the rollout is blocked."

## Summary

- **Twelve-Factor** is the methodology for cloud-native apps. It's the vocabulary, the checklist, the interview answer.
- **One codebase per app, many deploys.** Config in env. Stateless processes. Disposability. Logs to stdout. Admin processes as one-offs.
- **The 15-factor extension** adds API-first, telemetry, and auth as first-class concerns.
- **If you follow it, the platform (K8s, Heroku, Fly, Vercel, Lambda) takes care of you.** If you violate it, you fight the platform.
- **In interviews: name the factor by name, give an example of how your team followed it, name the violation you fixed.**

# The Twelve-Factor App

A deployment should replace an application instance without losing an accepted order, a user's session or the ability to identify the running release. The Twelve-Factor App gives a vocabulary for making that replacement predictable. It is a methodology for service applications, not a certification of security or availability.

## Definition

**The Twelve-Factor App** is a set of twelve guidelines for applications deployed as services. They cover code, dependencies, configuration, process execution and operations. They help make an application process replaceable: it can start, stop, scale and move between environments without hidden manual setup. Durable business state belongs outside that process.

> **Textbook Definition:** The Twelve-Factor App is a methodology for software-as-a-service applications that prescribes practices for codebases, dependencies, deployment configuration, attached resources, release stages, process execution and operations to improve portability and replaceability.

A **process** is one running application instance. A **backing service** is a resource it uses, such as a database, queue or object store. A **release** identifies the built code and configuration selected for deployment. These relationships matter more than memorizing the factor numbers.

## First Principles

An instance can disappear before cleanup runs. If the only copy of accepted work is in its memory or local filesystem, starting a new instance cannot recover it. Durable ownership must therefore cross a process-independent boundary before the application promises success.

Multiple instances do not share memory. If each owns a separate session or quota counter, routing a request elsewhere changes what the request observes. Separate shared business state from local, reconstructible optimization state.

A code artifact also cannot explain every environment on its own. Credentials, endpoints and capacity settings vary independently of source changes. Record the deployed artifact and its supplied configuration so a replacement is reproducible, while protecting those values appropriately.

## Why It Matters

The factors help diagnose concrete problems: deployment logs users out, scale-out duplicates a scheduler's work, a laptop-only dependency breaks the image build, or nobody knows which code/configuration is serving traffic. They do not eliminate database recovery, network failures, overload or application-specific invariants.

## How the Factors Fit Together

### I–II: Track the application and declare its dependencies

**I. Codebase:** one codebase for an application, many deploys. The original methodology associates the application with a repository. Modern monorepos adapt this boundary: make each application target, dependency graph and artifact identifiable. A frontend and backend are separate service applications even when they belong to one product. Shared code should be a declared library dependency, not an implicit copy between deploys.

**II. Dependencies:** declare and isolate language and system dependencies. A package manifest states allowed versions; a lockfile records the resolved tree. For Node.js, `npm ci` installs from its compatible lockfile. A container must also declare required system tools; a digest-pinned base does not by itself pin a later unversioned package download. Reproducibility also depends on inputs and build behavior.

### III–IV: Supply deployment configuration and resource bindings

**III. Config:** separate values that vary by deploy from application code. The original factor specifically recommends independent environment variables. Internal routing or module wiring that does not vary by deploy remains code. Validate supplied settings at startup, avoid printing credentials, and commit a non-secret example of required names.

Modern systems may deliberately use mounted configuration or secret-manager references. Explain that adaptation rather than claiming the original text never specified environment variables. Environment variables are not a secrecy mechanism: child processes, dumps and diagnostics can expose them. Fetching a secret into memory also leaves it in memory; restrict dump/debug access, redaction and credential lifetime.

**IV. Backing services:** attach resources through configuration instead of embedding their location in code. Changing a PostgreSQL connection URL can select another compatible server. It does not make PostgreSQL interchangeable with an unrelated database, remove TLS/permission differences, or migrate the data. Validate the resource contract as well as its address.

### V: Give build, release and run distinct identities

```text
source + declared build inputs → build artifact A
artifact A + deployment configuration C → release R
release R → running instances R.1, R.2, ...
```

The build produces the artifact. The release records the chosen artifact/configuration. The run stage starts instances from that release. A code or deployment-config change creates a new release rather than an untracked edit inside one instance.

Re-deploying the previous release restores its code/configuration identity. It does not reverse a migration or an external payment, and it may take time to restore capacity. Check backward compatibility and state recovery before calling rollback safe.

### VI–VIII: Replace and scale the right process types

**VI. Processes:** keep durable business state in backing services. Local caches, connection pools, temporary files and just-in-time compilation state are permitted when they are reconstructible and correctness survives their loss. Stateless does not mean a process has no memory. A durable volume can be appropriate for a stateful product or backing service, but its attachment/access model becomes part of that design.

**VII. Port binding:** a self-contained service exports its interface on a configured port. An HTTP application can embed its server library; a reverse proxy may still sit in front for routing or TLS. Some managed function runtimes invoke a handler instead of exposing an application-owned listening port: that is a different runtime interface.

**VIII. Concurrency:** scale process types according to their work. For example, one image can expose separate web and queue-worker commands. They can scale independently. A scheduler needs durable ownership/deduplication; setting its desired replica count to one does not guarantee that an old instance and replacement never overlap. Threads and asynchronous work inside a process remain useful; this factor does not prohibit them.

### IX–X: Bound replacement and reduce environment surprises

**IX. Disposability:** minimize startup time and shut down gracefully. There is no universal five-second startup or thirty-second shutdown requirement. Choose deadlines from measured readiness, request/job duration and the runtime's configured grace period.

For an HTTP process, stop accepting work, finish or terminate admitted work under the deadline, then close dependencies. A worker must stop claiming jobs and either commit/acknowledge completed effects or permit recoverable redelivery. A forced termination can bypass every handler, so durable identity and recovery still matter. See [lifecycle patterns](../../30-architecture/30.3-infra-patterns/01-liveness-lifecycle/30.3.1.01-health-checks-graceful-shutdown.md) for the implementation home.

**X. Dev/prod parity:** reduce gaps in delivery time, operational participation and tools. Local PostgreSQL helps exercise PostgreSQL semantics; it does not reproduce production latency, scale, permissions or failure topology. A SQLite unit fixture can be useful if real PostgreSQL integration tests cover the behavior the fixture cannot establish. Reuse the deployment path and test relevant environmental differences.

### XI–XII: Send events outward and run administration from a known release

**XI. Logs:** emit a stream of events and let the platform handle routing, rotation and retention. Structured fields help correlate events, but plain text is not prohibited by the original factor. Choose a schema, redact sensitive fields and define what happens when collection is slow or unavailable; stdout is not proof of durable storage.

**XII. Admin processes:** run migrations, backfills and maintenance as one-off tasks using compatible release code, dependencies and deployment configuration. A migration may legitimately use SQL while the application uses an object-relational mapper. The issue is compatibility and controlled execution, not identical APIs. Supply the task's identity, credentials, observability, retry policy and overlap control explicitly; starting a bare pod does not configure these for you.

## Example: Replace a Worker Without Losing an Accepted Order

Suppose an API and worker share one built image but run different commands.

| Step | Durable record | What a replacement can do |
| ------------------------------------------------------ | ------------------------------------------------------------ | -------------------------------------------------- |
| API commits order and publication intent together | Order and outbox event | Discover the committed intent after the API dies |
| Relay publishes the event | Broker acceptance plus still-pending intent if marking fails | Retry publication with the same event identity |
| Worker commits its local effect and processed identity | Effect and duplicate-detection record | Skip a repeated event's local effect |
| Worker dies before acknowledging | Broker may redeliver | Recover without relying on the old worker's memory |

This is an application-level recovery contract, not something Twelve-Factor creates automatically. The canonical mechanisms live in [outbox/CDC](../../30-architecture/30.2-system-design/01-theory/30.2.1.18-outbox-and-cdc.md) and [queues](../../30-architecture/30.2-system-design/01-theory/30.2.1.06-queues-and-async.md). If the worker calls a payment provider, its external operation identity and uncertain outcome need their own reconciliation path.

## Real-World Decisions

API-first contracts, telemetry and authentication/authorization are useful extensions discussed in *Beyond the Twelve-Factor App*. They are not additional factors in the original methodology. Define authentication (establishing identity) separately from authorization (deciding permitted actions); putting an identity provider outside the service does not enforce object-level access inside it.

Use the factors to name the boundary and explain a deviation. A model-serving process may need a long warm-up: set realistic startup/readiness behavior, retain enough ready capacity and measure scale-out delay. Moving model weights to a sidecar does not remove their load time or make the sidecar immortal.

## Mistakes

- Treating compliance as proof that rollouts, security and failover are solved.
- Promising success before durable work survives a process crash.
- Confusing a shared repository with one deployment identity, or assuming every process must be in its own repository.
- Assuming URL injection makes different resources behaviorally equivalent.
- Depending on graceful shutdown for correctness after abrupt termination.
- Describing an illustrative incident as personal experience. Use real actions and measured results in interviews.

## Best Practices

Record artifact/configuration identity, validate resource bindings, identify durable versus reconstructible state, and measure readiness/replacement under load. Keep administrative work observable and recoverable. For each factor, explain the mechanism, its remaining failure boundary and the evidence that the deployment meets its intended contract.

## Summary

The twelve factors help separate application code, deployment inputs, durable resources and replaceable processes. They make replacement easier to reason about; safe business effects, recoverable state and operational readiness still require explicit design and verification.

# 40.9.02 — Twelve-Factor App Interview Questions

> Senior-depth twelve-factor questions — grouped by difficulty, each with a short answer, the deeper senior reasoning, and the follow-up interviewers actually ask. Covers the diagnostic use of the factors: statelessness, config injection, build/release/run, disposability, log streams, and where violating a factor becomes a specific production failure.

## First Principles

This set probes the interchangeability contract (→ 40.9.01): the platform owns the environment; the app is a replaceable process.

1. **The senior tells are consequence statements**: "MemoryStore sessions are lost on restart *and* differ per replica" beats "processes should be stateless" — juniors recite factors; seniors name what breaks and when.
2. **Every question here maps to an axiom chain** — config is injected, state lives in backing services, releases are immutable. Derive from those and the scenario variants answer themselves.

## Answer Framework

```text
ANSWER STRUCTURE:
  1. The factor by name (III config, VI processes, IX disposability, ...)
  2. The mechanism (what the factor actually constrains)
  3. The failure mode when violated (the incident the interviewer is fishing for)
  4. The fix (the pattern, and where state/config goes instead)
  5. The trade-off (when a deviation is legitimate, and how you contain it)
```

## Beginner

**Q1: What is the Twelve-Factor App, in one sentence?**

**Short answer:** A 2011 Heroku methodology — twelve rules that make an application a disposable, stateless, environment-agnostic process so any platform can deploy, scale, and replace it without manual steps.

**Go deeper (senior):** "It's less a checklist than the *contract* between your app and the platform. Kubernetes, Heroku, Fly, Render all assume it — follow it and the platform takes care of you; violate it and you fight the platform."

**Q2: Why does config belong in environment variables?**

**Answer:** Factor III: config is everything that varies between deploys (DB URLs, keys, feature flags); code is everything that doesn't. Env vars keep the *same artifact* promotable across environments, keep secrets out of the diff, and let the platform inject per-environment values. A YAML file committed with prod URLs is a code-review surface and a leak risk.

**Q3: What does "backing services as attached resources" mean?**

**Answer:** Factor IV: databases, queues, caches, SMTP are addressed by URL and swappable per environment — swap local Postgres for RDS by changing one env var, no code branches, no `is-this-prod?` logic anywhere.

**Q4: Why must processes be stateless?**

**Answer:** Factor VI: any instance can be killed and replaced at any moment — that's what makes rolling deploys, autoscaling, and crash recovery work. Persistent data goes to backing services: sessions in Redis, uploads to object storage, never process memory or local disk.

**Q5: What is dev/prod parity, and what's the modern version?**

**Answer:** Factor X: same backing services, small time gap, same deploy process across environments. The modern form is Docker Compose with the same Postgres/Redis images in dev, ephemeral preview environments per PR, and one pipeline — only config differs.

## Intermediate

**Q6: Explain build, release, run — and why releases must be immutable.**

**Answer:** Factor V: build produces an artifact; a release is that artifact plus config, versioned; run executes it. Immutability is what makes rollback instant (redeploy release N-1) and hot-patching forbidden — `kubectl exec` edits vanish at the next deploy and leave reality diverging from every release. Config change? New release, not a mutation.

**Q7: What's wrong with `MemoryStore` sessions, in-memory rate limiters, and in-process job queues?**

**Answer:** All three violate factor VI the same way twice: state is lost on restart, *and* it differs per replica — a rate limiter counted per pod is N× looser than intended; a job queue loses jobs on every deploy. Fixes: Redis-backed session store, a centralized limiter (or gateway limits), a real queue (SQS/BullMQ) with workers as separate process types.

**Q8: How does factor VIII (concurrency) say you should scale?**

**Answer:** By process types, not threads inside one binary: `web` handles HTTP, `worker` runs jobs, `clock` runs schedules — each scaled independently. In Kubernetes each type is its own Deployment sharing one image with different commands. The anti-pattern is the monolith that does web + worker + scheduler: five replicas means five schedulers fighting over the same cron.

**Q9: What does disposability require, concretely?**

**Answer:** Factor IX: fast startup (seconds, so scaling and failover are responsive) and graceful shutdown — on SIGTERM, stop accepting work, finish in-flight, exit within the grace period. In Kubernetes: `terminationGracePeriodSeconds: 30`, a `preStop` hook if you need drain time, readiness probes so the pod leaves rotation before it dies. Crash-only: a restart needs no manual cleanup, which statelessness already bought you.

**Q10: How do logs work in twelve-factor, and why not log to files?**

**Answer:** Factor XI: the app writes structured events to stdout/stderr and *never manages files* — the platform ships them. Logging to disk means the app knows about volumes, rotation becomes the app's problem, and aggregation breaks per replica. Structured JSON (timestamps, request IDs, durations) makes the stream queryable; prose strings are grep archaeology.

## Advanced

**Q11: A teammate hot-patches a running container with `kubectl exec`. Diagnose.**

**Answer:** Factor V violation with a delayed fuse: the running process now diverges from its release — the edit is invisible to Git, lost at the next rollout, and unreproducible in staging. The fix isn't scolding, it's making the legitimate path faster than the hack: ship the config change as a release, or emergency-mitigate *then* converge through code. Same discipline as IaC drift (→ 40.12.02 Q12): classify the change, reconcile it into the declared state.

**Q12: "We mount a PVC for uploads" — is that twelve-factor?**

**Answer:** No — a writable mount is state in the process's environment, so replicas diverge and rescheduling strands data (factor VI). Object storage (S3/GCS) is the fix: addressed by URL, shared by all replicas, survives every restart. PVCs are legitimate for the *stateful backing services themselves* (a self-hosted Postgres), not for app instances.

**Q13: Where does the methodology fall short in practice?**

**Answer:** Two honest gaps: **databases-as-cattle is hard** — schema migrations are stateful, ordered, and shared, which is why factor XII runs them as gated one-off release steps rather than per-instance boot logic; and **single-tenant stateful products** (self-hosted installs, edge devices) bend factors VI/IX by design. The senior move is deviating *deliberately, at named boundaries* — not accidentally everywhere.

**Q14: Migrations on boot vs one-off admin processes — defend one.**

**Answer:** Factor XII: one-off processes in the same release. Migrations-on-boot breaks under horizontal scale (N replicas race the same DDL), couples app health to migration duration (slow migrations exceed readiness windows), and makes rollback incoherent. The production shape: CI runs the migration as a release-gated step, then the app rollout follows — forward-compatible migrations, expand-and-contract for zero-downtime.

**Q15: How does twelve-factor map to Kubernetes and to serverless?**

**Answer:** Kubernetes *is* the twelve-factor runtime: ConfigMap/Secret = factor III, Deployment = stateless VI, HPA = VIII, grace period + preStop = IX, stdout → Fluentd/Loki = XI, `kubectl run --rm` jobs = XII. Serverless is the factors taken to their limit: truly stateless functions, env config, platform-managed logs — which is why the vocabulary transfers even when the runtime changes.

## Behavioral & Scenario Drills

**Q16 (scenario): Autoscaling doesn't — pods come up, take 60 seconds to be ready, traffic still times out. Diagnose.**

**Answer:** Factor IX violation: slow startup defeats autoscaling because the new capacity arrives *after* the incident peaks. Find what boot does synchronously — connection warming, cache pre-loading, eager framework init — and make it lazy; set a readiness probe that reflects real serving capacity; and check factor VI too (60-second boots often mean reconstructing in-memory state that belongs in a backing service).

**Q17 (behavioral): Tell me about a time a factor violation caused a real incident.**

**Story to tell (situation → task → action → result):** Sessions in `MemoryStore` — every deploy logged users out, and per-replica stores made sticky users flicker between "logged in" and "logged out" behind the LB. Moved sessions to Redis, made the app fully replaceable, and deploys became invisible. The interview point is naming the factor (VI), the double failure (restart loss + per-replica divergence), and the review checklist added so it stayed fixed.

**Q18 (follow-up trap): "It's 2011 software — is twelve-factor still relevant?"**

**Answer (the nuanced answer they want):** The runtime evolved; the contract didn't. Kubernetes, serverless, and every PaaS are twelve-factor materialized — the factors describe what platforms assume about your app, so they're read today as the *interface definition* between app and platform. What's changed is the epilogue: the 15-factor extension (API-first, telemetry, authN/Z as backing services) and the judgment to deviate deliberately. Saying "it's obsolete" is the trap; saying "it's now the platform's spec for you" is the answer.

## The Modern Contract

**Q19: Factor XI in 2026 — is stdout still the log contract when OpenTelemetry exists?**

**Answer:** Yes, but it's one lane of two. Stdout remains the app↔platform contract: the platform owns shipping, rotation, and retention, and the app stays ignorant of all three. OpenTelemetry adds the *telemetry* lane — traces and metrics with context propagation that logs alone can't provide — and the modern shape is structured logs to stdout with trace IDs injected, OTLP for traces/metrics, and correlation by request ID across both. The violation that still bites: apps that write their own files, rotate them, or ship them — the platform's job. The senior nuance: structured JSON to stdout, not prose; the log stream is a data contract, and grep archaeology is the cost of breaking it.

**Q20: Env vars are flat strings — where does the config approach break down?**

**Answer:** At size, structure, and secrecy. Flat strings can't express nested config gracefully (the `DB__CONNECTION__POOL__MAX` convention is a workaround, not a design); large or binary secrets don't belong in env vars at all (they leak via logs, crash dumps, `/proc`, and child processes); and every replica holds the full config whether it needs it or not. The mature pattern: env vars as the *injection mechanism* for short connection strings and flags, a secrets manager (Vault/SSM) referenced at boot for credentials — fetched, held in memory, never echoed — and config files mounted only for tools that demand them. The interview point: factor III says config lives *outside the artifact*; it doesn't mandate that the mechanism be a giant flat bag of strings.

**Q21: What does factor II (dependency declaration) mean in a container world?**

**Answer:** The factor sharpens rather than dissolves: lockfiles declare the language-level dependency set exactly (no floating ranges in anything that deploys), and the image declares the *system* level — base image pinned by digest, OS packages enumerated in the Dockerfile, no `apt-get install` whatever-is-latest at build time. The violation that survives containerization: builds that reach for system packages implicitly (a CLI assumed present on the host), which works until the base image changes underneath. The modern form: reproducible builds end-to-end — lockfile + digest-pinned base + hermetic build — and `npm ci`/`pip install --require-hashes` as the enforcement, not the aspiration.

**Q22: How do you reconcile disposability with expensive warm state — connection pools, JIT warmup, caches?**

**Answer:** By refusing to hold the warm state *in the process*. Connection pools: initialize lazily and size for boot storms — a scale-out event opening 500 DB connections simultaneously is the pool version of a thundering herd. JIT/warmup: the 60-second boot that defeats autoscaling (Q16) is fixed by lazy init and ahead-of-time compilation, not by keeping instances alive. The tension is real for genuinely expensive warm state (model weights, large caches): the answer is externalizing it — shared cache tiers, sidecars that own the warm state, or accepting a readiness window *while making boot not block the fleet*. The principle: the process stays disposable; the warmth moves somewhere that survives replacement.

**Q23 (scenario): Secrets in env vars showed up in a crash dump. What's the fix set?**

**Answer:** Contain, then re-architect. Contain: rotate the exposed credentials immediately (they're burned by definition), purge the dump from every store it reached, and check whether it shipped to the log aggregator. Re-architect: secrets out of plain env — fetched at boot from a secrets manager, held in memory, and *never logged*: scrubbing rules on the logger, no secret values in error messages or debug dumps, and crash dumps to a redaction layer. The systemic fix is the review discipline: any new credential flows through the secrets path by default, and a test asserts that boot-time logs contain none of the secret values. The interview point: "secrets in env vars" is the common-but-leaky middle ground — factor III's *spirit* is out-of-artifact config, and the leak dictates the stronger mechanism.

**Q24 (behavioral): Tell me about migrating a legacy app to Kubernetes — what factor violations bit you?**

**Story to tell (situation → task → action → result):** A monolith that kept local uploads on disk, stored sessions in process memory, and ran migrations on boot. First deploy: replicas diverged (users' uploads vanished behind the LB), sessions flickered, and the migration race deadlocked two pods mid-DDL. The migration *was* the audit: uploads to object storage (factor VI), sessions to Redis, migrations pulled out of boot into a gated release step (XII), logs to stdout so the platform could aggregate (XI). Result: rolling deploys became possible at all — before the factor fixes, every deploy was an incident. The interview point: the violations weren't academic; each mapped to a concrete failure on day one, which is how you sell the refactor.

**Q25 (follow-up trap): "Env-var config can't express structure — doesn't twelve-factor prevent good config?"**

**Answer (the nuanced answer they want):** It prevents config *in the artifact*, not structure *around the artifact*. The layered pattern that satisfies both: defaults in code (versioned, reviewed), environment deltas injected as env vars (small, flat, the only thing that differs), and complex/structured config as a *declared, versioned input* — a mounted config file or a config service — with the file itself outside the artifact and per-environment. Feature flags are a third system on purpose: they change at runtime without deploys, so they live in their own store with their own audit. The trap is the false binary — "all config in env vars" vs "config files are heresy"; the factor's actual contract is: same artifact everywhere, environment expressed as injection, and every layer's change surface deliberate.

## Summary

1. **The process is the unit of deployment** — stateless, disposable, replaceable at any moment
2. **Config is injected, releases are immutable** — the same artifact everywhere, rollback as a first-class operation
3. **Scale by process types** — web/worker/clock, each independent; never one binary doing everything
4. **Logs are streams, admin is one-off** — the platform owns everything around the process
5. **Interviews test diagnosis** — name the violated factor, the failure mode, the fix, and the legitimate exception

# 40.9.02 — Twelve-Factor App Interview Questions

> Practice using the factors to diagnose process state, configuration, release identity, disposability and log ownership. Explain the failure and a justified adaptation; these prompts do not predict a particular interview.

## First Principles

This set probes the interchangeability contract (→ 40.9.01): the platform owns the environment; the app is a replaceable process.

1. **The senior tells are consequence statements**: "MemoryStore sessions are lost on restart *and* differ per replica" beats "processes should be stateless" — juniors recite factors; seniors name what breaks and when.
2. **Every question here maps to an axiom chain** — config is injected, state lives in backing services, releases are immutable. Derive from those and the scenario variants answer themselves.

## Answer Framework

```text
ANSWER STRUCTURE:
  1. The factor by name (III config, VI processes, IX disposability, ...)
  2. The mechanism (what the factor actually constrains)
  3. The failure mode when violated (the incident the interviewer is fishing for)
  4. The fix (the pattern, and where state/config goes instead)
  5. The trade-off (when a deviation is legitimate, and how you contain it)
```

## Beginner

**Q1: What is the Twelve-Factor App, in one sentence?**

**Answer:** A methodology for service applications that separates code, deployment inputs, attached resources and replaceable processes. It helps portability and replacement; a particular platform does not automatically enforce all factors or guarantee service correctness.

**Q2: Why does config belong in environment variables?**

**Answer:** The original factor III recommends independent environment variables for deployment-varying values. They keep the artifact independent of resource bindings. Internal routing stays code. Non-secret deployment manifests can be reviewed safely; env vars can still leak. Mounted config or secret-manager references are deliberate modern adaptations, not the original text.

**Q3: What does "backing services as attached resources" mean?**

**Answer:** Bind a compatible backing service through supplied configuration rather than hard-coding its location. A PostgreSQL URL can select a different compatible server; data migration, permissions, TLS and service capabilities still need verification.

**Q4: Why must processes be stateless?**

**Answer:** Correctness must survive instance loss or replacement. Persist accepted business state externally. Local caches, pools and temporary files may remain when they can be rebuilt and their loss cannot invalidate an acknowledged effect.

**Q5: What is dev/prod parity, and what's the modern version?**

**Answer:** Factor X reduces gaps in backing services, release timing, and operational tools. Matching a local PostgreSQL service to production can improve fidelity, but Compose images and preview environments are implementation choices, not requirements of the factor. Test the production-specific permissions, scale, latency, and failure behavior that local parity cannot reproduce.

## Intermediate

**Q6: Explain build, release, run — and why releases must be immutable.**

**Answer:** Build produces an artifact; release identifies the artifact plus deployment configuration; run executes it. Redeploying an earlier release restores that identity, but does not undo migrations, payments or all config-service changes. Verify compatibility, recovery and rollout time before claiming safe rollback.

**Q7: What's wrong with `MemoryStore` sessions, in-memory rate limiters, and in-process job queues?**

**Answer:** Process-owned session/job state can disappear on restart and differ across replicas. A local limiter can be valid for local resource admission but does not supply a shared quota without allocated budgets or coordination. Persist accepted jobs/sessions as required; shared storage still needs durability, expiry and recovery policies.

**Q8: How does factor VIII (concurrency) say you should scale?**

**Answer:** Separate web, worker and scheduler process types when independent scaling or ownership warrants it. Threads/asynchronous concurrency inside them are allowed. A single desired scheduler replica is not an exclusion guarantee during replacement; enforce durable schedule ownership and duplicate-safe effects.

**Q9: What does disposability require, concretely?**

**Answer:** Measured readiness and bounded graceful termination, plus correctness after abrupt death. Stop admission, resolve or recover in-flight work, then close dependencies under the configured grace period. Thirty seconds is a common Kubernetes default, not a universal requirement; startup probes and readiness should match the workload.

**Q10: How do logs work in twelve-factor, and why not log to files?**

**Answer:** The original factor emits events to stdout for collection by the environment. Structured fields make correlation easier but are not a requirement of the original methodology. Define redaction, collection backpressure, loss and retention; stdout alone does not prove that an event was stored.

## Advanced

**Q11: A teammate hot-patches a running container with `kubectl exec`. Diagnose.**

**Answer:** Factor V violation with a delayed fuse: the running process now diverges from its release — the edit is invisible to Git, lost at the next rollout, and unreproducible in staging. The fix isn't scolding, it's making the legitimate path faster than the hack: ship the config change as a release, or emergency-mitigate *then* converge through code. Same discipline as IaC drift (→ 40.12.02 Q12): classify the change, reconcile it into the declared state.

**Q12: "We mount a PVC for uploads" — is that twelve-factor?**

**Answer:** A durable mount makes storage identity/access part of the application design. Whether replicas diverge depends on the volume access model and ownership, not the existence of a mount alone. Object storage is often suitable for shared uploads. Explain a deliberate stateful deviation and its recovery instead of declaring every PVC unsafe.

**Q13: Where does the methodology fall short in practice?**

**Answer:** Two honest gaps: **database migrations remain stateful, ordered operations** — factor XII describes running administrative tasks as one-off processes, while production gating and overlap control are deployment policy; and **single-tenant stateful products** (self-hosted installs, edge devices) may deliberately adapt factors VI/IX. The senior move is deviating *deliberately, at named boundaries* — not accidentally everywhere.

**Q14: Migrations on boot vs one-off admin processes — defend one.**

**Answer:** Factor XII recommends one-off administrative processes using the release's code and configuration. Running migrations at every replica's boot can race unless a migration lock or single-owner mechanism serializes them; it also couples startup to migration duration. A separately gated migration job is often easier to observe and control. Use backward-compatible expand-and-contract steps when old and new application versions must overlap; neither approach makes a schema change automatically reversible.

**Q15: How does twelve-factor map to Kubernetes and to serverless?**

**Answer:** Kubernetes can supply config, process replacement, scaling and log collection, but it also hosts stateful workloads and does not certify Twelve-Factor compliance. Managed functions have handler invocation, reused warm instances and runtime-specific lifecycle limits. Their durable-state boundary is similar; port binding and shutdown do not map one-to-one.

## Behavioral & Scenario Drills

**Q16 (scenario): Autoscaling doesn't — pods come up, take 60 seconds to be ready, traffic still times out. Diagnose.**

**Answer:** Measure where boot time is spent, ready capacity, scale-out delay and downstream connection load. Lazy initialization may help, but moving required work onto the first request can just shift the incident. Set realistic startup/readiness probes, prepare bounded warm capacity and test the resulting service behavior.

**Q17 (behavioral): Tell me about a time a factor violation caused a real incident.**

**Answer:** Use a real incident from your experience. An illustrative structure: describe process-owned sessions lost during replacement, explain the chosen durable store and expiry/failure policy, report observed deployment/session results, and identify the prevention check. Do not claim the illustrative outcome as personal evidence.

**Q18 (follow-up trap): "It's 2011 software — is twelve-factor still relevant?"**

**Answer:** It remains a useful vocabulary for service deployment boundaries. The methodology was published in 2011; its original pages say they were last updated in 2017, and a community refresh began in 2024. The project says its current update work remains on `next` until maintainers agree the round is complete. Compare each factor with the actual runtime: managed functions, durable volumes and secret delivery may require adaptations. APIs, telemetry and access control add concerns the original text does not exhaust. See the [refresh announcement](https://12factor.net/blog/open-source-announcement) and [manifesto repository](https://github.com/twelve-factor/twelve-factor).

## The Modern Contract

**Q19: Factor XI in 2026 — is stdout still the log contract when OpenTelemetry exists?**

**Answer:** Stdout remains useful when the platform collects it. OpenTelemetry supplies additional signal/context protocols; structured logs may correlate with traces. Choose the collection path, redaction, sampling, overload and retention policy explicitly. Neither stdout nor OTLP alone guarantees durable or complete telemetry.

**Q20: Env vars are flat strings — where does the config approach break down?**

**Answer:** The original factor specifies independent env vars. Large structured inputs and secret exposure may justify mounted files or secret-manager references. Restrict each instance to needed values and validate them. A fetched credential held in memory can still appear in a dump; credential lifetime and diagnostic access remain relevant.

**Q21: What does factor II (dependency declaration) mean in a container world?**

**Answer:** Declare language and system inputs. A lockfile resolves manifest ranges; digest-pinning the base image does not pin every later download or ensure deterministic compilation. Verify clean locked installs and control external build inputs. Upgrade versions intentionally rather than assuming pins can remain forever.

**Q22: How do you reconcile disposability with expensive warm state — connection pools, JIT warmup, caches?**

**Answer:** Distinguish reconstructible warmth from durable business state. Pools, caches and JIT state can remain in-process. Measure warm-up and boot storms; choose bounded initialization, readiness, ready capacity and resource budgets. Moving warmth to a sidecar or shared tier introduces another lifecycle and dependency, not an automatic fix.

**Q23 (scenario): Secrets in env vars showed up in a crash dump. What's the fix set?**

**Answer:** Rotate exposed credentials, locate affected artifacts/access paths and restrict further disclosure while following retention requirements. Remove values from logs/debug output and control dumps. Short-lived credentials, least privilege and suitable delivery reduce exposure, but fetching into memory does not make a secret dump-proof. Validate the actual diagnostic path.

**Q24 (behavioral): Tell me about migrating a legacy app to Kubernetes — what factor violations bit you?**

**Answer:** Describe an actual migration. An illustrative outline is uploads/sessions lost under replacement and overlapping migration execution, followed by durable ownership, a recoverable migration gate and collected logs. State measured results and limitations; do not present an invented deployment as your own.

**Q25 (follow-up trap): "Env-var config can't express structure — doesn't twelve-factor prevent good config?"**

**Answer:** The original text recommends env vars and separates deploy-varying config from internal application wiring. Versioned non-secret deployment manifests, mounted structured inputs and runtime flag services can be deliberate adaptations. Identify each change surface, owner, validation, audit and rollback policy rather than rewriting the original recommendation.

## Summary

1. **The process is the unit of deployment** — stateless, disposable, replaceable under the stated recovery contract
2. **Config is injected, releases are immutable** — the same artifact everywhere, rollback as a first-class operation
3. **Scale by process types** — web/worker/clock, each independent; choose process boundaries for independent scaling
4. **Logs are streams, admin is one-off** — the platform handles collection and routing; the application still owns useful fields and redaction
5. **Interviews test diagnosis** — name the boundary, failure mode, correction, and legitimate exception

# Testing Overview

## Definition

Testing is the systematic process of evaluating a software application to identify defects, verify that requirements are met, and ensure the system behaves as expected under various conditions. In modern software development, testing is not merely a phase but an integral practice woven throughout the entire development lifecycle.

> **Textbook Definition:** Software testing evaluates a system or its components against explicit expectations using selected observations. A test result provides evidence within its inputs, environment and assertions; it cannot establish the absence of all defects.

## First Principles

Suppose a checkout change computes the right total but saves an order twice. Reading the price function would miss the persistence failure. A test must therefore choose both **a claim** and **a boundary** at which to observe it.

Every test needs three things:

1. A known starting state and input.
2. An action that exercises the behavior.
3. An **oracle**: a rule for deciding whether the observed result is correct. A product requirement, independently calculated result, or invariant can supply that rule.

A passing test establishes its particular claim under its particular conditions. It cannot cover inputs it never tries or a database it replaces with a mock. Increasing the scope includes more interactions, but usually adds setup, execution cost, and possible causes of failure. Choose the boundary that can actually expose the defect.

## How Test Boundaries Change the Evidence

Keep one example in view: a customer buys two items at 500 cents each, and an order must be recorded once.

| Boundary | What runs in this example | What the result can establish | What remains outside it |
| ---------------- | ------------------------------------------------------------- | ------------------------------------------------------------------------ | ---------------------------------------------------------- |
| Unit | Price function with explicit inputs | Two items produce a 1,000-cent subtotal; invalid quantities are rejected | Storage, HTTP routing, and browser behavior |
| Integration | Order service with a disposable real database | The actual schema and transaction preserve order and inventory rules | Any replaced payment or email provider |
| API | Real HTTP handler, authentication, and selected dependencies | Status, response, and authorization behavior at that boundary | Browser interaction; infrastructure omitted from the setup |
| End-to-end (E2E) | Browser through the deployed test application | A customer can complete the selected journey and observe its result | Untested journeys and any substituted external services |
| Contract | Producer/consumer messages checked against an agreed contract | The tested requests and responses remain compatible | Whether the entire distributed workflow succeeds |

**Unit** means a deliberately small unit of behavior; teams must state whether a component includes its collaborators. **Integration** means real collaboration across a selected boundary, such as application code executing against PostgreSQL. Test names alone do not describe the setup.

A browser test that intercepts every API request is valuable UI evidence, but it does not prove that the real backend saves the order. Conversely, a database integration test cannot reveal a submit button hidden by CSS.

### The pyramid is a cost model

The **testing pyramid**, popularized by Mike Cohn, recommends many small tests, fewer integration tests, and a limited set of broad journeys. Small tests often provide quicker, more specific feedback; broad tests catch wiring failures those small tests cannot see. It is a starting strategy, not a required 70/20/10 ratio. See [Fowler’s explanation](https://martinfowler.com/bliki/TestPyramid.html).

A service whose main behavior is SQL may need substantial database integration coverage. A pricing library may rely heavily on unit and property tests. Use observed defect risk, run time, and maintenance cost to choose the mix.

**Static analysis**—type checking and linting—checks source properties without running the application. It complements runtime tests. A valid type cannot establish that a stock decrement and an order insert commit atomically.

### Scope and purpose are different dimensions

A **smoke test** checks a small set of vital functions after a build or deployment. A **regression test** preserves behavior that should keep working. Either can run at unit, API, or browser level. Performance, security, and accessibility describe the property under examination; they are not additional levels above E2E.

## Example: Make One Requirement Observable

This self-contained JavaScript example models one price rule. Values use integer cents; it deliberately excludes tax, discounts, currency conversion, and payment settlement.

```javascript
// line-total.cjs — run with: node line-total.cjs
const assert = require('node:assert/strict');

function lineTotalCents(priceCents, quantity) {
  if (!Number.isSafeInteger(priceCents) || priceCents < 0) {
    throw new RangeError('Price must be non-negative integer cents');
  }
  if (!Number.isSafeInteger(quantity) || quantity < 1) {
    throw new RangeError('Quantity must be a positive integer');
  }
  const total = priceCents * quantity;
  if (!Number.isSafeInteger(total)) throw new RangeError('Total exceeds safe range');
  return total;
}

assert.equal(lineTotalCents(500, 2), 1000);
assert.equal(lineTotalCents(0, 1), 0);
assert.throws(() => lineTotalCents(500, 0), RangeError);
assert.throws(() => lineTotalCents(500, 1.5), RangeError);
assert.throws(() => lineTotalCents(-1, 2), RangeError);
assert.throws(() => lineTotalCents(Number.MAX_SAFE_INTEGER, 2), RangeError);
console.log('Price contract passed');
```

Trace the first assertion: the starting input is 500 cents and quantity 2; the function validates each value, multiplies them, then returns 1,000. The assertion compares that return value with an independently chosen expected result. If multiplication changes to addition, it returns 502 and the assertion fails.

The other assertions check distinct boundaries. Zero-priced items are valid; zero quantity is not. Type checking alone would accept both as numbers. Safe-integer checks also bound arithmetic: integer cents do not make arbitrarily large calculations exact.

### Add a real boundary when the claim changes

To test “an order is recorded once even when a request is retried,” the price function is insufficient. An integration scenario needs:

1. A disposable database with the actual migrations, including the uniqueness rule for the request’s idempotency key.
2. A known inventory row and an authenticated customer fixture.
3. Two requests using the same key, including a concurrent variant if concurrent retries are supported.
4. Assertions that one order exists, inventory changed once, and both responses satisfy the documented retry contract.
5. Cleanup or a fresh database/namespace so another test cannot supply the expected order accidentally.

A mock configured to return the same order twice only verifies how the caller uses that mock. It does not verify the database constraint or transaction. If payment is replaced by a fake adapter, test payment-provider compatibility separately and state that limitation. Use provider test mode and isolated outbound adapters for integration environments.

## Use TDD to develop behavior and BDD to agree on it

**Test-driven development (TDD)** uses a short red → green → refactor cycle:

- **Red:** express the next behavior and observe failure for the expected reason. A missing import can be a useful initial failure, but it is not yet evidence that the business assertion detects a defect.
- **Green:** implement enough behavior to satisfy that claim.
- **Refactor:** improve structure while preserving the behavior, then rerun relevant tests.

For the price example, start with `500 × 2 = 1000`, then introduce invalid-quantity and overflow requirements as separate steps. A bug fix should first reproduce the actual failure; a test that passes before the fix does not establish that the regression is covered.

**Behavior-driven development (BDD)** brings product, engineering, and testing perspectives together to discover concrete examples of required behavior. Given–When–Then is a useful way to express them; a particular syntax or Cucumber installation is not the whole practice. The [Cucumber BDD guide](https://cucumber.io/docs/bdd/) describes that collaboration.

```text
Given one item remains in stock
When two customers attempt to reserve it concurrently
Then exactly one reservation succeeds
And stock never becomes negative
```

That scenario forces decisions about concurrency and failure responses before implementation. Automation still requires step definitions or tests that create the stated conditions and verify the real outcome. A feature file alone does not execute the requirement.

## Use test results when deciding what to ship

Under deadline pressure, prioritize the highest-impact plausible failure and the cheapest test that exposes it. State what remains untested. A green suite cannot replace deployment evidence, monitoring or a rollback plan.

### Read coverage as execution, not correctness

Line coverage records which lines executed; branch coverage records selected control-flow outcomes. Neither proves that the assertion checks the right result. Calling the price function without asserting anything can still execute all of it.

Use uncovered critical paths to find missing scenarios. Review assertions and invalid inputs. **Mutation testing** deliberately changes the implementation—for example, multiplying becomes adding—to check whether the suite notices. A surviving mutation is a prompt to inspect missing assertions or cases; some mutations are equivalent or irrelevant to the contract.

### Diagnose flaky tests through uncontrolled state

A flaky test changes outcome without a relevant product change. Investigate shared data, real clocks, scheduler timing, network dependencies, and leaked resources. Await observable completion instead of sleeping for a guessed duration. If time is part of the requirement, control the clock and test before, exactly at, and after the boundary; restore fake timers afterward.

Retries can help collect evidence, but repeated green runs do not explain the first failure. Quarantine only with a named owner and repair date. Parallelize after isolating databases, ports and accounts; keep failure output tied to the violated claim; and measure the suite's critical path before setting run-time budgets.

Keep arrange → act → assert clear, clean up owned resources, and review changed snapshots or golden outputs against the requirement. Run relevant checks locally and automate required suites in continuous integration (CI).

## Summary

A useful test connects a concrete condition to an observable claim. Small tests isolate logic; real boundary tests expose collaboration failures; broad journeys check selected user outcomes. Choose their mix from risk and cost, control the environment, and interpret passing results within their actual scope. Coverage and repeatability support that evidence without proving every requirement is correct.

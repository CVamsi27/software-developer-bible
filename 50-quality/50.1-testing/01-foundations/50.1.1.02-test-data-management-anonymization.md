# Test Data Management & Anonymization

> An order test fails only when another test runs first, while staging contains customer details copied from production. Good test data must make the behavior reproducible, isolate each test, and fit the claim without carrying unnecessary personal information.

## Definition

**Test data management (TDM)** is the practice of planning, generating, provisioning, and maintaining the data that automated tests and staging environments need — with controlled quality, volume, and sensitivity.

> **Textbook Definition:** Test data management controls the creation, provision, lifecycle and protection of datasets used for testing. Anonymization removes reasonably likely identification paths; pseudonymization separates identifiers while retaining a route to re-identification.

## First Principles

A failing order test needs enough data to reproduce the failure, a fresh starting state, and no unintended contact with real customers. Those needs pull in different directions: production rows have realistic relationships, but carry sensitive information; generated rows are easier to control, but can miss important distributions.

Choose data from the claim being tested. One invalid quantity needs a tiny explicit fixture. A query-plan test needs representative row counts and value frequencies. Neither needs a customer’s real name or email address.

Reproduction also requires controlling every relevant input. A random seed controls a generator’s sequence; it does not fix the clock, shared database state, library version, or concurrent call order.

## What changes when data is shared, unrealistic or sensitive?

Data determines which behaviors a test can observe. An empty staging database hides slow joins; ASCII-only names hide Unicode bugs; a shared mutable account makes tests pass or fail according to execution order. Sensitive exports add a separate access and retention problem even when the application tests pass.

Treat datasets as managed artifacts: give each one a purpose, owner, source, version, lifecycle, and sensitivity classification. Synthetic data is usually the simplest starting point. Production-derived data needs an explicit justification and controls for the risk that remains.

## Build the dataset from the claim under test

### Start with small explicit fixtures

A **factory** returns a valid object with defaults. A test overrides the fields relevant to its claim. A **builder** offers named construction steps when a complex object benefits from them; it is not necessary for every fixture.

```javascript
// Self-contained fixture: no clock, global counter, or random source.
function buildUser(overrides = {}) {
  return {
    id: 'user-001',
    email: 'user-001@example.invalid',
    name: 'Test User',
    createdAt: '2024-01-01T00:00:00.000Z',
    role: 'member',
    ...overrides,
  };
}

const first = buildUser();
const second = buildUser({ id: 'user-002', email: 'user-002@example.invalid' });
console.log(first.id, second.id); // user-001 user-002
```

Each call creates a new object, so changing `first.name` does not change `second.name`. Explicit IDs make assertions readable. When inserting several users into a database with unique email constraints, supply distinct IDs and emails deliberately. A convenient constant default is not a unique-ID generator.

Use reserved domains and documentation IP ranges for fixtures, and also replace or disable email, SMS, payments, and other outbound adapters. A reserved address is a data convention; it cannot prevent a misconfigured application from contacting an external provider.

### Add generated variety without losing reproduction

A realistic generator such as Faker can produce many shapes and values. Keep hand-authored edge cases as well: random sampling may never produce the exact leap day, maximum length, or mixed-script input that matters.

This example requires the installed `@faker-js/faker` package. Pin its version in the lockfile. The seed, reference date, locale, and sequence of calls all affect the output.

```javascript
import { faker } from '@faker-js/faker';

function generateUsers(count) {
  if (!Number.isSafeInteger(count) || count < 0 || count > 10000) {
    throw new RangeError('Count must be an integer from 0 through 10000');
  }
  faker.seed(42);
  return Array.from({ length: count }, (_, index) => ({
    id: `user-${index + 1}`,
    email: `user-${index + 1}@example.invalid`,
    name: faker.person.fullName(),
    registeredAt: faker.date.recent({
      days: 365,
      refDate: '2024-01-01T00:00:00.000Z',
    }).toISOString(),
  }));
}

const first = generateUsers(3);
const replay = generateUsers(3);
console.log(JSON.stringify(first) === JSON.stringify(replay)); // true
```

The fixed reference date removes “today” as an input. Generated IDs and emails are explicitly unique within this batch; Faker’s random values do not promise uniqueness. Resetting Faker’s global seed inside concurrent tests can interfere with other calls, so isolate the generator per worker or run this seeding step before parallel tests. [Faker’s reproducibility guide](https://fakerjs.dev/guide/usage.html#reproducible-results) explains the date and version boundaries.

A seed can reproduce a generated name; it does not establish useful distribution. For volume tests, model relationships and skew explicitly: orders need existing customers, and a few large tenants may account for most traffic. Estimate generation time, insert in bounded batches, and validate foreign keys rather than promising a fixed throughput.

### Distinguish anonymization from pseudonymization

**Anonymization** aims to leave people no longer identifiable by means reasonably likely to be used. **Pseudonymization** replaces or separates identifying information while additional information can still attribute the data to a person. Pseudonymized personal data remains personal data under GDPR. These distinctions come from [GDPR Recital 26 and Article 4(5)](https://eur-lex.europa.eu/eli/reg/2016/679/oj/eng).

Removing a name alone is insufficient. A **quasi-identifier** is a field that may identify someone when combined with other data: exact birth date, location, or a distinctive sequence of events. Assess the whole release and available linkage, not just whether a transformation has an inverse function.

| Transformation | What changes | Risk still requiring assessment |
| -------------- | ----------------------------------------------- | ------------------------------------------------------------------------- |
| Drop fields | Remove notes or unnecessary columns | Remaining fields or rows may still identify someone |
| Generalize | Exact age becomes an age range | Rare combinations may remain unique |
| Shuffle | Reassign selected values between rows | Other identifiers persist; relationships may become false |
| Keyed token | Replace a subject ID consistently across tables | Stable linkage and knowledge of the key or source can support attribution |
| Vaulted token | Keep a separate mapping from token to original | Access to the mapping permits re-identification |
| Shift dates | Move a subject’s dates by one offset | Intervals and event patterns can still be distinctive |

These are tools, not a universal ranking from “safe” to “unsafe.” Even a dataset with no reversible identifier may remain identifiable through its unusual records. Free text, nested JSON, filenames, attachments, and logs need review alongside structured columns. [NIST’s de-identification report](https://nvlpubs.nist.gov/nistpubs/ir/2015/NIST.IR.8053.pdf) develops these risks.

## Example: Preserve Joins with a Pseudonymous ID

Suppose customer and order tables both reference customer `42`. Replacing each occurrence with the same token preserves their join without exporting the original ID. This is **pseudonymization**, not proof of anonymity.

The following Node.js example uses HMAC, a keyed message authentication code, rather than concatenating a secret with a value and calling it a keyed hash. The generated key is only for this local demonstration; an export pipeline needs a managed, stable secret held within its controlled transformation environment.

```javascript
const assert = require('node:assert/strict');
const { createHmac, randomBytes } = require('node:crypto');

const key = randomBytes(32); // Ephemeral demonstration key; never print it.
function customerToken(id) {
  if (typeof id !== 'string' || id.length === 0) {
    throw new TypeError('Customer ID must be a non-empty string');
  }
  return createHmac('sha256', key)
    .update('customer-id:v1:') // Separate this token namespace from other fields.
    .update(id)
    .digest('hex');
}

const customer = { id: customerToken('42') };
const order = { id: 'order-001', customerId: customerToken('42') };
assert.equal(customer.id, order.customerId);
assert.notEqual(customer.id, customerToken('43'));
console.log('Customer/order join preserved');
```

Both tables use the same key, namespace, and input representation, so the same ID produces the same token. A different key breaks that correspondence; a refresh must therefore version the token scheme and replace related datasets together. Retain the full digest and validate uniqueness when exporting. The function does not scrub dates, addresses, or event histories.

HMAC is not encryption and has no decrypt operation. However, someone with the key and candidate source IDs can recompute tokens, and other released fields may permit linkage without the key. Keep the output classified according to its remaining identifiability. The [Node.js HMAC API](https://nodejs.org/api/crypto.html#cryptocreatehmacalgorithm-key-options) documents the mechanism.

### Transform before exporting, then validate the result

If production-derived data is justified, keep raw extraction and transformation in the controlled source environment. Allowlist output fields; discard unnecessary free text; assess linkage; validate relationships; then release only the approved output to its destination. Restrict access, encrypt transport and storage, and expire raw intermediates and test copies according to their lifecycle.

A pattern scanner can flag suspected emails or phone numbers in rows and logs. It has false positives and false negatives: a synthetic address looks like an address, while an identifying event pattern may match no regular expression. Scanning supplements transformation review and access controls; it cannot prove that no personal data exists.

## Golden Datasets Need an Independent Oracle

A **golden dataset** is a reviewed set of inputs and expected outputs, reused to detect behavior changes. It can be entirely synthetic. Its value comes from the expected results, not from using production data or a large file.

```javascript
const assert = require('node:assert/strict');

const corpus = {
  version: 1,
  cases: [
    { input: { priceCents: 500, quantity: 2 }, expected: 1000 },
    { input: { priceCents: 0, quantity: 1 }, expected: 0 },
  ],
};

// Focused fixture contract; input validation belongs to the price function.
function quote({ priceCents, quantity }) { return priceCents * quantity; }
for (const example of corpus.cases) {
  assert.equal(quote(example.input), example.expected);
}
console.log('Golden cases passed');
```

The expected 1,000 comes from the agreed price rule. If a refactor returns 502, the test should fail. Regenerating the expected output directly from the defective implementation would erase the evidence.

Version the schema and corpus; review changes with their business rationale. A checksum can detect changes to stored bytes when compared against a separately recorded expected digest. It does not tell whether those bytes represent correct expectations. Define canonical serialization if comparing semantic data rather than exact file bytes.

## Preserve realism only where the evidence needs it

A customer-specific failure usually needs a synthetic input with the same structural property, not a raw customer dump. A migration rehearsal needs representative volumes, nulls, malformed legacy values and foreign-key relationships; a tiny clean fixture cannot estimate its lock window. A load test needs relevant tenant sizes, request patterns and value frequencies, because uniform random rows may produce an unrealistic query plan. Before a staging refresh, validate counts and constraints, keep a rollback snapshot and ensure an incomplete load cannot mix old and new IDs.

Before sharing a dataset, record its owner, purpose, version, sensitivity and retention. Pin the generator version, seed and reference date; isolate each test or worker's mutable state; replace live outbound email, SMS and payment adapters; and inspect backups, logs, attachments and raw exports as well as database rows. Review golden expectations against the business rule before accepting a changed file. Prefer synthetic data; when a transformed export is necessary, describe the identification risk that remains instead of treating a tokenization technique as proof of anonymity.

## Summary

Test data must match the behavior being examined and reproduce its conditions. Explicit fixtures make small claims clear; controlled generators add variety and volume; reviewed golden cases preserve expected behavior. A seed alone does not guarantee determinism, and tokenizing identifiers does not establish anonymity. Manage relationships, outbound effects, sensitivity and cleanup across the full dataset lifecycle.

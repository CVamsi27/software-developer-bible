# Test Data Management & Anonymization

An order test fails only when another test runs first, while staging holds customer rows copied from production. Good test data must make the behavior reproducible, isolate each test, and fit the claim — without carrying real personal information.

```javascript
// Claim-first fixture: explicit, isolated, no real customer data.
function buildUser(overrides = {}) {
  return {
    id: 'user-001',
    email: 'user-001@example.invalid',
    name: 'Test User',
    createdAt: '2024-01-01T00:00:00.000Z',
    role: 'member',
    ...overrides,
  };
}
```

## Definition

**Test data management** plans, generates, provisions and maintains the data that tests and staging environments need — with controlled quality, volume and **sensitivity**. **Anonymization** removes reasonably likely identification paths; **pseudonymization** separates identifiers while retaining a route to re-identification.

> **Textbook Definition:** Test data management controls the creation, provision, lifecycle and protection of datasets used for testing. Anonymization removes reasonably likely identification paths; pseudonymization separates identifiers while retaining a route to re-identification.

## First Principles

A failing order test needs enough data to reproduce the failure, a fresh starting state, and no contact with real customers. Those needs pull in different directions: production rows have realistic relationships but carry sensitive information; generated rows are easier to control but can miss important distributions. Choose data from the claim being tested — one invalid quantity needs a tiny explicit fixture, a query-plan test needs representative row counts — and neither needs a real name or email address.

## How It Works

### 1. Start With Small Explicit Fixtures

A **factory** returns a valid object with defaults; a test overrides the fields relevant to its claim. A **builder** offers named construction steps when a complex object benefits from them; it is not necessary for every fixture.

```javascript
const first = buildUser();
const second = buildUser({ id: 'user-002', email: 'user-002@example.invalid' });
console.log(first.id, second.id); // user-001 user-002
```

Each call creates a new object, so changing `first.name` does not change `second.name`. Explicit IDs make assertions readable; with unique email constraints, supply distinct IDs and emails deliberately. Use reserved domains and documentation IP ranges, and replace or disable email, SMS, payments and other outbound adapters — a reserved address is a data convention, it cannot stop a misconfigured app from contacting a provider.

### 2. Add Generated Variety Without Losing Reproduction

A realistic generator such as Faker produces many shapes and values, but keep hand-authored edge cases too: random sampling may never produce the exact leap day, maximum length or mixed-script input that matters. This example requires the installed `@faker-js/faker` package, pinned in the lockfile; the seed, reference date, locale and call sequence all affect output.

```javascript
import { faker } from '@faker-js/faker';

function generateUsers(count) {
  if (!Number.isSafeInteger(count) || count < 0 || count > 10000) {
    throw new RangeError('Count must be an integer from 0 through 10000');
  }
  faker.seed(42);
  return Array.from({ length: count }, (_, index) => ({
    id: `user-${index + 1}`,
    email: `user-${index + 1}@example.invalid`,
    name: faker.person.fullName(),
    registeredAt: faker.date.recent({
      days: 365,
      refDate: '2024-01-01T00:00:00.000Z',
    }).toISOString(),
  }));
}
```

The fixed reference date removes "today" as an input, and reseeding reproduces the sequence — but a seed reproduces values, not useful distribution. For volume tests, model relationships and skew explicitly: orders need existing customers, and a few large tenants may hold most traffic. Resetting Faker's global seed inside concurrent tests can interfere with other calls, so isolate the generator per worker. [Faker's reproducibility guide](https://fakerjs.dev/guide/usage.html#reproducible-results) explains the date and version boundaries.

### 3. Distinguish Anonymization From Pseudonymization

**Anonymization** aims to leave people no longer identifiable by means reasonably likely to be used. **Pseudonymization** replaces or separates identifiers while additional information can still attribute the data to a person. Under GDPR, pseudonymized data remains personal data wherever the person is identifiable by means reasonably likely to be used. See [GDPR Recital 26 and Article 4(5)](https://eur-lex.europa.eu/eli/reg/2016/679/oj/eng).

Removing a name alone is insufficient. A **quasi-identifier** — exact birth date, location, a distinctive event sequence — may identify someone when combined with other data. Assess the whole release and available linkage, not just whether a transformation has an inverse function.

| Transformation | What changes | Risk still requiring assessment |
| -------------- | ----------------------------------------------- | ------------------------------------------------------------------------- |
| Drop fields | Remove notes or unnecessary columns | Remaining fields or rows may still identify someone |
| Generalize | Exact age becomes an age range | Rare combinations may remain unique |
| Shuffle | Reassign selected values between rows | Other identifiers persist; relationships may become false |
| Keyed token | Replace a subject ID consistently across tables | Stable linkage and knowledge of the key or source can support attribution |
| Vaulted token | Keep a separate mapping from token to original | Access to the mapping permits re-identification |
| Shift dates | Move a subject's dates by one offset | Intervals and event patterns can still be distinctive |

These are tools, not a universal ranking from "safe" to "unsafe." Free text, nested JSON, filenames, attachments and logs need review alongside structured columns. [NIST's de-identification report](https://nvlpubs.nist.gov/nistpubs/ir/2015/NIST.IR.8053.pdf) develops these risks.

### 4. Preserve Joins With a Pseudonymous ID

Suppose customer and order tables both reference customer `42`. Replacing each occurrence with the same token preserves their join without exporting the original ID. This is **pseudonymization**, not proof of anonymity. The example uses HMAC — a keyed message authentication code — with an ephemeral local key; an export pipeline needs a managed, stable secret held in its controlled transformation environment.

```javascript
const assert = require('node:assert/strict');
const { createHmac, randomBytes } = require('node:crypto');

const key = randomBytes(32); // Ephemeral demonstration key; never print it.
function customerToken(id) {
  if (typeof id !== 'string' || id.length === 0) {
    throw new TypeError('Customer ID must be a non-empty string');
  }
  return createHmac('sha256', key)
    .update('customer-id:v1:') // Separate this token namespace from other fields.
    .update(id)
    .digest('hex');
}

const customer = { id: customerToken('42') };
const order = { id: 'order-001', customerId: customerToken('42') };
assert.equal(customer.id, order.customerId);
assert.notEqual(customer.id, customerToken('43'));
console.log('Customer/order join preserved');
```

Both tables use the same key, namespace and input representation, so the same ID yields the same token. A different key breaks that correspondence, so a refresh must version the token scheme and replace related datasets together. HMAC is not encryption and has no decrypt operation — but anyone with the key and candidate source IDs can recompute tokens. Keep the output classified by its remaining identifiability. The [Node.js HMAC API](https://nodejs.org/api/crypto.html#cryptocreatehmacalgorithm-key-options) documents the mechanism.

### 5. Transform Before Exporting, Then Validate the Result

If production-derived data is justified, keep raw extraction and transformation in the controlled source environment:

```text
allowlist fields → discard free text → assess linkage → validate
relationships → release only approved output → expire intermediates
```

Include backups, logs, attachments and raw exports in scope; deleting database rows does not erase their copies. Restrict access, encrypt transport and storage, and expire raw intermediates and test copies by lifecycle. A pattern scanner can flag suspected emails or phone numbers, but it has false positives and negatives — scanning supplements review and access controls, it cannot prove no personal data exists.

### 6. Prove Behavior With Golden Datasets

A **golden dataset** is a reviewed set of inputs and expected outputs, reused to detect behavior changes. It can be entirely synthetic; its value comes from the expected results, not from production data or file size.

```javascript
const assert = require('node:assert/strict');

const corpus = {
  version: 1,
  cases: [
    { input: { priceCents: 500, quantity: 2 }, expected: 1000 },
    { input: { priceCents: 0, quantity: 1 }, expected: 0 },
  ],
};

function quote({ priceCents, quantity }) { return priceCents * quantity; }
for (const example of corpus.cases) {
  assert.equal(quote(example.input), example.expected);
}
console.log('Golden cases passed');
```

The expected 1,000 comes from the agreed price rule — regenerating expectations from a defective implementation would erase the evidence. Version the schema and corpus, and review changes with their business rationale. A checksum detects changed bytes against a separately recorded digest; it does not tell whether those bytes are correct.

### 7. Use Representative Scale Only When the Claim Needs It

A customer-specific failure usually needs a synthetic input with the same structural property, not a raw customer dump. A migration rehearsal needs representative volumes, nulls, malformed legacy values and foreign-key relationships; a tiny clean fixture cannot estimate its lock window. A load test needs realistic tenant sizes and value frequencies because uniform random rows may produce an unrealistic query plan. Before switching a refreshed staging dataset into use, validate counts and constraints, keep a rollback snapshot, and prevent an incomplete load from mixing old and new identifiers.

## Summary

Test data must match the behavior being examined and reproduce its conditions. Explicit fixtures make small claims clear; seeded generators add variety and volume without guaranteeing determinism; reviewed golden cases preserve expected behavior. Tokenizing identifiers does not establish anonymity, and scanning does not prove absence of personal data. Manage relationships, outbound effects, sensitivity and cleanup across the full dataset lifecycle.

# Test Data Management & Anonymization

## Definition

**Test data management (TDM)** is the practice of planning, generating, provisioning, and maintaining the data that automated tests and staging environments need — with controlled quality, volume, and sensitivity.

> **Textbook Definition:** Test data management controls the creation, provision, lifecycle and protection of datasets used for testing. Anonymization removes reasonably likely identification paths; pseudonymization separates identifiers while retaining a route to re-identification.

**Anonymization** irreversibly transforms data so individuals can no longer be identified (by any means reasonably likely). **Pseudonymization** replaces identifying fields with tokens while retaining re-identification possibility via a separately held key — it reduces risk but is still personal data under GDPR.

```text
TEST DATA PYRAMID
                    /\
                   /  \   Golden / anonymized production-derived sets
                  /----\  (staging, regression suites) - slow to build,
                 /      \ high fidelity, strictest controls
                /--------\
               /          \ Faker-seeded synthetic datasets
              /------------\ (integration tests) - realistic shape,
             /              \ zero PII, generated per-run or nightly
            /----------------\
           /                  \ Factories & builders
          /--------------------\ (unit tests) - explicit fields,
         /                      \ defaults for everything else
        ────────────────────────────────────────────────────────
```

## First Principles

Test data has two colliding constraints: realism and privacy.

1. **Realism drives defect detection; privacy forbids production data** — the resolution is *synthetic-but-shaped* data: generated distributions, anonymization on export (k-anonymity style rules), and per-test seeding for reproducibility.
2. **Deterministic data makes deterministic tests**: seeded factories (→ 50.1.4.02) beat shared fixtures — shared mutable fixtures are the coupling that makes suites order-dependent.

## Why it matters

Interviewers rarely ask "how do you write a fixture" at senior level — they ask "your QA environment was breached and it contained real customer rows. What went wrong?" The answer lives in TDM: environments are lower-security by nature (broader access, weaker monitoring, third-party tools), so production data must never flow into them untransformed. GDPR fines apply to test environments exactly as to production; "it was just staging" has never been a defense. Beyond compliance, bad test data causes real failures: fixtures with `"test"` in every field pass trivially but miss Unicode names, negative amounts, leap days, and 10,000-character inputs that production serves daily.

## Why Do We Need It?

- **Compliance**: GDPR Art. 5(1)(f), HIPAA, PCI-DSS all prohibit uncontrolled copies of personal data; a staging database dump is a reportable breach if it contains live PII.
- **Realism without exposure**: bugs cluster where data is weird (long strings, mixed scripts, boundary dates); faker + curated edge cases deliver realism safely.
- **Deterministic debugging**: reproducible seeds make a failing test replay identically on any machine.
- **Regression confidence**: golden datasets pin behavior across refactors and migrations — same input, byte-comparable output.
- **Environment parity**: staging that looks nothing like production (empty tables, toy volumes) hides N+1s and index misses until launch week.
- **Developer velocity**: self-service factories beat waiting for a DBA-approved extract.

## How It Works

### Layer 1 — Factories and builders (unit tests)

Factories create valid objects with sensible defaults; tests override only what matters. Builders make intent explicit via chained setters. Recap of the pattern from mocking-and-patterns:

```typescript
// Factory: function returning a valid object, overrides last
type UserOverrides = Partial<User>;

export function buildUser(overrides: UserOverrides = {}): User {
  return {
    id: crypto.randomUUID(),
    email: `user-${Date.now()}-${Math.random().toString(36).slice(2)}@example.test`,
    name: 'Test User',
    createdAt: new Date('2024-01-01T00:00:00Z'),
    role: 'member',
    ...overrides,
  };
}

// Builder: fluent API when object construction has many optional parts
const invoice = new InvoiceBuilder()
  .forCustomer(customerId)
  .withLineItem({ sku: 'SKU-1', quantity: 2 })
  .issuedOn(new Date('2024-03-31'))
  .build();
```

Key rules: use `.example` / `.test` TLDs and reserved ranges so fixtures can never collide with real domains or emails; every field gets a default; helpers like `buildList(n, fn)` generate collections.

### Layer 2 — Realistic generators (integration tests)

Hand-written factories cover structure; **faker** covers *variety*. Seed the RNG for determinism:

```typescript
import { faker } from '@faker-js/faker';

// Deterministic runs: same seed -> same dataset everywhere
faker.seed(42);

export const userFactory = (): User => ({
  id: faker.string.uuid(),
  name: faker.person.fullName(),          // handles scripts, diacritics
  email: faker.internet.email(),
  address: {
    street: faker.location.streetAddress(),
    city: faker.location.city(),
    postcode: faker.location.zipCode(),
  },
  birthDate: faker.date.birthdate({ min: 18, max: 90 }),
});

// Volume testing locally: 50k orders in milliseconds
const bulk = Array.from({ length: 50_000 }, orderFactory);
```

Faker locales (`fakerDE`, `fakerJA`) surface internationalization bugs — collation, RTL text, non-Latin address formats — that ASCII-only fixtures never catch.

### Layer 3 — Anonymized production-derived data (staging)

When fidelity demands production-like distributions (query plans, cardinality, index statistics), derive staging data from production through a refresh pipeline that anonymizes before the data leaves the secure zone:

```text
PRODUCTION (secure zone)
    |
    v  extract (read replica)
+--------------------+
| Anonymization job  |  deterministic hashing for joins,
| - drop free text   |  format-preserving tokenization for cards,
| - hash/tok IDs     |  date shifting preserving intervals
| - shuffle dates    |
+--------------------+
    |
    v
STAGING (lower trust) ----> golden snapshot (versioned, checksummed)
```

Techniques, strongest first:

| Technique | What it does | Reversible? | Notes |
| ----------------------- | ------------------------------------------------ | ---------------------- | --------------------------------------------------- |
| Suppression / dropping | Remove column entirely | No | Default for free text (support notes, chat logs) |
| Generalization | `age 37` -> bucket `35-44`, exact city -> region | No | Loses precision, keeps distribution |
| Shuffling | Shuffle a column across rows | No | Preserves distribution, breaks row-level truth |
| Hashing (salted, keyed) | `sha256(email + secret)` | No | Deterministic -> preserves joins across tables |
| Tokenization | Replace with token, keep mapping vaulted | Yes (key holders only) | Format-preserving variants keep card/phone shapes |
| Date shifting | Shift each subject's dates by one random offset | No | Preserves inter-event intervals (session analytics) |

The classic failure is re-identification through **linkage**: an "anonymous" table where zip code + birth date + gender uniquely identify most US adults (Sweeney's research). Anonymize *quasi-identifiers*, not just direct identifiers — or better, synthesize rather than transform.

## Code Examples

### A faker-based seeder with a fixed seed

```typescript
import { faker } from '@faker-js/faker';
import { PrismaClient } from '@prisma/client';

const prisma = new PrismaClient();

export async function seedDatabase(rows: number): Promise<void> {
  faker.seed(2024); // identical dataset on every environment

  await prisma.user.createMany({
    data: Array.from({ length: rows }, () => ({
      email: faker.internet.email(),
      displayName: faker.person.fullName(),
      registeredAt: faker.date.recent({ days: 365 }),
      status: faker.helpers.arrayElement(['active', 'dormant', 'churned']),
    })),
  });
}
```

### Anonymizing an export before it reaches staging

```typescript
import { createHash } from 'node:crypto';

const SALT = process.env.ANONYMIZATION_SALT!; // held only in the secure zone

function keyedHash(value: string): string {
  return createHash('sha256').update(SALT + value).digest('hex');
}

type RawRow = {
  id: number;
  email: string;
  fullName: string;
  notes: string;
  createdAt: Date;
};

type SafeRow = {
  id: string;       // stable pseudonym: joins still work
  email: string;    // syntactically valid, semantically fake
  fullName: string; // replaced wholesale
  notes: null;      // free text suppressed outright
  createdAt: Date;  // shifted per-subject below
};

export function anonymizeRows(
  rows: RawRow[],
  shiftForId: Map<number, number>,
): SafeRow[] {
  return rows.map((row) => ({
    id: keyedHash(String(row.id)).slice(0, 24),
    email: `${keyedHash(row.email).slice(0, 16)}@example.invalid`,
    fullName: faker.person.fullName(),
    notes: null,
    createdAt: new Date(row.createdAt.getTime() + shiftForId.get(row.id)!),
  }));
}
```

Note the details that interviews probe: the salt never leaves the secure zone (otherwise hashing is reversible via rainbow tables against known emails); `.invalid` TLD guarantees no accidental sends; per-subject date shifts keep session durations truthful while hiding absolute times.

### Golden dataset for regression testing

```typescript
import { readFileSync, writeFileSync } from 'node:fs';
import { createHash } from 'node:crypto';

describe('pricing engine', () => {
  const GOLDEN_PATH = 'testdata/pricing/golden-v3.json';

  it('produces byte-stable quotes for the golden corpus', () => {
    const corpus: GoldenCase[] = JSON.parse(readFileSync(GOLDEN_PATH, 'utf8'));

    for (const tc of corpus.cases) {
      const actual = quote(tc.input);
      expect(actual).toEqual(tc.expected);
    }
    expect(corpus.checksum).toBe(
      createHash('sha256').update(JSON.stringify(corpus.cases)).digest('hex'),
    );
  });
});
```

Golden files are reviewed like code, versioned with a suffix (`golden-v3`), and regenerated deliberately — never silently overwritten on failure.

## Real-World Use Cases

1. **Nightly staging refresh** — cron extracts from a production read replica, runs the anonymizer inside the VPC, uploads a checksummed dump; staging restores at 04:00 and CI smoke tests validate row counts and referential integrity before anyone logs in.
2. **GDPR audit response** — DPO asks "prove no personal data exists in non-production." Answer: generator-based seeding end-to-end plus a scanner (Trufflehog-style regexes for emails/phones/IBANs) running against every restore, wired as a CI gate.
3. **Migration dress rehearsal** — copy the anonymized golden snapshot, run the schema migration against full-scale data, measure runtime and lock windows before touching production.
4. **Load-test correlation** — performance team needs 10M orders whose *distribution* matches production (order sizes, peak-hour skew); faker alone gives uniform noise, so sample statistical profiles from prod metadata (counts, histograms — not rows).
5. **Flaky bug reproduction** — support escalates a crash on a specific customer profile; engineer reconstructs an equivalent *synthetic* profile (same structural properties, zero real fields) and attaches it to the failing test permanently.

## Common Mistakes

```typescript
// BAD: copying prod "just this once", promising to scrub later
await exec('pg_dump prod > staging.sql'); // now you have a breach, not a shortcut

// GOOD: pipeline anonymizes inside the secure zone before any egress
const safe = anonymize(extract(replica));
uploadToStaging(safe);
```

```typescript
// BAD: naive masking destroys joins AND leaves quasi-identifiers intact
rows.map((r) => ({ ...r, email: 'redacted@example.com', zip: r.zip }));

// GOOD: deterministic keyed hashes preserve joinability; generalize zip
rows.map((r) => ({
  ...r,
  email: keyedHash(r.email),
  zip: r.zip.slice(0, 2) + '00', // generalization
}));
```

```typescript
// BAD: unseeded faker -> every CI run sees different data -> flaky tests
const user = { name: faker.person.fullName() };

// GOOD: seed once per suite for reproducibility
beforeAll(() => faker.seed(1234));
```

Other frequent errors:

- **Logging leaks**: anonymized DB, but the app logs request bodies with real-looking payloads — synthetic data must also feed log-capture tests; scan logs for PII patterns too.
- **Free text amnesia**: teams anonymize structured columns and forget `notes`, `bio`, uploaded filenames, JSON blobs — suppression is the only safe default for unstructured text.
- **Golden rot**: golden files updated by regenerating after failures ("make it green") until they assert nothing; treat changes as code review events with rationale.
- **One mega-fixture**: a single shared fixture file mutated by dozens of tests creates inter-test coupling; scope fixtures per suite and rebuild state per test.

## Best Practices

1. **Synthetic-first policy**: default answer is "generate"; production-derived data requires justification and approval.
2. **Seed everything**: deterministic seeds turn "flaky" into "reproducible" overnight.
3. **Anonymize at source, inside the secure zone**; salt/key never leaves production boundaries.
4. **Automate PII scanning** of any restored environment as a CI gate — defense in depth behind the pipeline.
5. **Version golden datasets** and review their diffs; document regeneration procedure.
6. **Refresh on a schedule** (nightly or weekly) so staging drift stays small; validate restores with smoke checks on counts and constraints.
7. **Use reserved TLDs** (`.example`, `.invalid`, `.test`) and RFC 5737 IPs so fake data can never reach real systems.

## Performance Considerations

Generating millions of faker rows is CPU-bound; parallelize workers and batch inserts (`createMany` / `COPY`) — row-by-row ORM inserts turn a 2-minute seed into an hour. Keep unit-test factories allocation-cheap (plain objects, no I/O); reserve heavy seeded datasets for dedicated integration jobs so PR CI stays fast. Snapshot golden datasets compressed (`zstd`) — they compress extremely well due to structural repetition. For very large staging volumes, consider subset cloning: extract a referentially-consistent slice (orders joined to their customers/products) rather than full-table percentages, which break foreign keys.

## Summary

- Test data follows its own pyramid: factories (unit) → faker-seeded synthetic sets (integration) → anonymized golden snapshots (staging/regression).
- Anonymization is irreversible; pseudonymization retains a key path and remains regulated personal data — know which one your pipeline actually performs.
- Quasi-identifiers (zip, birthdate, device IDs) re-identify people even after names/emails are stripped; suppress free text by default.
- Deterministic seeds make datasets reproducible across machines, killing a whole class of flaky failures.
- Treat test data as a versioned artifact produced by a pipeline — never by ad-hoc dumps from production.
- Automated PII scanning of non-production environments is the safety net that catches process violations before auditors do.

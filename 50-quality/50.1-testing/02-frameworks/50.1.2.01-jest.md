# Jest

## Definition

**Jest** discovers and runs tests, supplies assertions and mocks, and reports results and optional coverage. The runner decides *when and where* tests execute; a test environment supplies globals such as Node APIs or a simulated DOM; a transformer converts unsupported syntax into executable JavaScript. Those are separate responsibilities.

## First Principles

A useful test must fail when an observable contract breaks. Its result must also be independent of unrelated tests. Waiting for asynchronous work, controlling selected dependencies and cleaning up state make that result interpretable. Test-file isolation helps, but it cannot isolate a shared database, a remote service, a filesystem path or two tests in the same file.

## Trace a Failure Before Learning the Mock API

Suppose a notification operation should propagate a delivery failure. A test replaces the delivery dependency with a function that rejects, calls the operation and awaits the rejection assertion. If the operation swallows the error, the test fails. If the test forgets to await the assertion, it can finish before observing the behavior.

```text
discover test → load environment/transform → execute and await
      → compare observed contract → clean up → report result
```

Assertions compare observations. Mocks provide controlled dependency behavior and record calls. Hooks establish and release test resources. Coverage records executed code; it does not establish that the assertions distinguish correct from incorrect behavior.

## Configure the Runtime You Actually Need

For a plain CommonJS Node example, install Jest and use an explicitly named CommonJS config. No TypeScript transformer is needed here:

```javascript
// jest.config.cjs
module.exports = {
  testEnvironment: "node",
  testMatch: ["**/*.test.cjs"],
  clearMocks: true,
  restoreMocks: true,
};
```

```bash
npm install --save-dev jest
npx jest --config jest.config.cjs
```

For TypeScript, choose a compatible transformer (for example Babel, SWC or ts-jest) and run a type checker as a separate required step. Babel's type stripping does not type-check. A DOM suite also needs the separately installed `jest-environment-jsdom`; jsdom is not a real browser and cannot establish layout, rendering performance or cross-browser correctness.

| Configuration role | Setting | Boundary |
| --------------------------- | --------------------- | ---------------------------------------------------------------- |
| Test discovery | `testMatch` | Ensure the intended files actually run |
| Runtime globals | `testEnvironment` | Node versus simulated DOM |
| Syntax conversion | `transform` | Match language/module modes and tool versions |
| Before test framework setup | `setupFiles` | Runs per test file, before assertion/hook APIs are installed |
| After framework setup | `setupFilesAfterEnv` | Register matchers and per-file hooks |
| Module paths | `moduleNameMapper` | Match the application's resolution without hiding broken imports |
| Coverage scope | `collectCoverageFrom` | Include important source files that tests never import |
| Worker capacity | `maxWorkers` | Fit runner memory, CPU and dependency capacity |

A `beforeAll` declared by a setup file runs for that test file; it is not once for the entire repository. Use `globalSetup`/`globalTeardown` for suite-level orchestration where appropriate, and design how test workers obtain their resources. `--runInBand` is a CLI scheduling option, not a substitute for independent tests.

## Control One Dependency and Check Its Observable Contract

Save these as separate files. Dependency injection keeps the example independent of CommonJS/ESM module mocking differences:

```javascript
// notification.cjs
function makeNotifier(deliver) {
  return async function notify(address, message) {
    if (!address || !message) throw new Error("address and message required");
    await deliver({ to: address, body: message });
  };
}
module.exports = { makeNotifier };
```

```javascript
// notification.test.cjs
const { makeNotifier } = require("./notification.cjs");

test("forwards the intended delivery and waits for completion", async () => {
  const deliver = jest.fn().mockResolvedValue(undefined);
  await makeNotifier(deliver)("reader@example.test", "Welcome");
  expect(deliver).toHaveBeenCalledTimes(1);
  expect(deliver).toHaveBeenCalledWith({ to: "reader@example.test", body: "Welcome" });
});

test("propagates delivery failure", async () => {
  const deliver = jest.fn().mockRejectedValue(new Error("delivery unavailable"));
  await expect(makeNotifier(deliver)("reader@example.test", "Welcome"))
    .rejects.toThrow("delivery unavailable");
});

test("rejects invalid input before calling the dependency", async () => {
  const deliver = jest.fn();
  await expect(makeNotifier(deliver)("", "Welcome")).rejects.toThrow("required");
  expect(deliver).not.toHaveBeenCalled();
});
```

This is a unit test of orchestration, not evidence that an email reached a recipient. HTTP contract tests should exercise serialization and errors; provider integration tests should establish the supported request/response contract. Avoid checking only that an array exists or looping over an empty response: assert fixtures, expected membership and tenant boundaries so a vacuous response fails.

## Choose What to Compare

| Assertion | Contract |
| --------------------------- | ----------------------------------------------------------------------------------------- |
| `toBe` | Primitive equality or object identity, using Object.is semantics |
| `toEqual` / `toStrictEqual` | Structural equality; strict equality also distinguishes more type/undefined/array details |
| `toMatchObject` | Deliberately selected object fields |
| `toBeCloseTo` | Floating-point comparison with chosen precision |
| `toThrow` | Wrap synchronous invocation: `expect(() => operation()).toThrow()` |
| `resolves` / `rejects` | Await or return the assertion Promise |
| Mock call matchers | Verify a collaborator contract when the interaction matters |

If a callback might never execute, use an awaited Promise or an appropriate `expect.assertions`/`expect.hasAssertions` check. Assertions are not useful merely because the code line ran.

## Clear, Reset and Restore Affect Different State

| Operation | What it changes |
| --------------------------------- | --------------------------------------------------------------------------------------------------------------------- |
| `mockClear` / `clearAllMocks` | Recorded calls, instances, contexts and results; implementations remain |
| `mockReset` / `resetAllMocks` | Clear history and reset mock implementations |
| `mockRestore` / `restoreAllMocks` | Restore originals for spies/replaced properties supported by the API; not arbitrary manually assigned `jest.fn` mocks |
| `jest.mocked(value)` | Supplies mock-aware TypeScript typing; does not create a runtime mock |

`jest.spyOn(object, "method")` calls the real implementation unless you override it. Restore the spy after use. Calling `jest.mock("./api")` does not mock the global `fetch`: use a deliberate module mock, a spy on the global, or an HTTP interception tool.

Mocks created per test reduce accidental implementation carryover. Clearing calls alone leaves previous return/rejection behavior in place. Module registry resets and mock restoration are also different operations; choose the one that matches the state that leaked.

## Module Mode Changes Mock Registration

CommonJS targets use `jest.mock`; transformer-assisted hoisting is not a property of ordinary JavaScript execution. Native ESM static imports are evaluated before the body, so the CommonJS hoisting recipe cannot be assumed to work. Follow the installed Jest version's ESM guide: configure ESM output, the required Node VM-module mode, import `jest` from `@jest/globals`, and register supported ESM mocks before dynamically importing the subject.

`jest.unstable_mockModule` is an explicitly unstable ESM factory API. Node/Jest versions also affect mixed-module support, so migrating a configuration requires running the real suite, not replacing import syntax alone. Avoid mocking a function inside the same module and expecting lexical internal references automatically to change.

## Move Time Without Sleeping

Use fake timers when elapsed time is part of the contract; do not fake every dependency by default:

```javascript
// clock.test.cjs
beforeEach(() => jest.useFakeTimers());
afterEach(() => {
  jest.clearAllTimers();
  jest.useRealTimers();
});

test("does not run before its scheduled deadline", async () => {
  const observe = jest.fn();
  setTimeout(() => Promise.resolve().then(observe), 100);
  await jest.advanceTimersByTimeAsync(99);
  expect(observe).not.toHaveBeenCalled();
  await jest.advanceTimersByTimeAsync(1);
  expect(observe).toHaveBeenCalledTimes(1);
});
```

The async timer API allows Promise callbacks to run while timers advance. Recursive timers can make `runAllTimers` exhaust its loop limit; advance a bounded interval or run pending timers according to the behavior being tested. A test with user-event or real network/database I/O may need a different timer arrangement. Clean up the operation itself, not just the clock.

## Snapshots and Coverage Answer Narrow Questions

A snapshot detects a difference in serialized output. It does not prove the new baseline is correct, visually usable or accessible. Keep snapshots focused, stabilize inputs and review diffs before updating. Use behavior assertions for the requirement; see [React Testing Library](50.1.2.03-react-testing-library.md) for a canonical component-testing example rather than duplicating the UI here.

Coverage reports executed statements, branches and functions. Jest supports Babel/Istanbul-style instrumentation and V8 coverage providers. Include unimported source files and verify source maps. Thresholds are a team policy, not proof of test quality: a test can execute every branch without asserting a meaningful result. Never present fabricated output percentages as measurements of an example that was not run.

## Real-World Decisions

For database tests, reuse a connection pool when appropriate but isolate *data* through separate schemas/databases or correctly scoped transactions. Every worker clearing the same shared database creates races; serial execution merely hides that design weakness. Close pools, servers and subprocesses in teardown, including partial setup failure paths.

For an HTTP test with Supertest, know whether it executes the real application middleware, authorization and persistence or mocked substitutes. Test unauthenticated access, another tenant's resource, invalid input, bounded pagination and safe response fields alongside the successful operation. A successful response status alone is weak evidence.

For React/network tests, use the canonical [component chapter](50.1.2.03-react-testing-library.md) and [mocking chapter](../04-mocking-and-patterns/50.1.4.01-mocking.md). Modern MSW uses `http`/`HttpResponse`, not the removed `rest`/`res`/`ctx` recipe. Make unexpected network requests fail and await visible outcomes.

## Mistakes That Make a Green Result Untrustworthy

- An unreturned Promise or swallowed callback error lets the test finish early.
- `jest.mocked` gives types to an unmocked real function.
- Mock assertions replace all meaningful domain behavior with a tautology.
- A shared database or global implementation leaks across tests or workers.
- A large snapshot is updated without reviewing why it changed.
- A coverage percentage is treated as an authorization, concurrency or usability check.

## Best Practices

Name the behavior and failure you expect the test to distinguish. Use fresh fixtures, await completion and release owned resources. Keep selected mocks at clear boundaries, then add integration and browser checks for the contracts those mocks remove. Measure discovery, transformation, execution and resource usage before tuning workers or changing runners.

## Summary

Jest runs a configured runtime and observes assertions; it does not make tests independent or meaningful by itself. Await async work, distinguish mock history from implementations, account for module mode, and isolate external state. Snapshots and coverage provide useful signals within those boundaries, while integration and browser tests establish contracts outside the unit test.

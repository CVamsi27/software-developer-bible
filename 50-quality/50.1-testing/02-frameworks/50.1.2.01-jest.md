# Jest

A notification operation should propagate a delivery failure — but if the test forgets to await the rejection assertion, it finishes before observing the behavior and passes while the bug ships. Jest provides the runtime; awaiting the contract is your job.

```text
discover test → load environment/transform → execute and await
      → compare observed contract → clean up → report result
```

## Definition

**Jest** discovers and runs tests, supplies **assertions** and **mocks**, and reports results and optional coverage. The **runner** decides when and where tests execute; a test environment supplies globals such as Node APIs or a simulated DOM; a transformer converts unsupported syntax into executable JavaScript.

> **Textbook Definition:** Jest is a JavaScript testing framework that coordinates test discovery and execution with assertions, test doubles and reporting; configured environments and transformations determine which code it can exercise.

## First Principles

A useful test must fail when an observable contract breaks, and its result must be independent of unrelated tests. Waiting for asynchronous work, controlling selected dependencies and cleaning up state make that result interpretable. Test-file isolation helps, but it cannot isolate a shared database, a remote service, a filesystem path or two tests in the same file.

## 1. Configure the Runtime You Actually Need

For a plain CommonJS Node example, install Jest and use an explicitly named CommonJS config. No TypeScript transformer is needed here:

```javascript
// jest.config.cjs
module.exports = {
  testEnvironment: "node",
  testMatch: ["**/*.test.cjs"],
  clearMocks: true,
  restoreMocks: true,
};
```

```bash
npm install --save-dev jest
npx jest --config jest.config.cjs
```

Each setting owns one boundary:

- **Discovery** (`testMatch`): ensure the intended files actually run.
- **Runtime globals** (`testEnvironment`): Node versus simulated DOM.
- **Syntax conversion** (`transform`): match language and module modes with tool versions.
- **Setup order** (`setupFiles` vs `setupFilesAfterEnv`): before versus after assertion and hook APIs are installed — a `beforeAll` in a setup file runs per test file, not once per repository.
- **Module paths** (`moduleNameMapper`): match application resolution without hiding broken imports.
- **Coverage scope** (`collectCoverageFrom`): include important source files tests never import.
- **Worker capacity** (`maxWorkers`): fit runner memory, CPU and dependency capacity.

For TypeScript, choose a compatible transformer (Babel, SWC or ts-jest) and run a type checker as a separate required step — Babel's type stripping does not type-check. A DOM suite needs the separately installed `jest-environment-jsdom`; jsdom is not a real browser and cannot establish layout, rendering or cross-browser correctness.

## 2. Control One Dependency and Check Its Observable Contract

Dependency injection keeps this example independent of CommonJS/ESM module-mocking differences. Save as separate files:

```javascript
// notification.cjs
function makeNotifier(deliver) {
  return async function notify(address, message) {
    if (!address || !message) throw new Error("address and message required");
    await deliver({ to: address, body: message });
  };
}
module.exports = { makeNotifier };
```

```javascript
// notification.test.cjs
const { makeNotifier } = require("./notification.cjs");

test("forwards the intended delivery and waits for completion", async () => {
  const deliver = jest.fn().mockResolvedValue(undefined);
  await makeNotifier(deliver)("reader@example.test", "Welcome");
  expect(deliver).toHaveBeenCalledTimes(1);
  expect(deliver).toHaveBeenCalledWith({ to: "reader@example.test", body: "Welcome" });
});

test("propagates delivery failure", async () => {
  const deliver = jest.fn().mockRejectedValue(new Error("delivery unavailable"));
  await expect(makeNotifier(deliver)("reader@example.test", "Welcome"))
    .rejects.toThrow("delivery unavailable");
});

test("rejects invalid input before calling the dependency", async () => {
  const deliver = jest.fn();
  await expect(makeNotifier(deliver)("", "Welcome")).rejects.toThrow("required");
  expect(deliver).not.toHaveBeenCalled();
});
```

This is a unit test of orchestration, not evidence that an email reached a recipient. Assert fixtures, expected membership and tenant boundaries so a vacuous response fails — never check only that an array exists or loop over an empty response.

## 3. Choose What to Compare

- **`toBe`**: primitive equality or object identity, using `Object.is` semantics.
- **`toEqual` / `toStrictEqual`**: structural equality; strict mode also distinguishes type, `undefined` and array details.
- **`toMatchObject`**: deliberately selected object fields.
- **`toBeCloseTo`**: floating-point comparison with chosen precision.
- **`toThrow`**: wrap synchronous invocation — `expect(() => operation()).toThrow()`.
- **`resolves` / `rejects`**: await or return the assertion Promise, or the test ends early.
- **Mock call matchers**: verify a collaborator contract when the interaction itself matters.

If a callback might never execute, use an awaited Promise or `expect.assertions` / `expect.hasAssertions`. Assertions are not useful merely because the code line ran.

## 4. Separate Mock History From Implementations

| Operation | What it changes |
| --------------------------------- | --------------------------------------------------------------------------------------------------------------------- |
| `mockClear` / `clearAllMocks` | Recorded calls, instances, contexts and results; implementations remain |
| `mockReset` / `resetAllMocks` | Clear history and reset mock implementations |
| `mockRestore` / `restoreAllMocks` | Restore originals for spies/replaced properties supported by the API; not arbitrary manually assigned `jest.fn` mocks |
| `jest.mocked(value)` | Supplies mock-aware TypeScript typing; does not create a runtime mock |

`jest.spyOn(object, "method")` calls the real implementation unless overridden — restore the spy after use. Calling `jest.mock("./api")` does not mock the global `fetch`: use a deliberate module mock, a spy on the global, or an HTTP interception tool. Create mocks per test: clearing calls alone leaves previous return and rejection behavior in place.

## 5. Mind the Module Mode

CommonJS targets use `jest.mock`; transformer-assisted hoisting is not a property of ordinary JavaScript execution. Native ESM static imports evaluate before the body, so the CommonJS hoisting recipe cannot be assumed to work. Follow the installed Jest version's ESM guide: configure ESM output, run with Node's VM-module mode, import `jest` from `@jest/globals`, and register supported ESM mocks before dynamically importing the subject. Jest's ESM support remains experimental and still documents `--experimental-vm-modules`.

On Node.js 24.9 and later, Jest also supports `require()` for synchronously evaluable ESM modules from CommonJS code. This does not remove the VM-module requirement for native ESM test execution, and a graph containing top-level `await` must still load with `import()`. `jest.unstable_mockModule` is explicitly unstable — migrating configuration requires running the real suite, not replacing import syntax alone.

## 6. Move Time, Snapshots and Coverage Within Their Boundaries

Use fake timers when elapsed time is part of the contract; do not fake every dependency by default:

```javascript
// clock.test.cjs
beforeEach(() => jest.useFakeTimers());
afterEach(() => {
  jest.clearAllTimers();
  jest.useRealTimers();
});

test("does not run before its scheduled deadline", async () => {
  const observe = jest.fn();
  setTimeout(() => Promise.resolve().then(observe), 100);
  await jest.advanceTimersByTimeAsync(99);
  expect(observe).not.toHaveBeenCalled();
  await jest.advanceTimersByTimeAsync(1);
  expect(observe).toHaveBeenCalledTimes(1);
});
```

The async timer API lets Promise callbacks run while timers advance. Recursive timers can exhaust `runAllTimers` loop limits — advance a bounded interval instead. Clean up the operation itself, not just the clock.

A **snapshot** detects a difference in serialized output; it does not prove the new baseline is correct, usable or accessible. Keep snapshots focused, stabilize inputs and review diffs before updating. **Coverage** reports executed statements, branches and functions — Jest supports Babel/Istanbul-style and V8 providers — but a test can execute every branch without asserting a meaningful result. Never present fabricated output percentages as measurements of an example that was not run.

## Real-World Use Cases

- **Database tests**: reuse a connection pool where appropriate but isolate *data* through separate schemas, databases or correctly scoped transactions. Every worker clearing the same shared database creates races; close pools, servers and subprocesses in teardown, including partial setup failures.
- **HTTP tests with Supertest**: know whether the test executes real middleware, authorization and persistence or mocked substitutes. Test unauthenticated access, another tenant's resource, invalid input, bounded pagination and safe response fields alongside success — status alone is weak evidence.
- **React and network tests**: use the canonical [component chapter](50.1.2.03-react-testing-library.md) and [mocking chapter](../04-mocking-and-patterns/50.1.4.01-mocking.md). Modern MSW uses `http`/`HttpResponse`, not the removed `rest`/`res`/`ctx` recipe; make unexpected network requests fail and await visible outcomes.

## Summary

Jest runs a configured runtime and observes assertions; it does not make tests independent or meaningful by itself. Await async work, separate mock history from implementations, account for module mode, and isolate external state. Snapshots and coverage provide useful signals within those boundaries, while database, HTTP and browser tests establish the contracts a unit test cannot.

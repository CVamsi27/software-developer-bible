# Vitest

A read operation receives a transient 503, waits 100 milliseconds and retries once. The test supplies a controlled reader, advances the test clock, and observes both the result and the call count — Vite transforms the TypeScript, Vitest provides the clock and assertions, and a separate type checker validates static relationships.

```text
TypeScript + Vite config → transform/module resolution
                                     ↓
                        selected worker and environment
                                     ↓
                    controlled dependency → awaited result
```

## Definition

**Vitest** is a test runner that uses Vite's transformation and module tooling with a familiar assertion and mocking API. It runs Node tests, simulated-DOM component tests and configured Browser Mode tests. This chapter targets **Vitest 5**. Check the installed package's engine and peer ranges: version 5.0.5 accepts Node.js `^22.12.0 || ^24.0.0 || >=26.0.0` and Vite `^6.4.0 || ^7.0.0 || ^8.0.0`. A minimum version does not mean every newer Node major is supported; Node 23 and 25 are outside that range. See the [versioned package manifest](https://github.com/vitest-dev/vitest/blob/v5.0.5/packages/vitest/package.json).

> **Textbook Definition:** Vitest is a JavaScript and TypeScript test framework built around Vite's module transformation pipeline, with configurable execution environments, assertions, mocking and coverage integration.

## First Principles

An application and its tests need compatible source transformation and module resolution. Reusing that toolchain reduces configuration divergence, but tests still execute in a selected runtime with controlled dependencies. Similar API names do not guarantee the same module mocks, isolation, snapshots or timer behavior as another runner.

## 1. Configure a Node Suite First

```typescript
// vitest.config.ts
import { defineConfig } from "vitest/config";

export default defineConfig({
  test: {
    environment: "node",
    isolate: true,
    pool: "forks",
    clearMocks: true,
  },
});
```

```bash
npm install --save-dev vitest typescript
npx vitest run
npx tsc --noEmit
```

The checker command requires an appropriate tsconfig; runtime success does not substitute for it. A Vite app can reuse compatible plugins and aliases, but a separate `vitest.config` is not automatically a complete merge of every application setting — compose shared configuration deliberately and verify resolution. Import APIs explicitly from `vitest` unless globals are an intentional convention; enabling Vitest globals does not create Jest's `jest` object. For React component tests, install and configure the React plugin, jsdom or another supported environment, Testing Library and matchers.

## 2. Keep Retry Policy Small and Observable

This example retries one **read** for exactly one 503. It does not establish a safe retry policy for payments or another non-idempotent write.

```typescript
// retry.ts
export async function readWithRetry<T>(read: () => Promise<T>): Promise<T> {
  try {
    return await read();
  } catch (error) {
    if (!(error instanceof Error) || !("status" in error) || error.status !== 503) {
      throw error;
    }
    await new Promise<void>((resolve) => setTimeout(resolve, 100));
    return read();
  }
}
```

```typescript
// retry.test.ts
import { afterEach, expect, it, vi } from "vitest";
import { readWithRetry } from "./retry";

afterEach(() => {
  vi.clearAllTimers();
  vi.useRealTimers();
});

it("waits before retrying one transient failure", async () => {
  vi.useFakeTimers();
  const unavailable = Object.assign(new Error("unavailable"), { status: 503 });
  const read = vi.fn<() => Promise<string>>()
    .mockRejectedValueOnce(unavailable)
    .mockResolvedValueOnce("ready");
  const result = readWithRetry(read);
  await vi.advanceTimersByTimeAsync(99);
  expect(read).toHaveBeenCalledTimes(1);
  await vi.advanceTimersByTimeAsync(1);
  await expect(result).resolves.toBe("ready");
  expect(read).toHaveBeenCalledTimes(2);
});

it("does not retry a permanent failure", async () => {
  const denied = Object.assign(new Error("denied"), { status: 403 });
  const read = vi.fn<() => Promise<string>>().mockRejectedValue(denied);
  await expect(readWithRetry(read)).rejects.toBe(denied);
  expect(read).toHaveBeenCalledTimes(1);
});
```

A production policy may additionally need cancellation, a deadline, Retry-After handling, backoff and jitter — keep those requirements explicit and test the boundary cases. Fake time observes scheduling; it does not model a real provider or operating-system clock. Do not infer startup time, memory per worker or a fixed Jest speedup from this model; benchmark the same suite on the actual CI runner.

## 3. Register Module Mocks Before Imports Execute

`vi.mock` is transformed and hoisted for supported module loading; its factory cannot freely capture variables initialized later in the file. Use supported `vi.hoisted` setup when necessary, or inject the dependency as above. `vi.doMock` affects subsequent imports rather than previously loaded references, and imports through CommonJS `require` are not covered by the same mocking recipe.

`vi.mocked(value)` is a typing helper, not a runtime mock. `vi.spyOn` normally calls the original method until configured otherwise. Clear, reset, restore and module-cache reset affect different state — read the installed version's migration guide, especially reset and restore changes. Vitest 5 clears mock call history by default while preserving implementations. Avoid sharing mocks between `test.concurrent` cases: automatic clearing can erase history another concurrent case is still observing.

## 4. Choose the Runtime Before Interpreting a Result

| Runtime | What it can establish | What it does not establish |
| ----------------- | ---------------------------------------------------------------- | --------------------------------------------------------------------- |
| Node | Server/library logic using Node APIs | Browser layout, focus or actual browser networking |
| jsdom / happy-dom | DOM-driven component behavior within an emulation | Real rendering, complete browser APIs or cross-browser behavior |
| Browser Mode | Tests in a configured real browser provider | A full production server/navigation/deployment contract automatically |
| Playwright E2E | User journeys against a running application in selected browsers | Every integration, device or external delivery guarantee |

Vitest **does** support real browsers through Browser Mode, stable since Vitest 4 — but it needs a separately installed provider such as `@vitest/browser-playwright`, `@vitest/browser-webdriverio` or `@vitest/browser-preview`. Use Playwright E2E when the contract spans server routing, authentication and navigation. For native ESM paths, use `import.meta.url` and URL utilities instead of assuming `__dirname` exists.

## 5. Mock HTTP at the Boundary You Need to Exercise

Modern MSW uses `http` and `HttpResponse`; its Node server intercepts supported client requests without running a real remote server. This preserves more of the client's HTTP construction than replacing the entire API module — but only assertions on headers, body and status expose those errors. A handler that always returns success cannot catch a missing required header.

```typescript
// test setup: fail loudly on unhandled requests, reset overrides per test
server.listen({ onUnhandledRequest: "error" });
```

Reset per-test handler overrides and close interception afterward. Use concrete absolute URLs when the client or runtime requires them, and validate intercepted requests. See [the mocking chapter](../04-mocking-and-patterns/50.1.4.01-mocking.md) for the canonical HTTP example.

## 6. Share Policy, Workers and Coverage Deliberately

A shared config can establish environment, transforms, reporters and coverage policy across a monorepo — but resolve setup paths relative to the intended package location, select the supported project configuration for the installed major, and isolate databases, ports, temporary directories and secrets per worker. A shared config does not provide resource isolation.

**Workers**: forks use processes, threads use worker threads within a process. Threads are not forbidden from spawning subprocesses, and forks do not make leaked child processes disappear. Always await and terminate owned processes, and benchmark supported worker limits under CI memory pressure.

**Coverage**: install a matching `@vitest/coverage-v8` or `@vitest/coverage-istanbul` package and set `coverage.include` to capture relevant unimported source files. Both providers report branch coverage.

```typescript
// Example coverage block inside test: { ... }
coverage: {
  provider: "v8",
  include: ["src/**/*.ts"],
  reporter: ["text", "html", "lcov"],
  thresholds: { branches: 80, functions: 80, lines: 80, statements: 80 },
}
```

The threshold is illustrative policy, not proof of quality. Sharding (`vitest run --shard=1/4`) divides files across separately orchestrated runs — run every shard and combine their evidence. Protect test artifacts if they include sensitive fixtures or request data.

## Summary

Vitest reuses Vite tooling while supplying test scheduling, assertions and controlled dependencies. The environment defines what the result means; type checking, external-resource isolation and end-to-end coverage remain separate responsibilities. Register mocks before imports execute, choose workers and coverage deliberately, and treat speed and coverage claims as measurements of the configured suite — not properties of the runner.

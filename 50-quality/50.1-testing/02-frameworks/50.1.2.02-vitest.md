# Vitest

## Definition

**Vitest** is a test runner that uses Vite's transformation and module tooling with a familiar assertion/mocking API. It can run Node tests, simulated-DOM component tests and configured Browser Mode tests. Choosing an environment changes what the result can establish.

## First Principles

An application and its tests need compatible source transformation and module resolution. Reusing that toolchain reduces configuration divergence, but tests still execute in a selected runtime with controlled dependencies. Similar API names do not guarantee the same module mocks, isolation, snapshots or timer behavior as another runner.

## Trace a Retried Read Through the Runner

A read operation receives a transient 503, waits 100 milliseconds and retries once. The test supplies a controlled reader, advances the test clock and observes both the result and number of calls. Vite converts the TypeScript into executable code; Vitest provides the controlled clock and assertions. A separate type checker validates the source's static relationships.

```text
TypeScript + Vite config → transform/module resolution
                                     ↓
                        selected worker and environment
                                     ↓
                    controlled dependency → awaited result
```

Do not infer startup time, memory per worker or a fixed Jest speedup from this model. Benchmark the same suite and correctness requirements on the actual CI runner.

## Configure a Node Suite First

```typescript
// vitest.config.ts
import { defineConfig } from "vitest/config";

export default defineConfig({
  test: {
    environment: "node",
    isolate: true,
    pool: "forks",
    clearMocks: true,
  },
});
```

```bash
npm install --save-dev vitest typescript
npx vitest run
npx tsc --noEmit
```

The checker command requires an appropriate tsconfig; runtime success does not substitute for it. A Vite app can reuse compatible plugins/aliases, but a separate `vitest.config` is not automatically a complete merge of every application setting. Compose shared configuration deliberately and verify resolution.

For React component tests, install/configure the React plugin, jsdom or another supported environment, Testing Library and matchers. For native ESM paths, use `import.meta.url`/URL utilities where needed instead of assuming `__dirname` exists. Globals are optional; explicit imports make the runner boundary visible.

## Code Examples

### Keep Retry Policy Small and Observable

This example retries one **read** for exactly one 503. It does not establish a safe retry policy for payments or another non-idempotent write.

```typescript
// retry.ts
export async function readWithRetry<T>(read: () => Promise<T>): Promise<T> {
  try {
    return await read();
  } catch (error) {
    if (!(error instanceof Error) || !("status" in error) || error.status !== 503) {
      throw error;
    }
    await new Promise<void>((resolve) => setTimeout(resolve, 100));
    return read();
  }
}
```

```typescript
// retry.test.ts
import { afterEach, expect, it, vi } from "vitest";
import { readWithRetry } from "./retry";

afterEach(() => {
  vi.clearAllTimers();
  vi.useRealTimers();
});

it("waits before retrying one transient failure", async () => {
  vi.useFakeTimers();
  const unavailable = Object.assign(new Error("unavailable"), { status: 503 });
  const read = vi.fn<() => Promise<string>>()
    .mockRejectedValueOnce(unavailable)
    .mockResolvedValueOnce("ready");
  const result = readWithRetry(read);
  await vi.advanceTimersByTimeAsync(99);
  expect(read).toHaveBeenCalledTimes(1);
  await vi.advanceTimersByTimeAsync(1);
  await expect(result).resolves.toBe("ready");
  expect(read).toHaveBeenCalledTimes(2);
});

it("does not retry a permanent failure", async () => {
  const denied = Object.assign(new Error("denied"), { status: 403 });
  const read = vi.fn<() => Promise<string>>().mockRejectedValue(denied);
  await expect(readWithRetry(read)).rejects.toBe(denied);
  expect(read).toHaveBeenCalledTimes(1);
});
```

A production policy may additionally need cancellation, a deadline, Retry-After handling, backoff and jitter. Keep those requirements explicit and test the boundary cases. Fake time helps observe scheduling; it does not model a real provider or operating-system clock.

### Register Module Mocks Before Imports Execute

`vi.mock` is transformed/hoisted for supported module loading; its factory cannot freely capture variables initialized later in the file. Use supported `vi.hoisted` setup when necessary, or inject a dependency as above. `vi.doMock` affects subsequent imports rather than previously loaded references. Imports through CommonJS `require` are not covered by the same mocking recipe.

`vi.mocked(value)` is a typing helper, not a runtime mock. `vi.spyOn` normally calls the original method until configured otherwise. Clear, reset, restore and module-cache reset affect different state; read the installed version's migration guide, especially reset/restore changes. Restore spies and clocks after the tests that own them.

## Choose the Runtime Before Interpreting a Result

| Runtime | What it can establish | What it does not establish |
| ----------------- | ---------------------------------------------------------------- | --------------------------------------------------------------------- |
| Node | Server/library logic using Node APIs | Browser layout, focus or actual browser networking |
| jsdom / happy-dom | DOM-driven component behavior within an emulation | Real rendering, complete browser APIs or cross-browser behavior |
| Browser Mode | Tests in a configured real browser provider | A full production server/navigation/deployment contract automatically |
| Playwright E2E | User journeys against a running application in selected browsers | Every integration, device or external delivery guarantee |

Vitest **does** support real browsers through Browser Mode; it is incorrect to say it has no browser engine option. Use Playwright E2E when the contract spans server routing, authentication and navigation. Next.js's official guide currently recommends E2E for async Server Components; choosing happy-dom or mocking cache helpers does not supply the framework's server rendering semantics.

## Mock HTTP at the Boundary You Need to Exercise

Modern MSW uses `http` and `HttpResponse`; its Node server intercepts supported client requests without running a real remote server. This preserves more of the client's HTTP construction than replacing the entire API module, but only assertions on headers/body/status expose those errors. A handler that always returns success cannot catch a missing required header.

Configure `server.listen({ onUnhandledRequest: "error" })`, reset per-test handler overrides and close interception afterward. Use concrete absolute URLs when the client/runtime requires them, and validate intercepted requests. See [the mocking chapter](../04-mocking-and-patterns/50.1.4.01-mocking.md) for the canonical HTTP example.

## Real-World Decisions

### Share Policy Across a Monorepo Without Sharing Test Data

A shared config can establish environment, transforms, reporters and coverage policy. Resolve setup paths relative to the intended package/config location. Select the supported project configuration for the installed Vitest major, and isolate databases, ports, temporary directories and secrets per worker. A shared config does not provide that resource isolation.

### Choose Workers for Compatibility and Capacity

Forks use processes; threads use worker threads within a process. Threads are not forbidden from spawning subprocesses, and forks do not make leaked child processes disappear. Native module/global process behavior can make pool selection important. Always await and terminate owned processes, and benchmark supported worker limits under CI memory pressure.

### Collect Coverage Deliberately

Install a matching `@vitest/coverage-v8` or `@vitest/coverage-istanbul` package and set `coverage.include` to capture relevant unimported source files. Both providers report branch coverage. Since Vitest 3.2, its V8 provider uses AST-based remapping intended to align reports with Istanbul; source-map/toolchain issues and runtime support still matter. V8 is not universally a fixed multiple faster, and it requires a compatible V8 profiling runtime.

```typescript
// Example coverage block inside test: { ... }
coverage: {
  provider: "v8",
  include: ["src/**/*.ts"],
  reporter: ["text", "html", "lcov"],
  thresholds: { branches: 80, functions: 80, lines: 80, statements: 80 },
}
```

The threshold is illustrative policy. Sharding (`vitest run --shard=1/4`) divides files across separately orchestrated runs; run every shard and combine their evidence. A green single shard is not a green full suite. Protect test artifacts if they include sensitive fixtures or request data.

## Common Mistakes

- Renaming `jest` to `vi` without verifying mock/module/timer semantics.
- Believing `globals: true` creates a `jest` object; it supplies supported Vitest globals.
- Assuming `vi.mocked` replaces a real dependency.
- Running TypeScript without a required type-check step.
- Using a DOM emulator to claim full async Server Component or browser correctness.
- Measuring a runner after reducing meaningful coverage and calling the change a speedup.

## Best Practices

Start from one observable contract, then add the runtime and controlled dependency it requires. Prefer explicit imports and owned fixtures. Await effects, clean up clocks/processes and isolate external data. Verify the installed major's configuration and migration semantics, and measure the actual suite before claiming a performance improvement.

## Summary

Vitest reuses Vite tooling while supplying test scheduling, assertions and controlled dependencies. The environment defines what the result means; type checking, external-resource isolation and E2E coverage remain separate responsibilities. Verify mock and timer behavior during migration, and treat speed and coverage claims as measurements of the configured suite.

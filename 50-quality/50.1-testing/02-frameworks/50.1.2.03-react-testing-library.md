# React Testing Library

A reader types a name and presses Save. The component validates input, disables the form while awaiting the save dependency, and shows either confirmation or an error — and the test locates the same labeled field and named button the user would, supplies a controlled dependency, and awaits the visible result.

```text
render component → query labelled field → type/click
       → React update and async dependency → observe status/error
```

## Definition

**React Testing Library** renders React components into a DOM and supplies **queries**, cleanup and helpers for observing their behavior. A **runner** such as Jest or Vitest schedules the test and supplies assertions and mocks; `user-event` models interactions and `jest-dom` supplies DOM-specific matchers.

> **Textbook Definition:** React Testing Library is a set of utilities for rendering React components and querying their DOM output through user-observable semantics; it requires a separate runner and assertion library.

## First Principles

Users act on an interface, not on a component's private state. A test that selects a named control and observes the resulting interface survives internal refactoring while still failing when the behavior breaks. The modeled DOM is only part of the experience: layout, browser quirks and assistive technology need additional checks.

## How It Works

### 1. Pick the Query for the Observation

| Query | No matches | Multiple matches | Use |
| --------------- | -------------------------------- | --------------------- | ------------------------------------------------------------- |
| `getBy...` | Throws | Throws | An element should exist now |
| `queryBy...` | Returns null | Throws | Assert absence now |
| `findBy...` | Retries, then rejects | Retries, then rejects | Await one element appearing |
| `getAllBy...` | Throws | Returns array | Assert a current nonempty set |
| `queryAllBy...` | Empty array | Returns array | Assert a possibly empty set |
| `findAllBy...` | Retries until a match or timeout | Returns array | Await a nonempty set, then assert its expected contents/count |

Prefer role plus accessible name for controls, and labels for fields. Password inputs have no implicit textbox role, so a label query is appropriate. Use `within(region)` to disambiguate repeated controls, not an arbitrary `.first` selection. Role and name queries encourage useful semantics but do **not** prove complete accessibility — and never add misleading ARIA just to satisfy a test. Native HTML elements generally express their semantics more reliably than decorative roles.

### 2. Render, Act and Observe One Form

The example uses Vitest with a jsdom environment and automatic JSX transform. It deliberately implements custom validation with `noValidate`; otherwise browser-native validation can prevent `onSubmit` from reaching the custom error path. The server must validate and authorize independently.

```tsx
// NameForm.tsx
import { useId, useState, type FormEvent } from "react";

type Props = { save: (name: string) => Promise<void> };
export function NameForm({ save }: Props) {
  const id = useId();
  const [name, setName] = useState("");
  const [pending, setPending] = useState(false);
  const [error, setError] = useState("");
  const [saved, setSaved] = useState(false);

  async function submit(event: FormEvent<HTMLFormElement>) {
    event.preventDefault();
    if (pending) return;
    setError("");
    setSaved(false);
    const trimmed = name.trim();
    if (!trimmed) {
      setError("Name is required");
      return;
    }
    setPending(true);
    try {
      await save(trimmed);
      setSaved(true);
    } catch {
      setError("Could not save name");
    } finally {
      setPending(false);
    }
  }

  return (
    <form aria-label="Display name" noValidate onSubmit={submit}>
      <label htmlFor={id}>Name</label>
      <input id={id} value={name} disabled={pending}
        aria-invalid={error === "Name is required"}
        aria-describedby={error ? `${id}-error` : undefined}
        onChange={(event) => { setName(event.target.value); setSaved(false); }} />
      <button type="submit" disabled={pending}>{pending ? "Saving" : "Save"}</button>
      {error && <p id={`${id}-error`} role="alert">{error}</p>}
      {saved && <p role="status">Name saved</p>}
    </form>
  );
}
```

```tsx
// NameForm.test.tsx
import { afterEach, expect, it, vi } from "vitest";
import { act, cleanup, render, screen, within } from "@testing-library/react";
import userEvent from "@testing-library/user-event";
import "@testing-library/jest-dom/vitest";
import { NameForm } from "./NameForm";

afterEach(cleanup);

it("blocks empty input before invoking save", async () => {
  const save = vi.fn<() => Promise<void>>();
  const user = userEvent.setup();
  render(<NameForm save={save} />);
  await user.click(screen.getByRole("button", { name: "Save" }));
  expect(await screen.findByRole("alert")).toHaveTextContent("Name is required");
  expect(save).not.toHaveBeenCalled();
});

it("shows confirmation after the intended name is saved", async () => {
  const save = vi.fn<(name: string) => Promise<void>>().mockResolvedValue(undefined);
  const user = userEvent.setup();
  render(<NameForm save={save} />);
  const form = within(screen.getByRole("form", { name: "Display name" }));
  await user.type(form.getByLabelText("Name"), "Ada");
  await user.click(form.getByRole("button", { name: "Save" }));
  expect(await screen.findByRole("status")).toHaveTextContent("Name saved");
  expect(save).toHaveBeenCalledTimes(1);
  expect(save).toHaveBeenCalledWith("Ada");
  expect(screen.queryByRole("alert")).not.toBeInTheDocument();
});

it("disables another submission while saving is unresolved", async () => {
  let complete!: () => void;
  const save = vi.fn<(name: string) => Promise<void>>()
    .mockImplementation(() => new Promise<void>((resolve) => { complete = resolve; }));
  const user = userEvent.setup();
  render(<NameForm save={save} />);
  await user.type(screen.getByLabelText("Name"), "Ada");
  await user.click(screen.getByRole("button", { name: "Save" }));
  const saving = screen.getByRole("button", { name: "Saving" });
  expect(saving).toBeDisabled();
  await user.click(saving);
  expect(save).toHaveBeenCalledTimes(1);
  // The test settles a dependency outside a user interaction.
  await act(async () => { complete(); });
  expect(await screen.findByRole("status")).toHaveTextContent("Name saved");
});

it("shows a failure without a false success confirmation", async () => {
  const save = vi.fn<(name: string) => Promise<void>>()
    .mockRejectedValue(new Error("unavailable"));
  const user = userEvent.setup();
  render(<NameForm save={save} />);
  await user.type(screen.getByLabelText("Name"), "Ada");
  await user.click(screen.getByRole("button", { name: "Save" }));
  expect(await screen.findByRole("alert")).toHaveTextContent("Could not save name");
  expect(screen.queryByRole("status")).not.toBeInTheDocument();
  expect(screen.getByRole("button", { name: "Save" })).toBeEnabled();
});
```

The unresolved dependency makes the pending state observable; an immediately resolved mock could skip past it. The error test asserts both the failure and the absence of false confirmation. No real personal data or credentials are needed. This is a component contract — it cannot prove a server authorized the change, persisted it or prevented another tenant from accessing it.

### 3. Await the Effect Without Repeating the Action

`findBy` combines a query with waiting. Use `waitFor` for an assertion that is not itself an element query, such as a collaborator eventually being called. Its callback retries when it **throws**; returning false or using an empty callback does not wait for the desired behavior. Keep actions outside `waitFor` — its callback may execute multiple times, so clicking or sending requests inside it can duplicate the operation.

For removal, use an absence query inside a throwing assertion, or `waitForElementToBeRemoved` when the element exists before waiting. `getByRole(...).not.toBeInTheDocument()` throws when the absent element is correctly gone; use `queryByRole` instead. Testing Library helpers handle `act` for their supported operations, but direct hook state updates, manual timer advancement or settling an externally controlled dependency may require awaited `act`. Treat warnings as evidence of unobserved work.

### 4. Model Interaction at the Needed Fidelity

Create `userEvent.setup()` per test and await its interactions. It models multiple events plus focus, selection and interactability checks — a simulation, not a guarantee of actual browser behavior. `fireEvent` remains useful for an unsupported interaction or a deliberately specific low-level event; calling it is not inherently wrong.

When using fake timers, configure user-event's supported `advanceTimers` integration rather than disabling delays to make the test pass. Test keyboard paths such as Tab and Enter for controls where they matter, then verify actual focus and layout behavior in a browser. Emulated visibility and focus assertions do not establish contrast, screen-reader announcements or viewport geometry.

### 5. Cover Providers, Hooks and Network State

A custom render wrapper can install required router, query or context providers — but give each test a fresh mutable provider and cache; sharing one creates order dependencies. `rerender` updates props on the existing tree; `unmount` verifies cleanup. Never use a context implementation copied into the test instead of the application's actual provider.

Use `renderHook` when a reusable hook itself has a meaningful public contract; direct updates need `act`. For a hook used by one component, exercising the component often supplies better evidence. For data-fetching components, check loading, success, error, changed inputs and unmount cleanup: an old request completing after a new one must not overwrite the new result. Mocking every response as immediate success misses these races — HTTP interception and fixtures belong in [the canonical mocking chapter](../04-mocking-and-patterns/50.1.4.01-mocking.md), with modern MSW handlers and unexpected requests failing.

Form-library tests should establish the actual rules: matching passwords if confirmation is required, real label text, checkbox state and the submit callback's full signature. Never treat a successful client validation test as server-side authorization evidence.

### 6. Render the Smallest Boundary That Contains the Behavior

A Button test need not start the entire application; a checkout interaction may need its real provider and several components. A simulated-router component flow does not prove production redirects, payments or persistence — put those contracts into integration and E2E tests, and use supported payment sandbox values rather than actual card or customer data.

## Summary

RTL observes React through the rendered DOM; the runner, interaction library and matchers supply complementary roles. Query the intended user-facing boundary, await its real consequence without repeating the action, and isolate dependencies deliberately. These tests encourage accessible semantics but need integration, browser and manual checks for every contract beyond the modeled DOM.

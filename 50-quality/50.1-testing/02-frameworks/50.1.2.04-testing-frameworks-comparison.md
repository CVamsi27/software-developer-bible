# Testing Frameworks Comparison

Two callers attempt to reserve the same appointment slot. A unit test checks how the service handles an explicit conflict from its persistence dependency; only a database integration test with overlapping writes proves that exactly one succeeds. No framework name tells you which of those ran.

```text
browser interaction → API authorization → transaction/constraint
        UI outcome          HTTP contract         durable invariant
```

## Definition

Testing tools differ in the **runtime** they execute and the **boundary** they observe. **Runners** schedule and report tests; **component utilities** render and query an interface; **Hypertext Transfer Protocol (HTTP) clients** exercise an Application Programming Interface (API); **browser automation** drives a real browser.

> **Textbook Definition:** A testing toolchain combines execution, interaction, and observation facilities. Its verification boundary is determined by the actual runtime and collaborators exercised, rather than by the name of the chosen framework.

## First Principles

A broken contract is detectable only if the test reaches it and asserts the relevant outcome. Replacing a dependency removes its behavior from the test. More realistic boundaries reveal more interactions but demand more setup, isolation, and failure diagnosis. Choose a portfolio of checks from those contracts, then measure cost — no fixed test-count percentage or speed ratio follows from tool names.

## 1. Compare Responsibilities Before Features

| Tool | Primary responsibility | Important limit |
| --------------------- | -------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| Jest | Runner, assertions, and mocks with configured transforms and environments | Native ECMAScript module (ESM) and transform behavior depend on version and configuration |
| Vitest 5 | Runner using Vite tooling, with configurable environments and Browser Mode | Check the installed engine and peer ranges in the Vitest chapter; familiar Jest APIs still differ in mocking, reset, and execution semantics |
| React Testing Library | Render and query React behavior through the selected Document Object Model (DOM) | Needs a runner; DOM emulation is not complete browser and accessibility verification |
| Supertest | Make requests against an HTTP server and application | Real persistence and production middleware must be supplied deliberately |
| Playwright Test | Run browser-driven tests with fixtures, assertions, and diagnostics | Browser isolation does not isolate shared backend data or verify every device and provider |
| Testcontainers | Provision real dependency containers for integration tests | Requires supported container runtime, readiness, and data and resource cleanup |

The canonical executable examples live in [Jest](50.1.2.01-jest.md), [Vitest](50.1.2.02-vitest.md), and [React Testing Library](50.1.2.03-react-testing-library.md), while [Integration](../03-test-levels/50.1.3.02-integration-testing.md) and [End-to-End (E2E)](../03-test-levels/50.1.3.03-e2e-testing.md) own the larger application boundaries.

A sequential "book twice" test exercises an existing-conflict path without establishing race safety, and a browser toast does not prove durable persistence.

## 2. Decide Whether a Runner Migration Is Worth Its Cost

| Decision | Evidence to collect |
| ------------------------- | -------------------------------------------------------------------------------------------------------------------------- |
| Toolchain alignment | Actual transforms, aliases, Cascading Style Sheets (CSS), assets, decorators, and module modes |
| Correctness compatibility | Mock factories, hoisting, spies, reset, restore, timers, snapshots, and environment behavior |
| Suite cost | Cold Continuous Integration (CI) start, warm watch feedback, peak memory, worker scaling, and report and coverage overhead |
| Ecosystem requirements | Framework adapters, supported versions, custom reporters, and integration tooling |
| Migration value | Maintenance pain removed versus conversion and revalidation cost |

Vitest is a useful candidate when Vite tooling aligns with the application; an existing stable Jest suite may have no economic reason to migrate. Neither "always faster" nor "zero configuration" establishes the decision. Runtime transformation is separate from TypeScript checking in both toolchains.

## 3. Allocate Tests by Risk, Not a Fixed Pyramid Ratio

Prefer fast focused checks for local edge cases, real dependency tests for important integration invariants, and browser journeys for behavior that needs the whole interface. The testing pyramid is a reasoning aid rather than an `80/15/5` quota or a guarantee that units cost 1,000 times less.

A thin unit suite may suit an application whose primary risk is integration, whereas a giant E2E suite can still omit critical concurrency and authorization boundaries. Coverage must describe both what executed and what was asserted.

## 4. Run TypeScript, React and Sensitive Domains Deliberately

For a TypeScript monorepo, require type checks independently, scope shared config paths deliberately, and keep each worker's backend fixtures isolated. A Nest test application must install the same relevant pipes, guards, and interceptors as production; `app.init()` alone does not copy bootstrap configuration, and a placeholder valid token must not skip the authorization contract under test.

For a React or Next.js application, distinguish synchronous component tests from async Server Component journeys in the actual framework runtime. Playwright supplies Chromium, Firefox, and WebKit test engines — WebKit is not the branded Safari application. For sensitive domains, use synthetic tenant and customer fixtures; control artifact access and retention, and avoid indiscriminate request-body logging.

## Summary

Choose tools by the behavior they execute and observe: runners control tests, component utilities observe DOM behavior, HTTP tests exercise the application contract, and browser journeys verify the interface in a real engine. Combine those boundaries for concurrency, authorization, and user experience. Validate migrations and performance claims with the actual suite, never with tool names.

# Testing Frameworks Comparison
---

## Definition

Testing tools differ in the runtime they execute and the boundary they observe. **Runners** schedule and report tests; **component utilities** render/query an interface; **HTTP clients** exercise an API; **browser automation** drives a real browser. A framework name alone does not specify whether the database, authorization or external services were real or mocked.

> **Textbook Definition:** A testing toolchain combines execution, interaction and observation facilities. Its verification boundary is determined by the actual runtime and collaborators exercised, rather than by the name of the chosen framework.

## First Principles

A broken contract is detectable only if the test reaches it and asserts the relevant outcome. Replacing a dependency removes its behavior from the test. More realistic boundaries can reveal more interactions but also require more setup, isolation and failure diagnosis. Choose a portfolio of checks from those contracts, then measure cost; no fixed test-count percentage or speed ratio follows from the tool names.

## Trace One Booking Failure Across Test Boundaries

Suppose two callers attempt to reserve the same appointment slot:

1. A unit test can check how the service handles an explicit conflict returned by its persistence dependency.
2. A database integration test must issue overlapping writes against the actual constraint/transaction design and prove only one succeeds.
3. An API test can verify authentication, tenant scope, validation and safe conflict responses through the real application middleware.
4. A browser test can verify that the user sees a useful conflict and retains a recoverable form.

```text
browser interaction → API authorization → transaction/constraint
        UI outcome          HTTP contract         durable invariant
```

A sequential “book twice” test exercises an existing-conflict path; it does not establish race safety. A browser toast does not prove durable persistence. Keep each test's claim within the boundary it exercises.

## Compare Responsibilities Before Features

| Tool | Primary responsibility | Important limit |
| --------------------- | -------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------- |
| Jest | Runner/assertions/mocks with configured transforms and environments | Native ESM and transform behavior depend on version/configuration |
| Vitest 5 | Runner using Vite tooling, with configurable environments and Browser Mode | Node.js 22.12+ and Vite 6.4+; familiar Jest APIs still differ in mocking, reset and execution semantics |
| React Testing Library | Render/query React behavior through the selected DOM | Needs a runner; DOM emulation is not complete browser/accessibility verification |
| Supertest | Make requests against an HTTP server/application | Real persistence and production middleware must be supplied deliberately |
| Playwright Test | Run browser-driven tests with fixtures, assertions and diagnostics | Browser isolation does not isolate shared backend data or verify every device/provider |
| Testcontainers | Provision real dependency containers for integration tests | Requires supported container runtime, readiness and data/resource cleanup |

The canonical executable examples live in [Jest](50.1.2.01-jest.md), [Vitest](50.1.2.02-vitest.md) and [React Testing Library](50.1.2.03-react-testing-library.md). [Integration](../03-test-levels/50.1.3.02-integration-testing.md) and [E2E](../03-test-levels/50.1.3.03-e2e-testing.md) own the larger application boundaries.

## Decide Whether a Runner Migration Is Worth Its Cost

| Decision | Evidence to collect |
| ------------------------- | -------------------------------------------------------------------------------------------- |
| Toolchain alignment | Actual transforms, aliases, CSS/assets, decorators and module modes |
| Correctness compatibility | Mock factories, hoisting, spies/reset/restore, timers, snapshots and environment behavior |
| Suite cost | Cold CI start, warm watch feedback, peak memory, worker scaling and report/coverage overhead |
| Ecosystem requirements | Framework adapters, supported versions, custom reporters and integration tooling |
| Migration value | Maintenance pain removed versus conversion/revalidation cost |

Vitest is a useful candidate when Vite tooling aligns with the application. An existing stable Jest suite may have no economic reason to migrate. Neither “always faster” nor “zero configuration” establishes the decision. Runtime transformation is also separate from TypeScript checking in both toolchains.

## Allocate Tests by Risk, Not a Fixed Pyramid Ratio

Prefer fast focused checks for local edge cases, real dependency tests for important integration invariants and browser journeys for behavior that needs the whole interface. The testing pyramid is a reasoning aid, not an 80/15/5 quota or a guarantee that units cost exactly 1000 times less. A thin unit suite may be appropriate for an application whose primary risk is integration; a giant E2E suite can still omit critical concurrency and authorization boundaries.

Coverage has to describe both what executed and what was asserted. Avoid duplicated examples with weaker assertions in a comparison page: its job is to explain why a boundary needs a particular check, not restate every runner API.

## Real-World Decisions

For a TypeScript monorepo, require type checks independently, scope shared config paths deliberately, and keep each worker's backend fixtures isolated. A Nest test application must install the same relevant pipes, guards and interceptors as production; `app.init()` alone does not copy bootstrap configuration. Do not use a placeholder valid token to skip the authorization contract being tested.

For a React/Next application, distinguish synchronous component tests from async Server Component journeys in the actual framework runtime. Playwright supplies Chromium, Firefox and WebKit test engines; WebKit is not the branded Safari application. Add target-device or branded-browser checks when those differences affect the requirement.

For sensitive-domain applications, use synthetic tenant/customer fixtures. Authentication storage, screenshots, traces, videos and HTTP reports may contain secrets or personal data; control artifact access/retention and avoid indiscriminate request-body logging.

## Summary

Choose tools by the behavior they execute and observe. Runners control tests, component utilities observe DOM behavior, HTTP tests exercise the application contract and browser journeys verify the interface in a real engine. Combine those boundaries for concurrency, authorization and user experience; validate migrations and performance with the actual suite.

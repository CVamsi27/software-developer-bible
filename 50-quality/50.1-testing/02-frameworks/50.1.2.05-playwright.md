# Playwright: End-to-End Browser Journeys

A checkout test clicks "Submit", then asserts an order confirmation — and fails because the navigation had not finished when the assertion ran. Flaky tests like this are the reason teams abandon E2E suites. Playwright removes the guesswork: its locators auto-wait until an element is actionable, assertions retry until the condition holds or times out, and the test runs against a real browser with network control at the boundary.

```typescript
await page.getByRole('button', { name: 'Submit order' }).click();
await expect(page.getByText('Order confirmed')).toBeVisible();
```

## Definition

**Playwright** is a browser automation library for end-to-end testing. It drives Chromium, Firefox and WebKit through a single API, with **locators** that describe how to find an element, **auto-waiting** that waits for action-specific conditions and web assertions that retry until their expectations hold, and **Playwright Test fixtures** that give each test an isolated browser context. Network interception lets tests stub APIs, and storageState can reuse saved cookies and local storage. Its file is a credential-bearing artifact, not a fixture to commit.

> **Textbook Definition:** Playwright is an out-of-process browser automation library. Playwright Test adds test scheduling, assertions, diagnostics and isolated browser-context fixtures; the actual application and dependencies determine the boundary a test verifies.

## First Principles

Test against a real browser, not a simulated DOM: layout, focus, popups and network timing are real in production and should be real in the test. Resilient selectors target user-visible roles and labels, not fragile class names or DOM position. Control the network at the boundary (stub slow third parties, assert on request payloads) rather than asserting only on rendered pixels.

## 1. Locators and auto-waiting (retry until actionable)

Use locators to exercise the browser step whose outcome the test observes:

`page.getByRole(...)`, `page.getByLabel(...)` and `page.locator(...)` resolve lazily. A click checks visibility, stability, whether the element receives events and whether it is enabled. Other actions have different checks: filling a field also requires editability and does not use the identical click checklist. Assertions such as `expect(locator).toBeVisible()` retry until the condition holds or the timeout expires. Await the relevant assertion instead of guessing a sleep duration.

## 2. Fixtures: one isolated context per test

Playwright Test gives each test a fresh browser context by default. Cookies, localStorage and permissions are isolated, but a backend database, file store, shared account and external service are not. Allocate unique records/accounts or reset a disposable test namespace. The lower-level library does not create an automatic per-test context for you. `test.use()` configures fixture options for its test file or enclosing describe scope; custom fixtures can spin up a test database seed or a logged-in page and tear it down after the test.

## 3. Network interception and mocking

`page.route('**/api/**', route => route.fulfill({ ... }))` controls matching requests without calling the real API. This removes that dependency's timing and behavior; matching, fixture state and assertions still need to be correct. `page.request` can call real endpoints in setup, and storageState saves cookies/localStorage and can include IndexedDB when requested; it does not automatically persist sessionStorage. Reusing one saved login does not isolate concurrent server-side changes made by that account. Assert on the request payload (`route.request().postDataJSON()`) to verify what the client actually sends.

## 4. Observe the save contract after reload

This illustrative Playwright Test fixture controls a test-only API and checks the submitted JSON. It proves the browser-to-contract interaction, not a real database transaction:

```typescript
import { test, expect } from '@playwright/test';

test('saves an edited display name', async ({ page }) => {
  let saved = { name: 'Ada' };
  await page.route('**/api/profile', async route => {
    if (route.request().method() === 'PATCH') {
      const input = route.request().postDataJSON();
      expect(input).toEqual({ name: 'Grace' });
      saved = input;
    }
    await route.fulfill({ json: saved });
  });
  await page.goto('/profile'); // The fixture app must implement this route.
  await page.getByLabel('Display name').fill('Grace');
  await page.getByRole('button', { name: 'Save', exact: true }).click();
  await expect(page.getByRole('status')).toHaveText('Saved');
  await page.reload();
  await expect(page.getByLabel('Display name')).toHaveValue('Grace');
});
```

For a real persistence test, replace the route stub with an isolated backend fixture and verify after reload using the actual request path. Add a failure case that preserves the draft, then test unauthorized writes at the server boundary. A service worker can intercept traffic before ordinary routing; block it for route-mocked tests when appropriate, or test that worker separately.

The locator waits for its action's requirements; it does not infer that background saving is complete. An awaited business assertion supplies that boundary. Start request/download/popup waits before the triggering action where necessary to avoid losing the event.

## 5. Page Object vs locator-first trade-offs

Inline role-and-name locators make a small journey easy to follow. A Page Object can centralize a repeated interaction with a clear meaning, such as completing an address form. Introduce it when that shared meaning reduces maintenance without hiding important assertions; there is no minimum number of tests that makes the abstraction correct.

## 6. Evidence on failure: tracing, video, screenshots

`trace: 'retain-on-failure'` records actions, snapshots and network evidence for inspection in Trace Viewer. Inspecting a trace does not rerun the application or reproduce a database commit. Video and screenshots preserve selected visual evidence. Retain enough artifacts to explain the failure, with access and retention controls: traces can contain credentials, screenshots and sensitive response data. Opening a modal proves that interaction, not that a later booking or payment committed.

## 7. CI: sharding, retries, and visual regression limits

Sharding (`--shard=1/3`) partitions work; run every shard and combine their results. Bounded retries (`retries: 2`) can collect another attempt, but record a retry-pass result as flaky and inspect the first failure.

Screenshot comparisons can protect a stable page, component or critical layout. Control the browser version, operating system, fonts, viewport and data; disable animation or mask deliberately variable regions when those choices preserve the intended visual contract. Review a changed baseline rather than accepting it automatically. Pixel tolerances address bounded rendering variance, not a known layout defect. Screenshots complement behavior and accessibility assertions; they are useful beyond design-token surfaces. See [Playwright visual comparisons](https://playwright.dev/docs/test-snapshots).

## Summary

Playwright drives real browsers with locators that auto-wait, assertions that retry, fixtures that isolate, and network interception that controls the boundary. It helps control timing and browser state, but cannot make a shared backend deterministic by itself: act on user-visible roles, stub slow third parties, keep evidence on failure, and shard in CI.

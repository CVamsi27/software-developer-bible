# Unit Testing

## Definition

Unit testing is a software testing technique where individual units or components of software are tested in isolation to verify that each unit functions correctly. A "unit" is the smallest testable part of an application—typically a function, method, class, or module.

> **Textbook Definition:** A unit test evaluates a defined unit of behavior independently of selected external collaborators. The unit boundary is a design choice, and isolation does not require mocking every internal function.

The boundary is the behavior under examination, not necessarily the smallest function in the source tree. A class and its real internal helpers can form one unit. Replacing those helpers merely to test the outer method can remove the logic the test needs to verify.

## First Principles

Suppose a token cache should reuse an unexpired token and fetch a new one at expiry. A live provider and the real clock make a failure hard to interpret: did the rule fail, did the provider fail, or did time move between assertions?

Keep the cache’s real decision logic and control its external inputs. Supply a clock you can advance and a loader with known responses. This creates a narrow experiment: for the given time and loader outcome, does the cache return or reject as required?

The unit boundary determines what the experiment excludes. A successful test with a supplied loader cannot establish that HTTP headers, provider credentials, or transport retries work.
A separate unit test is useful when it makes a consequential rule easier to exercise or diagnose. A trivial helper may not need its own file; a short authorization predicate can merit several cases because one incorrect branch changes access.

## How to Arrange a Controlled Experiment

Use **arrange → act → assert (AAA)**:

1. **Arrange:** create fresh state and explicit dependencies.
2. **Act:** exercise the public behavior.
3. **Assert:** compare the observation with the agreed contract.

The **system under test** is the behavior actually exercised. A **test double** replaces a collaborator for the experiment. Doubles are different roles, not a hierarchy from weak to strong:

| Role | What it supplies | Token-cache example |
| ----- | ----------------------------------------- | --------------------------------------------------------- |
| Dummy | An argument the tested path does not use | A placeholder logger for a path that never logs |
| Stub | Controlled responses | Loader returns a known token and expiry |
| Spy | Records interactions for later assertions | Count loader calls; it may wrap real code or a substitute |
| Mock | Programmed interaction expectations | Require a refresh request with the agreed scope |
| Fake | A simplified working implementation | In-memory token store with read/write behavior |

One object may play several roles. A function that returns known tokens and records calls is both stub and spy. None of those roles guarantees that the substitute matches production; verify the actual adapter separately. See [Mocking](../04-mocking-and-patterns/50.1.4.01-mocking.md) for runner APIs and lifecycle.

## Example: Test the Exact Expiry Boundary

This self-contained Node.js example tests sequential access to one cache. Time values are milliseconds on the same chosen clock. The loader returns `{ value, expiresAt }`; a token is usable only while `now < expiresAt`.

```javascript
// token-cache.cjs — run with: node token-cache.cjs
const assert = require('node:assert/strict');

function createTokenCache(load, now) {
  let cached;
  return async function getToken() {
    if (cached && now() < cached.expiresAt) return cached.value;
    const fresh = await load();
    if (!fresh || typeof fresh.value !== 'string' || fresh.value.length === 0 ||
        !Number.isFinite(fresh.expiresAt) || fresh.expiresAt <= now()) {
      throw new Error('Loader returned an invalid or expired token');
    }
    cached = { value: fresh.value, expiresAt: fresh.expiresAt };
    return cached.value;
  };
}

async function main() {
  // Arrange: fresh cache, controlled clock, and two explicit responses.
  let time = 0;
  let calls = 0;
  const responses = [
    { value: 'token-A', expiresAt: 1000 },
    { value: 'token-B', expiresAt: 2000 },
  ];
  const getToken = createTokenCache(async () => responses[calls++], () => time);

  // Act and assert: initial load, reuse just before expiry, refresh at expiry.
  assert.equal(await getToken(), 'token-A');
  time = 999;
  assert.equal(await getToken(), 'token-A');
  assert.equal(calls, 1);
  time = 1000;
  assert.equal(await getToken(), 'token-B');
  assert.equal(calls, 2);

  // Independent failure case: preserve the loader's actual error.
  const failure = new Error('Provider unavailable');
  const failingCache = createTokenCache(async () => { throw failure; }, () => 0);
  await assert.rejects(failingCache(), error => error === failure);

  // An already-expired response must not be accepted as fresh.
  const expiredCache = createTokenCache(
    async () => ({ value: 'stale', expiresAt: 1000 }), () => 1000);
  await assert.rejects(expiredCache(), /invalid or expired token/);
  console.log('Reuse, exact expiry, loader failure, and stale response passed');
}
main().catch(error => { console.error(error); process.exitCode = 1; });
```

At time 0, the cache has no token, so the loader supplies A. At 999, A remains usable and the loader count stays at one. At 1,000, `now < expiresAt` becomes false; the loader supplies B and the count becomes two. Changing the comparison to `<=` incorrectly returns A at the boundary and fails the assertion.

The call-count assertion is appropriate because “reuse without fetching” is part of the cache contract. It does not assert the name of an internal helper or the shape of a private field. The failure case compares the original error object so a fabricated success or unrelated replacement error cannot pass it.

### State what this example does not establish

The example deliberately covers sequential calls. Two callers entering an empty cache together can each invoke the loader; preventing that requires shared ownership of an in-flight promise and explicit concurrency tests. A refresh margin before expiry is another policy, requiring its own boundary conditions.

Provider parsing, token scopes, server/client clock disagreement, cancellation, and remote availability are outside this unit. An injected clock is useful for deterministic tests, but it does not solve clock disagreement in production.

## Choose Cases From the Contract

For a pure function, test inputs and outputs directly. The [price example](../01-foundations/50.1.1.01-testing-overview.md#example-make-one-requirement-observable) demonstrates valid, invalid, and arithmetic-range inputs without external doubles.

For stateful behavior, test allowed transitions and rejected transitions. If an order cannot be shipped before confirmation, assert rejection and that its state remains pending; an exception alone does not prove the failed operation left state unchanged.

For an asynchronous unit, await its returned promise and attach the rejection assertion before advancing simulated time. A forgotten `await` can let the test finish before its assertion. Timers and promise continuations are separate scheduling steps; use the runner’s supported asynchronous timer advancement where the chain schedules timers after an awaited operation. Restore timers, spies, and global replacements after each test.

For a side-effecting unit, check both the intended interaction and relevant non-interaction: invalid input must not reach the payment adapter. A fake payment response only establishes the local branch. It does not prove a charge happened, and an unknown payment outcome cannot safely become “failed, retry immediately.” Follow the real boundary treatment in [Integration Testing](50.1.3.02-integration-testing.md).

### Use changed conditions to reveal weak assertions

Try changing the expiry comparison, returning the old token after refresh, or swallowing the loader error. The assertions should notice each changed behavior. This is the reasoning behind mutation testing: deliberately change logic and check whether tests detect a relevant deviation.

Also test missing and malformed inputs where the unit owns validation. A TypeScript generic such as `get<User>()` does not validate external JSON at runtime. A stub supplying a perfect object can hide a missing parser; test that parser with malformed values and test the transport at its own boundary.

## Extend the unit boundary deliberately

### Share behavior contracts with important fakes

An in-memory repository can make service tests fast, but it may differ from PostgreSQL in uniqueness, null ordering, driver types, and transaction behavior. Run appropriate contract cases against the fake and real implementation where their shared behavior matters. Use real database tests for guarantees the fake cannot represent.

### Control fixtures without coupling tests

Create new state for each scenario, including fresh nested objects when they may be mutated. A shallow copy of an array does not protect the objects inside it. Parallel workers need separate namespaces for any state that remains external to the unit.

Inject only useful boundaries; avoid adding indirection to every internal function solely to enable spying. A pure business rule and explicit I/O adapter often make the natural contract easier to test.

### Keep feedback useful rather than enforcing arbitrary speed

The FIRST mnemonic means **Fast, Isolated, Repeatable, Self-validating, Timely**. Treat it as guidance: tests should run often, own their state, produce repeatable evidence, fail automatically, and be written while the required behavior is understood. There is no universal ten-millisecond cutoff.

Measure slow setup, repeated transforms, and excessive workers. Parallelizing CPU-heavy tests beyond available capacity can make feedback slower. Use the runner’s supported project configuration and keep type checking as a separate gate when the runner only transforms TypeScript.

## Summary

Unit tests create controlled experiments around a defined behavior. Keep the real rule, replace only the collaborators you need to control, and compare outcomes against an independent contract. Trace boundaries and failures explicitly; a passing substitute-based test supports its local claim and still needs complementary evidence for real integrations.

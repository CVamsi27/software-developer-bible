# Unit Testing

A token cache should reuse an unexpired token and fetch a new one at expiry. With a live provider and the real clock, a failure is uninterpretable: did the rule fail, did the provider fail, or did time move between assertions? The fix is a narrow experiment — real decision logic, controlled clock and loader.

```text
arrange (fresh state + explicit doubles) → act (exercise behavior)
      → assert (compare with the agreed contract)
```

## Definition

**Unit testing** checks one defined **behavior** while controlling or removing selected external collaborators. The **unit** can be a function, a class, or several collaborating internal helpers — it is a chosen behavioral boundary, not automatically the smallest source-code element.

> **Textbook Definition:** A unit test evaluates a defined unit of behavior independently of selected external collaborators. The unit boundary is a design choice, and isolation does not require mocking every internal function.

## First Principles

Keep the cache's real decision logic and control its external inputs: a clock you can advance and a loader with known responses. For the given time and loader outcome, does the cache return or reject as required? The unit boundary determines what the experiment excludes — a passing test with a supplied loader cannot establish that HTTP headers, provider credentials or transport retries work.

## How It Works

### 1. Arrange a Controlled Experiment

Use **arrange → act → assert (AAA)**: create fresh state and explicit dependencies, exercise the public behavior, then compare the observation with the agreed contract. The **system under test** is the behavior actually exercised; a **test double** replaces a collaborator for the experiment. Doubles are different roles, not a hierarchy from weak to strong:

| Role | What it supplies | Token-cache example |
| ----- | ----------------------------------------- | --------------------------------------------------------- |
| Dummy | An argument the tested path does not use | A placeholder logger for a path that never logs |
| Stub | Controlled responses | Loader returns a known token and expiry |
| Spy | Records interactions for later assertions | Count loader calls; it may wrap real code or a substitute |
| Mock | Programmed interaction expectations | Require a refresh request with the agreed scope |
| Fake | A simplified working implementation | In-memory token store with read/write behavior |

One object may play several roles — a function returning known tokens while recording calls is both stub and spy. None of those roles guarantees the substitute matches production; verify the actual adapter separately. See [Mocking](../04-mocking-and-patterns/50.1.4.01-mocking.md) for runner APIs and lifecycle.

### 2. Test the Exact Expiry Boundary

This self-contained Node.js example tests sequential access to one cache. Time values are milliseconds on the same chosen clock. The loader returns `{ value, expiresAt }`; a token is usable only while `now < expiresAt`.

```javascript
// token-cache.cjs — run with: node token-cache.cjs
const assert = require('node:assert/strict');

function createTokenCache(load, now) {
  let cached;
  return async function getToken() {
    if (cached && now() < cached.expiresAt) return cached.value;
    const fresh = await load();
    if (!fresh || typeof fresh.value !== 'string' || fresh.value.length === 0 ||
        !Number.isFinite(fresh.expiresAt) || fresh.expiresAt <= now()) {
      throw new Error('Loader returned an invalid or expired token');
    }
    cached = { value: fresh.value, expiresAt: fresh.expiresAt };
    return cached.value;
  };
}

async function main() {
  // Arrange: fresh cache, controlled clock, and two explicit responses.
  let time = 0;
  let calls = 0;
  const responses = [
    { value: 'token-A', expiresAt: 1000 },
    { value: 'token-B', expiresAt: 2000 },
  ];
  const getToken = createTokenCache(async () => responses[calls++], () => time);

  // Act and assert: initial load, reuse just before expiry, refresh at expiry.
  assert.equal(await getToken(), 'token-A');
  time = 999;
  assert.equal(await getToken(), 'token-A');
  assert.equal(calls, 1);
  time = 1000;
  assert.equal(await getToken(), 'token-B');
  assert.equal(calls, 2);

  // Independent failure case: preserve the loader's actual error.
  const failure = new Error('Provider unavailable');
  const failingCache = createTokenCache(async () => { throw failure; }, () => 0);
  await assert.rejects(failingCache(), error => error === failure);

  // An already-expired response must not be accepted as fresh.
  const expiredCache = createTokenCache(
    async () => ({ value: 'stale', expiresAt: 1000 }), () => 1000);
  await assert.rejects(expiredCache(), /invalid or expired token/);
  console.log('Reuse, exact expiry, loader failure, and stale response passed');
}
main().catch(error => { console.error(error); process.exitCode = 1; });
```

At time 0 the loader supplies A; at 999 A remains usable and the count stays at one; at 1,000 `now < expiresAt` becomes false and the loader supplies B. Changing the comparison to `<=` incorrectly returns A at the boundary and fails the assertion. The call-count assertion is appropriate because "reuse without fetching" is part of the contract — it does not name an internal helper or private field.

This example deliberately covers sequential calls only. Two callers entering an empty cache together can each invoke the loader; preventing that needs shared ownership of an in-flight promise and explicit concurrency tests. Provider parsing, token scopes, clock disagreement, cancellation and remote availability are outside this unit — an injected clock gives determinism, not production clock agreement.

### 3. Choose Cases From the Contract

- **Pure functions**: test inputs and outputs directly. The [price example](../01-foundations/50.1.1.01-testing-overview.md#example-make-one-requirement-observable) covers valid, invalid and arithmetic-range inputs without doubles.
- **Stateful behavior**: test allowed and rejected transitions. If an order cannot ship before confirmation, assert rejection *and* that its state remains pending — an exception alone does not prove state was unchanged.
- **Async units**: await the returned promise and attach the rejection assertion before advancing simulated time. A forgotten `await` lets the test finish before its assertion; restore timers, spies and global replacements after each test.
- **Side-effecting units**: check both the intended interaction and the relevant non-interaction — invalid input must not reach the payment adapter. A fake payment response establishes the local branch only; follow the real boundary treatment in [Integration Testing](50.1.3.02-integration-testing.md).

Use changed conditions to reveal weak assertions: flip the expiry comparison, return the old token after refresh, or swallow the loader error — the suite should notice each change. Also test missing and malformed inputs where the unit owns validation: a TypeScript generic such as `get<User>()` does not validate external JSON at runtime, and a stub supplying a perfect object can hide a missing parser.

### 4. Share Behavior Contracts With Important Fakes

An in-memory repository makes service tests fast but may differ from PostgreSQL in uniqueness, null ordering, driver types and transaction behavior. Run the appropriate contract cases against both the fake and the real implementation where their shared behavior matters, and use real database tests for guarantees the fake cannot represent. Inject only useful boundaries — avoid adding indirection to every internal function solely to enable spying.

### 5. Keep Fixtures Isolated and Feedback Useful

Create new state for each scenario, including fresh nested objects when they may be mutated — a shallow array copy does not protect the objects inside it. Parallel workers need separate namespaces for any state that remains external to the unit. The FIRST mnemonic means **Fast, Independent, Repeatable, Self-validating, Timely**: run tests often, own their state, produce repeatable evidence, fail automatically, and write them while the behavior is understood. There is no universal ten-millisecond cutoff — measure slow setup, repeated transforms and excessive workers instead.

## Summary

Unit tests create controlled experiments around a defined behavior. Keep the real rule, replace only the collaborators you must control, and compare outcomes against an independent contract. Choose cases from that contract — valid and invalid inputs, transitions, async boundaries and non-interactions — and share behavior contracts with any fake that stands in for production. A passing substitute-based test supports its local claim and still needs complementary evidence for real integrations.

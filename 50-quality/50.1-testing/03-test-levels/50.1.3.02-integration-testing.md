# Integration Testing

A booking API receives two valid requests for the same tenant and slot. A preliminary availability read can say "free" to both callers — only the database write arbitrates. The test must create competing requests instead of feeding a mock two predetermined answers.

```text
POST A ──> handler ──> INSERT ──┐
                               ├─ unique tenant/slot constraint ──> one row
POST B ──> handler ──> INSERT ──┘
                      responses: one 201, one 409
```

## Definition

An **integration test** exercises selected components together and observes their **shared contract**. The boundary might be an HTTP handler plus database, a repository plus database, or an HTTP client plus controlled provider responses. State which participants are real before interpreting a passing result.

> **Textbook Definition:** Integration testing evaluates interactions and shared contracts between selected components assembled together, with the real and substituted participants explicitly identified.

## First Principles

An isolated unit cannot reveal a mismatch in the connection it replaced. A query can have the wrong column name, two transactions can race, or a client can serialize the wrong body while every stub returns success. Cross the seam that can break, make its inputs deterministic, and observe both the response and the durable effect.

## 1. Choose the Seam Before the Harness

| Test boundary | Real behavior observed | Still outside scope |
| ------------------------ | -------------------------------------------------------------- | -------------------------------------------------- |
| Repository + PostgreSQL | SQL, constraints, driver values, transaction behavior | HTTP parsing and identity propagation |
| HTTP app + PostgreSQL | Routing, validation, response mapping and durable writes | Browser, deployed proxy/TLS and provider behavior |
| Client + MSW response | Outgoing request construction and response/error handling | Actual provider authorization, schema and delivery |
| Consumer + actual broker | Publish/consume, acknowledgement, retry and delivery semantics | Unexercised provider limits or production topology |

Top-down, bottom-up and sandwich integration describe the order in which collaborators are assembled — not confidence or a required test distribution. A direct HTTP test belongs here when its real seam is HTTP plus storage; it does not become browser E2E merely because it has a URL.

## 2. Keep the Application Separate From Its Test Database

This uses Express 5, node-postgres and Vitest. The endpoint deliberately accepts only short non-empty slot and customer strings. The fixture owns the tenant argument; do not adapt it into a caller-controlled trusted identity header.

```typescript
// booking-app.ts
import express from "express";
import type { Pool } from "pg";

export function createBookingApp(db: Pool, tenant: string) {
  const app = express();
  app.use(express.json({ limit: "16kb" }));

  app.post("/bookings", async (req, res) => {
    const body: unknown = req.body;
    if (typeof body !== "object" || body === null ||
        !("slot" in body) || !("customer" in body) ||
        typeof body.slot !== "string" || typeof body.customer !== "string" ||
        body.slot.trim().length === 0 || body.customer.trim().length === 0 ||
        body.slot.length > 100 || body.customer.length > 100) {
      res.status(400).json({ error: "Invalid booking" });
      return;
    }
    const result = await db.query<{ slot: string; customer: string }>(
      `INSERT INTO bookings (tenant, slot, customer) VALUES ($1, $2, $3)
       ON CONFLICT (tenant, slot) DO NOTHING RETURNING slot, customer`,
      [tenant, body.slot, body.customer],
    );
    if (result.rows.length === 0) {
      res.status(409).json({ error: "Slot already booked" });
      return;
    }
    res.status(201).json(result.rows[0]);
  });
  return app;
}
```

The SQL values are parameterized. Dynamic column or table names cannot be made safe by passing them as value parameters — map a closed set of permitted identifiers first. Map snake_case database fields to the declared application shape, and account for driver types such as numeric and large integers instead of asserting every value arrives as a JavaScript number.

## 3. Exercise Success, Competition and Rejected Input

Install `@testcontainers/postgresql`, `pg`, `express`, `supertest`, `vitest` and their TypeScript declarations. Testcontainers needs a supported running container runtime. Select a PostgreSQL image matching production major, extensions and collation; `postgres:16` here illustrates a major-version choice, and pinning an image digest matters when exact build reproduction is required. Run the application's actual migrations in a real project.

```typescript
// booking.integration.test.ts
import { afterAll, beforeAll, beforeEach, expect, it } from "vitest";
import { PostgreSqlContainer, type StartedPostgreSqlContainer } from "@testcontainers/postgresql";
import { Pool } from "pg";
import request from "supertest";
import { createBookingApp } from "./booking-app";

let container: StartedPostgreSqlContainer | undefined;
let db: Pool | undefined;
let app: ReturnType<typeof createBookingApp>;

beforeAll(async () => {
  container = await new PostgreSqlContainer("postgres:16").start();
  db = new Pool({ connectionString: container.getConnectionUri(), max: 2 });
  await db.query(`CREATE TABLE bookings (
    tenant text NOT NULL, slot text NOT NULL, customer text NOT NULL,
    PRIMARY KEY (tenant, slot)
  )`);
  app = createBookingApp(db, "synthetic-tenant");
}, 60_000);

// These tests run sequentially and exclusively own this container/database.
// Do not share this TRUNCATE cleanup with concurrent tests.
beforeEach(async () => { await db!.query("TRUNCATE bookings"); });
afterAll(async () => {
  try { await db?.end(); } finally { await container?.stop(); }
}, 60_000);

it("returns and persists the created booking", async () => {
  const result = await request(app).post("/bookings")
    .send({ slot: "slot-1", customer: "customer-1" }).expect(201);
  expect(result.body).toEqual({ slot: "slot-1", customer: "customer-1" });
  const stored = await db!.query("SELECT tenant, slot, customer FROM bookings");
  expect(stored.rows).toEqual([
    { tenant: "synthetic-tenant", slot: "slot-1", customer: "customer-1" },
  ]);
});

it("permits one of two competing claims and persists only its customer", async () => {
  const results = await Promise.all(["customer-A", "customer-B"].map(customer =>
    request(app).post("/bookings").send({ slot: "same-slot", customer })));
  expect(results.map(result => result.status).sort()).toEqual([201, 409]);
  const winner = results.find(result => result.status === 201)!;
  const stored = await db!.query("SELECT customer FROM bookings WHERE slot = $1", ["same-slot"]);
  expect(stored.rows).toEqual([{ customer: winner.body.customer }]);
});

it("rejects invalid input without writing a booking", async () => {
  await request(app).post("/bookings").send({ slot: "", customer: "customer-1" }).expect(400);
  expect((await db!.query("SELECT * FROM bookings")).rows).toEqual([]);
});
```

This is competition evidence for one unique slot key — not proof of arbitrary interval overlap, complete scheduling rules or every possible timing. Add controlled interleavings and repeated stress where a larger transaction protocol requires them. Run TypeScript checking separately; a runner's source transform is not a type check.

## 4. Isolate the Application's Writes, Not Just the Test Connection

| Strategy | Suitable when | Boundary to account for |
| ------------------------------------- | ------------------------------------------------------------------------- | -------------------------------------------------------------- |
| Per-file/worker database or container | Parallel suites need independent namespaces | Startup capacity, migrations, credentials and cleanup |
| Per-test schema | Application consistently selects that schema | Pool connections and background workers must use it too |
| Rollback transaction | Every tested database operation uses the same injected client/transaction | An HTTP app's independent pool connection escapes the rollback |
| TRUNCATE/known-record cleanup | An exclusive fixture owns the affected tables | Other tests/consumers must not write concurrently |
| Snapshot/restore | Tool/database supports it and active connections are handled | Generic Database.createSnapshot is not a standard API |

In node-postgres, a transaction requires the same checked-out client for BEGIN, queries, COMMIT or ROLLBACK, and release — separate `pool.query` calls do not promise the same connection. A transaction also cannot undo an email or provider charge; test and recover those effects deliberately. Use synthetic fixtures and stable scenario names, and limit cleanup to the owned test environment — a variable named TEST_DB_URL is not by itself a guard against the wrong target.

## 5. Keep Controlled Provider Responses Honest

Use [Mocking](../04-mocking-and-patterns/50.1.4.01-mocking.md) for the canonical MSW handlers and lifecycle. Make the handler check method, URL, headers and body, and return controlled success, HTTP rejection and transport rejection cases with `http`/`HttpResponse` — the old `rest`/`res`/`ctx` API is obsolete. A permissive always-successful handler misses malformed requests, and a mocked SDK can accept invented fields a real charge API would reject. Test your adapter against the provider's actual supported sandbox and documented test data.

A payment timeout can leave an unknown outcome even when the client receives an exception. Model idempotency, lookup and reconciliation before asserting that a retry or refund is safe. An unimplemented operation must reject clearly rather than return fabricated success. Database uniqueness and an outbox coordinate local state; they do not make the remote side effect part of the same database transaction.

## 6. Exercise Broker Semantics and Contracts With Real Systems

An in-memory function dispatcher verifies local handler wiring. It cannot establish broker durability, acknowledgment, redelivery, ordering, dead-letter handling or duplicate recovery. For those claims, publish through the real test broker and await an observable consumer effect with a bounded deadline. Record duplicate processing and acknowledgment behavior explicitly. Likewise, returning an order object does not establish persistence, and setting `sent: true` does not establish delivery.

Pair controlled consumer tests with contract verification: Pact-style checks record the consumer's expected request and response and verify them against a provider with suitable states. That complements integration tests without establishing deployment reachability or a vendor's actual delivery. Limit concurrency by database connections, CPU and memory, and container startup budgets; namespace external state before increasing parallelism.

## Summary

Integration tests reveal defects in composition by crossing the seam that can break. A useful result identifies its real participants, exercises their contract, and observes durable effects — routing, validation, constraints, competition outcomes and rejected input. Database isolation must include the application's connections; controlled provider, broker or contract responses establish only the behavior actually exercised.

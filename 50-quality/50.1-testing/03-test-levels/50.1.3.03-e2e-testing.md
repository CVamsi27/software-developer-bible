# E2E Testing

## Definition

**End-to-end testing** exercises a declared application journey across its participating layers and checks the observable result. A browser-driven test commonly spans browser UI, server routing and persistence. External providers may be real sandboxes or controlled substitutes; document that boundary rather than claiming the test verifies everything.

## First Principles

A unit can behave correctly while its connections to other units fail: a route, cookie, serialization format or deployed asset can break a user's journey. A test must therefore cross the relevant integration path to observe that failure. More layers also create more possible causes, so deterministic data, useful observations and diagnostics are essential.

## Trace Creating a Note and Reading It Again

A synthetic reader creates a note, receives confirmation, reloads the page and sees the saved note. The browser click alone cannot establish persistence; the second read is part of the contract. The environment must run the intended backend and persistence layer for this to be a persistence test.

```text
labelled form → POST /api/notes → authorization + storage
       ↓ confirmation                    ↓
page reload → GET /api/notes → saved record → rendered heading
```

A separate forced-503 case intercepts the browser request to establish the UI's failure behavior. That case does not exercise the real backend's failure response. Keeping those claims distinct makes the result useful.

## What Playwright Controls

| Component | Role | Boundary |
| -------------------- | ----------------------------------------------------- | ------------------------------------------------------- |
| Test runner/fixtures | Schedule tests, own browser contexts, collect results | Shared backend records still need isolation |
| Browser project | Execute Chromium, Firefox or WebKit | WebKit is not the branded Safari application |
| Locator | Re-resolve the intended DOM target | Ambiguous selectors need a clearer contract |
| Actionability checks | Wait for supported interaction conditions | Clickability does not mean application data is ready |
| Web-first assertion | Retry an observable condition until timeout | Immediate value reads do not gain retries automatically |
| Trace/report | Explain browser actions, network and failures | May contain credentials or personal data |

Device emulation changes viewport/user-agent and selected capabilities; it does not reproduce every physical device or mobile OS. Choose target engines/devices from the actual user requirement, then add real-device checks when needed.

## Code Examples

### Configure a Running Application and Selected Browsers

This assumes the project provides `npm run start:e2e`, which starts an isolated test application and its dependencies on port 3000. The application implements `/notes`, a field labeled **Title**, a **Create note** button, and `/api/notes`. Do not point the test at a production account or customer dataset.

```typescript
// playwright.config.ts
import { defineConfig } from "@playwright/test";

export default defineConfig({
  testDir: "./tests",
  fullyParallel: true,
  forbidOnly: Boolean(process.env.CI),
  retries: process.env.CI ? 1 : 0,
  workers: process.env.CI ? 2 : undefined,
  reporter: [["list"], ["html", { open: "never" }]],
  use: {
    baseURL: "http://127.0.0.1:3000",
    trace: "on-first-retry",
    screenshot: "only-on-failure",
  },
  webServer: {
    command: "npm run start:e2e",
    url: "http://127.0.0.1:3000/notes",
    reuseExistingServer: !process.env.CI,
  },
  projects: [
    { name: "chromium", use: { browserName: "chromium" } },
    { name: "firefox", use: { browserName: "firefox" } },
    { name: "webkit", use: { browserName: "webkit" } },
  ],
});
```

```bash
npm install --save-dev @playwright/test typescript @types/node
npx playwright install --with-deps
npx playwright test
```

Run a separate TypeScript check with a compatible tsconfig (`types: ["node"]` for the Node globals/imports in these files). Playwright transforms TypeScript but does not type-check it. Install browser binaries matching the locked Playwright package. Set workers from actual environment capacity, not the illustrative value above. A startup HTTP response alone does not prove migrations, worker consumers or providers are ready; arrange readiness for the journey's dependencies.

### Assert Both the Write Result and the Subsequent Read

The fixture contract permits synthetic note creation and returns 201 after storing a note. Authenticated applications must provision a synthetic authorized account/tenant and scoped test data through owned fixtures before this test runs.

```typescript
// tests/notes.spec.ts
import { randomUUID } from "node:crypto";
import { test, expect } from "@playwright/test";

test("created note is visible after reloading", async ({ page }) => {
  const title = `E2E-${randomUUID()}`;
  await page.goto("/notes");
  await page.getByLabel("Title", { exact: true }).fill(title);
  const response = page.waitForResponse((candidate) =>
    new URL(candidate.url()).pathname === "/api/notes" &&
    candidate.request().method() === "POST");
  await page.getByRole("button", { name: "Create note", exact: true }).click();
  expect((await response).status()).toBe(201);
  await expect(page.getByRole("heading", { name: title, exact: true })).toBeVisible();
  await page.reload();
  await expect(page.getByRole("heading", { name: title, exact: true })).toBeVisible();
});

test("a failed create does not show a false saved note", async ({ page }) => {
  const title = `E2E-${randomUUID()}`;
  await page.route("**/api/notes", async (route) => {
    if (route.request().method() !== "POST") return route.continue();
    expect(route.request().postDataJSON()).toEqual({ title });
    await route.fulfill({
      status: 503,
      contentType: "application/json",
      body: JSON.stringify({ error: "Unavailable" }),
    });
  });
  await page.goto("/notes");
  await page.getByLabel("Title", { exact: true }).fill(title);
  await page.getByRole("button", { name: "Create note", exact: true }).click();
  await expect(page.getByRole("alert")).toHaveText("Could not create note");
  await expect(page.getByRole("heading", { name: title, exact: true })).toHaveCount(0);
  await expect(page.getByLabel("Title", { exact: true })).toHaveValue(title);
});
```

These are application contract examples, not a generic implementation of a notes service. The environment must establish data isolation and clean up its synthetic records after the run. Random identifiers prevent name collisions; they do not by themselves provide tenant isolation or cleanup. A local fixture server can validate the test's mechanics but does not establish production authorization or database behavior.

## Wait for the Consequence, Not an Arbitrary Delay

Register response/download/navigation observers **before** the action that triggers them. Await the action and a meaningful result. Locator assertions such as `toHaveCount`, `toBeVisible` and `toHaveURL` retry; `locator.count()` or `textContent()` returns an immediate observation and can race with rendering.

Auto-waiting checks supported action conditions such as visibility, stability and enabled state. It does not wait for every API call, a background job or a business invariant. Avoid `waitForTimeout` as synchronization and do not treat `networkidle` as universal application readiness. For an exact list, assert its expected membership/count rather than only that its first item exists.

Role/label locators expose useful semantics and usually survive markup changes. A stable test ID is reasonable when the contract lacks a suitable user-facing target. `.first()` can conceal an ambiguous locator and interact with the wrong record. Page-object helpers can centralize repeated actions, but keep important assertions visible and retain locators rather than converting them too early into non-retrying strings.

## Isolation Has a Browser Side and a Server Side

Playwright supplies fresh browser contexts for tests using its normal page/context fixtures. This separates browser cookies/storage, not a database, account settings or remote queue. A shared account is suitable only if parallel tests cannot interfere through its server state. Mutating tests need scoped accounts/tenants and fixtures that tolerate retries and cleanup after failure.

Persisted `storageState` can avoid repeating login. Authenticate in a setup project and declare it as a dependency; merely naming a file `auth.setup.ts` does not establish ordering. Wait for the application's authentication completion before saving state. Cookies/local storage and optional IndexedDB state have supported storage-state handling; sessionStorage requires a separate arrangement. Test logout/session expiry independently rather than assuming saved state proves authentication correctness.

Auth files can permit account impersonation. Gitignore them and keep them out of general artifact uploads, even in a private repository. Use synthetic accounts and controlled secret injection; traces, screenshots, videos and reports can also expose sensitive content. Restrict artifact access and retention instead of recording complete real request bodies by default.

## Decide Which External Boundary to Exercise

Interception is valuable for controlled errors, slow responses and malformed data, but a mocked payment response cannot establish provider compatibility or actual delivery. Keep a separate supported sandbox integration where that contract matters. Use the provider's current test values and expiry rules; do not carry expired sample dates into the suite. A page displaying a mocked confirmation message does not prove an email arrived.

Browser `page.route` does not intercept requests executed by a server-side component. Service workers can also affect interception; choose and document the supported strategy. Adding an Authorization header through a route handler can mask an application's missing credential propagation, so do not use that trick while claiming to test authentication.

For payments and other writes, a timeout may leave an unknown outcome. Test supported idempotency/recovery behavior rather than blindly submitting again. A browser success screen and a server response are different observations; persistence and provider state may require further verification.

## Visual Comparisons Need Stable Inputs

Playwright's `toHaveScreenshot` compares rendered images against an approved baseline; it is not a semantic or accessibility test. Stabilize browser/OS, fonts, viewport, animation and fixtures. Review baseline changes and choose a justified tolerance. A high allowed difference can hide the regression the test was meant to detect. Cypress image comparison requires the relevant configured plugin; a screenshot matcher is not automatically a core Cypress command.

## Run Every Shard and Retain Useful Evidence

```bash
npx playwright test --shard=1/4 --reporter=blob
# The CI matrix must also run shards 2/4, 3/4 and 4/4.
npx playwright merge-reports --reporter=html ./all-blob-reports
```

CI must install dependencies and browsers, start the application's real test dependencies, run all configured projects/shards and collect reports even when a shard fails. Blob report files from every shard must be downloaded into the merge directory. `fullyParallel` affects test-level distribution; sharding without it groups at file level. Follow the canonical [GitHub Actions chapter](../../../40-platform/40.3-ci-cd/01-ci-platforms/40.3.1.01-github-actions.md) for workflow permissions, current actions, secrets and artifact policy rather than copying an incomplete pipeline here.

Retries provide diagnostics and identify flaky outcomes; they do not explain or repair the failure. Track first-attempt failures separately, inspect traces and distinguish test races, environment instability and application defects. Quarantine needs an owner and a replacement verification path for the affected requirement.

## Real-World Decisions

Choose journeys from the application's risks: access denial and tenant separation, creation/recovery of important records, authentication redirects, imports/exports, and supported device behavior. There is no universal 3–10 journey limit or ten-percent test quota. Add lower-level tests for precise edge cases and concurrency invariants that a browser journey is expensive or poorly positioned to establish.

Playwright, Cypress and Selenium have different runtimes and ecosystem requirements. Check supported browsers and current tooling plans directly; do not infer a fixed speed ranking or claim every kind of Cypress parallel execution requires a paid service. Select the tool from the journey, existing investment and measured suite behavior.

## Common Mistakes

- Calling a routed/mock-response browser test proof of the real backend/provider.
- Treating retries or a visible first list item as evidence that a race was fixed.
- Sharing mutable account/database state across parallel tests.
- Saving auth state without setup dependencies or uploading it with reports.
- Checking an unchanged chart remains visible after a filter action without checking its new data.
- Recording sensitive fixtures or using expired payment test examples.

## Best Practices

Describe the exercised layers and the deliberately replaced dependencies. Isolate browser and server state, use synthetic data and await the consequence that matters. Keep diagnostics available with appropriate access and retention, execute every required project/shard, and investigate first-attempt failures instead of hiding them behind retries.

## Summary

E2E tests establish selected journeys across configured layers, not every property of an application. Trace interaction through response and subsequent state, distinguish mocked errors from real integrations, and isolate backend data as well as browser contexts. Real engines, meaningful waits and protected diagnostics make failures interpretable.

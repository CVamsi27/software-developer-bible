# E2E Testing

A synthetic reader creates a note, receives confirmation, reloads the page and sees the saved note. The browser click alone cannot establish persistence — the second read is part of the contract, and the environment must run the intended backend and persistence layer for this to be a persistence test.

```text
labeled form → POST /api/notes → authorization + storage
       ↓ confirmation                    ↓
page reload → GET /api/notes → saved record → rendered heading
```

## Definition

**End-to-end testing** exercises a declared application **journey** across its participating layers and checks the observable result. A browser-driven test commonly spans browser UI, server routing and persistence. External providers may be real sandboxes or controlled substitutes — document that boundary rather than claiming the test verifies everything.

> **Textbook Definition:** End-to-end testing evaluates an application journey through its declared system boundary by supplying inputs at an entry point and observing externally meaningful outcomes.

## First Principles

A unit can behave correctly while its connections to other units fail: a route, cookie, serialization format or deployed asset can break a user's journey. A test must therefore cross the relevant integration path to observe that failure. More layers also create more possible causes, so deterministic data, useful observations and diagnostics are essential.

## How It Works

### 1. Know What Playwright Controls

| Component | Role | Boundary |
| -------------------- | ----------------------------------------------------- | ------------------------------------------------------- |
| Test runner/fixtures | Schedule tests, own browser contexts, collect results | Shared backend records still need isolation |
| Browser project | Execute Chromium, Firefox or WebKit | WebKit is not the branded Safari application |
| Locator | Re-resolve the intended DOM target | Ambiguous selectors need a clearer contract |
| Actionability checks | Wait for supported interaction conditions | Clickability does not mean application data is ready |
| Web-first assertion | Retry an observable condition until timeout | Immediate value reads do not gain retries automatically |
| Trace/report | Explain browser actions, network and failures | May contain credentials or personal data |

Device emulation changes viewport, user-agent and selected capabilities; it does not reproduce every physical device or mobile OS. Choose target engines and devices from the actual user requirement, then add real-device checks when needed.

### 2. Configure a Running Application and Selected Browsers

This assumes the project provides `npm run start:e2e`, which starts an isolated test application and its dependencies on port 3000. The application implements `/notes`, a field labeled **Title**, a **Create note** button, and `/api/notes`. Do not point the test at a production account or customer dataset.

```typescript
// playwright.config.ts
import { defineConfig } from "@playwright/test";

export default defineConfig({
  testDir: "./tests",
  fullyParallel: true,
  forbidOnly: Boolean(process.env.CI),
  retries: process.env.CI ? 1 : 0,
  workers: process.env.CI ? 2 : undefined,
  reporter: [["list"], ["html", { open: "never" }]],
  use: {
    baseURL: "http://127.0.0.1:3000",
    trace: "on-first-retry",
    screenshot: "only-on-failure",
  },
  webServer: {
    command: "npm run start:e2e",
    url: "http://127.0.0.1:3000/notes",
    reuseExistingServer: !process.env.CI, // Reuse only a deliberately started test server.
  },
  projects: [
    { name: "chromium", use: { browserName: "chromium" } },
    { name: "firefox", use: { browserName: "firefox" } },
    { name: "webkit", use: { browserName: "webkit" } },
  ],
});
```

```bash
npm install --save-dev @playwright/test typescript @types/node
npx playwright install --with-deps
npx playwright test
```

Run a separate TypeScript check with a compatible tsconfig. Playwright transforms TypeScript but does not type-check it. Install browser binaries matching the locked Playwright package, and set workers from actual environment capacity rather than the illustrative value above. A startup HTTP response alone does not prove migrations, worker consumers or providers are ready — arrange readiness for the journey's dependencies.

### 3. Assert Both the Write Result and the Subsequent Read

The fixture contract permits synthetic note creation and returns 201 after storing a note. Authenticated applications must provision a synthetic authorized account and tenant with scoped test data through owned fixtures before this test runs.

```typescript
// tests/notes.spec.ts
import { randomUUID } from "node:crypto";
import { test, expect } from "@playwright/test";

test("created note is visible after reloading", async ({ page }) => {
  const title = `E2E-${randomUUID()}`;
  await page.goto("/notes");
  await page.getByLabel("Title", { exact: true }).fill(title);
  const response = page.waitForResponse((candidate) =>
    new URL(candidate.url()).pathname === "/api/notes" &&
    candidate.request().method() === "POST");
  await page.getByRole("button", { name: "Create note", exact: true }).click();
  expect((await response).status()).toBe(201);
  await expect(page.getByRole("heading", { name: title, exact: true })).toBeVisible();
  await page.reload();
  await expect(page.getByRole("heading", { name: title, exact: true })).toBeVisible();
});

test("a failed create does not show a false saved note", async ({ page }) => {
  const title = `E2E-${randomUUID()}`;
  await page.route("**/api/notes", async (route) => {
    if (route.request().method() !== "POST") return route.continue();
    expect(route.request().postDataJSON()).toEqual({ title });
    await route.fulfill({
      status: 503,
      contentType: "application/json",
      body: JSON.stringify({ error: "Unavailable" }),
    });
  });
  await page.goto("/notes");
  await page.getByLabel("Title", { exact: true }).fill(title);
  await page.getByRole("button", { name: "Create note", exact: true }).click();
  await expect(page.getByRole("alert")).toHaveText("Could not create note");
  await expect(page.getByRole("heading", { name: title, exact: true })).toHaveCount(0);
  await expect(page.getByLabel("Title", { exact: true })).toHaveValue(title);
});
```

The forced-503 case establishes the UI's failure behavior; it does not exercise the real backend's failure response. Random identifiers prevent name collisions but do not provide tenant isolation or cleanup — the environment must establish data isolation and clean up synthetic records after the run.

### 4. Wait for the Consequence, Not an Arbitrary Delay

Register response, download and navigation observers **before** the action that triggers them. Await the action and a meaningful result. Locator assertions such as `toHaveCount`, `toBeVisible` and `toHaveURL` retry; immediate reads like `locator.count()` or `textContent()` can race with rendering.

Auto-waiting checks supported action conditions such as visibility, stability and enabled state — not every API call, background job or business invariant. Avoid `waitForTimeout` as synchronization, and do not treat `networkidle` as universal readiness. For an exact list, assert its expected membership and count rather than only that its first item exists. Keep actions outside `waitFor`, and prefer role and label locators over `.first()`, which can conceal an ambiguous locator.

### 5. Isolate the Browser Side and the Server Side

Playwright supplies fresh browser contexts for tests using its normal page and context fixtures. That separates browser cookies and storage — not a database, account settings or remote queue. A shared account suits only tests that cannot interfere through server state; mutating tests need scoped accounts and tenants plus fixtures that tolerate retries and clean up after failure.

Persisted `storageState` can avoid repeating login: authenticate in a setup project and declare it as a dependency, since merely naming a file `auth.setup.ts` does not establish ordering. Test logout and session expiry independently rather than assuming saved state proves authentication correctness. Auth files can permit account impersonation — gitignore them, use synthetic accounts and controlled secret injection, and restrict artifact access and retention instead of recording complete real request bodies.

### 6. Decide Which External Boundary to Exercise

Interception is valuable for controlled errors, slow responses and malformed data, but a mocked payment response cannot establish provider compatibility or actual delivery — keep a separate supported sandbox integration where that contract matters, using the provider's current test values and expiry rules. A page displaying a mocked confirmation does not prove an email arrived.

Browser `page.route` does not intercept requests executed by a server-side component, and service workers can affect interception; choose and document the supported strategy. Adding an Authorization header through a route handler can mask missing credential propagation, so never use that trick while claiming to test authentication. For payments and other writes, a timeout may leave an unknown outcome — test supported idempotency and recovery behavior rather than submitting again blindly.

### 7. Run Every Shard and Match Journeys to Risk

```bash
npx playwright test --shard=1/4 --reporter=blob
# The CI matrix must also run shards 2/4, 3/4 and 4/4.
npx playwright merge-reports --reporter=html ./all-blob-reports
```

CI must install dependencies and browsers, start the application's real test dependencies, run all configured projects and shards, and collect reports even when a shard fails. `fullyParallel` affects test-level distribution; sharding without it groups at file level. Follow the canonical [GitHub Actions chapter](../../../40-platform/40.3-ci-cd/01-ci-platforms/40.3.1.01-github-actions.md) for workflow permissions, current actions, secrets and artifact policy rather than copying an incomplete pipeline here.

Choose journeys from application risk: access denial and tenant separation, creation and recovery of important records, authentication redirects, imports and exports, and supported device behavior. There is no universal 3–10 journey limit. Playwright's `toHaveScreenshot` compares rendered images against an approved baseline with stabilized inputs — it is not a semantic or accessibility test. Retries provide diagnostics for flaky outcomes; they do not explain or repair the failure, so track first-attempt failures separately.

## Summary

E2E tests establish selected journeys across configured layers, not every property of an application. Trace interaction through response and subsequent state, distinguish mocked errors from real integrations, and isolate backend data as well as browser contexts. Real engines, meaningful waits, protected diagnostics and complete shard runs make failures interpretable.

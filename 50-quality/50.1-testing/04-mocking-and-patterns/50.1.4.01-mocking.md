# Mocking

The application builds a receipt and calls its delivery boundary. The test makes that boundary reject — and your logic must expose the failure rather than report delivery. The provider protocol itself needs a separate integration test.

```text
real receipt logic → delivery interface → controlled rejection
          ↓
caller observes failure; no invented “sent” result
```

## Definition

A **test double** replaces a collaborator so a test can control its behavior or observe an interaction. **Mocking** is commonly used as an umbrella term for this practice. The double is part of the test arrangement; its realism and assertions determine which claims a passing test can support.

> **Textbook Definition:** A test double is a substitute for a production collaborator used to control inputs, supply responses or observe interactions. A mock is specifically a double that verifies expected interactions.

## First Principles

A remote service, clock or shared database introduces an input the test does not control. Replace the smallest relevant boundary to make the case repeatable, then exercise your real logic on that controlled input. Every replacement also removes behavior from observation: a fake database cannot establish PostgreSQL constraints, and a successful email stub cannot establish delivery.

## How It Works

### 1. Choose What the Double Must Do

These are roles, not an ordered hierarchy:

| Double | Purpose in the test | Evidence it does not provide |
| ------ | ------------------------------------------------------------ | ------------------------------------------------------ |
| Dummy | Fill an unused argument | Any behavior of that collaborator |
| Stub | Return or reject a controlled value | Remote implementation correctness |
| Spy | Record an interaction, optionally while calling the original | Successful delivery merely because a method was called |
| Mock | Configure/check expected interactions | A real database/provider effect |
| Fake | Run a simplified working implementation | Full equivalence to production semantics |

Libraries use these names differently — `jest.spyOn` calls the original by default until overridden, while a standalone mock function starts without an implementation. Inject an owned interface when it keeps the arrangement explicit; intercept actual HTTP request construction when serialization is the behavior under test. Replacing `fetch` itself suits a narrow unit but excludes the real transport and can miss request-format defects.

### 2. Assert the Delivery Contract With a Typed Dependency

This uses Vitest and a deliberately small owned interface. The token `synthetic-order` identifies fixture data, not a real customer.

```typescript
// receipt.ts
export type Deliver = (receipt: { orderId: string; subject: string }) => Promise<void>;

export async function sendReceipt(orderId: string, deliver: Deliver): Promise<void> {
  await deliver({ orderId, subject: "Order receipt" });
}
```

```typescript
// receipt.test.ts
import { expect, it, vi } from "vitest";
import { sendReceipt, type Deliver } from "./receipt";

it("passes the required receipt to the boundary", async () => {
  const deliver = vi.fn<Deliver>().mockResolvedValue(undefined);
  await sendReceipt("synthetic-order", deliver);
  expect(deliver).toHaveBeenCalledTimes(1);
  expect(deliver).toHaveBeenCalledWith({ orderId: "synthetic-order", subject: "Order receipt" });
});

it("exposes a rejected delivery without inventing success", async () => {
  const deliver = vi.fn<Deliver>().mockRejectedValue(new Error("Provider unavailable"));
  await expect(sendReceipt("synthetic-order", deliver)).rejects.toThrow("Provider unavailable");
});
```

An always-successful mock would miss the second contract. A payment rejection and a timeout with unknown payment outcome are different cases — configure the double to represent the actual contract rather than treating every exception as "nothing happened". Never test only that a mock returns the value you told it to return; apply it to the real consumer and assert that consumer's contract.

### 3. Keep Module Replacement Separate From Type Helpers

The canonical [Jest](../02-frameworks/50.1.2.01-jest.md) and [Vitest](../02-frameworks/50.1.2.02-vitest.md) chapters explain runner APIs. Choose the required operation before copying syntax:

- **`fn` + `mockReturnValue`**: function result — a plain value, not an implicitly awaited operation.
- **`mockResolvedValue` / `mockRejectedValue`**: Promise result — await the caller and the assertion.
- **`mockImplementation`**: actual double behavior — keep it smaller than the implementation under test.
- **`...Once` variants**: one queued call's behavior — check what subsequent calls will do.
- **`spyOn`**: observation or replacement of an existing method — the original can still execute until overridden.
- **Module mock**: imported collaborator implementation — transform, hoisting and CJS/ESM rules differ.
- **`jest.mocked` / `vi.mocked`**: type view only — no runtime replacement.

A class mock can replace methods and constructor behavior, but it does not automatically turn a deeply nested SDK object into a fully configured typed mock. Avoid `as any` casts that conceal missing methods, wrong signatures or invented provider fields. A manual mock under `__mocks__` must follow the runner's module conventions — do not paste a CJS `module.exports` file as native ESM. A fake SQL parser based on `sql.includes("FROM users")` implements no predicates, constraints, types or transactions.

### 4. Intercept the HTTP Request With Modern MSW

Save handlers and server in separate files. Relative URL patterns can match browser requests, but a Node `fetch` caller must construct a URL accepted by its runtime. Replace broad success handlers with assertions on headers and body when those are part of the contract — MSW interception does not verify a real remote provider.

```typescript
// mocks/handlers.ts
import { http, HttpResponse } from "msw";

export const handlers = [
  http.get("*/api/users", () => HttpResponse.json([
    { id: "1", name: "John Doe", email: "john@example.test" },
    { id: "2", name: "Jane Smith", email: "jane@example.test" },
  ])),
  http.get("*/api/users/:id", ({ params }) => {
    if (params.id === "non-existent") {
      return HttpResponse.json({ error: "User not found" }, { status: 404 });
    }
    return HttpResponse.json({ id: params.id, name: "John Doe", email: "john@example.test" });
  }),
  http.post("*/api/users", async ({ request }) => {
    const body: unknown = await request.json();
    if (typeof body !== "object" || body === null ||
        !("name" in body) || typeof body.name !== "string") {
      return HttpResponse.json({ error: "Invalid user" }, { status: 400 });
    }
    return HttpResponse.json({ id: "new-user-id", name: body.name }, { status: 201 });
  }),
];
```

```typescript
// mocks/server.ts
import { setupServer } from "msw/node";
import { handlers } from "./handlers";
export const server = setupServer(...handlers);
```

In the runner's setup file, register `server.listen({ onUnhandledRequest: "error" })` before tests, `server.resetHandlers()` after each test, and `server.close()` afterward. Resetting handlers removes overrides; mutable fixture data needs its own reset. A component test can override only the response boundary being exercised:

```tsx
// UserList.test.tsx — Jest + DOM setup; runner hooks configure server lifecycle
import { render, screen } from "@testing-library/react";
import { http, HttpResponse } from "msw";
import { server } from "./mocks/server";
import { UserList } from "./UserList";

it("shows an HTTP failure", async () => {
  server.use(http.get("*/api/users", () =>
    HttpResponse.json({ error: "Unavailable" }, { status: 500 })));
  render(<UserList />);
  expect(await screen.findByText("Failed to load users")).toBeInTheDocument();
});

it("distinguishes an empty successful result", async () => {
  server.use(http.get("*/api/users", () => HttpResponse.json([])));
  render(<UserList />);
  expect(await screen.findByText("No users found")).toBeInTheDocument();
});
```

For a true network rejection use `HttpResponse.error()` — an HTTP 500 is a received response, not a transport exception. Prefer explicit owned origins over broad wildcards when the test must prove where credentials or requests are sent. See [React Testing Library](../02-frameworks/50.1.2.03-react-testing-library.md) for the canonical render, interact and await behavior trace.

### 5. Control Time and Reset Only the State You Changed

A debounce test needs control over scheduled callbacks: call once, advance short of the delay, call again, advance to the new deadline, and check that only the last arguments reached the callback. State which clock your logic uses first — `setSystemTime` changes the fake wall clock but does not by itself run due timer callbacks. Use the canonical fake-timer example in [Jest](../02-frameworks/50.1.2.01-jest.md) or the bounded retry example in [Vitest](../02-frameworks/50.1.2.02-vitest.md), and restore real timers after each test.

| Cleanup | Clears call history | Resets mock behavior | Restores original method |
| ----------------------------- | ---------------------------------- | ------------------------------------------- | ----------------------------------- |
| mockClear / clearAllMocks | Yes | No | No |
| mockReset / resetAllMocks | Yes | Yes; exact reset behavior depends on runner | No |
| mockRestore / restoreAllMocks | For supported spies/restored mocks | Restore behavior | Yes for supported replacements |
| MSW resetHandlers | Handler overrides | Restores initial handler set | Does not reset mutable fixture data |

Jest and Vitest reset semantics are not identical for functions constructed with an implementation. Creating a fresh mock in a test is often the clearest isolation — not an inefficiency antipattern. `restoreAllMocks` does not rewind external database writes, module singletons, file data or directly assigned globals, and a shared double's configured result can leak even after its call history was cleared.

### 6. Keep Vendor Adapters Honest and Choose Real Dependencies Where Semantics Matter

An owned adapter can stabilize the application's interface while translating current vendor fields. Mock that owned interface for business logic, then verify the actual adapter with request-aware interception and a supported sandbox or contract. A mock cannot establish that `charges.create` accepts `payment_method`, that a status means settlement, or that a receipt reached a mailbox.

Use real PostgreSQL for SQL constraints and concurrent transactions, an actual broker for redelivery and acknowledgment, and real temporary files for filesystem behavior a simple map cannot represent. Use doubles for controlled errors and branch coverage alongside those tests. A hashing claim needs the supported hash and verify implementation — verify the stored value with the real verifier and ensure plaintext is not stored. A guessed prefix such as `hashed_` proves neither algorithm nor parameters. Factories produce fixtures; their canonical use is covered in [Test Patterns](50.1.4.02-test-patterns.md).

## Summary

A double controls or observes a boundary; it does not inherit the evidence of the behavior it replaced. Choose the role from the test's contract, exercise the real consumer, and distinguish HTTP responses from transport failures. Control time with the matching tool, reset both the double and any separate mutable fixture state, and verify adapters and semantic dependencies against their real counterparts.

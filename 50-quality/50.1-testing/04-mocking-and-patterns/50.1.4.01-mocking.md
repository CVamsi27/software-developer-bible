# Mocking

## Definition

**A test double** replaces a collaborator so a test can control its behavior or observe an interaction. Mocking is commonly used as an umbrella term for this practice. The double is part of the test arrangement; its realism and assertions determine which claims a passing test can support.

> **Textbook Definition:** A test double is a substitute for a production collaborator used to control inputs, supply responses or observe interactions. A mock is specifically a double that verifies expected interactions.

## First Principles

A remote service, clock or shared database can introduce an input that the test does not control. Replace the smallest relevant boundary to make the case repeatable, then exercise your real logic on that controlled input. Every replacement also removes behavior from observation: a fake database cannot establish PostgreSQL constraints, and a successful email stub cannot establish delivery.

## Trace a Receipt That the Provider Rejects

The application builds a receipt and calls its delivery boundary. The test makes that boundary reject. Your logic should expose the failure rather than report delivery; the provider protocol itself requires a separate integration test.

```text
real receipt logic → delivery interface → controlled rejection
          ↓
caller observes failure; no invented “sent” result
```

Inject an owned interface when it keeps this arrangement explicit. Intercept actual HTTP request construction when serialization is the behavior you need to exercise. Replacing fetch itself can be useful for a narrow unit; it is not automatically wrong, but it excludes the real transport and can miss request-format defects.

## Choose What the Double Must Do

These are roles, not an ordered hierarchy:

| Double | Purpose in the test | Evidence it does not provide |
| ------ | ------------------------------------------------------------ | ------------------------------------------------------ |
| Dummy | Fill an unused argument | Any behavior of that collaborator |
| Stub | Return or reject a controlled value | Remote implementation correctness |
| Spy | Record an interaction, optionally while calling the original | Successful delivery merely because a method was called |
| Mock | Configure/check expected interactions | A real database/provider effect |
| Fake | Run a simplified working implementation | Full equivalence to production semantics |

Libraries use these names differently. For example, jest.spyOn calls the original by default until overridden, while a standalone mock function usually starts without an implementation. Explain what it actually executes rather than relying on the label.

## Code Examples

### Assert the Delivery Contract With a Typed Dependency

Save these as separate files. This uses Vitest and a deliberately small owned interface. The token synthetic-order identifies fixture data, not a real customer.

```typescript
// receipt.ts
export type Deliver = (receipt: { orderId: string; subject: string }) => Promise<void>;

export async function sendReceipt(orderId: string, deliver: Deliver): Promise<void> {
  await deliver({ orderId, subject: "Order receipt" });
}
```

```typescript
// receipt.test.ts
import { expect, it, vi } from "vitest";
import { sendReceipt, type Deliver } from "./receipt";

it("passes the required receipt to the boundary", async () => {
  const deliver = vi.fn<Deliver>().mockResolvedValue(undefined);
  await sendReceipt("synthetic-order", deliver);
  expect(deliver).toHaveBeenCalledTimes(1);
  expect(deliver).toHaveBeenCalledWith({ orderId: "synthetic-order", subject: "Order receipt" });
});

it("exposes a rejected delivery without inventing success", async () => {
  const deliver = vi.fn<Deliver>().mockRejectedValue(new Error("Provider unavailable"));
  await expect(sendReceipt("synthetic-order", deliver)).rejects.toThrow("Provider unavailable");
});
```

An always-successful mock would miss the second contract. Add application-specific assertions on forbidden side effects when the surrounding workflow owns them. A payment rejection and a timeout with unknown payment outcome are different cases; configure the double to represent the actual contract rather than treating every exception as “nothing happened”.

### Keep Module Replacement Separate From Type Helpers

The canonical [Jest](../02-frameworks/50.1.2.01-jest.md) and [Vitest](../02-frameworks/50.1.2.02-vitest.md) chapters explain runner APIs and executable examples. Use this table to choose the required operation before copying syntax:

| Operation | What it changes | Detail to preserve |
| ------------------------------------- | --------------------------------------- | -------------------------------------------------- |
| fn + mockReturnValue | Function result | Plain value, not an implicitly awaited operation |
| mockResolvedValue / mockRejectedValue | Promise result | Await the caller/assertion |
| mockImplementation | Actual double behavior | Keep it smaller than the implementation under test |
| …Once variant | One queued call behavior | Check what subsequent calls will do |
| spyOn | Existing method observation/replacement | Original can still execute until overridden |
| module mock | Imported collaborator implementation | Transform/hoisting and CJS/ESM rules differ |
| jest.mocked / vi.mocked | Type view | Does not perform runtime replacement |

Do not test only that a mock returns the value you told it to return. Apply it to the real consumer and assert that consumer's contract. A class mock can replace methods/constructor behavior, but it does not automatically turn a deeply nested SDK object into a fully configured typed mock. Avoid as-any casts that conceal missing methods, wrong signatures or invented provider fields.

A manual mock under `__mocks__` must follow the runner's module conventions and be activated as required. Do not paste a CJS module.exports file as native ESM. If a fake file store supports empty files, test presence with Map.has or an own-property check; testing content truthiness incorrectly treats an empty string as missing. A fake SQL parser based on sql.includes("FROM users") does not implement predicates, constraints, types or transactions.

### Intercept the HTTP Request With Modern MSW

Save the handlers and server in separate files. Relative URL patterns can match browser requests, but a Node fetch caller must construct a URL accepted by its runtime. Replace broad success handlers with assertions on headers/body when those are part of the contract. MSW interception does not verify a real remote provider.

```typescript
// mocks/handlers.ts
import { http, HttpResponse } from "msw";

export const handlers = [
  http.get("*/api/users", () => HttpResponse.json([
    { id: "1", name: "John Doe", email: "john@example.test" },
    { id: "2", name: "Jane Smith", email: "jane@example.test" },
  ])),
  http.get("*/api/users/:id", ({ params }) => {
    if (params.id === "non-existent") {
      return HttpResponse.json({ error: "User not found" }, { status: 404 });
    }
    return HttpResponse.json({ id: params.id, name: "John Doe", email: "john@example.test" });
  }),
  http.post("*/api/users", async ({ request }) => {
    const body: unknown = await request.json();
    if (typeof body !== "object" || body === null ||
        !("name" in body) || typeof body.name !== "string") {
      return HttpResponse.json({ error: "Invalid user" }, { status: 400 });
    }
    return HttpResponse.json({ id: "new-user-id", name: body.name }, { status: 201 });
  }),
];
```

```typescript
// mocks/server.ts
import { setupServer } from "msw/node";
import { handlers } from "./handlers";
export const server = setupServer(...handlers);
```

In the runner's setup file, register `server.listen({ onUnhandledRequest: "error" })` before tests, `server.resetHandlers()` after each test and `server.close()` afterward. Resetting handlers removes overrides; mutable fixture data requires its own reset. Do not call an always-successful POST handler a real persistence test.

A component test can override only the response boundary being exercised. This assumes the actual UserList component displays the documented error/empty states; retain its real request code:

```tsx
// UserList.test.tsx — Jest + DOM setup; runner hooks configure server lifecycle
import { render, screen } from "@testing-library/react";
import { http, HttpResponse } from "msw";
import { server } from "./mocks/server";
import { UserList } from "./UserList";

it("shows an HTTP failure", async () => {
  server.use(http.get("*/api/users", () =>
    HttpResponse.json({ error: "Unavailable" }, { status: 500 })));
  render(<UserList />);
  expect(await screen.findByText("Failed to load users")).toBeInTheDocument();
});

it("distinguishes an empty successful result", async () => {
  server.use(http.get("*/api/users", () => HttpResponse.json([])));
  render(<UserList />);
  expect(await screen.findByText("No users found")).toBeInTheDocument();
});
```

For a true network rejection, use `HttpResponse.error()`; an HTTP 500 is a received response, not a transport exception. Prefer explicit owned origins over broad wildcard patterns when the test must prove where credentials or requests are sent. See [React Testing Library](../02-frameworks/50.1.2.03-react-testing-library.md) for the canonical render/interact/await behavior trace.

## Control Time Without Confusing Timers and Wall Time

A debounce test needs control over scheduled callbacks: call once, advance short of the delay, call again, advance to the new deadline, and check that only the last arguments reached the callback. An expiration test may instead need wall-clock control. State which clock your logic uses before choosing a tool.

Use the canonical fake-timer example in [Jest](../02-frameworks/50.1.2.01-jest.md) or bounded retry example in [Vitest](../02-frameworks/50.1.2.02-vitest.md). Async timer advancement is useful when callbacks also schedule promise work. Restore real timers after each test, including failures; some user-event interactions need an advanceTimers option when using fake timers.

setSystemTime changes the fake wall clock; it does not by itself run due timer callbacks. Assert an ISO timestamp or UTC fields for a UTC requirement: new Date(...Z).getHours() uses the machine's local timezone and can fail on another runner. Use ReturnType<typeof setTimeout> when a timer type must work across the chosen environment rather than assuming every browser returns NodeJS.Timeout.

## Reset the State You Actually Changed

| Cleanup | Clears call history | Resets mock behavior | Restores original method |
| ----------------------------- | ---------------------------------- | ------------------------------------------- | ----------------------------------- |
| mockClear / clearAllMocks | Yes | No | No |
| mockReset / resetAllMocks | Yes | Yes; exact reset behavior depends on runner | No |
| mockRestore / restoreAllMocks | For supported spies/restored mocks | Restore behavior | Yes for supported replacements |
| MSW resetHandlers | Handler overrides | Restores initial handler set | Does not reset mutable fixture data |

Jest and Vitest reset semantics are not identical for functions constructed with an implementation. Check the installed runner's API and use fresh per-test doubles where that makes ownership clearer. restoreAllMocks does not rewind external database writes, module singletons, file data or a global variable assigned directly. A shared double's configured result can leak even after its call history was cleared.

Creating a fresh mock in a test is often the clearest isolation; it is not intrinsically an inefficient antipattern. Optimize measured setup cost, and avoid a global beforeAll clear as a substitute for per-test state control. Modules with import-time state may require supported reset/isolation APIs and deliberate import ordering.

## Real-World Decisions

### Keep a Vendor Adapter Honest

An owned adapter can stabilize the application's interface while translating current vendor fields. Mock that owned interface for business logic, then verify the actual adapter with request-aware interception and a supported sandbox/contract. A mock cannot establish that charges.create accepts payment_method, that a status means settlement, or that a receipt reached a mailbox.

### Choose a Real Dependency When Its Semantics Matter

Use real PostgreSQL for SQL constraints/concurrent transactions, an actual broker for redelivery and acknowledgment, and real temporary files for filesystem behavior that a simple map cannot represent. Use doubles for controlled errors and branch coverage alongside those tests. Factories produce fixtures; they are not automatically collaborators or delivery mocks. Their canonical use is covered in [Test Patterns](50.1.4.02-test-patterns.md).

## Common Mistakes

| Mistake | Why the test misleads | Correction |
| -------------------------------------------------- | -------------------------------------------------- | --------------------------------------------------------------- |
| Mock a private helper and assert its call sequence | Refactoring changes a passing behavior's test | Assert the unit result and owned boundary effect |
| Return success for any HTTP body | Malformed requests still pass | Match method/origin and validate important fields |
| Treat HTTP 500 as a transport exception | Response handling and catch handling differ | Exercise both response rejection and network rejection |
| Clear calls while keeping an old configured result | Tests inherit hidden behavior | Reset deliberately or create fresh doubles |
| Assert password starts with hashed_ | A fake prefix can satisfy the test without hashing | Use the real supported verifier and assert no plaintext storage |
| Mock every component in an integration test | The composition itself disappears | Declare and retain the seam being exercised |

## Best Practices

Make the chosen replacement and its excluded behavior visible in the test. Use typed owned interfaces, fresh fixture state, awaited failure assertions and request-aware HTTP handlers. Keep runner-specific module/timer mechanics in their canonical chapters and pair controlled doubles with targeted real integration evidence.

## Summary

A double controls or observes a boundary; it does not inherit the evidence of the behavior it replaced. Choose the role from the test's contract, exercise the real consumer, distinguish HTTP responses from transport failures, and reset both the double and any separate mutable fixture state.

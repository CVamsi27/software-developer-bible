# Test Patterns

## Definition

**Test patterns** are reusable arrangements that make setup, execution, observation and cleanup understandable. Choose a pattern to solve a real test-maintenance problem: unclear scenarios, duplicated irrelevant data, leaked resources or assertions that fail for the wrong reason.

> **Textbook Definition:** A test pattern is a reusable arrangement of setup, execution and observation that solves a recurring testing problem while keeping the intended behavior and failure diagnosis explicit.

A test for “two books cost 2,500 cents” should make those facts visible. If the reader must inspect a shared factory's VIP status, current time and hidden discount settings to understand the expected total, reuse has obscured the contract.

## First Principles

A test's result depends on its initial state, action and observations. Hidden defaults or mutable shared state can change the result without changing the behavior under test. Repeated setup also creates several places to update when a data contract changes.

Patterns trade those costs against another cost: indirection. A useful helper hides irrelevant repetition while leaving the scenario and expected outcome visible. More abstractions or fewer assertions do not automatically make a test better.

## Give one scenario an observable contract

**Arrange–Act–Assert (AAA)** names setup, the behavior under test and its checks. **Given–When–Then** describes the precondition, event and expected outcome in business language. The two are compatible ways to describe a case; using those words alone does not establish behavior-driven development's collaboration process.

The **four-phase test** adds explicit teardown: setup → exercise → verify → cleanup. Test-runner hooks can schedule cleanup after a failure, but they do not automatically roll back database writes, restore replaced globals or close resources you created. Associate each resource with a cleanup owner and await asynchronous setup and teardown.

## Code Examples

### A complete cart contract and focused cases

Save the following as `cart.ts`. This illustrative contract uses nonnegative integer cents and positive integer quantities. It excludes currency conversion, discounts, persistence and checkout side effects.

```typescript
export type Line = { sku: string; unitPriceCents: number; quantity: number };

export function totalCents(lines: readonly Line[]): number {
  let total = 0;
  for (const line of lines) {
    if (!Number.isSafeInteger(line.unitPriceCents) || line.unitPriceCents < 0 ||
        !Number.isSafeInteger(line.quantity) || line.quantity <= 0) {
      throw new RangeError('Invalid price or quantity');
    }
    const subtotal = line.unitPriceCents * line.quantity;
    if (!Number.isSafeInteger(subtotal) || !Number.isSafeInteger(total + subtotal)) {
      throw new RangeError('Total exceeds safe integer range');
    }
    total += subtotal;
  }
  return total;
}

export function makeLine(overrides: Partial<Line> = {}): Line {
  return { sku: 'book-1', unitPriceCents: 1250, quantity: 1, ...overrides };
}

export class CartBuilder {
  private lines: Line[] = [];
  add(line: Line): this {
    this.lines.push({ ...line });
    return this;
  }
  build(): Line[] {
    return this.lines.map(line => ({ ...line }));
  }
}
```

A **factory** such as `makeLine` creates a fresh object with defaults and explicit overrides. It need not use a global counter or wall-clock timestamp. It is also allowed to create an invalid input intentionally for a rejection test; the production contract remains the validation authority.

A **builder** records several construction steps and returns a snapshot. Here, `add` copies the caller's line, and `build` copies the accumulated lines again. Since every field is a primitive, those copies isolate the shown state. Nested objects would require a defined copying/ownership contract. A `Partial<T> as T` cast would merely hide missing fields.

Save these tests as `cart.test.ts` and run them with Vitest:

```typescript
import { expect, it } from 'vitest';
import { CartBuilder, makeLine, totalCents } from './cart';

it('charges 2,500 cents for two books', () => {
  const lines = [makeLine({ quantity: 2 })]; // Arrange / Given
  const total = totalCents(lines);           // Act / When
  expect(total).toBe(2500);                  // Assert / Then
});

it.each([
  { name: 'empty cart', lines: [], expected: 0 },
  { name: 'free sample', lines: [makeLine({ unitPriceCents: 0 })], expected: 0 },
  { name: 'three pens', lines: [makeLine({ sku: 'pen-1', unitPriceCents: 75, quantity: 3 })], expected: 225 },
])('$name has the stated total', ({ lines, expected }) => {
  expect(totalCents(lines)).toBe(expected);
});

it.each([
  { quantity: 0 }, { quantity: 1.5 }, { unitPriceCents: -1 },
  { unitPriceCents: NaN }, { unitPriceCents: Number.MAX_SAFE_INTEGER, quantity: 2 },
])('rejects invalid or overflowing input %j without mutation', overrides => {
  const lines = [makeLine(overrides)];
  const before = lines.map(line => ({ ...line }));
  expect(() => totalCents(lines)).toThrow(RangeError);
  expect(lines).toEqual(before);
});

it('keeps each builder result independent of caller mutations', () => {
  const input = makeLine();
  const builder = new CartBuilder().add(input);
  input.quantity = 99;
  const first = builder.build();
  first[0].quantity = 50;
  expect(builder.build()[0].quantity).toBe(1);
});
```

The first case shows one action and its result. The rejection case uses two assertions for **one contract**: invalid input is rejected without mutation. Counting assertions cannot decide whether a test is focused; group observations that define the same behavior and separate unrelated scenarios.

**Parameterized tests** run the same contract over named cases. The expected values above are independent examples of the pricing rule, not values computed by calling the same function in the arrangement. Choose boundary and failure cases deliberately; ten copies of the same easy case add little confidence.

## Fixtures and named presets have different jobs

A **fixture** is the initial test environment or state: data, collaborators, clocks, files or a database arrangement. A factory may create part of that fixture. They are not competing patterns, and “factory rather than fixture” is not a general rule.

An **object mother** supplies named familiar scenarios, such as a free sample or a two-book cart. Returning fresh data lets a test adjust a scenario without corrupting the next test. Defaults still matter: if a shared preset silently becomes a VIP order, unrelated expected totals may change. Keep consequential fields visible and avoid a central preset with dozens of unrelated options.

For real integrations, isolation includes the resource namespace and ownership, not merely fresh JavaScript objects. A cleanup query that deletes every `fixture-user-%` record can erase another worker's data. Use the integration chapter's isolated schema or exact per-test ownership strategy; test hooks alone do not establish that boundary.

## Generate cases when a general relationship matters

**Property-based testing** generates inputs and checks a relationship over them. `fast-check` can reduce a failing input to a smaller counterexample, called **shrinking**, and report replay information. This complements named business cases; a property such as “totals are nonnegative” would still pass an implementation that always returns zero.

Install a reviewed fast-check version in the test project. Save the next example as `cart.property.test.ts` beside the two files above:

```typescript
import { expect, it } from 'vitest';
import fc from 'fast-check';
import { totalCents } from './cart';

it('preserves total when lines are reordered, without mutating input', () => {
  const line = fc.record({
    sku: fc.constantFrom('book-1', 'pen-1'),
    unitPriceCents: fc.integer({ min: 0, max: 10_000 }),
    quantity: fc.integer({ min: 1, max: 10 }),
  });
  fc.assert(fc.property(fc.array(line, { maxLength: 20 }), lines => {
    const snapshot = lines.map(item => ({ ...item }));
    expect(totalCents([...lines].reverse())).toBe(totalCents(lines));
    expect(lines).toEqual(snapshot);
  }), { seed: 20261008, numRuns: 100 });
});
```

The generator bounds guarantee the arithmetic stays within the example's valid range. The fixed seed and recorded version aid replay; a changed generator or package version can change the sequence. Keep the failure's reported seed and path when diagnosing a regression. A generated search checks sampled cases, not every possible input or production correctness.

For stateful logic, generate or enumerate **transitions**, not only end states. A shipment test must first confirm the order through the supported API before shipping it. Also check that attempting shipment from pending is rejected and leaves pending unchanged. If setup writes private state directly, it can bypass the invariant the test is supposed to exercise.

## Keep helpers and snapshots subordinate to the behavior

A render helper can install the real theme, routing and authentication providers for component tests while the case explicitly chooses the role and route. Avoid a helper that pre-stubs the component's whole behavior or hides shared state. Restore global history or injected configuration when a test changes it.

A **page object** groups UI actions and locators, such as `checkout()` using an accessible button. The test should still state the user outcome, such as a receipt with the expected total. A helper that silently handles every modal or ignores failed navigation can make a broken journey pass.

A **snapshot** compares a serialized result with a reviewed stored value. It can detect an unexpected structure change, but approving an update is a correctness decision, not maintenance housekeeping. Keep snapshots small, remove irrelevant changing fields deliberately and retain explicit assertions for important behavior. A DOM snapshot is not a visual layout, keyboard or screen-reader test.

To assess an assertion's strength, ask whether changing a meaningful rule would fail it. Replacing multiplication with addition in `totalCents` must fail the two-book case; a weak nonnegative property might survive. The [testing overview](../01-foundations/50.1.1.01-testing-overview.md) owns coverage and mutation-testing interpretation; use that evidence to investigate missing checks rather than chasing a score alone.

## Real-World Decisions

Inline a small setup when it makes the scenario clearer. Introduce a factory for repeated irrelevant defaults, a builder for a useful multi-step construction, a named preset for a stable domain scenario and a shared resource fixture when its lifecycle is genuinely expensive. Measure setup cost before sharing mutable state across tests.

Keep clocks, IDs and unique database keys deterministic or explicitly namespaced. `Date.now()` is not a uniqueness guarantee, especially under fake time or parallel execution. A fake service needs its own contract checks; it does not inherit the real provider's behavior because its class name resembles the SDK.

## Common Mistakes

- Calling setup a hierarchy of superior patterns instead of identifying the problem it solves.
- Returning a builder's mutable internal object or concealing incomplete data with a type cast.
- Expecting automatic cleanup of database records, files, timers or replaced globals.
- Computing an expected result with the same implementation being tested.
- Blindly updating snapshots or interpreting a generated invariant as a proof of all behavior.
- Replacing a failure assertion with a smaller assertion count while losing the state invariant.

## Best Practices

Make the important inputs, action and expected result visible. Keep defaults fresh and deterministic, separate resource ownership from object construction, and use named cases alongside generated relationships. Helpers should reduce repetition without hiding the behavior or the evidence boundary.

## Summary

Test patterns organize a contract and its state. Factories create data, builders isolate construction, fixtures own setup and cleanup, and parameterized or generated cases vary the inputs. Preserve clear expected outcomes, mutation boundaries and resource ownership so reuse strengthens the test rather than making a passing result harder to interpret.

# Test Patterns

A test for "two books cost 2,500 cents" should make those facts visible. If the reader must inspect a shared factory's VIP status, current time and hidden discount settings to understand the expected total, reuse has obscured the contract.

```typescript
import { makeLine, totalCents } from './cart';

const lines = [makeLine({ quantity: 2 })]; // Arrange: two books, visible facts
const total = totalCents(lines);            // Act
expect(total).toBe(2500);                   // Assert
```

## Definition

**Test patterns** are reusable arrangements that make setup, execution, observation and cleanup understandable. Choose a pattern to solve a real test-maintenance problem: unclear scenarios, duplicated irrelevant data, leaked resources, or assertions that fail for the wrong reason.

> **Textbook Definition:** A test pattern is a reusable arrangement of setup, execution and observation that solves a recurring testing problem while keeping the intended behavior and failure diagnosis explicit.

## First Principles

A test's result depends on its initial state, action and observations. Hidden defaults or mutable shared state can change the result without changing the behavior under test, while repeated setup creates several places to update when a data contract changes. Patterns trade those costs against indirection: a useful helper hides irrelevant repetition while leaving the scenario and expected outcome visible.

## How It Works

### 1. Give One Scenario an Observable Contract

**Arrange–Act–Assert (AAA)** names setup, the behavior under test and its checks. **Given–When–Then** describes the precondition, event and expected outcome in business language. The two are compatible ways to describe a case; using those words alone does not establish behavior-driven development's collaboration process.

The **four-phase test** adds explicit teardown: setup → exercise → verify → cleanup. Runner hooks can schedule cleanup after a failure, but they do not automatically roll back database writes, restore replaced globals or close resources you created. Associate each resource with a cleanup owner, and await asynchronous setup and teardown.

### 2. Write a Complete Cart Contract and Focused Cases

Save the following as `cart.ts`. This illustrative contract uses nonnegative integer cents and positive integer quantities. It excludes currency conversion, discounts, persistence and checkout side effects.

```typescript
export type Line = { sku: string; unitPriceCents: number; quantity: number };

export function totalCents(lines: readonly Line[]): number {
  let total = 0;
  for (const line of lines) {
    if (!Number.isSafeInteger(line.unitPriceCents) || line.unitPriceCents < 0 ||
        !Number.isSafeInteger(line.quantity) || line.quantity <= 0) {
      throw new RangeError('Invalid price or quantity');
    }
    const subtotal = line.unitPriceCents * line.quantity;
    if (!Number.isSafeInteger(subtotal) || !Number.isSafeInteger(total + subtotal)) {
      throw new RangeError('Total exceeds safe integer range');
    }
    total += subtotal;
  }
  return total;
}

export function makeLine(overrides: Partial<Line> = {}): Line {
  return { sku: 'book-1', unitPriceCents: 1250, quantity: 1, ...overrides };
}

export class CartBuilder {
  private lines: Line[] = [];
  add(line: Line): this {
    this.lines.push({ ...line });
    return this;
  }
  build(): Line[] {
    return this.lines.map(line => ({ ...line }));
  }
}
```

A **factory** such as `makeLine` creates a fresh object with defaults and explicit overrides — no global counter or wall-clock timestamp required. It may intentionally create an invalid input for a rejection test; the production contract remains the validation authority. A **builder** records construction steps and returns a snapshot: `add` copies the caller's line, `build` copies the accumulated lines. A `Partial<T> as T` cast would merely hide missing fields.

Save these tests as `cart.test.ts` and run them with Vitest:

```typescript
import { expect, it } from 'vitest';
import { CartBuilder, makeLine, totalCents } from './cart';

it('charges 2,500 cents for two books', () => {
  const lines = [makeLine({ quantity: 2 })]; // Arrange / Given
  const total = totalCents(lines);           // Act / When
  expect(total).toBe(2500);                  // Assert / Then
});

it.each([
  { name: 'empty cart', lines: [], expected: 0 },
  { name: 'free sample', lines: [makeLine({ unitPriceCents: 0 })], expected: 0 },
  { name: 'three pens', lines: [makeLine({ sku: 'pen-1', unitPriceCents: 75, quantity: 3 })], expected: 225 },
])('$name has the stated total', ({ lines, expected }) => {
  expect(totalCents(lines)).toBe(expected);
});

it.each([
  { quantity: 0 }, { quantity: 1.5 }, { unitPriceCents: -1 },
  { unitPriceCents: NaN }, { unitPriceCents: Number.MAX_SAFE_INTEGER, quantity: 2 },
])('rejects invalid or overflowing input %j without mutation', overrides => {
  const lines = [makeLine(overrides)];
  const before = lines.map(line => ({ ...line }));
  expect(() => totalCents(lines)).toThrow(RangeError);
  expect(lines).toEqual(before);
});

it('keeps each builder result independent of caller mutations', () => {
  const input = makeLine();
  const builder = new CartBuilder().add(input);
  input.quantity = 99;
  const first = builder.build();
  first[0].quantity = 50;
  expect(builder.build()[0].quantity).toBe(1);
});
```

The rejection case uses two assertions for **one contract**: invalid input is rejected without mutation. Counting assertions cannot decide whether a test is focused — group observations that define the same behavior and separate unrelated scenarios. **Parameterized tests** run the same contract over named cases whose expected values are independent examples of the rule, never values computed by calling the function in arrangement.

### 3. Give Fixtures and Named Presets Different Jobs

A **fixture** is the initial test environment or state: data, collaborators, clocks, files or a database arrangement. A factory may create part of that fixture — they are not competing patterns, and "factory rather than fixture" is not a general rule. An **object mother** supplies named familiar scenarios, such as a free sample or a two-book cart, returning fresh data so a test can adjust a scenario without corrupting the next test.

Defaults still matter: if a shared preset silently becomes a VIP order, unrelated expected totals change. Keep consequential fields visible and avoid a central preset with dozens of unrelated options. For real integrations, isolation includes the resource namespace and ownership — a cleanup query deleting every `fixture-user-%` record can erase another worker's data. Use the integration chapter's isolated schema or exact per-test ownership strategy.

### 4. Generate Cases When a General Relationship Matters

**Property-based testing** generates inputs and checks a relationship over them. `fast-check` reduces a failing input to a smaller counterexample (**shrinking**) and reports replay information. This complements named business cases: a property such as "totals are nonnegative" would still pass an implementation that always returns zero. Install a reviewed fast-check version, and save this as `cart.property.test.ts`:

```typescript
import { expect, it } from 'vitest';
import fc from 'fast-check';
import { totalCents } from './cart';

it('preserves total when lines are reordered, without mutating input', () => {
  const line = fc.record({
    sku: fc.constantFrom('book-1', 'pen-1'),
    unitPriceCents: fc.integer({ min: 0, max: 10_000 }),
    quantity: fc.integer({ min: 1, max: 10 }),
  });
  fc.assert(fc.property(fc.array(line, { maxLength: 20 }), lines => {
    const snapshot = lines.map(item => ({ ...item }));
    expect(totalCents([...lines].reverse())).toBe(totalCents(lines));
    expect(lines).toEqual(snapshot);
  }), { seed: 20261008, numRuns: 100 });
});
```

The generator bounds keep arithmetic within the valid range. A fixed seed and lockfile-pinned version aid replay; changing either can change the sequence, so keep the failure's reported seed and path when diagnosing a regression. For stateful logic, generate **transitions**, not only end states: a shipment test must confirm the order through the supported API first, reject shipment from pending, and leave pending unchanged. Setup that writes private state directly can bypass the invariant under test.

### 5. Keep Helpers and Snapshots Subordinate to the Behavior

A render helper can install the real theme, routing and authentication providers while the case explicitly chooses role and route — but never pre-stub the component's whole behavior or hide shared state. A **page object** groups UI actions and locators, yet the test must still state the user outcome, such as a receipt with the expected total. A helper that silently handles every modal or ignores failed navigation makes a broken journey pass.

A **snapshot** compares a serialized result with a reviewed stored value. Approving an update is a correctness decision, not housekeeping: keep snapshots small, remove irrelevant changing fields deliberately, and retain explicit assertions for important behavior. To assess an assertion's strength, ask whether changing a meaningful rule would fail it — replacing multiplication with addition in `totalCents` must fail the two-book case.

Inline a small setup when it makes the scenario clearer; introduce a factory for repeated irrelevant defaults, a builder for multi-step construction, a named preset for a stable domain scenario, and a shared resource fixture only when its lifecycle is genuinely expensive. Keep clocks, IDs and unique database keys deterministic or explicitly namespaced — `Date.now()` is not a uniqueness guarantee under fake time or parallel execution.

## Summary

Test patterns organize a contract and its state: factories create data, builders isolate construction, fixtures own setup and cleanup, and parameterized or generated cases vary the inputs. Preserve clear expected outcomes, mutation boundaries and resource ownership so reuse strengthens the test. Keep helpers and snapshots subordinate to the behavior they are meant to expose.

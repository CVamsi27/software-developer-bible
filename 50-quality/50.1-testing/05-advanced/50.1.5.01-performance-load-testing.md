# Performance & Load Testing

A booking service handles 1,000 lightweight availability reads per second yet fails at a far smaller rate of contended writes. "It handles 1,000 requests" is incomplete without the operation mix, dataset, environment and acceptance criteria — and a fast response from a tiny warm fixture is evidence about that fixture, not the production population.

```javascript
// k6 thresholds: the run fails unless the contract holds.
thresholds: {
  semantic_failures: ['rate==0'],
  http_req_failed: ['rate==0'],
  http_req_duration: ['p(95)<200'],
  dropped_iterations: ['count==0'],
},
```

## Definition

**Performance testing** measures a system's **latency**, **throughput**, resource consumption and stability under a specified **workload**. The workload includes how work arrives, which operations it performs, its data shape and how long it runs.

> **Textbook Definition:** Performance testing measures a system's latency, throughput, resource use and stability under a specified workload. Load, stress, spike and endurance tests vary the workload magnitude or its distribution over time.

## First Principles

Every operation consumes limited resources for some time. When incoming work exceeds the service rate of a bottleneck, a queue grows or work is rejected — and measuring only completed requests misses the waiting or dropped work users experience. A useful test therefore controls incoming demand, observes completed *and* failed work, and identifies where resources or queues constrain the result.

## 1. Choose the Workload Shape From the Question

| Test | What changes | Question to answer |
| -------------- | -------------------------------------------------- | ------------------------------------------------------------------------ |
| Load | Representative expected demand and operation mix | Do required outcomes hold at the forecast load? |
| Stress | Increase demand beyond the expected range | Where does saturation occur, and how does the service reject or recover? |
| Spike | Change arrival rate quickly | Can queues and scaling react within the tolerated impact window? |
| Soak/endurance | Hold a representative workload for a longer period | Do memory, connections, buffers or scheduled jobs accumulate problems? |

No fixed duration or universal acceptable failure rate applies to every service. State which measurements constitute success, which impact stops the test, and which background conditions matter. Test cold starts and warm steady state separately when both are relevant rather than excluding one automatically.

## 2. Explain the Load Model Before Selecting a Tool

In a **closed model**, each simulated user waits for its operation, possibly thinks, then sends more work. If 100 users each spend 0.2 seconds waiting and 0.8 seconds thinking, the approximate cycle rate is 100 operations per second — and if waiting rises to 1.2 seconds, the same users generate roughly 50 per second. The slower service reduces the offered load.

An **open arrival model** schedules new operations at a stated rate independent of earlier completion. The generator still needs enough execution capacity: if it cannot start scheduled work, record the dropped arrivals rather than interpreting reduced delivered load as success. A bounded population of interactive clients fits a closed model; independent external arrivals such as webhooks often fit an open model.

For a stable population, **Little's Law** relates average in-flight work to average throughput times average time in the system: at 100 completed operations per second and a mean end-to-end time of 0.25 seconds, average in-flight work is 25 operations. This is not `p99 latency × total registered users`, and it does not describe an indefinitely growing overload queue. A connection pool bounds one resource, not necessarily all requests waiting outside it.

## 3. Trace a Complete Local k6 Test

The example checks a read-only catalog fixture. It schedules five iterations per second for two seconds; each iteration sends one request, and every response contributes to the semantic failure rate. Start a local fixture in one terminal:

```python
# catalog_fixture.py
import json
from http.server import BaseHTTPRequestHandler, ThreadingHTTPServer

class Catalog(BaseHTTPRequestHandler):
    def do_GET(self):
        if self.path != '/api/catalog':
            self.send_error(404)
            return
        body = json.dumps({'items': [{'id': 'book-1', 'priceCents': 1250}]}).encode()
        self.send_response(200)
        self.send_header('Content-Type', 'application/json')
        self.send_header('Content-Length', str(len(body)))
        self.end_headers()
        self.wfile.write(body)

    def log_message(self, *_args):
        pass

ThreadingHTTPServer(('127.0.0.1', 18082), Catalog).serve_forever()
```

Save the next script as `catalog_load.js`. Install a reviewed k6 release for your platform; k6 runs this script in its own runtime, not Node.js.

```javascript
import http from 'k6/http';
import { check } from 'k6';
import { Rate } from 'k6/metrics';

const semanticFailures = new Rate('semantic_failures');
const rate = Number(__ENV.RATE || '5');
if (!Number.isSafeInteger(rate) || rate <= 0) throw new Error('RATE must be positive');
const baseUrl = (__ENV.BASE_URL || 'http://127.0.0.1:18082').replace(/\/$/, '');

export const options = {
  scenarios: {
    catalog_reads: {
      executor: 'constant-arrival-rate',
      rate,
      timeUnit: '1s',
      duration: __ENV.DURATION || '2s',
      preAllocatedVUs: 20,
      maxVUs: 100,
      gracefulStop: '5s',
    },
  },
  thresholds: {
    semantic_failures: ['rate==0'],
    http_req_failed: ['rate==0'],
    http_req_duration: ['p(95)<200'],
    dropped_iterations: ['count==0'],
  },
};

export default function () {
  const response = http.get(`${baseUrl}/api/catalog`, { timeout: '2s' });
  let body = null;
  try { body = response.json(); } catch { /* Invalid JSON is a failed contract. */ }
  const good = check(response, {
    'status is 200': r => r.status === 200,
    'expected item and exact price': () =>
      Array.isArray(body?.items) && body.items.length === 1 &&
      body.items[0].id === 'book-1' && body.items[0].priceCents === 1250,
  });
  semanticFailures.add(!good);
}
```

Run it against that fixture:

```bash
python3 catalog_fixture.py
# In another terminal:
k6 run catalog_load.js
```

A failed `check` is recorded but does not automatically fail the process. The custom `semantic_failures` Rate makes the combined status and payload result thresholdable — k6's built-in `checks` metric cannot itself be used in a threshold — so an HTTP 200 with the wrong price fails the run even though `http_req_failed` remains zero. Adding only failures to the Rate would make its denominator the failures themselves. This short run validates wiring and the local contract; its small sample cannot establish a production p99 or capacity limit.

## 4. Interpret the Curve and the Evidence

Capture configured arrival rate, achieved starts and completions, dropped iterations, failures, latency distribution and generator resource use. Correlate them with the system's CPU, memory, connection waits, database locks, queue age, dependency quotas and replica state.

For a **hypothetical** capacity run: 100 requests/s completes with low queue age; at 200 the database pool wait grows; at 300 admission starts returning documented overload responses. The conclusion is a measured limit for this operation mix and topology plus its rejection behavior — not "CPU is low, so double replicas", since more replicas can create more database connections and worsen the same bottleneck.

Separate failed and successful response latency when needed: fast rejection can reduce overall p95 while user success deteriorates, while excluding failed requests from every report can hide slow timeouts. For soak tests, observe the **application's** memory, connection counts, queue trend and garbage-collection pauses over time — k6's own virtual-user memory is a different measurement. Growing memory alone can reflect a useful cache; verify ownership and reclamation before calling it a leak.

## 5. Compare Tools and Make Regression Tests Repeatable

k6 expresses workload and metric thresholds in JavaScript within its own runtime. Artillery supports scenarios through YAML and JavaScript with protocol engines. Locust models users and tasks in Python. Gatling supports code-defined workload models and assertions across its supported SDKs. JMeter provides a mature test-plan and plugin ecosystem. Choose from the protocol, arrival model, required business scripting, generator scaling, reporting and maintenance needs — no fixed requests-per-second ceiling follows from the tool name.

Version the workload, fixture and data scale, dependency versions and measurement population. Record environment changes and repeat runs when variance affects the decision; compare equivalent windows and distributions rather than applying a universal 10% threshold. CI should create or identify the actual target, run the workload, preserve raw measurements and threshold results, and clean up the environment. Inject faults when testing load plus dependency failure, using the [chaos experiment's](50.1.5.02-chaos-engineering.md) control and observation contract — a random mock response not connected to the application changes nothing about its behavior.

## Summary

Performance results depend on the workload, arrival model, data and environment. The runnable catalog example connects each request to business checks and threshold-based exit status. Larger load, spike, stress and soak tests must measure delivered work, tail behavior, errors, queues and resources before supporting a scoped capacity or regression decision.

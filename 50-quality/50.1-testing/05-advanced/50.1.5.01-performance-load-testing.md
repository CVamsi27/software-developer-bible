# Performance & Load Testing

## Definition

**Performance testing** measures a system's latency, throughput, resource consumption and stability under a specified workload. The workload includes how work arrives, which operations it performs, its data shape and how long it runs.

> **Textbook Definition:** Performance testing measures a system's latency, throughput, resource use and stability under a specified workload. Load, stress, spike and endurance tests vary the workload magnitude or its distribution over time.

A booking service handling 1,000 lightweight availability reads per second may fail at a much smaller rate of contended writes. “It handles 1,000 requests” is incomplete without the operation mix, dataset, environment and acceptance criteria.

## First Principles

Every operation consumes limited resources for some time. When incoming work exceeds the service rate of a bottleneck, a queue grows or work is rejected. Measuring only completed requests can miss the waiting or dropped work that users experience.

A useful test therefore controls incoming demand, observes completed and failed work, and identifies where resources or queues constrain the result. A fast response from a tiny warm fixture is evidence about that fixture, not the production population.

## Choose the workload shape from the question

| Test | What changes | Question to answer |
| -------------- | -------------------------------------------------- | ------------------------------------------------------------------------ |
| Load | Representative expected demand and operation mix | Do required outcomes hold at the forecast load? |
| Stress | Increase demand beyond the expected range | Where does saturation occur, and how does the service reject or recover? |
| Spike | Change arrival rate quickly | Can queues and scaling react within the tolerated impact window? |
| Soak/endurance | Hold a representative workload for a longer period | Do memory, connections, buffers or scheduled jobs accumulate problems? |

No fixed duration or universal acceptable failure rate applies to every service. State which measurements constitute success, which impact stops the test and which background conditions matter. Test cold starts and warm steady state separately when both are relevant rather than excluding one automatically.

## Explain the load model before selecting a tool

In a **closed model**, each simulated user waits for its operation, possibly thinks, then sends more work. If 100 users each spend 0.2 seconds waiting and 0.8 seconds thinking, the approximate cycle rate is 100 operations per second. If waiting rises to 1.2 seconds, the same users generate roughly 50 per second. The slower service reduces the offered load.

An **open arrival model** schedules new operations at a stated rate independent of earlier response completion. The generator still needs enough execution capacity. If it cannot start scheduled work, record the dropped arrivals; do not interpret the reduced delivered load as the service meeting the configured rate.

Neither model is universally correct. A bounded population of interactive clients can fit a closed model. Independent external arrivals, such as incoming webhook events, often fit an open model. Include the real request mix and pacing; an open-model executor already handles arrival pacing, so adding sleeps there can consume virtual users unnecessarily.

### Relate throughput, time and concurrency

For a stable population, **Little's Law** relates average in-flight work to average throughput times average time in the system. At 100 completed operations per second and a mean end-to-end time of 0.25 seconds, average in-flight work is 25 operations.

Use consistent boundaries and means. This is not `p99 latency × total registered users`, and it does not describe an indefinitely growing overload queue as a stable system. Include queue time when the population includes waiting operations. A connection pool or concurrency limit bounds one resource, not necessarily all requests waiting outside it.

## Trace a complete local k6 test

The example checks a read-only catalog fixture. It schedules five iterations per second for two seconds; each iteration sends one request. Every response contributes to the semantic failure rate, including successful attempts.

Start a local fixture in one terminal:

```python
# catalog_fixture.py
import json
from http.server import BaseHTTPRequestHandler, ThreadingHTTPServer

class Catalog(BaseHTTPRequestHandler):
    def do_GET(self):
        if self.path != '/api/catalog':
            self.send_error(404)
            return
        body = json.dumps({'items': [{'id': 'book-1', 'priceCents': 1250}]}).encode()
        self.send_response(200)
        self.send_header('Content-Type', 'application/json')
        self.send_header('Content-Length', str(len(body)))
        self.end_headers()
        self.wfile.write(body)

    def log_message(self, *_args):
        pass

ThreadingHTTPServer(('127.0.0.1', 18082), Catalog).serve_forever()
```

Save the next script as `catalog_load.js`. Install a reviewed k6 release for your platform; k6 runs this script in its own runtime, not Node.js.

```javascript
import http from 'k6/http';
import { check } from 'k6';
import { Rate } from 'k6/metrics';

const semanticFailures = new Rate('semantic_failures');
const rate = Number(__ENV.RATE || '5');
if (!Number.isSafeInteger(rate) || rate <= 0) throw new Error('RATE must be positive');
const baseUrl = (__ENV.BASE_URL || 'http://127.0.0.1:18082').replace(/\/$/, '');

export const options = {
  scenarios: {
    catalog_reads: {
      executor: 'constant-arrival-rate',
      rate,
      timeUnit: '1s',
      duration: __ENV.DURATION || '2s',
      preAllocatedVUs: 20,
      maxVUs: 100,
      gracefulStop: '5s',
    },
  },
  thresholds: {
    semantic_failures: ['rate==0'],
    http_req_failed: ['rate==0'],
    http_req_duration: ['p(95)<200'],
    dropped_iterations: ['count==0'],
  },
};

export default function () {
  const response = http.get(`${baseUrl}/api/catalog`, { timeout: '2s' });
  let body = null;
  try { body = response.json(); } catch { /* Invalid JSON is a failed contract. */ }
  const good = check(response, {
    'status is 200': r => r.status === 200,
    'expected item and exact price': () =>
      Array.isArray(body?.items) && body.items.length === 1 &&
      body.items[0].id === 'book-1' && body.items[0].priceCents === 1250,
  });
  semanticFailures.add(!good);
}
```

Run it against that fixture:

```bash
python3 catalog_fixture.py
# In another terminal:
k6 run catalog_load.js
```

A request starts, k6 waits for the response up to its request timeout, the checks evaluate both status and business payload, and one Boolean sample enters `semantic_failures`. Adding only failures would make the metric's denominator the failures themselves, so one failure would misleadingly produce a 100% failure rate.

A failed `check` is recorded but does not automatically fail the process. The custom `semantic_failures` Rate makes the combined status/payload result thresholdable; k6's built-in `checks` metric cannot itself be used in a threshold. The configured thresholds fail the run when the semantic contract, request error rate, latency or achieved scheduling violates this example's requirements. An HTTP 200 with the wrong price can therefore fail even though `http_req_failed` remains zero.

This short run validates script wiring and the local contract. Its small sample cannot establish a meaningful production p99 or capacity limit. Adapt the operation, fixture, rate, duration and thresholds to the actual test question; ensure the larger test has enough generator capacity and representative data.

## Interpret the curve and the evidence

Capture configured arrival rate, achieved starts/completions, dropped iterations, failures, latency distribution and generator resource use. Correlate them with the system's CPU, memory, connection waits, database locks, queue age, dependency quotas and replica state.

For a **hypothetical** capacity run, 100 requests/s completes with low queue age. At 200, the database pool wait grows; at 300, admission starts returning documented overload responses. The conclusion is a measured limit for this operation mix and topology, plus its rejection behavior. It is not “CPU is low, so double replicas”: more replicas can create more database connections and worsen the same bottleneck.

Separate failed and successful response latency when needed. Fast rejection can reduce overall p95 while user success deteriorates. Conversely, excluding failed requests from every report can hide slow timeouts. Keep the measurement contract explicit.

For soak tests, observe the **application's** memory, connection counts, queue trend and garbage-collection pauses over time. k6's own virtual-user memory is a different measurement, and `vus_memory` is not a built-in application-memory metric. Increasing memory alone can reflect a growing useful cache; verify ownership and reclamation before calling it a leak.

## Compare tools by their execution model

k6 expresses workload and metric thresholds in JavaScript within its own runtime. Artillery supports scenarios through YAML and JavaScript with protocol engines. Locust models users and tasks in Python. Gatling supports code-defined workload models and assertions across its supported SDKs. JMeter provides a mature test-plan and plugin ecosystem.

Choose from the protocol, arrival model, required business scripting, generator scaling, reporting and maintenance needs. Check the chosen version's API rather than copying another runner's executor or inventing a user identifier. No fixed requests-per-second ceiling follows from the tool name; scripts, payloads, networking and hardware determine generator capacity.

## Make regression tests repeatable

Version the workload, fixture/data scale, dependency versions and measurement population. Record environment changes and repeat runs when variance affects the decision. Compare equivalent windows and distributions; a universal 10% threshold or median of three runs does not automatically distinguish a regression from noise.

CI should create or identify the actual target, run the workload, preserve raw measurements and threshold results, and clean up the environment. A deployment URL must come from a real step output, and a comparison script must consume an artifact that the runner actually emitted. Keep runner setup in the canonical CI chapter rather than duplicating an unverified workflow here.

Inject faults when testing load plus dependency failure, using the [chaos experiment's](50.1.5.02-chaos-engineering.md) control and observation contract. Load testing and chaos are complementary; a random mock response not connected to the application changes nothing about its behavior.

## Summary

Performance results depend on the workload, arrival model, data and environment. The runnable catalog example connects each request to business checks and threshold-based exit status. Larger load, spike, stress and soak tests should measure delivered work, tail behavior, errors, queues and resources before supporting a scoped capacity or regression decision.

# Chaos Engineering & Game Days

A booking API should reject work promptly when its dependency becomes slow. A happy-path test cannot establish that deadline behavior — but a controlled 500 ms delay reveals whether requests time out, queue indefinitely, or retry until the service saturates.

```text
hypothesis: at booking-read load, a 500 ms dependency delay produces
no request lasting beyond the 200 ms application deadline
```

## Definition

**Chaos engineering** runs controlled experiments that try to **falsify** a belief about a system's behavior under a stated disruption. Define a measurable **hypothesis**, introduce a bounded fault, and compare the observed outcome with the expected behavior.

> **Textbook Definition:** Chaos engineering evaluates a falsifiable reliability hypothesis by deliberately introducing bounded faults and comparing observed system behavior with a defined steady state.

## First Principles

Individual components can behave correctly while their interaction fails: a retry can increase load on an already slow dependency, and a fallback can exhaust a shared database. To investigate the interaction, vary a stated condition while observing the required user outcome. An experiment is one sample under stated conditions — it increases or reduces confidence in a single hypothesis without proving all redundancy works. Missing telemetry or insufficient traffic can leave the result inconclusive.

## How It Works

### 1. Build a Hypothesis That Could Be Wrong

Specify the operation, workload, disruption, permitted impact and observation window. "The system stays healthy" has no failure condition; "at the stated booking-read load, a 500 ms dependency delay does not produce requests lasting beyond the 200 ms application deadline" can be tested. Keep correctness separate from latency — a fallback returning a fast empty appointment list may satisfy a duration threshold while violating the user contract.

| Step | Action | Why it matters |
| ------------------------ | --------------------------------------------------------------------------- | --------------------------------------------------------------------- |
| Establish baseline | Confirm the required operation works and collect enough observations | An existing failure or broken measurement prevents a valid comparison |
| Bound the fault | Name the target, affected connection direction, duration and stop path | A tool selector is not the entire consequence boundary |
| Observe during fault | Confirm injection is active, then measure outcomes and internal constraints | Tests after fault expiry do not establish behavior during disruption |
| Stop and verify recovery | Remove the fault, examine queues, resources and affected state | Removal alone does not undo accumulated effects |
| Interpret | Record supported, falsified or inconclusive with scope and evidence | Avoid turning a limited result into a universal reliability claim |

If the hypothesis fails, change the responsible mechanism and rerun the **same** test. Changing both the target and the acceptance threshold can disguise the failure. This chapter owns experiment design and the local injection example; the [production chapter](../../50.4-production-engineering/50.4.03-chaos-engineering.md) owns authorization, game-day coordination, production stopping and follow-up.

### 2. Match the Fault to the Question

| Uncertainty | Controlled condition | What to observe |
| -------------------------------- | ------------------------------------------------------------- | -------------------------------------------------------------------- |
| Dependency deadline | Delay replies or hold a connection | End-to-end deadline, timeout classification and remaining work |
| Retry amplification | Return explicit failures from an HTTP-aware stub | Attempts per operation, retry delay, load and unknown write outcomes |
| Connection interruption | Reset an owned test connection | Reconnection, duplicate work and acknowledgment interpretation |
| Resource saturation | Limit one disposable worker or bounded test slice | Queue bounds, admission/rejection and recovery after release |
| Failover | Lose the stated writer or route under an approved plan | Write fencing, target freshness and recovered correctness |
| Certificate or clock assumptions | Use an isolated invalid certificate or controlled time source | Validation, expiry and scheduled-work behavior |

A TCP proxy changes transport behavior; it does not normally understand your HTTP business response, and a bandwidth cap is a throughput limit rather than "50% HTTP errors". Use the correct layer for the intended fault and verify the application actually connects through it.

### 3. Prove a Downstream Delay Is Injected and Removed

The complete fixture below uses Python's standard library and the Toxiproxy 2.x HTTP control API. It demonstrates **one local transport delay** — not a circuit breaker, payment workflow or production experiment. Install the reviewed Toxiproxy binary, then start an isolated server in a separate terminal:

```bash
toxiproxy-server -host 127.0.0.1 -port 8474
```

Keep the control API local: it can create and change upstream connections. The fixture requires unused ports 18080 and 18081, starts its own HTTP upstream at 18080, and routes requests through the proxy at 18081. Save as `delay_experiment.py` and run `python3 delay_experiment.py` while the proxy server is available.

```python
import json
import statistics
import threading
import time
import urllib.request
from http.server import BaseHTTPRequestHandler, ThreadingHTTPServer

CONTROL = 'http://127.0.0.1:8474'
PROXY_NAME = 'local-delay-example'

# Bypass any environment HTTP proxy for this local-only fixture.
opener = urllib.request.build_opener(urllib.request.ProxyHandler({}))

class Upstream(BaseHTTPRequestHandler):
    def do_GET(self):
        body = b'correct-response'
        self.send_response(200)
        self.send_header('Content-Length', str(len(body)))
        self.end_headers()
        self.wfile.write(body)

    def log_message(self, *_args):
        pass

def control(method, path, value=None):
    body = None if value is None else json.dumps(value).encode()
    request = urllib.request.Request(
        CONTROL + path, data=body, method=method,
        headers={'Content-Type': 'application/json'})
    with opener.open(request, timeout=2) as response:
        return response.read()

def sample():
    elapsed = []
    for _ in range(3):
        started = time.monotonic()
        with opener.open('http://127.0.0.1:18081/', timeout=2) as response:
            assert response.status == 200
            assert response.read() == b'correct-response'
        elapsed.append(time.monotonic() - started)
    return statistics.median(elapsed)

server = ThreadingHTTPServer(('127.0.0.1', 18080), Upstream)
thread = threading.Thread(target=server.serve_forever, daemon=True)
thread.start()
created = False
try:
    control('POST', '/proxies', {
        'name': PROXY_NAME,
        'listen': '127.0.0.1:18081',
        'upstream': '127.0.0.1:18080',
        'enabled': True})
    created = True
    baseline = sample()
    assert baseline < 0.1, 'Local baseline too slow for this comparison'
    control('POST', f'/proxies/{PROXY_NAME}/toxics', {
        'name': 'delay', 'type': 'latency', 'stream': 'downstream',
        'toxicity': 1.0, 'attributes': {'latency': 150, 'jitter': 0}})
    during = sample()
    assert during >= 0.1, 'Expected downstream delay was not observed'
    control('DELETE', f'/proxies/{PROXY_NAME}/toxics/delay')
    recovered = sample()
    assert recovered < 0.1, 'Local requests did not recover'
    print({name: round(value * 1000) for name, value in
           [('baseline_ms', baseline), ('during_ms', during),
            ('recovered_ms', recovered)]})
finally:
    try:
        if created:
            control('DELETE', f'/proxies/{PROXY_NAME}')
    finally:
        server.shutdown()
        server.server_close()
        thread.join(timeout=2)
```

The baseline receives the exact response through the proxy; adding the downstream toxic delays server-to-client bytes while the body stays correct; removing it restores fast responses. `toxicity: 1.0` applies the fault to every selected connection — not a business error rate. The 100 ms comparison is a local fixture check, not a user SLO, and a baseline that is already too slow prevents the comparison instead of being silently accepted. Cleanup handles ordinary Python exceptions, but a killed runner might never reach `finally` — use a disposable proxy process here. Production fault expiry and independent cleanup belong to the [operating contract](../../50.4-production-engineering/50.4.03-chaos-engineering.md#automation-must-survive-a-failed-runner).

### 4. Add an Application Contract Before Claiming Resilience

To test a deadline or circuit breaker, route the actual application dependency through the controlled proxy. Observe the application response plus its attempts, queue state and recovery. For a breaker, demonstrate the closed-to-open transition after the configured failures, rejection while open, and the permitted recovery probe — low error rate alone does not prove that state machine.

For writes, a timeout can occur after the dependency accepted the operation. Trace its operation identifier and reconciliation instead of retrying blindly or treating every timeout as "nothing happened". Rejecting a promise does not necessarily cancel the network operation. Keep fault setup, workload generation and assertions under one versioned test contract: a failed or skipped setup must fail or explicitly skip the experiment, never report a healthy system.

### 5. Choose a Tool After Identifying the Boundary

Toxiproxy fits transport disruption through a controlled TCP route; an HTTP-aware stub fits explicit status and body scenarios; Kubernetes fault controllers fit selected workloads under their deployment and permission constraints; managed cloud fault services use the provider's supported resources and stop conditions. Evaluate scope, independent lifetime limits, cleanup behavior, telemetry and maintainability. Scheduling an experiment hourly does not turn a sampled result into a proved property. A game day adds responder practice; its operational design lives in the companion production chapter.

## Summary

A chaos experiment tests a stated behavior under a controlled disruption. The local proxy example shows a delayed response and recovery; application resilience needs additional correctness, deadline and state-machine observations. Record the conditions and limitations of each result, then use it to guide a specific improvement or confirm the bounded hypothesis.

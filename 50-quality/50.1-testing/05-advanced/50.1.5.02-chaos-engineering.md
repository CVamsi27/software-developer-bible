# Chaos Engineering & Game Days

## Definition

**Chaos engineering** runs controlled experiments that try to falsify a belief about a system's behavior under a stated disruption. Define a measurable hypothesis, introduce a bounded fault and compare the observed outcome with the expected behavior.

> **Textbook Definition:** Chaos engineering evaluates a falsifiable reliability hypothesis by deliberately introducing bounded faults and comparing observed system behavior with a defined steady state.

Suppose a booking API should reject work promptly when its dependency becomes slow. A happy-path test cannot establish that deadline behavior. A controlled delay lets you observe whether requests time out, queue indefinitely or retry until the service saturates.

This chapter owns experiment design and the focused local injection example. The [production chapter](../../50.4-production-engineering/50.4.03-chaos-engineering.md) owns authorization, game-day coordination, production stopping and follow-up.

## First Principles

Individual components can behave correctly while their interaction fails. A retry can increase the load on an already slow dependency; a fallback can exhaust a shared database. To investigate the interaction, vary a stated condition while observing the required user outcome.

An experiment is a sample under stated conditions. Its result increases or reduces confidence in one hypothesis; it does not prove that all redundancy works or that future traffic will behave identically. Missing telemetry or insufficient traffic can leave the result inconclusive.

## Build a hypothesis that could be wrong

Specify the operation, workload, disruption, permitted impact and observation window. “The system stays healthy” has no clear failure condition. “At the stated booking-read load, a 500 ms dependency delay does not produce requests lasting beyond the 200 ms application deadline” can be tested.

Keep correctness separate from latency. A fallback that returns a fast empty appointment list may satisfy a duration threshold while violating the user contract. Define which stale or degraded responses are acceptable and which must be rejected explicitly.

### Trace the experiment lifecycle

| Step | Action | Why it matters |
| ------------------------ | --------------------------------------------------------------------------- | --------------------------------------------------------------------- |
| Establish baseline | Confirm the required operation works and collect enough observations | An existing failure or broken measurement prevents a valid comparison |
| Bound the fault | Name the target, affected connection direction, duration and stop path | A tool selector is not the entire consequence boundary |
| Observe during fault | Confirm injection is active, then measure outcomes and internal constraints | Tests after fault expiry do not establish behavior during disruption |
| Stop and verify recovery | Remove the fault, examine queues, resources and affected state | Removal alone does not undo accumulated effects |
| Interpret | Record supported, falsified or inconclusive with scope and evidence | Avoid turning a limited result into a universal reliability claim |

If the hypothesis fails, change the responsible mechanism and rerun the **same** relevant test. Changing both the target and the acceptance threshold can disguise the failure. Version any changed hypothesis so the comparison remains interpretable.

## Match the fault to the question

| Uncertainty | Controlled condition | What to observe |
| -------------------------------- | ------------------------------------------------------------- | -------------------------------------------------------------------- |
| Dependency deadline | Delay replies or hold a connection | End-to-end deadline, timeout classification and remaining work |
| Retry amplification | Return explicit failures from an HTTP-aware stub | Attempts per operation, retry delay, load and unknown write outcomes |
| Connection interruption | Reset an owned test connection | Reconnection, duplicate work and acknowledgment interpretation |
| Resource saturation | Limit one disposable worker or bounded test slice | Queue bounds, admission/rejection and recovery after release |
| Failover | Lose the stated writer or route under an approved plan | Write fencing, target freshness and recovered correctness |
| Certificate or clock assumptions | Use an isolated invalid certificate or controlled time source | Validation, expiry and scheduled-work behavior |

A TCP proxy changes transport behavior; it does not normally understand your HTTP business response. A bandwidth cap is a throughput limit, not “50% HTTP errors.” Use the correct layer for the intended fault and verify that the application actually connects through it.

## Example: prove a downstream delay is injected and removed

The complete fixture below uses Python's standard library and the Toxiproxy 2.x HTTP control API. It demonstrates **one local transport delay**, not a circuit breaker, payment workflow or production experiment.

Install the reviewed Toxiproxy binary for your platform, then start an isolated server in a separate terminal:

```bash
toxiproxy-server -host 127.0.0.1 -port 8474
```

Keep the control API local: it can create and change upstream connections. The fixture requires unused ports 18080 and 18081. It starts its own HTTP upstream at 18080; requests go through the proxy at 18081. Save the following as `delay_experiment.py` and run `python3 delay_experiment.py` while the proxy server is available.

```python
import json
import statistics
import threading
import time
import urllib.request
from http.server import BaseHTTPRequestHandler, ThreadingHTTPServer

CONTROL = 'http://127.0.0.1:8474'
PROXY_NAME = 'local-delay-example'

# Bypass any environment HTTP proxy for this local-only fixture.
opener = urllib.request.build_opener(urllib.request.ProxyHandler({}))

class Upstream(BaseHTTPRequestHandler):
    def do_GET(self):
        body = b'correct-response'
        self.send_response(200)
        self.send_header('Content-Length', str(len(body)))
        self.end_headers()
        self.wfile.write(body)

    def log_message(self, *_args):
        pass

def control(method, path, value=None):
    body = None if value is None else json.dumps(value).encode()
    request = urllib.request.Request(
        CONTROL + path, data=body, method=method,
        headers={'Content-Type': 'application/json'})
    with opener.open(request, timeout=2) as response:
        return response.read()

def sample():
    elapsed = []
    for _ in range(3):
        started = time.monotonic()
        with opener.open('http://127.0.0.1:18081/', timeout=2) as response:
            assert response.status == 200
            assert response.read() == b'correct-response'
        elapsed.append(time.monotonic() - started)
    return statistics.median(elapsed)

server = ThreadingHTTPServer(('127.0.0.1', 18080), Upstream)
thread = threading.Thread(target=server.serve_forever, daemon=True)
thread.start()
created = False
try:
    control('POST', '/proxies', {
        'name': PROXY_NAME,
        'listen': '127.0.0.1:18081',
        'upstream': '127.0.0.1:18080',
        'enabled': True})
    created = True
    baseline = sample()
    assert baseline < 0.1, 'Local baseline too slow for this comparison'
    control('POST', f'/proxies/{PROXY_NAME}/toxics', {
        'name': 'delay', 'type': 'latency', 'stream': 'downstream',
        'toxicity': 1.0, 'attributes': {'latency': 150, 'jitter': 0}})
    during = sample()
    assert during >= 0.1, 'Expected downstream delay was not observed'
    control('DELETE', f'/proxies/{PROXY_NAME}/toxics/delay')
    recovered = sample()
    assert recovered < 0.1, 'Local requests did not recover'
    print({name: round(value * 1000) for name, value in
           [('baseline_ms', baseline), ('during_ms', during),
            ('recovered_ms', recovered)]})
finally:
    try:
        if created:
            control('DELETE', f'/proxies/{PROXY_NAME}')
    finally:
        server.shutdown()
        server.server_close()
        thread.join(timeout=2)
```

The baseline receives the exact response through the proxy. Adding the downstream toxic delays bytes on the server-to-client path; the measured median rises while the body remains correct. Removing it restores fast local responses. `toxicity: 1.0` applies the fault to all selected links; it does not mean all business requests fail.

The 100 ms comparison is a local fixture check, not a user SLO. Operating-system scheduling affects timings, and this small sample cannot estimate a production tail percentile. A baseline that is already too slow prevents the intended comparison instead of being silently accepted.

Cleanup handles ordinary Python exceptions, including a failed assertion. A killed runner might never reach `finally`; use a disposable proxy process/environment here. Production fault expiry and independent cleanup belong to the [operating contract](../../50.4-production-engineering/50.4.03-chaos-engineering.md#automation-must-survive-a-failed-runner).

## Add an application contract before claiming resilience

To test a deadline or circuit breaker, route the actual application dependency through the controlled proxy. Observe the application response and its attempts, queue state and recovery. For a breaker, demonstrate the closed-to-open transition after the configured failures, rejection while open and the permitted recovery probe; low error rate alone does not prove that state machine.

For writes, a timeout can occur after the dependency accepted the operation. Trace its operation identifier and reconciliation instead of retrying blindly or treating every timeout as “nothing happened.” Define how much work remains after a response deadline: rejecting a promise does not necessarily cancel the network operation.

Keep fault setup, workload generation and assertions under one versioned test contract. A failed or skipped setup should fail or explicitly skip the experiment, not report a healthy system. Record the dependency version and routing path so the next run exercises the same seam.

## Choose a tool after identifying the boundary

Toxiproxy fits transport disruption through a controlled TCP route. An HTTP-aware stub fits explicit status/body scenarios. Kubernetes fault controllers fit selected workloads under their deployment and permission constraints. Managed cloud fault services use the provider's supported resources and stop conditions.

Evaluate scope, independent lifetime limits, cleanup behavior, telemetry and maintainability. A commercial product is not automatically the safest option, and scheduling an experiment hourly does not turn a sampled result into a proved property. A game day adds responder practice; its operational design is covered in the companion production chapter.

## Common Mistakes

- Claiming a delay or bandwidth cap generated a particular HTTP error percentage.
- Sending application traffic directly to the dependency while the unused proxy reports an active fault.
- Inferring a circuit breaker from latency/errors without observing its transition and recovery contract.
- Changing the hypothesis or pass line after a failed run without recording the change.
- Inventing case-study metrics or mandatory industry-wide experiment schedules.

## Best Practices

State the uncertainty and a falsifiable expectation before choosing tooling. Verify the injection, observe the required outcome while it is active, then check removal and recovery. Keep results scoped to the actual workload and environment, and rerun the relevant hypothesis after a repair.

## Summary

A chaos experiment tests a stated behavior under a controlled disruption. The local proxy example shows a delayed response and recovery; application resilience needs additional correctness, deadline and state-machine observations. Record the conditions and limitations of each result, then use it to guide a specific improvement or confirm the bounded hypothesis.

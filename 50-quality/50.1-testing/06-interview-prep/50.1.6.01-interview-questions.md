# Testing Interview Questions

## Definition

This bank practices testing decisions through the original forty questions. The chapters teach the mechanisms; here, explain the risk, choose an observable boundary, state the expected result and identify what a passing check does not establish.

## First Principles

A test samples behavior under an arrangement and compares observations with an expectation. Replacing dependencies reduces the observed system; broadening the system adds setup and failure sources. An interview answer must therefore connect its strategy to the actual failure risk, rather than rely on test counts, tool names or coverage percentages.

## Practice in two passes

First answer aloud without reading. Give a concrete example, then use the probe to change a condition. Revisit the linked source and its separate revision companion when you cannot predict the result. For experience questions, use supported personal work and distinguish measured results from hypothetical designs.

## Fundamentals and evidence boundaries

### 1. What is the testing pyramid?

**Answer:** The testing pyramid is a cost-and-feedback model: exercise many rules through small, controllable tests, then use real-component and complete-journey tests for behavior those small tests cannot observe. It does not prescribe a universal 70/20/10 split. For checkout, calculate prices in unit tests, verify database constraints and payment adapters in integrations, and test a small set of critical customer journeys in the browser. A service whose main risk is SQL semantics may need substantial integration coverage. Evaluate missed failures, diagnosis time and maintenance cost rather than making test counts fit a diagram.

**Probe:** Which failure would remain invisible if the database were replaced by a Map?

### 2. What is the difference between unit, integration, and E2E tests?

**Answer:** A unit test observes a selected small responsibility; an integration test observes cooperation across selected real boundaries; an end-to-end (E2E) test observes a complete configured journey. State those boundaries explicitly because teams use the labels differently. A real user repository plus a mocked email provider tests repository integration and the caller’s delivery request, not email delivery. A browser confirmation screen may establish visible completion while still needing a backend invariant check for duplicate charging. Speed and confidence depend on setup and assertions, not the label alone.

**Probe:** Does an E2E test using a payment sandbox establish live settlement?

### 3. What is Test-Driven Development (TDD)?

**Answer:** Test-driven development (TDD) develops behavior through red → green → refactor. Write a focused test and run it to see a failure caused by the missing behavior, implement enough to satisfy that contract, then improve the design while preserving the result. A test that fails only because of a missing import has not yet demonstrated the intended behavioral check. Add boundary and rejection cases as the contract develops; one happy-path test does not establish comprehensive coverage. Refactoring changes structure while preserving behavior, whereas a new requirement needs a changed or additional contract.

**Probe:** How would you prove that a passing test actually detects the bug it targets?

### 4. What is a mock and when should you use one?

**Answer:** A mock is an interaction-checking test double; many libraries also use the word for configurable replacements. Replace the smallest useful collaborator when an external response, clock or failure must be controlled. Run the real consumer and assert its outcome or required interaction, including failure and forbidden side effects. A mocked database cannot establish PostgreSQL constraints, and a called email function cannot establish delivery. Keep a separate real-boundary test where protocol or implementation compatibility matters.

**Probe:** What if the payment provider accepts a request but the response is lost?

### 5. What makes a good unit test?

**Answer:** A useful unit test is repeatable, independent, quick enough for its feedback role and self-validating. It states important inputs and an independently justified result, observes one meaningful contract and fails for the relevant defect. Include boundaries such as exactly the discount threshold, invalid input and unchanged state after rejection. Make time and identity controllable instead of relying on sleep or timestamps. Clear diagnostics matter more than a universal millisecond limit or a rigid assertion count.

**Probe:** Which wrong implementation could satisfy your current assertions?

### 6. What is the AAA pattern in testing?

**Answer:** Arrange–Act–Assert names setup, the action under test and the expected observations. Given–When–Then expresses the same scenario in domain language; the vocabulary alone does not establish a behavior-driven collaboration process. Keep consequential setup visible and let helpers hide only irrelevant repetition. One behavior can require several calls or observations, such as rejection and unchanged state, so the Act section need not be one line. Add an explicit cleanup owner for resources that outlive the case.

**Probe:** Why can a factory make the expected total harder to understand?

### 7. How do you test error handling?

**Answer:** Arrange the precise failure and await the real consumer’s result. Check the required error or fallback and also the state that must remain valid: no charge after a known decline, for example. Distinguish malformed input, a received HTTP error, a transport failure and an unknown remote outcome. If retries are permitted, verify bounded attempts, delay, cancellation and idempotency where side effects are involved. A test that checks only that an exception exists can miss partial writes or a misleading success notification.

**Probe:** When is retrying an error capable of causing a duplicate effect?

### 8. What is test coverage and what's a good target?

**Answer:** Coverage records which instrumented statements, branches or functions executed. It identifies unobserved code, but execution alone says nothing about whether assertions checked the right outcome. Choose local thresholds from risk and investigate uncovered critical branches rather than applying universal percentages. Pair coverage with boundary cases, escaped-defect analysis and targeted mutation testing. A fully covered function can still be wrong for an untested input or pass without a meaningful oracle.

**Probe:** How can 100% branch coverage coexist with an incorrect price calculation?

### 9. What is the difference between mocks, stubs, and fakes?

**Answer:** A stub supplies controlled responses; a mock checks required interactions; a fake executes a simplified implementation; a spy records calls and may still invoke the original. These describe roles rather than disjoint library types: one function can supply a value and record its use. State what actually runs and which expectations matter. Keep fakes small and test their supported contract, especially absence, empty values and failures. A fake’s name does not give it the real provider’s consistency, persistence or constraints.

**Probe:** What changes when a spy calls the original method by default?

### 10. When should you write tests?

**Answer:** Write checks while clarifying a new contract, before changing behavior during a refactor, and when reproducing a defect. For a bug, first make the regression check fail for the observed cause, then fix it and verify the surrounding contract. Prioritize consequential behavior and boundaries rather than testing every getter equally. Existing confusing code may first need characterization tests that record current behavior, with unwanted behavior identified separately. Make a test’s purpose and maintenance owner clear.

**Probe:** Which check would you add before changing a transaction boundary?

## Asynchronous behavior, tools and measurement

### 11. How do you test asynchronous code?

**Answer:** Return or await the promise that includes every assertion, and await rejects/resolves matchers. For callback APIs, use the runner-supported completion mechanism and propagate callback errors; do not both return a promise and use done for the same case. Wait for an observable state with a bounded timeout instead of guessing a sleep. Advancing fake timers and changing wall time are distinct, and promise work may need asynchronous timer APIs. End the test only after required cleanup completes.

**Probe:** Why can an assertion inside an unawaited setTimeout be missed?

### 12. How do you test React components?

**Answer:** Render the real component with the providers needed for its behavior, then use accessible queries and awaited user interactions. Query a button by role and accessible name; use findBy for an element that appears asynchronously. Control the response boundary while keeping the component’s request and state logic real. Assert visible loading, success, empty and failure behavior where those are contracts. A DOM test does not establish layout, actual assistive-technology behavior or the real remote service.

**Probe:** What extra test is needed when keyboard focus after an error is important?

### 13. How do you mock API calls?

**Answer:** Mock Service Worker (MSW) intercepts supported HTTP requests while preserving the consumer’s request construction. Match the method, URL and consequential body/headers; fail unexpected requests and reset test overrides. A status500 response and HttpResponse.error exercise different paths: one is received HTTP, the other transport rejection. Resetting handlers does not reset mutable fixture data. Provider compatibility remains a separate real-boundary test; use the [canonical mocking example](../04-mocking-and-patterns/50.1.4.01-mocking.md) for setup.

**Probe:** Could a permissive success handler accept a broken request?

### 14. What is snapshot testing?

**Answer:** A snapshot checks a serialized result against a reviewed stored value. It is useful for compact stable structure changes, but approving an update is a correctness decision. Normalize irrelevant variability deliberately and keep explicit assertions for consequential behavior. Large snapshots can hide defects among unrelated differences. A DOM snapshot does not establish visual layout, keyboard behavior or screen-reader output.

**Probe:** What evidence would justify updating a snapshot after a failing change?

### 15. How do you handle flaky tests?

**Answer:** First preserve the initial failure’s trace, logs, random seed, environment and data ownership. Determine whether the cause is a test synchronization defect, leaked state, an unstable dependency or an actual application race. Wait for observable outcomes, isolate resources and control only the boundaries appropriate to the test’s scope. A retry can aid diagnosis, but a later pass does not repair the cause. If quarantine is necessary, keep an owner, expiry, visible excluded coverage and a path back to enforcement. [Playwright distinguishes first-run passes, retry passes and failures](https://playwright.dev/docs/test-retries).

**Probe:** How will you prevent retries from hiding a concurrency bug?

### 16. What is contract testing?

**Answer:** A consumer-driven contract records the requests and responses a consumer actually relies on. The consumer runs against the contract-producing substitute; a verifier then sends those interactions to the real provider under specified provider states. Publishing a contract or calling addInteraction alone is not provider verification. Match types, status, relevant headers and failure behavior, and connect the verified consumer/provider versions to release compatibility. Contracts complement real workflows; they do not establish all business correctness or performance. [Pact describes both sides of this process](https://docs.pact.io/getting_started/how_pact_works).

**Probe:** What happens when the verified provider version differs from the deployed one?

### 17. How do you test custom hooks?

**Answer:** Use renderHook from @testing-library/react where directly observing a hook’s public result is the appropriate boundary. Wrap state-changing calls in the supported act flow, await asynchronous outcomes and supply required context providers. Check changed inputs, cleanup and stale-response behavior, not only one increment. A component-level test can be clearer when the hook’s purpose is a user-visible interaction. Keep the production hook intact rather than replacing its state machinery. [Testing Library documents the current API](https://testing-library.com/docs/react-testing-library/api/).

**Probe:** How would a response from the previous userId be prevented from overwriting the current one?

### 18. How do you test performance?

**Answer:** Define the behavior and population before choosing a performance measurement: render work, user interaction, endpoint latency and resource saturation are different observations. A DOM-runner wall-clock render assertion is usually a noisy proxy for browser experience. Use representative browser/device measurements for UI behavior and a production-like controlled workload for server limits. Preserve successful payload checks, request mix, offered/achieved rate and error population. Thresholds need enough observations and a justified budget; see the [load-testing chapter](../05-advanced/50.1.5.01-performance-load-testing.md) for the runnable fixture.

**Probe:** How could faster errors make aggregate latency look better?

### 19. How do you test database operations?

**Answer:** Use the actual database engine when its types, constraints, queries or transaction semantics are the risk. Rollback isolates a test only when all relevant writes use the controlled transaction/connection and do not escape through another worker or external service. Otherwise use an owned schema/database or exact namespace with awaited cleanup. Test uniqueness, null handling, failure rollback and concurrent behavior with explicit isolation. A successful insert/read alone does not establish those guarantees; follow the [integration chapter](../03-test-levels/50.1.3.02-integration-testing.md).

**Probe:** Why does a repository borrowing another pool connection defeat a wrapping rollback?

### 20. What is mutation testing?

**Answer:** Mutation testing changes selected implementation rules and observes whether tests detect the changes. A surviving mutant can reveal a missing case or weak assertion, but some changes are equivalent for the supported input domain. Check tool classifications for uncovered, invalid and timed-out mutants before interpreting a score. For isEven, checking2 cannot distinguish parity from num>=2; checking3=false detects that replacement. Use mutations to investigate meaningful contracts rather than treating a high score as proof. [Stryker defines its states and denominators](https://stryker-mutator.io/docs/mutation-testing-elements/mutant-states-and-metrics/).

**Probe:** Which assertion would catch a changed comparison exactly at a discount boundary?

## Application boundaries and release risk

### 21. How do you design testable code?

**Answer:** Keep domain rules separate from unstable I/O and inject narrow interfaces owned by the consumer where useful. Make time, identity and side-effect boundaries explicit; prefer pure calculations for rules that do not need I/O. Define both success and failure behavior for collaborators, so tests can observe outcomes without reproducing the whole system. Dependency injection makes substitution possible but does not by itself make a good test. Avoid redesigning simple code solely to mock every internal method.

**Probe:** Where should an unknown payment outcome be represented in the interface?

### 22. How do you test microservices?

**Answer:** Test local business rules, real service/database adapters, versioned consumer-provider compatibility and a small set of critical multi-service journeys. Include duplicate and out-of-order events, schema evolution, timeout after an accepted effect and retry idempotency. Verify eventual state within a defined deadline while asserting invariants that must hold throughout. A stubbed payment success does not establish real payment behavior, and an endpoint shape check is not the whole contract-verification process. Distribute effort according to failure risks rather than a fixed percentage formula.

**Probe:** What if the acknowledgment is lost after the consumer commits?

### 23. How do you handle testing in CI/CD?

**Answer:** For each pipeline job, state its input revision, required environment, executed command, enforceable result and retained failure evidence. Install dependencies from the lockfile, provision an isolated database, wait for readiness and use the matching runtime/browser versions. Independent jobs can run in parallel; later jobs need explicit dependencies if their execution is conditional. Upload useful traces on failure and distinguish failed, skipped, unavailable and passed gates. Credentials missing for an integration are a limitation to resolve, not a green result; use the [CI/CD stack](../../../40-platform/40.3-ci-cd/INDEX.md) for actual workflow syntax.

**Probe:** What fails if a database container is running but not ready?

### 24. How do you test security?

**Answer:** Begin with assets, trust boundaries and explicit forbidden actions. Test authorization with two users/tenants and assert both the denied response and unchanged protected state. Parameterization should prevent SQL structure changes; asserting that a result lacks the words DROP TABLE proves neither parameterization nor database integrity. Test output encoding in the actual rendering context rather than searching only for one script tag. Include token expiry/issuer/audience, rate-limit scope and secret handling; combine these checks with threat review and suitable analysis tools.

**Probe:** Would a403 response still be acceptable if a write occurred before authorization?

### 25. How do you test for performance?

**Answer:** For capacity, model the request mix, data size, concurrency or arrival rate, warmup, duration and expected business results. Closed-user workloads slow their offered rate when responses slow; open-arrival workloads also require checking missed starts and achieved rate. Inspect latency distributions, semantic errors, queueing and resource saturation together. A single query timing or HTTP-status-only check cannot establish sustained capacity. Keep regressions comparable under a controlled environment and separate load, stress and soak goals.

**Probe:** What conclusion is invalid when the generator cannot deliver the intended load?

### 26. How do you handle test data management?

**Answer:** Use synthetic fresh data with consequential inputs visible. Factories construct objects; fixtures arrange the whole environment and lifecycle; builders can simplify meaningful multi-step setup. Seed random generation and hold reference time fixed when replay depends on them. Assign unique resource ownership across workers and await cleanup without deleting another test’s records. Do not treat copied production data as anonymous merely because names were changed.

**Probe:** How would a process crash leave stale data that the next run must handle?

### 27. How do you test infrastructure as code?

**Answer:** Start with formatting, syntax, validation and plan review, then test consequential deployed behavior in an owned disposable environment. Check connectivity, access restrictions, routing and recovery, not merely that a resource ID exists. Tag or namespace resources and arrange cleanup before creation; defer/finally helps normal exits but cannot guarantee cleanup after runner death. Bound cost and give leaked resources an independent expiry or reconciliation owner. Integration evidence applies to the tested account, region, configuration and provider versions.

**Probe:** Why can a successful apply still leave a service unreachable?

### 28. How do you test real-time features?

**Answer:** Unit-test the connection state machine with controlled timers and events, then exercise the real client/server transport separately. Check authentication, subscribing, duplicate/out-of-order delivery, reconnect, replay gaps, cancellation and disposal. A fake socket’s connect call count cannot establish a real handshake or a restored subscription. After reconnect, inspect the user-visible authoritative state or cursor, not merely open. Distinguish transport delivery from application processing acknowledgment and bound buffered messages.

**Probe:** What if a stale socket fires an event after a new connection becomes active?

### 29. How do you handle testing with complex state?

**Answer:** Express setup and transitions through the supported API and assert public outcomes or defined state invariants. For an order, test pending→confirmed→shipped as well as forbidden pending→shipped, verifying rejection leaves state unchanged. Model duplicates, cancellation, retries and concurrent transitions where the domain permits them. Generating only final objects can bypass the transition rule; generate action sequences when that is the risk. Internal state can aid diagnosis, but incidental representation should not be the only contract.

**Probe:** How do two concurrent confirmation attempts avoid duplicate effects?

### 30. How do you measure test effectiveness?

**Answer:** Combine evidence about observed behavior, assertion strength and feedback cost. Coverage locates unobserved code; targeted mutations challenge assertions; escaped defects identify risks the suite missed. Define the population and denominator of each metric, and track first-run failures separately from retry passes. Compare stable scopes over time, including runtime and maintenance cost. A constant object saying trend=improving is an assertion, not an analysis, and fewer discovered defects may reflect less reporting.

**Probe:** Which change in traffic or reporting would make an apparent defect-rate improvement misleading?

## Strategy at scale

### 31. How would you design a testing strategy for a large-scale application?

**Answer:** Start from critical journeys, invariants, dependency boundaries and failure consequences. Put fast checks close to domain rules, real integrations around consequential adapters and constraints, contracts around independently versioned services, and complete journeys around deployment seams. Include data isolation, security, recovery, capacity and operability according to the application’s risks. Define required release evidence, ownership and exceptions, then measure which defects and diagnosis costs remain. Avoid allocating a universal percentage of tests or marking performance unimportant before understanding the workload.

**Probe:** Which release evidence is necessary for a schema migration with old clients still active?

### 32. How do you handle testing in a CI/CD pipeline?

**Answer:** Separate fast feedback from release evidence without silently weakening either. Run independent checks concurrently and reserve expensive environments for the revisions that need them, with explicit sequencing around deployment. Test-impact selection can save time only when its dependency model includes generated files, configuration, migrations and shared code; retain broader checks to catch missed dependencies. Require the same reviewed revision/artifact to reach later gates. Expired exceptions, skipped jobs and stale evidence should remain visible to the release decision.

**Probe:** Can a green report for the previous commit authorize this deployment?

### 33. How do you ensure test reliability at scale?

**Answer:** Make results reproducible through owned resources, known runtimes, controlled time and recorded seeds. Preserve first-failure evidence and compare runs of the same revision/environment when diagnosing nondeterminism; changing code between runs can explain mixed outcomes. Do not detect only10–90% pass rates: a1% intermittent critical failure can still matter. Bound quarantine with an owner, expiry and clear missing coverage. A retry pass is diagnostic evidence and must remain distinguishable from a first-run pass.

**Probe:** How would you distinguish a test race from a real application race?

### 34. How do you test complex user journeys?

**Answer:** Choose critical outcomes and divide independent behavior into focused cases, retaining at least one complete journey for the important seams. Seed isolated prerequisite data through supported APIs, keep the relevant UI actions real and use accessible locators with awaited outcome assertions. Verify consequential backend state where a confirmation message alone is insufficient. Page objects group actions but must not silently swallow errors or manufacture success. Keep the test’s identity and cleanup owned so parallel runs do not collide.

**Probe:** What additional assertion would detect a double charge behind one confirmation page?

### 35. How do you balance coverage with execution time?

**Answer:** Identify required risk checks before optimizing runtime. Remove redundant setup, improve fixtures, shard independent cases and investigate slow boundaries while retaining meaningful invariants. Selective execution needs a validated impact model and periodic broader runs. If the necessary evidence cannot fit the deadline, reduce change scope or record an owned release exception; do not silently omit required checks. Performance and visual behavior can be critical contracts depending on the product.

**Probe:** What happens when affected tests alone exceed the available budget?

## Experience and teaching

### 36. How has your testing approach evolved over your career?

**Answer:** Use your actual experience: name an earlier limitation, the concrete failure or evidence that changed your judgment, your contribution and the resulting practice. For example, a real escaped query bug might motivate real-engine tests while retaining fast calculation tests. Explain what remained untested and how you assessed maintenance cost. Do not adopt a scripted junior-to-senior progression or metrics you cannot substantiate. Connect the lesson to how you would handle a similar risk now.

**Probe:** What artifact or example supports the claimed improvement?

### 37. What testing tools have you used and why?

**Answer:** Name tools you actually used and the behavior they helped observe. Compare runtime/module compatibility, existing framework integration, assertions, diagnostics, plugin needs and measured execution cost under the same suite. Jest and Vitest differ in transforms, ESM/module replacement and runtime requirements; one is not universally faster or better. Testing Library’s user-oriented queries do not automatically establish accessibility. Discuss migration and team cost as well as tool capability, using the [framework comparison](../02-frameworks/50.1.2.04-testing-frameworks-comparison.md).

**Probe:** Which existing test or dependency would make migration expensive?

### 38. How do you handle testing legacy code?

**Answer:** Capture consequential current behavior before changing difficult code, distinguishing a characterization of reality from an endorsement of a bug. Introduce a narrow seam around an unstable dependency where it reduces risk, and protect the public outcome through incremental changes. Add new requirements with explicit expected behavior, including error and data compatibility. A gradual replacement needs a routing/ownership boundary and rollback plan; merely adding a method is not the full migration. Avoid broad refactoring before you can detect meaningful regressions.

**Probe:** What if callers rely on behavior the new implementation calls a bug?

### 39. What's the most complex testing problem you've solved?

**Answer:** Describe a real problem using context, constraint, your specific action, validation and outcome. For distributed processing, explain the actual duplicate, ordering or unknown-outcome risk and the invariant your tests observed. State which dependencies were real, which were simulated and how failures were reproduced. Use measured outcomes only with a known baseline, time window and attribution limits. An illustrative incident-reduction metric is not a supported personal result.

**Probe:** Which part did you personally implement, and what still failed afterward?

### 40. How do you teach testing to junior developers?

**Answer:** Start with one observable domain rule, then ask the learner to introduce a meaningful bug and explain why the test fails. Add boundary/rejection cases, controlled async behavior and resource ownership in that order as the example requires them. Pair on a real change and review the expected outcome, scope, diagnostics and failure evidence. Teach why a weak assertion or permissive mock can pass a broken implementation. Adapt the pace to demonstrated understanding rather than requiring a universal four-week schedule.

**Probe:** How would you assess understanding beyond counting the tests written?

## Summary

A defensible testing answer states the behavior, boundary, oracle, failure conditions and evidence limit. Select checks from risk, preserve first-failure evidence and resource ownership, and distinguish a passing simulation from a verified real integration. Use supported personal examples for experience questions.

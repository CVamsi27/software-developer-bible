# Chaos Engineering & Game Days

> **You can't trust a system you've never tried to break.** Unit tests prove the code does what you think. Integration tests prove the components work together. Load tests prove the system handles the expected traffic. **None of them prove the system survives the unexpected.** Chaos engineering is the discipline of *deliberately* breaking things in production (or production-like) to learn what fails, and game days are the scheduled events where the team runs the experiments. Netflix, Google, Stripe, Amazon, LinkedIn — every senior platform/DevOps/SRE interview asks about this. The candidates who can talk fluently about blast radius, steady-state hypothesis, and rollback plans are the ones who get hired.

## TL;DR

- **Chaos engineering** = the discipline of experimenting on a system to build confidence in its ability to withstand turbulent conditions. Not "break things for fun" — **hypothesis-driven, measured, with a blast radius**.
- **The 4 principles** (from the Principles of Chaos Engineering): (1) build a hypothesis around steady-state behavior, (2) vary real-world events, (3) run experiments in production, (4) automate the experiments to run continuously.
- **Tools**: **Chaos Monkey** (Netflix, terminates EC2 instances), **Gremlin** (commercial, broad failure modes), **Litmus** (Kubernetes), **ChaosBlade** (Alibaba, K8s + host), **Toxiproxy** (network-level), **AWS Fault Injection Service**, **Azure Chaos Studio**.
- **Game day** = a scheduled, multi-hour exercise where the team runs a series of chaos experiments together. Proves the team + tooling + runbooks work end-to-end.
- **Blast radius** = how much the experiment can affect. Start small (1 instance, 1 region, 1 user) and grow.
- **Steady-state hypothesis** = "we believe that when X fails, Y will continue to function with Z metric within bounds." You test the hypothesis, not the failure.
- **In interviews: name the steady-state, name the blast radius, name the abort criteria, name what you learned.**

## Why it matters

The "**9s**" question ("how do you get 99.99% availability?") has a textbook answer: redundancy, multi-region, retries, circuit breakers. The **interview-grade** answer is: **"we test it"**. You can't claim resilience you haven't verified. And you can't verify resilience by reading the code.

> "If you haven't tested how your system fails, you don't know how your system fails. And the production incident is the wrong time to find out." — every SRE, paraphrased

Netflix coined the term in 2010 with the release of Chaos Monkey. The original insight: "we want to know our system tolerates instance failures **before** an outage, not during one". The discipline has grown into a set of practices, tools, and certifications (e.g. the Chaos Engineering certification by Gremlin).

A senior platform / SRE / staff engineer is expected to:
1. **Define steady-state** for the system (latency, error rate, throughput).
2. **Hypothesize** what happens when a dependency fails.
3. **Run the experiment** with a controlled blast radius.
4. **Measure** deviation from steady-state.
5. **Document** findings + fix the gap.

Most candidates can't get past step 1. That's the difference between mid-level and senior.

## The 4 Principles (from the Principles of Chaos Engineering)

1. **Build a hypothesis around steady-state behavior.** Define what "working" looks like. Not "the service is up" — that's binary. "P99 latency under 200ms with 1% error rate" is a steady-state. You test the steady-state, not the failure.

2. **Vary real-world events.** Hardware failures, network partitions, slow dependencies, deploys, traffic spikes, malicious traffic, clock drift, certificate expiry, DNS outages, database failovers, dependency errors. The list is long; your chaos experiments should cover the top 5-10.

3. **Run experiments in production.** The system is different in production. A chaos experiment in staging tells you what would happen **if staging were production** — but staging is never production. Run in production, with a small blast radius, with an abort switch.

4. **Automate the experiments to run continuously.** A one-time game day is a snapshot. A chaos experiment that runs hourly is a property. Netflix's **ChAP** (Chaos Automation Platform) runs continuously in production; failures are detected and rolled back automatically.

## The 5 Stages of a Chaos Experiment

A standard framework (from the Chaos Engineering book by Casey Rosenthal et al.):

### 1. Define Steady State

What does "working" look like? Pick 2-3 metrics. Examples:
- **Latency**: p99 < 200ms
- **Error rate**: < 0.1%
- **Throughput**: > 1000 req/sec
- **Queue depth**: < 100
- **Customer-visible**: sign-up conversion > 50%

The steady-state must be **observable**. If you can't measure it, you can't test it.

### 2. Hypothesize

> "When database-primary fails over, the read-replica promotion completes in < 30s, and the service's p99 latency stays under 500ms with < 1% error rate during failover."

**Good hypothesis:** specific, measurable, falsifiable.
**Bad hypothesis:** "the system will be OK".

### 3. Run the Experiment

Inject the failure. With a **controlled blast radius**:
- 1 instance out of 100, not all of them
- 1 region, not all regions
- 1% of users, not all of them
- For 5 minutes, not indefinitely

**Always have an abort switch** — a way to stop the experiment immediately if it goes wrong. Gremlin has a "Halt" button. Chaos Monkey has a config to disable.

### 4. Measure

Compare the steady-state metrics before, during, and after the experiment.

```
              before     during    after
p99 latency   180ms     1450ms    220ms
error rate    0.05%     4.2%      0.08%
throughput    1100/s    850/s     1080/s
```

**Result:** the hypothesis was wrong. During failover, latency spiked to 1450ms (vs 500ms budget) and error rate to 4.2% (vs 1% budget). **Finding: failover is not graceful.**

### 5. Learn and Improve

Update the system, the runbook, or both. Then **re-run the experiment** to verify the fix.

```
Hypothesis v2: with connection draining + replica warmup, 
               failover completes in < 15s, p99 stays < 300ms.
Experiment v2: pass.
```

## The Failure Modes You Should Test

The senior-level list. Run a chaos experiment for each of these at least once a quarter.

| Failure mode | What you inject | What you're testing |
|--------------|-----------------|---------------------|
| **Instance death** | Terminate a server | Auto-scaling, health checks, service discovery |
| **Pod eviction** | `kubectl delete pod --force` | K8s restart policy, readiness probes |
| **Region outage** | Blackhole a region's egress | Multi-region failover, GeoDNS |
| **AZ outage** | Drop traffic to one AZ | Load balancer, replica placement |
| **Database primary failure** | Kill the primary, promote replica | Failover time, RPO/RTO |
| **Slow dependency** | Toxiproxy: +5s latency on user-svc | Circuit breaker, deadline propagation |
| **Error dependency** | Toxiproxy: 500 from payment-svc | Fallback behavior |
| **Network partition** | Drop packets between two services | Partition tolerance, conflict resolution |
| **DNS failure** | Blackhole the DNS resolver | Service discovery fallback |
| **Certificate expiry** | Inject an expired cert | Renewal automation, alerts |
| **Clock skew** | NTP jump forward 1 hour | Time-based logic, JWT expiry, scheduled jobs |
| **Disk full** | Fill disk to 100% | Log rotation, alerting |
| **Memory pressure** | cgroup limit; force OOM | Memory leaks, OOM handling |
| **CPU saturation** | Stress 100% CPU on 1 core | Thread pool behavior, request coalescing |
| **Dependency slow leak** | Gradually slow a service 1s, 2s, 5s | Latency degradation, hedging |
| **Process restart storm** | Kill all instances of a service simultaneously | Cold start, warmup |
| **Deploy during peak** | Deploy a buggy release | Rollback automation, canary |
| **Backpressure failure** | Producer 10× normal rate | Load shedding, queue depth |
| **Cache eviction storm** | Flush Redis | Cache stampede, request coalescing |
| **Configuration push** | Bad config rolled to all instances | Config validation, gradual rollout |

## Tools

### Toxiproxy (network-level)

The most flexible tool. Sits between your service and a dependency. Lets you inject latency, drop packets, return errors, **per dependency, per environment**.

```typescript
// Toxiproxy API client
import { Toxiproxy } from "toxicli";

const toxiproxy = new Toxiproxy("http://localhost:8474");

// Create a proxy for the user service
const userProxy = await toxiproxy.createProxy({
  name: "user-service",
  listen: "127.0.0.1:20001",
  upstream: "user-service:8080",
});

// Add 5 seconds of latency
const latency = await userProxy.addToxic("latency", {
  attributes: { latency: 5000 },
});

// Add 50% packet loss
await userProxy.addToxic("bandwidth", {
  attributes: { rate: 100 },  // 100 KB/s
});

// Run the experiment for 5 minutes
await sleep(5 * 60_000);

// Cleanup
await latency.remove();
await userProxy.destroy();
```

**Used in production by Shopify, Yelp, etc.** for both development and chaos experiments.

### Chaos Monkey (Netflix)

Terminates EC2 instances / pods on a schedule. The original. "What if your EC2 instance disappears right now?" Tests that your service can lose a node and still serve traffic.

- Open source: https://github.com/Netflix/chaosmonkey
- Modern versions: Spinnaker + Chaos Monkey, or **Chaos Mesh** for K8s

### Gremlin (commercial)

Failure-as-a-Service. Web UI. Broad attack types: CPU, memory, disk, network, process kill, clock skew. Safest option for getting started — built-in abort, blast radius controls, scheduling.

### Litmus (Kubernetes)

K8s-native chaos engineering. CRDs for chaos experiments. Used in K8s-heavy orgs (databases, microservices, ingress chaos).

### ChaosBlade (Alibaba)

Open source, supports host-level + K8s + multi-language. Used in Alibaba Cloud.

### AWS Fault Injection Service / Azure Chaos Studio

Managed services in the cloud. Use the cloud provider's primitives (e.g. terminate instance, partition VPC, fail over RDS).

## Game Days

A **game day** is a scheduled, multi-hour (or multi-day) exercise where the team runs a series of chaos experiments together.

### Format

```text
T-1 week:   Plan. Pick 3-5 experiments. Define steady-state, hypothesis, blast radius, abort criteria. Assign roles.
T-1 day:    Review with on-call + incident commander. Make sure runbooks are current.
T-0:        Game day. 4-8 hours. Use a war room or Zoom.

  09:00     Stand-up: review the plan, assign roles
  09:15     Experiment 1: inject X, measure, learn
  10:30     Debrief experiment 1, decide on next
  10:45     Experiment 2: ...
  12:00     Lunch
  13:00     Experiment 3: ...
  15:00     Debrief: what did we learn? what do we fix?

T+1 day:    Write up findings. File tickets for fixes.
T+1 week:   Re-run the experiments that failed. Verify the fixes.
T+1 month:  Run a smaller game day (1-2 hours) to keep muscle memory.
T+1 quarter: Full game day.
```

### Roles

- **Incident commander** — runs the experiments; calls abort.
- **Observer(s)** — watches metrics, traces, user impact.
- **Scribe** — takes notes; writes up findings.
- **Customer advocate** — "is this experiment going to break real users? what's the rollback?"

### Critical Rule: Production with Permission

Game days should run in **production** (or prod-like staging) with:
- **Pre-announced to stakeholders** (engineering, support, customer success)
- **Blameless** (no naming, no shaming, no punishment for "bad" findings)
- **Documented** (everything is recorded; the value is in the findings, not the drama)
- **A real abort switch** (the ability to stop the experiment in < 30 seconds)

If the team is afraid to run chaos in production, the org is not ready. Most teams start with **pre-production** (staging / canary) and graduate to production as confidence grows.

## Production Examples

### Netflix

- **Chaos Monkey** terminates random EC2 instances in production every business day.
- **ChAP** (Chaos Automation Platform) runs experiments continuously.
- **FIT** (Failure Injection Testing) runs entire failure scenarios (e.g. "simulate a full AWS region failure") in production, with a few-percent blast radius.
- Found and fixed: instance termination didn't always trigger re-routing within the LB's health-check window; EBS volume reattachment time varied 2-30s.

### Stripe

- Game days quarterly. Whole team. 4-6 hours.
- Each engineer proposes one experiment.
- Documented in an internal wiki. Findings are tracked as P0/P1 issues.
- Found and fixed: certificate renewal on the CDN was on a 60-day rotation but the alerting was on a 14-day window; if alerting broke, cert expired.

### Amazon

- **Game days** are mandatory. New service launches require a chaos game day.
- **Cell-based architecture** (the AWS design where each cell is isolated) was a result of game days exposing cross-cell failure modes.

### Google

- **DiRT (Disaster Recovery Testing)** is a yearly, week-long exercise where entire production systems are taken down or heavily impaired.
- The famous Google DiRT 2017 included a "DNS apocalypse" and a "Paxos leader failure storm".

## Code Example: A Simple Chaos Test with Toxiproxy

```typescript
// test/chaos/cascading-failure.test.ts
import { Toxiproxy } from "toxicli";

describe("chaos: cascading failure", () => {
  let proxy: any;

  beforeAll(async () => {
    proxy = await new Toxiproxy("http://localhost:8474").createProxy({
      name: "user-service-test",
      listen: "127.0.0.1:20001",
      upstream: "user-service:8080",
    });
  });

  afterAll(async () => {
    await proxy.destroy();
  });

  it("circuit breaker opens when user-svc returns 50% errors", async () => {
    // 1. Baseline: p99 < 200ms, error rate < 0.1%
    const baseline = await measureLatencyAndErrors();
    expect(baseline.p99).toBeLessThan(200);
    expect(baseline.errorRate).toBeLessThan(0.001);

    // 2. Inject 50% errors
    await proxy.addToxic("latency", { attributes: { latency: 0 } });
    await proxy.addToxic("bandwidth", { attributes: { rate: 1 } }); // effectively timeout

    // 3. Wait for circuit breaker to engage
    await sleep(5_000);

    // 4. Measure: p99 may be high, but error rate should stay bounded
    const duringFailure = await measureLatencyAndErrors();
    expect(duringFailure.errorRate).toBeLessThan(0.01); // 1% — circuit breaker working
    expect(duringFailure.p99).toBeLessThan(1000); // circuit breaker should fail fast

    // 5. Cleanup
    await proxy.removeAllToxics();

    // 6. Verify recovery
    await sleep(10_000);
    const after = await measureLatencyAndErrors();
    expect(after.p99).toBeLessThan(200);
    expect(after.errorRate).toBeLessThan(0.001);
  });
});
```

This is a **chaos test** that you run in CI. It fails if the circuit breaker doesn't engage, or if the system doesn't recover.

## Common Mistakes

- **No steady-state hypothesis.** "Let's just kill an instance and see what happens" is not an experiment. It's a stunt.
- **Too large a blast radius.** Killing 50% of production to "see what happens" is an outage, not a chaos experiment.
- **No abort switch.** Once injected, no way to stop. Then the experiment becomes the outage.
- **No customer advocate.** Experiments that break paying customers during a game day. Lose trust fast.
- **Blaming people for findings.** "Why didn't you know this would break?" — the whole point is to discover what you don't know.
- **Running once and stopping.** A single game day is a snapshot. Continuous experimentation is the goal.
- **Skipping the post-mortem.** Findings sit in a doc that nobody reads. Tie findings to tickets with owners and due dates.
- **Testing only the happy-path failure modes.** You test "instance dies". You don't test "DNS resolver returns stale records for 30s" or "NTP jumps 1 hour forward".
- **Chaos in production without permission.** Surprise outages. The platform team loses the right to run chaos.
- **No observability during the experiment.** You inject a failure, you don't have metrics, you don't know what happened. Useless.
- **Confusing load tests with chaos tests.** Load tests (50-quality/50.1-testing/50.1.11-performance-load-testing.md) test **expected** behavior under expected load. Chaos tests **unexpected** behavior under failure.

## Best Practices

1. **Start with a clear steady-state.** 2-3 metrics. Observable. If you can't define it, you can't test it.
2. **Start small.** 1 instance, 1 region, 1% of users. Grow the blast radius as confidence grows.
3. **Always have an abort switch.** Tested. < 30 seconds to halt.
4. **Run in production.** Production is the only environment that's actually production. With a small blast radius and stakeholder permission.
5. **Document the hypothesis before the experiment.** "We believe X will stay under Y during Z failure."
6. **Measure deviation, not success.** Compare before/during/after.
7. **Tie findings to action.** Tickets with owners and due dates. Re-run the experiment to verify the fix.
8. **Blameless post-mortems.** Even for "we broke production during a game day". Focus on the system, not the person.
9. **Schedule continuous experiments.** ChAP-style. Game days quarterly, smaller experiments monthly, micro-experiments on every deploy.
10. **Test the top 5 failure modes first.** Instance death, AZ outage, dependency slow, dependency errors, deploy during peak.
11. **Coordinate with on-call + customer success.** No surprises. They should know chaos is happening.
12. **Build a chaos library.** Common experiments as code. Reusable across services.

## When to Use Chaos

| Scenario | Chaos? |
|----------|--------|
| **New service launches** | ✅ Game day before public launch |
| **Major refactor** | ✅ Game day before traffic cutover |
| **Quarterly** | ✅ Game day |
| **Every deploy** | ✅ Micro-experiment: kill a canary pod |
| **After an incident** | ✅ Add the incident as a chaos experiment (regression test) |
| **Before a holiday** | ✅ Game day (Black Friday, holiday weekend) |
| **Single-team / single-service** | ✅ Start with Toxiproxy + circuit breaker tests in CI |
| **Multi-team / 50+ services** | ✅ ChAP-style continuous chaos |
| **Critical infra (banking, medical)** | ⚠️ Very carefully, with stakeholder sign-off |
| **Pre-launch / pre-product-market-fit** | ❌ Too early; focus on getting the product right |

## Chaos vs Load Testing vs Testing in General

| | Unit test | Integration test | Load test | Chaos test |
|--|-----------|------------------|-----------|------------|
| **What it tests** | A function | Components together | Expected traffic | Unexpected failure |
| **When it runs** | Every commit | Every commit | Before launch | Game day / continuous |
| **Failure injected** | Mock inputs | Mock services | More traffic | Real failure (kill, slow, error) |
| **Pass condition** | Output matches | Components integrate | System handles N req/s | Steady-state stays within bounds |
| **In production?** | No | No | Sometimes | Yes (with small blast radius) |

**They are complementary, not alternatives.** You need all four.

| Concern | Chaos Engineering |
|---------|-------------------|
| Cost of tools | Toxiproxy + chaos libraries = free; Gremlin = $$$ |
| Cost of game days | Engineering time (1 day/quarter × team size) |
| Cost of in-prod chaos | Slightly higher CPU/memory for the chaos sidecar |
| Customer impact | **Contained** — small blast radius + abort switch |
| Observability cost | Standard (your existing dashboards) |
| ROI | **High** — finds bugs that no other technique can find |

## Summary

- **Chaos engineering** = hypothesis-driven experiments that inject real-world failures into your system, in production, with a small blast radius.
- **The 4 principles**: steady-state hypothesis, real-world events, run in production, automate.
- **The 5 stages**: define steady-state, hypothesize, run, measure, learn.
- **Tools**: Toxiproxy, Chaos Monkey, Gremlin, Litmus, ChaosBlade, cloud-provider services.
- **Game day** = scheduled, multi-hour exercise. Quarterly at minimum. Blameless.
- **In interviews: name the steady-state, name the blast radius, name the abort criteria, name what you learned.**

# WCAG Overview

A booking form signals its error with only a red border. Someone who cannot distinguish that color never learns what failed; someone listening to the page may never encounter the change at all. The question is whether the user can complete and recover from the task — not whether the interface looks familiar.

```html
<label for="email">Email</label>
<input id="email" type="email" aria-invalid="true" aria-describedby="email-error">
<p id="email-error">Enter an email address, like name@example.com.</p>
```

## Definition

**WCAG** (Web Content Accessibility Guidelines) is the W3C standard of testable **success criteria** that make web content perceivable, operable, understandable and robust. It gives teams a shared way to describe and check barriers in content and interaction.

> **Textbook Definition:** The Web Content Accessibility Guidelines are a W3C standard of testable success criteria for making web content perceivable, operable, understandable and robust, with defined conformance levels and requirements.

## First Principles

An interface carries information through presentation, structure and interaction — perceived through sight, magnification, speech or braille, and operated with pointer, keyboard, voice or switch. A cue confined to one channel excludes another. So separate meaning from presentation: identify the field and its error in text, associate them programmatically, and preserve a usable route back to the field.

## How It Works

### 1. Turn Principles Into Checks

The four principles are abbreviated **POUR**. They organize related questions rather than prescribing four independent fixes. [W3C explains their relationship](https://www.w3.org/WAI/WCAG22/Understanding/intro#understanding-the-four-principles-of-accessibility).

| Principle | Question in the booking example |
| -------------- | ------------------------------------------------------------------------------------------- |
| Perceivable | Is the error available as text and through the supported presentation? |
| Operable | Can the user reach the field and submit without a pointer? |
| Understandable | Does the error say what happened and how to correct it? |
| Robust | Do the browser and assistive technology expose the control's name, state and relationships? |

A **guideline** describes a goal; a **success criterion** states a testable requirement with conditions and exceptions; a **technique** describes one possible implementation. A technique is not the entire standard, and an audit tool's rule is not necessarily a complete test of its criterion. [WCAG's layers of guidance](https://www.w3.org/TR/WCAG22/#wcag-2-layers-of-guidance) distinguish these roles.

### 2. Trace One Error Across the Whole Task

- **Label the field**: a visible label identifies the email input and stays associated with it — placeholder text alone does not survive typing.
- **Report the failure in text**: submitting an empty field produces a specific message; the application marks the field invalid and connects the message to it.
- **Make the failure discoverable**: a focus and notification strategy surfaces the failed submission without competing announcements, so the user can return to the field, correct it and keep other entered values.
- **Clear obsolete state**: on correction, stale errors are removed. The server still validates independently and may return a different error needing the same recoverable treatment.

The [forms chapter](50.2.05-forms-and-labels.md) owns the working implementation. Adding `aria-invalid` alone does not implement these steps, and a clean initial-form screenshot does not establish them.

### 3. Read a Conformance Claim Correctly

**Level A** requires the applicable A criteria; **AA** includes A and AA; **AAA** includes all three. These are cumulative requirements, not checklist percentages or audit scores — and a stated target must name the WCAG version and level. Conformance applies to full pages and complete processes: a checkout cannot claim success by evaluating only its first page while excluding payment. [Understanding conformance](https://www.w3.org/WAI/WCAG22/Understanding/conformance.html).

A passing component audit is useful evidence within a larger evaluation, not automatically a page or product claim. The standard is technical guidance; any legal or contractual obligation depends on its own scope and referenced version, so record that requirement explicitly. Conformance also does not cover every possible user need.

### 4. Pin the Version Before Choosing the Target

For a new evaluation, start with published WCAG 2.2 and confirm the version named by any contract or regulation — never treat an emerging draft as an established requirement. WCAG 2.2 adds criteria for barriers such as obscured keyboard focus, dragging-only operations, repeated data entry and accessible authentication. A sticky footer can hide the focused input even though its outline exists. [What is new in WCAG 2.2](https://www.w3.org/WAI/standards-guidelines/wcag/new-in-22/).

WCAG 2.2 removes the older Parsing criterion 4.1.1. That does not make duplicate IDs or malformed relationships harmless — they still break labels, names and state. Keep the target version visible when reporting findings. [WCAG version guidance](https://www.w3.org/WAI/standards-guidelines/wcag/).

## Summary

WCAG connects user barriers to testable criteria: explain the failed task, implement the necessary relationships and behavior, then evaluate complete pages and processes against a named version and level. Read conformance claims for their full-page scope and cumulative levels, and let automated findings support — never replace — manual and assistive-technology checks.

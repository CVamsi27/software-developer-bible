# ARIA (Accessible Rich Internet Applications)

## Definition

ARIA (Accessible Rich Internet Applications) is a set of attributes that supplies additional meaning for dynamic content and complex interface controls. It helps a browser expose their role, name, relationships and changing state to assistive technology.

> **Textbook Definition:** WAI-ARIA is a specification of roles, states and properties that communicate interface semantics to accessibility APIs. It supplements HTML semantics but does not implement keyboard interaction or visual behavior.

If a shipping-details button opens a panel, a listener needs to know both what the button does and whether its panel is currently open. aria-expanded supplies that state; application code must actually open or close the panel.

## First Principles

The visible DOM and an assistive technology's representation need not contain the same information. Browsers derive an **accessibility tree** from HTML semantics, text and accessibility attributes, then expose it through platform APIs. Styling a div to look like a button does not give it a button's activation behavior or meaning.

Choose a native control when it expresses the interaction. Where it does not, supplying a semantic contract also creates an obligation to implement the corresponding behavior. A role without that behavior is a promise the component cannot keep. The ARIA specification defines semantics; the WAI-ARIA Authoring Practices Guide (APG) recommends widget patterns but is not itself a conformance standard. [APG explains this distinction](https://www.w3.org/WAI/ARIA/apg/about/introduction/).

## Separate the parts of the contract

A **role** describes what the element is, a **name** identifies it, and states/properties describe relevant conditions and relationships. The distinction is useful when diagnosing a control: a correct name cannot compensate for a missing role, and a correct role cannot compensate for missing keyboard operation.

| Information | Example | Required implementation |
| ------------ | ------------------------------- | --------------------------------------- |
| Role | Native button | Supported activation and focus behavior |
| Name | Visible “Shipping details” text | Meaningful task-specific label |
| State | aria-expanded=false | Panel is actually closed |
| Relationship | aria-controls=shipping-panel | The referenced panel exists |
| Description | aria-describedby=shipping-hint | Additional useful instructions exist |

Visible text, labels and explicit naming attributes can contribute to an accessible name. For a button, aria-label or aria-labelledby can override its text-derived name; adding a different name can therefore make a visually labeled control harder to operate by voice. Keep the visible label represented in the name. A description adds context rather than replacing the name. [Names and descriptions guidance](https://www.w3.org/WAI/ARIA/apg/practices/names-and-descriptions/).

## Code Examples

### Keep a disclosure's state and panel synchronized

Save this complete fixture as shipping.html and open it in a browser. It is a disclosure, not an application menu. The native button handles Tab, Enter and Space; the script owns the panel state.

```html
<!doctype html>
<html lang="en">
<meta charset="utf-8">
<title>Shipping details disclosure</title>
<button type="button" id="shipping-toggle"
        aria-expanded="false" aria-controls="shipping-panel">
  Shipping details
</button>
<div id="shipping-panel" hidden>
  <p>Standard delivery takes five to seven working days.</p>
  <a href="#returns">Read the returns policy</a>
</div>
<h2 id="returns">Returns</h2>
<p>Return unused items within the stated return period.</p>
<script>
  const toggle = document.getElementById('shipping-toggle');
  const panel = document.getElementById('shipping-panel');
  toggle.addEventListener('click', () => {
    const expanded = toggle.getAttribute('aria-expanded') === 'true';
    panel.hidden = expanded;
    toggle.setAttribute('aria-expanded', String(!expanded));
  });
</script>
</html>
```

Initially the button is collapsed and the hidden panel's link is outside sequential keyboard navigation. Enter activates the button, reveals the panel and sets expanded=true. Focus stays on the button, and Tab can reach the revealed link. Space closes the disclosure again. The script sets both representations from one transition; changing only the attribute would leave contradictory behavior. [Disclosure pattern](https://www.w3.org/WAI/ARIA/apg/patterns/disclosure/).

For more complex controls, first identify the interaction pattern. Tabs, listboxes and menus have different focus/selection rules. Marking site-navigation links as menuitems creates an application-menu contract that ordinary links alone do not fulfill. The [keyboard chapter](50.2.03-keyboard-navigation.md) owns the working tabs and dialog examples.

## Hiding and disabling change different things

**hidden** removes the shown panel from rendering and ordinary navigation. **aria-hidden=true** removes content from the accessibility representation but does not hide it visually or prevent keyboard focus. Do not put it on a focusable control or an ancestor containing interactive descendants. Hiding only the semantics can leave a keyboard user focused on something a screen reader cannot identify.

A native **disabled** control receives browser-enforced disabled behavior. **aria-disabled=true** communicates a state but leaves activation and focus behavior to the application. Use that distinction deliberately when an unavailable action should remain discoverable, explaining the reason and blocking every activation path. Fixing only its color does not enforce the state.

For a modal, aria-modal=true communicates the intended modality but does not make the background inert, contain focus or close on Escape. Use a supported native dialog or an implementation that fulfills the complete contract; an attribute-only example is incomplete.

## Dynamic changes need an announcement strategy

A **live region** lets an update be conveyed without moving keyboard focus. Create the intended region before updating its text. role=status has polite live semantics; role=alert has assertive semantics. Use status for a useful completion update and reserve interruption for an urgent change. Combining contradictory live settings or announcing every keystroke can make the task harder.

An announcement is not a guaranteed spoken sentence at a precise instant: support, timing and the current assistive-technology interaction matter. Test the supported browser/reader combinations. A region that announces a form error also does not connect that error to its field; names, descriptions, invalid state and focus recovery remain distinct responsibilities.

## Summary

ARIA describes interface semantics through accessibility APIs. Native HTML often supplies the role and behavior together; custom widgets need both the exposed contract and its implementation. Keep state synchronized, distinguish hiding from disabling, and test naming, focus and announcements in the supported environment.

# Keyboard Navigation

## Definition

Keyboard navigation is the ability to reach and operate website functionality through a keyboard interface, without requiring a mouse. It supports people using keyboards, switch controls and other input methods that expose keyboard commands.

> **Textbook Definition:** Keyboard accessibility is the ability to reach and operate applicable interface functionality through a keyboard interface, with usable focus order, visible focus and no unintended keyboard traps.

A checkout may have correctly named controls and still fail if Tab skips its payment button or a dialog keeps focus after closing. A useful keyboard implementation covers the whole journey: entry, movement, activation, cancellation and recovery.

## First Principles

A pointer can choose a visible target directly. Sequential keyboard navigation needs a predictable next target and a visible indication of the current one. When a component replaces, hides or removes that target, the application needs a sensible continuation; otherwise the user's place can be lost.

Keep document structure in a meaningful reading order, use native controls for their activation behavior and add a component-specific movement model only when it improves navigation. A composite widget can offer one Tab stop and internal arrow-key movement without making every item a separate stop.

## Focus, selection and activation are different

**Focus** identifies the current keyboard target. **Selection** identifies the chosen item. **Activation** performs an action or makes a selection. A tab may receive focus before its panel is selected, and moving focus to a link does not follow it.

Tab and Shift+Tab usually move between controls in sequential order. Native buttons activate with Enter or Space; links activate with Enter. Composite controls use the keys of their pattern, such as arrows within a tablist. Do not intercept arrow keys globally: text fields need them for editing. [Keyboard interface guidance](https://www.w3.org/WAI/ARIA/apg/practices/keyboard-interface/).

## Choose the focus order deliberately

Native inputs, buttons and links with href are already focusable. **tabindex=0** adds a suitable custom target to ordinary sequential navigation. **tabindex=-1** allows a deliberate programmatic focus target without adding a Tab stop. Positive values create an earlier numbered order and are difficult to keep consistent with the rest of the page; fix the structure rather than assigning a long custom sequence.

DOM order usually determines ordinary sequential order, with browser/HTML qualifications. Reordering a form visually with CSS can leave its reading and keyboard sequence confusing. Check the actual journey instead of assuming that a visual layout establishes its order.

A skip link bypasses repetitive navigation. Its target must exist and be useful when reached. This fragment uses a programmatically focusable main region:

```html
<a class="skip-link" href="#main-content">Skip to main content</a>
<nav aria-label="Primary"><a href="/">Home</a></nav>
<main id="main-content" tabindex="-1">
  <h1>Booking details</h1>
  <label for="customer-name">Name</label>
  <input id="customer-name" autocomplete="name">
  <button type="button">Continue</button>
</main>
```

Keep the link visible on focus and above fixed headers. Test where focus and the next Tab go after activation; scrolling to the main heading is not the whole observation.

## Code Examples

### Manual-activation tabs keep focus separate from selection

Save this complete fixture as tabs.html. It demonstrates three local, horizontal, left-to-right tabs with static panels. **Roving tabindex** means exactly one tab is a sequential Tab stop; arrow keys change that stop and move focus. Enter, Space or a click activates the focused tab. The page uses manual activation, so arrow movement alone does not replace the panel.

```html
<!doctype html>
<html lang="en">
<meta charset="utf-8">
<title>Manual-activation tabs</title>
<style>
  :focus-visible { outline: 3px solid #005fcc; outline-offset: 3px; }
  [aria-selected="true"] { font-weight: bold; text-decoration: underline; }
</style>
<div id="product-tabs">
  <div role="tablist" aria-label="Product information">
    <button type="button" role="tab" id="details-tab"
      aria-selected="true" aria-controls="details-panel" tabindex="0">Details</button>
    <button type="button" role="tab" id="delivery-tab"
      aria-selected="false" aria-controls="delivery-panel" tabindex="-1">Delivery</button>
    <button type="button" role="tab" id="returns-tab"
      aria-selected="false" aria-controls="returns-panel" tabindex="-1">Returns</button>
  </div>
  <section role="tabpanel" id="details-panel" aria-labelledby="details-tab" tabindex="0">
    <p>Hardcover book, 240 pages.</p>
  </section>
  <section role="tabpanel" id="delivery-panel" aria-labelledby="delivery-tab" tabindex="0" hidden>
    <p>Standard delivery takes five to seven working days.</p>
  </section>
  <section role="tabpanel" id="returns-panel" aria-labelledby="returns-tab" tabindex="0" hidden>
    <p>Return unused items within the stated return period.</p>
  </section>
</div>
<a href="#after-tabs" id="after-tabs">Continue reading</a>
<script>
  const root = document.getElementById('product-tabs');
  const list = root.querySelector('[role="tablist"]');
  const tabs = [...list.querySelectorAll('[role="tab"]')];
  const panels = tabs.map(tab => document.getElementById(tab.getAttribute('aria-controls')));

  function focusTab(index) {
    tabs.forEach((tab, i) => { tab.tabIndex = i === index ? 0 : -1; });
    tabs[index].focus();
  }
  tabs.forEach((tab, index) => {
    tab.addEventListener('click', () => {
      focusTab(index);
      tabs.forEach((item, i) => item.setAttribute('aria-selected', String(i === index)));
      panels.forEach((panel, i) => { panel.hidden = i !== index; });
    });
  });
  list.addEventListener('keydown', event => {
    if (event.altKey || event.ctrlKey || event.metaKey) return;
    const current = tabs.indexOf(document.activeElement);
    if (current < 0) return;
    let next;
    switch (event.key) {
      case 'ArrowRight': next = (current + 1) % tabs.length; break;
      case 'ArrowLeft': next = (current - 1 + tabs.length) % tabs.length; break;
      case 'Home': next = 0; break;
      case 'End': next = tabs.length - 1; break;
      default: return;
    }
    event.preventDefault();
    focusTab(next);
  });
</script>
</html>
```

Trace Details → ArrowRight → Delivery. Focus moves and the one tabindex=0 moves, but Details stays selected and visible. Enter activates Delivery: selection and the visible panel change together. Tab leaves the tablist for the visible panel, then the following link. Home/End and wraparound work inside the list without scrolling the page.

Automatic activation changes selection during focus movement. Choose it only when panel display is sufficiently immediate; otherwise arrow navigation can repeatedly trigger expensive loading. Dynamic/disabled items, vertical layouts and right-to-left conventions need additional defined behavior. [Tabs pattern](https://www.w3.org/WAI/ARIA/apg/patterns/tabs/).

### A native modal owns entry, blocking and exit

Save this separately as dialog.html. Opening a modal differs from adding aria-modal to a visible div: showModal puts this dialog in the browser's modal layer and makes the rest of its document inert. The fixture chooses a safe initial action and restores the connected trigger after closing.

```html
<!doctype html>
<html lang="en">
<meta charset="utf-8">
<title>Keyboard dialog lifecycle</title>
<button type="button" id="open-confirm">Review cancellation</button>
<a href="#background" id="background">Background action</a>
<dialog id="confirm-dialog" aria-labelledby="confirm-title">
  <h2 id="confirm-title">Cancel this draft?</h2>
  <p>This fixture only demonstrates focus and dismissal.</p>
  <form method="dialog">
    <button id="keep-draft" value="keep" autofocus>Keep editing</button>
    <button value="cancel">Cancel draft</button>
  </form>
</dialog>
<script>
  const trigger = document.getElementById('open-confirm');
  const dialog = document.getElementById('confirm-dialog');
  trigger.addEventListener('click', () => {
    if (!dialog.open) dialog.showModal();
  });
  dialog.addEventListener('close', () => {
    if (trigger.isConnected) trigger.focus();
  });
</script>
</html>
```

Enter on the trigger opens the dialog and focuses Keep editing. Keyboard navigation cannot activate the background action while the dialog is modal. Escape or a dialog-form button closes it; focus returns to the trigger. method=dialog closes locally and records a return value; it does not submit a cancellation to a server. [Native dialog behavior](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/dialog).

If the trigger disappears, choose the next useful task location. For a long explanation, initial focus may belong on suitable static content rather than the first action; irreversible operations also warrant a safe initial choice. Custom modal implementations must manage inert background, focus entry/containment, dismissal and recovery across updates, including empty or disabled focus targets. [Modal dialog pattern](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/).

## Focus must remain visible and usable

Use a visible focus indicator with sufficient contrast in each theme. Check it against surrounding colors and at zoom, not just on a white canvas. A sticky header can obscure a correctly outlined target; appropriate scroll spacing helps but needs actual narrow-screen evaluation. The [contrast chapter](50.2.04-color-and-contrast.md) owns color measurement.

In forced-color environments, retain outlines and allow the user's palette. A component can use a system-color outline, such as Highlight, inside @media(forced-colors:active). Box shadow alone may disappear. Do not suppress every :focus outline without a reliable visible replacement.

When removing an item, move focus to the next sensible item or its controlling action. When a client-rendered route changes, choose an informative new page target without stealing focus during unrelated updates. Focus management is task continuity, not an automatic performance improvement.

## Shortcuts need their own boundaries

A shortcut supplements an operable control. aria-keyshortcuts describes a binding but does not implement it. Avoid overriding browser/assistive-technology commands, respect text editing and composition, and offer the necessary way to turn off, remap or scope single-character shortcuts. A global slash handler can otherwise interrupt typing in a contenteditable surface that an input-only guard misses.

## Summary

Keyboard operation needs predictable entry, movement, activation and recovery. Use native behavior where it fits; composite controls add scoped movement with explicit focus/selection rules. A modal owns its whole lifecycle, and focus remains visible, unobscured and useful after state changes.

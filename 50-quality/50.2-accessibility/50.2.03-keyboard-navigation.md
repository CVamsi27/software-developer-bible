# Keyboard Navigation

A checkout has correctly named controls — yet Tab skips its payment button, and a dialog keeps focus after closing. A useful keyboard implementation covers the whole journey: entry, movement, activation, cancellation and recovery.

```html
<a class="skip-link" href="#main-content">Skip to main content</a>
<nav aria-label="Primary"><a href="/">Home</a></nav>
<main id="main-content" tabindex="-1">
  <h1>Booking details</h1>
  <label for="customer-name">Name</label>
  <input id="customer-name" autocomplete="name">
  <button type="button">Continue</button>
</main>
```

## Definition

**Keyboard navigation** is the ability to reach and operate functionality through a **keyboard interface**, without requiring a mouse. It supports people using keyboards, switch controls and other input methods that expose keyboard commands.

> **Textbook Definition:** Keyboard accessibility is the ability to reach and operate applicable interface functionality through a keyboard interface, with usable focus order, visible focus and no unintended keyboard traps.

## First Principles

A pointer chooses a visible target directly; sequential keyboard navigation needs a predictable next target and a visible indication of the current one. When a component replaces, hides or removes that target, the application needs a sensible continuation — otherwise the user's place is lost. Keep document structure in meaningful reading order, use native controls for their activation behavior, and add a component-specific movement model only when it improves navigation.

## How It Works

### 1. Separate Focus, Selection and Activation

**Focus** identifies the current keyboard target. **Selection** identifies the chosen item. **Activation** performs an action or makes a selection. A tab may receive focus before its panel is selected, and moving focus to a link does not follow it.

Tab and Shift+Tab move between controls in sequential order. Native buttons activate with Enter or Space; links activate with Enter. Composite controls use their pattern's keys, such as arrows within a tablist. Never intercept arrow keys globally — text fields need them for editing. [Keyboard interface guidance](https://www.w3.org/WAI/ARIA/apg/practices/keyboard-interface/).

### 2. Choose the Focus Order Deliberately

Native inputs, buttons and links with `href` are already focusable. **`tabindex="0"`** adds a suitable custom target to ordinary sequential navigation. **`tabindex="-1"`** creates a deliberate programmatic focus target without adding a Tab stop. Positive values create an earlier numbered order that is difficult to keep consistent with the rest of the page — fix the structure instead of assigning a long custom sequence.

DOM order usually determines sequential order, with browser and HTML qualifications: reordering a form visually with CSS can leave its reading and keyboard sequence confusing. Check the actual journey instead of assuming the visual layout establishes its order. A **skip link** bypasses repetitive navigation, as in the hook example above — but its target must exist and be useful when reached. Keep the link visible on focus and above fixed headers, and test where focus and the next Tab go after activation; scrolling to the heading is not the whole observation.

### 3. Keep Manual-Activation Tabs' Focus Separate From Selection

Save this complete fixture as `tabs.html`. It demonstrates three local, horizontal, left-to-right tabs with static panels. **Roving tabindex** means exactly one tab is a sequential Tab stop; arrow keys change that stop and move focus, while Enter, Space or a click activates the focused tab. The page uses manual activation, so arrow movement alone does not replace the panel.

```html
<!doctype html>
<html lang="en">
<meta charset="utf-8">
<title>Manual-activation tabs</title>
<style>
  :focus-visible { outline: 3px solid #005fcc; outline-offset: 3px; }
  [aria-selected="true"] { font-weight: bold; text-decoration: underline; }
</style>
<div id="product-tabs">
  <div role="tablist" aria-label="Product information">
    <button type="button" role="tab" id="details-tab"
      aria-selected="true" aria-controls="details-panel" tabindex="0">Details</button>
    <button type="button" role="tab" id="delivery-tab"
      aria-selected="false" aria-controls="delivery-panel" tabindex="-1">Delivery</button>
    <button type="button" role="tab" id="returns-tab"
      aria-selected="false" aria-controls="returns-panel" tabindex="-1">Returns</button>
  </div>
  <section role="tabpanel" id="details-panel" aria-labelledby="details-tab" tabindex="0">
    <p>Hardcover book, 240 pages.</p>
  </section>
  <section role="tabpanel" id="delivery-panel" aria-labelledby="delivery-tab" tabindex="0" hidden>
    <p>Standard delivery takes five to seven working days.</p>
  </section>
  <section role="tabpanel" id="returns-panel" aria-labelledby="returns-tab" tabindex="0" hidden>
    <p>Return unused items within the stated return period.</p>
  </section>
</div>
<a href="#after-tabs" id="after-tabs">Continue reading</a>
<script>
  const root = document.getElementById('product-tabs');
  const list = root.querySelector('[role="tablist"]');
  const tabs = [...list.querySelectorAll('[role="tab"]')];
  const panels = tabs.map(tab => document.getElementById(tab.getAttribute('aria-controls')));

  function focusTab(index) {
    tabs.forEach((tab, i) => { tab.tabIndex = i === index ? 0 : -1; });
    tabs[index].focus();
  }
  tabs.forEach((tab, index) => {
    tab.addEventListener('click', () => {
      focusTab(index);
      tabs.forEach((item, i) => item.setAttribute('aria-selected', String(i === index)));
      panels.forEach((panel, i) => { panel.hidden = i !== index; });
    });
  });
  list.addEventListener('keydown', event => {
    if (event.altKey || event.ctrlKey || event.metaKey) return;
    const current = tabs.indexOf(document.activeElement);
    if (current < 0) return;
    let next;
    switch (event.key) {
      case 'ArrowRight': next = (current + 1) % tabs.length; break;
      case 'ArrowLeft': next = (current - 1 + tabs.length) % tabs.length; break;
      case 'Home': next = 0; break;
      case 'End': next = tabs.length - 1; break;
      default: return;
    }
    event.preventDefault();
    focusTab(next);
  });
</script>
</html>
```

Trace Details → ArrowRight → Delivery: focus moves and the one `tabindex="0"` moves, but Details stays selected and visible. Enter activates Delivery — selection and the visible panel change together. Tab leaves the tablist for the visible panel, then the following link. Automatic activation instead changes selection during focus movement; choose it only when panel display is sufficiently immediate, or arrow navigation repeatedly triggers expensive loading. [Tabs pattern](https://www.w3.org/WAI/ARIA/apg/patterns/tabs/).

### 4. Let a Native Modal Own Entry, Blocking and Exit

Save this separately as `dialog.html`. Opening a modal differs from adding `aria-modal` to a visible div: `showModal` puts the dialog in the browser's modal layer and makes the rest of its document inert. The fixture chooses a safe initial action and restores the connected trigger after closing.

```html
<!doctype html>
<html lang="en">
<meta charset="utf-8">
<title>Keyboard dialog lifecycle</title>
<button type="button" id="open-confirm">Review cancellation</button>
<a href="#background" id="background">Background action</a>
<dialog id="confirm-dialog" aria-labelledby="confirm-title">
  <h2 id="confirm-title">Cancel this draft?</h2>
  <p>This fixture only demonstrates focus and dismissal.</p>
  <form method="dialog">
    <button id="keep-draft" value="keep" autofocus>Keep editing</button>
    <button value="cancel">Cancel draft</button>
  </form>
</dialog>
<script>
  const trigger = document.getElementById('open-confirm');
  const dialog = document.getElementById('confirm-dialog');
  trigger.addEventListener('click', () => {
    if (!dialog.open) dialog.showModal();
  });
  dialog.addEventListener('close', () => {
    if (trigger.isConnected) trigger.focus();
  });
</script>
</html>
```

Enter on the trigger opens the dialog and focuses Keep editing. Keyboard navigation cannot activate the background action while the dialog is modal. Escape or a dialog-form button closes it; focus returns to the trigger. `method="dialog"` closes locally and records a return value — it does not submit a cancellation to a server. [Native dialog behavior](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/dialog).

If the trigger disappears, choose the next useful task location. For a long explanation, initial focus may belong on suitable static content; irreversible operations warrant a safe initial choice. Custom modal implementations must manage inert background, focus entry and containment, dismissal and recovery across updates. [Modal dialog pattern](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/).

### 5. Keep Focus Visible and Give Shortcuts Their Own Boundaries

Use a visible focus indicator with sufficient contrast in each theme — checked against surrounding colors and at zoom, not just on a white canvas. A sticky header can obscure a correctly outlined target; appropriate scroll spacing helps but needs narrow-screen evaluation. The [contrast chapter](50.2.04-color-and-contrast.md) owns color measurement. In forced-color environments retain outlines and allow the user's palette; box shadow alone may disappear, and never suppress every `:focus` outline without a reliable visible replacement.

When removing an item, move focus to the next sensible item or its controlling action. When a client-rendered route changes, choose an informative new page target without stealing focus during unrelated updates. A **shortcut** supplements an operable control: `aria-keyshortcuts` describes a binding but does not implement it. Avoid overriding browser and assistive-technology commands, respect text editing and composition, and offer a way to turn off, remap or scope single-character shortcuts.

## Summary

Keyboard operation needs predictable entry, movement, activation and recovery. Use native behavior where it fits; composite controls add scoped movement with explicit focus and selection rules. A modal owns its whole lifecycle — entry, blocking, dismissal and focus return. Focus stays visible, unobscured and useful after state changes, and shortcuts remain scoped, remappable supplements rather than replacements.

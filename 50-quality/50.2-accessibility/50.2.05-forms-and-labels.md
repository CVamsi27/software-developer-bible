# Forms & Labels

An invalid email should leave the user knowing which field failed, what to change, and how to return to it. A red border, an unnamed input, or a message elsewhere on the page cannot establish that recovery path alone.

```html
<label for="email">Email address (required)</label>
<input id="email" type="email" required autocomplete="email"
       aria-describedby="email-hint" aria-invalid="true">
<p id="email-hint">Use an address where you can receive account messages.</p>
<p id="email-error">Email address: use a format such as reader@example.test.</p>
```

## Definition

**Accessible forms** let users understand, reach, complete and recover from input tasks through supported input methods and assistive technologies. **Labels**, instructions, grouping, validation and focus behavior cooperate to make that possible.

> **Textbook Definition:** An accessible form exposes controls, labels, instructions, relationships and validation feedback in ways that users can perceive and operate across supported input methods and assistive technologies.

## First Principles

A form asks for information under rules. The user must identify each requested value before entering it and retain that context while editing — and when a value fails a rule, the system must connect the failed field, the explanation and the correction action without discarding other work. Input, validation and submission are separate boundaries: a client can assist with format checks, but only the server can enforce its contract and confirm a durable outcome.

## 1. Let a Name Identify and a Description Explain

A visible **label** identifies a control. Explicit `label-for`/`input-id` association and a wrapping label are both native options; clicking an associated label targets its control, and IDs must be unique across the document, including repeated component instances.

A **hint** explains the expected input; an **error** explains the current failure. `aria-describedby` connects these descriptions, while `aria-invalid` communicates invalid state without creating a message or validating the field. Placeholder text can illustrate a format but disappears while typing and never replaces the persistent label. [W3C's labelling guidance](https://www.w3.org/WAI/tutorials/forms/labels/). Use `aria-labelledby` when an existing visible element supplies the appropriate name — and keep visible wording represented in any override so voice users can refer to what they see. A visually hidden label is an intentional exception needing a clear visible cue, not a default for every field.

## 2. Build a Complete Client-Validation and Recovery Fixture

Save this as `form.html` and open it in a browser. It checks a nonblank display name and the browser's basic email-input constraint. It demonstrates the client recovery contract only: no request, no account creation, no proof that an address can receive mail. The form uses `novalidate` because this fixture supplies the full client error interaction — keep native validation unless there is a reason and a tested replacement, since server validation remains necessary either way.

```html
<!doctype html>
<html lang="en">
<meta charset="utf-8">
<title>Recoverable form validation</title>
<style>
  :focus-visible { outline: 3px solid #005fcc; outline-offset: 3px; }
  [aria-invalid="true"] { border: 2px solid #a30000; }
  .error { color: #a30000; }
</style>
<form id="signup" novalidate>
  <h1>Prepare account details</h1>
  <section id="error-summary" aria-labelledby="error-title" tabindex="-1" hidden>
    <h2 id="error-title">Correct the following fields</h2>
    <ul id="error-links"></ul>
  </section>
  <label for="display-name">Display name (required)</label>
  <input id="display-name" name="displayName" required autocomplete="nickname"
         aria-describedby="name-hint">
  <p id="name-hint">Enter the name you want displayed.</p>
  <p id="name-error" class="error" hidden></p>

  <label for="email">Email address (required)</label>
  <input id="email" name="email" type="email" required autocomplete="email"
         aria-describedby="email-hint">
  <p id="email-hint">Use an address where you can receive account messages.</p>
  <p id="email-error" class="error" hidden></p>
  <button type="submit">Check details</button>
  <p id="form-status" role="status"></p>
</form>
<script>
  const form = document.getElementById('signup');
  const summary = document.getElementById('error-summary');
  const list = document.getElementById('error-links');
  const status = document.getElementById('form-status');
  const fields = [
    { input: document.getElementById('display-name'), hint: 'name-hint', error: 'name-error',
      validate: input => input.value.trim() ? '' : 'Display name: enter a name.' },
    { input: document.getElementById('email'), hint: 'email-hint', error: 'email-error',
      validate: input => input.validity.valueMissing ? 'Email address: enter an address.' :
        input.validity.typeMismatch ? 'Email address: use a format such as reader@example.test.' : '' },
  ];
  let submitted = false;

  function updateErrors(moveFocus) {
    list.replaceChildren();
    let count = 0;
    for (const field of fields) {
      const message = field.validate(field.input);
      const error = document.getElementById(field.error);
      error.textContent = message;
      error.hidden = !message;
      field.input.setAttribute('aria-invalid', String(Boolean(message)));
      field.input.setAttribute('aria-describedby',
        message ? `${field.hint} ${field.error}` : field.hint);
      if (message) {
        count++;
        const item = document.createElement('li');
        const link = document.createElement('a');
        link.href = `#${field.input.id}`;
        link.textContent = message;
        link.addEventListener('click', event => {
          event.preventDefault();
          field.input.focus();
        });
        item.append(link);
        list.append(item);
      }
    }
    summary.hidden = count === 0;
    if (count && moveFocus) summary.focus();
    return count;
  }
  form.addEventListener('submit', event => {
    event.preventDefault();
    submitted = true;
    status.textContent = '';
    if (updateErrors(true) === 0) {
      status.textContent = 'Client format checks passed. Server validation is still required.';
    }
  });
  form.addEventListener('input', () => {
    if (submitted) {
      status.textContent = '';
      updateErrors(false);
    }
  });
</script>
</html>
```

Trace an empty submission: both errors become visible and associated with their inputs, and focus moves once to the summary. Activating the email error link focuses Email address, whose hint and error are available through the description relationship. Correcting the value removes its obsolete error and invalid state without moving focus while typing. Valid client input produces the explicitly limited status message — never "saved".

This fixture chooses focused-summary feedback rather than making the summary and every field an assertive alert. Another form may focus the first error or use a suitable live notification. Test the actual announcement strategy; do not move focus to a summary and then immediately to a field under the assumption that speech has finished. [W3C's notification guidance](https://www.w3.org/WAI/tutorials/forms/notifications/).

## 3. Group Options Under the Question They Answer

"Standard" and "Express" identify options but not what the user is choosing. A `fieldset` and `legend` supply the group question while each control keeps its own label:

```html
<fieldset>
  <legend>Shipping method</legend>
  <label><input type="radio" name="shipping" value="standard" checked>Standard: five to seven days</label>
  <label><input type="radio" name="shipping" value="express">Express: two to three days</label>
</fieldset>
```

The shared radio name defines one selection group; the legend describes its purpose. Several independent notification checkboxes can use the same grouping structure while allowing multiple choices. Native selection controls also supply established keyboard behavior. [Grouping guidance](https://www.w3.org/WAI/tutorials/forms/grouping/).

## 4. Express Input Purpose, Not Just Validation

Use appropriate `type`, `autocomplete` and `inputmode` where they express the requested value. `type="email"` provides basic format checking; `autocomplete="email"` identifies personal-data purpose for tools that recognize it; `inputmode` influences the input keyboard but does not enforce validation. Never make telephone numbers arithmetic or discard leading zeros.

For common information about the user, WCAG's Identify Input Purpose criterion applies under its stated conditions and defined purposes — not a claim that every arbitrary field needs a personal-data token. Authentication should support suitable password managers and paste flows. [Identify Input Purpose](https://www.w3.org/WAI/WCAG22/Understanding/identify-input-purpose.html).

## 5. Keep Recovery Intact Across Server and Multi-Step Flows

For server errors, preserve entered values, map field errors to the same relationships, and show a recoverable form-level error when no field owns it. A network timeout can leave an unknown submission outcome — never announce "saved" until the application contract confirms it. The backend's idempotency and retry rules determine what a repeated submission may do.

For a multi-step form, explain progress, preserve previous values, and place focus at an informative heading when the user intentionally changes steps. `aria-current="step"` describes progress; it does not move focus. Never re-request provided information without a reason, and make consequential financial or data actions reviewable or recoverable per their requirements. A disabled submit button can conceal why progress is blocked — prefer discoverable validation, or make the disabled state and its reason clear.

For uploads, show accepted types and size limits before choosing a file, report errors in text, and validate content on the server. The `accept` attribute assists selection; it is not a security boundary. A native input is a useful baseline, but added drag-and-drop and progress behavior need equivalent non-pointer paths.

## Summary

A form communicates the requested value, the rules and the outcome: labels identify, descriptions explain, grouping supplies context, and validation connects failures to correction. Preserve focus and entered work, clear stale errors, and state honestly which client or server boundary succeeded.

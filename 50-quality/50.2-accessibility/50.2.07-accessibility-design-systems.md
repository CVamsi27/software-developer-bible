# Accessibility in Design Systems

## TL;DR

Fixing accessibility one page at a time never scales — you fix it once, inside the design system, and every product inherits it. The modern recipe: build components on **accessible primitives** (Radix UI, React Aria) that own focus management and keyboard semantics; encode contrast themes as **design tokens**; enforce the floor with **lint gates** (`eslint-plugin-jsx-a11y`, axe CI checks); and make a11y part of the **definition of done**, with audit findings flowing back into components rather than into per-app hotfixes.

## Definition

An **accessible design system** is a shared component library plus tokens and process rules such that any product built from it is accessible by construction: the primitives guarantee behavior (focus order, keyboard interaction, ARIA states), tokens guarantee perception (contrast, target sizes), and governance guarantees regression safety (linting, automated audits, DoD criteria).

```text
A11Y-BY-CONSTRUCTION PIPELINE
┌──────────────────────────────────────────────────────────────┐
│ AUDIT (axe, manual SR pass)                                  │
│   │  findings triaged                                        │
│   v                                                          │
│ PRIMITIVES  Radix / React Aria -> unstyled, correct behavior │
│   │                                                          │
│ TOKENS      --color-text-on-surface: oklch(...)  >= 4.5:1    │
│   │         themes: light / dark / high-contrast             │
                                                               │   v                                                          |
│ COMPONENTS  Button, Dialog, Combobox = primitives + tokens   │
│   │                                                          │
│ CONSUMERS   product teams compose; lint blocks violations    │
│   │                                                          │
│ CI          jsx-a11y + axe + visual-contrast tests gate PRs  │
└──────────────────────────────────────────────────────────────┘
```

## Why it matters

Design systems are leverage points: one Dialog fix propagates to forty products overnight. Interviews at senior/staff level increasingly probe "how do you prevent a11y regressions across 12 squads?" — the expected answer names primitives vs. full components, token-driven theming, CI enforcement, and *governance* (who signs off, what blocks release). Teams without this answer ship the same focus-trap bug in every product after every refactor.

## Why Do We Need It?

- **Scale of reuse**: a component used in 40 places multiplies both value of an a11y fix and cost of an unfixed violation.
- **Consistency beats heroics**: product engineers are not a11y experts; they should not need to be — the system encodes expertise.
- **Legal posture**: centralized conformance evidence (audit trail per component version) simplifies ADA/EAA defense.
- **Velocity**: teams move faster when keyboard/focus/ARIA come free instead of being re-litigated per feature.
- **Theming pressure**: dark mode and high-contrast themes break hand-picked hex colors; tokens with computed contrast keep themes compliant automatically.
- **Regression economics**: a CI axe run costs seconds; a re-audit of a rewritten settings page costs days.

## How It Works

### Accessible primitives: the philosophy

Radix UI and React Aria (Adobe) share a philosophy: **behavior and semantics are hard, styling is easy**. They ship headless (unstyled or minimally styled) components that implement the WAI-ARIA Authoring Practices exactly — roving tabindex, typeahead, focus containment, screen-reader announcements — while leaving visuals to you.

| Concern | DIY component | Primitive-based |
| --------------------------- | ----------------------- | ------------------------- |
| Focus trap in modal | ~150 lines, edge cases | Built-in, tested |
| Combobox keyboard spec | Weeks to get right | Implemented per APG |
| Screen-reader announcements | Manual aria-live wiring | Hook API (`useAnnouncer`) |
| RTL, touch, virtualization | Your problem now | Handled |

The rule: **never hand-roll complex interactive widgets**. Compose your styled `Button` over a primitive; wrap primitives in your design-system skin.

### Focus management baked in

The system guarantees focus correctness centrally:

```tsx
// Design system dialog: consumers cannot get focus wrong
import * as DialogPrimitive from '@radix-ui/react-dialog';

export function Modal({ open, onOpenChange, title, children }: ModalProps) {
  return (
    <DialogPrimitive.Root open={open} onOpenChange={onOpenChange}>
      <DialogPrimitive.Portal>
        <DialogPrimitive.Overlay className="ds-overlay" />
        <DialogPrimitive.Content className="ds-modal">
          <DialogPrimitive.Title className="ds-h2">{title}</DialogPrimitive.Title>
          {/* focus trapped here; restored to trigger on close;
              Escape closes; scroll locked */}
          {children}
          <DialogPrimitive.Close aria-label="Close" className="ds-close" />
        </DialogPrimitive.Content>
      </DialogPrimitive.Portal>
    </DialogPrimitive.Root>
  );
}
```

Focus-visible styling ships via the system stylesheet so every component shows a visible indicator by default:

```css
.ds-button:focus-visible {
  outline: 3px solid var(--ds-focus-ring);
  outline-offset: 2px;
}
```

### Tokens for contrast themes

Contrast becomes data, not eyeballing. Define semantic tokens and validate pairs:

```css
:root {
  --ds-surface: oklch(100% 0 0);
  --ds-text-primary: oklch(25% 0.02 260);     /* ratio vs surface: 15.8 */
}

[data-theme='dark'] {
  --ds-surface: oklch(18% 0.01 260);
  --ds-text-primary: oklch(93% 0.01 260);
}

[data-theme='high-contrast'] {
  --ds-text-primary: black;
  /* forced-colors media query complements this */
}
@media (forced-colors: active) {
  .ds-button { border: 1px solid ButtonText; }
}
```

CI can compute WCAG ratios directly from exported token JSON and fail the PR that breaks a pairing — contrast bugs die before render.

### Lint gates

Static analysis catches the mechanical class of errors:

```javascript
// eslint.config.js
import jsxA11y from 'eslint-plugin-jsx-a11y';

export default [
  {
    plugins: { 'jsx-a11y': jsxA11y },
    rules: {
      ...jsxA11y.recommended.rules,
      // stricter-than-recommended picks for DS code:
      'jsx-a11y/no-autofocus': 'error',
      'jsx-a11y/aria-props': 'error',
      'jsx-a11y/role-supports-aria-props': 'error',
    },
  },
];
```

Layered with runtime checks: `jest-axe` in component unit tests, `@axe-core/playwright` on storybook pages in CI.

## Code Examples

### Component unit test asserting a11y cleanliness

```typescript
import { render } from '@testing-library/react';
import { axe } from 'jest-axe';
import { TextField } from './text-field';

describe('TextField', () => {
  it('has no axe violations', async () => {
    const { container } = render(
      <TextField label="Work email" hint="We never share it" required />,
    );
    expect(await axe(container)).toHaveNoViolations();
  });

  it('associates label, hint, and error programmatically', () => {
    const { getByLabelText } = render(
      <TextField label="Work email" error="Enter a valid address" />,
    );
    const input = getByLabelText(/work email/i);
    expect(input).toHaveAttribute('aria-invalid', 'true');
    expect(input).toHaveAttribute('aria-describedby');
  });
});
```

### CI workflow gating on audits

```yaml
name: a11y-gate
on: [pull_request]
jobs:
  audit:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 22 }
      - run: npm ci
      - name: ESLint a11y rules
        run: npx eslint . --max-warnings 0
      - name: Unit + jest-axe on all DS components
        run: npm run test -- src/components
      - name: Build Storybook and run axe on every story
        run: |
          npx storybook build -o sb-static
          npx @storybook/test-runner --jest-junit || true
          npx axe-storybook sb-static --exit-on-violation
```

### Audit-to-component pipeline

Findings from product audits become system backlog items, classified by whether the fix belongs in the component, token set, docs, or consumer app:

```markdown
## Audit intake template
- Finding:            "Date picker unreachable by keyboard" (WCAG 2.1.1)
- Affected component: DatePicker v3.2 (used in 6 apps)
- Owner:              design-systems team (component-level defect)
- Fix:                adopt React Aria useDatePicker; ship as v4.0
- Verification:       new jest-axe case + manual NVDA script in PR
- Comms:              changelog entry + migration note for consumers
```

## Real-World Use Cases

1. **Multi-product SaaS platform** — eight products share one library; a contrast failure found by legal complaint is fixed once in tokens, verified by CI across all stories, and shipped in the next minor.
2. **Bank rebuilding for EAA compliance** — audit produces 140 findings; 96 map to 14 components, so remediation is a quarter of library work instead of years of per-app patches; remaining findings become documented usage rules.
3. **Dark mode launch** — tokens recomputed for dark theme with CI contrast assertions catch 23 failing pairings before designers even preview the theme.
4. **Government portal** — procurement requires VPAT; the DS team generates evidence per component (test reports, manual scripts), turning compliance documentation into a byproduct of normal engineering.
5. **Acquired startup's codebase folded into the platform** — its bespoke widgets are replaced by DS equivalents, instantly inheriting focus management and passing the platform's a11y gate on first deploy.

## Common Mistakes

```typescript
// BAD: styling over a div and calling it a button
const MyButton = (props) => <div className="btn" {...props} />;
// no role, no keyboard activation, no disabled semantics

// GOOD: native element or primitive underneath
const MyButton = forwardRef<HTMLButtonElement, ButtonProps>(
  ({ variant, ...rest }, ref) => (
    <button ref={ref} className={cx('ds-button', variant)} {...rest} />
  ),
);
```

```typescript
// BAD: hard-coded hex sneaks past tokens, breaks dark theme + contrast
<span style={{ color: '#888' }}>{hint}</span>

// GOOD: semantic token whose pairings CI validates
<span className="ds-hint">{hint}</span>
```

Other recurring failures:

- **Lint as theater**: plugin installed at recommended level but warnings ignored (`--max-warnings 999`); gates must fail builds.
- **jest-axe only on happy path**: testing the empty state but not error states, loading skeletons, or overflowing content where violations hide.
- **Primitives re-skinned into oblivion**: removing focus outlines "because the design says so" — the system must make overriding focus-visible styles require an explicit, reviewed exception.
- **Governance vacuum**: nobody owns the backlog; audit findings rot in a spreadsheet while components ship unchanged.
- **Version skew**: products pin old DS versions; fixes exist but never propagate — require upgrades via renovate bots plus deprecation windows.

## Best Practices

1. Adopt primitives (Radix, React Aria) for anything with focus/keyboard complexity; hand-roll nothing beyond simple buttons/inputs.
2. Encode all color pairs as semantic tokens; compute WCAG ratios in CI against every theme.
3. Enforce three layers mechanically: eslint-plugin-jsx-a11y in lint, jest-axe in unit tests, axe on Storybook/E2E in CI — all blocking.
4. Write the definition of done including a11y: keyboard pass noted, jest-axe green, labels verified, contrast checked for new colors.
5. Route every external audit finding through the system backlog with a named owner and verification test.
6. Publish usage docs showing right/wrong composition; most violations in consuming apps are misuse, not defects.
7. Track a11y health as a metric (violations per story, time-to-fix) reported alongside coverage.

## Performance Considerations

Primitives add bundle weight — tree-shake and lazy-load heavy ones (date pickers, comboboxes). Runtime axe scanning is expensive (~100ms+ per subtree): reserve full scans for CI, not production monitoring loops; in prod, sample pages. Contrast computation over thousands of token pairs is trivial offline — run it as a script, not per request. Avoid shipping multiple overlapping a11y libraries; dedupe Radix + React Aria usage where possible to control bundle size.

## Summary

- Accessibility scales when it lives in the design system: fix once, inherit everywhere.
- Primitives (Radix, React Aria) own the hard parts — focus traps, roving tabindex, ARIA state — so product code stays simple and correct.
- Semantic tokens turn contrast into validated data across light/dark/high-contrast themes.
- Enforcement is layered: jsx-a11y at lint time, jest-axe at unit time, axe scans at Storybook/E2E time — each blocking merges.
- Governance closes the loop: definition-of-done criteria, owned audit backlogs, changelog discipline, and upgrade policies keep fixes propagating.
- The audit-to-component pipeline converts one-off compliance pain into permanent system improvements.

## Cheat Sheet
```text
ACCESSIBLE DESIGN SYSTEMS CHEAT SHEET
============================================================

STACK:
• Primitives : Radix UI / React Aria (headless, APG-correct)
• Tokens     : semantic color pairs, themes, forced-colors support
• Components : primitive + tokens + docs + tests
• Gates      : eslint-plugin-jsx-a11y -> jest-axe -> axe CI scan

PRIMITIVE RULES:
• Never hand-roll dialogs, comboboxes, menus, date pickers
• Focus trap/restore comes from the primitive, not the app
• Focus-visible outline: default ON, override requires review

TOKEN RULES:
• No raw hex in components - semantic tokens only
• CI computes WCAG ratios per theme; broken pair fails PR
• Support prefers-color-scheme AND explicit themes

GATES:
• Lint:  jsx-a11y strict, zero-warning policy
• Unit:  jest-axe per component incl. error/loading states
• CI:    axe over every Storybook story, exit on violation

GOVERNANCE:
• DoD includes: keyboard pass, axe clean, labels verified
• Audit finding -> owned backlog item -> component fix -> test
• Version policy: bots force upgrades before deprecation ends

INTERVIEW FORMULA:
• "Fix once, inherit everywhere"
• "Behavior is hard, styling is easy - hence primitives"
• "Contrast as data, not vibes - CI computes ratios"
• "Three blocking gates beat one annual audit"
```

# Accessibility in Design Systems

A shared dialog centralizes focus containment — yet a consumer can still omit its title, remove its trigger, or style the focus indicator out of view. Reuse needs a clear contract and a way to detect when composition violates it.

```text
failed user task → identify owning layer → reproduce and fix
                                             ↓
component/token/usage release → consumer upgrade → journey re-evaluation
```

## Definition

An **accessible design system** combines shared components, design **tokens** and usage rules to make accessible behavior easier to reuse. **Components** supply semantics and interaction, tokens express intended visual combinations, and review and release evidence helps preserve both.

> **Textbook Definition:** An accessible design system standardizes reusable interaction semantics, visual tokens and usage contracts, supported by evaluation and governance. Conformance of a composed product still depends on its content, configuration and complete journeys.

## First Principles

Repeated interaction code multiplies maintenance and inconsistent behavior. A shared implementation concentrates that responsibility — but also concentrates failures: one defective primitive can affect many products, and fixing the library does not fix a consumer until its deployed version changes. So define which layer owns each responsibility, test that layer's contract, and verify the complete journey after composition.

## How It Works

### 1. Trace a Finding to an Actual Consumer Fix

If a labeled dialog loses focus to the page, investigate the interaction primitive or wrapper. If its title is empty only in one screen, investigate the consumer's content. If its focus ring disappears in dark mode, investigate the rendered theme and state pair. These are different fixes — assigning every finding to the design-system team hides the actual owner.

After a library fix, record the tested version, limitations and migration steps. Track affected consumers and verify the upgrade rather than assuming the change propagates overnight. An accepted exception needs a scope, owner and expiry, not a permanently green report.

### 2. Choose a Primitive From Its Actual Contract

A **primitive** supplies reusable interaction behavior with flexible presentation. Libraries such as Radix UI and React Aria reduce the cost of complex focus and selection behavior — but guarantee no styling override, no assistive technology, no label and no application flow. Read the selected component's API and supported pattern, pin a compatible version, and evaluate the composed result.

```tsx
// ReviewDialog.tsx — @radix-ui/react-dialog; stylesheet must preserve focus visibility.
// Demonstrates reviewing and dismissing local content; submits no order.
import * as Dialog from '@radix-ui/react-dialog';

export function ReviewDialog() {
  return (
    <Dialog.Root>
      <Dialog.Trigger asChild>
        <button type="button">Review order</button>
      </Dialog.Trigger>
      <Dialog.Portal>
        <Dialog.Overlay className="dialog-overlay" />
        <Dialog.Content className="dialog-content">
          <Dialog.Title>Review this draft order</Dialog.Title>
          <Dialog.Description>No order is submitted by this example.</Dialog.Description>
          <p>Two books: 2,500 cents.</p>
          <Dialog.Close asChild>
            <button type="button">Keep editing</button>
          </Dialog.Close>
        </Dialog.Content>
      </Dialog.Portal>
    </Dialog.Root>
  );
}
```

The trigger participates in the same root as the dialog, the title supplies its name, and the description explains the boundary. Opening moves focus into the content; the close action or Escape dismisses it, and the trigger supplies the return target. Styling and complete-page behavior still require testing, and replacing or removing the trigger during an update needs an explicit restoration strategy. [Radix accessibility guidance](https://www.radix-ui.com/primitives/docs/overview/accessibility), [React Aria guidance](https://react-spectrum.adobe.com/react-aria/accessibility.html).

### 3. Treat Tokens as Pairs and Verify Rendered Use

Give colors semantic meanings such as text-on-surface and focus-on-surface, then validate their permitted pairs in every theme. The [contrast chapter](50.2.04-color-and-contrast.md) owns the complete calculator and example themes. A high-contrast theme must define both foreground and background — making text black while inheriting a dark surface is a regression.

Token checking cannot see opacity, images, gradients, inherited styles or unexpected nesting unless those states enter the model. Evaluate rendered components and pages too. Forced-color environments can replace tokens, so retain semantic controls, visible outlines and suitable system colors rather than opting out globally.

### 4. Combine Static, Runtime and Journey Checks

For JavaScript/JSX files, this flat-config fragment uses the plugin's actual exported recommended configuration. Save as `eslint.config.mjs` with compatible installed ESLint and plugin versions; a TypeScript project additionally needs its parser and configuration.

```javascript
import jsxA11y from 'eslint-plugin-jsx-a11y';

export default [{
  ...jsxA11y.flatConfigs.recommended,
  files: ['**/*.{js,jsx}'],
}];
```

Lint finds unsupported attributes or missing relationships visible in source; it cannot execute an open and close lifecycle. A runtime audit checks applicable rules in a rendered state, and explicit interaction tests observe behavior. Manual keyboard, zoom and assistive-technology sessions evaluate the complete task and meaning. The [testing chapter](50.2.08-testing-a11y.md) owns the runnable browser audit and its exit contract.

For CI, define the exact served revision, readiness check, visited states, retained results and nonzero failure behavior. Building Storybook without serving it and visiting the stories is not a browser audit. Suppressing the runner's exit with `|| true` silently discards failures unless a separately defined enforcing result owns the decision — a missing environment is not a passing scan.

## Summary

Shared components concentrate interaction responsibility, while tokens and usage contracts govern presentation and composition. Accessibility improves when findings reach the right owner, a tested release reaches consumers, and the resulting journey is evaluated. Reuse and automated checks support that process; neither alone establishes product conformance.

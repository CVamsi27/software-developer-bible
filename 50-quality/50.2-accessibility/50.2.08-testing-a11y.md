# Testing Accessibility

A dialog passes its static role and name check — while Tab reaches an operable background control. A form has labeled inputs — while its validation errors stay undiscoverable. Start from the task and observe each relevant state, not only the initial markup.

```bash
npm install --save-dev @playwright/test @axe-core/playwright
npx playwright install chromium
node audit.cjs http://127.0.0.1:18083/shipping.html  # nonzero exit on violation
```

## Definition

**Accessibility testing** checks whether people can perceive and operate content through supported input methods and assistive technologies. It combines standards-oriented **rule checks** with evaluating actual **tasks**, including their dynamic and failure states.

> **Textbook Definition:** Accessibility evaluation assesses whether users with disabilities can perceive and operate content, combining applicable standards checks with manual interaction and assistive-technology testing.

## First Principles

A tool can compare inspectable properties with encoded rules but cannot infer all intended meaning or simulate every user's interaction. Code structure, rendered relationships, keyboard behavior, spoken interpretation and actual task completion are different evidence sources. Make the evaluated scope explicit — revision, page, state, data, viewport and theme, tool rules, supported environment — since a passing sample supports claims about that sample only. [W3C evaluation guidance](https://www.w3.org/WAI/test-evaluate/).

## 1. Follow One Failure Through Several Observations

For a shipping disclosure, check its native control name and state, then operate it with Enter and Space. Observe the visible panel and the next Tab target separately from `aria-expanded`. Evaluate the closed and expanded states with automated rules, then listen and navigate with the supported screen reader to establish that the exposed information is actually useful.

A role and state assertion cannot establish a spoken announcement, and directly calling `element.focus` cannot establish natural Tab order. Synthetic `dispatchEvent` keyboard events do not reliably perform the browser's native activation behavior — use actual browser input for that boundary.

## 2. Run Browser Input Checks and Audits With an Enforcing Exit

Use the complete `shipping.html` fixture from [ARIA](50.2.02-aria.md). Serve its directory locally, for example with Python's HTTP server bound to 127.0.0.1 on port 18083. In a disposable Node project, install compatible reviewed versions of `@playwright/test` and `@axe-core/playwright`, install Playwright's matching Chromium, and save the following as `audit.cjs`.

```bash
npm install --save-dev @playwright/test @axe-core/playwright
npx playwright install chromium
# In another terminal, from the fixture directory:
python3 -m http.server 18083 --bind 127.0.0.1
# From the test project:
node audit.cjs http://127.0.0.1:18083/shipping.html
```

```javascript
// audit.cjs — CommonJS, Node and the installed Playwright browser
const fs = require('node:fs');
const assert = require('node:assert/strict');
const { chromium } = require('@playwright/test');
const { default: AxeBuilder } = require('@axe-core/playwright');

async function main() {
  const url = process.argv[2];
  if (!url) throw new Error('Pass the served shipping.html URL');
  const report = { url, node: process.version, states: [], errors: [] };
  let browser;
  try {
    browser = await chromium.launch();
    const context = await browser.newContext();
    const page = await context.newPage();
    await page.goto(url, { waitUntil: 'domcontentloaded' });
    const audit = async state => {
      const results = await new AxeBuilder({ page })
        .withTags(['wcag2a', 'wcag2aa', 'wcag21a', 'wcag21aa', 'wcag22aa']).analyze();
      report.states.push({ state, violations: results.violations, incomplete: results.incomplete });
      if (results.violations.length) process.exitCode = 1;
    };
    await audit('closed');
    const toggle = page.getByRole('button', { name: 'Shipping details', exact: true });
    await toggle.focus();
    await page.keyboard.press('Enter');
    assert.equal(await toggle.getAttribute('aria-expanded'), 'true');
    assert.equal(await page.locator('#shipping-panel').isVisible(), true);
    await page.keyboard.press('Tab');
    const link = page.getByRole('link', { name: 'Read the returns policy' });
    assert.equal(await link.evaluate(element => element === document.activeElement), true);
    await audit('expanded');
    await page.keyboard.press('Shift+Tab');
    await page.keyboard.press('Space');
    assert.equal(await toggle.getAttribute('aria-expanded'), 'false');
    assert.equal(await page.locator('#shipping-panel').isVisible(), false);
  } catch (error) {
    report.errors.push(error instanceof Error ? error.message : String(error));
    process.exitCode = 1;
  } finally {
    fs.writeFileSync('a11y-report.json', JSON.stringify(report, null, 2));
    if (browser) await browser.close();
  }
}
main().catch(error => { console.error(error); process.exitCode = 1; });
```

The script records initial and expanded-state findings plus keyboard-check errors; a violation or failed interaction exits nonzero. Incomplete automated checks require review — they do not become a conformance pass merely because this example's failure policy only blocks violations. This exercises native keyboard input and selected outcomes; it does not inspect every criterion, theme, mobile input, speech output or full journey. Record matching library and browser versions alongside the report. [Playwright's accessibility guidance](https://playwright.dev/docs/accessibility-testing).

## 3. Interpret Findings Rather Than a Score

axe reports **violations** where a rule fails and **incomplete** results that need review, alongside passed and inapplicable checks. Preserve rule IDs, affected elements, state and reproduction information. A missing name can be a concrete failure; whether a supplied image alternative conveys the needed meaning still requires judgment. [axe rule descriptions](https://github.com/dequelabs/axe-core/blob/develop/doc/rule-descriptions.md).

axe-core groups its WCAG 2.2 A/AA rules under the `wcag22aa` tag, but the available rules depend on the pinned release and some 2.2 rules are disabled by default — the filter still covers only automated rules, not every success criterion. [axe-core tag reference](https://github.com/dequelabs/axe-core/blob/develop/doc/API.md). DOM-runner integrations such as jest-axe check component semantics without reproducing real browser layout and contrast; a Lighthouse accessibility score summarizes its selected audits, not product conformance. For regressions, compare the same scope and rules — a lower violation count after excluding a failing page is not an improvement.

## 4. Evaluate Manually Along the User's Task

For **keyboard operation**, start at the page entry and use Tab and Shift+Tab, the widget's movement keys, activation and cancellation. Observe visible and unobscured focus, logical sequence, hidden targets and behavior after removal or closing. Use the [keyboard fixtures](50.2.03-keyboard-navigation.md) as concrete cases, then test the real composition.

For **screen-reader evaluation**, record browser, reader, versions and settings. Navigate by headings and landmarks as well as controls, listen to names, descriptions and changing state, and complete the task — a desktop result does not establish mobile behavior, and an automated snapshot is not a recording of speech. Include people who use the supported technologies when evaluating important journeys.

For **visual evaluation**, check contrast in actual themes and states, text resizing, reflow, text spacing and focus near sticky content. At a narrow viewport, a table or diagram may legitimately need two-dimensional scrolling while surrounding prose stays usable. Evaluate forms before and after empty, invalid and corrected submissions plus server failure; open disclosures and dialogs; test overflowing, localized and asynchronous content. A third-party payment or authentication step remains part of the complete process — evaluate the selected integration or record its missing evidence and ownership.

## Summary

Accessibility testing combines inspectable rule checks with actual interaction and human evaluation. Name the evaluated scope, preserve findings and enforcing results, and observe dynamic states and complete tasks. A passing automated sample is useful evidence with defined limits — never a complete-process claim on its own.

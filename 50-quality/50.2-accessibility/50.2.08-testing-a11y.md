# Testing Accessibility

## Definition

Accessibility testing checks whether people can perceive and operate content through supported input methods and assistive technologies. It combines standards-oriented checks with evaluating actual tasks, including their dynamic and failure states.

> **Textbook Definition:** Accessibility evaluation assesses whether users with disabilities can perceive and operate content, combining applicable standards checks with manual interaction and assistive-technology testing.

A dialog can pass a static role/name check while Tab reaches an operable background control. A form can have labeled inputs while its validation makes errors undiscoverable. Start from the task and observe each relevant state, not only the initial markup.

## First Principles

A tool can compare inspectable properties with encoded rules, but cannot infer all intended meaning or simulate every user's interaction. Code structure, rendered relationships, keyboard behavior, spoken interpretation and actual task completion are different evidence sources.

Make the evaluated scope explicit: revision, page, state, data, viewport/theme, tool rules and supported environment. A passing sample supports claims about that sample; missing or unavailable evaluation remains missing evidence. [W3C evaluation guidance](https://www.w3.org/WAI/test-evaluate/).

## Follow one failure through several observations

For a shipping disclosure, check its native control name and state, then operate it with Enter and Space. Observe the visible panel and the next Tab target separately from aria-expanded. Evaluate the closed and expanded states with automated rules, then listen and navigate using the supported screen reader to establish that the exposed information is useful.

A role/state assertion cannot establish a spoken announcement, and directly calling element.focus cannot establish natural Tab order. Synthetic dispatchEvent keyboard events also do not reliably perform the browser's native activation behavior. Use actual browser input for that boundary.

## Code Examples

### Run browser input checks and audits with an enforcing exit

Use the complete shipping.html fixture from [ARIA](50.2.02-aria.md). Serve its directory locally, for example with Python's HTTP server bound to 127.0.0.1 on port 18083. In a disposable Node project, install compatible reviewed versions of @playwright/test and @axe-core/playwright, install Playwright's matching Chromium, and save the following as audit.cjs.

```bash
npm install --save-dev @playwright/test @axe-core/playwright
npx playwright install chromium
# In another terminal, from the fixture directory:
python3 -m http.server 18083 --bind 127.0.0.1
# From the test project:
node audit.cjs http://127.0.0.1:18083/shipping.html
```

The script records initial and expanded-state findings and keyboard-check errors. A violation or failed interaction exits nonzero. Incomplete automated checks require review; they do not become a conformance pass merely because this example's failure policy only blocks violations.

```javascript
// audit.cjs — CommonJS, Node and the installed Playwright browser
const fs = require('node:fs');
const assert = require('node:assert/strict');
const { chromium } = require('@playwright/test');
const { default: AxeBuilder } = require('@axe-core/playwright');

async function main() {
  const url = process.argv[2];
  if (!url) throw new Error('Pass the served shipping.html URL');
  const report = { url, node: process.version, states: [], errors: [] };
  let browser;
  try {
    browser = await chromium.launch();
    const context = await browser.newContext();
    const page = await context.newPage();
    await page.goto(url, { waitUntil: 'domcontentloaded' });
    const audit = async state => {
      const results = await new AxeBuilder({ page })
        .withTags(['wcag2a', 'wcag2aa', 'wcag21a', 'wcag21aa', 'wcag22aa']).analyze();
      report.states.push({ state, violations: results.violations, incomplete: results.incomplete });
      if (results.violations.length) process.exitCode = 1;
    };
    await audit('closed');
    const toggle = page.getByRole('button', { name: 'Shipping details', exact: true });
    await toggle.focus();
    await page.keyboard.press('Enter');
    assert.equal(await toggle.getAttribute('aria-expanded'), 'true');
    assert.equal(await page.locator('#shipping-panel').isVisible(), true);
    await page.keyboard.press('Tab');
    const link = page.getByRole('link', { name: 'Read the returns policy' });
    assert.equal(await link.evaluate(element => element === document.activeElement), true);
    await audit('expanded');
    await page.keyboard.press('Shift+Tab');
    await page.keyboard.press('Space');
    assert.equal(await toggle.getAttribute('aria-expanded'), 'false');
    assert.equal(await page.locator('#shipping-panel').isVisible(), false);
  } catch (error) {
    report.errors.push(error instanceof Error ? error.message : String(error));
    process.exitCode = 1;
  } finally {
    fs.writeFileSync('a11y-report.json', JSON.stringify(report, null, 2));
    if (browser) await browser.close();
  }
}
main().catch(error => { console.error(error); process.exitCode = 1; });
```

This exercises native keyboard input and selected semantic/visibility outcomes; axe checks a selected rule set in two states. It does not inspect every WCAG criterion, theme, mobile input, speech output or full product journey. Record matching library/browser versions alongside the report. [Playwright's accessibility guidance](https://playwright.dev/docs/accessibility-testing).

## Interpret findings rather than just a score

axe reports **violations** where a rule fails and **incomplete** results that need review, alongside passed/inapplicable checks. Preserve rule IDs, affected elements, state and reproduction information. A missing name can be a concrete failure; whether a supplied image alternative conveys the needed meaning still requires judgment. [axe rule descriptions](https://github.com/dequelabs/axe-core/blob/develop/doc/rule-descriptions.md).

DOM-runner integrations such as jest-axe are useful for component semantics but do not reproduce real browser layout and contrast completely. Lighthouse's accessibility score summarizes its selected audits, not product conformance. WAVE can help inspect the rendered page. Configure each tool through its actual documented runtime rather than mixing a Node require, JSX component and browser DOM in one unconfigured snippet.

For regressions, compare the same evaluated scope and rules. A lower violation count after excluding a failing page is not an improvement. A rule baseline needs owned exceptions and expiry; it must not hide a new failure elsewhere under an old total.

## Manual evaluation follows the user's task

For keyboard operation, start at the page entry and use Tab/Shift+Tab, the widget's movement keys, activation and cancellation. Observe visible/unobscured focus, logical sequence, hidden targets and what happens after removal or closing. Use the [keyboard fixtures](50.2.03-keyboard-navigation.md) as concrete cases, then test the real composition.

For screen-reader evaluation, record browser, reader, versions and settings. Navigate by relevant headings/landmarks as well as controls, listen to names, descriptions and changing state, and complete the task. A desktop reader result does not establish mobile behavior. Learn the supported reader's interaction mode; an automated accessibility snapshot is not a recording of its speech.

For visual evaluation, check contrast in actual themes/states, text resizing, reflow, text spacing and focus near sticky content. At a narrow viewport, a table or diagram may legitimately need two-dimensional scrolling while the surrounding prose must stay usable. An axe pass cannot establish the clarity of a dense chart or the usefulness of its alternatives.

## Include loading, errors and third-party boundaries

Evaluate forms before and after empty/invalid submissions, after correction and after server failure. Open disclosures and dialogs; test overflowing/localized content and asynchronous updates. Populated states may introduce different names, headings or contrast combinations from an empty skeleton.

A third-party payment or authentication step remains part of the user's complete process. Evaluate the selected integration or record its missing evidence and ownership. A component-level result does not automatically transfer to every consumer, as the [design-system chapter](50.2.07-accessibility-design-systems.md) explains.

## Real-World Decisions

Use repeatable automated checks for rules they can observe, explicit input tests for interaction contracts and human evaluation for meaning and supported assistive-technology journeys. Involve people who use those technologies to identify real task barriers, while distinguishing usability findings from specific criterion tests.

Prioritize blocked critical tasks, missing alternatives, unusable input paths and failures repeated across shared components. Keep a reproducible state and owner for each finding. Retest the corrected journey and any shared consumers affected by the fix; a color change can reveal a new theme or focus issue.

## Common Mistakes

- Calling an automated score or empty violations list complete conformance.
- Treating direct focus calls or synthetic key events as a full keyboard journey.
- Auditing only the initial/happy state or ignoring incomplete findings.
- Losing failure reports, swallowing an exit code or labelling an unavailable scan passed.
- Assuming one desktop reader or component test covers every supported environment.

## Best Practices

Tie each result to revision, state, scope and environment. Preserve first-failure evidence, enforce the defined gate, and keep unresolved manual work visible. Evaluate the complete task through complementary methods and verify a fix through the same failing path.

## Summary

Accessibility testing combines inspectable rule checks with actual interaction and human evaluation. Name the evaluated scope, preserve findings and enforcing results, and observe dynamic states and complete tasks. A passing automated sample is useful evidence with defined limits.

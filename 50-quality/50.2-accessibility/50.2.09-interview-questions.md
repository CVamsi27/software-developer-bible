# Accessibility Interview Questions

## First Principles

An interface must preserve meaning and task operation across supported ways of perceiving and entering information. A defensible answer therefore connects semantics, behavior, state and evaluation scope, rather than stopping at tool names or an acronym.

## Practice the original questions and changed conditions

Answer aloud before reading the model. Give a concrete task and mechanism, then use the probe to change one condition. Complete the [section revision](REVISION.md) first; the source chapters own runnable examples and primary references. Use verified personal contributions for experience claims.

### 1. What is web accessibility and why is it important?

**Answer:** Web accessibility lets people perceive and operate a task through supported input methods and assistive technologies. A mouse-only payment flow can exclude someone who uses a keyboard, even when its text is readable. Design semantics, content, interaction and recovery together, then evaluate the complete journey. Technical conformance, usability and a specific legal requirement are related but separately scoped claims.

**Probe:** Which step would prevent a user from completing your product’s critical journey?

### 2. What are the four principles of WCAG?

**Answer:** Perceivable, Operable, Understandable and Robust organize WCAG’s requirements. For a form error, those questions become: is the failure available beyond color, can the user reach the field, does the explanation support correction, and do supported tools expose its name/state/relationships? The principles guide diagnosis; applicable success criteria make requirements testable. Memorizing POUR does not establish the implemented behavior.

**Probe:** Could a perceivable error still be impossible to correct?

### 3. What is the difference between Level A, AA, and AAA?

**Answer:** The levels are cumulative: A includes applicable A criteria, AA includes A and AA, and AAA includes all three. Name the version, level and evaluated scope; a percentage or Lighthouse score is not the conformance level. Full-page and complete-process requirements also matter. Select a target from the product’s documented requirements and user needs rather than assuming every organization has the same obligation.

**Probe:** Can a passing component establish conformance of the full checkout process?

### 4. What is semantic HTML and why does it matter?

**Answer:** Semantic HTML expresses the element’s actual purpose through browser-supported structure and controls. A native button supplies its role, focus and activation behavior; a styled div supplies none of those merely through appearance. Headings and landmarks make document structure navigable, while labels connect inputs with their purpose. Correct content, state, styling and interaction are still required; semantics are a foundation rather than complete accessibility by default.

**Probe:** What behavior remains missing after adding role=button to a div?

### 5. What is alt text and when should you use it?

**Answer:** Choose an image alternative from its purpose in context. Describe relevant information for an informative image, use empty alt for a decorative image, and name the action for an image that is the sole content of a control. A complex chart needs its relationships and precise-data path beyond a short label. Avoid repeating adjacent equivalent text unnecessarily or describing only appearance when the user needs a task outcome.

**Probe:** How does the alternative change when the same image becomes a link?

### 6. Why is color contrast important?

**Answer:** Contrast helps distinguish text or necessary visual information from its surroundings. Applicable normal text needs 4.5:1 at AA, large text 3:1; non-text requirements have their own scope and exceptions. Evaluate the unrounded rendered pair in each state/theme, including changing backgrounds and transparency. Contrast alone does not replace non-color status/series cues.

**Probe:** What if a passing foreground token is rendered on another card surface?

### 7. What are landmark roles?

**Answer:** Landmarks identify major regions that assistive technologies can navigate, such as main content, navigation and search. Native elements often provide them, but context matters: a header inside an article is not necessarily the page’s banner landmark. Label multiple similar regions meaningfully so users can distinguish them, and avoid making every small container a landmark. A useful heading structure complements regions rather than replacing them.

**Probe:** How would a reader distinguish primary navigation from footer navigation?

### 8. What is keyboard accessibility?

**Answer:** Users need to reach, operate and leave applicable functionality through a keyboard interface. Check sequential order, visible/unobscured focus, activation, widget-specific movement and recovery after state changes. Composite widgets can use one Tab stop with scoped arrow navigation. A modal intentionally contains task focus while open and releases it appropriately on dismissal; an unintended trap prevents progress.

**Probe:** What happens to focus when the current item is removed?

### 9. What is ARIA and when should you use it?

**Answer:** ARIA describes roles, names, states and relationships through accessibility APIs when native HTML does not fully express the needed semantics. It does not implement activation, focus, hiding or modality. Prefer an appropriate native control, then add the necessary relationship/state and keep it synchronized with rendered behavior. A disclosure’s expanded attribute must agree with whether its panel is open.

**Probe:** Can aria-modal=true make a background button inoperable?

### 10. What is the difference between `aria-label` and `aria-labelledby`?

**Answer:** aria-label supplies a naming string, while aria-labelledby references elements whose text supplies the name. Either can override the name a control would otherwise derive from visible content. Prefer a visible label where it fits and keep that wording represented in the accessible name for voice operation. aria-describedby supplies additional context rather than replacing the name; referenced IDs must exist and be unique.

**Probe:** What if a component instance accidentally references another instance’s label?

### 11. What are live regions?

**Answer:** Live regions expose useful content changes without moving keyboard focus. Create the intended region before updating it; role=status has polite semantics and role=alert has assertive semantics. Choose interruption according to urgency and avoid competing or per-keystroke announcements. Verify the supported reader/browser behavior rather than assuming a sentence is spoken immediately or exactly once.

**Probe:** Why could a focused error summary plus several alerts become confusing?

### 12. How do you make forms accessible?

**Answer:** Provide persistent visible labels, relevant instructions and grouped context, then connect validation errors to their fields. Preserve entered work, update invalid/description state and choose a coherent focus/notification strategy on failed submission. Native required/type/autocomplete behavior can assist; ARIA state alone does not validate. Client format acceptance is not a server transaction or confirmed delivery.

**Probe:** What should the interface say after a timeout with unknown submission outcome?

### 13. What is focus management?

**Answer:** Focus management maintains the user’s place across deliberate transitions. Define entry, movement and exit for overlays, route changes, removed items and failed submissions. A modal needs an appropriate initial target, operable dismissal and sensible restoration; a removed trigger needs an alternative continuation. Avoid stealing focus during unrelated updates or moving it twice before an explanation can be encountered.

**Probe:** Where would focus go after deleting the last item in a list?

### 14. What is the difference between `aria-hidden` and `hidden`?

**Answer:** hidden removes ordinary rendered visibility and navigation in its normal use. aria-hidden=true changes the accessibility representation without hiding the element visually or preventing focus/activation. Putting it on a focusable control or an ancestor with operable descendants can leave an unidentified keyboard target. CSS overrides and relationship references also matter: hidden text directly referenced by aria-describedby can still supply a description.

**Probe:** Why can a hidden old error remain in the field’s accessible description?

### 15. How do you test accessibility?

**Answer:** Name the revision, journey, states, environment and target criteria. Use automation for inspectable rules, explicit browser input tests for behavior, and manual/assistive-technology evaluation for meaning and complete task operation. Preserve violations, incomplete checks and first-failure evidence. An empty automated violations list supports its selected sample, not complete product conformance.

**Probe:** What additional states would you evaluate beyond an empty initial form?

### 16. What is skip navigation?

**Answer:** A skip link lets a user bypass repeated content and reach the useful task region. Make it operable and visible on focus, with an existing meaningful target. Check where focus and the next Tab go after activation, especially near sticky content. Scrolling to a heading alone is not the full keyboard outcome.

**Probe:** What happens if the target is removed during a client-side route update?

### 17. How do you implement accessibility in a design system?

**Answer:** Assign responsibility across interaction primitives, themed components, tokens, usage contracts and consumers. Reproduce findings at the owning layer and evaluate initial, error, loading and duplicate-instance states. Publish tested versions and migration guidance, then track upgrades and re-evaluate the composed journeys. A fixed library version cannot repair a product still deploying the old one.

**Probe:** Who owns an empty dialog title supplied by one consuming screen?

### 18. What is the impact of accessibility on SEO?

**Answer:** Some practices, such as clear document structure and meaningful image alternatives, can also help search engines interpret content. That overlap is not equivalence: keyboard containment, error recovery and announcements need accessibility evaluation whether or not they affect crawling. Do not promise ranking or conversion changes from accessibility work without relevant evidence. Prioritize the person’s task rather than treating accessibility as an SEO mechanism.

**Probe:** Which critical accessibility behavior would a search crawler fail to assess?

### 19. How do you handle accessibility in SPAs?

**Answer:** Client-side navigation needs an informative title/heading, sensible task-continuity focus and discoverable important updates. Rendering a new route does not automatically notify or orient a reader. Preserve standard links/navigation, avoid moving focus on unrelated rerenders and account for stale asynchronous responses. Evaluate loading, failed navigation, back/forward behavior and supported assistive-technology interactions.

**Probe:** How do you avoid an old request updating the newly selected page?

### 20. What are the challenges of accessibility in complex components?

**Answer:** A complex widget coordinates role, name, focus, selection, keyboard/pointer behavior and changing content. Choose the actual pattern before writing handlers: a native select, disclosure, tablist, combobox and application menu have different contracts. Handle cancellation, disabled/removed items, long/localized content and repeated instances. A library can supply parts of that behavior while styling or composition introduces new defects.

**Probe:** Why is a navigation dropdown not automatically an ARIA menu?

### 21. How do you make video content accessible?

**Answer:** Identify information carried by audio, video and interaction. Provide accurate captions for relevant speech/sounds, audio description or the applicable alternative for visual information, and suitable transcripts where they serve the content and target criteria. Keep the player operable through supported input paths and avoid uncontrollable playback. A transcript alone does not replace every synchronized-media requirement.

**Probe:** What important information remains unavailable if a silent chart is never described?

### 22. What is cognitive accessibility?

**Answer:** Cognitive accessibility reduces avoidable effort in understanding, remembering and completing a task. Use clear language, predictable controls, persistent instructions and recoverable errors; avoid unexplained timed steps and asking for information already supplied without a reason. Allow useful assistance such as password managers and supported paste flows. Test with people and tasks rather than assuming one checklist addresses every cognitive need.

**Probe:** How can a disappearing hint make correction harder even with a valid label?

### 23. How do you handle accessibility in internationalization?

**Answer:** Declare the appropriate page and language-change semantics, use understandable localized labels and evaluate layout, reading order and keyboard conventions for the locale. Translation can change text length, labels and names; right-to-left presentation can expose assumptions in movement handlers. Keep visible and accessible names aligned and check expanded/overflowing states. A mirrored visual layout does not automatically establish a meaningful document sequence.

**Probe:** What breaks if a translated button keeps an unrelated English aria-label?

### 24. What is the role of accessibility in inclusive design?

**Answer:** Inclusive design involves people and differing needs while defining and evaluating the product. Accessibility supplies concrete responsibilities and evidence within that process. Include diverse task/input paths early, then preserve them through content, components and releases. Participation does not remove the need to test implemented standards and failure states.

**Probe:** How would a participant’s blocked task change the implementation backlog?

### 25. How do you measure accessibility success?

**Answer:** Track task barriers and verified remediation alongside the target standard and evaluated scope. Record blocked journeys, affected states/users, time to reproduce/fix, shared-component adoption and relevant user feedback. Keep automated rule results distinct from human evaluation and unresolved findings. A smaller count after reducing audit scope or a higher tool score is not automatically improved accessibility.

**Probe:** What denominator would make two releases’ issue counts comparable?

### 26. Design an accessibility testing strategy for a large application.

**Answer:** Map critical complete journeys and shared components, then define supported environments and target criteria. Add repeatable automated rules and browser interaction checks to relevant changes, with retained results and enforcing exits. Schedule human and assistive-technology evaluation according to changes and risk, including third-party and failure states. Give findings owners, reproducible cases and adoption tracking; do not substitute a universal quarterly calendar for the actual risk model.

**Probe:** How would a new payment provider change the evaluation scope?

### 27. How would you make a complex data visualization accessible?

**Answer:** Preserve the chart’s task: trends, exact values, uncertainty and any filtering/drill-down. Provide an informative text explanation and equivalent structured data generated from the same dataset, with non-color distinctions where needed. Static image-like semantics and independently operable points are different designs; do not hide interactive children under an atomic role=img. Dense interaction needs a usable navigation model, not hundreds of unexplained Tab stops.

**Probe:** What happens if the chart filter updates but its table retains old data?

### 28. What are the business benefits of accessibility?

**Answer:** Removing task barriers can let more people complete the product’s intended work and reduce recurring defects or support friction. Some organizations also have scoped contractual or legal obligations. Specify the observed blocked task and evidence rather than promising universal revenue, SEO or conversion gains. Shared components can reduce repeated remediation cost, provided consumers actually adopt and evaluate the fix.

**Probe:** How would you distinguish an expected benefit from a measured business result?

### 29. How do you prioritize accessibility issues?

**Answer:** Prioritize task-blocking impact, affected populations/states, recurrence through shared components and the applicable requirements. Consider urgency, dependency and safe remediation rather than selecting only easy findings with high counts. Give consequential issues an owner and reproducible acceptance evidence. A low-frequency critical access failure can outrank many cosmetic findings.

**Probe:** What if the shared fix is ready but several products cannot upgrade immediately?

### 30. Design an accessible component library.

**Answer:** Choose supported interaction contracts and provide named, themed components with documented composition and extension points. Keep labels, unique IDs, selection state, focus and disabled behavior coherent. Test component variants and complete consumer journeys, including long content and errors. Publish tested-version evidence, migration guidance and an ownership process for findings; reuse alone does not establish conformance.

**Probe:** Which override points could let a consumer remove the focus indicator?

### 31. How does accessibility affect conversion rates?

**Answer:** A form barrier can prevent completion, so improving it may affect conversion for the affected task/population. Measure with a defined baseline, traffic mix, time window and appropriate causal design; other product changes can explain movement. Do not reuse unsupported universal percentages or imply every accessibility fix produces the same commercial effect. Success also includes people completing required work even where conversion is not the product’s goal.

**Probe:** What observation would support the claimed cause rather than a coincident trend?

### 32. What is the relationship between accessibility and progressive enhancement?

**Answer:** Progressive enhancement begins with a usable core and adds capabilities where supported. Native controls, links and meaningful content can preserve important behavior when an enhancement fails, but the core must itself be accessible. Every added dialog, filter or dynamic update needs compatible semantics and interaction. Graceful failure also needs an honest outcome and recovery path rather than a silent broken button.

**Probe:** Can a static fallback preserve an interactive chart’s filtering task?

### 33. How do you handle accessibility with JavaScript frameworks?

**Answer:** Frameworks render DOM and coordinate state; they do not automatically supply correct semantics or task continuity. Keep visible content, accessible relationships and state derived from the same source, with unique IDs and defined focus after transitions. Handle async races, portals, removed triggers and repeated instances. Test the composed browser journey alongside narrow component semantics.

**Probe:** How might a portal keep modal content mounted after its trigger disappears?

### 34. What is the future of accessibility?

**Answer:** Track published standards, supported browser/assistive-technology behavior and versioned tool changes through primary sources. A draft such as WCAG 3 is not the same as a published conformance target. Automated or AI-assisted suggestions need review and actual behavior evaluation; a generated label can still misdescribe a task. Adapt testing to changing interfaces without declaring future capabilities universal or already implemented.

**Probe:** What evidence would justify adopting a new rule as a release requirement?

### 35. How do you train developers on accessibility?

**Answer:** Teach one real blocked task, then let learners reproduce it through keyboard or assistive technology before fixing the mechanism. Compare semantics with activation, a field name with its description, and a tool result with actual task completion. Review the corrected state and a changed condition, such as removing a trigger or changing the theme. Use supported tools and participants respectfully, and assess understanding through explanation and working behavior rather than a memorized acronym count.

**Probe:** How would a learner demonstrate that a fix covers recovery as well as the happy path?

## Summary

Explain the user's task, required semantics and behavior, state changes and evidence boundary. Conformance has a defined version and scope; automated scores, a library or a model answer cannot establish a complete usable journey by themselves.

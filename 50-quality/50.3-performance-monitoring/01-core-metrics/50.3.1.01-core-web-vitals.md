# Core Web Vitals

A product page can paint its main image quickly yet freeze when Add to cart is pressed — or shift the button while an advertisement loads. A single page-load duration cannot explain all three experiences.

```typescript
// Field ratings use fixed cutoffs; 320 ms INP is needs-improvement, not poor.
rating('INP', 320);   // 'needs-improvement'
rating('CLS', 0.25);  // 'needs-improvement'
```

## Definition

**Core Web Vitals** are standardized Google metrics for **loading**, **responsiveness** and **visual stability** on the web. They inform Google's page-experience assessment, but good scores do not guarantee a particular search ranking.

> **Textbook Definition:** Core Web Vitals are Largest Contentful Paint (LCP), Interaction to Next Paint (INP) and Cumulative Layout Shift (CLS). Field assessment evaluates the distribution of visits, typically its 75th percentile, for each metric.

## First Principles

A browser downloads resources, executes work and paints frames. The user experiences when useful content appears, when an action produces visible feedback, and whether content stays in place. Measuring those moments separates a slow network path from a busy main thread or unstable layout. Visits also differ — a fast developer laptop with a warm cache does not represent a first visit on a slower phone — so keep a distribution for an explicit population before deciding whether an optimization helped.

## 1. Read the Three Measurement Boundaries

| Metric | Meaning for one visit | Good | Needs improvement | Poor |
| ------ | ------------------------------------------------------------------- | ---------- | ------------------- | ---------- |
| LCP | Render time of the largest eligible visible content candidate | ≤ 2,500 ms | > 2,500 to 4,000 ms | > 4,000 ms |
| INP | A near-worst qualifying interaction's latency to the next paint | ≤ 200 ms | > 200 to 500 ms | > 500 ms |
| CLS | Largest sum of eligible layout-shift scores within a session window | ≤ 0.1 | > 0.1 to 0.25 | > 0.25 |

The good cutoff is included; the poor cutoff is exceeded, not included. An INP of 320 ms is **needs improvement** — multiplying every good cutoff by 1.6 would incorrectly classify it as poor. CLS has no time unit. A product may set stricter local service objectives, but keep those separate from the standard field ratings above.

## 2. Follow the Visible Content Candidate

The heading may paint first, followed by a larger product image. The later image can become the LCP candidate — LCP is not the completion time of every resource. Eligible content includes text blocks, images and qualifying video content, with browser heuristics; reporting stops after qualifying interaction, so lifecycle handling matters. [LCP definition and measurement](https://web.dev/articles/lcp)

Trace a hypothetical image visit:

```text
navigation → first byte → image request → image downloaded → image painted
   0 ms        600 ms         900 ms           1,500 ms          1,800 ms
```

The four spans are 600 ms server/connection delay, 300 ms resource-discovery delay, 600 ms download and 300 ms render delay — 1,800 ms total. If the image is discovered only after application JavaScript runs, making the server 100 ms faster leaves that discovery delay intact. Verify the candidate in a trace before choosing a preload or changing rendering. Never lazy-load a likely above-the-fold LCP image by default: reserve its space, provide an appropriate size and make it discoverable early.

## 3. Measure Visible Response, Not Just the Handler

An interaction can wait for earlier work, run its handlers, then wait for the browser to paint. A hypothetical click with 90 ms input delay, 40 ms processing and 70 ms presentation delay has 200 ms latency — so a 40 ms handler alone is insufficient evidence of good responsiveness. Clicks, taps and keyboard interactions contribute; ordinary scrolling and hovering do not directly count. INP normally selects the worst interaction, with an outlier allowance for pages with many interactions, and a visit without qualifying interaction has no INP value. First Input Delay (FID), replaced in March 2024, measured a narrower first-interaction delay. [INP mechanism](https://web.dev/articles/inp)

Move unrelated work out of the interaction path or yield between bounded tasks. A worker can own suitable CPU work, while DOM changes still belong on the main thread. Showing a prompt loading state improves feedback but does not prove the server operation finished or shorten its duration.

## 4. Group Unexpected Movement Into Windows

Each eligible shift score combines the affected viewport area and movement distance. Shifts join one window when consecutive shifts are less than one second apart and the window spans less than five seconds; CLS is the largest window sum. A shift within 500 ms of qualifying user input is excluded, but later movement caused by an asynchronous response can still count. [CLS mechanism](https://web.dev/articles/cls)

Scores of 0.1 at 0 ms and 0.2 at 500 ms form a window worth 0.3; a score of 0.05 at 3,000 ms starts another window because the gap exceeds one second — CLS is 0.3, not the lifetime sum of 0.35. A recent-input shift is excluded from CLS but can still disrupt the person using the page. Reserve dimensions for media and stable space for dynamic content where appropriate, and never assume every movement following a click is excluded.

## 5. Trace a Field Percentile Without Mixing Populations

This complete TypeScript example classifies already collected per-visit values. It does not collect browser timings. Save it as `distribution.ts`, compile with TypeScript in strict mode and run the emitted JavaScript.

```typescript
type Vital = 'LCP' | 'INP' | 'CLS';
type Rating = 'good' | 'needs-improvement' | 'poor';
const cutoffs: Record<Vital, readonly [number, number]> = {
  LCP: [2500, 4000], INP: [200, 500], CLS: [0.1, 0.25],
};
function rating(name: Vital, value: number): Rating {
  if (!Number.isFinite(value) || value < 0) throw new RangeError('Invalid value');
  const [good, poor] = cutoffs[name];
  return value <= good ? 'good' : value <= poor ? 'needs-improvement' : 'poor';
}
function p75(values: readonly number[]): number | null {
  if (values.length === 0) return null;
  if (values.some(value => !Number.isFinite(value) || value < 0)) {
    throw new RangeError('Invalid sample');
  }
  const sorted = [...values].sort((a, b) => a - b);
  return sorted[Math.ceil(sorted.length * 0.75) - 1];
}
const mobileLcp = [1200, 1600, 2100, 2800, 3500, 3900, 4200, 6000];
const value = p75(mobileLcp);
console.log(value, value === null ? 'no data' : rating('LCP', value));
console.log(rating('INP', 320), rating('CLS', 0.25));
```

Eight sorted visits; nearest-rank p75 selects the sixth value, 3,900 ms — **needs improvement**. Sorting a copy preserves the caller's sample order, and empty samples return null: treating missing data as zero would falsely report success. The input must hold one appropriate observation per visit and metric — repeated callbacks from one visit are updates, not extra visits. Never average daily p75 values into a monthly p75; aggregate the underlying distribution or a supported mergeable representation.

## Collect once, then preserve the reporting contract

Use the maintained `web-vitals` library for browser lifecycle and metric logic. Register collectors once per document through application bootstrap — repeated React effects can register additional observers, and storing a metric in a ref does not make React rerender. The library's normal collection functions do not provide a React effect cleanup contract. [Library usage and lifecycle](https://github.com/GoogleChrome/web-vitals)

A reporting callback receives both `value` and `delta`: `value` is the current metric value, `delta` its change since the previous report. Upsert the current value by metric ID, or accumulate deltas under an explicitly chosen contract — renaming delta to value and treating every callback as another visit corrupts the distribution. Transport acceptance is also limited: `sendBeacon` returning true means queued, not acknowledged. Bound payloads and retries; avoid collecting user-entered text, raw sensitive URLs or full DOM nodes. Unsupported browser APIs and consent restrictions create missing samples that must stay visible in coverage reports. The ingestion and sampling mechanism lives in [real-user monitoring](../02-measurement/50.3.2.04-real-user-monitoring.md).

## Decide which evidence answers the question

| Question | Useful evidence | Boundary |
| ------------------------------------------------ | ---------------------------------------------------- | ---------------------------------------------- |
| Did a build delay the main image? | Repeatable lab run and resource/render trace | Fixed conditions do not represent all visits |
| Which production users have poor responsiveness? | Segmented field INP with sample/coverage information | No-interaction visits must not become zero INP |
| Did an ad cause movement? | Layout-shift trace and affected elements | Lifetime sums differ from CLS windows |
| Did a release improve the product journey? | Comparable field populations and task outcomes | Correlation alone does not prove causation |

Use phone and desktop segments plus relevant journey segments without combining incompatible units or hiding a small sample. A page-level INP is not a timer for just Add to cart. Lighthouse navigation diagnostics, including Total Blocking Time, help investigate responsiveness but do not supply production field INP. CI setup belongs in [Lighthouse CI](../02-measurement/50.3.2.03-lighthouse-ci.md), and local release thresholds belong in [performance budgets](../03-optimization-and-governance/50.3.3.02-performance-budgets.md).

## Summary

LCP explains visible loading, INP explains interaction response, and CLS explains unexpected movement — each with a different measurement boundary. Trace the delayed work or movement in one visit, then assess the relevant field distribution. Correct collection, update aggregation and explicit missing data matter as much as the threshold.

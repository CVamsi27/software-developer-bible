# Performance APIs

A shopper reports that checkout freezes after pressing Pay. Browser timing entries can distinguish a delayed request from main-thread work; application marks can measure the owned operation — but neither should be mistaken for a complete user-experience metric.

```typescript
// Elapsed time uses the monotonic clock; calendar time uses Date.
const start = performance.now();
await checkout();
const elapsedMs = performance.now() - start;
```

## Definition

The browser **Performance APIs** expose timing **entries** for navigation, resources, paints and application-defined work. They answer **which phase consumed time** rather than treating page load as one opaque duration. Entries describe measurements; optimizing still requires finding the cause.

> **Textbook Definition:** The Performance APIs expose standardized browser timing measurements and application-defined marks and measures through the performance timeline; observers receive supported entries for analysis.

## First Principles

**Wall clocks can change during a measurement** — use the monotonic `performance.now()` clock for elapsed time and `Date.now()` only when an event needs a calendar timestamp. **The browser owns network and rendering phases**, so application timestamps cannot reliably reconstruct DNS, TLS, response arrival or paint. **A measurement needs a boundary and a reporting rule**: request duration, navigation TTFB and a user interaction measure different intervals, and a correct timestamp with the wrong boundary misleads. **Observability changes the workload**, so bound buffers, sampling and payloads.

## 1. Choose the Entry That Matches the Question

| Question | API | Limitation |
| ------------------------------------------- | --------------------------------- | ------------------------------------------------ |
| When did navigation phases finish? | `PerformanceNavigationTiming` | Later phases are unavailable until they occur |
| Which resource took time? | `PerformanceResourceTiming` | Cross-origin detail may be restricted |
| How long did an application operation take? | User Timing marks/measures | Boundaries and cleanup belong to the application |
| When do new entries arrive? | `PerformanceObserver` | Supported entry types vary by browser |
| What are the page's Core Web Vitals? | `web-vitals` over browser entries | Lifecycle and aggregation rules matter |

Navigation and resource timestamps are relative to the performance time origin, not Unix time — use `performance.timeOrigin` only when converting to a common timestamp, accounting for reduced precision and privacy restrictions. Navigation Timing describes a document navigation, not each client-side route in a single-page application; measure an SPA transition with application-owned marks around a clearly defined route event.

## 2. Read Modern Navigation Entries After the Relevant Phase

Call this after `load` when you want final load duration. Before then, the function preserves `null` for an unfinished load event. The connection interval includes TLS where applicable — do not add the TLS interval to it again. Use Navigation Timing entries instead of the legacy `performance.timing` interface.

```typescript
function getNavigationTiming() {
  const entry = performance.getEntriesByType('navigation')[0] as
    PerformanceNavigationTiming | undefined;
  if (!entry) return null;

  return {
    // Navigation start to first response byte, including earlier phases.
    ttfb: entry.responseStart - entry.startTime,
    // Time after sending this request until its first response byte.
    requestWait: entry.responseStart - entry.requestStart,
    dns: entry.domainLookupEnd - entry.domainLookupStart,
    connection: entry.connectEnd - entry.connectStart,
    // Zero may mean no exposed/new TLS handshake. Do not subtract it.
    tls: entry.secureConnectionStart > 0
      ? entry.connectEnd - entry.secureConnectionStart : null,
    domInteractive: entry.domInteractive > 0 ? entry.domInteractive : null,
    load: entry.loadEventEnd > 0 ? entry.loadEventEnd - entry.startTime : null,
  };
}
```

A zero phase duration can be legitimate for a reused connection or cached response — or reflect restricted information. The result alone does not prove that no networking occurred.

## 3. Keep Concurrent User Timing Operations Independent

The helper preserves the operation's value or rejection, measures unsuccessful calls too, and clears only entries it owns. It uses a sequence number so concurrent calls with the same label do not overwrite each other's start marks. The label should be a stable operation name, not a URL containing user data.

```typescript
let operationSequence = 0;

async function measureOperation<T>(
  label: string,
  operation: () => Promise<T>,
  report: (label: string, duration: number) => void,
): Promise<T> {
  const name = `${label}:${++operationSequence}`;
  const start = `${name}:start`;
  performance.mark(start);
  try {
    return await operation();
  } finally {
    try {
      const measurement = performance.measure(name, start);
      report(label, measurement.duration);
    } catch {
      // Instrumentation failure must not replace the operation's result.
    } finally {
      performance.clearMarks(start);
      performance.clearMeasures(name);
    }
  }
}
```

To see the ownership contract, append this invocation after the helper in a browser TypeScript entry point:

```typescript
async function runExample() {
  const reports: Array<{ label: string; duration: number }> = [];
  const result = await measureOperation('catalog.fixture', async () => {
    await new Promise<void>(resolve => setTimeout(resolve, 20));
    return { items: 2 };
  }, (label, duration) => { reports.push({ label, duration }); });
  console.log(result.items, reports[0].label, reports[0].duration >= 0);
}
void runExample().catch(error => { console.error(error); });
```

Output starts with `2 catalog.fixture true`; the timer duration is not an exact promised measurement. Change the operation to reject: reporting still occurs and the caller receives the original rejection. Change the reporting callback to throw: that instrumentation failure is swallowed so it cannot replace the operation's value. This measures operation settlement, not a later browser paint. For React rendering, use the [React Profiler](../../../10-frontend/10.3-react/INDEX.md) — a mark inside render plus a passive effect mixes scheduling, commit and effect delay, and is not an accurate component timer under concurrent rendering.

## 4. Observe Entries and Release the Observer

```typescript
function observeResources(
  report: (entry: PerformanceResourceTiming) => void,
): () => void {
  if (typeof PerformanceObserver === 'undefined' ||
      !(PerformanceObserver.supportedEntryTypes ?? []).includes('resource')) {
    return () => {};
  }
  const observer = new PerformanceObserver((list) => {
    for (const entry of list.getEntries()) {
      report(entry as PerformanceResourceTiming);
    }
  });
  observer.observe({ type: 'resource', buffered: true });
  return () => observer.disconnect();
}
```

`buffered: true` requests earlier retained entries of that type; it does not recover entries already dropped from a full buffer. Resource names can contain query strings or identifiers — normalize or omit them before exporting telemetry. A cross-origin server's `Timing-Allow-Origin` controls which detailed timings are exposed; CORS permission alone does not unlock them. A zero `transferSize` can indicate caching or restricted data, so summing it is not a complete traffic bill.

## 5. Treat Raw Entries as Diagnosis, Not Complete Vitals

Use the maintained `web-vitals` package at document bootstrap, with the [metric lifecycle and reporting contract](../01-core-metrics/50.3.1.01-core-web-vitals.md#collect-once-then-preserve-the-reporting-contract). Its metric ID distinguishes updates; value and delta have different aggregation meanings. A raw observer is useful for diagnosis without implementing the full metric.

CLS is the largest layout-shift session window — eligible shifts less than one second apart, spanning less than five seconds per window. Adding every shift over the page lifetime computes a different quantity, and logging every LCP candidate as a final value produces duplicate or premature reports. INP requires selecting and aggregating interactions, not merely collecting long tasks.

For a slow checkout, combine navigation and resource entries with a named payment operation and field Core Web Vitals, comparing comparable device and network populations: a laboratory trace identifies a particular cause, while field distributions show whether that cause affects real users. For suspected memory retention, take heap snapshots and compare retained objects across repeatable interactions — the nonstandard `performance.memory` value is neither portable nor proof of a leak.

## Summary

Use browser entries for browser-owned phases and User Timing for application-owned operations. Correct boundaries, lifecycle aggregation, concurrency handling and cleanup matter as much as the API call. Raw entries diagnose; complete vitals require lifecycle and aggregation rules. Missing or restricted data needs an explicit interpretation before it reaches a dashboard.

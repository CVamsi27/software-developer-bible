# Performance APIs

## Definition

The browser Performance APIs expose timing entries for navigation, resources, paints, and application-defined work. They help answer **which phase consumed time**, rather than treating page load as one opaque duration. Entries describe measurements; optimizing an application still requires finding the cause.

## First Principles

1. **Wall clocks can change during a measurement.** Use the monotonic `performance.now()` clock for elapsed time; use `Date.now()` when an event needs a calendar timestamp.
2. **The browser owns network and rendering phases.** Application timestamps cannot reliably reconstruct DNS, TLS, response arrival, or paint. Read browser entries for those phases.
3. **A measurement needs a boundary and a reporting rule.** Request duration, navigation TTFB, and a user interaction measure different intervals. A correct timestamp with the wrong boundary gives a misleading metric.
4. **Observability changes the workload.** Bound buffers, sampling, and payloads so instrumentation does not become a source of latency or leak sensitive resource URLs.

## Why Do We Need It?

If a page feels slow, separate time waiting for the document from resource loading and main-thread work. If one operation is slow, add a mark around that operation. Start with a question, select the entry type that answers it, and report missing data separately from a measured zero.

## How It Works

| Question | API | Limitation |
| ------------------------------------------- | --------------------------------- | ------------------------------------------------ |
| When did navigation phases finish? | `PerformanceNavigationTiming` | Later phases are unavailable until they occur |
| Which resource took time? | `PerformanceResourceTiming` | Cross-origin detail may be restricted |
| How long did an application operation take? | User Timing marks/measures | Boundaries and cleanup belong to the application |
| When do new entries arrive? | `PerformanceObserver` | Supported entry types vary by browser |
| What are the page's Core Web Vitals? | `web-vitals` over browser entries | Lifecycle and aggregation rules matter |

Navigation/resource timestamps are relative to the performance time origin, not Unix time. Use `performance.timeOrigin` only when converting to a common timestamp, and account for reduced precision and privacy restrictions.

## Code Examples

### Navigation: Read Modern Entries After the Relevant Phase

Call this after `load` when you want final load duration. Before then, the function preserves `null` for an unfinished load event. The connection interval includes TLS where applicable; do not add the TLS interval to it again.

```typescript
function getNavigationTiming() {
  const entry = performance.getEntriesByType('navigation')[0] as
    PerformanceNavigationTiming | undefined;
  if (!entry) return null;

  return {
    // Navigation start to first response byte, including earlier phases.
    ttfb: entry.responseStart - entry.startTime,
    // Time after sending this request until its first response byte.
    requestWait: entry.responseStart - entry.requestStart,
    dns: entry.domainLookupEnd - entry.domainLookupStart,
    connection: entry.connectEnd - entry.connectStart,
    // Zero may mean no exposed/new TLS handshake. Do not subtract it.
    tls: entry.secureConnectionStart > 0
      ? entry.connectEnd - entry.secureConnectionStart : null,
    domInteractive: entry.domInteractive > 0 ? entry.domInteractive : null,
    load: entry.loadEventEnd > 0 ? entry.loadEventEnd - entry.startTime : null,
  };
}
```

A zero phase duration can be legitimate for a reused connection or cached response. It can also reflect restricted information. The result alone does not prove that no networking occurred.

### User Timing: Keep Concurrent Operations Independent

The helper preserves the operation's value or rejection, measures unsuccessful calls too, and clears only entries it owns. It uses a sequence number so concurrent calls with the same label do not overwrite each other's start marks. The label should be a stable operation name, not a URL containing user data.

```typescript
let operationSequence = 0;

async function measureOperation<T>(
  label: string,
  operation: () => Promise<T>,
  report: (label: string, duration: number) => void,
): Promise<T> {
  const name = `${label}:${++operationSequence}`;
  const start = `${name}:start`;
  performance.mark(start);
  try {
    return await operation();
  } finally {
    try {
      const measurement = performance.measure(name, start);
      report(label, measurement.duration);
    } catch {
      // Instrumentation failure must not replace the operation's result.
    } finally {
      performance.clearMarks(start);
      performance.clearMeasures(name);
    }
  }
}
```

For React rendering, use the [React Profiler](../../../10-frontend/10.3-react/INDEX.md). A mark inside render followed by a passive effect measures a mixture of scheduling, commit, and effect delay; it is not an accurate component render timer, especially with concurrent rendering.

### Observe Entries and Release the Observer

```typescript
function observeResources(
  report: (entry: PerformanceResourceTiming) => void,
): () => void {
  if (typeof PerformanceObserver === 'undefined' ||
      !PerformanceObserver.supportedEntryTypes.includes('resource')) {
    return () => {};
  }
  const observer = new PerformanceObserver((list) => {
    for (const entry of list.getEntries()) {
      report(entry as PerformanceResourceTiming);
    }
  });
  observer.observe({ type: 'resource', buffered: true });
  return () => observer.disconnect();
}
```

`buffered: true` requests earlier retained entries of that type; it does not recover entries already dropped from a full buffer. Resource names can contain query strings or identifiers. Normalize or omit them before exporting telemetry. A cross-origin server's `Timing-Allow-Origin` controls which detailed timings are exposed; CORS permission alone does not unlock them. A zero `transferSize` can indicate caching or restricted data, so summing it is not a complete traffic bill.

### Core Web Vitals: Use the Metric's Aggregation Rules

```typescript
import { onCLS, onINP, onLCP } from 'web-vitals';

function reportVital(metric: {
  name: string; value: number; id: string; delta: number;
}) {
  // Send a sampled, bounded payload through your telemetry client.
  console.log(metric.name, metric.value, metric.id, metric.delta);
}

onCLS(reportVital);
onINP(reportVital);
onLCP(reportVital);
```

Install `web-vitals` through the application's package manager. This snippet logs metrics; it does not implement a telemetry endpoint. Reports can update, so use the metric ID and the chosen final-value or delta strategy deliberately.

CLS is the largest layout-shift session window: eligible shifts less than one second apart, up to five seconds per window. Adding every shift over the page lifetime computes a different quantity. LCP also depends on page lifecycle; logging every candidate as if it were a final value produces duplicate or premature reports. INP requires selecting and aggregating interactions, not merely collecting long tasks.

## Real-World Use Cases

For a slow checkout, combine navigation/resource entries with a named payment operation and field Core Web Vitals. Compare comparable device and network populations. A laboratory trace identifies a particular cause; field distributions show whether that cause affects real users.

For suspected memory retention, take heap snapshots and compare retained objects across repeatable interactions. The nonstandard `performance.memory` value is neither portable nor proof of a leak: heap growth before garbage collection is normal, and shared heaps complicate attribution.

## Common Mistakes

- Using deprecated `performance.timing` rather than navigation entries.
- Calling request wait time “navigation TTFB,” or interpreting incomplete fields as fast results.
- Sharing mark names across concurrent operations, retaining unbounded entries, or letting telemetry errors replace application errors.
- Assuming every browser implements every observer entry type.
- Summing lifetime layout shifts and calling that sum CLS.
- Exporting raw resource URLs or measuring the telemetry requests repeatedly in a feedback loop.

## Best Practices

Choose a small set of useful metrics, feature-detect the required entries, and represent unavailable data explicitly. Sample field telemetry, enforce payload limits, and disconnect observers when their owner stops. Test instrumentation failures and concurrent operations. Keep an agreed measurement boundary alongside every dashboard metric.

## Summary

Use browser entries for browser-owned phases and User Timing for application-owned operations. Correct boundaries, lifecycle aggregation, concurrency, and cleanup matter as much as the API call. Missing or restricted data needs an explicit interpretation before it reaches a dashboard.

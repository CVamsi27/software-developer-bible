# Profiling Tools

A search box feels slow after typing. Is the browser waiting for a response, filtering a large array, updating thousands of elements — or painting them? The trace should answer that before any code change is chosen.

```javascript
// Attribute first: elapsed time alone cannot name the boundary.
const start = performance.now();
await applyFilter(query);
console.log(`filter settled in ${(performance.now() - start).toFixed(1)} ms`);
```

## Definition

**Profiling tools** are browser and external utilities that attribute execution and resource cost to operations, call paths and allocations. **Sampling** observes selected moments; **instrumentation** records selected events. Both have overhead and incomplete coverage.

> **Textbook Definition:** Profiling measures execution or resource use and attributes the observed cost to operations, call paths or allocations. Sampling observes selected moments; instrumentation records selected events. Both have overhead and incomplete coverage.

## First Principles

A user action crosses several boundaries: input dispatch, JavaScript work, resource waits, rendering and presentation. Time spent in one boundary cannot explain a different boundary without evidence connecting them — a stopwatch gives elapsed time, while attribution requires observations about what ran during that interval. Capturing those observations also consumes resources, so record a short repeatable journey with its build, device and cache conditions, then compare an intervention against a baseline.

## How It Works

### 1. Connect the Costs in One Recording

```text
input arrives → waits for a free main thread → handler runs
               → style/layout/paint → visible update
                      ↑
       fetched data or images may be prerequisites
```

The arrows show dependencies, not equal time slices. A request may overlap JavaScript — adding every row's duration would double-count overlapping work. Inspect the interval between the action and the visible result, then identify the work on that path.

| Observation | Useful view | What it cannot establish alone |
| ---------------------------------------- | ------------------------------------ | ------------------------------------------------ |
| Which task occupied the main thread? | Performance timeline and call stacks | The same cost on another device |
| Which call path contains expensive work? | Call tree | That the parent function itself did all the work |
| Where is time spent directly? | Bottom-up self time | Why the work was required by the product |
| Which request delayed a dependency? | Network waterfall | Browser rendering cost after arrival |
| What remains reachable after cleanup? | Heap snapshot and retaining paths | A leak from one rising memory sample |
| Which React subtree rendered? | React Profiler | Full input-to-paint latency |

A **flame chart** places events along elapsed time and stacks nested calls vertically. An aggregated **flame graph** groups sampled call stacks; its horizontal arrangement need not represent chronological order — always check the tool's units before interpreting width. `PerformanceObserver` exposes selected timing entries, not every JavaScript call stack; use a CPU profile to attribute execution to functions.

### 2. Trace One Interaction Before Optimizing

Use a production-like build, representative data, and a documented device, cache and network setup. Open Chrome DevTools' Performance panel, start recording, type one query, wait for results and stop. Select that interval. Connect the interaction, main-thread tasks and screenshot change before examining a call stack. Consider this illustrative call tree; the numbers describe a hypothetical trace:

```text
handleQuery: 120 ms total, 10 ms self
  filterRows: 80 ms total/self
  updateRows: 30 ms total, 5 ms self
    layout work: 25 ms
```

The parent includes its children: 10 + 80 + 5 + 25 = 120 ms, so adding 120 + 80 + 30 + 25 is wrong. **Total time** includes descendants; **self time** excludes them. The filter is the largest direct cost — reduce its repeated work first, replay the same query, and check the result remains correct. A faster filter can expose layout as the next bottleneck. Sampling can miss short calls, so interpret small differences cautiously; CPU throttling approximates slower execution on the current machine, so confirm important conclusions on actual target hardware.

### 3. Run a Focused Layout Experiment

Save this complete fixture as `layout.html`, serve it locally and open it in a browser. Record each button separately. The status gives a measured interval; DevTools supplies attribution.

```html
<!doctype html>
<html lang="en">
<meta charset="utf-8">
<title>Layout profiling experiment</title>
<style>
  .row { width: 120px; padding: 1px; border: 1px solid; }
</style>
<button id="interleave" type="button">Interleave writes and reads</button>
<button id="batch" type="button">Batch writes, then reads</button>
<p id="status" role="status"></p>
<div id="rows"></div>
<script>
  const container = document.querySelector('#rows');
  for (let index = 0; index < 500; index++) {
    const row = document.createElement('div');
    row.className = 'row';
    row.textContent = String(index);
    container.append(row);
  }
  const rows = [...container.children];
  let target = 180;
  function run(interleaved) {
    target = target === 180 ? 220 : 180;
    let total = 0;
    const start = performance.now();
    if (interleaved) {
      for (const row of rows) {
        row.style.width = `${target}px`;
        total += row.offsetWidth;
      }
    } else {
      for (const row of rows) row.style.width = `${target}px`;
      for (const row of rows) total += row.offsetWidth;
    }
    const elapsed = performance.now() - start;
    document.querySelector('#status').textContent =
      `${total} total pixels; ${elapsed.toFixed(2)} ms for synchronous work`;
  }
  document.querySelector('#interleave').onclick = () => run(true);
  document.querySelector('#batch').onclick = () => run(false);
</script>
</html>
```

A width write invalidates layout, and reading `offsetWidth` requires current geometry — interleaving can force repeated synchronous layout, while batching writes lets the subsequent reads share computed geometry. Both paths compute the same widths; the fixture alternates targets to avoid measuring unchanged writes. The timer ends before a future paint and does not measure the whole interaction. Repeat runs with order alternated, and never hard-code a guaranteed speedup. Removing a geometry read altogether may outperform both paths if the product does not need it.

### 4. Measure React Rendering Without a Fake Recording Switch

This complete TSX component uses React's callback for committed rendering work. Render it from an existing React application entry point.

```tsx
import { Profiler, useState, type ProfilerOnRenderCallback } from 'react';

const onRender: ProfilerOnRenderCallback = (
  id, phase, actualDuration, baseDuration, startTime, commitTime
) => {
  console.table([{ id, phase, actualDuration, baseDuration, startTime, commitTime }]);
};

export default function ProfiledCounter() {
  const [count, setCount] = useState(0);
  return (
    <Profiler id="Counter" onRender={onRender}>
      <button type="button" onClick={() => setCount(value => value + 1)}>
        Count: {count}
      </button>
    </Profiler>
  );
}
```

Clicking changes state and supplies another callback. `actualDuration` is rendering cost for this committed update; `baseDuration` estimates the subtree's cost without memoization. Neither includes all network, layout, paint or input delay, and development checks can add work. Normal production builds disable profiling by default — use an explicitly configured profiling build for production-like rendering. A boolean state labeled "start profiling" would not start a DevTools recording. Use the browser Performance panel alongside React evidence when the complaint is delayed presentation.

### 5. Prove Retention Before Calling It a Memory Leak

Open the Memory panel and take a heap snapshot at an idle baseline. Repeat a mount, use and unmount cycle, return to the same idle state, then compare another snapshot. Inspect the objects that remain and their **retaining path** — the chain of references keeping them reachable from a live root. For example, a `window` listener can retain a callback, which retains an obsolete component and its detached elements: remove the owned listener during teardown, repeat the cycle, and check that the accumulation stops.

Console references and legitimate caches can retain objects too. A sawtooth heap curve is compatible with ordinary allocation and garbage collection — a rising average alone does not prove a leak. Heap snapshots are debugging artifacts and may expose user data, so take them with an appropriate test dataset. Snapshot capture can pause execution and must not be mistaken for normal request latency.

Choose the tool by the question: Lighthouse CI for repeatable navigation audits and budget failure evidence ([setup](50.3.2.03-lighthouse-ci.md)); WebPageTest for a controlled remote location, browser and network setup — still a lab run, so specify cache state, repeated runs and the tested journey. Use [RUM](50.3.2.04-real-user-monitoring.md) to find affected populations, then reproduce a representative scenario locally. A local fix is a candidate until the deployed field result supports it.

## Summary

Locate the user-visible interval, attribute its costs, and test one cause at a time. CPU traces, network waterfalls, heap retaining paths and React callbacks answer different questions. Preserve workload and correctness while comparing changes, and keep the measured boundary explicit.

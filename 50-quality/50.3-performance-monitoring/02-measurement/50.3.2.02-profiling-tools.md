# Profiling Tools

A search box feels slow after typing. Is the browser waiting for a response, filtering a large array, updating thousands of elements or painting them? The trace should answer that before a code change is chosen.

## Definition

Profiling tools are browser and external utilities that help developers analyze, debug, and optimize web application performance by providing detailed insights into rendering, JavaScript execution, memory usage, and network activity.

> **Textbook Definition:** Profiling measures execution or resource use and attributes the observed cost to operations, call paths or allocations. Sampling observes selected moments; instrumentation records selected events. Both have overhead and incomplete coverage.

## First Principles

A user action crosses several boundaries: input dispatch, JavaScript work, resource waits, rendering and presentation. Time spent in one boundary cannot explain a different boundary without evidence connecting them. A stopwatch gives elapsed time; attribution requires additional observations about what ran during that interval.

Capturing those observations also consumes resources. Record a short repeatable journey with its build, device and cache conditions, then compare an intervention with a baseline. A trace is an observation under those conditions, not a universal prediction for every device.

## How a recording connects the costs

```text
input arrives → waits for a free main thread → handler runs
               → style/layout/paint → visible update
                      ↑
       fetched data or images may be prerequisites
```

The arrows show dependencies, not equal time slices. A request may overlap JavaScript; adding every row's duration would double-count overlapping work. Inspect the interval between the action and the visible result, then identify the work on that path.

| Observation | Useful view | What it cannot establish alone |
| ---------------------------------------- | ------------------------------------ | ------------------------------------------------ |
| Which task occupied the main thread? | Performance timeline and call stacks | The same cost on another device |
| Which call path contains expensive work? | Call tree | That the parent function itself did all the work |
| Where is time spent directly? | Bottom-up self time | Why the work was required by the product |
| Which request delayed a dependency? | Network waterfall | Browser rendering cost after arrival |
| What remains reachable after cleanup? | Heap snapshot and retaining paths | A leak from one rising memory sample |
| Which React subtree rendered? | React Profiler | Full input-to-paint latency |

A **flame chart** places events along elapsed time and stacks nested calls vertically. An aggregated **flame graph** groups sampled call stacks; its horizontal arrangement need not represent chronological order. Always check the tool's units before interpreting width.

`PerformanceObserver` exposes selected timing entries, not every JavaScript call stack. Use a CPU profile to attribute execution to functions.

## Trace one interaction before optimizing

Use a production-like build, representative data and a documented device/cache/network setup. Open Chrome DevTools' Performance panel, start recording, type one query, wait for results and stop. Select that interval. Connect the interaction, main-thread tasks and screenshot change before examining a call stack.

Consider this illustrative call tree; the numbers describe a hypothetical trace:

```text
handleQuery: 120 ms total, 10 ms self
  filterRows: 80 ms total/self
  updateRows: 30 ms total, 5 ms self
    layout work: 25 ms
```

The parent includes its children: 10 + 80 + 5 + 25 = 120 ms. Adding 120 + 80 + 30 + 25 is wrong. The filter is the largest direct cost. First reduce its repeated work, then replay the same query and check the result remains correct. A faster filter can expose layout as the next bottleneck.

**Total time** includes descendants; **self time** excludes them. The call tree explains how work was reached. Bottom-up aggregation helps find expensive leaf work across multiple callers. Sampling can miss short calls, so interpret small differences cautiously. CPU throttling approximates slower execution on the current machine; confirm important conclusions on actual target hardware.

## Code Examples

### A focused layout experiment

Save this complete fixture as `layout.html`, serve it locally and open it in a browser. Record each button separately. The status gives a measured interval; DevTools supplies attribution.

```html
<!doctype html>
<html lang="en">
<meta charset="utf-8">
<title>Layout profiling experiment</title>
<style>
  .row { width: 120px; padding: 1px; border: 1px solid; }
</style>
<button id="interleave" type="button">Interleave writes and reads</button>
<button id="batch" type="button">Batch writes, then reads</button>
<p id="status" role="status"></p>
<div id="rows"></div>
<script>
  const container = document.querySelector('#rows');
  for (let index = 0; index < 500; index++) {
    const row = document.createElement('div');
    row.className = 'row';
    row.textContent = String(index);
    container.append(row);
  }
  const rows = [...container.children];
  let target = 180;
  function run(interleaved) {
    target = target === 180 ? 220 : 180;
    let total = 0;
    const start = performance.now();
    if (interleaved) {
      for (const row of rows) {
        row.style.width = `${target}px`;
        total += row.offsetWidth;
      }
    } else {
      for (const row of rows) row.style.width = `${target}px`;
      for (const row of rows) total += row.offsetWidth;
    }
    const elapsed = performance.now() - start;
    document.querySelector('#status').textContent =
      `${total} total pixels; ${elapsed.toFixed(2)} ms for synchronous work`;
  }
  document.querySelector('#interleave').onclick = () => run(true);
  document.querySelector('#batch').onclick = () => run(false);
</script>
</html>
```

A width write invalidates layout. Reading `offsetWidth` requires current geometry; interleaving can force repeated synchronous layout. Batching writes lets the subsequent reads share computed geometry until another change invalidates it. Both paths compute the same widths for the same target; the fixture alternates targets to avoid measuring unchanged writes.

The timer ends before a future paint and does not measure the whole interaction. Repeat runs with order alternated; do not hard-code a guaranteed speedup or exact layout-event count. Removing a geometry read altogether may outperform both paths if the product does not need it.

### Measure React rendering without a fake recording switch

This complete TSX component uses React's callback for committed rendering work. Render it from an existing React application entry point.

```tsx
import { Profiler, useState, type ProfilerOnRenderCallback } from 'react';

const onRender: ProfilerOnRenderCallback = (
  id, phase, actualDuration, baseDuration, startTime, commitTime
) => {
  console.table([{ id, phase, actualDuration, baseDuration, startTime, commitTime }]);
};

export default function ProfiledCounter() {
  const [count, setCount] = useState(0);
  return (
    <Profiler id="Counter" onRender={onRender}>
      <button type="button" onClick={() => setCount(value => value + 1)}>
        Count: {count}
      </button>
    </Profiler>
  );
}
```

Clicking changes state and supplies another callback. `actualDuration` is rendering cost for this committed update; `baseDuration` estimates the subtree's cost without memoization. Neither includes all network, layout, paint or input delay. Development checks can add work. Normal production builds disable profiling by default; use an explicitly configured profiling build when measuring production-like rendering. A boolean state labeled “start profiling” would not start a DevTools recording.

Use the browser Performance panel alongside React evidence when the complaint is delayed presentation. Sending a request for every render can itself distort the workload; use bounded, deliberately sampled reporting if it is needed.

## Real-World Decisions

### Prove retention before calling it a memory leak

Open the Memory panel and take a heap snapshot at an idle baseline. Repeat a mount/use/unmount cycle, return to the same idle state, then compare another snapshot. Inspect objects that remain and their **retaining path**: the chain of references keeping them reachable from a live root.

For example, a listener on `window` can retain a callback, which retains an obsolete component and its detached elements. Remove the owned listener during teardown, repeat the cycle and check that the accumulation stops. Console references and legitimate caches can retain objects too. A sawtooth heap curve is compatible with ordinary allocation and garbage collection; a rising average alone does not prove a leak.

Heap snapshots are debugging artifacts and may expose user data. Take them with an appropriate test dataset. Page JavaScript has no `window.chrome.sendCommand` heap-snapshot API; use DevTools or a debugging-protocol client. Snapshot capture can pause execution and should not be mistaken for normal request latency.

### Choose a tool by the question

Use Lighthouse CI for repeatable navigation audits and budget failure evidence; its executable setup lives in the [Lighthouse CI chapter](50.3.2.03-lighthouse-ci.md). Use WebPageTest when a controlled remote location/browser/network setup answers the hypothesis. A remote result is still a lab run; specify cache state, repeated runs and the tested journey. Do not treat a public API endpoint, authentication or browser availability as interchangeable across hosted plans.

Use [RUM](50.3.2.04-real-user-monitoring.md) to find affected populations, then reproduce a representative scenario locally. A local fix is a candidate until the deployed field result supports it under comparable traffic and collection coverage.

## Summary

Locate the user-visible interval, attribute its costs and test one cause at a time. CPU traces, network waterfalls, heap retaining paths and React callbacks answer different questions. Preserve workload and correctness while comparing changes, and keep the measured boundary explicit.

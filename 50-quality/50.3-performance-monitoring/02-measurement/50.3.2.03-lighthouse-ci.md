# Lighthouse CI

A dependency change may delay the product image. A repeatable audit can catch a regression before release, but only on the routes, states and conditions the pipeline actually tests.

## Definition

Lighthouse CI automates Lighthouse laboratory audits around a built website. It collects reports, checks configured assertions and retains results. A failing assertion can block a release when the pipeline and branch rules require that check.

> **Textbook Definition:** Lighthouse CI is a toolchain for collecting Lighthouse audit results, asserting configured thresholds and retaining reports across builds. Its laboratory observations do not replace production user measurements.

## First Principles

An observation does not enforce a release decision on its own. The workflow needs a served build, an agreed measurement, a comparison rule and a checked exit status. If the command is allowed to fail or its status is ignored, the budget does not govern the release.

Measurements also vary with browser version, host contention, throttling, cache and page state. Repeated controlled runs make a regression easier to distinguish from noise; they do not make a laboratory deterministic or representative of every user.

## Follow the report into the decision

```text
production build → serve selected routes → collect Lighthouse reports
   → apply configured assertions → nonzero exit for an error-level failure
   → pipeline decision, with retained reports for diagnosis
```

The `@lhci/cli` commands collect, assert and upload have different responsibilities. `autorun` orchestrates them according to configuration. An upload target is separate from the assertion contract; public temporary storage makes reports available to people with their links. The fixture below retains files locally. [CLI configuration](https://github.com/GoogleChrome/lighthouse-ci/blob/main/docs/configuration.md)

## Run one complete static fixture

Use a scratch directory with Node and Chrome installed. Install the CLI, retain its lockfile and create `public/index.html`:

```bash
npm init -y
npm install --save-dev @lhci/cli
```

```html
<!doctype html>
<html lang="en">
<head><meta charset="utf-8"><meta name="viewport" content="width=device-width,initial-scale=1">
<title>Catalog fixture</title></head>
<body><main><h1>Catalog fixture</h1><p>One local page for checking an audit pipeline.</p>
<button type="button">Choose product</button></main></body>
</html>
```

Save this complete configuration as `lighthouserc.json`. The CLI serves the static directory during collection; an application requiring server rendering needs its production server and a verified readiness condition instead.

```json
{
  "ci": {
    "collect": {
      "staticDistDir": "./public",
      "numberOfRuns": 3,
      "settings": { "preset": "desktop" }
    },
    "assert": {
      "assertions": {
        "categories:performance": ["error", { "minScore": 0.9, "aggregationMethod": "median" }],
        "largest-contentful-paint": ["error", { "maxNumericValue": 2500, "aggregationMethod": "median" }],
        "cumulative-layout-shift": ["error", { "maxNumericValue": 0.1, "aggregationMethod": "median" }],
        "total-blocking-time": ["warn", { "maxNumericValue": 200, "aggregationMethod": "median" }]
      }
    },
    "upload": { "target": "filesystem", "outputDir": "./reports" }
  }
}
```

Run:

```bash
npx lhci autorun --config=./lighthouserc.json
```

If Chrome is not discoverable, set `CHROME_PATH` to the installed browser executable. Check the final exit status and retain `.lighthouseci/` plus the exported reports. The fixture may pass these budgets on a normal host, but its outcome is a measurement, not a promised constant.

Trace one LCP assertion: three per-route values are sorted, the configured median is compared with 2,500 ms, and an exceeded error-level threshold makes assertion fail. `warn` prints a finding without failing solely for that assertion. A 0.9 category score does not imply that each raw timing met a particular budget, which is why this configuration also checks LCP and CLS.

For a deliberate failure, copy the config and set LCP `maxNumericValue` to zero. Run `lhci assert` against the collected reports with that copy: a positive observed LCP should produce a nonzero status. Restore the realistic budget afterward. This proves the assertion path catches a violation; it is not evidence of a production regression.

## Use the actual assertion names and audit scope

| Assertion key | Meaning | Unit |
| -------------------------- | -------------------------------------- | ----------------------------------------- |
| `categories:performance` | Overall Lighthouse performance score | 0–1 |
| `categories:accessibility` | Automated accessibility category score | 0–1; incomplete evidence of accessibility |
| `largest-contentful-paint` | Lab loading measurement | ms |
| `cumulative-layout-shift` | Layout stability in the audited load | score |
| `total-blocking-time` | Blocking time during the audited load | ms |
| `first-contentful-paint` | First content paint | ms |
| `speed-index` | Visual progression measurement | ms |

Category keys require the `categories:` prefix; bare `performance` is not its category assertion. Audit IDs can change between Lighthouse versions, so check them against the version pinned in the pipeline rather than copying an old configuration blindly.

A normal navigation audit does not measure field INP across real interactions. Total Blocking Time can reveal main-thread risk but has a different boundary. Likewise, a perfect automated accessibility score does not establish keyboard recovery, screen-reader meaning or complete-process conformance. Use the relevant [accessibility checks](../../50.2-accessibility/50.2.08-testing-a11y.md) and [field measurements](50.3.2.04-real-user-monitoring.md).

## Make route, state and environment explicit

For a live application, configure `collect.url` with reachable production-build routes. Set up authentication and deterministic fixture data without exporting real credentials into reports. An unauthenticated login redirect is not evidence about dashboard performance; inspect the final URL and page identity.

Use separate configurations/jobs for desktop and mobile conditions. `collect` is an object, not an array of per-device configurations; desktop has a documented preset, while the standard mobile defaults need a compatible form factor and screen-emulation configuration if overridden. Keep each report population labeled so their scores are not mixed.

Record browser/Lighthouse/CLI versions, build identity, route state, collection settings and assertion aggregation. Repeat enough to investigate variability. A median allows some bad runs; optimistic aggregation allows still more. Choose the release policy deliberately rather than changing aggregation until a failure disappears.

## Retain evidence and own pipeline failure

The CLI is a command-line toolchain, not a documented `start`/`upload` function API imported from `@lhci/cli`. A Node orchestrator should invoke the documented executable and check its exit status, while owning server cleanup and timeouts.

In CI, install the locked dependencies, build, establish server readiness when needed, run the command and retain reports even after assertion failure. Protect branch rules with the intended required check; a failed optional job does not necessarily prevent merging. Do not append `|| true` to the gate or silently turn errors into warnings.

A missing report or failed collection is a failed measurement, not a green page. A report-upload failure is a separate retention problem whose blocking policy must be explicit. Local filesystem export needs the CI artifact system for persistence; it does not itself provide historical comparisons or PR comments. A self-hosted Lighthouse CI server provides additional storage and comparison capabilities. [Getting started](https://github.com/GoogleChrome/lighthouse-ci/blob/main/docs/getting-started.md)

## Summary

Lighthouse CI turns selected laboratory observations into an enforceable assertion contract. Make the build, route state, environment, aggregation and exit status explicit. Retain the report and test a deliberate failure. A passing lab gate supports a release decision within its scope; field responsiveness and complete accessibility still need their own evidence.

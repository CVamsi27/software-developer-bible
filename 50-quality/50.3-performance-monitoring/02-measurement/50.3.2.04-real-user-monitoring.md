# Real User Monitoring (RUM)

A product-page lab run looks fast, but customers on slower phones report delayed actions. Field measurements can show which observed population is affected — they cannot describe visits the collection system never reaches.

```json
{ "name": "LCP", "id": "visit-metric-1", "value": 1800,
  "sequence": 1, "route": "/catalog", "build": "fixture-build" }
```

## Definition

**Real User Monitoring** captures telemetry from actual application **visits**. It explains the experience users receive across journeys, devices, browsers and networks. A synthetic audit instead executes a chosen workload under controlled conditions.

> **Textbook Definition:** Real user monitoring collects telemetry from actual application sessions to characterize experienced behavior across devices, networks and journeys. Sampling and collection coverage constrain conclusions about the population.

## First Principles

A production population contains different workloads and environments that one fixed lab run cannot reproduce. Field collection observes some of those visits — so its conclusions depend on who was eligible, who was selected, what their browser could measure, and which reports arrived. An observation also needs identity: a metric can report a later value for the same visit, and counting that update as another independent visit distorts a percentile.

## 1. Trace the Ownership of One Observation

```text
eligible visit → visit-level sampling decision → browser metric update
  → bounded payload → transport attempt → ingestion validation
  → replace that metric's earlier snapshot → segment distribution → decision
```

The browser library owns metric calculation. Application bootstrap owns registration and sampling. The receiver owns validation, admission and persistence. Analysis owns population, units and estimator. A dashboard cannot repair missing identity or biased samples after those facts are discarded. For Core Web Vitals, distinguish [per-visit values and field percentiles](../01-core-metrics/50.3.1.01-core-web-vitals.md). Navigation timings, long tasks and custom operation durations are useful additional observations with different boundaries — never give every long task a Core Web Vitals rating.

## 2. Sample Before Observing the Result

A simple design makes one uniform random decision per eligible document, then keeps all metric updates from selected visits. For a 10 percent sample, generate that decision once at bootstrap rather than independently for each callback. Keep consent and eligibility separate from the random decision. SPA route transitions need an explicit document-versus-journey measurement policy; they do not automatically reset document Core Web Vitals.

Consider 100 visits: 90 fast and 10 slow. Uniform sampling treats both groups with the same probability. A policy keeping every slow visit but only 10 percent of fast visits expects about 9 fast plus 10 slow observations — a mostly slow distribution from a 10-percent-slow population. Such enriched diagnostics need a separate analysis or inclusion probabilities with a weighted estimator; they must never silently become the ordinary population p75. A chosen percentage does not guarantee statistical precision: report sample sizes, coverage, missing metrics and uncertainty. Very small route and device groups need caution, and missing INP is not zero INP.

## 3. Send Snapshots Through One Document-Level Reporter

Save this complete reporter as `reporter.ts` in a browser TypeScript project. The bootstrap supplies an approved route label, release label and the already-made sampling decision. The fixed route label avoids copying a patient ID, email or token from a URL path. This example targets one same-origin endpoint; it does not implement consent policy or production retry storage.

```typescript
type Snapshot = {
  name: 'LCP' | 'INP' | 'CLS'; id: string; value: number;
};
function createReporter(sampled: boolean) {
  let sequence = 0;
  return function report(metric: Snapshot): void {
    if (!sampled) return;
    if (!Number.isFinite(metric.value) || metric.value < 0) return;
    const body = JSON.stringify({
      name: metric.name, id: metric.id, value: metric.value, sequence: ++sequence,
      route: '/catalog', build: 'fixture-build',
    });
    const payload = new Blob([body], { type: 'application/json' });
    if (payload.size > 4096) return;
    try {
      if (navigator.sendBeacon('/api/rum', payload)) return;
    } catch {
      // A refused/unsupported beacon may use the bounded fallback below.
    }
    void fetch('/api/rum', {
      method: 'POST', body: payload, keepalive: true,
    }).then(response => {
      if (!response.ok) throw new Error('RUM rejected');
    }).catch(() => {
      // Teaching policy: drop this report. Never throw into the product flow.
    });
  };
}
```

At application bootstrap, import `onLCP`, `onINP` and `onCLS` from `web-vitals`, construct the reporter once and register each collector once. Pass only `{ name, id, value }` from its Metric — never spread the entire Metric object, whose entries can contain sensitive element and resource information. [Library reporting guidance](https://github.com/GoogleChrome/web-vitals). `sendBeacon` returning true means the browser queued the payload, not that the server stored it; keepalive fetch is also bounded and can fail. The browser's shared keepalive budget is not a guaranteed 64 KB allowance per beacon, and visibility changes or mobile process termination can lose reports. [Beacon delivery contract](https://developer.mozilla.org/en-US/docs/Web/API/Navigator/sendBeacon). A cross-origin JSON Blob can require CORS preflight; use an allowlisted route template, omit user text, and bound dimensions and retention.

## 4. Receive One Idempotent Metric Snapshot

This complete Node fixture demonstrates admission and snapshot identity. Save it as `ingest.cjs` and run `node ingest.cjs`; it listens only on loopback port 18084. It stores at most 1,000 metric identities in memory, loses them on restart, and is not a production telemetry service. The HTTP endpoint does not authenticate a trusted performance source.

```javascript
const http = require('node:http');
const MAX_BYTES = 4096;
function createIngestServer(rows = new Map()) {
  const server = http.createServer((req, res) => {
    if (req.url !== '/api/rum') { res.writeHead(404).end(); return; }
    if (req.method !== 'POST') { res.writeHead(405, { Allow: 'POST' }).end(); return; }
    let bytes = 0, rejected = false;
    const chunks = [];
    req.on('data', chunk => {
      if (rejected) return;
      bytes += chunk.length;
      if (bytes > MAX_BYTES) {
        rejected = true; chunks.length = 0;
        res.writeHead(413).end(); return;
      }
      chunks.push(chunk);
    });
    req.on('error', () => { if (!res.headersSent) res.writeHead(400).end(); });
    req.on('end', () => {
      if (rejected) return;
      let event;
      try { event = JSON.parse(Buffer.concat(chunks).toString('utf8')); }
      catch { res.writeHead(400).end(); return; }
      if (!event || typeof event !== 'object' || Array.isArray(event) ||
          !['LCP', 'INP', 'CLS'].includes(event.name) ||
          typeof event.id !== 'string' || event.id.length < 1 || event.id.length > 128 ||
          !Number.isFinite(event.value) || event.value < 0 ||
          !Number.isSafeInteger(event.sequence) || event.sequence < 1 ||
          event.route !== '/catalog' || event.build !== 'fixture-build') {
        res.writeHead(400).end(); return;
      }
      const key = JSON.stringify([event.build, event.route, event.name, event.id]);
      const previous = rows.get(key);
      if (!previous && rows.size >= 1000) { res.writeHead(503).end(); return; }
      if (!previous || event.sequence > previous.sequence) {
        rows.set(key, { name: event.name, id: event.id, value: event.value,
          sequence: event.sequence, route: event.route, build: event.build });
      }
      res.writeHead(204).end();
    });
  });
  server.requestTimeout = 5000;
  return server;
}
module.exports = { createIngestServer };
if (require.main === module) {
  createIngestServer().listen(18084, '127.0.0.1', () => {
    console.log('Fixture listening at http://127.0.0.1:18084/api/rum');
  });
}
```

Post the hook's JSON body: it creates one stored snapshot and returns 204. A second snapshot with the same identity, value 2200 and sequence 2 replaces it; replaying sequence 1 or 2 creates no new observation and overwrites nothing newer. Invalid data returns 400, oversized input 413, and a new identity at capacity 503. The key combines metric ID with bounded dimensions while the sequence resolves out-of-order callbacks — but establishes no verified users, durable acknowledgment, global deduplication or complete visit count. A production design needs those contracts plus edge admission and rate limits, expiry, durable storage where required, and operational ownership.

## 5. Aggregate the Intended Population

Compute a metric's distribution over the latest appropriate snapshot per identity, within a stated time window and segment. Never count every delivery attempt, mix milliseconds with CLS scores, average subgroup percentiles, or interpret a local in-memory sample as a whole production population. Choose bounded dimensions such as release, route template and a supported device class: browser device and network hints are optional, approximate and privacy-sensitive, so unavailable hints belong in an unknown group rather than a fabricated "mid-tier" default.

An alert needs sufficient observed traffic, collection health and a meaningful comparison. A global percentile can rise because traffic shifted toward slower devices — compare populations and sample policy before blaming a code release. A randomized performance experiment also needs valid assignment, exposure, comparable collection and enough evidence; a smaller treatment p75 alone is not a general significance test.

## 6. Keep Your RUM Separate From CrUX and Vendor Claims

The Chrome User Experience Report (CrUX) is Google's independently collected dataset from eligible Chrome users and sufficiently popular public origins and pages — it is not populated by your `/api/rum` endpoint. CrUX and your RUM can differ in population, coverage, time window, lifecycle handling and reporting granularity. [CrUX methodology](https://developer.chrome.com/docs/crux/methodology). CrUX may hold no URL-level record for a requested page, and a broader origin record answers a broader question. Use your field collection for application-specific routes and release context, treating Google's data as another explicitly scoped source.

A hosted SDK can provide ingestion, storage, dashboards and attribution, while a custom system leaves those responsibilities with your team. Verify each candidate's current collection semantics, sampling control, retention, geography, data handling and integration cost. Resource timing and operation measurements live in [Performance APIs](50.3.2.01-performance-apis.md) — do not add duplicate observers here without owning teardown and missing-data policy. A rage click is a possible frustration signal, not proof of an accessibility failure, and a slow interaction needs a causal trace before blaming a framework or network.

## Summary

RUM describes observed production visits under an explicit eligibility, sampling and delivery policy. Preserve metric identity and update semantics before computing a field distribution. Queue acceptance is not durable receipt, missing data is not a fast result, and enriched slow-case diagnostics are not an unbiased population sample. Keep your application RUM and CrUX populations distinct.

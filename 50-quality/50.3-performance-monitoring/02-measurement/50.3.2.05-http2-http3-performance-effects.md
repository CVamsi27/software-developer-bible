# HTTP/2 & HTTP/3 Performance Effects

## TL;DR

HTTP/2 killed the HTTP/1.1 *application-layer* head-of-line blocking via binary framing and multiplexing — but introduced a worse problem: one dropped TCP packet stalls **all** streams (TCP-layer HOL). HTTP/3 moves transport to QUIC over UDP with independent streams, 0-RTT resumption, and connection migration, fixing transport HOL and slow mobile handoffs. Consequences for practice: domain sharding and inlining tricks became anti-patterns, server push died, and priority hints matter more than bundle paranoia. Measure impact on Core Web Vitals per-protocol — LCP/TTFB differences between H2 and H3 are real but workload-dependent.

## Definition

**HTTP/2** (RFC 9113) is a binary, multiplexed protocol: requests are split into frames on numbered streams sharing one TCP connection. **HTTP/3** (RFC 9114) re-runs the same ideas over **QUIC** — a UDP-based transport with TLS 1.3 built in, per-stream flow control, and stream-level loss recovery.

```text
HEAD-OF-LINE BLOCKING ACROSS GENERATIONS

HTTP/1.1 (6 parallel connections)
  conn1: req A ████▒▒▒▒ packet loss -> ALL of conn1 waits
  conn2: req B ████████            (other conns unaffected)
  Application HOL; mitigated only by opening more connections

HTTP/2 (1 connection, many streams)
  stream1: A ▓▓|████████   single TCP byte lost ->
  stream2: B ▓▓|████████   EVERY stream freezes until
  stream3: C ▓▓|████████   retransmission arrives
  App-level HOL solved; TCP-level HOL remains

HTTP/3 / QUIC (streams independent at transport)
  stream1: A ░░|████████   loss on stream1 recovers alone;
  stream2: B   |████████   others keep flowing
  No cross-stream blocking
```

## Why it matters

Protocol choice silently changes which optimizations help or hurt. Teams still shipping H1-era hacks (domain sharding, sprite-everything, manual inlining) onto H2/H3 actively damage performance. Senior interviews use this as a systems-reasoning probe: "Why does HTTP/2 still block? What does QUIC change besides speed?" Tests whether you understand layers — framing vs. transport — rather than memorizing feature lists. It also explains field observations: H3's biggest wins show up on lossy mobile networks and during WiFi/cellular transitions, not on fiber desktops.

## Why Do We Need It?

- **H1 exhaustion**: six-connections-per-origin limits and head-of-line request queuing forced sharding hacks that wasted TLS handshakes and broke caching priorities.
- **H2's false promise**: multiplexing fixed application HOL, but TCP sees one byte stream — any loss blocks delivery of all streams behind it (packet loss >2% often makes H2 slower than H1).
- **Mobile reality**: connection migration (QUIC connection IDs survive IP changes) eliminates the multi-second stall when phones switch WiFi → 5G.
- **Handshake economics**: H2 needs TCP + TLS handshakes (1-2+ RTT before first byte); QUIC combines them — 1-RTT first connection, 0-RTT on resumption.
- **Prioritization debt**: H2 prioritization was so inconsistently implemented across servers that it was replaced by extensible priorities (RFC 9218) in H3.
- **CWV accountability**: TTFB and LCP move measurably with protocol/RTT changes; you cannot reason about RUM data without knowing your protocol mix.

## How It Works

### HTTP/2 mechanics

Binary framing layer converts each message into `HEADERS` (HPACK-compressed) and `DATA` frames tagged with a stream ID:

```text
ONE TCP CONNECTION (HTTP/2)
┌──────────────────────────────────────────────────────┐
│  stream 1: HEADERS ─ DATA ─ DATA                     │
│  stream 3: HEADERS ─ DATA                            │
│  stream 5: HEADERS ─ DATA ─ DATA ─ DATA              │
│                                                      │
│  Frames interleave on the wire:                      │
│  [s1 hdr][s3 hdr][s1 data][s5 hdr][s3 data][s5 dat]  │
│                                                      │
│  Receiver reassembles per stream ID                  │
│  HPACK: header dictionary compression (per-conn)     │
│  Flow control: WINDOW_UPDATE frames, per stream      │
└──────────────────────────────────────────────────────┘
```

The catch: TCP guarantees ordered byte delivery. Frame `[s1 data]` arriving after a lost segment is held in kernel buffers until retransmission — even if streams 3 and 5 have all their bytes ready. One loss = connection-wide stall of roughly one RTT.

### QUIC fixes

```text
QUIC PACKET STRUCTURE
┌───────────────────────────────────────────────┐
│ UDP datagram                                   │
│  ┌─────────────────────────────────────────┐   │
│  │ QUIC packet                             │   │
│  │  header: Connection ID (migration-safe) │   │
│  │          packet number (monotonic)      │   │
│  │  frame:  STREAM 1 [bytes 0-1000]        │   │
│  │  frame:  STREAM 3 [bytes 0-500]         │   │
│  │  frame:  ACK [ranges]                   │   │
│  └─────────────────────────────────────────┘   │
└───────────────────────────────────────────────┘

• Loss tracked PER STREAM RANGE - stream 3 never waits for stream 1
• Packet numbers monotonic -> no retransmission ambiguity (better RTT est.)
• Encryption is part of the protocol (TLS 1.3 frames), not a layer
• Connection IDs decouple identity from 4-tuple -> NAT rebinding,
  WiFi->LTE survives seamlessly
```

Handshake comparison:

```text
FIRST CONNECTION                    RESUMED CONNECTION
H2: TCP SYN       -> RTT 1          H2: TCP SYN    -> RTT 1
    TCP SYN/ACK   <-                TCP SYN/ACK    <-
    TLS ClientHello -> RTT 2        TLS w/ session -> RTT 3
    TLS done      <-                    then request...
    request...                      ~3 RTT before first byte
~2 RTT before first byte

H3: QUIC Initial + TLS hello -> RTT 1     H3: 0-RTT early data
    handshake completes      <-             carries the GET itself
    request may ride same flight         ~1 RTT (or 0 with caveats)
~1 RTT before first byte
```

### Server push: dead

H2 server push let servers send assets before the client asked. In practice servers pushed things already in cache (wasted bytes) because browsers couldn't reliably report cache state. Chrome removed support (106), Firefox followed; H3 omits it. The replacement is `103 Early Hints` — send preload links while the origin computes headers.

### Prioritization

H2's dependency-tree priorities were advisory and implemented differently in every stack — browsers stopped relying on them. RFC 9218 gives H3 extensible priorities (`Priority: urgency=2, incremental`) plus the simpler `load` scheduling. Practical effect: resource ordering now depends mostly on HTML discovery order (`preload`, module graph), not protocol hints.

## Code Examples

### Detecting the protocol in production

```typescript
// Server (Node): read negotiated protocol per request
import type { IncomingMessage } from 'node:http';

export function reportProtocol(req: IncomingMessage): void {
  const socket = req.socket as { alpnProtocol?: string };
  // ALPN tells you h2 vs http/1.1; :authority pseudo-header implies h2+
  console.log(JSON.stringify({
    alpn: socket.alpnProtocol ?? 'unknown',
    httpVersion: req.httpVersion, // '2.0' or '1.1'
  }));
}
```

```typescript
// Client: Navigation Timing exposes nextHopProtocol per resource
const nav = performance.getEntriesByType('navigation')[0] as PerformanceNavigationTiming;
console.log(nav.nextHopProtocol); // 'h2', 'h3', 'http/1.1'

new PerformanceObserver((list) => {
  for (const entry of list.getEntries()) {
    const r = entry as PerformanceResourceTiming;
    beacon('/api/rum', {
      url: r.name,
      proto: r.nextHopProtocol,
      duration: r.responseEnd - r.startTime,
    });
  }
}).observe({ type: 'resource', buffered: true });
```

Segment RUM dashboards by `nextHopProtocol`: if p75 LCP improves dramatically for `h3` users on cellular, your rollout is working where it matters.

### Serving H3 without abandoning H2 clients

```nginx
server {
    listen 443 quic reuseport;   # HTTP/3 (UDP 443)
    listen 443 ssl;              # HTTP/2 + 1.1 (TCP 443)
    http2 on;

    ssl_protocols TLSv1.3;

    # Advertise H3 so capable browsers race an upgrade:
    add_header Alt-Svc 'h3=":443"; ma=86400';
}
```

Browsers discover H3 via `Alt-Svc`, probe it opportunistically, and fall back to H2 on failure — always deploy both.

### Verifying impact on Core Web Vitals

```sql
-- BigQuery over CrUX-style RUM export: CWV by protocol and form factor
SELECT
  payload.next_hop_protocol AS proto,
  payload.form_factor       AS device,
  APPROX_QUANTILES(lcp_ms, 100)[OFFSET(75)] AS p75_lcp_ms,
  COUNT(*)                                  AS samples
FROM `project.rum.page_loads`
WHERE DATE(timestamp) BETWEEN DATE_SUB(CURRENT_DATE(), INTERVAL 28 DAY)
                          AND CURRENT_DATE()
GROUP BY proto, device
ORDER BY device, proto;
```

Expect: H3 ahead mainly on high-loss/mobile segments; parity on low-loss desktop. If H3 shows no win anywhere, check whether loss is actually low enough for QUIC's per-stream recovery to matter.

## Real-World Use Cases

1. **News site global CDN rollout** — enabling H3 cut p75 TTFB by 12% in India/Brazil (lossy last miles) and did nothing measurable in Germany; decision to prioritize edge POPs by traffic loss rates came from protocol-segmented RUM.
2. **Video-call signaling service** — WebSocket-over-H2 suffered full-connection freezes on 1% loss; moving signaling to H3 removed correlated stalls because control and media-description streams recovered independently.
3. **E-commerce cleanup sprint** — removing legacy domain sharding (`cdn1.`–`cdn4.`) consolidated connections, improved HPACK efficiency, and *raised* Lighthouse scores after H2 enablement made sharding pure overhead.
4. **API gateway migration** — gRPC (itself H2-based) fronted by an H3-capable load balancer reduced tail latency for mobile app users during commute-hour congestion; connection migration eliminated mid-request drops when riders' phones switched networks.
5. **SaaS dashboard regression hunt** — after a CDN config change, RUM showed p75 INP spiking only for `http/1.1` users: the change had disabled H2 on one edge region, tripling connection setups for old clients; rollback took minutes instead of weeks.

## Common Mistakes

```text
ANTI-PATTERNS THAT SURVIVED FROM HTTP/1.1

Domain sharding
  BAD:  assets split across cdn{1..4}.example.com
  WHY:  defeats HPACK (per-connection dicts), multiplies handshakes,
        breaks priority ordering. One origin wins on H2/H3.

Excessive inlining/sprites
  BAD:  everything bundled to "save requests"
  WHY:  requests are cheap now; giant bundles delay FCP/LCP.
        Split by actual criticality.

Manual concatenation of cacheable units
  WHY:  cache invalidation granularity matters more than request count.

Server push
  BAD:  pushing every asset unconditionally
  WHY:  wastes bandwidth re-sending cached resources; deprecated.
        Use 103 Early Hints + rel=preload instead.
```

```yaml
# BAD: assuming "we enabled H3" means clients use it
# No Alt-Svc header -> browsers never learn about h3
server:
  listen: 443 ssl http2   # only TCP; UDP 443 blocked/firewalled silently

# GOOD: advertise + verify
server:
  listen: 443 quic reuseport
  add_header: 'Alt-Svc h3=":443"; ma=86400'
# verify in RUM: SELECT count(*) WHERE next_hop_protocol='h3'
```

More traps:

- **Blocking UDP 443**: corporate firewalls drop QUIC silently; H3 adoption plateaus at ~60-70% — always keep H2 fallback healthy.
- **Measuring lab-only**: localhost has zero loss; H3's advantages vanish in lab tests. Judge from field data segmented by network quality.
- **Assuming 0-RTT is free**: 0-RTT early data is replayable — never accept non-idempotent requests in it without anti-replay defenses.
- **Ignoring flow-control windows**: H2 default window sizes throttle high-bandwidth paths; tune `SETTINGS_INITIAL_WINDOW_SIZE` before blaming the protocol.

## Best Practices

1. Serve H2 everywhere; add H3 alongside with `Alt-Svc`; keep both healthy since QUIC is frequently firewalled.
2. Delete H1-era workarounds: domain sharding, aggressive sprites, request-count paranoia.
3. Replace push thinking with `103 Early Hints` and explicit `rel=preload` for genuinely critical resources.
4. Segment RUM/CWV analytics by `nextHopProtocol` and network class before drawing conclusions.
5. Tune H2 flow-control windows on high-throughput APIs; default windows bottleneck fat pipes.
6. Treat 0-RTT as opt-in per endpoint: idempotent GETs yes, mutations protected against replay.
7. Keep certificates and ALPN configuration correct — most "H3 not working" tickets are misconfigured ALPN or UDP 443 blocks.

## Performance Considerations

The wins concentrate where loss and RTT live: expect H3 gains primarily on cellular, satellite, congested WiFi, and intercontinental paths; near-zero delta on clean datacenter-to-desktop routes. Multiplexing removes H1's browser six-connection cap, so latency budget shifts from connection management to server scheduling and content discovery (HTML scan, preload hints). QUIC runs in user space, costing some CPU versus kernel TCP — at CDN scale this matters for cost, not usually for your p75. Header compression differs fundamentally: HPACK (H2) uses dynamic per-connection tables; QPACK (H3) trades slightly larger overhead for independence from packet arrival order — avoid pathological header churn (unique cookies per request) which bloats either compressor.

## Summary

- HTTP/2 solved application-layer HOL with binary framing and multiplexing over one connection; TCP still imposes connection-wide stalls on any packet loss.
- HTTP/3 replaces TCP with QUIC: independent per-stream recovery, 1-RTT/0-RTT handshakes, and connection IDs enabling seamless network migration.
- Server push failed in practice and was removed — `103 Early Hints` plus preload links is the supported pattern.
- Domain sharding went from best practice to anti-pattern; single-origin serving wins under multiplexing.
- Priorities moved from unreliable H2 hints to RFC 9218; resource ordering is mostly your HTML's job now.
- Measure protocol effects in the field: segment Core Web Vitals by `nextHopProtocol`; the biggest H3 dividends appear on lossy mobile networks.

## Cheat Sheet
```text
HTTP/2 & HTTP/3 CHEAT SHEET
============================================================

GENERATIONS:
• H1.1 : text, 6 conns/origin, app-layer HOL, sharding era
• H2   : binary framing, multiplexed streams, HPACK,
         TCP-layer HOL remains, push (now dead)
• H3   : QUIC/UDP, per-stream loss recovery, QPACK,
         0-RTT resume, connection migration, no push

KEY MECHANISMS:
• Streams   : independent request/response lanes
• HPACK/QPACK: header compression (per-connection state)
• ALPN      : negotiates protocol during TLS
• Alt-Svc   : advertises h3 to browsers
• RFC 9218  : modern priority signals (urgency/incremental)

DO:
• Single origin, H2 + H3 dual-listen, Alt-Svc header
• 103 Early Hints + rel=preload for critical assets
• Segment CWV by nextHopProtocol x network type
• Tune H2 initial window size for high-BDP paths

DON'T:
• Shard domains (HPACK/priority/handshake losses)
• Push assets unconditionally (removed in browsers)
• Ship 0-RTT acceptance for unsafe methods
• Trust localhost benchmarks for protocol deltas

WHERE H3 WINS:
• Lossy networks (>1% loss): no cross-stream stalls
• Mobile handoffs: connection survives IP change
• High-RTT: 0-RTT resumption saves full round trips

INTERVIEW FORMULA:
• "H2 fixed app HOL, TCP kept transport HOL"
• "QUIC streams recover independently -> loss isolates"
• "Sharding: H1 hack, H2 anti-pattern"
• "Push is dead; Early Hints won"
```

# HTTP/2 & HTTP/3 Performance Effects

Imagine a page downloading a stylesheet and an image. Bytes for the stylesheet are lost, but image bytes arrive. Whether the image can be delivered immediately depends on where ordering is enforced. That is the central difference between HTTP/2 and HTTP/3.

## Definition

**HTTP/2** is a binary, multiplexed HTTP protocol: numbered request/response streams share a TCP connection. **HTTP/3** carries HTTP over **QUIC**, an encrypted transport using UDP that delivers ordered bytes separately for each stream.

> **Textbook Definition:** HTTP/2 multiplexes framed messages over TCP; HTTP/3 maps HTTP semantics onto QUIC streams. QUIC removes TCP's cross-stream ordered-delivery dependency while retaining shared congestion, connection flow-control and application dependencies.

## First Principles

A connection needs reliable delivery, capacity limits and a way to distinguish simultaneous messages. Putting every message in one ordered transport byte sequence couples their delivery: a gap must be filled before later bytes can be delivered to the application.

Giving messages independent ordered streams removes that particular dependency. They still use the same network path and finite sender/receiver capacity. An application can also create its own dependencies, such as waiting for a stylesheet before rendering an image. Separate transport streams cannot remove that requirement.

## How multiplexing and loss interact

**Multiplexing** interleaves pieces of separate messages over one connection. Each piece carries a stream identifier so the receiver can reconstruct the right message.

| Protocol | How simultaneous messages travel | Ordering boundary |
| -------- | ------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------- |
| HTTP/1.1 | Browsers commonly use multiple connections; a non-pipelined connection handles one active exchange at a time | TCP orders bytes on each connection; pipelined responses also have response-order constraints |
| HTTP/2 | HEADERS and DATA frames from multiple streams interleave | TCP orders all connection bytes before HTTP/2 receives them |
| HTTP/3 | HTTP frames travel on QUIC streams | QUIC orders delivery within each stream |

Browser connection limits are implementation choices, not a universal “six” in the HTTP specification. HTTP/2's **HPACK** and HTTP/3's **QPACK** compress headers using static and potentially dynamic tables. QPACK limits and tracks dependencies on dynamic entries; a header block can still wait for required decoder state.

### Trace a gap with two streams

Suppose A and B are independent responses. A's earlier bytes are missing; later B bytes have reached the receiver. No shared compression or application dependency blocks B in this example.

```text
HTTP/2 over TCP:
  missing connection bytes containing A
       ↓
  later bytes containing B remain behind the TCP delivery gap
       ↓
  recover gap → TCP releases bytes → HTTP/2 reconstructs A and B

HTTP/3 over QUIC:
  A has an ordered-stream gap → A waits for its missing bytes
  B has its required bytes   → B can be delivered independently
```

This is **head-of-line blocking**: earlier missing work prevents later work from progressing. QUIC does not retransmit a lost packet unchanged; needed stream data can be sent in new packets. If a lost packet carried data for both A and B, both may have gaps. Congestion control can also reduce the whole connection's sending rate after loss. There is no fixed one-round-trip duration or packet-loss percentage at which HTTP/3 must outperform HTTP/2.

## Connection setup, resumption and movement

**Round-trip time (RTT)** is the time for a network exchange to reach the peer and return. A typical fresh HTTP/2 connection over TCP and TLS 1.3 has sequential TCP and TLS establishment. QUIC combines transport establishment with TLS negotiation, commonly permitting application data after one round trip. Address validation, version negotiation, certificates and existing connections change the observed cost; these sketches do not predict time to first byte.

**0-RTT** uses a previous connection's state to send early application data on a resumed connection. Zero describes the extra setup wait before sending that data, not a zero-latency response. The server can reject early data. It is replayable, so an application must decide whether repeating the operation is acceptable. A GET endpoint with hidden side effects is not safe merely because it uses GET; non-idempotent effects need explicit replay protection or must wait for the handshake.

QUIC **connection IDs** let a peer associate packets with a connection even when an address changes. A mobile client may probe and validate a new path after switching networks. Migration depends on negotiated behavior, routing and successful validation; it is not a guarantee of an uninterrupted call. Reconnecting application sessions, retrying requests and preventing duplicate effects remain application responsibilities.

## Code Examples

### Observe the protocol without collecting resource URLs

Run this complete JavaScript snippet in a page's console. Call the returned cleanup function after your observation window. It uses an allowlist of coarse protocol labels and never reports full resource names or query strings.

```javascript
function watchProtocols(report) {
  function label(value) {
    return ['h2', 'h3', 'http/1.1'].includes(value) ? value : 'other-or-unavailable';
  }
  const navigation = performance.getEntriesByType('navigation')[0];
  if (navigation) report({ kind: 'navigation', protocol: label(navigation.nextHopProtocol) });
  if (typeof PerformanceObserver === 'undefined' ||
      !(PerformanceObserver.supportedEntryTypes ?? []).includes('resource')) return () => {};
  const observer = new PerformanceObserver(list => {
    for (const resource of list.getEntries()) {
      report({ kind: 'resource', protocol: label(resource.nextHopProtocol) });
    }
  });
  observer.observe({ type: 'resource', buffered: true });
  return () => observer.disconnect();
}
const stopProtocolObservation = watchProtocols(record => console.log(record));
// Later: stopProtocolObservation();
```

`nextHopProtocol` describes the browser's observed fetch hop, not every proxy-to-origin connection. An edge can serve HTTP/3 to the browser and use HTTP/2 upstream. Cached resources and timing access restrictions may leave protocol information unavailable; keep that state rather than relabeling it as HTTP/1.1. A page can fetch resources through several protocols. The navigation protocol is not a label for all its requests.

For production, integrate the approved coarse label into the bounded, sampled pipeline in [RUM](50.3.2.04-real-user-monitoring.md). Console output here is an observation fixture, not an ingestion system or a complete visit metric.

### Configure and verify an HTTP/3 edge

The following is a **server-block excerpt**, not a complete deployment. It assumes an NGINX build supporting the HTTP/3 module, valid TLS configuration and TCP/UDP reachability on port 443.

```nginx
listen 443 quic reuseport;
listen 443 ssl;
http2 on;
ssl_protocols TLSv1.3;
add_header Alt-Svc 'h3=":443"; ma=86400';
```

`Alt-Svc` advertises an alternative service; the client still chooses whether to use it. Other discovery mechanisms exist, including HTTPS DNS records. A listener does not establish successful negotiation. Check build capabilities and configuration, then inspect the negotiated protocol from a capable client. Test with UDP unavailable as well: the TCP fallback must still serve the journey. A failed HTTP/3 attempt can add delay before fallback.

No HTTP/3 edge or lossy-network integration is demonstrated by this excerpt. Validate certificate handling, edge routing, firewall rules, migration and fallback in the intended environment before rollout.

## Real-World Decisions

### Distinguish protocol capability from browser support

HTTP/3 defines server push; Chrome removed HTTP/2 push support. Protocol specification and implementation support are different questions. Use supported resource discovery, preload and, where supported, `103 Early Hints` for critical assets. Early hints can start a fetch before final response headers; incorrect hints can still waste bandwidth.

RFC 9218 defines extensible HTTP priorities usable with HTTP/2 and HTTP/3. Its field uses parameters such as `u=2, i`, not `urgency=2`. Priorities are advisory scheduling signals, not reserved bandwidth or guaranteed completion order. HTML discovery, fetch priorities and server scheduling all influence the result.

### Revisit old loading optimizations with a dependency trace

Domain sharding adds origins and potentially more connection setup. Multiplexing often removes its original benefit, but connection coalescing and deployment constraints affect the result. Compare the actual requests before consolidating origins. Bundling everything into one large file can delay discovery or invalidate otherwise cacheable code; splitting everything can add scheduling and execution overhead. Choose a boundary using the route's critical dependencies, caching and measured costs.

### Measure a rollout without inventing a result

A hypothetical checkout rollout enables HTTP/3 at one edge. First confirm adoption and healthy fallback. Compare the same route/build, region, device, cache state and observation window; report sample counts and unknown-protocol coverage. HTTP/3 users are self-selected by browser and network support, so a raw “h3 versus h2” percentile difference does not establish causation. Use a controlled rollout or account for population differences.

Expect the transport change to matter only where connection setup or delivery stalls contribute to the critical path. If main-thread work dominates the interaction, fix that work instead of assuming a protocol upgrade must lower INP. Do not claim a deployment's percentage improvement without measured evidence.

## Summary

HTTP/2 interleaves HTTP streams over one ordered TCP byte stream. HTTP/3 moves delivery ordering into separate QUIC streams, allowing independent delivery where no other dependency blocks it. Setup, replay, migration, congestion and application work still have costs and conditions. Verify negotiated protocols and measured populations before claiming a performance win.

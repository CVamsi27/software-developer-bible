# HTTP/2 & HTTP/3 Performance Effects

A page downloads a stylesheet and an image. Bytes for the stylesheet are lost, but image bytes arrive. Whether the image can be delivered immediately depends on where ordering is enforced — and that is the central difference between HTTP/2 and HTTP/3.

```javascript
// Which protocol delivered this navigation? Read the observed hop.
const nav = performance.getEntriesByType('navigation')[0];
console.log(nav && nav.nextHopProtocol); // e.g. 'h2', 'h3', or 'http/1.1'
```

## Definition

**HTTP/2** is a binary, multiplexed HTTP protocol: numbered request and response **streams** share a TCP connection. **HTTP/3** carries HTTP over **QUIC**, an encrypted transport using UDP that delivers ordered bytes separately for each stream.

> **Textbook Definition:** HTTP/2 multiplexes framed messages over TCP; HTTP/3 maps HTTP semantics onto QUIC streams. QUIC removes TCP's cross-stream ordered-delivery dependency while retaining shared congestion, connection flow-control and application dependencies.

## First Principles

A connection needs reliable delivery, capacity limits and a way to distinguish simultaneous messages. Putting every message in one ordered transport byte sequence couples their delivery: a gap must be filled before later bytes reach the application. Giving messages independent ordered streams removes that particular dependency — but they still share the network path and finite sender and receiver capacity. An application can also create its own dependencies, such as waiting for a stylesheet before rendering an image, and separate transport streams cannot remove that requirement.

## How It Works

### 1. See How Multiplexing and Loss Interact

**Multiplexing** interleaves pieces of separate messages over one connection. Each piece carries a stream identifier so the receiver can reconstruct the right message.

| Protocol | How simultaneous messages travel | Ordering boundary |
| -------- | ------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------- |
| HTTP/1.1 | Browsers commonly use multiple connections; a non-pipelined connection handles one active exchange at a time | TCP orders bytes on each connection; pipelined responses also have response-order constraints |
| HTTP/2 | HEADERS and DATA frames from multiple streams interleave | TCP orders all connection bytes before HTTP/2 receives them |
| HTTP/3 | HTTP frames travel on QUIC streams | QUIC orders delivery within each stream |

Browser connection limits are implementation choices, not a universal "six" in the HTTP specification. HTTP/2's **HPACK** and HTTP/3's **QPACK** compress headers using static and potentially dynamic tables; QPACK limits and tracks dependencies on dynamic entries, so a header block can still wait for required decoder state.

Suppose A and B are independent responses. A's earlier bytes are missing; B's later bytes have arrived. No shared compression or application dependency blocks B in this example:

```text
HTTP/2 over TCP:
  missing connection bytes containing A
       ↓
  later bytes containing B remain behind the TCP delivery gap
       ↓
  recover gap → TCP releases bytes → HTTP/2 reconstructs A and B

HTTP/3 over QUIC:
  A has an ordered-stream gap → A waits for its missing bytes
  B has its required bytes   → B can be delivered independently
```

This is **head-of-line blocking**: earlier missing work prevents later work from progressing. QUIC does not retransmit a lost packet unchanged — needed stream data can travel in new packets. If one lost packet carried data for both A and B, both may have gaps, and congestion control can reduce the whole connection's sending rate after loss. There is no fixed round-trip count or loss percentage at which HTTP/3 must outperform HTTP/2.

### 2. Trace Connection Setup, Resumption and Movement

**Round-trip time (RTT)** is the time for a network exchange to reach the peer and return. A typical fresh HTTP/2 connection over TCP and TLS 1.3 performs sequential TCP and TLS establishment; QUIC combines transport establishment with TLS negotiation, commonly permitting application data after one round trip. Address validation, version negotiation, certificates and existing connections change the observed cost — these sketches do not predict time to first byte.

**0-RTT** uses a previous connection's state to send early application data on a resumed connection. Zero describes the extra setup wait before sending, not zero-latency response — and the server can reject early data. Early data is replayable, so the application must decide whether repeating the operation is acceptable: a GET endpoint with hidden side effects is not safe merely because it uses GET. QUIC **connection IDs** let a peer associate packets with a connection even when an address changes, so a mobile client may probe and validate a new path after switching networks. Migration depends on negotiated behavior, routing and successful validation — not a guaranteed uninterrupted call.

### 3. Observe the Protocol Without Collecting Resource URLs

Run this complete JavaScript snippet in a page's console. Call the returned cleanup function after your observation window. It uses an allowlist of coarse protocol labels and never reports full resource names or query strings.

```javascript
function watchProtocols(report) {
  function label(value) {
    return ['h2', 'h3', 'http/1.1'].includes(value) ? value : 'other-or-unavailable';
  }
  const navigation = performance.getEntriesByType('navigation')[0];
  if (navigation) report({ kind: 'navigation', protocol: label(navigation.nextHopProtocol) });
  if (typeof PerformanceObserver === 'undefined' ||
      !(PerformanceObserver.supportedEntryTypes ?? []).includes('resource')) return () => {};
  const observer = new PerformanceObserver(list => {
    for (const resource of list.getEntries()) {
      report({ kind: 'resource', protocol: label(resource.nextHopProtocol) });
    }
  });
  observer.observe({ type: 'resource', buffered: true });
  return () => observer.disconnect();
}
const stopProtocolObservation = watchProtocols(record => console.log(record));
// Later: stopProtocolObservation();
```

`nextHopProtocol` describes the browser's observed fetch hop, not every proxy-to-origin connection — an edge can serve HTTP/3 to the browser while using HTTP/2 upstream. Cached resources and timing-access restrictions may leave protocol information unavailable; keep that state rather than relabeling it as HTTP/1.1. For production, integrate the approved coarse label into the bounded, sampled pipeline in [RUM](50.3.2.04-real-user-monitoring.md). Console output here is an observation fixture, not an ingestion system.

### 4. Configure and Verify an HTTP/3 Edge

The following is a **server-block excerpt**, not a complete deployment. It assumes an NGINX build supporting the HTTP/3 module, valid TLS configuration and TCP/UDP reachability on port 443.

```nginx
listen 443 quic reuseport;
listen 443 ssl;
http2 on;
ssl_protocols TLSv1.3;
add_header Alt-Svc 'h3=":443"; ma=86400';
```

`Alt-Svc` advertises an alternative service; the client still chooses whether to use it, and other discovery mechanisms exist, including HTTPS DNS records. A listener does not establish successful negotiation — check build capabilities and configuration, then inspect the negotiated protocol from a capable client. Test with UDP unavailable as well: the TCP fallback must still serve the journey, since a failed HTTP/3 attempt can add delay before fallback. Validate certificate handling, edge routing, firewall rules, migration and fallback in the intended environment before rollout.

### 5. Separate Capability From Support, Then Measure the Rollout

HTTP/3 defines server push; Chrome removed HTTP/2 push support. Protocol specification and implementation support are different questions — use supported resource discovery, preload and, where supported, `103 Early Hints` for critical assets. RFC 9218 defines extensible HTTP priorities usable with HTTP/2 and HTTP/3; its field uses parameters such as `u=2, i`, not `urgency=2`. Priorities are advisory scheduling signals, not reserved bandwidth.

Revisit old loading optimizations with a dependency trace. Domain sharding adds origins and potentially more connection setup; multiplexing often removes its original benefit, but coalescing and deployment constraints affect the result. Bundling everything into one large file can delay discovery or invalidate otherwise cacheable code; splitting everything can add scheduling and execution overhead.

For a rollout, first confirm adoption and healthy fallback, then compare the same route and build, region, device, cache state and observation window — reporting sample counts and unknown-protocol coverage. HTTP/3 users are self-selected by browser and network support, so a raw "h3 versus h2" percentile difference does not establish causation. Expect the transport change to matter only where setup or delivery stalls contribute to the critical path; if main-thread work dominates the interaction, fix that work instead.

## Summary

HTTP/2 interleaves HTTP streams over one ordered TCP byte stream. HTTP/3 moves delivery ordering into separate QUIC streams, allowing independent delivery where no other dependency blocks it. Setup, replay, migration, congestion and application work still carry costs and conditions. Verify negotiated protocols and measured populations before claiming a performance win.

# Performance Budgets

## Definition

A **performance budget** is a quantitative limit on measurements that affect user experience, such as shipped bytes, rendering delays or Core Web Vitals. A team evaluates it under stated conditions and defines what happens when a change exceeds it.

> **Textbook Definition:** A performance budget is an explicit bound on selected resource or user-experience measurements, evaluated under declared conditions and used as an acceptance criterion for changes.

Suppose a route's initial assets are near an agreed limit. Adding a feature creates a decision: reduce another cost, defer the feature's assets, change the design or approve a documented exception. The limit makes that decision visible; it does not establish a universal byte count for every product.

## First Principles

Small changes accumulate across a dependency graph. Individual changes that appear harmless can consume a journey's available capacity together. A useful constraint therefore needs a boundary, a measurement unit and an owner.

Measurements also vary in different ways. Built file bytes are usually deterministic for one artifact and toolchain; browser timings vary with workload and device. A gate must match the measurement: exact artifact checks can use exact limits, while timings need stable conditions, repeated runs and a deliberate noise policy.

## Why Do We Need It?

Budgets catch selected regressions before release and give reviewers evidence for trade-offs. They cannot guarantee a business outcome, prevent every slowdown or replace field monitoring. Their value depends on checking the right journey and enforcing failure.

## How to define a budget contract

| Contract field | Example | Why it matters |
| ------------------- | ------------------------------------------------------------ | ----------------------------------------------------------- |
| Journey | Cold initial dashboard, before opening reports | Separates initial assets from later feature loading |
| Unit | Sum of separately gzip-compressed asset bytes | Prevents comparison with raw or Brotli bytes |
| Bound | Initial total ≤ 200,000 bytes; each selected asset ≤ 120,000 | Aggregate and individual constraints catch different growth |
| Inputs | Explicit artifact manifest from the production build | An unmatched filename cannot silently count as zero |
| Enforcement | Nonzero checker status in a required CI job | Printing a warning alone does not block a merge |
| Owner and exception | Route team; dated exception with measured cost and expiry | A threshold change remains reviewable |

These numbers are illustrative limits, not standards. A chunk is not a route: a route can load an entry, shared dependencies and several other assets. Select the complete loading boundary before comparing its sum.

**KB** conventionally means 1,000 bytes; **KiB** means 1,024. Store thresholds as explicit bytes to avoid ambiguity. Gzip bytes approximate one transfer representation, not HTTP headers, retransmissions or the CPU cost of decoded JavaScript. TCP congestion windows do not create a universal 170 KB JavaScript budget.

## Code Examples

### A complete manifest-based byte gate

Save this as `budget.json`. In a real build, generate the asset list from its manifest and route graph. The following fixture uses explicit names so hashed filename patterns cannot accidentally match nothing.

```json
{
  "initialAssets": ["dist/main.js", "dist/vendor.js"],
  "maxInitialGzipBytes": 200000,
  "maxAssetGzipBytes": 120000
}
```

Save this as `check-budget.mjs` and run it with Node.js after building the files. It measures only the listed initial assets. Lazy routes, CSS, images and third-party assets need their own declared boundaries rather than being assumed covered.

```javascript
import { readFile } from 'node:fs/promises';
import { gzipSync } from 'node:zlib';

try {
  const budget = JSON.parse(await readFile('budget.json', 'utf8'));
  const { initialAssets, maxInitialGzipBytes, maxAssetGzipBytes } = budget;
  if (!Array.isArray(initialAssets) || initialAssets.length === 0 ||
      initialAssets.some(path => typeof path !== 'string' || !path.trim()) ||
      new Set(initialAssets).size !== initialAssets.length ||
      !Number.isSafeInteger(maxInitialGzipBytes) || maxInitialGzipBytes < 0 ||
      !Number.isSafeInteger(maxAssetGzipBytes) || maxAssetGzipBytes < 0) {
    throw new Error('Invalid budget: require unique assets and nonnegative byte limits');
  }
  let total = 0;
  const violations = [];
  for (const path of initialAssets) {
    const contents = await readFile(path); // missing artifact fails the gate
    const bytes = gzipSync(contents, { level: 9 }).byteLength;
    total += bytes;
    console.log(`${path}: ${bytes} gzip bytes`);
    if (bytes > maxAssetGzipBytes) violations.push(`${path} exceeds individual limit`);
  }
  console.log(`Initial total: ${total} / ${maxInitialGzipBytes} gzip bytes`);
  if (total > maxInitialGzipBytes) violations.push('Initial total exceeds limit');
  if (violations.length) {
    console.error(violations.join('\n'));
    process.exitCode = 1;
  }
} catch (error) {
  console.error(error instanceof Error ? error.message : String(error));
  process.exitCode = 1;
}
```

```bash
node check-budget.mjs
```

If the measured files are 80,000 and 90,000 bytes, each passes and their 170,000 total passes. Change them to 110,000 and 110,000: both individual checks pass, but the 220,000 total fails. If one is 130,000 and the other is 10,000, the total passes but the individual limit fails. Equality passes because the contract says ≤. These are hypothetical compressed sizes; use the script's actual output for a real artifact.

The checker fails for a missing file, empty asset list, duplicate asset or invalid limit. Those conditions mean the measurement contract is invalid, not that the product is fast. The manifest is trusted build configuration; it must reflect what the chosen journey really loads.

A required CI step must run the build first and preserve this command's nonzero exit status. Adding `|| true`, marking the job optional or swallowing the failure defeats enforcement. Keep the lockfile and compressor settings stable when comparing commits.

### Combine artifact, laboratory and field contracts

Use the executable [Lighthouse CI fixture](../02-measurement/50.3.2.03-lighthouse-ci.md) for navigation audits. Choose raw metric assertions, repeated runs and an aggregation rule under fixed conditions. A passing category score does not override a failed error-level assertion. Total Blocking Time is a lab diagnostic; it is not field INP.

A field objective might require p75 LCP ≤ 2,500 ms for eligible mobile dashboard visits in a stated window. It needs a sufficient sample, stable collection coverage and explicit treatment of unknown values. This is a population contract rather than a deterministic pull-request artifact check. A passing lab run cannot prove it; a field breach needs diagnosis, not an automatic conclusion that the last bundle change caused it.

## Real-World Decisions

### Set the first limit from a baseline

Measure the current journey on target devices and inspect the bottleneck. Start with a limit the team can explain and enforce, then schedule improvements where the current experience is inadequate. Avoid arbitrary bronze/silver/gold tiers or unsupported promises that a given bundle size guarantees good LCP.

If the route is CPU-bound, reducing decoded code and execution can matter more than compression. If an image is discovered late, improving discovery can help without changing its bytes. The resource budget is a proxy; link it to the relevant phase rather than deriving bytes from a user metric by a fixed formula.

### Review an over-budget feature

An illustrative report widget adds 25,000 initial gzip bytes. It is used rarely, so a team tests deferred loading. Initial bytes improve, but first report-open latency and chunk failure handling must still pass the product's requirements. If deferral is unsuitable, compare simpler dependencies, reduced functionality or an explicit exception.

Record the affected journey, measured costs, chosen mitigation, owner and expiry for an exception. Do not raise a threshold merely to make the check pass. Recheck field behavior after release and retire temporary exceptions when the underlying change lands.

### Cover costs outside the artifact list

Third-party scripts can change without rebuilding the app. Images, fonts, CSS and API-driven rendering can also dominate a journey. Keep separate measurements for these boundaries; a first-party JavaScript gate does not cover them automatically. Review shared assets at route and application levels so one team cannot move costs into an unowned bucket.

## Common Mistakes

- Labeling a sum over a glob as the “largest single chunk.”
- Measuring one main file while ignoring shared assets loaded by the same route.
- Counting missing inputs as zero or declaring success with no collected samples.
- Mixing raw, gzip and Brotli bytes or treating transfer bytes as execution cost.
- Calling universal byte/request-count tiers industry standards.
- Treating a warning, optional CI job or successful build as proof that budget enforcement works.
- Relaxing limits without explaining the cost, owner and user impact.

## Best Practices

Choose a small set of actionable budgets. Preserve baseline and new measurements in the same units. Prove a deliberate violation fails the gate, then restore the legitimate input. Review ownership and exceptions when usage or architecture changes. Include the failure and recovery path in code-splitting decisions, and use field observations to test whether the proxy remains useful.

## Summary

A budget needs a journey, units, valid inputs, bounds and an enforced decision. Individual assets, initial route totals, laboratory timings and field populations answer different questions. Keep those boundaries explicit, fail honestly when inputs are absent and review threshold changes with measured user impact.

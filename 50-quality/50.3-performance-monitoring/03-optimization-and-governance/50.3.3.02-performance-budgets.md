# Performance Budgets

A route's initial assets sit near the agreed limit. A new feature forces a decision: reduce another cost, defer its assets, change the design, or approve a measured exception. The limit makes that trade-off visible — it is not a universal byte target.

```bash
node check-budget.mjs  # nonzero exit when any bound or input contract fails
```

## Definition

A **performance budget** is a quantitative limit on measurements that affect user experience, such as shipped bytes, rendering delays or Core Web Vitals. A team evaluates it under stated **conditions** and defines what happens when a change exceeds it.

> **Textbook Definition:** A performance budget is an explicit bound on selected resource or user-experience measurements, evaluated under declared conditions and used as an acceptance criterion for changes.

## First Principles

Small changes accumulate across a dependency graph: individually harmless changes can consume a journey's available capacity together. A useful constraint therefore needs a boundary, a measurement unit and an owner. Measurements also vary differently — built file bytes are usually deterministic for one artifact and toolchain, while browser timings vary with workload and device. A gate must match the measurement: exact artifact checks can use exact limits, while timings need stable conditions, repeated runs and a deliberate noise policy.

## How It Works

### 1. Define the Budget Contract

| Contract field | Example | Why it matters |
| ------------------- | ------------------------------------------------------------ | ----------------------------------------------------------- |
| Journey | Cold initial dashboard, before opening reports | Separates initial assets from later feature loading |
| Unit | Sum of separately gzip-compressed asset bytes | Prevents comparison with raw or Brotli bytes |
| Bound | Initial total ≤ 200,000 bytes; each selected asset ≤ 120,000 | Aggregate and individual constraints catch different growth |
| Inputs | Explicit artifact manifest from the production build | An unmatched filename cannot silently count as zero |
| Enforcement | Nonzero checker status in a required CI job | Printing a warning alone does not block a merge |
| Owner and exception | Route team; dated exception with measured cost and expiry | A threshold change remains reviewable |

These numbers are illustrative limits, not standards. A chunk is not a route: a route can load an entry, shared dependencies and several other assets, so select the complete loading boundary before comparing its sum. **KB** conventionally means 1,000 bytes; **KiB** means 1,024 — store thresholds as explicit bytes to avoid ambiguity. TCP congestion windows do not create a universal 170 KB JavaScript budget.

### 2. Enforce Bytes With a Manifest-Based Gate

Save this as `budget.json`. In a real build, generate the asset list from its manifest and route graph. The fixture uses explicit names so hashed filename patterns cannot accidentally match nothing.

```json
{
  "initialAssets": ["dist/main.js", "dist/vendor.js"],
  "maxInitialGzipBytes": 200000,
  "maxAssetGzipBytes": 120000
}
```

Save this as `check-budget.mjs` and run it with Node.js after building the files. It measures only the listed initial assets — lazy routes, CSS, images and third-party assets need their own declared boundaries rather than being assumed covered.

```javascript
import { readFile } from 'node:fs/promises';
import { gzipSync } from 'node:zlib';

try {
  const budget = JSON.parse(await readFile('budget.json', 'utf8'));
  const { initialAssets, maxInitialGzipBytes, maxAssetGzipBytes } = budget;
  if (!Array.isArray(initialAssets) || initialAssets.length === 0 ||
      initialAssets.some(path => typeof path !== 'string' || !path.trim()) ||
      new Set(initialAssets).size !== initialAssets.length ||
      !Number.isSafeInteger(maxInitialGzipBytes) || maxInitialGzipBytes < 0 ||
      !Number.isSafeInteger(maxAssetGzipBytes) || maxAssetGzipBytes < 0) {
    throw new Error('Invalid budget: require unique assets and nonnegative byte limits');
  }
  let total = 0;
  const violations = [];
  for (const path of initialAssets) {
    const contents = await readFile(path); // missing artifact fails the gate
    const bytes = gzipSync(contents, { level: 9 }).byteLength;
    total += bytes;
    console.log(`${path}: ${bytes} gzip bytes`);
    if (bytes > maxAssetGzipBytes) violations.push(`${path} exceeds individual limit`);
  }
  console.log(`Initial total: ${total} / ${maxInitialGzipBytes} gzip bytes`);
  if (total > maxInitialGzipBytes) violations.push('Initial total exceeds limit');
  if (violations.length) {
    console.error(violations.join('\n'));
    process.exitCode = 1;
  }
} catch (error) {
  console.error(error instanceof Error ? error.message : String(error));
  process.exitCode = 1;
}
```

```bash
node check-budget.mjs
```

If the files measure 80,000 and 90,000 bytes, each passes and their 170,000 total passes. At 110,000 and 110,000, both individual checks pass but the 220,000 total fails. At 130,000 and 10,000, the total passes but the individual limit fails. Equality passes because the contract says ≤. The checker also fails for a missing file, empty asset list, duplicate asset or invalid limit — those mean the measurement contract is invalid, not that the product is fast. A required CI step must run the build first and preserve this command's nonzero exit status: adding `|| true`, marking the job optional or swallowing the failure defeats enforcement.

### 3. Combine Artifact, Laboratory and Field Contracts

Use the executable [Lighthouse CI fixture](../02-measurement/50.3.2.03-lighthouse-ci.md) for navigation audits: raw metric assertions, repeated runs and an aggregation rule under fixed conditions. A passing category score does not override a failed error-level assertion, and Total Blocking Time is a lab diagnostic rather than field INP.

A field objective might require p75 LCP ≤ 2,500 ms for eligible mobile dashboard visits in a stated window — with sufficient sample, stable collection coverage and explicit treatment of unknown values. That is a population contract, not a deterministic pull-request check: a passing lab run cannot prove it, and a field breach needs diagnosis rather than an automatic conclusion that the last bundle change caused it.

### 4. Set the First Limit From a Baseline

Measure the current journey on target devices and inspect the bottleneck. Start with a limit the team can explain and enforce, then schedule improvements where the current experience is inadequate. Avoid arbitrary bronze, silver and gold tiers, or promises that a given bundle size guarantees good LCP. If the route is CPU-bound, reducing decoded code and execution can matter more than compression; if an image is discovered late, improving discovery helps without changing its bytes. The resource budget is a proxy — link it to the relevant phase rather than deriving bytes from a user metric by a fixed formula.

### 5. Review an Over-Budget Feature

An illustrative report widget adds 25,000 initial gzip bytes. It is used rarely, so a team tests deferred loading: initial bytes improve, but first report-open latency and chunk failure handling must still pass the product's requirements. If deferral is unsuitable, compare simpler dependencies, reduced functionality or an explicit exception. Record the affected journey, measured costs, chosen mitigation, owner and expiry. Never raise a threshold merely to make the check pass. Recheck field behavior after release, and retire temporary exceptions when the underlying change lands.

### 6. Cover Costs Outside the Artifact List

Third-party scripts can change without rebuilding the app. Images, fonts, CSS and API-driven rendering can also dominate a journey — keep separate measurements for these boundaries, since a first-party JavaScript gate does not cover them automatically. Review shared assets at route and application levels so one team cannot move costs into an unowned bucket.

## Summary

A budget needs a journey, units, valid inputs, bounds and an enforced decision. Individual assets, initial route totals, laboratory timings and field populations answer different questions. Keep those boundaries explicit, fail honestly when inputs are absent, and review threshold changes against measured user impact.

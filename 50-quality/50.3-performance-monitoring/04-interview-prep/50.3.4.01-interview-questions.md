# Performance Monitoring Interview Questions

## Definition

This bank connects measurement, diagnosis and performance governance under interview constraints. Answer before reading; use the source chapters for executable examples rather than memorizing a second implementation here.

## First Principles

A measured delay has a workload, observation boundary and population. Different tools expose different parts of that delay. A useful answer defines those conditions, traces a cause and states what evidence would change the decision.

## How to practice

Give a direct answer, explain one mechanism and justify a decision. Then answer the changed-condition probe. Use actual career evidence when discussing your experience; the hypothetical cases below are practice, not claims about your work.

## Interview Questions

### Fundamentals

**Q1: What are Core Web Vitals?**

**Answer:** They describe loading (Largest Contentful Paint, LCP), responsiveness (Interaction to Next Paint, INP) and visual stability (Cumulative Layout Shift, CLS). Each has its own observation rules. Evaluate eligible visits at p75 rather than averaging all three into a score.

**Changed condition:** A page has no eligible interaction.

**Reasoning:** INP is unobserved, not zero; report coverage rather than inventing a fast interaction.

**Q2: What does LCP measure and what is a good score?**

**Answer:** LCP records the render time of the largest eligible content element observed during the loading measurement window. Good is ≤ 2,500 ms; needs improvement is > 2,500 to ≤ 4,000 ms; poor is > 4,000 ms. It does not certify that every page element has finished loading.

**Changed condition:** An LCP element arrives early but stays hidden.

**Reasoning:** Rendering delay can dominate; reducing its transfer bytes alone may not help.

**Q3: What is the difference between FID and INP?**

**Answer:** First Input Delay measured only the delay before processing the first eligible interaction. INP includes input delay, processing and presentation delay for eligible interactions over the visit, with a selection rule that allows outliers on highly interactive pages. It replaced FID as a Core Web Vital in 2024.

**Changed condition:** The handler is short but presentation is late.

**Reasoning:** A short handler does not imply good INP; inspect the delay until the next paint.

**Q4: How do you measure Core Web Vitals?**

**Answer:** Choose the boundary: field collectors and CrUX describe observed user populations; DevTools can investigate a local journey; Lighthouse provides controlled navigation diagnostics. A routine Lighthouse run does not measure the population's field INP.

**Changed condition:** Lighthouse passes while field INP is poor.

**Reasoning:** Reproduce the affected interaction and device population, not only the initial navigation.

**Q5: What is CLS and how is it calculated?**

**Answer:** A qualifying layout-shift entry scores impact fraction × distance fraction. CLS is the largest qualifying session-window sum: shifts less than one second apart, within a maximum five-second window. Exclusions such as recent qualifying input matter; CLS is not a lifetime sum of every movement.

**Changed condition:** Two shift clusters are far apart.

**Reasoning:** Their scores belong to separate windows; use the largest window rather than summing both.

### Measurement and implementation

**Q6: How do you track Core Web Vitals in production?**

**Answer:** Use supported collectors and a bounded reporting contract. Store metric value snapshots with visit/metric identity and update ordering; delta is a change since the previous report, not an interchangeable final value. Sample visits uniformly for ordinary percentiles, minimize identifiers and track delivery coverage.

**Changed condition:** Two snapshots arrive out of order.

**Reasoning:** The receiver keeps the latest update for one identity instead of counting a second visit or overwriting it with an older snapshot.

**Q7: What is the difference between lab and field metrics?**

**Answer:** Lab measurements control one workload and environment. Field measurements sample real visits under varied conditions. Neither is automatically complete: a lab may omit route states, and field coverage depends on browser support, consent, sampling and delivery.

**Changed condition:** The new release attracts more low-end devices.

**Reasoning:** The global percentile can worsen without a code regression; compare comparable segments and coverage.

**Q8: How do you set up performance budgets?**

**Answer:** Specify journey, units, valid inputs, bounds, owner and failure policy. Check artifact bytes after a real build; use repeated controlled lab runs for timings and a separate population objective for field metrics. Prove a deliberate violation produces a required CI failure.

**Changed condition:** The artifact glob matches no files.

**Reasoning:** Fail the measurement contract; zero matched bytes is absent evidence.

**Q9: What causes layout shifts and how do you prevent them?**

**Answer:** Reserve geometry for images, embeds and dynamic content; coordinate font metrics and loading so replacement does not move content unnecessarily. Trace the actual moving elements and their initiating work. Preloading every font can compete with critical assets.

**Changed condition:** A skeleton has different dimensions from its final content.

**Reasoning:** Space was reserved incorrectly; match the resulting layout rather than merely adding a skeleton.

**Q10: How do you measure performance of a Single Page Application?**

**Answer:** Define soft-navigation boundaries explicitly: route intent, data availability and visible/interactive completion. Use owned marks and measures, browser interaction traces and appropriate field collectors. Whole-document navigation metrics do not automatically reset for every client-side route.

**Changed condition:** Two route transitions overlap and one is cancelled.

**Reasoning:** Use separate identities and cancellation semantics; do not let the first transition finish the second's measure.

### Senior diagnosis and ownership

**Q11: Explain the Navigation Timing API and its key metrics.**

**Answer:** Use PerformanceNavigationTiming entries. Their timestamps are relative to the performance time origin; startTime is normally zero for navigation. Inspect DNS, connection, responseStart, DOMContentLoaded event boundaries and loadEventEnd. Reused connections/cache can make some phases zero; load completion is not “all future work complete.”

**Changed condition:** The measurement runs before loadEventEnd is populated.

**Reasoning:** Treat the unfinished value as unavailable until the boundary occurs; do not report a zero-duration completed load.

**Q12: How do you handle performance monitoring in a micro-frontend architecture?**

**Answer:** Define shell versus module ownership and one page-level metric identity. Modules can report bounded operation measurements; the shell correlates the journey without summing nested durations or separate p75 values. For cross-origin messages, validate origin, source and payload.

**Changed condition:** The shell and two modules each report the same page LCP.

**Reasoning:** Deduplicate the page observation; module attribution is additional context, not three independent visits.

**Q13: What is the relationship between TTFB and LCP?**

**Answer:** For a navigation, responseStart is an important milestone before the observed main-document LCP. Diagnose the path: response wait, resource discovery, transfer and rendering. DNS/TCP/TLS may be reused; server work is only one contribution. Optimize the dominant subpart instead of assuming the server must be the bottleneck.

**Changed condition:** TTFB is low while LCP is high.

**Reasoning:** Inspect late discovery, image transfer and render delay before changing server capacity.

**Q14: How do you optimize LCP for a content-heavy website?**

**Answer:** Identify the actual LCP element and decompose the delay. Make it discoverable, fetch appropriate responsive bytes and reduce blockers on its rendering path. Choose SSR, caching or preload only if it addresses the observed dependency; a guessed preload can waste bandwidth.

**Changed condition:** The supposed hero is not the measured LCP element.

**Reasoning:** Optimize the observed element and verify the candidate across target viewports and page states.

**Q15: Explain how you would design a Real User Monitoring (RUM) system.**

**Answer:** Design collection eligibility, uniform sampling, bounded payloads, visit/metric identity and ordering first. Choose transport and receiver validation, capacity and durability next. Aggregate defined populations with coverage and retention policies, then add dashboards and alerts. A queued beacon is not a storage acknowledgment.

**Changed condition:** The receiver is unavailable.

**Reasoning:** Apply the declared bounded retry/drop policy and expose lost coverage; unlimited localStorage buffering adds blocking and retention risks.

**Q16: How do you handle third-party script impact on performance?**

**Answer:** Identify request, execution and rendering costs for each third party. Defer work that the journey does not need, respect consent and evaluate removal. async permits execution when fetched; defer coordinates execution after parsing. Moving computation to a worker helps only when the code can operate without direct DOM ownership.

**Changed condition:** A deferred script still runs during the first interaction.

**Reasoning:** Deferral changed timing, not total execution; measure whether the new scheduling helps the actual journey.

**Q17: What is the difference between FCP and LCP?**

**Answer:** First Contentful Paint marks the first eligible content paint; LCP concerns the largest eligible content candidate during its measurement window. Early feedback and major content arrival are different observations. Neither means all resources or interactions are ready.

**Changed condition:** A small logo paints early but the article is delayed.

**Reasoning:** FCP can be good while LCP remains poor; trace the article's critical dependency.

**Q18: How do you detect and fix memory leaks?**

**Answer:** Compare heap snapshots at the same idle state after repeated use/cleanup cycles and inspect retaining paths. A global listener, subscription or cache can keep obsolete objects reachable. Remove the suspected ownership path and reproduce; rising memory alone does not prove a leak.

**Changed condition:** The retained object is referenced by the debugging console.

**Reasoning:** Eliminate debugger-induced retention before attributing it to the application.

**Q19: Explain the impact of web fonts on performance.**

**Answer:** Font loading can delay text or move it when a fallback is replaced. Choose font-display behavior, a compatible fallback, subsetting and selective preload under the actual content/layout requirements. swap can expose layout shifts; variable fonts do not always reduce transferred bytes.

**Changed condition:** The fallback and final font have different line breaks.

**Reasoning:** Use appropriate metric matching or layout policy and verify shifts; faster text appearance alone is insufficient.

**Q20: How do you optimize performance for global audiences?**

**Answer:** Segment by relevant region, device and network; inspect edge-to-origin dependencies, cache behavior and critical resources. Regional deployments and CDNs help selected network/server costs but add data, consistency and operational constraints. Network hints are optional and incomplete.

**Changed condition:** The connection-speed hint is absent.

**Reasoning:** Keep a useful default experience and rely on measured populations rather than making functionality depend on the hint.

### Scale and systems judgment

**Q21: Design a performance monitoring system that handles 1 billion events per day.**

**Answer:** One billion events/day averages about 11,574 events/s. Declare a burst factor, payload size, sampling and retention before choosing capacity. At 1,000 payload bytes/event, raw payload is about 1 TB/day before overhead. Use bounded ingestion, durable queues where required, partitioning, deduplication, backpressure and aggregations supporting the selected queries.

**Changed condition:** Traffic bursts to five times the average.

**Reasoning:** Plan for about 57,870 events/s plus overhead, or define bounded degradation. The average alone does not size the system.

**Q22: How would you detect performance regressions automatically?**

**Answer:** Use deterministic artifact checks and controlled repeated lab gates before release; compare relevant field distributions and coverage during rollout. Define minimum sample size, effect threshold and false-alert policy. Canary rollback must have an attributable signal and a tested recovery path; ML is optional.

**Changed condition:** Only a low-volume route moves at p99.

**Reasoning:** Check sample sufficiency and measurement noise before declaring a regression or rolling back.

**Q23: Explain the performance waterfall and how to optimize it.**

**Answer:** A waterfall shows requests over time and their dependencies; it is not one universal sequence ending with LCP after load. Connections may be reused, requests overlap and rendering depends on discovery and execution. Find the critical path, then test one bottleneck.

**Changed condition:** The load event occurs before an asynchronously inserted LCP candidate.

**Reasoning:** Load and the content paint are different boundaries; inspect the candidate's actual discovery and rendering path.

**Q24: How do you handle performance measurement in Server-Side Rendering?**

**Answer:** Separate server processing, network wait, browser paint and hydration/interaction boundaries. Correlate permitted request or trace identifiers and expose selected Server-Timing data where appropriate. Do not add clock timestamps from different machines without a defined model; SSR markup can paint before hydration completes.

**Changed condition:** Hydration is slow after an early content paint.

**Reasoning:** Diagnose interaction readiness and main-thread work; the early paint did not prove responsiveness.

**Q25: Design a system to track performance across micro-frontends.**

**Answer:** Use a shell-owned journey and page identity, module-owned operation spans and explicit attribution rules. Validate cross-origin reports and correlate backend traces where needed. Do not sum module percentiles, label nested durations independent or turn every module report into another visit.

**Changed condition:** A shared dependency appears in several modules.

**Reasoning:** Assign the real loaded/consumed resource once at the journey boundary and retain module context without double counting.

### Operational follow-ups

**Q26: How do you handle performance in a Progressive Web App?**

**Answer:** Measure cold load, warm cache, offline use and worker-update journeys separately. A service worker can improve repeat/offline access but introduces stale-data, update and cache-storage policies. Background sync and push are optional capabilities, not automatic performance improvements.

**Changed condition:** An old worker serves a cached shell referencing removed chunks.

**Reasoning:** Deployment compatibility and retention/recovery matter; a cache hit does not establish a usable journey.

**Q27: What is the impact of HTTP/2 on performance?**

**Answer:** HTTP/2 interleaves framed streams over one TCP connection and compresses headers. TCP still withholds later bytes behind a delivery gap; HTTP/3 moves ordering into QUIC streams while retaining shared congestion and other dependencies. Do not assume browser server-push support or a universal speedup.

**Changed condition:** One QUIC packet contains missing bytes for two streams.

**Reasoning:** Both can have gaps; per-stream ordering does not mean each lost packet affects only one stream.

**Q28: How do you profile performance in development vs production?**

**Answer:** Development traces locate causes but include development-specific work. Use a production-like build and representative devices/data for comparisons; use an explicit React profiling build if needed. Lighthouse, DevTools and RUM answer lab, attribution and field questions rather than belonging exclusively to development or production.

**Changed condition:** React Profiler callbacks disappear in a normal production build.

**Reasoning:** Profiling is disabled by default there; explicitly configure a profiling build and account for its overhead.

**Q29: Explain the relationship between performance and SEO.**

**Answer:** Core Web Vitals align with page-experience considerations in Google Search. Good metrics do not guarantee rankings; relevance and other signals still matter. Improve measured user experience and avoid claiming a fixed ranking or revenue change from milliseconds alone.

**Changed condition:** Metrics improve while rankings remain unchanged.

**Reasoning:** That is compatible with multiple ranking signals and competitive changes; it does not invalidate the measured UX improvement.

**Q30: How do you handle performance monitoring during incidents?**

**Answer:** Use the incident's affected journey/population, establish timing and correlate browser/network/backend evidence with recent changes. Bound diagnostic collection, redact identifiers and track coverage gaps. Choose mitigation from the suspected causal path and verify recovery before closing.

**Changed condition:** Telemetry stops during the incident.

**Reasoning:** Treat the missing coverage as an incident constraint, not a sudden performance improvement; seek independent health evidence.

## Summary

Define the measurement before choosing a tool. Trace the critical dependency, compare equivalent workloads/populations and state what the evidence cannot prove. Strong answers preserve identity, correctness, coverage and recovery when a condition changes.

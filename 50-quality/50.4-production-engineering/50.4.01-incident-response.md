# Incident Response — Triage, Communication, Postmortems

## Definition

**Incident response** is the defined process a team follows from *symptom* to *resolution* to *learning*, whose purpose is to shorten time-to-mitigation under stress by removing the need to decide who does what while the system is burning.

```text
detect ─▶ triage (severity) ─▶ declare ─▶ mitigate ─▶ resolve ─▶ postmortem
   │         SEV1/2/3             incident    stop the     root      actions with
   ▼                              channel     bleeding     cause     owners+dates
roles: Incident Commander (decides) · Ops lead (executes) · Comms lead (updates)
```

Three properties define a functioning process:

1. **Separation of roles, starting with the commander** — the reason a defined process exists is that the person debugging cannot simultaneously coordinate, decide, and communicate. An incident without a named commander degrades into several people investigating the same thing while nobody updates stakeholders.
2. **Mitigate before you diagnose** — the objective function is *time to mitigation* (roll back, fail over, disable the flag, shed load), not root cause. Confusing the two is the most expensive habit in incident work: a 40-minute root-cause hunt while the site is down is strictly worse than a 2-minute rollback followed by a calm postmortem.
3. **Severity is declared from impact, and it drives the process** — SEV definitions (customer impact, data loss risk, blast radius) decide who is paged, how often stakeholders are updated, and whether an exec is informed; declaring low to avoid attention is a documented anti-pattern.

The process closes with a **blameless postmortem** whose output is *owned, dated actions*, not prose: an incident that produces a document but no change to alerting, tests, or architecture will recur, which is the measure by which the practice is judged.

## First Principles

Incident response exists because outages are inevitable; *unmanaged* outages are not:

1. **Separate the three roles**: commander (coordinates, doesn't fix), comms (stakeholders/status page), investigators (fix) — the role split exists because context-switching between fixing and narrating degrades both (→ 50.4.05's responder load).
2. **Blameless postmortems are the learning engine**: the question is "why did the *system* allow this," not "who" — blame converts incidents into hidden information (people stop reporting near-misses) (→ 40.4.3.02's actionable-alerts culture).

## Incident Severity Levels

| Severity | Response Time | Examples |
| ------------------- | ----------------- | ------------------------------------------------ |
| **SEV1 (Critical)** | < 15 min | Data loss, security breach, complete outage |
| **SEV2 (High)** | < 1 hour | Major feature down, performance degradation >50% |
| **SEV3 (Medium)** | < 4 hours | Minor feature affected, workaround exists |
| **SEV4 (Low)** | Next business day | Cosmetic issues, non-urgent improvements |

## Incident Response Workflow

### 1. Detection & Alerting
```typescript
// Alert hierarchy
interface Alert {
  severity: 'SEV1' | 'SEV2' | 'SEV3' | 'SEV4';
  source: 'monitoring' | 'user-report' | 'synthetic';
  metric: string;
  threshold: number;
  current: number;
  timestamp: Date;
}

// Alert rules (Prometheus-style)
const alertRules = {
  highErrorRate: {
    condition: 'rate(http_requests_total{status=~"5.."}[5m]) / rate(http_requests_total[5m]) > 0.05',
    severity: 'SEV1',
    for: '5m'
  },
  highLatency: {
    condition: 'histogram_quantile(0.99, rate(http_request_duration_seconds_bucket[5m])) > 2',
    severity: 'SEV2',
    for: '10m'
  },
  diskSpace: {
    condition: 'node_filesystem_avail_bytes / node_filesystem_size_bytes < 0.1',
    severity: 'SEV3',
    for: '15m'
  }
};
```

### 2. Triage (First 15 Minutes)
```markdown
## Triage Checklist
- [ ] Acknowledge alert
- [ ] Check if user-facing impact
- [ ] Identify affected services
- [ ] Check recent deployments (last 30 min)
- [ ] Check dependency health (DB, Redis, external APIs)
- [ ] Determine if rollback is needed
- [ ] Assign incident commander
- [ ] Open incident channel
```

### 3. Investigation
```typescript
// Quick diagnostic commands
const diagnostics = {
  // Check service health
  health: 'curl -s https://api.docita.work/health | jq',

  // Check recent errors
  errors: 'kubectl logs -l app=api --since=30m --tail=100 | grep -i error',

  // Check database connections
  dbConnections: 'SELECT count(*) FROM pg_stat_activity WHERE state = \'active\';',

  // Check memory/CPU
  resources: 'kubectl top pods -l app=api',

  // Check recent deployments
  deployments: 'kubectl rollout history deployment/api'
};
```

### 4. Communication Templates
```markdown
## Status Update Template
**Incident:** [Brief description]
**Status:** Investigating / Identified / Monitoring / Resolved
**Impact:** [Who is affected, what features]
**Workaround:** [If available]
**Next update:** [Time]

## Example:
**Incident:** Elevated error rates on appointment booking API
**Status:** Investigating
**Impact:** ~30% of booking requests failing with 500 errors
**Workaround:** None currently
**Next update:** 15 minutes
```

## Chaos Engineering

### Principles
1. **Build confidence** in system's ability to handle failures
2. **Uncover weaknesses** before they cause outages
3. **Automate** failure injection in staging/production

### Common Experiments
```typescript
// Network latency injection
const chaosExperiments = {
  networkLatency: {
    target: 'postgres-primary',
    latency: '100ms',
    duration: '5m'
  },

  podKill: {
    target: 'deployment/api',
    mode: 'random',
    interval: '10m'
  },

  diskFill: {
    target: 'node-1',
    fillRate: '100MB/s',
    duration: '15m'
  },

  dnsFailure: {
    target: 'service redis',
    duration: '2m'
  }
};
```

### Game Day Checklist
```markdown
## Pre-Game Day
- [ ] Define hypothesis
- [ ] Identify blast radius
- [ ] Set up monitoring dashboards
- [ ] Notify stakeholders
- [ ] Prepare rollback plan

## During Experiment
- [ ] Inject failure
- [ ] Monitor system behavior
- [ ] Document observations
- [ ] Verify alerts fire correctly
- [ ] Test incident response process

## Post-Experiment
- [ ] Stop failure injection
- [ ] Verify system recovery
- [ ] Review monitoring/alerting gaps
- [ ] Update runbooks
- [ ] Schedule follow-up actions
```

## Runbook Example

````markdown
# Runbook: High Database Connection Usage

## Alert
PostgreSQL connection count > 80% of max_connections

## Symptoms
- Slow queries
- Connection timeouts
- Application logs: "FATAL: too many connections"

## Investigation
1. Check current connections:
   ```sql
   SELECT count(*) FROM pg_stat_activity;
   SELECT state, count(*) FROM pg_stat_activity GROUP BY state;
   ```

2. Check for connection leaks:
   ```sql
   SELECT pid, state, query, query_start 
   FROM pg_stat_activity 
   WHERE state != 'idle' 
   ORDER BY query_start;
   ```

## Remediation
1. Kill idle connections older than 10 minutes:
   ```sql
   SELECT pg_terminate_backend(pid) 
   FROM pg_stat_activity 
   WHERE state = 'idle' 
   AND query_start < now() - interval '10 minutes';
   ```

2. If persistent, restart application pods:
   ```bash
   kubectl rollout restart deployment/api
   ```

## Prevention
- Implement connection pooling (PgBouncer)
- Add connection count monitoring
- Set statement_timeout
````

## Interview Tips
- Explain incident response lifecycle (detect → triage → mitigate → remediate)
- Know postmortem blameless culture and action items
- Discuss chaos engineering principles and experiments
- Explain runbooks and their importance in incident response- Know how to communicate during incidents (status updates, stakeholder management)

## Summary

1. **The lifecycle is detect → triage → mitigate → remediate** — mitigation first, root cause later; stopping the bleeding outranks understanding it
2. **Blameless postmortems are how learning survives** — the question is "what allowed this," never "who did this"; action items get owners and dates
3. **Runbooks turn panic into procedure** — the mitigation you'll run at 3am must be written before 3am
4. **Incident communication is a role, not a side task** — an incident commander and a stakeholder-update cadence keep responders responding
5. **Every incident narrows the next one** — alerts that fired, alerts that didn't, and the runbook gaps all feed back into the detection layer

# SLIs, SLOs, and Error Budgets

## Definition

An **SLI** (service-level indicator) measures a user-relevant outcome. An **SLO** (service-level objective) sets its target over a defined window. An **SLA** (service-level agreement) is an external contract with specified consequences. An **error budget** is the amount of bad behavior the SLO permits.

For an appointment API, “the server is up” is weaker than “eligible booking requests succeed.” A healthy process can still reject every booking because its database is unavailable. Start from the user operation and its measurement contract.

> **Textbook Definition:** According to Google Site Reliability Engineering (Beyer et al., *Site Reliability Engineering: How Google Runs Production Systems*), a *Service Level Indicator (SLI)* is a carefully defined quantitative measure of some aspect of the level of service provided ($\text{good events} / \text{valid events}$). A *Service Level Objective (SLO)* is a target value or range of values measured by an SLI over a bounded temporal window (e.g., $99.9\%$ over 30 rolling days). An *Error Budget* is the mathematical fraction of unreliability ($1 - \text{SLO}$) available for deployments and controlled risk.

## First Principles

Perfect reliability has a cost, and users do not experience all failures equally. A target must say which events count, which outcomes are good and over what period. Only then can the allowed failure amount be calculated.

A measurement does not decide whether to halt a release. That is a separate policy agreed by engineering and product before an incident.

## Define the measurement before its target

| Contract field | Illustrative booking API choice |
| ---------------- | ---------------------------------------------------------------- |
| Population | Eligible booking requests observed at the API boundary |
| Good outcome | Documented successful response and required correctness checks |
| Bad outcome | Service failures/timeouts within the stated observation boundary |
| Window | Rolling 30 days |
| Objective | At least 99.9% good events |
| Missing coverage | Unavailable/incomplete, not healthy |

Decide explicitly how expected validation errors, authentication errors, dependency timeouts, cancellations and retries are counted. “Every status below 500 is good” may be an availability approximation, but can hide broken business behavior. Server counters also miss requests that never reach the server; combine boundary telemetry or user probes where the objective requires them.

A latency SLI might count eligible requests completed within 200 ms. A p95 latency value is a percentile observation, not that good-event fraction. Define whether a fast failed request is good for latency, and whether the reliability target combines success and speed.

## Trace a request-based budget

For 100,000 eligible requests and a 99.9% objective:

```text
allowed bad requests = 100,000 × (1 − 0.999) = 100
observed bad requests = 40
remaining allowance = 60 requests = 60% of this observed-population budget
```

This is not “43 minutes of downtime.” Request traffic varies. An **elapsed-time availability** contract at 99.9% over exactly 30 days permits 43.2 minutes; that is a different numerator and denominator. Keep a financial ledger or worker freshness target tied to its own user expectations instead of assigning an arbitrary number of nines by workload name.

The budget below is computed for the **observed population in the chosen window**, not a guaranteed future allocation. Rolling-window failures eventually age out; changing traffic volume changes the request allowance.

```typescript
export interface ErrorBudgetReport {
  allowedBadRequests: number;
  observedBadRequests: number;
  budgetRemainingPercentage: number;
  isBudgetExhausted: boolean;
}

export function calculateErrorBudget(
  sloPercent: number,
  failedRequests: number,
  totalRequests: number
): ErrorBudgetReport | null {
  if (!Number.isFinite(sloPercent) || sloPercent <= 0 || sloPercent >= 100 ||
      !Number.isSafeInteger(totalRequests) || totalRequests < 0 ||
      !Number.isSafeInteger(failedRequests) || failedRequests < 0 ||
      failedRequests > totalRequests) throw new RangeError('Invalid SLO or request counts');
  if (totalRequests === 0) return null; // No observed population, not a healthy zero.
  const allowedBadRequests = totalRequests * (1 - sloPercent / 100);
  // Tolerate floating-point rounding at the exact budget boundary.
  const tolerance = Math.max(1, allowedBadRequests) * Number.EPSILON * 8;
  const isBudgetExhausted = failedRequests + tolerance >= allowedBadRequests;
  const budgetRemainingPercentage = isBudgetExhausted ? 0 :
    Math.max(0, (1 - failedRequests / allowedBadRequests) * 100);
  return {
    allowedBadRequests,
    observedBadRequests: failedRequests,
    budgetRemainingPercentage,
    isBudgetExhausted,
  };
}
```



The report clamps remaining percentage to zero at exhaustion. Use observedBadRequests and allowedBadRequests to quantify overspend. No observed requests returns null; it does not establish that the service met its target.

## Alert on the pace of consumption

**Burn rate = observed bad-event fraction / allowed bad-event fraction.** At 99.9%, a 1.44% bad fraction burns at 14.4×. Sustained for one hour, that consumes 2% of a 30-day budget under the rate model; sustained for six hours, it consumes 12%, not 5%.

A long window detects sustained damage; a short window verifies that damage is still occurring. The example requires both one-hour and five-minute windows above 14.4× for two minutes. This reduces pages for resolved spikes; it does not make noise or low-volume problems impossible.

```yaml
# prometheus-slo-alerts.yaml
groups:
  - name: checkout_slo_alerts
    rules:
      # Page immediately: 2% of 30-day budget burned in 1 hour (14.4x burn rate)
      # Both 1-hour and 5-minute windows must validate burn to avoid transient spike pages
      - alert: CheckoutApiErrorBudgetBurningFast
        expr: |
          (
            sum(rate(http_requests_total{job="checkout-api", status=~"5.."}[1h]))
            /
            sum(rate(http_requests_total{job="checkout-api"}[1h]))
          ) > (1 - 0.999) * 14.4
          and
          (
            sum(rate(http_requests_total{job="checkout-api", status=~"5.."}[5m]))
            /
            sum(rate(http_requests_total{job="checkout-api"}[5m]))
          ) > (1 - 0.999) * 14.4
        for: 2m
        labels:
          severity: page
          tier: tier-1
        annotations:
          summary: "Checkout API burning error budget at 14.4x normal pace"
          description: "At current burn rate, 30-day error budget will deplete within 50 hours."
```



The rule's population is **all checkout-api counter events** and its bad set is **5xx**. Adopt it only if that matches the intended SLI. Missing metrics and zero traffic need separate availability/coverage signals and a low-volume alert policy. Do not clamp an empty denominator to a healthy ratio. Aggregate event counts/rates, not an unweighted average of route percentages.

The 50-hour depletion annotation assumes that burn rate continues and the full budget was initially available. Actual time remaining depends on already consumed budget, traffic and rolling-window history. Add slower-burn ticket alerts when they match the team's response policy; the platform chapter owns the broader alert design.

## Agree on the release policy separately

| Observation | Possible pre-agreed action | Why it is a policy decision |
| ------------------- | ------------------------------------------------------------ | ----------------------------------------- |
| Fast sustained burn | Page, mitigate, pause risky rollouts | Protect users while impact is active |
| Budget exhausted | Prioritize reliability work; restrict risky feature releases | Balance reliability with urgent fixes |
| Budget healthy | Permit normal release process | Does not waive correctness/security gates |
| Missing measurement | Repair telemetry; state uncertainty | Absence of evidence is not spare budget |

A feature freeze is not an automatic mathematical consequence. Decide exceptions for remediation/security releases, ownership and resumption criteria. An SLA can use different exclusions and windows; setting it “looser” than an internal SLO does not prove contractual compliance.

Choose rolling or calendar windows consciously. Rolling windows avoid an arbitrary monthly reset but require clear reporting; some contracts use calendar months. Select targets from user tolerance, dependency capability and operational cost, then revisit them with evidence.

## Summary

Define a user-relevant population and good outcome, measure the SLI, then set its SLO. Calculate budgets in the measurement's actual units and alert on sustained burn with coverage safeguards. Release restrictions come from an agreed policy; an SLA remains its own contract.

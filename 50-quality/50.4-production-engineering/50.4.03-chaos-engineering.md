# Chaos Engineering in Production — Game Days, Automation, Resilience Metrics

## Definition

**Chaos engineering as an operations practice** is the organisational side of controlled failure injection: who runs it, where it is allowed to run, how it is gated, and how its findings change the system. It treats "we believe we are resilient" as a claim that must be *exercised* — in production, by the on-call engineers who would be paged when it fails for real.

```text
readiness gate        policy                cadence              output
──────────────────────────────────────────────────────────────────────────
SLOs + alerting       staging first,        scheduled game       tickets, runbook
instrumented          prod with kill        days (people in      fixes, new alerts,
(you cannot judge     switch + blast        the room), plus      and rehearsed
 an experiment         radius limit         automated canary     on-call muscle
 without metrics)                            fault injection
```

Three properties define the practice (as distinct from the experiment design):

1. **It requires the observability and SLO foundation first** — a chaos experiment's verdict is a comparison against a defined steady state, so without SLIs and alerts there is no way to know whether an injected fault was survived. Reliability work is therefore ordered: SLOs → alerting → incident process → chaos.
2. **Game days are a rehearsal, not just a test** — running an exercise with the actual on-call rotation (including communication, escalation, and the "who declares" decision) tests the *socio-technical* system, which is where most real incidents actually fail.
3. **Production injection is a policy, not a preference** — it is allowed only behind explicit gates: a kill switch, a bounded blast radius, a defined abort condition, notification to on-call, and a rollback plan. The organisation's job is to make that policy explicit so injections are neither forbidden (and therefore never happen) nor reckless.

## Game Day Runbook

### Pre-Game Day

```markdown
- [ ] Define hypothesis ("When X fails, Y should happen")
- [ ] Identify blast radius (which services are affected)
- [ ] Set up monitoring dashboards
- [ ] Notify stakeholders and on-call
- [ ] Prepare rollback plan
- [ ] Schedule team availability
- [ ] Rehearse the experiment in staging first
```

### During the Experiment

```markdown
- [ ] Start with the smallest blast radius
- [ ] Monitor system behaviour against the steady-state baseline
- [ ] Document observations as they happen (timestamps, not memory)
- [ ] Verify the alerts fire — and that they reach a human
- [ ] Exercise the incident process (who declares, who communicates)
- [ ] Abort immediately on unexpected impact
```

### Post-Experiment

```markdown
- [ ] Stop failure injection
- [ ] Verify full system recovery (not just "errors stopped")
- [ ] Review monitoring/alerting gaps the experiment exposed
- [ ] Update runbooks with what actually happened
- [ ] File follow-up actions with owners and dates
- [ ] Write a postmortem if customers were impacted
```

## Production Automation

### Guardrails an automated injector must enforce

| Guardrail | Why |
| --------------------------- | ----------------------------------------------------------------------------------- |
| **Pre-check gate** | refuse to run if the system is already degraded (a red dashboard is not a baseline) |
| **Blast-radius cap** | percentage of pods/instances, one tenant, one AZ — never "all" |
| **Hard abort condition** | stop on SLO breach, error-rate threshold, or a human kill switch |
| **Time box** | auto-cleanup after N minutes even if the orchestrator dies |
| **Change freeze awareness** | never inject during a release, migration, or a declared incident |
| **Attribution** | every injection labelled, so dashboards and on-call can tell chaos from an outage |

### Experiment as an automated loop

```typescript
class ChaosRunner {
  async runExperiment(experiment: Experiment): Promise<ExperimentResult> {
    const result: ExperimentResult = {
      experiment: experiment.name,
      startTime: new Date(),
      observations: []
    };

    // Guardrail: never inject onto an already-degraded system
    if (!await this.preCheck(experiment)) {
      result.status = 'skipped';
      result.reason = 'Pre-check failed (system not in steady state)';
      return result;
    }

    try {
      await this.injectFailure(experiment.failure);

      const monitoring = await this.monitor(experiment.duration);
      result.observations = monitoring.observations;

      result.hypothesisVerified = this.verifyHypothesis(experiment.hypothesis, monitoring);
      result.status = result.hypothesisVerified ? 'passed' : 'failed';
    } catch (error) {
      result.status = 'error';
      result.error = error.message;
    } finally {
      // Always clean up — an experiment that leaks its fault is an outage
      await this.cleanup(experiment.failure);
      result.endTime = new Date();
    }

    return result;
  }

  private async injectFailure(failure: Failure): Promise<void> {
    switch (failure.type) {
      case 'network-latency':
        await this.network.injectLatency(failure.target, failure.latency);
        break;
      case 'pod-kill':
        await this.kubernetes.killPod(failure.target);
        break;
      case 'disk-fill':
        await this.disk.fill(failure.target, failure.rate);
        break;
    }
  }
}
```

### Chaos in CI/CD

```yaml
# Run the same experiment set against staging on every release candidate,
# so a resilience regression is caught by the pipeline rather than by an incident.
- name: Run chaos tests
  run: |
    kubectl apply -f k8s/
    kubectl rollout status deployment/api

    chaos-mesh run experiments/network-latency.yaml
    chaos-mesh run experiments/pod-kill.yaml

    npm run test:integration      # must pass *while* the fault is held

    chaos-mesh cleanup
```

## Failover Drills Worth Rehearsing

The three drills below are the ones whose *expected* behavior is easy to assume and expensive to be wrong about. Each is a hypothesis to falsify, not a script to run blindly:

| Drill | Hypothesis | What usually fails first | Abort on |
| ----------------------- | ------------------------------------------------------------- | ---------------------------------------------------------------------------------- | -------------------------------------------- |
| **Primary DB failover** | app continues on the replica; error rate < 1%, recovers < 30s | connection-pool invalidation (pooled connections to a dead primary), stale DNS/TTL | write errors on the new primary |
| **Cache cluster loss** | app degrades to the database, no customer-visible errors | database connection exhaustion under the added load — the real outage | DB saturation, not cache errors |
| **Broker loss** | messages buffer and are processed after recovery, no loss | producer buffer limits, consumer rebalance storms, duplicate processing | unconsumed-queue/broker lag without recovery |

The lesson common to all three is that the *second-order* failure (pool exhaustion, rebalance storm, DNS TTL) is the one that takes the system down — which is exactly why the drill is worth running before it happens for real.

## Resilience Testing Under Load

```typescript
// k6: prove the SLO holds *while* a fault is held, not just at rest
export const options = {
  stages: [
    { duration: '2m', target: 100 },  // ramp up
    { duration: '5m', target: 100 },  // steady state
    { duration: '2m', target: 200 },  // peak
    { duration: '2m', target: 0 },    // ramp down
  ],
  thresholds: {
    http_req_duration: ['p(99)<500'],
    http_req_failed: ['rate<0.01'],   // the experiment's pass/fail line
  },
};
```

Load alone answers "can it handle volume?"; load *with* a held fault answers the question that matters in production — does the latency budget survive the failover, or does it only survive at rest?

## Metrics and Observability

```typescript
const chaosMetrics = {
  // experiment bookkeeping
  experimentsRun:     'chaos_experiments_total',
  experimentsPassed:  'chaos_experiments_passed_total',
  experimentsFailed:  'chaos_experiments_failed_total',

  // resilience outcome (the numbers that go in the review)
  meanTimeToRecovery: 'chaos_mttr_seconds',
  errorRateDuringChaos: 'chaos_error_rate',
  latencyDuringChaos:  'chaos_latency_p99',
};
```

Dashboard panels that make a game day reviewable: **experiments run**, **pass rate**, **MTTR during chaos**, and **error/latency during chaos** — the last two compared against the *same* metrics from before the injection, which is only possible because the steady-state baseline was captured first.

Findings are the output: an experiment that produced neither a resilience fix nor a confirmed hypothesis produced nothing.

## Interview Tips

- Frame the practice by its **gate**: you may only inject where you can detect (SLOs + alerts) and abort (kill switch + blast-radius cap).
- Name the ordering: **SLOs → alerting → incident process → chaos** — chaos last, because without the first three there is no verdict.
- Distinguish the two chapters' halves: **experiment design** (hypothesis, failure taxonomy, tooling) from **operating practice** (game days, policy, automation, metrics).
- Know the three drills whose second-order failure bites: failover pool invalidation, cache-loss DB saturation, broker-loss rebalance storms.
- Close with the output: every experiment ends in a **ticket, an alert, or a runbook change** — otherwise it was theatre.

## Summary

1. **Chaos engineering is hypothesis-driven experimentation on production** — "the system survives X" is falsifiable only by injecting X.
2. **Steady state comes first** — you can only detect an experiment's damage if you know what normal looks like in metrics.
3. **Blast radius is the safety dial** — start with one instance in staging, grow scope as confidence and rollback automation grow.
4. **Game days turn experiments into organizational muscle memory** — on-call rehearsed failure responds faster than on-call surprised by it.
5. **Every experiment ends in either a resilience fix or a confirmed hypothesis** — findings without action items are theatre.

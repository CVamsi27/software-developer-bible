# Chaos Engineering — Experiments, Game Days, Resilience Testing

## Principles of Chaos Engineering

1. **Build confidence** in system's ability to handle failures
2. **Uncover weaknesses** before they cause outages
3. **Automate** failure injection in staging/production
4. **Minimize blast radius** during experiments

## Game Day Process

### Pre-Game Day
```markdown
## Preparation Checklist
- [ ] Define hypothesis ("When X fails, Y should happen")
- [ ] Identify blast radius (which services affected)
- [ ] Set up monitoring dashboards
- [ ] Notify stakeholders
- [ ] Prepare rollback plan
- [ ] Schedule team availability
- [ ] Test experiment in staging
```

### During Experiment
```markdown
## Execution Checklist
- [ ] Start with smallest blast radius
- [ ] Monitor system behavior
- [ ] Document observations
- [ ] Verify alerts fire correctly
- [ ] Test incident response process
- [ ] Stop if unexpected impact
```

### Post-Experiment
```markdown
## Review Checklist
- [ ] Stop failure injection
- [ ] Verify system recovery
- [ ] Review monitoring/alerting gaps
- [ ] Update runbooks
- [ ] Schedule follow-up actions
- [ ] Write postmortem if needed
```

## Common Experiments

### 1. Database Failover
```typescript
// Hypothesis: System continues with read replica
const experiment = {
  name: 'Database Primary Failover',
  hypothesis: 'Application continues with read replica during primary failure',
  steps: [
    '1. Start application load test',
    '2. Kill primary database',
    '3. Monitor error rates and latency',
    '4. Verify read replica takes over',
    '5. Restore primary'
  ],
  expected: 'Error rate spikes < 1%, recovers in < 30s',
  rollback: 'Restore primary database'
};
```

### 2. Cache Failure
```typescript
// Hypothesis: System degrades gracefully
const experiment = {
  name: 'Redis Cluster Failure',
  hypothesis: 'Application falls back to database queries',
  steps: [
    '1. Start application load test',
    '2. Stop Redis cluster',
    '3. Monitor database load',
    '4. Verify application continues',
    '5. Restore Redis'
  ],
  expected: 'Database load increases, no errors',
  rollback: 'Restore Redis cluster'
};
```

### 3. Message Queue Failure
```typescript
// Hypothesis: Messages are queued and processed later
const experiment = {
  name: 'Kafka Broker Failure',
  hypothesis: 'Messages are buffered and processed after recovery',
  steps: [
    '1. Start producing messages',
    '2. Kill one Kafka broker',
    '3. Continue producing messages',
    '4. Restore broker',
    '5. Verify all messages processed'
  ],
  expected: 'No message loss, processing resumes',
  rollback: 'Restore Kafka broker'
};
```

## Automation with Chaos Monkey

### Netflix Chaos Monkey Pattern
```typescript
class ChaosMonkey {
  private schedule: ChaosSchedule;
  private targets: ChaosTarget[];

  async runExperiment(experiment: Experiment): Promise<ExperimentResult> {
    const result: ExperimentResult = {
      experiment: experiment.name,
      startTime: new Date(),
      observations: []
    };

    // Pre-check
    if (!await this.preCheck(experiment)) {
      result.status = 'skipped';
      result.reason = 'Pre-check failed';
      return result;
    }

    // Inject failure
    try {
      await this.injectFailure(experiment.failure);

      // Monitor
      const monitoring = await this.monitor(experiment.duration);
      result.observations = monitoring.observations;

      // Verify hypothesis
      result.hypothesisVerified = this.verifyHypothesis(experiment.hypothesis, monitoring);
      result.status = result.hypothesisVerified ? 'passed' : 'failed';

    } catch (error) {
      result.status = 'error';
      result.error = error.message;
    } finally {
      // Cleanup
      await this.cleanup(experiment.failure);
      result.endTime = new Date();
    }

    return result;
  }

  private async injectFailure(failure: Failure): Promise<void> {
    switch (failure.type) {
      case 'network-latency':
        await this.network.injectLatency(failure.target, failure.latency);
        break;
      case 'pod-kill':
        await this.kubernetes.killPod(failure.target);
        break;
      case 'disk-fill':
        await this.disk.fill(failure.target, failure.rate);
        break;
    }
  }
}
```

## Resilience Testing

### Load Testing with Failures
```typescript
// k6 load test with chaos
export const options = {
  stages: [
    { duration: '2m', target: 100 }, // Ramp up
    { duration: '5m', target: 100 }, // Steady state
    { duration: '2m', target: 200 }, // Peak load
    { duration: '5m', target: 200 }, // Peak steady
    { duration: '2m', target: 0 }, // Ramp down
  ],
  thresholds: {
    http_req_duration: ['p(99)<500'],
    http_req_failed: ['rate<0.01'],
  },
};

// Inject failures during test
if (__VU === 1) {
  // After 3 minutes, kill a pod
  sleep(180);
  exec('kubectl', 'delete', 'pod', '--random');
}
```

## Interview Tips
- Explain chaos engineering principles (hypothesis, experiment, observe)
- Know common chaos experiments (network, resource, service failures)
- Discuss game day process and preparation
- Explain blast radius and how to minimize it
- Know chaos automation and CI/CD integration- Discuss resilience metrics (MTTR, error rate during chaos)

## Summary

1. **Chaos engineering is hypothesis-driven experimentation on production** — "the system survives X" is falsifiable only by injecting X
2. **Steady state comes first** — you can only detect an experiment's damage if you know what normal looks like in metrics
3. **Blast radius is the safety dial** — start with one instance in staging, grow scope as confidence and rollback automation grow
4. **Game days turn experiments into organizational muscle memory** — on-call rehearsed failure responds faster than on-call surprised by it
5. **Every experiment ends in either a resilience fix or a confirmed hypothesis** — findings without action items are theater

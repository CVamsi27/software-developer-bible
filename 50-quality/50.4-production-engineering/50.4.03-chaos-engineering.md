# Chaos Engineering in Production — Game Days, Automation, Resilience Metrics

A cache fallback works in a unit test yet overloads the database at peak traffic. A production experiment can expose that interaction — but it can also harm users. Authorization, observation and recovery are part of the experiment, not paperwork added afterwards.

```text
validate scope and permissions
  -> confirm baseline and available responder
  -> install one bounded fault with independent expiry
  -> observe user outcomes while the fault is active
  -> stop on threshold, telemetry loss, operator request or deadline
  -> verify fault removal AND service recovery
```

## Definition

**Chaos engineering as an operations practice** governs controlled failure experiments: who may run them, where faults are allowed, how impact is bounded and how findings change the service. It tests the claim "we can recover from this failure" against observed behavior, including the responders' access, alerts and runbooks.

> **Textbook Definition:** An operational chaos program governs fault experiments and response rehearsals through ownership, prerequisites, bounded scope, stopping conditions and follow-up changes to improve resilience.

## First Principles

A distributed service fails through interactions, not only individual components, and test environments cannot reproduce every traffic pattern, quota or human response. Confidence therefore comes from bounded observations in stated conditions — never a proof that the system withstands every failure. Removing an injected fault does not undo everything it caused: queued requests, repeated writes and exhausted pools can survive the injection, so an experiment needs both a way to stop the fault and a way to verify recovery.

## How It Works

### 1. Separate the Experiment From the Response Rehearsal

The [testing chapter](../50.1-testing/05-advanced/50.1.5.02-chaos-engineering.md) owns hypothesis design, fault types and the focused injection example. This chapter owns permission, operational coordination, stopping and follow-up. A **game day** is a scheduled rehearsal of the people and service together: responders practice detection, escalation, investigation and recovery. It may use fault injection, a simulated scenario or a controlled dependency failure. A chaos experiment can run without a game day; a game day need not damage a production dependency.

Before any real injection, establish a baseline for the user outcome, sufficient telemetry to notice harm, known recovery actions and an available response owner. A complete SLO program helps, but the prerequisite is measurable behavior and a response policy appropriate to the experiment.

### 2. Trace One Cache-Loss Rehearsal

The following is a **hypothetical** plan, not a tested deployment procedure. Its thresholds would need justification for the actual service.

| Phase | Concrete action | Observation or decision |
| -------- | -------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------- |
| Define | Select a noncritical read operation served by one canary instance; exclude payments and writes | Hypothesis: cache loss preserves correct responses within the agreed latency limit |
| Bound | Route at most 1% of eligible traffic to that instance; verify its label selector and dependency scope | A shared-cache fault would affect more than 1%; inject only on the selected instance's cache path |
| Baseline | Record request success, latency, fallback reads and database connection occupancy at representative load | A degraded baseline or missing observations blocks the run |
| Inject | Hold the selected cache-path fault for at most 60 seconds with an independently enforced expiry | Mark the experiment in telemetry and give the controller a manual stop path |
| Observe | Fallback reads rise; database occupancy crosses the approved stop threshold | Stop now rather than waiting to accumulate a convincing outage |
| Recover | Remove the fault and check new requests, pool waits, retries and outstanding work | Do not declare recovery merely because the injector reports cleanup |
| Learn | Compare before/during/after signals and the responder timeline | Add bounded fallback concurrency, then rerun the same hypothesis under the same stated conditions |

The selected canary may still share a database with the rest of the fleet. **Blast radius** means the actual reachable consequences of the fault, not only the number of pods selected — a small selector is insufficient when it can trigger a shared dependency failure.

### 3. Give the Controller Authority and Stop Conditions

| Responsibility | Required decision |
| --------------------- | --------------------------------------------------------------------- |
| Service owner | Approves the hypothesis, affected operations and residual user risk |
| Experiment controller | Confirms prerequisites, starts/stops the fault and keeps the timeline |
| Incident responder | Watches user impact and may request an immediate stop |
| Communication owner | States the exercise scope, current result and next update |

Small teams can combine roles if the responder still has capacity to observe and stop. Record who takes over if the controller disconnects. Avoid surprise pages unless that surprise is specifically authorized as part of the rehearsal and backup coverage is ready. Define stop thresholds for correctness, error rate, latency, dependency saturation and telemetry loss: a hard duration limit protects against a forgotten experiment but does not replace impact-based stopping. Pause planned injections during unrelated incidents or changes unless the interaction itself is the approved scenario.

### 4. Rehearse the Failures That Change Ownership or Load

| Scenario | Mechanism to verify | Important boundary |
| --------------------- | -------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| Primary database loss | Fence the old writer, promote an eligible target, reconnect clients and reconcile uncertain writes | A replica is not automatically a writable failover target; freshness and write ownership matter |
| Cache loss | Bound fallback work and preserve required correctness while misses rise | The database may become the bottleneck; not every operation permits stale data |
| Broker loss | Apply bounded buffering/backpressure and recover processing | In-memory producer buffers may be lost on crash; delivery and duplicate handling depend on acknowledgments and durable state |
| Network partition | Distinguish an unreachable peer from a dead peer and maintain the invariant | Restarting both sides does not establish one writer or remove conflicting work |

Choose load conditions deliberately: a successful quiet-period experiment may say little about peak queues. Protect the shared environment, and state the workload, duration, fault and correctness checks in the result. CI can automate an experiment in an isolated staging environment when setup, fault lifetime, test timing and cleanup are controlled — but running ordinary integration tests *after* a fault has expired tests recovery, not behavior under the fault. This control-flow model is not a tool command: a cluster controller, network proxy and managed chaos service have different scope and cleanup semantics.

### 5. Record Evidence, Including Inconclusive Outcomes

Report the hypothesis and exact scope, baseline, fault start and stop, observed user effects, response actions and recovery checks. Compare like populations and windows — an overall average can hide damage to the canary or one tenant. Use **supported in these conditions**, **falsified**, or **inconclusive**: missing metrics, too little traffic or an early abort may prevent a verdict. A confirmed hypothesis is useful evidence even when no repair ticket is needed; a failed hypothesis needs an owned improvement and a later verification, not just an impressive incident story.

## Automation must survive a failed runner

A `finally` block helps when a process reaches cleanup. It does not run after a killed process or unreachable controller. Give injected faults an expiry enforced by the fault mechanism, plus an independent recovery and check path. Test what happens when the orchestrator dies while the fault is active. The orchestration contract is the hook's control-flow model above: validate scope, confirm baseline, install one bounded fault with independent expiry, observe outcomes, stop on threshold, telemetry loss, operator request or deadline, then verify fault removal *and* service recovery.

For example, Chaos Mesh schedules experiments through Kubernetes resources; use its documented resource and recovery workflow rather than assuming a universal `chaos-mesh run` CLI.

## Common Mistakes

- Treating “one pod” as a complete blast-radius limit despite shared dependencies.
- Using automatic fault removal as proof that queues and written state recovered.
- Increasing scope while the baseline is already degraded or observation is missing.
- Reporting a pass from tests that never ran during the active fault.
- Claiming a few successful drills prove resilience to all production failures.

## Best Practices

Start from a consequential uncertainty, choose the smallest representative test and make stopping independent of the experiment runner. Rehearse the responders' access and escalation as well as the service mechanism. Keep the result tied to its environment and follow up on the specific weakness it exposed.

## Summary

An operational chaos program makes failure experiments authorized, observable, bounded and recoverable. Trace effects through shared dependencies, stop when the agreed risk limit is reached, and verify the service after the fault ends. Record what the experiment supports, what it disproves and what remains unknown.

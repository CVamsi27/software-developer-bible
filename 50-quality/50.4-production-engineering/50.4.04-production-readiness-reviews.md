# Production Readiness Reviews

## TL;DR

A **Production Readiness Review (PRR)** is a structured go/no-go gate that checks a service against reliability, operability, and security criteria *before* it takes production traffic — Google's answer to launching services that page their creators at 3 AM. The checklist covers capacity, quotas, alerting, runbooks, rollback, load testing, and security review. Done heavyweight it becomes bureaucracy; done right — risk-tiered, templated, lightweight for small teams — it is the cheapest incident prevention you can buy.

## Definition

A PRR is a documented assessment, performed by (or with) a platform/SRE function, verifying that a new or significantly changed service meets production standards across defined domains. It produces one of: **approved**, **approved-with-conditions**, **deferred** (with explicit gaps and dates). The review's output is evidence — dashboards linked, load tests attached, runbooks walked through — not promises.

```text
PRR AS LAUNCH GATE
   dev complete ──> staging validated ──> [ PRR ] ──> gradual rollout
                                          │
                              ┌───────────┼─────────────┐
                              v           v             v
                          APPROVED    APPROVED WITH   DEFERRED
                                      CONDITIONS      (gaps + date,
                                      (monitor in       re-review)
                                      prod + fix list)
```

## Why it matters

Most incidents trace back to things a checklist catches cheaply: no runbook for the known failure mode, alerts that fire on symptoms nobody can act on, no tested rollback, capacity sized by vibes. Interviews love this topic at staff level ("How do you make sure a service is ready?") because it reveals whether a candidate thinks in *systems of prevention* versus personal heroics. The counter-question every interviewer has in mind: "Doesn't this slow teams down?" — your answer (risk tiers, automation, checklists-as-code) is the actual senior signal.

## Why Do We Need It?

- **Launch-day failure is the default**: un-reviewed services reliably lack dashboards, quotas, and rollback paths — the PRR makes omissions visible before they page.
- **Institutional memory**: checklists encode every past postmortem action item so lessons stop being relearned per team.
- **Shared vocabulary**: "deferred pending load test" beats ambiguous "I think we're fine".
- **On-call protection**: whoever inherits the pager deserves documentation, sane alerts, and a rollback plan they didn't write.
- **Compliance adjacency**: security review and data-classification steps satisfy audit requirements as a side effect.
- **Forcing function for SLOs**: a service cannot pass without defined SLIs/SLOs, which later power error-budget decisions.

## How It Works

### The review flow

```text
T-2 WEEKS        T-1 WEEK          T-0            POST-LAUNCH
Author self-     Review meeting    Decision       30-day follow-up
assesses via     (30-60 min):      + conditions   verifies condition
template;        walk evidence     recorded       closure; retro on
attaches links   domain by domain  in launch      the PRR itself
                 (not slides)      tracker
```

Evidence over assertion is the core rule: "alerts exist" fails; link to Alertmanager rules with burn-rate thresholds passes.

### Checklist domains

| Domain | Key questions | Evidence |
| ----------------- | ------------------------------------------------------------------------------ | --------------------------------- |
| Architecture | Single points of failure? Blast radius understood? | Diagram + failure-mode notes |
| Capacity & quotas | Traffic estimate? Resource limits set? Downstream quota granted? | Load model, quota approvals |
| Load testing | Tested at 2x expected peak? Found breaking point? | Test report, graphs |
| SLIs/SLOs | Defined? Dashboards show them? Error budget policy agreed? | Dashboard + SLO config |
| Alerts | Page only on user impact / fast burn? Each actionable? | Alert rules, runbook links |
| Runbooks | Every alert links to steps? Restart/rollback procedures current? | Runbook URLs, last-reviewed dates |
| Rollback | Schema changes reversible? Feature flags to disable? Tested recently? | Rollback drill record |
| Deployment | Progressive rollout? Automated? Canary analysis? | Pipeline config |
| Security | Threat model? Secrets managed? Data classification done? Dependencies scanned? | Security review sign-off |
| Dependencies | What if each dependency dies? Timeouts/retries/circuit breakers set? | Resilience config |
| Data | Backups scheduled AND restored successfully? Retention/GDPR handled? | Restore test log |
| On-call handoff | Who pages? Escalation path? Contact channels live? | Rota entry, escalation doc |

### Go/no-go criteria

Decision logic stays boring and explicit:

1. Any **SEV-critical gap** (no rollback, no alerts, unencrypted secrets) → deferred.
2. Gaps with mitigations (e.g., missing dashboard but metrics flowing) → approved with conditions and a deadline.
3. Risk-tiered depth: tier-1 (customer-facing, money) gets full review; tier-3 internal tools get self-service checklist sign-off.

## Code Examples

### A machine-readable readiness template

Store the checklist as data so CI can track completeness:

```yaml
# prr/checkout-service.yaml
service: checkout-service
tier: 1
review_date: 2026-03-02
decision: approved_with_conditions

domains:
  capacity:
    - item: "Load tested at 2x Black Friday peak"
      status: pass
      evidence: "https://grafana/loadtest-checkout-2026-02"
    - item: "Downstream quota: payments API raised to 5k rps"
      status: pass
      evidence: "quota-ticket-4482"
  alerts:
    - item: "Every page alert links to a runbook"
      status: fail
      note: "HighErrorRate alert missing runbook link"
  rollback:
    - item: "Schema migration reversible within 5 min"
      status: conditional
      note: "expand-migrate-contract stage 3 not yet automated"

conditions:
  - id: COND-1
    description: "Add runbook link to HighErrorRate alert"
    owner: checkout-team
    due: 2026-03-09
  - id: COND-2
    description: "Automate contract-stage rollback drill"
    owner: checkout-team
    due: 2026-03-31
```

### Enforcing the gate in CI

```typescript
// scripts/check-prr.ts — fails the release pipeline when the PRR blocks
import { readFileSync } from 'node:fs';
import { parse } from 'yaml';

const prr = parse(readFileSync('prr/checkout-service.yaml', 'utf8'));

const blocking = [
  ...prr.domains.flatMap((d: Domain[]) =>
    d.filter((item) => item.status === 'fail')),
];

if (blocking.length > 0 && prr.decision === 'approved') {
  console.error(`PRR says approved but ${blocking.length} items FAIL:`);
  blocking.forEach((b) => console.error(` - ${b.item}`));
  process.exit(1);
}

if (prr.tier === 1 && prr.decision === 'deferred') {
  console.error('Tier-1 service may not ship while PRR is deferred.');
  process.exit(1);
}

console.log(`PRR OK (${prr.decision}), open conditions: ${prr.conditions.length}`);
```

### Lightweight variant for small teams

Teams without an SRE group run the same domains asynchronously: open a PR adding `prr.md` to the service repo, one senior engineer from *another* team reviews it as reviewer-of-record, and the merge itself is the approval. Same rigor, zero meetings.

## Real-World Use Cases

1. **Fintech launching instant payouts** — PRR surfaced that fraud-model latency spike would exhaust connection pools under peak load; load test reproduced it in staging, pool sizing fixed pre-launch, saving certain SEV1 on day one.
2. **Platform team institutionalizing PRRs after a quarter of launch incidents** — every postmortem action item became a checklist row; six months later launch-week SEVs dropped from four to zero.
3. **Startup adopting a 10-item mini-PRR** — the whole review fits in one issue template (dashboards? alerts actionable? rollback tested? backups restored?); enough discipline without dedicated SREs.
4. **Migration treated as re-launch** — moving a monolith module to its own service triggers full PRR even though "the code already runs", catching that nobody owned its dashboards after extraction.
5. **Third-party vendor integration** — PRR extended to vendors: their uptime SLO, status-page feed into our alerts, and contractual error budgets reviewed before traffic flows.

## Common Mistakes

```markdown
<!-- BAD: checkbox theater -->
- [x] Load testing performed
- [x] Alerts configured
- [x] Runbook written

<!-- GOOD: evidence-linked, falsifiable -->
- [x] Load testing performed
      -> report: grafana/loadtest-checkout-2026-02 (2x peak sustained, p99 340ms)
- [x] Alerts configured
      -> rules: alerts/checkout.yml (burn-rate multiwindow, all linked to runbooks)
- [x] Runbook written
      -> wiki/runbooks/checkout + last drill 2026-02-20 (rollback 4m12s)
```

Recurring failures:

- **Rubber-stamping**: reviews become calendar theater where nothing defers; if 100% pass rate, the gate is decoration — healthy pipelines defer some launches.
- **Reviewing slides instead of systems**: walkthroughs of architecture diagrams with no dashboard clicked open; demand live evidence.
- **One-size-fits-all depth**: applying Google-scale review to a cron job burns goodwill; tier by blast radius.
- **No follow-through**: conditions logged, never closed; pair every condition with an owner, due date, and automatic reminder.
- **Static checklists forever**: new postmortem learnings must mutate the template quarterly, or you codify yesterday's failures.

## Best Practices

1. Self-assessment first, meeting second — spend human time discussing gaps, not discovering them.
2. Evidence links mandatory; assertions are rejected.
3. Tier services by blast radius; scale review weight accordingly (full / standard / self-service).
4. Every alert created must reference a runbook before the review closes.
5. Require a *tested* rollback — restore drills and rollback rehearsals count more than plans.
6. Track conditions in the same system as work (issues, not wikis) with owners and dates.
7. Re-run abbreviated PRRs on major architecture changes, not just greenfield launches.
8. Feed every relevant postmortem action item into the checklist permanently.

## Performance Considerations

The PRR's own performance matters: a heavyweight review adds weeks and breeds circumvention. Automate what machines verify (dashboard exists, alert has runbook link, backup restore log fresh) via tooling like the YAML-plus-CI pattern above; reserve human judgment for risk trade-offs. Budget the review meeting to 60 minutes using timeboxing per domain — parking-lot anything contentious. For large fleets, sample: deep-review one service per team per quarter plus all tier-1 launches, keeping aggregate cost roughly flat while coverage stays broad.

## Summary

- A PRR is a go/no-go launch gate converting reliability expectations into checked, evidenced criteria across ~12 domains.
- Outcomes are explicit: approved, approved-with-conditions (owner + deadline), or deferred with named gaps.
- Evidence beats assertion — live dashboards, load-test reports, and rehearsed rollbacks, not checkboxes.
- Tier the depth: full review for customer-facing/money paths, self-service checklists for low-risk tools.
- Small teams get 80% of the value from a 10-item evidence-linked template reviewed by a peer engineer.
- Keep the checklist alive by folding in postmortem learnings; a never-deferring review is a broken review.

## Cheat Sheet
```text
PRODUCTION READINESS REVIEW CHEAT SHEET
============================================================

THE FLOW:
• Self-assess via template -> evidence meeting -> decision ->
  conditions tracked -> 30-day closure check

CHECKLIST DOMAINS (memorize 8):
• Capacity & quotas      • Load tests (2x peak)
• SLIs / SLOs + dashboard• Alerts actionable + runbook links
• Runbooks (current!)    • Rollback TESTED, schema reversible
• Security & secrets     • Dependency failure modes
• Backups RESTORED       • Progressive deploy pipeline
• On-call handoff        • Data retention / GDPR

DECISIONS:
• Approved                -> ship
• Approved w/ conditions  -> ship + monitored debt w/ owner+date
• Deferred                -> named blockers, re-review date

GATE RULES:
• Evidence links required (dashboards, test reports, drills)
• Fail-open checklist + "approved" = pipeline error
• Tier 1 blocked while deferred

SMALL TEAM VARIANT:
• 10-item md template, peer reviewer from another team,
  PR merge = approval. No committee needed.

HEALTH SIGNALS:
• Some launches defer (else it's rubber-stamping)
• Postmortem items join the checklist quarterly
• Conditions close on time >90%

INTERVIEW FORMULA:
• "Cheap prevention vs expensive incidents"
• "Evidence over assertion"
• "Risk-tiered so it scales without bureaucracy"
```

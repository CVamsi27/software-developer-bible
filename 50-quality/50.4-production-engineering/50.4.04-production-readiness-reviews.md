# Production Readiness Reviews

A booking service passes its functional tests — yet has no recovery plan for its database. The review asks what happens when the service reaches its load limit or loses a dependency, who responds, and what evidence supports the answer.

```typescript
releaseGate(review, 'booking-v2', new Date());
// → { allowed: true, reasons: [] } only for a matching, unexpired,
//   conditionally approved review with no blocking or overdue condition
```

## Definition

A **production readiness review (PRR)** is a documented assessment of whether a new or significantly changed service meets its **operational requirements**. Service owners and reviewers examine evidence, identify gaps, and record an approval, conditional approval or deferral.

> **Textbook Definition:** A production readiness review evaluates evidence that a service can meet its operational requirements across release, capacity, security, observability and recovery, recording approval conditions or unresolved gaps.

## First Principles

Tests cover selected behavior in selected conditions. Production adds uncertain demand, changing dependencies, sensitive data and continuing operational responsibility — so readiness needs several kinds of evidence, and no single green build establishes it. Review time is limited: let depth follow the consequences of failure and the novelty of the change, while explicit decisions stop unresolved risk from becoming an unspoken launch assumption.

## How It Works

### 1. Turn Requirements Into Evidence

- **Ownership**: who operates, funds and changes the service? Evidence: named team, working escalation and handoff.
- **User outcomes**: which operations must succeed, and how are failures noticed? Evidence: measurement contract, exercised alerts and dashboard.
- **Capacity**: where does the service saturate, including dependencies? Evidence: representative load profile, queue limits, quota and headroom model.
- **Change safety**: can exposure be stopped and correctness restored? Evidence: canary criteria, binary and schema compatibility, tested recovery.
- **Dependency failure**: which operations degrade, reject or queue? Evidence: timeout, retry and backpressure configuration plus observed failure tests.
- **Persistent data**: can required data be restored and reconciled? Evidence: restore result, recovery objectives and retention rules.
- **Security**: which identities can access which data or actions? Evidence: threat review, authorization tests, secret handling and access ownership.
- **Response**: can a responder perform the necessary action? Evidence: exercised runbook, access path and recovery check.

A dashboard link proves a dashboard exists, not that it detects the important failure. A backup log proves backup completion, not restorability. Record what each artifact actually demonstrated — plus its version, environment, date and limitations. "Twice expected peak" may be a useful margin but is not a universal capacity standard, and a destructive migration may need forward repair plus a verified restore strategy rather than a pretended instant rollback.

### 2. Trace a Conditional Launch Decision

The following **hypothetical** review concerns a booking service extracted from a monolith:

- The owner proposes the initial traffic, correctness requirements and recovery targets. Reviewers identify database pool capacity and write compatibility as the main uncertainties.
- A load test shows each replica stays below its local pool limit, but the proposed fleet exceeds the database's available connections. The capacity evidence does not yet support launch.
- The team reduces the fleet-wide allocation, adds bounded admission and repeats the representative test. Requests now reject predictably before pool saturation; reviewers assess whether that behavior meets the requirement.
- The previous binary can read the expanded schema. A rehearsal restores user operations without losing acknowledged bookings. The later contract step gets its own recovery plan and review gate.
- An alert's runbook lacks one diagnostic step. If response remains workable through an approved interim procedure, the reviewer may accept a dated condition; if responders cannot safely restore service, this is a blocker.
- The decision records the reviewed change, allowed rollout scope, owner, open conditions and expiry. A broader rollout or material design change requires revisiting the decision.

Conditional approval means a responsible owner accepted a **specific bounded gap** with a follow-up — not permission to launch while any item is marked failed. A deferral does not mean the architecture is bad; it means the required evidence or control is absent.

### 3. Automate the Decision Contract, Then Validate Behavior Separately

Machines can reject a deferred or stale decision and overdue conditions. They cannot infer that a recovery drill was sufficient from an evidence URL. The function below consumes a **validated typed review record**; parsing untrusted YAML or JSON requires schema validation before this boundary. Connect it to the actual deployment change identifier, not a service name that stays constant across releases.

```typescript
type Condition = {
  id: string;
  owner: string;
  dueAt: string; // ISO timestamp with an explicit time zone.
  status: 'open' | 'closed';
  blocksRelease: boolean;
};

type Review = {
  reviewedChange: string;
  decision: 'approved' | 'approved_with_conditions' | 'deferred';
  expiresAt: string;
  conditions: Condition[];
};

export function releaseGate(review: Review, change: string, now: Date) {
  const reasons: string[] = [];
  const nowMs = now.getTime();
  const expiry = Date.parse(review.expiresAt);
  if (!Number.isFinite(nowMs)) throw new RangeError('Invalid evaluation time');
  if (review.reviewedChange !== change) reasons.push('Change was not reviewed');
  if (!Number.isFinite(expiry) || nowMs >= expiry) reasons.push('Review expired or invalid');
  if (review.decision === 'deferred') reasons.push('Review deferred');

  for (const condition of review.conditions) {
    if (condition.status === 'closed') continue;
    const due = Date.parse(condition.dueAt);
    if (!condition.id.trim() || !condition.owner.trim()) reasons.push('Unowned condition');
    if (!Number.isFinite(due) || nowMs >= due) reasons.push(`Condition overdue: ${condition.id}`);
    if (condition.blocksRelease) reasons.push(`Blocking condition: ${condition.id}`);
    if (review.decision !== 'approved_with_conditions') reasons.push('Open condition lacks conditional approval');
  }
  return { allowed: reasons.length === 0, reasons };
}
```

For change `booking-v2`, a matching, unexpired conditional review with one owned, nonblocking condition due next week passes this **metadata gate**. The same review fails at the condition's deadline, for `booking-v3`, or with a blocking condition. The deployment pipeline must still run the applicable tests, access checks and rollout controls. Production integration also needs a trusted source for decisions, authorized reviewers, immutable evidence and version references, and validation of input shape and timestamp format — a TypeScript annotation alone does not validate a parsed object at runtime.

### 4. Keep the Review Proportionate and Current

Start the review during design so important gaps can change the implementation cheaply. Use a self-assessment to gather evidence, then spend reviewer time on uncertainties and trade-offs. Low-impact changes may need a short peer review; a new money-moving write path needs deeper correctness and recovery evidence. Never turn every postmortem action into a permanent checklist row: add or refine a check when it catches a relevant failure class, remove obsolete controls, and preserve the reason for each requirement.

Track conditions as owned work with deadlines, accepted residual risk and resumption criteria. Reassess significant changes to workload, dependencies, schema or operational ownership. Where legal or contractual requirements apply, the relevant specialist verifies them — a generic readiness checklist does not establish compliance. Tie each requirement to a failure consequence and observable evidence, and automate checks of that contract while retaining human judgment about residual risk.

## Common Mistakes

- Equating an artifact's existence with the behavior it should prove.
- Allowing a deferred review because the service happens to be a lower tier.
- Approving a new change using evidence for an older, materially different version.
- Hiding a blocking gap under “approved with conditions.”
- Requiring an arbitrary load multiplier or reversible schema change without considering the workload and recovery design.

## Summary

A readiness review makes operational requirements and unresolved risks visible before the relevant change. Examine behavior across load, dependencies, data, access and recovery; record what the evidence supports. Approval is scoped and revisitable, and conditional approval requires an owned, bounded gap rather than an unqualified pass.

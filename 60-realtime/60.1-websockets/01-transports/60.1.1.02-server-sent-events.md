# Server-Sent Events (SSE)

A download-progress page should update when the server has new progress — not repeatedly ask whether anything changed. SSE keeps one HTTP response open for those updates, while the browser still sends commands through ordinary requests.

```text
id: 42
event: progress
data: {"percent":75}

```

## Definition

**Server-Sent Events (SSE)** push text updates from a server over an HTTP response. The browser's **EventSource** interface parses events and can reconnect after an interrupted connection; **event IDs** support an application-defined replay cursor.

> **Textbook Definition:** Server-Sent Events defines a UTF-8 event stream carried in an HTTP response with media type `text/event-stream`. EventSource dispatches parsed events and manages reconnection; event IDs support an application-defined replay cursor.

## First Principles

An HTTP response body can arrive incrementally, but the receiver needs a framing rule to distinguish one update from the next — SSE supplies that rule with named text fields and a blank line between event blocks. A dropped connection raises a second problem: which updates were missed? Reopening restores a channel, but recovery needs a stable cursor plus server-side history or a new snapshot. A transport cannot reconstruct events the application never retained.

## How It Works

### 1. Match the Transport to the Direction

SSE suits feeds, progress updates and notifications where the browser mainly receives data. WebSockets offer a bidirectional text and binary channel when both peers must send independently. Neither choice supplies durable delivery, authorization or a universal latency advantage — compare message direction, payload, recovery and infrastructure constraints instead of assigning universal speed rankings.

### 2. Turn Bytes Into Events

```text
browser GET /events → server keeps HTTP response open
server writes UTF-8 fields + blank line → browser dispatches an event
connection ends → browser may reconnect with its last event ID
server validates cursor → replays retained updates or asks for a reset
```

These are separate steps. HTTP chunks and network packets are not SSE event boundaries: one event may span several reads, and one read may contain several events. `event` selects the listener name (defaulting to `message`); `data` supplies text the application may parse as JSON, with multiple data lines joined by newlines. A blank line completes a block; a comment beginning with `:` dispatches nothing; `retry` sets reconnection delay in milliseconds. IDs are strings, not necessarily numbers — monotonic decimal IDs are this chapter's convention.

On automatic reconnection, the same EventSource sends its remembered ID as `Last-Event-ID`; closing it and constructing a new one starts a fresh browser cursor. IDs do not acknowledge database storage, handler success or exactly-once effects — the application needs replay, deduplication and a retention-gap policy if those properties matter.

### 3. Run a Bounded Local Replay Server

Save this as `server.mjs` and the client below as `index.html` in one directory. Run `node server.mjs`, then open `http://127.0.0.1:18085`. Node.js supplies the HTTP server; no framework is required. The fixture publishes a temperature each second and retains the last 100 updates in memory.

```javascript
import { createServer } from 'node:http';
import { readFile } from 'node:fs/promises';
import { pathToFileURL } from 'node:url';

export function createDemo() {
  const history = [];
  const clients = new Set();
  let sequence = 0;
  function write(res, text) {
    if (res.destroyed || res.writableEnded) return false;
    if (!res.write(text)) {
      res.destroy(); // bounded slow-consumer policy: disconnect and resume later
      return false;
    }
    return true;
  }
  function encode(record) {
    return `id: ${record.id}\nevent: temperature\ndata: ${JSON.stringify(record)}\n\n`;
  }
  function publish(value) {
    if (!Number.isFinite(value)) throw new Error('Temperature must be finite');
    if (sequence === Number.MAX_SAFE_INTEGER) throw new Error('Sequence exhausted');
    const record = { id: ++sequence, value };
    history.push(record);
    if (history.length > 100) history.shift();
    for (const res of clients) write(res, encode(record));
    return record.id;
  }
  const server = createServer(async (req, res) => {
    const pathname = new URL(req.url, 'http://127.0.0.1').pathname;
    if (req.method === 'GET' && pathname === '/') {
      try {
        const html = await readFile(new URL('./index.html', import.meta.url));
        res.writeHead(200, { 'Content-Type': 'text/html; charset=utf-8' });
        res.end(html);
      } catch { res.writeHead(500).end('Client fixture unavailable'); }
      return;
    }
    if (req.method !== 'GET' || pathname !== '/events') {
      res.writeHead(404).end('Not found'); return;
    }
    if (clients.size >= 64) { res.writeHead(503).end('Connection limit'); return; }
    const raw = req.headers['last-event-id'];
    if (raw !== undefined && (typeof raw !== 'string' || !/^\d{1,16}$/.test(raw))) {
      res.writeHead(400).end('Invalid cursor'); return;
    }
    const cursor = raw === undefined ? null : Number(raw);
    if (cursor !== null && !Number.isSafeInteger(cursor)) {
      res.writeHead(400).end('Invalid cursor'); return;
    }
    res.writeHead(200, {
      'Content-Type': 'text/event-stream; charset=utf-8',
      'Cache-Control': 'no-cache, no-transform',
      'X-Accel-Buffering': 'no',
    });
    res.flushHeaders();
    const oldest = history[0]?.id ?? sequence + 1;
    if (cursor !== null && (cursor < oldest - 1 || cursor > sequence)) {
      res.end('event: reset\ndata: {"reason":"history-expired"}\n\n'); return;
    }
    if (!write(res, 'retry: 1000\n\n')) return;
    // No await between selecting replay and registering: one event-loop turn.
    const replay = cursor === null ? history.slice(-1) : history.filter(row => row.id > cursor);
    for (const row of replay) if (!write(res, encode(row))) return;
    clients.add(res);
    const heartbeat = setInterval(() => write(res, ': heartbeat\n\n'), 15000);
    res.once('close', () => {
      clearInterval(heartbeat);
      clients.delete(res);
    });
  });
  return { server, publish, connectionCount: () => clients.size,
    close: () => { for (const res of clients) res.destroy(); server.close(); } };
}

if (process.argv[1] && import.meta.url === pathToFileURL(process.argv[1]).href) {
  const demo = createDemo();
  demo.server.listen(18085, '127.0.0.1');
  const producer = setInterval(() => demo.publish(20 + Math.random() * 5), 1000);
  for (const signal of ['SIGINT', 'SIGTERM']) process.once(signal, () => {
    clearInterval(producer);
    demo.close();
  });
}
```

The event ID advances once per publication, not per subscriber. Reconnecting with 42 replays retained records above 42 before live updates resume; a first connection receives the latest temperature, which suits this snapshot-like display — an audit-log consumer would need a different initial-history contract. If a cursor is older than retained history, or ahead of the sequence after a restart, the server emits `reset` instead of silently skipping history. Restarting this fixture loses its history and sequence; it is not a durable replay service.

### 4. Let EventSource Own Reconnection

```html
<!doctype html>
<html lang="en">
<meta charset="utf-8">
<title>SSE temperature stream</title>
<p id="status" role="status">Connecting</p>
<output id="temperature">No update yet</output>
<button id="stop" type="button">Stop updates</button>
<script>
  const status = document.querySelector('#status');
  const output = document.querySelector('#temperature');
  const source = new EventSource('/events');
  let lastApplied = 0;
  source.onopen = () => { status.textContent = 'Connected'; };
  source.addEventListener('temperature', event => {
    try {
      const record = JSON.parse(event.data);
      if (!Number.isSafeInteger(record.id) || record.id <= 0 ||
          !Number.isFinite(record.value) || String(record.id) !== event.lastEventId) {
        throw new Error('Invalid temperature event');
      }
      if (record.id <= lastApplied) return; // deduplicate within this display session
      output.textContent = `${record.value.toFixed(1)} °C`;
      lastApplied = record.id;
    } catch {
      source.close();
      status.textContent = 'Invalid update. Reload to recover.';
    }
  });
  source.addEventListener('reset', () => {
    source.close();
    status.textContent = 'History expired. Reload to obtain the latest state.';
  });
  source.onerror = () => {
    status.textContent = source.readyState === EventSource.CLOSED
      ? 'Stream closed' : 'Connection interrupted; reconnecting';
  };
  document.querySelector('#stop').onclick = () => {
    source.close();
    status.textContent = 'Stopped';
  };
  window.addEventListener('pagehide', () => source.close(), { once: true });
</script>
</html>
```

A network interruption changes status while the same EventSource reconnects — there is no second retry timer competing with it. Stop, reset and invalid-data paths close the source deliberately. The client applies a validated record before advancing its own display cursor. The browser's ID still is not an application acknowledgment; side-effecting consumers need a stronger processing contract.

### 5. Authorize, Bound and Release Production Streams

**Authenticate and authorize the stream.** This fixture binds to loopback with generated public readings; a production stream must authenticate the session and authorize the specific subscription before sending headers, and revalidate permission when policy requires it. Native EventSource cannot set arbitrary Authorization headers — same-origin secure cookie sessions can work with the appropriate session, CSRF and origin policy, while cross-origin credentials need deliberate CORS and cookie configuration. Never place a durable bearer token in a URL.

**Bound backpressure and proxies.** A successful Node `res.write()` means the local writable accepted the data, not that the browser applied it. This fixture disconnects a pressured consumer instead of growing an unbounded queue; replay is possible only within retention. Proxies and compression middleware may buffer data — test first-event and ongoing flush latency through the actual path. `X-Accel-Buffering` addresses one NGINX policy, not all CDNs. Cleanup follows the response's close event so each connection releases its heartbeat and registry entry; also bound total connections, payload sizes, retention and ingestion work.

**Choose latest-state or every-event semantics.** Temperature displays and gauges often recover with a current snapshot. Chat, billing changes and audit logs may require ordered replay, stable IDs, durable storage and deduplicated effects — Redis Pub/Sub alone retains nothing for disconnected consumers. Define initial-state, replay, gap and restart behavior; keep one connection and retry owner; release resources on teardown. There is no universal per-connection memory, message-rate or latency ratio between SSE and WebSockets — measure runtime, intermediaries, message size, fan-out and recovery load.

## Summary

SSE carries framed UTF-8 updates in a long-lived HTTP response. EventSource parses and reconnects; the application owns authorization, history, cursor validation and processing semantics. A useful implementation explains what a first connection sees, how interrupted clients recover, and how slow or closed connections release resources.

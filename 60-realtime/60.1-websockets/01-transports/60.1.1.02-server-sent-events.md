# Server-Sent Events (SSE)

## Definition

Server-Sent Events (SSE) is a standardized technology that lets a server push text updates over an HTTP response. It suits feeds, progress updates and notifications where the browser mainly receives data. The browser's `EventSource` interface parses events and can reconnect after an interrupted connection.

> **Textbook Definition:** Server-Sent Events defines a UTF-8 event stream carried in an HTTP response with media type `text/event-stream`. EventSource dispatches parsed events and manages reconnection; event IDs support an application-defined replay cursor.

A download-progress page should update when the server has new progress, instead of repeatedly asking whether anything changed. SSE keeps a response open for those updates. The browser can still send commands through ordinary HTTP requests; the SSE stream itself runs from server to client.

## First Principles

An HTTP response body can arrive incrementally. The receiver needs a framing rule to distinguish one update from the next. SSE supplies that rule using named text fields and a blank line between event blocks.

A dropped connection creates a second problem: which updates were missed? Reopening the connection restores a channel, but recovery requires a stable cursor and server-side history or a new snapshot. A transport cannot reconstruct events the application never retained.

## When updates mostly flow from server to client

SSE is useful when server updates and ordinary HTTP commands match the product. WebSockets offer a bidirectional text/binary channel when that is needed. Neither choice supplies durable delivery, authorization or a universal latency advantage. Compare message direction, payload, recovery and infrastructure constraints.

## How the bytes become events

```text
browser GET /events → server keeps HTTP response open
server writes UTF-8 fields + blank line → browser dispatches an event
connection ends → browser may reconnect with its last event ID
server validates cursor → replays retained updates or asks for a reset
```

These are separate steps. HTTP chunks and network packets are not SSE event boundaries. One event may span several reads; one read may contain several events.

```text
id: 42
event: progress
data: {"percent":75}

```

`event` selects the listener name; without it the default is `message`. `data` supplies text, which the application may parse as JSON. Multiple data lines join with newline characters. A blank line completes a block; a comment beginning with `:` does not dispatch application data. `retry` can specify reconnection delay in milliseconds. IDs are strings, not necessarily numbers; monotonic decimal IDs are this chapter's application convention.

On automatic reconnection, the same EventSource uses its remembered ID in `Last-Event-ID`. Closing it and constructing a new EventSource starts a new browser cursor. IDs do not acknowledge database storage, handler success or exactly-once effects. The application needs replay, deduplication and a retention-gap policy if those properties matter.

## Code Examples

### A complete bounded local replay server

Save this as `server.mjs` and the client below as `index.html` in one directory. Run `node server.mjs`, then open `http://127.0.0.1:18085`. Node.js supplies the HTTP server; no framework is required. The fixture publishes a temperature each second and retains the last 100 updates in memory.

```javascript
import { createServer } from 'node:http';
import { readFile } from 'node:fs/promises';
import { pathToFileURL } from 'node:url';

export function createDemo() {
  const history = [];
  const clients = new Set();
  let sequence = 0;
  function write(res, text) {
    if (res.destroyed || res.writableEnded) return false;
    if (!res.write(text)) {
      res.destroy(); // bounded slow-consumer policy: disconnect and resume later
      return false;
    }
    return true;
  }
  function encode(record) {
    return `id: ${record.id}\nevent: temperature\ndata: ${JSON.stringify(record)}\n\n`;
  }
  function publish(value) {
    if (!Number.isFinite(value)) throw new Error('Temperature must be finite');
    if (sequence === Number.MAX_SAFE_INTEGER) throw new Error('Sequence exhausted');
    const record = { id: ++sequence, value };
    history.push(record);
    if (history.length > 100) history.shift();
    for (const res of clients) write(res, encode(record));
    return record.id;
  }
  const server = createServer(async (req, res) => {
    const pathname = new URL(req.url, 'http://127.0.0.1').pathname;
    if (req.method === 'GET' && pathname === '/') {
      try {
        const html = await readFile(new URL('./index.html', import.meta.url));
        res.writeHead(200, { 'Content-Type': 'text/html; charset=utf-8' });
        res.end(html);
      } catch { res.writeHead(500).end('Client fixture unavailable'); }
      return;
    }
    if (req.method !== 'GET' || pathname !== '/events') {
      res.writeHead(404).end('Not found'); return;
    }
    if (clients.size >= 64) { res.writeHead(503).end('Connection limit'); return; }
    const raw = req.headers['last-event-id'];
    if (raw !== undefined && (typeof raw !== 'string' || !/^\d{1,16}$/.test(raw))) {
      res.writeHead(400).end('Invalid cursor'); return;
    }
    const cursor = raw === undefined ? null : Number(raw);
    if (cursor !== null && (!Number.isSafeInteger(cursor) || cursor > sequence)) {
      res.writeHead(400).end('Invalid cursor'); return;
    }
    res.writeHead(200, {
      'Content-Type': 'text/event-stream; charset=utf-8',
      'Cache-Control': 'no-cache, no-transform',
      'X-Accel-Buffering': 'no',
    });
    res.flushHeaders();
    const oldest = history[0]?.id ?? sequence + 1;
    if (cursor !== null && cursor < oldest - 1) {
      res.end('event: reset\ndata: {"reason":"history-expired"}\n\n'); return;
    }
    if (!write(res, 'retry: 1000\n\n')) return;
    // No await between selecting replay and registering: one event-loop turn.
    const replay = cursor === null ? history.slice(-1) : history.filter(row => row.id > cursor);
    for (const row of replay) if (!write(res, encode(row))) return;
    clients.add(res);
    const heartbeat = setInterval(() => write(res, ': heartbeat\n\n'), 15000);
    res.once('close', () => {
      clearInterval(heartbeat);
      clients.delete(res);
    });
  });
  return { server, publish, connectionCount: () => clients.size,
    close: () => { for (const res of clients) res.destroy(); server.close(); } };
}

if (process.argv[1] && import.meta.url === pathToFileURL(process.argv[1]).href) {
  const demo = createDemo();
  demo.server.listen(18085, '127.0.0.1');
  const producer = setInterval(() => demo.publish(20 + Math.random() * 5), 1000);
  for (const signal of ['SIGINT', 'SIGTERM']) process.once(signal, () => {
    clearInterval(producer);
    demo.close();
  });
}
```

The event ID advances once per publication, not once per subscriber. Reconnecting with 42 replays retained records greater than 42 before receiving live updates. A first connection receives the latest temperature, which is sufficient for this snapshot-like display; an audit-log consumer would need a different initial-history contract.

The replay-to-live handoff is synchronous in this single process. A distributed log or asynchronous history fetch needs a coordinated snapshot/cursor and subscription boundary so updates cannot fall through a gap. If 42 is older than the retained range, the server emits `reset` instead of silently skipping lost history. Restarting this fixture loses its history and sequence; it is not a durable replay service.

### Let EventSource own reconnection

```html
<!doctype html>
<html lang="en">
<meta charset="utf-8">
<title>SSE temperature stream</title>
<p id="status" role="status">Connecting</p>
<output id="temperature">No update yet</output>
<button id="stop" type="button">Stop updates</button>
<script>
  const status = document.querySelector('#status');
  const output = document.querySelector('#temperature');
  const source = new EventSource('/events');
  let lastApplied = 0;
  source.onopen = () => { status.textContent = 'Connected'; };
  source.addEventListener('temperature', event => {
    try {
      const record = JSON.parse(event.data);
      if (!Number.isSafeInteger(record.id) || record.id <= 0 ||
          !Number.isFinite(record.value) || String(record.id) !== event.lastEventId) {
        throw new Error('Invalid temperature event');
      }
      if (record.id <= lastApplied) return; // deduplicate within this display session
      output.textContent = `${record.value.toFixed(1)} °C`;
      lastApplied = record.id;
    } catch {
      source.close();
      status.textContent = 'Invalid update. Reload to recover.';
    }
  });
  source.addEventListener('reset', () => {
    source.close();
    status.textContent = 'History expired. Reload to obtain the latest state.';
  });
  source.onerror = () => {
    status.textContent = source.readyState === EventSource.CLOSED
      ? 'Stream closed' : 'Connection interrupted; reconnecting';
  };
  document.querySelector('#stop').onclick = () => {
    source.close();
    status.textContent = 'Stopped';
  };
  window.addEventListener('pagehide', () => source.close(), { once: true });
</script>
</html>
```

A network interruption changes status; the same EventSource reconnects. There is no second retry timer competing with it. Stop/reset/invalid-data paths close the source deliberately. The client applies a validated record before advancing its own display cursor. The browser's ID still is not an application acknowledgment; side-effecting consumers need a stronger processing contract.

## Real-World Decisions

### Authentication and stream authorization

This fixture binds to loopback and exposes generated public readings. A production stream must authenticate the session and authorize the specific user's/tenant's subscription before sending headers. Revalidate permission when the application's policy requires it; a long-lived connection must not retain access indefinitely after revocation.

Native EventSource cannot set arbitrary Authorization headers. Same-origin secure cookie sessions can work with the appropriate session/CSRF/origin policy; cross-origin credentials require deliberate CORS and cookie configuration. Do not place a durable bearer token in a URL where logs and history may expose it. If custom headers are required, choose a supported fetch-stream client and implement its parser/reconnection lifecycle explicitly.

### Backpressure, proxy buffering and cleanup

A successful Node `res.write()` means the local writable accepted the data, not that the browser applied it. A false return signals buffered pressure. This fixture disconnects that consumer instead of growing an unbounded application queue; replay is possible only within retention. Alternatives include waiting for drain with a deadline or coalescing replaceable state. Preserve every event only when storage and recovery support it.

Heartbeat comments help keep a configured idle path active but do not prove client liveness or guarantee every intermediary's timeout behavior. Proxies and compression middleware may buffer data; test first-event and ongoing flush latency through the actual path. `X-Accel-Buffering` addresses a particular NGINX policy, not all CDNs. Avoid forcing HTTP/1.1-only connection headers onto HTTP/2 responses.

Cleanup follows the response's close event so every connection releases its own heartbeat and registry entry. Also bound total connections, payload sizes, retention and ingestion work. Browser connection limits can affect many tabs on HTTP/1.1; HTTP/2 multiplexing helps but does not remove server capacity limits.

### Choose latest-state or every-event semantics

Temperature displays and dashboard gauges can often recover with a current snapshot. Chat, billing changes and audit logs may require ordered replay, stable IDs, durable storage and deduplicated application effects. Redis Pub/Sub alone does not retain missed events for disconnected consumers. Choose retention and cursor ownership before treating automatic reconnection as reliable delivery.

There is no universal per-connection memory, message-rate or latency ratio between SSE and WebSockets. Measure the runtime, intermediaries, message size, fan-out and recovery load. Separate connected-client counts from active subscribers and successfully applied updates.

## Bound replay state and release each stream

Define initial-state, replay, gap and restart behavior. Keep one connection/retry owner and release its resources on teardown. Bound fan-out, queues and payloads. Test actual EventSource reconnection, malformed input, duplicate updates, cursor expiry and cleanup through the intended proxy path. Use production measurements rather than generic protocol throughput numbers.

## Summary

SSE carries framed UTF-8 updates in a long-lived HTTP response. EventSource parses and reconnects; the application owns authorization, history, cursor validation and processing semantics. A useful implementation explains what a first connection sees, how interrupted clients recover and how slow or closed connections release resources.

# Socket.IO

## Definition

Socket.IO is a **real-time, event-driven JavaScript library** for two-way communication between clients and servers. Its Engine.IO layer supports configured transports such as HTTP long-polling and WebSocket. Transport selection and upgrade behavior depend on configuration and network support; no fallback guarantees connectivity in every environment.

> **Textbook Definition:** Socket.IO is an event-oriented communication protocol and client/server library layered over Engine.IO transports, providing connection management, acknowledgments, namespaces and rooms. It is not wire-compatible with plain WebSocket.

Imagine a chat page that must receive messages, show who is typing and recover after a Wi-Fi interruption. Socket.IO supplies event routing and connection management. The application still decides who may enter the chat, where messages are stored and how missed updates are recovered.

## First Principles

A network connection can disappear while a user remains signed in. Consequently, a connection ID cannot be the user's durable identity. A command can commit before its response is lost, so reconnecting cannot tell us whether repeating that command is safe. A server may have many connected clients, so broadcasting requires an explicit audience rather than assuming every client may read the same data.

These constraints lead to separate responsibilities: the library manages the live channel; the application authenticates users, authorizes events, records durable results and reconciles interrupted work.

## Why Use It?

Use Socket.IO when an event API, room broadcasts and reconnection management save substantial application work. Choose plain WebSocket when protocol interoperability or a small custom protocol matters more. Choose SSE for a primarily server-to-browser feed; ordinary HTTP can handle commands.

Raw WebSocket supports binary messages. Socket.IO adds convenient serialization and event framing; binary capability itself is not unique to Socket.IO. Neither choice provides durable business delivery automatically.

## How the Pieces Fit Together

```text
application event: emit("chat:send", command, acknowledgment)
                    ↓
Socket.IO namespace and event framing
                    ↓
Engine.IO session, heartbeat and selected transport
                    ↓
HTTP long-polling or WebSocket connection
```

With the normal polling-first configuration, an HTTP handshake creates an Engine.IO session. Further polling requests carry events while the client probes a WebSocket upgrade. A WebSocket-only configuration removes polling but loses that alternative. A custom transport order needs deliberate fallback settings; a failed first transport does not imply every configured alternative will be attempted.

A **namespace**, such as `/chat`, separates event handlers and middleware. Several namespaces may share one underlying connection through a client Manager. A **room** is a server-maintained set of sockets inside a namespace, such as `team:42`. Clients request access; the server decides whether to join them. A room name is an address, not an authorization rule.

| Emission inside one namespace | Audience |
| -------------------------------------- | --------------------------------------------------- |
| `socket.emit("event", data)` | This socket |
| `socket.broadcast.emit("event", data)` | Every other socket in the namespace |
| `io.to(room).emit("event", data)` | Members of the room, including the sender if joined |
| `socket.to(room).emit("event", data)` | Members of the room except the sender |

`socket.broadcast` does **not** mean “all rooms this sender belongs to.” Broadcast permissions must be established before emitting. An adapter routes room events across server nodes; it does not persist chat history or grant access.

## Example: One Authorized Chat Room

This local Node.js fixture demonstrates a complete event path. Install Socket.IO 4.x and its client in a disposable project. Save the following as `server.mjs` and run `node server.mjs`. The server can be exercised with `socket.io-client` from Node.js. The browser snippet below shows integration into a same-origin application page; this server fixture does not serve that page.

The hard-coded tokens are disposable fixtures, not a production authentication design. The server listens only on loopback. Production requires TLS, a real session verifier, revocation/expiry handling and a durable store. The in-memory messages and duplicate-command records disappear when this process restarts.

### Server: validate, authorize, record, then acknowledge

```javascript
import { createServer } from 'node:http';
import { Server } from 'socket.io';

const httpServer = createServer();
const io = new Server(httpServer, { maxHttpBufferSize: 16 * 1024 });
const sessions = new Map([
  ['alice-demo-token', { userId: 'alice', rooms: new Set(['team:42']) }],
  ['bob-demo-token', { userId: 'bob', rooms: new Set(['team:42']) }],
  ['eve-demo-token', { userId: 'eve', rooms: new Set() }],
]);
const messages = [];
const commands = new Map();
const rate = new Map();
const MAX_MESSAGES = 100;
const MAX_COMMANDS = 200;

io.use((socket, next) => {
  const user = sessions.get(socket.handshake.auth.token);
  if (!user) return next(new Error('Authentication required'));
  socket.data.user = user;
  next();
});

io.on('connection', (socket) => {
  const user = socket.data.user;
  const allowed = (room) => typeof room === 'string' && user.rooms.has(room);
  socket.on('room:join', async (room, ack) => {
    if (typeof ack !== 'function') return;
    if (!allowed(room)) return ack({ ok: false, error: 'Forbidden room' });
    try {
      await socket.join(room);
      ack({ ok: true, messages: messages.filter((m) => m.room === room) });
    } catch {
      ack({ ok: false, error: 'Room unavailable' });
    }
  });

  socket.on('chat:send', (data, ack) => {
    if (typeof ack !== 'function') return;
    const now = Date.now();
    let budget = rate.get(user.userId);
    if (!budget || now >= budget.resetAt) {
      budget = { count: 0, resetAt: now + 1000 };
      rate.set(user.userId, budget);
    }
    if (++budget.count > 20) return ack({ ok: false, error: 'Rate limit' });
    if (!data || typeof data !== 'object' ||
        typeof data.commandId !== 'string' ||
        !/^[a-zA-Z0-9-]{1,64}$/.test(data.commandId) ||
        typeof data.text !== 'string' || !data.text.trim() ||
        data.text.length > 1000) {
      return ack({ ok: false, error: 'Invalid command' });
    }
    if (!allowed(data.room) || !socket.rooms.has(data.room)) {
      return ack({ ok: false, error: 'Join an authorized room first' });
    }
    const key = `${user.userId}:${data.commandId}`;
    const previous = commands.get(key);
    if (previous) {
      if (previous.room !== data.room || previous.text !== data.text) {
        return ack({ ok: false, error: 'Command identity reused' });
      }
      return ack({ ok: true, message: previous });
    }
    if (messages.length >= MAX_MESSAGES || commands.size >= MAX_COMMANDS) {
      return ack({ ok: false, error: 'Demo store full' });
    }
    // No await between duplicate check and write: atomic only in this process.
    const message = {
      id: messages.length + 1, room: data.room,
      userId: user.userId, text: data.text,
    };
    messages.push(message);
    commands.set(key, message);
    io.to(data.room).emit('chat:message', message);
    ack({ ok: true, message });
  });

});

httpServer.listen(3000, '127.0.0.1');
process.on('SIGTERM', () => {
  const deadline = setTimeout(() => process.exit(1), 5000);
  io.close(() => { clearTimeout(deadline); });
});
```

The server derives `userId` from the verified session rather than accepting a sender field. Alice can join `team:42`; Eve cannot. Alice must join before sending. Retrying the same command ID and content returns the earlier message without creating another. Reusing that ID for different content fails. The rate limit checks each command against an account budget, so reconnecting does not reset it in this fixture.

The fixed session map bounds this demo's account cardinality. A real limiter needs expiry and bounded storage, and a shared account budget across nodes. Durable duplicate-effect protection needs a database uniqueness constraint and transaction that stores both the result and operation identity. Do not transplant this process-local check into a distributed write path.

### Client: distinguish a response from an uncertain result

For a same-origin page on this local server, load `/socket.io/socket.io.js`, then run:

```javascript
const socket = io({
  auth: { token: 'alice-demo-token' },
  autoConnect: false,
  reconnectionAttempts: 5,
  reconnectionDelay: 1000,
  reconnectionDelayMax: 5000,
});
const room = 'team:42';
const seen = new Set();
let joined = false;

function apply(message) {
  if (seen.has(message.id)) return;
  seen.add(message.id);
  // Render with textContent, not unsanitized innerHTML.
  console.log(message.userId, message.text);
}

// Register once, outside connect, to avoid duplicate handlers after reconnect.
socket.on('chat:message', apply);
socket.on('connect', async () => {
  joined = false;
  try {
    const response = await socket.timeout(2000).emitWithAck('room:join', room);
    if (!response.ok) throw new Error(response.error);
    response.messages.forEach(apply);
    joined = true;
  } catch (error) {
    console.error('Room unavailable:', error.message);
  }
});
socket.on('disconnect', () => { joined = false; });
socket.on('connect_error', (error) => console.error(error.message));
socket.io.on('reconnect_attempt', (attempt) => console.log('Retry', attempt));
socket.io.on('reconnect_failed', () => console.error('Reconnect exhausted'));
socket.connect();

async function send(command) {
  if (!socket.connected || !joined) throw new Error('Chat is not ready');
  try {
    const response = await socket.timeout(2000).emitWithAck('chat:send', command);
    if (!response.ok) throw new Error(response.error);
    apply(response.message);
    return response.message;
  } catch (error) {
    // Keep this command ID for reconciliation or retry; do not create a new one.
    console.error('Send failed or outcome uncertain:', error.message);
    throw error;
  }
}

// Create once for one user action. Reuse this object if its result is uncertain.
const command = { commandId: crypto.randomUUID(), room, text: 'Hello' };
// After room:join succeeds: await send(command);
```

Socket-level `connect` runs for initial connection and reconnection. Manager events such as `reconnect_attempt` belong on `socket.io`. A rejected authentication handshake does not become successful through automatic transport retries. Refresh the session deliberately; never blindly reconnect after a server disconnect intended to revoke access.

### Trace a lost acknowledgment

1. Alice sends command `c1`. The server records message 1 and broadcasts it.
2. The connection closes before Alice receives the acknowledgment. A timeout leaves the result **uncertain**, not necessarily rejected.
3. Alice reconnects and rejoins. The demo returns its retained room snapshot; the client ignores IDs it already applied.
4. Alice retries `c1` with the same content. The server returns message 1. No second write or broadcast occurs.

This handles repeated commands while this process retains its records. It is not restart-safe delivery. A durable system needs retention rules, authorized replay or snapshot retrieval, and an explicit response when a resume cursor is too old. Socket.IO preserves event ordering, but default delivery is at most once. Client retry settings can repeat commands; they cannot make a database effect execute exactly once.

## Real-World Decisions

| Workload | Required application mechanism |
| ---------------------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| Chat or notifications | Persist important messages; recover with authorized history or a snapshot/cursor |
| Typing or cursor position | Coalesce and expire old state; volatile events may be dropped |
| Collaborative document edits | Define revisions and conflict resolution through an OT or CRDT algorithm; Socket.IO merely transports operations |
| Auction bids | Use server time, authorization and an atomic stored price/version check; an in-memory timer does not settle a multi-node auction |
| Game state | Server-authoritative actions, bounded update rate and sequence numbers; choose snapshots versus deltas deliberately |

**Operational transformation (OT)** transforms concurrent editing operations against one another. A **conflict-free replicated data type (CRDT)** encodes merge rules so replicas can converge. Neither algorithm appears automatically when an event is called `operation`.

For multiple Socket.IO servers, HTTP polling needs session affinity: successive requests must reach the node that owns the Engine.IO session. A WebSocket-only live connection stays on its selected backend. Both configurations still need a compatible adapter to broadcast across nodes. The ordinary Redis Pub/Sub adapter forwards live events and cannot supply durable replay; check connection-state recovery support for the selected adapter rather than assuming every adapter supports it.

## Common Mistakes

- **Trusting handshake fields as identity.** An `auth.userId` or query parameter is client input. Verify a credential and derive the user; reauthorize protected commands and address session expiry.
- **Calling an acknowledgment “delivered.”** Define whether it means validated, recorded, committed or applied. Timeout may follow a successful write.
- **Letting clients name any room.** Check membership policy for join and send; namespace middleware applies to that namespace, not automatically every other namespace.
- **Queueing indefinitely while offline.** Socket.IO can buffer client events. Add a product policy for queue length, expiry, cancellation and duplicate identities; use volatile events only for disposable state.
- **Marking a user offline when one tab closes.** Presence must account for other live connections and stale sessions. Socket.IO leaves its rooms automatically on disconnect; application timers and external subscriptions still require cleanup.
- **Treating CORS as authentication.** Browser CORS applies to HTTP polling. Protect WebSocket handshakes with an appropriate origin policy as well, and authenticate independently. Non-browser clients can choose their Origin header.
- **Escaping every string before storage.** Validate input shape and size, then encode at the output context. HTML escaping is not SQL protection, authorization or safe rendering in every context.

## Best Practices

Set maximum payload and command sizes, per-account event budgets and finite acknowledgment deadlines. Monitor connection failures, current transport, event latency, acknowledgment timeouts and rejected commands. Avoid user IDs and arbitrary event names as unbounded metric labels. Engine.IO transport closure is observed with its `close` event; it is not the Socket.IO namespace's `disconnect` event.

Choose overload behavior before traffic arrives: drop obsolete presence, coalesce snapshots, or disconnect slow consumers who can resynchronize. A volatile event is not a durable queue. During shutdown, stop new work, finish or safely reject accepted writes, close connections and enforce a deadline; `io.close()` alone does not drain your database work.

## Summary

Socket.IO supplies a useful live event channel with rooms, namespaces, acknowledgments and reconnection. Keep business identity, permissions, durable results and recovery explicit. Trace a lost acknowledgment and a missed server event before choosing retry or replay behavior.

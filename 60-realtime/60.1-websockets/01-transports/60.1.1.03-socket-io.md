# Socket.IO

A chat page must receive messages, show who is typing, and recover after a Wi-Fi interruption. Socket.IO supplies event routing and connection management — while the application still decides who may enter the chat, where messages are stored, and how missed updates are recovered.

```javascript
// One user action, one reusable identity: retry THIS object if the result is uncertain.
const command = { commandId: crypto.randomUUID(), room, text: 'Hello' };
const response = await socket.timeout(2000).emitWithAck('chat:send', command);
```

## Definition

**Socket.IO** is a real-time, event-driven JavaScript library for two-way client/server communication. Its **Engine.IO** layer supports configured transports such as HTTP long-polling and WebSocket. Transport selection and upgrade behavior depend on configuration and network support.

> **Textbook Definition:** Socket.IO is an event-oriented communication protocol and client/server library layered over Engine.IO transports, providing connection management, acknowledgments, namespaces and rooms. It is not wire-compatible with plain WebSocket.

## First Principles

A network connection can disappear while a user remains signed in — so a connection ID cannot be the user's durable identity. A command can commit before its response is lost, so reconnecting cannot tell us whether repeating that command is safe. A server may hold many connected clients, so broadcasting requires an explicit audience rather than assuming every client may read the same data. The library therefore manages the live channel while the application authenticates users, authorizes events, records durable results and reconciles interrupted work.

## How It Works

### 1. Match the Event API to the Work It Saves

Use Socket.IO when an event API, room broadcasts and reconnection management save substantial application work. Choose plain WebSocket when protocol interoperability or a small custom protocol matters more; choose SSE for a primarily server-to-browser feed, with ordinary HTTP handling commands. Raw WebSocket supports binary messages, and Socket.IO adds convenient serialization and event framing — but neither choice provides durable business delivery automatically.

### 2. Fit Namespaces, Rooms and Transports Together

```text
application event: emit("chat:send", command, acknowledgment)
                    ↓
Socket.IO namespace and event framing
                    ↓
Engine.IO session, heartbeat and selected transport
                    ↓
HTTP long-polling or WebSocket connection
```

With the normal polling-first configuration, an HTTP handshake creates an Engine.IO session; further polling requests carry events while the client probes a WebSocket upgrade. A WebSocket-only configuration removes polling but loses that alternative. A **namespace** such as `/chat` separates event handlers and middleware, with several namespaces sharing one underlying connection through a client Manager. A **room** is a server-maintained set of sockets inside a namespace, such as `team:42` — clients request access, the server decides whether to join them. A room name is an address, not an authorization rule.

| Emission inside one namespace | Audience |
| -------------------------------------- | --------------------------------------------------- |
| `socket.emit("event", data)` | This socket |
| `socket.broadcast.emit("event", data)` | Every other socket in the namespace |
| `io.to(room).emit("event", data)` | Members of the room, including the sender if joined |
| `socket.to(room).emit("event", data)` | Members of the room except the sender |

`socket.broadcast` does **not** mean "all rooms this sender belongs to." Broadcast permissions must be established before emitting. An adapter routes room events across server nodes; it does not persist chat history or grant access.

### 3. Validate, Authorize, Record, Then Acknowledge on the Server

This local Node.js fixture demonstrates a complete event path. Use the Socket.IO client 4.6 or later with a compatible 4.x server — the client example calls `emitWithAck`, added in 4.6. Save as `server.mjs` and run `node server.mjs`. The hard-coded tokens are disposable fixtures, not a production authentication design; the server listens only on loopback. The in-memory messages and duplicate-command records disappear when this process restarts.

```javascript
import { createServer } from 'node:http';
import { Server } from 'socket.io';

const httpServer = createServer();
const io = new Server(httpServer, { maxHttpBufferSize: 16 * 1024 });
const sessions = new Map([
  ['alice-demo-token', { userId: 'alice', rooms: new Set(['team:42']) }],
  ['bob-demo-token', { userId: 'bob', rooms: new Set(['team:42']) }],
  ['eve-demo-token', { userId: 'eve', rooms: new Set() }],
]);
const messages = [];
const commands = new Map();
const rate = new Map();
const MAX_MESSAGES = 100;
const MAX_COMMANDS = 200;

io.use((socket, next) => {
  const user = sessions.get(socket.handshake.auth.token);
  if (!user) return next(new Error('Authentication required'));
  socket.data.user = user;
  next();
});

io.on('connection', (socket) => {
  const user = socket.data.user;
  const allowed = (room) => typeof room === 'string' && user.rooms.has(room);
  socket.on('room:join', async (room, ack) => {
    if (typeof ack !== 'function') return;
    if (!allowed(room)) return ack({ ok: false, error: 'Forbidden room' });
    try {
      await socket.join(room);
      ack({ ok: true, messages: messages.filter((m) => m.room === room) });
    } catch {
      ack({ ok: false, error: 'Room unavailable' });
    }
  });

  socket.on('chat:send', (data, ack) => {
    if (typeof ack !== 'function') return;
    const now = Date.now();
    let budget = rate.get(user.userId);
    if (!budget || now >= budget.resetAt) {
      budget = { count: 0, resetAt: now + 1000 };
      rate.set(user.userId, budget);
    }
    if (++budget.count > 20) return ack({ ok: false, error: 'Rate limit' });
    if (!data || typeof data !== 'object' ||
        typeof data.commandId !== 'string' ||
        !/^[a-zA-Z0-9-]{1,64}$/.test(data.commandId) ||
        typeof data.text !== 'string' || !data.text.trim() ||
        data.text.length > 1000) {
      return ack({ ok: false, error: 'Invalid command' });
    }
    if (!allowed(data.room) || !socket.rooms.has(data.room)) {
      return ack({ ok: false, error: 'Join an authorized room first' });
    }
    const key = `${user.userId}:${data.commandId}`;
    const previous = commands.get(key);
    if (previous) {
      if (previous.room !== data.room || previous.text !== data.text) {
        return ack({ ok: false, error: 'Command identity reused' });
      }
      return ack({ ok: true, message: previous });
    }
    if (messages.length >= MAX_MESSAGES || commands.size >= MAX_COMMANDS) {
      return ack({ ok: false, error: 'Demo store full' });
    }
    // No await between duplicate check and write: atomic only in this process.
    const message = {
      id: messages.length + 1, room: data.room,
      userId: user.userId, text: data.text,
    };
    messages.push(message);
    commands.set(key, message);
    io.to(data.room).emit('chat:message', message);
    ack({ ok: true, message });
  });

});

httpServer.listen(3000, '127.0.0.1');
process.on('SIGTERM', () => {
  const deadline = setTimeout(() => process.exit(1), 5000);
  io.close(() => { clearTimeout(deadline); });
});
```

The server derives `userId` from the verified session rather than accepting a sender field. Alice can join `team:42`; Eve cannot, and Alice must join before sending. Retrying the same command ID with the same content returns the earlier message without another write; reusing that ID for different content fails. A real limiter needs expiry, bounded storage and a shared account budget across nodes — and durable duplicate-effect protection needs a database uniqueness constraint with a transaction storing both result and operation identity.

### 4. Distinguish a Response From an Uncertain Result on the Client

For a same-origin page on this local server, load `/socket.io/socket.io.js`, then run:

```javascript
const socket = io({
  auth: { token: 'alice-demo-token' },
  autoConnect: false,
  reconnectionAttempts: 5,
  reconnectionDelay: 1000,
  reconnectionDelayMax: 5000,
});
const room = 'team:42';
const seen = new Set();
let joined = false;
let connectionGeneration = 0;

function apply(message) {
  if (seen.has(message.id)) return;
  seen.add(message.id);
  // Render with textContent, not unsanitized innerHTML.
  console.log(message.userId, message.text);
}

// Register once, outside connect, to avoid duplicate handlers after reconnect.
socket.on('chat:message', apply);
socket.on('connect', async () => {
  const generation = ++connectionGeneration;
  joined = false;
  try {
    const response = await socket.timeout(2000).emitWithAck('room:join', room);
    if (generation !== connectionGeneration || !socket.connected) return;
    if (!response.ok) throw new Error(response.error);
    response.messages.forEach(apply);
    joined = true;
  } catch (error) {
    if (generation !== connectionGeneration) return;
    console.error('Room unavailable:', error.message);
  }
});
socket.on('disconnect', () => {
  ++connectionGeneration; // invalidate any join response from the previous channel
  joined = false;
});
socket.on('connect_error', (error) => console.error(error.message));
socket.io.on('reconnect_attempt', (attempt) => console.log('Retry', attempt));
socket.io.on('reconnect_failed', () => console.error('Reconnect exhausted'));
socket.connect();

async function send(command) {
  if (!socket.connected || !joined) throw new Error('Chat is not ready');
  try {
    const response = await socket.timeout(2000).emitWithAck('chat:send', command);
    if (!response.ok) throw new Error(response.error);
    apply(response.message);
    return response.message;
  } catch (error) {
    // Keep this command ID for reconciliation or retry; do not create a new one.
    console.error('Send failed or outcome uncertain:', error.message);
    throw error;
  }
}

// Create once for one user action. Reuse this object if its result is uncertain.
const command = { commandId: crypto.randomUUID(), room, text: 'Hello' };
// After room:join succeeds: await send(command);
```

The generation check stops an earlier asynchronous join response from marking a replacement connection ready. Manager events such as `reconnect_attempt` belong on `socket.io`. A rejected authentication handshake does not become successful through automatic transport retries — refresh the session deliberately, and never blindly reconnect after a server disconnect intended to revoke access.

### 5. Trace a Lost Acknowledgment

1. Alice sends command `c1`. The server records message 1 and broadcasts it.
2. The connection closes before Alice receives the acknowledgment. A timeout leaves the result **uncertain**, not necessarily rejected.
3. Alice reconnects and rejoins. The demo returns its retained room snapshot; the client ignores IDs it already applied.
4. Alice retries `c1` with the same content. The server returns message 1. No second write or broadcast occurs.

This handles repeated commands while this process retains its records — it is not restart-safe delivery. A durable system needs retention rules, authorized replay or snapshot retrieval, and an explicit response when a resume cursor is too old. Socket.IO preserves event ordering, but default delivery is at most once: client retry settings can repeat commands but cannot make a database effect execute exactly once.

### 6. Set Workload Semantics, Limits and Multi-Node Behavior

| Workload | Required application mechanism |
| ---------------------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| Chat or notifications | Persist important messages; recover with authorized history or a snapshot/cursor |
| Typing or cursor position | Coalesce and expire old state; volatile events may be dropped |
| Collaborative document edits | Define revisions and conflict resolution through an OT or CRDT algorithm; Socket.IO merely transports operations |
| Auction bids | Use server time, authorization and an atomic stored price/version check; an in-memory timer does not settle a multi-node auction |
| Game state | Server-authoritative actions, bounded update rate and sequence numbers; choose snapshots versus deltas deliberately |

**Operational transformation (OT)** transforms concurrent editing operations against one another. A **conflict-free replicated data type (CRDT)** encodes merge rules so replicas converge. Neither algorithm appears automatically when an event is called `operation`. For multiple Socket.IO servers, HTTP polling needs session affinity — successive requests must reach the node owning the Engine.IO session — while a WebSocket-only live connection stays on its selected backend. Both configurations still need a compatible adapter to broadcast across nodes, and the ordinary Redis Pub/Sub adapter forwards live events without durable replay.

Set maximum payload and command sizes, per-account event budgets and finite acknowledgment deadlines. Monitor connection failures, current transport, event latency, acknowledgment timeouts and rejected commands; avoid user IDs and arbitrary event names as unbounded metric labels. Choose overload behavior before traffic arrives: drop obsolete presence, coalesce snapshots, or disconnect slow consumers who can resynchronize. During shutdown, stop new work, finish or safely reject accepted writes, close connections and enforce a deadline — `io.close()` alone does not drain database work.

## Summary

Socket.IO supplies a useful live event channel with rooms, namespaces, acknowledgments and reconnection. Keep business identity, permissions, durable results and recovery explicit. Trace a lost acknowledgment and a missed server event before choosing retry or replay behavior.

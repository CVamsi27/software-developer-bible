# WebTransport

## Definition

**WebTransport** is a browser API for bidirectional client/server communication using multiple streams and datagrams within a session. Its HTTP/3 binding uses QUIC, a secure transport built over UDP. Choose streams when bytes must arrive in order within that stream, and datagrams when losing an update is acceptable.

> **Textbook Definition:** WebTransport exposes client-server sessions with multiple streams and datagrams, allowing applications to select reliable ordered byte streams or unreliable messages within a supported secure transport.

The browser API and wire protocol are separate specifications. As checked in October 2026, the [W3C API document](https://w3c.github.io/webtransport/) is an editor’s draft and the [HTTP/3 binding](https://datatracker.ietf.org/doc/html/draft-ietf-webtrans-http3) is an Internet-Draft. Do not label RFC 9298 as WebTransport: it specifies proxying UDP in HTTP.

## First Principles

A multiplayer game has two different requirements. A chat message should arrive intact; an old player position may be useless after a newer position arrives. Sending both through one reliable ordered channel can make fresh position information wait for retransmission of old data.

The application therefore needs separate delivery choices. Independent reliable streams separate ordered byte sequences. Datagrams carry individual messages without promising delivery or order. The receiver still needs a rule for stale updates, and important events still need an application-level result.

## Use streams and datagrams for distinct delivery needs

Use WebTransport when independent streams or unreliable messages solve a measured problem. It does not make bandwidth unlimited or remove every source of latency. Streams share connection-level congestion and resource limits; a congested connection can affect several streams even though loss recovery does not impose one shared ordered byte sequence. [QUIC’s transport specification](https://www.rfc-editor.org/rfc/rfc9000.html) defines these boundaries.

For ordinary chat, [WebSockets](60.1.1.01-websockets-overview.md) may already satisfy the requirement. For server-to-browser updates with ordinary HTTP requests in the other direction, [Server-Sent Events](60.1.1.02-server-sent-events.md) can be simpler. WebTransport adds server and network deployment requirements worth accepting only for a useful capability.

## How a Session Connects the Parts

For HTTP/3, the browser establishes a secure QUIC connection and requests a WebTransport session through extended CONNECT. The server checks the requested resource, allowed browser origin, and application credentials before accepting it. `transport.ready` fulfills when the session becomes usable.

```text
browser API → secure QUIC + HTTP/3 → WebTransport-capable endpoint
                                           ↓ accepts session
                          streams and datagrams → application handlers
```

A normal HTTPS endpoint that supports HTTP/3 does not automatically accept WebTransport. Its server implementation, proxy/load balancer, certificate, and UDP network path must support the required protocol. The HTTP/3 draft also disallows initiating a WebTransport session in 0-RTT packets; QUIC resumption is not a promise of zero-round-trip application readiness. See the [session establishment section](https://datatracker.ietf.org/doc/html/draft-ietf-webtrans-http3#section-3.2).

### Streams are byte sequences, not messages

A **bidirectional stream** has a readable side and a writable side. Either participant can send bytes on its side. A **unidirectional stream** sends in one direction; the receiver reads it. These streams are reliable and ordered within each stream, with no automatic ordering between separate streams.

If a sender writes `hello` followed by `world`, the receiver can read one chunk, two chunks, or several chunks. A read is not one message. Define framing—such as a bounded length prefix or newline-delimited JSON—and keep incomplete bytes until a full message is available. Incremental text decoding must also handle a Unicode character split across chunks.

Closing the writable side completes that sender’s byte sequence. It does not mean the other side has processed it or that the session has closed. An application acknowledgment should identify the operation and its durable result when that matters. [The bidirectional-stream API](https://developer.mozilla.org/en-US/docs/Web/API/WebTransport/createBidirectionalStream) exposes the two sides.

### Datagrams preserve message boundaries, with weaker delivery

A **datagram** is an individual message that may be dropped, duplicated, or observed out of order. It is useful for replaceable state: a full current position can supersede an earlier full position. A delta that depends on a missing previous update needs a recovery strategy.

Use the current `transport.datagrams.maxDatagramSize` after readiness rather than a hard-coded 1,200-byte application limit. Protocol overhead and negotiated/path constraints affect the usable size. A writable queue can also hold stale messages, so bound queued work and discard obsolete updates rather than accumulating every animation frame. `writer.ready` reflects stream backpressure; it is not a receiver acknowledgment or a direct promise that the congestion window is free. See [the datagram interface](https://developer.mozilla.org/en-US/docs/Web/API/WebTransportDatagramDuplexStream).

## Example: Ignore an Older Position

Assume one authenticated source sends full snapshots for one player during one session. Each snapshot has an increasing safe-integer sequence and finite coordinates. The application rule accepts newer snapshots and ignores older or repeated ones.

```javascript
function applyPosition(current, incoming) {
  if (!incoming || !Number.isSafeInteger(incoming.sequence) || incoming.sequence < 0 ||
      !Number.isFinite(incoming.x) || !Number.isFinite(incoming.y)) {
    throw new TypeError('Invalid position snapshot');
  }
  if (current && incoming.sequence <= current.sequence) return current;
  return { sequence: incoming.sequence, x: incoming.x, y: incoming.y };
}

let position = null;
position = applyPosition(position, { sequence: 2, x: 20, y: 5 });
position = applyPosition(position, { sequence: 1, x: 10, y: 5 });
console.log(position.sequence, position.x); // 2 20: delayed update ignored
position = applyPosition(position, { sequence: 4, x: 40, y: 5 });
console.log(position.sequence, position.x); // 4 40: missing update 3 not required
```

Datagrams do not supply that sequence or stale-update rule; the application does. This example avoids ordering across several players and sequence wraparound by restricting its contract to one player/session with safe integers. A reconnect needs a new session epoch or freshly scoped state so sequence 0 from the new session is not compared with sequence 4 from the old one.

The skipped update 3 is harmless only because update 4 is a full snapshot. If update 4 meant “move two units from update 3,” losing update 3 would corrupt the result. Use recovery snapshots, application retransmission, or a reliable stream for that protocol.

### Write reliable chat bytes on a separate stream

This browser helper requires an established WebTransport session and a server whose application protocol accepts **one newline-delimited chat record per stream**. It only writes the record; receiving acknowledgment is a separate step.

```javascript
async function writeChatRecord(transport, text) {
  if (typeof text !== 'string' || text.trim().length === 0) {
    throw new TypeError('Chat text must not be empty');
  }
  const bytes = new TextEncoder().encode(JSON.stringify({ text }) + '\n');
  if (bytes.byteLength > 4096) throw new RangeError('Chat record exceeds 4096 bytes');
  const stream = await transport.createBidirectionalStream();
  const writer = stream.writable.getWriter();
  try {
    await writer.write(bytes);
    await writer.close(); // Finish our sending half, not the whole session.
  } catch (error) {
    await writer.abort(error).catch(() => {});
    throw error;
  } finally {
    writer.releaseLock();
  }
  return stream.readable; // Caller owns acknowledgement parsing/cancellation.
}
```

The server must bound its parser buffer and reject malformed records. A complete client also needs deadlines, acknowledgment parsing, cancellation, and cleanup of the returned readable side. The helper is an API example, not an implemented Node.js server or tested end-to-end chat service.

## Own Session Closure and Recovery

`ready` and `closed` are promises, not repeating events. Network migration does not make `ready` fire again. Handle failed establishment and abnormal closure, stop producers, cancel owned readers/writers, and release locks. Register closure rejection handling promptly so an unexpected failure does not become an unhandled promise rejection.

`transport.close()` requests closure and returns synchronously; observe `transport.closed` for completion or failure. A React effect must also ignore completions from an obsolete session after its URL changes or the component unmounts. Follow [React effects and cleanup](../../../10-frontend/10.3-react/02-core-hooks/10.3.2.02-useeffect.md) for that lifecycle rather than attaching unguarded state updates to old promises. [The close API](https://developer.mozilla.org/en-US/docs/Web/API/WebTransport/close) describes session shutdown.

QUIC connection migration can preserve a connection across some network changes; it is not guaranteed continuity across server failure, unsupported paths, idle timeouts, or every device transition. When a session actually closes, establish a new session with bounded backoff and restore application state through a snapshot or cursor. Transport reliability does not provide durable replay by itself.

## Real-World Decisions

| Need | Delivery choice | Additional application responsibility |
| ------------------------------ | ------------------------------ | -------------------------------------------------------------- |
| Frequent replaceable positions | Datagrams | Sequence/epoch, stale discard, full-state recovery |
| Chat or important commands | Reliable streams | Framing, acknowledgement, authorization and duplicate handling |
| Independent large transfers | Separate streams | Bounded buffers, cancellation and shared-capacity budgets |
| Low-latency media | A purpose-built media protocol | Codec, timing, jitter handling and loss recovery |

Do not infer provider support from HTTP/3 support, a platform name, or a fictional adapter class. Choose a maintained server implementation, verify its protocol version against target browsers, and test the deployed endpoint. Node’s ordinary HTTP server does not become a QUIC WebTransport listener by adding an event handler.

As of this review, MDN marks the core interface Baseline 2026, newly available across current browser versions. Older devices and individual API features still need compatibility checks. Feature detection such as `'WebTransport' in globalThis` establishes API presence, not successful network reachability. Use a compatible WebSocket/SSE fallback where the product can accept its different semantics. A polyfill cannot reproduce unreliable UDP delivery over a reliable ordered WebSocket. [MDN lists the compatibility boundary](https://developer.mozilla.org/en-US/docs/Web/API/WebTransport).

## Verify the network and recovery path

Choose delivery from the data’s meaning. Bound messages, queues, parser buffers, and active streams. Authenticate the session and authorize each operation; an allowed origin does not identify a user. Exercise loss, reordering, blocked UDP, closure, reconnect, and stale-session callbacks. Benchmark the actual browser/server/network combination before changing transports.

## Summary

WebTransport separates reliable ordered byte streams from datagrams within a session. The application still owns framing, stale-update handling, acknowledgments, replay, and cleanup. Choose it for a concrete need, verify the complete deployment path, and qualify readiness, migration, compatibility, and performance claims against the actual environment.

# WebTransport

A multiplayer game has two requirements: a chat message must arrive intact, while an old player position is useless once a newer one arrives. Sending both through one reliable ordered channel makes fresh positions wait for retransmission of stale data.

```javascript
// Newer snapshots win; delayed duplicates are ignored.
position = applyPosition(position, { sequence: 2, x: 20, y: 5 });
position = applyPosition(position, { sequence: 1, x: 10, y: 5 });
console.log(position.sequence, position.x); // 2 20: delayed update ignored
```

## Definition

**WebTransport** is a browser API for bidirectional client/server communication using multiple **streams** and **datagrams** within a session. Its HTTP/3 binding uses QUIC, a secure transport built over UDP. Choose streams when bytes must arrive in order within that stream, and datagrams when losing an update is acceptable.

> **Textbook Definition:** WebTransport exposes client-server sessions with multiple streams and datagrams, allowing applications to select reliable ordered byte streams or unreliable messages within a supported secure transport.

## First Principles

The game needs separate delivery choices: independent reliable streams separate ordered byte sequences, while datagrams carry individual messages without promising delivery or order. The receiver still needs a rule for stale updates, and important events still need an application-level result. The browser API and wire protocol are separate specifications — as checked in October 2026, the [W3C API document](https://w3c.github.io/webtransport/) is an editor's draft and the [HTTP/3 binding](https://datatracker.ietf.org/doc/html/draft-ietf-webtrans-http3) is an Internet-Draft. Do not label RFC 9298 as WebTransport: it specifies proxying UDP in HTTP.

## How It Works

### 1. Use Streams and Datagrams for Distinct Delivery Needs

Use WebTransport when independent streams or unreliable messages solve a measured problem. Its preferred HTTP/3 mapping uses native QUIC streams and datagrams. A capsule-based variant can help intermediaries bridge HTTP/2 and HTTP/3, but it multiplexes streams over one HTTP/3 stream — reintroducing head-of-line blocking — and its datagrams are also retransmitted. Verify which mapping the deployed path uses before relying on those delivery properties. Even with native QUIC streams, the connection shares congestion control and resource limits, so congestion can affect several streams. [QUIC's transport specification](https://www.rfc-editor.org/rfc/rfc9000.html) defines the native stream boundary.

For ordinary chat, [WebSockets](60.1.1.01-websockets-overview.md) may already satisfy the requirement. For server-to-browser updates with ordinary HTTP requests in the other direction, [Server-Sent Events](60.1.1.02-server-sent-events.md) can be simpler. WebTransport adds server and network deployment requirements worth accepting only for a useful capability.

### 2. Connect the Parts in One Session

For HTTP/3, the browser establishes a secure QUIC connection and requests a WebTransport session through extended CONNECT. The server checks the requested resource, allowed browser origin, and application credentials before accepting it. `transport.ready` fulfills when the session becomes usable.

```text
browser API → secure QUIC + HTTP/3 → WebTransport-capable endpoint
                                           ↓ accepts session
                          streams and datagrams → application handlers
```

A normal HTTPS endpoint supporting HTTP/3 does not automatically accept WebTransport: its server implementation, proxy and load balancer, certificate, and UDP network path must all support the required protocol. The HTTP/3 draft also disallows initiating a WebTransport session in 0-RTT packets — QUIC resumption is not a promise of zero-round-trip application readiness. See the [session establishment section](https://datatracker.ietf.org/doc/html/draft-ietf-webtrans-http3#section-3.2).

### 3. Treat Streams as Byte Sequences, Not Messages

A **bidirectional stream** has a readable side and a writable side; either participant can send bytes on its side. A **unidirectional stream** sends in one direction. Streams are reliable and ordered within each stream, with no automatic ordering between separate streams. If a sender writes `hello` followed by `world`, the receiver can read one chunk, two chunks, or several — a read is not one message. Define framing, such as a bounded length prefix or newline-delimited JSON, keep incomplete bytes until a full message is available, and handle Unicode characters split across chunks when decoding incrementally.

```javascript
async function writeChatRecord(transport, text) {
  if (typeof text !== 'string' || text.trim().length === 0) {
    throw new TypeError('Chat text must not be empty');
  }
  const bytes = new TextEncoder().encode(JSON.stringify({ text }) + '\n');
  if (bytes.byteLength > 4096) throw new RangeError('Chat record exceeds 4096 bytes');
  const stream = await transport.createBidirectionalStream();
  const writer = stream.writable.getWriter();
  try {
    await writer.write(bytes);
    await writer.close(); // Finish our sending half, not the whole session.
  } catch (error) {
    await writer.abort(error).catch(() => {});
    throw error;
  } finally {
    writer.releaseLock();
  }
  return stream.readable; // Caller owns acknowledgement parsing/cancellation.
}
```

This browser helper requires an established session and a server accepting **one newline-delimited chat record per stream**; it only writes the record, with acknowledgment a separate step. The server must bound its parser buffer and reject malformed records. A complete client also needs deadlines, acknowledgment parsing, cancellation, and cleanup of the returned readable side. Closing the writable side completes that sender's byte sequence — not proof the other side processed it. [The bidirectional-stream API](https://developer.mozilla.org/en-US/docs/Web/API/WebTransport/createBidirectionalStream) exposes the two sides.

### 4. Treat Datagrams as Messages With Weaker Delivery

A **datagram** carries one WebTransport message, but QUIC does not retransmit it: datagrams can be lost and arrive out of order. An application retry may produce a duplicate, so give retried messages an identity when deduplication matters. Datagrams suit replaceable state — a full current position supersedes an earlier snapshot — while a delta depending on a missing update needs a recovery strategy.

```javascript
function applyPosition(current, incoming) {
  if (!incoming || !Number.isSafeInteger(incoming.sequence) || incoming.sequence < 0 ||
      !Number.isFinite(incoming.x) || !Number.isFinite(incoming.y)) {
    throw new TypeError('Invalid position snapshot');
  }
  if (current && incoming.sequence <= current.sequence) return current;
  return { sequence: incoming.sequence, x: incoming.x, y: incoming.y };
}
```

Datagrams do not supply that sequence or stale-update rule; the application does. This example restricts its contract to one player and session with safe integers, avoiding cross-player ordering and wraparound — a reconnect needs a new session epoch so sequence 0 from the new session is never compared with sequence 4 from the old one. The skipped update 3 is harmless only because update 4 is a full snapshot; if update 4 meant "move two units from update 3," losing update 3 would corrupt the result.

Use the current `transport.datagrams.maxDatagramSize` after readiness rather than a hard-coded 1,200-byte limit. A writable queue can hold stale messages, so bound queued work and discard obsolete updates. `writer.ready` reflects stream backpressure — not a receiver acknowledgment; even a QUIC acknowledgment reports transport handling, not successful application processing ([RFC 9221, Section 5.2](https://www.rfc-editor.org/rfc/rfc9221.html#section-5.2)). See [the datagram interface](https://developer.mozilla.org/en-US/docs/Web/API/WebTransportDatagramDuplexStream).

### 5. Own Session Closure and Recovery

`ready` and `closed` are promises, not repeating events — network migration does not make `ready` fire again. Handle failed establishment and abnormal closure, stop producers, cancel owned readers and writers, and release locks. Register closure rejection handling promptly so an unexpected failure does not become an unhandled promise rejection. `transport.close()` requests closure and returns synchronously; observe `transport.closed` for completion or failure. A React effect must also ignore completions from an obsolete session after its URL changes or the component unmounts — follow [React effects and cleanup](../../../10-frontend/10.3-react/02-core-hooks/10.3.2.02-useeffect.md) rather than attaching unguarded state updates to old promises. [The close API](https://developer.mozilla.org/en-US/docs/Web/API/WebTransport/close) describes session shutdown.

QUIC connection migration can preserve a connection across some network changes; it is not guaranteed continuity across server failure, unsupported paths, idle timeouts or every device transition. When a session actually closes, establish a new session with bounded backoff and restore application state through a snapshot or cursor. Transport reliability does not provide durable replay by itself.

### 6. Choose Delivery From Meaning and Verify the Recovery Path

| Need | Delivery choice | Additional application responsibility |
| ------------------------------ | ------------------------------ | -------------------------------------------------------------- |
| Frequent replaceable positions | Datagrams | Sequence/epoch, stale discard, full-state recovery |
| Chat or important commands | Reliable streams | Framing, acknowledgement, authorization and duplicate handling |
| Independent large transfers | Separate streams | Bounded buffers, cancellation and shared-capacity budgets |
| Low-latency media | A purpose-built media protocol | Codec, timing, jitter handling and loss recovery |

Never infer provider support from HTTP/3 support, a platform name, or a fictional adapter class. Choose a maintained server implementation, verify its protocol version against target browsers, and test the deployed endpoint — Node's ordinary HTTP server does not become a QUIC WebTransport listener by adding an event handler. As of this review, MDN marks the core interface Baseline 2026; older devices and individual API features still need compatibility checks, and feature detection such as `'WebTransport' in globalThis` establishes API presence rather than network reachability. Use a compatible WebSocket or SSE fallback where the product accepts its different semantics. [MDN lists the compatibility boundary](https://developer.mozilla.org/en-US/docs/Web/API/WebTransport).

Choose delivery from the data's meaning. Bound messages, queues, parser buffers and active streams. Authenticate the session and authorize each operation — an allowed origin does not identify a user. Exercise loss, reordering, blocked UDP, closure, reconnect and stale-session callbacks. Benchmark the actual browser, server and network combination before changing transports.

## Summary

WebTransport separates reliable ordered byte streams from datagrams within a session. The application still owns framing, stale-update handling, acknowledgments, replay and cleanup. Choose it for a concrete need, verify the complete deployment path, and qualify readiness, migration, compatibility and performance claims against the actual environment.

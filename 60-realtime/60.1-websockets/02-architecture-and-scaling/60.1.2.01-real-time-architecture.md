# Real-Time Architecture

Two receptionists share a booking screen. When one confirms an appointment, the other should see the change quickly. The hard question is not just how to send the update — it is how both screens reach the correct state if a server crashes between saving the booking and notifying them.

```text
authorized command → business service → database transaction
                                         ├─ current state
                                         └─ pending event (outbox)
                                                   ↓
                                             publication worker → broker → gateways
```

## Definition

**Real-time architecture** processes and delivers updates with low enough **latency** for the application's purpose. It combines **authoritative state**, event publication, connected clients and recovery after interruptions. Here "real time" means interactive applications such as chat and live dashboards — **hard real-time** systems carry deadlines whose violation invalidates the result, which an ordinary WebSocket application does not guarantee.

> **Textbook Definition:** A real-time architecture distributes updates within a defined latency objective while coordinating authoritative state, subscriptions and recovery. Low latency alone does not establish consistency or complete event delivery.

## First Principles

A database commit and a network send are separate actions: a crash can occur between them, a browser can be disconnected while valid changes continue, multiple gateways can own different clients interested in the same change, and a slow client can consume less data than the system produces. Therefore durable state must outlive the connection, publication must tolerate retries, subscriptions need explicit permissions, and recovery must cover both gaps and duplicates. Transport choice follows these requirements; it cannot replace them.

## 1. Start From an Event Path Only When Polling Falls Short

Polling current state is often sufficient when a short delay is acceptable. Push reduces repeated requests and helps users observe changes sooner. Neither approach is automatically more scalable: frequent small polls can be cheap, while one pushed event sent to a million clients can be expensive. Write a **latency objective** in observable terms, such as "95% of committed booking changes appear on connected authorized screens within 500 ms" — an example requirement, not a benchmark. Separate commit latency, publication lag, gateway delay and client rendering, and define what happens when the client is offline.

## 2. Fit Gateways, Services, Brokers and Logs Together

A **gateway** owns live connections and delivers updates. The **business service** validates commands and enforces invariants, such as preventing two bookings for the same slot. A **broker** routes messages between producers and consumers. An **event log** retains records for replay — though not every broker configuration offers retention. An **outbox** records an event in the same transaction as its business change so a worker can publish it later.

Small deployments may combine the service and gateway in one process. A broker becomes useful when work must reach clients on other nodes or publication needs separate capacity. A registry of user-to-node locations is one routing option, not a requirement: room adapters can route broadcasts while each gateway tracks only its local sockets.

## 3. Commit Before You Notify

Assume a relational database, an outbox worker and gateways using live Pub/Sub. The exact transaction and worker implementation belongs in the [canonical outbox chapter](../../../20-backend/20.6-microservices/03-data-and-consistency/20.6.3.06-transactional-outbox.md); the important trace here is the complete delivery path.

| Step | Durable fact | Failure and recovery |
| -------------------------------------------------------------- | ------------------------------- | -------------------------------------------------------------------------- |
| 1. Validate receptionist, clinic and slot | None yet | Reject an unauthorized or conflicting command |
| 2. Commit booking version 7 plus event `e7` in one transaction | Booking and pending event exist | A rollback creates neither |
| 3. Worker publishes `e7` | Database still owns truth | A crash before recording publication can cause another publish |
| 4. Gateways route to authorized clinic connections | Live transport only | A disconnected gateway or browser can miss the publication |
| 5. Client applies version 7 | Client display advances | Ignore duplicates; detect a version gap and fetch authorized current state |

The worker cannot usually atomically commit both an external publish and a database "sent" flag. Expect repeated publication and give events stable identities: marking an event sent before publishing risks loss, marking it afterward risks duplicates. Describe neither ordering as exactly-once end-to-end delivery. For a booking screen, the latest authorized snapshot may be enough; an audit processor or payment workflow may need every retained event plus a durable consumer checkpoint.

Close the subscribe-versus-snapshot gap: a naive client fetches a snapshot, then subscribes, and a change between those operations disappears from view. One correct protocol subscribes first, buffers updates, fetches a versioned snapshot, then applies buffered updates newer than that version. For independent bookings keep versions per booking — a global counter in each gateway is not a shared sequence. If the product needs a whole-clinic ordered feed, allocate its sequence through an authoritative ordering mechanism.

## 4. Choose the Distribution Semantics

| Mechanism | What it supplies | What remains your responsibility |
| ----------------------------------- | ------------------------------------------- | --------------------------------------------------------- |
| Live Redis Pub/Sub | Deliver publications to current subscribers | Missed publications need separate history or snapshots |
| Retained stream/log | Replay within configured retention | Consumer offsets, expiry, duplicates and effect atomicity |
| Work queue or shared consumer group | Distribute each job among workers | Fan-out to all interested gateways is a separate step |
| Per-user notification store | Recover a user's unread notifications | Authorization, retention and the meaning of “read” |

Putting all gateways in one Kafka or Redis Streams consumer group and assuming each sees every event is a common mistake: a shared group distributes work, so one gateway may receive an event while interested sockets live elsewhere. Either route that event onward, partition ownership consistently, or provide independent subscription and checkpoint domains. A Redis subscription must match its API — subscribing to the literal channel `user:` does not subscribe to `user:alice`. For retained consumers, acknowledgment normally follows the required processing checkpoint; a crash after committing an effect but before acknowledgment can repeat delivery, so make the effect idempotent. A **dead-letter queue** holds records needing diagnosis after bounded attempts — it does not automatically repair them.

## 5. Separate Event Sourcing, CQRS and Collaboration Patterns

**Event sourcing** stores domain events as the authoritative history from which state is reconstructed. An outbox attached to ordinary current-state tables is not automatically event sourcing — choose it when history and reconstruction justify schema evolution, replay and concurrency complexity. **CQRS** separates write behavior from read models and can use ordinary tables without event sourcing; a separate read projection may lag the write, so return the accepted version or a suitable result for the UI to distinguish pending projection from failure.

Collaborative editing needs an explicit convergence algorithm and operation and version model, not just a broadcast named `operation`. A game needs server-authoritative action rules and a snapshot and delta protocol. An auction needs an atomic accepted-bid rule and server-controlled deadline — a timer in one gateway's memory is not a distributed settlement rule.

## 6. Start Simple, Partition Deliberately, Load-Test Honestly

Start with durable state plus ordinary HTTP when the product tolerates polling. Add SSE for a one-way browser feed, or WebSocket and Socket.IO when bidirectional interaction is useful. MQTT suits device messaging when its session and quality-of-service behavior matches the device constraints. Partition by the entity whose updates must stay ordered, such as a document or auction — though a very active entity can become a hot partition, and adding gateways improves connection capacity without removing that single ordering bottleneck.

Use stable event IDs, explicit version domains and bounded queues. Define a cursor-expired response that requests resynchronization rather than silently continuing after a gap. Monitor commit-to-client latency, oldest pending outbox age, broker lag, rejected events, reconnect rate and per-client buffer pressure. Load-test the actual payload and audience distribution: a 100-byte event to 10 clients differs from a 10-KB event to 100,000 clients. Exercise process crashes after commit, repeated publication, expired history and slow consumers.

## Common Mistakes

- **Broadcasting before commit.** A client may display a change that later rolls back. Publish committed facts or explicitly label provisional state.
- **Treating a queue as automatically durable.** State persistence, replication, producer confirmation, acknowledgment and retention settings all matter.
- **Assuming an awaited database write blocks the event loop.** Asynchronous I/O can coexist with other work. CPU-heavy synchronous work is different; queues separate throughput and failure boundaries, not magically eliminate all waiting.
- **Using arbitrary throughput tables.** Broker speed depends on payloads, partitions, persistence, replication and batching. Connection memory includes application state, TLS and queued buffers, not a universal protocol constant.
- **Confusing socket IDs with users.** One account can have several tabs and connections. Presence must expire abandoned records and avoid marking the entire user offline after one tab closes.
- **Making private routing public.** Authenticate connections, authorize subscriptions and replay, validate payloads and revoke access when policy changes.

## Summary

Build the real-time path around committed state, authorized subscriptions and an explicit recovery contract. Choose live fan-out, retained logs and work queues by their delivery semantics. A fast notification helps a screen stay current; it does not prove an effect committed or every consumer received the event.

# Scaling WebSockets

Alice joins `team:42` on gateway A; Bob joins the same room on gateway B. Without cross-node routing, A's local broadcast reaches Alice and misses Bob. Scaling WebSockets means solving exactly this: distributing persistent connections and their event workload across servers.

```javascript
io.adapter(createAdapter(publisher, subscriber));
// After the application verifies membership and commits the message:
io.to('team:42').emit('chat:message', committedMessage);
```

## Definition

**Scaling WebSockets** distributes persistent connections and their event workload across servers. Each live socket belongs to one process, while interested users may be connected to many different processes. A server's limit depends on TLS, message rate, application state, buffers, heartbeat work and operating-system resources — there is no universal Node.js connection ceiling.

> **Textbook Definition:** WebSocket scaling distributes persistent connections and message routing across nodes, requiring explicit ownership, fan-out, resource bounds and recovery when a connection or node fails.

## First Principles

An established connection cannot move to a new process like an ordinary stateless request. A new connection can route elsewhere, but its application state must be recovered. More gateways divide connection work, yet events still have to reach the gateway owning each interested client. If clients consume updates too slowly, adding producers or gateways can increase queued work rather than relieve it. These constraints produce three separate decisions: route new connections, route updates to their audiences, and bound work during overload and failure.

## 1. Scale for Measured Reasons, With Headroom

Scale for measured capacity, failure tolerance or geography. Multi-node operation limits one node failure's immediate blast radius — but only if other nodes can absorb reconnections. Regional gateways can reduce network distance; they do not eliminate authoritative-store latency or cross-region consistency costs. Leave headroom for failure and deployment: a fleet at its tested peak has no room for clients leaving a failed node, and a traffic spike can arrive faster than new instances start, so overload policy remains necessary.

## 2. Route Connections and Fan Out Events Separately

```text
new connections → load balancer → gateway A: Alice's sockets
                               └→ gateway B: Bob's sockets
committed event → routing layer ├→ A → local interested clients
                               └→ B → local interested clients
```

The load balancer chooses a backend during the WebSocket handshake. After the upgrade, frames stay on that connection and therefore on that backend — distributing initial handshakes needs no cookie-based affinity for a WebSocket-only transport. Reconnection creates a new connection that can reach another healthy node; no routing policy resurrects the old node's memory. Socket.IO **HTTP long-polling** instead spans multiple requests in one Engine.IO session, and those requests need affinity to the owning node. A Redis adapter handles cross-node broadcasts without removing polling's affinity requirement.

## 3. Bridge One Room Across Two Gateways

With a Socket.IO Redis adapter, gateway A routes the event through Redis so gateway B can emit to its local room members as well. The adapter configuration below belongs after HTTP server creation and before accepting clients. It is an integration excerpt, not a complete authenticated application — use the [Socket.IO chapter's event contract](../01-transports/60.1.1.03-socket-io.md) for authorization and command handling.

```javascript
import { Server } from 'socket.io';
import { createAdapter } from '@socket.io/redis-adapter';
import { createClient } from 'redis';

const io = new Server(httpServer);
const publisher = createClient({ url: process.env.REDIS_URL });
const subscriber = publisher.duplicate();
publisher.on('error', (error) => console.error('Redis publisher:', error.message));
subscriber.on('error', (error) => console.error('Redis subscriber:', error.message));
await Promise.all([publisher.connect(), subscriber.connect()]);
io.adapter(createAdapter(publisher, subscriber));
// After the application verifies membership and commits the message:
io.to('team:42').emit('chat:message', committedMessage);
```

Use separate Redis connections for publishing and subscribing. Configure credentials, TLS and reconnect behavior; handle startup failure and close both clients during shutdown. For Redis 7 and later, current Socket.IO guidance recommends considering its sharded adapter — choose a subscription mode from the room and namespace audience pattern and verify the documented compatibility. If B disconnects from live Redis Pub/Sub while a message is published, Bob may miss it: an ordinary Pub/Sub adapter is not chat history. Redis replication or Sentinel improves service availability; it cannot retroactively deliver an unretained publication.

## 4. Choose a Routing Strategy

| Strategy | Useful when | Boundary |
| --------------------------------- | ------------------------------------------------------ | -------------------------------------------------------------------------------------- |
| Balanced connections plus fan-out | Most rooms can span several gateways | Measure broker traffic and slow-client queues |
| Polling affinity plus fan-out | Socket.IO retains HTTP polling | Cookies or another affinity key must survive the full session; failure needs reconnect |
| Entity ownership | A document/game/room benefits from one authority | Hot entities and ownership transfer need explicit handling |
| User-to-gateway registry | Targeted delivery should avoid broadcasting everywhere | Records need leases, expiry and support for multiple connections per user |
| Managed connection service | Its protocol, geography and operational contract fit | Application permissions, recovery, quotas and costs still need design |

IP affinity can concentrate many users behind one NAT. A session cookie can distribute users better but depends on browser and proxy behavior. "Sticky" means a routing preference while the backend is available, not a guarantee that every reconnect reaches the same process. Modulo routing such as `hash(userId) % nodeCount` moves many assignments when node count changes; consistent hashing reduces reassignment but does not transfer active sockets or recover state.

A Cloudflare Durable Object is a different ownership model: one object can coordinate a room's live connections and persist room state in its storage, with WebSocket hibernation letting the instance leave memory while accepted connections stay open. When it wakes, in-memory fields have reset — persist any history needed for recovery explicitly. One object can still become hot, so decide room partitioning, authorization, storage, recovery, regional behavior, quotas and pricing.

## 5. Measure Capacity With a Workload

Suppose an event is 500 bytes after application serialization, arrives 20 times per second, and reaches 2,000 subscribers. Payload egress alone is:

```text
500 bytes × 20 events/second × 2,000 recipients
= 20,000,000 bytes/second ≈ 20 MB/second (decimal)
```

This excludes framing, TLS, retransmission, broker traffic and other messages. If many recipients are slow, buffers can dominate memory. For a chosen fleet, measure baseline memory plus application state, per-connection overhead and worst permitted pending bytes. File descriptors must also cover database, broker and health-check connections. Compare candidate configurations using the same ramp rate, TLS, payload sizes, audience distribution and slow-client fraction — recording latency percentiles, CPU, memory, egress, rejected work and recovery time. Idle connection counts alone do not measure a busy room's capacity.

## 6. Plan Failure and Deployment

- **Readiness**: stop advertising a node as ready before drain. Check whether dependencies needed for accepted work are usable — an always-200 endpoint containing uptime is not sufficient readiness.
- **Accepted work**: finish or safely reject in-flight commands under a finite deadline. A transport close does not decide whether a database write committed.
- **Connections**: advise clients to reconnect under policy, then close remaining connections by the deadline. Socket.IO's close method closes connections; waiting inside its completion callback is not a pre-close drain.
- **Recovery**: another node verifies credentials, reauthorizes subscriptions and resumes history or returns a snapshot. Client retries reuse operation identities.
- **Surge control**: randomized backoff, admission limits and reserve capacity reduce a simultaneous reconnect storm.

Heartbeat intervals must fit proxy and NAT idle timeouts and tolerate expected network pauses — there is no universally correct 30-second interval. Socket.IO manages its Engine.IO heartbeat; raw WebSocket applications need their own liveness behavior. Separate durable business state from live connection ownership. Track per-node connection counts, message and fan-out rate, buffer pressure, broker reconnects and oldest recovery cursor — and test a node loss while writes are active, a broker interruption, expired replay history and a burst of reconnects.

## Common Mistakes

- **Assuming an adapter makes polling stateless.** Broadcast routing and Engine.IO session ownership are distinct.
- **Persisting sessions without live ownership.** A Redis session record does not tell you which of a user's tabs currently owns a socket unless you record and expire that mapping.
- **Broadcasting through raw WebSocketServer as an event bus.** Its local EventEmitter events do not serialize messages to every remote client. Iterate authorized open connections or use a suitable library/adapter.
- **Scaling only gateways.** A hot ordering partition, broker bandwidth or database write path may remain the bottleneck.
- **Using a universal provider latency or connection count.** Workload, region, configuration and failure objectives determine the useful limit.
- **Ignoring slow consumers.** Bound each queue; coalesce replaceable state, drop disposable updates or disconnect for later recovery. Durable events need another recovery path.

## Summary

Route new connections, route events and recover state as separate concerns. Use affinity for Socket.IO polling and a compatible fan-out layer for cross-node audiences. Measure the actual workload, bound slow-client queues, and leave capacity for reconnection after failures.

# GraphQL Subscriptions & Live Queries

## TL;DR

GraphQL subscriptions push server-side events to clients over a WebSocket using the **subscriptions-transport-ws** or newer **GraphQL over WebSocket** protocol; a resolver subscribes to a **pub-sub backend** (Redis in production) and an optional `withFilter` runs *server-side* filtering so clients receive only relevant events. They are event-triggered ("tell me when X happens") — fundamentally different from **live queries**, which re-execute a query when its underlying data changes. Scaling means shared pub-sub fan-out across gateway nodes plus careful auth at connect time; the hidden tax is **over-emitting**: every subscriber receives every matching event unless you filter and shard deliberately.

## Definition

A GraphQL **subscription** is a long-lived operation: the client sends a query-shaped request once; the server streams multiple responses as events occur. The transport is WebSocket (or SSE for one-way), speaking a small control protocol: `connection_init` / `connection_ack`, then `subscribe` messages keyed by operation id, with `next`, `error`, and `complete` payloads flowing back.

```text
SUBSCRIPTION LIFECYCLE (graphql-ws protocol)

Client                                   Server
  │ ── connection_init(auth token) ──────▶    │
  │ ◀───────────── connection_ack ────────    │
  │ ── subscribe(id:1){ orderUpdated } ──▶    │
  │ ◀── next(id:1) {orderUpdated{...}} ──     │
  │ ◀── next(id:1) {orderUpdated{...}} ── │   │ Redis pub-sub events
  │ ◀── next(id:1) {orderUpdated{...}} ──     │
  │ ── complete(id:1) ───────────────────▶    │
```

## Why it matters

Subscriptions sit at the intersection of three senior topics: GraphQL schema design, distributed pub-sub infrastructure, and connection lifecycle security. Interviewers use them to test whether you understand that "realtime GraphQL" is not free — every subscription is stateful server memory plus a fan-out path through your message broker. The live-query distinction matters because teams conflate them and build expensive change-detection systems when plain events would do (or vice versa).

## Why Do We Need It?

- **Granular realtime without REST sprawl**: clients declare exactly which fields they need updated — no bespoke `/events` endpoints per screen.
- **Typed contracts**: subscription payload shape lives in the schema; codegen gives clients typed update handlers.
- **Decoupled producers**: domain services publish domain events (`ORDER_UPDATED`) without knowing any UI exists — same events feed analytics.
- **Selective delivery**: `withFilter` + auth context delivers per-user views of shared event streams.
- **Replaces polling**: dozens of clients polling every 5s waste far more resources than held sockets receiving pushes.

## How It Works

### Pub-sub backbone

Each gateway instance holds thousands of subscriptions in memory as async iterators. Events originate anywhere (API mutations, workers, other services), so production uses a shared broker:

```text
                    ┌────────────────┐
 publish ORDER_42 ─▶│     REDIS      │
 (worker service)   │  pub/sub or    │
                    │  Redis Streams │
                    └───────┬────────┘
             subscribe      │      subscribe
                ┌───────────┴───────────┐
                v                       v
        ┌──────────────┐        ┌──────────────┐
        │  gateway A   │        │  gateway B   │
        │ 3k sockets   │        │ 4k sockets   │
        │ iterators    │        │ iterators    │
        └──────┬───────┘        └──────┬───────┘
               v                       v
          ws clients ...          ws clients ...
```

Redis pub/sub is fire-and-forget (a disconnected gateway misses events); Redis Streams or NATS JetStream add replay when delivery guarantees matter.

### Server-side filtering with withFilter

The filter runs on the server *before* payload resolution — clients never see rejected events:

```typescript
import { withFilter } from 'graphql-subscriptions';

export const resolvers = {
  Subscription: {
    orderUpdated: {
      subscribe: withFilter(
        () => pubSub.asyncIterator(['ORDER_UPDATED']),
        // (payload, variables, context) -> boolean
        (payload, vars, ctx) =>
          payload.orderUpdated.orgId === vars.orgId &&
          canSeeOrder(ctx.user, payload.orderUpdated),
      ),
    },
  },
};
```

### Auth at connect time

Authentication happens in two places, and both matter:

```typescript
import { createServer } from 'node:http';
import { WebSocketServer } from 'ws';
import { useServer } from 'graphql-ws/lib/use/ws';
import { execute, subscribe } from 'graphql';

const wsServer = new WebSocketServer({ server: httpServer, path: '/graphql' });

useServer(
  {
    schema,
    context: async (ctx) => {
      // 1. Per-CONNECTION auth: token arrives with connection_init
      const token = ctx.connectionParams?.authToken;
      const user = await verifyJwt(token); // throw -> connection rejected
      return { user, dataSources: buildDataSources(user) };
    },
    subscribe: async (_resolve, _root, args, ctx, info) => {
      // 2. Per-SUBSCRIPTION authz: is this user allowed THIS field?
      await assertCanSubscribe(ctx.user, info.fieldName);
      return subscribe(_root, args, ctx, info);
    },
  },
  wsServer,
);
```

Connect-time auth establishes identity cheaply (once); per-subscription checks enforce field-level authorization since a single socket may open many subscriptions with different sensitivity.

### Live queries vs subscriptions

| Subscriptions  | Live Queries               |                                                         |
| -------------- | -------------------------- | ------------------------------------------------------- |
| Trigger        | Explicit events published  | Data change detection                                   |
| Semantics      | "When X happens, send Y"   | "Keep result of query current"                          |
| Implementation | AsyncIterator + pub-sub    | Query re-execution / invalidation tracking              |
| Cost driver    | Event volume x subscribers | Recompute cost x watchers                               |
| Maturity       | Standard, widely supported | Experimental (e.g., `@live` directives, custom engines) |

Live queries answer "what changed in this list?" without designing an event per mutation — but require the server to know when query results go stale, typically via polling the DB for diffing or reactive storage (RethinkDB-style). Most teams implement live-ish behavior manually: subscription emits coarse invalidation signal, client refetches the query.

## Code Examples

### Complete Apollo-style setup with Redis

```typescript
import { ApolloServer } from '@apollo/server';
import { ApolloServerPluginDrainHttpServer } from '@apollo/server/plugin/drainHttpServer';
import { expressMiddleware } from '@apollo/server/express4';
import { createServer } from 'node:http';
import express from 'express';
import { WebSocketServer } from 'ws';
import { useServer } from 'graphql-ws/lib/use/ws';
import { makeExecutableSchema } from '@graphql-tools/schema';
import { RedisPubSub } from 'graphql-redis-subscriptions';
import Redis from 'ioredis';

const pubSub = new RedisPubSub({
  publisher: new Redis(process.env.REDIS_URL),
  subscriber: new Redis(process.env.REDIS_URL),
});

const typeDefs = `#graphql
  type Order {
    id: ID!
    status: String!
    totalCents: Int!
    orgId: ID!
  }

  type Subscription {
    orderUpdated(orgId: ID!): Order!
  }
`;

const resolvers = {
  Subscription: {
    orderUpdated: {
      subscribe: withFilter(
        () => pubSub.asyncIterator(['ORDER_UPDATED']),
        (payload, vars, ctx) => {
          const order = payload.orderUpdated;
          if (!ctx.user || order.orgId !== vars.orgId) return false;
          return ctx.user.orgIds.includes(order.orgId);
        },
      ),
      resolve: (payload) => payload.orderUpdated,
    },
  },
};

const schema = makeExecutableSchema({ typeDefs, resolvers });

const app = express();
const httpServer = createServer(app);

const wsServer = new WebSocketServer({
  server: httpServer,
  path: '/graphql',
});

const serverCleanup = useServer({ schema, context: buildContext }, wsServer);

const apollo = new ApolloServer({
  schema,
  plugins: [
    ApolloServerPluginDrainHttpServer({ httpServer }),
    {
      async serverWillStart() {
        return {
          async drainServer() {
            await serverCleanup.dispose(); // close all sockets gracefully
          },
        };
      },
    },
  ],
});

await apollo.start();
httpServer.listen(4000);
```

### Publishing from a mutation or worker

```typescript
// In an OrderService used by mutations AND background workers:
export class OrderService {
  constructor(private readonly pubSub: RedisPubSub) {}

  async markShipped(orderId: string): Promise<Order> {
    const order = await this.repo.updateStatus(orderId, 'SHIPPED');

    // Channel-per-topic keeps fan-out predictable;
    // filters narrow per-subscriber.
    await this.pubSub.publish('ORDER_UPDATED', { orderUpdated: order });

    return order;
  }
}
```

### Client with reconnect and typed handling

```typescript
import { createClient } from 'graphql-ws';

const client = createClient({
  url: 'wss://api.example.com/graphql',
  connectionParams: () => ({
    authToken: getAccessToken(), // re-evaluated on reconnect: fresh JWT
  }),
  retryAttempts: 30,
  shouldRetry: () => true,
});

const unsubscribe = client.subscribe(
  {
    query: `
      subscription Orders($orgId: ID!) {
        orderUpdated(orgId: $orgId) { id status totalCents }
      }
    `,
    variables: { orgId: currentOrgId },
  },
  {
    next: (msg) => updateOrderRow(msg.data.orderUpdated),
    error: (err) => console.error('subscription error', err),
    complete: () => console.log('server closed subscription'),
  },
);
```

## Real-World Use Cases

1. **Delivery tracking** — couriers' location updates publish coarse events; customers' map subscriptions filter to their own order, receiving position + ETA deltas at human-visible cadence rather than GPS tick rate.
2. **Collaborative editor presence** — document subscriptions carry cursor/selection patches; per-doc channels keep fan-out O(viewers-of-doc) instead of O(all-editors).
3. **Trading dashboard** — price ticks published per instrument; portfolio view subscribes to ~20 symbols via one multiplexed socket, with server-side entitlement filtering enforcing market-data licenses per user tier.
4. **CI/CD pipeline monitor** — job-status events drive live log-tailing subscriptions scoped to jobs the user can access; completed pipelines send `complete`, letting clients tear down cleanly.
5. **Support inbox** — ticket-updated events invalidate React Query caches client-side (coarse invalidation pattern): subscription says "ticket 8821 changed", client refetches full detail — subscriptions stay thin, caching stays standard.

## Common Mistakes

```typescript
// BAD: in-memory pubsub - breaks the moment you run >1 instance
import { PubSub } from 'graphql-subscriptions';
export const pubSub = new PubSub();
// gateway A publishes; gateway B's subscribers never hear it

// GOOD: shared backend
export const pubSub = new RedisPubSub({
  publisher: new Redis(url),
  subscriber: new Redis(url),
});
```

```typescript
// BAD: auth only on connect - any user can subscribe to anything after
context: async ({ req }) => ({ user: verify(req) })
// subscription resolvers assume "already authenticated"

// GOOD: check per subscription too
subscribe: withFilter(
  iterator,
  (payload, vars, ctx) => authorized(ctx.user, payload),
)
```

Other costly errors:

- **Over-emitting**: publishing fine-grained events (one per keystroke/price tick) to broad channels; every subscriber pays resolve cost even when filtered out late. Filter early (channel design), resolve rarely.
- **Unbounded payload growth**: shipping entire aggregates on each event instead of deltas — 10k subscribers × 50KB objects will saturate NICs before CPU.
- **Forgetting heartbeat/idle teardown**: dead TCP connections accumulate until fd limits kill the gateway; enable protocol-level ping/pong and reap stale sockets.
- **Subscription storms after deploys**: every gateway restart drops sockets; clients all reconnect simultaneously (thundering herd) — add jittered backoff client-side.
- **Treating pub/sub as reliable delivery**: Redis pub/sub loses events during subscriber disconnects; use streams/consumer groups where missed-event cost is real.

## Best Practices

1. Use `graphql-ws` (newer protocol) for new projects; support legacy `subscriptions-transport-ws` only for old clients.
2. Always pair `asyncIterator` sources with server-side `withFilter`; never trust client-supplied scoping alone.
3. Authenticate on `connection_init`, authorize per-subscription; refresh tokens via reconnect with fresh `connectionParams`.
4. Design channels around entity/topic granularity; keep filters cheap (ID comparisons) and pre-compute what filters need into payloads.
5. Run dedicated Redis instances (or dedicated DB indexes) for pub-sub traffic — it is latency-sensitive and noisy.
6. Emit minimal payloads; let clients fetch details via normal queries when needed.
7. Monitor subscriptions per connection, events/sec per channel, and filter-rejection ratios; alert on abnormal growth (leaked subscriptions).

## Performance Considerations

Fan-out cost = events/sec × active subscribers × (filter cost + resolve cost + serialization). Move cheap checks first in filters, short-circuit aggressively. For hot channels (>10k subs), consider pre-serialized payloads cached per event version. Backpressure: slow clients should not stall publishers — graphql-ws writes queue per socket; monitor send-buffer depths and disconnect chronically lagging clients rather than bloating memory. Connection churn after deployments causes CPU spikes from TLS handshakes; stagger restarts behind load balancers. Finally, cap subscriptions per connection (e.g., 50) — runaway client loops are the most common production incident trigger in subscription-heavy apps.

## Summary

- Subscriptions stream server events over WebSocket via a tiny control protocol (`connection_init` → `subscribe` → `next`); prefer the `graphql-ws` implementation.
- Production fan-out requires a shared pub-sub backend — Redis pub/sub for simplicity, Streams/NATS when replay guarantees matter.
- `withFilter` enforces scoping and authorization server-side; connect-time auth alone is insufficient.
- Subscriptions are event-driven; live queries are change-detected query re-execution — most teams approximate live queries with coarse invalidation signals plus refetch.
- The dominant scaling costs are over-emitting, fat payloads, and leaked/stale connections; channel design and caps prevent all three.
- Deploy-time socket storms need jittered client backoff and graceful gateway draining.

## Cheat Sheet
```text
GRAPHQL SUBSCRIPTIONS CHEAT SHEET
============================================================

PROTOCOL (graphql-ws):
• connection_init(token) -> connection_ack
• subscribe{id,query}    -> next{id,payload} | error | complete
• Auth at init; authorize per subscription too

BACKEND:
• Dev : in-memory PubSub (single instance ONLY)
• Prod: Redis pub/sub (simple) / Streams (replay) / NATS JetStream

FILTERING:
• withFilter(asyncIterator, (payload, vars, ctx) => bool)
• Runs server-side BEFORE resolve - reject cheaply
• Channel design > runtime filtering

LIVE QUERIES vs SUBSCRIPTIONS:
• Subs: explicit events, mature, cheap
• Live: auto-detect changes, experimental, expensive
• Pragmatic: sub emits invalidation, client refetches

SCALING CHECKLIST:
• Shared pubsub across gateways
• Minimal payloads (deltas, not aggregates)
• Ping/pong + idle socket reaping
• Cap subscriptions per connection (~50)
• Jittered reconnect backoff (deploy storms)

AUTH:
• connection_init: verify JWT, reject early
• Per-subscription: field/entity-level authz in filter

INTERVIEW FORMULA:
• "Stateful servers + shared bus = the architecture"
• "Filter server-side, resolve rarely"
• "pub/sub is fire-and-forget - know your delivery needs"
```

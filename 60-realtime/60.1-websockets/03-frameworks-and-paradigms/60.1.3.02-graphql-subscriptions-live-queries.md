# GraphQL Subscriptions and Live Queries

## Definition

A GraphQL **subscription** is a long-lived operation: the client sends an operation once, and the server produces multiple results as source events occur. GraphQL defines execution semantics; a separate protocol carries those results to the client.

> **Textbook Definition:** A GraphQL subscription produces a stream of operation results from events. A live query reevaluates a query as relevant state changes. Reconnection and replay require additional protocols beyond either execution model.

For an order dashboard, a subscription might deliver “order 42 changed status.” A live query would keep the whole query result, such as “my open orders,” current as its dependencies change. An event can also tell a client to refetch an ordinary query; that is a useful invalidation pattern, not automatically a complete live-query engine.

## First Principles

A query reads state once. If a screen must change later without polling, some producer must notify it or some mechanism must detect that its result is stale. The server then needs to know which operation and user should receive the update. A connected user can lose permissions while an operation is active, and a disconnected client can miss events.

Therefore, source events, result shaping, authorization and recovery are separate responsibilities. A schema describes fields; it does not supply event storage, dependency tracking or a durable delivery checkpoint.

## Why Use a Subscription?

Use subscriptions when clients already consume a GraphQL schema and need a defined stream of updates. Clients select fields from the event result, but nested field resolution can still perform expensive I/O. A typed schema does not validate every business permission or make arbitrary input safe.

Compare with SSE or ordinary polling using the actual update frequency, client count and query cost. A rarely changing screen may be cheaper to poll than to maintain subscriptions. An active shared dashboard may benefit from push. Neither is universally cheaper.

## How an Event Becomes a Result

```text
committed domain change → event source → subscription source iterator
                                             ↓
                                  permission check and field execution
                                             ↓
                                    selected GraphQL result
                                             ↓
                                      transport → client
```

An **async iterator** produces values over time through `next()` and supports completion through `return()`. A subscription's `subscribe` resolver establishes that source. GraphQL executes the selected fields for each yielded event. A subscription operation has one top-level subscription field; that field can contain many selected child fields.

With the `graphql-ws` library's `graphql-transport-ws` protocol, the connection starts with `connection_init` and `connection_ack`. Each operation has an ID and a `subscribe` message; the server sends `next`, `error` or `complete`. A `next` result can itself contain GraphQL errors. Protocol-level `error` and a result's `errors` array are distinct failure paths.

The old `subscriptions-transport-ws` protocol is incompatible despite similar names. Match the client and server protocol. For current `graphql-ws` 6.x, the `ws` server integration imports from `graphql-ws/use/ws`; older `lib/use/ws` examples are not its current export path.

## Example: An Authorized Order Status Stream

This runnable local fixture uses Node.js 20+, GraphQL 16, `graphql-ws` 6, `ws` 8 and `@graphql-tools/schema`. Install those packages in a disposable project, save the code as `server.mjs`, and run `node server.mjs`.

The source yields three simulated order changes. It deliberately demonstrates subscription execution without hiding a broker behind an undefined helper. Tokens are disposable loopback fixtures; there is no database, production JWT verifier, HTTP GraphQL endpoint or durable replay.

```javascript
import { GraphQLError } from 'graphql';
import { makeExecutableSchema } from '@graphql-tools/schema';
import { WebSocketServer } from 'ws';
import { useServer } from 'graphql-ws/use/ws';
import { setTimeout as delay } from 'node:timers/promises';

const sessions = new Map([
  ['alice-demo-token', { userId: 'alice', orgIds: ['org-1'] }],
  ['bob-demo-token', { userId: 'bob', orgIds: ['org-2'] }],
]);
const schema = makeExecutableSchema({
  typeDefs: `
    type Query { health: String! }
    type Order { id: ID!, orgId: ID!, status: String!, version: Int! }
    type Subscription { orderUpdated(orgId: ID!): Order! }
  `,
  resolvers: {
    Query: { health: () => 'demo' },
    Subscription: {
      orderUpdated: {
        subscribe: async function* (_, { orgId }, { user, token }) {
          if (!user.orgIds.includes(orgId)) {
            throw new GraphQLError('Forbidden organization');
          }
          let version = 0;
          for (const status of ['ACCEPTED', 'PACKED', 'SHIPPED']) {
            await delay(30);
            const current = sessions.get(token);
            if (current !== user || !current.orgIds.includes(orgId)) {
              throw new GraphQLError('Subscription permission revoked');
            }
            yield { orderUpdated: { id: 'order-42', orgId, status, version: ++version } };
          }
        },
      },
    },
  },
});
const wsServer = new WebSocketServer({
  host: '127.0.0.1', port: 4000, path: '/graphql', maxPayload: 16 * 1024,
});
const cleanup = useServer({
  schema,
  connectionInitWaitTimeout: 5000,
  onConnect: (ctx) => sessions.has(ctx.connectionParams?.authToken),
  context: (ctx) => {
    const token = ctx.connectionParams?.authToken;
    const user = sessions.get(token);
    if (!user) throw new GraphQLError('Authentication required');
    return { user, token };
  },
}, wsServer);
process.on('SIGTERM', async () => { await cleanup.dispose(); });
```

Connection authentication checks the fixture token before acknowledgment. The `context` function runs for an operation; it is not a once-per-connection authentication hook. The source resolver rejects an organization that the user cannot access, then rechecks current permission before each result. Production needs a real credential/session policy, expiry, origin handling, limits and revocation behavior.

Save this as `client.mjs` and run it while the server is listening:

```javascript
import { createClient } from 'graphql-ws';
import WebSocket from 'ws'; // Browser integration uses its native WebSocket instead.

const client = createClient({
  url: 'ws://127.0.0.1:4000/graphql',
  webSocketImpl: WebSocket,
  connectionParams: () => ({ authToken: 'alice-demo-token' }),
  retryAttempts: 3,
});
try {
  for await (const result of client.iterate({
    query: `subscription Orders($orgId: ID!) {
      orderUpdated(orgId: $orgId) { id status version }
    }`,
    variables: { orgId: 'org-1' },
  })) {
    if (result.errors) {
      console.error(result.errors);
      break;
    }
    console.log(result.data.orderUpdated);
  }
} finally {
  await client.dispose();
}
```

Alice receives versions 1, 2 and 3, then the finite source completes. Changing her requested organization to `org-2` fails rather than revealing Bob's organization. An invalid token rejects the connection. Ending a client iterator cancels that operation; disposing the client releases its connection resources.

### Replace the fixture source deliberately

In an application, the iterator comes from a publisher or retained event source. An in-memory `graphql-subscriptions` PubSub only reaches subscribers in the same process. Its v3 iterator method is `asyncIterableIterator`; a different Redis library may expose a different API. Do not mix their method names without checking the installed version.

A `withFilter` wrapper can discard events before field resolution, but it must receive the correct user context and current policy. Reject unauthorized subscription requests early as well; opening an idle iterator that silently drops everything is not a substitute for an explicit access decision. Scope channels by authorized organization/entity to reduce unnecessary work, and validate producer payloads before resolution.

## Subscriptions Versus Live Queries

| Question | Subscription | Live query |
| ----------------------------- | ---------------------------------------------- | ------------------------------------------------------------------------- |
| What starts an update? | An event enters the source stream | A query dependency is invalidated or change detection runs |
| What does the client receive? | Selected fields for each source event | A current result or a protocol-defined result difference |
| Main cost | Events × relevant subscribers × execution work | Invalidations × watchers × recomputation work |
| Recovery | Replay/cursor or refetch must be designed | Recompute current result; incremental protocols still need recovery rules |

A live-query engine must know which changes affect which queries, including inserts, deletes and filters that move items into or out of a list. `@live` is not a universally standardized built-in GraphQL directive. A custom engine or invalidation protocol defines its behavior.

A subscription that says “order 42 changed” can trigger an authorized refetch. Coalesce repeated invalidations and handle an event arriving during a fetch so the final view does not remain stale. An event stream and a query result are different things; document which one the UI treats as authoritative.

## Real-World Decisions

Use per-order delivery tracking for the customer's authorized order; limit location update cadence rather than forwarding every device sample. For a support inbox, coarse invalidation plus normal query caching can keep subscription payloads small. For market data, entitlements apply to each selected instrument and may change while a socket remains open.

A domain terminal status does not automatically send protocol `complete`. The source or server must close the operation deliberately, and the client must release abandoned watchers when navigating away.

For multiple gateways, choose distribution semantics that reach every interested gateway. A shared work-consumer group delivers a record to one member, not every socket server. Redis Pub/Sub loses updates during disconnects; a retained stream alone does not implement per-client replay. Redis Pub/Sub channels are not isolated by Redis database number; use appropriate channel permissions and infrastructure boundaries.

## Common Mistakes

- **Calling context construction connection authentication.** Use the connection hook where appropriate, then authorize operations and continuing results.
- **Overriding GraphQL subscribe with a field-resolver signature.** The execution function and an individual field's source resolver have different contracts. Put access rules at the correct layer.
- **Calling a setup complete with missing helpers or no Query root.** Build and validate the schema, match installed export paths, and test the actual protocol.
- **Blindly retrying forbidden operations.** Some errors are terminal. Token refresh must obtain a valid credential; repeated network attempts cannot grant permission.
- **Assuming reconnect replays missed results.** The simulated source restarts on a new operation. Durable systems need an authorized offset or snapshot and version checks.
- **Ignoring nested resolver cost.** A small top-level event can trigger many database reads across selected fields.

## Best Practices

Cap operations per connection, query depth/complexity, event size and queued work. Coalesce disposable updates and disconnect slow clients under a stated recovery policy. Monitor active operations, event execution time, authorization rejections, buffer pressure and reconnects without unbounded user-ID metric labels.

Publish committed facts through a recoverable event path when missed updates matter. A database update followed by a direct publish has a crash gap; use the [real-time architecture's outbox and recovery trace](../02-architecture-and-scaling/60.1.2.01-real-time-architecture.md). Test authentication failure, cross-tenant requests, revocation during a stream, cancellation, malformed operations and reconnect behavior separately.

## Summary

A subscription shapes an event stream through a GraphQL operation; a live query keeps a query result current through additional change detection. Match the transport protocol, authorize the requested scope and continuing results, and design recovery independently of reconnection.

# WebRTC Peer-to-Peer

## Definition

WebRTC is a browser-supported set of APIs and protocols for sending real-time audio, video and application data between peers. The application supplies **signaling**: a trusted way for peers to exchange connection descriptions and connectivity information.

> **Textbook Definition:** WebRTC is a set of APIs and protocols for negotiating and transporting encrypted real-time media and data between peers, using connectivity establishment and optional relays. Signaling is supplied by the application.

For a video call, the browser captures a microphone or camera, creates a peer connection and negotiates a route to the other endpoint. The route can be direct or use a relay. “Peer-to-peer” does not mean that a production call needs no servers: signaling, authentication, relay service and group conferencing can all require them.

## First Principles

Two browsers rarely have simple public addresses that can receive unsolicited traffic. Firewalls and address translation can prevent a direct connection. They must also agree on media formats and verify the endpoint whose encrypted transport they establish. For video, an obsolete frame may be less useful than a fresh one; for a file, a missing byte cannot simply be ignored.

Thus connection discovery, negotiation, transport security and reliability policy are separate mechanisms. The application chooses behavior appropriate to the data and handles the cases where no usable route exists.

## Why Use It?

Use WebRTC for interactive media or data that benefits from its browser APIs, congestion handling and peer/relay transport. Use WebSocket when a server-authoritative application channel is sufficient. Use a streaming delivery system when a large audience primarily watches and interactive latency is unnecessary.

A direct media path can avoid an application media-server hop, but actual latency and cost depend on encoding, networks, relays and topology. Do not promise fixed millisecond latency or free media delivery: relayed traffic and conferencing servers consume bandwidth.

## How the Components Fit Together

```text
microphone/camera → MediaStreamTrack → RTCPeerConnection → remote media
application data → RTCDataChannel   → RTCPeerConnection → remote data
                                      ↑
                         application signaling exchanges descriptions
                         and connectivity candidates between endpoints
```

`getUserMedia()` requests device access under browser permission rules and returns media tracks. `RTCPeerConnection` negotiates and carries the connection; `RTCDataChannel` carries application messages. Camera access needs an appropriate secure context and user permission. Screen capture has its own permission and API behavior.

A **Session Description Protocol (SDP)** offer describes proposed media/data capabilities and connection information. The answer selects compatible behavior. The caller sets its local offer; the receiver sets that offer as remote, creates and sets a local answer; the caller sets the answer as remote. Both ends need the corresponding descriptions before using the negotiated connection.

### Discover a route with ICE

**Interactive Connectivity Establishment (ICE)** gathers possible routes called candidates and tests candidate pairs. **Session Traversal Utilities for NAT (STUN)** helps discover a mapped address. **Traversal Using Relays around NAT (TURN)** supplies a relay allocation when a relay route is needed. A NAT is a network address translator; firewall and mapping behavior vary beyond simple historical “cone” labels.

| Candidate | Meaning | Boundary |
| ---------------- | ------------------------------------------ | --------------------------------------------------------------------- |
| Host | An interface-local route | Privacy controls may obscure addresses; not always reachable remotely |
| Server-reflexive | A mapped address discovered using STUN | Discovery does not guarantee another peer can reach it |
| Peer-reflexive | A route learned during connectivity checks | Not a separate signaling-server feature |
| Relay | A TURN allocation | Relay reachability, credentials, capacity and policy can still fail |

ICE selects a working route under its checks and priority rules. TURN is not “always works”; restrictive networks or failed relay service can block it too. Test relay paths and measure their share of traffic for your actual users.

**Trickle ICE** sends candidates as they are gathered rather than waiting for all of them. A candidate can arrive before the recipient has set its remote description, so queue it until that description is ready. Associate candidates with the correct call and negotiation generation; stale candidates from an earlier attempt must not be applied blindly.

### Encryption depends on the endpoint topology

Media uses Secure Real-time Transport Protocol (**SRTP**) keys established through Datagram Transport Layer Security (**DTLS**). Data channels use Stream Control Transmission Protocol (**SCTP**) over a protected transport. Reliability and ordering are configurable for data channels; a statement that “all WebRTC is unreliable UDP” misses this distinction. TURN can also provide transport paths suitable for restrictive networks.

A relay forwards packets; it is different from a conferencing server that terminates a WebRTC connection. An ordinary selective forwarding server terminates transport encryption even if it forwards encoded media without decoding it. End-to-end media encryption beyond such a server requires additional design. Trusted signaling and endpoint identity matter: encrypted transport alone does not establish that a caller joined the right private room.

## Example: Two Local Peers Exchange a Position

This browser-console fixture creates two peers inside one page. It uses no camera, signaling service, STUN or TURN. It demonstrates offer/answer ordering and a data channel; it does **not** test internet traversal or production call security. Run it in a current browser on an HTTP localhost page or HTTPS page.

It waits for complete candidate gathering and carries those candidates in the description rather than using trickle ICE. The finite deadlines prevent a stalled demonstration from waiting forever. Close both peers after the exercise.

```javascript
async function waitFor(target, event, ready, timeoutMs = 5000) {
  if (ready()) return;
  await new Promise((resolve, reject) => {
    const done = () => {
      if (!ready()) return;
      cleanup();
      resolve();
    };
    const timer = setTimeout(() => {
      cleanup();
      reject(new Error(`${event} timed out`));
    }, timeoutMs);
    const cleanup = () => {
      clearTimeout(timer);
      target.removeEventListener(event, done);
    };
    target.addEventListener(event, done);
    done();
  });
}

async function connectLocalPeers(onPosition) {
  const caller = new RTCPeerConnection();
  const receiver = new RTCPeerConnection();
  const outgoing = caller.createDataChannel('position', {
    ordered: false, maxRetransmits: 0,
  });
  let incoming;
  let latest = -1;
  const close = () => { caller.close(); receiver.close(); };
  receiver.addEventListener('datachannel', ({ channel }) => {
    incoming = channel;
    channel.addEventListener('message', ({ data }) => {
      if (typeof data !== 'string' || data.length > 1024) return;
      try {
        const position = JSON.parse(data);
        if (!position || !Number.isSafeInteger(position.sequence) ||
            position.sequence <= latest ||
            !Number.isFinite(position.x) || !Number.isFinite(position.y)) return;
        latest = position.sequence;
        onPosition(position);
      } catch {
        // Discard a malformed position; it is not an authoritative command.
      }
    });
  });
  try {
    await caller.setLocalDescription(await caller.createOffer());
    await waitFor(caller, 'icegatheringstatechange',
      () => caller.iceGatheringState === 'complete');
    await receiver.setRemoteDescription(caller.localDescription);
    await receiver.setLocalDescription(await receiver.createAnswer());
    await waitFor(receiver, 'icegatheringstatechange',
      () => receiver.iceGatheringState === 'complete');
    await caller.setRemoteDescription(receiver.localDescription);
    await waitFor(outgoing, 'open', () => outgoing.readyState === 'open');
    await waitFor(receiver, 'datachannel', () => Boolean(incoming));
    await waitFor(incoming, 'open', () => incoming.readyState === 'open');
    return { outgoing, close };
  } catch (error) {
    close();
    throw error;
  }
}

const peers = await connectLocalPeers((position) => console.log(position));
peers.outgoing.send(JSON.stringify({ sequence: 1, x: 120, y: 88 }));
// After observing the result: peers.close();
```

The receiver ignores a position older than one it has applied. Each message is a complete position snapshot, so missing sequence 1 does not prevent using sequence 2. That would be unsafe for dependent drawing strokes or file chunks: missing a required earlier record changes the result.

`ordered: false` permits reordering, and `maxRetransmits: 0` limits retransmission; neither automatically removes an old update that was already delivered. The application still checks sequence and age. For reliable file chunks, use the appropriate channel mode plus chunk identity, completion/integrity checks and bounded `bufferedAmount` handling. Even a reliable send is not proof that the receiver saved the file.

### Add media and real signaling

For a call, add the chosen local tracks before creating the initial offer. At the other endpoint, receive tracks through `track` events and attach them to media elements under autoplay/permission rules. Stop capture tracks when the user ends capture; closing a peer connection alone is not a replacement for releasing camera and microphone tracks.

Exchange descriptions through authenticated signaling. Validate envelope shape and size, authorize both peers to the call, route to the intended peer and reject stale negotiation messages. Wait for the signaling channel to open before sending. Handle malformed envelopes and permission/device errors without leaving abandoned connections or empty rooms.

During renegotiation, both peers can create an offer simultaneously. This **offer collision**, also called glare, needs a strategy such as the polite/impolite roles in the canonical perfect-negotiation reference. A single initial caller/receiver sketch does not solve renegotiation.

## Choose a Conferencing Topology

Assume one encoded stream per directed peer link; actual simulcast layers and subscriptions change these counts.

| Topology | Whole-system mechanism | Cost and trust boundary |
| ------------------------------- | ------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------- |
| Mesh | Each participant sends to each other participant | `n−1` outgoing streams per participant; `n(n−1)` directed streams overall; TURN may relay some links |
| Selective forwarding unit (SFU) | Each participant sends to a server that forwards selected streams/layers | Reduce repeated client uploads; server egress and each client's selected downloads still scale |
| Multipoint control unit (MCU) | A server decodes/mixes/composites media and sends combined output | Server compute increases; media is available at the mixing endpoint |

For five mesh participants, each sends four directed streams: 20 in total. That arithmetic is not a universal five-person limit. Device CPU, resolution, upload bandwidth and relay usage determine the useful topology. An SFU can receive several simulcast layers, so “one upload” means one server destination, not necessarily one encoded layer or fixed bitrate.

Use a measured small-call mesh when it fits. Choose an SFU when selective forwarding and client resource limits justify it. Choose an MCU for required mixing/interop behavior, while assessing compute, quality and privacy. Recording requires a stated consent, retention and access policy at the recording endpoint; a client MediaRecorder is not automatically a complete telehealth recording design.

## Common Mistakes

- **Shipping STUN-only and declaring traversal solved.** Provide and exercise suitable relay routes for supported networks; protect issued relay credentials and control abuse.
- **Calling encryption automatic end-to-end privacy.** Establish trusted peers and inspect where transport is terminated in the chosen topology.
- **Applying ICE candidates before remote description.** Queue them for the matching negotiation, or deliberately use complete descriptions as the local fixture does.
- **Restarting on every disconnected state.** A transient interruption differs from failure. Use a timed recovery policy and negotiate ICE restart when appropriate; `restartIce()` still needs signaling.
- **Ignoring queued bytes.** Data-channel buffers can grow under a slow link. Set high/low water policies and stop or reduce production before memory grows without bound.
- **Treating cursor traffic like authoritative state.** Lossy complete snapshots fit presence; payments, durable edits and file completion need different contracts.

## Best Practices

Track connection and ICE state, route type, packet loss, round-trip time and bitrate through `getStats()`. Show clear permission, connecting, reconnecting and failed states. Test real devices and relay-only paths; a same-page fixture establishes neither NAT traversal nor media quality.

Use `RTCRtpTransceiver.setCodecPreferences()` where supported and `RTCRtpSender.setParameters()` for applicable encoding controls. Codec support, hardware acceleration and quality vary by device; measure CPU, battery and bandwidth before choosing preferences. Release tracks, peer connections, timers and signaling listeners on end or failure.

## Summary

WebRTC negotiates encrypted media and data transport between endpoints; the application supplies trusted signaling and recovery. ICE tests routes, STUN helps discovery and TURN can relay traffic. Choose mesh, SFU or MCU from measured resource and privacy requirements, and choose reliability by whether an obsolete or missing message can be discarded safely.

# WebRTC Peer-to-Peer

## TL;DR

WebRTC is three APIs — `getUserMedia` (capture), `RTCPeerConnection` (encrypted media/data transport), `RTCDataChannel` (arbitrary data) — that let browsers exchange media directly. But peers cannot find each other alone: **signaling** (any channel, usually WebSocket) exchanges SDP offers/answers while **ICE/STUN/TURN** punch through NATs. Topology decides economics: **mesh** is free but caps around 4-6 participants, an **SFU** scales to hundreds at real bandwidth cost per upload stream, and MCUs trade flexibility for server-side compositing. P2P wins for 1:1 and small calls; the moment you say "group call", you are buying an SFU.

## First Principles

WebRTC is peer-to-peer media over a hostile network:

1. **NAT traversal is the problem**: peers are behind NATs — STUN discovers public addresses, TURN relays when traversal fails (the media relay cost you can't avoid ~15% of the time), signaling exchanges the offers (any channel; often → 60.1.1.01).
2. **The transport is UDP with congestion control**: media tolerates loss, hates latency — SRTP/ICE/DTLS stack exists to deliver *fresh* frames, not complete ones (the inverse of TCP's philosophy).

## Definition

**WebRTC** is a browser-native stack for real-time audio/video/data between peers: capture via `getUserMedia`, negotiate connectivity via SDP offer/answer relayed by your signaling server, traverse NATs using ICE candidates gathered with STUN (reflexive address discovery) and TURN (relayed fallback), then stream SRTP/SCTP flows peer-to-peer.

```text
THE WEBRTC TRIANGLE
        getUserMedia ──── capture mic/cam/screen
             │
             v
      RTCPeerConnection ──── encrypt, encode, transport
         │           │
         v           v
   RTCDataChannel   SRTP media ── direct or TURN-relayed
   (arbitrary data)

SIGNALING IS NOT WEBRTC - you build it (WS + your protocol)
```

## Why it matters

Video interviewing platforms, telehealth, and collaborative tools all rest on this stack, and system-design interviews increasingly include "design a video call app" where topology cost math separates senior from junior answers. The counterintuitive core: *media does not flow through your servers in P2P mode* — only signaling does. That single fact reshapes infrastructure costs, privacy posture (E2E encryption comes nearly free), and failure modes (NAT traversal becomes your biggest operational risk).

## Why Do We Need It?

- **Latency**: direct paths skip server hops; glass-to-glass delay drops to 100-300ms versus 1-3s for server-relayed HLS-style delivery.
- **Bandwidth economics**: N-way mesh means each client uploads N-1 streams; the server pays nothing for media — unbeatable for 1:1 and trios.
- **Privacy**: DTLS-SRTP encryption end-to-end means even your backend cannot see pixels (unless you route through SFU/MCU).
- **Data channels without servers**: game state, file transfer, whiteboard strokes can bypass servers entirely with SCTP reliability/ordering controls.
- **Standardization**: no plugins since ~2014; every modern browser plus native SDKs speak the same negotiation dance.

## How It Works

### The connection dance

```text
PEER A                          SIGNALING (WS)              PEER B
  │                                  │                         │
  │ getUserMedia()                   │                         │
  │ createOffer() -> localSDP        │                         │
  │ ───────────── offer(sdpA) ─────▶ │ ──────────────────────▶ │
  │                                  │                    setRemote(sdpA)
  │                                  │                    createAnswer()
  │ ◀────────────────────────────── answer(sdpB) ──────────────│
  │ setRemote(sdpB)                  │                         │
  │                                  │                         │
  │ ───────────── ICE candidate ───▶ │ ─── trickle to B ─────▶ │
  │ ◀──────────────────────────── ICE candidates ──────────────│
  │                                  │                         │
  │ ══════════════ DTLS handshake, then SRTP media ══════════  │
```

ICE gathers candidates in priority order:

| Type | Meaning | Cost |
| ----- | -------------------------------------- | --------------------------------- |
| host | Local LAN address | Direct, fastest |
| srflx | NAT-mapped address learned from STUN | Direct if NAT allows |
| prflx | Peer-reflexive, discovered mid-session | Rare |
| relay | TURN server allocation | Always works, full bandwidth bill |

Connectivity checks pair candidates; highest-priority working pair wins. Roughly 8-15% of sessions need TURN (symmetric NATs, strict firewalls) — budget for it.

### NAT types and why they matter

```text
FULL CONE       : any outsider may reply to mapped port -> easy P2P
RESTRICTED      : replies allowed to addresses you contacted -> STUN ok
PORT-RESTRICTED : same, plus exact port must match -> STUN usually ok
SYMMETRIC       : mapping differs per destination -> STUN useless,
                  TURN REQUIRED (carrier-grade NAT, mobile networks)
```

### Topology math

```text
MESH (pure P2P): every peer uploads to every other
  participants n -> uploads per client = n-1
  total streams  = n(n-1)
  n=2 : 2 streams    n=5 : 20 streams    n=8 : 56 streams
  Client bandwidth dies around n=4-6 on residential uplinks.
  Server cost: ~0 for media. E2EE preserved.

SFU (Selective Forwarding Unit): each peer uploads ONCE
  uploads per client = 1 (simulcast layers)
  server forwards selected layers downstream
  n=50 : still 1 upload per client
  Server egress = sum(all downloads). You pay per bit.
  Simulcast (1080p+360p+180p) lets SFU pick per-receiver quality.

MCU (Multipoint Control Unit): server decodes everything,
  recomposites ONE stream out
  uploads/downloads per client = 1 each
  CPU-heavy transcoding; breaks E2EE; legacy/telephony bridge use.
```

Decision rule: 1:1/small group → mesh; group calls beyond ~5 → SFU; heterogeneous device fleets or PSTN bridges → MCU.

## Code Examples

### Minimal working call sketch

```typescript
const rtcConfig: RTCConfiguration = {
  iceServers: [
    { urls: 'stun:stun.l.google.com:19302' },
    {
      urls: 'turn:turn.example.com:3478',
      username: 'user',
      credential: await fetchTurnCredentials(), // short-lived HMAC creds
    },
  ],
};

// --- Caller side ---
const ws = new WebSocket('wss://signal.example.com');

const pc = new RTCPeerConnection(rtcConfig);

const localStream = await navigator.mediaDevices.getUserMedia({
  video: { width: 1280 },
  audio: { echoCancellation: true, noiseSuppression: true },
});
localStream.getTracks().forEach((track) => pc.addTrack(track, localStream));

pc.onicecandidate = ({ candidate }) => {
  if (candidate) ws.send(JSON.stringify({ type: 'ice', candidate }));
};

pc.ontrack = (event) => {
  document.querySelector<HTMLVideoElement>('#remote')!.srcObject =
    event.streams[0];
};

const offer = await pc.createOffer();
await pc.setLocalDescription(offer);
ws.send(JSON.stringify({ type: 'offer', sdp: offer.sdp }));

ws.onmessage = async ({ data }) => {
  const msg = JSON.parse(data);
  if (msg.type === 'answer') {
    await pc.setRemoteDescription({ type: 'answer', sdp: msg.sdp });
  } else if (msg.type === 'ice') {
    await pc.addIceCandidate(msg.candidate);
  }
};
```

### Data channel for non-media sync

```typescript
const dc = pc.createDataChannel('whiteboard', {
  ordered: false,          // drop stale strokes rather than stall
  maxRetransmits: 0,       // unreliable like UDP - good for live cursors
});

dc.onopen = () => dc.send(JSON.stringify({ t: 'cursor', x: 120, y: 88 }));

dc.onmessage = ({ data }) => renderRemoteCursor(JSON.parse(data));
```

Choose channel options deliberately: `maxRetransmits: 0` (or `maxPacketLifeTime`) gives UDP-like semantics for cursor/presence; reliable-ordered default suits chat and file chunks.

### Signaling server (Node, minimal)

```typescript
import { WebSocketServer } from 'ws';

const rooms = new Map<string, Set<WebSocket>>();
const wss = new WebSocketServer({ port: 8080 });

wss.on('connection', (socket, req) => {
  const roomId = new URL(req.url!, 'http://x').searchParams.get('room')!;
  const peers = rooms.get(roomId) ?? new Set();
  peers.add(socket);
  rooms.set(roomId, peers);

  socket.on('message', (raw) => {
    // Relay offers/answers/candidates to other room members ONLY.
    // Production: authenticate here, validate message shape, rate-limit.
    const text = raw.toString();
    if (!['offer', 'answer', 'ice'].includes(JSON.parse(text).type)) return;
    for (const peer of peers) {
      if (peer !== socket && peer.readyState === socket.OPEN) peer.send(text);
    }
  });

  socket.on('close', () => peers.delete(socket));
});
```

Signaling stays trivially simple because WebRTC carries its own description of what it needs — the server just relays envelopes.

## Real-World Use Cases

1. **Telehealth consult** — 1:1 mesh call with mandatory TURN fallback for hospital firewalls; screen share for reviewing scans uses a second transceiver; recording happens consent-gated via MediaRecorder before any upload.
2. **Interview platform (this repo's audience)** — structured 1:1 calls with data-channel code-editor sync; mesh keeps infra costs near zero while signaling runs on cheap WS gateways.
3. **All-hands town hall (500 viewers)** — pure WebRTC mesh impossible; SFU with simulcast distributes one presenter's layered streams; viewers' downlinks pick layers adaptively, presenters still mesh among themselves.
4. **Multiplayer browser game** — RTCDataChannel in unreliable-unordered mode drives position updates at 30Hz; authoritative server remains over WS for state reconciliation — hybrid architecture.
5. **IoT drone feed** — WHEP (WebRTC-HTTP Egress Protocol) pulls low-latency video from camera edge devices into ops dashboards; sub-second latency beats HLS's multi-second glass delay.

## Common Mistakes

```typescript
// BAD: creating offer BEFORE adding tracks -> empty SDP, renegotiation pain
const offer = await pc.createOffer();          // m-lines missing
await pc.setLocalDescription(offer);
stream.getTracks().forEach((t) => pc.addTrack(t, stream)); // too late-ish

// GOOD: tracks first, then negotiate
stream.getTracks().forEach((t) => pc.addTrack(t, stream));
const offer = await pc.createOffer();
await pc.setLocalDescription(offer);
```

```typescript
// BAD: shipping STUN-only config and calling NAT "handled"
{ iceServers: [{ urls: 'stun:stun.example.com' }] } // symmetric NAT fails

// GOOD: TURN with short-lived credentials as guaranteed fallback
{
  iceServers: [
    { urls: 'stun:stun.example.com' },
    { urls: 'turn:turn.example.com:443?transport=tcp',
      username: userId,
      credential: hmacToken }, // expires in 5 min, issued by your API
  ],
  iceTransportPolicy: 'all',
}
```

Other classic failures:

- **Signaling treated as secure-by-default**: relaying SDP unauthenticated lets anyone join any room; enforce auth tokens on the WS handshake and room membership checks per message.
- **Ignoring `oniceconnectionstatechange`**: networks flap; production apps monitor `disconnected`/`failed` states and restart ICE (`restartIce()`) instead of forcing users to rejoin.
- **Forgetting perfect-negotiation**: glare (both sides offer simultaneously) corrupts sessions; implement the polite/impolite peer pattern for renegotiations.
- **TURN credentials baked into clients**: static shared secrets get scraped; issue short-lived HMAC tokens from your backend.
- **Mesh beyond six people**: mobile uplink saturates, everyone's CPU spikes decoding N-1 streams — plan SFU migration before launch week, not after.

## Best Practices

1. Always configure both STUN and TURN (TCP 443 variant for restrictive firewalls); measure your TURN usage ratio monthly.
2. Use simulcast when sending to SFUs so receivers on weak links stay functional.
3. Implement ICE restart handling and connection-state UX ("reconnecting…") — network blips are routine.
4. Keep signaling payloads schema-validated and authenticated; rate-limit per connection.
5. Prefer data channels with explicit reliability settings matching semantics (cursors unreliable, files reliable).
6. Adopt adapter-based APIs carefully: check `RTCPeerConnection` feature support instead of user-agent sniffing.
7. For group growth, design mesh → SFU migration up front: same client codec stack, different remote endpoint.

## Performance Considerations

Codec choice dominates CPU: VP9/AV1 save bandwidth at encoding cost; H.264 hardware encoders keep battery drain low on mobile — expose `codecPreferences` when supported. Audio processing (echo cancellation, noise suppression) is DSP-expensive; disable only deliberately. In mesh, cap outbound resolution to what uplink sustains — `sender.getParameters().encodings[0].maxBitrate` — and listen to `getStats()` network estimates to step down dynamically. SFU sizing rule of thumb: egress bandwidth is the constraint (viewers × chosen layer bitrate), CPU mostly forwarding (cheap) unless transcoding. TURN adds one hop (~10-40ms) plus full relay bandwidth — colocate TURN regions with users, not with origin servers.

## Summary

- WebRTC = `getUserMedia` + `RTCPeerConnection` + `RTCDataChannel`; signaling is yours to build (WebSocket + envelope relay).
- ICE/STUN/TURN handle NAT traversal; symmetric NATs force TURN for roughly 8-15% of real-world sessions.
- Topology determines cost: mesh scales to ~4-6 peers free, SFU scales to hundreds with egress bills, MCU trades E2EE for compatibility.
- Perfect negotiation, ICE restarts, and connection-state UX separate demos from products.
- Data channels give configurable reliability — unreliable for live cursors, reliable for transfers.
- Security hinges on authenticated signaling and short-lived TURN credentials; media itself arrives encrypted (DTLS-SRTP).

## Cheat Sheet
```text
WEBRTC CHEAT SHEET
============================================================

THREE APIS:
• getUserMedia      : capture mic/cam/screen
• RTCPeerConnection : encrypt + transport (SRTP)
• RTCDataChannel    : SCTP data, configurable reliability

CONNECTION DANCE:
• addTracks -> createOffer -> signal -> setRemote(answer)
• Trickle ICE candidates both directions
• DTLS handshake -> media flows

ICE CANDIDATE TYPES:
• host   : LAN direct
• srflx  : STUN reflexive (most NATs)
• relay  : TURN (symmetric NAT / strict fw, ~8-15%)

TOPOLOGY MATH:
• Mesh : n-1 uploads/client, n(n-1) total, $0 media infra,
         E2EE, dies >4-6 participants
• SFU  : 1 upload/client, server pays egress, simulcast,
         hundreds OK
• MCU  : transcode/composite server-side, 1up/1down,
         no E2EE, legacy bridges

DATA CHANNEL SETTINGS:
• Cursors/presence : ordered=false, maxRetransmits=0
• Files/chat       : reliable (default)

PRODUCTION MUSTS:
• STUN + TURN(tcp:443) + short-lived HMAC TURN creds
• Auth + validate on signaling messages
• Handle iceConnectionState failed -> restartIce()
• Perfect negotiation for glare
• getStats()-driven bitrate adaptation

INTERVIEW FORMULA:
• "Media is P2P; only signaling touches my servers"
• "Symmetric NAT = TURN required"
• "n(n-1) kills mesh past 5 people - SFU time"
```

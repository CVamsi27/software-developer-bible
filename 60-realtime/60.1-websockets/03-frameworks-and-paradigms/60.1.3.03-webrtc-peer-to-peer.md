# WebRTC Peer-to-Peer

For a video call, the browser captures a microphone or camera, creates a peer connection, and negotiates a route to the other endpoint — direct or relayed. "Peer-to-peer" does not mean a production call needs no servers: signaling, authentication, relay service and group conferencing can all require them.

```javascript
const peers = await connectLocalPeers((position) => console.log(position));
peers.outgoing.send(JSON.stringify({ sequence: 1, x: 120, y: 88 }));
// After observing the result: peers.close();
```

## Definition

**WebRTC** is a browser-supported set of APIs and protocols for sending real-time audio, video and application data between **peers**. The application supplies **signaling**: a trusted way for peers to exchange connection descriptions and connectivity information.

> **Textbook Definition:** WebRTC is a set of APIs and protocols for negotiating and transporting encrypted real-time media and data between peers, using connectivity establishment and optional relays. Signaling is supplied by the application.

## First Principles

Two browsers rarely have simple public addresses that accept unsolicited traffic — firewalls and address translation can block a direct connection. They must also agree on media formats and verify the endpoint whose encrypted transport they establish. For video, an obsolete frame may matter less than a fresh one; for a file, a missing byte cannot simply be ignored. So connection discovery, negotiation, transport security and reliability policy are separate mechanisms, and the application handles the cases where no usable route exists.

## How It Works

### 1. Match WebRTC to Interactive Media and Data

Use WebRTC for interactive media or data that benefits from its browser APIs, congestion handling and peer or relay transport. Use WebSocket when a server-authoritative application channel is sufficient; use a streaming delivery system when a large audience primarily watches and interactive latency is unnecessary. A direct media path can avoid an application media-server hop, but actual latency and cost depend on encoding, networks, relays and topology — never promise fixed millisecond latency or free media delivery, since relayed traffic and conferencing servers consume bandwidth.

### 2. Fit Signaling, Negotiation and Transport Together

```text
microphone/camera → MediaStreamTrack → RTCPeerConnection → remote media
application data → RTCDataChannel   → RTCPeerConnection → remote data
                                      ↑
                         application signaling exchanges descriptions
                         and connectivity candidates between endpoints
```

`getUserMedia()` requests device access under browser permission rules and returns media tracks. `RTCPeerConnection` negotiates and carries the connection; `RTCDataChannel` carries application messages. Camera access needs an appropriate secure context and user permission, and screen capture has its own permission and API behavior.

A **Session Description Protocol (SDP)** offer describes proposed media and data capabilities plus connection information; the answer selects compatible behavior. The caller sets its local offer; the receiver sets that offer as remote, creates and sets a local answer; the caller sets the answer as remote. Both ends need the corresponding descriptions before using the negotiated connection.

### 3. Discover a Route With ICE

**Interactive Connectivity Establishment (ICE)** gathers possible routes called candidates and tests candidate pairs. **STUN** (Session Traversal Utilities for NAT) helps discover a mapped address. **TURN** (Traversal Using Relays around NAT) supplies a relay allocation when a relay route is needed. A NAT is a network address translator; firewall and mapping behavior vary beyond simple historical "cone" labels.

| Candidate | Meaning | Boundary |
| ---------------- | ------------------------------------------ | --------------------------------------------------------------------- |
| Host | An interface-local route | Privacy controls may obscure addresses; not always reachable remotely |
| Server-reflexive | A mapped address discovered using STUN | Discovery does not guarantee another peer can reach it |
| Peer-reflexive | A route learned during connectivity checks | Not a separate signaling-server feature |
| Relay | A TURN allocation | Relay reachability, credentials, capacity and policy can still fail |

ICE selects a working route under its checks and priority rules. TURN is not "always works" — restrictive networks or a failed relay service can block it too, so test relay paths and measure their traffic share for your actual users. **Trickle ICE** sends candidates as they are gathered rather than waiting for all of them; a candidate can arrive before the recipient has set its remote description, so queue it until that description is ready, and never apply stale candidates from an earlier attempt blindly.

Media uses SRTP keys established through DTLS; data channels use SCTP over a protected transport, with configurable reliability and ordering — "all WebRTC is unreliable UDP" misses this distinction. A relay forwards packets, unlike a conferencing server that terminates a WebRTC connection: an ordinary selective forwarding server terminates transport encryption even when forwarding encoded media without decoding it. Trusted signaling and endpoint identity matter — encrypted transport alone does not establish that a caller joined the right private room.

### 4. Exchange a Position Between Two Local Peers

This browser-console fixture creates two peers inside one page. It uses no camera, signaling service, STUN or TURN. It demonstrates offer and answer ordering plus a data channel; it does **not** test internet traversal or production call security. Run it in a current browser on an HTTP localhost or HTTPS page. It waits for complete candidate gathering rather than trickle ICE, applies finite deadlines, and closes both peers after the exercise.

```javascript
async function waitFor(target, event, ready, timeoutMs = 5000) {
  if (ready()) return;
  await new Promise((resolve, reject) => {
    const done = () => {
      if (!ready()) return;
      cleanup();
      resolve();
    };
    const timer = setTimeout(() => {
      cleanup();
      reject(new Error(`${event} timed out`));
    }, timeoutMs);
    const cleanup = () => {
      clearTimeout(timer);
      target.removeEventListener(event, done);
    };
    target.addEventListener(event, done);
    done();
  });
}

async function connectLocalPeers(onPosition) {
  const caller = new RTCPeerConnection();
  const receiver = new RTCPeerConnection();
  const outgoing = caller.createDataChannel('position', {
    ordered: false, maxRetransmits: 0,
  });
  let incoming;
  let latest = -1;
  const close = () => { caller.close(); receiver.close(); };
  receiver.addEventListener('datachannel', ({ channel }) => {
    incoming = channel;
    channel.addEventListener('message', ({ data }) => {
      if (typeof data !== 'string' || data.length > 1024) return;
      try {
        const position = JSON.parse(data);
        if (!position || !Number.isSafeInteger(position.sequence) ||
            position.sequence <= latest ||
            !Number.isFinite(position.x) || !Number.isFinite(position.y)) return;
        latest = position.sequence;
        onPosition(position);
      } catch {
        // Discard a malformed position; it is not an authoritative command.
      }
    });
  });
  try {
    await caller.setLocalDescription(await caller.createOffer());
    await waitFor(caller, 'icegatheringstatechange',
      () => caller.iceGatheringState === 'complete');
    await receiver.setRemoteDescription(caller.localDescription);
    await receiver.setLocalDescription(await receiver.createAnswer());
    await waitFor(receiver, 'icegatheringstatechange',
      () => receiver.iceGatheringState === 'complete');
    await caller.setRemoteDescription(receiver.localDescription);
    await waitFor(outgoing, 'open', () => outgoing.readyState === 'open');
    await waitFor(receiver, 'datachannel', () => Boolean(incoming));
    await waitFor(incoming, 'open', () => incoming.readyState === 'open');
    return { outgoing, close };
  } catch (error) {
    close();
    throw error;
  }
}

const peers = await connectLocalPeers((position) => console.log(position));
peers.outgoing.send(JSON.stringify({ sequence: 1, x: 120, y: 88 }));
// After observing the result: peers.close();
```

The receiver ignores a position older than one it has applied. Each message is a complete position snapshot, so missing sequence 1 does not block sequence 2 — unsafe for dependent drawing strokes or file chunks, where a missing earlier record changes the result. `ordered: false` permits reordering and `maxRetransmits: 0` limits retransmission, but neither removes an already delivered old update; the application still checks sequence and age. For reliable file chunks, use the appropriate channel mode plus chunk identity, completion and integrity checks, and bounded `bufferedAmount` handling.

### 5. Add Media, Real Signaling and a Conferencing Topology

For a call, add the chosen local tracks before creating the initial offer. At the other endpoint, receive tracks through `track` events and attach them to media elements under autoplay and permission rules. Stop capture tracks when the user ends capture — closing a peer connection alone does not release camera and microphone tracks. Exchange descriptions through authenticated signaling: validate envelope shape and size, authorize both peers, route to the intended peer, reject stale negotiation messages, and handle malformed envelopes and permission errors without leaving abandoned connections.

During renegotiation, both peers can create an offer simultaneously. This **offer collision**, also called glare, needs a strategy such as the polite and impolite roles in the canonical perfect-negotiation reference. Assume one encoded stream per directed peer link; actual simulcast layers and subscriptions change these counts.

| Topology | Whole-system mechanism | Cost and trust boundary |
| ------------------------------- | ------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------- |
| Mesh | Each participant sends to each other participant | `n−1` outgoing streams per participant; `n(n−1)` directed streams overall; TURN may relay some links |
| Selective forwarding unit (SFU) | Each participant sends to a server that forwards selected streams/layers | Reduce repeated client uploads; server egress and each client's selected downloads still scale |
| Multipoint control unit (MCU) | A server decodes/mixes/composites media and sends combined output | Server compute increases; media is available at the mixing endpoint |

For five mesh participants, each sends four directed streams: 20 in total — arithmetic, not a universal five-person limit. Device CPU, resolution, upload bandwidth and relay usage determine the useful topology. Recording requires a stated consent, retention and access policy at the recording endpoint; a client MediaRecorder is not automatically a complete telehealth recording design.

### 6. Track Stats, Release Resources and Avoid the Classic Mistakes

Track connection and ICE state, route type, packet loss, round-trip time and bitrate through `getStats()`. Show clear permission, connecting, reconnecting and failed states. Test real devices and relay-only paths — a same-page fixture establishes neither NAT traversal nor media quality. Use `RTCRtpTransceiver.setCodecPreferences()` where supported and `RTCRtpSender.setParameters()` for applicable encoding controls; codec support, hardware acceleration and quality vary by device. Release tracks, peer connections, timers and signaling listeners on end or failure.

## Common Mistakes

- **Shipping STUN-only and declaring traversal solved.** Provide and exercise suitable relay routes for supported networks; protect issued relay credentials and control abuse.
- **Calling encryption automatic end-to-end privacy.** Establish trusted peers and inspect where transport is terminated in the chosen topology.
- **Applying ICE candidates before remote description.** Queue them for the matching negotiation, or deliberately use complete descriptions as the local fixture does.
- **Restarting on every disconnected state.** A transient interruption differs from failure. Use a timed recovery policy and negotiate ICE restart when appropriate; `restartIce()` still needs signaling.
- **Ignoring queued bytes.** Data-channel buffers can grow under a slow link. Set high/low water policies and stop or reduce production before memory grows without bound.
- **Treating cursor traffic like authoritative state.** Lossy complete snapshots fit presence; payments, durable edits and file completion need different contracts.

## Summary

WebRTC negotiates encrypted media and data transport between endpoints; the application supplies trusted signaling and recovery. ICE tests routes, STUN helps discovery and TURN can relay traffic. Choose mesh, SFU or MCU from measured resource and privacy requirements, and choose reliability by whether an obsolete or missing message can be discarded safely.

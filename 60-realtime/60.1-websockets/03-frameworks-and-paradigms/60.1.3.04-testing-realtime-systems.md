# Testing Real-Time Systems

## Definition

Real-time system testing checks live connection behavior, pushed updates and application recovery under timing, concurrency and network failures. It includes functional, load, resilience and long-running resource tests.

> **Textbook Definition:** Real-time system testing evaluates connection lifecycles, message behavior and state convergence under timing, concurrency and network faults, with explicit ordering, loss and recovery expectations.

An HTTP health check can succeed while a connected dashboard stops updating. To test that dashboard, prove that an authorized event reaches the intended client and that a disconnected client can recover the state promised by the application.

## First Principles

A connection can be open without carrying useful updates. A message can arrive twice or arrive after a timeout. A client can recover its transport while its display remains stale. Resources can accumulate across repeated connects even when every individual operation succeeds.

Therefore, tests need an oracle for correct application state, explicit deadlines and observation across a sequence of events. Testing one successful handshake does not establish delivery, recovery or capacity.

## Why Add These Checks?

Ordinary HTTP tests remain useful for commands, snapshots and authorization. Add protocol-aware clients for persistent event streams. A raw WebSocket client does not automatically speak Socket.IO, and a GraphQL WebSocket handshake needs the correct subprotocol and control messages. Use the matching library unless the protocol framing itself is under test.

Separate properties: default at-most-once live delivery can legitimately miss events during disconnect; an application with a durable recovery contract must restore the required state. Do not assert “no losses and no duplicates” without defining the delivery and effect semantics.

## How to Structure the Evidence

| Layer | Question | Evidence |
| -------------------- | -------------------------------------------------- | -------------------------------------------------------------------- |
| Focused unit test | Is a version/permission/retry decision correct? | Controlled clock and inputs |
| Protocol integration | Does a real client follow the server contract? | Valid/invalid operations, results, close codes and cancellation |
| Load and churn | Does the workload meet capacity objectives? | Ramp/hold/churn, latency, queues, failures and generator utilization |
| Fault and recovery | Does the promised state return after interruption? | Injected fault, durable record comparison and recovery deadline |
| Soak | Are resources retained across repeated work? | Comparable active load, cleanup checkpoints and resource trends |

Use a fake clock for isolated timer policy, with a real clock for actual socket integration unless the networking libraries support that clock model. Globally freezing timers around live sockets can stall heartbeats and reconnect behavior. Local integration proves protocol behavior; it does not replace network-path or capacity tests.

## Example: Smoke-Test the GraphQL Fixture

Run the [GraphQL chapter's server](60.1.3.02-graphql-subscriptions-live-queries.md) locally on port 4000. Save these tests as `subscription.test.mjs` in the same disposable package environment and run `node --test subscription.test.mjs`. The server's finite three-event source makes completion an observable contract.

This suite uses a real GraphQL WebSocket client, bounded waits and cleanup. It proves only this fixture's execution and permission behavior, not a live broker, durable replay or production capacity.

```javascript
import test from 'node:test';
import assert from 'node:assert/strict';
import { createClient } from 'graphql-ws';
import WebSocket from 'ws';

const query = `subscription($orgId: ID!) {
  orderUpdated(orgId: $orgId) { id status version }
}`;
async function collect(token, orgId) {
  const client = createClient({
    url: 'ws://127.0.0.1:4000/graphql',
    webSocketImpl: WebSocket,
    connectionParams: { authToken: token },
    retryAttempts: 0,
  });
  const results = [];
  let stop = () => {};
  try {
    await new Promise((resolve, reject) => {
      const timer = setTimeout(() => reject(new Error('Stream deadline')), 3000);
      const finish = (error) => {
        clearTimeout(timer);
        if (error) reject(error); else resolve();
      };
      stop = client.subscribe({ query, variables: { orgId } }, {
        next: (result) => results.push(result),
        error: (error) => finish(error),
        complete: () => finish(),
      });
    });
    return results;
  } finally {
    stop();
    await client.dispose();
  }
}

test('authorized stream has three ordered versions and completes', async () => {
  const results = await collect('alice-demo-token', 'org-1');
  assert(results.every((result) => !result.errors));
  assert.deepEqual(results.map((result) => result.data.orderUpdated.version), [1, 2, 3]);
  assert.deepEqual(results.map((result) => result.data.orderUpdated.status),
    ['ACCEPTED', 'PACKED', 'SHIPPED']);
});

test('authenticated user cannot select another organization', async () => {
  await assert.rejects(collect('alice-demo-token', 'org-2'),
    (error) => Array.isArray(error) &&
      error.some((item) => item.message === 'Forbidden organization'));
});

test('bad credential rejects the connection', async () => {
  await assert.rejects(collect('bad-token', 'org-1'),
    (error) => error.code === 4403);
});
```

A forbidden connection is observed as a close-code error in this protocol, not a legacy `connection_error` JSON message. A forbidden subscription is an operation error. The positive test also checks GraphQL result errors rather than assuming every `next` is successful data.

A raw protocol test must register its receive handler before sending the message that causes a response, maintain a bounded receive queue and clean up handlers on timeout/close. Repeated `once('message')` calls installed after sends can miss a fast response. Do not hide those races in undefined helpers and call the test deterministic.

## Design a Load Experiment

Write the target protocol, authentication, subscription scope, event source and expected state first. For example, authorized clients watch a room while an independent producer commits numbered messages. Wait until subscriptions are ready before publishing.

A useful workload separates connection ramp, steady concurrent clients, message fan-out, churn and slow consumers. Arrival rate and active concurrency are different quantities. Roughly, active clients equal arrival rate times mean session duration in a stable workload: 10 arrivals/second holding for 30 seconds gives about 300 active clients, not 20,000 merely because a configured maximum is 20,000.

Measure commit-to-apply latency if that is the product objective. Across hosts, wall-clock skew contributes error; synchronize and quantify it or use a measurement design that avoids comparing unrelated clocks. Merely putting a server timestamp in a payload does not remove skew. Report sample count, percentile, payload, audience and failure count together.

Watch the load generator's CPU, memory, network and socket limits. A saturated generator can imitate a server bottleneck. Measure its capacity rather than quoting a universal clients-per-worker number. Check the selected Artillery/k6 engine's current protocol support and configuration before running; WebSocket mode alone does not add GraphQL or Socket.IO semantics.

### Prove the slow-consumer policy

A busy producer should not make one lagging client consume unlimited server memory. Create a consumer that actually limits network reads or application processing, observe the relevant queue and cross its configured threshold. Ignoring messages in a callback may still allow the library to drain the network, so it is not necessarily a slow-network simulation.

For disposable positions, the policy might coalesce or drop old snapshots. For durable notifications, disconnect and resume from stored state. Assert the configured policy and the continued service for other clients, rather than requiring disconnection for every workload.

## Trace a Recovery Drill

Use an isolated test deployment with a known event set and fault target. This is a procedure to implement, not evidence that a drill has run:

1. Connect clients, verify authorization and confirm subscription readiness.
2. Commit records with stable IDs and versions; retain the authoritative expected set.
3. Interrupt one gateway or broker connection during publication.
4. Record which clients remain connected, which updates stop and whether buffers remain bounded.
5. Restore the dependency; let clients resume or fetch a snapshot under the application's contract.
6. Compare final state/effects with the durable oracle, including duplicate attempts, expired cursors and unauthorized replay.
7. Verify cleanup after clients disconnect and publish the measured recovery interval.

A live Redis Pub/Sub system should not be required to replay messages it never retained. A retained queue may repeat delivery after a crash; assert that repeated delivery does not repeat a business effect, rather than treating every duplicate packet as a failure. A stream consumer also needs pending-record recovery and retention rules; storage alone does not prove recovery.

## Real-World Decisions

For chat, check room isolation, command retry identity, missed-message history and ordering within the defined room sequence. For a dashboard of current values, verify convergence to an authorized snapshot rather than delivery of every intermediate tick. For a collaborative document, compare the final document under concurrent edits and dropped/repeated operations using its convergence algorithm.

For WebRTC, test signaling permissions separately from media behavior. Exercise different devices, permission denial, negotiation collisions, relay-only paths and interrupted networks. A localhost two-peer data-channel test cannot prove TURN connectivity, camera quality or internet latency.

## Common Mistakes

- **Testing only connect and receive.** Include malformed operations, cross-tenant access, expiry/revocation, cancellation and timeout paths.
- **Assuming sequences start at 1 for every stream.** Establish a baseline or cursor and order within the correct entity/partition domain.
- **Removing a fault and immediately claiming recovery.** Wait for observable subscription/state restoration under a deadline, then compare the result.
- **Sampling the wrong process.** `/proc/self/fd` in a newly executed shell reports that shell's descriptors, not the gateway's. Select the gateway PID or expose process metrics.
- **Starting the sampler after the load run finishes.** Run measurement concurrently, clean up forwarding/background processes and stop both at a finite deadline.
- **Declaring every RSS increase a leak.** Warmup, caches, allocation behavior and changed active load affect resident memory. Compare repeatable phases and live-object/handle evidence.
- **Presenting illustrative incidents as history.** Record actual fixture/tool/version and observed outcomes; proposed experiments remain proposed.

## Best Practices

Keep fast integration tests bounded and isolated by test-run identities. Use event/readiness signals instead of arbitrary sleeps for setup. Every connection, iterator, timer, process and port forward needs an owner and cleanup path, including failures.

Choose heavier load and soak durations from the deployment risk and expected retention cycles. Record baseline and plateau measurements at comparable load, then inspect post-disconnect resources. Treat missed measurements and unexercised provider paths as limitations, not green checks.

## Summary

Test live protocol behavior and final application state as separate properties. Use real compatible clients, explicit deadlines, controlled faults and a durable oracle for recovery. Capacity and resource evidence requires a measured workload and a load generator that can sustain it.

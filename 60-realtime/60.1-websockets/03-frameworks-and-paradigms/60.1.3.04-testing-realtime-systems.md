# Testing Real-Time Systems

## TL;DR

HTTP test tools miss the point of WebSocket systems: they model request/response, not thousands of held connections with churn, backpressure, and ordering guarantees. Real-time testing needs **connection-oriented load scenarios** (Artillery WS engines: connect rates, churn, message throughput), assertions on **backpressure and message order**, **chaos drills** (kill Redis pub/sub mid-stream), **soak tests** that catch fd/memory leaks, and a fast, deterministic **socket smoke suite** wired into CI.

## Definition

Real-time system testing verifies properties HTTP never exercises: long-lived connection state, server push latency, delivery guarantees under partial failure, and resource behavior across thousands of concurrent sockets. It layers four disciplines — functional smoke tests (protocol correctness), load tests (connect storms, throughput), resilience tests (dependency death mid-stream), and soak tests (leak detection over hours) — each with metrics HTTP testing lacks (open-socket counts, per-message latency percentiles, send-buffer depth).

```text
REALTIME TEST LAYERS
┌─────────────────────────────────────────────────────┐
│ SMOKE  (CI, seconds)   connect/subscribe/receive     │
│ LOAD   (nightly)       connect rate, churn, msg/s    │
│ CHAOS  (weekly)        kill redis pubsub mid-stream  │
│ SOAK   (pre-release)   hours at steady load -> leaks │
└─────────────────────────────────────────────────────┘
```

## Why it matters

A WebSocket gateway that passes every HTTP check can still fall over on Tuesday: file descriptors exhausted by leaked dead sockets, GC pauses stacking because 50k subscriptions hold closures, or silent message reordering after a Redis failover. Interviews probe this as systems thinking: "How would you test your chat backend?" expects named failure classes and tooling — not "we have unit tests". Teams skipping realtime-specific testing discover these bugs in production, where symptoms (random disconnects, stale feeds) are hardest to attribute.

## Why Do We Need It?

- **Statefulness**: each socket is server memory + an fd; behavior depends on *history*, which stateless HTTP tests never model.
- **Churn is the workload**: production traffic is constant connect/disconnect cycles, not steady request rates; only churn scenarios reveal fd leaks and adapter desync.
- **Ordering and delivery guarantees are contracts**: chat must be ordered; cursors need not be. Nothing tests these except message-sequence assertions.
- **Backpressure kills silently**: slow consumers balloon send buffers until OOM; you must test that lagging clients get dropped rather than sinking the node.
- **Dependency coupling**: pub-sub backends (Redis) sit in the hot path; their failure mode mid-stream differs completely from HTTP dependency failures.
- **CI needs speed**: full-scale load rigs are nightly; developers need a 30-second smoke gate catching protocol breakage per PR.

## How It Works

### Why HTTP tools miss

Request/response tools (ab, most CI perf checks) measure: open → send → read → close. They cannot express: hold N sockets open while subscribing to different channels, emit events from an admin client, measure push latency distribution, simulate disconnect storms. Even k6/Artillery's HTTP modes lack subscribe semantics — you need WS-native scenario engines.

### The four test types mapped to tooling

| Type | Tool | Duration | Key metric |
|------|------|----------|------------|
| Smoke | jest + `ws` client | seconds | connect+receive works |
| Load/churn | Artillery WS / k6 ws | minutes | p95 push latency @ target conn count |
| Chaos | Artillery + docker kill scripts | minutes | recovery time, no dupes/losses |
| Soak | k6/Gatling sustained profile | 4-24h | RSS trend, fd count trend |

### Backpressure assertion strategy

Server-side, expose lag metrics; test-side, create a deliberately slow consumer and assert the system's policy:

```text
HEALTHY BACKPRESSURE BEHAVIOR
fast producer ──▶ server ──▶ normal clients : real-time delivery
                     │
                     └──▶ slow client buffer grows
                          -> crosses threshold (e.g., 1MB or 5s lag)
                          -> DISCONNECT slow client (policy!)
                          -> other clients unaffected

BROKEN (what tests must catch)
                     └──▶ buffer grows unbounded -> node OOMs,
                          EVERY client on that process dies
```

### Chaos: killing the backbone mid-stream

The scenario: 10k subscribers receiving order updates; kill Redis; assert (a) clients stop receiving but stay connected or reconnect cleanly, (b) no duplicates after restore, (c) no lost messages if using streams-based replay, (d) memory returns to baseline.

## Code Examples

### CI smoke suite with raw `ws` (fast, deterministic)

```typescript
import { WebSocket } from 'ws';

const WS_URL = process.env.TEST_WS_URL ?? 'ws://localhost:4000/graphql-ws';

describe('gateway smoke', () => {
  let client: WebSocket;

  afterEach(() => client?.close());

  it('connects, authenticates, and receives a pushed event', async () => {
    client = new WebSocket(WS_URL);
    await waitForOpen(client);

    client.send(JSON.stringify({
      type: 'connection_init',
      payload: { authToken: testJwt },
    }));
    expect(await nextMessage(client)).toMatchObject({ type: 'connection_ack' });

    client.send(JSON.stringify({
      id: '1',
      type: 'subscribe',
      payload: { query: 'subscription { ping }' },
    }));

    // Trigger via admin channel - proves end-to-end push
    await triggerTestEvent({ channel: 'ping' });

    const msg = await nextMessage(client, { timeoutMs: 5000 });
    expect(JSON.parse(msg.toString())).toMatchObject({
      type: 'next',
      payload: { data: { ping: expect.any(String) } },
    });
  }, 10_000);

  it('rejects invalid auth tokens', async () => {
    const bad = new WebSocket(WS_URL);
    await waitForOpen(bad);
    bad.send(JSON.stringify({ type: 'connection_init', payload: { authToken: 'junk' } }));
    const reply = JSON.parse((await nextMessage(bad)).toString());
    expect(['connection_error', 'error']).toContain(reply.type);
    bad.close();
  });
});

function waitForOpen(ws: WebSocket): Promise<void> {
  return new Promise((resolve, reject) => {
    ws.once('open', resolve);
    ws.once('error', reject);
  });
}

function nextMessage(
  ws: WebSocket,
  opts: { timeoutMs?: number } = {},
): Promise<string> {
  return new Promise((resolve, reject) => {
    const timer = setTimeout(
      () => reject(new Error('message timeout')),
      opts.timeoutMs ?? 3000,
    );
    ws.once('message', (data) => {
      clearTimeout(timer);
      resolve(data.toString());
    });
  });
}
```

### Artillery scenario: connect storm + churn + throughput

```yaml
# artillery/ws-load.yml
config:
  target: "wss://staging.example.com/ws"
  phases:
    # 1. Connect storm: how does handshake scale?
    - duration: 60
      arrivalRate: 100          # 100 new connections/sec
      name: "connect ramp"
    # 2. Steady hold: subscriptions active
    - duration: 300
      arrivalRate: 10
      maxVusers: 20000
      name: "steady subscribe"
    # 3. Churn: rapid connect/disconnect cycles
    - duration: 120
      arrivalRate: 200
      maxVusers: 5000
      name: "churn storm"
  ws:
    headers:
      Authorization: "Bearer {{ $env.LOAD_JWT }}"
  processor: "./ws-hooks.js"

scenarios:
  - engine: ws
    flow:
      - function: "subscribeOrders"
      - think: 30                # hold subscription open
      - function: "checkOrderedMessages"
```

```javascript
// ws-hooks.js
const seen = new Map(); // clientId -> last sequence number per stream

module.exports = {
  subscribeOrders(context, events, done) {
    context.ws.on('message', (raw) => {
      const msg = JSON.parse(raw.toString());
      if (msg.type === 'order') {
        const last = seen.get(context.vars.clientId) ?? 0;
        // ORDERING ASSERTION: sequences must increase without gaps
        if (msg.seq !== last + 1) {
          events.emit('counter', 'order.gap_or_reorder', 1);
        }
        seen.set(context.vars.clientId, msg.seq);
        context.vars.lastReceivedAt = Date.now();
        events.emit('counter', 'messages.received', 1);
      }
    });
    context.ws.send(JSON.stringify({ action: 'subscribe', channel: 'orders' }));
    return done();
  },

  checkOrderedMessages(context, events, done) {
    const idle = Date.now() - (context.vars.lastReceivedAt ?? 0);
    if (idle > 10_000) events.emit('counter', 'starved_subscribers', 1);
    return done();
  },
};
```

Run nightly against staging; alert when p95 of *push* latency (server event → client receipt) exceeds budget — a metric no HTTP test produces.

### Chaos drill: kill Redis mid-stream

```typescript
import { execSync } from 'node:child_process';
import { WebSocket } from 'ws';

describe('pubsub failure drill', () => {
  it('recovers without duplicate delivery after redis restart', async () => {
    const clients = await spawnSubscribers(500);   // connected, subscribed
    const feed = startPublisher(50);               // seq-numbered events

    await sleep(5000);
    execSync('docker kill test-redis');            // BOOM mid-stream

    const duringOutage = await observe(clients, 10_000);
    expect(duringOutage.errors).toEqual([]);       // no crashes, clean errors

    execSync('docker start test-redis');
    await sleep(15_000);                           // reconnect window

    const report = await drainAndAnalyze(clients, feed.stop());
    expect(report.duplicateSequences).toEqual([]);
    expect(report.maxGap).toBeLessThanOrEqual(feed.expectedGapDuringOutage());
    expect(processMemoryOf('gateway')).toBeLessThan(baselineMb * 1.2);
  }, 120_000);
});
```

What each assertion protects: no-crash (resilience), no-dupes (idempotent resubscribe logic), bounded gaps (replay semantics documented honestly), memory recovery (no leak from zombie iterators).

### Soak test for fd leaks

```bash
#!/usr/bin/env bash
# soak.sh - run overnight; graph results in the morning
set -euo pipefail
DURATION_HOURS=${1:-8}

kubectl port-forward svc/gateway 4000:4000 &
sleep 3

npx artillery run \
  --output soak-report.json \
  --config <(yq '.config.phases = [
      {"duration": "'"$((DURATION_HOURS*3600))"'",
       "arrivalRate": 5, "maxVusers": 8000, "name": "soak"}]' \
      artillery/ws-load.yml)

# While running, sample resource counters every minute:
while true; do
  date +%s >> soak-metrics.log
  kubectl exec deploy/gateway -- sh -c \
    'ls /proc/self/fd | wc -l' >> soak-metrics.log          # fds
  kubectl top pod -l app=gateway --no-headers >> soak-metrics.log
  sleep 60
done
```

Verdict rule: monotonic fd growth across a flat-vuser phase = leak (missing close handler, unsubscribed-but-open iterator). RSS sawtoothing ±20% is fine; staircase growth = heap leak.

## Real-World Use Cases

1. **Chat platform pre-launch audit** — churn storm at 200 connects/sec exposed fd leak in disconnect handler (room membership map never cleaned); fixed before launch, verified by 12-hour soak showing flat fd count.
2. **Trading dashboard SLA defense** — customer disputed "data stops sometimes"; ordered-message counters in load rig reproduced gap patterns correlated with Redis sentinel failovers; fix was streams-based replay plus client resume tokens.
3. **Collab editor scaling review** — connect-ramp test found the room-broadcast path went synchronous at ~6k sockets per node (O(n²) fan-out loop); rewrite to batched broadcast lifted ceiling to 40k.
4. **CI gate for gateway PRs** — 45-second smoke suite (auth, subscribe, receive, malformed-frame handling) runs per PR; caught a graphql-ws major upgrade breaking `connection_ack` shape before merge.
5. **Game backend chaos program** — weekly automated drills kill one gateway pod and the Redis primary alternately; recovery-time budget (30s to full subscription restoration) enforced as a release criterion.

## Common Mistakes

```javascript
// BAD: asserting only that "a message arrived" - no ordering, no gaps
let received = false;
ws.on('message', () => { received = true; });
await waitFor(() => received);

// GOOD: sequence-aware assertions
ws.on('message', (raw) => {
  const { seq } = JSON.parse(raw.toString());
  if (seq !== lastSeq + 1) failures.push({ expected: lastSeq + 1, got: seq });
  lastSeq = seq;
});
expect(failures).toEqual([]);
```

```yaml
# BAD: load test models HTTP habits - short-lived requests
phases:
  - duration: 60
    arrivalRate: 500        # 500 connects/sec, immediately closed
    # measures nothing about held-socket reality

# GOOD: three distinct phases - ramp, HOLD (the real workload), churn
phases:
  - { duration: 60,  arrivalRate: 100 }
  - { duration: 300, arrivalRate: 10, maxVusers: 20000 }
  - { duration: 120, arrivalRate: 200, maxVusers: 5000 }
```

Other frequent errors:

- **Testing against localhost**: loopback has no loss/jitter; even basic staging reveals timeout misconfigs invisible locally.
- **No time bounds on waits**: unbounded `waitFor` turns any regression into a hung CI job instead of a red test.
- **Shared mutable client state across parallel tests**: two suites subscribing to the same test channel steal each other's events; namespace channels per test run.
- **Soaking too little load**: 50 vusers for 8h proves nothing about leaks that manifest at 8k sockets; soak at realistic concurrency.
- **Ignoring clock skew in latency math**: measuring push latency across machines requires NTP-synced hosts or server-timestamped events.

## Best Practices

1. Ship a deterministic smoke suite (<60s) running per PR: auth, subscribe, receive, error paths, malformed frames.
2. Model production shape in load tests: ramp + hold + churn phases, not single-phase request floods.
3. Assert protocol-level properties — ordering, gaps, duplicates, starvation — not just connectivity.
4. Include a deliberate slow-consumer scenario proving backpressure policy (disconnect threshold) works.
5. Automate chaos drills for the pub-sub backbone and pod kills; publish recovery times.
6. Soak at realistic concurrency before major releases; watch fd count and RSS trends, not just pass/fail.
7. Track first-class realtime metrics in every environment: current sockets, connects/sec, push-latency percentiles, send-buffer depths.

## Performance Considerations

Load rigs themselves saturate: one Artillery worker handles roughly 10-30k sockets depending on message rate — shard workers (`--count`) and aggregate counters, or numbers lie. Run load tests from separate network zones than staging services to avoid NIC contention distorting latency. Keep smoke suites free of sleeps — event-driven waits keep them fast enough for PR gates. For soak analysis, sample at low frequency (per-minute) to avoid observer overhead on large fleets. Finally, calibrate: record one production day's connect-rate/message-volume histogram and parameterize nightly runs from it — synthetic shapes drift from reality within weeks otherwise.

## Summary

- HTTP test tooling cannot express held connections, churn, subscriptions, or push latency — use WS-native engines (Artillery ws, k6).
- Structure load tests as ramp → hold → churn; the hold phase is your actual production workload.
- Assert semantic properties: message ordering/gaps/duplicates, subscriber starvation, backpressure-driven disconnects.
- Chaos-test the backbone: killing Redis mid-stream validates reconnection, replay honesty, and iterator cleanup.
- Soak tests catch what functional tests cannot see: fd leaks and heap growth visible only in hour-scale trends.
- A fast deterministic smoke suite in CI prevents protocol regressions while heavier rigs run nightly.

• Kill backbone mid-stream

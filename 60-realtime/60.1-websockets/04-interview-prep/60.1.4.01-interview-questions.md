# WebSockets and Real-Time Interview Questions

## Definition

This bank contains 30 authored prompts and their follow-ups. Use it after the learning chapters and section revision companions. It is practice material, not a measured list of employer question frequency or a guarantee of interview success.

## First Principles

A useful answer must connect the live channel to authoritative state, permissions and recovery. Start with the concrete workload and required outcome, trace one update through failure, then explain which mechanism preserves the contract.

## Why Do We Need It?

These prompts progress from protocol mechanics through implementation to system design. For each answer, state the ordering/delivery domain, distinguish transport progress from business commit and name the evidence you would gather. Use actual experience where supported; label hypothetical designs as designs.

## How It Works

Answer aloud before reading. Use the linked canonical examples when a mechanism is unclear. Preserve the follow-up as a separate challenge rather than treating a remembered definition as sufficient.

## Deep-Dive Answers

### Fundamentals (1–10)

**Q1: What are WebSockets and how do they differ from HTTP?**

**Answer:** WebSocket supplies a full-duplex application channel after negotiation. HTTP uses request/response semantics but can reuse connections, multiplex requests and carry streaming responses. Neither protocol has a universal latency advantage: network distance, payload and application work matter. A browser must wait for WebSocket open before sending, and must bound pending bytes. For a predominantly one-way update feed, SSE plus HTTP commands may be simpler. See the [protocol and bounded echo example](../01-transports/60.1.1.01-websockets-overview.md).

**Follow-up:** When would you choose SSE over WebSockets?

**Q2: Explain the WebSocket handshake process.**

**Answer:** In the common HTTP/1.1 flow, the client requests an upgrade on an already established connection with version and a random key. A successful server response is 101 with the expected acceptance value; it switches that connection to WebSocket framing. It does not establish a new TCP connection afterward. The acceptance value combines the key with the protocol GUID through SHA-1 and Base64, demonstrating the expected handshake; it is not a credential or encryption key. Authenticate and authorize separately. Extended-connect variants exist for newer HTTP versions.

**Follow-up:** What is the purpose of `Sec-WebSocket-Key`?

**Q3: What is Socket.io and how does it differ from raw WebSockets?**

**Answer:** Socket.IO adds its own event protocol over Engine.IO transports, including configured polling/WebSocket behavior, namespaces, rooms, acknowledgments and reconnection. It is not wire-compatible with a plain WebSocket endpoint. Raw WebSocket already supports binary messages. Choose Socket.IO for its connection/event conventions and ecosystem, or plain WebSocket for interoperability and control. Transport reconnection does not replay all missed messages or guarantee one business effect. Trace the [authorized chat and lost acknowledgment](../01-transports/60.1.1.03-socket-io.md).

**Follow-up:** When would you use raw WebSockets over Socket.io?

**Q4: What are Server-Sent Events (SSE) and when should you use them?**

**Answer:** SSE carries a server-to-client event stream over HTTP. Native EventSource reconnects and can send Last-Event-ID, but the server must retain and authorize events to replay from that cursor. It must detect an expired cursor and request resynchronization rather than silently skip data. Use ordinary HTTP for client commands. Ensure proxy buffering, timeouts, connection limits and backpressure match the deployment; SSE is not guaranteed to cross every firewall. The [complete SSE fixture](../01-transports/60.1.1.02-server-sent-events.md) covers cleanup and bounded replay.

**Follow-up:** How does SSE handle reconnection?

**Q5: What is the difference between WebSockets and HTTP Long Polling?**

**Answer:** Long polling holds an HTTP request until data or a timeout is available, then the client issues another request. It need not open a new TCP connection each time. WebSocket negotiates one live two-way channel instead. Compare request/header work, proxy support, authentication and the actual event rate. Long polling needs cancellation, bounded retry and a cursor or snapshot boundary between requests. Avoid an unhandled recursive retry loop that immediately retries every error. Socket.IO polling sessions across nodes need affinity.

**Follow-up:** What are the scaling challenges with long polling?

**Q6: How do you handle WebSocket reconnection?**

**Answer:** Use a finite retry policy with capped exponential backoff and random jitter. Distinguish transient transport failure from deliberate close, authentication rejection and permanent policy failure; wasClean alone is not a retry decision. Cancel retry timers when the owning view closes and avoid accumulating handlers. After reconnect, reauthenticate, reauthorize subscriptions and recover history or current state. Retried durable commands reuse operation IDs and reconcile uncertain outcomes. Connection recovery without application-state recovery can leave a visually connected but stale screen.

**Follow-up:** How do you handle missed messages during reconnection?

**Q7: What are WebSocket rooms and how do they work?**

**Answer:** Rooms are a Socket.IO library feature, not a native WebSocket protocol field. Within a namespace, the server maintains sets of sockets for scoped broadcasts. A room name is not permission: check membership policy before joining, sending and replaying. socket.to(room) excludes the sender, while namespace.to(room) includes all matching members. Socket.IO leaves rooms on disconnect, but application presence and external subscriptions still need cleanup. Across nodes, use a compatible adapter and account for missed live publications.

**Follow-up:** How do you track room membership at scale?

**Q8: What are WebSocket namespaces?**

**Answer:** Socket.IO namespaces separate event handlers, middleware and rooms; a client Manager can multiplex namespaces over one transport connection. Rooms group sockets inside a namespace. Use a namespace for a distinct application/event policy and rooms for authorized audiences such as teams or documents. Authenticate each protected namespace and authorize its actions. Namespace separation itself does not make data private, and a /chat room does not automatically share membership with a similarly named /admin room.

**Follow-up:** When would you use namespaces vs rooms?

**Q9: How do you secure WebSocket connections?**

**Answer:** Use TLS, verified sessions, runtime shape/size validation, object/action permissions, connection and event budgets, and bounded queues. For cookie-authenticated browser connections, validate Origin under the application policy to reduce cross-site WebSocket hijacking; browser CORS for HTTP polling is not a complete WebSocket access-control mechanism. Non-browser clients can choose Origin, so it cannot prove identity. Handle expiry/revocation during long connections and stop private outbound subscriptions when access is removed. Avoid credentials in URLs and logs.

**Follow-up:** How do you prevent cross-site WebSocket hijacking?

**Q10: What is the WebSocket frame structure?**

**Answer:** A frame includes FIN, reserved bits, opcode, mask flag, payload length and optional extended length/masking key. FIN marks the last fragment; opcode distinguishes data, continuation and control frames. Message and frame boundaries differ because a message can be fragmented. Client-to-server frames are masked with a fresh masking key; server-to-client frames are not. Masking protects intermediaries from chosen byte patterns, not confidentiality or authentication. Control frames have stricter size/fragmentation rules. Use a protocol library rather than implementing framing casually.

**Follow-up:** Why must client-to-server messages be masked?

### Implementation and Operations (11–20)

**Q11: How do you scale WebSockets across multiple servers?**

**Answer:** Balance new connections across gateways and route events to every interested gateway's local clients. A live WebSocket stays on its chosen backend; Socket.IO polling spans requests and needs affinity. Configure the chosen adapter before accepting traffic and await its Redis clients' readiness. The ordinary Redis Pub/Sub adapter forwards live room events but stores no history and cannot replay a missed publication. Measure broker bandwidth, hot rooms and per-client buffers as well as connection count. See the [two-gateway trace](../02-architecture-and-scaling/60.1.2.02-scaling-patterns.md).

**Follow-up:** What are the limitations of Redis Pub/Sub at scale?

**Q12: How do you handle message ordering in distributed WebSockets?**

**Answer:** First define the ordering domain: one room, entity, partition or whole system. Allocate sequence/version through an authority appropriate to that domain; independent process counters do not create a shared total order. TCP ordering covers one live connection, not disconnected periods or independent publishers. Vector clocks can identify causal relationships, including concurrent updates, but do not automatically select a total order. Repeated or missing versions need a deduplication/recovery rule. CRDTs address convergence through defined merge semantics, not merely another sequence format.

**Follow-up:** When would you use CRDTs instead of sequence numbers?

**Q13: What is backpressure and how do you handle it?**

**Answer:** Backpressure arises when accepted work grows faster than downstream consumption. Bound queued bytes/items and choose semantics: coalesce replaceable snapshots, drop obsolete presence, slow admission or disconnect for recoverable history. Arbitrary dropping is unsafe for dependent deltas and durable commands. Browser WebSocket exposes bufferedAmount but no standard bufferedAmountChange event; inspect it through a bounded policy. RTCDataChannel has bufferedamountlow, a different API. Handle send/processing failures and reset processing state during cleanup. A local send completion is not a durable receiver acknowledgment.

**Follow-up:** What are the trade-offs between dropping vs buffering messages?

**Q14: How do you implement real-time notifications?**

**Answer:** Persist important notifications with stable IDs and authorized per-user retrieval; live room pushes are an acceleration path. Derive the user from a verified session, then join its server-selected audience. A client-supplied userId must not grant access to another user's room. Decide whether read status is per account or device and handle multiple tabs. Offline clients fetch retained unread history or a snapshot with a cursor; live Redis Pub/Sub alone cannot deliver publications made while they were absent.

**Follow-up:** How do you handle offline users?

**Q15: How do you test WebSocket applications?**

**Answer:** Use the compatible protocol client, attach listeners before triggering responses, wait for observable subscription readiness and give every wait a deadline. Verify positive data, malformed input, cross-tenant rejection, expiry, cancellation, retry identity and state recovery. A Socket.IO client does not expose the server's room set; test permission and actual delivery instead. Clean up sockets, iterators, timers and servers on failure. Separate loopback protocol checks from measured load, slow consumers, network faults and soak evidence. The [testing chapter](../03-frameworks-and-paradigms/60.1.3.04-testing-realtime-systems.md) includes a runnable smoke suite.

**Follow-up:** How do you test reconnection behavior?

**Q16: How do you handle WebSocket authentication?**

**Answer:** Verify a supported credential/session during connection acceptance, then enforce current operation and object permissions. JWT is one option, not a WebSocket requirement; validate the applicable signature, issuer, audience and expiry policy when using it. Do not assume a refreshed token updates an already authenticated socket: define reconnect or reauthentication behavior and resubscribe only after success. Revoke outbound private access as well as incoming commands. Prefer an explicit session-storage policy rather than recommending localStorage without considering script access and browser threats.

**Follow-up:** How do you handle token expiration during long connections?

**Q17: What is the difference between polling, long polling, SSE, and WebSockets?**

**Answer:** Polling repeatedly fetches current state; long polling waits for an update or timeout; SSE streams one-way server events; WebSocket carries two-way messages on a negotiated live channel. HTTP transports may reuse connections, and SSE/long polling do not impose a universal latency class. Choose by direction, update frequency, proxy/browser behavior, authentication, resource use and recovery requirements. A server-push channel still needs an authorized current-state or replay contract. Do not choose the protocol from invented fixed latency tables.

**Follow-up:** How do you choose between these technologies?

**Q18: How do you handle binary data in WebSockets?**

**Answer:** Browser WebSocket sends strings, Blob, ArrayBuffer or buffer views and receives binary as Blob or ArrayBuffer according to binaryType. A Node ws handler supplies data plus an isBinary flag. Wait until the connection is open, cap payload size and validate binary framing, type and declared lengths. Byte order and view offsets matter when interpreting typed data; transmitting an entire backing buffer can include unrelated bytes. Choose Blob for suitable browser file/media handling or ArrayBuffer for direct byte processing. Neither grants validation or compression automatically.

**Follow-up:** When would you use ArrayBuffer vs Blob?

**Q19: How do you implement rate limiting for WebSockets?**

**Answer:** Limit connection creation separately from message actions. A connection middleware runs on connection acceptance, not for every emitted command. Use a per-account/action budget after authentication, with an appropriate pre-auth network budget as well. Socket-ID-only budgets are reset by reconnecting. Token buckets can permit controlled bursts; sliding windows account for recent requests. Bound and expire limiter storage. Across nodes, make the shared decision atomic or document a local approximation and outage behavior; define retry advice without pretending admission guarantees success.

**Follow-up:** How do you handle rate limiting across multiple servers?

**Q20: What are WebSocket subprotocols?**

**Answer:** A WebSocket subprotocol is an application protocol selected from the client's offered names during the handshake. The selected value appears in ws.protocol; it is separate from transport framing. The graphql-ws library implements graphql-transport-ws; legacy subscriptions-transport-ws used graphql-ws. Those names are not interchangeable. A raw WebSocket cannot speak Socket.IO merely by offering socket.io or a GraphQL protocol string. In current Node ws, the offered protocols collection is a Set, so use has rather than Array.includes if implementing selection.

**Follow-up:** How do you implement GraphQL subscriptions with WebSockets?

### System Design (21–30)

**Q21: Design a chat system supporting 10 million concurrent users.**

**Answer:** Clarify whether ten million means users, active sockets or simultaneous sends. Estimate peak connections, sessions per user, event rate, payload, audience distribution, retention and regional objectives. Separate durable command acceptance/history from connection gateways and live fan-out. Partition ordering by room/entity, address hot rooms and route cross-node audiences. Define repeat-command handling, missed-event recovery, slow-client policy, failure headroom and reconnect surge control. Select stores from access patterns and measured capacity, not a compulsory Redis/Kafka/Cassandra shopping list. Show the commit-to-publication crash boundary and how recovery closes it.

**Follow-up:** How do you handle message ordering at this scale?

**Q22: How do you implement real-time collaboration (Google Docs style)?**

**Answer:** Choose an actual OT or CRDT algorithm and explain its convergence conditions, identity/version model and offline behavior. OT transforms operations against relevant concurrent operations; CRDTs use defined replicated data/operation rules. A partial insert-transform function labeled CRDT proves neither. Separate durable document operations, snapshots/history, undo and compaction from disposable cursor presence. Authenticate document access and reauthorize during the session. Test concurrent edits, deletes, retries, reordering and offline merge against the final document oracle. The [canonical collaboration case study](../../../30-architecture/30.2-system-design/02-case-studies/30.2.2.22-real-time-collaboration.md) supplies the full model.

**Follow-up:** What are the trade-offs between OT and CRDTs?

**Q23: How do you handle WebSocket connections during deployment?**

**Answer:** Remove the node from readiness/new admission, decide accepted-work completion under a deadline, notify/close live connections and let clients recover elsewhere with jitter. Socket.IO close actively closes its connections; calling it before notifications and then waiting for a drain does not implement the intended order. Track in-flight business work separately from socket count, cancel cleanup timers and enforce a hard deadline. You do not migrate a live socket between processes: establish a new one, reverify access and reconstruct state from durable history or snapshots.

**Follow-up:** How do you handle session migration between servers?

**Q24: How do you monitor WebSocket connections in production?**

**Answer:** Track current connections as a gauge; connection attempts, messages and failures as counters; and a clearly named latency distribution as a histogram. Distinguish handler time, publication lag, transport acknowledgment and client apply time. Include buffer pressure, oldest replay/outbox age and reconnect rate. Bound event/namespace labels and avoid user IDs or arbitrary client event names. Instrumenting socket.emit alone misses other broadcast paths and does not measure delivery. Alert on the latency/recovery objective and sustained resource pressure, using actual workload baselines.

**Follow-up:** How do you set up alerting for WebSocket issues?

**Q25: How do you handle WebSocket in microservices?**

**Answer:** A connection gateway can accept explicitly allowed event contracts, authenticate the user and call the owning business service. Do not forward arbitrary event names into internal service actions. Carry authorized actor/tenant context, stable operation identity, deadline and trace context, then define the response/acknowledgment checkpoint. Services own durable state; gateways own local live sockets. Brokers or adapters route committed updates back to interested gateways. A shared consumer group is work distribution, not automatic all-gateway fan-out. Choose sync commands versus queued work from the business contract.

**Follow-up:** How do you handle state in stateless microservices?

**Q26: How do you implement WebSocket message persistence?**

**Answer:** Choose an authoritative store and retention/access model. Ordinary message tables plus a transactional outbox can be sufficient; persisting messages is not automatically event sourcing. Separate acceptance, live publication and query projection to avoid uncoordinated dual writes. Stable IDs and uniqueness protect repeated commands. An ordered room cursor or suitable stable pagination key supports recovery, with permission checks and explicit cursor expiry. If using a retained log as authority, define projection rebuild and schema evolution. Replay ordering follows its declared partition/entity domain, not arbitrary timestamps alone.

**Follow-up:** How do you handle message ordering during replay?

**Q27: How do you optimize WebSocket performance?**

**Answer:** Measure the actual bottleneck before changing encoding or topology. Smaller payloads, coalesced snapshots and narrow audiences can reduce work. Compression saves bytes at CPU/memory cost and needs suitable security assessment; binary encoding is not universally faster. Batching adds latency and needs byte/count bounds, timer cleanup and open-socket checks. Use the same TLS, payload, audience and slow-client workload for comparisons. Record latency percentiles, queue growth, CPU, memory and egress. Additional server-to-server connections do not fix a hot ordered entity by themselves.

**Follow-up:** How do you measure WebSocket performance?

**Q28: How do you handle WebSocket in a serverless environment?**

**Answer:** A managed WebSocket service can own the persistent connection while short-lived functions handle connect and message events. Store verified identity, current subscription permissions and connection IDs with expiry/cleanup; do not accept a query-string userId as identity. Server-to-client sends use the service's management interface and must handle stale connections, throttling and partial failures. Functions do not inherit a global in-memory room map. Assess current service limits, regional behavior, ordering, acknowledgment semantics and cost for the measured workload. A durable room actor is another ownership model with different limits.

**Follow-up:** How do you handle connection state in serverless?

**Q29: How do you implement WebSocket with GraphQL subscriptions?**

**Answer:** Use a schema with a subscription source iterator, a matching transport protocol and a compatible client. In current graphql-ws 6, useServer imports from graphql-ws/use/ws and the wire protocol is graphql-transport-ws. Authenticate connection acceptance, build operation context, authorize requested scope and check continuing event access. Handle GraphQL result errors, operation errors and close codes separately. Cancel abandoned operations and bound queued work. Reconnection alone does not replay missed results. The [complete local subscription example](../03-frameworks-and-paradigms/60.1.3.02-graphql-subscriptions-live-queries.md) demonstrates these boundaries.

**Follow-up:** How do you handle subscription filtering?

**Q30: How do you handle WebSocket in a multi-region deployment?**

**Answer:** Route new connections to a suitable healthy region, while assigning durable state and ordering ownership deliberately. A user can have sockets in several regions, so one unexpired user-to-region string is not sufficient ownership tracking. Define cross-region event transport, duplicate identities, lag, residency, failover and split-brain prevention. Independent regional Redis Pub/Sub services do not replicate publications merely because their channel names match. Live failover requires reconnect and authorized state recovery. Compare active/passive or multi-writer trade-offs against consistency and latency objectives; geography does not decide them automatically.

**Follow-up:** How do you handle data consistency across regions?

## Summary

An effective senior answer states the workload and invariant, traces the event path, explains failure and recovery, and compares measured trade-offs. Practice all original prompts and follow-ups; reproduce the linked mechanisms rather than memorize library names.

# Judgment Calls & Ambiguity: Deciding Under Incomplete Data

## Definition

**Judgment under ambiguity** means choosing an action when useful information is missing and the consequences matter. Explain what was unknown, what you could learn, who owned the decision, and what would make you revise it.

## First Principles

Information takes time or resources to obtain. The useful question is whether a specific new fact could change the choice enough to justify that cost. When consequences cannot be undone, prevention deserves more attention; when a bounded experiment is safe, feedback can supply the missing information.

## Why it matters

Decision frameworks make an explanation inspectable. They do not guarantee a good outcome or supply a universal information threshold. A story is stronger when it shows how the uncertainty changed the action and how later evidence was used.

## Deciding Under Incomplete Data

The instinct under ambiguity is to gather more data. The skill is knowing when more data changes nothing. Three disciplines:

1. **Classify before analyzing.** Is this decision reversible? Cheap to undo means bias to act; expensive to undo means bias to analysis.
2. **Cost-of-delay math.** Every week of analysis has a price (missed learning, blocked teams, market window). Compare it against the expected value of better information.
3. **Pre-mortem the top option.** "It's 6 months later and this failed — why?" surfaces risks that more data collection never would.

```text
DECISION FLOW
──────────────────────────────────────────────
Is the problem well-defined? ──no──► define success metrics
│                                     first, then re-enter
yes
▼
Reversible (two-way door)?
├─ yes ──► bound the risk and run a safe trial,
│          measure the uncertain part, set review date
└─ no ───► slow down:
           • quantify worst case per option
           • buy information cheaply (spike, pilot)
           • pre-mortem + externalize reasoning (ADR)
```

A useful sentence pattern in interviews: *"We couldn't know X for certain, so I made the call reversible instead of waiting to be certain."*

## Reversible vs Irreversible: One-Way and Two-Way Doors

The door metaphor describes undo cost, not an intrinsic label for a technology. Ask what changes become durable after the decision: customer contracts, data writes, obligations, and operational dependencies.

| Decision type | Examples | Posture |
| ---------------------- | --------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------- |
| Two-way (reversible) | Feature flag default, library choice in a small service, queue tech behind an interface, pricing experiment, internal tooling | Bound the trial; measure; verify how to revert |
| One-way (irreversible) | Database engine for a 10-year system, public API contract, partner-facing data model, deleting data without backups, compliance posture | Review consequences; buy relevant evidence; involve affected owners |

Questions that reveal costly or irreversible consequences:

- Would unwinding cost more than a quarter of effort or customer trust?
- Does it create a public contract others build on?
- Does it move or destroy data irrecoverably?
- Does it lock hiring, compliance, or vendor commitments?

A public API can evolve through versions, and a database can migrate through a staged plan; both may still be expensive to unwind. Classify the actual commitment and write path, not the product name.

### Making reversibility on purpose

```text
Ways to limit the scope of a commitment:
• Feature flags              → ship dark, flip per cohort
• Strangler facade           → new impl behind old interface
• CDC/outbox + shadow reads  → compare before changing write ownership
• Pilot tenant               → one customer team opts in first
• Stable API boundary        → evolve implementation behind the contract
```

## Decide What Evidence Is Enough

Amazon’s [2016 shareholder letter](https://www.aboutamazon.com/news/company-news/2016-letter-to-shareholders) offers an informal “70%” heuristic for decision speed. It is not a measurable confidence level or a safety standard. Apply the underlying question: what information is essential before acting, and what can a bounded action teach us?

For a reversible trial, agree on the expected benefit, unacceptable harm, measurement window, and review owner. A threshold such as “review after 30 days if adoption remains below the agreed target” needs a defined population and enough observations to interpret. Security, legal, and other mandatory constraints are not optional percentages to trade away.

## Disagree and Commit

The mechanism has three phases, and interviews check all three:

```text
1. DISAGREE visibly — present evidence, name your concern,
                      put it in one written artifact
2. COMMIT fully     — execute as if it were your own idea;
                      no eye-rolling, no I-told-you-so trail
3. REVIEW honestly  — if it fails: help fix it first, then
                      retrospect calmly; if it succeeds: say so
```

Credibility rules:

- Disagree about the *what*, never impugn the *who*.
- Put the disagreement in one artifact (doc/email), not hallway whispers.
- Commitment is behavioral, not verbal — your calendar and code reviews should show it.
- If new evidence reveals a safety, legal, or integrity issue, use the relevant escalation process. Commitment does not require concealing a material risk or continuing an unauthorized action.

## Escalation Judgment

Escalation is a tool, not a failure — but doing it badly is. Decision checklist:

1. **Right decision owner?** Is this within my authority, or does it require another owner? Urgent safety issues may need immediate escalation.
2. **Material stakes?** Would a wrong default meaningfully hurt users, revenue, or the roadmap?
3. **Decision-ready framing?** Can I hand my manager a one-page brief: options, trade-offs, my recommendation?
4. **Joint where possible?** Escalate *with* the other party, not against them.

Good escalation: "Design and I each have a defensible answer and different risk appetites; here's a joint one-pager; we need a call by Thursday."

Bad escalation: surprising a skip-level with complaints after weeks of silent resentment.

## Five Example Stories

These are fictional illustrations of the reasoning sequence. Use your own events and evidence when answering an interview question.

### Story 1: Choosing a Database Under a Hard Deadline (One-Way Door Handled Honestly)

**Competency:** Classifying irreversible decisions; buying information cheaply.

**[Situation]** "Our event-tracking pipeline was hitting write limits on MongoDB — 40K events/sec peaks, and shard rebalancing caused consumer lag spikes. Leadership gave us one quarter and two engineers to fix ingestion before a marquee client's launch doubled our volume."

**[Task]** "I had to choose between scaling Mongo further, migrating to Cassandra, or a managed time-series store. It was a genuinely one-way door: years of data, downstream jobs coupled to our storage semantics, and no realistic path back."

**[Action]** "Because it was irreversible, I slowed down deliberately even though the deadline argued otherwise. Week one: I wrote down the actual requirements instead of vibes — sustained vs peak throughput, the only three query paths that mattered, retention, and our ops appetite for self-managed clusters. That killed Cassandra early: we had no appetite for running it. Weeks two-three: I ran load-test spikes on the two survivors using production-shaped traffic — not synthetic benchmarks from vendor blogs. The managed time-series option failed on query flexibility; Mongo sharding with hashed keys and pre-split chunks passed everything except a 15% cost increase. I wrote an ADR with the rejected alternatives and the specific numbers that rejected them, got review from a staff engineer on another team precisely because he'd disagree with me, and set a checkpoint: if rebalance lag reappeared above 30 seconds twice in 60 days, we'd revisit the managed vendor."

**[Result]** "Rebalancing changes rolled out in week nine — snapshot-backed rehearsal, staged shard changes, lag monitoring, and a rollback plan for configuration changes. Peak launch day hit 71K events/sec with p99 consumer lag of 4 seconds, down from over 90. Cost increase came in at 11%, not 15%. Six months later the checkpoint had never triggered. The ADR became the template for infra decisions across the org — mostly because of its 'rejected with numbers' section."

The fallback was to remain on the existing store with an agreed retention reduction if no option met the requirements.

### Story 2: Shipping Without Perfect Data (Two-Way Door at 70%)

**Competency:** The 70% rule; converting a scary decision into a reversible one.

**[Situation]** "Growth wanted dynamic homepage ranking. Data science proposed a full personalization model — three months of ML work. Product needed something within six weeks for a growth-review commitment. We had almost no clean data on what actually drove homepage engagement."

**[Task]** "As tech lead I had to pick a path with materially incomplete information and make it defensible to both sides."

**[Action]** "First I classified it: this was a two-way door hiding inside a one-way costume. Nobody would be harmed if the ranking was mediocre — but burning three months of ML capacity on unvalidated assumptions was expensive and nearly irreversible at the planning level. So I inverted the work: ship a rules-based ranker in four weeks (recency, category affinity from click history, social-proof counts) purely as an instrument to generate the training signal a real model would need. Before writing code I agreed with DS and PM on the evaluation plan: a 50/50 A/B with session depth as primary metric, guardrails on diversity and load time, and an explicit kill criterion — if session depth didn't beat control by at least 3%, we question the whole approach rather than iterate blindly. My conviction going in was maybe 65%; the point was that the experiment itself was how we purchased information."

**[Result]** "Rules-based ranking lifted session depth 9% over control — clearing the bar. It also produced logged interactions with recorded variant and item exposure. Assignment was randomized, but the rules-based ranking still biased which items users saw; the modeling team accounted for that selection effect. The kill criterion did its job quietly too: the popularity-heavy variant B was switched off after week one for tanking diversity metrics. 'Instrument first, model second' became the standing pattern for growth work."

The rules-based path remained the model’s fallback, so the experiment also exercised a durable operational path.

### Story 3: Disagreeing With a Director's Mandate — and Committing

**Competency:** Disagree and commit, done credibly.

**[Situation]** "A newly hired engineering director mandated that all services standardize on a company-wide shared library for auth, logging, and DB access — essentially a mini-framework from his previous company. My team's service had unusual latency requirements, and the framework's synchronous middleware added overhead we couldn't afford. I pushed back hard in the architecture forum: benchmarks, alternatives, an adapter-based opt-in proposal. He heard me out, then decided: standardize everywhere, revisit in six months."

**[Task]** "The decision went against me. I had to commit without poisoning my team — several engineers had watched me argue and were ready to treat the mandate as illegitimate."

**[Action]** "Same day I told my team exactly where things stood: 'I disagreed, the decision is made, and we're executing it like we chose it — org-level consistency compounds across 20 services even if it costs us 5% locally.' Then commitment became concrete: we migrated within the original timeline, filed precise issues instead of snarky ones, and I volunteered our service as pilot for framework v2 so our latency constraints would shape it. Privately I kept one artifact honest: the benchmark doc stayed in the repo with dated numbers. When the director later asked for v2 input, he read it."

**[Result]** "The six-month review happened on schedule. V2 adopted an async middleware path influenced directly by our pilot data — local overhead dropped from 8ms to under 1ms. The director later told a skip-level that this episode was why he trusted my pushback: 'he fights hard, then commits harder.' Two years later he sponsored my promotion, citing backbone plus commitment."

Repeated disagreement with fresh evidence can use the same decision forum; it need not become passive resistance.

### Story 4: Knowing When NOT to Decide Yet (Escalation and Deferral)

**Competency:** Escalation judgment; refusing premature closure.

**[Situation]** "Two product lines wanted mutually exclusive identity models: Platform wanted one global user account; Enterprise sales wanted per-org sub-accounts with billing isolation. Both VPs had roadmaps committed against their model. I inherited the unification project after the previous lead burned out trying to satisfy both."

**[Task]** "Everyone wanted me to just pick quickly. I had to judge whether picking fast was actually right — or whether forcing a decision would lock in a one-way door on behalf of people who hadn't confronted the trade-off."

**[Action]** "I resisted the pressure to heroically decide. Instead I mapped consequences: a written comparison showing which roadmap items died under each model, sent to both VPs simultaneously, framed neutrally, without my recommendation — because the missing ingredient wasn't analysis, it was an executive priority call I had no mandate to make. I paired it with de-risking interim work: an abstraction layer letting both teams keep building non-conflicting features while the VPs deliberated. And I set the deadline myself — decision by a date certain, or it escalates to the CTO with my tiebreaker recommendation attached. They aligned on a global-account-with-org-scoping hybrid in nine days, each having seen exactly which commitments bent."

**[Result]** "That hybrid shipped as the identity foundation for the next two years without a rework cycle. Both VPs credited the consequence map — not my judgment alone — for making alignment possible. My manager's feedback: 'knowing this decision wasn't yours to make solo was the most senior thing you did.' Deferring upward with a prepared tiebreaker and a hard date is still deciding — it is choosing the decider."

Interim work and a dated decision owner distinguish a deliberate deferral from leaving the problem unowned.

### Story 5: The Call I Got Wrong — and the Tripwire That Saved Us

**Competency:** Owning bad judgment; reversal triggers in practice.

**[Situation]** "I championed adopting a graph database for a recommendations feature. My analysis was solid by the standards I applied — vendor benchmarks, a successful spike, team enthusiasm. We migrated. Three months in, production told a different story: cluster tuning and memory pressure consumed a full engineer's capacity, and the modeling benefit turned out smaller than the spike suggested, because real query patterns clustered into two shapes our relational schema already handled fine."

**[Task]** "My recommendation had cost real money and momentum. I had to decide: dig in, or unwind publicly?"

**[Action]** "The saving grace: when proposing the migration I'd written a reversal trigger into the ADR — 'if monthly ops burden exceeds 0.5 engineer-FTE, or latency gains fall below 25% vs the relational baseline, we schedule a rebuild-vs-retain review.' Both conditions tripped. Because the trigger was pre-agreed, the review wasn't a personal defeat to litigate; it was the process working. I led the review myself, presented numbers against my own original claims, and recommended migrating back to PostgreSQL while keeping the graph store for the one query family where it genuinely won. Total unwind took six weeks. We had retained an authoritative event log, replayed it idempotently into the relational store, checked parity, and switched write ownership only after the checks passed."

**[Result]** "Ops burden dropped to near zero, and the hybrid stayed stable until the feature was eventually simplified away entirely. Team trust in my judgment arguably grew — I'd built the mechanism that caught my own error. My director started requiring reversal triggers in all ADRs, citing this case. The lesson I tell mentees: being wrong is unavoidable; being wrong WITHOUT a tripwire is a choice."

The original spike lacked production query-shape diversity; representative replay became a requirement for later evaluations.

## Check the Explanation

Use these dimensions to check clarity; they are not an employer’s pass rubric:

| Dimension | Incomplete explanation | Inspectable explanation |
| -------------------- | --------------------------------------- | -------------------------------------------------------------------- |
| Classification | Dives straight into analysis | Names reversible vs irreversible FIRST; matches speed to stakes |
| Information level | "We gathered lots of data" | Names essential evidence and what would change the call |
| Reversibility design | Binary ship/no-ship | Bounded trials, migration checkpoints, and explicit review triggers |
| Stakeholder handling | Persuades or overrides | Brings affected parties into criteria before outcomes are known |
| Disagree-and-commit | Caves silently, or wins by rank | Visible disagreement → full commitment → calm retrospective |
| Escalation | Surprises leadership or hoards the call | Joint framing, decision-ready brief, hard dates, prepared tiebreaker |
| Owning errors | Blames context or vendors | Owns the miss, points to the pre-built tripwire, exports the lesson |
| Outcome reporting | "It worked out" | Metrics, plus what the org institutionalized afterward |

The useful output is a missing fact or decision link to repair, not a score claiming that a hiring bar has been met.

## Summary

1. Identify the durable consequences and undo cost of the actual decision.
2. Limit exposure with safe trials and explicit cutover or rollback boundaries.
3. Decide which evidence is essential and which a bounded action can supply.
4. Pre-commit to reversal triggers with numeric thresholds — they turn future errors into routine process instead of political battles.
5. Disagree visibly and in writing, commit behaviorally, review calmly; integrity lines are exempt.
6. Escalate to the right owner with options and evidence; urgent risks may need immediate escalation.
7. Explain a genuine mistaken decision and how feedback changed your response.

# Judgment Calls & Ambiguity: Deciding Under Incomplete Data

A ranking model could take three months to build, but the team has little clean data about user behavior. The decision is whether a small, bounded experiment can answer the important question safely.

```text
Reversible (two-way door)?
├─ yes ──► bound the risk and run a safe trial, set review date
└─ no ───► slow down: quantify worst case, buy information cheaply, pre-mortem
```

## Definition

**Judgment under ambiguity** means choosing an action when useful information is missing and the consequences matter. Explain what was unknown, what you could learn, who owned the decision, and what would make you revise it.

> **Textbook Definition:** Decision-making under uncertainty selects an action from incomplete evidence by comparing consequences, reversibility and the value of obtaining further information.

## First Principles

Information takes time or resources to obtain. The useful question is whether a specific new fact could change the choice enough to justify that cost. When consequences cannot be undone, prevention deserves more attention; when a bounded experiment is safe, feedback can supply the missing information.

## How It Works

### 1. Classify Before Analyzing

More information is useful only when it could change the choice enough to justify its cost. A strong story shows what was unknown, how that changed the action, and which later evidence would force revision. Use three disciplines: **classify before analyzing** (cheap to undo means bias to act; expensive to undo means bias to analysis), **cost-of-delay math** (every week of analysis costs missed learning and blocked teams — compare it against the expected value of better information), and **pre-mortem the top option** ("it is 6 months later and this failed — why?").

```text
DECISION FLOW
──────────────────────────────────────────────
Is the problem well-defined? ──no──► define success metrics
│                                     first, then re-enter
yes
▼
Reversible (two-way door)?
├─ yes ──► bound the risk and run a safe trial,
│          measure the uncertain part, set review date
└─ no ───► slow down:
           • quantify worst case per option
           • buy information cheaply (spike, pilot)
           • pre-mortem + externalize reasoning (ADR)
```

A useful interview sentence: *"We couldn't know X for certain, so I made the call reversible instead of waiting to be certain."*

### 2. Separate One-Way From Two-Way Doors

The door metaphor describes undo cost, not an intrinsic technology label. Ask what becomes durable after the decision: customer contracts, data writes, obligations and operational dependencies.

| Decision type | Examples | Posture |
| ---------------------- | --------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------- |
| Two-way (reversible) | Feature flag default, library choice in a small service, queue tech behind an interface, pricing experiment, internal tooling | Bound the trial; measure; verify how to revert |
| One-way (irreversible) | Database engine for a 10-year system, public API contract, partner-facing data model, deleting data without backups, compliance posture | Review consequences; buy relevant evidence; involve affected owners |

Questions revealing costly or irreversible consequences: would unwinding cost more than a quarter of effort or customer trust? Does it create a public contract others build on? Does it move or destroy data irrecoverably? Does it lock hiring, compliance or vendor commitments? A public API can evolve through versions and a database can migrate through a staged plan — both may still be expensive to unwind, so classify the actual commitment and write path. Ways to limit a commitment's scope: feature flags (ship dark, flip per cohort), strangler facades (new implementation behind the old interface), CDC and outbox with shadow reads (compare before changing write ownership), pilot tenants, and stable API boundaries.

### 3. Decide What Evidence Is Enough

Amazon's [2016 shareholder letter](https://www.aboutamazon.com/news/company-news/2016-letter-to-shareholders) offers an informal "70%" heuristic for decision speed. It is not a measurable confidence level or a safety standard — apply the underlying question: what information is essential before acting, and what can a bounded action teach us? For a reversible trial, agree on the expected benefit, unacceptable harm, measurement window and review owner. A threshold such as "review after 30 days if adoption stays below the agreed target" needs a defined population and enough observations to interpret. Security, legal and other mandatory constraints are not optional percentages to trade away.

### 4. Disagree and Commit

The mechanism has three phases, and interviews check all three:

```text
1. DISAGREE visibly — present evidence, name your concern,
                      put it in one written artifact
2. COMMIT fully     — execute as if it were your own idea;
                      no eye-rolling, no I-told-you-so trail
3. REVIEW honestly  — if it fails: help fix it first, then
                      retrospect calmly; if it succeeds: say so
```

Disagree about the *what*, never impugn the *who*. Put the disagreement in one artifact (doc or email), not hallway whispers. Commitment is behavioral, not verbal — your calendar and code reviews should show it. If new evidence reveals a safety, legal or integrity issue, use the relevant escalation process: commitment never requires concealing a material risk or continuing an unauthorized action.

### 5. Escalate With Judgment

Escalation is a tool, not a failure — but doing it badly is. Run the checklist: **right decision owner?** (is this within my authority, or does it need another owner? Urgent safety issues may need immediate escalation); **material stakes?** (would a wrong default meaningfully hurt users, revenue or the roadmap?); **decision-ready framing?** (can I hand my manager a one-page brief with options, trade-offs and my recommendation?); **joint where possible?** (escalate *with* the other party, not against them).

Good escalation: "Design and I each have a defensible answer and different risk appetites; here's a joint one-pager; we need a call by Thursday." Bad escalation: surprising a skip-level with complaints after weeks of silent resentment.

## Real-World Use Cases

These are fictional illustrations of the reasoning sequence. Use your own events and evidence when answering an interview question.

**Example 1: choosing a database under a hard deadline.** Classify a costly-to-reverse choice and buy relevant information before committing. Situation: "Our event-tracking pipeline was hitting write limits on MongoDB — 40K events/sec peaks, with shard rebalancing causing consumer lag spikes. Leadership gave us one quarter and two engineers before a marquee client's launch doubled our volume." Task: "I had to choose between scaling Mongo further, migrating to Cassandra, or a managed time-series store — with years of data and downstream jobs making reversal expensive." Action: "Because reversal was costly, I slowed down deliberately. Week one: I wrote down actual requirements — sustained vs peak throughput, the only three query paths that mattered, retention, and our ops appetite for self-managed clusters. That killed Cassandra early. Weeks two-three: load-test spikes on the two survivors with production-shaped traffic. The managed time-series option failed on query flexibility; Mongo sharding with hashed keys and pre-split chunks passed everything except a 15% cost increase. I wrote an ADR with the rejected alternatives and the numbers that rejected them, got review from a staff engineer on another team precisely because he would disagree, and set a checkpoint: if rebalance lag exceeded 30 seconds twice in 60 days, we would revisit the managed vendor." Result: "Changes rolled out in week nine. Peak launch day hit 71K events/sec with p99 consumer lag of 4 seconds, down from over 90. Cost rose 11%, not 15%, and the checkpoint never triggered. The fallback was remaining on the existing store with an agreed retention reduction."

**Example 2: testing a growth idea before funding a full model.** Use a bounded experiment to test whether more investment is justified. Situation: "Growth wanted dynamic homepage ranking. Data science proposed a full personalization model — three months of ML work — against a six-week product commitment, with almost no clean data on what drove homepage engagement." Action: "We bounded a ranking trial with exposure, privacy, diversity and latency checks, and shipped a rules-based ranker as a short experiment after Product, Data Science and I set the primary metric, guardrails, sample requirements and a review date — agreeing a weak result would trigger review, not automatic rollout." Result: "The trial met the agreed practical threshold without breaching guardrails, so the team funded the next evaluation step. A popularity-heavy variant was stopped when it breached the diversity guardrail. The result is meaningful only with its sample size, window and uncertainty reported."

**Example 3: disagreeing with a director's mandate — and committing.** Situation: "A newly hired engineering director mandated standardizing all services on a company-wide shared library. My team's service had unusual latency requirements the framework's synchronous middleware could not afford. I pushed back in the architecture forum with benchmarks and an adapter-based opt-in proposal. He heard me out, then decided: standardize everywhere, revisit in six months." Action: "I told my team the decision was made and we would execute it professionally. We migrated on schedule, filed precise issues, and volunteered as a pilot for the next version so our constraints could inform it." Result: "At the six-month review, the next version included an asynchronous path informed by the pilot measurements. Repeated disagreement with fresh evidence can reuse the same decision forum; it need not become passive resistance."

**Example 4: deferring a decision that belongs to another owner.** Situation: "Two product lines wanted mutually exclusive identity models, with both VPs' roadmaps committed against their model. I inherited the unification project after the previous lead burned out trying to satisfy both." Action: "I resisted deciding heroically. I mapped consequences — a written comparison showing which roadmap items died under each model, sent to both VPs simultaneously without my recommendation, since the missing ingredient was an executive priority call I had no mandate to make. I paired it with de-risking interim work (an abstraction layer letting both teams keep building) and set the deadline myself: decision by a date certain, or escalation to the CTO with my tiebreaker attached. They aligned on a global-account-with-org-scoping hybrid in nine days." Result: "That hybrid shipped as the identity foundation for two years without rework. Deferring upward with a prepared tiebreaker and a hard date is still deciding — it is choosing the decider."

**Example 5: reversing a decision after its trigger fires.** Situation: "I championed a graph database for recommendations. Three months in, cluster tuning consumed a full engineer's capacity and the modeling benefit proved smaller than the spike suggested, because real query patterns clustered into two shapes our relational schema already handled." Action: "When proposing the migration I had written a reversal trigger into the ADR — if monthly ops burden exceeded 0.5 engineer-FTE, or latency gains fell below 25% vs the relational baseline, schedule a rebuild-vs-retain review. Both conditions tripped. I led the review myself, presented numbers against my own claims, and recommended migrating back to PostgreSQL while keeping the graph store for the one query family where it won — replaying the retained event log idempotently, checking parity, and switching write ownership only after the checks passed." Result: "The burden fell and the hybrid stayed stable. The reversal trigger did not prevent the initial mistake; it made the cost visible and helped the team act on it."

Check your explanation against these dimensions: **classification** (name reversible vs irreversible first), **information level** (essential evidence and what would change the call), **reversibility design** (bounded trials and explicit triggers, not binary ship/no-ship), **stakeholder handling** (bring affected parties into criteria before outcomes), **disagree-and-commit** (visible disagreement, full commitment, calm retrospective), **escalation** (joint framing, decision-ready brief, hard dates), **owning errors** (own the miss, point to the pre-built tripwire), and **outcome reporting** (metrics plus what the org institutionalized). The useful output is a missing fact or decision link to repair, not a score.

## Summary

Name the durable consequences and undo cost of the actual decision before analyzing. Limit exposure with safe trials and explicit rollback boundaries, and decide which evidence is essential versus obtainable through bounded action. Agree on review triggers with an owner and measurement window, disagree visibly and in writing while committing behaviorally, and escalate to the right owner with options and evidence.

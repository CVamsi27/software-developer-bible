# Technical Decision Stories: From Constraint to Verified Outcome

One endpoint has high tail latency, and someone proposes replacing the service. A credible answer traces the request and measures the bottleneck before choosing a redesign.

```text
user need → limiting behavior → candidate changes → chosen trade-off
          → rollout + failure path → comparable measurement → next decision
```

## Definition

A **technical-decision story** explains a past design choice: what the system needed, what you considered, what you personally did, and what the result established. It differs from a hypothetical design by making claims about actual work.

> **Textbook Definition:** A technical decision account connects an engineering constraint to evaluated alternatives, the chosen action and evidence of its consequences, distinguishing personal contribution from collective work.

## First Principles

A technology is useful only in relation to a constraint. A retrospective must also distinguish the decision from its execution, and the measured result from the explanation for that result — otherwise an attractive architecture diagram can hide an untested assumption. For a slow page, trace where the request waits: a repeated-query bottleneck suggests fixing that query path first, not by itself new services, a cache and a new database.

## Why It Matters

Technical and behavioral prompts overlap when a design depends on migration, operating risk, or agreement across teams. Prepare to show the reasoning and the human work that made the change possible.

## 1. Design and Migrate Systems

These fictional situations illustrate how to frame an answer. They are not product benchmarks or employment experiences. Build your own account with the [STAR method](../../00-strategy/00.03-star-method.md), then use the limits below to check its technical reasoning.

- **Design a system from scratch.** Support needs a searchable knowledge base. Identify the recurring user questions, define a small release, compare managed search with database search, and keep article updates and index updates observable. Explain how unanswered searches and ticket resolution were measured — an apparent deflection rate needs a defined denominator.
- **Migrate a critical system.** Orders must move to a new service without losing updates. Choose one authoritative write path. Backfill from a consistent checkpoint, capture later changes with CDC or an outbox, replay idempotently, and compare reads before switching ownership. State the cutover and rollback boundary: independent dual writes can partially fail, and neither a facade nor CDC alone makes rollback safe after new writes.

## 2. Optimize Slow Paths and Cache Deliberately

- **Optimize a slow system.** A customer page spends most of its time waiting for repeated queries. Trace one request, fix the measured N+1 path, and remeasure before adding denormalization or caching. Use a stable cursor and unique tiebreaker for pagination. Compare equivalent workloads and freshness requirements.
- **Design for a slow dependency.** A pricing call blocks checkout. Budget request time, bound retries, and isolate the dependency. Agree whether a cached quote is valid for the product and for how long — a stale price needs an explicit price-validity policy, and a fallback must not silently change what the customer agrees to pay.
- **Use data to decide on caching.** A few products dominate read traffic. Measure database work, prototype cache-aside reads, and test stale-data behavior, invalidation, stampedes, key isolation and fallback as well as hit rate. A cache pattern safe for public products may be unsafe for carts or user profiles.
- **Improve service reliability.** Connection waits and repeated retries cause cascading failures. Set a database connection budget across replicas, bound waits, and test load shedding. Use idempotent payment retries and reconcile unknown outcomes; stagger cache refreshes. A maximum pool size is a limit, not a guarantee of adaptive sizing.

## 3. Choose Vendors, Platforms and Tools

- **Choose a vendor.** A notification service needs email, push and SMS. Compare channel support, regional constraints, delivery telemetry, support, integration effort and current quoted costs on a representative pilot. Separate provider acceptance, delivery, inbox placement and opens — a delivery-rate difference is not automatically the same number of additional opens.
- **Introduce a test runner.** The current suite has slow feedback and the team proposes Vitest. Benchmark equivalent test sets and environments, audit mocking and setup compatibility, and run old and new suites during a bounded migration. Report runtime, missing behavior and maintenance cost — renaming `jest.fn` to `vi.fn` is only one part of compatibility.
- **Revise a previous decision.** A build-tool migration improves development but worsens the initial bundle. Reproduce the regression under equivalent settings, inspect split boundaries, and adjust or reverse the decision against pre-agreed user metrics. Describe the version and actual configuration — [Vite 8 migration notes](https://vite.dev/guide/migration.html) document its production bundler changes.

## 4. Handle Payments, APIs and Incidents With Exactness

- **Handle a payment incident.** A payment request times out during a provider outage. Treat the charge outcome as unknown: reconcile by the existing payment identifier and reuse the original idempotency key for a supported retry. Keep pending orders pending until the authoritative result is known. Reroute only through a tested path — a successful health check does not authorize a charge, and "fail open" can cause unpaid or duplicate orders. See [Stripe idempotent requests](https://docs.stripe.com/api/idempotent_requests) for supported retry semantics.
- **Design an API others consume.** Partners receive order events through webhooks. Give each event a stable ID, sign the exact payload with a timestamp, retry with bounded backoff, and preserve failed events for inspection or replay. Document deduplication and schema evolution. Finite retries can still exhaust without acknowledgment, and a signature without freshness checks permits replay. See [Stripe webhook verification and delivery](https://docs.stripe.com/webhooks).

## 5. Decide Debt, Cost and Incomplete Data

- **Make a debt trade-off.** One service mixes identity, billing and profile logic. Map incidents and coupling, compare modular boundaries with service extraction, and test the critical contract before moving it. Explain the failure mode reduced and the debt left behind — extracting a service neither proves better architecture nor automatically reduces compliance scope.
- **Build a shared platform.** Several teams have different profile-read requirements. Document each consumer's latency, freshness and consistency needs. Offer clear read contracts and ownership rather than silently routing everyone through one cache. Synchronous reads do not themselves guarantee strong consistency.
- **Decide with incomplete data.** An event pipeline could use stream processors or short-lived workers. Compare ordering, window state, replay, checkpoints, concurrency and measured costs. Pilot the smallest path that can test the uncertain requirement, and record a review trigger tied to the chosen workload.
- **Reduce cloud costs.** The infrastructure bill grows faster than workload. Attribute costs, inspect CPU, memory, I/O, burst headroom and failover needs. Test resizing, bound storage retention, and use interruptible capacity only for restartable work. State savings against a comparable period and demand — low average CPU alone does not make resizing risk-free.

## Real-World Use Cases

For a performance result, record workload, traffic, version, time window, percentile and error behavior. For reliability, define the indicator and denominator. For delivery, distinguish a provider's acknowledgment from the user-visible outcome. Keep rejected options real, and say which assumptions would change the decision. A diagram or runbook establishes what was designed or documented; deployment records, incident timelines, replay checks and measurements establish what was exercised. Describe your contribution separately from collaborators' work. [Architecture Decision Records](https://adr.github.io/) and the [Debezium outbox event router](https://debezium.io/documentation/reference/stable/transformations/outbox-event-router.html) ground the migration and identity evidence above.

## Summary

Explain the constraint before the technology, the component's role before its variant, and the failure path before claiming safety. Finish with evidence that supports the result and the conditions under which you would choose differently.

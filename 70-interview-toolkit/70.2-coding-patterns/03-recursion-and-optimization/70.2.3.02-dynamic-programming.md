# Dynamic Programming

## Definition

Dynamic Programming (DP) is an algorithmic technique for solving optimization, counting, or feasibility problems through a recurrence over subproblems and storing the results of subproblems to avoid redundant computations. It's applicable when the problem has overlapping subproblems and optimal substructure.

> **Textbook Definition:** Dynamic programming evaluates a recurrence over overlapping subproblems and retains their results for reuse. The state must contain all information needed to determine subsequent transitions.

## First Principles

DP exists because naive recursion re-solves overlapping subproblems:

1. **Repeated states create reusable work.** A valid recurrence must retain enough information for later choices to depend only on the state. Optimization uses optimal substructure; counting combines contributions without double-counting. Caching each reachable state removes repeated evaluation, but an exponential number of states remains exponential.
2. **The state is the entire game**: define the state minimal (what the future needs to know about the past) and the transition writes itself; memoization (top-down) vs tabulation (bottom-up) is the same recurrence evaluated in different orders; their memory costs depend on stored states and traversal depth.

## Why it matters

DP starts with a model of the subproblem, not a familiar-looking loop. The bar: derive the **state**, the **recurrence**, the **base cases**, and the **answer location** before writing any code. Common variants: 1D (climbing stairs, house robber), 2D (grid paths, edit distance, LCS), knapsack (subset sum, coin change), and DP on strings (palindromes). The senior trick: always start with **"what does dp[i] (or dp[i][j]) mean?"** before writing recurrence.

## When to Use

- Optimization problems (min/max)
- Counting problems
- Problems with overlapping subproblems
- Problems with optimal substructure
- When brute force is exponential

## How It Works

```text
State: f(i) = Fibonacci number at index i
Base:  f(0)=0, f(1)=1
Rule:  f(i)=f(i-1)+f(i-2)

Naive f(5) asks for f(3) through both f(4) and its own second branch.
Memoization computes f(3) once and reuses it.
Tabulation evaluates 0,1,2,3,4,5 so each dependency already exists.
A rolling pair retains only the two values needed by the next state.
```

## Code Examples (TypeScript)

### Problem 1: Fibonacci Number

```typescript
// Memoization
function fibMemo(n: number): number {
  if (!Number.isInteger(n) || n < 0 || n > 78) throw new RangeError("Number implementation supports indices 0..78");
  const memo = new Map<number, number>();

  function dp(n: number): number {
    if (n <= 1) return n;
    if (memo.has(n)) return memo.get(n)!;

    memo.set(n, dp(n - 1) + dp(n - 2));
    return memo.get(n)!;
  }

  return dp(n);
}

// Tabulation
function fibTab(n: number): number {
  if (!Number.isInteger(n) || n < 0 || n > 78) throw new RangeError("Number implementation supports indices 0..78");
  if (n <= 1) return n;

  let prev = 0;
  let curr = 1;

  for (let i = 2; i <= n; i++) {
    const next = prev + curr;
    prev = curr;
    curr = next;
  }

  return curr;
}

// Example
console.log(fibMemo(10)); // 55
console.log(fibTab(10)); // 55

```

Fibonacci values after index 78 exceed JavaScript’s exact integer range. Use BigInt for larger exact values; memoization does not correct numeric precision loss.

### Problem 2: 0/1 Knapsack

`dp[i][w]` is the best value using the first i items within capacity w. Reading only the previous item row prevents using an item twice. The same distinction matters in a 1D optimization: descending capacities enforce 0/1 use, while ascending capacities permit reuse.


```typescript
function knapsack(weights: number[], values: number[], capacity: number): number {
  if (!Number.isInteger(capacity) || capacity < 0 || weights.length !== values.length || weights.some(w => !Number.isInteger(w) || w < 0)) throw new RangeError("invalid knapsack inputs");
  const n = weights.length;
  const dp = Array(n + 1).fill(null).map(() => Array(capacity + 1).fill(0));

  for (let i = 1; i <= n; i++) {
    for (let w = 0; w <= capacity; w++) {
      if (weights[i - 1] <= w) {
        dp[i][w] = Math.max(
          dp[i - 1][w],
          dp[i - 1][w - weights[i - 1]] + values[i - 1]
        );
      } else {
        dp[i][w] = dp[i - 1][w];
      }
    }
  }

  return dp[n][capacity];
}

// Example
console.log(knapsack([2, 3, 4, 5], [3, 4, 5, 6], 5)); // 7

```

### Problem 3: Longest Common Subsequence

```typescript
function longestCommonSubsequence(text1: string, text2: string): number {
  const m = text1.length;
  const n = text2.length;

  const dp = Array(m + 1).fill(null).map(() => Array(n + 1).fill(0));

  for (let i = 1; i <= m; i++) {
    for (let j = 1; j <= n; j++) {
      if (text1[i - 1] === text2[j - 1]) {
        dp[i][j] = dp[i - 1][j - 1] + 1;
      } else {
        dp[i][j] = Math.max(dp[i - 1][j], dp[i][j - 1]);
      }
    }
  }

  return dp[m][n];
}

// Example
console.log(longestCommonSubsequence("abcde", "ace")); // 3
console.log(longestCommonSubsequence("abc", "abc")); // 3
console.log(longestCommonSubsequence("abc", "def")); // 0

```

### Problem 4: Longest Increasing Subsequence

```typescript
function lengthOfLIS(nums: number[]): number {
  const n = nums.length;
  if (n === 0) return 0;
  const dp = new Array(n).fill(1);

  for (let i = 1; i < n; i++) {
    for (let j = 0; j < i; j++) {
      if (nums[j] < nums[i]) {
        dp[i] = Math.max(dp[i], dp[j] + 1);
      }
    }
  }

  let longest = 0;
  for (const length of dp) longest = Math.max(longest, length);
  return longest;
}

// Example
console.log(lengthOfLIS([10, 9, 2, 5, 3, 7, 101, 18])); // 4 ([2,3,7,101])

```

### Problem 5: Coin Change

```typescript
function coinChange(coins: number[], amount: number): number {
  if (!Number.isInteger(amount) || amount < 0 || coins.some(c => !Number.isInteger(c) || c <= 0)) throw new RangeError("positive integer coins and nonnegative amount required");
  const dp = new Array(amount + 1).fill(Infinity);
  dp[0] = 0;

  for (let i = 1; i <= amount; i++) {
    for (const coin of coins) {
      if (i >= coin && dp[i - coin] !== Infinity) {
        dp[i] = Math.min(dp[i], dp[i - coin] + 1);
      }
    }
  }

  return dp[amount] === Infinity ? -1 : dp[amount];
}

// Example
console.log(coinChange([1, 2, 5], 11)); // 3 (5 + 5 + 1)
console.log(coinChange([2], 3)); // -1

```

### Problem 6: Edit Distance

```typescript
function minDistance(word1: string, word2: string): number {
  const m = word1.length;
  const n = word2.length;

  const dp = Array(m + 1).fill(null).map(() => Array(n + 1).fill(0));

  for (let i = 0; i <= m; i++) dp[i][0] = i;
  for (let j = 0; j <= n; j++) dp[0][j] = j;

  for (let i = 1; i <= m; i++) {
    for (let j = 1; j <= n; j++) {
      if (word1[i - 1] === word2[j - 1]) {
        dp[i][j] = dp[i - 1][j - 1];
      } else {
        dp[i][j] = 1 + Math.min(
          dp[i - 1][j], // delete
          dp[i][j - 1], // insert
          dp[i - 1][j - 1] // replace
        );
      }
    }
  }

  return dp[m][n];
}

// Example
console.log(minDistance("horse", "ros")); // 3
console.log(minDistance("intention", "execution")); // 5

```

## Common Mistakes

1. **Not identifying overlapping subproblems**: Use memoization to avoid redundant work

2. **Wrong recurrence relation**: Carefully define the relationship between subproblems

3. **Incorrect base case**: Always define base cases before recurrence

4. **Not considering all options**: In knapsack, consider both including and excluding items

5. **Space optimization not needed**: Sometimes O(n) space is sufficient, don't over-optimize

## Time/Space Complexity

| Problem | Time | Space | Optimized Space |
| ------------- | ----------- | --------- | ------------------------------------------------------- |
| Fibonacci | O(n) | O(n) | O(1) |
| Knapsack | O(n×W) | O(n×W) | O(W) |
| LCS | O(m×n) | O(m×n) | O(min(m,n)) |
| LIS | O(n²) | O(n) | O(n); a different algorithm improves time to O(n log n) |
| Coin Change | O(n×amount) | O(amount) | O(amount) |
| Edit Distance | O(m×n) | O(m×n) | O(min(m,n)) |

Knapsack’s O(n·W) bound depends on the numeric capacity W, making it pseudo-polynomial in the input’s bit length. More generally, estimate state count × transitions per state, plus output and arithmetic costs. The string examples index UTF-16 code units; tokenize differently when the required symbol is a Unicode code point or grapheme.

## Summary

Define the state, valid transitions, base cases, evaluation order, and answer location. Reusing a computed state removes duplicate work, but total cost still depends on how many states exist. Reduce memory only after identifying which earlier states future transitions need.

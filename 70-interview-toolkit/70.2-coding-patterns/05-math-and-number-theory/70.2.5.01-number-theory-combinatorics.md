# Number Theory & Combinatorics

## TL;DR

Most interview math reduces to **three templates plus overflow discipline**: the sieve of Eratosthenes for primes, Euclid's algorithm for GCD/LCM (and its extended form for modular inverses), and fast exponentiation for `a^b mod m`. Combinatorics is the same discipline with factorials — precompute factorials and inverse factorials once, then answer `nCr` in O(1) with modular arithmetic. The signal interviewers look for is not the formula but the **overflow reflex**: reduce after every multiply, and know when a value must be a 64-bit intermediate.

---

> Interview math essentials: primes and primality, GCD/LCM, modular arithmetic, combinatorics and probability, with practice problems. Language-agnostic.

## First Principles

Number-theory interview problems are *structure recognition*:

1. **Divisibility structure (gcd, primes, modular arithmetic) constrains answers before any code runs**: gcd identity (gcd(a,b)·lcm(a,b)=a·b), Fermat/Euler for modular exponents, sieve for prime enumeration — each is a constraint you import, not an algorithm you invent.
2. **Combinatorics is counting without enumeration**: multiplication principle, stars-and-bars, inclusion-exclusion — the discipline is writing the counting argument before the formula, which is also the DP state-design skill (→ 70.2.3.02).

## Definition

This chapter is a toolkit of two exact-arithmetic subjects that appear in coding rounds under **overload and overflow constraints**:

```text
number theory                     combinatorics
  primality / sieve (n ≤ 10^7)      permutations & combinations  nCr, nPr
  GCD / LCM (Euclid)                counting with constraints (inclusion–exclusion)
  modular arithmetic + fast pow     probability as a ratio of counts
  modular inverse (Fermat)          Catalan / derangements / stars-and-bars
     → "compute mod 1e9+7"             → "count the ways"
```

Three properties define how to use them in an interview:

1. **The modulus is a design instruction** — "return the answer mod 10⁹+7" means the true count overflows 64-bit and that division must use a **modular inverse**, not `/`. Recognising that phrasing converts an impossible computation into a `pow(x, MOD-2, MOD)` call.
2. **Counting problems are recognition problems** — the work is classifying the shape (ordered or not? repetition allowed? distinct items? at least one constraint?) and then applying inclusion–exclusion or a known sequence; the code is trivial once the classification is right, which is why the interview signal is the derivation, not the loop.
3. **Overflow is the actual bug source** — `(a * b) % m` must be computed as `((a % m) * (b % m)) % m`, and intermediate values in nCr/gcd-lcm routinely overflow before the modulus is applied. This is the most common silent failure in these problems, and it is why the chapter emphasises language-specific handling (`__int128` in C++, `BigInt` in Java, exact integers in Python).

The pair belongs with the other coding-pattern chapters because the *pattern* being tested is the same: recognize the problem shape, derive the invariant or formula, then implement the edge cases (zero, negative, overflow) that the naive solution misses.

## Prime Numbers

```java
// Check if prime — O(√n)
boolean isPrime(int n) {
    if (n < 2) return false;
    for (int i = 2; i * i <= n; i++) {
        if (n % i == 0) return false;
    }
    return true;
}

// Sieve of Eratosthenes — O(n log log n)
boolean[] sieve(int n) {
    boolean[] isPrime = new boolean[n + 1];
    Arrays.fill(isPrime, true);
    isPrime[0] = isPrime[1] = false;

    for (int i = 2; i * i <= n; i++) {
        if (isPrime[i]) {
            for (int j = i * i; j <= n; j += i) {
                isPrime[j] = false;
            }
        }
    }
    return isPrime;
}

// Count primes up to n
int countPrimes(int n) {
    boolean[] isPrime = new boolean[n];
    Arrays.fill(isPrime, true);
    int count = 0;
    for (int i = 2; i < n; i++) {
        if (isPrime[i]) {
            count++;
            for (long j = (long) i * i; j < n; j += i) {
                isPrime[(int) j] = false;
            }
        }
    }
    return count;
}

// Prime Factorization
Map<Integer, Integer> primeFactorization(int n) {
    Map<Integer, Integer> factors = new HashMap<>();
    for (int i = 2; i * i <= n; i++) {
        while (n % i == 0) {
            factors.put(i, factors.getOrDefault(i, 0) + 1);
            n /= i;
        }
    }
    if (n > 1) factors.put(n, 1);
    return factors;
}

```

## GCD and LCM

```java
// Euclidean Algorithm — O(log(min(a, b)))
int gcd(int a, int b) {
    while (b != 0) {
        int temp = b;
        b = a % b;
        a = temp;
    }
    return a;
}

// LCM
int lcm(int a, int b) {
    return a / gcd(a, b) * b; // divide first to avoid overflow
}

// Extended Euclidean — finds x, y such that ax + by = gcd(a, b)
int[] extendedGCD(int a, int b) {
    if (b == 0) return new int[]{a, 1, 0};
    int[] prev = extendedGCD(b, a % b);
    int gcd = prev[0];
    int x = prev[2];
    int y = prev[1] - (a / b) * prev[2];
    return new int[]{gcd, x, y};
}

```

## Modular Arithmetic

```java
final long MOD = 1_000_000_007;

// Modular addition
long addMod(long a, long b) {
    return (a + b) % MOD;
}

// Modular multiplication
long mulMod(long a, long b) {
    return (a * b) % MOD;
}

// Modular exponentiation — O(log n)
long powerMod(long base, long exp, long mod) {
    long result = 1;
    base %= mod;
    while (exp > 0) {
        if ((exp & 1) == 1) {
            result = result * base % mod;
        }
        exp >>= 1;
        base = base * base % mod;
    }
    return result;
}

// Modular inverse (when MOD is prime)
long modInverse(long a) {
    return powerMod(a, MOD - 2, MOD); // Fermat's little theorem
}

// nCr modulo MOD
long nCr(int n, int r, long mod) {
    if (r > n) return 0;
    long[] fact = new long[n + 1];
    fact[0] = 1;
    for (int i = 1; i <= n; i++) fact[i] = fact[i - 1] * i % mod;

    long num = fact[n];
    long den = fact[r] * fact[n - r] % mod;
    return num * powerMod(den, mod - 2, mod) % mod;
}

```

## Combinatorics and Probability

```java
// Generate all permutations
void permutations(int[] nums, int start, List<List<Integer>> result) {
    if (start == nums.length) {
        result.add(Arrays.stream(nums).boxed().collect(Collectors.toList()));
        return;
    }
    for (int i = start; i < nums.length; i++) {
        swap(nums, start, i);
        permutations(nums, start + 1, result);
        swap(nums, start, i);
    }
}

// Generate all combinations
void combinations(int n, int k, int start, List<Integer> current, List<List<Integer>> result) {
    if (current.size() == k) {
        result.add(new ArrayList<>(current));
        return;
    }
    for (int i = start; i <= n; i++) {
        current.add(i);
        combinations(n, k, i + 1, current, result);
        current.remove(current.size() - 1);
    }
}

```

## Summary

1. **Three templates carry most math problems** — sieve of Eratosthenes for primes, Euclid's algorithm for GCD/LCM, fast exponentiation for modular power
2. **Modular arithmetic is overflow discipline** — reduce after every multiply; a 64-bit intermediate product is the classic silent bug
3. **Counting without double-counting is the combinatorics game** — nCr via multiplicative formula or Pascal's row (never raw factorials), complements ("total − invalid"), stars-and-bars for distributions
4. **Probability reduces to counting** — favorable / total, with independence stated explicitly before multiplying
5. **The skill being tested is recognition speed** — "primes up to N" → sieve, "pairs divisible by k" → modular buckets, "number of paths" → combinatorics, not simulation

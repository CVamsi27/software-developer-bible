# React & Next.js Cheat Sheet

A page needs a database read and an interactive button. Put both in one client module and the framework rejects its server-only database import. Trace which code enters the client bundle and where the mutation is authorized.

```typescript
// app/actions.ts — the mutation boundary: authorize, validate, write, revalidate.
'use server';
export async function createPost(formData: FormData) {
  const editor = await requireEditor(); // verifies session + posting permission
  const title = formData.get('title');
  if (typeof title !== 'string' || !title.trim() || title.length > 200) {
    throw new Error('Invalid post');
  }
  await db.post.create({ data: { title: title.trim(), authorId: editor.id } });
}
```

## Definition

**React** computes UI from props, state and context. **Next.js** adds routing and server/client boundaries around that UI. A hook manages one part of React's work; a route file determines where that work enters the application.

> **Textbook Definition:** React is a declarative UI library that reconciles rendered element descriptions with committed UI; Next.js supplies framework conventions for routing, rendering, server operations and delivery.

## First Principles

A render may be repeated or discarded, so it must not cause external effects. The committed UI needs browser event handling, while privileged data access needs a server boundary. Caching and streaming decide when results are reused or revealed; neither supplies authorization.

## How It Works

### 1. Trace a Request to an Interactive Screen

```text
request → route + layout → server data/render → HTML + component payload
        → browser hydration of client components → event → authorized mutation
```

Server Components do not ship their component implementation to the browser. The page still needs framework and client JavaScript where it contains interactive components. Client Components can be server-prerendered initially; their directive defines a client module graph, not "execute only in a browser." A state update starts React rendering: reconciliation compares element identity, commit applies the resulting DOM changes, and effects synchronize a committed UI with external systems. Transitions can interrupt React render work but cannot preempt a long synchronous JavaScript function or move it to a worker.

### 2. Choose React APIs by Their Role

| Concept | Key point |
| ----------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| Component | Function returning JSX; may render again when props, state or context change: `function Button({ label }) { return <button>{label}</button>; }` |
| JSX | Syntax extension transformed to JSX-runtime calls; older transforms use `createElement` |
| Element tree | React describes the desired UI and reconciles it with prior elements; a tree alone is not a speed guarantee |
| Reconciliation | Matches element type, position and keys; a type change resets that subtree — keys identify which items changed |
| Fiber | Internal reconciler implementation representing units of work — not an application API |
| Concurrent rendering | React can prioritize, interrupt or restart render work; Suspense controls fallbacks — never moves sync JS to another thread |

| State and effect hook | Role |
| ----------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| `useState` | `const [count, setCount] = useState(0);` — setter triggers re-render |
| `useEffect` | Synchronize after commit; cleanup runs before a changed-dependency setup and on unmount |
| `useContext` | `const value = useContext(MyContext);` — consume context without nesting consumers |
| `useRef` | Mutable ref object persisting across renders; DOM element access |
| `useReducer` | Complex state logic: `(state, action) => newState` |
| `useLayoutEffect` | Fires synchronously after DOM mutations, before paint — use for measuring DOM elements |

| Performance and identity hook | Role |
| ----------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| `useMemo` | Cache a computation by dependencies — a performance aid, not a correctness guarantee |
| `useCallback` | Cache function identity; can help a memoized child skip renders |
| `useTransition` | Mark a state update as non-urgent: `const [isPending, startTransition] = useTransition();` |
| `useDeferredValue` | Defer re-render of a non-urgent part; shows the stale value while pending |
| `useId` | Generate a unique, stable ID for accessibility (opaque; do not parse its format) |
| `use()` API | Read a promise or context conditionally during render without nesting |

| Advanced hook | Role |
| ----------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| `useImperativeHandle` | Customize the ref value exposed to a parent — only when a parent needs an explicit imperative interface |
| `useActionState` | React 19 form action hook tracking state, pending transition and payload |
| `useOptimistic` | React 19 optimistic UI hook rendering projected state immediately while the action executes |

### 3. Choose Next.js Routing and File Conventions

| Convention | Role |
| ----------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| App Router | File-based routing in `app/`; layouts, loading and error boundaries — `app/dashboard/layout.tsx` wraps `app/dashboard/page.tsx` |
| Pages Router | File-based routing in `pages/` with `getServerSideProps` and `getStaticProps` — legacy, still supported |
| Layouts | Shared layouts retain state across child navigation; crossing root layouts or identity changes can reset it |
| Loading UI | `loading.tsx` shows the Suspense fallback while a route segment loads |
| Error boundaries | `error.tsx` catches errors in a route segment |
| Not found | `not-found.tsx` supplies the custom 404 for a route segment |

| Route pattern | Convention |
| ----------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| Dynamic routes | `[slug]` catches one segment; `[[...slug]]` is the optional variant — `app/blog/[slug]/page.tsx` |
| Catch-all routes | `[...slug]` matches `/a/b/c` as `params.slug = ['a','b','c']` |
| Parallel routes | `@slot` renders multiple pages simultaneously in one layout — `app/dashboard/@analytics/page.tsx` |
| Intercepting routes | `(.)` same level, `(..)` parent, `(...)` root; segment levels excluding `@slot` and route groups determine the marker |
| Proxy (Next.js 16) | Request boundary for rewrites and redirects with the Node.js runtime — `proxy.ts` (older versions used `middleware.ts`) |
| Route handlers | `route.ts` API endpoints: `export async function GET() { return Response.json({}); }` |

### 4. Apply Server, Client and Action Boundaries

| Boundary | Rule |
| ----------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| Server Component | Default in App Router; runs on the server; can access the DB directly — no `'use client'` directive |
| Client Component | `'use client'` directive; interactive client graph, also server-prerendered on initial load — required for `useState`, `useEffect`, event handlers |
| Server Actions | `'use server'` directive; functions called from the client, executed on the server |
| `fetch` in RSC | Matching GET/HEAD fetches memoize during a render; persistent caching is a separate opt-in |
| `cookies()` / `headers()` | Read cookies and headers in Server Components and Route Handlers (async in Next.js 15) |
| `redirect()` / `notFound()` | Terminate the relevant render and control flow — not ordinary values to ignore |

| Caching layer | Rule |
| ----------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Previous fetch model | In Next.js 15+, fetch is not persistently cached by default; explicit fetch options and route settings control reuse |
| Cache Components (Next.js 16) | Opt-in model with explicit cached scopes and lifetimes; route-segment `revalidate` and `fetchCache` exports are removed when enabled — use `'use cache'`, `cacheLife`, `cacheTag` |
| Router cache | Browser-side reuse of route segments; prefetch and staleness rules affect navigation — separate from server caches |
| ISR | In the previous model, Incremental Static Regeneration refreshes eligible static route output: `export const revalidate = 60;` |
| Streaming | Send HTML progressively; Suspense boundaries define chunks: `<Suspense fallback={<Loading />}>` |

Matching eligible GET/HEAD fetches can share results during React rendering. That request memoization is distinct from persistent data caching, route output, and browser Router Cache reuse. Route Handlers sit outside the React render tree. Read request-specific values such as `cookies()` or `headers()` outside a cached scope, then pass only the values the cached work needs.

### 5. Navigate and Deliver Content

| Navigation hook | Role |
| ----------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| `useRouter()` | Client-side navigation: `push`, `replace`, `back`, `prefetch` |
| `usePathname()` | Current URL pathname (client) |
| `useSearchParams()` | URL search params (client) |
| `useParams()` | Dynamic route params (client): `const { slug } = useParams();` |
| `useSelectedLayoutSegment()` | Active child segment under a layout |

| Delivery API | Role |
| ----------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| `next/image` | Optimized images: lazy loading, resize, WebP — `<Image src="/pic.jpg" alt="..." width={500} height={300} />` |
| `next/font` | Self-host fonts and reduce font-related layout shifts via CSS variables |
| `next/link` | Client-side navigation; prefetch behavior depends on version and route |
| `next/script` | Script loading strategies: `beforeInteractive`, `afterInteractive`, `lazyOnload` |
| `next/headers` | Read request headers and cookies (server only) |
| `generateStaticParams` | Pre-generate dynamic routes at build time |
| `generateMetadata` | Dynamic metadata per page (`params` is a Promise in Next.js 15) |
| Metadata API | `generateMetadata` for SEO metadata per route |

Image, font and script components address different work; none guarantees a universally fast page — verify effects with actual content and device workload. Full examples live in the [context chapter](../../10-frontend/10.3-react/02-core-hooks/10.3.2.05-context-api.md) and [App Router chapter](../../10-frontend/10.4-next.js/01-rendering-fundamentals/10.4.1.02-app-router.md).

### 6. Work the Boundaries in Small Examples

**Reveal a slow server read under a fallback.** `PostsPage` renders a `Suspense` boundary with a `PostsSkeleton` fallback around an async `PostsList` that fetches, validates with a type predicate, and renders keyed list items:

```typescript
// app/posts/page.tsx (Server Component)
import { Suspense } from 'react';

type Post = { id: string; title: string };
function isPost(value: unknown): value is Post {
  return typeof value === 'object' && value !== null
    && 'id' in value && typeof value.id === 'string'
    && 'title' in value && typeof value.title === 'string';
}
function PostsSkeleton() { return <p role="status">Loading posts…</p>; }

export default function PostsPage() {
  return (
    <div>
      <h1>Posts</h1>
      <Suspense fallback={<PostsSkeleton />}>
        <PostsList />
      </Suspense>
    </div>
  );
}

// Illustration: replace this placeholder URL with the application's public read API.
async function PostsList() {
  const value: unknown = await fetch('https://api.example.com/posts')
    .then(res => {
      if (!res.ok) throw new Error(`HTTP ${res.status}`);
      return res.json();
    });
  if (!Array.isArray(value) || !value.every(isPost)) throw new TypeError('Invalid posts');
  const posts: Post[] = value;
  return (
    <ul>
      {posts.map(post => <li key={post.id}>{post.title}</li>)}
    </ul>
  );
}
```

**Authorize and validate a server mutation.** `createPost` verifies the editor session, validates and bounds title and content, writes with the editor's ID, then revalidates and redirects. The form posts to it directly. `db` and `requireEditor` are application dependencies, not framework APIs — protect private reads and mutations at their data-access boundary, and never pass an unchecked request body into an ORM create:

```typescript
// app/actions.ts
'use server';

import { revalidatePath } from 'next/cache';
import { redirect } from 'next/navigation';
import { db } from '@/lib/db';
import { requireEditor } from '@/lib/auth';

export async function createPost(formData: FormData) {
  const editor = await requireEditor(); // App helper verifies session + posting permission.
  const title = formData.get('title');
  const content = formData.get('content');
  if (typeof title !== 'string' || !title.trim() || title.length > 200
      || typeof content !== 'string' || content.length > 50_000) {
    throw new Error('Invalid post');
  }
  await db.post.create({ data: { title: title.trim(), content, authorId: editor.id } });
  revalidatePath('/posts');
  redirect('/posts');
}

// app/posts/new/page.tsx
import { createPost } from '../../actions';

export default function NewPost() {
  return (
    <form action={createPost}>
      <input name="title" required />
      <textarea name="content" required />
      <button type="submit">Create Post</button>
    </form>
  );
}
```

**Optimistic request redirect (Next.js 16 Proxy).** Presence is only an optimistic UX check, not verified authentication — verify the session and permissions in every protected data access and mutation:

```typescript
// proxy.ts
import { NextResponse, type NextRequest } from 'next/server';

export function proxy(request: NextRequest) {
  // Presence is only an optimistic UX check, not verified authentication.
  if (!request.cookies.has('auth-token')) {
    return NextResponse.redirect(new URL('/login', request.url));
  }
  return NextResponse.next();
}

export const config = { matcher: ['/dashboard/:path*'] };
```

**Parallel routes (dashboard panels).** `DashboardLayout` receives `children` and the `analytics` slot; `app/dashboard/@analytics/page.tsx` fills it:

```typescript
// app/dashboard/layout.tsx
export default function DashboardLayout({
  children,
  analytics,
}: {
  children: React.ReactNode;
  analytics: React.ReactNode;
}) {
  return (
    <div className="dashboard">
      {children}
      {analytics}
    </div>
  );
}

// app/dashboard/@analytics/page.tsx
export default function AnalyticsPage() {
  return <div className="analytics-panel">...</div>;
}
```

**Preserve a background route while showing a modal.** Soft navigation shows the modal; direct navigation needs the regular `app/photos/[id]/page.tsx`. Supply the layout's `modal` slot and its unmatched-route fallback — one intercepted page file alone is not a complete modal flow:

```typescript
// app/@modal/(.)photos/[id]/page.tsx
import Modal from '@/components/Modal';

export default async function PhotoModal({ params }: { params: Promise<{ id: string }> }) {
  const { id } = await params; // params is a Promise in Next.js 15+
  return (
    <Modal>
      <img src={`/photos/${id}`} alt="Photo" />
    </Modal>
  );
}
```

**Optimistic updates with `useOptimistic`.** The form action supplies the action context for the optimistic update. The parent must refresh the authoritative `todos` after persistence — a local optimistic item is not durable evidence. Handle rejected actions through the error boundary or explicit error UI:

```typescript
'use client';
import { useOptimistic } from 'react';

type Todo = { id: string; text: string; done: boolean };
function TodoList({ todos, addTodo }: {
  todos: Todo[];
  addTodo: (text: string) => Promise<void>;
}) {
  const [optimisticTodos, addOptimisticTodo] = useOptimistic(
    todos,
    (state: Todo[], newTodo: { id: string; text: string }) => [...state, { ...newTodo, done: false }]
  );

  async function handleAdd(formData: FormData) {
    const value = formData.get('text');
    if (typeof value !== 'string' || !value.trim() || value.length > 200) {
      throw new Error('Invalid todo text');
    }
    const text = value.trim();
    addOptimisticTodo({ id: crypto.randomUUID(), text }); // Action runs this outside render
    await addTodo(text); // Server mutation
  }

  return (
    <form action={handleAdd}>
      <ul>{optimisticTodos.map(t => <li key={t.id}>{t.text}</li>)}</ul>
      <input name="text" />
    </form>
  );
}
```

**Validate a public read at a route handler.** Public catalog only, with bounded offset pagination — for large changing collections use a stable cursor and unique tiebreaker:

```typescript
// app/api/products/route.ts — public catalog only.
import { db } from '@/lib/db';

export async function GET(request: Request) {
  const rawPage = new URL(request.url).searchParams.get('page') ?? '1';
  if (!/^[1-9]\d{0,3}$/.test(rawPage)) {
    return Response.json({ error: 'Invalid page' }, { status: 400 });
  }
  const products = await db.product.findMany({
    where: { published: true },
    orderBy: { id: 'asc' },
    skip: (Number(rawPage) - 1) * 10,
    take: 10,
    select: { id: true, name: true },
  });
  return Response.json(products);
}
```

### 7. Connect Route Files to Navigation Behavior

| File or convention | Role in the screen |
| ------------------------------------ | -------------------------------------------------------------------------------------- |
| `layout.tsx` | Shared surrounding UI; a root layout supplies `html` and `body` |
| `loading.tsx` | Suspense fallback for a route segment |
| `error.tsx` | Client error boundary for descendants; errors in its own layout need a higher boundary |
| `not-found.tsx` / `notFound()` | Missing-resource UI and status behavior |

| Segment convention | Role in the screen |
| ------------------------------------ | -------------------------------------------------------------------------------------- |
| `[slug]`, `[...slug]`, `[[...slug]]` | One dynamic segment, required catch-all, optional catch-all |
| `@slot` | Parallel layout input; it does not add a URL segment |
| `(.)`, `(..)`, `(...)` | Intercept at the same, parent, or root segment level |
| `default.tsx` | Fallback for an unmatched parallel slot during a hard load |
| `template.tsx` | A fresh instance when its route identity changes, unlike a shared layout |

For the root-level `@modal` example, `(.)photos` matches sibling `/photos`. Use `next/link` and the navigation hooks for route changes; `useParams`, `useSearchParams`, `usePathname` and `useSelectedLayoutSegment` read different pieces of route state. Use context for shared client state. Prisma in Next.js needs a compatible client and connection setup for the runtime — serverless instances and pool limits still matter, so keep a singleton in `lib/prisma.ts`.

## Summary

Trace render, commit, server data access, browser interaction, and mutation as separate steps. Choose routing and cache APIs for their role in that trace, and enforce authorization and validation at the privileged operation.

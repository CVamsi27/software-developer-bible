# System Design Cheat Sheet

## Definition

System design connects a user operation to storage, communication, and failure handling under stated constraints. A design is assessable when each component has a job and each claimed guarantee has a boundary.

> **Textbook Definition:** Software system design specifies cooperating components, data models and protocols to meet functional requirements and quality constraints under a stated workload and failure model.

## First Principles

Requests consume finite processing and storage resources. Messages can be delayed, duplicated, or lost, and concurrent operations can disagree unless the system coordinates them. Scaling changes how work and state are distributed; it does not remove these constraints.

## Trace One Operation Through the Whole System

For placing an order, identify which data must commit together and which work can follow asynchronously:

```text
client → gateway → order service → database transaction
                                  ├─ order + outbox event commit
                                  └─ relay → broker → notification worker
read client → query service → cache or database
```

The gateway routes and checks entry conditions. The order service owns the business invariant. The database commits related state. The broker lets a worker process later; it does not make email delivery part of the database transaction. A cache accelerates an eligible read; it does not become the authority merely because it is faster.

## Size the Work Before Splitting It

With a hypothetical one million daily active users making ten requests each, average traffic is `10,000,000 / 86,400 ≈ 115.7 requests/s`. Peak traffic, fan-out, retries, and long-lived connections require separate estimates.

If each request returns 1 KB, average response bandwidth is about 115.7 KB/s before protocol overhead. If—not merely because—each request also persists 1 KB retained for a year, raw annual storage is 3.65 TB in decimal units. Add indexes, replication, backups, and retention behavior separately.

## Route Work and Distribute State

| Mechanism | Job | Limit |
| ----------------------------------------------------------- | ----------------------------------------- | -------------------------------------------------------------------------------------------------------- |
| Transport-layer (L4) / application-layer (L7) load balancer | Route connections or application requests | Health checks and draining are separate from the selection algorithm |
| Round robin | Rotate eligible backends | Does not account for each request’s cost; it can still exclude unhealthy backends |
| Least connections | Prefer fewer active connections | Connection count is only a proxy for remaining work |
| IP hash / affinity | Keep a routing association | NAT, client address changes, and backend membership changes affect it; shared state may still be needed |
| Horizontal scaling | Add workers or storage nodes | The state partition, coordination, and bottleneck determine scalability |
| Vertical scaling | Increase one node’s resources | Hardware, failure domain, and workload limits remain |
| Read replica | Offload eligible reads | Replication lag and the chosen consistency contract affect read-after-write behavior |
| Sharding | Partition records by a routing key | Resharding, skew, cross-shard queries, and transactions add work |
| API gateway | Centralize client-facing routing/policy | It should not silently take ownership of every domain rule |
| Backend for frontend | Shape operations for one client’s needs | It may aggregate calls; domain invariants still need a clear owner |
| Service mesh | Apply service-to-service transport policy | Implementations can use sidecars or other data-plane layouts |
| Content delivery network (CDN) | Reuse cacheable responses near clients | Cache keys, private data, invalidation, and origin behavior matter for dynamic as well as static content |

SQL and NoSQL describe families of models, not fixed guarantees. Both can provide transactions and distributed operation under particular products/configurations. Choose by access patterns, invariants, indexing, query requirements, and operating cost. Command Query Responsibility Segregation (CQRS) and event sourcing are design choices, not mandatory stages after sharding.

## Decide Which Reads May Be Reused

| Cache pattern | Data path | Failure or freshness question |
| ---------------------------- | ---------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------- |
| Cache-aside | Application reads cache, then source on a miss, then fills cache | Can a fill race with invalidation and restore stale data? |
| Write-through | Writes pass through a cache layer to the source | What happens when one write succeeds and the other fails? The name does not imply an atomic transaction |
| Write-behind | A layer acknowledges before later source persistence | What durable log/recovery path protects acknowledged writes? |
| Expiration/versioning/events | Limit lifetime or invalidate a prior result | What stale interval and lost-invalidation behavior are acceptable? |
| Coalescing / early refresh | Share an in-flight fill or refresh before expiry | Are key, tenant, timeout, and cancellation boundaries correct? |
| Stale-while-revalidate | Return an eligible old value while refreshing | Which values are safe to serve stale, and for how long? |

A cache stampede is a burst of fills for missing/expired keys. A cache hit can still be an incorrect answer if it crosses authorization boundaries or violates a freshness requirement.

## Commit Locally and Deliver Later

| Mechanism | Job | Delivery boundary |
| --------------------------- | ------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------- |
| Queue / competing consumers | Distribute asynchronous work | Acknowledgements, visibility/leases, and retries determine loss or duplication |
| Pub/sub | Fan out to interested consumers | Ephemeral Redis Pub/Sub differs from durable logs and independent consumer groups |
| Kafka partitions/groups | Order within a partition and divide work among a group | Persistence depends on broker/producer configuration; processing order can differ if the application parallelizes |
| Transactional outbox | Commit an entity and its event record together | A separate relay may publish duplicates; the consumer needs stable event identity |
| Change data capture (CDC) | Capture source changes from a database log | Requires permissions, retention, snapshots/checkpoints, schema handling, and an operational owner |
| Webhook | Deliver an event to another service | Authenticate exact bytes, reject replay, deduplicate, and expose exhausted retries for replay/recovery |
| Event sourcing | Retain domain events as the authoritative history | Enforce per-aggregate concurrency/versioning, event evolution, and replay rules |
| CQRS | Separate command and read representations | Projection lag and reconciliation are explicit parts of the read contract |

Do not implement idempotency as “check cache, perform effect, then cache result”: concurrent requests can both perform the effect, and a crash can lose the result. Reserve the scoped key atomically, match the request parameters, and couple it to the durable effect/outcome where possible. External effects need their own idempotency or reconciliation contract.

For Kafka, commit the next offset after the contiguous processed records of each partition. A broad commit of fetched offsets can skip unprocessed records. Before skipping a failed message to a dead-letter destination, confirm durable publication and retain identity; a crash between publish and commit may duplicate it.

## Bound Work During Partial Failure

| Mechanism | What it bounds | Contract to explain |
| ------------------------- | ------------------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| Timeout/deadline | Time spent on an operation | Propagate remaining time, reserve local cleanup time, and cancel work where supported |
| Retry with backoff/jitter | Repeated attempts after a transient failure | Bound attempts/elapsed time, distinguish retryable failures, and make effects idempotent |
| Circuit breaker | Attempts to a failing dependency | Closed collects failures; open rejects; half-open permits bounded probes; recovery resets the defined counters |
| Load shedding | Admitted work during overload | Measure relevant capacity, return an appropriate rejection, and prevent retry amplification |
| Request hedging | Tail latency of an eligible operation | A second attempt increases load; deduplication/cancellation and correlated slowness determine the benefit |
| Feature flag / canary | Exposure to a change | Define cohort, success/abort signals, ownership, and fallback behavior |
| Blue-green deployment | Traffic between two release environments | In-flight work and data/schema compatibility determine whether rollback is safe |
| Chaos experiment | A specific untested failure assumption | State steady behavior, blast radius, observability, and abort conditions |

A fixed-window limiter counts a bucket such as `floor(time / window)`. It can permit nearly twice the nominal limit across a bucket boundary. A sliding window tracks or approximates recent time; token/leaky buckets provide different burst behavior. Updating a counter and its expiration must follow an atomic policy, especially when workers share the limiter.

A Redis lease can use `SET key unique-token NX PX ttl` and a compare-token/delete script for release. This prevents one owner from deleting another owner’s lease, but does not stop a paused old owner from acting after expiry. A protected resource must enforce fencing/version conditions when that stale work would violate correctness. `SETNX` alone is not a complete lock or leader-election algorithm.

## State the Consistency Contract Per Operation

Linearizability makes each operation appear to take effect at one point between invocation and response. Eventual consistency permits divergence while updates propagate under its convergence assumptions. These are not interchangeable meanings of “the latest write.”

During a network partition, the consistency, availability and partition-tolerance (CAP) result shows that a distributed read/write object cannot provide both linearizable behavior and termination of every request at every non-failed node under the theorem’s model. Partition tolerance is an operating assumption; this is not a general instruction to “pick any two” for the whole product. Different operations can block, reject, or accept divergence differently. PACELC names the same partition availability/consistency decision (P→A/C), then the latency/consistency tradeoff when operating normally (else→L/C).

Multi-region design therefore starts with write ownership, conflict policy, replication, failover, and recovery-point/time objectives. Active-passive and active-active describe traffic/state arrangements, not fixed cost multipliers or guaranteed recovery times. DNS TTL is only one part of failover. Financial invariants require a valid coordination model wherever writes occur; a region label alone does not enforce them.

## Choose an Approximation for a Specific Question

| Structure | Question | Error/assumption |
| ---------------- | ------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------ |
| Bloom filter | Might this item be present? | Ordinary insert-only filters can give false positives; correctly inserted values have no false negatives under the model |
| Cuckoo filter | Might this item be present, with deletion? | Fingerprints collide; insertion can fail at high load; delete only values whose membership is known |
| HyperLogLog | How many distinct values? | Memory/error depend on precision; Redis’s implementation uses up to 12 KB with about 0.81% standard error |
| Count-Min Sketch | How often was this key observed? | Standard nonnegative updates overestimate through collisions; it is not itself a complete top-k algorithm |
| Merkle tree | Does a branch match a trusted digest? | A balanced tree permits logarithmic-size proofs; collision-resistant hashes and trusted root context matter |

## Operate the Components You Added

Containers package a process and dependencies; Kubernetes reconciles workloads, endpoints, and scaling. Deployments manage replica changes, Services select reachable endpoints, and Ingress/Gateway implementations handle eligible traffic. Probes, resource requests/limits, PDBs, and HPA address different conditions; use the [platform reference](70.3.06-docker-kubernetes-cicd-cheat-sheet.md) for their contracts rather than duplicating manifests here.

Metrics aggregate behavior, logs record selected events, and traces connect operations; none alone explains every failure. OpenTelemetry standardizes instrumentation/export paths, including trace context. Choose sampling based on the evidence needed and cost. Baggage propagates across boundaries and can expose data; it is not trusted authorization state.

A service-level indicator (SLI) measures behavior, a service-level objective (SLO) defines its target, and a service-level agreement (SLA) defines contractual commitments. For a simple time-based 99.9% availability target over exactly 30 days, the unavailable-time allowance is 43.2 minutes. Request-based indicators use different denominators.

The twelve-factor principles address configuration, dependencies, processes, backing services, lifecycle, logs, and administrative work; deployment platforms do not automatically satisfy them. Soft deletion marks application state, while retention and access policies decide what can still be read or restored. A Kafka tombstone is a keyed null value used by compaction; a CDC delete event and its optional tombstone are related but distinct records.

## Summary

Give each component one stated role in a concrete operation. Size that work, identify the authoritative state, and define concurrency, freshness, delivery, and recovery boundaries. Add distribution or approximation only for a requirement it demonstrably addresses.

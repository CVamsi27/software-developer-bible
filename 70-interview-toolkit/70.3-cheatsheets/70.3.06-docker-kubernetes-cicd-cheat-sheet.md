# Docker, Kubernetes & CI/CD Cheat Sheet

## Definition

Container delivery moves a tested application from source to an image, then from an image to running workloads. Docker builds and runs the artifact; Kubernetes reconciles workloads; CI and GitOps systems establish how an approved artifact becomes desired state.

## First Principles

A tag can change, a process can start without being ready, and a replacement can fail after the old instance has stopped. Delivery therefore needs identifiable artifacts, separate startup/traffic checks, and a rollout path whose failure and rollback behavior is understood.

## Follow the Artifact and the Control Loops

```text
source + lockfile → build/test → image digest → desired manifests
                                            → controller → pods → ready endpoints
CI establishes evidence and identity; GitOps compares desired state with live state.
```

A Deployment updates replica ownership, a Service selects reachable endpoints, and an HPA adjusts the target replica count. A PDB governs eligible eviction requests. These controls solve different problems; combining them does not guarantee zero downtime.

## Inspect the Stage That Failed

| Command / Concept | Key Point | Example |
| ---------------------------------- | -------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------ |
| `docker build` | Build with tags; use BuildKit | `DOCKER_BUILDKIT=1 docker build -t app:1.4.2 .` |
| `docker run` | `-e` env, `-p` ports, `--rm` cleanup | `docker run --rm -p 3000:3000 --env-file .env app:1.4.2` |
| `docker exec` | Shell into running container | `docker exec -it app sh` |
| `docker logs` | Follow + tail | `docker logs -f --tail 100 app` |
| `docker system df` / builder prune | Inspect usage before deleting build cache | `docker system df`; `docker builder prune` prompts before deletion |
| Multi-stage build | Compile stage heavy, runtime stage slim | see pattern below |
| `.dockerignore` | Exclude node_modules, .git, dist | speeds context upload massively |
| Distroless/alpine runtime | Fewer packages can reduce exposed dependencies; compatibility and updates still matter | Use a supported image version compatible with native dependencies; pin its digest |
| `kubectl get` | `-o wide`, `-o yaml`, label selectors | `kubectl get pods -l app=api -o wide` |
| `kubectl describe` | First stop for debugging | `kubectl describe pod api-7d9f-x2v` |
| `kubectl logs` | `-f` follow, `-c` container, `-p` previous crash | `kubectl logs api-7d9f-x2v -c worker --previous` |
| `kubectl exec` | Interactive shell in pod | `kubectl exec -it api-7d9f-x2v -- sh` |
| `kubectl port-forward` | Local access to svc/pod | `kubectl port-forward svc/api 8080:80` |
| `kubectl rollout status` | Watch deployment progress | `kubectl rollout status deploy/api` |
| `kubectl rollout undo` | Rollback to previous revision | `kubectl rollout undo deploy/api --to-revision=3` |
| `kubectl rollout restart` | Rolling restart (config reload) | `kubectl rollout restart deploy/api` |
| `kubectl scale` | Manual replica count | `kubectl scale deploy/api --replicas=5` |
| `kubectl top` | Live resource usage | `kubectl top pods --sort-by=memory` |
| `kubectl events` | Chronological event stream | `kubectl events --for pod/api-7d9f-x2v` |
| `kubectl diff` | Preview apply changes | `kubectl diff -f k8s/` |
| `kubectl apply` | Declarative upsert | `kubectl apply -f k8s/ --recursive` |
| CrashLoopBackOff | App dies at startup → check logs `--previous` | inspect termination reason, probe failures, and previous logs |
| ImagePullBackOff | Bad tag / registry auth | check `describe` Events section |
| OOMKilled | Runtime reports an out-of-memory termination | inspect usage and termination reason; exit 137 alone also means other SIGKILL causes |
| Liveness probe | Restart unhealthy container | must be cheap; never depends on external services |
| Readiness probe | Gate traffic until ready | startup slow? add `startupProbe` instead of huge delays |
| Resource requests/limits | requests = scheduling, limits = cap | CPU limits can throttle; memory pressure can trigger OOM termination |
| PDB (PodDisruptionBudget) | Constrains Eviction API requests such as a voluntary drain | `minAvailable: 1` for small fleets |
| HPA | Autoscale on CPU/memory/custom metrics | CPU/memory utilization metrics need relevant requests; other metric types differ |
| Helm install/upgrade | Package manager for k8s manifests | `helm upgrade --install api ./chart -f values.prod.yaml` |
| Argo CD sync | GitOps pull-based deploy | `argocd app sync api --prune` |

## Build an Artifact That Can Run Independently

### Separate Build Dependencies From Runtime Dependencies

```dockerfile
# ── Stage 1: deps ─────────────────────────────────────────────
FROM node:22-alpine AS deps
WORKDIR /app
COPY package.json package-lock.json ./
RUN npm ci

# ── Stage 2: build ────────────────────────────────────────────
FROM node:22-alpine AS build
WORKDIR /app
COPY --from=deps /app/node_modules ./node_modules
COPY . .
RUN npm run build && npm prune --omit=dev

# ── Stage 3: runtime ──────────────────────────────────────────
FROM node:22-alpine AS runtime
ENV NODE_ENV=production
WORKDIR /app
RUN addgroup -S app && adduser -S app -G app
COPY --from=build --chown=app:app /app/dist ./dist
COPY --from=build --chown=app:app /app/node_modules ./node_modules
COPY --from=build --chown=app:app /app/package.json ./
USER app
EXPOSE 3000
HEALTHCHECK --interval=30s --timeout=3s CMD wget -qO- http://localhost:3000/health || exit 1
CMD ["node", "dist/main.js"]
```

### Keep Dependency Inputs Stable for Cache Reuse

```text
Order from least to most volatile:
1. base image + system deps   (apt/apk)
2. dependency manifests       (package.json lockfile) → npm ci
3. source code                (COPY . .)
4. build output               (npm run build)

Copy lockfiles before source when they are the only install inputs;
also include required workspace manifests, install scripts, or config.
Changed inputs invalidate the layer; actual time depends on the build.
```

### Keep Local Artifacts and Secrets Out of the Context

```text
node_modules
dist
.git
.env*
coverage
.github
```

Adjust exclusions to the build: a workspace may need additional package manifests, and generated or documentation inputs may be required. Docker HEALTHCHECK describes Docker container health; Kubernetes uses its own configured probes.

## kubectl One-Liners

### Trace Scheduling, Startup, and Traffic Readiness

```bash
kubectl get pods -l app=api                       # inspect current state
kubectl describe pod api-7d9f-x2v                  # inspect scheduling and termination events
kubectl logs api-7d9f-x2v --previous --tail=50     # prior container attempt logs
kubectl exec -it api-7d9f-x2v -- sh                # live inspection
kubectl top pod api-7d9f-x2v                       # CPU/mem vs limits
kubectl events --for pod/api-7d9f-x2v --watch      # event stream
```

### Rollouts and rollbacks

```bash
kubectl rollout status deploy/api
kubectl rollout history deploy/api
kubectl rollout undo deploy/api                    # previous revision
kubectl rollout undo deploy/api --to-revision=3
kubectl rollout restart deploy/api                 # pick up configmap/secret changes
kubectl set image deploy/api api=app:1.4.3
kubectl annotate deploy/api kubernetes.io/change-cause="release 1.4.3"  # audit trail
```

### Cross-cutting utilities

```bash
kubectl get all -n staging                      # selected common resources, not literally all kinds
kubectl get events -A --sort-by=.lastTimestamp | tail -20
kubectl auth can-i create deployments --as=system:serviceaccount:staging:ci-bot
kubectl cp api-7d9f-x2v:/tmp/dump.json ./dump.json # requires tar inside the container
kubectl drain node-3 --ignore-daemonsets         # Eviction API; inspect PDBs/local data first
```

### Pod states quick table

| State | Meaning | First move |
| ----------------------- | --------------------------------------------- | ------------------------------------------------------------------------------------- |
| `CrashLoopBackOff` | process exits repeatedly | `logs --previous`; check env/secrets/config |
| `ImagePullBackOff` | can't fetch image | verify tag exists; registry secret present |
| `Pending` | not yet running, possibly scheduling or setup | `describe` → insufficient CPU/mem? taints? PVC bound? |
| `OOMKilled` | runtime-reported OOM | inspect limits, historical usage, and node pressure; `top` may miss a transient spike |
| `Running` but not ready | failing readiness probe | hit the probe endpoint from inside the pod |
| `Evicted` | pod was terminated by an eviction path | inspect reason; node-pressure eviction is not prevented by PDB |

## Kubernetes Manifest Snippets

### Distinguish Startup, Restart, and Traffic Checks

```yaml
startupProbe:                      # gates both liveness and readiness during startup
  httpGet: { path: /health, port: 3000 }
  failureThreshold: 30             # approximate configured startup allowance: 30 x 5s
  periodSeconds: 5
livenessProbe:                     # dead process → restart. NEVER check downstream DBs here
  httpGet: { path: /health, port: 3000 }
  periodSeconds: 10
  timeoutSeconds: 2
readinessProbe:                    # not ready → removed from Service endpoints
  httpGet: { path: /ready, port: 3000 }
  periodSeconds: 5
```

### Budget Resources and Voluntary Disruptions Separately

```yaml
resources:
  requests: { cpu: 250m, memory: 512Mi }   # scheduling + HPA baseline
  limits:   { cpu: "1",  memory: 1Gi }     # CPU can throttle; memory-limit pressure can cause OOM
---
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata: { name: api-pdb }
spec:
  minAvailable: 1                 # constrains eligible voluntary evictions
  selector: { matchLabels: { app: api } }
---
strategy:
  rollingUpdate: { maxSurge: 1, maxUnavailable: 0 }   # illustrative rollout policy; readiness/capacity still matter
```

### Let the HPA Adjust a Specific Target

```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata: { name: api-hpa }
spec:
  scaleTargetRef: { apiVersion: apps/v1, kind: Deployment, name: api }
  minReplicas: 3
  maxReplicas: 20
  metrics:
    - type: Resource
      resource: { name: cpu, target: { type: Utilization, averageUtilization: 70 } }
```

## Render a Release and Observe Its Rollout

```bash
helm upgrade --install api ./chart \
  --namespace prod --create-namespace \
  -f values.prod.yaml \
  --set image.tag=1.4.3 \
  --wait --timeout 5m                # observes Helm readiness criteria; not application acceptance

helm rollback api 12 -n prod         # release revision, not k8s revision
helm history api -n prod
helm diff upgrade api ./chart -f values.prod.yaml   # plugin; preview like terraform plan
helm template api ./chart -f values.prod.yaml       # render locally, pipe to kubectl diff
helm lint ./chart && helm show values ./chart
```

## Connect CI Evidence to a Deployment

CI should install from the lockfile, run the relevant checks, build once, and publish an identifiable artifact. A deployment must then obtain cluster credentials, choose the exact artifact, apply an authorized change, and check its rollout. A YAML job calling Helm without a configured cluster or release values is not a working deployment pipeline.

| Concern | Mechanism | Limit |
| --------------------- | ------------------------------------------------ | -------------------------------------------------------------------------------------------------------------- |
| Dependency downloads | `setup-node` package-manager cache | Caches the package manager’s downloads, not a ready `node_modules` tree |
| Docker layers | Buildx GitHub Actions cache backend | Cache availability/permissions and keys still affect reuse |
| Task outputs | Turborepo/Nx local or configured remote cache | `actions/cache` archives a directory; it does not itself create a remote-cache service |
| Stale validation runs | Workflow concurrency groups | Canceling a live deployment can interrupt a multi-step change; define deployment policy separately |
| Deployment protection | GitHub environment rules | Naming an environment does not create required reviewers; support depends on plan/repository and configuration |
| Supply-chain identity | Pinned action commits, image digests, provenance | Pinning identifies content; updates, permissions, and validation remain necessary |

Use the [GitHub Actions chapter](../../40-platform/40.3-ci-cd/01-ci-platforms/40.3.1.01-github-actions.md) for the complete workflow and [artifact promotion chapter](../../40-platform/40.3-ci-cd/02-build-and-deploy/40.3.2.03-artifact-registries-release-promotion.md) for the handoff from build to deployment.

## Argo CD Commands

```bash
argocd login argocd.example.com --sso
argocd app list
argocd app get api                        # sync status + health
argocd app diff api                       # git vs cluster drift
argocd app sync api                       # deploy git state
argocd app sync api --revision 1a2b3c4    # sync specific commit
argocd app sync api --prune --resource apps:Deployment:api   # scoped sync
argocd app history api
argocd app rollback api 14                # NOT recommended in GitOps: revert the commit instead
argocd app terminate-op api               # kill stuck sync
```

In GitOps, change the desired Git state to the intended prior release and reconcile it. Argo CD does not permit a rollback operation while automated sync is enabled. A one-off live change without a corresponding desired-state change may be overwritten when reconciliation runs.

## Summary

Follow the artifact from build inputs to a digest, desired manifests, running pods, and ready endpoints. Separate resource, rollout, eviction, and scaling controls; connect CI evidence to the system that owns deployment state.

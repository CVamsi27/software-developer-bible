# Docker, Kubernetes & CI/CD Cheat Sheet

A new image passed CI, but the Pods never become Ready and the Service has no healthy endpoints. Trace the artifact, startup process, probes, scheduling, and rollout before changing cluster settings.

```bash
kubectl get pods -l app=api -o wide      # inspect current state
kubectl describe pod api-7d9f-x2v        # scheduling and termination events
kubectl logs api-7d9f-x2v --previous     # prior container attempt logs
```

## Definition

**Container delivery** moves a tested application from source to an **image**, then from an image to running workloads. **Docker** builds and runs the artifact; **Kubernetes** reconciles workloads; **CI** and GitOps systems establish how an approved artifact becomes desired state.

> **Textbook Definition:** Containerization packages an application with its execution dependencies; orchestration reconciles workloads against desired state, while continuous integration and delivery establish validation and release processes.

## First Principles

A tag can change, a process can start without being ready, and a replacement can fail after the old instance has stopped. Delivery therefore needs identifiable artifacts, separate startup and traffic checks, and a rollout path whose failure and rollback behavior is understood.

## How It Works

### 1. Follow the Artifact and the Control Loops

```text
source + lockfile → build/test → image digest → desired manifests
                                            → controller → pods → ready endpoints
CI establishes evidence and identity; GitOps compares desired state with live state.
```

A Deployment updates replica ownership, a Service selects reachable endpoints, and a HorizontalPodAutoscaler (HPA) adjusts the target replica count. A PodDisruptionBudget (PDB) governs eligible eviction requests. These controls solve different problems; combining them does not guarantee zero downtime.

### 2. Build an Artifact That Can Run Independently

| Command | Key point | Example |
| ---------------------------------- | -------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------ |
| `docker build` | Build with tags; use BuildKit | `DOCKER_BUILDKIT=1 docker build -t app:1.4.2 .` |
| `docker run` | `-e` env, `-p` ports, `--rm` cleanup | `docker run --rm -p 3000:3000 --env-file .env app:1.4.2` |
| `docker exec` | Shell into running container | `docker exec -it app sh` |
| `docker logs` | Follow + tail | `docker logs -f --tail 100 app` |
| `docker system df` / builder prune | Inspect usage before deleting build cache | `docker system df`; `docker builder prune` prompts before deletion |

| Image hygiene | Key point |
| ---------------------------------- | ----------------------------------------------------------------------------------------------------- |
| Multi-stage build | Compile stage heavy, runtime stage slim (see pattern below) |
| `.dockerignore` | Exclude node_modules, .git, dist — speeds context upload massively |
| Distroless/alpine runtime | Fewer packages can reduce exposed dependencies; compatibility and updates still matter — pin a digest |

The Dockerfile assumes a single npm package with `package-lock.json`, a build producing `dist/main.js`, and a server listening on `0.0.0.0:3000` with a `/health` endpoint. It uses Node 24, the current LTS line for this example. The `node:24-alpine` tag keeps the snippet readable and can move over time; pin the same reviewed base-image digest in each stage for a reproducible release. A workspace, native library or required runtime asset needs its own build inputs.

```dockerfile
# ── Stage 1: deps ─────────────────────────────────────────────
FROM node:24-alpine AS deps
WORKDIR /app
COPY package.json package-lock.json ./
RUN npm ci

# ── Stage 2: build ────────────────────────────────────────────
FROM node:24-alpine AS build
WORKDIR /app
COPY --from=deps /app/node_modules ./node_modules
COPY . .
RUN npm run build && npm prune --omit=dev

# ── Stage 3: runtime ──────────────────────────────────────────
FROM node:24-alpine AS runtime
ENV NODE_ENV=production
WORKDIR /app
RUN addgroup -S app && adduser -S app -G app
COPY --from=build --chown=app:app /app/dist ./dist
COPY --from=build --chown=app:app /app/node_modules ./node_modules
COPY --from=build --chown=app:app /app/package.json ./
USER app
EXPOSE 3000
HEALTHCHECK --interval=30s --timeout=3s CMD wget -qO- http://localhost:3000/health || exit 1
CMD ["node", "dist/main.js"]
```

Order layers from least to most volatile for cache reuse: base image and system deps, then dependency manifests (`npm ci`), then source code, then build output. Copy lockfiles before source when they are the only install inputs; changed inputs invalidate the layer. Keep local artifacts and secrets out of the context (`node_modules`, `dist`, `.git`, `.env*`, `coverage`, `.github`) — adjusting exclusions to the build. Docker HEALTHCHECK describes Docker container health; Kubernetes uses its own configured probes.

### 3. Inspect the Stage That Failed

| kubectl inspection | Key point |
| ---------------------------------- | -------------------------------------------------------------------------------------- |
| `kubectl get` | `-o wide`, `-o yaml`, label selectors: `kubectl get pods -l app=api -o wide` |
| `kubectl describe` | First stop for debugging: `kubectl describe pod api-7d9f-x2v` |
| `kubectl logs` | `-f` follow, `-c` container, `-p` previous crash |
| `kubectl exec` | Interactive shell in pod: `kubectl exec -it api-7d9f-x2v -- sh` |
| `kubectl port-forward` | Local access to svc/pod: `kubectl port-forward svc/api 8080:80` |
| `kubectl top` / `events` / `diff` | Live resource usage; chronological event stream; preview apply changes |

| kubectl rollout and mutation | Key point |
| ---------------------------------- | -------------------------------------------------------------------------------------- |
| `kubectl rollout status` | Watch deployment progress: `kubectl rollout status deploy/api` |
| `kubectl rollout undo` | Rollback to previous revision: `kubectl rollout undo deploy/api --to-revision=3` |
| `kubectl rollout restart` | Rolling restart for config reload: `kubectl rollout restart deploy/api` |
| `kubectl scale` | Manual replica count: `kubectl scale deploy/api --replicas=5` |
| `kubectl apply` | Declarative upsert: `kubectl apply -f k8s/ --recursive` |
| `kubectl drain` | Eviction API — inspect PDBs and local data first |

| Pod state | Meaning | First move |
| ----------------------- | --------------------------------------------- | ------------------------------------------------------------------------------------- |
| `CrashLoopBackOff` | process exits repeatedly | `logs --previous`; check env/secrets/config |
| `ImagePullBackOff` | can't fetch image | verify tag exists; registry secret present |
| `Pending` | not yet running, possibly scheduling or setup | `describe` → insufficient CPU/mem? taints? PVC bound? |
| `OOMKilled` | runtime-reported OOM | inspect limits, historical usage, and node pressure; `top` may miss a transient spike |
| `Running` but not ready | failing readiness probe | hit the probe endpoint from inside the pod |
| `Evicted` | pod was terminated by an eviction path | inspect reason; node-pressure eviction is not prevented by PDB |

`kubectl rollout restart` creates new Pods. ConfigMap and Secret values exposed as environment variables change only in newly created Pods. Normal projected volume files update eventually, but the application must reload them; a `subPath` mount does not receive updates. If an HPA owns the replica count, a manual `kubectl scale` can be overwritten by its next reconciliation. Cross-cutting utilities: `kubectl get events -A --sort-by=.lastTimestamp | tail -20`, `kubectl auth can-i create deployments --as=system:serviceaccount:staging:ci-bot`, and `kubectl cp` (requires tar inside the container).

### 4. Declare Probes, Budgets and Autoscaling

Probe and resource fragments belong under a container in a Pod template; strategy belongs under a Deployment spec. Documents containing only those fragments cannot be applied as complete resources. The PDB and HPA blocks are full resource shapes but still require matching workloads and metrics support.

```yaml
startupProbe:                      # gates both liveness and readiness during startup
  httpGet: { path: /health, port: 3000 }
  failureThreshold: 30             # approximate configured startup allowance: 30 x 5s
  periodSeconds: 5
livenessProbe:                     # dead process → restart. NEVER check downstream DBs here
  httpGet: { path: /health, port: 3000 }
  periodSeconds: 10
  timeoutSeconds: 2
readinessProbe:                    # not ready → normally excluded from ready Service endpoints
  httpGet: { path: /ready, port: 3000 }
  periodSeconds: 5
```

```yaml
resources:
  requests: { cpu: 250m, memory: 512Mi }   # scheduling + HPA baseline
  limits:   { cpu: "1",  memory: 1Gi }     # CPU can throttle; memory-limit pressure can cause OOM
---
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata: { name: api-pdb }
spec:
  minAvailable: 1                 # constrains eligible voluntary evictions
  selector: { matchLabels: { app: api } }
---
strategy:
  rollingUpdate: { maxSurge: 1, maxUnavailable: 0 }   # illustrative rollout policy; readiness/capacity still matter
```

```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata: { name: api-hpa }
spec:
  scaleTargetRef: { apiVersion: apps/v1, kind: Deployment, name: api }
  minReplicas: 3
  maxReplicas: 20
  metrics:
    - type: Resource
      resource: { name: cpu, target: { type: Utilization, averageUtilization: 70 } }
```

### 5. Render a Release and Observe Its Rollout

```bash
helm upgrade --install api ./chart \
  --namespace prod --create-namespace \
  -f values.prod.yaml \
  --set image.tag=1.4.3 \
  --wait --timeout 5m                # observes Helm readiness criteria; not application acceptance

helm rollback api 12 -n prod         # release revision, not k8s revision
helm history api -n prod
helm diff upgrade api ./chart -f values.prod.yaml   # plugin; preview like terraform plan
helm template api ./chart -f values.prod.yaml | kubectl diff -f - # render and preview locally
helm lint ./chart && helm show values ./chart
```

The `image.tag=1.4.3` value above is illustrative. In production, deploy an immutable image tag or digest through the chart's supported value so rollback identifies the exact artifact.

### 6. Connect CI Evidence to Deployment and Reconcile GitOps State

CI should install from the lockfile, run the relevant checks, build once, and publish an identifiable artifact. A deployment must then obtain cluster credentials, choose the exact artifact, apply an authorized change, and check its rollout. A YAML job calling Helm without a configured cluster or release values is not a working deployment pipeline.

| Concern | Mechanism | Limit |
| --------------------- | ------------------------------------------------ | -------------------------------------------------------------------------------------------------------------- |
| Dependency downloads | `setup-node` package-manager cache | Caches the package manager’s downloads, not a ready `node_modules` tree |
| Docker layers | Buildx GitHub Actions cache backend | Cache availability/permissions and keys still affect reuse |
| Task outputs | Turborepo/Nx local or configured remote cache | `actions/cache` archives a directory; it does not itself create a remote-cache service |
| Stale validation runs | Workflow concurrency groups | Canceling a live deployment can interrupt a multi-step change; define deployment policy separately |
| Deployment protection | GitHub environment rules | Naming an environment does not create required reviewers; support depends on plan/repository and configuration |
| Supply-chain identity | Pinned action commits, image digests, provenance | Pinning identifies content; updates, permissions, and validation remain necessary |

```bash
argocd login argocd.example.com --sso
argocd app list
argocd app get api                        # sync status + health
argocd app diff api                       # git vs cluster drift
argocd app sync api                       # deploy git state
argocd app sync api --revision 1a2b3c4    # sync specific commit
argocd app sync api --prune --resource apps:Deployment:api   # scoped sync
argocd app history api
argocd app rollback api 14                # NOT recommended in GitOps: revert the commit instead
argocd app terminate-op api               # kill stuck sync
```

In GitOps, change the desired Git state to the intended prior release and reconcile it. Argo CD does not permit a rollback operation while automated sync is enabled. A one-off live change without a corresponding desired-state change may be overwritten when reconciliation runs. Use the [GitHub Actions chapter](../../40-platform/40.3-ci-cd/01-ci-platforms/40.3.1.01-github-actions.md) for the complete workflow and [artifact promotion chapter](../../40-platform/40.3-ci-cd/02-build-and-deploy/40.3.2.03-artifact-registries-release-promotion.md) for the build-to-deployment handoff.

## Summary

Follow the artifact from build inputs to a digest, desired manifests, running pods, and ready endpoints. Separate resource, rollout, eviction, and scaling controls; connect CI evidence to the system that owns deployment state.

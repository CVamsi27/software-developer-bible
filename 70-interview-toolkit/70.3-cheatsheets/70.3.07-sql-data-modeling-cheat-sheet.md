# SQL & Data Modeling Cheat Sheet

A report joins customers to orders and shows the same customer twice. That may be correct — a join emits one row per matching pair. Understand row meaning and multiplicity before adding DISTINCT or changing the index.

```text
row meaning + constraints → joins (combine rows) → windows/aggregates (calculate)
                          → predicates + indexes (access) → isolation (concurrency)
```

## Definition

**SQL** describes which rows to select and combine. **Data modeling** defines what a row represents and which constraints must hold; **indexes** help the database find rows without changing their meaning.

> **Textbook Definition:** SQL is a declarative language for relational data operations; relational modeling defines keys, constraints and dependencies that determine valid states and query meaning.

## First Principles

A result can contain duplicates, missing matches, and NULL values. Constraints prevent invalid stored states, while isolation governs what concurrent operations can observe. Performance tuning must preserve those semantics before changing the plan.

## How It Works

### 1. Combine Rows With Join Types

A join forms a row for each matching pair. It is not a set intersection: two matching right rows repeat the left values twice.

| Join | Role |
| ------------ | -------------------------------------------------------------------------------------- |
| INNER | Keep matching pairs |
| LEFT / RIGHT | Also preserve unmatched rows from the chosen side with NULL padding |
| FULL OUTER | Preserve unmatched rows from both sides, as well as all matching pairs |
| CROSS | Produce every pair; useful for an intentionally constructed grid |
| SELF | Join aliases of the same table, such as employee and manager |
| LATERAL | Let a right-side subquery reference each left row, for example its top matching orders |

An outer join's `ON` condition determines matches; a later `WHERE` condition can remove the NULL-padded rows and effectively change the result. Ordinary `=` with NULL yields unknown; `IS NOT DISTINCT FROM` supplies null-safe equality when that is the desired relationship.

```sql
-- Anti-join: users with no orders.
SELECT u.id, u.email
FROM users u
LEFT JOIN orders o ON o.user_id = u.id
WHERE o.id IS NULL;

-- Same columns and semantics; compare plans rather than assuming a winner:
SELECT u.id, u.email FROM users u
WHERE NOT EXISTS (SELECT 1 FROM orders o WHERE o.user_id = u.id);
```

### 2. Calculate Across Rows With Window Skeletons

Each snippet assumes the named tables and columns exist. A window calculates across related rows without collapsing them like GROUP BY. Ordering chooses which row comes before another; its frame chooses which of those rows contribute to an aggregate. Output order still needs an outer ORDER BY when the caller requires it.

```sql
-- Latest row per user (dedup pattern)
SELECT * FROM (
  SELECT *, ROW_NUMBER() OVER (PARTITION BY user_id
                               ORDER BY created_at DESC, id DESC) AS rn
  FROM sessions
) t WHERE rn = 1;

-- Period-over-period delta
SELECT ts, price,
       price - LAG(price) OVER (ORDER BY ts) AS change,
       price::numeric / NULLIF(LAG(price) OVER (ORDER BY ts), 0) - 1 AS pct_change
FROM prices;

-- One row per day; a seven-row frame is seven days only without gaps
SELECT day, revenue,
       SUM(revenue) OVER (ORDER BY day ROWS UNBOUNDED PRECEDING) AS running_total,
       AVG(revenue) OVER (ORDER BY day
         ROWS BETWEEN 6 PRECEDING AND CURRENT ROW) AS avg_last_7_rows
FROM daily_sales;

-- Top three distinct ratings per group; ties can return more than three rows
SELECT * FROM (
  SELECT *, DENSE_RANK() OVER (PARTITION BY category
                               ORDER BY rating DESC) AS rnk
  FROM products
) t WHERE rnk <= 3;
```

For latest-row selection, use a unique tiebreaker and a defined NULL ordering if timestamps may be NULL. The price example assumes one sample per timestamp; otherwise add a unique tiebreaker to each window order. **Frame syntax in PostgreSQL:** the default frame is `RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW` when ORDER BY is present — RANGE lumps peer rows with the same sort value together, so use `ROWS` explicitly when you mean physical row counts.

### 3. Find Rows With Indexing Rules

A composite B-tree groups rows by its key order. Equality constraints on leading keys followed by a range key often bound a useful slice, for example `(tenant_id, created_at)` for one tenant's recent records. A trailing-column predicate can still use an index; PostgreSQL 18 may use skip scan when repeatedly searching the few distinct leading-key values is economical. The leading-prefix guideline describes efficiency, not an absolute usability ban.

`INCLUDE` supplies output columns without making them search keys. An index-only scan can still fetch heap pages to verify tuple visibility. A partial index is eligible when the planner can prove the query implies its predicate; exact textual repetition is not required. A suitable index may supply sort order, including a backward scan; otherwise sorting can be the best plan. Every index consumes storage and maintenance work — check selectivity, query frequency, update cost and the chosen plan. Before dropping an apparently unused index, inspect a representative measurement period and whether it enforces a constraint or serves rare critical work.

### 4. Read EXPLAIN Output With a Checklist

`EXPLAIN ANALYZE` executes the statement; writes and triggers can have side effects. Inspect an appropriate workload and use a rollback plan for transactional changes. Work down this list:

1. **Scan type**: compare scanned rows and predicate selectivity. A sequential scan can be appropriate even on a large table; an index-only scan may still report heap fetches.
2. **Rows estimate vs actual**: a large gap suggests statistics, skew, or correlated predicates to investigate; it does not prove one cause.
3. **Sort nodes**: `Sort Method: external merge (Disk)` means the sort spilled to disk; check workload, sort volume and per-operation memory before changing memory or indexes.
4. **Join algorithm**: Nested Loop can fit when the outer side is small and the inner side is indexed; Hash Join can fit larger equality joins; Merge Join can fit ordered inputs. Assess actual repeated work rather than judging an algorithm by its name.
5. **Filter pushed down?**: look for the filter inside the scan node, not applied after a wide fetch.
6. **Buffers**: shared hits versus reads show PostgreSQL buffer behavior; a read may still be served by the operating-system cache.
7. **Loops**: per-loop average time × loops helps identify repeated work. Parent timings include child work, so do not sum every node as independent cost.

### 5. Normalize With One-Liners

| Form | One-liner | Classic violation |
| ---- | --------------------------------------------------------------------- | ----------------------------------------------------------------------- |
| 1NF | Values follow the chosen domains; avoid encoded repeating groups | `children: "Ann, Bob"` in one cell |
| 2NF | No non-prime attribute depends on a proper subset of a candidate key | course_name depends only on course_id inside (student_id, course_id) PK |
| 3NF | Non-key facts do not depend transitively on a key | employee row repeats department_name determined by department_id |
| BCNF | Every determinant of a nontrivial functional dependency is a superkey | teaching-dependent anomalies in (student, course, teacher) |

State functional dependencies before splitting tables. When a measured read path needs duplication, define its update and refresh mechanism plus tolerated staleness. Arrays or JSON are not automatically modeling errors; the chosen row meaning and access patterns determine whether they belong.

### 6. Apply Common Modeling Patterns

**Audit / history table.** Populate via trigger or explicit app-layer write in the same transaction as the update:

```sql
CREATE TABLE order_audit (
  id           bigint GENERATED ALWAYS AS IDENTITY,
  order_id     bigint        NOT NULL,
  changed_at   timestamptz   NOT NULL DEFAULT now(),
  changed_by   text,
  diff         jsonb         NOT NULL,     -- {field: [old, new]}
  PRIMARY KEY (id)
);
CREATE INDEX ON order_audit (order_id, changed_at DESC);

-- populate via trigger or explicit app-layer write in the
-- same transaction as the update
```

Partitioning requires `PARTITION BY` and actual partitions; merely including a timestamp in a primary key does not partition this table. An audit table is append-only only if permissions and mutation paths enforce that policy. Variants: slowly changing dimension (SCD) Type 2 with valid_from, valid_to and current_flag columns for point-in-time entity state; append-only events table when consumers want the stream itself.

**Soft delete done safely.** The view supplies a filtered read interface, but callers with direct base-table access can bypass it — enforce privileges and, where appropriate, row-level security:

```sql
ALTER TABLE documents ADD COLUMN deleted_at timestamptz;

-- unique constraint that ignores deleted rows (Postgres):
CREATE UNIQUE INDEX documents_name_live
  ON documents (owner_id, name) WHERE deleted_at IS NULL;

-- every read path MUST filter; enforce with views/RLS:
CREATE VIEW live_documents AS
  SELECT * FROM documents WHERE deleted_at IS NULL;
```

Restoring a deleted record can conflict with the partial unique index if its name was reused. Pitfalls to name in interviews: uniqueness enforcement, foreign keys referencing deleted rows, and forgotten filters leaking "deleted" data. Alternative: hard delete plus an audit and archive table.

**Many-to-many with attributes (junction entity).** If the link table grows real attributes or an independent lifecycle, promote it to a first-class entity:

```sql
CREATE TABLE enrollments (
  student_id  bigint REFERENCES students(id),
  course_id   bigint REFERENCES courses(id),
  grade       numeric(4,2),
  enrolled_at timestamptz NOT NULL DEFAULT now(),
  PRIMARY KEY (student_id, course_id)      -- natural composite key
);
CREATE INDEX ON enrollments (course_id);    -- reverse lookup direction
```

| Other pattern | One-liner use case |
| --------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| Polymorphic association (type + id) | An ordinary foreign key cannot select a target table dynamically; compare explicit subtype or association tables |
| Single Table Inheritance vs Class Table Inheritance | STI: few sparse columns; CTI: many shared FKs/joins |
| Entity–attribute–value (EAV) | Flexible attribute rows; cross-attribute constraints and queries require explicit design |
| Materialized view | precomputed aggregate refreshed on schedule |
| Outbox table | reliable event publishing alongside DB commit |
| Ledger (append-only entries) | record immutable postings; derived or cached balances must reconcile to the postings |

### 7. Decide What Concurrent Reads May Observe

| Level | Dirty read | Non-repeatable read | Phantom read | Notes |
| ---------------- | ---------------- | ------------------- | ---------------- | ----------------------------------------------------------------------------- |
| Read Uncommitted | no in PostgreSQL | possible | possible | PostgreSQL treats it as Read Committed |
| Read Committed | no | possible | possible | Postgres default |
| Repeatable Read | no | no | no in PostgreSQL | Stable snapshot; write skew can still occur |
| Serializable | no | no | no | conflicts abort → retry logic required |

```sql
BEGIN ISOLATION LEVEL REPEATABLE READ;
SELECT balance FROM accounts WHERE id = 1;   -- snapshot taken
SELECT balance FROM accounts WHERE id = 1;   -- same snapshot, unless this transaction changed the row
COMMIT;

-- serialization failure handling:
-- SQLSTATE 40001 / PG 'could not serialize' → retry the tx
```

Anomaly one-liners: dirty read = uncommitted data visible; non-repeatable = the same row changes between your own reads; phantom = the same predicate returns new rows. Write skew (one reason to use Serializable): two transactions read overlapping rows, then write disjoint rows that jointly break an invariant — for example, each on-call doctor assumes the other remains available.

## Summary

Define row meaning and constraints first. Preserve duplicate/NULL and window-frame semantics while tuning access paths, then select an isolation strategy that protects the operation’s invariant under concurrency.

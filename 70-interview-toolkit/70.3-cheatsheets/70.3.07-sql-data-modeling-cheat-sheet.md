# SQL & Data Modeling Cheat Sheet

## Quick Reference Table

| Concept                   | Key Point                                             | Example                                                             |
| ---------                   | -----------                                             | ---------                                                             |
| INNER JOIN                | Only matching rows both sides                         | `FROM orders o JOIN users u ON o.user_id = u.id`                    |
| LEFT JOIN                 | All left rows; NULLs where no match                   | anti-join pattern: `WHERE b.id IS NULL`                             |
| RIGHT JOIN                | Mirror of LEFT (avoid; flip for readability)          | rarely needed in practice                                           |
| FULL OUTER JOIN           | Union of both sides with NULL padding                 | reconciliation/diff queries                                         |
| CROSS JOIN                | Cartesian product                                     | generate grids/date ranges: `CROSS JOIN generate_series(...)`       |
| SELF JOIN                 | Table joined to itself                                | org chart, adjacency lists: `ON e.manager_id = m.id`                |
| LATERAL join              | Correlated subquery per row                           | top-3 per group without window functions                            |
| `ROW_NUMBER()`            | 1,2,3... deterministic dedup/ranking                  | `ROW_NUMBER() OVER (PARTITION BY u ORDER BY d DESC) = 1`            |
| `RANK()` / `DENSE_RANK()` | Ties share rank; DENSE has no gaps                    | leaderboards with ties                                              |
| `LAG()` / `LEAD()`        | Previous/next row value                               | `price - LAG(price) OVER (ORDER BY ts)` = delta                     |
| Running total             | Aggregate frame                                       | `SUM(x) OVER (ORDER BY d ROWS UNBOUNDED PRECEDING)`                 |
| Moving average            | Bounded frame                                         | `AVG(x) OVER (ORDER BY d ROWS BETWEEN 6 PRECEDING AND CURRENT ROW)` |
| Leftmost-prefix rule      | Composite index used only via leading columns         | index `(a,b,c)` serves `a`, `a+b`, `a+b+c` — not `b` alone          |
| Covering index            | INCLUDE columns → index-only scan                     | `CREATE INDEX ... ON t(a) INCLUDE (b,c)`                            |
| Partial index             | Index a slice of rows                                 | `WHERE status = 'pending'` in index + query must match predicate    |
| Selectivity               | Low-cardinality columns rarely worth indexing alone   | composite beats single-column on gender/status                      |
| `EXPLAIN ANALYZE`         | Actual plan with timings; never trust estimates alone | `EXPLAIN (ANALYZE, BUFFERS) SELECT ...`                             |
| 1NF                       | Atomic values, no repeating groups                    | split `phones = "a, b"` into rows                                   |
| 2NF                       | 1NF + no partial dependency on composite key          | move course-name out of (student_id, course_id) table               |
| 3NF                       | 2NF + no transitive dependencies                      | zip→city belongs in its own table                                   |
| Denormalization           | Deliberate duplication for read speed                 | cached `order_total` on orders header                               |
| Audit table               | Append-only history of changes                        | triggers or app-level dual-write                                    |
| Soft delete               | `deleted_at IS NULL` filter everywhere                | partial index helps: `WHERE deleted_at IS NULL`                     |
| Junction w/ attributes    | M:N plus payload columns                              | `enrollments(student_id, course_id, grade, enrolled_at)`            |
| Isolation levels          | RU < RC < RR < Serializable                           | see table below                                                     |

## Join Types at a Glance

```text
A INNER JOIN B → A ∩ B
A LEFT JOIN B   → all A, matched B or NULL
A LEFT JOIN B WHERE B.key IS NULL → A minus B (anti-join)
A FULL JOIN B   → A ∪ B
A CROSS JOIN B  → every A × every B

Gotchas:
• JOIN ... ON vs comma+WHERE: same result, different semantics
  for outer joins — always use explicit ON.
• NULL never matches anything, not even NULL → use
  IS NOT DISTINCT FROM for null-safe equality joins.
```

### Anti-join: users with no orders

```sql
SELECT u.id, u.email
FROM users u
LEFT JOIN orders o ON o.user_id = u.id
WHERE o.id IS NULL;

-- equivalent, often faster on modern planners:
SELECT id FROM users u
WHERE NOT EXISTS (SELECT 1 FROM orders o WHERE o.user_id = u.id);
```

## Window Function Skeletons

```sql
-- Latest row per user (dedup pattern)
SELECT * FROM (
  SELECT *, ROW_NUMBER() OVER (PARTITION BY user_id
                               ORDER BY created_at DESC) AS rn
  FROM sessions
) t WHERE rn = 1;

-- Period-over-period delta
SELECT ts, price,
       price - LAG(price) OVER (ORDER BY ts) AS change,
       price / LAG(price) OVER (ORDER BY ts) - 1 AS pct_change
FROM prices;

-- Running total and moving 7-day average
SELECT day, revenue,
       SUM(revenue) OVER (ORDER BY day) AS running_total,
       AVG(revenue) OVER (ORDER BY day
         ROWS BETWEEN 6 PRECEDING AND CURRENT ROW) AS avg_7d
FROM daily_sales;

-- Top-N per group (no correlated subquery)
SELECT * FROM (
  SELECT *, DENSE_RANK() OVER (PARTITION BY category
                               ORDER BY rating DESC) AS rnk
  FROM products
) t WHERE rnk <= 3;
```

**Frame syntax one-liner:** default frame is `RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW` when ORDER BY present — RANGE means peer rows (same sort value) are lumped together. Use `ROWS` explicitly when you mean physical row counts.

## Indexing Rules

```text
COMPOSITE INDEX COLUMN ORDER:
1. equality predicates first      WHERE tenant_id = ?
2. then range/sort column          AND created_at > ?
   index (tenant_id, created_at)
   ✓ supports the above; ✗ cannot seek on created_at alone

LEFTMOST PREFIX:
index (a, b, c) serves:
  WHERE a=…                       ✓
  WHERE a=? AND b=?               ✓
  WHERE a=? AND b=? AND c=?       ✓
  WHERE b=?                       ✗ full scan

COVERING (index-only scan):
  CREATE INDEX idx ON orders(user_id, created_at DESC) INCLUDE (total);
  SELECT total FROM orders WHERE user_id=? AND created_at>? ;
  → no heap access; watch "Index Only Scan" in EXPLAIN

PARTIAL:
  CREATE INDEX idx_pending ON orders(created_at)
    WHERE status = 'pending';
  → tiny index; query must repeat the exact predicate

SORT MATCHING:
  ORDER BY a ASC, b DESC needs matching mixed-direction index
  (Postgres: (a ASC, b DESC)); otherwise Sort node appears

WRITE COST:
every index slows INSERT/UPDATE; audit unused indexes via
pg_stat_user_indexes (idx_scan = 0 over months → drop candidate)

RULE OF THUMB:
index what you filter, join, and sort on — nothing speculative
```

## Reading EXPLAIN Output — Checklist

Work down this list when reading `EXPLAIN (ANALYZE, BUFFERS)`:

1. **Scan type**: Seq Scan on large table with selective filter = missing/wrong-order index. Index Scan vs Index Only Scan (latter avoids heap).
2. **Rows estimate vs actual**: off by >10x = stale statistics (`ANALYZE table`) or data-skew trap; planner makes bad choices on bad estimates.
3. **Sort nodes**: `Sort Method: external merge Disk` = spilled to disk; memory bump or matching index removes it.
4. **Join algorithm**: Nested Loop good when outer side small + inner indexed; Hash Join for larger equality joins; Merge Join for pre-sorted inputs. Nested Loop over 1M rows = missing index smell.
5. **Filter pushed down?**: look for the filter inside the scan node, not applied after a wide fetch.
6. **Buffers**: shared hit vs read — high `read` = cache misses; check working set size.
7. **Loops**: actual time × loops is the real cost; a fast step looped 100K times dominates.

```text
GOOD SIGNS                          BAD SIGNS
──────────────────────────────     ──────────────────────────────
Index Only Scan                     Seq Scan + big Filter
Nested Loop (small outer)           Nested Loop (huge outer)
Hash Join (hashed small side)       Sort: external merge Disk
rows est ≈ rows actual              rows est 10 ≠ rows actual 50000
shared hit ≈ 100%, read low         Buffers: read >> shared hit
```

## Normalization Forms — One-Liners

| Form | One-liner                                        | Classic violation                                                       |
| ------ | -----------                                        | -------------------                                                       |
| 1NF  | Attributes atomic; no repeating groups           | `children: "Ann, Bob"` in one cell                                      |
| 2NF  | Every non-key attribute depends on the WHOLE key | course_name depends only on course_id inside (student_id, course_id) PK |
| 3NF  | Non-key attributes depend on nothing but the key | city stored in table keyed by zip                                       |
| BCNF | Every determinant is a candidate key             | teaching-dependent anomalies in (student, course, teacher)              |

Interview line: *"Normalize writes, denormalize reads — and make denormalization explicit (materialized views, sync jobs), not accidental."*

## Common Modeling Patterns

### Audit / history table

```sql
CREATE TABLE order_audit (
  id           bigint GENERATED ALWAYS AS IDENTITY,
  order_id     bigint        NOT NULL,
  changed_at   timestamptz   NOT NULL DEFAULT now(),
  changed_by   text,
  diff         jsonb         NOT NULL,     -- {field: [old, new]}
  PRIMARY KEY (id, changed_at)             -- enables monthly partitions
);
CREATE INDEX ON order_audit (order_id, changed_at DESC);

-- populate via trigger or explicit app-layer write in the
-- same transaction as the update
```

Variants: SCD Type 2 (valid_from/valid_to/current_flag columns) when you need point-in-time entity state; append-only events table when consumers want the stream itself.

### Soft delete done safely

```sql
ALTER TABLE documents ADD COLUMN deleted_at timestamptz;

-- unique constraint that ignores deleted rows (Postgres):
CREATE UNIQUE INDEX documents_name_live
  ON documents (owner_id, name) WHERE deleted_at IS NULL;

-- every read path MUST filter; enforce with views/RLS:
CREATE VIEW live_documents AS
  SELECT * FROM documents WHERE deleted_at IS NULL;
```

Pitfalls to name in interviews: uniqueness enforcement, FK references to deleted rows, and forgotten filters causing "deleted" data leaks. Alternative: hard delete + audit/archive table.

### Many-to-many with attributes (junction entity)

```sql
CREATE TABLE enrollments (
  student_id  bigint REFERENCES students(id),
  course_id   bigint REFERENCES courses(id),
  grade       numeric(4,2),
  enrolled_at timestamptz NOT NULL DEFAULT now(),
  PRIMARY KEY (student_id, course_id)      -- natural composite key
);
CREATE INDEX ON enrollments (course_id);    -- reverse lookup direction
```

Rule: if the link table grows real attributes or an independent lifecycle, promote it to a first-class entity ("association class" in UML terms).

### Other patterns worth naming

| Pattern                                             | One-liner use case                                                              |
| ---------                                             | --------------------                                                              |
| Polymorphic association (type + id)                 | last resort; FKs can't enforce — prefer supertype/subtype tables                |
| Single Table Inheritance vs Class Table Inheritance | STI: few sparse columns; CTI: many shared FKs/joins                             |
| EAV                                                 | extreme flexibility, terrible querying — avoid unless building metadata systems |
| Materialized view                                   | precomputed aggregate refreshed on schedule                                     |
| Outbox table                                        | reliable event publishing alongside DB commit                                   |
| Ledger (append-only balances)                       | money: store immutable entries, derive balance by SUM                           |

## Transaction Isolation Quick Table

| Level            | Dirty read | Non-repeatable read | Phantom read | Notes                                                                         |
| -------            | -----------  | --------------------- | -------------- | -------                                                                         |
| Read Uncommitted | possible   | possible            | possible     | almost never used                                                             |
| Read Committed   | no         | possible            | possible     | Postgres default                                                              |
| Repeatable Read  | no         | no                  | possible*    | *Postgres RR actually blocks phantoms (snapshot); MySQL InnoDB uses MVCC gaps |
| Serializable     | no         | no                  | no           | conflicts abort → retry logic required                                        |

```sql
BEGIN ISOLATION LEVEL REPEATABLE READ;
SELECT balance FROM accounts WHERE id = 1;   -- snapshot taken
SELECT balance FROM accounts WHERE id = 1;   -- identical value guaranteed
COMMIT;

-- serialization failure handling:
-- SQLSTATE 40001 / PG 'could not serialize' → retry the tx
```

Anomaly one-liners: dirty read = uncommitted data visible; non-repeatable = same row changes between your own reads; phantom = same predicate returns new rows. Write skew (Serializable's raison d'être): two tx each read overlapping set and write disjoint rows, jointly breaking an invariant — on-call doctors example.

## Top 10 Things to Remember

1. **Anti-join** for "rows with no match": `NOT EXISTS` or `LEFT JOIN ... IS NULL`.
2. **`ROW_NUMBER() = 1`** is the latest-per-group workhorse; `DENSE_RANK` keeps ties.
3. **LAG/LEAD turn time series into deltas** without self-joins.
4. **Composite index order**: equalities left, range/sort right; verify with EXPLAIN, not faith.
5. **Covering indexes** (`INCLUDE`) buy index-only scans for hot read paths.
6. **Estimates lying?** Rows mismatch > 10x means stale stats or skew before it means bad hardware.
7. **Normalize writes, denormalize deliberately** with a sync mechanism you can name.
8. **Soft delete needs a plan** for uniqueness, FKs, and default filters — or don't soft delete.
9. **Money lives in ledgers**: append-only entries, derived balances, never mutable totals.
10. **Serializable requires retry loops**; Read Committed + optimistic versioning covers most web apps.

## Red Flags (Things NOT to Say)

- "I add an index on every column in the WHERE clause" — composite ordering and write cost matter more than index count.
- "LEFT JOIN is safer so I always use it" — silently multiplies rows and hides missing matches; choose semantics deliberately.
- "We denormalize from day one for performance" — premature; name the measured read path first.
- "Isolation levels don't matter, we have transactions" — transactions give you YOUR level's guarantees, not magic consistency.
- "N+1 is an ORM problem" — it's a modeling/access-pattern problem; batch or dataload regardless of ORM.
- "DELETE FROM users" without soft-delete/audit discussion in any system-of-record context.

## Green Flags (Things TO Say)

- "I verify index usage with `EXPLAIN (ANALYZE, BUFFERS)` before and after."
- "For latest-per-group I use ROW_NUMBER with a partition instead of correlated subqueries."
- "The audit trail is a partitioned append-only table written in the same transaction."
- "Unique constraints that should ignore deleted rows go in a partial unique index."
- "Our default is Read Committed with retries on deadlock; anything invariant-critical bumps to Serializable with a retry budget."
- "Balances are derived from an immutable ledger, never stored as a mutable column."

## 5-Minute Pre-Interview Review

- Joins: INNER ∩, LEFT keep-all, anti-join via NOT EXISTS, LATERAL for per-row subqueries.
- Windows: ROW_NUMBER dedup · RANK ties · LAG deltas · SUM OVER running · explicit ROWS frames.
- Indexes: leftmost prefix · covering INCLUDE · partial WHERE · mixed-direction sorts need matching indexes · drop unused ones.
- EXPLAIN checklist: scan type → row estimate gap → Sort spill → join algorithm → buffers.
- Normal forms: atomic → whole-key → nothing-but-the-key → determinants are keys.
- Patterns: audit table (+SCD2) · soft delete + partial unique index · junction-with-attributes · ledger for money · outbox for events.
- Isolation: RC default; RR kills non-repeatable reads; Serializable adds write-skew protection but demands retries.

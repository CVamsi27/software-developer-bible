# Take-Home Playbook

[![Role priority](https://img.shields.io/badge/role--priority-Important-blue)](../docs/topic-importance.md)
[![General importance](https://img.shields.io/badge/general--importance-Important-blue)](../docs/topic-importance.md)



A take-home is a bounded sample of your engineering work. Start with the employer's brief and time limit, then deliver the smallest complete solution that demonstrates the requested behavior. Neither a preferred framework nor a test count guarantees a pass.

## First Principles

The reviewer cannot observe your development process directly. A runnable submission, focused tests, and a short explanation let them inspect your decisions. A time limit also constrains scope: adding infrastructure consumes time that could complete the required behavior.

## Read the brief before choosing a stack

Write down required behavior, input and output contracts, acceptance criteria, the deadline, permitted tools, and submission visibility. Ask about ambiguities that could change the solution. Follow the stated AI policy and disclose assistance when requested; never conceal it by adding intentional mistakes.

Separate mandatory requirements from optional polish. Use the specified stack. If none is specified, choose tools you can run and explain confidently. A small service does not automatically need NestJS, a state library, or a database.

## Deliver one complete path, then its failures

For a four-hour budget, one possible allocation is:

| Stage | Time | Deliverable |
| --------------- | ----------- | ------------------------------------------------------------ |
| Scope and setup | 30 minutes | Acceptance list and reproducible environment |
| Core path | 100 minutes | One working feature from input through persistence to output |
| Failure cases | 50 minutes | Validation, errors, focused tests, security boundaries |
| Handoff | 40 minutes | Clean checkout rehearsal and README |
| Buffer | 20 minutes | Fix the largest remaining blocker |

These are planning examples, not instructions to exceed an employer's time limit. Report actual time honestly. If requirements cannot fit, explain the trade-off rather than quietly spending a full weekend.

For a database-backed feature, define its invariant and migration early. Build the narrow backend path and UI together enough to prove the contract. Test behaviors that can fail: malformed input, missing records, duplicate requests, permissions, and concurrent updates where relevant. Handle errors at the boundary that can recover or report them; a `try/catch` around every async call adds little by itself.

## Example: a small workflow engine

Suppose the brief requests an HTTP trigger, transform step, outbound request, persisted execution, and completion webhook. Establish the execution states and what a retry means before designing a large framework.

A useful first slice runs one bounded workflow and records the result. Follow with input validation, execution failure, and retry behavior. Outbound URLs need protection against **server-side request forgery (SSRF)**: a submitted URL must not let the workflow reach internal services or other forbidden destinations. Transforms need a constrained format rather than arbitrary server-side `eval`. Provider timeouts can leave the outcome unknown, so do not claim that an execution ID alone makes every external side effect idempotent.

Keep modules separate where responsibilities differ, but do not create dozens of empty layers to resemble a production platform. State omitted durability or isolation features in the handoff.

## Make the submission reproducible

Your README should answer, in this order:

1. What does this implement, and which requirements remain incomplete?
2. How does a reviewer install the pinned dependencies, configure sample values, migrate data, and run it?
3. How do they run tests, lint, and type checking?
4. Which design decisions protect correctness, and what alternatives did you reject?
5. What would you improve next, and why?

Use `.env.example` with placeholders. Do not commit real credentials or private company data. Rehearse from a clean checkout rather than relying on your local database or global tools.

Share through the employer's requested channel. A private repository is valid and may be required; public visibility is not evidence of better commit hygiene. A short walkthrough can help if allowed, but it does not replace a runnable submission.

## Common mistakes

Missing a required feature while polishing architecture is a scope failure. Silent time overruns hide estimation decisions. Fabricated metrics, disguised AI use, and invented employer rubrics undermine the submission. A useful test suite proves the risky behaviors; neither a fixed test count nor 100% line coverage establishes correctness.

## Summary

Respect the brief, deliver a complete path, test its important failures, and explain the remaining work. Stop when the time budget expires and give an honest handoff.

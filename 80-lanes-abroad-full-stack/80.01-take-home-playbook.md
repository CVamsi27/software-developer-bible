# Take-Home Playbook — How to Ship a Winning One

> **The single highest-leverage thing you do in this lane.** Mid-stage EU companies (n8n, SumUp, Scalable, sennder, THRYVE) filter heavily on take-homes. A 4-6 hour take-home replaces the LeetCode phone screen. Master this, and the rest of the loop is straightforward.

## TL;DR

- **Plan for 5-6 hours minimum, even if the brief says "2 hours"** — under-engineering is the #1 reason candidates fail
- **Lead with schema design, then backend, then frontend, then tests, then README** — show engineering judgment
- **Code that compiles, type-safe, no `any`, has tests, has a README = pass** — the bar isn't perfection, it's "can this person ship production code"
- **8-10 hours of work visible in 5 hours of clock time = great signal** — show you've done this before

---

## Why it matters

At FAANG, your LeetCode phone screen is the gate. At EU mid-stage, the take-home is the gate. The company is asking: **"Can you ship a small full-stack feature production-quality in a few hours of async work?"** That's exactly what you'll do on day 1.

A great take-home beats a great system design round. A bad take-home kills your chances even with a great interview loop.

## The 4-Phase Take-Home Framework

### Phase 1: Read the brief (15-20 min, non-negotiable)

Before writing a line of code:

1. **Re-read the brief 3 times.** Mark every requirement. Some are explicit, some implied.
2. **List what's OUT of scope.** If the brief says "small REST API + minimal UI", don't build a dashboard with auth + observability.
3. **Identify the 2-3 things they're secretly testing.** Common patterns:
   - "REST endpoint + DB schema" → can you design a schema, write clean SQL, use transactions correctly
   - "CLI tool" → can you handle edge cases, write good error messages, structure a TS project
   - "Frontend feature + small backend" → can you ship end-to-end, manage state, talk to an API
   - "Workflow engine" (n8n-style) → can you model state, handle concurrency, write tests for async code
4. **Make a 1-page plan before coding.** Write it down. This is the "what I'd do with 24 more hours" sketch.

### Phase 2: Foundation (30-45 min)

- Initialize the repo: TypeScript, ESLint, Prettier, package.json with a real README
- Set up the DB schema first (if applicable) — write a migration
- Set up the API skeleton: routes, controllers, basic validation
- Set up the frontend skeleton: routing, state, API client

**Do not skip this.** A clean foundation means everything after is fast.

### Phase 3: Core implementation (3-4 hours)

The bulk of your time. Order of work:

1. **Schema + migrations** (30 min) — this is your chance to show SQL fluency
2. **Backend core logic** (60-90 min) — endpoints, validation, business logic
3. **Tests** (45-60 min) — at least 5-8 tests covering the happy path + key edge cases
4. **Frontend** (45-60 min) — minimal but complete. Forms, list views, error states.
5. **README** (20-30 min) — see template below
6. **Polish** (30 min) — error handling, edge cases, that one test that's been bugging you

### Phase 4: Submit (15 min)

- Run the test suite one more time
- Push to a public GitHub repo (private repos don't show your commit hygiene)
- Write a 1-paragraph cover note in the application: "I spent ~5 hours, focused on [X], skipped [Y] for time, would add [Z] with more time"
- **Include a 2-3 min Loom video walkthrough** if the brief allows. This is the single highest-ROI thing you can add. Shows communication, walks through decisions, explains trade-offs.

## What they actually evaluate (in order of importance)

| Signal              | Weight | What it means                                                                                                               |
| ------------------- | -----: | --------------------------------------------------------------------------------------------------------------------------- |
| **Code quality**    | 30%    | Type-safe, no `any`, clean structure, readable, idiomatic TS. Show you write code others want to work with.                 |
| **Product sense**   | 20%    | Did you think about edge cases? Error states? UX? Empty states? Loading states?                                             |
| **System thinking** | 15%    | Schema design, API design, observability hooks, security basics. Did you make the right trade-offs?                         |
| **Tests**           | 15%    | 5-10 focused tests. Not 100% coverage, not 0. Real tests for real edge cases.                                               |
| **Commit hygiene**  | 10%    | Meaningful commit messages ("Add user schema", not "fix"), logical PR structure, no `git push --force` history              |
| **README**          | 10%    | Explains design decisions, how to run, what you'd do with more time. **The README is your interview before the interview.** |

## What gets you REJECTED

These are the silent killers. Don't do them.

- **No tests.** Even one is better than zero.
- **No README.** A blank repo with code is a rejection.
- **`any` everywhere in TypeScript.** `unknown` + type guards or proper generics. Always.
- **Hardcoded credentials** in commits (even test ones — use `.env.example`).
- **No error handling.** Every async call needs a try/catch. Every API call needs a 4xx/5xx path.
- **`git push --force` history.** Use a fresh branch.
- **"I'll add tests later" comments.** Add them now. It's 45 minutes.
- **Looks AI-generated without modification.** The bar is "this person clearly wrote this, not pasted from ChatGPT". Vary variable names, leave a typo or two in a comment, make it yours.
- **Over-engineering.** Don't add Kubernetes, GraphQL, microservices, gRPC, OpenTelemetry to a "small REST API" brief.
- **Under-engineering.** Don't submit a single file with no structure, no tests, no README.

## README template (use this)

```markdown
# [Project Name]

> [One sentence: what this does and why]

## Quick start

\`\`\`bash
npm install
npm run db:migrate
npm run dev
\`\`\`

Open http://localhost:3000.

## Design decisions

### Schema
[Brief: what tables, why this shape, what indexes]

### API
[Brief: REST or GraphQL, how errors are returned, how auth works]

### Trade-offs
- I chose [X] over [Y] because [Z]
- I didn't add [A] because [B] but it would be 30 min to add

## What I'd do with 24 more hours

- [ ] Add [X]
- [ ] Add integration tests
- [ ] Add observability hooks
- [ ] Add CI pipeline
- [ ] Add [feature that's in the brief but I cut for time]

## Tests

\`\`\`bash
npm test
\`\`\`

[Number] tests covering [what].
```

**The "What I'd do with 24 more hours" section is gold.** It shows you know what's missing, you just ran out of time. That signals seniority more than a perfect 8-hour take-home does.

## Stack to use (unless the brief says otherwise)

Default to the stack the company uses. If you don't know, use:

- **Backend:** NestJS + Prisma + PostgreSQL — shows you can ship a real TS backend
- **Frontend:** React 18 + TypeScript + a small state lib (Zustand is fine)
- **Validation:** Zod
- **Tests:** Jest + supertest for API, RTL for frontend
- **DB:** PostgreSQL with migrations

If the brief specifies a stack, **use that stack.** Don't argue. They want to see if you can be productive in their world, not yours.

The bible's [Backend Stack/06 Nestjs](../20-backend/20.2-nestjs/INDEX.md), [Backend Stack/08 Database](../20-backend/20.4-database/INDEX.md), [Backend Stack/09 Security](../20-backend/20.5-security/INDEX.md) are your reference.

├── prisma/
│ ├── schema.prisma (Workflow, Execution, Step, StepExecution models)

├── src/
│ ├── main.ts
│ ├── app.module.ts
│ ├── workflows/
│ │
│ │
│ │

│ │
│ │

│ │
│ │

## TL;DR checklist before submitting

- [ ] All tests pass locally
- [ ] Type-check passes (`tsc --noEmit`)
- [ ] Lint passes (`eslint .`)
- [ ] README is filled in with design decisions + "what I'd do with 24h"
- [ ] `.env.example` exists, no real secrets in commits
- [ ] Repo is public (or shared with their HR)
- [ ] Commit history is clean (meaningful messages, no force pushes)
- [ ] Optional: 2-3 min Loom walkthrough
- [ ] 1-paragraph cover note in the application explaining your approach

**Now ship it.**

# Take-Home Playbook

[![Role priority](https://img.shields.io/badge/role--priority-Important-blue)](../docs/topic-importance.md)
[![General importance](https://img.shields.io/badge/general--importance-Important-blue)](../docs/topic-importance.md)

Many senior engineers fail take-home assignments for the exact opposite reason they expect: they spend three hours setting up Docker Compose, clean-architecture folder hierarchies, and custom authentication middleware, then run out of time before the core feature works cleanly.

A take-home is a **time-boxed work sample** — reviewers reward a small, runnable, well-tested vertical slice with clear trade-offs far more than an over-engineered, half-finished platform.

> **Formal definition:** A take-home assessment is a time-bounded work-sample evaluation in which a candidate implements a specified task outside the live interview and submits the result for review.

## First Principles

Because the reviewer was not sitting beside you while you coded, your repository must speak for itself in three ways: it must **run cleanly from a fresh checkout**, its **tests must prove the risky edge cases**, and its README must show why you made your design choices. Every minute spent on unrequested infrastructure steals time from those three signals.

## 1. Lock Down Scope and Rules Before Writing Code

Spend the first 15–20 minutes reading the brief carefully and writing a short checklist:
- **Must-have behavior:** exact application programming interface (API) and user interface (UI) contract, acceptance criteria, and edge cases.
- **Explicit constraints:** time cap, deadline, required stack (if any), and private repository versus ZIP archive submission method.
- **AI and tooling policy:** follow the employer's stated policy honestly and disclose AI assistance whenever asked — never try to hide assistance by planting artificial mistakes.

Ask the recruiter or hiring manager about genuine ambiguities before starting. If no stack is mandated, pick the simplest stack you can build and debug fast; a small Representational State Transfer (REST) service rarely needs microservices or a heavy state library.

## 2. Budget Your Time Around One Working Vertical Slice

For a typical **4-hour timebox**, protect your schedule like this (scale proportionally to the employer's actual limit, and never silently burn a whole weekend pretending it took 4 hours):

| Block | Time | Concrete deliverable |
| ------------------------------ | ------- | -------------------------------------------------------------------------------- |
| **1. Scope and setup** | 30 min | Minimal repository, pinned dependencies, green test runner, acceptance checklist |
| **2. Core vertical slice** | 100 min | End-to-end happy path working (input → persistence → output or UI) |
| **3. Failure cases and tests** | 50 min | Input validation, error responses, security checks, and risky-path tests |
| **4. Clean-checkout handoff** | 40 min | Fresh-directory run check, `.env.example`, and crisp reviewer `README.md` |
| **5. Buffer** | 20 min | Fix the single biggest remaining rough edge |

When building a database-backed feature, enforce the core data invariant (such as a `UNIQUE` constraint or atomic transaction) early. Focus tests on things that break in production — malformed payloads, missing IDs, duplicate requests, permission boundaries, and concurrent updates — rather than chasing arbitrary line-coverage percentages.

## 3. Concrete Example: Scoping a Mini Workflow Engine

Suppose a take-home asks for a Hypertext Transfer Protocol (HTTP)-triggered workflow with a transform step, an outbound HTTP call, persisted run state, and a completion webhook:

1. **First working slice:** Persist one workflow run with explicit states (`pending → running → completed | failed`) and return its status via API.
2. **Real failure and security boundaries:**
   - **Server-Side Request Forgery (SSRF) protection:** User-supplied outbound URLs can trick your server into calling internal metadata endpoints (`169.254.169.254`) or private Virtual Private Cloud (VPC) services. Validate schemes, block private Internet Protocol (IP) ranges, and restrict redirects.
   - **Safe transforms:** Use a constrained JavaScript Object Notation (JSON) mapping or safe expression parser — never server-side `eval()`.
   - **Retry honesty:** If an outbound HTTP call times out, the remote server may have already processed it. Explain that a local execution ID alone does not make an arbitrary external API idempotent without remote idempotency support or reconciliation.
3. **Skip unrequested ceremony:** Keep modules cleanly separated by responsibility without inventing ten boilerplate abstraction layers; list deferred production work (like distributed worker queues) honestly in your `README.md`.

## 4. Make the Reviewer's First 5 Minutes Effortless

Structure your `README.md` in five short sections:
1. **What works and what was intentionally scoped out** (plus honest time spent).
2. **Exact setup and run commands** using pinned versions and `.env.example` (zero committed secrets).
3. **How to run tests, type-check, and lint.**
4. **Key design decisions and trade-offs** (why you chose this schema, concurrency rule, or library).
5. **What you would build next** with another day of engineering time.

**Mandatory final check:** Clone your own submission into a clean temporary folder and follow your `README.md` literally before sending it — local database state or global command-line interface (CLI) tools frequently mask missing setup steps.

## Common Mistakes

- Polishing folder architecture while leaving a core requirement unfinished.
- Silently spending 18 hours on a 4-hour prompt (which misrepresents your estimation judgment).
- Writing 40 trivial unit tests while leaving the real race condition or validation edge case untested.
- Submitting broken setup instructions or committing real API keys.

## Summary

Respect the brief and timebox: build one complete vertical slice first, test the real failure and security boundaries, rehearse setup from a clean checkout, and hand off a short `README.md` that clearly explains your trade-offs and omitted work.

# Tech Screen Patterns — A Focused Starting Set

[![Role priority](https://img.shields.io/badge/role--priority-Important-blue)](../docs/topic-importance.md)
[![General importance](https://img.shields.io/badge/general--importance-Important-blue)](../docs/topic-importance.md)



A coding screen samples problem solving under time constraints. Use the confirmed interview format to set your preparation depth. Geography and company size do not establish which algorithms will appear.

## First Principles

An interviewer sees your reasoning only when you make it observable. Clarifying the input, stating an invariant, tracing a counterexample, and checking complexity provide evidence beyond the final code. Memorizing a pattern without its preconditions does not transfer to an unfamiliar problem.

## Choose breadth from the actual loop

Ask the recruiter about duration, environment, language, and whether the round emphasizes algorithms, debugging, frontend work, or a practical feature. The set below is a starting curriculum, not a claim to cover a percentage of European interviews. Expand it when the job or practice failures call for trees, binary search, union-find, advanced dynamic programming (DP), or another topic.

Use the [canonical coding-pattern flow](../70-interview-toolkit/70.2-coding-patterns/INDEX.md) for implementations and invariants. This guide selects practice; it does not teach a second version of each algorithm.

## Six starting families

| Family | Mechanism to explain | Representative exercises |
| ------------------------ | ---------------------------------------------------------------------------- | ---------------------------------------------------------------------------- |
| Hash map and set | Membership, counts, and accumulated state; expected constant-time lookup | Two Sum, Group Anagrams, Subarray Sum Equals K |
| Sliding window | Maintain a contiguous interval and justify when advancing an edge is safe | Fixed-size maximum sum, longest distinct substring, Minimum Window Substring |
| Two pointers | Use sorted order or another monotonic constraint to eliminate candidates | Sorted Two Sum, 3Sum, Container With Most Water |
| Graph and tree traversal | Track visited state; distinguish shortest unweighted paths from reachability | Number of Islands, level order, Course Schedule, Clone Graph |
| Dynamic programming | Define state, recurrence, base case, and evaluation order | Climbing Stairs, House Robber, Coin Change, Longest Increasing Subsequence |
| Stack and queue | Preserve an ordering invariant and account for each push/pop | Valid Parentheses, Min Stack, Daily Temperatures |

Daily Temperatures uses a monotonic stack. It cannot coherently be recommended while banning that pattern. Likewise, a shortest transformation such as Word Ladder may be a challenging graph exercise; a company's location does not make it easy.

## Practice a mechanism, then vary it

First solve a representative exercise and state why the approach works. Change one constraint: allow negative values, introduce duplicate keys, return indices rather than values, or require online updates. Decide whether the original invariant survives.

For example, shrinking a sliding window when its sum is too large relies on monotonicity for nonnegative inputs. With negative values, that reasoning can fail; a prefix-sum map may suit a different sum problem. Recognizing the boundary matters more than reproducing a memorized template.

Keep an error log with the failed assumption and a delayed reattempt. After reading a solution, close it and reconstruct the reasoning. Mark a topic ready only after you can explain and solve an unfamiliar variation, rather than after a fixed number of completed problems.

## Use the interview time deliberately

A possible 60-minute rehearsal allocates five minutes to clarification, five to an approach and invariant, thirty to implementation, ten to tests and complexity, and ten to follow-ups. Adjust to the interviewer's actual schedule.

Confirm input sizes, ordering, duplicates, mutability, and expected output. Trace a tiny example before coding. Test empty and singleton inputs, boundary values, and a case that violates an attractive but incorrect approach. If stuck, explain the blocked assumption and consider a correct baseline before optimizing. Continuous narration is not required; a brief thinking pause is reasonable.

## Summary

Prepare from the known loop, learn the invariant behind each pattern, and use varied problems to expose gaps. A two-week plan or thirty solved exercises can organize effort; neither guarantees readiness or hiring outcomes.

# Tech Screen Patterns — A Focused Starting Set

[![Role priority](https://img.shields.io/badge/role--priority-Important-blue)](../docs/topic-importance.md)
[![General importance](https://img.shields.io/badge/general--importance-Important-blue)](../docs/topic-importance.md)

Many senior full-stack engineers get tripped up in live coding screens not because they forgot syntax, but because they memorized a LeetCode template without understanding *when that template breaks*. When an interviewer changes one small constraint — like allowing negative numbers in a subarray-sum problem — a memorized sliding window silently fails. This guide gives you a high-leverage starting set of six problem families and a practice method built around **invariants** rather than rote memorization.

> **Formal definition:** A technical screening interview is an initial assessment of role-relevant technical competence through observable reasoning, implementation, or diagnosis under stated constraints.

## First Principles

Your interviewer can only grade reasoning they can observe. Clarifying input constraints, naming the **invariant** your loop maintains, tracing a concrete edge case before coding, and deriving real time/space complexity demonstrate senior problem solving even when you hit a snag midway through.

## 1. Confirm the Screen Format Before Drilling

Ask the recruiter what the live technical screen actually covers: algorithmic coding, debugging an existing codebase, building a small React/Node feature, or SQL/API design. Do not assume European startups never ask algorithms or that US companies only ask LeetCode Hard.

Use the [canonical coding-pattern curriculum](../70-interview-toolkit/70.2-coding-patterns/INDEX.md) for full code implementations and derivations. Expand beyond the six starting families below whenever the role or mock feedback calls for binary search, heaps, tries, union-find, or interval problems.

## 2. Six High-Value Starting Families

| Pattern family | Core invariant to explain aloud | Classic starter problems |
| ---------------------------- | ----------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------- |
| **Hash map & set** | Trade $O(n)$ memory for $O(1)$ average lookup of seen values, counts, or prefix sums | Two Sum, Group Anagrams, Subarray Sum Equals K |
| **Sliding window** | Maintain a valid contiguous `[left..right]` window and advance `left` only when validity breaks | Max Sum Subarray of Size K, Longest Distinct Substring, Minimum Window Substring |
| **Two pointers** | Exploit sorted order or symmetry to eliminate impossible pairs without nested loops | Sorted Two Sum, 3Sum, Container With Most Water |
| **Graph & tree BFS/DFS** | Track `visited` state so cycles never loop; use BFS for unweighted shortest paths | Number of Islands, Level-Order Traversal, Course Schedule, Clone Graph |
| **Dynamic programming (DP)** | Define subproblem state, recurrence transition, base cases, and evaluation order | Climbing Stairs, House Robber, Coin Change, Longest Increasing Subsequence |
| **Stack & monotonic stack** | Keep unresolved items ordered so each element is pushed and popped at most once ($O(n)$) | Valid Parentheses, Min Stack, Daily Temperatures |

*Example invariant (`Daily Temperatures`):* keep a stack of unresolved day indices in strictly decreasing temperature order; the moment a warmer day arrives, pop every cooler day from the top and record its wait distance.

## 3. How to Practice So Patterns Transfer to Unseen Problems

Memorizing 50 solutions breaks the moment a constraint shifts. Instead, run a **three-step variation drill** on every problem:

1. **Solve & explain the invariant:** State in one sentence *why* your algorithm cannot miss the optimal answer.
2. **Mutate one constraint:** Allow negative numbers, duplicate keys, streaming inputs, or returning indices instead of values — then check whether your invariant still holds.
   - *Classic trap:* Shrinking a sliding window when `sum > target` only works if all numbers are **non-negative** (so removing from the left strictly shrinks the sum). Once negative numbers are allowed, shrinking can *increase* the sum — you must switch to a **prefix-sum hash map**.
3. **Log failed assumptions:** Keep a short error log of *which assumption failed* and re-solve that variant cold 3–5 days later without looking at notes.

## 4. Pacing a 60-Minute Coding Screen

Use this flexible rhythm (adjust to the interviewer's exact clock):
- **0–5 min (Clarify):** Confirm input sizes, empty/null cases, duplicates, negative values, mutability, and return format.
- **5–10 min (Design & trace):** State a brute-force baseline first if helpful, then propose the clean approach with its invariant and trace a 4-element example by hand.
- **10–40 min (Code cleanly):** Write modular, readable code with clear variable names. It is fine to pause silently for 15 seconds when thinking — just say *"Give me a second to check this edge case."*
- **40–50 min (Test & analyze):** Walk through empty, single-element, duplicate, and boundary inputs line by line; state time and extra space complexity accurately.
- **50–60 min (Follow-ups):** Reason through scale, streaming, or concurrency extensions.

## Summary

Match your prep to the confirmed screen format, master the invariants behind six core problem families, and test every pattern against mutated constraints (like negative numbers breaking sliding windows) so you can reason through unseen problems calmly under interview time pressure.

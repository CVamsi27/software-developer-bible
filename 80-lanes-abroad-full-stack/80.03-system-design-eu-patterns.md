# System Design — From Requirements to Failure Recovery

A design interview asks you to justify a system under stated constraints. Use the role and product to choose rehearsal cases; do not assume that all European startups share a particular loop or that a few rehearsals guarantee readiness.

## First Principles

Capacity comes from workload, not a technology name. Distributed components can fail independently, so a useful design must explain how its invariants survive partial failure. Team size, operating cost, privacy, and recovery objectives constrain which mechanisms are practical.

## Start with a decision the system must protect

Clarify the critical user operation, its correctness invariant, peak workload, acceptable latency, durability, and recovery target. Separate requirements from assumptions. A booking system might allow stale search results while requiring one confirmed owner per seat; saying the whole system is either “strong” or “eventual” hides that distinction.

Draw the simplest end-to-end path that meets these constraints. Add a cache, queue, or additional service only when a requirement justifies it. [The general design approach](../30-architecture/30.2-system-design/01-theory/30.2.1.15-how-to-approach.md) provides the full framework.

## Make estimates change the design

For a hypothetical 10,000 daily users making twenty requests each, average load is `200,000 / 86,400 ≈ 2.3 requests/second`. A chosen 10× peak factor gives about 23 requests/second; it is an assumption to validate, not a measured percentile.

At 1,000 persisted transactions/second and 1 KB each, raw storage grows by about 86.4 GB/day or 31.5 TB/year, before indexes, replicas, and retention. This is very different from 100 GB/year. State units, retention, and overhead; then decide whether partitioning or archival is warranted.

A CDN can serve appropriate cacheable responses. It does not automatically absorb authenticated mutations or arbitrary database traffic.

## Rehearse six different correctness boundaries

| Case | Invariant and useful deep dive | Failure to address |
| -------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------- |
| [Payment gateway](../30-architecture/30.2-system-design/02-case-studies/30.2.2.06-payment-gateway.md) | Record a stable request key, bound it to the payload, and reconcile the ledger with the provider | A timeout may follow a successful charge; query/reconcile before issuing a new charge |
| Workflow engine | Persist execution state, constrain outbound requests, and bound retries/concurrency | A worker can die after an external side effect but before recording completion |
| Multi-tenant SaaS | Authorize membership in the selected tenant, scope all data access, and verify isolation | A signed token or `tenant_id` column alone does not prevent cross-tenant reads |
| [Ticket booking](../30-architecture/30.2-system-design/02-case-studies/30.2.2.08-ticket-booking.md) | Enforce inventory ownership in a transaction or conditional write; define hold expiry | Payment can complete as a hold expires; resolve late outcomes explicitly |
| Event processing | Partition ordering by the required key; use durable deduplication or idempotent effects | A crash between processing and acknowledgement leads to redelivery |
| [Notifications](../30-architecture/30.2-system-design/02-case-studies/30.2.2.07-notification-service.md) | Keep user preferences and durable send intent; bound retries by channel | Provider acceptance is not delivery; a timeout can make resend outcomes ambiguous |

A normal payment-provider API is not a participant in your database's two-phase commit. A saga coordinates local transactions and compensations; it does not make a refund equivalent to “the charge never happened.” An outbox couples local state with publish intent, while consumers and external providers still need their own retry semantics.

For SaaS analytics, moving data into another database does not remove authorization or privacy requirements. Minimize and aggregate data according to purpose. GDPR does not impose a universal EU-only hosting rule; see the [scoped compliance guide](80.24-eu-regulatory-compliance.md).

## Follow one request through success and failure

Explain the schema and constraints for the main operation. Trace a normal request, then a duplicate, a timeout, and a component restart. Identify where state becomes durable and how another worker discovers incomplete work. Discuss the consistency requirement at each boundary rather than claiming end-to-end exactly-once delivery.

Show how metrics expose an invariant violation or a growing queue. Define an alert from a user-facing objective, a recovery procedure, and any deliberate degraded behavior. Some operations should fail closed; “graceful degradation” is not permission to sell the same seat twice.

## Summary

A coherent design connects workload, invariants, mechanisms, and recovery. Rehearse several domains to discover missing reasoning, then deepen the weak boundary rather than repeating the same boxes.

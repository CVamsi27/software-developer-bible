# System Design for EU Mid-Stage — Patterns and Cases

> **System design at EU mid-stage is 45-60 min, 1 problem, focused on shipping judgment.** Not the 5-component monstrosity FAANG wants. This file is the framework + the most common EU cases (payment gateway, multi-tenant SaaS, event-driven workflows, real-time booking).

## TL;DR

- **The 4-phase framework:** Clarify → Estimate → High-level → Deep-dive. Always. Don't skip.
- **EU mid-stage cases are usually company-adjacent** — n8n asks about workflow engines, SumUp asks about payment gateways, sennder asks about event-driven systems.
- **Depth over breadth:** pick 2-3 critical components, go deep. Don't try to cover 8 services shallowly.
- **Always discuss trade-offs:** CAP, eventual consistency, idempotency, exactly-once, cost.

The bible's [Architecture Stack/11 System Design](../30-architecture/30.2-system-design/INDEX.md) has 31 case studies. This file is the **what to drill for EU mid-stage** subset + framework.

## First Principles

1. **EU startup design interviews weight *cost and team-fit of the solution* alongside scale** — a Kafka+K8s design for 10k MAU reads as over-engineering; the constraint set is small team + runway + B2B SLAs, so the right answer is usually boring and observable.
2. **GDPR is a design input, not a compliance footnote**: data residency, deletion paths, and PII segmentation change architecture (→ 80.24) — mentioning them proactively is the single cheapest seniority signal in this market.

## The 4-Phase Framework (use every time)

### Phase 1: Clarify (5 min)

Before drawing anything, ask:

- **What's the functional scope?** "Build a URL shortener" — is it just encode/decode, or also analytics, auth, custom aliases?
- **What's the scale?** "10K DAU" vs "10M DAU" — totally different designs.
- **What's in scope vs out?** Auth? Rate limiting? Analytics dashboard?
- **What are the non-functional requirements?** Latency target (p99 < 200ms?), durability (no data loss?), consistency (strong or eventual?).

**You do NOT start drawing boxes until you've asked 3-5 questions.** This is the #1 mistake candidates make.

### Phase 2: Estimate (2 min)

Back-of-envelope numbers. Just rough.

- **QPS:** "10K DAU, 1 req/s/user peak = 10K QPS. Average 1K QPS, p99 5K."
- **Storage:** "1KB per record × 10M records = 10GB. 1KB × 100M records × 365 days = 36TB/year."
- **Bandwidth:** "10K QPS × 1KB = 10MB/s. CDN can absorb this."

Numbers don't need to be exact. They need to be in the right order of magnitude and to inform your design choices.

### Phase 3: High-level design (10 min)

Boxes and arrows. Top-down.

```
[Client] → [CDN] → [API Gateway] → [Service] → [Database]
                              ↓
                         [Cache]
                              ↓
                         [Queue] → [Worker]
```

**Don't dive deep yet.** Get the architecture on the page. Then ask "what's the most important component to discuss?" — usually the database, the queue, or the cache.

### Phase 4: Deep-dive (20 min)

Pick 2-3 critical components. Go deep.

- **Database:** schema, indexes, partitioning, replication, migrations
- **Cache:** what to cache, TTL, invalidation strategy, cache stampede
- **Queue:** at-least-once vs at-most-once vs exactly-once, DLQ, retry
- **API:** REST vs GraphQL, versioning, pagination, auth
- **Observability:** metrics, logs, traces, alerting, SLI/SLO

Discuss trade-offs explicitly. "We chose [X] over [Y] because [Z]." The senior signal.

## Most common EU mid-stage cases

### 1. Payment Gateway (SumUp, Scalable Capital, any fintech)

This is asked at virtually every EU fintech. The 4-phase answer:

**Clarify:** Online + in-person? Multi-currency? Fraud detection? Idempotency requirements?
**Estimate:** 1K TPS, 1KB per transaction, 100GB/year.
**High-level:** Client → API → Payment Service → PSP (Stripe/Adyen) → Bank. Async webhook for confirmation.
**Deep-dive:**
- **Idempotency keys** — every request needs one, so retries don't double-charge
- **Two-phase commit** between ledger DB and PSP — saga pattern
- **Reconciliation** — daily batch to compare internal ledger with PSP records
- **PCI compliance** — never store card numbers, tokenize via PSP
- **Fraud detection** — rule engine + ML, sync in request path

See: [Payment Gateway](../30-architecture/30.2-system-design/02-case-studies/30.2.2.06-payment-gateway.md)

### 2. Workflow Engine (n8n, sennder, Hostaway, GoGlobal)

The "node-based" or "DAG execution" pattern. Very common.

**Clarify:** Triggers? HTTP only or also scheduled? Webhooks? Retries? Concurrency?
**Estimate:** 100K executions/day, 1KB per execution, 100MB/day.
**High-level:** Trigger → Queue → Worker → Execute steps → Update state → Webhook on complete.
**Deep-dive:**
- **State machine** for execution: queued → running → completed / failed / retried
- **Idempotency** per step so retries don't double-execute
- **Concurrency control** — limit parallel executions per workflow
- **Persistence** — every state transition must be durable
- **Observability** — execution trace per workflow, step-level timings
- **Error handling** — retry policy per step, DLQ for permanent failures

This is n8n's exact use case. Read their engineering blog before the interview.

### 3. Multi-Tenant SaaS (any B2B SaaS — Docita, Hostaway, Scalable)

**Clarify:** How many tenants? 100? 100K? Data isolation requirement? Per-tenant customization?
**Estimate:** 1K tenants, 100 users each, 10M records total.
**High-level:** Tenant ID on every row → API gateway extracts tenant from JWT → RLS in DB.
**Deep-dive:**
- **Tenant isolation** — shared DB + tenant_id column vs schema-per-tenant vs DB-per-tenant
- **RBAC** — roles per tenant, audit logging
- **Data partitioning** — by tenant_id for query performance
- **Cross-tenant analytics** — separate analytics DB, no tenant_id filter
- **Migrations** — backwards-compatible, no downtime

### 4. Real-Time Booking (Peter Park, Booking.com, GetYourGuide)

The "two users grab the last slot" problem.

**Clarify:** Single resource? Multi-resource? Hold timeout? Payment integration?
**Estimate:** 10K searches/sec, 100 bookings/sec peak, 1M bookings/day.
**High-level:** Search service (Elasticsearch) → Booking service (Postgres + row-level locks) → Payment service → Confirmation.
**Deep-dive:**
- **Concurrency** — `SELECT ... FOR UPDATE` on slot row, or optimistic locking with version
- **Hold/release pattern** — slot held for 10 min during payment, then released
- **Idempotency** — booking ID is idempotency key
- **Saga** — hold → charge → confirm, with compensating actions
- **Cache** — slot availability in Redis with short TTL

See: [Ticket Booking](../30-architecture/30.2-system-design/02-case-studies/30.2.2.08-ticket-booking.md)

### 5. Event-Driven Microservice (sennder, THRYVE, any data platform)

**Clarify:** What events? Throughput? Ordering requirements? Schema evolution?
**Estimate:** 10K events/sec, 1KB per event, 1TB/day.
**High-level:** Producers → Kafka → Consumers (multiple) → Storage / Downstream services.
**Deep-dive:**
- **Topic design** — one topic per domain event type
- **Schema evolution** — Avro/Protobuf with schema registry, backwards-compat
- **Ordering** — partition by aggregate ID, single consumer per partition
- **Idempotency** — consumer-side dedup by event ID
- **DLQ** — poison message handling
- **Replay** — keep topics for 7 days, support re-processing

See: [Microservices](../20-backend/20.6-microservices/INDEX.md) for the full microservices reference.

### 6. Notification Service (every company has one)

The "push, email, SMS, in-app" problem.

**Clarify:** Channels? User preferences? Templating? Batching? Priority?
**Estimate:** 1M notifications/day, 10K/min peak.
**High-level:** API → Queue → Channel workers (email/SMS/push) → Provider → Retry/DLQ.
**Deep-dive:**
- **Provider abstraction** — same interface for SendGrid, Twilio, FCM
- **Idempotency** — same notification_id won't send twice
- **Templating** — Handlebars or similar, locale-aware
- **Rate limiting** — per-channel, per-user
- **Retry** — exponential backoff, max 5 attempts, then DLQ

See: [Notification Service](../30-architecture/30.2-system-design/02-case-studies/30.2.2.07-notification-service.md)

## What gets you REJECTED on system design

- **Start drawing before clarifying.** Always ask 3-5 questions first.
- **No estimates.** Always give QPS, storage, bandwidth numbers (rough is fine).
- **Single point of failure everywhere.** Every service needs a backup or graceful degradation.
- **"I'll just add Redis" without explaining what for.** Be specific: cache, rate limit, distributed lock, pub/sub.
- **Cannot discuss trade-offs.** Always picking "scale" or "consistency" without nuance = junior.
- **No observability.** "How do you know it's broken?" — metrics, logs, traces, alerts.
- **No failure modes.** "What if this service goes down?" — every service needs a degraded-mode answer.
- **Can't code the data model.** If you say "users table" you should be able to sketch columns + indexes on a whiteboard.

## Practice: 5 cases, 1 each, with timer

Pick 5 of the cases above. Set a 45-min timer. Record yourself (Loom or Zoom). Then review:

1. Did you ask clarifying questions?
2. Did you give estimates?
3. Did you do high-level before deep-dive?
4. Did you discuss trade-offs?
5. Did you address failure modes?

After 5 rounds of this, you'll be sharper than 90% of candidates.

# System Design — From Requirements to Failure Recovery

[![Role priority](https://img.shields.io/badge/role--priority-Important-blue)](../docs/topic-importance.md)
[![General importance](https://img.shields.io/badge/general--importance-Important-blue)](../docs/topic-importance.md)

The fastest way to bomb a senior system design interview at a product startup is drawing Kafka, Redis, Kubernetes, and five microservices before asking how many users the system has or what happens when a payment times out. Product-company interviewers care far more about whether you can protect a **business invariant** cleanly — and recover gracefully when one network call fails — than how many boxes fit on a whiteboard.

> **Formal definition:** System design is the specification of components, data models, interfaces, and interactions that satisfy a system's functional requirements and quality constraints.

## First Principles

Complexity should be **earned by workload or failure requirements**, never added by habit. Every distributed call can time out or execute twice, so a senior design always answers two questions: *what must never go wrong (the invariant)*, and *how does the system recover when a component crashes halfway through?*

## 1. Start With the One Invariant the System Must Protect

Before drawing anything, lock down five constraints with the interviewer:
1. Core user action and **non-negotiable correctness rule** (e.g., never double-book a seat, never charge a customer twice).
2. Expected traffic, read/write ratio, and burstiness.
3. Consistency needs **per operation** (a booking app can serve 30-second-stale search results while requiring strong consistency on the final checkout confirmation).
4. Durability, retention, and privacy/tenancy boundaries.
5. Team size and operational simplicity.

Draw the **simplest end-to-end path** that works first (client → API → database). Introduce caches, queues, or extra services only when a concrete bottleneck or failure mode demands them. See [How to Approach System Design](../30-architecture/30.2-system-design/01-theory/30.2.1.15-how-to-approach.md) for the full 45-minute structure.

## 2. Do Simple Back-of-the-Envelope Math That Actually Changes Decisions

Numbers only matter when they tell you whether one PostgreSQL instance is enough or whether you need partitioning, caching, or async queues:

- **Traffic example:** `10,000 daily users × 20 requests/day = 200,000 requests/day`. Divide by `86,400 seconds/day` ≈ **2.3 requests/second average**. Even with a generous 10× peak assumption (~23 req/sec), one well-indexed PostgreSQL database handles this comfortably without sharding.
- **Storage example:** `1,000 persisted transactions/second × 1 KB/row = 86.4 GB/day` ≈ **31.5 TB/year** of raw rows before indexes, backups, and replicas. That immediately tells you partitioning, retention policies, and cold archival matter on day one.
- **CDN boundary:** A CDN absorbs public static assets and cacheable `GET` responses — it does **not** solve authenticated writes or database lock contention.

## 3. Six Core Product-Engineering Failure Boundaries to Master

| Domain | Core invariant to enforce | Classic failure interviewers probe |
| ------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------ |
| **[Payment gateway](../30-architecture/30.2-system-design/02-case-studies/30.2.2.06-payment-gateway.md)** | Bind an idempotency key to the exact payload; reconcile internal ledger with provider | Provider call times out *after* charging the card — reconcile before issuing a new charge |
| **Workflow engine** | Persist step state & versioned definition; guard outbound URLs against SSRF | Worker crashes after calling an external API but before saving completion |
| **Multi-tenant SaaS** | Verify tenant membership on every request and enforce scope in queries/jobs/caches | A `tenant_id` column alone leaks data if one endpoint, export, or background worker forgets the filter |
| **[Ticket booking](../30-architecture/30.2-system-design/02-case-studies/30.2.2.08-ticket-booking.md)** | Atomic hold with owner + expiry via transaction or conditional write | Payment callback arrives right as the hold-expiry job releases the seat |
| **Event processing** | Partition by aggregate ordering key; deduplicate durably at the consumer | Worker crashes after updating DB but before acking broker → duplicate redelivery |
| **[Notifications](../30-architecture/30.2-system-design/02-case-studies/30.2.2.07-notification-service.md)** | Save durable send intent atomically with the business write; bound retries per channel | SMS/email provider accepts request, then connection drops before your app records success |

### Three senior distinctions interviewers love to hear

- **External APIs don't join your DB transaction:** A payment gateway cannot participate in PostgreSQL two-phase commit. A **saga** coordinates local commits plus explicit compensations (a refund is a *new* ledger event, not pretending the charge never happened).
- **Outbox != magic end-to-end exactly-once:** A transactional outbox guarantees your local DB commit and event record happen atomically, but consumers and remote APIs still need idempotency or reconciliation.
- **Analytics & compliance follow the data:** Copying rows into an analytics warehouse does not erase tenant authorization or GDPR duties (see [EU Regulatory Compliance](80.24-eu-regulatory-compliance.md) — note GDPR does not mandate EU-only hosting universally, it governs lawful transfer mechanisms).

## 4. Trace One Request Through Happy Path AND Failure

Once your core diagram is up, walk the interviewer through four concrete moments:
1. **Happy path:** Schema, primary/unique constraints, and where state becomes durable.
2. **Duplicate request:** User double-clicks or client retries after a 504.
3. **Mid-flight crash:** Server dies right after an external API call or right before acking a queue message.
4. **Observability & fail-closed rule:** Which metric pages you when the invariant drifts or queues back up, and which operations must **fail closed** (refuse safely rather than corrupting inventory or leaking data).

## Summary

Anchor every system design in one clear business invariant and realistic workload math, build the simplest end-to-end architecture that satisfies it, and spend your deep-dive time tracing duplicates, timeouts, crashes, and recovery rather than piling on unrequested distributed components.

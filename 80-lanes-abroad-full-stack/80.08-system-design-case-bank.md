# System Design Case Bank — Twelve Failure Boundaries

[![Role priority](https://img.shields.io/badge/role--priority-Important-blue)](../docs/topic-importance.md)
[![General importance](https://img.shields.io/badge/general--importance-Important-blue)](../docs/topic-importance.md)



Use these cases to practice different engineering decisions. They are hypothetical workloads, not claims about a company's interview questions or a second implementation library. Read the [design approach](80.03-system-design-eu-patterns.md), follow the canonical links where needed, then use [section revision](REVISION.md) for retrieval practice.

## First Principles

Transfer comes from recognizing the same invariant under changed constraints. Repeating a memorized diagram can hide that ability. A good case therefore changes the failure boundary, not just the product name.

## Case 1: Workflow execution

Model a trigger, durable execution state, step attempts, and completion delivery. Start with one sequential workflow before introducing branches or parallelism. Workers may restart between an external side effect and the state update; choose provider idempotency, reconciliation, or an explicit ambiguous state rather than claiming that a queue guarantees exactly-once effects.

Use leases with ownership/version checks for concurrent workers, a constrained transform format, and an outbound-request security boundary. Queue ordering depends on partitioning and worker behavior, not merely one queue per workflow. Rehearse a step that waits a day without holding a process or database transaction open.

## Case 2: Payments

Protect one payment intent across retries and provider timeouts. Bind a request key to its payload and scope; persist the outcome and reject a key reused with different input. Authorization, capture, void, refund, and reconciliation are separate operations. A saga is not a distributed two-phase commit with a normal PSP API.

At a hypothetical 1,000 transactions/second and 1 KB each, raw records grow by about 31.5 TB/year before replicas and indexes. Retention changes the storage design. Hosted payment collection can reduce card-data exposure but does not automatically remove all PCI obligations. See the [payment case](../30-architecture/30.2-system-design/02-case-studies/30.2.2.06-payment-gateway.md).

## Case 3: Tenant isolation

Authenticate the user, authorize tenant membership and the operation, then constrain queries and writes to that tenant. Include background work, object storage, cache keys, exports, and analytics in the boundary. Moving analytics to another database does not permit unrestricted access.

For PostgreSQL RLS, verify the actual runtime role, owner/BYPASSRLS behavior, read and write policies, and transaction-local tenant context when pooling. A connection-time session setting can leak between requests. A tenant column alone or an uncalled policy file proves little. See [multi-tenancy](../30-architecture/30.2-system-design/02-case-studies/INDEX.md) for the case library.

## Case 4: Inventory and booking

Separate searchable availability from authoritative inventory. Commit a hold with an owner, expiry, and a conditional write or transaction that prevents competing claims. On payment completion, verify the hold still belongs to the request; an expiry worker can race the callback.

A zero-row conditional update means the claim failed; it is not permission to retry a charge. Retry confirmation safely or compensate a late payment according to policy. Inventory, payment, and message delivery each have their own idempotency boundary. See [ticket booking](../30-architecture/30.2-system-design/02-case-studies/30.2.2.08-ticket-booking.md).

## Case 5: Event processing

Choose the ordering key before the topic layout. Different topics do not provide a single order for an aggregate across all its event types. Preserve partition ordering through consumer processing and define a policy for a poison event: skipping it may violate the domain sequence.

Deduplication must cover the replay horizon and be coupled to the business effect where possible. A seven-day Redis TTL is not a universal guarantee. Schema compatibility depends on format and consumer versions; validate the configured rules rather than applying “never change any field” mechanically. See [message brokers](../20-backend/20.9-message-brokers/INDEX.md).

## Case 6: Caching

Choose data whose permitted staleness you can describe. Tenant-scoped keys are necessary but do not replace authorization. Sensitive data can require additional controls; schedules can also contain sensitive information, so “schedules safe, patients forbidden” is an inadequate policy.

An invalidation can race a stale cache refill. Short TTL limits some stale periods but does not enforce a booking invariant. Plan stampede protection and database capacity when the cache fails; unrestricted fallback can overload the database. See [caching](../20-backend/20.8-caching/INDEX.md).

## Case 7: Analytics

Start with the required metric, freshness, retention, and access purpose. A small operational report may need a SQL query or scheduled job, not Kafka plus Flink plus ClickHouse. Introduce stream processing when latency and workload justify it.

Omitting patient names does not automatically anonymize an event. Identifiers, timing, and rare combinations can still identify people. Aggregate and minimize data, enforce tenant access, and specify late-event/deduplication rules. See [compliance scope](80.24-eu-regulatory-compliance.md).

## Case 8: Rate limiting

Distinguish burst capacity from sustained rate and select a key from trusted identity. A token bucket needs atomic refill and consume against a consistent time source; a fixed-window counter is a different algorithm.

For 100 tenants at 100 requests/minute each, the combined steady quota is 10,000/minute, about 167/second. A proposed 10,000/second peak needs a separate burst assumption. Local fallback across ten instances can multiply the effective quota; choose that trade-off explicitly or fail closed for a hard spending/security limit. See [Redis patterns](../20-backend/20.8-caching/INDEX.md).

## Case 9: Feature flags

Choose the stable bucketing unit: a tenant-wide rollout should hash the tenant, not each user. Define how configuration versions reach evaluators and what happens when the provider is unavailable. Flags are not an authorization boundary.

A sixty-second result cache cannot provide an instantaneous kill switch. State a propagation target and verify it across clients and server instances. A local evaluator can be appropriate without a Redis round trip for each decision. See the [design library](../30-architecture/30.2-system-design/02-case-studies/INDEX.md).

## Case 10: Disaster recovery

Define RPO (acceptable data loss) and RTO (recovery time) from the business operation. Model backup restore and replica promotion as distinct recovery paths. An async replica can preserve corruption too; backups and restore tests remain necessary.

Amazon RDS manages automated backups and engine replication; its read replicas do not consume a hand-built S3 WAL archive as depicted in the older diagram. RPO depends on actual lag and recoverable points, while RTO includes promotion/restore, credentials, routing, capacity, and validation. A 500 GB restore cannot be promised in thirty minutes without a measured drill. [RDS backups](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/USER_WorkingWithAutomatedBackups.html), [RDS read replicas](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/USER_ReadRepl.html).

## Case 11: Notifications

Write durable delivery intent with the business transaction, then track each channel's attempts and outcome separately. An outbox does not prevent a provider from accepting a message before a worker crashes. Use supported idempotency and reconciliation, and distinguish accepted, delivered, and read states.

Choose channel permissions and content minimization explicitly. A patient name is not inherently necessary in an email; a secure portal link may meet the requirement. A blanket “in-app always on for clinical safety” rule needs a product-specific safety contract. See [notifications](../30-architecture/30.2-system-design/02-case-studies/30.2.2.07-notification-service.md).

## Case 12: Connection pooling

At a hypothetical 2,000 requests/second with each holding a database connection for 0.1 seconds, average demand is about 200 busy connections. Twenty backends at the same hold time serve about 200 requests/second; a pool does not create tenfold query capacity.

Measure database time, waiting time, transaction duration, and aggregate pools across instances. Reduce demand or bound admission before merely increasing connections. Transaction pooling changes session features and does not fix leaked transactions automatically. [PgBouncer's feature matrix](https://www.pgbouncer.org/features.html) documents compatibility boundaries.

## Summary

For each case, protect one invariant, trace a partial failure, and explain recovery. Vary the assumptions after a rehearsal so the reasoning must transfer. Keep implementations in the canonical chapters and practice questions in the separate revision file.

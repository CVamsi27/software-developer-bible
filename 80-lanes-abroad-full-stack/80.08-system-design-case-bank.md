# System Design Case Bank — Twelve Failure Boundaries

[![Role priority](https://img.shields.io/badge/role--priority-Important-blue)](../docs/topic-importance.md)
[![General importance](https://img.shields.io/badge/general--importance-Important-blue)](../docs/topic-importance.md)

Memorizing one "Design Twitter" diagram falls apart the moment an interviewer shifts the constraint to double-booking, tenant leaks, or crashed background workers.

Each of the twelve compact cases below isolates **one real-world production failure boundary** that appears repeatedly in senior full-stack interviews. Read [System Design — From Requirements to Failure Recovery](80.03-system-design-eu-patterns.md) first, practice deriving the invariant for each case below, and follow the canonical chapter links whenever a mechanism feels rusty.

## First Principles

Real senior fluency shows up when you recognize the *same* underlying failure mode under a new product wrapper. Practice mutating one assumption in every case (for example, a slow worker wakes up late, a payment callback arrives after expiry, a cache falls over) rather than repeating memorized component diagrams.

## Case 1: Workflow execution

**Core boundary:** A worker executes an external application programming interface (API) step and crashes *before* writing `completed` to the database.

- Start with a sequential run before adding parallel branches; persist immutable run input and definition version so edits do not corrupt in-flight runs.
- Protect concurrent worker claims with **leases plus fencing and version checks**: if Worker A pauses during a garbage-collection (GC) stall and wakes up after its lease expired, the state store must reject its stale write.
- A queue alone never guarantees exactly-once remote side effects. Combine provider idempotency keys, outcome reconciliation, or an explicit `ambiguous` or `needs_review` state.
- For outbound Hypertext Transfer Protocol (HTTP) steps, enforce Server-Side Request Forgery (SSRF) checks (block private and metadata Internet Protocol (IP) ranges) and avoid arbitrary `eval()` transforms. For long waits (for example, "wait 24 hours"), persist a `resume_at` timestamp and release the worker — never hold a thread or database transaction open.

## Case 2: Payments

**Core boundary:** A charge request to Stripe or Adyen times out — you do not know whether the customer's card was charged.

- Bind a client-supplied **idempotency key** to the normalized request payload and reject reuse with a different amount or currency.
- Separate **authorization, capture, void, refund, and reconciliation** cleanly; a saga coordinates local commits and compensating refunds rather than running distributed two-phase commit with an external payment service provider (PSP).
- Check storage math early: `1,000 tx/sec × 1 KB` = **~31.5 TB per year** raw before indexes and replicas, so retention and partitioning matter. Hosted checkout reduces Payment Card Industry (PCI) scope yet rarely eliminates all compliance obligations. See [Payment Gateway](../30-architecture/30.2-system-design/02-case-studies/30.2.2.06-payment-gateway.md).

## Case 3: Tenant isolation

**Core boundary:** Every query, background job, cache key, file bucket, and analytics export must stay strictly inside the authenticated tenant.

- Never rely solely on a `tenant_id` column remembered manually in every service method.
- If using PostgreSQL **Row-Level Security (RLS)**, verify four details: the runtime database role does **not** have `BYPASSRLS` or table-owner privileges, both `USING` (reads) and `WITH CHECK` (writes) policies exist, and tenant context is set **transaction-locally** (`SET LOCAL` or `set_config(..., true)`) so connection poolers cannot leak Tenant A's context onto Tenant B's next request.
- Copying operational tables into an analytics warehouse does not waive tenant authorization. See the [system design case library](../30-architecture/30.2-system-design/02-case-studies/INDEX.md).

## Case 4: Inventory and booking

**Core boundary:** Two customers click "Book" for the last seat simultaneously — or a payment webhook arrives one second *after* a 10-minute reservation hold expired.

- Separate fast, slightly stale availability search from authoritative inventory writes.
- Claim a hold atomically with an owner and expiry (`UPDATE slots SET held_by = $1 WHERE id = $2 AND status = 'open'`). A zero-row update means someone else won — never proceed to charge the card.
- When the payment webhook arrives, verify the hold still belongs to that order; if it expired and another user took the seat, trigger an explicit automatic refund or compensation path. See [Ticket Booking](../30-architecture/30.2-system-design/02-case-studies/30.2.2.08-ticket-booking.md).

## Case 5: Event processing

**Core boundary:** A consumer updates its database and crashes before committing its Kafka or broker offset, causing the broker to redeliver the same event.

- Pick the **partition and ordering key** first (for example, `order_id`): spreading events across different topics destroys ordering across an aggregate's lifecycle.
- Pair at-least-once broker delivery with **durable consumer deduplication** inside the same local transaction as the business write (a short 7-day Redis time to live (TTL) is not enough if replays span weeks).
- Define a concrete **poison-pill policy** (dead-letter queue (DLQ) plus alert) — blindly skipping one corrupt message can violate ordering for later updates on the same entity. See [Message Brokers](../20-backend/20.9-message-brokers/INDEX.md).

## Case 6: Caching

**Core boundary:** A stale read refills the cache *after* a write just invalidated it — or a hot key expires and 5,000 requests slam the database at once (cache stampede).

- Cache only data with an explicit staleness budget; prefix every key by `tenant_id` and still enforce authorization at the API boundary (never assume "schedules are non-sensitive" if they carry patient or customer metadata).
- Protect hot keys against stampedes with single-flight coalescing, jittered TTLs, or background refresh, and plan database load-shedding if Redis fails completely. See [Caching](../20-backend/20.8-caching/INDEX.md).

## Case 7: Analytics

**Core boundary:** Over-building a streaming stack when a daily Structured Query Language (SQL) job works — or accidentally leaking personal data inside "anonymous" event streams.

- Start from the required freshness and query shape: hourly or daily operational dashboards often run cleanly on read replicas or scheduled rollups without needing Kafka, Flink, and ClickHouse.
- Dropping a user's name does **not** automatically anonymize analytics rows — user IDs, exact timestamps, and rare combinations can still re-identify individuals. Enforce minimization, tenant filtering, and late-event deduplication. See [EU Regulatory Compliance](80.24-eu-regulatory-compliance.md).

## Case 8: Rate limiting

**Core boundary:** Enforcing both steady quotas and short bursts across multiple API servers without clock drift or race conditions.

- Key limits on a **trusted server identity** (authenticated user or tenant ID or verified API key, not spoofable `X-Forwarded-For` headers).
- Use atomic Redis scripts (Lua) for token-bucket or sliding-window checks; understand the difference from fixed windows (which allow 2× boundary bursts).
- Check the math: `100` tenants at `100` requests per minute equals `10,000` requests per minute (~167 requests per second steady) — a `10,000` requests per second burst needs separate admission control. If Redis goes down, decide consciously per endpoint: **fail open** with conservative per-instance local limits for normal traffic, or **fail closed** for hard billing or security caps. See [Caching & Redis](../20-backend/20.8-caching/INDEX.md).

## Case 9: Feature flags

**Core boundary:** Keeping tenant behavior consistent while still being able to kill a broken release fast.

- Hash by the right **bucketing unit** (`tenant_id` for business-to-business (B2B) organization features so coworkers do not see conflicting user interfaces (UIs), `user_id` for consumer A/B tests).
- Never use a feature flag as an authorization boundary — still check real permissions on the server.
- Be honest about kill-switch latency: a 60-second client or software development kit (SDK) cache cannot stop traffic instantaneously. Use streaming Server-Sent Events (SSE) flag push or local evaluation with explicit propagation bounds and safe offline defaults. See the [system design case library](../30-architecture/30.2-system-design/02-case-studies/INDEX.md).

## Case 10: Disaster recovery

**Core boundary:** Confusing a live read replica with a backup — an accidental `DROP TABLE` replicates to a replica in milliseconds!

- Define **Recovery Point Objective (RPO)** (maximum acceptable data loss, for example, 5 minutes) and **Recovery Time Objective (RTO)** (maximum acceptable downtime, for example, 30 minutes) from real business impact.
- Combine **automated backups and Write-Ahead Logging (WAL) archiving (Point-In-Time Recovery)** for human-error corruption with **multi-Availability Zone (Multi-AZ) and cross-region replicas** for hardware or region outages. ([RDS automated backups](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/USER_WorkingWithAutomatedBackups.html) · [RDS read replicas](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/USER_ReadRepl.html))
- Never promise a "30-minute restore of a 500 GB database" until you have timed a real restore drill including Domain Name System (DNS) cutover, secrets, and smoke checks.

## Case 11: Notifications

**Core boundary:** Recording send intent reliably without spamming duplicate emails or Short Message Service (SMS) alerts or leaking private text in inbox previews.

- Commit the business update and a durable notification intent row inside **one atomic database transaction** (outbox), then track each channel's attempts (`pending → accepted → delivered | failed`) separately.
- Remember that an email or SMS API returning `202 Accepted` proves provider intake, not handset delivery — and a crash right after `202` needs provider idempotency or reconciliation.
- Minimize sensitive content in emails and SMS alerts (link to an authenticated portal instead of putting medical or financial details directly in plain-text messages). See [Notification Service](../30-architecture/30.2-system-design/02-case-studies/30.2.2.07-notification-service.md).

## Case 12: Connection pooling

**Core boundary:** Scaling API replicas until PostgreSQL collapses under thousands of idle or contending connections.

- Apply Little's Law (`concurrency = arrival rate × hold time`): at `2,000` requests per second where each request holds a database connection for `0.1 s`, you need **~200 active connections** simultaneously. Twenty backend connections holding queries for `0.1 s` max out at **~200 requests per second** — a connection pool multiplexes idle connections cleanly, yet it does **not** magically multiply database query throughput.
- Sum pool sizes across *all* API and worker replicas, keep transactions short (never hold a database transaction open across external HTTP calls), and verify transaction-pooling compatibility (prepared statements, `SET` session variables, advisory locks) in [PgBouncer's feature matrix](https://www.pgbouncer.org/features.html).

## Summary

Treat these twelve cases as reusable failure-boundary lenses: name the invariant, trace what breaks during a crash, race, or network split, and pair the right local database guarantee with explicit remote reconciliation or load shedding.

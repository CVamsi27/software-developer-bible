# System Design Case Bank — 5 EU Cases to Practice

> **5 cases hand-picked for EU mid-stage interviews.** Each one has the framework, sample answer, and the 2-3 trade-offs the company will want to discuss. Practice each one with a 45-min timer + recording.

## TL;DR

- **5 cases:** workflow engine, payment gateway, multi-tenant SaaS, real-time booking, event-driven microservices
- **Each:** framework + sample answer + trade-off discussion + what gets you rejected
- **Practice order:** start with URL shortener (universal), then your target company's most-likely case
- **For 17 more cases (canonical set):** see [../../3-Architecture-Stack/11-System-Design/](../30-architecture/30.2-system-design/INDEX.md)

The bible's [Architecture Stack](../30-architecture/INDEX.md) has the full case library. This file is the **5 must-practice for this lane** subset.

## The 4-Phase Framework (use every time)

Before diving into cases, internalize the framework:

1. **Clarify (5 min):** Ask 3-5 questions. Functional scope, scale, in/out, non-functional.
2. **Estimate (2 min):** QPS, storage, bandwidth (rough).
3. **High-level (10 min):** Boxes and arrows. Client → CDN → API → Service → DB.
4. **Deep-dive (20 min):** Pick 2-3 critical components. Schema, indexes, queue, cache, consistency.

Don't start drawing before Phase 1. Don't go wide before Phase 3. Don't skip trade-offs in Phase 4.

## Case 1: Workflow Engine (n8n, sennder, Hostaway, GoGlobal)

**The most common case at EU mid-stage.** Building a node-based workflow execution platform.

### Clarifying questions to ask

- What kind of triggers? HTTP only or also scheduled, webhook, email?
- What step types? HTTP request, transform, conditional, parallel?
- Retries on failure? DLQ?
- Concurrency limits? Can multiple executions of the same workflow run in parallel?
- How long should execution history be kept?
- Multi-tenancy? Each user/team has their own workflows?

### Estimates

- 100K executions/day at scale
- 1KB per execution record (state + metadata)
- 100MB/day storage
- Peak: 100 executions/sec, p99 500

### High-level design

```
[HTTP trigger] → [API gateway] → [Workflow Service] → [Queue (Kafka/SQS)]
                                                       ↓
                                              [Worker pool] → [Step executor]
                                                       ↓
                                              [State DB] (Postgres)
                                                       ↓
                                       [Webhook on completion]
```

**Critical components:**
1. **Queue** for executions (decouples trigger from execution, retries, scaling)
2. **Worker pool** that picks up executions and runs steps
3. **State DB** for execution history (Postgres with `executions` and `step_executions` tables)
4. **Webhook service** for completion notifications

### Deep-dive (pick 2-3)

**Database schema:**
```sql
CREATE TABLE workflows (
  id UUID PRIMARY KEY,
  tenant_id UUID NOT NULL,
  name TEXT,
  trigger JSONB,         -- HTTP path, schedule, etc.
  steps JSONB,           -- array of step definitions
  created_at TIMESTAMPTZ
);

CREATE TABLE executions (
  id UUID PRIMARY KEY,
  workflow_id UUID REFERENCES workflows(id),
  tenant_id UUID NOT NULL,
  status TEXT,           -- queued / running / completed / failed / retry
  started_at TIMESTAMPTZ,
  completed_at TIMESTAMPTZ,
  trigger_payload JSONB,
  result JSONB
);

CREATE TABLE step_executions (
  id UUID PRIMARY KEY,
  execution_id UUID REFERENCES executions(id),
  step_index INT,
  step_type TEXT,
  status TEXT,
  started_at TIMESTAMPTZ,
  completed_at TIMESTAMPTZ,
  input JSONB,
  output JSONB,
  error TEXT
);

CREATE INDEX idx_executions_workflow ON executions(workflow_id, started_at DESC);
CREATE INDEX idx_executions_tenant ON executions(tenant_id, started_at DESC);
CREATE INDEX idx_step_executions_execution ON step_executions(execution_id, step_index);
```

**Trade-offs to discuss:**
- **At-least-once vs exactly-once execution:** at-least-once is simpler but requires idempotency. Exactly-once is hard and usually means "effectively once" via dedup.
- **Synchronous vs async trigger:** sync gives immediate feedback but blocks on the first step. Async is more flexible but adds latency.
- **Persistent state vs in-memory:** persistent state survives worker crashes but adds DB load. In-memory is faster but loses state on crash.
- **Per-workflow vs global queue:** per-workflow guarantees ordering but limits throughput. Global queue scales better but loses ordering.
- **Concurrency limits:** limit parallel executions per workflow (fairness) vs unlimited (throughput).

### What gets you rejected

- "I'll just use a queue" without specifying Kafka, SQS, BullMQ, etc.
- No mention of state recovery on worker crash
- No idempotency strategy
- "How do you handle a step that takes 24 hours?" — long-running steps need special handling (checkpoints, resume)
- "What if the same workflow is triggered twice in 1 second?" — idempotency, rate limiting

## Case 2: Payment Gateway (SumUp, Scalable Capital, any fintech)

### Clarifying questions to ask

- Online + in-person? Multi-currency? Fraud detection? Idempotency?
- What PSP? Stripe, Adyen, internal? Or are we the PSP?
- Refunds, chargebacks, disputes? Full lifecycle or just authorize + capture?
- Webhook reliability?

### Estimates

- 1K TPS at scale
- 1KB per transaction record
- 30GB/year storage
- p99 latency target: 200ms (card-not-present), 2s (card-present)

### High-level design

```
[Client] → [API] → [Payment Service] → [PSP (Stripe/Adyen)]
                       ↓
                  [Ledger DB] (Postgres)
                       ↓
                  [Webhook handler] ← PSP webhook
                       ↓
                  [Reconciliation service] (daily batch)
```

### Deep-dive

**Idempotency:** every API request has an `Idempotency-Key` header. Server stores the key + result for 24h. Duplicate requests return the same result. This is the single most important thing in payments.

**Two-phase write (Saga):**
1. Hold funds (pre-auth) → write to ledger
2. Confirm with PSP → update ledger
3. If step 2 fails, refund step 1 (compensating action)

**Reconciliation:** daily batch compares internal ledger with PSP records. Discrepancies alert on-call.

**PCI compliance:** never store card numbers. Tokenize via PSP. Use their hosted fields or SDK.

**Fraud:** rule engine (velocity, amount, geo) in request path, ML model async.

### Trade-offs

- **Strong consistency vs eventual:** payments need strong consistency for the ledger. Use Postgres + transactions.
- **Synchronous PSP call vs async:** sync gives immediate feedback (good UX) but blocks the user. Async is faster but requires webhook handling.
- **Pre-auth vs post-auth flow:** pre-auth (hold funds) is safer for high-risk. Post-auth (charge immediately) is faster but harder to reverse.

### What gets you rejected

- No idempotency story
- "I'll use a queue" without saying how you handle webhook ordering
- No mention of reconciliation
- "What if the PSP is down for 4 hours?" — circuit breaker, retry, queue, eventually reconcile
- No PCI compliance mention

## Case 3: Multi-Tenant SaaS (Hostaway, Scalable, Docita-style)

### Clarifying questions

- How many tenants? 100? 100K? 1M?
- Data isolation: shared DB with tenant_id, schema-per-tenant, DB-per-tenant?
- Per-tenant customization (themes, workflows, custom fields)?
- Cross-tenant analytics?
- Tenant onboarding flow?

### Estimates

- 1K tenants, 100 users each, 10M records total
- 1KB per record, 10GB total
- p99 query latency: 100ms

### High-level

```
[Client] → [Auth] (extract tenant from JWT)
                ↓
            [API Gateway] (tenant context)
                ↓
            [Service] (all queries filter by tenant_id)
                ↓
            [Postgres with RLS]
                ↓
            [Analytics DB] (no tenant filter, separate)
```

### Deep-dive

**Row-level security (RLS):**
```sql
ALTER TABLE records ENABLE ROW LEVEL SECURITY;
CREATE POLICY tenant_isolation ON records
  USING (tenant_id = current_setting('app.tenant_id')::UUID);
```

Every query automatically filters by `tenant_id` from the session variable. Application sets it on connect.

**Tenant isolation trade-offs:**
- **Shared DB + tenant_id:** cheapest, but loud neighbor risk, hard to scale
- **Schema-per-tenant:** better isolation, more overhead, harder migrations
- **DB-per-tenant:** strongest isolation, most expensive, hardest ops

**RBAC:** roles per tenant, audit logging. Roles are tenant-scoped, not global.

**Migrations:** backwards-compatible. Never drop a column in the same release that adds the replacement. Use expand-contract pattern.

### Trade-offs

- **Customization via config vs code:** config is faster, code is more flexible. Use config for fields/themes, code for workflows.
- **Cross-tenant analytics:** separate analytics DB (ClickHouse, BigQuery) without tenant_id filter, fed via CDC from operational DB.
- **Per-tenant rate limiting:** Redis-based, key by tenant_id, returns 429 with retry-after.

### What gets you rejected

- "I'll add tenant_id to every query" without RLS or middleware
- No mention of loud neighbor
- "What if tenant A sees tenant B's data?" — silent failure is the worst
- No migration strategy
- "What if a tenant has 100x more data than average?" — partitioning by tenant_id

## Case 4: Real-Time Booking (Peter Park, Booking.com, GetYourGuide)

### Clarifying questions

- Single resource (one slot) or multi-resource (many slots)?
- Hold timeout (10 min during payment)?
- Payment integration?
- Cancellation flow?
- Multi-region, multi-currency?

### Estimates

- 10K searches/sec, 100 bookings/sec peak
- 1M bookings/day
- 1KB per booking, 1GB/day
- p99 search: 50ms, p99 booking: 500ms

### High-level

```
[Client] → [Search Service] (Elasticsearch) → [Results]
                ↓
[Client] → [Booking Service] (Postgres + row-level locks)
                ↓
            [Payment Service] (PSP)
                ↓
            [Confirmation]
                ↓
            [Webhook + Email]
```

### Deep-dive

**Concurrency: "two users grab the last seat"**

Option 1: **Pessimistic locking**
```sql
BEGIN;
SELECT * FROM slots WHERE id = ? FOR UPDATE;
-- check if available
UPDATE slots SET status = 'held' WHERE id = ? AND status = 'available';
COMMIT;
```

Option 2: **Optimistic locking with version**
```sql
UPDATE slots SET status = 'held', version = version + 1
WHERE id = ? AND version = ? AND status = 'available';
-- if 0 rows affected, retry
```

**Hold/release pattern:**
1. Booking creates a "hold" with 10-min TTL
2. Background job releases expired holds every minute
3. Payment confirms hold → status = "booked"
4. If payment fails, hold expires → released

**Idempotency:** booking ID is the idempotency key. Same booking ID won't double-book.

**Saga for hold → charge → confirm:**
- Hold slot (compensating: release)
- Charge payment (compensating: refund)
- Confirm booking (compensating: cancel + refund)
- Send confirmation (no compensation needed)

### Trade-offs

- **Pessimistic vs optimistic locking:** pessimistic is simpler but blocks. Optimistic is more scalable but requires retry.
- **Hold vs immediate charge:** hold is safer but more complex. Immediate charge is simpler but harder to undo.
- **Single-region vs multi-region:** single-region is simpler, multi-region needs geo-routing and conflict resolution.

### What gets you rejected

- No concurrency strategy
- "I'll use a transaction" without specifying the lock type
- "What if the user closes the browser during payment?" — hold + TTL
- "What if payment succeeds but confirmation fails?" — outbox pattern, retry

## Case 5: Event-Driven Microservices (sennder, THRYVE, any data platform)

### Clarifying questions

- What events? Throughput? Ordering requirements? Schema evolution?
- At-least-once vs exactly-once?
- How long to retain events?
- Cross-region?

### Estimates

- 10K events/sec, 1KB per event, 1TB/day
- 7-day retention typical
- 3-5 consumer services

### High-level

```
[Producer services]
    ↓
[Kafka topic per event type]
    ↓
[Consumer services] (multiple, partitioned by aggregate ID)
    ↓
[Storage / Downstream services]
```

### Deep-dive

**Topic design:** one topic per domain event type (`order.created`, `order.updated`, `order.cancelled`). Not one topic for "orders".

**Schema evolution:** Avro or Protobuf with schema registry (Confluent, Apicurio). Backwards-compatibility:
- Add optional field with default
- Never remove required field
- Never change field type

**Ordering:** partition by aggregate ID (e.g., `customer_id`). All events for one customer go to one partition, processed by one consumer, in order. Different customers can be in parallel.

**Idempotency:** consumer-side dedup by event ID. Store processed event IDs in Redis (TTL 7 days) or DB.

**DLQ (dead letter queue):** poison message handling. After 5 retries, send to DLQ for manual investigation.

**Replay:** keep topics for 7 days, support re-processing. Useful for bug fixes and new consumer onboarding.

### Trade-offs

- **Kafka vs RabbitMQ vs SQS:** Kafka for high throughput + replay, RabbitMQ for complex routing, SQS for managed simplicity.
- **At-least-once vs exactly-once:** at-least-once is the default. Exactly-once is hard and usually means "effectively once" via idempotency + dedup.
- **Push vs pull consumers:** push is lower latency, pull gives more control over throughput. Kafka uses pull.

### What gets you rejected

- "I'll use Kafka" without mentioning partitioning, retention, schema registry
- No idempotency strategy on the consumer side
- "What if the consumer crashes mid-processing?" — offset commit after processing, or use a transactional outbox
- No DLQ story
- "What if event ordering matters?" — partitioning by aggregate ID

## Case 6: Distributed Caching Layer (Healthcare SaaS)

### Clarifying questions to ask
- What data needs caching? (schedules, patient records, config)
- Multi-tenant? Each clinic has its own cache keys?
- What happens when cache is stale? (patient safety implications)
- What's the hit rate target? (95%+ for schedules, 0% for patient data)
- What's the cache invalidation strategy?

### Estimates
- 100K cache reads/day, 10K writes/day
- 1KB per cached value, 100MB total cache
- p95 cache read latency: 1ms (Redis), 50ms (PostgreSQL fallback)

### High-level design
```
[API] → [Cache Service] → [Redis Cluster]
                ↓ (miss)
            [PostgreSQL]
                ↓ (write)
         [Cache Invalidation]
```

### Deep-dive
**Cache strategy:** Cache-aside for schedule data (30s TTL), no-cache for patient data (PHI sensitivity). Key format: `cache:{clinicId}:schedule:{practitionerId}`. Invalidation: event-driven (outbox event triggers cache invalidation for schedule changes), TTL-based for config (5min).

**Multi-tenant:** Keys scoped by clinic_id. Invalidation is per-clinic. One clinic's cache flush doesn't affect others.

**Failure modes:** Redis down → fall through to PostgreSQL (slower but correct). Cache stampede → use single-flight (one request repopulates, others wait). Stale data → short TTL (30s) + event-driven invalidation.

**Monitoring:** Cache hit rate (>95% target), eviction rate, memory usage, Redis connection count.

### What gets you rejected
- Caching patient records (PHI sensitivity, freshness requirement)
- No fallback to PostgreSQL when cache misses
- Cache keys not scoped by clinic_id (cross-tenant data leak)
- No invalidation strategy (stale data forever)

## Case 7: Real-Time Analytics Pipeline (Clinic Operations)

### Clarifying questions to ask
- What metrics? (appointments/hour, no-show rate, revenue)
- Real-time or batch? (both: real-time dashboard + daily reports)
- How many clinics? (100+)
- Data retention? (90 days detailed, 1 year aggregated)
- PHI in analytics? (aggregated only, no patient names)

### Estimates
- 100K events/day (appointments, billing, notifications)
- 1KB per event, 100MB/day
- Real-time: update dashboard every 30 seconds
- Batch: daily reports at 6am

### High-level design
```
[API/Worker] → [Kafka Topic] → [Flink] → [ClickHouse] → [Grafana]
                                        ↓
                               [Daily Report Worker]
```

### Deep-dive
**Event design:** Each business action emits an event: `{ type: 'appointment_booked', clinicId, practitionerId, timestamp, duration }`. PHI: patient name is NOT included — only aggregated identifiers.

**Real-time path:** Kafka → Flink (windowed aggregation: appointments per clinic per hour) → ClickHouse (OLAP store) → Grafana dashboard (auto-refresh every 30s).

**Batch path:** ClickHouse → daily SQL query → PDF report → email to clinic admin.

**PHI handling:** Events contain clinic_id and practitioner_id but NOT patient_id or patient name. Analytics are clinic-scoped aggregates. Individual patient data is never in the analytics pipeline.

### What gets you rejected
- Patient names in analytics events (PHI violation)
- No real-time path (clinicians need live dashboards)
- No batch path (daily reports are a business requirement)
- ClickHouse for OLTP (it's OLAP — use PostgreSQL for transactions)

## Case 8: Global Rate Limiting System

### Clarifying questions to ask
- Per-tenant or per-user rate limiting?
- What's the rate limit? (100 req/min per clinic)
- What happens when limit is exceeded? (429 with Retry-After)
- Multiple API instances? (yes, 2-10)
- Redis available? (yes)

### Estimates
- 10K requests/second peak
- 100 clinics × 100 req/min = 100K req/min = 1.7K req/s
- Redis latency: 1ms per operation

### High-level design
```
[API Instance 1] → [Redis] ← [API Instance 2]
                      ↓
              [Rate Limit Check]
                      ↓
              [Allow / Reject (429)]
```

### Deep-dive
**Algorithm:** Token bucket per clinic. Redis key: `ratelimit:{clinicId}:{window}`. Lua script for atomic check-and-decrement. Headers: `X-RateLimit-Limit`, `X-RateLimit-Remaining`, `X-RateLimit-Reset`, `Retry-After`.

**Multi-instance:** All instances share the same Redis counter. Atomic operations via Lua script prevent race conditions. Trade-off: Redis latency adds ~1ms per request.

**Failure modes:** Redis down → local rate limiting (less accurate but functional). Use in-memory fallback with per-instance limits. Redis recovery → sync counters.

**Per-tenant:** Higher limits for premium clinics. Configuration stored in database, cached in Redis.

### What gets you rejected
- Per-IP rate limiting for a multi-tenant SaaS (use clinic_id)
- No Redis fallback when Redis is down
- No Retry-After header (clients can't know when to retry)
- Fixed window (causes burst at window boundaries — use token bucket)

## Case 9: Feature Flag System

### Clarifying questions to ask
- What types of flags? (boolean, percentage, user segment)
- How many flags? (10-50 active)
- Evaluation latency target? (<10ms)
- Kill switch requirement? (instant disable)
- Multi-tenant? (per-clinic rollouts)

### Estimates
- 10K evaluations/second
- 1KB per flag definition
- 100 flags × 1KB = 100KB total

### High-level design
```
[App] → [Flag SDK] → [Redis Cache] ← [Admin API] → [PostgreSQL]
```

### Deep-dive
**Flag definition:** `{ name: 'new-booking-flow', type: 'percentage', percentage: 10, segment: 'beta-clinics', default: false }`. Stored in PostgreSQL, cached in Redis.

**Evaluation:** Hash(user_id + flag_name) for consistent bucketing. If hash % 100 < percentage, flag is enabled. Cache evaluation result for 60 seconds.

**Kill switch:** Admin API sets flag to `enabled: false`. Redis cache is invalidated immediately. All evaluations return false within 60 seconds (cache TTL).

**Multi-tenant:** Flags can target specific clinics: `{ segment: 'clinic:{clinicId}' }`. Percentage rollouts are per-clinic, not global.

### What gets you rejected
- No kill switch (must be able to disable instantly)
- Evaluation in database (too slow — cache in Redis)
- No consistent bucketing (user sees flag flip between requests)
- No multi-tenant targeting (rollouts should be per-clinic)

## Case 10: Disaster Recovery System (RPO < 1 Hour)

### Clarifying questions to ask
- Current infrastructure? (AWS RDS, single region)
- RPO target? (<1 hour)
- RTO target? (<1 hour)
- Data sensitivity? (healthcare — zero data loss preferred)
- Budget? (moderate — not unlimited)

### Estimates
- Database size: 500GB
- WAL generation: 1GB/hour
- Backup window: continuous (WAL archival)
- Restore time: ~30 minutes (500GB restore + WAL replay)

### High-level design
```
[Primary RDS] → [WAL Archival to S3] → [Cross-Region Replica]
       ↓                                       ↓
[Read Replica]                          [DR Region Primary]
```

### Deep-dive
**Backup strategy:** RDS automated snapshots (daily, 35-day retention) + WAL archival to S3 (every minute, 7-day retention) + cross-region read replica (async replication).

**Recovery process:** (1) detect failure (health check), (2) promote cross-region replica to primary, (3) update DNS (Route 53 failover), (4) verify application connectivity, (5) notify stakeholders. RPO: 1 minute (WAL archival interval). RTO: 30 minutes (promotion + DNS + verification).

**Testing:** Quarterly DR drills. Restore to a separate environment, verify data integrity, measure actual RTO.

**Trade-offs:** Async replication = possible data loss (up to 1 minute of WAL). Sync replication = zero data loss but higher write latency. For healthcare: async is acceptable if RPO < 5 minutes.

### What gets you rejected
- No WAL archival (RPO depends on snapshot frequency — could be 24 hours)
- No cross-region replica (single region = no DR)
- No testing (DR plan that's never tested is a hope, not a plan)
- No DNS failover (manual DNS change = 30+ minutes of downtime)

## Case 11: Notification System (Multi-Channel)

### Clarifying questions to ask
- Channels? (in-app, email, SMS, push)
- Volume? (10K notifications/day)
- Retry policy? (exponential backoff, max 3)
- User preferences? (opt-out per channel)
- PHI in notifications? (patient names in emails, not in logs)

### Estimates
- 10K notifications/day, 1K/hour peak
- 1KB per notification
- Email delivery: 2-5 seconds
- SMS delivery: 5-10 seconds
- In-app: <100ms (WebSocket)

### High-level design
```
[Business Event] → [Outbox] → [Worker] → [Channel Router]
                                            ↓
                          [In-App (WebSocket)] [Email (SendGrid)] [SMS (Twilio)]
```

### Deep-dive
**Outbox pattern:** Business action writes outbox event in same transaction. Worker picks up event, determines channels based on user preferences, delivers via each channel independently.

**Channel-specific:** In-app: insert into notifications table + WebSocket push. Email: SendGrid API with retry. SMS: Twilio API with retry. Each channel has independent retry and DLQ.

**User preferences:** Per-user, per-channel. In-app always ON (clinical safety). Email/SMS opt-out per user. Preferences stored in database, cached in Redis.

**PHI handling:** Patient name is in the email body (necessary for clinical communication) but NOT in logs, metrics, or trace spans. Sentry scrubber removes patient names from error reports.

### What gets you rejected
- No outbox pattern (direct provider calls = lost notifications on failure)
- No user preferences (can't opt out of SMS = compliance risk)
- PHI in logs or metrics (healthcare violation)
- No DLQ (poison messages block the queue)

## Case 12: Connection Pooling System (PostgreSQL)

### Clarifying questions to ask
- Current connection count? (50 at 10 clinics, 200 at 100 clinics)
- Max PostgreSQL connections? (200)
- Transaction duration? (50-200ms average)
- PgBouncer available? (yes)
- Pool mode? (transaction — best for Prisma)

### Estimates
- 100 clinics × 10 users × 2 req/s = 2000 req/s
- Each request holds a connection for 100ms
- Connections needed: 2000 × 0.1 = 200 (at max_connections limit)
- With PgBouncer: 20 backend connections handle 2000 req/s

### High-level design
```
[API Instances] → [PgBouncer] → [PostgreSQL]
                    ↓
            [Connection Pool]
            [20 backend connections]
            [2000 app connections]
```

### Deep-dive
**Pool configuration:** Transaction mode (connections released after each transaction). Pool size: 20 (for a 4-core PostgreSQL server). Server idle timeout: 300s. Client idle timeout: 600s.

**Monitoring:** PgBouncer stats: active connections, waiting clients, query wait time. PostgreSQL: pg_stat_activity (active, idle, idle in transaction). Alert: waiting clients > 10, idle in transaction > 5 minutes.

**Failure modes:** Pool exhaustion → queue requests (latency increases). Connection leak → PgBouncer kills idle connections. PostgreSQL crash → PgBouncer reconnects automatically.

**Scaling:** At 500 clinics: multiple PgBouncer instances behind a load balancer, or PgBouncer per API instance. At 1000 clinics: connection pooling per cell (cell-based architecture).

### What gets you rejected
- Session mode (holds connections too long — use transaction mode)
- No monitoring (can't see pool exhaustion until it's too late)
- No idle connection cleanup (leaked connections accumulate)
- Pool size = max_connections (wastes memory — use 10-20% of max)

## How to practice these 12 cases

1. **Start with cases 1-5** (existing) — these are the most common at EU mid-stage.
2. **Then practice cases 6-12** (new) — these are Google-level depth.
3. **For each case:** Set a 45-min timer, use the 4-phase framework, record yourself.
4. **Review:** Did you ask clarifying questions? Give estimates? Discuss trade-offs? Address failure modes?
5. **Total practice:** 12 cases × 4 reps × 45 min = 36 hours over 3-4 weeks.

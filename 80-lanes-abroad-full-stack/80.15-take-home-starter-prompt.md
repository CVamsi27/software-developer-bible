# Workflow Portfolio Starter

[![Role priority](https://img.shields.io/badge/role--priority-Important-blue)](../docs/topic-importance.md)
[![General importance](https://img.shields.io/badge/general--importance-Important-blue)](../docs/topic-importance.md)



Build one workflow that a reviewer can run and inspect. This is a practice brief; an employer's assignment, time limit, and AI policy take precedence. A runnable slice demonstrates a decision. A long feature list does not demonstrate that those features work.

## First Principles

A workflow can stop between recording state and performing a side effect. A bounded exercise must therefore make those transitions visible and define what happens on retry. Adding infrastructure before demonstrating that contract increases the work without establishing correctness.

## Start with one run

A seeded workflow receives a small JSON input, assigns a value, and produces a result. The interface starts the run and shows its final status. Use the stack you can explain and maintain; choose and pin compatible versions during setup rather than mixing a named old release with an unqualified `latest` command.

```text
validated input → immutable workflow snapshot → ordered steps → persisted result
                                      ↘ failed step → explicit failed status
```

Keep the first version local and single-user. Do not expose it publicly with ownership fields that are never authorized. Use a deterministic fixture executor instead of fetching arbitrary user-supplied URLs. An HTTP executor introduces destination validation, redirects, timeouts, response-size limits, and protection against server-side request forgery (SSRF), where a submitted URL reaches an internal or forbidden destination that deserve a separate design.

## A bounded brief for an assistant

> Help me build a local workflow demo with one seeded workflow, two deterministic step types, a run endpoint, and one inspection screen. Before editing, show the proposed slice and the assumptions that affect correctness. Keep inputs, step counts, and stored outputs bounded. Persist an immutable workflow snapshot for each run. Stop and explain failures rather than inventing successful checks. Add tests for the observable contracts below, document the actual setup, and record unfinished work. Follow the assignment's AI policy when this is used for an interview.

Keep ownership of the design: ask the assistant to explain why a run can fail, then check that explanation against the implementation. Disclose assistance as required by the assignment; a prompt history is useful context, not proof of independent competence.

## Three stages within a four-hour practice budget

| Stage | Example budget | Deliverable |
| -------------------------- | -------------: | ---------------------------------------------------- |
| Build the vertical slice | 2 hours | Start one run and inspect its persisted outcome |
| Exercise failure contracts | 1 hour | Repeated requests, invalid input, and a failing step |
| Prepare the handoff | 1 hour | Reproducible setup, seeded example, limitations |

These are planning allocations, not a promised completion time. If setup consumes the budget, reduce the slice and report the actual result. Do not describe an eleven-hour schedule as a six-hour build.

## Add reliability only when its contract is clear

| Feature | Contract to demonstrate |
| ----------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| Idempotent run creation | Atomically claim a scoped key; the same payload returns the same run, while changed payloads conflict |
| Retry | Retry only classified transient failures; three total attempts means at most two retry delays |
| Workflow editing | An existing run continues against its saved version |
| Concurrent workers | A durable claim prevents duplicate active ownership; recovery handles worker loss |
| External side effect | A crash after remote acceptance leaves an uncertain outcome unless the provider supports reconciliation or idempotency |

Do not hold a database transaction and row lock across network calls. A lock alone does not make a remote side effect exactly once. Avoid adding background workers until the claim and recovery behavior can be explained and tested.

## Handoff with evidence

Give the reviewer one setup path and one sample run. Test that path in a clean environment and state what you actually checked. Include configuration placeholders, prerequisites, failure behavior, and the most consequential tradeoff. Remove secrets and sensitive payloads from logs and fixtures.

There is no universal minimum test count, commit count, or two-minute startup guarantee. Choose checks that can falsify the contracts you claim. Keep known limitations visible rather than deleting TODOs to imply completion.

## Describe only the finished artifact

After building, record the actual repository, capabilities, elapsed effort if relevant, and verification results in the [private portfolio records](personal/README.md). A planned feature cannot become a résumé claim. Do not publish a private repository's link as if access were already available; arrange access when requested.

## Summary

Start with one inspectable run. Add a reliability feature only after defining its failure contract. The handoff should let another person reproduce the claimed behavior and see the limits.

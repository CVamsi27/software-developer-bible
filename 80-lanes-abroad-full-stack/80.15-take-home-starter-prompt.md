# Workflow Portfolio Starter

[![Role priority](https://img.shields.io/badge/role--priority-Important-blue)](../docs/topic-importance.md)
[![General importance](https://img.shields.io/badge/general--importance-Important-blue)](../docs/topic-importance.md)

The best way to prepare for practical startup take-homes and architecture interviews is to build **one small, clean, runnable workflow slice** under a 4-hour timebox — then deliberately break it and test how it recovers. This is a practice brief (always follow a real employer's brief, time limit, and artificial intelligence (AI) policy during an actual assessment).

## First Principles

Workflow systems fail in the gap between saving local state and running an external step. A small, deterministic slice that makes state transitions, validation, and retries completely inspectable teaches (and proves) far more than a sprawling half-working clone with ten unverified services.

## 1. Start With One Clean, Local Vertical Slice

Build one seeded workflow that accepts a small validated JavaScript Object Notation (JSON) input, executes two deterministic local step types (for example, `transform` plus `validate` and `branch`), persists an **immutable snapshot** of the workflow definition for that run, and displays the run's step-by-step outcome in a simple inspection screen:

```text
Validated JSON input ─► Immutable definition snapshot ─► Ordered steps ─► Persisted COMPLETED result
                                                              └─ step throws ─► Explicit FAILED status + error
```

**Why keep v1 local and deterministic (no arbitrary outbound URLs yet)?**
Accepting arbitrary user Uniform Resource Locators (URLs) to fetch immediately pulls in **Server-Side Request Forgery (SSRF)** defense (blocking private and metadata Internet Protocol (IP) ranges, validating redirects, and enforcing response-size caps and timeouts). Master the core state-machine contract locally first, then add outbound Hypertext Transfer Protocol (HTTP) calls only when you can implement and test that security boundary properly.

## 2. Reusable 4-Hour Practice Budget

| Stage | Time | Deliverable |
| ---------------------------------- | ------: | ------------------------------------------------------------------------------------------ |
| **1. Core vertical slice** | 2 hours | Pinned setup, seeded workflow, `POST /runs` endpoint, persisted status and inspection view |
| **2. Failure contracts and tests** | 1 hour | Invalid payload (`400`), duplicate idempotency key, failing step recovery test |
| **3. Clean-checkout handoff** | 1 hour | Fresh-clone test, `.env.example`, concise `README.md` listing trade-offs and limits |

If you pair with an AI assistant while practicing, give it a tight scope: ask it to propose the slice and assumptions first, keep inputs and steps bounded, write tests that can genuinely fail on contract violations, and never invent passing checks. Always verify every line yourself — you must be able to explain and modify the code live.

## 3. Add Reliability Features One Contract at a Time

Only add a reliability feature once you can test its exact failure boundary:

| Feature | Exact contract to prove |
| --------------------------- | --------------------------------------------------------------------------------------------------------------------------------------- |
| **Idempotent run creation** | Atomically claim a scoped key: same key plus same payload returns original run; same key plus different payload returns `409 Conflict` |
| **Transient step retries** | Retry only transient errors; `maxAttempts = 3` means at most **2 retry delays** |
| **Safe definition edits** | Editing a workflow saves a new version; existing in-flight runs finish against their original snapshot |
| **Concurrent workers** | Atomic durable claim with lease expiry; stale workers resuming after expiry are rejected by version check |
| **External side effects** | Never hold a database transaction open across an HTTP call; document that remote crashes require provider idempotency or reconciliation |

## 4. Handoff and Honest Portfolio Hygiene

Rehearse setup in a fresh directory before calling the practice done. Record what works, any known limits, and exact test commands in `README.md`. Only describe features you built and tested on your resume — never claim planned roadmap items as shipped production systems.

## Summary

Build one small, deterministic workflow slice inside a 4-hour practice box first, prove its input validation, state transitions, and failure contracts with real tests, add worker and HTTP boundaries only when you can enforce their security and concurrency rules, and verify the handoff from a clean checkout.

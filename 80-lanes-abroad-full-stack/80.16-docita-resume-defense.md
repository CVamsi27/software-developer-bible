# Prepare a Defensible Docita Walkthrough

[![Role priority](https://img.shields.io/badge/role--priority-Important-blue)](../docs/topic-importance.md)
[![General importance](https://img.shields.io/badge/general--importance-Important-blue)](../docs/topic-importance.md)

The fastest way to lose credibility in a senior project deep dive is reciting a long laundry list of tools (*"NestJS, Prisma, PostgreSQL, Redis, RLS"*) and stumbling on the very first follow-up (*"Wait — how do you stop Tenant A's pooled connection from leaking into Tenant B's query?"*). Instead of pitching the whole platform at once, pick **one end-to-end user workflow** and separate clearly what exists in code, what is enabled in production, and what you actually observed. Keep personal metrics and private draft answers strictly in your private workspace.

## First Principles

One user click touches validation, authorization, database constraints, and background workers — yet having a library in `package.json` never guarantees the whole chain protects your invariant. Tracing one concrete state transition end-to-end forces you to name the exact mechanism enforcing correctness and the exact failures it still leaves open.

## 1. Trace One Real Workflow End to End

Pick one high-value operation (like booking a clinic appointment) and walk the interviewer along the arrows:

```text
User click ─► Input validation ─► Tenant & resource authZ
                ─► Capacity / business invariant ─► DB commit ─► Async notification / outbox
```

At each arrow, be ready to name the enforcing code/constraint, the failure status returned, and how you tested it. Two sharp distinctions to keep clear:
- **UI guards != backend safety:** Disabling the submit button improves UX; it never enforces booking capacity against concurrent requests.
- **Idempotency != concurrency control:** An idempotency key handles *one user retrying the same request*; a database lock or constraint handles *two different users competing for the same slot*.

## 2. Keep Four Levels of Proof Strictly Separate

| What you want to say | Proof required | What it does **not** prove |
| ----------------------------------- | ---------------------------------------------- | --------------------------------------------- |
| **"We implemented control X"** | Current source file + focused test | That every single code path actually calls it |
| **"Control X runs in production"** | Live deployment config & active runtime role | That it survives every failure mode |
| **"Behavior X works under stress"** | Executed test/command with environment & date | Every unseen production traffic spike |
| **"It improved business metric Y"** | Approved measurement with period & denominator | That one change alone caused the whole gain |

Always re-check current manifests, schema files, and live deployments before quoting counts or versions — older markdown notes are navigation leads (`packages/db/prisma/schema.prisma`, `packages/authorization/src/policies/`, `apps/api/src/shared/common/interceptors/tenant-context.interceptor.ts`, `packages/db/scripts/safe-migrate.sh`), not live audits.

## 3. Bring 2–3 Deep Proof Packets Instead of 20 Shallow Slides

Pick the two or three boundaries most relevant to the role you are interviewing for:

| Boundary | Exact mechanics to walk through | Classic failure to explain |
| ------------------------------ | ------------------------------------------------------------------------- | --------------------------------------------------------------------------------------- |
| **Tenant isolation** | Auth context → resource policy → transaction-local DB scope (`SET LOCAL`) | Connection pooler leaking prior request's session variable; privileged `BYPASSRLS` role |
| **Booking correctness** | Contested clinician/room capacity constraint + transaction isolation | Locking the *patient* instead of the *clinician slot* lets two patients double-book |
| **Durable background work** | Atomic business commit + outbox row → worker claim → retry/DLQ | Worker crashes *after* SMS/email provider accepts, *before* DB records success |
| **Sensitive data & telemetry** | Field redaction, audit access scope, safe exports | Identifiers or aggregates in logs/traces still revealing patient identity |
| **Safe delivery** | CI gates, expand-contract migrations, rollback path | Zero-downtime claims broken by exclusive table locks or old/new code version skew |

## 4. Keep Proposed Scaling Separate From Shipped Reality

When an interviewer asks *"How would you scale this 10×?"*, clearly label proposals as future evolutions triggered by real measurements — never by arbitrary clinic-count rules:
- **Connection pooler:** triggered by measured connection contention (verify session-feature compatibility).
- **Read replicas:** triggered by heavy read load (design explicitly for replication lag).
- **Caching:** triggered by repeated expensive reads (enforce tenant-scoped keys and safe fallback).
- **Cells / multi-region DR:** triggered by real isolation or RPO/RTO targets (remember DNS failover alone does not fence an old writer, and GDPR does not impose a universal EU-only hosting rule — see [EU Regulatory Compliance](80.24-eu-regulatory-compliance.md)).

## 5. Deliver the Walkthrough in Six Crisp Beats

Frame every architecture story as: **Problem → Constraint → Decision → Rejected alternative & trade-off → Proof/evidence → Next improvement.** Narrow any claim immediately if you cannot point to its concrete evidence.

## Summary

Anchor your Docita project interview in one concrete end-to-end workflow and 2–3 deeply understood boundaries (tenant isolation, booking concurrency, durable async work). Keep code, deployment, tests, and business metrics cleanly separated, trace failure modes before talking about hypothetical 10× scale, and clearly label future improvements as proposals.

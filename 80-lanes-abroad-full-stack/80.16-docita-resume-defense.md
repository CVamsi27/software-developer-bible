## Truth contract

- **Code-confirmed:** point to the current repository path or test.
- **Product metric:** state the approved figure and its measurement boundary; verify it in analytics before the interview.
- **Personal/operational:** describe only incidents, team process, customer facts, deployment settings, compliance status, or commercial data you personally know and may share.

Never turn source code into a claim of GDPR, HIPAA, DPDP, ISO 27001, a specific SLA, data residency, encryption configuration, RPO/RTO, or legal retention period. Those need production and legal evidence.

When source documentation and executable configuration disagree, prefer current code and package manifests, then update the documentation. The frontend package manifests currently resolve React Router v8 even though some architecture prose still says v7.

## 1. Product, scope, and ownership

### Q1. What is Docita?

Docita is a multi-tenant healthcare SaaS for clinic operations: scheduling, patient records, consultations, prescriptions, billing, clinic administration, messaging, and related workflows. The central engineering challenge is correctness and access isolation around sensitive records, not hyperscale traffic.

### Q2. Who uses it?

Clinic staff and clinicians use operational workflows, with patient-facing flows where appropriate. Name the exact user and workflow first—such as a receptionist scheduling, a clinician reviewing a record, or an administrator handling billing—then explain its authorization and failure mode.

### Q3. What was your role?

“As Founding Engineer, I have end-to-end ownership across React workflows, NestJS APIs, the PostgreSQL model, quality gates, and production delivery. That lets me explain trade-offs across layers rather than only one component.” Do not claim team composition or employment arrangements beyond what is true today.

### Q4. Is it production software?

`docita.work` is the live product. State the approved clinic and appointment metrics, but do not claim an SLA, revenue, retention, or a particular incident without current evidence.

### Q5. Why healthcare rather than generic CRUD?

One workflow can affect scheduling, patient history, billing, auditability, and downstream notification work. That raises the bar for tenant isolation, resource authorization, idempotency, observability, migration safety, and careful telemetry.

### Q6. What was the hardest technical problem?

Choose the role-relevant story: tenant isolation for backend/security, the patient-list path for performance, durable background work for systems, or stateful clinic workflows for frontend. Use problem → decision → trade-off → measured result → what you would improve.

### Q7. How do you prioritize features and debt?

Protect data correctness, authorization, active clinic workflows, and reversible delivery first. Build reusable primitives when a risk repeats; otherwise ship a narrow feature and record the specific debt/trade-off. Name a real ADR, ticket, or pull request if asked for evidence.

### Q8. What would you do differently?

Give an engineering lesson, not an invented failure: formalize API contracts earlier, broaden tenant-isolation tests, define product analytics boundaries earlier, or invest in restore tests/runbooks as scale grows. Explain why deferral was reasonable and what would trigger change.

## 2. Architecture and system design

### Q9. Walk me through the high-level architecture.

The frontend is a Vite/React SPA, the NestJS API owns synchronous request handling and PostgreSQL access, and a separate worker handles durable asynchronous work. The repository has Cloudflare frontend configuration and Fly.io worker deployment configuration; confirm the live provider setup before describing it as a production fact.

### Q10. Why separate the API and worker?

Interactive requests need predictable latency; document generation, messaging, scheduled jobs, and retries have different latency and failure characteristics. A worker keeps provider slowness and retry loops out of the request path, at the cost of queue state and eventual consistency.

### Q11. How is the current runtime topology split?

The monorepo has five applications: API, worker, clinician app, internal app, and landing site. The operationally important split is synchronous API work versus the worker, which can release and scale independently. The trade-off is more configuration and monitoring, but background jobs need not consume API capacity or force an API deployment.

### Q12. Why PostgreSQL?

Patients, appointments, prescriptions, invoices, permissions, audit records, and jobs are strongly related and require transactions, constraints, joins, indexes, and query planning. PostgreSQL gives a simpler correctness model than moving relationships and consistency checks into application code.

### Q13. Why shared-schema tenancy rather than one database per clinic?

Shared schema is operationally efficient at current scale and supports shared product evolution. The risk is cross-tenant access, so Docita layers request tenant context, ABAC policies, clinic-scoped data access, tests, and optional PostgreSQL RLS. Database-per-tenant improves blast-radius isolation but multiplies migrations, pools, and operations.

### Q14. How is tenant context established?

`TenantContextInterceptor` reads the authenticated user, stores clinic/user context for the request, and—when RLS is enabled—opens a transaction, applies tenant scope, and routes Prisma work through that transaction. Internal users are explicit privileged subjects, not an implicit bypass flag.

### Q15. How do you prevent cross-clinic leakage?

Use defense in depth: request context identifies the clinic; ABAC compares subject and resource clinic IDs; repository/service checks remain explicit; policy/E2E tests seed separate clinics; and RLS can enforce scope in the database. Do not say any one layer makes leakage impossible.

### Q16. What is the outbox pattern and why use it?

Persist the state change and an outbox event in the same transaction when a business write must trigger asynchronous work. A relay/worker processes the durable event later. This avoids “database committed but provider call failed,” while accepting eventual delivery and requiring idempotency/retry behavior.

### Q17. Why are audit records and outbox events different?

Audit records answer “who did what to which sensitive resource and when.” Outbox events answer “what downstream work must be attempted.” They can surround the same workflow but have different readers, retention needs, and failure behavior.

### Q18. How would you scale 10x?

Measure the bottleneck first: request latency/error rate, query plans, connection saturation, queue lag, and provider latency. Prioritize query/index fixes, independent worker capacity, safely scoped caching, and vertical database scaling before adding distributed complexity. Do not quote traffic or instance counts you have not measured.

## 3. NestJS, Prisma, PostgreSQL, and APIs

### Q19. Why NestJS over plain Express?

NestJS gives a consistent module, dependency-injection, guard, interceptor, validation, and exception-handling structure for a large domain. Plain Express can work, but conventions reduce drift when many workflows need the same authentication, tenant, audit, and error-handling boundaries.

### Q20. Explain the API request lifecycle.

An authenticated request passes through framework concerns such as request identification and tenant context; guards/policies validate who may act; DTO/validation code constrains input; the service/repository performs domain work; and observability/audit hooks record safe context. Use the actual controller/service path for the feature you discuss.

### Q21. How do DTO validation, guards, and interceptors differ?

DTO validation rejects malformed input. Guards decide whether a subject can enter a route. Interceptors add cross-cutting behavior such as request ID or tenant context. Resource-level authorization belongs close to the resource access, not only in the UI.

### Q22. How do you use Prisma safely?

Use it for typed CRUD, relations, transactions, migrations, and parameterized query construction. Keep hot query behavior observable, avoid raw SQL unless necessary, bind parameters for raw queries, and inspect generated SQL/query plans when performance matters.

### Q23. How do you handle transactions?

Put the minimal atomic business boundary in one transaction: for example, a core record, its audit record, and a durable outbox event when they must succeed together. Keep slow external provider calls out of the transaction; the worker processes durable work afterward.

### Q24. How do you avoid N+1 queries?

Measure round trips and trace the page/API path. Fetch needed relations deliberately, batch by IDs, select only required fields, add the right index, and re-measure p95. The repository enforces N+1 and API-latency guardrails; state a numerical before/after only when the current dashboard or benchmark is available.

### Q25. How do you choose an index?

Start with the actual filter, join, sort, and cardinality in `EXPLAIN ANALYZE`. Add a composite or partial index only when it matches a repeatable access pattern, then re-measure write cost and query benefit. Indexes add storage and write overhead.

### Q26. How do you manage schema changes safely?

Use Prisma migrations and the repository’s `safe-migrate.sh` tooling for backup, dry-run, deploy, verification, and restore paths. For destructive changes, use expand/contract: add compatible schema, deploy compatible code, backfill/verify, stop old reads/writes, then remove the old column later.

### Q27. How do you design pagination and filtering?

Bound the response, make sort order deterministic, validate filter input, include clinic ownership in every relevant query, and make indexes match the common filter/sort path. Explain cursor pagination for changing large datasets and offset pagination only when its trade-off is acceptable.

### Q28. How do you prevent duplicate appointment or webhook effects?

Use an idempotency key or provider event ID that maps repeated requests to one durable result. The API has idempotency support and E2E tests; webhook tests also cover duplicate delivery. Distinguish duplicate-request prevention from a separate business rule such as schedule capacity.

### Q29. What happens when two users book the same slot?

Clarify the invariant first: one clinician/time slot, one room/bed, or capacity scheduling. Enforce it transactionally through the relevant query, constraint, or locking strategy and return a conflict response. Idempotency prevents a retried client request; it does not solve two distinct users racing for the same slot.

## 5. Security, privacy, and governance

### Q38. How do authentication and authorization differ?

Authentication establishes who the subject is. Authorization evaluates whether that subject may perform this action on this resource in this clinic. A valid JWT is not enough to view another clinic’s patient; ABAC/resource checks and tenant scope make that decision.

### Q39. How does Docita implement ABAC?

`packages/authorization/src/policies/` contains policies for patients, appointments, prescriptions, invoices, lab orders, and audit logs. They evaluate subject roles/clinic/ownership against resource attributes and return an allow, deny, or not-applicable decision. The policy tests provide evidence for cross-clinic denial.

### Q40. How do you audit patient access?

Patient-PHI access utilities and audit E2E tests record sensitive access. Explain the evidence needed for an investigation—actor, clinic, action, target, request context, and time—then state the limits honestly: retention and legal response depend on confirmed governance policy.

### Q41. How do you keep PHI out of Sentry?

`sentry.utils.ts` redacts PHI from request payloads, query strings, headers, cookies, contexts, tags, extras, breadcrumbs, and messages before send. Preserve error shape and request correlation without sending clinical payloads to an error-tracking vendor.

### Q42. Are you GDPR/HIPAA/DPDP compliant?

“I do not describe the product as certified or legally compliant without a completed assessment. I can describe engineering controls: tenant isolation, ABAC, audit events, consent-related code, PHI-safe telemetry, and secure webhook patterns. Formal obligations, contracts, retention, and breach notification are owned with legal and security stakeholders.”

### Q43. How do you handle consent, deletion, export, and correction?

The code has a `ConsentGuard`, patient-consent hooks, patient export audit actions, and patient deletion actions. The flow is authenticate, authorize, record the action, preserve records required for audit/legal retention, and apply the confirmed data policy. A UI delete is not an erasure claim across backups or logs.

### Q44. How do you handle a suspected breach?

Contain the affected path, preserve evidence, rotate/revoke appropriate credentials, determine impact from audit/operational data, involve the responsible legal/security owners, remediate, and document the outcome. Do not quote a statutory deadline or a recurring drill unless confirmed.

### Q45. How do you validate webhooks?

Verify the provider signature before business processing, deduplicate repeats, process the durable effect transactionally, and make retries safe. Webhook E2E tests cover valid/tampered signatures, duplicate delivery, and CSRF treatment of webhook routes.

### Q46. How do you secure uploads and generated documents?

Authorize and tenant-scope access before upload/download; validate file type/size server-side; use upload/session capabilities only within their intended lifetime; keep PHI out of logs; and confirm storage encryption, malware scanning, and lifecycle policy from production evidence before claiming them.

### Q47. How do you apply OWASP thinking?

Map threats to concrete controls: ABAC/RLS for broken access control, validation and parameter binding for injection, secrets/configuration hygiene, signature verification and dependency review for integrity, and PHI-safe monitoring. Name the code/test for a control rather than listing generic compliance claims.

## 6. Reliability, performance, and observability

### Q48. What performance evidence can you defend?

The repository supports a defensible method: measure p95 and round trips, inspect query shape, identify N+1 work, reduce round trips, and re-measure. Quote a before/after only from a current dashboard or benchmark; source code alone does not prove historical latency.

### Q49. Why p95 instead of average latency?

An average hides the slowest meaningful slice of users. p95 identifies whether clinic staff regularly encounter a slow screen, while p99 exposes tail failures. Pair latency with error rate and actual workflow completion.

### Q50. How do you investigate a slow endpoint?

Start from a correlated request ID and route/tenant-safe logs, check recent deploy and provider health, inspect query count and `EXPLAIN ANALYZE`, then change the smallest bottleneck. Re-measure the same workload; do not add Redis or indexes by reflex.

### Q51. What belongs in a background worker?

Retryable work not required for the immediate response: messaging, generated documents, scheduled work, webhooks, and reconciliation. The API persists durable work; the worker owns attempts, backoff, idempotency, terminal failure, and observability.

### Q52. How do you handle duplicate delivery and poison jobs?

The worker contract includes attempts, fixed/exponential backoff, idempotency keys, DLQ behavior, manual replay metadata, and a bounded replay policy. This provides at-least-once processing with idempotent consumers—not magical exactly-once delivery.

### Q53. How do you monitor health?

Use layered signals: structured request context, Sentry errors/metrics, API health checks, worker/queue state, and domain-level signals such as failed or dead-lettered jobs. Alert thresholds and response commitments are operational policy; verify them before quoting numbers.

### Q54. What is your cache strategy?

Include `clinicId` in the key, invalidate or version around writes, and degrade safely to PostgreSQL. Do not claim a cache implementation or TTL convention without current code evidence.

### Q55. How do you plan backups and recovery?

The repository provides `safe-migrate.sh` with backup/restore paths. A credible production answer includes backup scope, restore testing, RPO/RTO, retention, access control, and owner—but those are operations facts to confirm, not infer from a script.

## 10. PostgreSQL Internals and Advanced Topics

### Q75. Explain MVCC. How does PostgreSQL handle concurrent reads and writes?

"MVCC means every row has multiple versions. Readers see a snapshot at transaction start — they never block writers. Writers create new tuple versions rather than modifying in place. Dead tuples accumulate until VACUUM reclaims them. The trade-off: fast reads, but VACUUM must keep up to prevent bloat."

**Code-confirmed:** Query plans in `EXPLAIN ANALYZE` output, `pg_stat_user_tables` for dead tuple counts.

### Q76. What is the WAL and how does it enable crash recovery?

"The Write-Ahead Log records every change before it's applied to data files. On crash, PostgreSQL replays committed WAL and rolls back uncommitted changes. WAL also enables point-in-time recovery and streaming replication. The trade-off: WAL writes add latency to every write operation."

**Code-confirmed:** `safe-migrate.sh` uses WAL-aware backup/restore paths.

### Q77. Why is PgBouncer necessary? What happens when you exhaust connections?

"Each PostgreSQL connection spawns a backend process (~5-10MB). At 500 connections, that's 2.5-5GB just for overhead. PgBouncer multiplexes many app connections onto fewer database connections. Docita uses transaction mode — connections are released after each transaction, not held for the session."

### Q78. How do you choose between a composite index on (a, b) vs (b, a)?

"A composite index (a, b) satisfies queries on (a), (a, b), or (a) with ORDER BY b. It cannot efficiently satisfy queries on (b) alone. Example: index on (clinic_id, created_at) works for 'all appointments in clinic X, sorted by date' but not for 'all appointments created today, grouped by clinic.'"

### Q79. What is a partial index and when would you use one?

"A partial index indexes only rows matching a WHERE clause. Example: `CREATE INDEX idx_active ON appointments (clinic_id, slot_start) WHERE status = 'booked'`. Smaller and faster than a full index because it excludes cancelled/completed appointments. Use when you frequently query a small subset of a large table."

## 11. Kafka and Message Queue Internals

### Q80. How does Kafka maintain ordering? What are the limits?

"Kafka guarantees ordering within a partition, not across partitions. If you need ordering for a specific entity (e.g., appointments for one patient), all events for that entity must go to the same partition (partition by patient_id). More partitions = more parallelism but harder ordering guarantees."

### Q81. What are consumer groups and how does rebalancing work?

"A consumer group is a set of consumers that jointly consume a topic. Each partition is assigned to exactly one consumer. When a consumer joins or leaves, partitions are redistributed (rebalance). During rebalance, consumption pauses briefly. Minimize rebalance frequency with static membership and longer session timeouts."

### Q82. What is exactly-once semantics in Kafka?

"Exactly-once means each message is processed once despite retries. Kafka achieves this via: idempotent producer (sequence numbers), transactional producer (atomic writes), and transactional offset commits. In practice, most systems use at-least-once + idempotent consumers (effectively-once)."

### Q83. What is the difference between Kafka and RabbitMQ?

"Kafka: high throughput, log-based, messages persist after consumption, replay capability. RabbitMQ: traditional broker, messages deleted after consumption, complex routing (exchanges, bindings), lower latency for small messages. Choose Kafka for event sourcing and streaming; RabbitMQ for task queues and complex routing."

### Q84. How do you handle dead letter queues?

"DLQ: a queue where messages go after max retry attempts. Use when: message is poison (permanently failing), business logic rejects it, or retry budget is exhausted. Replay after fixing the root cause. Monitor DLQ depth and rate — alert on DLQ depth > 0 for > 5 minutes."

## 12. Caching Deep-Dive

### Q85. Explain cache-aside vs read-through vs write-through.

"Cache-aside: app reads cache → miss → reads DB → writes to cache. Read-through: cache reads DB on miss (app only talks to cache). Write-through: writes go to cache and DB simultaneously. Docita uses cache-aside for schedule data — the app explicitly controls what's cached and when it's invalidated."

### Q86. What is cache stampede and how do you prevent it?

"When a cached value expires, many concurrent requests all miss the cache and hit the DB simultaneously. Prevention: (1) lock/mutex — one request repopulates, others wait, (2) probabilistic early expiration, (3) background refresh before TTL expires, (4) stale-while-revalidate — return stale data while refreshing."

### Q87. How do you handle cache invalidation in a multi-tenant system?

"Cache keys must include clinic_id: `cache:clinic:{clinicId}:schedule:{practitionerId}`. Invalidation strategies: TTL-based (accept staleness), event-driven (outbox event triggers invalidation), write-through (invalidate on every write). For Docita: TTL for schedule data (30s), event-driven for patient data."

### Q88. What happens when Redis goes down?

"Graceful degradation: all cache reads fall through to PostgreSQL (slower but correct). Cache writes are skipped. The system continues to function at reduced performance. Prevention: Redis Sentinel for failover, circuit breaker on Redis, monitor health and alert on failure."

## 13. Observability and Reliability

### Q89. Explain SLI, SLO, and SLA for Docita.

"SLI: what you measure (API latency p95, error rate). SLO: the target (p95 < 500ms, error rate < 0.1%). SLA: the contract with users (99.9% uptime). For Docita: SLI = API latency, error rate, booking success rate. SLO = p95 < 500ms, error rate < 0.1%. SLA = uptime commitment if contractually required."

### Q90. What is an error budget?

"Error budget = 1 - SLO. If SLO is 99.9% uptime, budget is 0.1% (~43 minutes/month). If you've consumed 50% in the first week, slow down releases and focus on reliability. If <10%, ship faster. Error budgets balance velocity and reliability."

### Q91. How do you trace a request across API → worker → provider?

"Trace context propagation: API creates a trace, writes outbox event with trace context, worker reads and continues the trace, worker calls provider and adds a child span. Full trace shows: API processing → outbox write → worker pickup → provider call → completion. Use OpenTelemetry with W3C Trace Context."

### Q92. How do you handle PHI in observability data?

"PHI must never appear in trace spans, logs, or metrics. Sanitize: remove patient names from query text, remove appointment details from attributes, use abstract identifiers. Implementation: OpenTelemetry span processor that scrubs PHI before export. Testing: assert trace export contains no PHI patterns."

### Q93. Walk me through your incident response playbook.

"(1) Detect — alert fires or user reports. (2) Triage — is it patient-safety-critical? Escalate immediately. (3) Contain — disable affected feature. (4) Diagnose — trace request, check logs. (5) Remediate — fix or rollback. (6) Communicate — update stakeholders. (7) Postmortem — blameless review within 48 hours. Patient safety is always priority #1."

## 14. Security Advanced

### Q94. Explain the full OAuth 2.0 flow for Docita's SPA.

"Authorization code with PKCE: (1) SPA redirects to /auth/login, (2) user authenticates, (3) server returns authorization code, (4) SPA exchanges code for access token + refresh token (httpOnly cookie), (5) access token expires in 15min, (6) SPA uses refresh token to get new access token. PKCE prevents authorization code interception."

### Q95. How do you prevent IDOR in a multi-tenant system?

"Every resource access checks: (1) clinic_id (tenant boundary), (2) ownership/assignment (ownership boundary), (3) role (role boundary). E2E tests seed two clinics and assert cross-clinic denial. UUIDs are not a security boundary — the policy check is."

### Q96. How do you handle CORS for a healthcare SPA?

"Strict CORS: only allow the specific frontend origin (`https://app.docita.work`), never use `*`. Allow Authorization and Content-Type headers. Allow credentials (httpOnly cookies). Preflight: browser sends OPTIONS before actual request. SPA with JWT in Authorization header is inherently CSRF-safe."

### Q97. How do you secure file uploads for medical documents?

"Pre-signed URL flow: (1) client requests pre-signed URL from API, (2) API validates authorization, generates time-limited URL scoped to storage path, (3) client uploads directly to S3/R2, (4) client confirms, API validates metadata, creates DB record. Security: URL expires in 5 minutes, path includes clinic_id + UUID, file type validated by magic bytes, PHI never logged."

### Q98. How do you balance security with developer experience?

"Security as defaults (new endpoints protected by default), security tooling in CI (pre-commit hooks, SAST), security champions (one per team), practical training. Shortcuts to avoid: disabling security checks, hardcoding credentials, skipping review for 'small' changes. Security is not optional, but it should be easy."

## 15. Performance Engineering

### Q99. How do you profile a Node.js application?

"Tools: clinic.js (flame graph, event loop delay, heap snapshot), Chrome DevTools, 0x. Process: reproduce in staging → capture profile → analyze flame graph → identify bottleneck → optimize → re-profile. For Docita: CPU profiling for slow API endpoints, memory profiling for the worker (long-running process)."

### Q100. How do you load test Docita's booking endpoint?

"k6 script: 50 virtual users booking the same slot simultaneously. Assert: exactly 1 succeeds (201), 49 get 409, no deadlocks, no orphaned locks, p95 < 500ms. Realistic scenarios: morning rush (8-10am), Monday peak, mixed read/write (80% reads, 20% writes)."

### Q101. What is capacity planning for Docita?

"Current: 25 clinics, 1000 appointments/month. Growth: 10 clinics/month. At 100 clinics: need PgBouncer, read replica, 2 API instances. At 500 clinics: need cell-based architecture, multi-region. Rule of thumb: plan for 3x current load, review quarterly. Identify bottleneck first (usually DB connections or query latency)."

### Q102. How do you handle a traffic spike?

"Options: auto-scale API instances, auto-scale worker, cache schedule data, rate limit per clinic, queue notifications. For Docita: auto-scale behind load balancer, cache practitioner schedules (30s TTL), rate limit by clinic_id, queue non-critical work. Plan ahead for known spikes (Monday morning clinic rush)."

### Q103. How do you optimize a Prisma query?

"Common pitfalls: findMany without select (fetches all columns), include without take (loads all related records), N+1 (loop with individual queries), missing index on filtered columns. Fix: use select for needed fields, take/skip for pagination, $transaction for batch operations, enable query logging, run EXPLAIN ANALYZE on generated SQL."

## 16. Advanced System Design

### Q104. How would you scale Docita from 25 to 500 clinics?

"25 clinics: shared PostgreSQL, single API, single worker. 100 clinics: PgBouncer, read replica, 2 API instances. 500 clinics: partition by clinic (cell-based), per-clinic caching, connection pool per cell, multiple read replicas, queue partitioning. Key changes: connection pooling critical, query latency matters, blast radius must be limited."

### Q105. How do you design a feature flag system?

"Components: flag definitions (name, type, default, targeting rules), evaluation engine (hash user_id for consistent bucketing), admin UI (create/edit/kill switch), SDK for client-side evaluation. Targeting: percentage rollout, user segments, individual users. For Docita: feature flags for gradual rollout, kill switches for risky features."

### Q106. How do you implement chaos engineering for Docita?

"Experiments: (1) kill a worker instance → verify outbox events reprocessed, (2) simulate DB connection exhaustion → verify PgBouncer handles it, (3) delay notification provider → verify booking still works, (4) partition API from DB → verify error responses (not hangs). Start with staging, then production with safeguards."

### Q107. How do you design a disaster recovery system with RPO < 1 hour?

"Current state: managed Postgres with automated backups; single region by recorded decision (ADR 0006). Design if RPO<1h were required: WAL archival to object storage + warm standby in second AZ/region, promotion runbook (detect → promote → repoint Fly app env → verify), restore drills before trusting it. Say honestly: DR *drills* are not currently scheduled — that's the gap this design would close."

### Q108. How do you handle zero-downtime database migrations?

"Expand/contract: (1) expand: add new columns/tables (backward compatible), (2) deploy code that writes to both, (3) backfill in batches, (4) verify consistency, (5) deploy code that reads only from new, (6) contract: remove old columns. Tooling: safe-migrate.sh wraps Prisma with backup, dry-run, deploy, restore."

## 17. Docita-Specific Deep Dives

### Q109. Walk me through the concurrent booking flow from button click to database.

"(1) Frontend disables button (duplicate-submit protection). (2) TanStack Query sends POST with idempotency key. (3) API validates DTO (Zod). (4) TenantContextInterceptor sets clinic context. (5) ABAC policy checks role and clinic. (6) Service opens Prisma transaction. (7) SELECT FOR UPDATE on patient row. (8) Check overlapping appointments. (9) If overlap → 409 Conflict. (10) If no overlap → INSERT appointment + outbox event, COMMIT. (11) Return 201. (12) Worker picks up outbox event, sends notification."

### Q110. How does the TenantContextInterceptor work with Prisma RLS?

"(1) Interceptor extracts { userId, clinicId, role } from JWT. (2) Stores in request-scoped context (AsyncLocalStorage). (3) If RLS enabled: opens Prisma transaction, runs `SET app.current_clinic = '<clinicId>'`. (4) All Prisma calls within that transaction are scoped by RLS. (5) After request: closes transaction, clears context. Internal users: explicit clinic override."

### Q111. How does the ABAC policy engine evaluate a patient access request?

"Policy file evaluates: (1) subject role (RECEPTIONIST can view, CLINICIAN can edit), (2) subject clinic == resource clinic (cross-clinic denied), (3) ownership/assignment (CLINICIAN only assigned patients), (4) action type (CRUD). Decision: ALLOW, DENY, or NOT_APPLICABLE. DENY returns 403 immediately. Tests seed two clinics and assert cross-clinic denial."

### Q112. What happens when the worker is down for 30 minutes?

"Outbox events accumulate (unprocessed). Relay continues polling (events stay in table). When worker recovers, relay publishes accumulated events. Worker processes in order (FIFO). All notifications eventually sent. Key: no events lost, just delayed. User impact: notifications late, but bookings never lost."

### Q113. How does the webhook verification system work?

"(1) Provider sends webhook. (2) API extracts signature from header. (3) Verifies HMAC against known secret. (4) Invalid → 403, log tampered attempt. (5) Valid: check event ID for deduplication. (6) Duplicate → 200 (acknowledge, don't reprocess). (7) New: create outbox event atomically. (8) Return 200. Tests: valid → 200, tampered → 403, duplicate → 200, missing → 403."

### Q114. How would you add real-time updates to the calendar view?

"Architecture: (1) WebSocket gateway authenticated and scoped to clinic room. (2) When appointment booked/cancelled, API publishes event to clinic room. (3) Client receives event, updates calendar via TanStack Query. Failure modes: disconnect → polling fallback, restart → reconnect with last event ID, simultaneous bookings → UI merges (calendar is a projection)."

### Q115. What would break if Docita scaled to 100 clinics? 500? 1000?

"100 clinics: connection pool exhaustion (need PgBouncer), query latency (need read replica), outbox table growth (need partitioning). 500 clinics: shared PostgreSQL bottleneck (need cell-based), worker throughput (need multiple workers), notification volume (need dedicated service). 1000 clinics: cell-based architecture, multi-region (data residency), dedicated DBA."

## 18. Migration and Evolution

### Q116. How do you migrate from shared-schema to database-per-tenant?

"Steps: (1) add clinic_id to every query (verify), (2) create per-tenant databases, (3) dual-write: both shared and per-tenant, (4) backfill per-tenant databases, (5) verify consistency (row counts, checksums), (6) switch reads to per-tenant, (7) remove dual-write, (8) remove clinic_id from shared tables. Timeline: 3-6 months. Only if regulatory requirements demand it."

### Q117. How do you handle API versioning during a major rewrite?

"Strategy: (1) v1 API continues (no breaking changes), (2) v2 API is new implementation, (3) migrate clients one by one, (4) deprecate v1 after all migrate. For Docita: keep REST v1 running, add GraphQL as v2, migrate clinician app, deprecate REST. Timeline: 6-12 months."

### Q118. How do you migrate from Express to NestJS?

"Steps: (1) set up NestJS alongside Express, (2) route new features to NestJS, (3) migrate existing endpoints one by one, (4) verify correctness, (5) remove Express. Key: don't rewrite at once, use feature flags, keep tests passing, have rollback plan."

### Q119. How do you handle database schema evolution at scale?

"Expand/contract: (1) expand: add new columns/tables (backward compatible), (2) deploy code that writes to both, (3) backfill data, (4) verify consistency, (5) deploy code that reads only from new, (6) contract: remove old columns. Tools: Prisma migrations for DDL, safe-migrate.sh for production safety."

### Q120. How do you migrate from one database to another?

"Steps: (1) dual-write to both, (2) backfill new database, (3) verify (row counts, checksums), (4) cutover reads to new, (5) remove dual-write. Key: new DB must handle same query patterns, dual-write adds latency, verification must be thorough. For PostgreSQL to Aurora: straightforward (same engine)."

## 19. Multi-Region and Data Residency

### Q121. How do you handle data residency requirements for GDPR?

"Patient data must stay in EU. Implementation: (1) pin clinic data to region (clinic metadata includes region), (2) route API requests to clinic's region, (3) replicate within region only, (4) cross-region queries use anonymized/aggregated data. For Docita: single region is fine at current scale; multi-region when expanding to multiple EU countries."

### Q122. How would you design a multi-region deployment?

"Architecture: (1) each region has its own PostgreSQL primary + read replicas, (2) API and worker per region, (3) patient data pinned to clinic's region, (4) global load balancer routes to nearest region. Challenges: cross-region eventually consistent, schema changes across regions, failover requires data sync."

### Q123. How do you handle a region outage?

"Process: (1) detect via health checks, (2) Route 53 failover to DR region, (3) DR region has read replica promoted to primary, (4) verify application connectivity, (5) communicate to stakeholders. RPO depends on replication mode (async: may lose recent writes, sync: zero data loss but higher latency)."

### Q124. How do you handle cross-region data consistency?

"Options: (1) synchronous replication (zero data loss, higher latency), (2) asynchronous replication (some lag, lower latency), (3) conflict resolution (last-write-wins, merge). For Docita: async replication within region (read replicas), no cross-region patient data transfer (data residency). Cross-region: aggregated/anonymized analytics only."

### Q125. How do you design for disaster recovery across regions?

"Architecture: (1) primary in EU-West, (2) async replica in EU-Central, (3) WAL archival to cross-region S3, (4) quarterly DR drills. RPO: 1 hour (WAL archival interval). RTO: 1 hour (restore + replay). Process: detect → promote replica → update DNS → verify. Trade-off: RPO < 1 hour requires synchronous replication (higher latency)."

## 20. Cost Optimization

> **Infra reality check (v2):** Docita compute runs on **Fly.io machines** (suspended outside IST business hours), frontends on **Cloudflare Workers**, storage on **Cloudflare R2**, database on **managed Postgres (RDS)**. The answers below are framed accordingly — never describe AWS/Kubernetes estates that don't exist.

### Q126. How do you optimize infrastructure costs for Docita?

"Levers actually used: Fly machines suspend to zero outside IST clinic hours (`min_machines_running=0`, scheduled workflow — ADR 0011); Cloudflare Workers free-tier-friendly static assets (~50KB proxy worker after the Vite cutover); R2 storage with zero egress fees; Redis kept optional/gated (`CACHE_BACKEND=memory`); single-region Postgres right-sized rather than multi-AZ by default. Monitor per-clinic cost trend monthly."

### Q127. How do you estimate the cost of scaling to 100 clinics?

"Current posture scales mostly vertically: bigger Postgres instance first, second API machine + second worker next, then connection multiplexing (PgBouncer-style) before any architectural change. Cost drivers in order: database instance size, Fly machine hours (which scale-to-zero already optimizes), R2 growth, WhatsApp/message-provider spend (per-conversation pricing — often bigger than infra). Present as unit economics: infra cost per clinic per month."

### Q128. How do you balance cost with reliability?

"Framework: patient-facing reliability is non-negotiable; everything else is elastic. Concrete examples from Docita: we suspend servers overnight (accepting cold-start seconds) because no clinics operate then — but the queue/outbox/DLQ machinery stays simple and durable because lost notifications harm patients. Right-size on measured load; keep one reliable stateful dependency (Postgres) over many cheap ones."

### Q129. When would you change your database setup?

"Triggers: sustained connection pressure → multiplexing/pooler; read-heavy calendar load → read replica; residency or latency needs by geography → region-pinned cells (ADR 0006 records why not yet). Engine migration (e.g., Aurora-style) only when managed-Postgres limits are demonstrably hit — at 25→100 clinics they aren't."

### Q130. How do you estimate cost for a new feature?

"Steps: (1) name new dependencies (compute pattern, storage growth, external provider), (2) estimate usage at approved scale (25+ clinics, 1,000+ appointments/month), (3) price providers honestly — messaging/AI per-call costs usually dominate infra, (4) add buffer, (5) express as cost-per-clinic-per-month against plan revenue. Example: AI features ship behind a credit guard so spend is capped by design."

# Docita Interview Defense — Current-Code Q&A

> A source-grounded guide for defending Docita in technical, product, security, system-design, and behavioral interviews. It is not a script: answer in your own words and use only facts you can verify.

## Truth contract

Use one of these three evidence levels in every answer:

- **Code-confirmed:** point to the current repository path or test.
- **Product metric:** state the approved figure and its measurement boundary; verify it in analytics before the interview.
- **Personal/operational:** describe only incidents, team process, customer facts, deployment settings, compliance status, or commercial data you personally know and may share.

Never turn source code into a claim of GDPR, HIPAA, DPDP, ISO 27001, a specific SLA, data residency, encryption configuration, RPO/RTO, or legal retention period. Those need production and legal evidence.

When source documentation and executable configuration disagree, prefer current code and package manifests, then update the documentation. The frontend package manifests currently resolve React Router v8 even though some architecture prose still says v7.

## 1. Product, scope, and ownership

### Q1. What is Docita?

Docita is a multi-tenant healthcare SaaS for clinic operations: scheduling, patient records, consultations, prescriptions, billing, clinic administration, messaging, and related workflows. The central engineering challenge is correctness and access isolation around sensitive records, not hyperscale traffic.

### Q2. Who uses it?

Clinic staff and clinicians use operational workflows, with patient-facing flows where appropriate. Name the exact user and workflow first—such as a receptionist scheduling, a clinician reviewing a record, or an administrator handling billing—then explain its authorization and failure mode.

### Q3. What was your role?

“As Founding Engineer, I have end-to-end ownership across React workflows, NestJS APIs, the PostgreSQL model, quality gates, and production delivery. That lets me explain trade-offs across layers rather than only one component.” Do not claim team composition or employment arrangements beyond what is true today.

### Q4. Is it production software?

`docita.work` is the live product. State the approved clinic and appointment metrics, but do not claim an SLA, revenue, retention, or a particular incident without current evidence.

### Q5. Why healthcare rather than generic CRUD?

One workflow can affect scheduling, patient history, billing, auditability, and downstream notification work. That raises the bar for tenant isolation, resource authorization, idempotency, observability, migration safety, and careful telemetry.

### Q6. What was the hardest technical problem?

Choose the role-relevant story: tenant isolation for backend/security, the patient-list path for performance, durable background work for systems, or stateful clinic workflows for frontend. Use problem → decision → trade-off → measured result → what you would improve.

### Q7. How do you prioritize features and debt?

Protect data correctness, authorization, active clinic workflows, and reversible delivery first. Build reusable primitives when a risk repeats; otherwise ship a narrow feature and record the specific debt/trade-off. Name a real ADR, ticket, or pull request if asked for evidence.

### Q8. What would you do differently?

Give an engineering lesson, not an invented failure: formalize API contracts earlier, broaden tenant-isolation tests, define product analytics boundaries earlier, or invest in restore tests/runbooks as scale grows. Explain why deferral was reasonable and what would trigger change.

## 2. Architecture and system design

### Q9. Walk me through the high-level architecture.

The frontend is a Vite/React SPA, the NestJS API owns synchronous request handling and PostgreSQL access, and a separate worker handles durable asynchronous work. The repository has Cloudflare frontend configuration and Fly.io worker deployment configuration; confirm the live provider setup before describing it as a production fact.

### Q10. Why separate the API and worker?

Interactive requests need predictable latency; document generation, messaging, scheduled jobs, and retries have different latency and failure characteristics. A worker keeps provider slowness and retry loops out of the request path, at the cost of queue state and eventual consistency.

### Q11. How is the current runtime topology split?

The monorepo has five applications: API, worker, clinician app, internal app, and landing site. The operationally important split is synchronous API work versus the worker, which can release and scale independently. The trade-off is more configuration and monitoring, but background jobs need not consume API capacity or force an API deployment.

### Q12. Why PostgreSQL?

Patients, appointments, prescriptions, invoices, permissions, audit records, and jobs are strongly related and require transactions, constraints, joins, indexes, and query planning. PostgreSQL gives a simpler correctness model than moving relationships and consistency checks into application code.

### Q13. Why shared-schema tenancy rather than one database per clinic?

Shared schema is operationally efficient at current scale and supports shared product evolution. The risk is cross-tenant access, so Docita layers request tenant context, ABAC policies, clinic-scoped data access, tests, and optional PostgreSQL RLS. Database-per-tenant improves blast-radius isolation but multiplies migrations, pools, and operations.

### Q14. How is tenant context established?

`TenantContextInterceptor` reads the authenticated user, stores clinic/user context for the request, and—when RLS is enabled—opens a transaction, applies tenant scope, and routes Prisma work through that transaction. Internal users are explicit privileged subjects, not an implicit bypass flag.

### Q15. How do you prevent cross-clinic leakage?

Use defense in depth: request context identifies the clinic; ABAC compares subject and resource clinic IDs; repository/service checks remain explicit; policy/E2E tests seed separate clinics; and RLS can enforce scope in the database. Do not say any one layer makes leakage impossible.

### Q16. What is the outbox pattern and why use it?

Persist the state change and an outbox event in the same transaction when a business write must trigger asynchronous work. A relay/worker processes the durable event later. This avoids “database committed but provider call failed,” while accepting eventual delivery and requiring idempotency/retry behavior.

### Q17. Why are audit records and outbox events different?

Audit records answer “who did what to which sensitive resource and when.” Outbox events answer “what downstream work must be attempted.” They can surround the same workflow but have different readers, retention needs, and failure behavior.

### Q18. How would you scale 10x?

Measure the bottleneck first: request latency/error rate, query plans, connection saturation, queue lag, and provider latency. Prioritize query/index fixes, independent worker capacity, safely scoped caching, and vertical database scaling before adding distributed complexity. Do not quote traffic or instance counts you have not measured.

## 3. NestJS, Prisma, PostgreSQL, and APIs

### Q19. Why NestJS over plain Express?

NestJS gives a consistent module, dependency-injection, guard, interceptor, validation, and exception-handling structure for a large domain. Plain Express can work, but conventions reduce drift when many workflows need the same authentication, tenant, audit, and error-handling boundaries.

### Q20. Explain the API request lifecycle.

An authenticated request passes through framework concerns such as request identification and tenant context; guards/policies validate who may act; DTO/validation code constrains input; the service/repository performs domain work; and observability/audit hooks record safe context. Use the actual controller/service path for the feature you discuss.

### Q21. How do DTO validation, guards, and interceptors differ?

DTO validation rejects malformed input. Guards decide whether a subject can enter a route. Interceptors add cross-cutting behavior such as request ID or tenant context. Resource-level authorization belongs close to the resource access, not only in the UI.

### Q22. How do you use Prisma safely?

Use it for typed CRUD, relations, transactions, migrations, and parameterized query construction. Keep hot query behavior observable, avoid raw SQL unless necessary, bind parameters for raw queries, and inspect generated SQL/query plans when performance matters.

### Q23. How do you handle transactions?

Put the minimal atomic business boundary in one transaction: for example, a core record, its audit record, and a durable outbox event when they must succeed together. Keep slow external provider calls out of the transaction; the worker processes durable work afterward.

### Q24. How do you avoid N+1 queries?

Measure round trips and trace the page/API path. Fetch needed relations deliberately, batch by IDs, select only required fields, add the right index, and re-measure p95. The repository enforces N+1 and API-latency guardrails; state a numerical before/after only when the current dashboard or benchmark is available.

### Q25. How do you choose an index?

Start with the actual filter, join, sort, and cardinality in `EXPLAIN ANALYZE`. Add a composite or partial index only when it matches a repeatable access pattern, then re-measure write cost and query benefit. Indexes add storage and write overhead.

### Q26. How do you manage schema changes safely?

Use Prisma migrations and the repository’s `safe-migrate.sh` tooling for backup, dry-run, deploy, verification, and restore paths. For destructive changes, use expand/contract: add compatible schema, deploy compatible code, backfill/verify, stop old reads/writes, then remove the old column later.

### Q27. How do you design pagination and filtering?

Bound the response, make sort order deterministic, validate filter input, include clinic ownership in every relevant query, and make indexes match the common filter/sort path. Explain cursor pagination for changing large datasets and offset pagination only when its trade-off is acceptable.

### Q28. How do you prevent duplicate appointment or webhook effects?

Use an idempotency key or provider event ID that maps repeated requests to one durable result. The API has idempotency support and E2E tests; webhook tests also cover duplicate delivery. Distinguish duplicate-request prevention from a separate business rule such as schedule capacity.

### Q29. What happens when two users book the same slot?

Clarify the invariant first: one clinician/time slot, one room/bed, or capacity scheduling. Enforce it transactionally through the relevant query, constraint, or locking strategy and return a conflict response. Idempotency prevents a retried client request; it does not solve two distinct users racing for the same slot.

## 4. React, Vite, and frontend workflows

### Q30. Why Vite rather than Next.js?

The clinical/admin interface is a stateful dashboard, not a content-first SEO site. A Vite SPA simplifies static delivery and keeps client-side routing/data-fetching explicit. Next.js remains valid for content-heavy or server-rendered work; this is a workload decision, not framework loyalty.

### Q31. What is the current frontend stack?

The app uses React 19, Vite 6, React Router v8, and TanStack Query. Quote versions only after checking `apps/app/package.json`; the resume intentionally uses framework names rather than brittle versions.

### Q32. How do you manage server state and UI state?

Keep server data, cache invalidation, loading/error states, and mutations in the data-fetching layer; keep local interaction state close to the component or feature. Do not put every form field or modal in a global store.

### Q33. How do you design clinic forms?

Start with the user task and validation boundary: accessible labels, useful field errors, predictable keyboard flow, loading/submission states, duplicate-submit protection, and a clear recovery path. Validate on the client for feedback and on the API for trust.

### Q34. What does offline support actually do?

The app has a production service worker that caches the SPA shell and falls back to an offline page. Do not claim IndexedDB-backed synchronization, an offline mutation queue, or conflict resolution; those are not current code-confirmed capabilities.

### Q35. How do you improve frontend performance?

Measure a real workflow: route load, bundle size, expensive renders, request waterfalls, and Core Web Vitals. Apply the smallest fix—route/code splitting, memoization after profiling, query caching, asset optimization, or fewer requests—and verify no accessibility or correctness regression.

### Q36. How do you make a React feature accessible?

Use semantic controls before ARIA, associate labels/errors with fields, maintain keyboard order and focus, expose loading/error changes appropriately, and test with keyboard navigation plus focused automated checks.

### Q37. How do you handle real-time updates?

The API has notification gateway code scoped by clinic. Explain connection authentication, clinic-room membership, authorization before publish, reconnect behavior, and fallback/polling where a real-time signal is not essential. Do not claim a specific product flow until you open its implementation.

## 5. Security, privacy, and governance

### Q38. How do authentication and authorization differ?

Authentication establishes who the subject is. Authorization evaluates whether that subject may perform this action on this resource in this clinic. A valid JWT is not enough to view another clinic’s patient; ABAC/resource checks and tenant scope make that decision.

### Q39. How does Docita implement ABAC?

`packages/authorization/src/policies/` contains policies for patients, appointments, prescriptions, invoices, lab orders, and audit logs. They evaluate subject roles/clinic/ownership against resource attributes and return an allow, deny, or not-applicable decision. The policy tests provide evidence for cross-clinic denial.

### Q40. How do you audit patient access?

Patient-PHI access utilities and audit E2E tests record sensitive access. Explain the evidence needed for an investigation—actor, clinic, action, target, request context, and time—then state the limits honestly: retention and legal response depend on confirmed governance policy.

### Q41. How do you keep PHI out of Sentry?

`sentry.utils.ts` redacts PHI from request payloads, query strings, headers, cookies, contexts, tags, extras, breadcrumbs, and messages before send. Preserve error shape and request correlation without sending clinical payloads to an error-tracking vendor.

### Q42. Are you GDPR/HIPAA/DPDP compliant?

“I do not describe the product as certified or legally compliant without a completed assessment. I can describe engineering controls: tenant isolation, ABAC, audit events, consent-related code, PHI-safe telemetry, and secure webhook patterns. Formal obligations, contracts, retention, and breach notification are owned with legal and security stakeholders.”

### Q43. How do you handle consent, deletion, export, and correction?

The code has a `ConsentGuard`, patient-consent hooks, patient export audit actions, and patient deletion actions. The flow is authenticate, authorize, record the action, preserve records required for audit/legal retention, and apply the confirmed data policy. A UI delete is not an erasure claim across backups or logs.

### Q44. How do you handle a suspected breach?

Contain the affected path, preserve evidence, rotate/revoke appropriate credentials, determine impact from audit/operational data, involve the responsible legal/security owners, remediate, and document the outcome. Do not quote a statutory deadline or a recurring drill unless confirmed.

### Q45. How do you validate webhooks?

Verify the provider signature before business processing, deduplicate repeats, process the durable effect transactionally, and make retries safe. Webhook E2E tests cover valid/tampered signatures, duplicate delivery, and CSRF treatment of webhook routes.

### Q46. How do you secure uploads and generated documents?

Authorize and tenant-scope access before upload/download; validate file type/size server-side; use upload/session capabilities only within their intended lifetime; keep PHI out of logs; and confirm storage encryption, malware scanning, and lifecycle policy from production evidence before claiming them.

### Q47. How do you apply OWASP thinking?

Map threats to concrete controls: ABAC/RLS for broken access control, validation and parameter binding for injection, secrets/configuration hygiene, signature verification and dependency review for integrity, and PHI-safe monitoring. Name the code/test for a control rather than listing generic compliance claims.

## 6. Reliability, performance, and observability

### Q48. What performance evidence can you defend?

The repository supports a defensible method: measure p95 and round trips, inspect query shape, identify N+1 work, reduce round trips, and re-measure. Quote a before/after only from a current dashboard or benchmark; source code alone does not prove historical latency.

### Q49. Why p95 instead of average latency?

An average hides the slowest meaningful slice of users. p95 identifies whether clinic staff regularly encounter a slow screen, while p99 exposes tail failures. Pair latency with error rate and actual workflow completion.

### Q50. How do you investigate a slow endpoint?

Start from a correlated request ID and route/tenant-safe logs, check recent deploy and provider health, inspect query count and `EXPLAIN ANALYZE`, then change the smallest bottleneck. Re-measure the same workload; do not add Redis or indexes by reflex.

### Q51. What belongs in a background worker?

Retryable work not required for the immediate response: messaging, generated documents, scheduled work, webhooks, and reconciliation. The API persists durable work; the worker owns attempts, backoff, idempotency, terminal failure, and observability.

### Q52. How do you handle duplicate delivery and poison jobs?

The worker contract includes attempts, fixed/exponential backoff, idempotency keys, DLQ behavior, manual replay metadata, and a bounded replay policy. This provides at-least-once processing with idempotent consumers—not magical exactly-once delivery.

### Q53. How do you monitor health?

Use layered signals: structured request context, Sentry errors/metrics, API health checks, worker/queue state, and domain-level signals such as failed or dead-lettered jobs. Alert thresholds and response commitments are operational policy; verify them before quoting numbers.

### Q54. What is your cache strategy?

Cache only when the value is tenant-scoped, invalidation/fallback behavior is defined, and the database path is understood. Include `clinicId` in the key, invalidate or version around writes, and degrade safely to PostgreSQL. Do not claim a cache implementation or TTL convention without current code evidence.

### Q55. How do you plan backups and recovery?

The repository provides `safe-migrate.sh` with backup/restore paths. A credible production answer includes backup scope, restore testing, RPO/RTO, retention, access control, and owner—but those are operations facts to confirm, not infer from a script.

## 7. CI/CD, infrastructure, and engineering quality

### Q56. Walk through the delivery path.

Start with the repository’s current workflow files: review/CI checks, build/package tasks, migration compatibility checks, deployment configuration for SPA/API/worker, smoke/health verification, and post-deploy monitoring. Do not quote a deployment duration, automatic rollback, or branch policy unless the workflow proves it.

### Q57. Why Turborepo and pnpm?

pnpm manages workspace dependencies; Turborepo models task dependencies and caching across apps/packages. The value is consistent commands and only rebuilding/testing affected surfaces. Explain the actual `turbo.json` task graph instead of claiming a remote-cache provider unless configured.

### Q58. How do you manage environment configuration?

Use `.env.example` for non-secret documentation, validate required runtime configuration at startup, keep production secrets in the deployment platform’s secret mechanism, and avoid logging credentials or sensitive payloads. Confirm provider and rotation process before stating them.

### Q59. Why Fly.io, Cloudflare, Render, and Vercel?

Be precise: the repository supports Cloudflare frontend delivery and Fly.io API/worker deployment; Render is staging exposure and Vercel is prior deployment exposure. Do not collapse all providers into “production” or claim regions, pricing, or scaling behavior you have not verified.

### Q60. How do you roll back safely?

Application code can normally roll back to a prior artifact. Database changes require compatibility planning: expand first, deploy compatible code, backfill/verify, then contract later. A rollback plan must explain data written by the newer version.

### Q61. How do you test the system?

Use unit tests for pure domain logic/policies, integration tests for repositories/transactions, and E2E tests for high-risk HTTP paths such as tenant isolation, idempotency, webhooks, audit access, and authentication. Coverage is useful, but the matrix must target failure modes and authorization boundaries.

### Q62. How do you do code review as a founder?

Review correctness before style: tenant/resource scope, transaction boundaries, idempotency, validation, error paths, migration safety, tests for risky behavior, PHI-safe logs, and whether the change can be observed/rolled back. Ask a reviewer to challenge the trade-off, not merely approve the diff.

## 8. Ownership, behavioral questions, and role fit

### Q63. Why can a founder work well in a team?

Founding experience creates ownership, but a healthy team needs written decisions, early communication of uncertainty, code review, willingness to accept feedback, and shared operational responsibility. Give one genuine example of changing your approach after feedback.

### Q64. How do you handle technical disagreement?

Align on user impact and constraints, make options/trade-offs explicit, run a small experiment when cost is low, document the decision, and revisit it if an assumption changes. Do not frame disagreement as winning an argument.

### Q65. Tell me about a mistake or risky decision.

Use a real example. State the context, your decision, consequence, detection, correction, and prevention mechanism. Never invent an outage, breach, or customer incident.

### Q66. How do you prioritize when everything is urgent?

Protect patient safety/data correctness and active clinic workflows first, then security/regulatory risk, then reversible product work. Make the trade-off visible and define what is intentionally deferred.

### Q67. Why seek a full-time engineering role while working on Docita?

Answer honestly and consistently with your actual arrangement. Focus on contributing in a collaborative engineering environment, learning from a stronger peer group, and owning well-scoped production work end-to-end. Do not promise a part-time/exit arrangement unless already true.

### Q68. How do you show evidence without exposing patient data?

Share a sanitized architecture diagram, aggregate metrics, safe code samples, test names, query-plan summaries, or a controlled walkthrough. Never share patient records, clinic identifiers, credentials, private dashboards, or contracts.

### Q69. What do you know about Python, geospatial/GIS, or a tool not used in Docita?

Be direct: TypeScript/Node/React/PostgreSQL are production strengths. Python is familiarity, not primary production ownership; geospatial/GIS is not a Docita claim. Explain how you would ramp: learn the domain model, make a small tested change, use observability, and request review from a domain expert.

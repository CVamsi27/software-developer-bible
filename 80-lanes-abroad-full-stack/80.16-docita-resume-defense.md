# Prepare a Defensible Docita Walkthrough

[![Role priority](https://img.shields.io/badge/role--priority-Important-blue)](../docs/topic-importance.md)
[![General importance](https://img.shields.io/badge/general--importance-Important-blue)](../docs/topic-importance.md)



An interview answer should distinguish what the source implements, what a deployment enables, and what actually happened. Use this guide to build one current evidence packet; keep personal answers and approved metrics in the [private workspace](personal/README.md).

## First Principles

One user operation crosses several components, but a component’s presence does not establish the whole operation’s guarantee. Following the actual state transition reveals which boundary maintains the invariant and which downstream outcome needs separate evidence.

## Choose one workflow

Start with a real user action, such as booking an appointment. Trace it through the actual implementation rather than reciting a stack:

```text
user action → request validation → tenant and resource authorization
            → business invariant → committed state → downstream work
```

At each arrow, identify the source path, the failure response, and the check that exercises it. A disabled button helps interaction; it does not enforce a booking constraint. Idempotency handles repeated requests; a separate invariant handles different users competing for capacity.

## Separate four kinds of evidence

| Statement | Evidence needed | What it does not establish |
| -------------------------- | ------------------------------------------------------- | ----------------------------------- |
| A control exists | Current source plus a focused check | That every relevant path uses it |
| A control is enabled | Effective runtime configuration and deployment identity | That it succeeds under failure |
| A behavior works | Executed check with environment, result, and date | All production workloads |
| A business result occurred | Approved measurement with period and definition | Your individual causal contribution |

Package versions, model counts, test-file counts, provider configuration, clinic counts, and appointment volumes in older guides are historical leads. Recheck them before using them. A manifest beats outdated prose for dependency declarations; installed resolution and the deployed artifact determine the actual runtime.

## Assemble a small proof packet

| Boundary | Open and explain |
| ------------------- | --------------------------------------------------------------------------- |
| Tenant isolation | Request context, resource policy, database scope, cross-tenant denial check |
| Booking correctness | Capacity invariant, concurrency control, conflicting-request result |
| Durable work | Atomic state/outbox boundary, claim, attempts, recovery, terminal failure |
| Sensitive data | Redaction path, access audit, disclosure limits |
| Delivery | Actual CI job, migration compatibility, deployment and rollback evidence |

Paths previously recorded include `packages/db/prisma/schema.prisma`, `packages/authorization/src/policies/`, `apps/api/src/shared/common/interceptors/tenant-context.interceptor.ts`, and `packages/db/scripts/safe-migrate.sh`. Locate them in the current Docita checkout and follow their callers. They are navigation leads, not a new code audit performed by this guide.

Choose two or three artifacts you can explain deeply. A list of hundreds of checks does not establish which executed, which failed, or whether a release was authorized.

## Explain failures before scale

For tenant scope, check that every database operation uses the scoped transaction and that pooled connections cannot retain another request's context. A row-level security (RLS) flag in a file does not establish effective policies, the runtime role, or coverage of privileged paths.

For asynchronous work, explain what happens after a worker crashes before acknowledgment and after a provider accepts a request before the worker records success. Durable jobs can still be delayed, duplicated, dead-lettered, or expire. Do not promise FIFO, no lost events, or eventual success without the corresponding contract and evidence.

For booking, lock or constrain the shared capacity being contested. Locking different patients does not serialize two requests for the same clinician's slot. Test distinct requests and repeated requests separately.

For telemetry, identifiers and aggregates can remain personal data. Redaction tests reduce risk but do not prove that every sensitive value has been removed from every export.

## Keep hypotheses visibly separate

| Proposed change | Evidence that could justify it |
| ------------------------------ | --------------------------------------------------------------------------------- |
| Add a pooler | Measured connection pressure and compatible session behavior |
| Add a replica | Read workload benefit with acceptable lag and routing |
| Add caching | Repeatable expensive reads, authorization scope, freshness and fallback contract |
| Split into cells | A demonstrated capacity or isolation need plus routing and operational capability |
| Add a disaster-recovery region | Required recovery objective, replication boundary, tested restore and failover |

Clinic count alone cannot prescribe a topology. An asynchronous replica can meet a sub-hour recovery point objective (RPO), the permitted loss of recent data, when lag and recovery behavior support it; synchronous replication is not automatically required. DNS failover alone does not fence an old writer or reconcile lost acknowledged writes.

## Build the answer around your decision

Use **problem → constraint → decision → tradeoff → evidence → next improvement**. Describe your actual contribution and one alternative you rejected for a stated reason. A hypothetical design is useful when labeled as a proposal; it cannot become a past achievement.

Do not infer compliance, certification, an SLA, retention, encryption settings, or recovery objectives from source code. GDPR does not impose a universal EU-only hosting rule. Discuss the actual data, roles, transfer mechanism, and assessed obligations through the [compliance guide](80.24-eu-regulatory-compliance.md).

## Summary

Prepare one workflow trace and a few current artifacts. Keep implementation, deployment, observed behavior, and business outcomes distinct. Rehearse the decision and its failure boundary, then narrow any claim whose evidence is missing.

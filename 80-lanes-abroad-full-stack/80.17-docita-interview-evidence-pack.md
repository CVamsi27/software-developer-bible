# Assemble a Docita Interview Evidence Pack

[![Role priority](https://img.shields.io/badge/role--priority-Important-blue)](../docs/topic-importance.md)
[![General importance](https://img.shields.io/badge/general--importance-Important-blue)](../docs/topic-importance.md)

The [Docita Walkthrough](80.16-docita-resume-defense.md) gives you the narrative flow; this guide helps you assemble **2–3 rock-solid evidence cards** behind your biggest claims so you never get caught hand-waving under technical follow-ups. Keep your complete personal evidence packet in your private workspace, and share only sanitized, synthetic excerpts during interviews.

## First Principles

Code proves an implementation exists; an executed test proves a specific case ran; a production measurement proves a real-world outcome. Each evidence card records **what was checked, where, and what remains outside its scope** so you never accidentally overstate your proof. (Keep synthetic capacity drills like the [hypothetical 25-clinic metrics scenario](../projects/docita/23-hypothetical-clinic-metrics.md) clearly labeled as practice exercises, never production facts.)

## 1. The 5-Line Evidence Card Template

| Field | What to write down |
| ---------------- | -------------------------------------------------------------------------------------- |
| **Claim** | One crisp sentence matching your resume bullet |
| **Source** | Repository, revision or commit, key file path, and callers |
| **Verification** | Exact command or test run, environment, date, outcome, and any skipped or mocked parts |
| **Boundary** | Which users, failures, and concurrency cases it actually proves (and what it does not) |
| **Disclosure** | Confirm zero real patient data, secrets, or restricted infrastructure details appear |

## 2. Three High-Leverage Cards to Build First

| Card | Core proof to gather | Senior follow-up to be ready for |
| --------------------------- | ------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------- |
| **1. Tenant isolation** | Request context setup, database policy, and cross-tenant denial test | Can a join, background worker, privileged role, or pooled connection bypass tenant scope? |
| **2. Booking concurrency** | Capacity constraint or lock plus real-database concurrent booking test | What happens when two *different* users submit overlapping intervals (`10:00–10:30` and `10:15–10:45`)? |
| **3. Durable side effects** | Atomic database and outbox write plus worker claim, retry, and dead-letter queue (DLQ) path | What if the worker crashes *after* the external provider accepts, *before* updating local state? |

Swap in a frontend accessibility, query-optimization, or migration card whenever the target role emphasizes those areas.

## 3. Four Subtle Database and Realtime Traps to Verify Before Interviewing

1. **Equal start time is not overlapping intervals:** `UNIQUE (patient_id, slot_start)` blocks identical starts, **not** overlapping ranges (`10:00–10:30` versus `10:15–10:45`). Standard PostgreSQL `CHECK` constraints cannot inspect other rows; preventing interval overlaps requires exclusion constraints (`EXCLUDE USING gist`) or synchronized capacity locking. ([PostgreSQL constraints](https://www.postgresql.org/docs/current/ddl-constraints.html))
2. **`Promise.all` is not a deterministic concurrency test:** Firing two asynchronous calls in JavaScript does not guarantee they interleave inside the vulnerable Structured Query Language (SQL) window — use explicit synchronization barriers against a real PostgreSQL instance. `READ COMMITTED` permits non-repeatable and phantom reads, while `SERIALIZABLE` requires bounded retry loops on serialization errors (`40001`). ([PostgreSQL transaction isolation](https://www.postgresql.org/docs/current/transaction-iso.html))
3. **Transaction-local Row-Level Security (RLS) under connection pooling:** Always pass tenant IDs via parameterized `set_config('app.tenant_id', $1, true)` (never string-interpolated raw SQL!) and run all protected queries on that same transaction's connection. ([PostgreSQL configuration functions](https://www.postgresql.org/docs/current/functions-admin.html))
4. **Realtime room membership is not payload authorization:** Authorizing a socket to join a clinic room does not mean every user in that room may receive every clinical field — and WebSockets alone never replay missed events after a disconnect without a persisted, authorized cursor.

## 4. Document Capacity and Performance Numbers With Full Context

Never quote an isolated 95th-percentile (`p95`) number without its test environment. When building a performance card (referencing [Deployment Infrastructure](../projects/docita/10-deployment-infrastructure.md), [Analytics & Dashboards](../projects/docita/14-analytics-and-dashboards.md), and [Hypothetical Clinic Metrics](../projects/docita/23-hypothetical-clinic-metrics.md)), keep separate cards for separate boundaries (SQL fixture versus local Hypertext Transfer Protocol (HTTP) runner versus production telemetry) and attach six concrete fields:

| Capacity field | Exact details to record |
| --------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| **Topology** | Replica counts, region, central processing unit (CPU) and random-access memory (RAM), heap flags, cold versus warm state |
| **Database** | Provider and tier, connection limits, storage and index size, pooling mode |
| **Workload** | Synthetic tenant count, endpoints tested, arrival rate, concurrency |
| **Outcomes** | Per-route 50th, 95th, and 99th percentiles (`p50`, `p95`, `p99`), error and timeout rates, correctness checks |
| **Resource pressure** | CPU throttling, heap and event-loop lag, pool waits, database locks, and job backlog |
| **Reproduction** | Exact command, git revision, tool versions, and any excluded routes (for example, health checks) |

## 5. Final Hygiene Check Before Sharing

Verify that synthetic fixtures contain zero real patient IDs, secrets, or proprietary keys. Remember that a backup script is not a tested restore drill, a presigned upload Uniform Resource Locator (URL) does not validate file contents, and a log redactor does not prove complete regulatory compliance. Cross-check every phrasing against [Resume Claim Crosswalk](80.18-resume-claim-crosswalk.md).

## Summary

Back your top 2–3 Docita interview claims with crisp evidence cards tying exact source paths, real executed checks, clear failure boundaries, and complete measurement context — keeping synthetic drills clearly labeled and all real data sanitized.

## 1. Concurrent appointment booking — full-stack deep dive

This is the #1 senior question you will get. Walk through every layer.

### Q: How does Docita handle two clinicians booking the same patient into overlapping slots?

**Answer skeleton:**

"The invariant is: a patient cannot be in two concurrent consultations at the same time. The enforcement is layered:

**DB layer:** The appointment table has a composite unique constraint or a deferred CHECK constraint on `(patient_id, slot_start)` where `status = 'booked'`. When two transactions try to insert overlapping rows, the second one hits a constraint violation and rolls back. PostgreSQL's transaction isolation (SERIALIZABLE or READ COMMITTED with SELECT FOR UPDATE) prevents phantom reads.

**Backend layer:** The booking service wraps the conflict check and insert in a single Prisma `$transaction`. The flow is: (1) acquire a row-level lock on the patient record with `SELECT ... FOR UPDATE`, (2) query existing overlapping appointments within that lock, (3) insert the new appointment, (4) emit an outbox event for downstream notification. If step 2 finds an overlap, the transaction returns a 409 Conflict with a human-readable message.

**Frontend layer:** The booking form disables the submit button on click (duplicate-submit protection). TanStack Query's `onMutate` optimistically updates the calendar view, and `onError` rolls back. If the API returns 409, the UI shows 'This slot was just taken' and refreshes the available slots via `invalidateQueries`.

**Testing:**
- **Unit:** Test the conflict-detection logic in isolation with two simulated appointment objects.
- **Integration:** Use two parallel Prisma transactions in a test harness; the second must throw a unique constraint error.
- **E2E:** Two Playwright browser contexts race to book the same slot; assert one succeeds (201) and one gets 409. Verify the UI refreshes correctly.
- **Load:** k6 script with 50 virtual users booking the same slot simultaneously; assert exactly 1 succeeds, 49 get 409, no deadlocks, no orphaned locks."

**What to show:** The booking service transaction code, the constraint in `schema.prisma`, the E2E test file.

**What NOT to claim:** "We use distributed locking" (it's a single PostgreSQL instance), "exactly-once booking" (it's at-least-once with idempotency), or a specific lock timeout value without evidence.

---

### Q: What about room/bed scheduling conflicts?

**Answer skeleton:**

"The same pattern applies but with a different resource key. A room has capacity constraints (e.g., single-bed rooms are 1:1, shared wards are N:1). The conflict check queries `(room_id, slot_start, slot_end)` with an overlap predicate: `NOT (new.end <= existing.start OR new.start >= existing.end)`. For capacity-based rooms, count active appointments in the slot and compare against room capacity. The transaction still holds the patient lock to prevent double-booking the patient, plus a room-level lock to prevent over-capacity."

---

### Q: How do you test the concurrency path end-to-end?

**Answer skeleton:**

"I use a layered testing strategy:

1. **Contract test:** The booking endpoint's OpenAPI spec declares 409 as a possible response. The contract test verifies the shape.
2. **Deterministic concurrency test:** In a NestJS integration test, start two transactions simultaneously using `prisma.$transaction` with explicit `Promise.all`. One commits first; the other must fail with a known error code.
3. **Browser-level race:** Two Playwright contexts with authenticated sessions hit the same booking endpoint. Use `page.waitForResponse` to synchronize the race. Assert exactly one 201 and one 409.
4. **Regression guard:** The test seeds a clinic with one clinician, one slot, two receptionist users. It is tagged as `@concurrency` in the test suite and runs on every PR that touches the booking flow.
5. **What I do NOT do:** I do not rely on `sleep()` for race conditions. I use `Promise.all` with real concurrent requests. Sleep-based tests are flaky and miss the actual race window."

## 2. Multi-tenant query lifecycle — every API request

### Q: Walk me through what happens to a single API request from the moment it arrives, from a tenancy perspective.

**Answer skeleton:**

"Every request passes through five tenant-aware boundaries:

1. **Authentication (JWT):** The JWT contains `sub` (user ID) and `clinicId`. The auth guard validates the signature, checks expiry, and attaches the payload to the request object. A valid token is necessary but not sufficient — it establishes identity, not authorization.

2. **TenantContextInterceptor:** Reads the authenticated user's `clinicId` from the JWT. Stores `{ userId, clinicId, role }` in a request-scoped context (AsyncLocalStorage or NestJS request object). When RLS is enabled, it opens a Prisma transaction, runs `SET app.current_clinic = '<clinicId>'`, and routes all subsequent Prisma calls through that transaction. Internal users (admin role) get an explicit clinic override — they are not implicitly bypassed.

3. **ABAC policy evaluation:** Before the controller handler executes, the relevant policy in `packages/authorization/src/policies/` evaluates: (a) does the subject have the required role? (b) is the subject's clinic the same as the resource's clinic? (c) does ownership or assignment match? The policy returns ALLOW, DENY, or NOT_APPLICABLE. DENY returns 403 immediately.

4. **Repository/service data access:** The service layer queries PostgreSQL. Every query includes `WHERE clinicId = $1` (explicit or via RLS). The query planner uses the composite index on `(clinicId, ...)` to scope the scan. A missing clinic scope is a bug that the integration tests catch — they seed two clinics and assert cross-clinic denial.

5. **Response filtering:** The response is serialized through a DTO/exclude decorator that strips internal fields (e.g., other clinics' data that might have leaked through a join). This is defense-in-depth, not the primary security boundary."

**What to show:** The interceptor code, a policy file, a test that seeds two clinics and asserts denial.

**What NOT to claim:** "RLS makes cross-tenant access impossible" (it's one layer, not the only layer), "every query goes through RLS" (some internal/admin paths bypass it explicitly).

---

### Q: How does RLS work with Prisma specifically?

**Answer skeleton:**

"Prisma doesn't have native RLS support, so we route RLS-enforced queries through a raw transaction. The flow is:

1. `TenantContextInterceptor` calls `prisma.$transaction(tx => ...)`.
2. Inside the transaction, execute `tx.$executeRawUnsafe('SET app.current_clinic = $1', clinicId)`.
3. All Prisma operations within that transaction execute against the same connection, so PostgreSQL applies the RLS policy defined on the table.
4. The RLS policy is: `CREATE POLICY clinic_isolation ON appointments USING (clinic_id = current_setting('app.current_clinic')::uuid)`.
5. The trade-off: every RLS-enforced request holds a transaction open for its full duration. This increases connection hold time. At current scale it's fine; at 100x we'd need connection pooling tuning or a different isolation strategy."

---

### Q: What happens when an internal admin user accesses a patient from a different clinic?

**Answer skeleton:**

"Internal users have an explicit `INTERNAL_ADMIN` role. The ABAC policy checks: if `role = INTERNAL_ADMIN`, allow access regardless of clinic match — but log the access with a `privilegedAccess: true` flag in the audit trail. The key design decisions: (1) the bypass is explicit in the policy code, not a hidden flag; (2) every privileged access is auditable; (3) the frontend still respects clinic scope — the internal app has a clinic-switcher that sets the request context, so the admin explicitly chooses which clinic they're operating in."

## 3. Security and auth system deep-dive

### Q: Explain the full auth architecture.

**Answer skeleton:**

"Three layers: authentication, authorization, and audit.

**Authentication:** JWT-based. Login endpoint validates credentials against bcrypt-hashed passwords, returns a short-lived access token (15min) and a refresh token (7 days, httpOnly cookie). The access token contains `sub`, `clinicId`, `role`, `iat`, `exp`. Token validation happens in a global guard; no route is unprotected by default.

**Authorization:** Two tiers:
- **Role-based (coarse):** Eight roles in the enum — PATIENT, RECEPTIONIST, CLINICIAN, LAB_TECHNICIAN, PHARMACIST, BILLING_ADMIN, CLINIC_ADMIN, INTERNAL_ADMIN. The role determines which routes a user can even see.
- **ABAC (fine-grained):** Policies in `packages/authorization/src/policies/` evaluate subject attributes (role, clinic, ownership) against resource attributes (clinic_id, created_by, assigned_to). A CLINICIAN can only view their own assigned patients. A RECEPTIONIST can book appointments but cannot view clinical notes. The policy engine is extensible — adding a new resource means writing one policy file and its tests.

**Audit:** Patient-PHI access is logged with actor, action, resource, clinic, timestamp, and request context. The audit records are append-only. The audit E2E tests verify that accessing a patient from a different clinic produces a denial AND that the denial is logged."

---

### Q: How do you handle token refresh and session management?

**Answer skeleton:**

"Access tokens are short-lived (15 min). When they expire, the client uses the refresh token (httpOnly cookie, 7-day expiry) to get a new access token. The refresh endpoint: (1) validates the refresh token signature and expiry, (2) checks it hasn't been revoked (token family tracking), (3) issues a new access token and rotates the refresh token. If a stolen refresh token is used after rotation, the old family is invalidated — this limits the blast radius of token theft. On logout, both tokens are revoked server-side."

---

### Q: How do you secure file uploads in a healthcare context?

**Answer skeleton:**

"The upload flow: (1) the client requests a pre-signed upload URL from the API, (2) the API validates the requestor's authorization (must be a clinic member with upload permission), generates a time-limited pre-signed URL scoped to a specific storage path, and returns it, (3) the client uploads directly to storage (S3/R2) using the pre-signed URL — the API never touches the file bytes, (4) the client confirms upload completion, the API validates the file metadata (size, type) against policy, and creates a database record linking the file to the patient/appointment. Key security points: (a) the pre-signed URL expires in 5 minutes, (b) the storage path includes the clinic ID and a UUID — no sequential or guessable paths, (c) file type is validated server-side by magic bytes, not just MIME type, (d) PHI-containing files are never logged, (e) download URLs are also pre-signed and time-limited."

---

### Q: How do you prevent IDOR (Insecure Direct Object Reference) vulnerabilities?

**Answer skeleton:**

"IDOR prevention is the intersection of tenant isolation and ABAC. Every resource access goes through: (1) the resource's clinic_id is checked against the requestor's clinic_id (tenant boundary), (2) the resource's ownership/assignment is checked against the requestor's identity (ownership boundary), (3) the resource's type is checked against the requestor's role (role boundary). The E2E tests specifically seed two clinics with overlapping resource IDs (same UUID pattern) and assert cross-clinic denial. The key insight: UUIDs are not a security boundary — they're hard to guess but not impossible. The real boundary is the policy check."

## 4. Toughest decisions and trade-offs

### Q: What was the hardest technical decision you made?

**Option A — Shared-schema tenancy vs database-per-tenant:**

"I chose shared-schema tenancy. The operational argument was strong at 25 clinics: one migration, one connection pool, one backup, one monitoring setup. Database-per-tenant would mean 25 schemas to migrate, 25 connection pools to manage, and 25 restore procedures. The risk is cross-tenant data leakage, which I mitigate with explicit ABAC policies, clinic-scoped queries, RLS, and cross-clinic E2E tests. The trade-off I accept: a single misconfigured query could expose data across clinics. The trade-off I reject: the operational overhead of per-tenant databases at this scale. If we hit 500+ clinics or regulatory requirements demand physical isolation, I would revisit with a migration strategy."

**Option B — Outbox pattern vs direct provider calls:**

"I chose the outbox pattern for anything that touches external providers (email, SMS, document generation). The problem: if the API sends an email and the provider is down, the request fails and the user sees an error — but the appointment was already created. With the outbox: the API creates the appointment AND an outbox event in one transaction. The worker picks up the event and retries the provider call with exponential backoff. The trade-off: the user doesn't get immediate confirmation that the email was sent. The benefit: the appointment is never lost, and the email eventually goes out. I would switch to direct calls only if the provider guaranteed <100ms uptime — which none do."

**Option C — Vite SPA vs Next.js SSR:**

"The clinician dashboard is a stateful SPA, not a content site. Vite gives me fast builds, explicit client-side routing, and no server-rendering complexity. The trade-off: no SEO for the dashboard (irrelevant — it's behind auth), no server-side data loading (I use TanStack Query with explicit cache management), and no edge rendering (Cloudflare handles static asset delivery). If Docita ever needs a patient-facing portal with SEO, I would add a separate Next.js app, not retrofit the SPA."

### Q: How do you balance speed and correctness in a healthcare product?

**Answer skeleton:**

"I use a risk-based approach. Patient safety and data correctness are non-negotiable — I will not ship a booking feature without the concurrency test, even if it means slipping a day. UI polish and nice-to-have integrations can ship with known debt if the debt is documented and tracked. The mental model: 'Could this bug cause a patient to receive the wrong medication? Then it blocks. Could this bug cause a button to be misaligned? Then it ships with a ticket.' I make the trade-off explicit in PR descriptions and sprint notes so the team knows what is intentionally deferred."

## 5. Senior-level system design topics

### Q: How would you design the appointment scheduling system from scratch?

**Answer skeleton:**

"The core entities: Clinic, Practitioner, Patient, Appointment, Slot, Room. The invariants: (1) a patient cannot be in two concurrent appointments, (2) a practitioner cannot have overlapping appointments, (3) a room cannot exceed capacity, (4) all access is clinic-scoped.

**Write path:** The booking API acquires locks in a consistent order (patient → practitioner → room) to prevent deadlocks. Inside a transaction: check patient overlap, check practitioner overlap, check room capacity, insert appointment, emit outbox event for notifications. If any check fails, the transaction rolls back and returns a specific error.

**Read path:** The calendar view uses a composite index on `(clinic_id, practitioner_id, slot_start)` and returns available slots by subtracting booked slots from the practitioner's working hours. The query is: `SELECT * FROM slots WHERE clinic_id = $1 AND practitioner_id = $2 AND slot_start BETWEEN $3 AND $4 AND id NOT IN (SELECT slot_id FROM appointments WHERE status = 'booked' AND ...)`.

**Optimizations:** Cache the practitioner's weekly schedule (invalidated on booking/cancellation). Use cursor pagination for appointment lists. Precompute 'available slots' as a materialized view for high-traffic clinics.

**Scaling:** At 10x, the bottleneck is the lock contention on popular practitioners. Solutions: partition the lock by time window (hourly locks instead of session-wide), or use optimistic concurrency with a version column and retry."

---

### Q: How would you design the notification system?

**Answer skeleton:**

"Notifications are triggered by outbox events. The flow: (1) a business action (appointment booked, prescription ready) creates an outbox event in the same transaction, (2) the worker polls the outbox table, (3) for each event, the worker determines the notification channel (in-app, email, SMS) based on user preferences and event type, (4) the worker calls the provider (SendGrid, Twilio, or internal WebSocket) with retry and idempotency, (5) on success, the outbox event is marked as processed; on terminal failure, it's moved to DLQ.

**Design decisions:**
- **In-app notifications:** Stored in a `notifications` table with `clinic_id`, `user_id`, `type`, `payload`, `read_at`. Queried with the same tenant scope. Real-time delivery via WebSocket scoped to the clinic room.
- **Email/SMS:** Provider calls with idempotency keys. The same appointment booked twice produces one notification (deduplication by event ID).
- **Preferences:** Users can opt out of SMS but not in-app notifications (clinical safety). Preferences are stored per-user, not per-clinic.
- **Retry:** Exponential backoff with jitter. Max 5 attempts. DLQ for manual investigation. The worker dashboard shows DLQ depth as a health signal."

### Q: How would you handle a multi-region deployment?

**Answer skeleton:**

"At current scale (25 clinics), multi-region is not justified. But if we needed it: (1) each region gets its own PostgreSQL primary with read replicas, (2) the API and worker are deployed per-region, (3) patient data is pinned to the clinic's region (data residency), (4) cross-region reads are eventually consistent via read replicas, (5) writes are always to the region's primary. The hard part is migration: schema changes must be applied to all region primaries in a compatible order. The approach: expand/contract with backward-compatible code, deploy to all regions, then contract."

---

### Q: How would you implement real-time updates for the clinic dashboard?

**Answer skeleton:**

"WebSocket connections are authenticated and scoped to a clinic room. The flow: (1) the client connects with a JWT, (2) the gateway validates the token and joins the client to the `clinic:{clinicId}` room, (3) when an appointment is booked/cancelled, the API publishes an event to the clinic room via the WebSocket gateway, (4) the client receives the event and updates the calendar view via TanStack Query's `setQueryData` or `invalidateQueries`.

**Failure modes:** (1) If the WebSocket disconnects, the client falls back to polling every 30s. (2) If the WebSocket server restarts, clients reconnect with the last known event ID and receive missed events (event sourcing on the notification table). (3) If two clinicians book simultaneously, both events arrive and the UI merges them — the calendar is a projection, not a source of truth."

### Q: How do you handle database migrations in production without downtime?

**Answer skeleton:**

"The expand/contract pattern: (1) **Expand:** Add new columns/tables without removing old ones. Deploy code that writes to both old and new schema. (2) **Backfill:** Migrate existing data from old to new schema in batches. (3) **Verify:** Run consistency checks comparing old and new data. (4) **Contract:** Deploy code that reads only from new schema. Remove old columns in a later migration.

**The tooling:** `safe-migrate.sh` wraps Prisma migrations with: (a) backup before migration, (b) dry-run on staging, (c) deploy to production with health check, (d) automatic restore if health check fails. The key insight: application rollback is easy (redeploy the old image), but database rollback is hard (you can't un-migrate). So the migration must be forward-compatible — the old code must work with the new schema."

## 6. Cross-cutting senior topics

### Q: How do you approach observability in a healthcare SaaS?

**Answer skeleton:**

"Three pillars, scoped by tenant: (1) **Logs:** Structured JSON with request ID, user ID, clinic ID, action, duration. PHI is scrubbed before emission — the Sentry redactor removes request bodies, query strings, headers, cookies, and message content. (2) **Metrics:** Request latency (p50/p95/p99), error rate by endpoint, queue depth, worker processing time. All metrics are tenant-scoped so we can debug 'clinic X is slow' without guessing. (3) **Traces:** Request ID flows from API to worker to provider calls. A slow booking can be traced from the HTTP request through the Prisma transaction through the outbox write through the worker's email send.

**The healthcare constraint:** PHI must never appear in logs, metrics, or traces. This means no patient names in log messages, no appointment details in metric tags, no prescription content in trace spans. The redactor is tested — there are E2E tests that trigger an error and assert the Sentry payload contains no PHI."

---

### Q: How do you handle data export and deletion (GDPR/privacy)?

**Answer skeleton:**

"The code has patient export and deletion actions. Export produces a structured JSON bundle of the patient's records (appointments, prescriptions, invoices, audit logs). Deletion soft-deletes the patient record and hard-deletes associated media files. The key design decisions: (1) audit logs are retained separately from patient records — deleting a patient does not delete the audit trail of who accessed their data, (2) the deletion is idempotent — calling it twice does not fail, (3) the export is scoped to the clinic — a clinic admin can only export their own patients.

**What I cannot claim:** That this constitutes GDPR compliance. Legal compliance requires a Data Protection Impact Assessment, a Record of Processing Activities, a legal basis for each processing activity, breach notification procedures, and a DPO. The code provides technical controls; the legal framework is a separate workstream."

### Q: How do you think about testing strategy for a healthcare product?

**Answer skeleton:**

"The testing pyramid, adapted for healthcare:

1. **Unit tests (60%):** Pure domain logic — conflict detection, date arithmetic, price calculation, policy evaluation. Fast, deterministic, no external dependencies.

2. **Integration tests (25%):** Repository queries, transaction boundaries, Prisma operations, queue behavior. Use a test database (Docker PostgreSQL) with seeded data. These catch the 'this query works in isolation but breaks in a transaction' bugs.

3. **E2E tests (15%):** High-risk HTTP paths — tenant isolation (cross-clinic denial), idempotency (double-submit), webhook verification (valid/tampered/duplicate), audit logging (PHI access is recorded), authentication (expired/revoked tokens). Playwright for UI flows that involve multi-step booking or form submission.

4. **What I do NOT test in E2E:** CRUD operations that are covered by integration tests, pure UI rendering (covered by component tests), third-party provider behavior (mocked).

**The healthcare-specific tests:** (a) Cross-clinic denial: seed two clinics, assert Clinic A cannot read Clinic B's patients. (b) PHI scrubbing: trigger an error, assert Sentry payload contains no patient data. (c) Audit completeness: access a patient, assert the audit record exists with the correct actor/action/resource. (d) Idempotency: submit the same booking twice, assert exactly one appointment is created."

## 7. Behavioral questions — senior-level framing

### Q: Tell me about a time you had to make a decision with incomplete information.

**Answer skeleton (adapt Story 1 or 5):**

"The decision was shared-schema vs database-per-tenant for Docita. I had incomplete information: I didn't know the eventual clinic count, regulatory requirements, or performance characteristics. I chose shared-schema because: (1) the operational cost of per-tenant databases was certain and high, (2) the risk of cross-tenant leakage was mitigatable with code-level controls, (3) migrating from shared to per-tenant later is feasible (add clinic_id to every query, then partition). The key was making the decision reversible — I didn't lock into a physical separation that would be hard to undo."

### Q: How do you handle technical disagreement?

**Answer skeleton:**

"I align on user impact and constraints first. Then I make options and trade-offs explicit — not 'I think X is better' but 'Option A costs X and gets Y, Option B costs P and gets Q.' I have changed my mind in code review when a reviewer showed me a failure mode I hadn't considered — that's a feature, not a weakness."

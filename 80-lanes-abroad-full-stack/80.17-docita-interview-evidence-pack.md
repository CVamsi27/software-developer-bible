# Assemble a Docita Interview Evidence Pack

[![Role priority](https://img.shields.io/badge/role--priority-Important-blue)](../docs/topic-importance.md)
[![General importance](https://img.shields.io/badge/general--importance-Important-blue)](../docs/topic-importance.md)

The [Docita Walkthrough](80.16-docita-resume-defense.md) gives you the narrative flow; this guide helps you assemble **2–3 rock-solid evidence cards** behind your biggest claims so you never get caught hand-waving under technical follow-ups. Keep your complete personal evidence packet in your private workspace, and share only sanitized, synthetic excerpts during interviews.

## First Principles

Code proves an implementation exists; an executed test proves a specific case ran; a production measurement proves a real-world outcome. Each evidence card records **what was checked, where, and what remains outside its scope** so you never accidentally overstate your proof. (Keep synthetic capacity drills like the [hypothetical 25-clinic metrics scenario](../projects/docita/23-hypothetical-clinic-metrics.md) clearly labeled as practice exercises, never production facts.)

## 1. The 5-Line Evidence Card Template

| Field | What to write down |
| ---------------- | -------------------------------------------------------------------------------------- |
| **Claim** | One crisp sentence matching your resume bullet |
| **Source** | Repo, revision/commit, key file path, and callers |
| **Verification** | Exact command/test run, environment, date, outcome, and any skipped/mocked parts |
| **Boundary** | Which users, failures, and concurrency cases it actually proves (and what it does not) |
| **Disclosure** | Confirm zero real patient data, secrets, or restricted infra details appear |

## 2. Three High-Leverage Cards to Build First

| Card | Core proof to gather | Senior follow-up to be ready for |
| --------------------------- | ------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------- |
| **1. Tenant isolation** | Request context setup + DB policy + cross-tenant denial test | Can a join, background worker, privileged role, or pooled connection bypass tenant scope? |
| **2. Booking concurrency** | Capacity constraint/lock + real-DB concurrent booking test | What happens when two *different* users submit overlapping intervals (`10:00–10:30` and `10:15–10:45`)? |
| **3. Durable side effects** | Atomic DB + outbox write + worker claim/retry/DLQ path | What if the worker crashes *after* the external provider accepts, *before* updating local state? |

Swap in a frontend accessibility, query-optimization, or migration card whenever the target role emphasizes those areas.

## 3. Four Subtle Database & Realtime Traps to Verify Before Interviewing

1. **Equal start time != overlapping intervals:** `UNIQUE (patient_id, slot_start)` blocks identical starts, **not** overlapping ranges (`10:00–10:30` vs. `10:15–10:45`). Standard PostgreSQL `CHECK` constraints cannot inspect other rows; preventing interval overlaps requires exclusion constraints (`EXCLUDE USING gist`) or synchronized capacity locking. ([PostgreSQL constraints](https://www.postgresql.org/docs/current/ddl-constraints.html))
2. **`Promise.all` != deterministic concurrency test:** Firing two async calls in JS does not guarantee they interleave inside the vulnerable SQL window — use explicit synchronization barriers against a real PostgreSQL instance. Remember `READ COMMITTED` permits non-repeatable/phantom reads, while `SERIALIZABLE` requires bounded retry loops on serialization errors (`40001`). ([PostgreSQL transaction isolation](https://www.postgresql.org/docs/current/transaction-iso.html))
3. **Transaction-local RLS under connection pooling:** Always pass tenant IDs via parameterized `set_config('app.tenant_id', $1, true)` (never string-interpolated raw SQL!) and run all protected queries on that same transaction's connection. ([PostgreSQL configuration functions](https://www.postgresql.org/docs/current/functions-admin.html))
4. **Realtime room membership != payload authorization:** Authorizing a socket to join a clinic room does not mean every user in that room may receive every clinical field — and WebSockets alone never replay missed events after a disconnect without a persisted, authorized cursor.

## 4. Document Capacity & Performance Numbers With Full Context

Never quote an isolated p95 number without its test environment. When building a performance card (referencing [Deployment Infrastructure](../projects/docita/10-deployment-infrastructure.md), [Analytics & Dashboards](../projects/docita/14-analytics-and-dashboards.md), and [Hypothetical Clinic Metrics](../projects/docita/23-hypothetical-clinic-metrics.md)), keep separate cards for separate boundaries (SQL fixture vs. local HTTP runner vs. production telemetry) and attach six concrete fields:

| Capacity field | Exact details to record |
| --------------------- | ----------------------------------------------------------------------------------------- |
| **Topology** | Replica counts, region, CPU/RAM, heap flags, cold vs. warm state |
| **Database** | Provider/tier, connection limits, storage/index size, pooling mode |
| **Workload** | Synthetic tenant count, endpoints tested, arrival rate, concurrency |
| **Outcomes** | Per-route p50/p95/p99, error/timeout rates, correctness checks |
| **Resource pressure** | CPU throttling, heap/event-loop lag, pool waits, DB locks & job backlog |
| **Reproduction** | Exact command, git revision, tool versions, and any excluded routes (e.g., health checks) |

## 5. Final Hygiene Check Before Sharing

Verify that synthetic fixtures contain zero real patient IDs, secrets, or proprietary keys. Remember that a backup script is not a tested restore drill, a presigned upload URL does not validate file contents, and a log redactor does not prove complete regulatory compliance. Cross-check every phrasing against [Resume Claim Crosswalk](80.18-resume-claim-crosswalk.md).

## Summary

Back your top 2–3 Docita interview claims with crisp evidence cards tying exact source paths, real executed checks, clear failure boundaries, and complete measurement context — keeping synthetic drills clearly labeled and all real data sanitized.

# Resume Claim Crosswalk

[![Role priority](https://img.shields.io/badge/role--priority-Important-blue)](../docs/topic-importance.md)
[![General importance](https://img.shields.io/badge/general--importance-Important-blue)](../docs/topic-importance.md)



Before submitting a résumé, connect each material claim to evidence that supports its exact wording. Keep the actual CV, approved figures, employment facts, and private artifacts in the [canonical personal workspace](personal/README.md). This public guide describes the method rather than declaring an August or September snapshot to be current.

## First Principles

The words in a resume can outlive the code revision or measurement that supported them. A claim crosswalk must retain its source, date and verification state; an old supported claim does not automatically describe current behavior.

## Work from the sentence, not the stack

Consider “I improved the appointment-list response time.” That sentence needs an actual contribution and comparable before/after observations. A database index in the source shows an implementation; it cannot establish historical latency or who caused the improvement.

```text
claim → supporting artifact → date and scope → uncertainty → defensible wording
```

A useful claim does not need a number. “Implemented tenant-scoped resource authorization” can be precise when a change and its tested boundary support it. Adding an unsupported percentage makes it weaker.

## Use a compact evidence table

| Claim type | Evidence to attach | Wording boundary |
| ---------------------------- | ------------------------------------------------------------------ | ----------------------------------------------------------------- |
| Owned an implementation | Change history, role, relevant source and checks | Identify your contribution rather than claiming all project work |
| Improved performance | Comparable workload, environment, percentile, errors, before/after | Separate a local benchmark from production measurements |
| Served users or workflows | Approved report, period, definition, disclosure permission | Booked appointments and completed visits are different measures |
| Enforced a security boundary | Actual enforcement path and denial checks | A policy file or configuration flag alone is insufficient |
| Operated a service | Deployment identity, operational records, responsibilities | Source configuration does not establish production behavior |
| Eligible for a work route | Current route, qualifications, offer and salary conditions | Eligibility is conditional and is not existing work authorization |

Record the table alongside the actual private CV. Keep missing evidence visible while gathering it; remove or narrow the claim if the gap remains. Do not fabricate a metric simply to fit a résumé formula.

## Review common overclaims

| Proposed phrase | What to verify or change |
| ------------------------------- | ----------------------------------------------------------------------------------------------------------- |
| “RLS in production” | Effective policies, runtime roles, bypass behavior, transaction scope and denial evidence |
| “Immutable audit trail” | Whether enforcement is application-only or database-enforced, plus privileged mutation paths |
| “AI spend capped” | Atomic reservation, concurrency, retries, failures, and fail-open behavior |
| “Exactly-once notifications” | Remote idempotency or reconciliation across acceptance and acknowledgment failures |
| “Compliant healthcare platform” | Assessed obligations and governance evidence; engineering controls alone are narrower |
| “Hundreds of tests” | Cases versus files, actual execution, result, skips and relevant failure coverage |
| “No sponsorship required” | The actual immigration route and employer paperwork; do not imply a binding offer alone completes admission |

Framework names and repository counts can help orientation, but should not substitute for a decision or result. If a count matters, attach a reproducible method and date. Historical counts in project notes are not a current count of a different checkout.

## Match the evidence to the interview

Choose one implementation boundary, one measured or otherwise evidenced outcome, and one genuine ownership decision that relate to the role. Follow the [walkthrough guide](80.16-docita-resume-defense.md) to trace the mechanism. Use [behavioral preparation](80.04-behavioral-eu-style.md) to explain your action without inventing incidents or team arrangements.

Check the rendered CV and any generated PDF against the approved source after changes. An old document saying “matches both PDFs” does not verify the current files. Share sanitized artifacts with appropriate permission, never raw patient records, secrets, or private contracts.

## Summary

Make each claim no broader than its evidence. Dates, measurement definitions, and contribution boundaries make an answer easier to defend; an unsupported number does not.

# Langfuse Product Engineering Preparation

[![Role priority](https://img.shields.io/badge/role--priority-Important-blue)](../docs/topic-importance.md)
[![General importance](https://img.shields.io/badge/general--importance-Important-blue)](../docs/topic-importance.md)

When preparing for an AI developer-tools or LLM-observability product team like **Langfuse**, memorizing a generic list of frameworks misses what actually makes the product hard. Langfuse focuses on **LLM tracing, prompt management, and evaluations** ([official docs](https://langfuse.com/docs)) and announced **joining ClickHouse** ([company announcement](https://langfuse.com/blog/joining-clickhouse)). Use this guide as a worked blueprint for studying one core product workflow — while confirming the live opening's stack, team, compensation, and loop directly with the recruiter.

## First Principles

An LLM request can return `HTTP 200` in 400 milliseconds and still give the user a hallucinated or unsafe answer. Observability for AI apps therefore connects three separate signals: **what executed (the trace)**, **what it cost/took (tokens & latency)**, and **whether the output was actually right (evaluations & human feedback)**.

## 1. Trace One LLM Request Through the Product

Follow a realistic user query through retrieval, generation, and evaluation:

```text
Trace (user request)
  ├─ Span: Retrieval    ─► retrieved chunk IDs, tenant scope, latency_ms
  ├─ Generation: LLM    ─► prompt_name@version, model, input/cached/output tokens, cost, ttft_ms
  └─ Score: Evaluation  ─► rule check + rubric score + human feedback (with method & limits)
```

**Key insight to surface in interviews:** Lower latency after a prompt tweak is **not** automatically an improvement — the faster prompt might have dropped citations or increased hallucinations. Quality, latency, and unit cost must always be evaluated together on comparable workloads.

## 2. Six High-Value Engineering Boundaries to Prepare

Use these boundaries to anchor technical conversations (always verify Langfuse's current open-source implementation in the [official repo](https://github.com/langfuse/langfuse) and [self-hosting docs](https://langfuse.com/self-hosting) rather than assuming outdated blog posts):

| Product boundary | Senior engineering trade-offs to be ready to discuss |
| ---------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| **SDK export (client/server)** | Bounded in-memory queue, batching, retry classification, graceful flush on shutdown, and drop policy so tracing never crashes the host app |
| **High-volume ingestion** | Project API-key auth, payload size caps, idempotent event deduplication, and backpressure under burst traffic |
| **Transactional vs. analytical storage** | Separating low-latency project metadata/config from high-volume append-only trace analytics, updates, and retention |
| **Dashboard queries** | Enforcing `project_id` authorization on every query, cursor pagination, filter selectivity, and acceptable data freshness |
| **Prompt versioning** | Linking every production generation to an immutable prompt version and comparing variants against a held-out eval dataset |
| **Sensitive payloads (PII/PHI)** | Opt-in redaction/masking before ingestion, strict access control, retention windows, and real deletion workflows |

## 3. Study One Real Source Path & Connect Your Own Experience Honestly

Instead of skimming 17 random topics, open one concrete path in the repo (an ingestion handler, an eval pipeline, or a dashboard query), inspect its validation, authorization, and storage calls, and try running the documented local setup if feasible.

Connect the product's challenges back to real systems **you** have owned — for example, linking durable background queues to SDK batching/ingestion, tenant isolation to project scoping, or query tuning to dashboard filtering. Be transparent about what differs (e.g., if you have not operated ClickHouse at petabyte scale yet), and never treat open-source PRs as a guaranteed interview shortcut.

## Summary

Anchor preparation for an LLM-observability product in one end-to-end trace (execution + cost/latency + quality evaluation), study its core ingestion, storage, authorization, and privacy trade-offs directly against official docs and source, and connect your own production engineering experience honestly without overclaiming.

## 1. Turborepo & Monorepo Architecture

### Q1. Explain Turborepo and its role in a monorepo. How does it differ from Lerna or Yarn workspaces?

**Answer:** Turborepo is a build system and monorepo manager that orchestrates builds across multiple packages with intelligent caching and parallelization.

```json
// turbo.json
{
  "tasks": {
    "build": {
      "outputs": ["dist/**"],
      "cache": true,
      "dependsOn": ["^build"]
    },
    "test": { "cache": false, "dependsOn": ["build"] }
  }
}
```

| Feature | Turborepo | Lerna | Yarn Workspaces |
|---------|-----------|-------|-----------------|
| Caching | Content-based | No | No |
| Parallel | Yes | Limited | Yes |
| Remote caching | Yes | No | No |
| Publishing | No (use npm) | Yes | No |
| Incremental | Yes | Limited | No |

### Q2. How would you structure a monorepo with multiple packages (frontend, backend, SDKs) in Turborepo?

**Answer:**
```
langfuse/
├── packages/
│ ├── core/ # Shared types (Trace, Span, ScoreEvent)
│ ├── web/ # Next.js frontend
│ ├── api/ # Express backend
│ ├── sdk-js/ # JavaScript SDK
│ ├── sdk-python/ # Python SDK
│ └── ui/ # Shadcn/UI shared components
├── turbo.json
├── tsconfig.json
└── package.json # { "workspaces": ["packages/*"] }
```

### Q3. What is task caching in Turborepo? How does it improve build times?

**Answer:** Turborepo hashes inputs (source files, config, dependencies, env vars) and skips re-execution if the hash matches. Local cache in `node_modules/.cache/turbo/`, remote cache via Vercel.

```bash
# First run: 20s (all cache miss)
# Second run: <1s (all cache hit)
# With remote cache: 5s (just download)
```

### Q4. How do you handle shared types/utilities across packages?

**Answer:** Dedicated `@langfuse/core` package with `workspace:*` dependency. TypeScript strict mode. Export only public API.

### Q5. Explain Turborepo's lockfile strategy.

**Answer:** Single `pnpm-lock.yaml` for all packages. pnpm uses hardlinks for dependencies (saves space). `workspace:*` resolves locally, resolves to version at publish time.

## 2. tRPC (Type-Safe APIs)

### Q6. What is tRPC and how does it differ from REST/GraphQL?

**Answer:** tRPC provides end-to-end type safety without schema generation or code generation. Types are inferred from procedure definitions.

```typescript
// Server: define procedure
const router = t.router({
  traces: t.router({
    getWithSpans: t.procedure
      .input(z.object({ traceId: z.string() }))
      .query(async ({ input }) => {
        return db.trace.findUnique({ where: { id: input.traceId }, include: { spans: true } });
      })
  })
});

// Client: fully typed automatically
const trace = await trpc.traces.getWithSpans.query({ traceId: '123' });
// trace.spans — autocomplete works, TypeScript knows the shape
```

### Q7. Explain tRPC's type inference. End-to-end type safety?

**Answer:** Server exports `typeof router` as `AppRouter`. Client imports this type. Any schema change on server → compile error on client. No runtime surprises.

### Q8. How would you structure a tRPC router for a complex application?

**Answer:** Domain-based sub-routers (users, traces, spans, analytics, scores) composed into `appRouter`. Each sub-router owns its Zod schemas.

### Q9. What are tRPC middleware? Auth middleware?

**Answer:** Middleware runs before procedures. Can modify context or enforce conditions:

```typescript
const isAuthenticated = t.middleware(async (opts) => {
  const token = opts.ctx.req?.headers.authorization?.split(' ')[1];
  if (!token) throw new TRPCError({ code: 'UNAUTHORIZED' });
  const payload = jwt.verify(token, JWT_SECRET);
  return opts.next({ ctx: { ...opts.ctx, userId: payload.userId } });
});

const protectedProcedure = t.procedure.use(isAuthenticated);
```

### Q10. File uploads in tRPC? Streaming responses?

**Answer:** Presigned S3 URLs for uploads. WebSocket subscriptions for streaming.

### Q11. Error handling in tRPC?

**Answer:** Custom error classes extending `TRPCError`. Client-side `TRPCClientError` handling with code matching.

### Q12. Real-time subscriptions in tRPC?

**Answer:** WebSocket-based subscriptions using `observable`. Event emitter pattern for trace/span updates. Buffer + flush for batch updates.

### Q13. tRPC procedure API — query, mutation, subscription?

**Answer:** `query()` = read (GET), `mutation()` = write (POST), `subscription()` = real-time (WebSocket). Input validated with Zod schemas.

## 3. Next.js Advanced

### Q14-Q20. App Router vs Pages Router, Server Components, data fetching, ISR, Suspense, Middleware

**Key answers:**
- **Server Components** = render on server, send HTML. No client JS. Use for data fetching, static content.
- **Client Components** = `'use client'` directive. Use for interactivity, browser APIs.
- **Server Actions** = functions called from forms/client code. Run on server. No API endpoint needed.
- **ISR** = `revalidate: 60` in `fetch()`. Stale-while-revalidate pattern.
- **Middleware** = runs on Edge. Auth, redirects, geolocation, A/B testing.

## 4. Express Advanced

### Q21-Q25. Middleware execution, request validation, streams, rate limiting

**Key answers:**
- Middleware executes in order (top to bottom). Error middleware has 4 params `(err, req, res, next)`.
- Validate with Zod at the boundary. Parse once, use everywhere.
- Use streams for large file downloads. `pipeline()` for backpressure handling.

## 5. Prisma ORM at Scale

### Q26-Q33. Schema design, migrations, query optimization, transactions, connection pooling

**Key answers:**
- **N+1 prevention:** Use `include` or `select` with joins. Never loop and query.
- **Migrations:** `prisma migrate dev` for local, `prisma migrate deploy` for production.
- **Connection pooling:** `connection_limit` in datasource. For serverless: use Prisma Accelerate or PgBouncer.
- **Transactions:** Interactive transactions for multi-step operations. Batch for independent writes.

## 7. Observability & OpenTelemetry

### Q40-Q48. Three pillars, spans, context propagation, instrumentation

**Key answers:**
- **Three pillars:** Logs (what happened), Metrics (how much), Traces (request flow).
- **OpenTelemetry:** Vendor-neutral SDK. Instrument once, export to any backend.
- **Spans:** Start time, end time, attributes, events, status. Parent-child relationships.
- **Context propagation:** W3C Trace Context header (`traceparent`). Automatic in OTel SDK.
- **Sampling:** Head-based (1% at SDK), tail-based (100% errors + slow at collector).

## 9. ClickHouse (Analytics Database)

### Q59-Q66. OLAP vs OLTP, table engines, schema design, partitioning, replication

**Key answers:**
- **OLAP vs OLTP:** ClickHouse = column-oriented, append-heavy, fast aggregations. PostgreSQL = row-oriented, transactional.
- **MergeTree engine:** Ordered data, background merges, efficient compression.
- **Partitioning:** By time range (monthly). Primary key = sort order (not unique).
- **Schema for traces:** `MergeTree PARTITION BY toYYYYMM(timestamp) ORDER BY (project_id, trace_id, timestamp)`.
- **Batch inserts:** Use Buffer table or batch every 1-5 seconds.

## 10. Redis (Caching & Sessions)

### Q67-Q74. Data structures, caching strategies, rate limiting, persistence, failover

**Key answers:**
- **Data structures:** Strings (cache), Hashes (objects), Sorted Sets (leaderboards), Lists (queues), Sets (unique items).
- **Cache strategies:** Cache-aside (read: check Redis → fallback to DB → write to Redis). Write-through, write-behind.
- **Rate limiting:** Sliding window with `ZRANGEBYSCORE` or fixed window with `INCR` + `EXPIRE`.
- **Persistence:** RDB (snapshot, fast restore), AOF (every write, better durability), both (recommended).

## 11. PostgreSQL (Aurora)

### Q75-Q84. Read replicas, serverless, EXPLAIN ANALYZE, JSONB, window functions, CTEs, partitioning, full-text search

**Key answers:**
- **EXPLAIN ANALYZE:** Shows actual query plan + execution time. Look for Seq Scan (missing index), Nested Loop (N+1).
- **JSONB:** Binary JSON. GIN index for containment queries (`@>`). Use for semi-structured data, not as primary storage.
- **Window functions:** `ROW_NUMBER()`, `RANK()`, `LAG()`/`LEAD()`. Analytics without subqueries.
- **Full-text search:** `tsvector` + `tsquery` + GIN index. For complex search: use Meilisearch/Typesense.

## 12. Terraform & Infrastructure as Code

### Q85-Q93. State management, modules, workspaces, sensitive data

**Key answers:**
- **State:** Remote backend (S3 + DynamoDB lock). Never commit state files.
- **Modules:** Reusable infrastructure components. Input variables, output values.
- **Workspaces:** Per-environment state (dev/staging/prod). Or use separate state files.
- **Sensitive data:** `sensitive = true` on variables. Use AWS SSM/Secrets Manager, not Terraform variables.

## 13. SDK Development

### Q94-Q102. Python SDK design, auth, retries, error handling, versioning

**Key answers:**
- **Auth:** API key in header (`Authorization: Bearer <key>`). Token refresh for long-lived sessions.
- **Retries:** Exponential backoff with jitter. Max 3 retries. Retry on 429, 500, 502, 503.
- **Error handling:** Custom exception hierarchy. Surface HTTP status + message + request ID.
- **Versioning:** Semantic versioning. Breaking changes = major bump. Deprecation warnings.

## 14. Langfuse-Specific (LLM Observability)

### Q103-Q112. LLM monitoring, cost tracking, prompt versioning, privacy

**Key answers:**
- **Key metrics:** Token usage (input/output), latency, cost per model, error rate, user satisfaction scores.
- **Cost tracking:** Map model name → price per token. Multiply by actual usage. Dashboard per project/model/day.
- **Prompt versioning:** Store prompts as versioned entities. Link traces to prompt versions. A/B test prompts.
- **Privacy:** Data retention policies, PII redaction, EU data residency, opt-out mechanisms.
- **Batch processing:** Buffer traces in Redis/Kafka. Bulk insert to ClickHouse every 1-5 seconds.

## 15. Distributed Systems & Performance

### Q113-Q120. Eventual consistency, CAP, billion-scale events, message queues, idempotency

**Key answers:**
- **Eventual consistency:** Writes propagate eventually. Read-your-writes via session stickiness or causal consistency.
- **CAP theorem:** Partition tolerance is mandatory. Choose availability (Cassandra) or consistency (PostgreSQL).
- **Billion-scale:** Tiered storage (Redis hot → ClickHouse warm → S3 cold). Sampling at ingestion.
- **Idempotency keys:** Client generates UUID. Server checks dedup table before processing. Safe to retry.

## 16. System Design for Langfuse

### Q121-Q125. Architecture, ingestion pipeline, query engine, cost calculation, multi-tenancy

**Key answers:**
- **Architecture:** SDK → API Gateway → Express/tRPC → PostgreSQL (metadata) + ClickHouse (traces) + Redis (cache) + S3 (artifacts)
- **Ingestion:** SDK batches traces → HTTP endpoint → Kafka/SQS buffer → ClickHouse bulk insert
- **Query engine:** ClickHouse for aggregation queries. PostgreSQL for metadata lookups. Redis for dashboard cache.
- **Multi-tenancy:** `project_id` foreign key on all tables. Row-level security. Separate ClickHouse clusters for large tenants.

Use one project workflow to reason through failures and alternatives. “Google-level” is not a measurable property of a study guide, and no list can guarantee a company's questions. Confirm the actual loop, prepare current evidence, and label proposed designs as proposals.

## First Principles

A design that maintains an invariant under one workload can fail when concurrency, tenancy or deployment changes. A useful advanced discussion changes one assumption and traces the new failure boundary instead of adding familiar technology names.

## Choose a boundary to challenge

Start from the [workflow walkthrough](80.16-docita-resume-defense.md) and its [evidence cards](80.17-docita-interview-evidence-pack.md). Select one boundary, then change one assumption. The exercise is to derive the consequence rather than recite a thirty-second script.

| Boundary | Changed assumption | Reasoning to demonstrate |
| ---------------- | --------------------------------------------------- | ---------------------------------------------------------------------------------------- |
| Tenant context | A worker job lacks an HTTP request | Establish authorized tenant scope explicitly and inspect every data path |
| Job processing | A worker crashes after remote acceptance | Distinguish local deduplication from remote outcome reconciliation |
| Booking | Two different patients request one clinician's time | Enforce the contested capacity, not merely each patient's duplicate requests |
| Refresh rotation | Two tabs present one refresh token concurrently | Define atomic rotation, legitimate races, reuse detection and recovery |
| Migration | Old and new application versions overlap | Maintain schema and write compatibility until retirement is verified |
| Realtime | The client disconnects while records change | Reconcile against an authorized source; a socket reconnect alone does not replay history |
| AI budget | Concurrent calls approach the remaining balance | Reserve atomically and account for retries and incomplete usage |

## Work one failure all the way through

Take the remote-acceptance case:

```text
worker claims durable job
  → provider accepts request
  → worker crashes before saving outcome
  → job becomes eligible for another attempt
```

The next attempt may duplicate the side effect. An outbox key can deduplicate local creation, but it cannot prove the provider acted once. Describe a provider-supported idempotency key, reconciliation lookup, or an explicit uncertain-outcome state and operator procedure. Include the retention and scope limits of the chosen mechanism.

Then locate the actual code and checks. If this mechanism is only a proposed improvement, say so. Do not turn an architectural intention into an observed guarantee.

## Compare alternatives using constraints

| Decision | What to compare |
| ----------------------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| Database queue versus broker | Atomic enqueue, workload, claim recovery, ordering, retention, operational cost |
| Shared schema versus cells | Isolation needs, routing, migration, restore scope, capacity and ownership |
| Single-page application (SPA) versus server rendering | Actual user workflow, initial load, caching, interactivity, infrastructure and deployment constraints |
| In-process versus shared cache | Invalidation, authorization, multi-instance behavior, fallback capacity |
| Single region versus recovery region | Required objectives, lag, writer fencing, legal boundaries, restore evidence |

Avoid scale prescriptions such as “100 clinics requires a replica” or “500 clinics requires cells.” Workload and service objectives determine the bottleneck. Shared source also does not guarantee API and worker deploy simultaneously; check schema and event compatibility across version skew.

## What NOT to Claim (v2 — updated against the code)

This heading is retained for existing links. Older versions asserted current production facts from source notes. Treat those notes as investigation leads until refreshed.

| Unsupported shortcut | Defensible boundary |
| ------------------------------------------------- | ------------------------------------------------------------------------------------------- |
| “Every claim here is verified” | State which revision, artifact and check supports this claim |
| “RLS prevents every leak” | Inspect effective policies, roles, scope, privileged paths and denial behavior |
| “Exactly-once produce” | Describe the atomic local write and key scope, then separately explain delivery and effects |
| “AI disabled means no patient data can leave” | Verify every egress path; one provider flag has a narrower effect |
| “Credit guard caps spend” | Demonstrate concurrency, reservation, retries, failures and fail-open behavior |
| “CI wiring means a release passed” | Show actual execution, failures, skips and required release evidence |
| “Clinics are closed, so suspension has no impact” | Verify user hours, external callbacks, scheduled work and cold-start requirements |
| “UTC storage solves scheduling” | Define local calendar recurrence, daylight-saving ambiguity and display semantics |

Do not use an approved metric pair as a substitute for checking its current measurement and disclosure permission. Counts and package versions from a historical snapshot can drift independently.

## Finish with a falsifiable conclusion

State the invariant, your chosen mechanism, the failure it handles, the failure it still permits, and the evidence that would change your decision. Keep personal examples in the [private story bank](personal/story-bank.md). Rehearse the questions in [category revision](REVISION.md) after studying the mechanism.

## Summary

Change one assumption and trace the resulting failure. Compare alternatives against the actual constraint, then distinguish current evidence from a proposed improvement.

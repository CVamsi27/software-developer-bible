# Docita Advanced Design Rehearsal

[![Role priority](https://img.shields.io/badge/role--priority-Important-blue)](../docs/topic-importance.md)
[![General importance](https://img.shields.io/badge/general--importance-Important-blue)](../docs/topic-importance.md)

The difference between a mid-level project walkthrough and a senior/staff architecture defense happens in minute fifteen, when the interviewer says: *"Okay, that works in the happy path — now kill the worker right after Stripe returns 200."* Use this rehearsal guide alongside your [Docita Walkthrough](80.16-docita-resume-defense.md) and [Evidence Pack](80.17-docita-interview-evidence-pack.md) to practice **mutating one production assumption** and tracing the exact consequence aloud.

## First Principles

An architecture that holds cleanly at low concurrency or single-instance deployment can quietly break under retries, connection pooling, or rolling deploys. Real senior mastery means tracing *where* the invariant breaks when one condition shifts — and separating what your code already handles from what you would propose next.

## 1. Seven High-Signal Assumption Mutations to Practice

Pick one row, close your notes, and trace what breaks and how to protect the invariant:

| Boundary | Mutate this assumption | What your explanation must establish |
| ------------------ | ---------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------- |
| **Tenant context** | A background worker runs with no HTTP request | Explicit job-carried tenant identity + scoped DB transaction on every query |
| **Async jobs** | Worker dies *after* remote provider accepts, *before* DB ack | Why local outbox deduplication cannot stop a duplicate remote call; need provider idempotency or reconciliation |
| **Booking** | Two *different* patients request the same clinician slot at once | Locking the shared clinician/slot capacity — not just deduplicating one patient's retry |
| **Auth tokens** | Two browser tabs submit the same refresh token concurrently | Atomic rotation handling legitimate race windows vs. stolen-token reuse detection |
| **Deployments** | Old and new API versions run side-by-side during rollout | Expand-contract schema & payload compatibility before retiring old columns |
| **Realtime** | Client drops Wi-Fi for 90 seconds while clinic bookings change | Authorized cursor/catch-up sync — reconnecting a WebSocket alone misses interim events |
| **AI budget** | Five concurrent calls hit the remaining spend allowance at once | Atomic conditional budget reservation before dispatch + settling actual token cost afterward |

## 2. Worked Failure Trace: The Remote-Acceptance Crash

```text
Worker claims durable job
  ─► Calls external SMS/payment provider ─► Provider ACCEPTS & executes side effect!
       ─► Worker crashes BEFORE saving status = 'sent'
            ─► Lease expires ─► Second worker re-claims job ─► Risk of duplicate side effect!
```

Explain clearly: an outbox key deduplicates *creating* the local job row, **not** executing the remote API. Closing that gap requires passing a stable **provider idempotency key** (within the provider's retention window), polling a **reconciliation lookup API** on retry, or transitioning ambiguous failures into an explicit `needs_reconciliation` state with operator tooling. Always state openly whether this mechanism is already shipped or a proposed improvement.

## 3. Compare Architecture Alternatives by Real Constraints

Never parrot arbitrary thresholds like *"100 clinics = add a replica"* or *"500 clinics = split into cells."* Compare options against actual workload, isolation, and ops cost:

| Trade-off | Real constraints to compare |
| ---------------------------------------- | ----------------------------------------------------------------------------------------------- |
| **PostgreSQL queue vs. Kafka/RabbitMQ** | Atomic enqueue with business commit, throughput/contention, retention, replay, and ops overhead |
| **Shared schema (RLS) vs. tenant cells** | Noisy-neighbor isolation, routing complexity, per-tenant restore scope, and migration fan-out |
| **SPA vs. SSR/Next.js** | Authenticated interactivity vs. initial load/SEO, caching rules, and deployment simplicity |
| **In-process vs. Redis cache** | Multi-instance invalidation, tenant-scoped keys, memory caps, and DB fallback load |
| **Single region vs. multi-region DR** | Real RPO/RTO targets, replication lag, writer fencing (preventing split-brain), and legal rules |

Remember too that a monorepo does not guarantee API and workers deploy in the exact same millisecond — always design schemas and events for rolling version skew.

## What NOT to Claim (v2 — updated against the code)

*(Heading kept stable for incoming links.)* Audit your talking points against these eight common traps before every senior loop:

| Overstated shortcut | Accurate, defensible framing |
| --------------------------------------------------- | -------------------------------------------------------------------------------------------- |
| *"Every claim here is verified"* | Cite the exact git revision, file, and executed test supporting each claim |
| *"RLS prevents every leak"* | Confirm active policies, non-`BYPASSRLS` role, transaction-local scope, and denial tests |
| *"Exactly-once event produce"* | State atomic local write + key scope separately from at-least-once delivery & remote effects |
| *"AI flag off means zero data egress"* | Verify *all* egress paths — one provider feature flag only disables that single client |
| *"Credit guard caps all spend"* | Prove atomic concurrency reservation, retry accounting, and fail-closed behavior |
| *"CI exists so release is proven"* | Confirm which checks actually ran, passed, or were skipped on the deployed revision |
| *"Clinics close at night so sleep has zero impact"* | Check webhooks, scheduled jobs, timezone differences, and cold-start timeouts |
| *"Storing UTC solves all scheduling"* | Distinguish UTC instants from local-timezone recurring rules across daylight-saving shifts |

## 4. Close Every Defense With a Falsifiable Conclusion

End every architecture answer cleanly in four lines: **(1)** the invariant protected, **(2)** the enforcing mechanism, **(3)** the failure still outside its guarantee, and **(4)** the exact measured metric that would trigger moving to the next architecture. Rehearse cold using [Section Revision](REVISION.md).

## Summary

Practice mutating one real constraint at a time — crashes, races, version skew, and lost connections — to prove deep system ownership. Compare alternatives by measured bottlenecks rather than arbitrary scale numbers, avoid overstated shortcuts, and always separate shipped behavior from proposed upgrades.

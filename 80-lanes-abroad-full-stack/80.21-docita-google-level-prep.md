## Part I — Architecture & Multi-Tenancy

### Q1. "Walk me through Docita's overall architecture."

**30-sec:** Turborepo monorepo, five apps: a NestJS API and worker sharing source, two Vite+React SPAs, an Astro landing page. One PostgreSQL database behind everything; a Postgres-backed job queue and transactional outbox instead of Redis/Kafka; Cloudflare serves the SPAs through a tiny Hono proxy that keeps `/api/*` same-origin; Fly.io runs the compute. Deliberate modular-monolith posture — no microservices until a concrete failure mode demands them.

**Deep:** The API is organized as 29 domains (`appointments`, `billing`, `prescriptions`, …), each layered `core → application → infrastructure → presentation`. Cross-cutting concerns live in `shared/modules` (queue, outbox, ai, messaging, idempotency, webhooks, fhir, rls). The worker is a thin bootstrap importing the *same* modules — schedulers for reminders, WhatsApp reconciliation, outbox relay, DLQ replay run there. 119 check scripts in `scripts/checks/` enforce architectural invariants at PR time (measured 2026-09-03).

 *Follow-ups:* "Why share source between api and worker?" (one deploy artifact per module change; no version skew between producer and consumer of jobs). "Why not microservices?" (team of one-to-few; Postgres is the only stateful dependency; network hops would add failure modes faster than they'd remove coupling).

**What NOT to claim:** Kafka, Redis queues, Kubernetes, multiple regions — none exist.

---

### Q2. "How does multi-tenancy work? Walk me through one request."

**30-sec:** Shared schema keyed by `clinicId`. A `TenantContextInterceptor` seeds AsyncLocalStorage per request with `{clinicId, userId, role}` extracted from the JWT. A Prisma extension reads that context and auto-scopes *every* query to the clinic — including cron/worker paths via explicit `withTenant()` wrappers. On top of that, Postgres Row-Level Security is enabled in production so even raw SQL or a missed app-layer filter can't leak across tenants.

**Deep:** Two layers on purpose:
1. **App layer (ALS + Prisma extension):** ergonomic, catches 99% by construction because devs never write `where: { clinicId }` manually.
2. **DB layer (RLS):** policies keyed off a session variable set inside each transaction; defense-in-depth against application bugs. Bypassing requires a code comment `// RLS-BYPASS:` which CI greps for — bypasses are visible in review.

 *Follow-ups:* "ALS vs request-scoped DI container?" (ALS survives async boundaries incl. worker loops without prop-drilling; cheaper than CLS contexts per query). "How do workers get tenant context?" (`withTenant(clinicId, fn)` wrapper around scheduled work). "What if JWT clinic ≠ URL clinic?" (trust the token, reject mismatch).

**What NOT to claim:** "database-per-tenant" (it's shared schema), "RLS only planned" (it's enabled in prod).

---

### Q3. "Why is authorization ABAC and not just RBAC?"

**30-sec:** Roles alone couldn't express healthcare rules — *which* doctor may touch *which* patient record depends on assignment, tenancy, and action, not just role. Docita layers a pure-TypeScript ABAC policy engine (default-deny, deny-overrides) over RBAC: guards do coarse role checks; a global PolicyGuard evaluates declarative policies per resource/action; cross-clinic reads are technically allowed but audited under a break-the-glass flow.

**Deep:** `packages/authorization` has zero framework imports — pure functions returning ALLOW/DENY/NOT_APPLICABLE, so it's unit-testable without NestJS. Policies are wired via `@RequirePolicy(resource, action)` decorators; build-time checks ensure every resolver has policy coverage. E2E "differential-oracle" tests seed two clinics and assert wire-equivalent denials. Emergency access = read-only, flagged `privilegedAccess`, fully logged.

 *Follow-ups:* "Why not OPA/Cedar/Zanzibar?" (policy logic is small enough to own; zero infra; testability beats feature breadth at this scale). "Policy drift between services?" (single package consumed everywhere — one source of truth).

---

### Q4. "You migrated Next.js to Vite SPAs. Defend that."

**30-sec:** OpenNext-on-Cloudflare produced ~3.5MB-gzip bundles against a 3MB Workers limit, fighting the platform for SSR we didn't need: both apps are login-gated dashboards with no SEO surface. We cut over to Vite + React Router SPAs served as static assets, and the API proxy moved into a ~50KB Hono Worker keeping `/api/*` and `/socket.io/*` same-origin — cookies, CSRF, and CORS semantics stayed stable while bundle size and build times collapsed.

**Deep:** Trade-offs accepted: lost streaming SSR/RSC niceties (irrelevant behind auth), gained instant dev server, simpler caching, no server-side rendering infrastructure at all. The migration was possible because data fetching already went through typed clients (`packages/data-access`), not Next-specific fetch layers.

 *Follow-ups:* "When WOULD you keep Next.js?" (public marketing/search-driven pages, per-user server-rendered content needing SEO). "Landing page?" (Astro — static, SEO-relevant).

**What NOT to claim:** "we abandoned React Server Components everywhere" — the SPAs never needed them.

## Part II — Data, Queue & Outbox

### Q5. "Docita uses Postgres as a queue. Why not SQS/BullMQ/Kafka?"

**30-sec:** Jobs must commit atomically with business writes — enqueue-without-commit is exactly the failure mode that loses notifications after successful bookings. Postgres gives us transactional enqueue for free, `SELECT … FOR UPDATE SKIP LOCKED` gives safe competing consumers, and one fewer stateful dependency matters enormously for a small team. Volume (1,000+ appointments/month scale) is nowhere near broker territory.

**Deep:** Mechanics: producers INSERT job rows inside the same `$transaction` as the domain write; workers poll with `SKIP LOCKED` so N workers never grab the same row; failed attempts get retry counts/backoff; exhausted jobs move to a dead-letter table with an operator-facing replay endpoint. ADR `0001` records the decision.

 *Follow-ups:* "When does this break?" (very high throughput — lock contention on the jobs table hot tail; long transactions holding locks; then you reach for a broker). "How do you monitor it?" (queue-depth metrics, oldest-job age alerting, DLQ non-zero alerts).

**What NOT to claim:** "BullMQ with Redis" or "Kafka" — explicitly false; the repo's own docs call this out.

---

### Q6. "Explain the transactional outbox end-to-end."

**30-sec:** Command handlers call `outbox.append(tx, event)` inside the same Prisma transaction as the write — so either both the state change AND its event exist, or neither does. A relay scheduler polls unpublished rows and dispatches them (EventEmitter2 internally), with exponential backoff on failure. Unique `idempotencyKey` per event makes producer-side delivery effectively exactly-once (duplicate inserts hit a P2002 and are treated as no-ops). A CI check bans direct event emits from command paths.

**Deep:** Consumers are still expected to be idempotent (at-least-once delivery overall — the outbox fixes atomicity of publishing, not consumer dedup). Relay lag is a monitored signal; events carry correlation IDs for tracing.

 *Follow-ups:* "Outbox table growth?" (archive/purge policy post-publication). "Ordering guarantees?" (per-aggregate ordering isn't guaranteed by polling relay — consumers key off event payloads; strict ordering would need partitioned streams).

**What NOT to claim:** "exactly-once end-to-end" — say exactly-once produce, at-least-once deliver, idempotent consume.

---

### Q7. "PHI encryption — how does it actually work?"

**30-sec:** Field-level encryption applied transparently through a Prisma extension boundary: 13 sensitive patient fields (names, phone, email, emergency contacts, insurance ID) are encrypted using AES-256-GCM with versioned keys (`v1:iv:tag:ciphertext`). Key versioning allows key rotation without bulk table downtime. Because it lives in the Prisma extension chain, repositories don't know it exists.

**Deep:** GCM gives confidentiality *and* tamper detection (auth tag). The Prisma client composes six extensions in order — tenant scoping, encryption, audit immutability, RLS routing, slow-query logging, query budget — so security controls are structural rather than developer discipline. ADR `0005`.

 *Follow-ups:* "Where do keys live?" (KMS-backed / versioned secret manager environment variables; never in app database plaintext). "Searchable encryption?" (exact-match via deterministic derived columns where needed; range search on PHI is deliberately avoided).

---

### Q8. "Tell me about your Prisma usage — any advanced patterns?"

**30-sec:** Three standouts: (1) driver adapters — Prisma 7 running over a managed pg Pool, giving us pool control and edge-compat; (2) the six-extension composition chain implementing tenancy, crypto, audit, RLS routing, slow-query logs, and query budgets as middleware; (3) UTC-only discipline — every datetime is `timestamptz(3)` with `TimeZone=UTC` on the pool, IST conversions happen purely at presentation.

 *Follow-ups:* "Extension ordering bugs?" (tenant scope before RLS routing; encryption last-touch on write path — covered by integration tests). "$queryRaw escape hatches?" (raw SQL goes through the same transaction/RLS session variable setup).

## Part III — Security

### Q9. "Describe the auth token design."

**30-sec:** Dual-token: 15-minute access JWT + 30-day refresh token delivered as httpOnly, Secure, SameSite=Strict cookie. Every refresh rotates: the old row stores `replacedByToken = SHA256(new)`; presenting an already-rotated token means a stolen chain is being replayed → revoke the entire family (all descendants of that login session). Race safety comes from conditional `updateMany` requiring affected-row count === 1. Plus TOTP MFA and Turnstile captcha on sensitive entry points.

 *Follow-ups:* "Why SameSite=Strict over Lax here?" (first-party SPA behind same-origin proxy; no OAuth redirect flows to preserve). "Access-token revocation window?" (≤15 min by design; sensitive ops re-check user status/password-expiry server-side anyway).

**What NOT to claim:** "7-day refresh" (it's 30 days), "JWT in Authorization header for the SPA" (cookie transport through same-origin proxy).

---

### Q10. "List the request pipeline for a staff endpoint."

**30-sec:** Ten-stage guard chain, then interceptors: E2E throttler → JWT auth → staff-audience check → tenant context → tenant rate-limit → roles → subscription-status → password-expired (90-day rotation) → email-verified → user rate-limit. Interceptors layer CSRF double-submit (timingSafeEqual), idempotency (`@RequiresIdempotency()`), PHI read-audit, and break-the-glass marking.

**Deep:** Each stage fails closed with specific status codes; order matters — cheap/global first (throttle), expensive/contextual later (policies). This pipeline is documented with citations in `SYSTEM_DESIGN_AND_PATTERNS.md §2.2` — cite it when asked "how do you know?"

 *Follow-ups:* "Why both tenant AND user rate limits?" (blast-radius isolation: one abusive clinic can't exhaust the global budget; one compromised account can't hammer its clinic's quota).

---

### Q11. "Rate limiting — how many layers and why?"

**30-sec:** Five: IP-level, user-level (~120 rpm default), tenant-level quotas persisted to `clinicApiQuota` (burst + sustained + monthly budget), global throttler, and account lockout for credential paths. One subtlety worth volunteering: since Fly can't filter ingress by source IP, `CF-Connecting-IP` is trusted **only** when the socket peer is a verified Cloudflare range — otherwise spoofable (ADR `0014`).

 *Follow-ups:* "Where are counters stored?" (Redis optional/gated; memory fallback per instance — quotas that need cross-instance truth persist to Postgres tables).

---

### Q12. "Webhooks — how do you make them trustworthy both ways?"

**30-sec:** Inbound (Razorpay/Meta): verify raw-body HMAC signature, dedupe by event ID against a replay store, process idempotently, return fast. Outbound: signed deliveries with retries/backoff and DLQ. Both directions have dedicated CI checks (replay protection can't be removed without failing `verify:standard`).

 *Follow-ups:* "Why raw body?" (JSON re-serialization reorders/renormalizes bytes → verification breaks or gets bypassed). "Provider retries a delivered event?" (idempotency key → 200 duplicate ack, no double side-effects).

---

### Q13. "How do you prevent PHI leaking into logs/error trackers?"

**30-sec:** Structured logging via Pino with scrubbing; Sentry configured with a PHI redaction util (`sentry.utils.ts`) plus before-send hooks — and a CI script asserts the scrubbing stays wired (`check-sentry-scrubbing`). PHI *reads* themselves emit audit records (PatientDataAuditInterceptor), separate from debug logs.

 *Follow-ups:* "Prove it." (point to the check scripts + audit interceptor tests — this is the strongest differentiator vs candidates who 'believe' their scrubber works).

## Part IV — Reliability, Delivery & Ops

### Q14. "A booking succeeded but the confirmation message didn't send. Debug it."

**30-sec skeleton:** Booking commits + outbox row exist? (check `outbox_events` by correlation id) → relay picked it up? (relay lag metric) → dispatched to messaging orchestrator? (event handler logs) → provider accepted? (WhatsApp/ZeptoMail status, retries) → terminal failure? (DLQ + operator replay endpoint). Every stage has a metric/log — answer ends with "and here's which alert should have fired."

 *Traps:* "Why not just try/catch around send?" (that's the exact bug the outbox exists to kill: message loss on crash-after-commit).

---

### Q15. "Explain idempotency in Docita — producer, transport, consumer."

**30-sec:** Producer-side: unique `idempotencyKey` on outbox rows (P2002 = already published). Request-side: IdempotencyInterceptor stores response fingerprints keyed by client-supplied keys (`@RequiresIdempotency()`) so retried POSTs return the original result. Consumer-side: processed-event tracking so redelivered events are no-ops. Webhooks add provider event-ID dedupe on top.

 *Traps:* "Client doesn't send an idempotency key?" (enforced by decorator — 400 without one on money/booking routes; that's a deliberate API contract).

---

### Q16. "Zero-downtime migrations — your actual procedure."

**30-sec:** Expand/contract wrapped in `safe-migrate.sh`: backup → dry-run → apply → verify → restore-on-failure. Schema changes land backward-compatible (add column, backfill in batches, dual-read/write, flip, contract later). Migrations run gated in CI; destructive steps require an explicit second release.

 *Traps:* "Long backfills block?" (batched by PK cursor with sleep windows; monitored progress; resumable). "Prisma migrate drift in prod?" (shadow DB checks + locked migrate deployment).

### Q17. "Your API suspends overnight. Tell me about cold starts."

**30-sec:** Cost lever: Fly machines `auto_stop_machines='suspend'` with `min_machines_running=0`, driven by a scheduled GitHub workflow aligned to IST clinic hours — clinics simply aren't open at 3 AM. Resume latency on first morning request is seconds, hidden behind Cloudflare and acceptable for the first user of the day; the trade-off is recorded in ADR `0011`.

 *Traps:* "What about cron jobs overnight?" (worker schedule aligns; compliance/reminders jobs run inside business-hours windows or briefly resume machines).

## Part VI — System Design Drills (Docita-Domain)

### Q25. "Design the appointment-booking flow for zero double-bookings." *(the signature question)*

**Answer skeleton:**

```text
1. Invariants first: a patient holds ≤1 confirmed booking per (doctor, time-slot);
   slot must not overlap existing bookings; tenant-scoped always.
2. Layers of enforcement:
   ├── DB: unique/exclusion constraint on (doctor_id, slot_range) WHERE status='confirmed'
   │ (tstzrange && overlap exclusion — DB is final arbiter)
   ├── App: Prisma $transaction → lock patient row (SELECT … FOR UPDATE) →
   │ overlap check → INSERT + outbox.append(event) → COMMIT
   ├── API: idempotency key on POST (retry-safe), Zod DTO validation
   └── UI: disable-on-submit + TanStack Query optimistic update with rollback on 409
3. Concurrency story: two tabs race → both pass app checks → one INSERT wins,
   other violates constraint → 409 Conflict surfaced as "slot taken, refresh".
4. Aftermath: outbox event → worker → WhatsApp/email confirmation.
```

 *Traps:* "Does SELECT FOR UPDATE alone stop phantom inserts?" (No — it locks existing rows; the *constraint* is what stops conflicting inserts. Say this explicitly; it's the senior tell). "Why lock the patient row at all?" (serializes a patient's concurrent attempts cheaply; the constraint still backstops). "Isolation level?" (READ COMMITTED + explicit locking + constraint; don't claim SERIALIZABLE).

### Q26. "Design notifications for 25→500 clinics."

**Skeleton:** Outbox events → orchestrator picks channels (WhatsApp > email > SMS by urgency/user prefs) → per-provider clients behind ports → provider failures retry w/ exponential backoff+jitter → DLQ after budget → operator replay UI. Scale levers: batch window per clinic, template caching, provider rate-limit budgets, quiet hours. Tenancy in every dimension: templates per clinic, quotas per plan tier.

### Q27. "Design the calendar view end-to-end."

**Skeleton:** Read model query `(clinic_id, doctor_id, date range)` covered by composite index; React Query cache with server-events invalidation via Socket.IO room; optimistic add on booking; conflict resolution = server state wins on 409/refresh merge ("calendar is a projection" framing); empty-state and timezone handling (UTC storage, IST display only).

---

### Q28. "Scale math: what breaks from 25 → 100 clinics?"

**30-sec:** Connection pressure first (pool sizing → PgBouncer-style multiplexing), then read-heavy calendar queries (read replica + covering indexes), then queue throughput (more workers, SKIP LOCKED scales fine), then notification provider budgets. Nothing architectural breaks until ~500+: that's when cell-based sharding or broker-offload conversations start — and you'd have the metrics to justify them.

 *Traps:* "Just add Kafka?" (name the concrete failure mode first — matching the repo's own stated posture earns credibility).

---

### Q29. "How would you evolve toward multi-region?"

**Skeleton:** Trigger = data-residency or latency need by geography, not vanity. Steps: pin tenants to region at signup → region-pinned Postgres + compute cells → global control plane for auth/routing only → cross-region reporting via anonymized aggregates. Cost honesty: multi-region Postgres is the expensive part; single-region RDS ap-south-1 is a recorded decision (ADR `0006`) until a real trigger.

---

### Q30. "Design public clinic booking (unauthenticated traffic) differently from staff flows."

**30-sec:** Different threat model: Turnstile captcha, aggressive IP rate limits, no PHI until identity proofing, slot availability served from cache-safe projections, conversion funnel ends in patient-account creation or WhatsApp handoff. Staff endpoints keep the ten-stage chain — never share guard assumptions between publics and internals.

| "Left things better?" | ~200-check `verify:standard` regime making invariants enforceable by anyone | root `package.json` |
| "Failure/incident story" | Use a REAL one from your experience; never invent Docita incidents | — |

**Delivery rules:** punchline first · numbers only from the approved set (25+ clinics, 1,000+ appointments/month) · every "we use X" survives "show me" · gaps stated plainly ("that's sandbox-stage", "that's roadmap") score higher than bluffing.

## Part VIII — Rapid-Fire (60-second answers)

| Question | Answer spine |
| -------------------------- | ----------------------------------------------------------------------------------------- |
| Monolith or microservices? | Modular monolith, 29 domains, shared-source worker; split only on concrete failure mode |
| SQL or NoSQL? | Postgres for everything relational+queue+outbox; R2 blobs; no document store needed |
| REST or GraphQL? | REST + Zod-typed clients; GraphQL not present |
| Push or pull for jobs? | Pull (worker polls SKIP LOCKED) — simple, backpressured, transactional |
| Caching layer? | Optional Redis gated off; memory cache per instance; DB-first doctrine for clinical truth |
| State management? | TanStack Query = server state; URL = view state; minimal client-only stores |
| Auth transport? | httpOnly SameSite=Strict cookies through same-origin Hono proxy |
| Time zones? | UTC timestamptz(3) everywhere; IST at presentation edge only |
| Errors? | RFC 7807 problem details via exception filters; PHI-safe messages enforced |
| Biggest scale risk today? | Connection count + calendar read growth — both have named, costed next steps |

## Section 1: PostgreSQL Internals (25 questions)

### 1.1 MVCC and Concurrency

**Q1: "Explain MVCC. How does PostgreSQL handle concurrent reads and writes without locking?"**

**Answer skeleton:**
"MVCC (Multi-Version Concurrency Control) means every row has multiple versions. When a transaction reads, it sees a snapshot of the database at the time the transaction started — not the current state. When a transaction writes, it creates a new tuple version rather than modifying the existing one. Readers never block writers, and writers never block readers. The trade-off: dead tuple accumulation requires VACUUM to reclaim space."

**What to show:** The PostgreSQL documentation on MVCC, or a query plan showing snapshot behavior.
**What NOT to claim:** "PostgreSQL uses optimistic locking everywhere" (it uses MVCC + row-level locks).

---

**Q2: "What are transaction IDs? How does PostgreSQL track which rows are visible to which transaction?"**

**Answer skeleton:**
"Every transaction gets a unique monotonically increasing transaction ID (XID). Every tuple version stores the XID that created it (xmin) and the XID that deleted/updated it (xmax, if applicable). When a transaction reads, it checks: is xmin committed and before my snapshot? Is xmax not yet committed or after my snapshot? If both conditions hold, the tuple is visible. This is how PostgreSQL determines visibility without locking."

---

**Q3: "What is a tuple version? How does UPDATE create a new version rather than modifying in place?"**

**Answer skeleton:**
"When you UPDATE a row, PostgreSQL marks the old tuple as dead (sets xmax) and inserts a new tuple with the updated data (sets xmin to the current XID). The old tuple is not immediately removed — it stays until VACUUM reclaims it. This means UPDATEs are effectively INSERT + DELETE. The trade-off: reads are fast (no locks), but writes create garbage that VACUUM must clean up."

---

**Q4: "What is transaction ID wraparound? How does VACUUM prevent it?"**

**Answer skeleton:**
"Transaction IDs are 32-bit unsigned integers, so they wrap around after ~4 billion transactions. PostgreSQL freezes old tuple versions (replaces XIDs with FrozenTransactionId) during VACUUM to prevent wraparound. If VACUUM falls behind, PostgreSQL forces a shutdown to prevent data corruption. This is why autovacuum must keep up — a neglected database can hit wraparound and go offline."

---

**Q5: "What is read committed vs repeatable read vs serializable in PostgreSQL? How does each affect Docita's booking queries?"**

**Answer skeleton:**
"Read committed: each statement sees only committed data at statement start. Repeatable read: each statement sees committed data at transaction start (snapshot isolation). Serializable: like repeatable read but detects dangerous read-write patterns and aborts one transaction. For Docita's booking: read committed is default and usually sufficient because the conflict check is in a single statement. Serializable would prevent phantom reads but adds abort overhead."

---

**Q6: "What is a snapshot? How does PostgreSQL determine which tuple version a transaction sees?"**

**Answer skeleton:**
"A snapshot is a data structure that records: (1) the current max XID, (2) a list of active XIDs at snapshot time, (3) a list of completed XIDs. When checking tuple visibility, PostgreSQL compares the tuple's xmin/xmax against the snapshot: xmin must be committed and in the 'completed' list; xmax must be either uncommitted or in the 'future' list."

---

**Q7: "How does PostgreSQL handle a long-running transaction that blocks VACUUM?"**

**Answer skeleton:**
"A long-running transaction holds a snapshot that prevents VACUUM from reclaiming tuples that transaction might still read. This causes dead tuple accumulation and table bloat. Solutions: (1) set statement_timeout to kill long queries, (2) use idle_in_transaction_session_timeout, (3) monitor pg_stat_activity for long transactions, (4) use SELECT FOR UPDATE with NOWAIT to fail fast on contention."

---

**Q8: "What is predicate locking in serializable isolation? How does it prevent phantom reads?"**

**Answer skeleton:**
"Serializable isolation in PostgreSQL uses SSI (Serializable Snapshot Isolation). It tracks read and write dependencies between transactions. If it detects a dangerous pattern (a write that would have changed a transaction's read set), it aborts one transaction. This prevents phantoms without predicate locks on the actual rows — it's a logical lock, not a physical one."

---

### 1.2 WAL and Recovery

**Q9: "What is the WAL? How does it enable crash recovery?"**

**Answer skeleton:**
"The Write-Ahead Log (WAL) records every change to the database before the change is applied to the actual data files. On crash recovery, PostgreSQL replays the WAL from the last checkpoint, re-applying committed changes and rolling back uncommitted ones. The trade-off: WAL writes add latency to every write operation, but they enable crash recovery, point-in-time recovery, and streaming replication."

---

**Q10: "How does WAL archiving work? How does it enable point-in-time recovery?"**

**Answer skeleton:**
"WAL archiving copies completed WAL segments to a secondary location (S3, NFS, etc.). To restore to a specific point in time: (1) restore the base backup, (2) replay WAL segments from the backup time to the desired point, (3) stop at the target timestamp. This gives you RPO of the WAL segment duration (typically 1-5 minutes)."

---

**Q11: "What is synchronous vs asynchronous replication? What's the trade-off?"**

**Answer skeleton:**
"Asynchronous: the primary commits before the replica confirms receipt. Trade-off: the replica may lag, so failover loses recent writes. Synchronous: the primary waits for the replica to confirm before committing. Trade-off: higher write latency, but zero data loss on failover. For Docita: async is fine for read replicas; sync would be for a hot standby if zero data loss is required."

---

**Q12: "How does WAL relate to streaming replication? How do you set up a read replica?"**

**Answer skeleton:**
"Streaming replication sends WAL records from primary to replica in real-time (via a walsender/walreceiver process). Setup: (1) configure primary with wal_level = replica, (2) create a replication user, (3) configure pg_hba.conf for replication, (4) use pg_basebackup to initialize replica, (5) configure standby.signal and primary_conninfo on replica, (6) start the replica. The replica applies WAL records and stays in sync."

---

**Q13: "What is a WAL segment? How does checkpointing work?"**

**Answer skeleton:**
"A WAL segment is a fixed-size file (typically 16MB) that contains WAL records. Checkpointing is the process of flushing dirty pages from shared_buffers to disk and updating the control file. After a checkpoint, WAL segments before the checkpoint are no longer needed for crash recovery and can be archived or removed. Checkpoints are triggered by WAL volume, timeout, or manual command."

### 1.3 VACUUM and Bloat

**Q14: "What is VACUUM? How does it reclaim dead tuple space?"**

**Answer skeleton:**
"VACUUM scans the table and marks dead tuples (those with xmax committed and no longer visible to any active transaction) as reusable. It does not shrink the table file — it marks space as available for future inserts. VACUUM FULL would rewrite the table and shrink the file, but it requires an exclusive lock and blocks all reads/writes."

---

**Q15: "What is VACUUM FULL? When would you use it vs regular VACUUM?"**

**Answer skeleton:**
"VACUUM FULL rewrites the entire table, removing dead tuples and compacting the file. It requires an ACCESS EXCLUSIVE lock — no reads or writes during the operation. Use it only when table bloat is severe and regular VACUUM hasn't helped. Alternative: pg_repack which does an online rebuild without long locks."

---

**Q16: "What is autovacuum? How does it decide when to run?"**

**Answer skeleton:**
"Autovacuum is a background process that runs VACUUM and ANALYZE automatically. It triggers when: (1) the number of dead tuples exceeds autovacuum_vacuum_threshold + autovacuum_vacuum_scale_factor × table size, or (2) the number of inserted tuples exceeds autovacuum_analyze_threshold + autovacuum_analyze_scale_factor × table size. Tuning: for high-write tables like appointments, lower the scale factor (e.g., 0.01) so VACUUM runs more frequently."

---

**Q17: "What is table bloat? How do you detect and fix it?"**

**Answer skeleton:**
"Table bloat is wasted space from dead tuples that VACUUM hasn't reclaimed. Detection: (1) pg_stat_user_tables shows n_dead_tup, (2) pg_size_pretty(pg_total_relation_size('table')) shows total size, (3) pgbadger or pg_stat_statements for query-level analysis. Fix: (1) tune autovacuum for the bloated table, (2) run VACUUM ANALYZE, (3) if severe, use pg_repack for online table rebuild."

---

**Q18: "What is index bloat? How does it affect query performance?"**

**Answer skeleton:**
"Index bloat is wasted space in B-tree indexes from deleted/updated entries. It slows down index scans because the tree is deeper than necessary. Detection: pgstatindex() function shows average leaf density. Fix: REINDEX (requires lock) or pg_repack (online). Prevention: autovacuum keeps up, and you periodically REINDEX during low-traffic periods."

### 1.4 Connection Pooling

**Q19: "Why is PgBouncer necessary? What happens when you exhaust PostgreSQL connections?"**

**Answer skeleton:**
"Each PostgreSQL connection spawns a backend process (~5-10MB memory). At 500 connections, that's 2.5-5GB just for connection overhead. Plus context switching and lock contention. PgBouncer sits between the app and PostgreSQL, multiplexing many app connections onto fewer database connections. When you exhaust connections: new queries queue, latency spikes, eventually the database becomes unresponsive."

---

**Q20: "What is connection pooling mode — session vs transaction vs statement? Which does Docita use?"**

**Answer skeleton:**
"Session: a client gets a server connection for the entire session. Transaction: a client gets a connection for the duration of a transaction, then it's returned. Statement: a client gets a connection per statement (most aggressive, breaks transactions). Docita should use transaction mode with Prisma, since Prisma uses short-lived transactions and doesn't need session-level features like prepared statements (which PgBouncer in transaction mode doesn't support well)."

---

**Q21: "How do you tune connection pool size? What's the formula?"**

**Answer skeleton:**
"Formula: connections = (CPU cores × 2) + effective_spindle_count. For SSDs: connections ≈ (cores × 2) + 1. For a 4-core server: ~9 connections per PgBouncer instance. The key insight: more connections ≠ better performance. Beyond a threshold, context switching hurts more than parallelism helps. Monitor pg_stat_activity and connection wait times."

---

**Q22: "What happens when a connection hangs? How does PgBouncer handle it?"**

**Answer skeleton:**
"PgBouncer has query_timeout and client_idle_timeout settings. If a query runs longer than query_timeout, PgBouncer disconnects the client and returns an error. The PostgreSQL backend process is terminated. This prevents a single slow query from holding a connection indefinitely. Monitor: pg_stat_activity for idle in transaction, and PgBouncer's stats for query wait time."

### 1.5 Query Planning and Indexes

**Q23: "How does the query planner choose between seq scan, index scan, and bitmap scan? Show me the EXPLAIN ANALYZE output for a patient list query."**

**Answer skeleton:**
"Seq scan: reads every row (good for small tables or when most rows are returned). Index scan: follows B-tree index to find matching rows (good for selective queries). Bitmap scan: builds a bitmap of matching row locations, then fetches them (good for medium selectivity). The planner uses statistics (pg_statistic) to estimate row counts and costs. For a patient list with clinic_id filter: bitmap index scan on (clinic_id) + heap fetch."

---

**Q24: "When does a composite index on (a, b) work but (b, a) doesn't?"**

**Answer skeleton:**
"A composite index (a, b) can satisfy queries on: (a), (a, b), or (a) with ORDER BY b. It cannot efficiently satisfy queries on (b) alone because the index is sorted by (a) first — b is only sorted within each a value. Example: index on (clinic_id, created_at) works for 'all appointments in clinic X, sorted by date' but not for 'all appointments created today, grouped by clinic.'"

---

**Q25: "What is a partial index? When would you use one on the appointments table?"**

**Answer skeleton:**
"A partial index indexes only rows matching a WHERE clause. Example: `CREATE INDEX idx_active_appointments ON appointments (clinic_id, slot_start) WHERE status = 'booked'`. This is smaller and faster than a full index because it excludes cancelled/completed appointments. Use it when: (1) you frequently query a subset of rows, (2) the subset is a small fraction of the table, (3) the WHERE clause is static."

## Section 2: Distributed Systems (20 questions)

### 2.1 CAP Theorem and Consistency

**Q26: "Apply CAP theorem to Docita. Is it CP or AP? What happens when the database is partitioned?"**

**Answer skeleton:**
"Docita is CP (Consistency + Partition tolerance). If the database partitions, Docita sacrifices availability — it returns errors rather than stale data. This is correct for healthcare: a clinician seeing stale patient data is worse than seeing an error. The trade-off: during a network partition between the API and PostgreSQL, booking requests fail until connectivity is restored. The outbox pattern helps: writes are queued and replayed when connectivity returns."

---

**Q27: "What is eventual consistency? How do you test for it in Docita's outbox pattern?"**

**Answer skeleton:**
"Eventual consistency means that after a write, all replicas will eventually see the same value — but there's a window where reads may be stale. In Docita's outbox: the appointment is committed, but the notification is sent asynchronously. A user might book an appointment but not immediately see the confirmation email. Testing: write an appointment, immediately check notification delivery, assert the notification eventually arrives within the expected latency window."

---

**Q28: "What is linearizability? When would you need it vs eventual consistency?"**

**Answer skeleton:**
"Linearizability means every operation appears to take effect atomically at some point between invocation and completion. All subsequent reads see the result. Docita's appointment booking needs linearizability for the conflict check (two users booking the same slot must see a consistent state). But notification delivery can be eventual (the email can arrive 30 seconds later). Use linearizability for correctness-critical paths; eventual consistency for everything else."

---

**Q29: "What is read-your-writes consistency? How does Docita ensure a user sees their own booking immediately?"**

**Answer skeleton:**
"Read-your-writes consistency means a user always sees their own writes, even if replicas lag. In Docita: after a user books an appointment, the API returns the created appointment in the response. Subsequent reads from the same session hit the primary (or a session stickiness mechanism ensures the same connection). The trade-off: if the user switches sessions or the primary fails, they might briefly see stale data until the replica catches up."

---

**Q30: "What is causal consistency? How does it relate to event ordering in the notification system?"**

**Answer skeleton:**
"Causal consistency preserves the order of causally related events. If event A causes event B, all observers see A before B. In Docita's notification system: if a clinician books an appointment (event A) and then sends a message (event B), all users should see the appointment before the message. This is guaranteed if both events go through the same service or use a causal ordering mechanism (e.g., vector clocks)."

---

**Q31: "What is the PACELC theorem? How does it extend CAP?"**

**Answer skeleton:**
"PACELC says: if there's a Partition, choose between Availability and Consistency (like CAP). Else (normal operation), choose between Latency and Consistency. Docita chooses C in partitions (CP) and C during normal operation (strong consistency via PostgreSQL transactions). The trade-off: higher latency for writes (must wait for transaction commit) but guaranteed consistency. A system like Cassandra would choose A in partitions and L during normal operation (eventual consistency for lower latency)."

### 2.2 Distributed Transactions

**Q32: "Explain the outbox pattern in detail. What are the failure modes at each step?"**

**Answer skeleton:**
"Step 1: API writes business data + outbox event in one transaction. Failure: transaction rolls back, nothing happens (safe). Step 2: Outbox relay polls for unprocessed events. Failure: relay crashes, events stay unprocessed (safe — relay restarts). Step 3: Worker processes the event. Failure: worker crashes mid-processing, event is reprocessed (idempotency required). Step 4: Worker marks event as processed. Failure: mark fails, event is reprocessed (idempotency required). The key: every step is idempotent, so retries are safe."

---

**Q33: "What is a saga? How does it differ from two-phase commit? When would you use each?"**

**Answer skeleton:**
"A saga is a sequence of local transactions with compensating actions for rollback. Two-phase commit (2PC) is a coordinator that locks resources across all participants until all commit. Saga: no global lock, eventual consistency, each step is independent. 2PC: strong consistency, global lock, blocking if coordinator fails. Use saga for long-running business processes (booking → payment → notification). Use 2PC for short-lived atomic operations across two databases (rare)."

---

**Q34: "What is the transactional outbox vs the polling publisher vs the CDC-based publisher?"**

**Answer skeleton:**
"Transactional outbox: write event to outbox table in same transaction as business data. Polling publisher: separate process polls the outbox table and publishes to the message broker. CDC-based publisher: use Change Data Capture (Debezium) to capture changes from the WAL and publish to the broker. Trade-offs: transactional outbox is simplest but adds DB load from polling. CDC is most efficient but adds operational complexity (Debezium, Kafka Connect)."

---

**Q35: "How do you handle a saga that's partially completed? What are compensating transactions?"**

**Answer skeleton:**
"A partially completed saga needs compensating actions to undo completed steps. Example: booking → payment → notification. If payment succeeds but notification fails, the saga compensates: refund the payment, cancel the booking. Compensating transactions must be idempotent (calling them twice has the same effect as calling them once). Design principle: every step in the saga must have a compensating action, and the compensation must be idempotent."

---

**Q36: "What is the dual-write problem? How does the outbox pattern solve it?"**

**Answer skeleton:**
"The dual-write problem: you need to write to both the database and the message broker atomically, but they're separate systems. If you write to the DB first then the broker, the broker might fail and you've lost the event. If you write to the broker first then the DB, the DB might fail and you've published a ghost event. The outbox pattern solves this: write both to the DB in one transaction, then asynchronously publish from the outbox. The outbox is the single source of truth."

---

### 2.3 Clock Skew and Ordering

**Q37: "How do you handle clock skew in a distributed system? What breaks when clocks disagree?"**

**Answer skeleton:**
"Clock skew breaks: (1) TTL-based cache expiration, (2) token expiry validation, (3) log correlation across services, (4) timeout detection. Solutions: (1) use logical clocks (Lamport timestamps) for ordering, (2) use NTP for rough synchronization, (3) use vector clocks for causal ordering, (4) never depend on wall-clock time for correctness — use monotonic clocks for durations."

---

**Q38: "What is a logical clock? How does a vector clock work?"**

**Answer skeleton:**
"A logical clock is a counter that increments on each event, providing a partial ordering without relying on wall-clock time. A vector clock is a map of {node → counter} that tracks the happened-before relationship across all nodes. If VC(a) < VC(b) for all elements, then a happened before b. Vector clocks detect concurrent events (neither happened before the other). Used for conflict detection in distributed databases (Dynamo, Riak)."

---

**Q39: "How does Kafka maintain ordering? What are the limits?"**

**Answer skeleton:**
"Kafka guarantees ordering within a partition, not across partitions. If you need ordering for a specific entity (e.g., appointments for one patient), all events for that entity must go to the same partition (partition by patient_id). The trade-off: more partitions = more parallelism but harder ordering guarantees. Across partitions, ordering is not guaranteed — consumers must handle out-of-order events if they read from multiple partitions."

---

**Q40: "How do you ensure event ordering across multiple services?"**

**Answer skeleton:**
"Options: (1) Single partition with one consumer — guarantees ordering but limits throughput. (2) Partition by entity ID — orders per entity, parallel across entities. (3) Causal ordering via vector clocks — detects concurrent events. (4) Application-level ordering — consumer sorts events by timestamp before processing. The trade-off: strict global ordering limits parallelism. Most systems need per-entity ordering, not global ordering."

---

### 2.4 Failure Modes

**Q41: "What is split-brain? How do you prevent it in a PostgreSQL cluster?"**

**Answer skeleton:**
"Split-brain: two nodes both think they're the primary, accepting writes independently. When they rejoin, you have conflicting data. Prevention: (1) use a fencing mechanism (STONITH — Shoot The Other Node In The Head), (2) use a witness node or quorum, (3) use synchronous replication so the primary waits for replica confirmation, (4) use a consensus algorithm (Patroni with etcd/ZooKeeper for leader election)."

---

**Q42: "Explain circuit breaker pattern. When does it trip? How does it recover? What's the half-open state?"**

**Answer skeleton:**
"Circuit breaker wraps an external call. States: (1) Closed — calls pass through, failures are counted. (2) Open — after N failures, calls are rejected immediately (fast fail). (3) Half-open — after a timeout, one test call is allowed. If it succeeds, close the circuit; if it fails, re-open. Prevents cascading failures when a dependency is down. For Docita: circuit breaker on the notification provider — if SendGrid is down, don't queue emails that will fail; wait until it recovers."

---

**Q43: "What is graceful degradation? How would Docita degrade if the notification service is down?"**

**Answer skeleton:**
"Graceful degradation: the system continues to function with reduced capabilities. If the notification service is down: (1) appointment booking still works (notification is queued, not blocking), (2) in-app notifications still work (they're in the same database), (3) email/SMS notifications are delayed (outbox events accumulate, processed when the service recovers), (4) the dashboard shows a 'notifications temporarily unavailable' banner. The key: the core workflow (booking) is never blocked by a non-critical dependency."

---

**Q44: "How do you handle partial failures in a microservices architecture?"**

**Answer skeleton:**
"Partial failures: one service is down but others are up. Solutions: (1) circuit breaker — fast-fail on the failing service, (2) fallback — return cached data or a degraded response, (3) timeout — never wait indefinitely, (4) retry with backoff — transient failures may recover, (5) bulkhead — isolate failure to one service, don't let it cascade. The key insight: in a distributed system, partial failure is the norm, not the exception. Design for it from day one."

---

**Q45: "What is the bulkhead pattern? How does it prevent cascading failures?"**

**Answer skeleton:**
"Bulkhead isolates components so a failure in one doesn't bring down the whole system. Implementation: (1) separate connection pools per dependency (notification provider gets 10 connections, payment provider gets 10), (2) separate thread pools per service, (3) separate rate limits per tenant. If the notification pool is exhausted, payment still works. The metaphor: ship bulkheads prevent one hull breach from flooding the entire ship."

## Section 3: Caching Deep-Dive (15 questions)

### 3.1 Cache Patterns

**Q46: "Explain cache-aside vs read-through vs write-through vs write-behind. Which does Docita use and why?"**

**Answer skeleton:**
"Cache-aside: app reads cache → miss → reads DB → writes to cache. Read-through: cache reads DB on miss (app only talks to cache). Write-through: writes go to cache and DB simultaneously. Write-behind: writes go to cache, async flush to DB. Docita uses cache-aside for schedule data: the app explicitly controls what's cached, when it's invalidated, and falls back to PostgreSQL on cache miss. The trade-off: cache-aside has more code but more control."

---

**Q47: "What is cache stampede? How do you prevent it when a popular clinic's schedule is accessed?"**

**Answer skeleton:**
"Cache stampede: when a cached value expires, many concurrent requests all miss the cache and hit the DB simultaneously. Prevention: (1) lock/mutex — one request repopulates, others wait, (2) probabilistic early expiration — randomly refresh before TTL expires, (3) background refresh — keep the cache warm before it expires, (4) stale-while-revalidate — return stale data while refreshing in the background."

---

**Q48: "What is the Thundering Herd problem? How does it relate to cache expiration?"**

**Answer skeleton:**
"Thundering Herd: when a resource becomes available (e.g., a cache key is repopulated), all waiting requests wake up simultaneously and compete for the resource. Similar to cache stampede but broader. Prevention: (1) jitter — add random delay to cache TTLs so keys don't expire simultaneously, (2) single-flight — deduplicate concurrent requests for the same key, (3) request coalescing — merge multiple requests into one DB query."

---

**Q49: "How do you handle cache invalidation in a multi-tenant system? What's the key strategy?"**

**Answer skeleton:**
"Multi-tenant cache keys must include clinic_id: `cache:clinic:{clinicId}:schedule:{practitionerId}`. Invalidation strategies: (1) write-through — invalidate on every write (simple, may over-invalidate), (2) TTL-based — accept staleness for TTL duration, (3) event-driven — outbox event triggers cache invalidation (more complex, more accurate). For Docita: TTL for schedule data (30 seconds), event-driven for patient data (must be fresh)."

---

**Q50: "What is cache warming? When would you proactively populate the cache?"**

**Answer skeleton:**
"Cache warming: proactively populate the cache before it's needed. Use cases: (1) after a deploy — warm the cache with the most popular clinic schedules, (2) after a cache flush — pre-populate known hot keys, (3) for predictable traffic — warm the cache before morning clinic hours. The trade-off: warming uses DB resources proactively; if you guess wrong, you waste resources on cold data."

---

### 3.2 Cache Architecture

**Q51: "How would you design a caching layer for Docita? What to cache, what not to cache?"**

**Answer skeleton:**
"Cache: (1) practitioner schedules (read-heavy, changes infrequently), (2) clinic configuration (rarely changes), (3) permission/role lookups (changes on admin action). Don't cache: (1) patient records (PHI sensitivity, freshness requirement), (2) appointment status (must be real-time), (3) audit logs (write-heavy, append-only). Key strategy: `cache:{clinicId}:{entity}:{id}`. TTL: 30s for schedules, 5min for config, 0 for patient data."

---

**Q52: "What is CDN edge caching? How does it work for a healthcare SPA?"**

**Answer skeleton:**
"CDN caches static assets (JS, CSS, images) at edge nodes close to users. For Docita's Vite SPA: the HTML shell, JS bundles, and CSS are cacheable (fingerprinted filenames). API responses are not CDN-cached (they're tenant-specific and dynamic). Trade-off: CDN reduces latency for asset delivery but doesn't help with API response time. Healthcare consideration: never cache API responses containing PHI at the CDN edge."

---

**Q53: "How do you handle cache consistency across multiple services?"**

**Answer skeleton:**
"Options: (1) distributed cache (Redis) — single source of truth, all services read/write the same cache, (2) per-service cache with invalidation events — each service has its own cache, invalidation is propagated via events, (3) read-through with TTL — accept eventual consistency. For Docita: shared Redis cache for schedule data (read by API and worker), per-service cache for service-specific data. Invalidation: event-driven for schedule changes, TTL for everything else."

---

**Q54: "What is the N+1 caching problem? How does it differ from the N+1 query problem?"**

**Answer skeleton:**
"N+1 query: one query for the list, then N queries for each item's details. N+1 caching: one cache miss triggers N cache misses for related data. Example: cache miss for clinic schedule → miss for each practitioner's schedule → miss for each appointment. Prevention: batch cache lookups (mget in Redis), or cache the aggregated result (clinic schedule with all practitioners pre-included)."

---

**Q55: "How do you choose a TTL? What are the trade-offs for patient data vs schedule data?"**

**Answer skeleton:**
"TTL = freshness requirement / acceptable staleness. Patient data: TTL = 0 (never cache, must be real-time). Schedule data: TTL = 30s (clinician can tolerate 30s stale availability). Clinic config: TTL = 5min (changes rarely, staleness acceptable). The trade-off: shorter TTL = more DB hits, longer TTL = more staleness. Monitor cache hit rate: if >95%, TTL is probably too short; if <80%, TTL might be too long."

### 3.3 Cache Failure Modes

**Q56: "What happens when Redis goes down? How does Docita degrade?"**

**Answer skeleton:**
"Graceful degradation: (1) all cache reads fall through to PostgreSQL (slower but correct), (2) cache writes are skipped (no error), (3) the system continues to function at reduced performance. Prevention: (1) Redis Sentinel for automatic failover, (2) circuit breaker on Redis — if Redis is slow, stop waiting and go to DB, (3) monitor Redis health and alert on failure."

---

**Q57: "How do you handle a cache that's returning stale data?"**

**Answer skeleton:**
"Stale data scenarios: (1) TTL too long — reduce TTL, (2) invalidation missed — add invalidation event, (3) race condition between write and invalidation — use cache-aside with versioned keys. Detection: (1) compare cache value with DB value periodically, (2) track cache hit/miss ratio, (3) user reports of inconsistent data. Fix: flush the specific cache key and reduce TTL."

---

**Q58: "What is a cache avalanche? How do you prevent it?"**

**Answer skeleton:**
"Cache avalanche: many cache keys expire simultaneously, causing a flood of DB queries. Prevention: (1) jitter — add random seconds to each TTL (30s ± 5s), (2) staggered expiration — don't populate all keys at the same time, (3) background refresh — proactively refresh before expiration, (4) circuit breaker — if DB load exceeds threshold, serve stale data."

---

**Q59: "How do you test caching behavior? What are the failure modes in tests?"**

**Answer skeleton:**
"Test: (1) cache hit — assert DB is not queried, (2) cache miss — assert DB is queried and cache is populated, (3) cache invalidation — assert cache is cleared after write, (4) cache failure — assert DB fallback works, (5) stale data — assert TTL is respected. Failure modes: (1) tests pass with caching disabled but fail with caching enabled, (2) tests don't account for cache propagation delay, (3) tests mock Redis incorrectly."

---

**Q60: "What is the cache-aside race condition? How do you handle two concurrent writes?"**

**Answer skeleton:**
"Race condition: Thread A writes to DB, Thread B writes to DB, Thread A invalidates cache, Thread B invalidates cache, Thread A reads cache (miss) and repopulates with old data, Thread B reads cache (hit) and gets stale data from Thread A. Fix: (1) write-through — write to cache and DB simultaneously, (2) versioned cache keys — include a version number, (3) short TTL — accept brief staleness, (4) single-flight — serialize cache repopulation."

## Section 4: Message Queue Internals (15 questions)

### 4.1 Kafka Internals

**Q61: "Explain Kafka partitions. How does partitioning affect ordering and throughput?"**

**Answer skeleton:**
"A partition is an ordered, immutable sequence of records. Partitions enable parallelism: multiple consumers can read from different partitions simultaneously. Ordering: Kafka guarantees ordering within a partition, not across partitions. Throughput: more partitions = more parallelism but more overhead (more files, more file handles, more memory). The trade-off: 100 partitions is typical for moderate throughput; 10,000 partitions requires careful tuning."

---

**Q62: "What are consumer groups? How does rebalancing work?"**

**Answer skeleton:**
"A consumer group is a set of consumers that jointly consume a topic. Each partition is assigned to exactly one consumer in the group. Rebalancing: when a consumer joins or leaves, partitions are redistributed. During rebalance, consumption pauses briefly. Rebalance triggers: (1) consumer joins, (2) consumer leaves (crash or graceful), (3) new partitions added. Minimize rebalance frequency: use static membership, longer session timeouts."

---

**Q63: "Explain offset management. What happens when a consumer crashes mid-processing?"**

**Answer skeleton:**
"Each consumer tracks its position (offset) in each partition. Offsets are committed periodically (not after every message). If a consumer crashes: uncommitted messages are reprocessed by the new consumer. This means at-least-once delivery. For exactly-once: commit offsets transactionally with the business effect (Kafka transactions). The trade-off: more frequent commits = less reprocessing on crash but more overhead."

---

**Q64: "What is exactly-once semantics in Kafka? How is it achieved?"**

**Answer skeleton:**
"Exactly-once means each message is processed exactly once, despite retries and failures. Kafka achieves this via: (1) idempotent producer — assigns sequence numbers to detect duplicates, (2) transactional producer — atomically writes to multiple partitions, (3) consumer offset commit — commit offsets transactionally with processing. The trade-off: exactly-once adds complexity and latency. In practice, most systems use at-least-once + idempotent consumers (effectively-once)."

---

**Q65: "How does schema evolution work with Avro/Protobuf?"**

**Answer skeleton:**
"Avro/Protobuf schemas are versioned. Schema evolution rules: (1) add optional fields with defaults (backward compatible), (2) never remove required fields, (3) never change field types. Schema registry stores schemas and enforces compatibility. Producers write with the latest schema; consumers read with their own schema version. The registry handles the translation. Trade-off: schema evolution adds operational complexity but prevents breaking changes."

---

**Q66: "What is backpressure in a message queue? How do you implement it?"**

**Answer skeleton:**
"Backpressure: the consumer is slower than the producer. Implementation: (1) consumer pulls messages at its own pace (Kafka default), (2) rate limiting on the producer, (3) bounded queue with overflow policy (reject oldest, drop, block), (4) adaptive batch size — consumer processes larger batches when behind. Kafka handles backpressure naturally via pull-based consumption: the consumer requests messages when it's ready."

---

**Q67: "How do you handle message ordering guarantees across partitions?"**

**Answer skeleton:**
"You can't guarantee ordering across partitions. Solutions: (1) single partition — guarantees global ordering but limits throughput, (2) partition by entity ID — orders per entity, (3) application-level ordering — consumer sorts by timestamp. For Docita: partition by clinic_id for clinic-specific events (ordering per clinic is sufficient), single partition for global events (e.g., system-wide announcements)."

---

**Q68: "What is the difference between Kafka and RabbitMQ? When would you choose each?"**

**Answer skeleton:**
"Kafka: high throughput, log-based, messages persist after consumption, replay capability, partition-based ordering. RabbitMQ: traditional message broker, messages deleted after consumption, complex routing (exchanges, bindings), lower latency for small messages. Choose Kafka for: event sourcing, log aggregation, high-throughput streaming. Choose RabbitMQ for: task queues, complex routing, request-reply patterns. For Docita: Kafka for event streaming, RabbitMQ (or BullMQ) for task queues."

---

### 4.2 Dead Letter Queues and Replay

**Q69: "Explain dead letter queues. When do you use them? How do you replay messages?"**

**Answer skeleton:**
"DLQ: a queue where messages go after max retry attempts. Use when: (1) message is poison (unparseable, permanently failing), (2) business logic rejects the message, (3) message exceeds retry budget. Replay: (1) fix the root cause, (2) move messages from DLQ back to the main queue (manual or scripted), (3) reprocess. Monitoring: alert on DLQ depth > 0, dashboard shows DLQ rate."

---

**Q70: "What is a poison message? How do you detect and handle it?"**

**Answer skeleton:**
"Poison message: a message that causes the consumer to crash or fail every time it's processed. Detection: (1) message fails N times (retry budget), (2) consumer crashes on specific message pattern. Handling: (1) move to DLQ after N retries, (2) log the message content (without PHI), (3) alert the on-call engineer, (4) analyze and fix the root cause, (5) replay from DLQ after fix."

---

**Q71: "How do you implement DLQ monitoring and alerting?"**

**Answer skeleton:**
"Metrics: (1) DLQ depth (current number of messages), (2) DLQ rate (messages per minute entering DLQ), (3) DLQ age (oldest unprocessed message). Alerting: (1) DLQ depth > 0 for > 5 minutes (immediate), (2) DLQ rate > 10/minute (trend), (3) DLQ age > 1 hour (stale). Dashboard: DLQ depth over time, DLQ by topic, DLQ by error type."

---

**Q72: "What is the retry budget? How do you decide when to move to DLQ?"**

**Answer skeleton:**
"Retry budget: max retries before giving up. Factors: (1) transient vs permanent failure — network timeout (retry) vs validation error (don't retry), (2) retry cost — each retry consumes resources, (3) user impact — how long is the user waiting? For Docita: 3 retries with exponential backoff (1s, 2s, 4s) for transient failures, immediate DLQ for permanent failures (validation, authorization). Total max wait: ~7 seconds."

---

### 4.3 Worker Patterns

**Q73: "How do you design a worker that processes jobs at-least-once with idempotent consumers?"**

**Answer skeleton:**
"At-least-once: the worker processes every message at least once, possibly more. Idempotent consumers: processing the same message twice has the same effect as processing it once. Implementation: (1) idempotency key per message (event ID), (2) check if already processed before executing, (3) mark as processed atomically with the business effect. The trade-off: idempotency adds code complexity but enables safe retries."

---

**Q74: "What is the outbox relay pattern vs the change data capture pattern?"**

**Answer skeleton:**
"Outbox relay: a process polls the outbox table and publishes messages. Simple, explicit, but adds DB polling load. CDC (Change Data Capture): a process reads the WAL and publishes changes. More efficient (no polling), but adds operational complexity (Debezium, Kafka Connect). For Docita: outbox relay is simpler and sufficient at current scale. CDC would be considered at 10x scale."

---

**Q75: "How do you handle worker scaling? What's the relationship between partitions and consumers?"**

**Answer skeleton:**
"Kafka: each partition is assigned to one consumer in the group. More consumers than partitions = idle consumers. More partitions than consumers = consumers handle multiple partitions. Scaling: add partitions for more parallelism, add consumers for more throughput. Non-Kafka (BullMQ): workers pull from a shared queue, scaling is automatic. For Docita's PostgreSQL-backed worker: scale by adding worker instances, each pulling from the outbox table with row-level locking to prevent double-processing."

## Section 5: API Design at Scale (15 questions)

### 5.1 Versioning and Evolution

**Q76: "How do you version a REST API? URL vs header vs query parameter? Trade-offs?"**

**Answer skeleton:**
"URL versioning: `/v1/patients` — explicit, cacheable, but clutters URLs. Header versioning: `Accept: application/vnd.api+json;version=1` — clean URLs, but harder to test/debug. Query parameter: `/patients?version=1` — easy to implement, but easy to forget. For Docita: URL versioning for major changes (v1 → v2), header versioning for minor variations. Trade-off: URL versioning is the most common and easiest to understand."

---

**Q77: "What is API deprecation strategy? How do you migrate clients without breaking them?"**

**Answer skeleton:**
"Strategy: (1) announce deprecation with timeline (e.g., 6 months), (2) add deprecation headers to old version responses, (3) log usage of deprecated endpoints, (4) notify clients proactively, (5) remove old version after timeline. For Docita's internal clients (clinician app, internal app): coordinate deprecation with app releases. For external clients: longer deprecation window with migration guides."

---

**Q78: "How do you handle backward-compatible schema evolution in API responses?"**

**Answer skeleton:**
"Rules: (1) add new fields (clients ignore unknown fields), (2) never remove fields without deprecation period, (3) never change field types, (4) use nullable/optional for new fields. Implementation: (1) version the response schema, (2) use OpenAPI to document changes, (3) test backward compatibility in CI (backward compatibility checker). For Docita: add new fields to DTOs, never remove without deprecation."

---

**Q79: "What is the expand/contract pattern for API changes?"**

**Answer skeleton:**
"Expand: add new field/endpoint alongside the old one. Both work simultaneously. Contract: migrate clients to the new field/endpoint. Remove the old one. Example: rename `clinic_id` to `tenant_id`: (1) add `tenant_id` field (expand), (2) write to both fields (dual-write), (3) migrate clients to read `tenant_id`, (4) stop writing to `clinic_id` (contract), (5) remove `clinic_id`. This enables zero-downtime migrations."

---

**Q80: "How do you version a GraphQL schema? How does it differ from REST versioning?"**

**Answer skeleton:**
"GraphQL: no explicit versioning. Instead, deprecate fields with `@deprecated` and add new fields. Clients choose which fields to request. The schema evolves additively. Trade-off: no breaking changes possible (clients control their query), but schema grows over time. For Docita: if using GraphQL, deprecate fields instead of removing them, and use schema directives for documentation."

### 5.2 Rate Limiting

**Q81: "Explain rate limiting algorithms. Token bucket vs sliding window vs fixed window."**

**Answer skeleton:**
"Fixed window: count requests in fixed time windows (e.g., 100 requests per minute). Simple but has burst problem at window boundaries. Sliding window: count requests in a rolling window. Smoother, but more memory. Token bucket: tokens added at fixed rate, each request consumes one token. Allows bursts up to bucket size. For Docita: token bucket per clinic (allows bursty booking patterns, prevents abuse). Implementation: Redis with Lua script for atomic token consumption."

---

**Q82: "How do you implement rate limiting across multiple API instances?"**

**Answer skeleton:**
"Centralized rate limiting: all instances share a Redis counter. Each request decrements the counter atomically (Redis Lua script). Trade-off: Redis latency adds to every request. Distributed rate limiting: each instance tracks its own counter, periodically synced. Faster but less accurate. For Docita: centralized via Redis is fine (low latency, accurate). At scale: use local rate limiting with periodic sync for hot paths."

---

**Q83: "What is per-tenant rate limiting? How do you prevent one clinic from consuming all resources?"**

**Answer skeleton:**
"Per-tenant rate limiting: each clinic gets its own rate limit (e.g., 100 requests/minute). Key: `ratelimit:{clinicId}:{window}`. This prevents one busy clinic from starving others. Implementation: Redis key per clinic, atomic decrement. Monitoring: track which clinics hit limits, adjust limits based on tier. For Docita: rate limit by clinic_id, with higher limits for premium clinics."

---

**Q84: "How do you handle rate limit headers (X-RateLimit-Remaining, Retry-After)?"**

**Answer skeleton:**
"Headers: `X-RateLimit-Limit` (max requests), `X-RateLimit-Remaining` (current remaining), `X-RateLimit-Reset` (window reset time), `Retry-After` (seconds until retry). Implementation: (1) check rate limit before processing, (2) if exceeded, return 429 with Retry-After header, (3) always include rate limit headers in response. Client behavior: respect Retry-After, implement exponential backoff."

---

**Q85: "What is the difference between rate limiting and throttling?"**

**Answer skeleton:**
"Rate limiting: reject requests that exceed the limit (429 error). Throttling: slow down requests that exceed the limit (queue them, add delay). Rate limiting is simpler and more predictable. Throttling provides better UX (no errors, just slower). For Docita: rate limiting for API endpoints (hard limit), throttling for background jobs (soft limit, queue and process slowly)."

## Section 6: Observability and Reliability (20 questions)

### 6.1 SLI/SLO/SLA

**Q91: "Explain SLI, SLO, and SLA. How do you define them for Docita?"**

**Answer skeleton:**
"SLI (Service Level Indicator): what you measure (e.g., API latency p95, error rate). SLO (Service Level Objective): the target (e.g., p95 < 500ms, error rate < 0.1%). SLA (Service Level Agreement): the contract with users (e.g., 99.9% uptime). For Docita: SLI = API latency p95, error rate, appointment booking success rate. SLO = p95 < 500ms, error rate < 0.1%, booking success > 99.9%. SLA = uptime commitment (if contractually required)."

---

**Q92: "What is an error budget? How do you use it to make release decisions?"**

**Answer skeleton:**
"Error budget = 1 - SLO. If SLO is 99.9% uptime, error budget is 0.1% (~43 minutes/month). If you've consumed 50% of the budget in the first week, you slow down releases and focus on reliability. If you've consumed <10%, you can ship faster. The trade-off: error budgets balance velocity and reliability. For Docita: track error budget per service, review monthly, adjust release cadence accordingly."

---

**Q93: "How do you set an SLO for API latency? What's the target for a healthcare dashboard?"**

**Answer skeleton:**
"Measure current latency, then set target based on user experience. For a healthcare dashboard: p50 < 100ms (snappy), p95 < 500ms (acceptable), p99 < 2s (slow but functional). SLO: p95 < 500ms for 99% of days. The trade-off: tighter SLO = more engineering effort to maintain. Start with a realistic target based on current performance, then tighten over time."

---

**Q94: "What is the difference between availability SLO and latency SLO?"**

**Answer skeleton:**
"Availability SLO: the percentage of time the service is operational (e.g., 99.9% = 8.76 hours downtime/year). Latency SLO: the percentage of requests that meet the latency target (e.g., 99% of requests < 500ms). Availability measures uptime; latency measures responsiveness. A service can be available but slow (100% uptime, p95 = 5s). Both matter for healthcare: clinicians need the system to be up AND fast."

---

**Q95: "How do you report SLO compliance to non-technical stakeholders?"**

**Answer skeleton:**
"Translate technical metrics to business impact: (1) 'Our system was available 99.95% last month, exceeding our 99.9% target,' (2) 'Average appointment booking time was 200ms, well under our 500ms target,' (3) 'We had 0 data loss incidents.' Use dashboards with green/yellow/red status. Avoid jargon: say 'uptime' not 'availability SLO,' say 'response time' not 'p95 latency.'"

### 6.2 Distributed Tracing

**Q96: "Explain distributed tracing. How does OpenTelemetry work?"**

**Answer skeleton:**
"Distributed tracing tracks a request across multiple services. OpenTelemetry: (1) instruments code with spans (units of work), (2) propagates trace context across service boundaries (HTTP headers), (3) exports traces to a backend (Jaeger, Zipkin, Grafana Tempo). Each span has: name, start time, end time, attributes, status. A trace is a tree of spans showing the full request journey."

---

**Q97: "How do you trace a request across API → worker → provider?"**

**Answer skeleton:**
"Trace context propagation: (1) API creates a trace when the request arrives, (2) API writes the outbox event with trace context, (3) worker reads the event and continues the trace, (4) worker calls the provider and adds a child span. The full trace shows: API processing → outbox write → worker pickup → provider call → completion. Use OpenTelemetry context propagation via W3C Trace Context headers."

---

**Q98: "What is a trace span? How do you instrument a Prisma query?"**

**Answer skeleton:**
"A span is a timed unit of work within a trace. Prisma instrumentation: (1) use OpenTelemetry Prisma instrumentation library, (2) it automatically creates spans for each Prisma query, (3) span attributes include: query text (sanitized), duration, rows affected. Manual instrumentation: `tracer.startSpan('prisma.query').setAttribute('db.statement', query)`. For Docita: instrument Prisma, HTTP requests, and external provider calls."

**Q99: "How do you handle tracing in a healthcare context (PHI in spans)"**

**Answer skeleton:**
"PHI must never appear in trace spans. Sanitize: (1) remove patient names from query text, (2) remove appointment details from attributes, (3) use abstract identifiers (clinic ID, not clinic name). Implementation: OpenTelemetry span processor that scrubs PHI before export. Testing: assert that trace export contains no PHI patterns (name formats, medical terms). The trade-off: less detail in traces, but HIPAA/GDPR compliance."

---

**Q100: "What is the difference between sampling strategies — head-based vs tail-based?"**

**Answer skeleton:**
"Head-based: decide to trace at request start (e.g., trace 1% of requests). Simple, low overhead, but may miss interesting traces. Tail-based: trace all requests, decide to keep/export after processing. More storage, but captures interesting traces (errors, slow requests). For Docita: head-based sampling at 10% for normal traffic, 100% for error responses. This balances cost and visibility."

## Section 7: Security Deep-Dive (20 questions)

### 7.1 Authentication and Authorization

**Q111: "Explain OAuth 2.0 flows. Authorization code vs client credentials vs PKCE."**

**Answer skeleton:**
"Authorization code: user logs in, gets an authorization code, exchanges it for a token. Secure because the code is short-lived and exchanged server-side. PKCE: authorization code + a code verifier/challenge. Prevents authorization code interception (for SPA/mobile). Client credentials: service-to-service, no user involved. For Docita: authorization code with PKCE for the clinician app (SPA), client credentials for API-to-worker communication."

---

**Q112: "What is OIDC? How does it extend OAuth 2.0?"**

**Answer skeleton:**
"OIDC (OpenID Connect) is a layer on top of OAuth 2.0 that adds identity. OAuth 2.0 only handles authorization ('can you access this resource?'). OIDC adds authentication ('who are you?'). OIDC adds: ID token (JWT with user info), userinfo endpoint, standardized scopes (openid, profile, email). For Docita: if integrating with external identity providers (Google, Azure AD), use OIDC. For internal auth, plain JWT is sufficient."

---

**Q113: "Explain RBAC vs ABAC vs ReBAC. How does Docita implement ABAC?"**

**Answer skeleton:**
"RBAC: role-based (admin can do X, user can do Y). Simple but coarse. ABAC: attribute-based (user's clinic + resource's clinic + action = decision). Fine-grained, policy-driven. ReBAC: relationship-based (user is a member of this clinic, which has this relationship to the patient). Natural for social/graph data. Docita uses ABAC: policies evaluate subject attributes (role, clinic, ownership) against resource attributes (clinic_id, created_by). Example: CLINICIAN can only view patients where patient.assigned_clinician_id == subject.id AND patient.clinic_id == subject.clinic_id."

---

**Q114: "How do you handle token refresh in a SPA? What are the failure modes?"**

**Answer skeleton:**
"Refresh flow: (1) access token expires (15min), (2) client detects 401, (3) client sends refresh token (httpOnly cookie) to /auth/refresh, (4) server validates refresh token, issues new access token + refresh token, (5) client retries original request. Failure modes: (1) refresh token expired → force re-login, (2) refresh token stolen → token family tracking invalidates all tokens in the family, (3) server down → client shows 'session expired' message. Implementation: axios interceptor that queues requests during refresh."

---

**Q115: "What is token binding? How does it prevent token theft?"**

**Answer skeleton:**

**Q122: "How do you prevent IDOR in a multi-tenant system?"**

### 8.3 Database Performance

**Q141: "How do you handle a table that's grown to 500GB and queries are slow?"**

**Answer skeleton:**
"Steps: (1) identify slow queries (pg_stat_statements), (2) check indexes (pg_stat_user_indexes), (3) run EXPLAIN ANALYZE on slow queries, (4) options: (a) add missing index, (b) partition the table (by date range for appointments), (c) archive old data (move to separate table/database), (d) add read replica for read-heavy queries, (e) tune PostgreSQL parameters (shared_buffers, work_mem). The key: measure first, don't guess."

---

**Q142: "What is query plan regression? How do you detect and fix it?"**

**Answer skeleton:**
"Regression: a query that was fast becomes slow because the query planner chose a different plan. Causes: (1) table statistics stale (ANALYZE not run), (2) data distribution changed (more rows, different distribution), (3) index was dropped or changed. Detection: (1) pg_stat_statements tracks mean execution time, (2) pganalyze or similar tool, (3) manual EXPLAIN ANALYZE comparison. Fix: (1) run ANALYZE, (2) adjust statistics target, (3) add missing index, (4) use plan hints if needed."

---

**Q143: "How do you optimize a Prisma query?"**

**Answer skeleton:**
"Common pitfalls: (1) `findMany` without `select` (fetches all columns), (2) `include` without `take` (loads all related records), (3) N+1 (loop with individual queries instead of `findMany` with `where: { id: { in: ids } }`), (4) missing index on filtered columns. Optimization: (1) use `select` to fetch only needed columns, (2) use `take` and `skip` for pagination, (3) use `$transaction` for batch operations, (4) enable Prisma query logging to see generated SQL, (5) run EXPLAIN ANALYZE on the generated SQL."

---

**Q144: "How do you tune PostgreSQL shared_buffers, work_mem, and effective_cache_size?"**

**Answer skeleton:**
"shared_buffers: cache for table/index data (default 128MB, set to 25% of RAM). work_mem: memory for sort/hash operations (default 4MB, increase for complex queries). effective_cache_size: estimate of OS cache + shared_buffers (set to 75% of RAM). For Docita: shared_buffers = 1GB (for 4GB RAM server), work_mem = 16MB (for complex patient queries), effective_cache_size = 3GB. Monitor: `pg_stat_bgwriter` for buffer hit ratio (should be >99%)."

---

**Q145: "What is the difference between latency and throughput? How do you optimize for each?"**

**Answer skeleton:**
"Latency: time for one request to complete. Throughput: number of requests per second. Trade-off: optimizing one can hurt the other. Example: batching increases throughput (fewer round trips) but increases latency (wait for batch). For Docita: optimize latency for patient-facing endpoints (schedule view, booking), optimize throughput for background jobs (notification sending, report generation)."

**Q148: "Explain blue-green deployments. How do you handle database migrations with blue-green?"**

**Q150: "Explain event sourcing vs CQRS. When would you use each?"**

Use event sourcing when: (1) you need complete audit trail, (2) you need to time-travel (replay state at any point), (3) events are the primary abstraction. Use CQRS when: (1) read and write patterns differ significantly, (2) you need different query optimizations. For Docita: event sourcing for audit logs (append-only), CQRS if read patterns diverge from write patterns."

**Q169: "Why PostgreSQL over MongoDB for a healthcare SaaS?"**

### 10.2 Implementation Deep Dives

**Q174: "Walk me through the concurrent appointment booking flow — from button click to database constraint."**

**Answer skeleton:**
"(1) User clicks 'Book' → frontend disables button (duplicate-submit protection), (2) TanStack Query sends POST /appointments with idempotency key, (3) API validates DTO (Zod schema), (4) TenantContextInterceptor sets clinic context, (5) ABAC policy checks: subject has RECEPTIONIST role, patient belongs to same clinic, (6) Service opens Prisma transaction, (7) SELECT FOR UPDATE on patient row (locks patient), (8) Check for overlapping appointments (same patient, same time), (9) If overlap → return 409 Conflict, (10) If no overlap → INSERT appointment, INSERT outbox event, COMMIT, (11) Return 201 with created appointment, (12) Worker picks up outbox event, sends notification."

---

**Q175: "How does the TenantContextInterceptor work?"**

**Answer skeleton:**
"(1) Interceptor runs before every request, (2) Reads JWT from Authorization header, (3) Extracts { userId, clinicId, role } from JWT payload, (4) Stores in request-scoped context (AsyncLocalStorage), (5) If RLS enabled: opens Prisma transaction, runs SET app.current_clinic, routes all Prisma calls through that transaction, (6) After request: closes transaction, clears context. Internal users: explicit clinic override via query parameter or header."

---

**Q176: "How does the ABAC policy engine work?"**

**Answer skeleton:**
"Policy file: patient.policy.ts evaluates: (1) subject role (RECEPTIONIST can view, CLINICIAN can edit), (2) subject clinic == resource clinic (cross-clinic denied), (3) ownership/assignment (CLINICIAN can only view assigned patients), (4) action type (create/read/update/delete). Decision: ALLOW, DENY, or NOT_APPLICABLE. DENY returns 403 immediately. NOT_APPLICABLE falls through to the next policy. Tests: seed two clinics, assert cross-clinic denial."

---

**Q177: "How does the outbox relay work? What happens when the worker is down for 30 minutes?"**

**Answer skeleton:**
"Relay: polls outbox table every 5 seconds for unprocessed events, publishes to worker queue. Worker down for 30 minutes: (1) outbox events accumulate (unprocessed), (2) relay continues polling (events stay in table), (3) when worker recovers, relay publishes accumulated events, (4) worker processes events in order (FIFO), (5) all notifications are eventually sent. The key: no events are lost, just delayed. User impact: notifications arrive late, but bookings are never lost."

---

**Q178: "How does the webhook verification system work?"**

**Answer skeleton:**
"(1) Provider sends webhook to POST /webhooks/sendgrid, (2) API extracts signature from header, (3) Verifies HMAC signature against known secret, (4) If signature invalid → return 403, log tampered attempt, (5) If valid: check event ID for deduplication (idempotency), (6) If duplicate → return 200 (acknowledge, don't reprocess), (7) If new: create outbox event atomically, (8) Return 200. Tests: (1) valid signature → 200, (2) tampered signature → 403, (3) duplicate event ID → 200, (4) missing signature → 403."

---

**Q179: "How does the patient list query avoid N+1?"**

**Answer skeleton:**
"Before: SELECT patients WHERE clinic_id = ? → then for each patient: SELECT appointments WHERE patient_id = ?. N+1. After: SELECT patients WHERE clinic_id = ? → then SELECT appointments WHERE patient_id IN (?). Batch fetch. Further optimization: use Prisma's `include: { appointments: true }` with `select` to fetch only needed fields. Monitoring: check-n-plus-1.mjs script runs in CI, fails the build if N+1 patterns are detected."

---

**Q180: "How does the offline service worker work?"**

**Answer skeleton:**
"Service worker: caches the SPA shell (HTML, JS, CSS) on install. On fetch: (1) if cached → return from cache, (2) if not cached → fetch from network, cache response. Offline: returns cached SPA shell, falls back to offline page for API calls. Limitations: (1) no IndexedDB-backed data sync, (2) no offline mutation queue, (3) no conflict resolution. The service worker is for resilience (SPA loads offline), not for offline-first functionality."

**Q181: "How does the notification system handle multi-channel delivery?"**

**Answer skeleton:**
"Outbox event specifies: { type: 'appointment_booked', channels: ['in-app', 'email'], userId, clinicId }. Worker: (1) in-app → insert into notifications table, (2) email → call SendGrid API, (3) SMS → call Twilio API. Each channel: independent retry, independent DLQ. **Q252: "How do you handle backpressure in Node.js streams?"**

Handling: (1) respect the return value of write() — if false, stop writing until 'drain', (2) use pipe() which handles backpressure automatically, (3) use pipeline() for proper error handling and cleanup. For Docita: streams are used for file uploads — backpressure handling prevents memory exhaustion."

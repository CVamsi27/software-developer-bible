Use a project problem to find the lesson you need, then return to the implementation with a specific question. This map supplies design exercises. It does not declare that Docita implements every pattern or that you personally operated each mechanism.

## First Principles

A project problem can illustrate several technical concepts, but copying each concept into the project guide creates competing explanations. A mapping should start from the problem and point to the canonical lesson, while distinguishing observed implementation from a proposed application.

## Follow problem → mechanism → evidence

A delayed confirmation leads to the outbox and retry lessons. Read those lessons, trace the actual booking-to-provider boundary, and collect the evidence described in the [interview evidence pack](80.17-docita-interview-evidence-pack.md). If a pattern is absent, explain when you would introduce it as a proposal.

## Avoid misleading shortcuts

A fixed five-second primary-read window does not guarantee a replica has caught up. Partitioning does not by itself establish tenant isolation. A partial index's size benefit must be measured; changing `NOT IN` to `NOT EXISTS` can change null semantics and does not promise a tenfold speedup.

A database row lock is not automatically a lease with fencing. A notification outage can exhaust a retry budget; durable storage does not promise eventual successful delivery. A circuit breaker closes only according to its recovery policy. Per-tenant rate limits reduce interference but do not guarantee that every other shared resource is unaffected.

An audit log is not necessarily a complete event source. A request identifier is not automatically a propagated distributed trace. Write-through caching and “write database then invalidate” are different mechanisms. An authorized realtime room does not grant every member access to every resource payload.

## Turn one mapping into an exercise

Pick a lesson and state its preconditions. Describe one normal execution, one failure, and one recovery. Then locate the corresponding implementation and a meaningful check. Keep invented incidents, metrics, SLOs, provider names, and deployment arrangements out of the answer.

When studying a proposal, state the trigger and adoption cost. For example, a replica might help a measured read bottleneck, but introduces lag, routing, failover, and operational work. A useful mapping explains those consequences rather than attaching every fashionable pattern to the project.

## Summary

Use the table to choose a canonical lesson from a concrete problem. Trace the mechanism, expose its failure boundary, and verify the actual implementation before claiming experience.

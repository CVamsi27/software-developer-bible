The fastest way to study technical chapters so they stick in interviews is to start from a **real engineering problem in your project** instead of reading textbooks front to back. Use the table below to jump straight from a concrete failure symptom to its single canonical chapter in the study stacks — keeping what your project actually implements cleanly separate from proposed future patterns.

## First Principles

Duplicating technical explanations inside project notes quickly creates stale, conflicting copies. Keep each mechanism in its canonical study-stack chapter, use this map to navigate from symptom to mechanism, and return to your project with a concrete question to verify in code.

## 2. Twelve Technical Shortcuts Interviewers Catch Immediately

Watch out for these subtle half-truths when mapping concepts back to your project:
- A fixed 5-second "read from primary" window does not *guarantee* an asynchronous replica caught up.
- Table partitioning optimizes storage and scans; it does **not** enforce tenant authorization.
- Rewriting `NOT IN` to `NOT EXISTS` fixes Structured Query Language (SQL) `NULL` traps — it does not magically guarantee a 10× speedup.
- `SELECT ... FOR UPDATE SKIP LOCKED` claims a row during one transaction; it is **not** a long-lived worker lease with fencing.
- A durable job table does not guarantee delivery if a downstream provider stays down past the retry budget.
- Per-tenant API rate limits reduce noisy-neighbor bursts without automatically isolating shared database central processing unit (CPU) or connection pools.
- An audit log is not full event sourcing; a request ID is not distributed tracing; write-through caching is not write-then-invalidate; joining a WebSocket room does not authorize every clinical payload inside it.

## 3. Turn Any Row Into a 20-Minute Deep Study Exercise

Pick one row, study its canonical chapter, then trace three things aloud: **(1)** the happy path, **(2)** one real failure and recovery path, and **(3)** whether your current project implements it or what measured bottleneck would justify proposing it next. Attach proof via your [Evidence Pack](80.17-docita-interview-evidence-pack.md).

## Summary

Use concrete project symptoms to pull in the exact canonical study chapter you need, steer clear of common half-truths about locks, replicas, and caches, and keep observed implementation cleanly separated from proposed future patterns.

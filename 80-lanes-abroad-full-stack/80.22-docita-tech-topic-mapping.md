# Docita × Tech Topic Mapping — Every Topic to a Docita Use Case

> How every system design, architecture, and production engineering topic applies to Docita. Use this to answer "how would you apply this?" in interviews.
>
> > **How to use this file honestly (read first).** This is a *design-vocabulary map*: it shows you can apply concepts to the domain. Rows marked **[future]** describe designs that do **not** exist in the codebase yet (Kafka pipelines, partitioning schemes, Stripe, multi-region audit logs, data lake, event sourcing of appointments). Present those as *"here's exactly how I'd introduce X when trigger Y appears"* — never as current practice. Current practice = Postgres queue + transactional outbox + Fly.io + Cloudflare + RDS single-region (see [80.21 fact sheet](80.21-docita-google-level-prep.md)). Column naming: appointments use `slot_start`/`slot_end` (not `scheduled_at`).

Legend: *(no tag)* = grounded in current code · **[future]** = aspirational design exercise

## 1. Database Scaling → Docita

### Partitioning
| Topic                               | Docita Application                                                                                                                                          |
| -------                               | --------------------                                                                                                                                          |
| **Range partitioning** **[future]** | `appointments` partitioned by `slot_start` monthly — at 1,000+ appointments/month this is a "when index scans slow down" conversation, not current practice |
| **Hash partitioning** **[future]**  | `patient_records` by `clinic_id` — aligns with multi-tenant isolation if table growth demands it                                                            |
| **List partitioning** **[future]**  | `audit_logs` by region — presupposes multi-region residency requirements that don't exist today (single-region, ADR 0006)                                   |

### Replication
| Topic                        | Docita Application                                                                                                                                            |
| -------                        | --------------------                                                                                                                                            |
| **Streaming replication**    | Read replica for the clinician dashboard — calendar views are read-heavy; replica takes the read load off the primary                                         |
| **Logical replication**      | Replicate appointment data to an analytics database — the worker needs appointment stats without slowing down the primary                                     |
| **Replication lag handling** | After booking an appointment, read from primary for 5 seconds (session stickiness), then allow reads from replica — prevents "I just booked but don't see it" |

### Connection Pooling
| Topic                          | Docita Application                                                                                                                |
| -------                          | --------------------                                                                                                                |
| **PgBouncer transaction mode** | 25 clinics × 10 concurrent users = 250 app connections, but PostgreSQL only needs ~20 database connections; PgBouncer multiplexes |
| **Pool exhaustion**            | Peak hours (8-10 AM clinic opening) cause connection spikes; pool monitoring alerts when >80% utilized                            |
| **Statement timeout**          | A complex patient search query hangs; `statement_timeout = 5s` kills it before it holds a connection                              |

### Query Optimization
| Topic               | Docita Application                                                                                                                                |
| -------               | --------------------                                                                                                                                |
| **Composite index** | `CREATE INDEX idx_appt_clinic_scheduled ON appointments (clinic_id, slot_start DESC)` — every calendar query filters by clinic + date             |
| **Partial index**   | `CREATE INDEX idx_appt_active ON appointments (clinic_id, slot_start) WHERE status = 'confirmed'` — only indexes active appointments, 60% smaller |
| **EXPLAIN ANALYZE** | Patient list query degrades at 10K records; EXPLAIN reveals seq scan — adding index on `(clinic_id, last_name)` fixes it                          |
| **Query rewriting** | `NOT IN (subquery)` for "patients without appointments" → rewrite to `NOT EXISTS` for 10x speedup                                                 |

## 2. Resilience Patterns → Docita

### Circuit Breaker
| Topic                             | Docita Application                                                                                                                                                   |
| -------                             | --------------------                                                                                                                                                   |
| **Notification provider**         | SendGrid goes down → circuit breaker trips after 5 failures → booking still works, emails queued in outbox → SendGrid recovers → circuit closes → emails send        |
| **Payment provider** **[future]** | Razorpay API slow → circuit breaker opens → billing UI shows "payments temporarily unavailable" instead of hanging for 30s (today: retries/backoff + DLQ cover this) |
| **External lab API**              | Lab results integration fails → circuit opens → clinician sees "lab data pending" → lab API recovers → results flow again                                            |

### Bulkhead Isolation
| Topic                         | Docita Application                                                                                                                              |
| -------                         | --------------------                                                                                                                              |
| **Separate connection pools** | Notification provider gets 10 connections, payment provider gets 5, database gets 20 — if notifications exhaust their pool, payments still work |
| **Per-clinic rate limiting**  | Clinic A sends 1,000 requests/min (misbehaving script) → rate limiter isolates them → Clinics B-Z unaffected                                    |

### Retry with Backoff
| Topic                        | Docita Application                                                                                          |
| -------                        | --------------------                                                                                          |
| **Email delivery**           | SendGrid returns 503 → retry after 1s, 2s, 4s → third attempt succeeds → appointment confirmation delivered |
| **File upload**              | Pre-signed URL upload fails (network blip) → retry with exponential backoff → file eventually uploads       |
| **Database transient error** | PostgreSQL returns "too many connections" → retry after 500ms → connection freed → query succeeds           |

### Idempotency
| Topic                     | Docita Application                                                                                                                    |
| -------                     | --------------------                                                                                                                    |
| **Double-submit booking** | User clicks "Book" twice → idempotency key in header → server detects duplicate → returns same 201 response, no duplicate appointment |
| **Webhook verification**  | Payment webhook arrives twice (Razorpay retries) → event-ID + idempotency dedupe → invoice marked as paid once                        |
| **Notification dedup**    | Same outbox event processed twice (worker crash + restart) → idempotency check → one email sent, not two                              |

## 3. Leader Election & Consensus → Docita

### Leader Election
| Topic                           | Docita Application                                                                                                                         |
| -------                           | --------------------                                                                                                                         |
| **Cron job coordination**       | 3 API instances running → only one should run the daily appointment reminder cron → database-based leader election ensures single executor |
| **Outbox relay**                | Multiple workers polling the outbox → leader election ensures only one worker processes each batch → prevents duplicate notifications      |
| **Scheduled report generation** | Monthly clinic reports → leader election ensures one worker generates, others skip                                                         |

### Distributed Locks
| Topic                              | Docita Application                                                                                                                     |
| -------                              | --------------------                                                                                                                     |
| **Concurrent appointment booking** | Two receptionists book same patient → `SELECT FOR UPDATE` on patient row → second transaction waits → conflict detected → 409 returned |
| **Patient record export**          | Admin exports all patient data → distributed lock prevents concurrent export of the same clinic's data (resource-intensive operation)  |
| **Schema migration**               | Prisma migrate acquires a lock → prevents concurrent migrations → ensures schema consistency                                           |

### Fencing Tokens
| Topic                     | Docita Application                                                                                                                                                |
| -------                     | --------------------                                                                                                                                                |
| **Stale lock prevention** | Lock holder's process pauses (GC) → lock expires → another process acquires lock → first process resumes → fencing token prevents it from writing with stale lock |

## 4. Event-Driven Architecture → Docita

### Kafka / Message Brokers
| Topic                                   | Docita Application                                                                                                                                                |
| -------                                   | --------------------                                                                                                                                                |
| **Appointment events**                  | `APPOINTMENT_CREATED`-style events already flow through the **transactional outbox** → relay → consumers (notifications, audit). Present tense: outbox, not Kafka |
| **Partition by clinic_id** **[future]** | If event volume ever demands a broker: partition by clinic for per-clinic ordering + cross-clinic parallelism — name the trigger first ("relay lag SLO breach")   |
| **Consumer groups** **[future]**        | Same framing: today the worker *is* the consumer; independent scaling groups arrive with real volume                                                              |

### Event Sourcing
**[future]** — current practice is an append-only `audit_logs` table + explicit state columns, not full event sourcing. If asked:
| Topic                       | Docita Application                                                                                                                                                                            |
| -------                       | --------------------                                                                                                                                                                            |
| **Appointment audit trail** | Today: append-only audit records every transition (scheduled → confirmed → completed) for compliance; full ES replay would come only if temporal reconstruction becomes a product requirement |
| **Patient record history**  | "Who changed this phone number and when?" is answerable from audit logs today                                                                                                                 |

### CQRS
| Topic                     | Docita Application                                                                                                                                             |
| -------                     | --------------------                                                                                                                                             |
| **Read/write separation** | Write model: normalized tables for booking integrity. Read model: denormalized calendar view for fast rendering. Writes go to primary, reads from projection.  |
| **Dashboard performance** | Clinic dashboard needs aggregated stats (appointments today, revenue this week, patients seen) → pre-computed projection → O(1) reads instead of complex JOINs |

### Dead Letter Queues
| Topic                       | Docita Application                                                                                                               |
| -------                       | --------------------                                                                                                               |
| **Poison message handling** | Malformed notification event → fails 3 times → moves to DLQ → alert fires → developer investigates → fix deployed → DLQ replayed |
| **Provider outage**         | SendGrid down for 2 hours → events accumulate in queue → on recovery, batch process → no data loss                               |

## 5. Production Engineering → Docita

### Incident Response
| Topic                        | Docita Application                                                                                                                    |
| -------                        | --------------------                                                                                                                    |
| **SEV1: Database down**      | All clinics can't book → incident commander assigned → status page updated → fallback to read replica → primary restored → postmortem |
| **SEV2: Slow queries**       | One clinic's patient list takes 10s → identified as missing index after migration → hotfix deployed → query back to 200ms             |
| **SEV3: Notification delay** | Emails arriving 30 min late → worker backlog growing → scale worker machines → backlog cleared → root cause: SendGrid rate limit      |

### SLIs, SLOs, Error Budgets
| Topic                  | Docita Application                                                                                                    |
| -------                  | --------------------                                                                                                    |
| **Availability SLO**   | 99.9% uptime = 43 min/month downtime. Error budget: if 20 min consumed in first week, reduce deployment frequency     |
| **Latency SLO**        | 99th percentile booking API < 500ms. If p99 exceeds 500ms, investigate query performance before shipping new features |
| **Error rate SLO**     | <0.1% 5xx responses. If error budget is 50% consumed, code freeze until reliability improves                          |
| **Burn rate alerting** | Error rate spike at 14x normal → page on-call immediately. Gradual increase at 3x → create ticket for investigation   |

### Chaos Engineering
| Topic                 | Docita Application                                                                                                    |
| -------                 | --------------------                                                                                                    |
| **Redis failure**     | Kill Redis in staging → verify booking still works (falls back to DB) → verify cache warming works on recovery        |
| **Network partition** | Simulate API-to-DB latency spike → verify timeout handling → verify circuit breaker on notification provider trips    |
| **Pod kill**          | Randomly kill API machines during load test → verify Fly reschedules them → verify no booking failures during restart |

## 6. Caching → Docita

### Cache Patterns
| Topic                           | Docita Application                                                                                                                    |
| -------                           | --------------------                                                                                                                    |
| **Cache-aside for schedules**   | Clinician opens calendar → check Redis for `cache:clinic:{id}:schedule:{practitionerId}` → miss → query DB → populate cache (30s TTL) |
| **Write-through for config**    | Admin updates clinic settings → write to DB + invalidate cache simultaneously → next read gets fresh data                             |
| **No caching for patient data** | Patient records contain PHI and must be real-time → always read from DB → never cache at application level                            |

### Cache Invalidation
| Topic                        | Docita Application                                                                                               |
| -------                        | --------------------                                                                                               |
| **Event-based invalidation** | Appointment booked → outbox event → notification worker invalidates schedule cache → next calendar load is fresh |
| **Multi-tenant keys**        | `cache:clinic:{clinicId}:schedule:{practitionerId}` — invalidating Clinic A's cache never affects Clinic B       |
| **TTL jitter**               | 25 clinics' caches don't all expire at :00 → add random 0-10s jitter → prevents thundering herd at cache expiry  |

### Stampede Prevention
| Topic                      | Docita Application                                                                                                                       |
| -------                      | --------------------                                                                                                                       |
| **Mutex lock**             | 10 receptionists open the same clinic calendar simultaneously → first request populates cache, others wait 100ms → one DB query, not ten |
| **Stale-while-revalidate** | Cache expired → return stale schedule (30s old) while refreshing in background → clinician never sees loading spinner                    |

## 7. Zero-Downtime Deployments → Docita

### Blue-Green
| Topic                | Docita Application                                                                                                         |
| -------                | --------------------                                                                                                         |
| **API deployment**   | Deploy v2 alongside v1 → switch traffic → if error rate spikes → instant rollback to v1 → zero downtime                    |
| **Schema migration** | Expand phase: add column, deploy code that writes both columns → verify → contract phase: remove old column in next deploy |

### Canary
| Topic               | Docita Application                                                                                                  |
| -------               | --------------------                                                                                                  |
| **Feature rollout** | New booking flow → 10% of clinics get it → monitor error rates and booking success → if healthy, roll to 50% → 100% |
| **Risk mitigation** | Healthcare product = can't afford bugs → canary reduces blast radius to 10% of users                                |

### Feature Flags
| Topic               | Docita Application                                                                                               |
| -------               | --------------------                                                                                               |
| **Gradual rollout** | `new-calendar-view` flag → enabled for internal team first → then 3 clinics → then all                           |
| **Kill switch**     | New notification template causes complaints → disable flag instantly → revert to old template → no deploy needed |
| **A/B testing**     | Two booking flows → flag splits users → measure conversion rate → pick winner                                    |

### Expand-Contract Migrations
| Topic             | Docita Application                                                                                                              |
| -------             | --------------------                                                                                                              |
| **Column rename** | Rename `slot_time` to `slot_start` → add new column → backfill → deploy code reading both → remove old column                   |
| **Table split**   | Break `patients` table into `patients` + `medical_records` → add foreign key → migrate data → update queries → drop old columns |

## 13. System Design (Case Studies) → Docita

### Appointment Scheduling System
| Design Decision               | Docita Choice                                                        | Trade-off                                                                        |
| ----------------                | ---------------                                                        | -----------                                                                        |
| **Lock ordering**             | Patient → Practitioner → Room                                        | Prevents deadlocks; if order changes, deadlocks can occur                        |
| **Optimistic vs pessimistic** | Pessimistic (SELECT FOR UPDATE) for booking                          | Correctness over throughput; at 10x scale, switch to optimistic with retry       |
| **Read path**                 | Composite index `(clinic_id, practitioner_id, scheduled_at)` + cache | Calendar loads in <100ms; cache hit rate >95%                                    |
| **Write path**                | Single transaction with outbox event                                 | Atomic booking + notification trigger; if outbox write fails, booking rolls back |

### Notification System
| Design Decision    | Docita Choice                                        | Trade-off                                             |
| ----------------     | ---------------                                        | -----------                                             |
| **Async vs sync**  | Async via outbox                                     | Booking never fails because email provider is down    |
| **Retry strategy** | Exponential backoff, max 5 attempts                  | Balance between delivery guarantee and resource usage |
| **DLQ**            | Manual investigation after 5 failures                | Prevents poison messages from blocking the queue      |
| **Multi-channel**  | In-app (WebSocket) + email (SendGrid) + SMS (Twilio) | In-app is real-time, email/SMS are best-effort        |

### Multi-Region (Future)
| Design Decision      | Docita Choice                          | Trade-off                                                                              |
| ----------------       | ---------------                          | -----------                                                                              |
| **Data residency**   | Patient data pinned to clinic's region | GDPR compliance; cross-region reads are eventual                                       |
| **Schema migration** | Expand/contract across all regions     | Backward-compatible code must work with old + new schema in all regions                |
| **Failover**         | Regional primary with read replicas    | If EU region goes down, EU clinics are unavailable (correct for healthcare compliance) |

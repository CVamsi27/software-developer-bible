# Review a Take-Home Before Handoff

[![Role priority](https://img.shields.io/badge/role--priority-Important-blue)](../docs/topic-importance.md)
[![General importance](https://img.shields.io/badge/general--importance-Important-blue)](../docs/topic-importance.md)

A great solution can still fail review if the interviewer clones your repo, runs `npm start`, hits a missing environment variable or undocumented migration step, and gives up after ten minutes. Use [Take-Home Playbook](80.01-take-home-playbook.md) while building and [Workflow Portfolio Starter](80.15-take-home-starter-prompt.md) for practice; use this checklist in the **final 45–60 minutes** before submitting to make sure your handoff runs cleanly on a stranger's machine.

## First Principles

A reviewer can only judge what they can actually execute. A working clean-checkout setup, targeted failure tests, and a clear explanation of your main trade-off beat impressive prose every time — no README can rescue code that fails to start.

## 1. Run a True Clean-Checkout Rehearsal

Never trust *"it works in my editor"* — your local shell already has `.env`, running Postgres tables, and global packages installed. Clone your repo (or unzip your archive) into a brand-new temporary directory and follow your own README step by step:

```text
Clean folder ─► Install pinned deps ─► Setup/Seed DB ─► Run sample happy path ─► Trigger 1 failure case ─► Run tests
```

Fix every hidden assumption you discover (missing `.env.example` keys, wrong Node version note, forgotten seed script, hardcoded local port) and record the exact commands that passed.

## 2. Verify the Risky Contracts Your Brief Actually Asked For

Test only the failure modes relevant to the assignment — do **not** bolt on unrequested auth, Docker, or Kafka just to look senior:

| If the brief includes… | Prove this before submitting |
| ------------------------------- | ----------------------------------------------------------------------------------------------------------- |
| **CRUD / API endpoints** | Invalid input returns clear 4xx error; missing resource returns 404; illegal state transitions fail cleanly |
| **Competing writes / bookings** | Two distinct concurrent requests cannot break capacity; repeated requests obey idempotency |
| **Workflow / job execution** | Failed step leaves explicit error status; run uses immutable input/version snapshot |
| **Multi-tenant data** | Tenant B cannot read or mutate Tenant A's record through the real query layer |
| **Realtime updates** | Disconnect and reconnect recover cleanly without corrupting UI state |
| **External API calls** | Timeouts are bounded, retries are classified, and unknown remote outcomes are documented clearly |

Quality comes from tests that would catch a real bug in your core invariant — not a padded test count.

## 3. Structure a 1-Page Reviewer README

Keep sections short, scannable, and in the order a busy reviewer reads them:
1. **Scope:** What works today (and anything intentionally deferred within the timebox).
2. **Prerequisites & Quickstart:** Exact runtime version (e.g., Node 24) and copy-paste commands to install, configure `.env.example`, migrate/seed, and start.
3. **Sample request / walkthrough:** One `curl` command or UI flow with its expected response.
4. **Verification:** Exact test/lint/typecheck commands that actually exist in `package.json` (never paste made-up script names).
5. **Key design decision & trade-off:** The one choice protecting correctness and what alternative you skipped.
6. **Next steps:** What you would add first for production scale.

## 4. Keep Time Reporting and Walkthrough Honest

Reserve handoff time *inside* the assignment's stated budget (for instance, in a 6-hour exercise: 30 min scope, 3 hr core build, 1 hr failure tests, 1 hr setup/README, 30 min clean-checkout check). If a setup snag eats into your time, cut optional polish and state your exact hours and remaining limits openly rather than silently working overnight.

During the follow-up review call, walk through **one user problem → your enforcing invariant → one failure mode you tested → one known limitation**. Naming a known edge case clearly scores far higher than trying to hide it.

## Summary

Always rehearse your take-home from a fresh checkout before submitting, verify the real failure contracts requested by the brief instead of adding unrequested infrastructure, and ship a short, accurate README that lets a reviewer run, test, and understand your trade-offs in minutes.

# Review a Take-Home Before Handoff

[![Role priority](https://img.shields.io/badge/role--priority-Important-blue)](../docs/topic-importance.md)
[![General importance](https://img.shields.io/badge/general--importance-Important-blue)](../docs/topic-importance.md)



A reviewer should be able to start the project, exercise the required behavior, and understand one important decision. This guide covers the handoff. Use the [take-home playbook](80.01-take-home-playbook.md) for execution and the [workflow starter](80.15-take-home-starter-prompt.md) for a bounded practice brief.

## First Principles

A reviewer must be able to reproduce the delivered behavior before evaluating the design. The handoff therefore needs a working run path, focused verification and explicit limits; adding explanation cannot compensate for instructions that do not run.

## Review from a clean start

Use the submitted files and documented prerequisites rather than your already-running development environment. Follow the instructions literally. Check that configuration placeholders, database setup, seed data, and start commands match the actual project and pinned dependencies.

```text
fresh checkout → setup → sample behavior → failure case → design explanation
```

Record what ran and what did not. Do not promise a two-minute startup, “production quality,” or passing every take-home unless evidence and scope support that statement. A local demo can be useful with clearly stated limits.

## Test the required contract

| Assignment behavior | Handoff check |
| ----------------------------------------- | ------------------------------------------------------------------------------------------------- |
| Create/read/update/delete (CRUD) resource | Invalid input, missing resource, supported state transitions and required access rules |
| Competing writes | Distinct requests enforce the shared invariant; repeated requests follow the idempotency contract |
| Workflow | Failed step, immutable run input/version, bounded work and visible outcome |
| Tenant access | Another tenant's resource is denied through the actual data path |
| Realtime update | Disconnect and reconciliation behavior match the stated contract |
| External provider | Timeout, retry classification and uncertain acceptance are explained |

Select the relevant rows from the actual brief. Do not add authentication, refresh rotation, a broker, event sourcing, Docker, or a second application merely to satisfy a generic checklist. Those features consume time and introduce contracts that may be outside the assignment.

A percentage or test count is not the quality target. A meaningful check should be capable of exposing a failure in the behavior you claim.

## Write a short reviewer README

Keep the instructions in this order:

1. What the submitted slice does and its scope.
2. Required prerequisites and exact setup/start commands.
3. One sample interaction and its expected result.
4. How to run the relevant checks and what they cover.
5. The most consequential design decision and its tradeoff.
6. Known limitations and the next justified improvement.

Use the commands that exist in this repository. Do not paste a generic `npm test:e2e` command and label it integration testing without checking its actual target. Environment variables hold deployment-dependent configuration and secrets; ordinary named constants need not all become environment variables.

## Keep the time budget honest

Reserve time for the handoff inside the assignment limit. A hypothetical six-hour allocation could be thirty minutes to interpret the brief, three hours to build the required slice, one hour for focused failure checks, one hour for setup/docs, and thirty minutes for final review. The total is six hours; it is a planning example, not a speed guarantee.

If setup or a defect takes longer, remove optional scope and state the remaining limit. Do not exceed a requested timebox silently and then present the extra work as if it fit. Follow the actual assistance policy and disclose tools as required.

## Walk through one decision

Explain the user's need, the constraint, your mechanism, its failure boundary, and the check that supports it. Demonstrate a failure as well as a successful path. A known gap is easier to assess when stated precisely than when hidden behind a large architecture diagram or a “strong hire” label.

## Summary

Reproduce setup from the submitted artifact, check the required failure contracts, and hand off a short README with truthful scope and results. The assignment's actual requirements determine what belongs.

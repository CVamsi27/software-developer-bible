# Brush Up Without Rereading the Whole Library

[![Role priority](https://img.shields.io/badge/role--priority-Important-blue)](../docs/topic-importance.md)
[![General importance](https://img.shields.io/badge/general--importance-Important-blue)](../docs/topic-importance.md)



Brushup starts with an attempt to recall or apply a mechanism. Use the gap you observe to choose the next chapter. A fixed thirty-day schedule cannot guarantee that every file has been learned; the earlier roadmap listed only a subset and pointed to many retired flat paths.

## First Principles

Familiarity with a chapter does not establish unaided recall or transfer to a changed case. A brushup must expose the missing mechanism first, then use a focused read and another attempt to determine whether the gap was repaired.

## Prioritize the Full-Stack Resume Route

For product-focused TypeScript/React/Node.js roles, start with the mechanisms your resume makes interviewable. Follow the order below; the exercises expose whether a topic needs reading. Do not read all linked stacks in full before practicing. Use their category flow to learn the missing mechanism, then retry the task. Scope tricky topics to their actual semantics: TypeScript types do not validate runtime input, an effect is not the default home for derived state, a transaction does not automatically prevent every race, and a test count does not establish production correctness.

## Reuse One Practical Rehearsal Across the Route

Use synthetic clinic/appointment data in a small full-stack rehearsal. Begin with one form and a paginated list, then add authenticated tenant scope and a booking operation. Change one assumption at a time: a slow earlier search response, duplicate submit, a different user competing for the slot, and a worker/provider interruption. The point is to expose a boundary, not build another hospital platform.

Keep the minimum evidence: runnable instructions, the invariant, one allowed and denied case, a controlled concurrency test where required, and a concise explanation of the failure/recovery path. Use a real local database for database locking/isolation claims. Label mocked provider behavior as mocked and keep remote delivery outcomes uncertain until reconciled.

After implementing a slice, give a two-minute explanation: problem, constraint, mechanism, failure boundary, tradeoff and observed result. Then change one assumption and explain which part must change. If the explanation falls back to a framework list or an unsupported resume number, return to that specific source/evidence gap.

Fit this into the existing study plan's budget. A confirmed frontend loop moves interface work ahead of queue detail; a backend/data loop deepens transactions and authorization; a founding/full-stack loop emphasizes prioritization and delivery across boundaries. Reading priority follows the actual role rather than an assumed national interview style.

## Check senior readiness with changed constraints

Use the [mock interview script](80.30-mock-interview-script.md) to rehearse the role you are targeting. Score each dimension from observed work, then choose the next chapter from the weakest dimension.

| Dimension | Evidence to produce |
| ---------------- | ----------------------------------------------------------------------------------------------------- |
| Mechanism | Trace one operation, including who owns state and where authorization occurs |
| Implementation | Produce a working slice with a clear invariant, meaningful checks and bounded resource use |
| Failure analysis | Change a condition, explain the resulting failure, and demonstrate recovery or a deliberate rejection |
| Judgment | Compare a viable alternative using correctness, latency, cost and operational constraints |
| Ownership | Connect a resume claim to your contribution, an artifact and an observed outcome |

Use **0** for an incorrect or missing explanation, **1** for a correct happy-path account, **2** for a correct response to a changed constraint, and **3** for a defended decision with evidence and explicit limits. Treat a 0 or 1 as a concrete practice gap. This is a self-assessment scale, not an employer's scoring system.

For frontend roles, change request order, lose a mutation response, or navigate the form with a keyboard. For backend roles, use two competing writes, a repeated callback, or a worker crash after an external effect. For full-stack ownership, introduce a mixed-version release or incomplete telemetry. Explain the new boundary before choosing another tool. Resume technologies should lead to this depth of reasoning; optional topics can wait until the vacancy calls for them.

## Diagnose before reading

Pick a category from its learning-flow INDEX. Try one question in its separate `REVISION.md` or explain a small unfamiliar example. Name the assumption you could not justify. Then read the relevant chapter and try a changed case.

```text
recall or apply → identify the missing mechanism → focused reading
  → changed example → later recall
```

If the topic is new, begin with the category's introductory chapters instead of treating repeated failure as brushup. Revision tests recall after learning; it does not replace an explanation.

## Keep the reading session small

Choose one mechanism and one useful output: a trace, a comparison, a corrected example, or a short explanation. Read until you can explain the missing step. Return to the exercise rather than highlighting an arbitrary three facts in every file.

For example, a failed same-slot booking explanation might require distinguishing idempotency from a capacity invariant. Read the relevant transaction lesson, trace two distinct requests, and state what prevents the conflicting commits. Do not expand that session into every database feature unless another gap calls for it.

## Record what changed

| Record | Useful detail |
| ----------- | ---------------------------------------------------- |
| Attempt | The question or scenario you tried without notes |
| Gap | The incorrect assumption or missing step |
| Source | The canonical chapter used to resolve it |
| New attempt | A changed case and what you explained or implemented |
| Recheck | A later recall task within the available budget |

Keep actual progress in private records and use the [study plan](80.13-study-plan.md) for one time budget. Completing a read or recognizing an answer is a different observation from applying it correctly. Revise priorities when mocks or real work expose a more consequential gap.

## Summary

Use revision to locate a gap, canonical chapters to learn the mechanism, and changed examples to check transfer. Follow the INDEX flows rather than an oversized list of stale filenames.

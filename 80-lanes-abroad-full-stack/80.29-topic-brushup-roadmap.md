# Brush Up Without Rereading the Whole Library

[![Role priority](https://img.shields.io/badge/role--priority-Important-blue)](../docs/topic-importance.md)
[![General importance](https://img.shields.io/badge/general--importance-Important-blue)](../docs/topic-importance.md)

Trying to reread 680 chapters before an interview guarantees burnout and shallow recall. The smart way to brush up is **diagnostic first, reading second**: try one small closed-book exercise, see the exact step where you stumble, read *only* the canonical chapter that fixes that gap, and re-test on a mutated constraint.

## First Principles

Recognizing an explanation while reading feels like mastery, yet falls apart the moment an interviewer asks you to apply it to a slightly different bug. Real brushup follows a short loop: **cold attempt → pinpoint missing mechanism → targeted read → changed-case re-attempt → delayed recall**.

Remember four classic full-stack traps while brushing up: TypeScript types vanish at runtime, `useEffect` is rarely the right home for derived state, a database transaction alone doesn't prevent every race condition, and a passing mocked SQL test does not prove real PostgreSQL locking behavior.

## 2. Reuse One Tiny Practice App Across All Nine Passes

Build one small synthetic appointment/booking slice (form + paginated list + tenant auth + booking write), then stress-test it by changing one constraint at a time: a slow earlier search response, a duplicate submit, two different users booking the same slot against a real local PostgreSQL database, and a simulated provider crash. After each slice, deliver a 2-minute spoken summary (**problem → constraint → mechanism → failure boundary → trade-off**).

## Check senior readiness with changed constraints

*(Heading kept stable for incoming links.)* Use the [Mock Interview Script](80.30-mock-interview-script.md) to evaluate yourself across five observable dimensions, then spend next week's budget on your lowest score:

| Dimension | What Level 3 readiness actually looks like |
| -------------------- | --------------------------------------------------------------------------------------------------------------- |
| **Mechanism** | Traces state ownership, authorization, and data flow accurately end to end |
| **Implementation** | Delivers a clean, bounded working slice with tests that can catch real invariant bugs |
| **Failure analysis** | Mutates a constraint (race, crash, disconnect, version skew) and designs safe recovery or fail-closed rejection |
| **Judgment** | Compares a viable alternative using correctness, latency, cost, and ops complexity |
| **Ownership** | Ties every resume claim to your exact contribution, verifiable proof, and honest limits |

**Simple 0–3 self-check scale** (a practice tool, not an employer rubric): **0** = missing/wrong, **1** = happy path only, **2** = handles one changed constraint cleanly, **3** = defended trade-off with clear limits and evidence. Treat any `0` or `1` as your immediate next study target.

## Summary

Never reread the whole library passively. Start with a closed-book exercise from the 9-pass full-stack route, score yourself honestly on changed-constraint readiness (`0–3`), study only the single canonical chapter that closes your weakest gap, and prove transfer on a new variation before moving on.

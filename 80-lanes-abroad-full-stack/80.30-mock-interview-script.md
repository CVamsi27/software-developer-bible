# Mock Interview Script — Senior Full-Stack Engineer

> **How to use:** Record yourself answering each question. Time yourself. Follow the scoring rubric to self-evaluate. Practice until you can answer every question within the time limit with confidence.

---

## Setup

- **Duration:** 60 minutes (10 questions × 6 minutes each)
- **Format:** 1 minute to think, 3-4 minutes to answer, 1-2 minutes for follow-ups
- **Recording:** Use your phone or laptop to record audio/video
- **Scoring:** Rate yourself 1-5 on each dimension after each question

---

## Question 1: System Design (10 min)

**Interviewer:** "Design a multi-tenant appointment booking system that handles concurrent bookings from multiple clinics. Walk me through the architecture from frontend to database."

**What to cover:**
- Multi-tenant isolation (shared schema vs database-per-tenant)
- Concurrent booking handling (SELECT FOR UPDATE, optimistic locking)
- Outbox pattern for async notifications
- API → Worker separation
- Database schema design

**Follow-up probes:**
- "What happens if two receptionists book the same slot simultaneously?"
- "How do you prevent one clinic from affecting another's performance?"
- "How would you scale this to 500 clinics?"

**Scoring (1-5):**
| Dimension | Criteria |
|-----------|----------|
| **Architecture** | Clear separation of concerns, appropriate patterns |
| **Concurrency** | Correctly handles race conditions |
| **Scalability** | Addresses growth from 25 → 500 clinics |
| **Trade-offs** | Explains why choices were made |
| **Communication** | Clear, structured, no jargon without explanation |

## Question 2: PostgreSQL Deep-Dive (6 min)

**Interviewer:** "Explain how MVCC works in PostgreSQL. How does it handle concurrent reads and writes without locking?"

**What to cover:**
- Transaction IDs (xmin, xmax)
- Snapshot isolation
- Visibility rules
- Dead tuples and VACUUM
- Trade-offs (bloat vs concurrency)

**Follow-up probes:**
- "What happens if a long-running transaction blocks VACUUM?"
- "How does this affect the appointment booking flow?"
- "What's the difference between READ COMMITTED and REPEATABLE READ?"

**Scoring (1-5):**
| Dimension | Criteria |
|-----------|----------|
| **Depth** | Explains internals, not just surface-level |
| **Accuracy** | Correct about xmin/xmax, visibility rules |
| **Practical** | Connects to Docita's booking scenario |
| **Trade-offs** | Acknowledges limitations |

## Question 3: Caching Strategy (6 min)

**Interviewer:** "How would you implement caching for a healthcare SaaS? What would you cache, what wouldn't you, and why?"

**What to cover:**
- What to cache: practitioner schedules, clinic settings (read-heavy, changes infrequently)
- What NOT to cache: patient data (PHI sensitivity, freshness required)
- Cache patterns: cache-aside, write-through, write-behind
- Cache invalidation strategies
- TTL decisions

**Follow-up probes:**
- "How do you handle cache stampede?"
- "What happens when a practitioner's schedule changes mid-day?"
- "How do you ensure cache consistency across multiple API instances?"

**Scoring (1-5):**
| Dimension | Criteria |
|-----------|----------|
| **PHI awareness** | Correctly identifies what NOT to cache |
| **Patterns** | Knows cache-aside vs write-through |
| **Invalidation** | Has a strategy for stale data |
| **Performance** | Understands TTL and stampede prevention |

## Question 4: Kafka & Event-Driven Architecture (6 min)

**Interviewer:** "Explain the outbox pattern. Why did you choose it over direct provider calls or CDC?"

**What to cover:**
- Problem: direct calls fail when providers are down
- Solution: write event + business data atomically
- Outbox relay polls and publishes
- Comparison: outbox relay vs CDC (Debezium)
- Failure modes and recovery

**Follow-up probes:**
- "What happens if the outbox relay crashes?"
- "How do you handle duplicate events?"
- "At what scale would you switch to CDC?"

**Scoring (1-5):**
| Dimension | Criteria |
|-----------|----------|
| **Problem framing** | Explains WHY outbox is needed |
| **Implementation** | Correct atomic write + relay |
| **Trade-offs** | Compares outbox vs CDC |
| **Failure modes** | Addresses crash, duplicates, growth |

## Question 5: Security & Multi-Tenancy (6 min)

**Interviewer:** "How do you ensure tenant isolation on every API call and database query? What are the failure modes?"

**What to cover:**
- JWT-based tenant context
- TenantContextInterceptor (AsyncLocalStorage)
- Prisma global filters or RLS
- ABAC policies
- Failure modes: missing filter, cross-clinic join

**Follow-up probes:**
- "What if a developer forgets to add clinic_id to a query?"
- "How do you test for cross-clinic data leaks?"
- "How does Row-Level Security work in PostgreSQL?"

**Scoring (1-5):**
| Dimension | Criteria |
|-----------|----------|
| **Zero-trust** | Doesn't rely on developers remembering |
| **Defense in depth** | Multiple layers (middleware + DB) |
| **Testing** | Has E2E tests for cross-clinic access |
| **PHI protection** | Understands regulatory requirements |

## Question 6: API Design (6 min)

**Interviewer:** "How do you version a REST API? When would you choose URL versioning vs header versioning vs additive-only?"

**What to cover:**
- URL versioning: `/api/v1/`, `/api/v2/`
- Header versioning: `Accept: application/vnd.api+json;version=2`
- Additive-only: add fields, never remove
- Expand/contract pattern for migrations
- Deprecation strategy

**Follow-up probes:**
- "How do you migrate clients without breaking them?"
- "What's the expand/contract pattern?"
- "How do you handle backward-compatible schema evolution?"

**Scoring (1-5):**
| Dimension | Criteria |
|-----------|----------|
| **Approaches** | Knows all three versioning strategies |
| **Trade-offs** | Explains when to use each |
| **Migration** | Has a plan for zero-downtime changes |
| **Client experience** | Considers developer experience |

- "How do you handle PHI in distributed traces?"

**Scoring (1-5):**
| Dimension | Criteria |
|-----------|----------|
| **Methodology** | Knows RED and USE |
| **SLOs** | Can define and track SLIs/SLOs |
| **Alerting** | Prevents fatigue, actionable alerts |
| **PHI** | Sanitizes traces and logs |

## Question 8: Testing Strategy (6 min)

**Interviewer:** "How do you test concurrent appointment booking? Walk me through the test design from unit to load testing."

**What to cover:**
- Unit test: business logic isolation
- Integration test: two concurrent Prisma transactions
- E2E test: two Playwright contexts, same slot
- Load test: k6 with 50 VUs
- Assertion: exactly 1 succeeds (201), rest fail (409)

**Follow-up probes:**
- "How do you test tenant isolation?"
- "How do you test the outbox pattern?"
- "How do you test PHI scrubbing in Sentry?"

**Scoring (1-5):**
| Dimension | Criteria |
|-----------|----------|
| **Test layers** | Unit → Integration → E2E → Load |
| **Concurrency** | Correctly tests race conditions |
| **Assertions** | Tests exact expected behavior |
| **Coverage** | Tests isolation, idempotency, edge cases |

## Question 9: Behavioral — Failure (6 min)

**Interviewer:** "Tell me about a time you made a mistake that affected production. What happened and what did you learn?"

**Use STAR format:**
- **Situation:** Context of the mistake
- **Task:** What you were trying to do
- **Action:** What went wrong, how you fixed it
- **Result:** Impact and what you learned

**Good answers:**
- Deployed migration with NOT NULL without default
- Added feature without tenant-isolation test
- Missed a connection leak in error path

**Follow-up probes:**
- "How did you prevent it from happening again?"
- "How did you communicate the incident to stakeholders?"
- "What would you do differently?"

**Scoring (1-5):**
| Dimension | Criteria |
|-----------|----------|
| **Honesty** | Admits mistake without deflection |
| **Root cause** | Identifies why it happened |
| **Fix** | Explains the immediate fix |
| **Prevention** | Describes systemic changes |
| **Learning** | Shows growth from the experience |

## Question 10: Behavioral — Ambiguity (6 min)

**Interviewer:** "Tell me about a time you had to make a decision with incomplete information. How did you approach it?"

**Use STAR format:**
- **Situation:** Ambiguous requirements or missing data
- **Task:** What needed to be decided
- **Action:** How you gathered info, made the call
- **Result:** Outcome and what you'd do differently

**Good answers:**
- Choosing shared-schema tenancy without knowing clinic count
- Building notification system without knowing provider requirements
- Deciding on tech stack without full performance data

**Follow-up probes:**
- "How did you make the decision reversible?"
- "What information would have changed your decision?"
- "How did you communicate the uncertainty to stakeholders?"

**Scoring (1-5):**
| Dimension | Criteria |
|-----------|----------|
| **Framework** | Has a systematic approach to ambiguity |
| **Reversibility** | Makes decisions that can be undone |
| **Communication** | Keeps stakeholders informed |
| **Outcome** | Result was acceptable given the uncertainty |

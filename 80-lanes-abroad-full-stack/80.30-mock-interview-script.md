# Run and Review a Mock Interview

[![Role priority](https://img.shields.io/badge/role--priority-Important-blue)](../docs/topic-importance.md)
[![General importance](https://img.shields.io/badge/general--importance-Important-blue)](../docs/topic-importance.md)

A mock interview only improves your performance when the debrief turns vague feelings (*"felt okay, maybe 7/10"*) into **one concrete missing mechanism to repair before next week**. Pick prompts from the [Mock Interview Bank](80.11-mock-interview-bank.md) and use this guide to run a tight 60-minute session with a peer or solo recording.

## First Principles

Mock feedback must separate **what actually happened** from guesswork about an imaginary hiring bar. A mock cannot assign you a permanent "Senior" or "Staff" label — its job is to expose one breakable assumption while the stakes are zero.

## 1. Set Up a Clean 60-Minute Architecture / Project Mock

Agree upfront on format, exact clock, allowed notes, and recording consent (keep solo recordings private and never share confidential employer data):

| Block | Minutes | Goal |
| -------------------------------- | ------: | ---------------------------------------------------------------------------- |
| **1. Scope & ground rules** | 5 | Confirm prompt, constraints, and expected outputs |
| **2. Core workflow / design** | 20 | State the business invariant and walk through the clean end-to-end mechanism |
| **3. Mutated-constraint probes** | 15 | Inject crashes, concurrent writes, stale reads, or version skew |
| **4. Ownership story** | 10 | One real behavioral/project decision + follow-up questions |
| **5. Actionable debrief** | 10 | Name top strength, #1 gap, and next changed-case recheck |

Adjust block lengths cleanly when running a pure coding or behavioral mock.

## 2. How to Probe Like a Senior Interviewer

Skip gotcha trivia and inject realistic production shifts: *"Now two identical webhooks arrive at the same millisecond"*, *"Now the worker loses its lease mid-flight"*, *"Now the user switches tabs while offline."* Give the candidate quiet seconds to reason aloud.

Keep four sharp technical distinctions front of mind during debrief:
- **Outbox & CDC complement each other:** Change Data Capture (CDC) can relay outbox rows reliably — they are not mutually exclusive.
- **MVCC reduces reader/writer blocking, not all locks:** Concurrent writers on the same row still contend on locks.
- **Sensitive caching needs scope & freshness rules:** Never treat "cache everything" or "cache nothing" as an architecture.
- **Explanations != executed proof:** When someone claims a concurrency fix works, ask what real-database test proves it.

## 3. Write Observable Debrief Notes (Not Vague Labels)

| Dimension | Write this (actionable) | Avoid this (useless) |
| ----------------- | ------------------------------------------------------------------- | ---------------------------- |
| **Correctness** | *"Missed that payment timeout leaves remote charge state unknown"* | *"System design felt shaky"* |
| **Evidence** | *"Claimed 40% speedup without knowing before/after workload"* | *"Needs better stories"* |
| **Trade-offs** | *"Picked Kafka without comparing simpler Postgres queue ops cost"* | *"Over-engineered"* |
| **Communication** | *"Spent 12 minutes listing stack before drawing core booking flow"* | *"Not senior enough"* |
| **Pacing** | *"Ran out of time before covering monitoring and rollback"* | *"Too slow"* |

## 4. Turn Feedback Into One Verified Repair

Pick the **single highest-risk gap**, study its canonical chapter ([Brushup Roadmap](80.29-topic-brushup-roadmap.md)), fix the explanation or code, and re-test on a **changed variation** next week — repeating the exact same prompt only tests memorization, not real transfer. Fit the repair inside your existing [Study Plan](80.13-study-plan.md).

## Summary

Run mocks on a clear clock, probe real failure mutations instead of trivia, log specific observable breakdowns instead of vague level scores, and prove improvement on an unseen variation before moving on.

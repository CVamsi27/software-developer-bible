## Part I — Healthtech Germany (Snke · MVST · Redcare)

### The regulatory map in 90 seconds

```text
EU level                          Germany level
─────────                         ─────────────
GDPR        privacy baseline      BDSG (national GDPR implementation)
MDR         Medical Device       DiGA   digital health apps on prescription
(EU 2017/745) regulation —        (Digitale Gesundheitsanwendungen,
            software can BE a     reimbursed via statutory insurance)
            medical device
EHDS (new)  European Health      gematik → runs the TI
            Data Space —          (Telematikinfrastruktur): ePA,
            interoperability      e-Rezept, communication
```

**The one distinction to never fumble:** *"designed to meet GDPR/MDR expectations"* ≠ *"certified"*. Medical-device software needs a QMS (ISO 13485), technical documentation, clinical evaluation, and conformity assessment before it may be placed on the EU market. In interviews, speak in controls and process; never claim certification status.

### MDR — when is software a medical device?

| Software behavior | MDR status |
|---|---|
| Diagnoses, predicts, decides treatment | ✅ Medical device (higher risk class) |
| Stores/transmits/displays patient data (record-access apps) | Usually NOT a device — but integrates with device ecosystems; still GDPR-heavy |
| Wellness/lifestyle tracking | Not a device; consumer rules |

Risk classes I–III by intended use (IIa/IIb typical for clinical software). Senior-engineer takeaway: **intended-use statements drive engineering constraints** — change control, verification depth, and release cadence all tighten with class.

| Piece | What it is | Interview one-liner |

### FHIR in 3 minutes (the depth you need)

- Everything is a **Resource** (JSON): `Patient`, `Observation`, `Condition`, `MedicationRequest` — canonical schemas with RESTful interactions (`GET/POST /Patient/{id}`).
- **Profiles/IGs** constrain resources per use case; terminology bindings tie fields to code systems.
- **Bundles** batch resources; **Subscriptions** push change notifications.
- Trade-off vs custom API: FHIR buys interoperability and regulator trust at the cost of verbose payloads and modeling friction. Common architecture: internal canonical model + FHIR facade at the edge.

```json
{
  "resourceType": "Observation",
  "status": "final",
  "code": { "coding": [{ "system": "http://loinc.org", "code": "8867-4", "display": "Heart rate" }] },
  "subject": { "reference": "Patient/123" },
  "valueQuantity": { "value": 72, "unit": "beats/minute" }
}
```

## Part II — Geospatial & Satellite Analytics (LiveEO)

### The mental model: vector vs raster

```text
VECTOR (geometries)                RASTER (grids of pixels)
roads, parcels, asset lines        satellite imagery, elevation
PostGIS geometry/geography         GeoTIFF → COG, tiles
Query: ST_Intersects(a, b)         Query: window reads, band math
Best: assets, boundaries, routes   Best: continuous phenomena, ML input
```

LiveEO is both worlds: **assets as vectors** (power lines, pipelines), **imagery as raster**, joined by spatial analysis.

### PostGIS essentials (what "geospatial workloads in PostgreSQL" means)

| Concept | One-liner | The interview trap |
|---|---|---|
| `geometry` vs `geography` | Planar (fast, CRS units) vs spheroidal (accurate over long distances) | Distance on `geometry` returns degrees unless you pick a metric CRS/transform |
| SRID / CRS | Coordinate system ID (`4326` = lat/lon WGS84; web maps reproject to `3857`) | Mixing SRIDs silently breaks joins; always state it |
| GiST index | Spatial index on bounding boxes | A functional index must match the exact expression used in queries |
| `ST_Intersects` / `ST_DWithin` | Containment vs distance-with-tolerance | `ST_DWithin(geog, geog, meters)` uses the index; `ST_Distance(...) < x` often doesn't |
| `ST_AsMVT` | Server-side vector-tile encoding | Streaming Mapbox Vector Tiles straight from SQL powers fast map UIs |
| Partitioning by region/grid | Big tables split spatially | Combine with tenant scoping for multi-tenant geo |

```sql
-- the canonical fast query: all vegetation-risk alerts near one power-line segment
SELECT a.id, a.risk_score
FROM   vegetation_alerts a
JOIN   line_assets l ON ST_Intersects(l.geom, a.geom)
WHERE  l.network_id = $1
AND    ST_DWithin(l.geog, a.geog, 30)          -- 30 m corridor, index-assisted
ORDER  BY a.detected_at DESC;
```

### Imagery pipeline vocabulary

| Term | Meaning |
|---|---|
| **COG** (Cloud-Optimized GeoTIFF) | Tiled + overviews GeoTIFF; HTTP range requests fetch only needed windows |
| **STAC** (SpatioTemporal Asset Catalog) | JSON catalog standard to *find* imagery (bbox/time/collection) |
| **Tiles / XYZ** | Web-map pyramid: z=zoom, x/y tile grid; browsers request tiles lazily |
| **Vector tiles (MVT)** | Geometry tiles for crisp client rendering w/ styling client-side |
| **GDAL / Rasterio** | The raster swiss-army knives (Python side) |
| **Change detection** | Compare co-registered scenes over time (indices like NDVI for vegetation) |
| **Optical vs SAR** | Optical needs daylight/no clouds; SAR sees through both — fusion is LiveEO's SPRIND-funded frontier |

### Design drill you should be able to whiteboard

**"Alert operators within hours when vegetation threatens their grid section."**

```text
1. INGEST    new scene metadata → STAC item; imagery → COG in object storage
2. DETECT    ML inference per tile (batch, idempotent keyed on scene+tile)
3. FUSE      detections ∩ asset corridors (ST_DWithin) → risk events (deduped)
4. DELIVER   event → outbox → notification fan-out (email/dashboard/WebSocket)
5. SURFACE   map UI: MVT tiles + alert list; audit trail for regulator-facing exports
Non-functionals: reprocessing = rerun stage keyed by scene id; backpressure via queue depth;
cost lever = only process tiles intersecting customer corridors.
```

Notice this is **exactly your Docita pipeline shape**: transactional outbox, idempotent consumers, DLQ/replay, tenancy-scoped everything. Say that sentence.

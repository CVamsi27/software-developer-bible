Many strong German and European product startups operate in regulated or specialized domains — especially **digital health** and **geospatial and climate analytics**.

You do not need ten years of clinical or satellite experience to pass a senior full-stack interview there, yet you *do* need enough domain fluency to spot the real data invariants and ask sharp questions. Use [Company Product Preparation Sheets](80.32-company-prep-sheets.md) to pick the right workflow and your [Interview Evidence Pack](80.17-docita-interview-evidence-pack.md) to back up your own past engineering work.

## First Principles

In ordinary Create, Read, Update, and Delete (CRUD) applications, a valid JavaScript Object Notation (JSON) schema is usually enough. In healthcare and geospatial systems, **valid JSON can still be dangerously wrong** if the patient identity, measurement unit, coordinate system, timestamp, or source provenance is missing or mismatched. Always trace meaning and provenance alongside storage types.

## Part I — Healthtech Germany (Snke · MVST · Redcare)

Start every healthcare design discussion by answering one sentence: **which clinical fact, from which source system, for which authorized user?**

### Key clinical systems and standards (plain-English map)

| Acronym or Standard | What it actually does in plain English |
| ----------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **HIS** (Hospital Information System) | Core hospital record system managing admissions, billing, and clinical records |
| **RIS** (Radiology Information System) | Manages imaging orders, scheduling, and radiology reports |
| **PACS** (Picture Archiving and Communication System) | Stores and serves medical images (Computed Tomography (CT), Magnetic Resonance Imaging (MRI), X-ray) |
| **HL7 v2** | Legacy pipe-delimited message protocol still widely used between hospital systems |
| **FHIR** (Fast Healthcare Interoperability Resources) | Modern resource-based standard (`Patient`, `Observation`, `Encounter`) with Representational State Transfer (REST), JSON, Extensible Markup Language (XML), and messaging options |
| **DICOM** | File format and network protocol for medical imaging plus embedded patient metadata |
| **ICD** (for example, `ICD-10` and `ICD-11`) | Standardized diagnosis classification codes used for billing and clinical reporting |
| **SNOMED CT** | Detailed clinical terminology capturing symptoms, procedures, and relationships |
| **LOINC** | Standardized codes identifying laboratory tests and clinical measurements (for example, body temperature) |

Do not treat these as interchangeable buzzwords. Any clinical integration must lock down exact standard version, patient identifier matching, code system, units, timestamps, authorization, and duplicate or out-of-order message reconciliation.

### FHIR in practice: why units and identity beat syntax

A FHIR `Observation` resource looks clean as JSON, yet two bugs happen constantly in real integrations:
1. **Dropped or mismatched units:** Sending `38.2` without `{ unit: "°C", system: "http://unitsofmeasure.org" }` lets a downstream consumer misread Fahrenheit versus Celsius.
2. **Wrong patient match:** Perfectly valid FHIR JSON attached to the wrong `subject.reference` (`Patient/123` instead of `Patient/124`) silently corrupts a real patient's chart.

```json
// excerpt: simplified FHIR Observation sketch (not a full country-profile implementation)
{
  "resourceType": "Observation",
  "status": "final",
  "code": { "coding": [{ "system": "http://loinc.org", "code": "8310-5", "display": "Body temperature" }] },
  "subject": { "reference": "Patient/example-123" },
  "effectiveDateTime": "2026-11-23T09:15:00Z",
  "valueQuantity": { "value": 38.2, "unit": "°C", "system": "http://unitsofmeasure.org", "code": "Cel" }
}
```

In production, FHIR **Profiles** tighten which fields and code sets are mandatory for a specific region or workflow, and a server's `CapabilityStatement` advertises what it supports. See the [HL7 FHIR R5 overview](https://hl7.org/fhir/R5/overview.html).

### Regulatory scope follows intended use, not marketing labels

Calling an app a "wellness tool" does not exempt it from European Union (EU) Medical Device Regulation (MDR) if its **intended purpose** diagnoses, monitors, or guides clinical treatment. Conversely, plain appointment scheduling or encrypted document storage carries very different obligations from diagnostic decision support.

Keep **qualification and classification**, **engineering quality controls** (such as ISO 13485 processes), and **formal conformity assessment** distinct, and consult [EU Regulatory Compliance](80.24-eu-regulatory-compliance.md) before quoting legal rules.

## Part II — Geospatial & Satellite Analytics (LiveEO)

Start every geospatial design discussion with four questions: **where (geometry), when (acquisition time), in which coordinate system (Spatial Reference Identifier (SRID)), and with what uncertainty?**

```text
Vector data (roads, pipelines, land parcels)  ──► exact shapes & geometric queries (PostGIS)
Raster data (satellite imagery, elevation)    ──► pixel grids, spectral bands & cloud tiles (STAC + COG)
                                                   └──► aligned analysis ─► bounded risk alerts
```

### PostGIS essentials: picking the right type and spatial predicate

| `PostGIS` Concept | Plain-English meaning and common trap |
| ------------------------------ | ----------------------------------------------------------------------------------------------------------------- |
| **`geometry`** | Planar math in the coordinate system's native units — **trap:** degrees in WGS 84 (`SRID 4326`) are *not* meters! |
| **`geography`** | Earth-curvature (geodetic) math where `ST_DWithin` distances are natively in **meters** |
| **`ST_Intersects(a, b)`** | True when two shapes touch or overlap — does *not* find nearby objects 10 meters away |
| **`ST_DWithin(a, b, meters)`** | True when objects lie within `meters`, using a fast bounding-box index scan first |
| **GiST index** | Spatial R-tree index that makes bounding-box filters fast (verify actual plan with `EXPLAIN`) |
| **`ST_AsMVT`** | Packs queried rows into compact Mapbox Vector Tiles for fast browser map rendering |

```sql
-- excerpt: find risk detections within 30 meters of a tenant's pipeline corridor
SELECT d.id, d.detected_at, d.confidence
FROM detections d
JOIN assets a ON a.id = $1 AND a.tenant_id = $2
WHERE ST_DWithin(d.location::geography, a.corridor::geography, 30);
```

Notice two subtle traps:
- Requiring `ST_Intersects` for a 30-meter safety corridor misses dangerous trees 10 meters away from the line.
- Setting an SRID label (`ST_SetSRID`) merely *tags* coordinates; it does **not** reproject them (`ST_Transform` actually converts coordinates between projections).

Reference documentation: [ST_DWithin](https://postgis.net/docs/ST_DWithin.html), [ST_Intersects](https://postgis.net/docs/ST_Intersects.html), and [ST_AsMVT](https://postgis.net/docs/ST_AsMVT.html).

### Satellite imagery: catalog discovery versus reading pixels

Satellite images are gigabytes each — you never download whole scenes just to inspect one pipeline corridor:

| Standard or Tool | Role in the pipeline |
| --------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **STAC** (SpatioTemporal Asset Catalog) | Standardized JSON catalog to search *which* scenes cover a bounding box and date range ([STAC spec](https://stacspec.org/en/about/stac-spec/)) |
| **COG** (Cloud Optimized GeoTIFF) | Tiled GeoTIFF layout allowing Hypertext Transfer Protocol (HTTP) Range requests to fetch *only* the pixels inside your window ([OGC COG standard](https://docs.ogc.org/is/21-026/21-026.html)) |
| **Vector tiles** | Lightweight tiled vector geometry streamed to interactive browser maps |
| **`GDAL` and `Rasterio`** | Core libraries for reading, warping, and clipping raster imagery |
| **Change detection** | Comparing two aligned observations over time while accounting for cloud cover, shadows, and sensor differences |

### Tracing a full detection-to-alert workflow

```text
Scene ID + Acquisition Timestamp ─► Authorized Asset Match
  ─► Aligned Processing (pinned model & code version)
       ─► Bounded Detections + Confidence Score
            ─► Idempotent Alert Delivery ─► Operator Review
```

Key every processing job by `(scene_id, tile_or_region, model_version)` so reprocessing a satellite pass updates detections cleanly without spamming duplicate operator alerts. Keep **acquisition time** (when the satellite captured the ground) separate from **delivery time** (when the alert fired).

## Transfer Your Real Engineering Strengths Honestly

Strong fundamentals — idempotent job queues, tenant authorization, index tuning, schema validation, and observability — transfer directly into both healthtech and geospatial engineering. Explain the exact mechanism you built in your own systems, then state clearly what domain specifics you would ramp up on in your first 30 days.

## Summary

In healthtech, focus on patient identity, standardized codes and units (`FHIR`, `LOINC`, `ICD`), and regulatory intended use. In geospatial analytics, focus on coordinate systems (`SRID`), planar `geometry` versus geodetic `geography`, `ST_DWithin` indexing, and separating imagery discovery (`STAC`) from partial pixel reads (`COG`). Transfer your core backend and frontend reliability skills openly while staying honest about domain-specific gaps.

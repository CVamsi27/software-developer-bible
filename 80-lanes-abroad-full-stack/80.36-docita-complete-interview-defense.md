## 1. What Is Docita

**Docita** is a production healthcare SaaS platform — a "Clinic OS" that takes small-to-mid clinics from paper/Excel to cloud. It handles scheduling, patient records, prescriptions, billing, inventory, WhatsApp communication, and insurance claims for **25+ active clinics** and **1,000+ appointment workflows per month**.

**Positioning:** WhatsApp-first clinic OS. A small clinic owner in India should be able to run their clinic without opening a browser — WhatsApp is the primary interface, the web app is power-user mode.

**Live:** [docita.work](https://docita.work) (landing), [app.docita.work](https://app.docita.work) (clinician app), [internal.docita.work](https://internal.docita.work) (admin portal)

### Request Flow

```text
Browser → Vite SPA (React client component)
  → packages/data-access (React Query + Axios)
    → Hono proxy Worker (/api/*)
      → apps/api HTTP controller
        ├── JWT auth guard
        ├── TenantGuard (AsyncLocalStorage)
        ├── RBAC roles matrix
        ├── Subscription/tier guard
        ├── PolicyGuard (ABAC)
        └── Service / Use-case
          → Repository (PrismaClient)
            → PostgreSQL (RLS enforced)
```

### Key Design Principles

1. **Thin controllers** — orchestration in services/use-cases, not controllers
2. **Repository pattern** — only repositories import PrismaClient (CI-enforced via `check:prisma-boundary`)
3. **Zod-first types** — schemas in `packages/types` are the single source of truth; TS types are inferred
4. **Tenant context via AsyncLocalStorage** — every Prisma call is automatically tenant-safe
5. **Defense in depth** — application + ORM + RLS for tenant isolation

## 4. Key Architecture Decisions & Trade-offs

### Decision 1: PostgreSQL as Queue (not Redis/BullMQ)

**Context:** API and worker need a durable job queue for emails, WhatsApp, PDF generation, audit fan-out.

**Decision:** Use a `QueueJob` table in PostgreSQL with `SELECT ... FOR UPDATE SKIP LOCKED`.

**Why not Redis:**
- Adds another managed service (cost + ops surface)
- No transactional enqueue with business writes
- We already pay for AWS RDS HA

**Trade-off:** Not suitable for >1k jobs/sec sustained. If we hit that, revisit.

**Code:** `packages/db/prisma/schema.prisma` (QueueJob model), `apps/api/src/shared/modules/queue/`

### Decision 2: Transactional Outbox (not EventEmitter2 directly)

**Context:** Domain events were emitted via in-process `EventEmitter2`. Single pod = fine. But listener failures aren't retried, and splitting across pods drops cross-pod events.

**Decision:** Write events to `OutboxEvent` table in same `prisma.$transaction` as business write. Relay scheduler polls and republishes.

**Why not Kafka/NATS:** Premature — single region, single API pod. Outbox solves the problem with zero new infrastructure.

**Trade-off:** Relay lag (seconds). Acceptable for our scale.

**Code:** `apps/api/src/shared/modules/outbox/outbox.service.ts`, `outbox-relay.scheduler.ts`

### Decision 3: Vite SPA (not Next.js SSR)

**Context:** Started with Next.js. Migration to Vite + React Router completed 2026-08-10.

**Why:**
- No SEO need (dashboard app, not marketing)
- Simpler deployment (Cloudflare Static Assets)
- No server runtime for frontend = lower cost
- Faster dev experience (Vite HMR vs Next.js)

**Trade-off:** Lost server-side rendering benefits. Acceptable for a logged-in SaaS dashboard.

**Code:** ADR 0012, `apps/app/`, `apps/internal/`

### Decision 4: Fly.io (not AWS ECS/Lambda)

**Context:** Need container hosting for NestJS API + worker.

**Why:**
- `fly deploy` simplicity vs ECS cluster management
- Auto-stop/start for cost savings (low traffic initially)
- Same region as AWS RDS (Singapore ≈ Mumbai latency)

**Trade-off:** Less flexibility than Kubernetes. Acceptable for single-region.

**Code:** `fly.toml`, `apps/api/Dockerfile`

### Decision 5: ABAC-on-RBAC (not pure ABAC)

**Context:** RBAC roles (ADMIN, DOCTOR, NURSE, RECEPTIONIST, PATIENT) couldn't express "doctor can view only their assigned patients."

**Decision:** Keep existing RBAC guard chain, add `PolicyGuard` as the final stage for object-level conditions.

**Why not pure ABAC:** Too complex for our scale. RBAC handles 90% of cases; ABAC adds the missing 10%.

**Trade-off:** Two authorization systems to maintain. But each is simple.

**Code:** `packages/authorization/`, `apps/api/src/shared/modules/authorization/`

### Decision 6: AsyncLocalStorage for Tenant Context (not explicit param threading)

**Context:** Every Prisma call needs `tenantId`. Threading it through every function signature is verbose and error-prone.

**Decision:** Use Node.js `AsyncLocalStorage` to carry request-scoped context.

**Why:** One missed parameter = data leak. ALS makes it implicit and impossible to forget.

**Trade-off:** `setTimeout` loses context. Mitigated by `check-detached-promises.mjs` CI check.

**Code:** `apps/api/src/shared/modules/tenant/tenant-context.ts`, ADR 0008

### Decision 7: Zod-First Type Architecture

**Context:** TypeScript interfaces, Prisma models, and NestJS DTOs were diverging.

**Decision:** Zod schemas in `packages/types` are the single source of truth. All other types are inferred.

**Flow:** `Zod Schema → infer TS types → API contracts → UI forms → DB-safe DTOs`

**Trade-off:** Slightly more verbose schema definitions. But eliminates type drift entirely.

**Code:** `packages/types/`, `docs/architecture/zod-first-architecture.md`

## 5. Testing Strategy

### Test Pyramid

```text
┌──────────────────────────────────────────────────────────────┐
│ E2E (Playwright) — 48 spec files, ~1,092 tests              │
│ ├── Critical flows: login, patient CRUD, appointment,        │
│ │   consultation, billing, WhatsApp, upgrade                 │
│ ├── Accessibility: axe audits on key routes                 │
│ └── Smoke: health checks, navigation routes                 │
├──────────────────────────────────────────────────────────────┤
│ Integration (Jest + Supertest) — backend E2E                │
│ ├── Fresh DB snapshot per test                               │
│ ├── Multi-clinic data isolation                              │
│ ├── Doctor-scope authorization                               │
│ └── Mocked external services (Razorpay)                     │
├──────────────────────────────────────────────────────────────┤
│ Unit (Vitest) — 705 passing tests (122 files)               │
│ ├── Component logic, hooks, rules                           │
│ ├── ABAC policy evaluation                                   │
│ └── Utility functions                                        │
├──────────────────────────────────────────────────────────────┤
│ CI Checks — automated gatekeepers                           │
│ ├── check:prisma-boundary (only repos import PrismaClient)  │
│ ├── check:phi-encryption-coverage (encrypt/decrypt aligned)  │
│ ├── check:policy-resolver-coverage (every policy has resolver)│
│ ├── check-detached-promises.mjs (ALS context safety)        │
│ ├── check-job-idempotency.mjs (queue jobs are idempotent)   │
│ └── check-worker-size.mjs (Cloudflare bundle <3MB)          │
└──────────────────────────────────────────────────────────────┘
```

### Testing Philosophy

1. **Multi-clinic isolation tests** — every integration test verifies that clinic A cannot see clinic B's data
2. **Critical path E2E** — Playwright runs the full patient journey: register → schedule → consult → prescribe → bill → pay
3. **Accessibility-first** — axe audits run on every key route in CI
4. **Policy coverage gates** — CI fails if a declared ABAC policy has no registered resolver
5. **Idempotency verification** — CI checks that every queue job handler is idempotent

## 7. Security & Compliance

### Defense-in-Depth Layers

```text
┌──────────────────────────────────────────────────────────────┐
│ Layer 7: Audit logging — every PHI access logged             │
│ Layer 6: RLS — PostgreSQL row-level security (DB-level)      │
│ Layer 5: Repository tenant scoping — Prisma middleware        │
│ Layer 4: PolicyGuard (ABAC) — object-level conditions        │
│ Layer 3: Subscription/tier guard — feature gating            │
│ Layer 2: RBAC roles matrix — role → permission               │
│ Layer 1: TenantGuard — AsyncLocalStorage tenant context      │
│ Layer 0: JWT auth — token validation + session management    │
└──────────────────────────────────────────────────────────────┘
```

### PHI Protection

- **Encrypted fields:** firstName, lastName, email, phoneNumber, address, emergencyContactPhone, emergencyContactName
- **Encryption boundary:** Prisma extension — encrypt before persist, decrypt on read
- **CI gate:** `check:phi-encryption-coverage` ensures encrypt/decrypt field lists stay aligned
- **Plaintext exceptions:** MRN, bloodGroup, allergies, medicalHistory (needed for lookup/display, protected by RLS + audit)

### Payment Flow Separation

Three distinct payment rails that must never mix:
1. **Flow A (Clinic settings):** Clinic's own Razorpay credentials for their payment config
2. **Flow B (Patient → Clinic):** Patient pays clinic using Flow A credentials
3. **Docita SaaS:** Clinic pays Docita for subscription — separate merchant account

### Compliance

- **DPDP (India):** Data residency in ap-south-1, subprocessor disclosure, PHI encryption
- **Audit trail:** Every access to patient data logged with subject, resource, action, decision
- **Emergency access:** Break-the-glass with audit logging, read-only, reason-gated

## 8. Common Interview Questions & Answers

### Q: "Tell me about the most complex system you've built."

> "I'm the founding engineer of Docita, a healthcare SaaS serving 25+ clinics with 1,000+ appointment workflows per month. The most complex aspect was multi-tenant data isolation — we needed provable separation between clinics handling Protected Health Information. I implemented a 7-layer defense-in-depth: JWT auth, AsyncLocalStorage tenant context, RBAC roles, ABAC policies for object-level access, Prisma repository scoping, PostgreSQL RLS, and audit logging. The ABAC layer was the hardest — we needed 'doctor can view only their assigned patients' without role explosion. I designed a deny-overrides policy engine that evaluates subject, resource, and environment attributes, with an emergency break-the-glass escape hatch that's audited and read-only."

### Q: "Why PostgreSQL as a queue instead of Redis?"

> "Operational simplicity. We already run AWS RDS PostgreSQL — adding Redis means another managed service, another failure mode, another secret to rotate. Our queue volume is ~0.4 jobs/sec sustained, well within Postgres capabilities. The key advantage: transactional enqueue. A `prisma.$transaction` covers both the business write AND the job emission — no dual-write problem. We use `SELECT ... FOR UPDATE SKIP LOCKED` for pop-and-claim. The trade-off is throughput — if we hit >1k/sec sustained, we'd revisit Redis/NATS. But for 25 clinics, Postgres is sufficient and simpler."

### Q: "How do you handle data consistency across services?"

> "We use the transactional outbox pattern. Domain events are written to an `OutboxEvent` table in the same `prisma.$transaction` as the business write — atomic, no dual-write. A relay scheduler polls unpublished rows every 2 seconds and republishes to in-process EventEmitter2. Consumers are idempotent — they check a deduplication cache before processing. Failed events go through exponential backoff retry, then to a DLQ for manual inspection. We chose this over Kafka/NATS because we're single-region single-pod — outbox solves the problem with zero new infrastructure."

### Q: "How do you test multi-tenant isolation?"

> "Every integration test uses a fresh database snapshot and verifies cross-tenant isolation. The test creates data for clinic A, then attempts to access it as clinic B — asserting a 404 (not 403, to avoid leaking existence). We also have a CI check `check:prisma-boundary` that enforces only repository files import PrismaClient — preventing business logic from bypassing tenant scoping. Playwright E2E tests run the full patient journey across multiple clinics to verify isolation end-to-end."

### Q: "Why did you migrate from Next.js to Vite SPA?"

> "Docita's apps are authenticated dashboards — no SEO need, no public content. Next.js SSR added complexity (server runtime, build pipeline, edge middleware) without benefit. Vite + React Router gives us: simpler deployment (Cloudflare Static Assets), faster dev experience (sub-second HMR), smaller bundle (no Next.js runtime), and zero server cost for frontend. The Hono proxy Worker handles `/api/*` routing to our Fly.io backend — same domain, no CORS. The migration was completed in one sprint with zero downtime."

### Q: "How do you handle the 'WhatsApp-first' positioning?"

> "WhatsApp is the primary interface for small clinics in India. The doctor already gets appointment requests and prescription photos on WhatsApp. We inverted the traditional SaaS model: WhatsApp is the OS, the web app is power-user mode. Patients receive appointment reminders, prescriptions, and follow-ups via WhatsApp. The clinic staff manages everything from the web app, but patient-facing communication goes through WhatsApp. This eliminated the 'download an app' friction that kills adoption in small clinics."

### Q: "Walk me through the ABAC implementation."

> "We layered ABAC on top of existing RBAC — not a replacement. The guard chain is: JWT → TenantGuard → RBAC roles → Subscription/tier → PolicyGuard (ABAC). The PolicyGuard is a global NestJS guard that's a no-op unless a route declares `@RequirePolicy(resource, action)`. Policies are typed TypeScript classes in `packages/authorization` — pure functions, no framework imports. We use deny-overrides: any policy deny wins over any allow, and unmatched policies default to deny. For example, the patient resource resolver checks: same clinic? Doctor assigned to patient? Role permitted? Environment valid? All must pass. The emergency break-the-glass bypasses assignment checks but is audit-logged and read-only."

### Q: "How do you handle deployment and migrations?"

> "Deploy order: DB migrations first, then API/worker, then frontends. Fly.io runs `prisma migrate deploy` before API deploy — a verification script confirms no pending migrations or schema drift. The API and worker share the same Docker image base but have separate fly.toml configs. Frontends deploy to Cloudflare Workers with Static Assets. GitHub Actions triggers selective deploys — only apps whose related paths changed. We use `fly deploy` from the repo root, and Cloudflare's wrangler for SPA deploys. Auto-stop/start on Fly.io scales to zero when idle, saving cost during low-traffic periods."

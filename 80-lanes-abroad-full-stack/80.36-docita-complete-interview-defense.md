# Docita Interview Defense — Explain One Decision Under Follow-up

[![Role priority](https://img.shields.io/badge/role--priority-Important-blue)](../docs/topic-importance.md)
[![General importance](https://img.shields.io/badge/general--importance-Important-blue)](../docs/topic-importance.md)

> **Purpose:** Deliver a crisp, senior-level defense of one real Docita engineering decision and handle deep technical follow-ups calmly. Start with [Docita Walkthrough](80.16-docita-resume-defense.md) and your [Evidence Pack](80.17-docita-interview-evidence-pack.md), keep implementation deep dives in [projects/docita](../projects/docita/INDEX.md), and store personal metrics strictly in your private workspace.

## First Principles

Interviewers rarely care how many microservices or modules you can list — they care whether you can name **one non-negotiable invariant**, point to the **exact mechanism enforcing it**, trace **what breaks if a process crashes mid-flight**, and state **what proof backs your claim**.

## 1. Frame One Concrete Decision in Five Tight Pieces

Pick one high-stakes operation — such as preventing duplicate payment recording, enforcing clinic tenant isolation, or serializing conflicting appointment bookings — and lead with the failure it stops:

> *"Payment webhooks can arrive twice. Recording the same provider payment twice must never credit the invoice twice."*

Then organize your 3-minute defense cleanly around five pieces:

| Piece | Question you answer aloud | Proof you attach |
| -------------------------- | ---------------------------------------------------------------------- | --------------------------------------------------------------------------------------- |
| **1. Constraint** | What must stay true even under retries or crashes? | Requirement or failing test scenario |
| **2. Enforcing mechanism** | Which exact database constraint, transaction, or policy stops the bug? | Handler, Structured Query Language (SQL) constraint, or Row-Level Security (RLS) policy |
| **3. Trade-off** | What viable alternative did you reject, and why? | Concrete operations, latency, and correctness cost |
| **4. Remaining limit** | Which failure still sits outside this single mechanism? | Explicit boundary or recovery rule |
| **5. Observed outcome** | What changed after shipping (or leave unmeasured if unknown)? | Dated measurement or verified behavior |

Keep three proof levels distinct: a **source file** proves implementation, a **passing test** proves the tested case on that commit, and a **dated production metric** proves real-world impact. Cross-check wording via [Resume Claim Crosswalk](80.18-resume-claim-crosswalk.md).

## 2. Worked Walkthrough: Payment Callback Across Four Crash Points

Trace this realistic payment-webhook flow (confirming against your current code before describing deployed behavior):

```text
Webhook arrives (provider_payment_id)
  ─► 1. Verify cryptographic signature & merchant context
  ─► 2. BEGIN TRANSACTION
          • INSERT payment with DB UNIQUE(provider_payment_id)
          • UPDATE invoice state (guarded transition)
          • INSERT outbox event row
        COMMIT
  ─► 3. Return HTTP 200 ACK to provider
  ─► 4. Async relay reads outbox and dispatches downstream notification
```

Now show senior depth by tracing a crash at **every single boundary**:
1. **Crash before `COMMIT`:** PostgreSQL rolls back all three writes cleanly; provider retries and succeeds cleanly.
2. **Crash after `COMMIT`, before Hypertext Transfer Protocol (HTTP) `200`:** Provider retries the same webhook; the `UNIQUE(provider_payment_id)` constraint catches the duplicate cleanly (a pre-insert `SELECT` check alone races under concurrent webhooks!).
3. **Crash during outbox relay before marking sent:** Relay redelivers the event; downstream consumers must remain idempotent.
4. **Crash after remote notification application programming interface (API) accepts, before worker saves completion:** Local outbox deduplication cannot undo a remote call — explain provider idempotency keys or status reconciliation.

See canonical implementation notes in [Payment Flows](../projects/docita/04-payment-flows.md) and [Async Processing](../projects/docita/03-async-processing.md).

## 3. Nine Sharp Mechanism Boundaries to Keep Crystal Clear

| Area | Exact boundary to get right | Deep dive |
| ------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------- |
| **Tenant context** | `AsyncLocalStorage` propagates context across asynchronous calls — it does *not* authorize access on its own | [Multi-Tenancy & RLS](../projects/docita/02-multi-tenancy-rls.md) |
| **PostgreSQL RLS** | Confirm active policies, non-`BYPASSRLS` role, and transaction-local `set_config(..., true)` on pooled connections | [Multi-Tenancy & RLS](../projects/docita/02-multi-tenancy-rls.md) |
| **Queue claiming** | `SKIP LOCKED` claims rows inside a short transaction; long-running jobs still need leases, expiry, and fencing | [Async Processing](../projects/docita/03-async-processing.md) |
| **Patient data encryption** | Encryption at rest protects raw disk and backups — not data already decrypted inside an authorized app process | [Architecture Decisions](../projects/docita/01-architecture-decisions.md) |
| **Clinical checks** | Automated validation catches known input and interaction patterns — it never replaces clinical judgment | [Prescription Safety](../projects/docita/07-prescription-safety.md) |
| **Realtime updates** | Active WebSockets deliver live events; missed events during disconnects still need persisted replay and sync | [Docita Walkthrough](80.16-docita-resume-defense.md) |
| **Artificial intelligence (AI) guardrails** | Feature flags, timeouts, schemas, and atomic spend reservations are four separate controls | [Advanced Rehearsal](80.21-docita-google-level-prep.md) |
| **CI gates** | Script counts prove nothing; cite what each gate checks and whether it passed on the release commit | [Evidence Pack](80.17-docita-interview-evidence-pack.md) |
| **Origin and proxy trust** | Trusting raw `CF-Connecting-IP` headers without verifying origin access lets attackers spoof client Internet Protocol (IP) addresses | [Architecture Decisions](../projects/docita/01-architecture-decisions.md) |

## 4. Discuss Alternatives and Capacity Without Fake Rules of Thumb

Never quote arbitrary limits like *"PostgreSQL queues die at 1,000 jobs per second"* — throughput depends on row size, index contention, claim batching, vacuuming, and hardware.

Likewise, adding Kafka does not magically remove the database-to-message atomicity problem, MongoDB supports transactions, and Single-Page Applications (SPAs) are not automatically faster than Server-Side Rendering (SSR) on every screen. Justify any architectural swap from a **measured bottleneck** and its real operational cost.

## 5. Rehearse Capacity Claims Under Changed Conditions

Pair [Deployment Infrastructure](../projects/docita/10-deployment-infrastructure.md), [Analytics & Dashboards](../projects/docita/14-analytics-and-dashboards.md), and [Hypothetical Clinic Metrics](../projects/docita/23-hypothetical-clinic-metrics.md) with the drills in [Docita Revision](../projects/docita/REVISION.md#read-a-fly-machine-before-describing-its-capacity).

Practice mutating one condition at a time aloud: adding an API replica, a 10× morning check-in burst, an exhausted database pool, a cold start, a stopped background worker, or a crashed provider call. For each one, name the **resource or correctness boundary**, the **first metric or log you inspect**, and **one reversible mitigation**. Use [Section Revision](REVISION.md) and [Mock Interview Script](80.30-mock-interview-script.md) to stress-test your answers aloud.

## Summary

Defend one concrete Docita workflow deeply instead of reciting the entire stack: lead with the failure prevented, trace every crash point across database commit, acknowledgment, and remote side effects, keep implementation, test, and production proof separate, and explain scaling choices from real bottlenecks rather than memorized thresholds.

## 1. What Is Docita

**Docita** is a production healthcare SaaS platform — a "Clinic OS" that takes small-to-mid clinics from paper/Excel to cloud. It handles scheduling, patient records, prescriptions, billing, inventory, WhatsApp communication, and insurance claims for **25+ active clinics** and **1,000+ appointment workflows per month**.

**Positioning:** WhatsApp-first clinic OS. A small clinic owner in India should be able to run their clinic without opening a browser — WhatsApp is the primary interface, the web app is power-user mode.

**Why this matters for interviews:** Healthcare SaaS is one of the hardest domains — PHI compliance, multi-tenancy, real-time workflows, payment separation, and regulatory requirements. Every architectural decision has compliance implications.

## 2. The Hard Problems

### Problem 1: Multi-Tenant Data Isolation in Healthcare

**Challenge:** 25+ clinics share one database. A single missed `WHERE clinicId = ?` leaks patient data across clinics. In healthcare, this isn't just a bug — it's a compliance violation (DPDP, HIPAA-equivalent).

**What we tried first:** Application-level filtering via Prisma middleware. Every repository had to manually add `clinicId` to queries.

**What went wrong:** A developer added a new repository method and forgot the clinic filter. Code review caught it, but it revealed the fragility. We needed a database-level guarantee.

**Solution:** 7-layer defense-in-depth:

```text
Layer 7: Audit logging — every PHI access logged
Layer 6: RLS — PostgreSQL row-level security (database-level)
Layer 5: Repository tenant scoping — Prisma middleware
Layer 4: PolicyGuard (ABAC) — object-level conditions
Layer 3: Subscription/tier guard — feature gating
Layer 2: RBAC roles matrix — role → permission
Layer 1: TenantGuard — AsyncLocalStorage tenant context
Layer 0: JWT auth — token validation + session management
```

**Key insight:** RLS was the hardest to implement. The challenge: Prisma's connection pool means each query might run on a different connection. We had to route ALL queries through a single interactive transaction per request, using a custom Prisma extension (`rls-routing`). Without this, the `SET LOCAL app.current_clinic_id` would be set on one connection but the query would run on another — silently bypassing RLS.

**Code:** `apps/api/src/shared/common/middleware/tenant.middleware.ts`, `apps/api/src/shared/common/interceptors/tenant-context.interceptor.ts`, `apps/api/src/shared/modules/rls/apply-rls-scope.ts`

### Problem 2: Reliable Async Processing Without Redis

**Challenge:** The platform needs to send WhatsApp messages, generate PDFs, process payments, and run analytics — all asynchronously. Traditional approach: Redis + BullMQ.

**Why we rejected Redis:** Adding Redis means another managed service (AWS ElastiCache), another failure mode, another secret to rotate, and no transactional enqueue with business writes. At our scale (~0.4 jobs/sec), Postgres is sufficient.

**Solution:** PostgreSQL-backed queue using `SELECT ... FOR UPDATE SKIP LOCKED`. A `QueueJob` table stores pending jobs. The API writes jobs in the same `prisma.$transaction` as business data — atomic, no dual-write problem. A worker process polls and executes.

**What went wrong initially:** Early versions used in-process `EventEmitter2` for domain events. This worked for single-pod but would silently drop cross-pod listeners. We migrated to a transactional outbox pattern (ADR 0010).

**Key insight:** The outbox pattern solved the "emission happens but listener fails" problem. Events are written to an `OutboxEvent` table in the same transaction as the business write. A relay scheduler polls and republishes. Consumers are idempotent — they check a deduplication cache before processing.

**Code:** `apps/api/src/shared/modules/outbox/outbox.service.ts`, `apps/api/src/shared/modules/outbox/outbox-relay.scheduler.ts`, `apps/api/src/shared/modules/queue/postgres-queue.service.ts`

### Problem 3: Payment Flow Separation

**Challenge:** Three distinct payment flows that must never mix:

| Flow | Purpose | Merchant Key | Who Gets Paid |
| --------------- | ----------------------------------- | ------------------ | --------------- |
| **Flow A** | Clinic's own Razorpay credentials | Clinic's | Clinic |
| **Flow B** | Patient pays clinic | Flow A credentials | Clinic |
| **Docita SaaS** | Clinic pays Docita for subscription | Docita's | Docita |

**Why this is hard:** If a developer accidentally uses Docita's Razorpay merchant key for a patient payment, Docita receives the patient's money instead of the clinic. This is a financial compliance issue.

**Solution:** Three separate injection sites in the NestJS config, documented in `docs/product/PAYMENT_FLOWS.md`. Code reviews block PRs that cross flow boundaries. The naming convention makes it explicit: `CLINIC_INVOICE_PAYMENT_LINK_PROVIDER_TOKEN` (Flow B) vs `DOCITA_PLATFORM_PAYMENT_LINK_PROVIDER_TOKEN` (Docita SaaS).

**Key insight:** Technical debt exists — Flow B still delegates to a shared adapter instead of resolving a clinic-scoped provider from Flow A settings. This is documented and gated by code review.

### Problem 4: PHI Encryption at the Field Level

**Challenge:** DPDP (India's data protection law) and clinic compliance require encryption beyond disk-level. A stolen database snapshot must be unreadable without the key.

**Solution:** Field-level encryption — 13 sensitive patient fields are encrypted using AES-256-GCM with versioned keys (`v1:iv:tag:ciphertext`). The Prisma extension transparently encrypts before persist and decrypts on read. Key versioning enables rotation without data rewrites.

**Encrypted fields:** firstName, lastName, email, phoneNumber, address, emergencyContactPhone, emergencyContactName.

**Why not encrypt everything:** MRN, bloodGroup, allergies, medicalHistory need to be searchable/displayable. They're protected by RLS + audit logging instead.

**What went wrong:** Initially, the encrypt and decrypt field lists drifted apart — a new field was added to encrypt but not to decrypt. A CI check (`check:phi-encryption-coverage`) now enforces alignment.

### Problem 5: Real-Time Clinic Operations

**Challenge:** Clinic staff need real-time updates — new appointments, payment confirmations, WhatsApp delivery status. Traditional REST polling is too slow and wastes bandwidth.

**Solution:** WebSocket gateways for real-time notifications. The payment gateway notifies the front desk instantly when a patient pays. The appointment system updates the calendar in real-time.

**What went wrong:** WebSocket connections are stateful — they don't survive server restarts gracefully. We implemented connection heartbeat and reconnection logic on the client.

### Why DDD (Domain-Driven Design)?

**Challenge:** 28 business domains (patients, appointments, billing, prescriptions, etc.) were growing organically. Services were importing from each other, creating coupling.

**Decision:** Each domain has 4 layers:

```text
domain/
├── core/           → entities, value objects, repository interfaces (no framework deps)
├── application/    → use-cases, DTOs, service orchestration
├── infrastructure/ → Prisma repositories, external API adapters
└── presentation/   → NestJS controllers, guards, interceptors
```

**Key rule:** Only repositories import PrismaClient. Enforced by CI check (`check:prisma-boundary`). This means business logic is testable without a database.

**Trade-off:** More boilerplate per domain. But the testability and maintainability payoff is worth it at 29 domains.

### Why Zod-First Types?

**Challenge:** TypeScript interfaces, Prisma models, and NestJS DTOs were diverging. A field added to Prisma wasn't reflected in the API contract.

**Decision:** Zod schemas in `packages/types` are the single source of truth. All other types are inferred via `z.infer`.

**Flow:** `Zod Schema → infer TS types → API contracts → UI forms → DB-safe DTOs`

**Trade-off:** Slightly more verbose schema definitions. But eliminates type drift entirely. The CI check ensures no schema is orphaned.

## 4. 14 Architecture Decisions (ADRs)

### ADR 0001: PostgreSQL as Queue (not Redis/BullMQ)

**Context:** Need a durable job queue for emails, WhatsApp, PDF generation.

**Alternatives considered:**

| Option | Pros | Cons |
| ------------------ | ------------------------------------------------------------------ | ----------------------------------------------------------------- |
| **Redis + BullMQ** | Sub-ms latency, mature ecosystem | Extra service cost, no transactional enqueue, extra failure mode |
| **AWS SQS** | Managed, reliable | Vendor lock-in, no transactional enqueue, cross-region complexity |
| **PostgreSQL** | Already paying for RDS HA, transactional enqueue, one less service | Throughput ceiling ~1k jobs/sec |

**Decision:** Postgres-backed queue using `SELECT ... FOR UPDATE SKIP LOCKED`.

**Key code pattern:**

```typescript
// apps/api/src/shared/modules/queue/postgres-queue.service.ts
async enqueue<T>(name: string, data: T, options?: QueueJobOptions): Promise<QueueJob<T>> {
  // Idempotency check — skip if recent completed job exists
  if (options?.idempotencyKey) {
    const recent = await this.findRecentCompletedByIdempotency(name, options.idempotencyKey);
    if (recent) return this.rowToJob(recent);
  }
  // RLS-BYPASS: background queue workers run without per-request clinic session
  const row = await this.prisma.runUnrestricted(async () =>
    this.prisma.queueJob.create({ data: { name, data, status: 'WAITING', ... } })
  );
  return this.rowToJob(row);
}
```

**Trade-off:** Not suitable for >1k jobs/sec. At our scale (~0.4 jobs/sec), fine.

**What would trigger revisiting:** If we add >100 clinics or real-time event streaming requirements.

### ADR 0005: Field-Level Encryption with Versioned Keys for PHI

**Context:** DPDP compliance requires field-level encryption. Stolen DB snapshot must be unreadable.

**Alternatives considered:**

| Option | Pros | Cons |
| ------------------------------------- | ---------------------------------- | --------------------------------------------------------------------- |
| **Full-disk encryption** | Zero code change | Doesn't protect against SQL injection or authorized-user exfiltration |
| **Application-level encrypt/decrypt** | Flexible | Easy to forget fields, drift between encrypt/decrypt |
| **Prisma extension** | Transparent, enforces at ORM level | Requires careful field list management |

**Decision:** 13 sensitive patient fields encrypted with AES-256-GCM (`v1:iv:tag:ciphertext`) using versioned keys. Prisma extension transparently encrypts before persist and decrypts on read.

**Why not full-disk encryption only:** Doesn't protect against SQL injection or authorized-user data exfiltration.

**Trade-off:** Cannot search encrypted fields. MRI, allergies, etc. stay plaintext (protected by RLS + audit).

### ADR 0006: Single-Region Postgres

**Context:** DPDP encourages Indian-region hosting. Multi-region active-active has significant complexity.

**Decision:** One primary in ap-south-1 (Mumbai) with managed PITR + daily snapshots.

**Why not multi-region:** Conflict resolution, replication lag, RLS interactions are premature at 25 clinics.

**What would trigger multi-region:** >200 clinics or explicit data residency requirements outside India.

### ADR 0008: AsyncLocalStorage for Tenant Context

**Context:** Every Prisma call needs `tenantId`. Threading it through every function is verbose and error-prone.

**Decision:** Use Node.js AsyncLocalStorage to carry request-scoped context.

**Why:** One missed parameter = data leak. ALS makes it implicit and impossible to forget.

**Code:**

```typescript
// apps/api/src/shared/common/middleware/tenant.middleware.ts
import { AsyncLocalStorage } from 'async_hooks';

interface TenantContext {
  clinicId?: string;
  userId?: string;
  bypassed?: boolean;
  preTenant?: boolean;
}

export const tenantStorage = new AsyncLocalStorage<TenantContext>();

export function getCurrentTenant(): TenantContext | undefined {
  return tenantStorage.getStore();
}
```

**Trade-off:** `setTimeout` loses context. Mitigated by `check-detached-promises.mjs` CI check.

### ADR 0010: Transactional Outbox

**Context:** Domain events emitted via in-process `EventEmitter2`. Single pod = fine. But listener failures aren't retried, and splitting across pods drops events.

**Alternatives considered:**

| Option | Pros | Cons |
| ---------------------------- | -------------------------------------- | --------------------------------------------- |
| **In-process EventEmitter2** | Simple, zero latency | No persistence, no cross-pod, no retry |
| **Kafka/NATS** | Durable, high throughput | Extra infrastructure, premature at 25 clinics |
| **Transactional outbox** | Durable, transactional, zero new infra | Relay lag (seconds), polling overhead |

**Decision:** Write events to `OutboxEvent` table in same transaction. Relay scheduler polls and republishes.

**Key code pattern:**

```typescript
// apps/api/src/shared/modules/outbox/outbox.service.ts
async append(tx: Prisma.TransactionClient, event: OutboxAppend): Promise<void> {
  try {
    await tx.outboxEvent.create({
      data: {
        eventName: event.eventName,
        clinicId: event.clinicId,
        payload: toPrismaInputJsonValue(event.payload),
        idempotencyKey: event.idempotencyKey ?? null,
      },
    });
  } catch (error) {
    // P2002 on idempotencyKey means duplicate — treat as no-op
    const code = isRecord(error) ? error.code : undefined;
    if (event.idempotencyKey && code === 'P2002') return;
    throw error;
  }
}
```

**Relay scheduler:** Uses `FOR UPDATE SKIP LOCKED` for concurrent-safe batch processing, advisory locks to prevent cross-replica duplication, and exponential backoff for failed events.

**Trade-off:** Relay lag (seconds). Acceptable for our scale.

### ADR 0011: Fly.io Auto-Suspend Fix

**Context:** Fly.io auto-stop shut down the VM after idle. Next request triggered a 3-minute cold start. Fly's HTTP proxy only waits ~10-15s → 502 Bad Gateway on every cold start.

**Decision:** Keep one machine running (`min_machines_running = 1`), suspend scale-out capacity.

**How it evolved (current state in `fly.toml`):** usage is peak-hours (clinics run 8:30 AM–8:30 PM IST), so a flat always-on machine wasted money overnight. A CI workflow (`scale-api-hours.yml`) now schedules the floor: 1 machine during IST business hours, 0 off-hours, with `auto_start_machines` waking the suspended machine on demand. Cost is roughly halved while the 9-5 cold-start path is eliminated — a measured refinement of the original decision, not a reversal.

**Lesson learned:** Don't trust platform defaults for health check timeouts. Measure actual bootstrap time.

### ADR 0012: Replace Next.js with Vite SPA

**Context:** Next.js 16 + OpenNext bundle was ~3.5 MB gzip, over Cloudflare's 3 MB Free limit. Both apps are login-gated — no SEO need.

**Alternatives considered:**

| Option | Pros | Cons |
| ------------------------- | --------------------------------------- | -------------------------------------------------------------------------- |
| **Next.js SSR** | SEO, streaming, RSC | 3.5MB bundle, over Cloudflare limit, unnecessary for auth-gated dashboards |
| **Vite SPA + Cloudflare** | Tiny bundle, fast dev, zero server cost | No SSR, no SEO |
| **Remix** | Nested routes, progressive enhancement | Extra migration effort, less ecosystem |

**Decision:** Vite + React Router v7 SPAs on Cloudflare Static Assets. Tiny Hono proxy for `/api/*`.

**Why not Next.js SSR:** No SEO value for authenticated dashboards. Simpler deployment, faster dev.

**Trade-off:** Lost SSR benefits. Acceptable for SaaS dashboard.

### ADR 0013: ABAC-on-RBAC

**Context:** RBAC roles couldn't express "doctor can view only their assigned patients." Adding more roles = role explosion.

**Decision:** Keep RBAC guard chain, add `PolicyGuard` for object-level conditions.

**Why not pure ABAC:** Too complex for our scale. RBAC handles 90%; ABAC adds the missing 10%.

**Implementation:** Typed TypeScript classes in `packages/authorization`. Deny-overrides: any deny wins. Default deny.

**Code:** `packages/authorization/src/evaluator.ts`, `packages/authorization/src/policies/`

### ADR 0014: Cloudflare Origin Protection

**Context:** Fly.io origin is publicly reachable. Anyone who discovers the Fly IP can bypass Cloudflare's WAF, rate limiting, and bot protection.

**Decision:** Fly.io network policies don't support ingress filtering for `http_service` traffic. Mitigated at application layer: verify `CF-Connecting-IP` header, rate limit by application-level IP detection.

**Lesson:** Don't assume your CDN/proxy hides your origin. Always protect the origin directly.

### Appointment Workflow — Step by Step

**1. Create Appointment** (`CreateAppointmentUseCase`)

The appointment entity is a rich domain model with 30+ fields covering every clinical need:

```typescript
// apps/api/src/domains/appointments/core/entities/appointment.entity.ts
export interface AppointmentProps {
  id: string;
  clinicId: string;
  patientId: string;
  doctorId: string;
  startTime: Date;
  endTime: Date;
  status: AppointmentStatus;
  // Clinical fields (specialty-aware)
  chiefComplaint?: string;
  historyOfPresentIllness?: string;
  pastMedicalHistory?: string;
  reviewOfSystems?: string;
  provisionalDiagnosis?: string;
  finalDiagnosis?: string;
  treatmentPlan?: string;
  // Specialty-specific exam fields
  generalExamination?: unknown;
  systemicExamination?: unknown;
  dentalChart?: DentalChartData;
  ophthalmologyExam?: unknown;
  cardiologyExam?: unknown;
  gynecologyExam?: unknown;
  dermatologyExam?: unknown;
  psychiatryExam?: unknown;
  // Payment
  advance?: AppointmentAdvance;
  // Optimistic concurrency
  version: number;
}
```

**Why the entity is so large:** Each specialty (dental, cardiology, ophthalmology, etc.) needs different exam fields. Rather than separate entities per specialty, we use optional JSON fields. This keeps the schema unified while allowing specialty-specific UIs.

**Decision: Overlap detection** — The `AppointmentSchedulingRulesService` validates:
- Start time < end time
- No overlapping appointments for the same doctor (using interval arithmetic)
- Doctor time-off conflicts
- Minimum 15-minute, maximum 480-minute duration
- 5-minute buffer between appointments
- Business hours (9 AM – 6 PM local time)

**What happened:** Early versions used naive `startTime >= existing.endTime` checks. A timezone bug caused double-bookings when doctors跨越 UTC midnight. Fix: all scheduling uses clinic-local time converted to UTC bounds.

### Queue Management — Walk-in Patients

**Challenge:** Indian clinics have walk-in patients. Need a physical queue display (token numbers) + real-time updates.

**Solution:** `QueueCommandService` manages check-in → call → complete lifecycle:

```typescript
// apps/api/src/domains/appointments/application/services/queue.service.ts
checkIn(clinicId, appointmentId)   // Patient arrives
callPatient(clinicId, queueId)     // Doctor calls next patient
completePatient(clinicId, queueId) // Consultation done
resetQueue(clinicId)               // End of day
```

**Key design decision:** Queue tokens are generated from appointment IDs (not sequential numbers). This avoids race conditions when two front-desk staff check in patients simultaneously. The token is a hash prefix — unique, short, and deterministic.

### WhatsApp Response Handling — The Complex Part

**Challenge:** Patients reply to WhatsApp appointment reminders with "yes", "no", "delay 30 min", or custom text. The system must parse these, update appointment status, detect conflicts, and send confirmations.

**Solution:** `ResponseHandlerService` orchestrates the full flow — parse the reply, handle the two-step delay, persist the response, update the appointment, check for conflicts, confirm and notify. The method is owned by [06-whatsapp-integration](../projects/docita/06-whatsapp-integration.md) (Decision 2), which carries the code and its rationale.

**What was hard:** The two-step delay flow. Patient says "delay" → system asks "how many minutes?" → patient says "30" → system must associate the "30" with the pending delay request. We used a `pendingDelayResponse` lookup with a 6-hour follow-up window.

**Failure mode:** A patient replied "30" without a pending delay request. The system treated it as unknown. Fix: we now log a warning and send a clarifying message.

### Prescription Creation — Clinical Safety

**Challenge:** Prescriptions must not violate drug allergies, controlled substance regulations, or dosage limits.

**Solution:** `PrescriptionsCommandService` enforces multiple safety checks:

```typescript
// apps/api/src/domains/prescriptions/application/services/prescriptions-command.service.ts
async create(data: CreatePrescriptionCommand) {
  // 1. Doctor compliance check — must have digital signature + verified registration
  const doctorProfile = await this.repository.findDoctorCompliance(data.doctorId, data.clinicId);
  if (!doctorProfile.signatureUrl) throw new BadRequestException('DOCTOR_SIGNATURE_REQUIRED');
  if (doctorProfile.verificationStatus !== 'VERIFIED') throw new BadRequestException('DOCTOR_VERIFICATION_REQUIRED');

  // 2. Patient allergy check — critical allergies block prescription
  const allergyCheck = checkPrescriptionAllergies(data.medications, patientAllergies);
  if (allergyCheck.criticalWarnings.length > 0) throw new BadRequestException('Cannot prescribe due to critical allergies');

  // 3. Controlled substance validation
  for (const med of data.medications) {
    validateControlledSubstances(med.name, med.dosage);
    validateDosage(med.name, med.dosage);
  }

  // 4. Create prescription + emit event for PDF generation
  const prescription = await this.repository.create(data);
  this.eventEmitter.emit(ApplicationEvents.PRESCRIPTION_CREATED, new PrescriptionCreatedEvent(...));
}
```

**Why doctor verification is required:** Indian law requires prescriptions to carry a verified doctor registration number. An unverified doctor cannot issue prescriptions — the system blocks it at the application level.

### Invoice Generation — Tax & Payment Complexity

**Challenge:** Indian healthcare invoicing involves GST (Goods and Services Tax), place-of-supply rules, and multiple payment methods.

**Solution:** `InvoicesCommandService` builds the seller/buyer registration snapshots from clinic and patient context — the builder is owned by [08-billing-invoicing](../projects/docita/08-billing-invoicing.md) (Decision 1), not reproduced here.

**Key design decision:** Tax snapshots are immutable — once an invoice is created, the tax calculation is frozen. If clinic tax settings change, existing invoices retain their original calculation. This is critical for audit trails.

### Razorpay Webhook Processing — Idempotency

**Challenge:** Razorpay can send the same webhook multiple times (at-least-once delivery). Processing a payment twice = double-crediting the clinic.

**Solution:** `RazorpayInvoiceWebhookService` checks the provider payment id first, then updates the session, transitions the invoice, and appends the outbox event in one transaction. The handler is owned by [04-payment-flows](../projects/docita/04-payment-flows.md) (Flow B).

**Why the outbox is used here:** The payment webhook triggers downstream events (update patient wallet, send receipt WhatsApp, update dashboard). These events must be delivered even if the API crashes after committing the payment. The outbox ensures exactly-once delivery with idempotent consumers.

## 6. Domain Deep Dives — Every Domain Explained

**What it does:** Clinical settings, lab workflow (order → sample → result → paid → release), medical coding (ICD-10, CPT), lab directory.

**Design decision:** A `CodeCatalogProvider` port hides two licensing realities — the **composite provider resolves the CPT source from configuration** (`nlm_hcpcs` by default, `licensed` when a CPT license + API key is configured), never "tries NLM then falls back" at runtime; ICD always routes to NLM. Search has a per-system circuit breaker; sync streams in batched, idempotent upserts. Full lifecycle in deep-dive 20.

### webhooks — 6 files (domain) → drill: [22-long-tail-domains](../projects/docita/21-long-tail-domains.md), [03-async-processing](../projects/docita/03-async-processing.md)

**What it does:** Webhook trust and delivery, split across two layers: the `webhooks` *domain* persists inbound webhook errors and audit events (into `errorLog`/`auditLog`, with payload hashes, never raw payloads); the shared `modules/webhooks` layer verifies inbound signatures (HMAC, timestamp tolerance, replay dedupe) and runs **outgoing** signed delivery with retry state.

**Key challenge:** Exactly-once semantics in both directions — inbound replay dedupe on the consumer side (e.g., Razorpay payment events), idempotency-keyed delivery rows on the producer side (`OutgoingWebhookDelivery`, max 5 attempts, exponential backoff).

**Correction vs. earlier drafts:** there is no single `WebhookEvent` table with a dead-letter queue; deliveries are per-subscription rows with retry counters, and inbound verification uses a TTL'd replay-claim store.

## 8. Security & Compliance

### Defense-in-Depth (7 layers)

```text
Layer 7: Audit logging — every PHI access logged
Layer 6: RLS — PostgreSQL row-level security (database-level)
Layer 5: Repository tenant scoping — Prisma middleware
Layer 4: PolicyGuard (ABAC) — object-level conditions
Layer 3: Subscription/tier guard — feature gating
Layer 2: RBAC roles matrix — role → permission
Layer 1: TenantGuard — AsyncLocalStorage tenant context
Layer 0: JWT auth — token validation + session management
```

### PHI Protection

- **Encrypted fields (13, source of truth `mapPatientRecordFields`):** firstName, lastName, preferredName, email, phoneNumber, address, emergencyContactPhone, emergencyContactName, insuranceProvider, insurancePolicyNumber, insuranceGroupNumber, allergies, abhaAddress
- **Encryption boundary:** Prisma extension — encrypt before persist, decrypt on read
- **CI gate:** `check:phi-encryption-coverage` enforces that the encrypt and decrypt field lists stay aligned and every encrypted field has a decryptor
- **Plaintext exceptions (not in the encrypted list):** MRN, bloodGroup, medicalHistory — kept plaintext for lookup/display, protected by tenant scoping + RLS + audit; the PHI policy mandates a migration plan before encrypting any lookup or indexed field

### RLS Rollout (Staged)

**Why staged:** RLS is a structural change with cross-cutting impact. Flipping it on in one shot risks breaking every query.

**Step 1:** Deploy migration (additive, policies short-circuit until `app.rls_enabled = 'on'`)
**Step 2:** Provision `docita_app` role (non-owner, subject to RLS)
**Step 3:** Set `RLS_ENABLED=true` in production
**Step 4:** Monitor for policy violations

**Key code:**

```typescript
// apps/api/src/shared/modules/rls/apply-rls-scope.ts
export async function applyRlsScope(tx: Tx, clinicId: string): Promise<void> {
  assertRlsClinicId(clinicId);  // regex validation — fail loudly
  // set_config(name, value, is_local) — is_local=true = SET LOCAL (reverts at tx end)
  await tx.$executeRaw`SELECT set_config('app.rls_enabled', 'on', true)`;
  await tx.$executeRaw`SELECT set_config('app.current_clinic_id', ${clinicId}, true)`;
}
```

**Why `set_config` not `SET LOCAL`:** The function-call form binds the value as a parameter, preventing SQL injection. The regex check is a second wall.

## 9. Failure Modes & Lessons Learned

### Failure 1: Cold Start Outage

**What happened:** Fly.io auto-stop shut down the VM after idle. Next request triggered a 3-minute cold start. Fly's HTTP proxy only waits ~10-15s → 502 Bad Gateway on every cold start.

**Root cause:** Trusted platform defaults without measuring actual bootstrap time.

**Fix:** Keep one machine running (`min_machines_running = 1`). Measure bootstrap time in CI.
**Later refinement:** usage is peak-hours, so `scale-api-hours.yml` now schedules the floor — 1 machine in IST business hours, 0 off-hours (auto-start wakes suspended machines).

**Lesson:** Don't trust platform defaults for health check timeouts.

### Failure 2: Cross-Pod Event Loss

**What happened:** Domain events emitted via in-process `EventEmitter2`. When we considered splitting the API across pods, cross-pod listeners would silently drop events.

**Root cause:** In-process event bus doesn't work across pods.

**Fix:** Transactional outbox pattern (ADR 0010). Events written to DB in same transaction, relay scheduler polls and republishes.

**Lesson:** In-process patterns don't survive horizontal scaling.

### Failure 3: Origin IP Exposure

**What happened:** Fly.io origin was publicly reachable. Anyone who discovered the Fly IP could bypass Cloudflare's WAF, rate limiting, and bot protection.

**Root cause:** Assumed CDN hides the origin.

**Fix:** Application-level origin verification (ADR 0014). Rate limiting by application-level IP detection.

**Lesson:** Always protect the origin directly, don't rely on CDN hiding it.

### Failure 4: RLS Silent Bypass

**What happened:** During RLS rollout testing, queries ran on a different connection than the one with `SET LOCAL app.current_clinic_id`. RLS policies short-circuited on the missing GUC — effectively a silent bypass.

**Root cause:** Prisma connection pool routes queries to different connections.

**Fix:** Route ALL queries through a single interactive transaction per request (`RlsService.runScopedTransaction`). This ensures the `SET LOCAL` and the query run on the same connection.

**Lesson:** Connection pooling + session variables = silent bypass unless you control the transaction scope.

### Failure 5: Encrypt/Decrypt Drift

**What happened:** A new PHI field was added to the encrypt list but not to the decrypt list. Patients could write data but not read it back.

**Root cause:** Manual alignment of two lists.

**Fix:** CI check (`check:phi-encryption-coverage`) enforces alignment.

**Lesson:** Any manual alignment between two lists will drift. Automate the check.

### Failure 6: WhatsApp Rate Limit Burst

**What happened:** A clinic sent 100+ appointment reminders simultaneously. Meta's WhatsApp API rate-limited the batch, causing 30+ messages to fail silently.

**Root cause:** No per-clinic rate limiting on outbound messages.

**Fix:** Rate limiter per clinic (configurable, default 30/min), exponential backoff on 429 responses, batch sending with 100ms delays between messages.

**Lesson:** External APIs have rate limits. Always implement client-side throttling.

### Failure 7: Invoice Double-Crediting

**What happened:** Razorpay sent the same `payment.captured` webhook twice within 5 seconds. The second webhook created a duplicate payment record and double-credited the clinic's wallet.

**Root cause:** At-least-once delivery without idempotency check.

**Fix:** Check `findByProviderPaymentId('razorpay', payment.id)` before processing. If exists, return early. Also added a unique constraint on `(provider, providerPaymentId)`.

**Lesson:** External webhook delivery is at-least-once. Always check for duplicates before processing.

## 11. Interview Q&A Scripts

### Q: "Tell me about the most complex system you've built."

> "I'm the founding engineer of Docita, a healthcare SaaS serving 25+ clinics with 1,000+ appointment workflows per month. The most complex aspect was multi-tenant data isolation — we needed provable separation between clinics handling Protected Health Information. I implemented a 7-layer defense-in-depth: JWT auth, AsyncLocalStorage tenant context, RBAC roles, ABAC policies for object-level access, Prisma repository scoping, PostgreSQL RLS, and audit logging. The hardest part was the RLS layer — Prisma's connection pool routes queries to different connections, so `SET LOCAL` session variables were silently bypassed. I solved it by routing all queries through a single interactive transaction per request using a custom Prisma extension."

### Q: "Why PostgreSQL as a queue instead of Redis?"

> "Operational simplicity. We already run AWS RDS PostgreSQL — adding Redis means another managed service, another failure mode, another secret to rotate. Our queue volume is ~0.4 jobs/sec sustained, within Postgres capabilities. The key advantage: transactional enqueue. A `prisma.$transaction` covers both the business write AND the job emission — no dual-write problem. We use `SELECT ... FOR UPDATE SKIP LOCKED` for pop-and-claim. The trade-off is throughput — if we hit >1k/sec sustained, we'd revisit Redis/NATS. But for 25 clinics, Postgres is sufficient and simpler."

### Q: "How do you handle data consistency across services?"

> "We use the transactional outbox pattern. Domain events are written to an `OutboxEvent` table in the same `prisma.$transaction` as the business write — atomic, no dual-write. A relay scheduler polls unpublished rows every 2 seconds and republishes to in-process EventEmitter2. Consumers are idempotent — they check a deduplication cache before processing. Failed events go through exponential backoff retry, then to a DLQ for manual inspection. We chose this over Kafka/NATS because we're single-region single-pod — outbox solves the problem with zero new infrastructure."

### Q: "How do you test multi-tenant isolation?"

> "Every integration test uses a fresh database snapshot and verifies cross-tenant isolation. The test creates data for clinic A, then attempts to access it as clinic B — asserting a 404 (not 403, to avoid leaking existence). We also have a CI check `check:prisma-boundary` that enforces only repository files import PrismaClient — preventing business logic from bypassing tenant scoping. Playwright E2E tests run the full patient journey across multiple clinics to verify isolation end-to-end."

### Q: "Why did you migrate from Next.js to Vite SPA?"

> "Docita's apps are authenticated dashboards — no SEO need. Next.js 16 + OpenNext bundle was ~3.5 MB gzip, over Cloudflare's 3 MB Free limit. Every feature port increased bundle size with framework overhead rather than app code. Vite + React Router gives us: simpler deployment (Cloudflare Static Assets), faster dev experience (sub-second HMR), smaller bundle, and zero server cost for frontend. The Hono proxy Worker handles `/api/*` routing to our Fly.io backend — same domain, no CORS. The migration was completed in one sprint with zero downtime."

### Q: "Walk me through the ABAC implementation."

> "We layered ABAC on top of existing RBAC — not a replacement. The guard chain is: JWT → TenantGuard → RBAC roles → Subscription/tier → PolicyGuard (ABAC). The PolicyGuard is a global NestJS guard that's a no-op unless a route declares `@RequirePolicy(resource, action)`. Policies are typed TypeScript classes in `packages/authorization` — pure functions, no framework imports. We use deny-overrides: any policy deny wins over any allow, and unmatched policies default to deny. For example, the patient resource resolver checks: same clinic? Doctor assigned to patient? Role permitted? Environment valid? All must pass. The emergency break-the-glass bypasses assignment checks but is audit-logged and read-only."

### Q: "How do you handle deployment and migrations?"

> "Deploy order: DB migrations first, then API/worker, then frontends. Fly.io runs `prisma migrate deploy` before API deploy — a verification script confirms no pending migrations or schema drift. The API and worker share the same Docker image base but have separate fly.toml configs. Frontends deploy to Cloudflare Workers with Static Assets. GitHub Actions triggers selective deploys — only apps whose related paths changed. We had a cold-start outage early on because Fly's proxy only waits ~10-15s but our NestJS bootstrap takes ~3 minutes. Fix: keep one machine running, measure bootstrap time in CI."

### Q: "What's the hardest technical challenge you faced?"

> "The RLS silent bypass. We enabled PostgreSQL Row-Level Security, but Prisma's connection pool routes queries to different connections. So `SET LOCAL app.current_clinic_id` would be set on connection A, but the actual query would run on connection B — which has no tenant context. RLS policies short-circuited on the missing GUC, effectively bypassing the security layer. We solved it by routing ALL queries through a single interactive transaction per request using `RlsService.runScopedTransaction`. This ensures the `SET LOCAL` and the query run on the same connection. It's the kind of bug that doesn't show up in unit tests — only in production with connection pooling."

### Q: "How do you handle WhatsApp at scale?"

> "WhatsApp is our primary patient communication channel — appointment reminders, prescription delivery, payment confirmations. We support three sender modes: shared Meta number (free), bring-your-own number (clinic's), and Docita-managed number. The challenge was handling patient responses — they reply with free text like 'yes', 'no', 'delay 30 min'. We built a response parser that maps these to appointment actions, with a two-step flow for delays. We also hit Meta's rate limits when a clinic sent 100+ reminders simultaneously — fixed with per-clinic rate limiting and exponential backoff. The reconciliation service runs daily to verify message delivery status matches our records."

### Q: "Explain the payment flow separation."

> "Three distinct payment rails that must never mix. Flow A: clinic's own Razorpay credentials (optional). Flow B: patient pays clinic using Flow A credentials. Docita SaaS: clinic pays Docita for subscription — separate merchant account. The risk: if a developer accidentally uses Docita's merchant key for a patient payment, Docita receives the patient's money. We enforce separation through naming conventions (`CLINIC_INVOICE_PAYMENT_LINK_PROVIDER_TOKEN` vs `DOCITA_PLATFORM_PAYMENT_LINK_PROVIDER_TOKEN`), code review gates, and documented flow boundaries. Technical debt: Flow B still delegates to a shared adapter instead of resolving a clinic-scoped provider from Flow A settings."

## 13. Docita Decision Deep-Dive — Why Everything Is the Way It Is

> This section is the interview armor for the "why" questions. For **every** decision in the repo, it answers the four questions interviewers actually probe: **Why was this chosen? What was rejected and why? What is honestly weak about it? What would make you revisit it?** Numbers here are measured from the repository at `~/repos/docita`, not estimated.

### 13.1 Stack Decisions — Every Choice Decoded

#### TypeScript (strict, everywhere)

- **Why chosen:** (1) The whole stack — API, worker, frontend, tests, scripts — shares one language, so domain types (Zod schemas) cross every boundary without impedance mismatch. (2) Strict mode turns the most expensive class of runtime bugs (undefined access, wrong shapes) into compile errors — critical when a solo engineer ships clinical features. (3) The `packages/types` + Zod-first architecture (below) only works if types are the first-class contract.
- **Rejected:** A polyglot split (e.g., Go API + TS frontend). Faster API, but two type systems, two testing cultures, and no shared contract layer — the exact thing multi-tenant healthcare needs most.
- **Weakness:** Build-time cost and the occasional type-drill-through (deep generics in Prisma + Zod + Nest). Nothing user-facing breaks because of it.
- **Revisit trigger:** If API p95 CPU-bound work became the bottleneck and a compile-time-only language would fix it without losing the shared-schema property.

#### NestJS 11 (API framework)

- **Why chosen:** (1) Opinionated modular structure (modules/controllers/services) that mirrors the DDD bounded contexts — each domain is a Nest module, which makes 29 domains navigable. (2) Built-in DI container, lifecycle hooks, pipes/guards/interceptors — the ABAC guard, tenant interceptor, and audit interceptor are framework features, not hand-rolled. (3) Decorator-driven design lets the Prisma tenant extension and validation pipes attach declaratively. (4) Large ecosystem for the boring parts (validation, config, logging).
- **Rejected:** Express (no structure — 29 domains would become a file graveyard), Fastify (faster, but plugins don't map to bounded contexts; slower adoption for an unfamiliar team), raw Node (no).
- **Weakness:** Nest is heavier than Express for simple routes; reflection/decorator magic makes flow harder to trace in a debugger.
- **Revisit trigger:** If we hit a hard performance wall that Nest's request pipeline added to (measured, not assumed).

#### Prisma 7 (ORM)

- **Why chosen:** (1) Single source of truth: `schema.prisma` (149 models, 5,045 lines) generates types — the schema IS the API contract. (2) The client extension system is what makes tenant scoping possible (the `tenant.extension.ts` auto-injects `clinicId` filters — see §4 ADR 0008). (3) Migrations are reviewable SQL; the repo runs schema changes through CI.
- **Rejected:** Raw SQL (correct but no type safety; 29 domains × 149 models would be unmaintainable), TypeORM/Drizzle (evaluated; Drizzle is lighter but its extension model didn't support the transaction-scoped tenant injection we needed), Knex (query builder only — no schema-as-contract).
- **Weakness:** Prisma's connection pooling and `SET LOCAL` interaction was THE source of the RLS silent-bypass failure (§9 Failure 4). Also: N+1 risk is easy to write; the team added query-plan reviews to compensate.
- **Revisit trigger:** If Prisma's generated-query overhead shows up in profiling as a real share of p95.

#### PostgreSQL 16 (single region)

- **Why chosen:** (1) One database does everything at this scale: relational data, the job queue (ADR 0001), the outbox (ADR 0010), advisory locks, JSONB for flexible fields. (2) RLS is the compliance-grade isolation mechanism (ADR 0004). (3) Transactionality across data + queue + outbox is the property that prevents double-crediting (§9 Failure 7).
- **Rejected:** MySQL (weaker RLS story, weaker advisory locks), MongoDB (no transactions at the level needed for billing; multi-tenant isolation harder to prove), Redis-as-primary (volatile, no transactions).
- **Weakness:** Single region = single point of failure (ADR 0006 accepts this deliberately at 25+ clinics).
- **Revisit trigger:** Multi-region need (real requirement, not hypothetical) — then RLS + read replicas + queue partitioning.

#### React 19 + Vite SPA (frontend)

- **Why chosen:** (1) After ADR 0012, the Next.js SSR layer was removed — at this scale, a SPA + CDN is faster to ship, cheaper, and eliminates server cold starts for the UI. (2) TanStack Query owns server state; Zod shared schemas own types (see Zod-first below). (3) Accessibility: the app ships keyboard/screen-reader tested flows — a compliance argument for clinic software.
- **Rejected:** Next.js (see ADR 0012 — the SSR value didn't justify the deploy complexity at single-region scale), Remix (similar reasoning).
- **Weakness:** SEO is irrelevant for an authenticated clinic app, so the SPA trade is free here — but the public booking/landing flows use separate static rendering where they need it.
- **Revisit trigger:** If a product need emerges for server-rendered public pages beyond what the Hono proxy + static assets already handle.

#### Zod-first types (shared contracts)

- **Why chosen:** (1) The same Zod schema validates HTTP input (NestJS pipe), form input (React Hook Form + zodResolver), and WebSocket payloads — one source of truth per domain. (2) `z.infer` derives TypeScript types, so `packages/types` is generated from schemas, never hand-synced. (3) Schema changes fail CI when clients would break (the zod-first architecture doc `docs/architecture/zod-first-architecture.md` codifies this).
- **Rejected:** Manual DTO types (drift between validation and types — the class of bug that leaks PHI-shaped data), io-ts (more FP ceremony than the team needed).
- **Weakness:** Schema-first means more boilerplate than type-first; occasionally schema rewriting is needed when DB shape diverges from API shape.
- **Revisit trigger:** If a GraphQL-style schema (Apollo/urql) ever justifies itself — Zod schemas port naturally.

#### pnpm + Turborepo (monorepo)

- **Why chosen:** (1) One repo = one PR can cross API, worker, frontend, and packages — essential when a feature touches 29 domains. (2) Turborepo caches test/build per package; CI runs only what changed. (3) pnpm's strict node_modules prevents phantom dependencies — a real bug source in npm/Yarn classic monorepos. (4) Shared packages (`auth`, `authorization`, `data-access`, `db`, `types`, `utils`, `ui`, `hooks`) enforce boundaries: the API cannot accidentally import frontend code.
- **Rejected:** Multi-repo (versioning sync hell for shared schemas), single flat package (no boundaries).
- **Weakness:** Tooling complexity (turbo + pnpm + workspace configs); contributors need to learn the workspace conventions.
- **Revisit trigger:** If a second team joins and the monorepo needs code-owner-based splitting.

#### Pino (logging) — ADR 0003

- **Why chosen:** (1) Structured JSON by default — logs are queryable, not greppable. (2) Performance: Pino is the fastest JSON logger; at high request rates the difference is measurable. (3) `nestjs-pino` binds request context (`requestId`, `tenantId`, `userId`) from AsyncLocalStorage — the same ALS used for tenancy, so every log line is attributable to a tenant (an audit requirement). (4) Sentry integration for error events.
- **Rejected:** Winston (slower, noisier structured output; its plugin ecosystem wasn't worth the perf cost), Nest's built-in logger (no JSON, no context binding — insufficient for production auditing).
- **Weakness:** Fewer transports/plugins than Winston; some tooling expects Winston-shaped output.
- **Revisit trigger:** If a log-shipping integration (e.g., a vendor) only supports Winston.

#### Infra: Fly.io (API/worker) + Cloudflare (edge/CDN/WAF) — ADRs 0002, 0009, 0011, 0014

- **Why chosen:** (1) Fly: the API app runs in region `sin` (Singapore — moved from `bom`/Mumbai 2026-07-29 when Fly shelved bom capacity; the Postgres primary stays on AWS RDS `ap-south-1`, so compute is close to the data). Per-machine config solved the cold-start problem (ADR 0011), now schedule-scaled by business hours. (2) Cloudflare: DNS + WAF + CDN + Workers + R2 in one account — DDoS protection, edge geo-control, and static hosting for the Vite SPAs. (3) R2 holds generated PDFs and documents (26-file `documents` domain, prescription PDFs).
- **Rejected:** AWS (overwhelming service surface for a solo founder; cost), Vercel (retired — ADR 0009 — because Cloudflare already hosted the frontend and the dual-target ambiguity hurt contributors), self-hosted Kubernetes (operational overhead with zero benefit at 25 clinics).
- **Weakness:** Fly is a smaller platform — fewer managed features than AWS; Cloudflare Workers have cold starts and runtime limits for heavy compute (kept light by design: the Worker is a tiny Hono proxy, static assets, and R2 signing).
- **Revisit trigger:** If the API needs horizontal auto-scaling beyond Fly's machine model, or if a clinic contract demands AWS/GCP.

### 13.2 All 14 ADRs — Full Reasoning, Including What Could Be Better

> §4 above summarizes the decisions and their context. This section adds the parts interviews probe hardest: the ranked **why**, the **rejected alternatives with their real rejection reason**, and an honest **weakness** + **revisit trigger** for each.

#### ADR 0001 — PostgreSQL as Queue (not Redis/BullMQ)

- **Why this was chosen, ranked:** (1) *Transactional enqueue* — the job row commits in the same transaction as the business data. If creating an appointment and enqueuing a WhatsApp reminder must be atomic, only a DB queue gives you that for free. (2) *One less service* — no Redis to run, secure, monitor, and pay for. (3) *Scale honesty* — at ~0.4 jobs/sec sustained, a `FOR UPDATE SKIP LOCKED` queue is overkill-in-reverse; Redis would be idle complexity. (4) *Survivability* — jobs survive restarts by construction.
- **Rejected:** Redis/BullMQ (sub-ms latency, mature — but non-transactional enqueue means a crash between business write and enqueue loses the job; extra failure mode), AWS SQS (vendor lock, no transactional enqueue, cross-region latency).
- **Weakness:** Throughput ceiling (~1k jobs/sec); long-polling workers on Fly machines are a fixed cost even when idle; no built-in scheduling/retry UI.
- **What could be better:** Add a proper dead-letter + replay UI (replay exists via scripts; a dashboard would help ops), and back-pressure stats per queue name.
- **Revisit trigger:** >100 clinics or real-time event streaming needs. The outbox (ADR 0010) already isolates the *write* path; the queue is the *delivery* path and can swap independently.

#### ADR 0002 — Cloudflare via OpenNext (superseded by ADR 0012)

- **Why it was chosen then:** Next.js apps needed a host; Cloudflare Workers via OpenNext gave edge + CDN + geo-locality in one account, at lower cost than Vercel's egress/function pricing at our scale. The internal admin app needed SSO + strict geo-allowlist, which Cloudflare made enforceable at the edge.
- **Rejected:** Vercel (zero-config, best Next DX — but egress pricing and less geo control; India-locality preference), self-host Next on Fly (single stack — but reinventing OpenNext for cold starts and edge caching).
- **What happened next:** Replaced entirely by ADR 0012 (Vite SPA + Hono proxy Worker). The lesson: the decision was right for the *then* stack; when the stack changed, the deploy target changed with it. Interviews love this story — it shows decisions are coupled and revisitable.
- **Revisit trigger:** Gone — superseded.

#### ADR 0003 — Pino over Winston

Covered in §13.1 (logging).

#### ADR 0004 — Defer RLS to a phased rollout

- **Why this was chosen, ranked:** (1) *Risk sequencing* — flipping RLS on 149 models at once would have been a compliance incident waiting to happen; the app-layer extension already worked, so RLS was hardening, not a bug fix. (2) *Learnable rollout* — enabling RLS on read-mostly models first (AuditEvent, Notification) surfaces integration bugs cheaply, before write-heavy models (Patient, Appointment, Prescription) where a mistake corrupts clinical data. (3) *Belt-and-suspenders permanence* — the plan keeps the app-layer extension forever; RLS is the second wall, not a replacement.
- **Rejected:** Full RLS cutover in one release (single point of failure: if the `SET LOCAL` path breaks, ALL tenant queries fail), RLS-only with no app layer (no defense in depth; a policy bug becomes a leak).
- **Weakness:** The application layer remains the effective control today; RLS is staged, so the DB-level invariant is not yet universal. That's the honest answer to "is it fully RLS-enforced yet?" — no, deliberately, and here's the rollout plan.
- **Revisit trigger:** Completion of phase 3 (write-heavy models), or a security audit finding that demands DB-level enforcement sooner.

#### ADR 0005 — Field-Level Encryption with Versioned Keys for PHI

- **Why this was chosen, ranked:** (1) *Field-level granularity* — 13 identity/contact fields are encrypted at the Prisma boundary (`mapPatientRecordFields` in `encryption-patient-fields.boundary.ts`: name fields, phone, email, address, emergency contacts, insurance identifiers, allergies, ABHA address), not whole rows; queries that don't touch PHI stay indexable. (2) *Rotation with key versioning* — prefixing payloads with `v1:iv:tag:ciphertext` allows new writes to use the current key version while existing records decrypt with their tagged version, avoiding forced table rewrites. (3) *Stolen-snapshot defense* — a DB dump is unreadable without the secret key (which lives in env/secret manager, not the DB).
- **Rejected:** Full-disk encryption (doesn't protect against SQL injection or authorized-user exfiltration — the actual threat model), app-level ad-hoc encrypt (drift between encrypt/decrypt — the failure this design exists to prevent), encryption at rest only (same gap).
- **Weakness:** Encrypted fields can't be filtered/searched in SQL — queries on PHI must decrypt in app code (acceptable for 13 fields); automated background re-encryption of older versions is manual today (ADR 0007 addresses this).
- **Revisit trigger:** New PHI field types that need queryability — would require a searchable-encryption design (hash index + encrypted payload).

#### ADR 0006 — Single-Region Postgres

- **Why this was chosen, ranked:** (1) *Consistency beats availability here* — billing and prescriptions must never silently diverge; single-region Postgres with HA gives strong consistency with zero replication lag complexity. (2) *All clinics are India-based* — multi-region would add latency, not customers. (3) *Operational simplicity for a solo founder* — one region, one backup story, one failover path.
- **Rejected:** Multi-region active-passive (read replicas + RPO/RTO engineering that 25 clinics don't need), CockroachDB/Yugabyte (distributed SQL — enormous complexity for this scale).
- **Weakness:** A regional outage takes everything down. Mitigation: automated backups, documented restore runbook, and the fact that clinics tolerate minutes of downtime better than data divergence.
- **Revisit trigger:** A clinic contract with an availability SLA, or a second-region customer base.

#### ADR 0007 — Key rotation cadence (proposed, not yet implemented)

- **Why proposed:** Field-level encryption supports key versioning, but today re-encrypting older records to the latest version is manual or on-read. That's a compliance gap: DPDP-style regimes expect *demonstrable* periodic key rotation.
- **The plan:** (1) `ENCRYPTION_KEY_VERSIONS` env (JSON list of `{version, key}`) so old + new keys decrypt during a window. (2) Scheduled re-encryption worker job (`kek-rewrap.scheduler.ts`) batching row re-encryption. (3) 12-month default cadence, ad-hoc on incident.
- **Why not done yet:** Security-critical, touches every encrypted read/write; prioritized after RLS rollout. **Say this in interviews**: "I know exactly what's missing — it's documented with a plan, and here's why it's sequenced after RLS." That's a stronger answer than pretending everything is done.
- **Revisit trigger:** RLS phase 2 complete, or any security review.

#### ADR 0008 — AsyncLocalStorage for Tenant Context

- **Why this was chosen, ranked:** (1) *Implicit propagation* — the tenant id rides the async context, so service code doesn't pass `clinicId` through every signature (which is exactly how it gets forgotten). (2) *Framework-native* — works with Nest DI, interceptors, and the queue worker via `runWithContext`. (3) *Bypass escape hatch* — the tenant extension supports `tenant.bypassed` for background workers, but that's an explicit, reviewed action — the bypass is visible in code review, not silent.
- **Rejected:** Thread-local storage (not async-aware — the classic Node footgun), manual propagation (parameter threading — the forgetting risk that caused real bugs), per-request context objects (same).
- **Weakness:** Context leakage if a promise escapes the request scope (mitigated by `ALS` lifecycle hooks and tests); ALS is invisible — debugging "why did this query scope to clinic X" requires knowing the mechanism.
- **Revisit trigger:** If a new runtime (e.g., a different worker runtime) doesn't support ALS — then an explicit context parameter pattern becomes necessary.

#### ADR 0009 — Retire Vercel

- **Why this was chosen:** One deploy path. Both `vercel.json` and `wrangler.toml` were wired at some point, leaving contributors unsure which is canonical. Cloudflare won (ADR 0002 lineage) — Vercel became a config that could silently diverge.
- **Rejected:** Keeping both (dual-target ambiguity = drift = broken CI expectations), Vercel-only (would strand the Cloudflare WAF/origin-protection investment).
- **Weakness:** Team members who preferred Vercel preview deployments lost that workflow.
- **Revisit trigger:** A new ADR superseding this one — deliberately required, so a Vercel comeback is a considered decision, not a config revert.

#### ADR 0010 — Transactional Outbox

- **Why this was chosen, ranked:** (1) *Atomicity* — the event row commits with the business transaction; no window where "invoice created but event lost." (2) *Ordering* — the outbox preserves commit order, which matters for money events (double-crediting prevention, §9 Failure 7). (3) *Recovery* — a poller scans for `PENDING` rows with retry/backoff and dead-letter replay; the data is the source of truth, not a broker's in-memory state. (4) *Multi-pod readiness* — advisory locks coordinate pollers when the app scales past one machine.
- **Rejected:** Kafka (event streaming at 25 clinics is a solar panel on a flashlight), Redis pub/sub (at-least-once with no persistence — loses events on crash), direct `await emit()` in the request path (the failure ADR 0010 exists to fix — slow consumers block requests).
- **Weakness:** Polling latency (bounded ~seconds); outbox rows need cleanup; the pattern is DB-bound by design — high throughput would outgrow it.
- **Revisit trigger:** Event volume that exceeds poller throughput, or multi-region needs — then a broker with transactional ordering (or Kafka-compatible) becomes justified.

#### ADR 0011 — Fly Auto-Suspend Fix

- **Why this was chosen:** Fly's zero-machine auto-suspend caused 20-30s cold starts for the first request after idle — unacceptable for a clinic opening the app during a consultation. `min_machines_running=1` keeps one machine warm; cost is a fraction of the value.
- **Rejected:** Client-side keepalive pings (works only while tabs are open — clinics close the app), accepting the cold start (a doctor mid-consultation will not wait 30s), moving to a serverless API (the Prisma/WebSocket long-lived needs don't fit Workers).
- **How it evolved:** A flat always-on machine wasted money overnight. Current `fly.toml` schedules the floor via `scale-api-hours.yml` — 1 machine during IST business hours, 0 off-hours, auto-start waking suspended machines. Halves cost, keeps the 9-5 path warm.
- **Weakness:** Off-hours requests still pay a cold-start wake-up; the schedule assumes clinic hours (a 24/7 clinic would need the floor always on).
- **Revisit trigger:** A 24/7 clinic customer, or if cost per clinic becomes material.

#### ADR 0012 — Replace Next.js with Vite SPA

- **Why this was chosen, ranked:** (1) *Deploy simplicity* — static assets + a tiny Hono proxy Worker replaced the OpenNext compatibility layer (which had shims, bootstrap hacks like `globalThis.__name`, and upgrade verification friction). (2) *Performance* — no SSR cold starts; the SPA + CDN is faster for authenticated app users than a server-rendered flow. (3) *Auth reality* — the app is 100% behind login; SSR's SEO benefit is worthless here. (4) *Consistency* — both `apps/app` and `apps/internal` moved; one pattern.
- **Rejected:** Keep Next (OpenNext friction + dual deploy paths), Remix (same SSR trade-offs), SPA on Fly (would couple static hosting to API machines — Cloudflare does it better/cheaper).
- **Weakness:** Client-side routing means JS must load before first paint; the public landing page needed separate static handling.
- **Revisit trigger:** A public, SEO-sensitive surface (e.g., public booking pages) — then a lightweight SSR layer (or prerendering) for that surface only.

#### ADR 0013 — ABAC on RBAC

- **Why this was chosen, ranked:** (1) *Deny-by-default at the object level* — RBAC answers "can a doctor log in?" but not "can THIS doctor edit THAT patient's record?" ABAC policies (`packages/authorization/src/policies`, 6 policies: Patient, Appointment, AuditLog, Prescription, Invoice, LabOrder) evaluate attributes (owner, clinic, role, status). (2) *Pure evaluator* — the ABAC engine is a pure function (`evaluator.ts`) with property tests (`evaluator.test.ts`); security logic has zero I/O, so it's exhaustively testable. (3) *Composable with RLS* — ABAC is the app-layer half of defense-in-depth; RLS is the DB half.
- **Rejected:** RBAC-only (coarse — object-level leaks between same-role users), hand-rolled `if` chains in services (unbounded, untested, easy to bypass — the exact thing ABAC centralizes), policy-as-DB-rows (runtime-configurable but harder to review/version — policies live in code and go through PR review).
- **Weakness:** Policy evaluation adds a query/attribute lookups per request; policy maintenance requires understanding the DSL.
- **Revisit trigger:** If policy count grows beyond ~15, consider a policy language (OPA-style) or policy-as-code tooling — the pure evaluator makes that migration mechanical.

#### ADR 0014 — Cloudflare Origin Protection

- **Why this was chosen, ranked:** (1) *The origin was exposed* — a misconfigured DNS/WAF gap let requests bypass Cloudflare straight to the Fly origin (§9 Failure 3). (2) *Application-level verification* — the API verifies that requests actually passed through Cloudflare (header/IP verification), so DNS misconfiguration cannot silently expose the origin again. (3) *Defense in depth* — even if WAF rules regress, the app rejects non-Cloudflare traffic.
- **Rejected:** Cloudflare-only WAF rules (they failed once; the app must not depend on them alone), IP allowlisting only (breaks legitimately changing origin IPs, brittle), moving the API behind a VPN (kills public API clients).
- **Weakness:** If Cloudflare's proxy is down, the API rejects valid traffic too (dependency coupling) — accepted for DDoS protection.
- **Revisit trigger:** If a second CDN/provider is added (multi-CDN traffic steering already exists in `40-platform` patterns — then per-provider verification).

### 13.3 Why Five Apps

| App | Role | Why separate |

### 13.6 The Recurring Decision Logics

Every ADR above reduces to five logics. Name them when interviewers ask "what patterns do you repeat?"

1. **Transactional integrity > latency.** Queue in Postgres (0001), outbox (0010), idempotency on webhooks — every money path prefers "correct under crash" over "fast".
2. **Defense in depth, never a single control.** RLS + app extension + ABAC + audit (0004, 0008, 0013) — each layer is designed to fail safe even if another is bypassed.
3. **Fewer services until measurement says otherwise.** One Postgres, one region, one queue (0001, 0006) — every rejected option (Redis, Kafka, SQS) was rejected on "at 25 clinics, this is idle complexity".
4. **Explicit over clever.** Bypasses are named and reviewed; policies live in code, not DB rows; superseded ADRs are recorded, not deleted (0002 → 0012 → 0009 chain).
5. **Automate the invariants.** CI gates check Prisma boundaries, PHI encryption coverage, policy coverage — the same philosophy as the alignment tooling: if it can drift, a script must catch it.

### 15.1 Drill 1 — "Why not Redis? Why not Kafka?" (Queue + Outbox)

**Q:** "Your worker processes WhatsApp sends, PDFs, and payments. Everyone uses Redis or Kafka for this — why is your queue a Postgres table?"

**Expected core answer (60s):** Two async paths, two reasons. *Delivery path* (jobs): ADR 0001 — a Postgres queue because the enqueue must be **transactional with the business write**. When an invoice is created and a job must follow, `prisma.$transaction` commits both or neither — no dual-write, no "job lost between write and enqueue" window. At ~0.4 jobs/sec sustained, `FOR UPDATE SKIP LOCKED` pop-and-claim is far inside Postgres's ceiling. *Event path* (domain events): ADR 0010 — the **transactional outbox** writes events in the same transaction, a relay publishes them, consumers are idempotent with a dedup cache. Both rejected a broker because at 25 clinics a broker is idle complexity with a real ops tax.

**Follow-up ladder:**

| Probe | What it tests | If you only say… |
| -------------------------------------------------------------------------------------------- | ------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| "But Redis gives you sub-ms latency and BullMQ is battle-tested — what exactly do you lose?" | Whether "not Redis" is a real trade analysis, not dogma | "It's simpler" → probe: "Simpler for whom, at what throughput cost?" |
| "What happens if a worker crashes between reading a job row and finishing it?" | The **claim-and-timeout** mechanics of a DB queue | "Jobs are re-queued" → probe: "How? What prevents two workers from processing the same job?" (Answer: `SKIP LOCKED` claim, then a lease/timeout that returns the job; idempotency keys are the second wall.) |
| "You said transactional enqueue — walk me through the exact SQL/transaction boundary." | Whether you've actually written the `$transaction` | Names `prisma.$transaction` + the outbox row insert without hand-waving |
| "When would you switch to Kafka — what's the measured trigger?" | That you know the ceiling, not just the story | "If we scale up" → probe: "Scale of what — clinics, events/sec, or regions?" (Answer: >1k jobs/sec sustained, event volume exceeding poller throughput, or multi-region — ADR 0001/0010 revisit triggers.) |
| "Why not SQS?" | Broker options beyond the famous two | "Vendor lock" + "no transactional enqueue" + the at-25-clinics framing |

**Pass bar (5/5):** You name the *two paths* (delivery vs events), say "transactional enqueue" unprompted, describe `SKIP LOCKED` claiming with a timeout, and give a *measured* revisit trigger. ### 15.2 Drill 2 — "RLS mechanics — how does it actually work?"

**Q:** "You mention Row-Level Security. Walk me through the mechanism — how does a query from clinic A know to only see clinic A's rows?"

**Expected core answer (60s):** RLS is a **database-enforced per-row filter**. Every tenant table gets a policy like `USING (clinic_id = current_setting('app.current_clinic_id')::uuid)`. The API doesn't rely on the app remembering to filter — the database refuses rows that don't match the session's clinic. The session is set with `set_config('app.current_clinic_id', $clinicId, true)` — the `true` makes it `SET LOCAL`, scoped to the transaction and reverted at commit/rollback so a clinic can't leak into the next transaction. It's applied transaction-scoped, not connection-scoped, so pooled connections can't carry one clinic's scope into another tenant's work (that was the RLS silent-bypass failure — Failure 4).

**Follow-up ladder:**

| Probe | What it tests | If you only say… |
| --------------------------------------------------------------------------------------------------------- | ------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| "`set_config` vs raw `SET LOCAL` — why the function form?" | SQL-injection awareness at the *mechanism* level | "They're the same" → the function form parameterizes the value; raw `SET LOCAL` string-concatenates it |
| "The Prisma tenant extension also filters every query — so why RLS too? Isn't that redundant?" | Defense-in-depth vs cargo-cult | "Belt and suspenders" → probe: "What specific failure does the *second* wall catch that the first can't?" (Answer: a future query path — raw SQL, a new developer, an ORM bypass — that forgets the app-layer filter; RLS is the invariant that can't be forgotten.) |
| "Your ADR defers RLS to a phased rollout. Isn't that admitting your data isn't actually protected today?" | The honest-gap frame without collapsing | "We're not protected" (wrong — app layer is the effective control) *or* "we're fully protected" (wrong — DB invariant isn't universal). The answer: app layer is live now; RLS is the second wall rolling out read-mostly → write-heavy; the *plan* is the answer, sequenced for risk |
| "What breaks when you enable RLS on a model — concretely?" | That you've felt the failure, not read about it | Failure 4: Prisma + connection pooling + `SET LOCAL` interaction silently bypassed policies — the integration bugs are *why* it's staged |
| "How do background workers run queries outside a request's clinic context?" | The bypass design | `tenant.bypassed` is an explicit, reviewed action visible in code review — not silent; and it's annotated/CI-checked (`check-rls-bypass-annotation`) |

**Pass bar (5/5):** You can draw the policy line, explain `set_config(..., true)` = transaction-scoped `SET LOCAL`, name the pooling/bypass failure mode, and defend the staged rollout as risk sequencing rather than incomplete work.

| "What would you add next if you had a month?" | Forward thinking + honesty | "Nothing, it's done" → the honest list: a check that flags PHI added outside the 13-field boundary (partial today), cross-domain *runtime* (not just import) coupling, and policy-as-code parity between the RLS rollout and the checks that track it |

**Pass bar (5/5):** You name 2-3 real check names from §14.2, tell one failure story they exist to prevent, and — the differentiator — articulate what the checks *can't* catch and how you compensate.

### 15.4 Drill 4 — "The AI gating — controlled how?"

**Q:** "Your resume says 'controlled AI-assisted capabilities.' What does controlled mean in production — what stops a clinic from getting features they shouldn't, and what happens when the model is down?"

**Expected core answer (60s):** Every word maps to code. **Controlled**: AI is a paid add-on gated by `intelligenceAddon === 'ACTIVE'` **and** `meetsMinimumTier(clinic.tier)` — deny by default; every feature flag (`predictiveAnalytics`, `prescriptionAssistant`, …) defaults to **false** and flips per clinic after validation. **Quotas**: AI rides the same usage-tracking path as paid features (subscriptions domain). **Timeouts**: `AI_REQUEST_TIMEOUT = 5000` ms — an OpenAI call never hangs a prescription screen. **Validated**: Zod-validated DTOs on every AI boundary; `check-json-column-zod.mjs` forbids untyped JSON columns. **Resilience**: singleton client (CI-enforced) + a circuit breaker — so an OpenAI outage becomes "feature unavailable", not degraded clinical flows. Because AI sits behind the *existing* tier/quota system, monetization and abuse-control reuse one code path.

**Follow-up ladder:**

| Probe | What it tests | If you only say… |
| ------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| "Your honest weakness note says some flags are provisioned ahead of real models. Isn't that claiming AI you don't have?" | The honesty frame under pressure | Defensive → answer: "The *controls* are production — tiering, quotas, timeouts, circuit breaker, gating. Specific models behind individual flags roll out progressively. I'd rather say that than imply the models do more than they do." |
| "Why a circuit breaker for an external API — what's the failure it prevents?" | You understand the resilience pattern, not just the word | "So it doesn't crash" → probe: "What state does the breaker hold, and what happens to the request while it's open?" (Answer: fail-fast fallback to 'feature unavailable'; the registry tracks failure thresholds so a degrading provider doesn't eat request timeouts one-by-one — cross-ref the circuit-breaker pattern in the resilience stack.) |
| "PHI goes to OpenAI — how is that legal/safe?" | You've thought about the data boundary | "We encrypt everything" → probe: "Encryption at rest doesn't help a model provider. What's the actual boundary?" (Answer: which fields/features may call the provider, geo/processing terms, and that the *sensitive* features are gated + the payload is minimized — plus the compliance docs §14.4.) |
| "Who decides a clinic gets a feature, and how is that auditable?" | The governance story | Vague → the feature-flags module + subscriptions domain + audit log = the decision is data, not a conversation |

**Pass bar (5/5):** You map each resume word to code (§14.1 table), state the deny-by-default posture, describe the breaker + timeout behavior under provider failure, and volunteer the honest gap yourself before being pushed.

### 15.5 Drill 5 — "The honest gaps — what's NOT done?"

**Q (the closing probe of a senior interview):** "You've talked about a lot of engineering. What in this system is *not* done — what would you fix first with a month of runway?"

**Expected core answer (60s):** Lead with the three documented gaps, each with a plan: (1) **Automated key rotation and background re-encryption is proposed, not shipped** (ADR 0007) — the biggest open security gap; field-level encryption supports key versioning but background re-encryption of older records is manual today; the plan is versioned key env + scheduled batch re-encrypt + 12-month cadence, sequenced after RLS phase 2. (2) **RLS is mid-rollout** — the app layer is the effective control; DB-level enforcement isn't universal yet, deliberately, per the phased plan. (3) **Real-time is single-machine** — WebSockets work today; the multi-machine scaling doc is the plan, not the state. Then the self-critique (§13.7): I'd have started RLS earlier and shipped the outbox from day one — the outbox arrived *after* a real double-credit failure, which is the expensive way to learn a cheap pattern.

**Follow-up ladder:**

| Probe | What it tests | If you only say… |
| -------------------------------------------------------------------------------------------------- | ------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| "Which single gap would an auditor find first?" | Prioritization under a compliance lens | Any answer without reasoning → Automated key rotation (a DPDP-style regime expects *demonstrable* rotation; it's documented as proposed) |
| "You said the outbox arrived after a failure. What was the failure and why did the outbox fix it?" | You can tell a failure story with the *mechanism* | Failure 7: invoice double-crediting — an event emitted outside the business transaction could be lost/duplicated on crash; the outbox made emit-and-commit atomic, and consumers became idempotent |
| "If RLS is the real control you want, why not just finish it before anything else?" | Sequencing judgment | "Good question" → risk sequencing: read-mostly models first surface integration bugs cheaply; write-heavy clinical models are where a policy bug corrupts data — you stage by blast radius, and the app layer holds meanwhile |
| "What would make you *not* recommend Docita's architecture to another startup?" | Transferable judgment, not blind advocacy | Nothing → honest transfer: the DB-queue + single-region + field-level encryption stack assumes ≤ low-hundreds of clinics and India-only operation; a global multi-region product with real-time needs would start with a broker and a different replication story from day one |

**Pass bar (5/5):** You volunteer the gaps *before* the interviewer finds them, each with a plan and a sequencing reason — the §14.7 closing-script posture, but now with the full §13.7 self-critique depth behind it. This drill is the single highest-leverage one: it converts "I know what's missing" from a sentence into a rehearsed, defensible position.

### 15.6 Rapid-Fire (5 minutes — answer each in 1-2 sentences)

1. Why Postgres for the queue? → *Transactional enqueue with the business write; no dual-write; 0.4 jobs/sec is inside the ceiling.*
2. SKIP LOCKED — what does it do? → *Claims the row atomically without blocking other claimants; workers never fight over the same job.*
3. Outbox — one sentence. → *Events commit with the business data, then a relay publishes them — emit is never a separate, losable step.*
4. RLS — where does the session scope live? → *Transaction-scoped `SET LOCAL` via `set_config(..., true)`, so pooled connections can't leak one clinic into another.*
5. Why RLS *and* an app-layer filter? → *The app layer is the fast control; RLS is the invariant that can't be forgotten — two walls, different failure classes.*
6. One CI check that prevents a PHI leak. → *`check-phi-encryption-coverage` — a PHI field added without encryption fails the PR.*
7. AI — what's the actual production control? → *Tier + add-on gate, deny-by-default flags, quota path, 5s timeout, circuit breaker, Zod-validated boundary.*
8. OpenAI is down — what do users see? → *"Feature unavailable" — the breaker fails fast; clinical flows never hang on the model.*
9. Your biggest open gap? → *Automated key rotation — proposed with a plan, sequenced after RLS phase 2.*
10. What would you redo? → *RLS earlier and the outbox from day one — the outbox cost a real double-credit failure to learn.*
11. When do you add Kafka? → *>1k jobs/sec sustained, event volume past poller throughput, or multi-region — measured, not speculative.*
12. Why not just use Vercel? → *Retired (ADR 0009) — Cloudflare hosts the frontend; one deploy path beats two that can silently diverge.*

**Rapid-fire pass bar:** 10/12 without hesitation. Anything you pause on is a section to re-read — 15.1-15.5 map to the drills above.

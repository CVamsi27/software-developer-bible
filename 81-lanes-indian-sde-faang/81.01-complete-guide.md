# SDE Interview Preparation — Build a Defensible Solution

Begin with the assessment you need to prepare for and an observed skill gap. This lane organizes practice; the shared chapters contain the language, algorithm and architecture explanations.

## Definition

Interview preparation develops the ability to establish a contract, derive a correct approach, implement it, and explain how it behaves when inputs or constraints change.

## First Principles

A correct answer depends on its assumptions. Preparation must expose those assumptions through examples, traces and follow-ups. Reading the same algorithm in several files adds maintenance work without showing that you can reconstruct it.

## Stage 1: establish the actual assessment

Record the role, interview format, language, tools, duration and expected scope from the invitation. Separate confirmed requirements from unknowns. A company name or seniority label does not supply a universal loop, problem difficulty, or hidden scoring rubric.

If Java is the confirmed language, start with [language fundamentals](../20-backend/20.13-java/20.13.01-java-language-fundamentals.md), [OOP and interfaces](../20-backend/20.13-java/20.13.02-java-oop-solid.md), and [concurrency](../20-backend/20.13-java/20.13.03-java-concurrency-multithreading.md). For a JavaScript or TypeScript assessment, use their [JavaScript](../10-frontend/10.1-javascript/INDEX.md) and [TypeScript](../10-frontend/10.2-typescript/INDEX.md) learning paths.

Run a short [diagnostic practice attempt](81.06-leetcode-study-plan.md). Record the actual gap in [the practice log](81.08-progress-tracker.md): contract, reasoning, implementation, boundary handling or explanation.

## Stage 2: derive the algorithm before selecting a pattern

Use a concrete input, describe a straightforward solution, and identify the work you can remove. Then state the invariant that makes the improved solution correct.

For a fixed window of two values:

```text
input: [4, -6, 3]
first sum: 4 + (-6) = -2
move once: remove 4, add 3 → -2 - 4 + 3 = -3
largest valid window sum: -2
```

Zero is not the correct result when a nonempty window is required and every window sum is negative. Validate the window length before indexing, and select a numeric representation that can hold cumulative sums.

Continue in [coding patterns](../70-interview-toolkit/70.2-coding-patterns/INDEX.md), where each mechanism has one maintained explanation. [Reference cards](81.12-quick-reference-cards.md) preserve the invariant; they do not replace the implementation.

## Stage 3: account for the actual work and storage

State the input sizes, cost model and which case you are analyzing. Big O is an asymptotic upper bound; it is not itself a synonym for worst-case analysis, an exact operation count or an elapsed-time prediction.

Check hidden work:

- Enumerating all subsets has `2^n` outputs; copying their elements adds output-size work.
- A recursive tree traversal uses stack depth proportional to height, which can be linear for a chain.
- Expected hash lookup cost is different from a guaranteed worst-case bound.
- An amortized bound accounts for a sequence of operations; it does not make every individual resize constant time.
- A two-dimensional DP table does not determine runtime by itself: count work per state as well.

Include auxiliary storage, recursion and output separately when that distinction matters. For strings, define whether “character” means a code unit, code point or another unit; an ASCII-only frequency array is not a general Unicode contract.

## Stage 4: test the boundary that could invalidate the solution

| Method | Boundary to test |
| -------------------------- | ------------------------------------------------------------------- |
| Window or matrix traversal | Empty input, invalid window length, ragged input if allowed |
| Heap selection | Zero requested results, too many results, equal priorities |
| Tree operation | Empty tree, skewed depth, absent targets, duplicate policy |
| Shortest path | Weight domain, unreachable vertices, overflow and negative cycles |
| Sorting | Empty input, repeated values, numeric domain and required stability |
| Dynamic programming | Smallest state, unreachable result, update order and numeric growth |

Avoid comparator subtraction when it can overflow; use a comparison operation. A repeated call should not accidentally reuse mutable state from a previous input. A sentinel such as `-1` must be distinguishable from valid output or replaced with an explicit result contract.

Study [advanced structures](81.05-advanced-topics.md) only when the required operations justify them.

## Stage 5: add systems and experience preparation

Read [core CS](81.02-core-cs-fundamentals.md) to explain memory, transport and synchronization boundaries. Use [design preparation](81.03-system-design-apis-security.md) to trace one operation through concurrent requests and failure. Add [engineering and career preparation](81.04-devops-behavioral-career.md) for operating changes and explaining real contributions.

Prepare one experience account with the constraint, responsibility, decision, alternative, observed result and limitation. Avoid invented metrics or a copied success script.

## Stage 6: rehearse, repair, and schedule another attempt

Use [the mock bank](81.09-mock-interview-question-bank.md) for timed tasks. Afterward, record one concrete weakness and attempt a changed version after repair. Allocate time using [the weekly calendar](81.21-week-study-schedule.md); adapt recall using [spaced repetition](81.10-spaced-repetition-schedule.md).

Problem counts, study hours and company tags do not guarantee readiness. Readiness evidence is your ability to explain and implement a changed case with less assistance.

## Summary

Confirm the assessment, diagnose a gap, derive a solution, trace its boundaries and rehearse a follow-up. Use the shared chapters for mechanisms and this lane for practice decisions.

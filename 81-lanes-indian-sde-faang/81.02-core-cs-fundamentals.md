# Core CS Fundamentals — Resources, Memory and Network Delivery

[![Role priority](https://img.shields.io/badge/role--priority-Deferred-lightgrey)](../docs/topic-importance.md)
[![General importance](https://img.shields.io/badge/general--importance-Important-blue)](../docs/topic-importance.md)



## Start with the resource being shared

A concurrent program may share memory inside a process, contend for CPU time, wait for a device or send data across a network. These are different boundaries. First identify the resource and the required behavior, then choose the mechanism.

## First Principles

Two executions can interleave while touching the same state, so a multi-step update can fail even when each individual instruction is valid. Processes and threads determine which memory is shared; synchronization must protect the invariant across the whole update. Data crossing a network introduces another boundary: delivery of bytes and completion of an application operation are separate events.

## Processes isolate an address space; threads share one

A **process** is a running program with its own virtual address space and operating-system resources. A **thread** is an execution path within that process. Threads share the process’s memory while keeping their own execution state and stack.

| Boundary | What it gives you | What it still requires |
| ---------------------- | ------------------------------ | -------------------------------------------------------------------------------------- |
| Separate processes | Address-space separation | An explicit communication channel; shared services can still fail together |
| Threads in one process | Direct access to shared memory | Synchronization around conflicting access; a fatal process failure affects its threads |

Creation and switching costs depend on the operating system and workload. “Threads are always cheaper” is not a substitute for measurement.

## CPU scheduling decides who runs next

The scheduler allocates CPU time among runnable work. Waiting for I/O and waiting for CPU are different states; adding threads does not create more CPU capacity.

Consider two CPU-only jobs that arrive together: A needs four time units and B needs one. On one CPU, running A then B finishes them at times four and five. Running B then A finishes them at one and five. The total work is the same, but the average completion time differs.

| Teaching policy | Selection rule | Boundary |
| ------------------------ | ---------------------------------- | ------------------------------------------------------ |
| First come, first served | Arrival order | A long job can delay short ones |
| Shortest job first | Smallest estimated CPU burst | Requires an estimate; long jobs can starve |
| Shortest remaining time | Preempt for smaller remaining work | Requires estimates and switching |
| Round robin | Rotate after a time quantum | Quantum balances switching overhead and responsiveness |
| Priority scheduling | Prefer higher-priority work | Can starve lower priorities without countermeasures |
| Multilevel queues | Separate classes of work | Behavior depends on how classes are scheduled |

For a simple CPU-only model, turnaround is completion minus arrival; response is first run minus arrival; waiting is turnaround minus CPU execution time. With I/O, do not count I/O waiting as time waiting in the runnable queue.

## Locks protect a shared invariant

Suppose two threads both read stock as one and both write zero. The final quantity looks plausible, but two orders consumed one item. Protect the operation that checks and changes the shared state as one critical section.

A **mutex** permits one holder at a time. A **semaphore** manages a count of permits. A **monitor** combines mutual exclusion with a way to wait for a condition. A **barrier** waits for participants to reach a phase boundary; a **latch** waits for a count of events to reach zero.

A monitor protects code using the same monitor; it does not automatically lock every access to an object. Condition waits must recheck the predicate when awakened.

### Release only the lock you actually acquired

```java
boolean acquired = lock.tryLock(1, TimeUnit.SECONDS);
if (!acquired) {
    return; // report timeout or follow an explicit retry policy
}
try {
    updateSharedState();
} finally {
    lock.unlock();
}
```

This is an excerpt: `lock` is a `ReentrantLock`, the caller handles `InterruptedException`, and `updateSharedState` represents the protected operation. If acquisition times out or is interrupted, unlocking a lock the thread does not own raises `IllegalMonitorStateException`. See [ReentrantLock](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/util/concurrent/locks/ReentrantLock.html).

## Deadlock is a cycle of waiting owners

If thread A holds lock one and waits for lock two while thread B holds lock two and waits for lock one, neither can proceed.

The classic necessary conditions are exclusive resources, holding while waiting, no forced resource removal, and circular waiting. A consistent global lock order prevents circular waiting when every participant follows it.

Timed acquisition is useful only if failure releases any held resources and follows a bounded retry policy. Repeated synchronized retries can produce **livelock**: threads keep acting but make no progress. **Starvation** means a participant repeatedly loses access while others progress.

The banker’s algorithm is an avoidance model: grant a resource request only if some completion sequence remains possible. It requires information about maximum demands that general application locks often do not provide.

## Virtual memory translates addresses before accessing RAM

A program uses virtual addresses. Page tables map virtual pages to physical frames or record that the access requires operating-system handling. This permits isolation and mappings such as files, shared memory and demand-allocated pages.

A **page fault** means the access could not complete through the current mapping or permissions. It need not mean a disk read: the OS may allocate a zero-filled page, perform copy-on-write, load data or reject an invalid access.

When memory pressure repeatedly displaces pages needed soon afterward, paging can dominate useful work; this is **thrashing**. Page size and replacement behavior are platform-dependent.

| Replacement model | Idea | Limit |
| ----------------- | ----------------------------------------------- | ------------------------------------------------------------- |
| FIFO | Evict the oldest resident page | More frames can sometimes cause more faults: Belady’s anomaly |
| LRU | Evict the least recently used page | Exact access tracking is expensive |
| Clock | Approximate recency using reference information | An approximation, not exact LRU |
| LFU | Prefer frequently used pages | Old frequencies may outlive the workload |
| Optimal | Evict the page used farthest in the future | A comparison model requiring future knowledge |

CPU caches solve a different problem: they keep nearby copies of memory data close to execution. Cache size, sharing and latency vary by hardware. Direct mapping permits one candidate location, full associativity permits any, and set associativity permits locations within a selected set.

## Inter-process communication needs a channel and a protocol

Pipes, named pipes, local or network sockets, message queues and shared memory can carry data across process boundaries. Signals notify a process of events; they are not a general large-message channel. Shared memory also needs synchronization and an agreed data layout.

A Unix pipe or FIFO is ordinarily a byte stream, not a bidirectional request/response protocol by itself. Use two directions or a suitable socket when the interaction requires replies. Even a local byte stream needs framing to separate application messages.

## Transport delivery is different from application success

**TCP** supplies an ordered byte stream with retransmission and congestion control. A connection can still fail, and TCP does not confirm that the remote application committed your operation. Messages need application framing.

**UDP** supplies datagrams without TCP’s connection state, ordering or retransmission. Applications can build reliability on top of it. Performance depends on the protocol and workload; UDP is not automatically faster. Its checksum rules depend on the IP version.

A TCP connection commonly opens with SYN, SYN-ACK and ACK. Each direction can close independently; do not memorize a fixed three-message termination sequence. See [TCP specification](https://www.rfc-editor.org/rfc/rfc9293.html) and [UDP specification](https://www.rfc-editor.org/rfc/rfc768.html).

### Receiver capacity and network capacity are separate limits

**Flow control** uses the receiver’s advertised window to avoid overrunning it. **Congestion control** adjusts sending to network conditions. Slow start and congestion avoidance are common teaching models; actual algorithms vary.

An application can remain slow even when the transport connection is healthy: it may be waiting for a database lock or processing backlog. Trace the layer holding the work before choosing a fix.

## Use layers to locate the failure

The OSI model names physical, data-link, network, transport, session, presentation and application responsibilities. The Internet stack does not map every protocol neatly to those seven layers; TLS, HTTP authentication and application sessions should not be treated as exact one-layer assignments.

For a failed request, distinguish link or routing failure, connection establishment, TLS negotiation, message parsing, authorization and business-state changes. A retry at one layer may repeat an effect completed at another.

## Summary

Identify what is shared and what can fail. Threads share process memory; locks protect an agreed invariant; virtual memory maps addresses; transport protocols deliver data under their own contracts. None of these alone establishes application correctness.

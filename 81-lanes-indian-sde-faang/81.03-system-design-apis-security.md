# System Design, APIs & Security — Trace an Operation Before Drawing Services

[![Role priority](https://img.shields.io/badge/role--priority-Deferred-lightgrey)](../docs/topic-importance.md)
[![General importance](https://img.shields.io/badge/general--importance-Important-blue)](../docs/topic-importance.md)



## Start with one operation and its constraint

A design discussion becomes concrete when you can describe what the user does and what must remain true. “Book the last available seat without selling it twice” is a clearer starting point than “use microservices and Redis.” Confirm the scope, workload and interview time with the interviewer.

## First Principles

A system cannot enforce a requirement until the relevant state transition and failure boundary are defined. Concurrent requests can observe the same earlier state; remote failures can hide whether an operation completed. A useful design must therefore identify an invariant, its enforcing operation and a way to handle uncertain outcomes before choosing its component layout.

## Follow the request across trust and state boundaries

```text
Client submits an operation
  → API parses and validates its contract
  → authentication establishes identity
  → authorization checks this action on this resource
  → storage enforces the state transition
  → committed state is reported or delivered downstream
```

For each arrow, identify who can fail, what is retried and which state proves completion. A successful network send is not proof of a committed business operation. A timeout may leave the outcome unknown.

## Explain the trade-off under a changed condition

After the basic trace, change one assumption: requests overlap, the database is unavailable, a provider accepts a request before a timeout, or a user’s permissions change. Show which mechanism still maintains the constraint and which response or recovery path changes.

Measure capacity from stated inputs. Do not substitute a memorized architecture, mandatory estimate or security checklist for the actual problem. Include observability for the failure you need to detect and a recovery path appropriate to its effect.

## Summary

Start with a user operation, follow its trust and state boundaries, then justify each mechanism against a concrete failure. Use the shared chapters to repair gaps and the category revision to test the explanation.

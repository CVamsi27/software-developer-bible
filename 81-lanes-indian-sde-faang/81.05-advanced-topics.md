# Advanced Topics — Choose the Structure From the Required Operations

[![Role priority](https://img.shields.io/badge/role--priority-Deferred-lightgrey)](../docs/topic-importance.md)
[![General importance](https://img.shields.io/badge/general--importance-Important-blue)](../docs/topic-importance.md)



## Begin with the operations, not the interview label

An advanced data structure earns its cost when simpler structures cannot meet the required update and query behavior. Confirm the problem’s operations, input bounds and expected complexity before deciding to implement a segment tree, balanced search tree or distributed system.

## First Principles

Precomputing information speeds up reads only if updates keep it valid. Balancing a search tree shortens paths only if structural changes preserve ordering. Resource assignment is correct only if competing claims cannot both succeed. Each choice therefore depends on the invariant and operations it must maintain.

## Range queries: decide whether the data changes

Suppose an array needs repeated range sums. For immutable data, a prefix-sum array answers a range by subtracting two prefixes. Changing an element makes later prefixes stale.

With point updates, a Fenwick tree maintains additive partial sums; a segment tree stores aggregates over array intervals. A segment tree’s combine operation must be associative with an appropriate identity. Min, max and sum need different identities and update rules.

The canonical implementations and traces live in [Segment Tree & Fenwick Tree](../70-interview-toolkit/70.2-coding-patterns/04-heaps-stacks-selection/70.2.4.04-segment-tree.md). Use that chapter rather than another copy here.

| Required operation | Candidate | Boundary to check |
| ---------------------------------------- | ----------------------------------------- | -------------------------------------------------------------------------- |
| Immutable range sum | Prefix sums | Updates invalidate later prefixes |
| Point changes and prefix/range sums | Fenwick tree | Range subtraction needs a suitable invertible aggregate |
| Point changes and other range aggregates | Segment tree | Combine rule and identity must match the operation |
| Many compatible range changes | Lazy segment tree or a specialized method | A point-update implementation does not automatically provide range updates |

Check empty input, index conventions and numeric bounds. In a one-based Fenwick implementation, updating index zero without validation can loop forever because its lowest set bit is zero.

## An AVL tree repairs the shape of an ordered search tree

A **binary search tree** orders keys: smaller keys occur on one side and larger keys on the other, according to its duplicate policy. An unbalanced tree can degenerate into a chain. An **AVL tree** adds a condition at every node: its left and right subtree heights differ by at most one.

A **rotation** changes local parent-child links while preserving key order. It is the repair operation inside the AVL structure, not a separate kind of tree.

### Trace a left-heavy insertion

Insert 30, then 20, then 10. Before repair, all three lie on a left path. A right rotation around 30 promotes 20:

```text
Before                    After right rotation
    30                            20
   /                             /  \
  20                            10  30
 /
10
```

The ordered traversal remains 10, 20, 30. The LL imbalance is repaired by a **right** rotation; RR uses a left rotation. LR first rotates the left child left, then the unbalanced node right; RL uses the mirrored sequence. Update height metadata after rewiring.

The AVL height bound gives logarithmic search, insertion and deletion when the invariant is maintained. Deletion may require repairs while walking back toward the root. See [Cornell: AVL trees](https://www.cs.cornell.edu/courses/cs2112/2021fa/lectures/lecture.html?id=avl).

Choose a library structure when implementing balancing is not the task. “AVL is always faster for reads” and “red-black is always faster for writes” hide workload and implementation costs. Java’s TreeMap and some HashMap collision-bin implementations use red-black structures, but that does not make every HashMap operation an ordered-tree operation.

## Object design: allocate one parking spot without double ownership

The [parking-lot case study](../30-architecture/30.2-system-design/02-case-studies/30.2.2.28-parking-lot.md) owns the design. Before drawing classes, establish the invariant: one active assignment per spot and an explicit lifecycle for entry, occupancy, payment and release.

An in-memory “find a free spot, then set its vehicle” loop can race. A class diagram and two SQL tables do not enforce exclusivity. Trace two entry terminals selecting the same spot and identify the operation that permits only one assignment.

Keep recorded assignment, physical occupancy and payment status distinct. A failed or uncertain payment should follow a defined recovery path rather than blindly freeing an occupied spot. Validate identifiers, time units, missing exits and repeated requests.

Derive the structure from the operations and invariant. Use the canonical range-query and parking-lot chapters for implementation; understand rotations as the local repair that keeps an ordered AVL tree balanced.

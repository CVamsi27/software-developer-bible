# Coding Study Plan — Derive, Implement and Test a Changed Problem

[![Role priority](https://img.shields.io/badge/role--priority-Deferred-lightgrey)](../docs/topic-importance.md)
[![General importance](https://img.shields.io/badge/general--importance-Important-blue)](../docs/topic-importance.md)



## Start with the skill the attempt exposed

This guide chooses a coding practice sequence. The [weekly schedule](81.21-week-study-schedule.md) assigns available time, the [tracker](81.08-progress-tracker.md) records attempts, and [spaced repetition](81.10-spaced-repetition-schedule.md) sets later checks. Keep those jobs in their own files.

Confirm the interview language, environment and allowed tools. Solve one representative task without reviewing its solution first, then identify the gap: understanding the input, choosing an invariant, implementation, testing or complexity analysis.

## First Principles

Remembering a solution to one problem does not establish which property makes it valid. A changed input can remove the property the algorithm relied on. Practice must therefore connect the requirement, invariant and implementation, then test what happens when a condition changes.

## Follow one complete practice cycle

1. Restate the input, output and relevant bounds. Clarify assumptions rather than silently supplying them.
2. Describe a correct simple approach. Identify the work or storage cost that needs improvement.
3. State the proposed invariant or recurrence and why each step preserves it.
4. Implement in the assessment’s language. Check ordinary, empty, boundary and adverse cases relevant to its contract.
5. Analyze time and space, including output size, sorting, recursion and container assumptions.
6. Record any hint, failing case and repair. Later solve a changed example without reopening the earlier answer.

If stuck, use a focused hint and label the assistance. Copying a solution and running it is a different observation from deriving it; both can inform learning when recorded accurately.

Skip ahead when a diagnostic establishes the prerequisite, and return when a later task exposes a missing mechanism. Specialized topics belong in the plan when the role or gap requires them, not because a fixed twelve-week calendar lists them.

## Change the condition that justified the solution

Suppose a minimum-length subarray task supplies only positive numbers. A shrinking-window argument can rely on how removing a leftmost positive value changes the sum. If negative values become legal, that monotonic argument no longer holds. Reusing the same window template without reconsidering the condition can miss the answer.

Similarly, BFS’s edge-count layers do not establish shortest total cost for arbitrary edge weights, and binary search needs more than an array-shaped input. Practice explaining the failed assumption before choosing another algorithm.

Changing only variable names does not test transfer. Change duplicates, signs, input ordering, mutation, weights or the requested output in a way that affects the mechanism.

## Recheck weak steps before adding volume

Use the tracker to decide whether the next task should be a prerequisite repair, another boundary case or a mixed mock. A fixed problem count or time threshold does not establish a hiring bar. Time limits can simulate a confirmed assessment; they should still leave a debrief that identifies what needs work.

Include design and behavioral practice in the calendar when the process assesses them. This coding sequence does not replace those formats or imply that every role uses the same proportions.

## Summary

Practice one mechanism through requirement, invariant, implementation and checks, then change an assumption. Choose later work from the observed gap and the actual assessment rather than a universal daily quota.

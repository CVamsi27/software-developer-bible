# Last-Minute Review — Rehearse Decisions You Can Explain

Use this page after studying. Its purpose is to make familiar decisions easy to retrieve before an interview; learning twenty-eight subjects the night before creates more uncertainty than it resolves.

## Definition

A last-minute review is a short rehearsal of your problem-solving process and the assumptions behind familiar techniques. Open the linked chapter when you cannot explain an item from memory.

## First Principles

Interview time is limited. A technique is useful only when its assumptions fit the problem, and an answer must survive a follow-up. Review those assumptions and your reasoning before memorizing another API name.

## Before the interview: prepare one working path

Confirm the interview format, language, editor, duration, and any permitted references from the invitation. Check the equipment and prepare the questions you need to clarify the task.

Choose one familiar coding problem. Explain its input, a straightforward solution, the improvement, and the condition that makes the improvement valid. Then trace an empty input and an awkward boundary case. Use [the study sequence](81.06-leetcode-study-plan.md) to repair a gap; use [the timed-session guide](81.11-daily-study-timer.md) to keep this rehearsal bounded.

## During a coding task: make each choice defensible

1. Establish the input and required output with a small example.
2. Describe a correct straightforward approach.
3. Name the repeated work or unnecessary storage you can remove.
4. State the invariant that keeps the improved approach correct.
5. Implement, trace boundaries, and account for time and space.

For example, a fixed-length window can replace repeated sums because moving the window removes exactly one value and adds one. A variable-length window for a sum threshold needs additional assumptions; negative numbers can invalidate the rule that shrinking always reduces the sum.

## During a design task: follow one operation through failure

Start with the operation the user needs, such as reserving the last seat. Explain the request, authorization, atomic state change, and response. Then introduce a timeout, a concurrent request, or a duplicate message and show what changes.

Keep these distinctions clear:

- TCP delivers an ordered byte stream; it does not prove a business operation committed.
- A cache can be stale. Identify the source of truth and acceptable staleness.
- A transaction protects a stated database boundary; it does not automatically include a remote service.
- An idempotent operation has the same intended effect when repeated. Responses can differ, and a POST can implement an idempotency-key contract.
- During a network partition, CAP concerns the conflict between its specific consistency and availability guarantees. It is not a permanent “pick two” product label.

Use [the design guide](81.03-system-design-apis-security.md) and [core CS](81.02-core-cs-fundamentals.md) for the underlying explanation.

## During an experience discussion: separate evidence from interpretation

Choose one contribution you actually made. State the constraint, your responsibility, the decision, an alternative, and the observed result. Explain what you did not measure. A truthful qualitative outcome is stronger than an invented percentage.

Review [resume preparation](81.15-resume-negotiation.md) and [behavioral preparation](../70-interview-toolkit/70.1-behavioral/INDEX.md). Company-specific expectations should come from the current invitation and recruiter guidance, rather than a universal round sequence.

## Mistakes that make the rehearsal less useful

Reading a long syntax list can feel familiar without showing that you can solve anything. Replace that passive pass with one trace and one changed assumption. Avoid adding an unfamiliar framework on interview morning or treating problem counts as evidence of readiness.

## Summary

Rehearse a complete explanation, the assumptions behind your choices, and one failure or boundary case. Repair a specific gap in its canonical chapter.

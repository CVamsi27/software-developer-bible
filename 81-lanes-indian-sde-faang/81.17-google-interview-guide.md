# Google Interviews — Derive the Answer and Handle the Follow-Up

[![Role priority](https://img.shields.io/badge/role--priority-Deferred-lightgrey)](../docs/topic-importance.md)
[![General importance](https://img.shields.io/badge/general--importance-Important-blue)](../docs/topic-importance.md)



Use the actual job description and interview instructions to choose your preparation. This guide focuses on reasoning through a changed requirement; it does not predict a universal Google loop or question distribution.

## Definition

A follow-up changes an input assumption, resource limit, failure condition, or required output. Handling it means revisiting the reasoning that justified the original answer.

> **Textbook Definition:** Problem-solving assessment evaluates how a candidate derives, implements and verifies a solution under stated constraints, including their ability to revise assumptions after a follow-up.

## First Principles

A memorized implementation solves one stated contract. When that contract changes, correctness and cost can change too. Preserve the chain from requirement to invariant to implementation so you can identify which step needs revision.

## Confirm what will actually be assessed

Record the confirmed format, duration, language, coding environment, design scope, and permitted tools. Ask the recruiting contact about missing details. Do not assume every role uses Google Docs, has an AI assessment, follows one committee/team-matching order, or evaluates seniority with a fixed product-design question.

Use [the common study sequence](81.06-leetcode-study-plan.md) and [practice log](81.08-progress-tracker.md). Company-tagged problem lists are practice material, not evidence that a question is likely to recur.

## Coding rehearsal: change one assumption

Start with shortest paths in an unweighted graph. BFS is appropriate because each edge contributes the same cost: processing vertices by discovery level finds the fewest edges.

Now change the graph:

```text
A → B costs 10
A → C costs 1
C → B costs 1
```

The one-edge route costs 10; the two-edge route costs 2. Plain BFS minimizes edge count and therefore cannot solve this weighted contract. With nonnegative weights, consider Dijkstra. If negative weights are allowed, revisit that assumption too.

This trace is more useful than rehearsing “graphs are 30% of the interview”. Study the implementation and complexity in [coding patterns](../70-interview-toolkit/70.2-coding-patterns/INDEX.md).

## Design rehearsal: define the scale and consistency need

For autocomplete, establish the data source, matching rule, ranking, freshness, and privacy boundary before choosing a trie or cache. A periodically rebuilt index cannot also promise immediate visibility of every update without another update path.

For a shared cache, state what an access changes. An LRU hit updates recency, so it is not a read-only operation. A concurrent map plus a concurrent deque does not make their combined updates atomic. Protect their shared invariant or choose an explicitly different concurrency contract.

Use [design preparation](81.03-system-design-apis-security.md) for operation traces. Derive throughput and storage from stated demand; the word “Google” does not establish millions of requests per second for the hypothetical system.

## When referencing Spanner, name the transaction contract

Spanner’s default or serializable transactions provide external consistency: transactions appear serially ordered, and a completed transaction precedes a later transaction that starts to commit. TrueTime exposes clock uncertainty and participates in timestamp ordering; it does not eliminate clock uncertainty or replace replication consensus.

Current documentation also describes repeatable-read isolation. Do not assign the default isolation guarantee to every possible transaction configuration. A stale snapshot read is a deliberate timestamped view, not simply an uncontrolled eventually consistent read.

Read the official contract before using the product as evidence for a design. Understanding one guarantee is more useful than calling a whole service “CP” without describing what occurs during a partition.

## Experience rehearsal: explain a changed decision

Choose a real instance where feedback or new evidence changed your approach. State the original reasoning, the new information, your action, and the observed result. Keep unmeasured outcomes explicit. Do not substitute a generic speech about scale, innovation, or a presumed “20% time” entitlement for an actual reason the role interests you.

See [behavioral preparation](../70-interview-toolkit/70.1-behavioral/INDEX.md) for organizing supported experience and [resume preparation](81.15-resume-negotiation.md) for checking each claim.

## Summary

Confirm the assessment and practice changing one assumption at a time. Explain exactly why the original method works and where it stops working.

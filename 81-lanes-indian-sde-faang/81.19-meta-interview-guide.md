# Meta Interviews — Trace the User Workflow Before Scaling It

[![Role priority](https://img.shields.io/badge/role--priority-Deferred-lightgrey)](../docs/topic-importance.md)
[![General importance](https://img.shields.io/badge/general--importance-Important-blue)](../docs/topic-importance.md)



Confirm the actual interview format and role scope from the recruiting team. This guide offers a product-workflow rehearsal; it does not claim a current company-wide coding quota, assessment platform, or hiring sequence.

## Definition

A product architecture discussion connects a user action to client behavior, API contracts, stored state and failure recovery. An infrastructure discussion can focus more deeply on service boundaries, throughput and reliability. Confirm the intended scope rather than inferring it from a company name.

## First Principles

A product succeeds only if its user-visible behavior remains coherent across requests, state changes and failures. Start with that behavior so each cache, queue or service has an explicit job and a testable boundary.

## Trace a hypothetical feed request

Define the product contract first: eligible posts, ordering, freshness, pagination, authorization and deletion behavior.

```text
open feed → identify viewer → retrieve eligible candidates
→ rank candidates → return a page and continuation information
→ render → request another page
```

Each step creates a design decision. Authorization must exclude posts the viewer cannot access. Pagination must specify behavior when ranking or eligibility changes. A cached candidate list can become stale after an author deletes a post or changes its audience; decide how current access checks and invalidation protect the contract.

This is a practice design, not a description of Meta’s current production architecture.

## Choose fan-out from measured work

| Approach | Work shifted to | Boundary to explain |
| ---------------- | -------------------------------------------------- | ------------------------------------------------------------------------------------- |
| Fan-out on write | Publishing prepares entries for recipient feeds | Large audiences amplify writes; propagation, deletion and stale entries need handling |
| Fan-out on read | Viewing retrieves and combines relevant sources | Reads can be expensive; caching and ranking inputs can still be stale |
| Hybrid | Different sources or workloads use different paths | Merge results, deduplicate and preserve the stated ordering and access contract |

A pull design is not automatically “always fresh”, and a hybrid design is not evidence that a named company uses a particular celebrity threshold. Derive the choice from audience distribution, posting rates, reads and freshness requirements.

Follow [system design](../30-architecture/30.2-system-design/INDEX.md) for full implementation choices. Meta’s published 2021 ranking article is a dated example of candidate evaluation and ranking, not an up-to-date blueprint for every feed surface.

## Add a mobile failure to the design

An interrupted upload should have an explicit retry contract, server-confirmed state and a way to avoid presenting an uncommitted item as complete. A disconnected client can show cached data, but should distinguish it from a successful refresh when that distinction affects the user.

For reactions, define whether repeating the operation sets a state or increments a count. A stable “set my reaction to like” contract is easier to retry than an unconditional increment. Aggregated display counts can have a different freshness requirement from an individual user’s stored reaction.

These decisions make the architecture concrete before scale estimates or technology names are introduced.

## Prepare a real product trade-off

Choose an experience in which a user need conflicted with cost, latency, reliability or delivery time. Explain the evidence, alternatives, decision and observed outcome. Avoid invented impact metrics or assigning an old corporate-values table to a current hidden interview rubric.

See [behavioral preparation](../70-interview-toolkit/70.1-behavioral/INDEX.md) for the common method. Company interest should connect the actual role to work you can discuss accurately.

## Summary

Confirm the assessment, trace a user operation, and identify its authorization, freshness and retry boundaries. Choose scaling mechanisms from stated demand and distinguish your hypothetical design from dated published systems.

# Apple Interviews — Prepare for the Domain and Resource Boundary

[![Role priority](https://img.shields.io/badge/role--priority-Deferred-lightgrey)](../docs/topic-importance.md)
[![General importance](https://img.shields.io/badge/general--importance-Important-blue)](../docs/topic-importance.md)



Read the actual role description before selecting a language or practice topic. A mobile framework role, a cloud role and a systems role need different evidence. Confirm the assessment format and permitted tools with the recruiting contact.

## Definition

Domain preparation connects the role’s operations and constraints to concrete examples: ownership, state transitions, concurrency, latency, memory or device resources.

> **Textbook Definition:** Domain-specific preparation selects mechanisms and trade-offs relevant to the role's operating environment, including its resource limits, reliability requirements and hardware or software boundaries.

## First Principles

Resources are finite and operations can overlap. A design must identify who owns state, which transitions are atomic, and what remains valid after suspension or failure. Those constraints determine the implementation more reliably than a company-wide topic-frequency table.

## Select the relevant boundary

| Role evidence | Practice example | Decision to explain |
| ----------------------- | ----------------------------------------- | --------------------------------------------------------- |
| Device application work | Interrupt a download and retry | Persisted state, cancellation and user-visible completion |
| Framework or API work | Two clients modify shared state | Ownership, mutation contract and compatibility |
| Systems work | Process a large input with bounded memory | Allocation, lifetime, throughput and failure cleanup |
| Cloud work | Resume a request after a timeout | Durable outcome, retry identity and reconciliation |

These are role-derived practice choices. They are not assertions about Apple’s internal scoring or a universal interview loop. Use [coding practice](81.06-leetcode-study-plan.md) and [design preparation](81.03-system-design-apis-security.md) for the shared method.

## Explain Swift ownership without hiding lifetime assumptions

**Automatic Reference Counting (ARC)** tracks strong references to class instances. Strong-reference cycles can keep instances alive. A weak reference does not retain its target and becomes nil after deallocation; use it when the target may disappear. An unowned reference assumes its target remains alive during access; ordinary unowned access after deallocation traps. Choose the reference from the lifetime relationship, rather than treating weak and unowned as interchangeable fixes.

Structs have value semantics and classes have reference identity. Value semantics do not promise a physical deep copy at every assignment; implementations can share storage while preserving the required behavior.

## Explain what actor isolation protects

An actor isolates mutable state. Keep a state check and its mutation together when their correctness depends on each other:

```swift
actor Inventory {
    private var remaining: Int

    init(remaining: Int) {
        precondition(remaining >= 0)
        self.remaining = remaining
    }

    func reserveOne() -> Bool {
        guard remaining > 0 else { return false }
        remaining -= 1
        return true
    }
}

@main
struct ReservationDemo {
    static func main() async {
        let inventory = Inventory(remaining: 1)
        let successes = await withTaskGroup(of: Bool.self, returning: Int.self) { group in
            for _ in 0..<2 {
                group.addTask { await inventory.reserveOne() }
            }
            var count = 0
            for await reserved in group {
                if reserved { count += 1 }
            }
            return count
        }
        print(successes) // 1
    }
}
```

Save this complete example as `inventory.swift`. Compile with `swiftc -parse-as-library inventory.swift -o inventory`, then run `./inventory`. The task group starts two reservations and waits for both results; it does not guarantee which caller runs first.

With one item, two calls can produce one success and one failure. There is no suspension between the stock check and decrement.

An actor method containing `await` can suspend and allow other work to change its state. Recheck assumptions after suspension or use an explicit state machine. Isolation prevents conflicting state access; it does not make a whole workflow spanning remote calls atomic. Cancellation is cooperative, so code must observe it and clean up appropriately.

## Compare local and remote processing for this operation

Local processing can reduce network transfers and support offline work, but it still consumes compute, memory, energy and storage. Remote processing also has finite capacity, operational cost and a data-access boundary. Neither is universally faster or inherently private.

For an image-search feature, specify what leaves the device, which results are stored locally, how updates arrive, and what happens offline. Local computation can coexist with cross-device synchronization. Evaluate the actual operation rather than copying “on-device means no sync” or “cloud means unlimited compute”.

## Prepare one measured improvement

Choose a real case where profiling, failure analysis or user feedback changed a decision. State the initial behavior, measurement method, action and observed outcome. Separate your contribution from team work and make unmeasured effects explicit.

Use [behavioral preparation](../70-interview-toolkit/70.1-behavioral/INDEX.md) for the account and [resume preparation](81.15-resume-negotiation.md) to verify its claims. Avoid inventing a fixed memory or latency saving to make the story sound stronger.

## Summary

Match practice to the confirmed role. Explain state ownership, lifetime and suspension boundaries, then connect resource choices to the operation and evidence.

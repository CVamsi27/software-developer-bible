## 1. What Is Docita

**Docita** is a production healthcare SaaS platform — a "Clinic OS" that takes small-to-mid clinics from paper/Excel to cloud. It handles scheduling, patient records, prescriptions, billing, inventory, WhatsApp communication, and insurance claims for **25+ active clinics** and **1,000+ appointment workflows per month**.

**Positioning:** WhatsApp-first clinic OS. A small clinic owner in India should be able to run their clinic without opening a browser — WhatsApp is the primary interface, the web app is power-user mode.

**Why this matters for interviews:** Healthcare SaaS is one of the hardest domains — PHI compliance, multi-tenancy, real-time workflows, payment separation, and regulatory requirements. Every architectural decision has compliance implications.

## 2. The Hard Problems

### Problem 1: Multi-Tenant Data Isolation in Healthcare

**Challenge:** 25+ clinics share one database. A single missed `WHERE clinicId = ?` leaks patient data across clinics. In healthcare, this isn't just a bug — it's a compliance violation (DPDP, HIPAA-equivalent).

**What we tried first:** Application-level filtering via Prisma middleware. Every repository had to manually add `clinicId` to queries.

**What went wrong:** A developer added a new repository method and forgot the clinic filter. Code review caught it, but it revealed the fragility. We needed a database-level guarantee.

**Solution:** 7-layer defense-in-depth:

```text
Layer 7: Audit logging — every PHI access logged
Layer 6: RLS — PostgreSQL row-level security (database-level)
Layer 5: Repository tenant scoping — Prisma middleware
Layer 4: PolicyGuard (ABAC) — object-level conditions
Layer 3: Subscription/tier guard — feature gating
Layer 2: RBAC roles matrix — role → permission
Layer 1: TenantGuard — AsyncLocalStorage tenant context
Layer 0: JWT auth — token validation + session management
```

**Key insight:** RLS was the hardest to implement. The challenge: Prisma's connection pool means each query might run on a different connection. We had to route ALL queries through a single interactive transaction per request, using a custom Prisma extension (`rls-routing`). Without this, the `SET LOCAL app.current_clinic_id` would be set on one connection but the query would run on another — silently bypassing RLS.

**Code:** `apps/api/src/shared/common/middleware/tenant.middleware.ts`, `apps/api/src/shared/common/interceptors/tenant-context.interceptor.ts`, `apps/api/src/shared/modules/rls/apply-rls-scope.ts`

### Problem 2: Reliable Async Processing Without Redis

**Challenge:** The platform needs to send WhatsApp messages, generate PDFs, process payments, and run analytics — all asynchronously. Traditional approach: Redis + BullMQ.

**Why we rejected Redis:** Adding Redis means another managed service (AWS ElastiCache), another failure mode, another secret to rotate, and no transactional enqueue with business writes. At our scale (~0.4 jobs/sec), Postgres is sufficient.

**Solution:** PostgreSQL-backed queue using `SELECT ... FOR UPDATE SKIP LOCKED`. A `QueueJob` table stores pending jobs. The API writes jobs in the same `prisma.$transaction` as business data — atomic, no dual-write problem. A worker process polls and executes.

**What went wrong initially:** Early versions used in-process `EventEmitter2` for domain events. This worked for single-pod but would silently drop cross-pod listeners. We migrated to a transactional outbox pattern (ADR 0010).

**Key insight:** The outbox pattern solved the "emission happens but listener fails" problem. Events are written to an `OutboxEvent` table in the same transaction as the business write. A relay scheduler polls and republishes. Consumers are idempotent — they check a deduplication cache before processing.

**Code:** `apps/api/src/shared/modules/outbox/outbox.service.ts`, `apps/api/src/shared/modules/outbox/outbox-relay.scheduler.ts`, `apps/api/src/shared/modules/queue/postgres-queue.service.ts`

### Problem 3: Payment Flow Separation

**Challenge:** Three distinct payment flows that must never mix:

| Flow | Purpose | Merchant Key | Who Gets Paid |
|------|---------|-------------|---------------|
| **Flow A** | Clinic's own Razorpay credentials | Clinic's | Clinic |
| **Flow B** | Patient pays clinic | Flow A credentials | Clinic |
| **Docita SaaS** | Clinic pays Docita for subscription | Docita's | Docita |

**Why this is hard:** If a developer accidentally uses Docita's Razorpay merchant key for a patient payment, Docita receives the patient's money instead of the clinic. This is a financial compliance issue.

**Solution:** Three separate injection sites in the NestJS config, documented in `docs/product/PAYMENT_FLOWS.md`. Code reviews block PRs that cross flow boundaries. The naming convention makes it explicit: `CLINIC_INVOICE_PAYMENT_LINK_PROVIDER_TOKEN` (Flow B) vs `DOCITA_PLATFORM_PAYMENT_LINK_PROVIDER_TOKEN` (Docita SaaS).

**Key insight:** Technical debt exists — Flow B still delegates to a shared adapter instead of resolving a clinic-scoped provider from Flow A settings. This is documented and gated by code review.

### Problem 4: PHI Encryption at the Field Level

**Challenge:** DPDP (India's data protection law) and clinic compliance require encryption beyond disk-level. A stolen database snapshot must be unreadable without the key.

**Solution:** Envelope encryption — each row carries a per-row Data Encryption Key (DEK) wrapped by a Key Encryption Key (KEK). The Prisma extension transparently encrypts before persist and decrypts on read.

**Encrypted fields:** firstName, lastName, email, phoneNumber, address, emergencyContactPhone, emergencyContactName.

**Why not encrypt everything:** MRN, bloodGroup, allergies, medicalHistory need to be searchable/displayable. They're protected by RLS + audit logging instead.

**What went wrong:** Initially, the encrypt and decrypt field lists drifted apart — a new field was added to encrypt but not to decrypt. A CI check (`check:phi-encryption-coverage`) now enforces alignment.

### Problem 5: Real-Time Clinic Operations

**Challenge:** Clinic staff need real-time updates — new appointments, payment confirmations, WhatsApp delivery status. Traditional REST polling is too slow and wastes bandwidth.

**Solution:** WebSocket gateways for real-time notifications. The payment gateway notifies the front desk instantly when a patient pays. The appointment system updates the calendar in real-time.

**What went wrong:** WebSocket connections are stateful — they don't survive server restarts gracefully. We implemented connection heartbeat and reconnection logic on the client.

### Why DDD (Domain-Driven Design)?

**Challenge:** 28 business domains (patients, appointments, billing, prescriptions, etc.) were growing organically. Services were importing from each other, creating coupling.

**Decision:** Each domain has 4 layers:

```text
domain/
├── core/           → entities, value objects, repository interfaces (no framework deps)
├── application/    → use-cases, DTOs, service orchestration
├── infrastructure/ → Prisma repositories, external API adapters
└── presentation/   → NestJS controllers, guards, interceptors
```

**Key rule:** Only repositories import PrismaClient. Enforced by CI check (`check:prisma-boundary`). This means business logic is testable without a database.

**Trade-off:** More boilerplate per domain. But the testability and maintainability payoff is worth it at 28 domains.

### Why Zod-First Types?

**Challenge:** TypeScript interfaces, Prisma models, and NestJS DTOs were diverging. A field added to Prisma wasn't reflected in the API contract.

**Decision:** Zod schemas in `packages/types` are the single source of truth. All other types are inferred via `z.infer`.

**Flow:** `Zod Schema → infer TS types → API contracts → UI forms → DB-safe DTOs`

**Trade-off:** Slightly more verbose schema definitions. But eliminates type drift entirely. The CI check ensures no schema is orphaned.

## 4. 14 Architecture Decisions (ADRs)

### ADR 0001: PostgreSQL as Queue (not Redis/BullMQ)

**Context:** Need a durable job queue for emails, WhatsApp, PDF generation.

**Alternatives considered:**

| Option | Pros | Cons |
|--------|------|------|
| **Redis + BullMQ** | Sub-ms latency, mature ecosystem | Extra service cost, no transactional enqueue, extra failure mode |
| **AWS SQS** | Managed, reliable | Vendor lock-in, no transactional enqueue, cross-region complexity |
| **PostgreSQL** | Already paying for RDS HA, transactional enqueue, one less service | Throughput ceiling ~1k jobs/sec |

**Decision:** Postgres-backed queue using `SELECT ... FOR UPDATE SKIP LOCKED`.

**Key code pattern:**

```typescript
// apps/api/src/shared/modules/queue/postgres-queue.service.ts
async enqueue<T>(name: string, data: T, options?: QueueJobOptions): Promise<QueueJob<T>> {
  // Idempotency check — skip if recent completed job exists
  if (options?.idempotencyKey) {
    const recent = await this.findRecentCompletedByIdempotency(name, options.idempotencyKey);
    if (recent) return this.rowToJob(recent);
  }
  // RLS-BYPASS: background queue workers run without per-request clinic session
  const row = await this.prisma.runUnrestricted(async () =>
    this.prisma.queueJob.create({ data: { name, data, status: 'WAITING', ... } })
  );
  return this.rowToJob(row);
}
```

**Trade-off:** Not suitable for >1k jobs/sec. At our scale (~0.4 jobs/sec), fine.

**What would trigger revisiting:** If we add >100 clinics or real-time event streaming requirements.

### ADR 0005: Envelope Encryption for PHI

**Context:** DPDP compliance requires field-level encryption. Stolen DB snapshot must be unreadable.

**Alternatives considered:**

| Option | Pros | Cons |
|--------|------|------|
| **Full-disk encryption** | Zero code change | Doesn't protect against SQL injection or authorized-user exfiltration |
| **Application-level encrypt/decrypt** | Flexible | Easy to forget fields, drift between encrypt/decrypt |
| **Prisma extension** | Transparent, enforces at ORM level | Requires careful field list management |

**Decision:** Each row has a DEK wrapped by a KEK. Prisma extension transparently encrypts/decrypts.

**Why not full-disk encryption only:** Doesn't protect against SQL injection or authorized-user data exfiltration.

**Trade-off:** Cannot search encrypted fields. MRI, allergies, etc. stay plaintext (protected by RLS + audit).

### ADR 0006: Single-Region Postgres

**Context:** DPDP encourages Indian-region hosting. Multi-region active-active has significant complexity.

**Decision:** One primary in ap-south-1 (Mumbai) with managed PITR + daily snapshots.

**Why not multi-region:** Conflict resolution, replication lag, RLS interactions are premature at 25 clinics.

**What would trigger multi-region:** >200 clinics or explicit data residency requirements outside India.

### ADR 0008: AsyncLocalStorage for Tenant Context

**Context:** Every Prisma call needs `tenantId`. Threading it through every function is verbose and error-prone.

**Decision:** Use Node.js AsyncLocalStorage to carry request-scoped context.

**Why:** One missed parameter = data leak. ALS makes it implicit and impossible to forget.

**Code:**

```typescript
// apps/api/src/shared/common/middleware/tenant.middleware.ts
import { AsyncLocalStorage } from 'async_hooks';

interface TenantContext {
  clinicId?: string;
  userId?: string;
  bypassed?: boolean;
  preTenant?: boolean;
}

export const tenantStorage = new AsyncLocalStorage<TenantContext>();

export function getCurrentTenant(): TenantContext | undefined {
  return tenantStorage.getStore();
}
```

**Trade-off:** `setTimeout` loses context. Mitigated by `check-detached-promises.mjs` CI check.

### ADR 0010: Transactional Outbox

**Context:** Domain events emitted via in-process `EventEmitter2`. Single pod = fine. But listener failures aren't retried, and splitting across pods drops events.

**Alternatives considered:**

| Option | Pros | Cons |
|--------|------|------|
| **In-process EventEmitter2** | Simple, zero latency | No persistence, no cross-pod, no retry |
| **Kafka/NATS** | Durable, high throughput | Extra infrastructure, premature at 25 clinics |
| **Transactional outbox** | Durable, transactional, zero new infra | Relay lag (seconds), polling overhead |

**Decision:** Write events to `OutboxEvent` table in same transaction. Relay scheduler polls and republishes.

**Key code pattern:**

```typescript
// apps/api/src/shared/modules/outbox/outbox.service.ts
async append(tx: Prisma.TransactionClient, event: OutboxAppend): Promise<void> {
  try {
    await tx.outboxEvent.create({
      data: {
        eventName: event.eventName,
        clinicId: event.clinicId,
        payload: toPrismaInputJsonValue(event.payload),
        idempotencyKey: event.idempotencyKey ?? null,
      },
    });
  } catch (error) {
    // P2002 on idempotencyKey means duplicate — treat as no-op
    const code = isRecord(error) ? error.code : undefined;
    if (event.idempotencyKey && code === 'P2002') return;
    throw error;
  }
}
```

**Relay scheduler:** Uses `FOR UPDATE SKIP LOCKED` for concurrent-safe batch processing, advisory locks to prevent cross-replica duplication, and exponential backoff for failed events.

**Trade-off:** Relay lag (seconds). Acceptable for our scale.

### ADR 0011: Fly.io Auto-Suspend Fix

**Context:** Fly.io auto-stop shut down the VM after idle. Next request triggered a 3-minute cold start. Fly's HTTP proxy only waits ~10-15s → 502 Bad Gateway on every cold start.

**Decision:** Keep one machine running (`min_machines_running = 1`), suspend scale-out capacity.

**Lesson learned:** Don't trust platform defaults for health check timeouts. Measure actual bootstrap time.

### ADR 0012: Replace Next.js with Vite SPA

**Context:** Next.js 16 + OpenNext bundle was ~3.5 MB gzip, over Cloudflare's 3 MB Free limit. Both apps are login-gated — no SEO need.

**Alternatives considered:**

| Option | Pros | Cons |
|--------|------|------|
| **Next.js SSR** | SEO, streaming, RSC | 3.5MB bundle, over Cloudflare limit, unnecessary for auth-gated dashboards |
| **Vite SPA + Cloudflare** | Tiny bundle, fast dev, zero server cost | No SSR, no SEO |
| **Remix** | Nested routes, progressive enhancement | Extra migration effort, less ecosystem |

**Decision:** Vite + React Router v7 SPAs on Cloudflare Static Assets. Tiny Hono proxy for `/api/*`.

**Why not Next.js SSR:** No SEO value for authenticated dashboards. Simpler deployment, faster dev.

**Trade-off:** Lost SSR benefits. Acceptable for SaaS dashboard.

### ADR 0013: ABAC-on-RBAC

**Context:** RBAC roles couldn't express "doctor can view only their assigned patients." Adding more roles = role explosion.

**Decision:** Keep RBAC guard chain, add `PolicyGuard` for object-level conditions.

**Why not pure ABAC:** Too complex for our scale. RBAC handles 90%; ABAC adds the missing 10%.

**Implementation:** Typed TypeScript classes in `packages/authorization`. Deny-overrides: any deny wins. Default deny.

**Code:** `packages/authorization/src/evaluator.ts`, `packages/authorization/src/policies/`

### ADR 0014: Cloudflare Origin Protection

**Context:** Fly.io origin is publicly reachable. Anyone who discovers the Fly IP can bypass Cloudflare's WAF, rate limiting, and bot protection.

**Decision:** Fly.io network policies don't support ingress filtering for `http_service` traffic. Mitigated at application layer: verify `CF-Connecting-IP` header, rate limit by application-level IP detection.

**Lesson:** Don't assume your CDN/proxy hides your origin. Always protect the origin directly.

### Appointment Workflow — Step by Step

**1. Create Appointment** (`CreateAppointmentUseCase`)

The appointment entity is a rich domain model with 30+ fields covering every clinical need:

```typescript
// apps/api/src/domains/appointments/core/entities/appointment.entity.ts
export interface AppointmentProps {
  id: string;
  clinicId: string;
  patientId: string;
  doctorId: string;
  startTime: Date;
  endTime: Date;
  status: AppointmentStatus;
  // Clinical fields (specialty-aware)
  chiefComplaint?: string;
  historyOfPresentIllness?: string;
  pastMedicalHistory?: string;
  reviewOfSystems?: string;
  provisionalDiagnosis?: string;
  finalDiagnosis?: string;
  treatmentPlan?: string;
  // Specialty-specific exam fields
  generalExamination?: unknown;
  systemicExamination?: unknown;
  dentalChart?: DentalChartData;
  ophthalmologyExam?: unknown;
  cardiologyExam?: unknown;
  gynecologyExam?: unknown;
  dermatologyExam?: unknown;
  psychiatryExam?: unknown;
  // Payment
  advance?: AppointmentAdvance;
  // Optimistic concurrency
  version: number;
}
```

**Why the entity is so large:** Each specialty (dental, cardiology, ophthalmology, etc.) needs different exam fields. Rather than separate entities per specialty, we use optional JSON fields. This keeps the schema unified while allowing specialty-specific UIs.

**Decision: Overlap detection** — The `AppointmentSchedulingRulesService` validates:
- Start time < end time
- No overlapping appointments for the same doctor (using interval arithmetic)
- Doctor time-off conflicts
- Minimum 15-minute, maximum 480-minute duration
- 5-minute buffer between appointments
- Business hours (9 AM – 6 PM local time)

**What happened:** Early versions used naive `startTime >= existing.endTime` checks. A timezone bug caused double-bookings when doctors跨越 UTC midnight. Fix: all scheduling uses clinic-local time converted to UTC bounds.

### Queue Management — Walk-in Patients

**Challenge:** Indian clinics have walk-in patients. Need a physical queue display (token numbers) + real-time updates.

**Solution:** `QueueCommandService` manages check-in → call → complete lifecycle:

```typescript
// apps/api/src/domains/appointments/application/services/queue.service.ts
checkIn(clinicId, appointmentId)   // Patient arrives
callPatient(clinicId, queueId)     // Doctor calls next patient
completePatient(clinicId, queueId) // Consultation done
resetQueue(clinicId)               // End of day
```

**Key design decision:** Queue tokens are generated from appointment IDs (not sequential numbers). This avoids race conditions when two front-desk staff check in patients simultaneously. The token is a hash prefix — unique, short, and deterministic.

### WhatsApp Response Handling — The Complex Part

**Challenge:** Patients reply to WhatsApp appointment reminders with "yes", "no", "delay 30 min", or custom text. The system must parse these, update appointment status, detect conflicts, and send confirmations.

**Solution:** `ResponseHandlerService` orchestrates the full flow:

```typescript
// apps/api/src/domains/whatsapp/application/services/response-handler.service.ts
async handlePatientResponseForAppointment(context, responseText, phoneNumber, messageSid) {
  // 1. Parse response type (YES/NO/DELAY/UNKNOWN)
  const responseType = parsePatientResponse(responseText);
  const delayMinutes = extractDelayMinutes(responseText);
  
  // 2. Handle delay follow-up (two-step: "delay" → "30 minutes")
  if (pendingDelayResponse && delayMinutes !== null) {
    await this.handleDelayMinutesFollowUp(context, pendingDelayResponse.id, responseText, delayMinutes);
    return;
  }
  
  // 3. Persist response
  await this.persistence.appointmentResponse.create({ data: { appointmentId, responseType, ... } });
  
  // 4. Update appointment status (YES → confirmed, NO → cancelled)
  await this.updateAppointmentStatus(context, responseType);
  
  // 5. Detect delay conflicts (does 30-min delay overlap with next appointment?)
  if (responseType === 'DELAY' && delayMinutes !== null) {
    const conflict = await this.evaluateDelayConflict(...);
    // conflict.conflictDetected → notify staff
  }
  
  // 6. Send confirmation + staff notification
  await this.patientConfirmation.sendPatientConfirmation(context, responseType, delayContext, ...);
  await this.patientStaffNotification.notifyStaff(context, responseType, delayContext, ...);
}
```

**What was hard:** The two-step delay flow. Patient says "delay" → system asks "how many minutes?" → patient says "30" → system must associate the "30" with the pending delay request. We used a `pendingDelayResponse` lookup with a 6-hour follow-up window.

**Failure mode:** A patient replied "30" without a pending delay request. The system treated it as unknown. Fix: we now log a warning and send a clarifying message.

### Prescription Creation — Clinical Safety

**Challenge:** Prescriptions must not violate drug allergies, controlled substance regulations, or dosage limits.

**Solution:** `PrescriptionsCommandService` enforces multiple safety checks:

```typescript
// apps/api/src/domains/prescriptions/application/services/prescriptions-command.service.ts
async create(data: CreatePrescriptionCommand) {
  // 1. Doctor compliance check — must have digital signature + verified registration
  const doctorProfile = await this.repository.findDoctorCompliance(data.doctorId, data.clinicId);
  if (!doctorProfile.signatureUrl) throw new BadRequestException('DOCTOR_SIGNATURE_REQUIRED');
  if (doctorProfile.verificationStatus !== 'VERIFIED') throw new BadRequestException('DOCTOR_VERIFICATION_REQUIRED');
  
  // 2. Patient allergy check — critical allergies block prescription
  const allergyCheck = checkPrescriptionAllergies(data.medications, patientAllergies);
  if (allergyCheck.criticalWarnings.length > 0) throw new BadRequestException('Cannot prescribe due to critical allergies');
  
  // 3. Controlled substance validation
  for (const med of data.medications) {
    validateControlledSubstances(med.name, med.dosage);
    validateDosage(med.name, med.dosage);
  }
  
  // 4. Create prescription + emit event for PDF generation
  const prescription = await this.repository.create(data);
  this.eventEmitter.emit(ApplicationEvents.PRESCRIPTION_CREATED, new PrescriptionCreatedEvent(...));
}
```

**Why doctor verification is required:** Indian law requires prescriptions to carry a verified doctor registration number. An unverified doctor cannot issue prescriptions — the system blocks it at the application level.

### Invoice Generation — Tax & Payment Complexity

**Challenge:** Indian healthcare invoicing involves GST (Goods and Services Tax), place-of-supply rules, and multiple payment methods.

**Solution:** `InvoicesCommandService` builds tax snapshots from clinic and patient context:

```typescript
// apps/api/src/domains/billing/application/services/invoices-command.service.ts
private buildTaxSnapshots(patient: PatientInvoiceContext) {
  const taxSettings = parseTaxSettings(patient.clinic.settings);
  const gstin = taxSettings.registrationId || extractClinicGstin(patient.clinic);
  const stateCode = taxSettings.stateCode || extractGstinStateCode(gstin);
  
  const seller = taxRegistrationSnapshotSchema.parse({
    countryCode: taxSettings.countryCode,
    regime: taxSettings.regime,
    registrationId: gstin,
    legalName: taxSettings.legalName || patient.clinic.name,
    stateCode,
    stateName: taxSettings.stateName,
  });
  
  const buyer = taxRegistrationSnapshotSchema.parse({
    countryCode: seller.countryCode,
    regime: seller.regime,
    legalName: getPatientFullName(patient).trim(),
    address: patient.address || undefined,
  });
  
  return { taxSettings, seller, buyer };
}
```

**Key design decision:** Tax snapshots are immutable — once an invoice is created, the tax calculation is frozen. If clinic tax settings change, existing invoices retain their original calculation. This is critical for audit trails.

### Razorpay Webhook Processing — Idempotency

**Challenge:** Razorpay can send the same webhook multiple times (at-least-once delivery). Processing a payment twice = double-crediting the clinic.

**Solution:** `RazorpayInvoiceWebhookService` checks for existing payment sessions before processing:

```typescript
// apps/api/src/domains/billing/application/services/razorpay-invoice-webhook.service.ts
private async handlePaymentCaptured(payload) {
  const payment = payload.payload.payment?.entity;
  
  // Idempotency: skip if we already processed this payment
  const existing = await this.repository.findByProviderPaymentId('razorpay', payment.id);
  if (existing) return;
  
  // Find the session this payment belongs to
  const session = await this.repository.findByProviderSessionId(payment.order_id);
  if (!session || !session.invoiceId || !session.patientId) throw new BadRequestException('...');
  
  // Process in a transaction: update session + transition invoice + append outbox event
  await this.transactionRunner.run(async (tx) => {
    await this.repository.updatePaymentSession(session.id, { providerPaymentId: payment.id, ... }, tx);
    await this.invoiceRepository.transitionStatus(session.invoiceId, InvoiceStatus.PAID, tx);
    await this.outbox.append(tx, { eventName: ApplicationEvents.PAYMENT_CAPTURED, ... });
  });
}
```

**Why the outbox is used here:** The payment webhook triggers downstream events (update patient wallet, send receipt WhatsApp, update dashboard). These events must be delivered even if the API crashes after committing the payment. The outbox ensures exactly-once delivery with idempotent consumers.

## 6. Domain Deep Dives — Every Domain Explained

### patients (25+ files)

**What it does:** Patient registration, medical history, tags, timeline, metrics, ABHA verification.

**Key challenge:** PHI encryption + timeline aggregation. The patient timeline aggregates events from appointments, prescriptions, invoices, and lab results into a single chronological view.

**Code pattern:** `PatientTimelineAggregator` queries multiple sources, merges by timestamp, and returns a unified view. This avoids N+1 queries — the aggregator fetches all sources in parallel using `Promise.allSettled`.

### appointments (50+ files)

**What it does:** Scheduling, queue management, follow-ups, OPD slips, consultation workflow.

**Key challenge:** Real-time updates + scheduling conflict detection. The `AppointmentSchedulingRulesService` uses interval arithmetic to detect overlaps, accounting for timezone conversion.

**Design decision:** Separate read/write repositories (`IAppointmentReadRepository` / `IAppointmentWriteRepository`). Read side optimized for list views with cursor pagination. Write side uses optimistic concurrency (`version` field) to prevent lost updates.

### prescriptions (15+ files)

**What it does:** Prescription creation, allergy checking, controlled substance validation, PDF generation, template management.

**Key challenge:** Clinical safety. Every prescription must pass allergy checks, dosage validation, and controlled substance verification before persistence.

**Design decision:** PDF generation is async (queued via Postgres queue). The doctor creates the prescription → event emitted → worker generates PDF → stored in Cloudflare R2 → URL returned to frontend via WebSocket.

### billing (60+ files)

**What it does:** Invoice generation, tax calculation, payment processing, daybook, insurance claims.

**Key challenge:** Three payment flows + GST tax calculation + idempotent webhook processing.

**Design decision:** `InvoicesService` is a facade that delegates to `InvoicesQueryService` and `InvoicesCommandService`. This preserves the existing constructor signature while splitting read/write logic.

### clinical (15+ files)

**What it does:** Clinical settings, lab workflow, medical coding (ICD-10, CPT).

**Key challenge:** Medical code synchronization. The `MedicalCodeSyncService` runs a cron job to sync ICD-10 and CPT codes from external catalogs (NLM, licensed CPT).

**Design decision:** Composite code catalog provider — tries NLM first (free), falls back to licensed CPT (paid). This gives comprehensive coverage while minimizing cost.

### whatsapp (50+ files)

**What it does:** Template management, message delivery, patient response handling, staff notifications, reconciliation.

**Key challenge:** Three-way communication: clinic → patient, patient → clinic, system → staff. Each has different delivery guarantees and error handling.

**Design decision:** WhatsApp sender modes: `SHARED` (Meta shared number), `BYO` (bring your own number), `MANAGED` (Docita-managed number). Each clinic can choose based on their budget and branding needs.

**Failure mode:** Meta's WhatsApp API has rate limits. A clinic sending 100+ reminders simultaneously hit the limit. Fix: rate limiter per clinic, exponential backoff, and batch sending with configurable delays.

### webhooks (5 files)

**What it does:** Outgoing webhook delivery to external systems (lab integrations, EMR systems).

**Key challenge:** Reliable delivery with retries. Webhooks must be delivered exactly once to external systems.

**Design decision:** Webhook events are stored in a `WebhookEvent` table with retry counters. Failed deliveries are retried with exponential backoff. A dead-letter queue holds events that exhausted retries.

### subscriptions (80+ files)

**What it does:** SaaS billing, tier management, overage tracking, referral system, partner portal.

**Key challenge:** Tier-based feature gating. Each clinic tier (Free, Starter, Pro, Enterprise) has different feature access and usage limits.

**Design decision:** `SubscriptionEntity` is a rich domain model with value objects for billing cycles, pricing, and status. The lifecycle is managed by a state machine: `ACTIVE → PAST_DUE → GRACE_PERIOD → EXPIRED`.

**Code pattern:** Razorpay webhook handlers are organized as a registry — each event type (payment.captured, subscription.charged, etc.) has a dedicated handler class. The registry resolves the handler at runtime.

### insurance-claims (5+ files)

**What it does:** Insurance claim workflow state machine, document generation.

**Key challenge:** Claims follow a strict workflow: `DRAFT → SUBMITTED → UNDER_REVIEW → APPROVED/REJECTED → SETTLED`. Each transition has prerequisites.

**Design decision:** State machine pattern. Each state has a set of allowed transitions. Invalid transitions throw `InvariantViolationError`.

## 8. Security & Compliance

### Defense-in-Depth (7 layers)

```text
Layer 7: Audit logging — every PHI access logged
Layer 6: RLS — PostgreSQL row-level security (database-level)
Layer 5: Repository tenant scoping — Prisma middleware
Layer 4: PolicyGuard (ABAC) — object-level conditions
Layer 3: Subscription/tier guard — feature gating
Layer 2: RBAC roles matrix — role → permission
Layer 1: TenantGuard — AsyncLocalStorage tenant context
Layer 0: JWT auth — token validation + session management
```

### PHI Protection

- **Encrypted fields:** firstName, lastName, email, phoneNumber, address, emergencyContactPhone, emergencyContactName
- **Encryption boundary:** Prisma extension — encrypt before persist, decrypt on read
- **CI gate:** `check:phi-encryption-coverage` ensures encrypt/decrypt field lists stay aligned
- **Plaintext exceptions:** MRN, bloodGroup, allergies, medicalHistory (needed for lookup/display, protected by RLS + audit)

### RLS Rollout (Staged)

**Why staged:** RLS is a structural change with cross-cutting impact. Flipping it on in one shot risks breaking every query.

**Step 1:** Deploy migration (additive, policies short-circuit until `app.rls_enabled = 'on'`)
**Step 2:** Provision `docita_app` role (non-owner, subject to RLS)
**Step 3:** Set `RLS_ENABLED=true` in production
**Step 4:** Monitor for policy violations

**Key code:**

```typescript
// apps/api/src/shared/modules/rls/apply-rls-scope.ts
export async function applyRlsScope(tx: Tx, clinicId: string): Promise<void> {
  assertRlsClinicId(clinicId);  // regex validation — fail loudly
  // set_config(name, value, is_local) — is_local=true = SET LOCAL (reverts at tx end)
  await tx.$executeRaw`SELECT set_config('app.rls_enabled', 'on', true)`;
  await tx.$executeRaw`SELECT set_config('app.current_clinic_id', ${clinicId}, true)`;
}
```

**Why `set_config` not `SET LOCAL`:** The function-call form binds the value as a parameter, preventing SQL injection. The regex check is a second wall.

## 9. Failure Modes & Lessons Learned

### Failure 1: Cold Start Outage

**What happened:** Fly.io auto-stop shut down the VM after idle. Next request triggered a 3-minute cold start. Fly's HTTP proxy only waits ~10-15s → 502 Bad Gateway on every cold start.

**Root cause:** Trusted platform defaults without measuring actual bootstrap time.

**Fix:** Keep one machine running (`min_machines_running = 1`). Measure bootstrap time in CI.

**Lesson:** Don't trust platform defaults for health check timeouts.

### Failure 2: Cross-Pod Event Loss

**What happened:** Domain events emitted via in-process `EventEmitter2`. When we considered splitting the API across pods, cross-pod listeners would silently drop events.

**Root cause:** In-process event bus doesn't work across pods.

**Fix:** Transactional outbox pattern (ADR 0010). Events written to DB in same transaction, relay scheduler polls and republishes.

**Lesson:** In-process patterns don't survive horizontal scaling.

### Failure 3: Origin IP Exposure

**What happened:** Fly.io origin was publicly reachable. Anyone who discovered the Fly IP could bypass Cloudflare's WAF, rate limiting, and bot protection.

**Root cause:** Assumed CDN hides the origin.

**Fix:** Application-level origin verification (ADR 0014). Rate limiting by application-level IP detection.

**Lesson:** Always protect the origin directly, don't rely on CDN hiding it.

### Failure 4: RLS Silent Bypass

**What happened:** During RLS rollout testing, queries ran on a different connection than the one with `SET LOCAL app.current_clinic_id`. RLS policies short-circuited on the missing GUC — effectively a silent bypass.

**Root cause:** Prisma connection pool routes queries to different connections.

**Fix:** Route ALL queries through a single interactive transaction per request (`RlsService.runScopedTransaction`). This ensures the `SET LOCAL` and the query run on the same connection.

**Lesson:** Connection pooling + session variables = silent bypass unless you control the transaction scope.

### Failure 5: Encrypt/Decrypt Drift

**What happened:** A new PHI field was added to the encrypt list but not to the decrypt list. Patients could write data but not read it back.

**Root cause:** Manual alignment of two lists.

**Fix:** CI check (`check:phi-encryption-coverage`) enforces alignment.

**Lesson:** Any manual alignment between two lists will drift. Automate the check.

### Failure 6: WhatsApp Rate Limit Burst

**What happened:** A clinic sent 100+ appointment reminders simultaneously. Meta's WhatsApp API rate-limited the batch, causing 30+ messages to fail silently.

**Root cause:** No per-clinic rate limiting on outbound messages.

**Fix:** Rate limiter per clinic (configurable, default 30/min), exponential backoff on 429 responses, batch sending with 100ms delays between messages.

**Lesson:** External APIs have rate limits. Always implement client-side throttling.

### Failure 7: Invoice Double-Crediting

**What happened:** Razorpay sent the same `payment.captured` webhook twice within 5 seconds. The second webhook created a duplicate payment record and double-credited the clinic's wallet.

**Root cause:** At-least-once delivery without idempotency check.

**Fix:** Check `findByProviderPaymentId('razorpay', payment.id)` before processing. If exists, return early. Also added a unique constraint on `(provider, providerPaymentId)`.

**Lesson:** External webhook delivery is at-least-once. Always check for duplicates before processing.

## 11. Interview Q&A Scripts

### Q: "Tell me about the most complex system you've built."

> "I'm the founding engineer of Docita, a healthcare SaaS serving 25+ clinics with 1,000+ appointment workflows per month. The most complex aspect was multi-tenant data isolation — we needed provable separation between clinics handling Protected Health Information. I implemented a 7-layer defense-in-depth: JWT auth, AsyncLocalStorage tenant context, RBAC roles, ABAC policies for object-level access, Prisma repository scoping, PostgreSQL RLS, and audit logging. The hardest part was the RLS layer — Prisma's connection pool routes queries to different connections, so `SET LOCAL` session variables were silently bypassed. I solved it by routing all queries through a single interactive transaction per request using a custom Prisma extension."

### Q: "Why PostgreSQL as a queue instead of Redis?"

> "Operational simplicity. We already run AWS RDS PostgreSQL — adding Redis means another managed service, another failure mode, another secret to rotate. Our queue volume is ~0.4 jobs/sec sustained, within Postgres capabilities. The key advantage: transactional enqueue. A `prisma.$transaction` covers both the business write AND the job emission — no dual-write problem. We use `SELECT ... FOR UPDATE SKIP LOCKED` for pop-and-claim. The trade-off is throughput — if we hit >1k/sec sustained, we'd revisit Redis/NATS. But for 25 clinics, Postgres is sufficient and simpler."

### Q: "How do you handle data consistency across services?"

> "We use the transactional outbox pattern. Domain events are written to an `OutboxEvent` table in the same `prisma.$transaction` as the business write — atomic, no dual-write. A relay scheduler polls unpublished rows every 2 seconds and republishes to in-process EventEmitter2. Consumers are idempotent — they check a deduplication cache before processing. Failed events go through exponential backoff retry, then to a DLQ for manual inspection. We chose this over Kafka/NATS because we're single-region single-pod — outbox solves the problem with zero new infrastructure."

### Q: "How do you test multi-tenant isolation?"

> "Every integration test uses a fresh database snapshot and verifies cross-tenant isolation. The test creates data for clinic A, then attempts to access it as clinic B — asserting a 404 (not 403, to avoid leaking existence). We also have a CI check `check:prisma-boundary` that enforces only repository files import PrismaClient — preventing business logic from bypassing tenant scoping. Playwright E2E tests run the full patient journey across multiple clinics to verify isolation end-to-end."

### Q: "Why did you migrate from Next.js to Vite SPA?"

> "Docita's apps are authenticated dashboards — no SEO need. Next.js 16 + OpenNext bundle was ~3.5 MB gzip, over Cloudflare's 3 MB Free limit. Every feature port increased bundle size with framework overhead rather than app code. Vite + React Router gives us: simpler deployment (Cloudflare Static Assets), faster dev experience (sub-second HMR), smaller bundle, and zero server cost for frontend. The Hono proxy Worker handles `/api/*` routing to our Fly.io backend — same domain, no CORS. The migration was completed in one sprint with zero downtime."

### Q: "Walk me through the ABAC implementation."

> "We layered ABAC on top of existing RBAC — not a replacement. The guard chain is: JWT → TenantGuard → RBAC roles → Subscription/tier → PolicyGuard (ABAC). The PolicyGuard is a global NestJS guard that's a no-op unless a route declares `@RequirePolicy(resource, action)`. Policies are typed TypeScript classes in `packages/authorization` — pure functions, no framework imports. We use deny-overrides: any policy deny wins over any allow, and unmatched policies default to deny. For example, the patient resource resolver checks: same clinic? Doctor assigned to patient? Role permitted? Environment valid? All must pass. The emergency break-the-glass bypasses assignment checks but is audit-logged and read-only."

### Q: "How do you handle deployment and migrations?"

> "Deploy order: DB migrations first, then API/worker, then frontends. Fly.io runs `prisma migrate deploy` before API deploy — a verification script confirms no pending migrations or schema drift. The API and worker share the same Docker image base but have separate fly.toml configs. Frontends deploy to Cloudflare Workers with Static Assets. GitHub Actions triggers selective deploys — only apps whose related paths changed. We had a cold-start outage early on because Fly's proxy only waits ~10-15s but our NestJS bootstrap takes ~3 minutes. Fix: keep one machine running, measure bootstrap time in CI."

### Q: "What's the hardest technical challenge you faced?"

> "The RLS silent bypass. We enabled PostgreSQL Row-Level Security, but Prisma's connection pool routes queries to different connections. So `SET LOCAL app.current_clinic_id` would be set on connection A, but the actual query would run on connection B — which has no tenant context. RLS policies short-circuited on the missing GUC, effectively bypassing the security layer. We solved it by routing ALL queries through a single interactive transaction per request using `RlsService.runScopedTransaction`. This ensures the `SET LOCAL` and the query run on the same connection. It's the kind of bug that doesn't show up in unit tests — only in production with connection pooling."

### Q: "How do you handle WhatsApp at scale?"

> "WhatsApp is our primary patient communication channel — appointment reminders, prescription delivery, payment confirmations. We support three sender modes: shared Meta number (free), bring-your-own number (clinic's), and Docita-managed number. The challenge was handling patient responses — they reply with free text like 'yes', 'no', 'delay 30 min'. We built a response parser that maps these to appointment actions, with a two-step flow for delays. We also hit Meta's rate limits when a clinic sent 100+ reminders simultaneously — fixed with per-clinic rate limiting and exponential backoff. The reconciliation service runs daily to verify message delivery status matches our records."

### Q: "Explain the payment flow separation."

> "Three distinct payment rails that must never mix. Flow A: clinic's own Razorpay credentials (optional). Flow B: patient pays clinic using Flow A credentials. Docita SaaS: clinic pays Docita for subscription — separate merchant account. The risk: if a developer accidentally uses Docita's merchant key for a patient payment, Docita receives the patient's money. We enforce separation through naming conventions (`CLINIC_INVOICE_PAYMENT_LINK_PROVIDER_TOKEN` vs `DOCITA_PLATFORM_PAYMENT_LINK_PROVIDER_TOKEN`), code review gates, and documented flow boundaries. Technical debt: Flow B still delegates to a shared adapter instead of resolving a clinic-scoped provider from Flow A settings."
